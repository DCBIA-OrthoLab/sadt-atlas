ALI

ALI does not compute anything itself: it is a dispatch widget that chooses between two backends with no shared code — ALI_CBCT (reinforcement-learning agents that move through a volume) and ALI_IOS (multi-view rendering and per-pixel segmentation on a mesh) — to place anatomical landmarks in LPS.

Gillot 2023 · Orthod Craniofac Res ALI_CBCT ALI_IOS CBCT: Slicer Python — IOS: shapeaxi conda env Bibliography

Non-obvious point: ALI_CBCT does not go through conda. It runs in Slicer's own Python, which is why itk, dicom2nifti, pydicom and monai are installed by install_function (ALI.py:875). ALI_IOS needs pytorch3d, which does not exist in Slicer: it goes through conda run. CUDA is required nowhere — both fall back to CPU (DEVICE = cuda if available else cpu), at the cost of time.

The ALI_IOS CLI is also registered as a Slicer module (slicer.modules.ali_ios, ALI_IOS.xml), and AREG calls it through that route — in Slicer's Python, then, where pytorch3d is not installed. A fragile path, see §7.

3. ALI_CBCT — agents inside the volume

3.1 Preprocessing

Two steps, both written into temp_fold and never cleaned up:

  1. Histogram windowing, CorrectHisto(scan, out, 0.01, 0.99) (preprocess.py:27): a 1000-bin histogram, normalized cumulative, clipped to the 1% and 99% percentiles, hard-bounded to [-1500, 4000] HU. Output int16, spacing/origin/direction preserved. Watch out: the default signature says max_porcent=0.95, but the call passes 0.99.
  2. Isotropic resampling, one file per scale: SetSpacing (itk, linear interpolation — nearest-neighbor if seg/Seg is in the name) for each sp in spacing = [1, 0.3] mm. The new size is size * spacing / sp and the origin is recentered on the same physical box.
Pitfall

The files are named <stem>_sp<1|0-3><suffixes> and reused if they already exist: it's a cache, and therefore also a trap if the input changes without a name change.

At load time (environment.py:81): sitk.DICOMOrient(img, "LPS") — without this, the agents, which only ever read the raw array and never the direction cosines, walk through a mirrored volume. Then EnsureChannelFirst + BorderPad(padding) with padding = agent_FOV/2 + 1 = [33,33,33], so that any 64³ crop is valid wherever the agent stands.

The array is stored in numpy (z,y,x) order and the origin is reversed to match that same order — but not the spacing, which stays (x,y,z). This has no effect only because resampling makes the spacing isotropic.

3.2 The environment

Environment (environment.py:26) is a patient: a dictionary {scale_key: {image, spacing, origin, size}} plus the list of predicted landmarks. One instance per patient, with every scale held in memory.

GetZone(scale, center, crop_size) is the only thing the agent ever sees of the world:

cropTransform = SpatialCrop(center.tolist() + self.padding, crop_size)
rescale = ScaleIntensity(minv=-1.0, maxv=1.0, factor=None)
crop = rescale(cropTransform(self.data[scale]["image"])).type(torch.float32)

A 64×64×64-voxel cube centered on the agent, renormalized per crop to [-1,1] (local min/max, not a global normalization). At scale 1 it covers a 64 mm side, at scale 0-3 19.2 mm.

3.3 The agent and its network

One agent per landmark (agent.py:73), instantiated once and then reused for every patient. A fresh Brain is built and its weights reloaded for each (patient, landmark) pair (ALI_CBCT.py:194) — 2 DenseNets rebuilt and 2 .pth files reread per point and per scan.

The network, DNet (brain.py:48):

self.featNet = DenseNet(spatial_dims=3, in_channels=1, out_channels=1024,
                        growth_rate=34, block_config=(6, 12, 24, 16))
self.dens = DN(in_channels=1024, out_channels=6)   # MLP 1024-512-256-128-6

A 3D DenseNet-121 from monai (growth rate 34 instead of 32), followed by a 4-layer MLP. Input [1, 1, 64, 64, 64], output 6 scores, one per move: Up / Down / Back / Front / Left / Right — that is, ±1 voxel along each of the array's three axes (constants.py:22).

This is not a heatmap: it is a direction classifier. The network's prediction does not say where the point is, it says which way to step. Predict takes the argmax of the 6 scores (brain.py:166).

Confirmed bug

Note that DN.forward applies a relu to the last layer too. So the scores are ≥ 0, and if all pre-activations are negative, all 6 come out as 0 and argmax systematically returns 0 ("Up"). The softmax commented out just below it suggests this wasn't the intent.

One network per scale: Brain instantiates one per scale_key, and LoadModels loads <label>/1/*.pth then <label>/0-3/*.pth.

3.4 The search

Agent.Search() (agent.py:242):

  1. scale 0 (1 mm), position at the center of the volume;
  2. loop: PredictAction() → Move() by a step of speed_per_scale[scale] = 1 voxel;
  3. stopping criterion = oscillation. Visited() checks whether the current position is among the last 10 positions (shortmem_size = 10). Once the agent retraces its steps, it is considered to have arrived;
  4. UpScale(): moves to scale 0-3, position converted through the spacing ratio, short-term memory cleared, and the search restarts;
  5. at the final scale, Visited() ends the search.

Time budget: 15 s on GPU, 60 s on CPU, per landmark and per patient, overridable with ALI_SEARCH_MAX_TIME. Overrun → -1, landmark not written. Same if the agent leaves the volume three times (search_atempt > 2); each time it exits, it is respawned at random (spawn_radius = 10 voxels around the start, at scales > 0).

The final refinement, Focus() (agent.py:215): from the position found, six restarts at 4 voxels (1.2 mm at the final scale) along ±x, ±y, ±z; each one walks again until Visited(); the retained position is the average of the six landings. That is what makes the result sub-voxel.

Pitfall

Focus has no bound at all: no time limit, no step count, no search_atempt check. An agent that leaves the volume is respawned at random and the while not found loop starts over from scratch.

3.5 Output

SavePredictedLandmarks(scale_keys[-1], output_dir) (environment.py:118) converts the index back into a physical coordinate:

physical_origin = abs(ref_origin / ref_spacing)
real_label_pos  = (pos - physical_origin) * ref_spacing
real_label_pos  = [real_label_pos[2], real_label_pos[1], real_label_pos[0]]  # back to x,y,z
Confirmed bug

The abs() assumes the origin is negative on all three axes — true for an LPS volume centered at the origin, false in general.

Points are grouped by anatomical family (LABEL_GROUPS: CB, U, L, CI) and one file is written per group: <patient without extension>_lm_Pred_<group>.mrk.json, coordinateSystem: "LPS", description always empty (io.py:5). GreedyReg flips it back to RAS (Logic.py:518).

4. ALI_IOS — multi-view rendering

4.1 Inputs

.vtk, .vtp, .stl, .obj, .off. But everything depends on a tooth-label array, looked up under PredictedID, predictedId or Universal_ID (surface.py:207): that's what gives the centroid of each tooth, and therefore the camera position. Without an array, RI is set to zero and no label is found.

If the scan doesn't have one, SegmentSurface (segmentation.py:80) calls dentalmodelseg on a copy (a .stl passed to shapeaxi with --overwrite 1 is deleted by dental_model_seg.py), via a csv (passing --surf a single file crashes shapeaxi on an attribute it doesn't define). Segmentation doesn't move the points — 5e-5 mm measured over 118k points according to the comment — so the landmarks stay valid in the original file.

Canonical scaling, ScaleSurf (surface.py:94): centering on the bounding-box midpoint, then scale = 1 / ||max - center||. The whole pipeline works inside this unit sphere; Upscale reverses the process at the end.

Leveling (MG only), LowerArchMatrix (orientation.py:98): the MG cameras are built around a vertical axis assumed to be Z. The occlusal plane is fitted with SVD on the centroids of teeth 18–31 (at least 4 teeth, spread ≥ 4 labels), with the sign fixed so the crowns point up, then a minimal rotation (Rodrigues) brings the normal onto +Z. Below MAX_TILT_DEGREES = 12° the scan is left strictly untouched — sending an already-level scan into a fixed frame would rotate it within the plane and degrade the prediction. Landmarks are passed back through inv(matrix) before being written.

4.2 The cameras

GenPhongRenderer (render.py:20):

cameras = FoVPerspectiveCameras(znear=0.01, zfar=10, fov=90)
raster_settings = RasterizationSettings(image_size=224, blur_radius=0, faces_per_pixel=1)

image_size / blur_radius / faces_per_pixel are positional arguments of the CLI, but every caller passes 224 / 0 / 1 (IOS.py:286, IOSCBCT.py:335, FlexReg.py:2517). blur_radius = 0 plus faces_per_pixel = 1 means hard rasterization, one face per pixel: that's what makes pix_to_face usable as a pixel-to-face lookup table.

The texture isn't a color: TexturesVertex(verts_features=CN) where CN is the per-vertex normal remapped to RGB ((n*0.5+0.5)*255, surface.py:171). So the network sees a Phong-lit normal map, plus the z-buffer as a 4th channel.

One camera is placed per tooth, at radius from its centroid:

ModelRadiusCamerasGeometry
O (occlusal)0.25dic_cam['O'], occlusal axis + 4 tilts
C (cervical)0.312dic_cam['C'], buccal/lingual crown
MG (mucogingival)0.23computed on the fly, see below
Confirmed bug

The directions in dic_cam['O'] are normalized incorrectly: np.array([0.5,0,1.0]) / linalg.norm([0.5,0.5,1.0]) divides by the norm of a different vector (model.py:66). So the cameras are not on the sphere of radius radius. Harmless as long as the weights were trained with the same table.

The MG cameras, the only adaptive part (agent.py:192):

  • arch tangent: the difference between the centroids of teeth label-1 and label+1 (the lower labels 18→31 run in sequence along the arch), flattened in z;
  • buccal normal: horizontal perpendicular to the tangent, flipped if it points inward. The radial direction (tooth center − mesh center) used by the previous version is off by 35° on teeth 19/30 and 53° on tooth 31: the cameras were looking along the arch and the point fell outside the render;
  • aim point: not the tooth centroid but centroid + b·normal + t·tangent, z += v, with (b,t,v) read from MG_AIM_OFFSET (model.py:35) — the per-tooth median over 155 training scans, spread 0.02–0.03;
  • three cameras: the buccal normal, plus ±0.35 rad around the Y axis, placed at radius from the aim point and lowered by 0.15·radius.

4.3 The network

A 2D monai.networks.nets.UNet, loaded for every tooth (net.load_state_dict inside the loop, ALI_IOS.py:443):

O / CMG
in_channels4 (RGB + z-buffer)12 (3 cameras × 4)

strides(2,2,2,2,2)same

A structural difference: for O/C each camera is an independent sample and each view produces its own map; for MG the three views are stacked as channels and the network produces a single map, interpreted in camera 0's frame (the indexing tens_pix_to_face_model[0,0,0,y,x] targets the first camera after the permute(1,0,4,2,3)).

This isn't a heatmap in the Gaussian-regression sense: it's a per-pixel segmentation. Class 1 is the landmark (MG, or O), 2 and 3 carry MB/DB (O model) or CB (C model) — see MODELS_DICT and dic_label (model.py:51).

Decoding the output is where the two paths diverge (ALI_IOS.py:453):

# MG: argmax on the raw logits
pred_data = torch.argmax(images_pred.detach().cpu().float(), dim=1)...
# O / C: cast to int16 BEFORE the argmax
pred_data = images_pred.detach().cpu().unsqueeze(0).type(torch.int16)
pred_data = torch.argmax(pred_data, dim=2).unsqueeze(2)
Confirmed bug

The comment in the MG code explains why the second one is wrong: truncating the logits to integers merges close classes, and on a tie, argmax falls back to index 0 (the background). The fix was only applied to MG.

4.4 From pixel to 3D point

  1. index = (pred_data == 1.).nonzero(): the pixels of the target class;
  2. tens_pix_to_face[...]: the rendered face under each of those pixels;
  3. filtering — and it differs:
    • O/C: RemoveExtraFaces keeps only faces where at least one vertex carries the tooth's Universal_ID (surface.py:229);
    • MG: no per-tooth filtering, only face >= 0. The mucogingival point sits on the gum, not on the crown; RemoveExtraFaces would eliminate all of them;
  4. the 3 vertices of each retained face, averaged;
  5. vtkOctreePointLocator.FindClosestPoint: the mean point is snapped onto an existing vertex — the average of a curved patch falls below the surface;
  6. Upscale(pos, mean_arr, scale_factor): back to the file's coordinates.

4.5 Forced points, and the description field

Pitfall

Three safeguards, MG only, driven by CLI options (ALI_IOS.py:654) that no caller in the repository passes — so their defaults always apply:

OptionDefaultEffect
--force_landmarksTrueif class 1 wins no pixel, take the k pixels where it is most likely
--force_topk50this k — softmax(logits)[:,1], topk(50), these pixels stand in for the prediction
--estimate_missingFalseplace a point on a tooth missing from the segmentation, cameras aimed from a quadratic fit of the arch

EstimateMissingArchPositions (ALI_IOS.py:89) fits a degree-2 polynomial of each centroid coordinate against the label index, on the teeth present (≥ 4 teeth, spread ≥ 4 labels), and evaluates it at label and label ± 0.5 for the tangent. According to the code's error message, these points land 4 to 21 mm off, against 0.5 mm for a point aimed at a real tooth — hence the default of False.

Last resort if nothing lands on the mesh: the point is anchored on the tooth itself, lowered by 0.2 in unit-sphere space, then snapped (ALI_IOS.py:550).

Every degradation is written into the json. entry["desc"] becomes the control point's description field (io.py:23):

ValueCause
cameras aimed from an arch fit, tooth not segmented--estimate_missing
forced (confidence 0.123)top-k on class 1
fallback (nothing predicted on the mesh)anchored on the tooth
combinations, joined with "; "

This is the field that FlexReg and AREG_IOS read: DoubtfulLandmarks (mgl_patch.py:142) treats any non-empty description as doubtful and discards the point, letting the spline skip over the gap — unless fewer than 3 points would remain. Measured over 364 predictions according to the comment: 4.2 mm median deviation from the neighboring curve, against 1.2 mm for the others.

Note

Corollary: O/C points and every ALI_CBCT point have an empty description, whatever their quality. The flagging mechanism only exists for MG.

4.6 Output and weights

One file per (patient, arch, model): <patient>_<Lower|Upper>_<O|C|MG>_Pred.json, coordinateSystem: "LPS" (io.py:64). The coordinates are those of the input mesh, with no flip: the "LPS" label is true because the .vtk files in this pipeline are LPS, not because the code checks it.

GenControlPoint filters on landmarks_selected: an O model always predicts XO/XMB/XDB, but only the requested types are written.

Weight discovery (ALI_IOS.py:205) — from the file name alone:

<jaw>_<model_id>_<anything>.pth
 ^ "Lower" present in the name? otherwise "Upper"
        ^ basename.split("_")[1], must be O, C or MG

Verified on one installation: Lower_O_model.pth, Upper_C_model.pth, Lower_MG_v6.pth. Two candidates for the same pair → sorted() settles it and a warning is issued. The widget itself detects _O_/_C_ by substring (ALI.py:2070) and Lower_MG_* separately (HasMGModel, ALI.py:856): two conventions for the same file.

Download: https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/ALI_IOS_models/Models.zip (IOS.py:161) — the contents of the historical ALIDDM v1.0.3 archive plus Lower_MG_v6.pth. 7. Pitfalls and fragile spots

  • Focus() has no safeguard: no time budget, no search_atempt check. It's the only unbounded loop in the CBCT pipeline.
  • Move() tests its bounds wrong: if new_pos.all() > 0 and (...) — .all() returns a boolean, compared against 0. The test checks "no coordinate is zero," not "no coordinate is negative" (agent.py:193).
  • The int16 cast before argmax is still there on the O and C models. The comment in the MG code explains precisely why it's wrong.
  • get_view_rasterize for non-MG rasterizes without R/T: renderer.rasterizer(meshes.clone()) (agent.py:366) doesn't pass the matrices used by the render right above it, so pix_to_face comes from the default camera, not the one that produced the image. The MG path was written explicitly to fix this ("with the SAME R,T so pix_to_face stays aligned", agent.py:267). That's the original upstream code, and it was never replayed for O/C.
  • val_pred / post_pred (ALI_IOS.py:447): an AsDiscrete(argmax=True, to_onehot=4) is computed on every view and then never read. Dead computation on every single tooth.
  • MG name collisions. Six of the 13 output names are the training name of a different tooth: LR1MG is the output for tooth 26 and the training name for tooth 25 (model.py:25). Any translation between the two conventions has to be decided on the whole label set, never label by label.
  • The widget's DICOM path is broken. Auto_CBCT implements neither NumberScanDCM, nor TestScanDCM, nor getTestFileListDCM: the base versions return None. Checking "DICOM" gives nb_patient = None, then a TypeError when downloading the test files and a division by None in OnEndProcess. The CLI itself knows how to convert.
  • The Agent manifest is incomplete. ali_cbct declares 6 parameters for 10 expected positionals, ali_ios declares 6 for 10 and omits teeth_mg (index 4): the following values shift by one slot (manifest.yaml:48).
  • temp_fold is never cleaned up by ALI_CBCT, and resampled files are reused as-is if they exist: a silent cache between two runs.
  • Auto_IOS.getALIModelList returns super().getALIModelList(), an empty abstract method → None (IOS.py:172).
  • slicer.modules.ali_ios is called by AREG through slicer.cli.run (IOSCBCT.py:350), so inside Slicer's Python, where pytorch3d and shapeaxi are not installed. The ALI widget itself only ever calls it through conda run. The two paths cannot both work on the same install.
  • SURFACE_LANDMARKS (ALI.py:127) offers R, RIP, OIP, which have no entry in MODELS_DICT: selecting them alone makes the CLI fail with "No matching models found."
  • onPredictButton chains the two IOS processes badly: the if "CrownSegmentationcli" and the if "ALI_IOS" that follows are not mutually exclusive, and the else after it attaches to the second one (ALI.py:987). When segmentation is needed, ALI_IOS is relaunched from onProcessUpdate; otherwise from onPredictButton. Two entry points for the same step.

8. Literature

Both backends have their own paper, and the code matches what they describe — with one reservation for ALI_IOS.

ALI_CBCT — Automatic landmark identification in cone-beam computed tomography, Gillot, Baquero, Cevidanes et al., Orthodontics & Craniofacial Research, 2023. Detection is reframed as a classification problem: a virtual agent placed in the volume learns to navigate a multi-scale space toward the landmark.

Verified

Reported mean error 1.54 ± 0.87 mm over 32 landmarks, 4.2 s inference. That's exactly what the code does, including the two scales, 1 mm / 0.3 mm.

Original repository: Maxlo24/ALI_CBCT.

ALI_IOS — Automatic Landmark Identification on IntraOralScans, Baquero, Gillot, Prieto, Cevidanes, Clinical Image-Based Procedures (CLIP 2022), LNCS 13746, p. 32-42.

Verified

Unit-sphere scaling, 5 2D views per tooth, per-view patch segmentation, averaging the patch coordinates, scaling back up — the description of the code's O model, to the letter.

Original repository: DCBIA-OrthoLab/ALI_IOS; on the prototype side, ALIDDM.

Note

The MG path is not published. Adaptive buccal cameras, MG_AIM_OFFSET, 12-channel stacking, arch leveling, forced points and the description field: none of this appears in the CLIP paper, which only knows the spherical 5-view scheme. The figures cited (155 training scans, 4–21 mm for an estimated point, 364 predictions for FlexReg's threshold) are sourced only in the code comments.
