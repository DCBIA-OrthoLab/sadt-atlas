ALI

ALI places anatomical points, called landmarks, on a 3D scan automatically. This page explains how, step by step, with the maths: what goes in, what each step does to it, and what comes out. The module is a dispatcher between two separate programs: ALI_CBCT, where an agent walks through a head volume, and ALI_IOS, where a tooth is photographed from virtual cameras. Where the code does something worth checking, a link leads to the code page. This page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26); the server port is ALI on VISOR.

Code (developers) Gillot 2023 · Orthod Craniofac Res ALI_CBCT ALI_IOS CBCT: Slicer Python, IOS: shapeaxi conda env VISOR Bibliography

Overview: what goes in, what comes out

ALI takes a 3D image of a patient and returns a list of 3D points, each with a name: the tip of a tooth, a point on the skull base. The module on the Slicer screen does no computing itself. It only asks which kind of image you have and hands the work to one of two separate programs, which share no code. Other tools then use the points to orient a scan or to register two scans.

ALI_CBCTALI_IOS
Inputa CBCT volume (the head scan), NIfTI or DICOMan intraoral surface mesh of the teeth, with a tooth number on every vertex (computed first if missing)
Ideaan agent walks through the volume, one step at a time, until it reaches the pointeach tooth is photographed from fixed virtual cameras, a network labels the pixels of each picture, and the labelled pixels are projected back onto the mesh
Outputone file per scan and per landmark group, in the format Slicer reads (.mrk.json)one file per patient, jaw and network (.json)

Coordinates are written in LPS. The two programs run in different Python environments: ALI_CBCT inside Slicer's own, ALI_IOS in a separate conda environment, because it needs a graphics library Slicer does not ship.

1. Where it sits in the pipeline

ALI is a landmark provider for most of the toolbox. The modules that call it, and why:

  • ALI itself, used directly, for both modes.
  • ASO asks ALI_CBCT for landmarks to orient a scan.
  • AREG_IOSCBCT asks both for 12 occlusal points on the CBCT and on the mesh, to register one onto the other.
  • GreedyReg (distant registration) asks ALI_CBCT for landmark-based registration.
  • FlexReg asks ALI_IOS for the 13 mucogingival points of the lower patch.

When a mesh has no tooth labels, ALI_IOS needs a crown segmentation first. It can run it itself or receive it from the widget: two routes to the same result.

In the codeThe callers, with file and line, and the other tools that call ALI

2. Files involved

Two programs and a widget that picks between them. ALI_CBCT runs in Slicer's own Python, so it needs no extra environment. ALI_IOS needs pytorch3d, which does not exist in Slicer: it runs through a conda environment shared with several other tools. Neither needs a graphics card, but both are much slower without one.

In the codeThe file table, where each part runs and why CBCT skips conda

3. ALI_CBCT: agents inside the volume

The idea comes from reinforcement learning, but at run time nothing is learned: a trained network is used as a compass. For each landmark there is one agent, which is a position in the volume. At every step the network looks at a small cube of the image around the agent and says which of six one-voxel moves brings it closest to the landmark. The agent moves, looks again, and repeats until it starts going in circles, which means it has arrived. It does this on a coarse grid, then again on a fine one, and averages six last attempts.

3.1 Preprocessing

Two operations, once per scan, before any agent moves.

The files written for each grid are named after the scan and reused if they already exist: a cache, and so also a trap if the input changes without a name change. When the volume is loaded it is also reoriented to LPS and padded by 33 voxels on every side, so that the cube the agent looks at always has data, even at the border.

In the codePercentiles, bins, interpolation, the cache files and the load-time padding

3.2 The environment

The “environment” is one patient: the image at each of the two grids. It answers a single question for the agent, what is around this position?, and it answers it with a cube.

In the codeThe environment class and the crop call

3.3 The agent and its network

The network is a 3D DenseNet followed by a small decision head. This is not a heatmap: it does not say where the point is, it says which way to step. There is one agent per landmark, and one network per landmark and per grid: the program rebuilds the networks and rereads their weights for every scan and landmark. The head ends in a ReLU, so if all six scores are negative before it, all become 0 and the agent takes the first move (see known issues).

In the codeThe network definition, the move order and the ReLU

3.4 The search

Rules around the walk: a move that would leave the volume is refused and the agent respawns at a random position; after three exits the landmark is dropped. The number of steps is also bounded: the legacy module stops a search after 1000 steps by default, with a 900 s guard and an early stop on known ground.

In the codeThe agent loop, the memory, respawn, the step budget and the final averaging in the code

3.5 Output

The absolute value assumes the origin is negative on all three axes, true for an LPS volume centred at the origin. Since the legacy module reorients every volume to LPS first, the damage is limited (known issues).

Points are grouped by anatomical family (CB, U, L, CI) and one file is written per group, coordinates in LPS. The description field of each point is always empty.

In the codeThe coordinate conversion and the markups writer

3.6 Weights

The trained networks are found by their folder layout: one folder per landmark, one subfolder per grid (1 mm and 0.3 mm). The module downloads eight archives (cranial base, mandible, lower and upper teeth), and ASO and GreedyReg fetch the same weights from another release.

In the codeWeight discovery and the eight archives

4. ALI_IOS: multi-view rendering

The mesh is scaled into a unit sphere. Around each tooth, a few virtual cameras take pictures. A 2D network labels each pixel, and the pixels of the landmark class are traced back to triangles of the mesh, whose centre is the landmark. The network is the only trained part; everything else is geometry.

4.1 Inputs

Five mesh formats are read. But everything depends on a tooth-label array on the mesh: it gives the centre of each tooth, and therefore where the camera goes. Without one, no tooth is found. If the scan has none, a crown segmentation is run first, on a copy of the file; it does not move the points, so the landmarks stay valid in the original file.

Levelling (mucogingival network only). Its cameras are built around a vertical axis assumed to be Z, so the occlusal plane is fitted through the lower teeth and the scan is tilted to bring that plane's normal onto Z. Under 12 degrees of tilt the scan is left untouched, and the landmarks are mapped back through the inverse rotation before being written.

In the codeLabel lookup, the segmentation call, scaling and levelling

4.2 The cameras

The rendering is hard: one triangle per pixel, 224 by 224 pixels, so each pixel can be traced back to the triangle it shows. What the network sees is not a colour photo: each surface normal is turned into a colour, and the depth is added as a fourth channel.

The occlusal (O) cameras use a table of directions in which two rows are normalised by the wrong vector, so they are slightly shorter than 1. It is harmless as long as the weights were trained with the same table, and VISOR keeps it on purpose (details).

The mucogingival (MG) cameras are the only adaptive ones. The arch direction at a tooth is taken from its two neighbours; the cheek side is the horizontal perpendicular to it. The cameras do not look at the tooth's centre but at a point shifted by a typical offset for that tooth, learned from 155 training scans, so the gum point falls inside the picture.

In the codeThe renderer settings, the direction tables and the adaptive MG cameras

4.3 The network

A 2D UNet from the MONAI library is loaded for every tooth. For the occlusal and cervical networks each camera is an independent picture and gets its own map of four classes. For the mucogingival network the three views are stacked as 12 channels and the network produces one map of three classes, read in the frame of the first camera. This is a per-pixel segmentation, not a heatmap: class 1 is the landmark, the others carry the secondary points (mesial and distal buccal for O, buccal for C).

One difference between paths is a known problem: for O and C the scores are truncated to integers before the most likely class is chosen, which merges close classes and falls back to the background on a tie. The mucogingival path uses the raw scores, and VISOR uses them everywhere.

In the codeNetwork parameters, batching and the decoders

4.4 From pixel to 3D point

For O and C only the triangles that touch the tooth's own vertices are kept. For MG there is no such filter, because the gum point is on the gum, not on the crown. The point is then scaled back to the coordinates of the file.

In the codeThe pixel-to-face filters and the octree snap

4.5 Forced points, and the description field

For the mucogingival network, three safeguards keep a point from going missing. If the landmark class wins no pixel, the 50 pixels where it is most likely stand in for the prediction. A tooth missing from the segmentation can get a point from a polynomial fit of the arch, but that option is off by default, because such points land 4 to 21 mm off, according to the code. If nothing lands on the mesh, the point is anchored on the tooth itself.

Every degradation is written into the description field of the point. FlexReg and AREG_IOS read it: any non-empty description is treated as doubtful and the point is skipped, so the curve passes over the gap. Points from the occlusal and cervical networks, and every CBCT point, have an empty description whatever their quality.

In the codeOptions, defaults, the arch fit and every description value

4.6 Output and weights

One file per patient, jaw and network, in the coordinates of the input mesh. The weights are found from the file name alone (jaw, then network, then anything, then .pth). The module downloads one archive that contains the historical weights plus the mucogingival one, in the folder FlexReg expects.

6. Environment

ALI_CBCT uses Slicer's Python plus a few installed libraries. ALI_IOS uses a conda environment shared with AREG, ASO, FlexReg and DOCShapeAXI, with pytorch3d chosen to match the installed PyTorch. Neither requires a GPU. On Windows, conda is reached through WSL. The exact versions are listed on the code page.

7. Pitfalls and fragile spots

Each point is checked in the code and described, with its evidence, on the code page; the list also appears in the findings.

  • The final network layer is a ReLU, so an all-negative output makes the agent always take the first move. Evidence.
  • The millimetre conversion uses an absolute value that is only right for a negative origin; reorienting to LPS first limits the damage. Evidence.
  • O and C scores are truncated to integers before the argmax, merging close classes. Evidence.
  • The O and C pictures are rasterised without the camera matrices used to render them, so the pixel-to-triangle lookup can come from the wrong camera. Evidence.
  • The widget's DICOM path is broken: ticking DICOM ends in an error, although the CLI itself converts DICOM. Evidence.
  • The Agent manifest is incomplete, so values shift by one slot for ali_ios. Evidence.
  • A silent cache between runs: resampled files are reused if they exist and are never cleaned up. Evidence.
  • Two ways of running ALI_IOS cannot both work on one install: AREG calls it inside Slicer's Python, where pytorch3d is absent. Evidence.
  • Landmarks R, RIP and OIP have no model: selecting them alone makes the CLI fail. Evidence.
  • MG output names collide with the training names of other teeth; translate on the whole label set, never label by label. Evidence.
  • Other fragile spots (chained IOS processes, dead computation, the empty model list, the earlier unbounded Focus and bounds test) are described one by one on the code page. All pitfalls.

8. Literature

Both programs have their own paper, and the code matches what they describe, with one reservation for ALI_IOS. ALI_CBCT: Gillot, Baquero, Cevidanes et al., Orthodontics & Craniofacial Research, 2023, which reframes detection as navigation of a virtual agent through a multi-scale volume; the code does exactly that, with the same two grids. ALI_IOS: Baquero, Gillot, Prieto, Cevidanes, CLIP 2022: the unit sphere, five views per tooth, per-view segmentation and averaging describe the occlusal network to the letter. The mucogingival path is not published. The reported accuracy figures are the papers' and were not re-measured. Full references: SOURCES.md; the comparison with the code is on the code page.
