MRI2CBCT, legacy: the code

For developers: what the legacy MRI2CBCT module does in the code, with file:line references, code, arguments, environment and traps. The readable explanation of the same pipeline, with the maths, is on the atlas page.

Code Atlas (explanation) Leroux 2024 · earlier version, CLIP, LNCS 15196 3 MRI2CBCT_* CLIs + 4 borrowed Slicer's Python, no conda Bibliography VISOR: not ported

Since PRs #277 and #278 the module is a single panel (MRI2CBCT.py, 753 lines) over a Slicer-free package, MRI2CBCT_core/. Seven steps are chained by one Run button: three CLIs of its own (MRI2CBCT_PREPARE, MRI2CBCT_SEGMENT_MRI, MRI2CBCT_REGISTER) and four borrowed from ASO, ALI and AMASSS. Two nnU-Net-family networks segment the cranial base, one on the CBCT and one on the MRI; everything after that is geometry on two point clouds. The run can pause after any step so the clinician can check it.

Two code bases

Everything numbered below describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26, the rewritten version). There is no VISOR port: SADT-VISOR has no MRI2CBCT tool, VISOR-serve has no deployment section for it, and the client module is kept in the tree but not built. See what exists of MRI2CBCT in VISOR.

1. Where it sits in the pipeline

Plain-language explanation and maths: atlas page.

Nothing calls the three new CLIs but the module's own panel: a search for MRI2CBCT_PREPARE, MRI2CBCT_SEGMENT_MRI and MRI2CBCT_REGISTER across the whole extension finds them in plan.py and in their own folders only. Agent's manifest still knows a single MRI2CBCT CLI, mri2cbct_resample (Agent_CLI/manifest.yaml:491), and none of the three. The module declares dependencies = [] (MRI2CBCT.py:49): it no longer depends on SlicerNNUNet, nnU-Net comes from pip.

The step list is built once, in plan.build (plan.py:57), and the panel runs whatever it returns. plan.py:7-8 says why the borrowed CLIs get fresh folders under the output: ALI's shared temporary folder under ~/Documents "reuses stale files by name".

What the rewrite replaced · not in VISOR

Legacy only (3c67957); not present in VISOR. In VISOR, VFACE no longer calls the resample CLI: it carries its own copy (SADT-VISOR tools/VFACE/src/sadt_vface/resample.py:1-34), and no file under SADT-VISOR tools/AREG mentions MRI2CBCT. The six-CLI layout survives only in the unbuilt client copy (see the VISOR page).

The earlier module had six CLIs (ORIENT_CENTER_MRI, LR_CROP, RESAMPLE_CBCT_MRI, APPROX, TMJ_CROP, REG), a .ui file, a manual approximation tool, a condyle-segmentation network applied to the CBCT and a rigid elastix registration on mutual information. None of it is in the tree any more. Only MRI2CBCT_RESAMPLE_CBCT_MRI and its helper package MRI2CBCT_CLI_utils remain, and they are outside this chain: they are still built (MRI2CBCT_CLI/CMakeLists.txt:2) and still called, but by AREG_IOSCBCT (AREG/AREG_Method/IOSCBCT.py:601) and VFACE (VFACE/VFACE_utils/createlistprocess.py:119), as the comment at MRI2CBCT_CLI_utils/__init__.py:1-3 says. The previous page's statement that no one consumes them was wrong on this point and is withdrawn.

3. Pipeline order, and what is actually mandatory

Plain-language explanation and maths: atlas page.

pair → [resample] [split L/R] → orient CBCT (ASO) → cranial base on CBCT → cranial base on MRI → register

The panel counts seven steps (plan.py:69-98): PREPARE, PRE_ASO_CBCT, ALI_CBCT, SEMI_ASO_CBCT, AMASSS_CLI, SEGMENT_MRI, REGISTER. The figure groups the three orientation CLIs in one box.

#StepStatusWhy
1MRI2CBCT_PREPAREmandatorypairs the patients and writes the manifest every later CLI reads; resampling and left/right split inside it are options (MRI2CBCT.py:118-135, both on by default)
2 to 4PRE_ASO_CBCT, ALI_CBCT, SEMI_ASO_CBCTmandatorythe AMASSS step runs on the oriented CBCT and REGISTER reads the ASO transform (MRI2CBCT_REGISTER.py:51); without it the patient fails "before registration" (:52-56)
5AMASSS_CLI (CB)mandatorythe fixed surface
6MRI2CBCT_SEGMENT_MRImandatorythe moving surface; exits with code 1 if any output is missing (MRI2CBCT_SEGMENT_MRI.py:31-34)
7MRI2CBCT_REGISTERthe goalexits with code 1 if no joint registered (MRI2CBCT_REGISTER.py:119-120)
pausesfive review pointsoptionaloff by default (§9)

This is the main change from the six independent buttons of the previous version: the order and the provenance of the files are now enforced by the plan, and a step that fails stops the run with its error text (MRI2CBCT.py:421-424).

4. Pairing and MRI preparation

Plain-language explanation and maths: atlas page.

4.1 Pairing by patient ID

Plain-language explanation and maths: atlas page.

pair_folders (pairing.py:81). The modality comes from the folder the clinician chose, never from the file name (pairing.py:3-4). The ID is the leading letters followed by a number, ^([A-Za-z]+)[_\-\s]*0*(\d+) (pairing.py:12): P01, B038, A3_scan. Leading zeros do not count, so P1 and P01 are the same patient, and case does not either (patient_key, :27-32). Accepted extensions are .nii.gz, .nii and .nrrd (:11), searched recursively (list_images, :41-47).

A file or patient is left out, with a message, when: no ID can be read, there is an MRI but no CBCT, a CBCT but no MRI, or more than one CBCT for the same ID (pairing.py:92, :98, :106, :109, :111-113). The panel lists them and asks for confirmation before going on (MRI2CBCT.py:350). A patient may have one or two MRIs.

Swapped folders. folders_swapped (pairing.py:73-78) reads only the headers of up to four files per folder. looks_like (:50-70) calls a file an MRI if its spacing is anisotropic by more than a factor 2 or if any extent is under 90 mm, and a CBCT if it is isotropic within 5% and at least 120 mm across in every direction; anything else is "neither". The panel then offers to swap the two folders (MRI2CBCT.py:328-336).

4.2 Preparing each MRI

Plain-language explanation and maths: atlas page.

MRI2CBCT_PREPARE.py. First it deletes the whole _steps/ folder of the output (:23-24), then links each CBCT into _steps/0_cbct_in/<PID> (a symlink, a copy if the link fails, :45-48), then for each MRI file asks mri_prep.plan_joints what the volume is. The MRI's header is kept as is: the earlier "Orient" step overwrote the direction matrix with a fixed one, which "throws away the only record of which way the slices run" (mri_prep.py:3-6), so the new code reads the world coordinates from the native header.

  • Side from the header. side_from_header (mri_prep.py:64-66) calls a slab LEFT if its world centre has LPS x > 0, RIGHT otherwise. The docstring states the rule was right 355 out of 355 on single-joint slabs of known side (97 patients).
  • A gapped bilateral slab. NIfTI cannot store the gap between two stacks, so the file spreads all slices evenly. The docstring's example is B038: 18 slices at 6.876 mm that are really 9 + 9 at 3.0 mm with 69 mm between them. Only the two end slices are in the right place, so each half is rebuilt at the acquisition spacing anchored on its own end slice (split_gapped, :90-128), assuming the two stacks have the same number of slices; an odd count adds "check the split" to the note (:150-151). The acquisition spacing is the panel's field, 3.0 mm by default.
  • Resampling. resample_iso (:20-42) brings the volume to 0.3 mm isotropic, the spacing Dataset516 was trained on (:12-13), linear interpolation, and keeps the physical extent: size is extent / spacing. The docstring notes the earlier resampler kept the voxel count and shrank a 100 × 100 × 30 mm slab to 76.8 × 76.8 × 3 mm.
  • One joint per side. A second MRI that would also be the patient's L (or R) joint is skipped with a message (MRI2CBCT_PREPARE.py:56-58).

Output: _steps/1_mri/<PID>_<S>_MRI.nii.gz with S = L, R or B, plus the manifest listing, per patient, the CBCT path and each joint's source file, side and note (:38-40, :64-66).

5. Orienting the CBCT (ASO)

Plain-language explanation and maths: atlas page.

Three CLIs borrowed from ASO and ALI, called "exactly as their own modules call them" (plan.py:3-5):

  1. PRE_ASO_CBCT centres the scan: a translation by minus the physical position of the image centre, then a resample. It receives a model_folder argument (plan.py:73-76) that the CLI parses and never reads (PRE_ASO_CBCT.py:272 is the only use), which is why MRI2CBCT's downloads do not include the PreASO models.
  2. ALI_CBCT places seven landmarks: Ba, LPo, N, RPo, S, LOr, ROr (plan.py:14), with the arguments spacing [1,0.3], speed_per_scale [1,1], agent_FOV [64,64,64], spawn_radius 10 (plan.py:81-82). One model per landmark is downloaded (requirements.py:43).
  3. SEMI_ASO_CBCT turns the scan onto the Frankfurt horizontal and midsagittal reference (MAMP_0002_T1.mrk.json in the reference folder, plan.py:45), suffix Or.

Outputs: _steps/2_cbct_oriented/<PID>_Or.nii.gz and <PID>_Or_transform.tfm (layout.py:57-62). The transform maps oriented-frame points back to the original CBCT, in the resampling convention (frames.py:8-10); aso_original_to_oriented_ras (frames.py:33-36) turns it into the RAS point map the registration needs. Orientation matters here for a concrete reason: the CBCT is cut into a left and a right half at the median x of its cranial base (§7), which only means something once the head is in a standard pose.

6. The two networks

Plain-language explanation and maths: atlas page.

Neither network registers anything. Each produces one binary cranial-base mask; the registration works on the surfaces of those two masks.

All joints of all patients go through one predictor in one call (predict_from_files_sequential, seg516.py:30; the lists are built at MRI2CBCT_SEGMENT_MRI.py:23-26). Two environment variables are forced before nnU-Net is imported: nnUNet_compile = f because torch.compile breaks in Slicer's Python, and dummy nnUNet_raw, nnUNet_preprocessed, nnUNet_results set to /unused, which "must be set; never read for inference" (seg516.py:9-11).

The network's patch size, intensity normalization and training data live in the downloaded plans.json and dataset.json: not determinable from the repository. Nothing in the repository documents how Dataset516 was trained or evaluated; the archive name (MRICBManual) is the only hint. There is no post-processing at inference; the MRI mask is cleaned when the registration loads it (§7).

7. Registration

Plain-language explanation and maths: atlas page.

MRI2CBCT_REGISTER loads, per patient, the CBCT cranial-base mask once and the ASO transform (MRI2CBCT_REGISTER.py:50-51), then registers each joint with ladder.register_joint (:70-73). The images are not read at this point: the only inputs are two masks.

7.1 Surfaces

Plain-language explanation and maths: atlas page.

  • MRI mask (mri_surface, ladder.py:131-147): threshold at 0.5, refuse a mask under 50 voxels, keep the largest connected component (6-connectivity), sample the surface. The component filter is called mandatory in surface.py:35-41, because normal orientation is propagated across a connectivity graph and detached islands get their normals flipped. The mask volume in cm³ is kept for the QC (§7.3).
  • CBCT mask (cbct_surface, :150-157): same threshold and sampling, with no component filter.
  • Surface points (surface_points_normals, surface.py:10-30): the voxels of mask minus its erosion, subsampled to 20 000 points with a fixed random seed (NPTS, reg/pipeline.py:14), world coordinates in RAS, normals from the gradient of the mask smoothed with σ = 1.5 voxels.
  • Side cut (side_cut, ladder.py:94-102): for a joint labelled L or R, the CBCT surface keeps the points up to MARGIN = 5 mm past the median x of the whole surface on the scanned side (RAS +x is the patient's right). This is what lets a one-joint MRI slab be registered against a full-head CBCT. A joint labelled B (whole volume) uses the entire surface.

7.2 One draw

Plain-language explanation and maths: atlas page.

register (reg/global_reg.py:27-47), parameters from reg/pipeline.py:14-17:

StageValue
Down-samplingvoxel 1.5 mm, then orient_normals_consistent_tangent_plane(20) (:18-24)
DescriptorsFPFH, hybrid search radius 5 × voxel = 7.5 mm, at most 100 neighbours (:31-35)
Global searchRANSAC on feature matching, distance 1.5 × voxel, point-to-point without scaling, 3 points per sample, edge-length checker 0.9 and a distance checker, at most 4 000 000 iterations at 0.999 confidence (:36-42)
RefinementICP point-to-plane from the RANSAC pose, threshold 1.5 × voxel (:44-46)
Scorethe ICP's inlier fitness (and inlier RMSE)
Draws50 independent draws, the highest fitness kept (NDRAW); only the draws run in parallel

The module comment in global_reg.py:1-12 gives the reason for this design: ICP is local and "settled on a 172-degree flip for B108", where a global feature search handles partial overlap and an unknown starting pose. The draws run in a pool of spawn processes (ladder.py:64-86); the clouds are sent once per worker, not once per draw (:35-44), and each worker is limited to OMP_NUM_THREADS = 4 because Open3D "oversubscribes badly when unconstrained". The default worker count is cpu_count // 4, between 1 and 50 (:89-90).

7.3 The verdict

Plain-language explanation and maths: atlas page.

qc_tag (reg/pipeline.py:26-41) needs no reference transform. It tests in this order:

TagConditionMeaning
FLIProtation of the pose > 90°"impossible for one head"; the only criterion said to catch the laterality failures, which fitness did not
FLAGfitness < 0.75 (GATE)weak overlap
SMALLMRI mask < 11.21 cm³a pre-registration warning: the code's comment records that every flip came from this group (5 of 46 against 0 of 172, Fisher p = 3.5e-04)
OKnone of the above

The comment calls these settings and numbers "published" (reg/pipeline.py:12, :19) and points to scripts (run_02_register_w48.py, snap_icp.py) that are not in the repository; see §13.

7.4 The FLIP ladder

Plain-language explanation and maths: atlas page.

  1. Rung 0, the published registration (:205-216): 50 draws; if the best pose is not a FLIP the result is accepted as it is.
  2. More draws (:221-227): EXTRA_DRAWS = 100 more, the best passing pose among all 150 is kept.
  3. Rotate 180° (:229-242): the flipped pose composed with a half-turn about each of the three axes (rot180, :105-113) around the MRI surface's centroid, each refined by point-to-plane ICP in parallel.
  4. The other side (:244-254), only for L or R: the CBCT is cut to the opposite hemisphere and 50 draws are tried, because "the MRI side label may be wrong". If it passes, the joint is relabelled (side L → R) in the log and the summary.
  5. Mirror (:256-267): the MRI surface is reflected across the plane normal to the left-right index axis through its centroid (mirror_matrix, :116-124), and registered again; the reflection is composed into the reported transform. It "fixes a left-right handedness error in the file itself; a wrong mirror fits visibly badly". The QC is scored on the rigid part, because qc_tag cannot read a rotation off a reflection (:260-261).
  6. Unresolved (:269-271): the result is written with the suffix _FLAGGED.
Verified · not in VISOR

Legacy only (3c67957); not present in VISOR. MRI2CBCT is not a tool in SADT-VISOR (SADT-VISOR PROVENANCE.md:46-47) and the client modules are not built (AutomatedDentalToolsRemote CMakeLists.txt:31-32), so no VISOR code exists to check this against.

The registration never looks at the MRI or CBCT intensities. MRI2CBCT_REGISTER feeds register_joint the two segmentation files only (MRI2CBCT_REGISTER.py:70); the images are read later, to be moved or resampled (§8). Whatever the segmentation misses or invents, the registration inherits. This is the opposite of the earlier version, where the CBCT segmentation was only a mask and the match was made on intensities.

8. Outputs, and the frame they are in

Plain-language explanation and maths: atlas page.

Everything is written in the original CBCT's frame, not the ASO-oriented one: T = inv(T_aso) @ T_register (MRI2CBCT_REGISTER.py:93). Per patient, in <output>/<PID>/ (:4-8, :34-36):

FileContent
<PID>_<S>_MRI_REG<TAG>.nii.gzthe MRI, registered onto the CBCT
<PID>_<S>_MRI_MASK<TAG>.nii.gzits Dataset516 cranial base, registered
<PID>_<S>_MRI_transform<TAG>.tfmthe transform, MRI → CBCT
<PID>_CBCT_MASK.nii.gzonce per patient: the AMASSS cranial base, brought back to the original CBCT
summary.csvone row per joint: patient, side, status, qc, tag, fitness, rotation_deg, mask_cm3, resolved_by, ladder, note (:30-31)

TAG is empty, _MIRRORED or _FLAGGED (:92).

  • Header move or resample. By default (on_cbct_grid off) the volumes keep the MRI's own voxels and only their origin and direction are rewritten (move_header, frames.py:53-68): nothing is interpolated, and the MRI "opens on top of the CBCT in any viewer that reads the header", mirrored results included (a reflection gives a left-handed direction matrix, which NIfTI stores). With the option on, the volumes are resampled onto the CBCT grid (linear for the MRI, nearest neighbour for masks, frames.py:71-79).
  • The .tfm. ITK stores the resampling direction, fixed → moving, in LPS: to_itk_resampling (frames.py:39-46) applies L @ inv(T) @ L with L = diag(-1, -1, 1). Loading the native MRI in Slicer and giving it this transform reproduces the result at full resolution.
  • Side relabelling. If the ladder moved a joint to the other side, the files take the new side, unless the patient already has a joint on that side, in which case the original name is kept and the note says so (:82-91).
  • Failures are rows. A patient whose CBCT surface or ASO transform cannot be read gets a failed row per joint (:52-56), a joint that raises gets one too (:73-78); the others carry on.

9. The panel

Plain-language explanation and maths: atlas page.

MRI2CBCTWidget. Top to bottom:

  • One-time setup (MRI2CBCT.py:529, :544): a line that reads "One-time setup needed (packages and models, about 5 GB)" until everything is present, with a button; Run does it too. quick_status only looks at installed packages and download markers, with no torch import and no GPU query (:529-542). If PyTorch had to be installed or replaced, the panel asks for a Slicer restart and stops (:576-581).
  • Inputs: the MRI, CBCT and output folders, and Use test files (onTestFiles, :274): downloads a sample patient (one CBCT, two MRIs) to SlicerDownloads/MRI2CBCT/TestFiles, fills the three folders (output: TestFiles_output beside it, :286) and points to reference/, the expected result (env.py:26-30).
  • Options: resample to 0.3 mm (on), separate left and right (on) with the acquisition slice spacing (3.0 mm, range 0.5 to 10, enabled only when separating). Advanced, collapsed: all 5 folds or 1 fold ("for computers without a GPU"), put the registered MRI on the CBCT grid (off), keep the _steps folder (off), registration workers (0 = automatic).
  • Review: "Pause during the run to check the results", with one checkbox per step (plan.REVIEW_STEPS, plan.py:17-28): MRI joints and sides, CBCT oriented, CBCT cranial base, MRI cranial base, Registration. The choice is remembered in QSettings. At a pause the panel loads the image, with the mask drawn as an outline over it, in the four-up layout, one item per patient or joint, Previous / Next (MRI2CBCT.py:628-715). The first pause also has Swap left / right for this patient (swap_sides, :717-736), which renames the joint files and edits the manifest; a whole-volume MRI (B) has nothing to swap. At the end a message lists each joint's verdict (_finish, :442-458).

12.1 Open3D on Linux

Plain-language explanation and maths: atlas page.

Open3D needs a folder of its own on Linux: Slicer's pip caps the manylinux tag at 2_28, while Open3D's wheel is 2_31 (env.py:12-15). The wheel runs on any glibc 2.31 or newer, so the panel checks the system's glibc (an older one raises "Open3D needs glibc 2.31 or newer", MRI2CBCT.py:612-615) and installs it with --no-deps --only-binary :all: --platform manylinux_2_31_x86_64 --target <py_deps> (:618-621); other systems use a plain pip_install (:623). Open3D is detected on disk, not by importing it, since a running Slicer keeps an open3d it already imported after its folder is deleted while each CLI starts a fresh interpreter (env.py:67-78). At run time ensure_open3d uses the interpreter's own copy, else py_deps, appended to sys.path so that Slicer's numpy and SciPy win (env.py:81-94). ladder.py calls it at import, so MRI2CBCT_REGISTER fails at once with "Open3D is not installed" if neither exists; the panel itself does not import ladder and opens without Open3D.

13. Literature

Plain-language explanation and maths: atlas page.

The paper linked from this tool is Novel CBCT-MRI Registration Approach for Enhanced Analysis of Temporomandibular Degenerative Joint Disease, Leroux G. et al., Clinical Image-Based Procedures (CLIP 2024), LNCS vol. 15196, Springer. As this folder's bibliography reads its abstract, it describes the earlier sequence: automatic orientation, resampling, MRI inversion, normalization, then rigid registration by mutual information. That is not what the code does any more. The current registration is a global search on two predicted surfaces and uses no intensity. The same goes for the two NA-MIC reports kept beside this page: PW43 (2025) is the TorchReg plus elastix generation, PW45 (2026) lists fixes to that generation and, as next steps, a more robust automated approximation, a wider elastix capture range and validation on target registration error.

No document in the folder describes FPFH, RANSAC or the ladder. The code comments speak of "published" settings, of a cohort statistic (5 of 46 against 0 of 172, reg/pipeline.py:22-23) and of scripts outside the repository (run_02_register_w48.py, run_03_export.py, snap_icp.py, itk_io.py:10, surface.py:3-5); the bibliography has found no publication that carries them. That is a question for the maintainers, not something this page can settle. FPFH (Rusu et al., ICRA 2009) and Open3D (Zhou et al., 2018) are the usual references for the building blocks; neither is retrieved here.
