MRI2CBCT

MRI2CBCT places an MRI of the jaw joint onto the CBCT of the same patient. It predicts the cranial base on both scans with two networks, then aligns the two predicted surfaces and checks the result. This page explains how, step by step, with the maths: what goes in, what each step does to it, and what comes out. The files, lines and traps are on the code page. There is no VISOR port: see what exists.

Code (developers) Leroux 2024 · earlier version, CLIP, LNCS 15196 3 MRI2CBCT_* CLIs + 4 borrowed Slicer's Python, no conda Bibliography VISOR: not ported

Overview: what goes in, what comes out

MRI2CBCT places an MRI of the jaw joint (the temporomandibular joint) onto the CBCT of the same patient. The module pairs an MRI folder with a CBCT folder, orients each CBCT, predicts the cranial base on both scans with two networks, and then aligns the two predicted surfaces. The images themselves are never compared: only the two cranial-base masks are used. When the result comes out turned the wrong way, a recovery ladder tries other possibilities. The whole run is started by one Run button and can pause after any step so that the clinician can check it.

MRI2CBCT, legacy module
Inputa folder of MRIs and a folder of CBCTs, matched by patient identifier
Methodprepare the MRIs, orient the CBCT, predict the cranial base on both, align the two surfaces, check the verdict
Outputper patient and joint: the MRI moved onto the CBCT, its mask, the transform, and one summary table with a quality tag for each joint
Whereinside Slicer’s own Python, with a one-time download of packages and models (about 5 GB, the panel’s own estimate)

This page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, the rewritten version). There is no VISOR port: see what exists of MRI2CBCT in VISOR. File names, line numbers and traps are on the code page.

In the codeWhich code base this describes

1. Where it sits in the pipeline

Seven steps are chained by the panel: three small programs of its own (prepare, segment the MRI, register) and four borrowed from ASO, ALI and AMASSS (the lab’s other tools: ASO orients a CBCT, ALI finds landmarks on it, AMASSS segments it). Nothing else calls the three new programs. The step list is built once and the panel runs whatever it returns; the borrowed programs get fresh folders under the output so that they cannot pick up stale files. The module no longer depends on SlicerNNUNet: nnU-Net is installed with pip.

In the codeThe table of what is called, how, and when, with lines

2. Files involved

One panel file, plus a Slicer-free package that holds the logic: the plan of the seven steps, the pairing, the MRI preparation, the inference of the MRI network, the registration with its ladder, the conversions between coordinate frames, and the setup of environment and models. Everything runs in Slicer’s Python. The three new programs each need the manifest written by the first one and the files left by the earlier steps, so they are not usable alone.

In the codeThe file table, the three programs and their arguments

3. Pipeline order, and what is actually mandatory

The order is: pair the patients, optionally resample and split left from right, orient the CBCT, predict the cranial base on the CBCT, predict it on the MRI, register. Steps 1 to 6 are all mandatory, because the registration (step 7) reads the files they leave behind; only resampling and the left-right split inside the first step are options, and both are on by default. Five optional review pauses are off by default. Click a box to read its section.

In the codeThe step table with its status, why and exit codes

4. Pairing and MRI preparation

Before any network runs, the module has to decide which MRI belongs to which CBCT and what each MRI file contains.

4.1 Pairing by patient ID

The modality comes from the folder the clinician chose, never from the file name. The patient identifier is the leading letters followed by a number (P01, B038); leading zeros and capitals do not count, so P1 and p01 are the same patient. The folders are searched recursively. A file or a patient is left out, with a message, when no identifier can be read, when there is an MRI but no CBCT or the reverse, or when there is more than one CBCT for the same identifier. The panel lists them and asks for confirmation. The panel also checks whether the two folders were swapped, by looking only at file headers: an MRI has strongly non-cubic voxels or a small field, a CBCT has cubic voxels and a field of at least 12 cm.

In the codeThe pairing function, the regular expression and the swap detection with their thresholds

4.2 Preparing each MRI

The MRI’s header is kept as it is: the earlier version overwrote the direction matrix, which threw away the only record of which way the slices run. For each file the module decides from its size and slice gaps whether it holds one joint or both, and, with the option on, separates them.

The side of a single-joint slab is read from where its header puts it: a slab at positive left-right position is called left. If the two joints were acquired as two stacks separated by a gap, each stack is rebuilt at the acquisition spacing (3.0 mm by default). With resampling on, every resulting joint is brought to 0.3 mm isotropic voxels.

In the codeThe decision function, the side rule, the gap test and the resampler

5. Orienting the CBCT (ASO)

Three programs borrowed from ASO and ALI put the CBCT in a standard pose. The first centres the scan; the second places seven landmarks (Ba, LPo, N, RPo, S, LOr, ROr) with ALI’s trained models; the third turns the scan onto the Frankfurt horizontal and midsagittal reference computed from those points. The result is an oriented CBCT and the transform that maps back to the original scan. Orientation matters here for a concrete reason: the CBCT is cut into a left and a right half at the median of its cranial base (section 7), which only means something once the head is in a standard pose.

In the codeThe three programs, their arguments and the files they write

6. The two networks

Neither network registers anything. Each produces one binary mask of the cranial base: AMASSS on the oriented CBCT, and a nnU-Net trained for the purpose (called Dataset516) on each prepared MRI joint. The registration then works on the surfaces of those two masks. The MRI network runs on the graphics card when there is one, on the processor otherwise, and can use all five of its folds or only the first one on a computer without a card. All joints of all patients go through one predictor in one call. How the MRI network was trained and evaluated is documented nowhere in the repository.

In the codeThe comparison table of the two networks, the environment variables and the missing documentation

7. Registration

For each patient, the CBCT cranial-base mask is loaded once, together with the orientation transform, and each joint is registered with it. The images are not read at this point: the only inputs are two masks.

In the codeThe register loop and its inputs

7.1 Surfaces

Each mask becomes a cloud of surface points with normals. The MRI mask is first cleaned: it is thresholded, refused if it is under 50 voxels, and reduced to its largest connected piece, because detached islands would get their normals flipped in the next step. The CBCT surface is then cut to the scanned side for a single-joint MRI, which is what lets a one-joint slab be registered against a full head.

In the codeThe surface functions, the component filter, the point count and the side-cut code

7.2 One draw

One draw has three stages. Both clouds are thinned to a 1.5 mm grid. A fast global search then matches local shape descriptors, short lists of numbers that describe how the surface is curved around a point (FPFH, computed in a 7.5 mm neighbourhood) between the two clouds, and a RANSAC loop (repeated random guesses, each scored by how many matches agree with it) picks three matches at a time, keeps the pose that agrees best and stops at 0.999 confidence or after four million tries. Finally a point-to-plane ICP polishes that pose. The global search is there because ICP alone is local and once settled on a 172-degree flip for one patient. The draws are independent and run in parallel in separate processes.

In the codeThe parameter table, the worker pool and the threads setting

7.3 The verdict

A short test, needing no reference transform, gives each joint a tag, in this order: FLIP if the rotation exceeds 90 degrees (the only criterion that caught the left-right failures; fitness did not), FLAG if the fitness is under 0.75, SMALL if the MRI mask is smaller than 11.21 cm³ (a warning: in the code’s own comment, every flip came from this group), otherwise OK.

In the codeThe tag function with its thresholds and the cohort statistic quoted in the comment

7.4 The FLIP ladder

When the best pose of rung 0 (the first registration, 50 draws) is a flip, the module climbs rungs 1 to 4 of a ladder of increasingly drastic remedies, stopping at the first that gives a pose that is not a flip and has a fitness of at least 0.75:

  1. Rung 1, more draws: 100 more, keep the best passing pose among all 150.
  2. Rung 2, rotate 180 degrees: turn the flipped pose by 180 degrees about each of the three axes around the MRI surface’s centre, and refine each with ICP.
  3. Rung 3, the other side: for a single-joint MRI, cut the CBCT to the opposite half and register again with 50 draws, because the side label may be wrong. If this works, the joint is relabelled.
  4. Rung 4, mirror: reflect the MRI surface left to right and register again with 50 draws; this repairs a file whose handedness is wrong.

If no rung passes, the case is unresolved: the best pose of rung 0 is written with the suffix _FLAGGED.

The registration never looks at image intensities: whatever the two segmentations miss or invent, the registration inherits. This is the opposite of the earlier version, where the CBCT segmentation was only a mask and the match was made on intensities.

In the codeThe ladder code with the rotation and mirror matrices and the acceptance rules

8. Outputs, and the frame they are in

Everything is written in the original CBCT’s frame, not the oriented one: the final transform composes the registration with the inverse of the orientation transform. Per patient the module writes the MRI registered onto the CBCT, its cranial-base mask, the transform file (MRI to CBCT, in the convention ITK uses), and once per patient the CBCT cranial-base mask; one summary.csv holds a row per joint with the tag, the fitness, the rotation, the mask volume and which rung resolved it. By default the volumes keep the MRI’s own voxels and only their position and direction are rewritten, so nothing is interpolated and the MRI opens on top of the CBCT in any viewer; an option resamples onto the CBCT grid instead. A patient that fails produces a row marked as failed and the others carry on.

In the codeThe file table, the frame conversions and the failure rows

9. The panel

The panel shows a one-time setup line (packages and models, about 5 GB by its own estimate), the three folders and a button to use a sample patient, the options (resample to 0.3 mm, separate left and right with the acquisition spacing, and advanced choices: all five folds or one, put the result on the CBCT grid, keep the intermediate folder, number of registration workers), and the review pauses. At a pause the panel loads the image with the mask drawn as an outline in a four-up layout, one item per patient or joint, and the first pause offers a button to swap left and right for a patient. At the end a message lists each joint’s verdict.

11. Known issues

  • A weak registration (fitness under 0.75, but not a flip) keeps a clean file name; only the summary table says so. See the trap.
  • An unresolved flip writes the best pose of the first 50 draws, not the best found by the later rungs. See the trap.
  • The side comes from where the header puts the slab, so a badly centred file gets the wrong side without a message. See the trap.
  • An output folder placed inside an input folder is read back on the next run. See the trap.
  • The run log does not survive a successful run. See the note.
  • Only the MRI surface is cleaned to its largest connected piece. See the note.

Dead code and leftovers

12. Environment

Everything runs in Slicer’s Python, with no conda. The graphics card is optional for the MRI network. On first use the panel installs the Python packages and downloads the models into the folders the borrowed modules already use, so nothing is fetched twice; the versions, the numpy handling and the paths are on the code page.

In the codeThe environment table with versions, paths and override variables

12.1 Open3D on Linux

Open3D, the library behind the registration, needs a special install on Linux, which the panel does. The registration step fails at once with a clear message if Open3D is missing, while the panel itself opens without it; the details are on the code page.

In the codeThe install arguments, the glibc check and the path order

13. Literature

The paper linked from this tool (Leroux et al., CLIP 2024) describes the earlier sequence: automatic orientation, resampling, MRI inversion, normalisation and rigid registration by mutual information. That is not what the code does any more: the current registration is a global search on two predicted surfaces and uses no intensity. No document in the folder describes the descriptor matching, the RANSAC or the ladder, and the code comments cite scripts outside the repository; that is a question for the maintainers. The only published numerical evaluation predates the rewrite, so nothing published measures the current version. Full bibliography: the sources page; the links are on the code page.
