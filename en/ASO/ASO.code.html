Two code bases

Everything numbered below describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, is described in ASO on VISOR. Notes added to the callouts say whether each finding still holds in VISOR; they cite SADT-VISOR at 6ba2a78, with ASO/ for tools/ASO/src/sadt_aso/ when the path is not written in full. 1. Where it sits in the pipeline

Plain-language explanation and maths: atlas page.

Nothing in the repository calls ASO. ASO, however, calls six tools (three on the CBCT side, three on the IOS side), and AREG_IOS consumes its output directly: AREG_IOS.py:273 looks for <patient>_SegOr.tfm in the T1 and T2 folders, exactly the name written by PRE_ASO_IOS.py:221, and composes inv(areg_matrix @ inv(matrix_aso)) to produce a single matrix from raw scan to registered.

Legacy only. In VISOR ASO calls one tool, ALI_CBCT, and is called by four: AREG_CBCT, AREG_IOS, AREG_IOSCBCT and VFACE (see Status and where it lives).

3. The shared geometric principle

Plain-language explanation and maths: atlas page.

The target is not an analytical frame ("occlusal plane = z=0") but a reference patient case, downloaded from a release: scan + fiducials for the CBCT, two meshes + two jsons for the IOS. The choice of frame is thus offloaded into the data: Occlusal and Midsagittal Plane or Frankfurt Horizontal and Midsagittal Plane (CBCT.py:50-51) are two different golds, the same code producing two different orientations.

In both backends the estimation follows the same two-stage scheme:

  1. A 3-point initialization: a translation followed by two rotations around hand-built axes, never a least-squares Procrustes/Kabsch;
  2. a vtkIterativeClosestPointTransform in RigidBody mode on the anchor point clouds, to refine.

This is the point to remember: the matrix is not an optimal solution in the least-squares sense over N correspondences. It is built through successive rotations on a chosen triplet, then polished by an ICP that, for its part, re-pairs the points by nearest neighbor rather than by label.

4.2 PRE_ASO_CBCT: recentering, no more network computed

Plain-language explanation and maths: atlas page.

Despite its name and its six arguments, this CLI now does only one thing (PRE_ASO_CBCT.py:100):

T = -np.array(img.TransformContinuousIndexToPhysicalPoint(np.array(img.GetSize()) / 2.0))
translation = sitk.TranslationTransform(3); translation.SetOffset(T.tolist())
img_trans = ResampleImage(img, translation.GetInverse())

ResampleImage keeps the size (ratio = 1), the spacing and the direction, and sets new_origin = orig_origin - orig_center. Since the applied transform exactly cancels this offset, no real interpolation takes place: only the physical origin moves, and the volume ends up centered on the world origin. This is the prerequisite for §4.4, where the rotation is applied around the origin.

The arguments model_folder, SmallFOV and temp_folder are parsed and never used. PreASOResample (ResamplePreASO.py:193, an isotropic 128³ resampling) is imported but never called, and DenseNet (Net.py:28, a 3D monai DenseNet169 regressing a unit direction vector via cosine loss) is commented out in __init__.py. There is no longer any pre-orientation network in ASO_CBCT at all: its training code remains, the PreASOModels.zip weights are still downloaded and validated (CBCT.py:112-116, and TestModel at CBCT.py:74-78 requires a .ckpt), for nothing.

Output: the recentered volume under its original name, and <name without extension>.tfm containing the translation T, not inverted, even though it is translation.GetInverse() that was applied to the volume.

4.3 ALI_CBCT: the landmark provider predicted

Plain-language explanation and maths: atlas page.

Called on the temporary folder, both for input and output, with hard-coded constants (CBCT.py:515): spacing="[1,0.3]", speed_per_scale="[1,1]", agent_FOV="[64,64,64]", spawn_radius="10", and lm_type reformatted into a literal Python list by format_lm_string (CBCT.py:471, called at :508). ALI_CBCT is a two-scale search agent system (1 mm then 0.3 mm, a FOV 64³ voxels around the agent); it writes one json per anatomical group, <id>_lm_Pred_<group>.mrk.json (ALI_CBCT_utils/environment.py:152), in LPS. The weights are <Landmark>_Net*.pth files downloaded one per landmark from ALI_CBCT/releases/download/models_v01/<LM>.zip.

This is the whole point of MergeJson (utils.py:63), the first call made by SEMI_ASO_CBCT: gluing the per-group jsons back into a single <patient>_lm_MERGED.mrk.json , and deleting the source files (os.remove).

4.4 SEMI_ASO_CBCT: the orientation computed

Plain-language explanation and maths: atlas page.

a) Pruning outlier landmarks. GetLandmarkToRemove (utils.py:341) compares the full distance matrix and the direction matrix between all the landmarks of the scan and those of the gold. Actual constants: distance gap > 15 mm, angular gap > 0.4 rad (and -1 if < 0.1 rad, meaning a very consistent pair offsets a doubtful one). A landmark is dropped if its total count exceeds the number of landmarks, or if its angular count alone exceeds half of it. The analysis covers all landmarks in the json, not only the checked ones.

b) The optimal triplet. FindOptimalLandmarks (utils.py:166) randomly draws triplets (A, B, C), runs the initialization for each, and keeps the one that minimizes the final average distance. Bounds: n(n-1)(n-2) distinct triplets or 2500 draws, whichever comes first (utils.py:166-191). The picks come from the global np.random.randint (utils.py:573, :590, :617), never seeded: nothing makes two runs draw the same triplets, and a repeated triplet is skipped (utils.py:188). The initial angle and axis are AngleAndAxisVectors(v2, v1), which also divides each vector by its largest component (utils.py:890-891).

c) The initialization, InitICP (utils.py:556):

  1. translation bringing A_source onto A_target;
  2. rotation about the axis cross(v2, v1) by the angle arccos of the dot product, where v1 = abs(B - A) on the source side and v2 = abs(B - A) on the target side (utils.py:598-600): component-wise absolute values, which folds both vectors into the positive octant and is not the angle between the actual vectors;
  3. a third rotation whose axis is abs(B - A) itself, not a cross product, taken on the source after the second step has rotated it: a roll with its angle computed from C (utils.py:624-633).

RotationMatrix (utils.py:838) is the quaternion-based Rodrigues formula, identical to the one in FlexReg and ASO_IOS. A crucial point: transform_matrix = rotation_transform_matrix # @ TranslationTransformMatrix (utils.py:612) , the translation from step 1 is deliberately excluded from the returned matrix. It is used to compute the rotations, not to move the volume.

d) The ICP. ICP_Transform (utils.py:527) converts the two dictionaries into vertex vtkPolyData and runs a vtkIterativeClosestPointTransform: SetModeToRigidBody(), SetMaximumNumberOfIterations(1000), StartByMatchingCentroidsOn(). Its translation is then zeroed out: transform_matrix_bis[:3, 3] = [0, 0, 0] (utils.py:710).

e) Composition. transform_list accumulates [translation, R1, R2, R_icp], then (utils.py:719-728):

for i in range(len(transform_list) - 1, 0, -1):   # stops at 1: the translation is discarded
    transform_sitk.AddTransform(transform_list[i])
transform_sitk_final = sitk.CompositeTransform(transform_sitk)
transform_sitk_final.AddTransform(input_transform)   # the PRE_ASO .tfm
transform_sitk_final = transform_sitk_final.GetInverse()
transform_sitk = transform_sitk.GetInverse()

The final result is therefore a pure rotation around the world origin. This is consistent because PRE_ASO_CBCT centered the volume on that origin, and this is precisely what the semi mode lacks.

ResampleImage (utils.py:752) calls SetReferenceImage(image): same grid, same size, same spacing, linear interpolation, DefaultPixelValue = 0. The volume rotates within its existing box, nothing is resampled to a different resolution, and whatever falls outside the FOV is lost.

f) Outputs, in output_folder with the same relative tree structure as the input:

FileContent
<patient>_<suffix>.nii.gzreoriented volume, always .nii.gz regardless of the input format
<patient>_lm_<suffix>.mrk.jsonrotated landmarks, written by WriteJson in LPS
<patient>_<suffix>_transform.tfmtransform_sitk_final, ITK convention (fixed → moving)

All three writes are guarded by if not os.path.exists(...): rerunning on a non-empty output folder rewrites nothing and still ends in success.

The ASO_CBCT chain, step by step

Plain-language explanation and maths: atlas page.

T1: a CBCT in any pose

Automatic mode

  1. PRE_ASO_CBCT recentres the scan computed: there is no network here any more a translation, written as .tfm
  2. ALI_CBCT predicts the orientation landmarks predicted .mrk.json, LPS
  3. SEMI_ASO_CBCT fits those landmarks onto a gold standard’s: 3-landmark initialisation, then a rigid vtkIterativeClosestPointTransform, 1000 iterations computed <pat>_<suffix>_transform.tfm

Semi-automatic mode

  1. the operator supplies the landmarks: steps 1 and 2 are skipped, step 3 is unchanged same .tfm

After step 3 the mid-sagittal plane sits on x = 0. That is the condition every downstream module relies on: VFACE mirrors about that exact plane, and AREG_CBCT calls this very chain as its own upstream. The matrices are written out in §4.5.

4.5 The orientation, written out

Plain-language explanation and maths: atlas page.

Everything above is prose about code. Here is the same thing as arithmetic, because two of ASO's choices only become visible once they are written down. Notation: p→A is landmark A on the scan being oriented, q→A the same landmark on the gold.

The translation moves the source so the rotations can be computed on superimposed points. It is then dropped: transform_matrix = rotation_transform_matrix, with the translation commented out of the product. The volume is never translated: PRE_ASO_CBCT already centred it on the origin.

Read those bars carefully. They are a component-wise absolute value, not a norm. Both vectors are folded into the positive octant before the angle is taken, so what follows is the angle between |u→| and |v→|, which is not the angle between u→ and v→. A landmark pair pointing one way and its gold counterpart pointing the opposite way give the same vector here.

θ1=arccos(v→2⋅v→1∥v→2∥∥v→1∥) , a→1=v→2×v→1

In the code the two vectors are first divided by their largest component (v1_u = v1 / np.amax(v1)). That is a positive scaling, so it cancels in both the quotient and the cross product: it changes nothing.

The second rotation is the other surprise. Its axis is not a cross product but the first-to-second vector as the source stands after the first rotation, folded again with abs() (RotationMatrix(abs(source[secondpick] - source[firstpick]), angle), utils.py:630). It is a roll around that axis, and its angle comes from a third landmark, measured between the folded reference vector and the folded, already rotated, scan vector (utils.py:624-626). The roll keeps what the first rotation did only if the rotated vector has no negative component (or no positive one); otherwise it turns about the folded copy, which points elsewhere. The angle is the unsigned arccos, applied counterclockwise about the axis.

R=[α2+β2−γ2−δ22(βγ+αδ)2(βδ−αγ)2(βγ−αδ)α2+γ2−β2−δ22(γδ+αβ)2(βδ+αγ)2(γδ−αβ)α2+δ2−β2−γ2]

Two sign flips cancel here: the vector part carries a minus, and the matrix is written transposed relative to the usual quaternion form. The result is the ordinary Rodrigues rotation of θ about a→̂. The same function serves FlexReg and ASO_IOS.

The ICP contributes a rotation only: its translation column is explicitly zeroed (transform_matrix_bis[:3, 3] = [0, 0, 0]). The composite is therefore a pure rotation about the world origin.

Why this is not a fit · Also true in VISOR

With N paired landmarks there is a closed-form rotation that minimises the sum of squared distances, Kabsch, by the singular value decomposition of the cross-covariance:

with D=diag(1,1,det(VU⊤)) guarding against a reflection. ASO computes nothing of the sort. It builds two rotations from a triplet, keeps the triplet that happens to score best over up to 2500 draws, and hands the result to an ICP that re-pairs the points by nearest neighbour rather than by label. It is a search, not a solution. The ICP itself does fit a rotation by least squares at each step, but on pairs it chooses by distance, not on the labelled landmarks.

Also true in VISOR, with one difference: the triplet search is exhaustive when there are at most max_triplets (2500) ordered triplets (7 landmarks give 210), otherwise a sample from a generator seeded by seed, instead of random draws from the global generator (SADT-VISOR ASO/geometry.py:323-359; legacy ASO_CBCT_utils/utils.py:182-191). The rotation is still handed to vtkIterativeClosestPointTransform (ASO/cbct/icp.py:200-204, ASO/ios/icp.py:107-111).

5. ASO_IOS

Plain-language explanation and maths: atlas page.

5.1 Automatic mode: crown centroids

Plain-language explanation and maths: atlas page.

a) Segmentation bypass. __BypassCrownseg__ (IOS.py:196) opens each mesh and looks for a PredictedID, UniversalID or Universal_ID array. Already-segmented meshes are copied directly into the segmentation's output folder with the suffix _Seg; the others go to the input folder to be segmented, with exotic formats converted to .vtk along the way.

b) DentalModelSeg predicted, via conda (IOS.py:278-289):

conda run -n shapeaxi python -m CrownSegmentationcli \
  None <csv> <out> 0 latest 0 Universal_ID 0 Seg <vtk_folder> <dentalmodelseg_path>

Argument order: surf, input_csv, out, overwrite, model, crown_segmentation, array_name, fdi, suffix, vtk_folder, dentalmodelseg_path. overwrite = "0" and suffix = "Seg": unlike FlexReg, ASO does not overwrite the input file, it produces a <name>_Seg.vtk in a temporary folder. The network is the same one (multi-view Fly-by-CNN, universal 1–32 numbering in Universal_ID), bundled in the pip package shapeaxi: the latest architecture and weights cannot be determined from this repository.

The dentalmodelseg_path computed in Process is dead: run_conda_tool (ASO.py:1459) replaces it with the result of a which dentalmodelseg inside the environment. The if os.path.isfile(path_input) branch (IOS.py:268) is dead too, path_input is always a folder created by os.makedirs, and it references a self.input that does not exist. path_preor is created and never used.

Execution is synchronous and blocking: run_conda_tool loops on process.is_alive() while calling slicer.app.processEvents(), tracks progress by re-reading the log, then removes the step from the queue before onPredictButton launches slicer.cli.run on the next one.

c) PrePreAso: the orientation computed, the core (pre_icp.py:76). organizeLandmark (pre_icp.py:16) sorts the 3 or 4 chosen teeth into (left, middle(s), right) using the universal numbering: on the upper arch (1–16) the number increases from right to left, so max → left; on the lower arch (17–32) it's the reverse.

vtkMeanTeeth (icp.py:413) averages the vertices carrying each Universal_ID. With 4 teeth, the two middle centroids are averaged together → it always comes back to three points.

make_vector builds, for each triplet, a local basis: normal = cross(m→d, m→g) (the normal of the plane through the three points), perpen = the right→left direction, direction = cross(normal, perpen). Then:

  1. rotation about the axis cross(normal_source, normal_target) by the angle arccos(dot): the plane of the scan's three centroids is brought onto the gold's;
  2. direction_source is rotated by this matrix, then a second rotation about the axis cross(direction_source, direction_target) fixes the roll within this plane;
  3. a translation that makes the centroids of the two triplets coincide.

No scaling. The 4×4 matrix is returned along with the transformed mesh.

d) The refinement. ICP([InitIcp(), vtkICP()], option=vtkMeanTeeth(dents)) (PRE_ASO_IOS.py:331-336). The option is applied to both meshes before the chain runs: the ICP only ever sees the 3 or 4 centroids, never the crown geometry. InitIcp (icp.py:156) is the class version of ASO_CBCT's InitICP: the same abs(), the same roll axis, the same FindOptimalLandmarks with 2500 draws. vtkICP is the same rigid vtkIterativeClosestPointTransform (icp.py:142-143), but with 100 iterations instead of 1000, and its translation is not zeroed out. Unlike the CBCT version, InitIcp keeps the translation of step 1 in the matrix it returns (icp.py:242), and its FindOptimalLandmarks is the same unseeded random draw (icp.py:279-312).

The final matrix is output_icp["matrix"] @ matrix: ICP after PrePreAso (PRE_ASO_IOS.py:216). Inside ICP.run, however, the list [InitIcp(), vtkICP()] is multiplied in list order, matrix_final = matrix_final @ matrix (icp.py:106), so output_icp["matrix"] is M_init @ M_icp. With column vectors (vtkTransform.SetMatrix) that applies the ICP matrix first, although VTK computed it on points the initialisation had already moved. VISOR multiplies M_icp @ M_init (ASO/ios/icp.py:98). Read from the code; the effect on a real arch was not measured.

5.2 Semi mode: supplied landmarks computed

Plain-language explanation and maths: atlas page.

SEMI_ASO_IOS.py. Same machinery, option becomes SelectKey(liste_de_landmarks) (icp.py:478): a simple key filter over the landmark dictionaries. No more PrePreAso, no more segmentation: InitIcp then vtkICP on the named landmarks.

Landmark names are built by a Cartesian product in the UI: {dent}{repère} with repère ∈ O, MB, DB (occlusal) or CB, CL, OIP, R, RIP (cervical), then listlandmark2diclandmark splits them by arch based solely on the initial U/L (ASO_IOS_utils/utils.py:144).

The matrix obtained from the landmarks is then applied to the full mesh.

The ASO_IOS chain, step by step

Plain-language explanation and maths: atlas page.

an intra-oral scan: a surface mesh, no volume

Automatic mode: crown centroids

  1. __BypassCrownseg__ looks for a PredictedID, UniversalID or Universal_ID array: an already-segmented mesh skips the network copied as <name>_Seg
  2. DentalModelSeg labels the crowns, through conda run -n shapeaxi predicted <name>_Seg.vtk, in a temporary folder
  3. the centroid of each labelled crown becomes a landmark computed one point per tooth
  4. PRE_ASO_IOS then a rigid ICP onto the gold standard’s centroids computed the oriented mesh + its .tfm

Semi mode: supplied landmarks

  1. SelectKey filters the landmark dictionaries by name, then InitIcp and vtkICP run on those names alone: no segmentation, no PrePreAso computed same .tfm

Unlike FlexReg, ASO does not overwrite the input mesh: overwrite = "0" and suffix = "Seg", so the segmentation lands in a temporary folder.

5.3 Occlusion

Plain-language explanation and maths: atlas page.

A checkbox that forces a single arch (ASO.py:2544, ASO.py:2552): the chosen arch drives the orientation, and the same matrix is applied to the opposite arch (file[jaw.inv()], PRE_ASO_IOS.py:283-285) to preserve the occlusal relationship. Upper/lower pairing is done by file name, via Files_vtk_link / Files_vtk_json_semilink (data_file.py): the recognized markers are Upper/_U_ and Lower/_L_.

Pitfall · Legacy only

UpperOrLower (ASO_IOS_utils/utils.py:98-107) defaults to "Lower" when no marker is found: a poorly named file is silently treated as mandibular.

Legacy (3c67957): still true, ASO_IOS/ASO_IOS_utils/utils.py:98-107 (default="Lower"). Not present in VISOR: a file with no jaw token raises JawError, is skipped and counted, with no default (SADT-VISOR ASO/ios/pipeline.py:43, :83-107).

saveMatrixAsTfm (ASO_IOS_utils/utils.py:172) inverts the matrix (ITK fixed → moving convention) and writes it as an AffineTransform. This is consistent end to end with AREG_IOS, which reads it back as is.

Legacy (3c67957): ASO_IOS_utils/utils.py:172-184. Also true in VISOR: same inverted matrix written as an AffineTransform (SADT-VISOR ASO/ios/pipeline.py:548-554). The file name is not the same: <patient>_<Upper|Lower>_<suffix>.tfm (:542), not <patient>_SegOr.tfm. AREG_IOS in VISOR collects the upper-arch .tfm files by patient stem with the jaw tokens dropped (tools/AREG/AREG_IOS/src/sadt_areg_ios/dispatch.py:255-280); the end-to-end chain was not run.

6. Comparison with FlexReg's orientation

Plain-language explanation and maths: atlas page.

FlexReg_Method/orientation.py and ASO_IOS_utils/pre_icp.py are the same algorithm, copy-pasted. make_vector is identical character for character; the bodies of orientation() and PrePreAso() differ only on three points:

ASO_IOS PrePreAsoFlexReg orientation
Targetthe gold mesh's centroids, read with the same vtkMeanTeeththree hard-coded points, [[-0.5,-0.5,0], [0,0,0], [0.5,-0.5,0]]
Teeth3 or 4 chosen by the operator, sorted by organizeLandmark3, 5, 12, 14 hard-coded (UR6, UR4, UL4, UL6)
Return(mesh, matrix)mesh alone

transformation.py is likewise duplicated between the two (same RotationMatrix, TransformSurf, TransformDict, formatting aside), and ASO_IOS's icp.py holds the classes from which FlexReg_Method/util.py reuses vtkTeeth, vtkMeanTeeth and vtkMeshTeeth.

Practical consequence: FlexReg produces a canonical and reproducible frame (occlusal plane ≈ z=0, +y anterior), which then lets it reason in 2D within the XY plane. ASO_IOS produces an orientation relative to a reference patient: no guarantee that the occlusal plane lands on z=0, and no ICP refinement in FlexReg where ASO adds one.

8. Environment

Plain-language explanation and maths: atlas page.

Two distinct regimes, and this is a source of confusion.

The CLIs run in Slicer's Python. install_function (ASO.py:74) pip_installs whatever is missing there: itk, pytorch_lightning, dicom2nifti>=2.6.2, pydicom==3.0.2 and monai at 1.3.2 (Python ≥ 3.10) or 0.7.0 otherwise. torch is no longer pinned: it is not in that list (ASO.py:81-88), and the build that suits the GPU is chosen by torch_install_arguments() (ASO.py:92, installed first and on its own at :139-144).

Not present in VISOR: nothing is installed in Slicer's Python, and the ASO environment has no torch (SADT-VISOR tools/ASO/pyproject.toml).

9. Pitfalls and fragile points

Plain-language explanation and maths: atlas page.

Confirmed bug · First half superseded at 3c67957, second half Legacy only

The .tfm requirement is fixed in the legacy. An earlier revision of this page said SEMI_ASO_CBCT.py required data["tfm"] and failed with a KeyError on every patient without a .tfm. At 3c67957 it reads data.get("tfm") and registers from the landmarks alone, with an identity as the prior transform (SEMI_ASO_CBCT/SEMI_ASO_CBCT.py:52-59, ASO_CBCT_utils/utils.py:666-676; commit e703ec0, 2026-09-29). In VISOR no .tfm is read at all and the recentering is folded into the transform it writes (SADT-VISOR ASO/cbct/icp.py:168-170).

And even without that, the semi mode has no recentering. Since the orientation is a pure rotation around the world origin (§4.4e), an off-center volume ends up outside its own FOV, DefaultPixelValue = 0.

This second part is still true of the legacy at 3c67957: Semi_CBCT.Process launches semi_aso_cbct and nothing else (ASO/ASO_Method/CBCT.py:379-393). Not present in VISOR: every scan is recentered before the orientation, whatever the mode (SADT-VISOR ASO/dispatch.py:719, and the supplied landmarks are moved with it, :756).

Confirmed bug · Legacy only

MergeJson deletes files in the input folder. In semi mode, input_dir is the user's folder: all of its .mrk.json files without MERGED in their name are merged and then erased (utils.py:120).

Legacy (3c67957): still true, ASO_CBCT_utils/utils.py:63-120 (the os.remove is at :120), called at SEMI_ASO_CBCT.py:172; since de4600b (2026-10-06) it skips JSON files that are not markups, so ALI's report is no longer merged or deleted, but landmark files still are. Not present in VISOR: the files are merged in memory per patient, nothing is written or deleted in the input (SADT-VISOR ASO/cbct/pipeline.py:232-253).

Pitfall · Also true in VISOR

The coordinate system of the jsons is never checked. LoadJsonLandmarks reads position raw; ALI and ASO write LPS, but a fiducial exported as RAS from Slicer will be read with x and y flipped, with no warning.

Legacy (3c67957): ASO_CBCT_utils/utils.py, LoadJsonLandmarks reads position and never coordinateSystem. Also true in VISOR: load_landmarks reads the position as it is (SADT-VISOR ASO/markups.py:35-64); the only occurrence of coordinateSystem in the tool's sources is the "LPS" it writes (markups.py:75).

Pitfall · Legacy only

Inconsistent minimum landmark count. The UI requires 3 checked landmarks (TestCheckbox, CBCT.py:67-70) but ICP bails out as soon as len(list_landmark) <= 3 (utils.py:661). So 4 are actually needed, and more if pruning removes some.

Legacy (3c67957): still true, the interface check is ASO/ASO_Method/CBCT.py:70 (< 3) and the ICP exit is ASO_CBCT_utils/utils.py:661 (<= 3). Not present in VISOR: the minimum is 3 everywhere (SADT-VISOR ASO/cbct/icp.py:27, :134; ASO/dispatch.py:251-255).

  • The ICP re-pairs by nearest neighbor. vtkIterativeClosestPointTransform ignores labels: on landmarks that are pairwise close (left/right pairs), it can lock in a crossed pairing that the initialization had already gotten wrong.
  • The abs() calls in InitICP. The vectors are folded into the positive octant before the angle calculation, in both backends. Since the retained triplet is the one that minimizes the measured error, the search compensates for this, but nothing should be concluded from the geometry of this step taken in isolation.
Pitfall · Legacy only

Nothing is rewritten if the file already exists. All three CBCT outputs are guarded by if not os.path.exists. A second pass after fixing a parameter produces no visible effect and still ends in success.

Legacy (3c67957): still true, SEMI_ASO_CBCT.py:94, :111, :124 and PRE_ASO_CBCT.py:134, :156. Not present in VISOR: each job writes into a fresh output folder created by the server (VISOR-serve execution/dispatch.py:427-430) and the outputs are written unconditionally (SADT-VISOR ASO/cbct/pipeline.py:367-374).

Confirmed bug · Legacy only

Patient identifiers diverge between ASO and AREG. PatientNumber (ASO_IOS_utils/utils.py:167) cuts on _U/_L, while AREG_IOS rebuilds it as patient_id.split("_")[0] (AREG_IOS.py:271). A name like P01_T1_U.vtk gives P01_T1 on one side and P01 on the other: ASO's .tfm is never found, and AREG settles for a logger.warning.

Legacy (3c67957): the divergence is still there, at other lines: PatientNumber is ASO_IOS/ASO_IOS_utils/utils.py:167 and AREG_IOS builds the short id at AREG_IOS/AREG_IOS.py:271. ASO writes <PatientNumber>_SegOr.tfm only when the occlusion is linked; with independent arches the jaw stays in the name (ASO_IOS/PRE_ASO_IOS/PRE_ASO_IOS.py:216-224). The second PatientNumber definition mentioned in an earlier revision of this page no longer exists in this file. Not present in VISOR as stated: ASO writes <patient>_<jaw>_<suffix>.tfm (SADT-VISOR ASO/ios/pipeline.py:542) and AREG_IOS pairs by patient_stem with the jaw tokens dropped (AREG_IOS/dispatch.py:255-280); read in code, the chain was not run end to end.

  • Dead code: Net.py (DenseNet) and PreASOResample on the CBCT side; the search with a phantom self; DisplayALIIOS; Files_vtk_json_link; vtkMiddleTeeth; npSameNumberPoint (the source.shape[0] < target.shape[0] branch, which references an undefined target_points); the orphan file LinearTransform_t.tfm, referenced nowhere.
  • PRE_ASO_CBCT's .tfm is written non-inverted, even though it is its inverse that was applied to the volume. It is later composed and then inverted as a block in SEMI_ASO_CBCT; worth checking before reusing this file on its own.
  • Time-point suffixes. PatientScanLandmark (CBCT.py:27) only cuts on _T1/_T2; a _T3 breaks the pairing. The comment is already there in the code.

10. Literature

Plain-language explanation and maths: atlas page.

The reference paper for ASO_CBCT is Automated Orientation and Registration of Cone-Beam Computed Tomography Scans (Anchling, Hutin, Cevidanes et al., Lecture Notes in Computer Science, 2023). Its description matches the code: ALI_CBCT identifies the landmarks regardless of the input orientation, then the orientation is obtained "by first aligning 3 randomly chosen landmarks, then refining with ICP." Reported errors: < 3° and < 2 mm against experts. The paper does not mention the DenseNet pre-orienter, consistent with the fact that it is no longer connected.

For ALI_CBCT itself: Automatic landmark identification in cone-beam computed tomography (Gillot et al., Orthodontics & Craniofacial Research, 2023).

ASO_IOS has no paper of its own. The closest published text is AReg IOS: Automatic Registration on IntraOral Scans (Hutin, Anchling, Cevidanes et al., LNCS 2023), which describes the initial alignment by shared tooth centroids, that is, exactly PrePreAso. The rest (tooth selection by the operator, ICP refinement on 3 centroids, occlusion mode) is unpublished internal development.
