ASO

ASO looks for a rigid rotation that brings a CBCT or an intraoral scan into the frame of a reference case (the “gold”), through a 3-point initialisation followed by ICP: never an optimal least-squares registration. This page explains how, step by step, with the maths. Files, lines, code blocks and pitfalls are on the code page.

Anchling 2023 · LNCS 14242 Atlas (explanation) Code (developers) PRE_ASO_CBCT SEMI_ASO_CBCT PRE_ASO_IOS SEMI_ASO_IOS conda env: shapeaxi (IOS auto only) VISOR Bibliography

Two code bases. This page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, is described in ASO on VISOR. Where VISOR differs, a sentence says so.

Overview: what goes in, what comes out

A scan can be in any pose in its file. ASO finds the rotation that brings it onto a reference patient who is already oriented, using a few anatomical points that both share. It works in two modalities and, for each, in two modes.

CBCTIntraoral scan (IOS)
Inputa head scan; Semi mode also needs landmark filesupper and lower tooth meshes; Semi mode also needs landmark files
Automatic modelandmarks predicted by ALI_CBCTtooth centroids, after a crown segmentation
Methoda first alignment from three points, then a rigid ICP
Outputthe oriented scan or mesh, the moved landmarks, and a transform

1. Where it sits in the pipeline

Nothing in the repository calls ASO. ASO, however, calls three tools, and AREG_IOS consumes its output directly: it looks for the transform file written by ASO and composes it with its own matrix to produce a single matrix from the raw scan to the registered one. In IOS, the anchor points are not predicted landmarks but tooth centroids; ALI_IOS is never called.

Legacy only. In VISOR, ASO calls one tool, ALI_CBCT, and is called by four (see the VISOR page).

In the codeThe tools ASO calls, how, and the file AREG_IOS expects

2. Files involved

A widget (interface, downloads, chaining of the command-line modules, conda), two helpers that build the parameters, and four command-line modules: one to recentre, one to orient a CBCT, one for IOS by centroids, one for IOS by landmarks. All of them go through Slicer’s own Python; only the crown segmentation goes through a conda environment. None needs a GPU: it is VTK and SimpleITK. Part of the code now lives in the shared ADTLib layer.

3. The shared geometric principle

The target is not an analytical frame (“occlusal plane = z = 0”) but a reference patient case, downloaded from a release: a scan and fiducials for the CBCT, two meshes and two landmark files for the IOS. The choice of frame is thus in the data: the Occlusal-and-midsagittal and the Frankfurt-and-midsagittal references are two different golds, and the same code produces two different orientations.

In both backends the estimation follows the same two-stage scheme:

  1. A 3-point initialisation: a translation followed by two rotations around hand-built axes, never a least-squares fit;
  2. a rigid ICP on the anchor point clouds, to refine.

This is the point to remember: the matrix is not an optimal solution in the least-squares sense over N correspondences. It is built through successive rotations on a chosen triplet, then polished by an ICP that re-pairs the points by nearest neighbour rather than by label.

4.2 PRE_ASO_CBCT: recentering, no more network computed

Despite its name and its six arguments, this module now does only one thing: recentre the volume. The pre-orientation network it was named for is disconnected; its training code and weights remain, downloaded and validated for nothing.

No real interpolation takes place, only the physical origin moves. This is the prerequisite for the orientation, where the rotation is applied about the origin. The module also writes a transform holding the translation, not inverted, even though its inverse is what was applied to the volume.

In the codeThe recentering code, the dead arguments, the broken DICOM fallback

4.3 ALI_CBCT: the landmark provider predicted

Called on the temporary folder, with hard-coded constants (two scales, 1 mm then 0.3 mm, a field of view of 64³ voxels around the agent). ALI_CBCT is a two-scale search agent system; it writes one landmark file per anatomical group, in LPS. The weights are downloaded one per landmark. The first thing the orientation module does is glue the per-group files back into one per patient, and delete the sources.

In the codeThe constants passed to ALI_CBCT and the merge

4.4 SEMI_ASO_CBCT: the orientation computed

a) Pruning outlier landmarks. The full distance matrix and direction matrix between all landmarks of the scan and those of the gold are compared. A landmark is dropped if it disagrees by more than 15 mm or 0.4 rad too often; a very consistent pair (under 0.1 rad) offsets a doubtful one. The analysis covers all landmarks in the file, not only the checked ones.

b) The optimal triplet. Triplets (A, B, C) are drawn at random, the initialisation is run for each, and the one that minimises the final mean distance is kept. The bound is the number of distinct triplets or 2500 draws, whichever comes first.

c) The initialisation is three steps: a translation of A onto its counterpart, a rotation about the cross product of the two folded vectors, and a roll about the axis just aligned. Its maths are in section 4.5. The translation is deliberately excluded from the returned matrix: it is used to compute the rotations, not to move the volume.

d) The ICP. A rigid ICP, 1000 iterations, starting by matching centroids; its translation is then zeroed out.

e) Composition. The rotations are composed, the recentering transform is added, and the whole is inverted. The final result is a pure rotation about the world origin. This is consistent because the first module centred the volume on that origin, and this is precisely what the semi mode lacks.

f) Outputs. In the output folder, with the input’s folder tree: the reoriented volume (always .nii.gz regardless of the input format), the rotated landmarks (in LPS), and the transform. All three writes are skipped if the file already exists: rerunning on a non-empty output folder rewrites nothing and still ends in success.

T1: a CBCT in any pose

Automatic mode

  1. PRE_ASO_CBCT recentres the scan computed: there is no network here any more a translation, written as .tfm
  2. ALI_CBCT predicts the orientation landmarks predicted .mrk.json, LPS

Semi-automatic mode

After step 3 the mid-sagittal plane sits on x = 0. That is the condition every downstream module relies on: VFACE mirrors about that exact plane, and AREG_CBCT calls this very chain as its own upstream. The matrices are written out in §4.5.

4.5 The orientation, written out

Everything above is prose about code. Here is the same thing as arithmetic, because two of ASO’s choices only become visible once they are written down. Notation: p→A is landmark A on the scan being oriented, q→A the same landmark on the gold.

1. Translation onto the first landmark: computed, then thrown away. The volume is never translated: the first module already centred it on the origin.

t→=q→A−p→A

2. First rotation. Read the bars carefully: they are a component-wise absolute value, not a norm. Both vectors are folded into the positive octant before the angle is taken, so what follows is the angle between the folded vectors, which is not the angle between the actual vectors. In the code the two vectors are first divided by their largest component, a positive scaling that cancels.

3. Second rotation. Its axis is not a cross product but the vector the previous step just aligned: a roll about that axis, with an angle from a third landmark.

4. The rotation matrix is the quaternion-based Rodrigues formula, identical to the one in FlexReg and ASO_IOS. Two sign flips cancel: the vector part carries a minus, and the matrix is written transposed relative to the usual quaternion form. The result is the ordinary rotation of the angle about the axis.

The matrix, written out from those four numbers:

R=[α2+β2−γ2−δ22(βγ+αδ)2(βδ−αγ)2(βγ−αδ)α2+γ2−β2−δ22(γδ+αβ)2(βδ+αγ)2(γδ−αβ)α2+δ2−β2−γ2]

5. Composition. The ICP contributes a rotation only: its translation column is zeroed. The composite is therefore a pure rotation about the world origin.

M=RicpR2R1 (Ricp[0:3,3]=0)

Why this is not a fit. With N paired landmarks there is a closed-form rotation that minimises the sum of squared distances, Kabsch, by the singular value decomposition of the cross-covariance:

H=∑k(p→k−p→¯)(q→k−q→¯)⊤
H=UΣV⊤
R=VDU⊤

with D = diag(1, 1, det(V U⊤)) guarding against a reflection. ASO computes nothing of the sort. It builds two rotations from a triplet, keeps the triplet that happens to score best over up to 2500 draws, and hands the result to an ICP that re-pairs the points by nearest neighbour rather than by label. It is a search, not a solution, which is exactly why the numbers in the viewer above show the ICP doing more of the turning than the initialisation it is supposed to refine. In VISOR the triplet search is exhaustive when there are few enough, otherwise seeded.

5. ASO_IOS

5.1 Automatic mode: crown centroids

a) Segmentation bypass. Each mesh is opened and looked at for a tooth-label array. Already-segmented meshes skip the network; the others go to the segmentation. b) The segmentation predicted, through conda: a multi-view network that numbers the teeth in the universal 1–32 scheme. ASO does not overwrite the input mesh: the segmented copy lands in a temporary folder. The step is synchronous and blocking.

c) The orientation computed, the core. The 3 or 4 chosen teeth are sorted into left, middle(s) and right using the universal numbering; each tooth becomes the mean of the vertices carrying its label; with 4 teeth the two middle centroids are averaged, so it always comes back to three points.

No scaling. d) The refinement. The ICP only ever sees these 3 or 4 centroids, never the crown geometry: the same initialisation as in CBCT (with absolute values and a roll), then a rigid ICP with 100 iterations instead of 1000, whose translation is not zeroed out. The final matrix is the ICP composed after the jaw alignment.

In the codeSegmentation bypass, the conda call, PrePreAso, the ICP chain

5.2 Semi mode: supplied landmarks computed

Same machinery: the landmark dictionaries are filtered by name, then the initialisation and the ICP run on the named landmarks alone, with no segmentation and no jaw alignment. Landmark names are built in the interface as tooth by type (occlusal, or cervical), and split by arch from their first letter. The matrix obtained from the landmarks is then applied to the whole mesh.

In the codeSelectKey and landmark names

The ASO_IOS chain, step by step

an intra-oral scan: a surface mesh, no volume

Automatic mode: crown centroids

  1. __BypassCrownseg__ looks for a PredictedID, UniversalID or Universal_ID array: an already-segmented mesh skips the network copied as <name>_Seg
  2. DentalModelSeg labels the crowns, through conda run -n shapeaxi predicted <name>_Seg.vtk, in a temporary folder
  3. the centroid of each labelled crown becomes a landmark computed one point per tooth
  4. PRE_ASO_IOS then a rigid ICP onto the gold standard’s centroids computed the oriented mesh + its .tfm

Semi mode: supplied landmarks

  1. SelectKey filters the landmark dictionaries by name, then InitIcp and vtkICP run on those names alone: no segmentation, no PrePreAso computed same .tfm

Unlike FlexReg, ASO does not overwrite the input mesh: overwrite = "0" and suffix = "Seg", so the segmentation lands in a temporary folder.

5.3 Occlusion

A checkbox forces a single arch: the chosen arch drives the orientation, and the same matrix is applied to the opposite arch to preserve the occlusal relationship. Upper and lower files are paired by name, from a few recognised markers. When no marker is found, the legacy silently treats the file as lower; VISOR refuses it.

The transform is written inverted (ITK’s fixed-to-moving convention), as an affine transform, with no LPS-RAS conversion: meshes are read and written in the file’s own coordinates. This is consistent end to end with AREG_IOS, which reads it back as it is. VISOR keeps the convention and changes the file name.

6. Comparison with FlexReg’s orientation

FlexReg’s orientation and ASO_IOS’s jaw alignment are the same algorithm, copy-pasted. They differ on three points:

ASO_IOSFlexReg
Targetthe gold mesh’s centroidsthree hard-coded points
Teeth3 or 4 chosen by the operator3, 5, 12, 14 hard-coded (UR6, UR4, UL4, UL6)
Returnthe mesh and the matrixthe mesh alone

Practical consequence: FlexReg produces a canonical and reproducible frame (occlusal plane near z = 0, +y anterior), which lets it reason in 2D within the XY plane. ASO_IOS produces an orientation relative to a reference patient: no guarantee that the occlusal plane lands on z = 0, and FlexReg has no ICP refinement where ASO adds one.

7. What is predicted vs. what is computed

BlockNature
CBCT recenteringgeometric a translation
CBCT landmarks (auto mode)network multi-scale search agents, ALI_CBCT
Pruning outlier landmarksgeometric distances and angles
Optimal triplet and rotationsgeometric random search, up to 2500 draws
Refinementgeometric rigid ICP
IOS crown segmentationnetwork multi-view, DentalModelSeg
Tooth centroidsgeometric vertex averaging
IOS orientationgeometric two rotations and a translation

The two networks that are called are pre-trained and only serve to supply anchor points. ASO_CBCT’s learned pre-orienter has been disconnected.

8. Environment

Two distinct regimes. The command-line modules run in Slicer’s Python, which the widget fills with whatever is missing (itk, torch, pytorch_lightning, dicom2nifti, pydicom, monai). The conda environment (Python 3.12, shared with ALI, AREG, FlexReg and DOCShapeAXI) is only set up for the automatic IOS mode. No GPU is required by ASO itself; it is required by the crown segmentation. In VISOR nothing is installed in Slicer and the ASO environment has no torch.

9. Pitfalls and fragile points

Each point is checked in the code and described, with its evidence, on the code page.

  • The semi mode has no recentering, so an off-centre volume ends up outside its own field of view (and the old transform-file requirement is fixed). Evidence.
  • The landmark merge deletes files in the input folder. Evidence.
  • The DICOM fallback is broken. Evidence.
  • The coordinate system of landmark files is never checked. Evidence.
  • Inconsistent minimum landmark count (3 in the interface, 4 in practice). Evidence.
  • Nothing is rewritten if the output exists. Evidence.
  • Patient identifiers diverge between ASO and AREG, so ASO’s transform is never found for some names. Evidence.
  • A mesh with no jaw marker is silently treated as lower. Evidence.
  • Libraries installed for nothing, at the risk of overwriting another module’s torch. Evidence; pytorch3d wheels.
  • The ICP re-pairs by nearest neighbour, and the initialisation folds vectors with absolute values: nothing should be concluded from the geometry of that step in isolation. Why this is not a fit.
  • Dead code, a non-inverted transform file and time-point suffixes (only _T1 and _T2 are cut) are listed on the code page.

10. Literature

The reference paper for ASO_CBCT is Automated Orientation and Registration of Cone-Beam Computed Tomography Scans (Anchling, Hutin, Cevidanes et al., Lecture Notes in Computer Science, 2023). Its description matches the code: ALI_CBCT identifies the landmarks regardless of the input orientation, then the orientation is obtained “by first aligning 3 randomly chosen landmarks, then refining with ICP.” Reported errors: under 3° and 2 mm against experts. The paper does not mention the pre-orientation network, consistent with the fact that it is no longer connected.

For ALI_CBCT itself: Automatic landmark identification in cone-beam computed tomography (Gillot et al., Orthodontics & Craniofacial Research, 2023).

ASO_IOS has no paper of its own. The closest published text is AReg IOS: Automatic Registration on IntraOral Scans (Hutin, Anchling, Cevidanes et al., LNCS 2023), which describes the initial alignment by shared tooth centroids, that is, exactly the jaw alignment. The rest (tooth selection by the operator, ICP refinement on 3 centroids, occlusion mode) is unpublished internal development.
