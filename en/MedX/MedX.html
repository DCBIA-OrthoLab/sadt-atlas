MedX

Extraction of TMD clinical indicators from free-text notes by a locally run language model (a fine-tuned BART-large-CNN), then aggregation of the cohort into a single figure panel — text from end to end; no medical image ever enters this module, whatever its name might suggest.

Gaydamour 2025 · CLIP, LNCS medx_summarize medx_dashboard conda env: summaries Bibliography

1. Where it sits in the chain

MedX is self-contained in both directions: nothing in the repository calls it, and it calls no other module in the repository. Grepping for MedX outside MedX/ and MedX_CLI/ turns up only the table of contents in README.md and the root CMakeLists.txt.

Two independent paths, two tabs, two CLIs:

PathButtonExecutable calledWhere
SummarizationSummarizeButtonpython -m MedX_Summarizeconda run -n summaries
DashboardDashboardButtonslicer.modules.medx_dashboardSlicer's Python, via slicer.cli.run

The Dashboard path consumes the output of the Summarization path (a folder of .txt files), but nothing chains them together: the operator reruns it by hand.

Note

No network call to an LLM. No endpoint, no API key, no ollama, no openai — verified by grepping the whole of MedX/ and MedX_CLI/. The only outbound traffic is downloading the weights from a GitHub release.

An important asymmetry: summarization does not go through slicer.cli.run. onSummarizeButton (MedX.py:845) builds the list_Processes_Parameters like the other modules do, but ignores the "Process" entry and calls run_conda_tool() (MedX.py:1079), which assembles conda run -n summaries python -m MedX_Summarize <positional args>. The Slicer CLI MedX_Summarize declared in MedX_Summarize.xml therefore only serves to get the file installed in the right place and to give it a slicer.modules.medx_summarize — it is never actually run as a Slicer CLI.

The dashboard, on the other hand, does go through slicer.cli.run (MedX.py:938): it runs in Slicer's Python and therefore requires pandas, matplotlib and numpy<2.0.0 inside Slicer, installed by install_function() (MedX.py:89) after confirmation.

No GPU required: the summarization CLI takes cuda if it's there (MedX_Summarize.py:32), otherwise CPU.

3. Inputs and preprocessing

3.1 Grouping by patient

process_notes() (MedX_Summarize.py:67) walks the folder non-recursively (os.listdir, no recursion), keeps only .pdf, .docx, .txt, and groups by file_name.split("_")[0]. Everything before the first underscore is the patient identifier; several notes from the same patient are concatenated into a single text before inference.

The progress bar's count, however, uses Method.search(), which is recursive (glob.iglob(..., recursive=True), Method.py:115). On a tree with subfolders, the denominator counts more files than the CLI actually processes.

Pitfall

The progress count (recursive) and the actual processing (non-recursive) don't operate on the same set of files: with subfolders, the bar never reaches 100%.

3.3 Chunking — the most carefully engineered part

split_text_by_paragraphs() (utils.py:83) then create_chunks_from_paragraphs() (utils.py:128).

Four section headers are hardcoded:

section_headers = ["CLINICAL EXAMINATION", "CLINICAL EVALUATION",
                   "RADIOGRAPHIC EXAMINATION", "RADIOGRAPHIC EVALUATION"]

Rules, in order:

  1. split on a double line break, the start of a numbered list (\n(?=\d+\.\s)), a bullet (-, *), or a section header;
  2. a paragraph under 150 characters is merged back into the previous one (list items stay with their heading);
  3. a whole section (header + the paragraphs that follow up to the next header) is treated as an indivisible block for as long as it fits in the chunk: this is the chunking invariant — a clinical section must not be split across two prompts;
  4. if it doesn't fit, fall back to paragraph by paragraph, then sentence by sentence (re.split(r'(?<=[.!?])\s+')).

Chunk size: 3500 characters, passed in by generate_combined_summary (MedX_Summarize.py:29) — the default value of create_chunks_from_paragraphs (1800) is never used. 3500 characters ≈ 900 BPE tokens, under the model's 1024 limit, but the tokenization is truncated to max_length=1024 regardless.

4. The model

4.1 What actually gets loaded

load_model_and_tokenizer() (utils.py:22):

tokenizer = BartTokenizer.from_pretrained(model_path)
model = BartForConditionalGeneration.from_pretrained(model_path)

Nothing else. No peft, no quantization, despite peft and bitsandbytes being listed among the packages installed in the environment (MedX.py:849) — those two, plus evaluate and scikit-learn, are leftovers from training.

4.2 The weights

URL: https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/MedX/BART.zip (summarize.py:43), 1.51 GB.

The archive contains a standard Hugging Face folder: config.json, generation_config.json, model.safetensors (1.63 GB uncompressed, fp32), merges.txt, vocab.json, special_tokens_map.json, tokenizer_config.json.

The config.json (read from inside the archive) gives the exact architecture:

So this is a fine-tune of BART-large-CNN (~406M parameters), not a model trained from scratch — identified directly from the config.json shipped inside the weights archive, not from the documentation.

The task_specific_params.summarization inherited from the original (max_length=142, min_length=56) is entirely overridden at generation time.

The configuration file still carries _num_labels: 3 and LABEL_0..2: a leftover from the upstream checkpoint, with no effect on BartForConditionalGeneration.

Pitfall

Beam search and sampling at the same time (num_beams=4 + do_sample=True) → transformers falls back to beam sample: the output is not deterministic, two runs on the same note don't produce the same summary. No seed is set.

BART is not an instruction-tuned model: the instruction sentence is simply prefixed to the source text. It only has an effect if the fine-tune was done with that same prefix — something that can't be verified from the repository.

What the network literally produces: free text, a sequence decoded via tokenizer.decode(..., skip_special_tokens=True). The key: value format is never enforced or checked at this stage; it's a learned property, not a guarantee. The chunk summaries are concatenated with a line of 100 dashes.

There is no validation pass on the key/value pair on the CLI side: extract_key_value_pairs() and save_dict_to_csv() (utils.py:227) are dead code, never imported (the __init__.py doesn't re-export them).

5. The algorithmic core — the dashboard

No learning here, just parsing and matplotlib.

5.1 Text summary → DataFrame

read_summaries() (display_figure.py:33) only reads files ending in _summary.txt, key = split("_")[0].

initialize_key_value_summary() (dashboard_utils.py:343) creates a dict of 56 keys, all typed str, all initialized to "": patient_age, headache_intensity, disc_displacement, muscle_pain_score, sleep_disorder_type, cpap_used, pain_onset_date… This is the module's target schema, and the only place in the repository where it's written down.

update_dictionary() (display_figure.py:69) walks the summary line by line, line.split(":") — a line that doesn't yield exactly two pieces is skipped (so any value containing a : is lost). ; characters in the value become ,. A key outside the 56 is ignored.

Merging successive values (the same field recurring across several chunks) is the subtle part:

  • empty existing value → replaced;
  • value already present → nothing happens;
  • an existing value that is a substring of the new one is replaced by the new one (the more detailed wording is kept);
  • otherwise the new value is appended, separated by " | ", unless it's already contained in an existing piece.

The boolean branch (if current_value in {"True", "False"}) is dead: values are initialized to "" and the model writes true/false in lowercase, as shown by the sample CSV dashboard_full_dataframe.csv.

process_summaries() then converts 6 fields to numeric via extract_numbers(): patient_age, headache_intensity, average_daily_pain_intensity, diet_score, tmj_pain_rating, disability_rating. The rule: if there's a /, take the number before the first / ("7/10" → 7); otherwise the average of every number found ("8-9" → 8.5, hence the 9.5 and 41.0 in the sample CSV).

5.2 The aggregators

One per panel, all in dashboard_utils.py, all regex over free text:

Two underlying fragilities in these aggregators:

  • set_upper_donuts_data compares df[metric] == "true" (lowercase) but set_disc_displacement_data and set_muscle_pain_data apply .lower() first. A model that wrote True would silently drop the donuts to 0%.
  • Percentages are always divided by len(df), never by the number of filled-in values: a missing field counts as a negative.
Confirmed bug

set_upper_donuts_data tests the lowercase "true" while other aggregators normalize with .lower() before comparing: a case inconsistency confirmed in the code, which silently drops all six donuts to 0% if the model writes True/False capitalized.

set_migraine_data contains an unreachable return after the first one (dashboard_utils.py:81): an older 5-category version, left in place.

Confirmed bug

set_migraine_data (dashboard_utils.py:81) contains a second return, placed after an unconditional first return: dead code, never executed, a leftover from a 5-category version.

set_disc_displacement_data is called (display_figure.py:208) but its two results are never plotted: a dead computation.

5.3 The figure

generate_dashboard_figure(): figsize=(22,14), a 2×2 gridspec (width_ratios=[3,1.5], height_ratios=[1,1.5]), split into panels: age / sleep disorder / tenderness pie charts top left, six donuts on the right, bar charts of clinical scores ± SD and maximum opening at the bottom, then muscle pain distribution, joint pain areas, and age crossed with how long the pain has lasted.

A curiosity worth knowing before touching this (display_figure.py:179): the function receives output_folder as an argument, then reads it back by introspecting its own frame (inspect.getargvalues) to reassign it to itself. It's a no-op; the parameter alone was enough.

9. Pitfalls and fragile points

Pitfall

The Download button downloads nothing. setup() creates <Documents>/SlicerDownloads/MedX (MedX.py:394), then downloadModel calls DownloadUnzip(directory=SlicerDownloadPath, folder_name=SlicerDownloadPath). os.path.join with an absolute path makes that path absolute, so out_path = the folder already created, and the if not os.path.exists(out_path) (MedX.py:770) skips the whole block. Result: a "Folder must have model for" warning and an empty lineEdit. You have to fetch BART.zip by hand.

Confirmed bug

The result of the environment check is ignored. check_env = self.onCheckRequirements(list_libs) and then check_env is never read again (MedX.py:860): summarization starts even if conda isn't configured.

Confirmed bug

The dashboard's progress bar never moves. MedX_Dashboard.py receives log_path and never writes to it. DisplayMedX.isProgress waits for that file to change.

Confirmed bug

OnEndProcess divides by self.nb_scans (MedX.py:1289): ZeroDivisionError on an empty input folder.

  • Non-deterministic generation (do_sample=True + beams, no seed): two runs give two summaries, hence two dashboards.
  • Everything rests on split("_")[0]. A file BLANC_Jean_2021.pdf and a file BLANC_2022.docx are the same patient; 2021-05-12_B082.pdf has 2021-05-12 as its identifier.
  • Values containing a : are lost during parsing (len(key_value) != 2).
  • Hardcoded paths from a development machine at the top of dashboard_utils.py:18 and of display_figure.py: they mention a Qwen1.5B_full_V3/predictions_500 folder. The summaries used to develop the dashboard — and the 500-row dashboard_full_dataframe.csv checked into the repository — were therefore produced by a Qwen 1.5B, not by the distributed BART. The two output formats are assumed to be interchangeable; nothing guarantees that.
  • Dead code: extract_key_value_pairs, save_dict_to_csv, MedX_Summarize.xml as a Slicer CLI, set_disc_displacement_data (computed, never plotted), registerSampleData (points at the sample volumes from the Slicer template), MedXLogic.process() (pass), updateParameterNodeFromGUI (references self.ui.inputSelector, absent from the .ui), saveOutput, UpdateTime, UpdateProgressBar (which displays "Matrix applied with success", copied from another module).
  • peft and bitsandbytes are installed in the environment and never imported: ~2GB of unused dependencies.

10. Literature

The corresponding paper is AI-Driven Multimodal TMJ Patient Modeling: From Unstructured Notes to Precision Treatment (2025, Springer LNCS). It describes fine-tuning BART and DeepSeek-R1 on 1,813 annotated segments drawn from 500 TMD records, to extract 56 clinical indicators — the exact number of keys in initialize_key_value_summary() — and feed a patient and cohort dashboard. The paper concludes that BART beats DeepSeek on field-extraction accuracy despite a slightly lower ROUGE score; that's consistent with the module shipping a BART.

Gaps between the paper and the repository's code:

  • the paper places summarization within a multimodal framework (registered MRI and CBCT); none of that is in MedX, which only reads text;
  • the development comments point to a Qwen 1.5B, a third model not mentioned in the paper's abstract;
  • the paper's metrics can't be reproduced by any script in the repository (evaluate and scikit-learn are installed but unused).
