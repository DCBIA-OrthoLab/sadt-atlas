MedX

Extraction of TMD clinical indicators from free-text notes by a locally run language model (a fine-tuned BART-large-CNN), then aggregation of the cohort into a single figure panel: text from end to end; no medical image ever enters this module, whatever its name might suggest. This page explains the pipeline step by step; the code details are on the code page.

Gaydamour 2025 · CLIP, LNCS medx_summarize medx_dashboard conda env: summaries Bibliography VISOR: not ported, module removed Code (developers) Guide

MedX is no longer in the legacy tree: it was removed on 2026-09-17 (commit 34d496f) and kept on the branch archive/medx, whose last commit is fbfa0fb. Everything below describes that archived code; its build had already been switched off on 2026-03-18, when it was replaced by CNE. There is no VISOR port; what is left of MedX in VISOR is a stub.

Overview: what goes in, what comes out

Path 1: summarisePath 2: dashboard
Inputa folder of clinical notes (.pdf, .docx, .txt); notes of one patient share the part of the name before the first underscorethe folder of summaries written by path 1
What happenseach patient’s notes are cut into chunks and a fine-tuned BART model writes field: value lines for each chunkthe lines are parsed into 56 fields per patient, counted over the cohort and drawn
Outputone <patient>_summary.txt per patientdashboard.png and two CSV tables

No image enters the module, whatever its name suggests.

1. Where it sits in the chain

MedX is self-contained: no other module calls it and it calls no other module (the Agent’s tool catalogue lists the two jobs, but only as a description). The two paths are independent, each with its own button and its own job. The dashboard reads what the summariser wrote, but nothing chains them: the operator reruns the dashboard by hand. Neither path calls a language model over the network; the only outbound traffic is downloading the weights from a GitHub release.

In the codeThe two jobs, how each is launched, the no-network check

2. Files involved

A widget with a dark stylesheet and the conda handling, two small method files, the summariser job with its helper module (reading, chunking, model loading), and the dashboard job with a parsing and figure file and a file of aggregation functions. The summariser runs in a conda environment of its own, the dashboard in Slicer’s Python. A GPU is used if present and not required.

In the codeFile table, the conda launch and the CLI that is never run

3. Inputs and preprocessing

Three steps turn a folder of notes into pieces the model can read: group by patient, extract text, cut into chunks.

3.1 Grouping by patient

The folder is read without descending into sub-folders. Everything before the first underscore in a file name is the patient identifier, and the notes of one patient are concatenated into one text before the model sees them. The progress bar, however, divides the number of patients finished by the number of files it finds in all sub-folders, so as soon as a patient has more than one note, or there are sub-folders, it cannot reach 100 %. Notes of one patient are joined with nothing between them.

In the codeThe grouping code and the progress mismatch

3.2 Text extraction

A PDF gives the text of its pages, a Word file gives its paragraphs, a text file is read as it is. The only cleaning rewrites two characters: the curly apostrophe and the en dash become plain ones.

In the codeThe extractors and the cleaning function

3.3 Chunking: the most carefully engineered part

The text is first split into paragraphs: at a blank line, at the start of a numbered or bulleted item, and at four section headers (clinical examination, clinical evaluation, radiographic examination, radiographic evaluation), which are cut out only when they are written in capitals. The pieces are then glued back together by two rules. A numbered or bulleted item always sticks to the piece before it. A paragraph under 150 characters swallows the piece that comes after it, so a short heading takes the text under it, and a short paragraph is joined to what follows, not to what came before. A section header always starts a new paragraph.

When a section is too big for one chunk it is cut paragraph by paragraph, and a paragraph that is still too big is cut sentence by sentence. An ordinary paragraph that does not fit in what is left of the chunk is cut sentence by sentence straight away. 3,500 characters is roughly 850 to 950 tokens (an estimate made on the CNE test notes, not a measurement with the real tokenizer), plus about 20 for the instruction sentence, so under the model’s limit of 1,024; anything beyond that limit is cut off without a warning.

In the codeThe two chunking functions, the regular expressions and the size arguments

4. The model

4.1 What actually gets loaded

The model and its tokeniser are loaded with the standard library calls and nothing else: no adapter and no quantisation, although the environment installs packages for both (leftovers from training).

In the codeThe loading lines and the unused packages

4.2 The weights

The weights are a 1.51 GB archive from a GitHub release. Its configuration shows a fine-tune of facebook/bart-large-cnn, an encoder and decoder of 12 layers each (about 406 million parameters, from the size of the weights file), able to read at most 1,024 positions, not a model trained from scratch. The download button of the widget does not actually download anything; the archive has to be fetched by hand (details).

In the codeThe archive contents and the configuration fields

4.3 The prompt and generation

For each chunk, one sentence is placed in front of the text: “Using the following note, extract structured key-value pairs about the patient’s symptoms and diagnoses”. BART is not an instruction-following model, so the sentence only helps if the fine-tuning used the same prefix, which cannot be checked from the repository. The model then writes free text: the field: value format is a learned habit, never checked here.

Generation combines beam search with four beams and random sampling, which makes the output different on every run (no seed is set). The summaries of a patient’s chunks are joined with a line of 100 dashes.

In the codeThe prompt, the full generation table and the dead extraction helpers

5. The algorithmic core: the dashboard

No learning here: text parsing, counting and drawing.

5.1 Text summary to table

The dashboard reads the files ending in _summary.txt. A dictionary of 56 fields, all empty text at the start (the headache intensity, the disc displacement, the sleep disorder, whether a CPAP is used, and so on), is the module’s target schema, and the only place it is written down. Each line of a summary is cut at its colon; a line that does not give exactly two pieces is skipped, so a value that itself contains a colon is lost, and a field outside the 56 is ignored.

In the codeThe parsing and merging code, the six numeric fields and the dead boolean branch

5.2 The aggregators

Each panel has one function, all of them pattern matching on free text followed by a count: age groups (labelled 12 to 19, 20 to 40 and over 40), sleep disorder or not, tenderness, mean and spread of five pain scores, maximum mouth opening read from strings like “33 mm” (or from any bare number), where headaches and joint pain are located (by lists of synonyms), six yes or no symptoms, five levels of muscle pain, and months since onset read from phrases like “1 year and 9 months ago”.

The other panels follow their own rules. The sleep pie counts every value except “unknown”, an empty field included, as a sleep disorder. The tenderness pie puts a patient in the “unknown” slice when none of the three fields is positive and they are not all “false”. The score bars and the mouth-opening bars are means over the values that exist.

Two fragilities follow. Some functions compare the text to lowercase true while others lowercase it first, so a model writing True would silently zero five of the six yes or no donuts, the jaw one being the only one protected (details). And the disc displacement is computed but never drawn.

In the codeThe function table, the case bug and the dead computation

5.3 The figure

One large figure (22 by 14 inches) in a 2 by 2 grid: pie charts for age, sleep disorder and tenderness and two small donuts for migraine and headache at the top left, six donuts on the right, bar charts of scores with their spread, of maximum opening and of headache locations at the bottom left, then muscle pain, joint pain areas, and age against how long the pain has lasted at the bottom right.

In the codeThe grid specification and a self-assignment that does nothing

6. Post-processing and outputs

The summariser writes one text file per patient and a log file that holds the number of patients done. The dashboard writes dashboard.png, a 58-column table patient_data.csv (the 56 fields plus two helper columns the figure code adds), and the 56-column table dashboard_full_dataframe.csv, written before those two columns exist. If the box is ticked, the picture is loaded into Slicer as if it were a volume, in the red slice view, for lack of an image viewer.

In the codeThe file table, the two CSV files, the log path and the image-as-volume load

8. Environment

The summariser needs a conda environment of its own (Python 3.12) with the language-model and PDF packages; on Windows conda goes through WSL. The dashboard runs in Slicer’s Python and needs numpy below 2, pandas and matplotlib.

In the codePackage lists, the environment checks, the process-group kill

9. Known problems

  • The Download button downloads nothing; the weights must be fetched by hand (details).
  • The result of the environment check is ignored, so summarising starts even without conda (details).
  • The dashboard progress bar never moves (details), and an empty input folder causes a division by zero (details).
  • Generation is not reproducible: beam search and sampling together, no seed (details).
  • The patient is whatever comes before the first underscore, so two different patients, or one patient under two names, are easily mixed (all pitfalls).
  • Values containing a colon are lost at parsing (all pitfalls).
  • A comment in the dashboard code points to summaries from a Qwen 1.5B model, not to the BART the module ships (all pitfalls).
  • One of the aggregators is computed and never drawn, and four installed packages are never imported (all pitfalls).

10. Literature

The corresponding paper is AI-Driven Multimodal TMJ Patient Modeling: From Unstructured Notes to Precision Treatment (2025, Springer LNCS). It describes fine-tuning BART and DeepSeek-R1 on 1,813 annotated segments drawn from 500 TMD records, to extract 56 clinical indicators, the exact number of keys in initialize_key_value_summary(), and feed a patient and cohort dashboard. The paper concludes that BART beats DeepSeek on field-extraction accuracy despite a slightly lower ROUGE score; that's consistent with the module shipping a BART.

Gaps between the paper and the repository's code:

  • the paper places summarization within a multimodal framework (registered MRI and CBCT); none of that is in MedX, which only reads text;
  • the development comments point to a Qwen 1.5B, a third model not mentioned in the paper's abstract;
  • the paper's metrics can't be reproduced by any script in the repository (evaluate and scikit-learn are installed but unused).
