MedX, legacy: the code

For developers: what the archived MedX code does (branch archive/medx at fbfa0fb), with file:line references (all checked against that commit), code blocks, parameters, environment and confirmed bugs. The readable explanation of the same pipeline, with the small calculations it contains, is on the atlas page.

Gaydamour 2025 · CLIP, LNCS medx_summarize medx_dashboard conda env: summaries Bibliography VISOR: not ported, module removed Code Atlas (explanation) Guide
Two code bases

MedX is no longer in the legacy tree either. It was removed on 2026-09-17 (commit 34d496f, "Drop MedX and SurgMovPred, kept on archive branches"), so SlicerAutomatedDentalTools at 3c67957 (2026-10-26) has no MedX/ folder. Everything numbered below describes the code kept on the branch archive/medx, whose last commit is fbfa0fb (2026-09-17): every file:line on this page was checked against that commit. (Earlier, at b1ae78c of 2026-05-26, the files were longer: MedX.py had 1552 lines there against 1282 here, because the dark stylesheet and the conda helpers now live in ADTLib.) The build had already been switched off on 2026-03-18 (af2e894, "Deactivate MedX"): both add_subdirectory lines are commented out in the root CMakeLists.txt (lines 44-46, under the remark "Replaced by CNE"). There is no VISOR port: no server tool and no client module. See what is left of MedX in VISOR.

1. Where it sits in the chain

Plain-language explanation and maths: atlas page.

MedX is self-contained in both directions: no module in the repository calls it, and it calls no other module (apart from the shared ADTLib: logging, theming, conda helpers, and the search function). Grepping for MedX outside MedX/ and MedX_CLI/ at fbfa0fb turns up: the table of contents and the module section of README.md; the commented-out lines of the root CMakeLists.txt (44-46); two catalogue entries, medx_dashboard and medx_summarize, in Agent_CLI/manifest.yaml (lines 491 and 509); and comments in four ADTLib files and one test (ADT/ADTLib/env/deps.py:9, format.py:21, method.py:7,13, ADT/Testing/Python/test_deps.py:34). The two Agent entries only describe the tools to the Agent, and they do not match the real command lines: the dashboard entry has no log_path argument, input_model of the summarizer defaults to t5-base while the CLI takes a folder of BART weights, and the dashboard is described as producing HTML while the code writes a PNG.

Two independent paths, two tabs, two CLIs:

An important asymmetry: summarization does not go through slicer.cli.run. onSummarizeButton (MedX.py:636) builds the list_Processes_Parameters like the other modules do, but ignores the "Process" entry and calls run_conda_tool() (called at MedX.py:686, defined at :870), which assembles conda run -n summaries python -m MedX_Summarize <positional args> (:874). condaRunCommand (:1192) then prefixes <conda> run -n summaries once more on Linux and macOS (:1219-1221), so the string given to the shell holds conda run twice (read from the code, not run). No GPU required: the summarization CLI takes cuda if it's there (MedX_Summarize.py:37), otherwise CPU.

3.1 Grouping by patient

Plain-language explanation and maths: atlas page.

process_notes() (MedX_Summarize.py:72) walks the folder non-recursively (os.listdir, line 75, no recursion), keeps only .pdf, .docx, .txt (:76), and groups by file_name.split("_")[0] (:78). Everything before the first underscore is the patient identifier; several notes from the same patient are concatenated into a single text before inference (combined_text +=, :89-94), with no separator added between them.

The progress bar's count, however, comes from NumberScan (MedX_Method/summarize.py:26-29), which calls search(): ADTMethod.search (ADT/ADTLib/method.py:66) delegates to ADTLib/io/fs.py:27, which is recursive (glob.iglob(..., recursive=True), fs.py:51). On a tree with subfolders, the denominator counts more files than the CLI actually processes. And its unit is the file, while the number the CLI writes to the log is the number of patients finished (log_f.write(str(idx + 1)), MedX_Summarize.py:103-104).

3.3 Chunking: the most carefully engineered part

Plain-language explanation and maths: atlas page.

split_text_by_paragraphs() (utils.py:74) then create_chunks_from_paragraphs() (utils.py:119).

Four section headers are hardcoded (utils.py:84 and again at :120):

section_headers = ["CLINICAL EXAMINATION", "CLINICAL EVALUATION",
                   "RADIOGRAPHIC EXAMINATION", "RADIOGRAPHIC EVALUATION"]

Rules, in order:

  1. split (utils.py:88) on a double line break, the start of a numbered list (\n(?=\d+\.\s)), a bullet (-, *), or a section header. This split is case-sensitive: only the headers written in capitals are cut out (the optional full stop after the header is dropped), whereas the section test of create_chunks_from_paragraphs compares in lower case (:151, :157);
  2. the pieces are glued back (utils.py:93-111). A piece that is exactly a header always opens a new paragraph, even after a short one. A piece that starts like a list item (^\d+\.\s|^[\-*]\s) is appended to the paragraph before it, whatever its size. And when the paragraph being built is under 150 characters, the next piece is appended to it (elif ... or (current_paragraph and len(current_paragraph) < 150), :104-106): the short paragraph absorbs the one that follows, it is not folded back into the previous one;
  3. a whole section (header + the paragraphs that follow up to the next header) is treated as an indivisible block for as long as it fits in the chunk (utils.py:151-165): this is the chunking invariant, a clinical section must not be split across two prompts;
  4. if a section doesn't fit, it goes to a fresh chunk when it is small enough on its own (:172-173); otherwise it is cut paragraph by paragraph (:176-184), then sentence by sentence (:186-194, re.split(r'(?<=[.!?])\s+') at :126). An ordinary paragraph that doesn't fit in what is left of the chunk skips the paragraph level and is poured in sentence by sentence straight away (:198-209).

Chunk size: 3500 characters, the default of generate_combined_summary (MedX_Summarize.py:34, passed on at :35); the default value of create_chunks_from_paragraphs (1800, utils.py:119) is never used. Every fit test is len(current) + len(block) + 1 <= max_chunk_size (utils.py:164,179,189,198,204), while what is appended is "\n\n" (two characters) after a paragraph or a section and one space after a sentence; the chunk is stripped when closed, and in a random test of the archived function (3,000 texts) the longest chunk had 3,499 characters.

3500 characters is roughly 850 to 950 BPE tokens, under the model's 1024 limit. This is an estimate, not a measurement with the real tokenizer: re-applying BART's byte-pair rules (vocab.json and merges.txt from BART.zip, the pre-tokenization pattern approximated) to the CNE test notes gives about 4.2 characters per token on the two TMJ notes and 3.7 on an Ortho note, and the instruction sentence adds about 20 tokens. The prompt is truncated to max_length=1024 regardless (MedX_Summarize.py:56), silently: the if ... shape[1] > model_max_tokens warning at :58-59 can never fire, since the tensor has just been capped at that length.

Archived code (archive/medx at fbfa0fb, removed from the legacy tree on 2026-09-17); not present in VISOR. No VISOR code exists for MedX to compare with: nothing under SADT-VISOR tools/ and no module in AutomatedDentalToolsRemote.

Beam search and sampling at the same time (num_beams=4 + do_sample=True) → transformers falls back to beam sample: the output is not deterministic, two runs on the same note don't produce the same summary. No seed is set.

BART is not an instruction-tuned model: the instruction sentence is simply prefixed to the source text. It only has an effect if the fine-tune was done with that same prefix: something that can't be verified from the repository.

What the network literally produces: free text, a sequence decoded via tokenizer.decode(..., skip_special_tokens=True). The key: value format is never enforced or checked at this stage; it's a learned property, not a guarantee. The chunk summaries are concatenated with a line of 100 dashes (MedX_Summarize.py:69).

There is no validation pass on the key/value pair on the CLI side: extract_key_value_pairs() (utils.py:218) and save_dict_to_csv() (:242) are dead code, never imported (the __init__.py doesn't re-export them).

5.1 Text summary → DataFrame

Plain-language explanation and maths: atlas page.

read_summaries() (display_figure.py:24) only reads files ending in _summary.txt (:36), key = split("_")[0] (:37).

initialize_key_value_summary() (dashboard_utils.py:333, the keys from :340) creates a dict of 56 keys, all typed str, all initialized to "": patient_age, headache_intensity, disc_displacement, muscle_pain_score, sleep_disorder_type, cpap_used, pain_onset_date… This is the module's target schema, and the only place in the repository where it's written down.

update_dictionary() (display_figure.py:60) walks the summary line by line, line.split(":") (:69-70): a line that doesn't yield exactly two pieces is skipped (so any value containing a : is lost). ; characters in the value become , (:74). A key outside the 56 is ignored (:80-81), and patient_id is never overwritten (:77-78).

Merging successive values (the same field recurring across several chunks) is the subtle part:

  • empty existing value → replaced (:94-96);
  • value equal to one of the stored pieces → nothing happens (:99-103);
  • a stored piece that is a substring of the new value is replaced by the new value (the more detailed wording is kept), and duplicates are removed (:106-120);
  • a new value that is itself contained in a stored piece is dropped (redundant, :123);
  • otherwise the new value is appended, separated by " | " (:126-129).

The boolean branch (if current_value in {"True", "False"}, :86-91) is dead: values are initialized to "" and the model writes true/false in lowercase, as shown by the sample CSV dashboard_full_dataframe.csv.

process_summaries() (:131) then converts 6 fields to numeric (:152-156) via extract_numbers() (:42-58): patient_age, headache_intensity, average_daily_pain_intensity, diet_score, tmj_pain_rating, disability_rating. The rule: if there's a /, take the number before the first / ("7/10" → 7); otherwise the average of every number found ("8-9" → 8.5, hence the 9.5 and 41.0 in the sample CSV).

Two underlying fragilities in these aggregators:

  • set_upper_donuts_data compares df[metric] == "true" (lowercase, dashboard_utils.py:168, :176-178) but set_disc_displacement_data, set_muscle_pain_data, set_tenderness_data and set_migraine_data apply .lower() first, and so does the jaw line of the same function (:172). A model that wrote True would silently drop five of the six donuts to 0%.
  • Most percentages are divided by len(df), never by the number of filled-in values: for the six donuts, the headache locations, the joint pain areas, the muscle pain levels, the migraine and headache donuts, a missing field counts as a negative. There are four exceptions: the age pie divides by the patients with a valid age (value_counts(normalize=True) drops the NaN, :16); in the sleep pie a missing field counts as a disorder (:21-35); in the tenderness pie it falls in the unknown slice unless another of the three fields is positive; and the score and opening bars are means over the values that exist.
Confirmed bug · archived code

Archived code (archive/medx at fbfa0fb, removed from the legacy tree on 2026-09-17); not present in VISOR. No VISOR code exists for MedX to compare with: nothing under SADT-VISOR tools/ and no module in AutomatedDentalToolsRemote.

set_upper_donuts_data tests the lowercase "true" (dashboard_utils.py:168, :176-178) while other aggregators normalize with .lower() before comparing: a case inconsistency confirmed in the code. If the model writes True/False capitalized, five of the six donuts (earache, tinnitus, vertigo, hearing loss, mental health) silently drop to 0%; only the jaw donut survives, because its line lowercases (:172). Checked by running the archived function on four patients all written True: 0% on those five, 100% on the jaw donut.

set_migraine_data (dashboard_utils.py:60-71) has a single return at fbfa0fb. An older state of the file (b1ae78c) still carried a second, unreachable return after the first one, a leftover from a 5-category version; it was removed before the archive's last commit.

set_disc_displacement_data is called (display_figure.py:199) but its two results are never plotted (nothing reads left_tmj_data or right_tmj_data afterwards): a dead computation.

10. Literature

Plain-language explanation and maths: atlas page.

The corresponding paper is AI-Driven Multimodal TMJ Patient Modeling: From Unstructured Notes to Precision Treatment (2025, Springer LNCS). It describes fine-tuning BART and DeepSeek-R1 on 1,813 annotated segments drawn from 500 TMD records, to extract 56 clinical indicators, the exact number of keys in initialize_key_value_summary(), and feed a patient and cohort dashboard. The paper concludes that BART beats DeepSeek on field-extraction accuracy despite a slightly lower ROUGE score; that's consistent with the module shipping a BART.

Gaps between the paper and the repository's code:

  • the paper places summarization within a multimodal framework (registered MRI and CBCT); none of that is in MedX, which only reads text;
  • the development comments point to a Qwen 1.5B, a third model not mentioned in the paper's abstract;
  • the paper's metrics can't be reproduced by any script in the repository (evaluate and scikit-learn are installed but unused).
