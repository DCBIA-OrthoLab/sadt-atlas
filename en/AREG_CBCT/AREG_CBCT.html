AREG_CBCT

AREG_CBCT puts a follow-up CBCT (T2) in the same position as the baseline CBCT (T1) of the same patient, using only a bone region that should not have changed: the cranial base, the mandible or the maxilla. It is plain elastix with mutual information and no network of its own; everything learned sits upstream, in the masks and the landmarks. This page explains the method step by step, with the maths; developers will find the code, with file and line references, on the code page.

Code (developers) Anchling 2023 · LNCS 14242 areg_cbct Slicer's Python: no conda, CPU only VISOR Bibliography

Everything on this page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, has its own page: AREG_CBCT on VISOR. Where the two differ, the difference is named in the text as “Legacy only” or “also true in VISOR”. The code, with file and line references, is on the code page.

Overview: what goes in, what comes out

A patient is scanned twice: at the start (T1, the baseline) and later (T2, the follow-up). To see what treatment or growth really changed, the two scans must be put in the same position. AREG_CBCT finds the rigid motion (a rotation and a translation, six numbers) that brings the T2 onto the T1, using only a bone region that should not have changed: the cranial base, the mandible or the maxilla.

What it takes and gives
Inputa T1 and a T2 CBCT of the same patient (.nii.gz, .nii, .nrrd, .gipl, or DICOM); in Semi-Automated mode, also the T1 masks
Methodthe T1 is masked to the chosen region, then elastix searches the six numbers of the motion by mutual information, from coarse to fine (section 5)
Outputfor each ticked region: the T2 moved onto the T1 (on the T2’s own grid) and its transform file (.tfm)
ModesSemi-Automated, Fully-Automated, Orientation & Registration (section 3)

The registration itself is plain elastix with no network: everything learned sits upstream, in the masks and the landmarks.

1. Where it sits in the pipeline

The AREG widget in Slicer drives three modalities (CBCT, IOS, and IOS on CBCT). It computes nothing itself: for each mode it builds a list of steps and runs them one after another, each step being a separate program. The CBCT mode calls, in order:

StepModesRole
Centre the T2 (and the T1 in Orientation mode)all 3a translation of the image centre; no network
ALI_CBCTOrientation onlyplaces 6 or 7 landmarks on the T1 predicted
Orientation of the T1Orientation onlyrigid ICP of those landmarks onto a gold standard computed
AMASSSFully-Automated, Orientationthe masks of the reference region on the T1 predicted
AREG_CBCTall 3the registration itself, once per ticked region computed
AMASSS againall 3, optionalfinal segmentations of the T1 and of the registered T2 predicted

Nothing in the repository calls AREG: it is a terminal tool. Its .tfm files are, however, reused by AutoMatrix and the analysis modules.

2. Files involved

The module is a Slicer widget (the form, the chaining of steps, the review pauses), a class per mode that builds the step lists, and a command-line program that does the registration in a separate process. Unlike the IOS path, nothing on the CBCT side goes through conda: the packages are installed into Slicer’s own Python. The registration needs no GPU; AMASSS does.

3. The three modes and the exact chain

The mode is chosen in the widget. All three share the same tail, centre the T2, register for each region, run the final AMASSS, and only differ upstream:

ModeUpstreamT1 masks
Semi-Automatednonesupplied by the operator (“T1 Masks” field)
Fully-AutomatednoneAMASSS predicts them, written into the input T1 folder predicted
Orientation & Registrationcentre the T1, ALI_CBCT, orient the T1AMASSS on the oriented T1 predicted

The reference region is an operator choice, not something inferred: the checkboxes Cranial Base, Mandible, Maxilla. Checking two regions launches two independent registrations, each with its own output folder.

The chain of the Orientation & Registration mode, step by step

T1 and T2: two CBCT of the same patient

Preparation: this mode only

  1. PRE_ASO recentres the T1: no network, a translation <T1 folder>Or
  2. ALI_CBCT places the orientation landmarks predicted landmarks of the T1
  3. SEMI_ASO orients the T1 onto the gold standard <T1 folder>Or

Segmentation: what the registration will be allowed to see

  1. AMASSS predicts CBMASK, MANDMASK, MAXMASK on the oriented T1 predicted <base>_seg_<STRUCT>.nii.gz, beside the scans

Registration: once per checked region

  1. centre the moving T2 T2_Center
  2. mask the fixed T1: elastix never sees anything outside fixed_image_masked
  3. one elastix pass: Mattes mutual information, 3 pyramid levels, 1500 iterations each a rigid transform
  4. MatrixRetrieval turns it into an Euler3DTransform <pat>_<REG>Reg_matrix.tfm
  5. resample the T2: on its own grid, not the T1’s Registered/<Region>/<pat>_OutReg/

Finish

  1. AMASSS runs again for the final segmentations, twice, on the input folder, then recursively on the output tree, with genVtk=True <Region>/<pat>_OutReg/

Steps 4 to 10 are the tail the three modes share. The other two differ only upstream: Fully-Automated skips 1–3 and lets AMASSS predict the masks on the T1 as supplied; Semi-Automated skips 1–4 entirely and takes the masks from the operator’s “T1 Masks” field. Checking two reference regions launches two independent registrations, each with its own output folder.

4. Inputs, pairing, preprocessing

Accepted formats are .nii.gz, .nii, .nrrd, .nrrd.gz, .gipl and .gipl.gz; a DICOM series is converted per patient into a NIfTI file written inside the input folder.

Pairing. A patient’s identifier is whatever remains of the file name after cutting a fixed list of markers (_Scan, _Or, _MAND, _CB, _lm, _T2, _T1 and a few more). A file whose name contains mask, seg or pred is taken as a segmentation, any other is a T1 or a T2 scan. The mask of a region is looked up by keyword in the name (cb, mand or md, max or mx), and the first file found wins: the lookup never checks that the file really is a mask, so a scan named P1_T1_MAX.nii.gz would be taken for the segmentation.

Centring the T2. Despite its name and the model folder it is given, this step uses no network. It computes the translation that puts the image centre at the origin, resamples the T2 and writes that translation as a .tfm next to the copy. The direction prediction by a network once existed and was removed.

Only the fixed image is masked. The T2 is read with no mask. The mask is applied to the T1 with a label if one is requested, otherwise every non-zero voxel of the mask is kept; in practice no label is ever requested, because that combo box is hidden.

5. The algorithmic core: the registration

Once the masks and the centred T2 exist, the registration is six steps: read the T2, mask the T1, run a single elastix pass, read its result, compose it, and resample the T2. The scene below replays them on a published test set; the cards after it explain what each step computes.

The library is itk-elastix, not SimpleITK or ANTs. On top of elastix’s default rigid map the code fixes: six degrees of freedom, Mattes mutual information on 64 bins, a conjugate-gradient optimiser (step from 2.0 down to 0.001, tolerances 1e-6), three resolution levels of up to 1500 iterations, a regular sampling grid with a single thread for determinism, automatic initialisation on the image centres and automatic scale estimation.

There is no coarse step any more. The “Include Approximation Step” checkbox goes all the way down and is never read: the pre-registration on the unmasked images was removed in September 2025. The only coarse-to-fine left is the three-level pyramid; the coarse pre-alignment is now done by the centring of the T2 and by elastix’s own initialisation.

Legacy only. Reading the elastix result, the module keeps the three angles and the translation but never the centre of rotation. The rebuilt transform therefore turns around the origin instead of around c. The two agree only when c is the origin or the rotation is the identity; in practice the volumes arrive close to the origin because the T2 is centred first and the T1 is oriented, so the gap stays small, but nothing guarantees it. The registered volume is rebuilt from that same matrix, so the file and the volume agree with each other and both drift together from what elastix optimised. VISOR fixes this (details).

The composition step multiplies rotations and adds translations; with one transform it is a plain copy, so that code is never exercised.

6. What runs upstream: exact arguments

AMASSS, for the masks. It is called on the T1 with the structures for the ticked regions (cranial base, mandible, maxilla masks) and writes one file per structure next to the scans. AMASSS is today an nnU-Net v2 with a separate model per group predicted. AMASSS, for the final segmentations, is called twice more, on the input folder and then recursively on the output tree, skipping its own outputs.

ALI_CBCT (Orientation mode only) places the landmarks the orientation needs. It works with multi-scale reinforcement-learning agents (1 mm then 0.3 mm); see ALI for how an agent walks to a landmark predicted. The list depends on the reference plane: N, S, Ba, RPo, LPo, LOr, ROr for the Frankfurt plane, or IF, ANS, PNS, UR1O, UR6O, UL6O for the occlusal one.

The orientation of the T1 is a rigid ICP of those landmarks onto a gold standard, after discarding outliers computed. The result is written into a folder next to the T1, with the suffix Or.

7. Outputs

For each region and patient, in the output folder: the registered T2 (16-bit integers, on the T2’s own grid) and its transform, in a subfolder per region and per patient. The suffix is concatenated to the name with no separator.

The .tfm is written in the ITK convention, so in LPS, and maps output space to input space; no flip is needed anywhere in the registration program. The only place that flips between RAS and LPS is the manual correction of a review pause. The centring transform written when the T2 is centred is not composed with the registration transform: to bring the original T2 back onto the T1, the two files must be chained by hand.

8. Review pauses and batch navigation

In “Review and manual adjustment” the operator ticks the steps after which the run should stop for a look. Five can be checked in the CBCT mode: the landmarks (editable, points can be moved and are rewritten), the oriented T1, the masks, the centred T2, the registration (adjustable: the registered scan is loaded on the T1 at half opacity and can be moved by hand), and the final segmentation of the T2. A manual correction is composed into the existing .tfm, so whatever uses it downstream still applies one matrix per patient.

The review covers the patients of the current run only, and for the registration it is scoped to one region, so a mandible adjustment never folds into the cranial base matrix. In the batch, the operator can go to the previous or next patient without advancing the run, flag a patient to redo, go back to the last correctable step (the intermediate steps are replayed only for the flagged patients, through links rather than copies of the scans), and finally move on to the next step, which logs how many patients were accepted without being opened.

10. Environment

Everything is installed into Slicer’s own Python the first time the button is clicked, after a confirmation dialog: the registration engine itself (itk-elastix), DICOM conversion, the deep-learning libraries AMASSS needs, and a few numerical packages. There is no conda. Versions are checked when the module starts. The registration alone runs on the CPU; AMASSS wants a GPU. The version numbers, and a note on how the GPU stack is chosen, are on the code page.

11. Traps and fragile spots

Each point is checked in the code and written up, with its evidence, on the code page; the list also appears in the findings.

  • A time point other than T1 or T2 pairs with nothing. A file ending in _T3 keeps that suffix in its patient id and the pair is silently dropped. The supported answer is to rename the inputs. Also true in VISOR, but there the orphan is reported. Evidence.
  • The centre of rotation of elastix is lost when the result is converted (legacy only, fixed in VISOR). Evidence, and a hypothesis on why results are nevertheless usually right.
  • The mask lookup is a keyword test. A scan whose name contains max can be taken for a mask. Legacy only. Evidence.
  • The masked image is written to one fixed file name in a temporary folder shared by the whole batch: harmless in sequence, fatal if the program were ever run in parallel. Legacy only. Evidence.
  • The approximation checkbox does nothing since September 2025 and is still ticked by default.
  • Output folders are created next to the inputs (centred T2, oriented T1) and reused on a second run, so modified inputs may be ignored; in Fully-Automated mode the masks are written into the input T1 folder, so at the registration pause every mask is loaded beside the scan.
  • DICOM input is only offered in Orientation mode, the opposite of what the code seems to intend.
  • A manually corrected .tfm becomes a composite transform, which a downstream consumer expecting a simple one may fail to read.
  • Dead code remains: several unused functions and arguments are listed on the code page.

12. Literature

The reference paper is Anchling, Hutin, Huang, Barone, Roberts, Miranda, Gurgel, Al Turkestani, Tinawi, Bianchi, Yatabe, Ruellas, Prieto, Cevidanes, "Automated Orientation and Registration of Cone-Beam Computed Tomography Scans," LNCS 14242, 2023, p. 43-58: Springer, PMC11104011. Reported accuracy: < 3° and < 2 mm against experts, under 5 min per case.

The code diverges from the paper on three verified points:

  1. the paper describes a two-stage registration: "VBR between the full images, then with the masked image as a refinement step," 10,000 iterations on the masked pass. The code now runs only one masked pass at 1500 iterations;
  2. the paper reports SimpleElastix; the code uses itk-elastix (itk.ElastixRegistrationMethod);
  3. the paper obtains its masks via AMASSS / UNETR MONAI; AMASSS is today an nnU-Net v2.

On the underlying question, voxel-based superimposition on the cranial base, the lab's historical reference is Cevidanes et al., Superimposition of 3D cone-beam CT models of orthognathic surgery patients (2005, PubMed 16227481).

Not to be confused with Accuracy and Reproducibility of Voxel Based Superimposition…, PLOS One 2011, which is not from the lab: it is by Nada, Maal, Kuijpers-Jagtman et al. (Radboud UMC, Nijmegen). It is an independent validation of the method, which gives it more weight, not less, but attributing it to the group would be a mistake.

Repositories: lucanchling/AREG, DCBIA-OrthoLab/SlicerAutomatedDentalTools. The review pauses and batch navigation are described in no publication: internal development.
