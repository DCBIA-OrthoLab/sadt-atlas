Agent — full pipeline

A natural-language assistant that picks a module from the extension, extracts its parameters, builds the command line, and launches it. No medical neural network is called here — the Agent only does routing and form-filling.

unpublished Agent_CLI Slicer Python qwen3:8b via Ollama cross-encoder MiniLM-L6 Bibliography

Everything runs locally: an 8B LLM served by Ollama, plus a small cross-encoder to preselect candidate tools.

1. Position in the chain

Nobody calls Agent. A grep for slicer.modules.agent turns up no caller outside the module itself. It is a terminal entry point.

Outbound, there are two levels:

CalledHowWhere
Agent_CLIslicer.cli.run(slicer.modules.agent_cli, ...) (Agent/Agent.py:798)separate CLI process, Slicer Python
the target module (ALI_CBCT.py, AMASSS_CLI.py, …)subprocess.run(cli_args) (Agent/Agent.py:962)child process of the widget, Slicer Python
Ollamapython client ollama, HTTP on 127.0.0.1:11434local server, launched/installed by the module

The inventory of targets is purely declarative: it lives in Agent_CLI/manifest.yaml, a YAML file with 23 scripts entries. The Agent discovers nothing on its own — it only knows this file.

Dead code

AgentLogic.process() (Agent.py:1315) reruns the CLI with only folders and prompt (missing modeagent and temp_folder, both required on the XML side) and reads GetOutputText() immediately after a wait=False. Never called. Agent_CLI/Resources/UI/Agent_CLI.ui is likewise inert: a CLI module does not load a .ui file.

No conda, no mandatory CUDA. The whole module runs inside Slicer's Python; the only GPU used is indirect, through the Ollama server.

3. The models

3.1 The LLM — qwen3:8b via Ollama

A single constant, duplicated at both ends: DEFAULT_MODEL = "qwen3:8b" (utils.py:21) and MODEL_NAME = "qwen3:8b" (Agent.py:18). get_router_model() honors a ROUTER_MODEL environment variable that lets you swap in any Ollama model without touching the code.

The same model serves all three calls: routing, parameter extraction, repair. No specialized model, no fine-tuning.

PointValueSource
Inference engineOllama (so llama.cpp underneath), local HTTP APIimport ollama, port 11434
Weight formatGGUF — imposed by Ollama, no transformers checkpointinferred from the engine
Downloadollama pull qwen3:8b from the ollama.com registryAgent.py:1266, and automatic fallback in chat_with_auto_pull
Size / quantizationdefault tag: 5.2 GB, Q4_K_M, 8.19 G parametersnot determinable from the repository: read on ollama.com/library/qwen3
CPU or GPUdecided by Ollama, not by the codesee below
Ollama installed via snap = CPU

The module never passes a device directive. The Ollama binary decides, and the code draws an explicit consequence from that: on Linux, an Ollama installed via snap is sandboxed, does not see the NVIDIA GPU, and falls back to CPU — 80–90 s per response for an 8B model, a figure measured and hardcoded in the code (Agent.py:1231). The module detects /snap/ in the binary's realpath and warns about it, without being able to fix it (the snap server already holds port 11434, and removing it needs sudo).

When no Ollama is found, install_official_ollama() (Agent.py:101) downloads the official portable archive into ~/.slicer_agent/ollama (overridable via SLICER_AGENT_HOME): ollama-linux-{amd64,arm64}.tgz, ollama-windows-{amd64,arm64}.zip, or Ollama-darwin.zip, extracted with ditto and then de-quarantined with xattr. These archives bundle the CUDA/Metal libraries, hence the deliberate choice not to use curl | sudo sh (no root password from the GUI) nor the snap package. LD_LIBRARY_PATH is pointed at <install>/lib/ollama so the binary finds its own libs (Agent.py:56).

Only two call settings, in chat_with_auto_pull (utils.py:96):

  • keep_alive="30m" instead of the 5-minute default, so as not to reload 5 GB into VRAM between two messages;
  • format="json" for the router, the extraction, and the repair (a grammar constraint on Ollama's side) — not for consultant mode.

No temperature, seed, num_ctx, or think is passed. Since qwen3 is a hybrid-reasoning model, consultant mode can therefore let reasoning text leak through depending on the Ollama version; the only post-processing is output.replace("*","").replace("#","") (Agent_CLI.py:215), which strips markdown by stripping the characters.

If the model is not present, chat_with_auto_pull intercepts the not found message, runs ollama.pull(model, stream=True) while printing progress, then replays the chat. Any other error is re-raised as-is.

3.2 The cross-encoder — ms-marco-MiniLM-L-6-v2

It is the only real network loaded in the process. CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") (utils.py:53), via sentence-transformers — so transformers/safetensors weights downloaded from the Hugging Face Hub and cached in ~/.cache/huggingface.

MiniLM, 6 layers, 22.7 M parameters, distilled from MiniLM-L12-H384-uncased, trained on MS MARCO Passage Ranking. It is not an embedding model: there are no vectors and no cosine similarity. The query and the document are concatenated and fed together into the transformer, which outputs a single unbounded relevance scalar (typically −10 to +10). The device is whichever one sentence-transformers picks on its own, based on the installed torch wheel.

The _cross_encoder_model cache serves no purpose in practice: Agent_CLI.py is a fresh process on every request, so the model gets reloaded on every message. The code comment admits as much.

Silent cross-encoder fallback

If loading fails, the fallback is blunt: scripts[:k], i.e. the first three tools in the manifest (ali_cbct, ali_ios, amasss_cli) regardless of the question (utils.py:90). The operator is not informed.

4. Routing

Two stages, and the LLM only steps in at the second one.

Stage 1 — cross-encoder preselection. cross_encoder_retrieve_candidates(manifest, prompt, k=3) builds one document per tool:

docs.append(f"{s['name']}: {s['description']} (tags: {tags})")
scores = model.predict([(user_text, doc) for doc in docs])
ranked = sorted(zip(scores, scripts), reverse=True)
return [s for _, s in ranked[:k]]

23 pairs scored, sorted in descending order, hardcoded top-3 (k=3 is never parameterized). The manifest's priority field (values 1 to 23) is never read — the line that would read it is commented out (utils.py:216). The right tool, if it ranked 4th, is permanently lost; the LLM will never see it.

Stage 2 — choice by the LLM. The system prompt (Agent_CLI.py:105):

You are a tool router. Output ONLY one JSON object.
Schema:
{"tool": string|null, "confidence": number, "reason": string}

Rules:
- Choose tool ONLY from the candidate list provided by the user message.
- If none match, set tool = null and confidence <= 0.4.
- Do not invent tool names.
- Keep reason short (max 1 sentence).

The user message is USER_REQUEST: <prompt> followed by CANDIDATES (choose exactly one name from this list): and the block built by build_candidates_block: one line per candidate, i) name — description (truncated to 140 characters) | tags: t1, t2, … (8 max).

Three things worth noting:

  • The folder context is not given to the router. folders_context is only added to the extraction prompt.
  • The conversation history is injected between the system and the user turns (*history), and it contains the widget's raw chat bubbles ("After reflection, I would like to run …"). The JSON router therefore receives interface prose as "assistant" turns.
  • confidence and reason serve no purpose. confidence is parsed, rounded, serialized into the output JSON as tool_confidence… and never read back by the widget. No threshold anywhere. The instruction "confidence ≤ 0.4" is not a constraint, just a suggestion to the model.

The only safety net is textual: if selected_tool and selected_tool != "null" and selected_tool != "None". A hallucinated tool name that is not in the manifest passes this test, then makes build_cli_args fail with a KeyError, caught by the global try in main() and returned as {"error": …}.

tools = build_tool_spec(manifest) (Agent_CLI.py:72) is computed and then never used: dead code, along with all the handling of the "old structure" (patterns, defaults) that no entry in the current manifest uses.

5. Parameter extraction

A second LLM call, with a tool already chosen, inside extract_parameters (utils.py:220).

Masking technical parameters. Parameters named temp_fold, tmp_folder, temp_folder, log_path or logPath are removed from the spec before building the prompt — no point asking the model to invent a temporary folder. They are reinjected afterward with the value input.temp_folder, i.e. the slicer.util.tempDirectory() created by the widget on every click (Agent_CLI.py:153), and removed from missing_required.

The extraction prompt (parameter_extraction_improved.py:40) lists each parameter as - name (type) [REQUIRED|optional] (encode: …): description, then imposes seven rules: list formatting per encode (comma_no_brackets, space_separated, comma_separated, python_literal), bare-JSON booleans and numbers, "if the name contains folder or dir, give a folder with no file name," and above all:

7. ONLY extract parameters mentioned in the user request
   - Do NOT invent values
   - Leave unmentioned optional parameters absent

Mandatory output: {"extracted": {...}, "confidence": 0.0-1.0, "missing_required": [...], "notes": "..."}. The missing_required produced by the model is ignored — the validator is what counts.

Path resolution is entirely delegated to the LLM

The widget passes the list of items dropped into the drop zone, joined with commas (Agent.py:790); the CLI splits it back on , and wraps it:

FOLDERS_CONTEXT:
<one path per line>

Rules:
- Treat FOLDERS_CONTEXT as the source of truth for paths.
- If a required path parameter is missing, try to infer it from FOLDERS_CONTEXT.
- If multiple candidates exist, pick the most specific match and explain briefly in 'reason'.

This block is concatenated onto the user prompt, not passed separately. There is no heuristic matching, no inspection of folder contents, no existence check: it is up to the model to guess which of the dropped paths is the T1, which is the T2, which is the model folder. A path containing a comma gets cut in two by the split(",").

Validation (parameter_validator.py) chains six passes: missing required fields, type coercion (bool/int/float/list/path/string), path syntax, choices, min/max, out-of-spec parameters. Two useful details:

  • encode: lower_str_bool forces the "true"/"false" string to lowercase, because several CLIs compare the raw argument without .lower() — str(True) would give "True" and would never match.
  • _check_paths only checks two things: that Path(str(value)) does not raise (it almost never does) and that a parameter whose name contains folder/dir does not end with a known extension. The path's existence is never tested.

The validation result is almost entirely discarded: errors and warnings surface nowhere. Their only effect is final_confidence = confidence * 0.6 when invalid — and that confidence is read by nobody. Only params and missing_required survive.

6. Building and executing the command

Yes, the module is actually launched. Unambiguously.

The CLI only builds the command. build_cli_args (utils.py:350) merges the manifest's default values with the extracted parameters, then:

return [sys.executable, tool_path] + cli

sys.executable is the Agent_CLI process's interpreter, i.e. Slicer's Python. For cli_style: positional (21 tools out of 23), the values are concatenated in the manifest's declaration order — positional_order is supported but no entry sets it. For any other cli_style, execution falls into the --flag value branch, iterating over merged: hallucinated out-of-spec parameters therefore do get emitted.

The list is returned to the widget in the command field of the JSON. It is AgentWidget that executes it, and only if missing_required == []:

  1. a chat bubble, "After reflection, I would like to run X";
  2. QMessageBox.question listing key=value for each parameter (Agent.py:864);
  3. on Yes → runToolWithRepair → subprocess.run(cli_args, capture_output=True).

If missing_required is not empty, the agent launches nothing: it displays the list of what is missing along with the values already known, and waits for a follow-up message (which the conversation history will let it hook back onto).

Slicer is frozen during the job

subprocess.run is synchronous and runs on the GUI thread: Slicer is frozen for the entire duration of the job — which, for an AMASSS segmentation or an AREG registration, is measured in tens of minutes.

7. The repair loop

On a nonzero return code, runToolWithRepair (Agent.py:943) asks the LLM to fix the parameters, at most MAX_REPAIR_ATTEMPTS = 2 times. build_repair_prompt (utils.py:282) sends the parameter definitions, the values used, the full command, and the last 2000 characters of stderr, and asks it to return only the parameters to change.

This path runs inside the Slicer process, not the CLI: _proposeRepair adds the Agent_CLI folder to sys.path and reimports Agent_CLI_utils so as not to duplicate the logic. The fix goes back through ParameterValidator then build_cli_args, an old -> new diff is displayed, and a new Yes/No confirmation is required. If the diff is empty, the loop stops.

_suggestFixFor (Agent.py:903) supplements this with a non-LLM, keyword-based diagnosis: missing Ollama model, ModuleNotFoundError, NameError: name 'nn' is not defined (a known regression in transformers>=4.53.0, huggingface/transformers#43784), Numpy is not available (numpy 2 ABI clash against the torch wheels), or an Ollama connection failure.

Since no parameter is named on the CLI side (everything is positional), a signature that is too short does not raise a clean error but produces a silent shift: on areg_ios, the log file path ends up as a filename suffix.

Script paths do not resolve

A more fundamental problem than the signatures. The manifest only gives bare names (path: "ALI_CBCT.py"). resolve_tool_path (utils.py:143) looks, in order, at: $AGENT_CLI_TOOLS_DIR/<name>, <manifest_dir>/CLI files/<name>, <manifest_dir>/<name>, then <ancestor>/CLI files/<name> walking up 4 levels.

Without AGENT_CLI_TOOLS_DIR, the Agent cannot launch any module

There is no CLI files folder anywhere in SlicerAutomatedDentalTools. The code comment cites the AI_Agent/Agent_CLI/ + .../CLI files/ layout, the one from the original repository Agent_CLI was extracted from. Here, each script lives in its own module's folder (ALI_CBCT/ALI_CBCT.py, …). No candidate matches, and the function returns candidates[0] "so the error message points to a debuggable path," i.e. <Agent_CLI>/CLI files/ALI_CBCT.py.

subprocess.run does not raise (the executable, sys.executable, exists); it is Python that exits with code 2 on a file it cannot find, which triggers the repair loop — which, since it fixes parameters, can structurally do nothing about it.

And even with paths resolved, some targets would still fail: DOCShapeAXI_CLI.py imports shapeaxi, MRI2CBCT_TMJ_CROP.py imports nnunetv2. These packages live in conda environments that their respective Slicer modules invoke via conda run -n … or CondaSetUpCall. The Agent, for its part, launches everything with sys.executable, i.e. Slicer's Python, never conda.

9. The two modes

Mode (comboBox)Agent_CLI outputExecution

Ask (Interactive)free textnone

In Ask mode, build_candidates_block(..., include_parameters=True) appends | parameters:<raw YAML list of dicts> to each line — the Python repr of the manifest's structure gets injected as-is into the system prompt of an "expert medical image analysis consultant." No format="json"; the response is displayed after stripping the * and # characters.

Three names for two modes

The README calls this mode "Consultant," the UI says "Ask (Interactive)." The code only tests == "Agent (Automated)", so any other value falls through to consultant mode.

10. Guardrails

What exists:

  • A mandatory modal confirmation before every execution, listing all the parameters, and a second one before every repair attempt.
  • Blocking on missing required parameters: nothing is launched while missing_required is not empty.
  • Type coercion and choices / min / max / extension-on-folder checks.
  • Masking of temporary folders, filled in from slicer.util.tempDirectory() rather than by the model.
  • Bounding: MAX_REPAIR_ATTEMPTS = 2, history truncated to MAX_HISTORY_ENTRIES = 40 turns.
  • Global try in main(): stdout always stays parsable JSON, the traceback goes to stderr.

What does not exist:

  • No confidence threshold. tool_confidence and parameters_confidence are computed and serialized, then ignored. A routing at 0.1 is treated the same as a routing at 0.95.
  • No path existence check. A hallucinated path passes validation, passes the confirmation (the operator has to spot it by eye in the dialog box), and only fails when the target module launches.
  • The validator's errors are never displayed. errors, warnings, and extra_params are produced and then discarded.
  • No protection on output folders. If the model picks an input data folder as output_folder, nothing stops it. Several CLIs in the repository overwrite their input file.
  • Out-of-spec parameters are not filtered in --flag mode.
  • log_path receives a folder, not a file: the names log_path and logPath are in the list of parameters replaced by input.temp_folder. CLIs that open this path for writing will fail.
  • No executable whitelist. subprocess.run takes the list exactly as built. The real protection is that tool_path comes from the manifest, not from the LLM — the model controls the values, not the binary.

11. Environment

CheckDependencies (Agent.py:1141) runs a slicer.util.pip_install inside Slicer's Python, in this order, which matters:

PackageReason for the pin
ollamapython client only — pip does not provide the server
pyyamlreading the manifest
transformers<4.53.0regression NameError: name 'nn' is not defined in integrations/accelerate.py, breaks the cross-encoder import
numpy<2numpy ≥ 2 breaks the ABI of the pip torch wheels (RuntimeError: Numpy is not available)
sentence-transformerspulls in torch; installed last so as not to bump the pins

Agent_CLI.py runs in a separate process but shares Slicer's site-packages, hence the installation on the widget side. No conda environment is created or used.

The Ollama server is checked with a simple socket probe on 127.0.0.1:11434 (_ollama_responding, 0.5 s timeout), relaunched if needed via Popen([binary, "serve"]) with a wait of up to ~30 s in 500 ms steps while keeping the UI alive. ensure_agent_ollama_running() is called again before every message (Agent.py:772), because a server launched by the module does not survive a Slicer restart.

Windows: CREATE_NO_WINDOW so as not to flash a console window. No WSL, unlike the rest of the repository.

12. Pitfalls and fragile points

  • resolve_tool_path finds nothing in this repository (§8). This is blocker number one. Possible fixes: create a CLI files folder with links, set AGENT_CLI_TOOLS_DIR, or put repository-relative paths in the manifest and extend the search.
  • 17 signatures out of 23 are wrong, and the shift is silent.
  • batchdentalseg and clic are not CLIs. cli_style: ui_module is handled nowhere: it falls into the --flag branch, which produces a command that cannot work on a scripted Slicer module.
  • input.folders.split(",") breaks any path containing a comma, both for the folder list and for the join(",") on the widget side.
  • The cross-encoder is reloaded on every message (fresh process), and its failure degrades to the first three tools in the manifest without the operator being informed.
  • k=3 is hardcoded. 23 tools, 3 candidates: a bad cross-encoder scoring cannot be recovered by the LLM.
  • priority is inert, which makes the manifest's ranking misleading.
  • subprocess.run blocks the GUI thread for the entire execution of the module.
  • The history mixes UI prose with routing context: chat bubbles are sent back as-is as assistant turns to a router constrained to JSON.
  • OnRetrieveButton rebuilds the history by splitting on the emoji 👨: / 🤖: (Agent.py:1126): a message containing these characters desynchronizes the alternation.
  • Theme detection by pixel sampling (widget.grab(), luminance of pixel (5,5)), because QPalette returns light-theme colors even under a dark theme in Slicer (Agent.py:656). It works, but depends on the timing of the first render — hence the QTimer.singleShot(0, ...) in setup.
  • Dead code: AgentLogic.process(), build_tool_spec() (and all the patterns/defaults support around it), ValidationReport, positional_order, the manifest's examples field, _cross_encoder_model, Agent_CLI/Resources/UI/Agent_CLI.ui.
  • extract_parameters returns 4 values while its annotation declares 3.

14. Literature

No paper

Neither on this module nor on the approach. A search for SlicerAutomatedDentalTools + LLM agent turns up only the repository's documentation and general literature on LLMs in dentistry, unrelated to this code. The only real external references are those of the two models used, both generic and not trained for this domain.

  • Qwen3 on Ollama — routing and extraction model
  • cross-encoder/ms-marco-MiniLM-L-6-v2 — MS MARCO reranker used for preselection
