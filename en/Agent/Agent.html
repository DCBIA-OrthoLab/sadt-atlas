Agent: full pipeline

A natural-language assistant that picks a module from the extension, extracts its parameters, builds the command line, and launches it. No medical neural network is called here: the Agent only does routing and form-filling. This page explains how, step by step; the details a developer needs are on the code page.

unpublished Agent_CLI Slicer Python qwen3:8b via Ollama cross-encoder MiniLM-L6 Code (developers) Bibliography VISOR: partial

Everything runs locally: an 8B language model served by Ollama, plus a small cross-encoder to preselect candidate tools.

Two code bases. Everything described here is the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). VISOR has a server tool called Agent, a router over an external Ollama endpoint, but no client calls it: the AgentRemote panel shipped in the VISOR client is a copy of the legacy widget that still runs locally. Both are described on the VISOR page for Agent. Evidence.

Overview: what goes in, what comes out

Agent (Automated)Ask (Interactive)

1. Position in the chain

Nobody calls Agent. No other module of the extension uses it: it is a terminal entry point. Outbound, three things are called:

CalledHowWhere
Agent_CLISlicer’s command-line runnerseparate process, Slicer Python
The target module (ALI_CBCT, AMASSS_CLI, ...)started as a child process of the panelSlicer Python
Ollamaits Python client, over HTTP on the machine’s own portlocal server, installed and launched by the module

The inventory of targets is purely declarative: it lives in manifest.yaml, a YAML file with 16 entries. The Agent discovers nothing on its own: it only knows this file.

In the codeCall sites with file and line, and the dead code that remains in the module

2. Files involved

The panel (chat, drop zone, Ollama installation, confirmation, launch, repair) runs in Slicer. A separate command-line program does the routing and the extraction and prints JSON, executing nothing. A utility file holds the manifest, the cross-encoder, the call to Ollama, the path search and the command building. A validator coerces and checks the values, and the manifest lists the 16 addressable tools. No conda environment and no mandatory GPU: everything runs inside Slicer’s Python; the only GPU used is indirect, through the Ollama server.

3. The models

3.1 The language model, qwen3:8b via Ollama

One model serves all three calls, routing, parameter extraction and repair: Qwen3 with 8 billion parameters, run by Ollama (so llama.cpp underneath) in the GGUF format that Ollama imposes. There is no specialised model and no fine-tuning. The model name is written in two places in the code and can be swapped with an environment variable. The default tag weighs 5.2 GB (read on ollama.com, not determinable from the repository).

Whether it runs on CPU or GPU is decided by Ollama, not by the module. The code draws one consequence: on Linux, an Ollama installed through snap is sandboxed, does not see the NVIDIA GPU and falls back to CPU, at 80 to 90 seconds per answer for an 8B model, a figure measured and written in the code. The module detects it and warns, without being able to fix it.

When no Ollama is found, the module downloads the official portable archive into a folder of its own, so no root password is needed from the panel. Only two call settings are used: the model stays loaded for 30 minutes instead of 5, and the answer is constrained to JSON for the router, the extraction and the repair (not for consultant mode). No temperature, seed or context size is passed. If the model is not present, it is pulled and the call replayed.

In the codeConstants, the snap test, the Ollama installer and the two call settings

3.2 The cross-encoder: ms-marco-MiniLM-L-6-v2

It is the only real neural network loaded in the process: MiniLM, 6 layers, 22.7 million parameters, trained on the MS MARCO passage-ranking task, downloaded from the Hugging Face Hub. It is not an embedding model: the request and the tool text are fed together into the transformer, which outputs one unbounded relevance number. The command-line program is a fresh process on every message, so the model is reloaded each time.

If loading the cross-encoder fails, the fallback is blunt: the first three tools of the manifest, whatever the question, and the chat is not told (a line goes to the program output only). The manifest’s priority field is never read.

4. Routing

Two stages, and the language model only steps in at the second one. Stage 1 is the cross-encoder above. In stage 2 the model receives the request and the three candidates, one line each (name, description cut at 140 characters, at most 8 tags), and must answer with one JSON object: a tool name, a confidence and a one-sentence reason. Three things are worth knowing:

  • The folder context is not given to the router; it is only added later, for the extraction.
  • The conversation history is injected as it appears on screen, including the panel’s own sentences such as “After reflection, I would like to run ...”, so the JSON router receives interface prose as earlier answers.
  • The confidence and the reason serve no purpose. The confidence is parsed and written out, then never read back: no threshold exists anywhere, and the instruction “confidence at most 0.4 when nothing matches” is only a suggestion to the model.

The only safety net is textual: the answer must not be null. A tool name that is not in the manifest passes that test, then makes the command builder fail; the error is caught and returned as an error message.

5. Parameter extraction

A second model call, with a tool already chosen. Technical parameters (a temporary folder, a log path) are removed from what the model sees and filled in by the panel afterwards: the model is not asked to invent them. The prompt lists each parameter with its type, whether it is required and how a list must be written, then imposes seven rules, above all: only extract what the request mentions, do not invent values, leave unmentioned optional parameters absent. The list of required parameters the model returns is ignored: the validator is what counts.

The validator also forces the text “true” or “false” to lower case where a tool compares the raw argument. The validation report is otherwise almost entirely discarded: its errors and warnings surface nowhere.

Paths are left entirely to the model. The folders dropped on the panel are appended to the request, with the instruction to treat them as the source of truth. There is no heuristic matching, no look inside the folders and no existence check: the model alone guesses which dropped path is the T1, which is the T2, which is the model folder. VISOR fixes only the comma part of this: the server tool receives the folders as a list.

In the codeThe extraction prompt, the six validation passes and the path block with its comma split

6. Building and executing the command

Yes, the module is actually launched. The command-line program only builds the command: it merges the manifest’s default values with the extracted ones and prepends Slicer’s own interpreter and the script path. For 14 of the 16 tools the values are simply written one after the other in the order the manifest declares them (positional style).

The panel then runs the command, and only if nothing required is missing: a chat bubble says what it would like to run, a Yes/No dialog lists every parameter, and on Yes the module starts. If something required is missing, nothing is launched: the panel lists what is missing with the values already known, and waits for a follow-up message. The launch is synchronous and happens on the interface thread: Slicer is frozen for the whole job, which for a segmentation or a registration is measured in tens of minutes.

In the codeThe command builder, the dialog, and the blocking subprocess call

7. The repair loop

This path runs inside the Slicer process, not in the command-line program. The fix goes back through the validator and the command builder, an old-to-new difference is displayed, and a new Yes/No confirmation is required; an empty difference stops the loop. A keyword-based diagnosis, with no model, adds hints for a missing Ollama model, a missing Python module, a known regression in a recent transformers release, a numpy 2 clash with the torch wheels, and an Ollama connection failure.

In the codeThe repair prompt, the re-import trick and the keyword diagnosis

8. Addressable modules, and their real state

The manifest lists 16 tools. Its list of parameters was compared, file by file, with the real command line of each target script. Only 2 signatures out of 16 are correct: DOCShapeAXI and MRI2CBCT_resample. Two more (BatchDentalSeg and CLIC) are scripted Slicer modules, not command-line tools, and cannot be run this way. AMASSS refuses outright (“Expected 13 arguments”). The others each lack one to four parameters.

Because nothing is named on the command line, a list that is too short does not raise a clean error: on AREG_IOS, for example, the log file path ends up as a file name suffix. Missing from the manifest, and therefore out of reach of the Agent: VFACE, GreedyReg, CNE, AREG_IOSCBCT, SurgMovPred and Medical_Data_Anonymizer.

In the codeThe 16-row table with the manifest and actual parameter counts for each script

Script paths do not resolve

A more fundamental problem than the signatures. The manifest only gives bare script names. The path search looks, in order, in a folder named by the AGENT_CLI_TOOLS_DIR variable, in a “CLI files” folder next to the manifest, in the manifest folder itself, then up to four levels above. None of them exists in this repository, where each script lives in its own module’s folder, so no candidate matches and the function returns the first one “so the error message points to a debuggable path”.

The launch itself does not raise (Slicer’s interpreter exists): it is Python that exits with code 2 on a file it cannot find, which triggers the repair loop. Even with paths resolved, some targets would still fail: DOCShapeAXI needs a package that lives in a conda environment, while the Agent launches everything with Slicer’s Python.

9. The two modes

ModeWhat Agent_CLI returnsExecution
Agent (Automated)A JSON object with the tool, its confidence, the parameters, what is missing and the commandyes, after confirmation
Ask (Interactive)Free textnone

In Ask mode each candidate line also carries the raw list of its parameters, pasted as it is into the system prompt of an “expert medical image analysis consultant”. The answer is not constrained to JSON and is shown after the characters * and # have been stripped. The README calls this mode “Consultant”, the interface says “Ask (Interactive)”, and the code only tests for the Agent name, so any other value falls through to consultant mode.

10. Guardrails

What exists:

  • A mandatory confirmation before every execution, listing all the parameters, and a second one before every repair attempt.
  • Nothing is launched while a required parameter is missing.
  • Type coercion, and checks of choices, ranges and the extension of folder-like names.
  • Temporary folders are filled in by the panel, not by the model.
  • Bounds: 2 repair attempts, a history of at most 40 turns, and a global catch so that the program’s output always stays parsable JSON.

What does not exist:

  • No confidence threshold: a routing at 0.1 is treated like one at 0.95.
  • No check that a path exists: a hallucinated path passes validation and the confirmation (the operator has to spot it by eye) and only fails when the module starts.
  • The validator’s errors are never displayed.
  • No protection of output folders: if the model picks an input data folder as the output, nothing stops it.
  • No executable whitelist, but the real protection is that the script path comes from the manifest, not from the model: the model controls the values, not the program that gets launched.

11. Environment

The panel installs five packages into Slicer’s Python, in an order that matters: the Ollama Python client, a YAML reader for the manifest, transformers older than 4.53 (a regression breaks the cross-encoder import), numpy older than 2 (numpy 2 breaks the torch wheels) and, last so as not to bump the pins, sentence-transformers. The command-line program runs in a separate process but shares Slicer’s packages. No conda environment is created.

The Ollama server is probed on its local port, started when needed and waited for up to about 30 seconds while the interface stays alive. It is checked again before every message, because a server launched by the module does not survive a Slicer restart. On Windows no console window is shown; there is no WSL support, unlike the rest of the repository.

12. Pitfalls and fragile points

  • Module scripts cannot be found, which blocks the whole tool. Evidence.
  • 14 signatures out of 16 are wrong, and the shift is silent. Evidence.
  • The cross-encoder falls back silently to the first three tools, is reloaded on every message, and keeps a hard-coded top 3. Evidence.
  • Slicer is frozen during the whole job. Evidence.
  • Path resolution is entirely left to the model. Evidence.
  • An Ollama installed with snap runs on CPU. Evidence.
  • Three names for two modes. Evidence.
  • Dead code remains: an unused process(), an unused tool-spec builder, an unused cache of the cross-encoder, and an interface file that a command-line module never loads. Evidence.
  • The history mixes interface prose with routing context, and when a saved discussion is reloaded the history is rebuilt by splitting the text on two emoji, so a message that contains them desynchronises it (a live chat keeps its turns as a list).

14. Literature

No paper, neither on this module nor on the approach. A search for SlicerAutomatedDentalTools and LLM agents turns up only the repository’s documentation and general literature on language models in dentistry. The only real external references are those of the two models used, both generic and not trained for this domain. The VISOR server tool is the same approach; its README gives a provenance section naming the legacy files it was ported from, not a publication. Evidence.

  • cross-encoder/ms-marco-MiniLM-L-6-v2: MS MARCO reranker used for preselection
