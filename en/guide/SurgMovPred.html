SurgMovPred — estimate the expected bone movement after surgery

SurgMovPred doesn't look at your volumes or your meshes: it takes a spreadsheet of cephalometric measurements and turns it into a numeric estimate of the bone displacements expected after orthognathic surgery — how far a point such as Pogonion or the posterior nasal spine should move, along the three axes of space. No imaging, no neural network: 112 small, independent statistical models, one per predicted value, applied row by row to your table.

On video
  • Surgical Movement Prediction: Machine learning model to help surgery preparation 28 s (overview) · DCBIA Videos channel

When to use it

Use it once you already have, per patient, a set of cephalometric measurements — the pre-surgical state and the intended occlusal outcome — and you want a quick numeric estimate of the corresponding bone displacements, across a whole batch of patients at once rather than one at a time. It's a numeric complement to your own surgical planning, not a 3D visualization tool.

A spreadsheet-only tool

SurgMovPred doesn't read any volume, surface, or Slicer landmark, and it doesn't touch your 3D scene: nothing is created or displayed there. Everything happens on disk — a folder of spreadsheets in, a folder of spreadsheets out.

The input spreadsheet format

This is where most people get stuck with this module: what it expects on input is quite specific, and nothing warns you clearly when it isn't met.

  • A folder, not a single file. Every .csv, .xlsx, and .ods file inside is read and stacked into one big table, with no check that their columns actually match. Subfolders aren't scanned.
  • Only one sheet per workbook. For an Excel or .ods file, only the first sheet is read. If your workbook has several sheets (demographics, raw measurements…), make sure the one with per-patient measurements comes first.
  • Column headers get lightly cleaned up automatically: quotes and brackets stripped, stray characters and spaces turned into underscores, doubled underscores collapsed, "total" capitalized, and a header starting with a digit gets a prefix. So you can generally keep your own headers as-is — SM-A-FH becomes SM_A_FH automatically, and apostrophes are kept on purpose for names like Jarabak's ratio.
  • But that cleanup doesn't excuse missing the right columns. Each of the 112 models expects a precise list of roughly 145 measurements: point positions relative to cephalometric reference planes, soft-tissue points, standard 2D cephalometric measurements (SNA, ANB, Wits…), and occlusal measurements duplicated into two sets — one for the starting state, the other most likely for the intended target (that isn't spelled out anywhere; it's inferred from both being present on input). A small tolerance exists for one of those two sets, but nothing beyond that: the safest approach is to start from the example spreadsheet shipped with the module and only replace its values.
  • Patient ID column. It's auto-detected among common headers (#, ID, Patient ID, Patient Number, Subject…). If none matches, the output simply keeps an empty ID column — the run still completes, but you lose the link back to your patients.
  • No missing value is ever filled in. An empty cell stays empty all the way through; it isn't estimated, and it doesn't get the rest of its row skipped either.

What it needs, what you get

What to provide

  • A folder of spreadsheets (.csv, .xlsx, or .ods) in the format described above
  • The trained models, downloaded once (dedicated button, about 700 MB)
  • An output folder

What comes out

  • Two identical spreadsheets (.xlsx and .csv) in the output folder
  • One row per input patient, one column per predicted displacement value
  • Your input spreadsheets and your Slicer scene are left untouched

Steps

  1. Download the models. Dedicated button, about 700 MB, only needed once but required before the first run.
  2. Prepare your input folder following the format above — one consolidated spreadsheet or several files, either way, as long as the expected columns are there.
  3. Set the three folders: input, downloaded models, output.
  4. Run it. There's nothing to tune: no threshold, no target selection, no skeletal-class option. All 112 values are predicted at once, for every row of the assembled table.
  5. Collect the two output spreadsheets from the folder you chose.

How to read the result — and not read too much into it

Each output column is a predicted displacement value for a given point on the maxilla, the mandible, or the genioplasty segment, expressed along three components of the cephalometric frame (front/back, left/right, up/down), plus a fourth "Total" column that's most likely an overall magnitude. The unit is written nowhere in the tool; it's probably millimeters, but that's an inference, not a stated certainty.

Each point is predicted on its own, not the whole segment

The 112 output values come from 112 independent models, one per value. Nothing guarantees that the ten points predicted for the maxilla, say, stay consistent with each other: the result isn't a rigid transform of the bone block, only a collection of pointwise displacements computed separately from one another. Don't reconstruct an overall movement from these numbers without checking them against each other first.

The table carries no confidence interval and no reliability score: every cell is a single value, with no margin of error attached. And the prediction stops at the spreadsheet — SurgMovPred moves nothing in Slicer, builds no transform, opens no view. It's up to you to carry the values into your planning software if you want to visualize or apply them.

If something's off

Clicking Apply reinstalls a dependency every time

Clicking Apply always forces a reinstall of numpy, even when everything was already working. That makes the run slower, and swapping out a core numerical library inside an already-running Slicer session can unsettle other tools that depend on it. If another module starts misbehaving after you've used SurgMovPred, restart Slicer before looking any further.

A missing column in the output isn't a crash

If one of the expected values is missing from the result, nothing errors out visibly: the model behind it was simply skipped because one of the columns it needed couldn't be found after the header cleanup. The warning stays in Slicer's log, not in the spreadsheet — if your output has almost no predicted columns, compare your headers against the example spreadsheet before looking elsewhere.

Check which sheet is active in your workbook

Only the first sheet of an .xlsx or .ods file is read. If your per-patient measurements aren't on the first sheet, SurgMovPred will read a different one — or an empty one — without saying so.

The test-files button doesn't fill anything in by itself

It does download an archive, but it only fills in the input and output folders if another module's test data (VFACE's) is already present on the machine. On a machine without it, clicking the button has no visible effect.

All models are loaded on every run

SurgMovPred loads all 112 models into memory as soon as it runs, even for a single patient or a single value you actually care about — roughly 1.5 GB of RAM before it even reads your spreadsheet. Plan for that on a memory-constrained machine.

Further reading

No publication describes the module. Its only public description is a NA-MIC project report, and the models it runs are evaluated nowhere.

On SurgMovPred itself

  • NA-MIC Project Week 45, Boston 2026 — New 3D Slicer Module to predict surgery movement for maxillofacial surgery. The project report: the intent, the starting data, and the state of the work.

Around the method

  • de Oliveira et al., Orthod Craniofac Res 2024 — Artificial intelligence as a prediction tool for orthognathic surgery assessment. The same lab on the same question, but published and evaluated. Read it before trusting a prediction from the module.
  • Cheng et al., BMC Oral Health 2023 — Prediction of orthognathic surgery plan from 3D cephalometric analysis via deep learning. A neighbouring approach, open access, with errors reported measurement by measurement.
