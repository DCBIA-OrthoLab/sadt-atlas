CNE — extract information from clinical notes

The name doesn't say it: CNE doesn't touch any image, volume, or mesh. It's a reading tool — it takes free-text clinical notes and pulls structured information out of them, as key/value pairs, using a language model (LLM) that runs locally inside Slicer.

When to use it

Any time you have a batch of free-text notes — TMJ or Ortho visits — and want the key facts (symptoms, diagnoses) pulled out quickly instead of reading each one by hand. CNE processes a whole folder of notes at once, using a different model depending on whether the notes are TMJ or Ortho.

Nothing leaves your machine

The model runs inside Slicer's own Python, on your computer. Notes aren't sent to any online service during extraction — the only step that touches the network is the one-time model download.

What it needs, what you get

What to provide

  • A folder of notes, placed directly inside it (no subfolders) — .txt, .pdf, or .docx
  • The note type: TMJ or Ortho, each with its own model
  • The matching model, downloaded once (a few GB)

What comes out

  • One text file per note, Extraction_<note name>.txt, in the output folder
  • key : value lines summarizing the note
  • No summary table, no CSV: one file per note, to be checked one at a time

Steps

  1. Choose the note type. TMJ or Ortho: this decides which model gets used and how long a note it can take in one go.
  2. Download the matching model. On the first click on "Apply", the module installs whatever is missing (after you confirm), then fetches the model from Hugging Face. Only needed once per note type.
  3. Point it to the notes folder. Files must sit directly at the root of the chosen folder, not sorted into per-patient subfolders.
  4. Set an output folder.
  5. Launch, then wait. Notes are processed one after another; expect several tens of seconds per note.

How long it takes, how much memory

Even though the module mentions using a graphics card, the install only sets up CPU packages: in practice, extraction always runs on CPU. Expect roughly a minute per note depending on its length; on a batch of several dozen notes, it's better to start the run and come back later. The loaded model needs about 5 to 6 GB of RAM on top of what Slicer already uses, and its download is several gigabytes, done once per note type.

Check the result

All the clinical content in the output file comes from the model: there's no rule, no term dictionary, no schema check behind it. The module expects a JSON reply but doesn't enforce it technically — it just looks for the first opening brace and the last closing brace in the response. If the model's output isn't well formed, its raw text lands in the file as-is, with no indication that formatting failed. Check every file it produces before relying on it.

If something's off

The Ortho model won't download

The file the module asks for the Ortho model doesn't exist at the address listed on Hugging Face: the download fails with "Download failed or was cancelled", with no further explanation. TMJ mode downloads fine. If you pick Ortho today, expect this failure — it isn't something on your end.

Notes sorted into per-patient subfolders

CNE only looks at files sitting directly in the folder you chose, not at anything inside subfolders. A folder organized with one subfolder per patient will produce no output at all, with no error message.

Scanned PDF

PDF text extraction doesn't do OCR: if your PDF is actually a scanned image, the extracted text is empty and the note can't produce anything.

Tables inside a .docx

Only paragraph text is read from a Word document; table content is skipped. If your key information sits in a table, it never reaches the model.

Note too long

There's no chunking: a note longer than the model can read in one pass fails entirely instead of being processed in pieces. The margin is especially tight in Ortho mode.

No anonymization

Notes are read as-is, with no personal-data removal. If your files contain identifying information, run them through MedicalDataAnonymizer first if needed.

Further reading

The module has no publication, and the models it runs are lab fine-tunes uploaded without a model card: no described training set, no evaluation. The readings below give what is generally known about how reliable this kind of extraction is.

Around the method

  • Wiest et al., npj Digital Medicine 2024 — Privacy-preserving large language models for structured medical information retrieval. Exactly the intended use — pulling structured fields out of a report with a locally-run model — and what it actually achieves.
  • Panchal et al., BMJ Health & Care Informatics 2026 — Benchmarking large language models for de-identification of electronic health record notes. A quantified comparison of several models on clinical notes: where they fail, and on which kinds of field.
  • Dorémus et al., JMIR 2025 — Harnessing Moderate-Sized Language Models for Reliable Patient Data Deidentification in Emergency Department Records. What to expect from a model the size of those used here, rather than from a very large remote one.

The tool's full bibliography — what was found, and what was looked for without success — is in its sources.
