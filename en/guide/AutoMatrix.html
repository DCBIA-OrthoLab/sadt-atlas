AutoMatrix — apply a matrix across a whole batch of files

AutoMatrix applies one or more ITK transformation matrices to an entire folder of volumes and landmark files in a single pass. No neural network, no GPU: it's a batch tool, not a computation step — the matrix itself comes from a registration you ran somewhere else.

When to use it

You ran a registration module (AREG, ASO, FlexReg…) and got a transformation matrix (.tfm) out of it. Now you want to apply that same matrix to other files for the same patient — a segmentation, a second volume, a set of landmarks — without opening each one in Slicer by hand. Or you ran that registration on a whole series of patients and want to process the entire folder in one go. That's what AutoMatrix is for: it doesn't register anything itself, it replays a transformation you already computed.

One matrix, one motion

Applied to a volume, the matrix moves its content. Applied to a landmark file, it moves the points by exactly the same motion. That's what keeps a scan and its landmarks aligned after going through AutoMatrix — as long as you use the same matrix for both.

How files and matrices get matched

AutoMatrix never asks you to point out by hand which matrix goes with which patient. It guesses the pairing by comparing file names: it strips a list of known keywords (_Seg, _Or, _MAND, _CB, a timestamp like _T1, _T2…) from the scan's name, and a slightly different list from the matrix's name, until it's left with a patient identifier on each side. If the two identifiers match, the file and the matrix are paired.

The catch: those two keyword lists aren't the same. The rule that works reliably: start every file name with the patient identifier, then an underscore, then whatever else you need. Example that works: patient1_T1_MA.nii.gz and patient1_left_MA.tfm both reduce to patient1, because _T1 is stripped on the scan side and _left on the matrix side. Example that fails: patient1_MA.nii.gz with no timestamp reduces to patient1_MA on the scan side but patient1 on the matrix side — the two no longer match, and that file gets no matrix at all.

There's a shortcut: point to a single matrix file, rather than a folder, and it gets applied as-is to every patient in the input folder — no name matching needed.

What it needs, what you get

What to provide

  • A folder of volumes as .nii, .nii.gz or .nrrd, and/or Slicer landmark files (.mrk.json)
  • An ITK matrix (.tfm, .h5 or .mat), or a folder of matrices named following the same rule as the scans
  • Check this if your volumes are segmentations: the dedicated box, so labels don't get smoothed out by interpolation
  • Optional: a reference file to force the output grid (size, orientation)

What comes out

  • A transformed copy of each matched file, laid out in the same folder structure as the input
  • Your original files are never modified
  • In a landmark file, only the points marked as defined get moved
  • No new matrix is ever produced: AutoMatrix consumes transformations, it doesn't write them

Steps

  1. Point it to the input folder. Scans and/or landmark files to transform; the whole folder is processed in one go.
  2. Point it to the matrix, or a folder of matrices. Check that the names follow the patient + suffix rule above, or point straight at a single file to apply it to everyone.
  3. Check the segmentation box if your volumes are labelmaps.
  4. Give it a reference file if you want to force the output grid; otherwise each file keeps its own input volume's grid, and anything pushed outside the field of view by the transform is lost.
  5. Pick an output suffix, and decide whether the matrix name should be appended to it — needed as soon as a patient has more than one matrix (see below).
  6. Set an output folder, then run it. A progress bar tracks the files as they go through.

Flipping left/right without hunting for a matrix

If all you need is a left/right mirror, there's no need to build your own matrix: the Mirror mode downloads a ready-made reflection matrix and fills it into the matrix field for you, with its own output suffix (_mir).

The mirror isn't centered on your patient

The reflection happens across the sagittal plane of the scene's origin, not the patient's own sagittal plane. If your patient isn't already centered in the scene, the result will come out both mirrored and shifted — plan on a registration step afterward to correct the offset.

If something's off

Some advertised formats no longer work

The interface still offers meshes (.vtk, .vtp, .stl, .off, .obj) as input scans for intraoral surfaces, and matrices as .npy — both get counted in the progress bar, but neither produces any output: each file of that kind is simply skipped, with a line in the error log. A .txt matrix only works if it's an actual ITK transform file, not a plain 4×4 array.

A failed match gives no warning

If a scan's name and a matrix's name don't reduce to the same patient identifier (see above), that file is simply never transformed — no error message, no visible warning. If a patient is missing from the output, the first thing to check is that patient's file names.

One output can overwrite another

If you uncheck the option that appends the matrix name to the output file, and a patient has more than one matrix, every result gets the same file name: each one overwrites the last, and only the final matrix processed survives. Keep this option checked whenever you're applying more than one matrix per patient.

A landmark file can vanish silently

Some transformations (dense deformation fields, B-splines) can't be inverted mathematically. When that happens, the matching landmark file is skipped with just a warning in the log, while the volume itself still gets transformed — so a scan and its landmarks can end up out of sync with nothing on screen to flag it.

Matrices aren't chained

When a patient has several matrices, each one is applied separately to the original input file: you get one output file per matrix, never a composition of one after the other.
