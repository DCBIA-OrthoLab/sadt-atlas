DOCShapeAXI — classify a 3D shape and see what drove it

DOCShapeAXI takes already-segmented meshes and sorts them into a category — a severity stage, a presence or absence of obstruction, or a continuous ratio depending on the case. For every shape it classifies, it also writes a map directly onto the mesh showing where the network looked most closely to reach its decision.

When to use it

Reach for it whenever you have 3D shapes already extracted — condyles, airways, cleft bone defects — and want an automatic classification instead of a case-by-case visual read, with a map thrown in that gives you a lead on the model's reasoning. DOCShapeAXI does not segment anything itself: the .vtk meshes you feed it must already exist, produced by another tool (AMASSS for condyles, an airway segmentation, and so on).

Three shape families, one window

The data type you pick is the only thing that decides which model runs and which categories come out:

  • Mandibular Condyle — a severity stage out of 4 classes.
  • Nasopharynx Airway Obstruction — three results produced one after another in a single run: presence or absence of obstruction (2 classes), a severity stage (4 classes), and a continuous ratio of obstruction between 0 and 100.
  • Alveolar Bone Defect in Cleft — a severity stage out of 4 classes.

For all three severity stages, the 4 classes are really quarters of a continuous 0–100 scale: class 1 covers the low quarter, class 4 the high one.

What you need, what you get

To provide

  • A folder of already-segmented .vtk meshes, all of the same shape type
  • The data type picked from the list — condyle, airway, or cleft
  • An output folder, created ahead of time before you launch

What comes out

  • A csv listing every mesh with its prediction, one column per task
  • A copy of each mesh, per task, carrying the explainability map as a per-point scalar
  • Your original meshes are left untouched

Steps

  1. Pick the data type. Mandibular condyle, airway obstruction, or cleft bone defect. This choice alone decides which model gets downloaded and which categories come back.
  2. Point to the input folder. It should hold only already-segmented .vtk meshes of the type you just picked.
  3. Create and point to an output folder. On the first run against that folder, the matching trained model is downloaded automatically (roughly 70 MB).
  4. Launch. For airway, three passes chain automatically — obstruction, severity, ratio; for the other two types, a single pass is enough. Every mesh then gets its explainability map right after, with no extra action from you.

Reading the result

The prediction csv adds one column per task to your list of meshes: a class (an integer) for a severity stage or a binary obstruction call, a number between 0 and 100 for the airway's continuous ratio. No confidence score comes with the class — DOCShapeAXI only reports the category it settled on, not how close the call was between two neighboring classes.

For the explainability map, open the mesh produced in the explainability subfolder for that task. In Slicer's Models module, under the Scalars tab, set Active Scalar to the array named after the class you're interested in (one array per class for a classification task, a single array for a continuous ratio), then apply the ColdToHotRainbow color table. Warm areas are the ones that weighed most in favor of that class; cold or zero areas did not particularly catch the model's attention for that class.

The map only shows part of what mattered

The model decides by combining two sources: the shape of a sampled point cloud and a rendering of several views of the mesh. The explainability map only describes the second one. If a decision leaned mostly on the point-cloud geometry, the map you see will look faint — with nothing to tell you that's the reason, rather than the decision genuinely having no clear focus.

Two runs, not necessarily the same result

The points sampled from the mesh are not drawn the same way twice. Two passes on the same files can therefore produce slightly different saliency maps, and in cases sitting near the boundary between two classes, a different predicted class.

If something's stuck

The output folder has to exist before you launch

If the folder you point to doesn't exist yet, the model download is simply skipped, and the error only surfaces later, when the model tries to load. Create the output folder yourself before starting.

Adding files mid-way has no effect

The list of meshes to process is only rebuilt if it doesn't already exist in the output folder. If you drop more meshes into the input folder without changing the output folder, they simply won't be processed.

Disk space

The downloaded model isn't cached: every new output folder re-downloads it in full. Across several batches, reuse the same output folder where you can, or clean up the old ones.

Re-running on the same folder

Prediction columns are overwritten in place on every re-run, but columns left over from a different task are never cleared out — they sit side by side in the csv.
