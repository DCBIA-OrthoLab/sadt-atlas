Using VISOR: run the tools on a server from 3D Slicer

With VISOR, the computation no longer runs on your computer. You pick a tool in Slicer, the files you select are sent to a server, the server computes, and the result comes back into your scene. This page covers what you have to set up, what you provide, and what to check before sending patient data. How VISOR is built is in the VISOR Atlas.

client: implemented and tested de-identification: not implemented MRI2CBCT: not shipped
Before using patient data

The VISOR client sends your files as they are on disk. Nothing is de-identified. See What leaves your machine.

What changes for you

The rest of this site describes the legacy extension, SlicerAutomatedDentalTools: each module runs on your own computer. VISOR is a different Slicer extension, AutomatedDentalToolsRemote. Its modules are thin panels over a remote server.

  • The calculation leaves your computer. A laptop that cannot run a segmentation can still ask for one.
  • Nothing to install into Slicer's Python, and no model to download: the extension declares no dependency on other extensions, and the models live on the server.
  • The form comes from the server. A tool's panel is built when you open it, from the description the server publishes. A field added on the server appears in Slicer without a new release of the extension.
  • You need a server, an address and a key. Setting one up is the server's subject, not this page's; see deployment.

Sources: AutomatedDentalToolsRemote CMakeLists.txt:10,15 and README.md:3-8, 150-165 (commit 19b95e8).

Install the extension

The README and the build file say the following, and nothing more is assumed here.

  • The extension is AutomatedDentalToolsRemote. It works with the stable and the nightly versions of 3D Slicer, and its modules appear under the category Automated Dental Tools Remote.
  • It lists no extension dependency (EXTENSION_DEPENDS "NA"): you do not need SlicerConda, SlicerDentalModelSeg or NNUNet for it.
  • The README states it is listed in the Extensions Catalog during the transition.
  • Do not install it next to the legacy extension. The README asks you to use one or the other, because many modules share names and Slicer keeps only one of two same-named modules.

Connect Slicer to a server

Open Server Tools Settings (category Automated Dental Tools Remote.Advanced). Until you save something here, the address is a placeholder (https://set-your-server.invalid) that reaches nothing, so no file leaves your machine.

To provide

  • Server URL: an https:// address whose certificate is signed by a public authority.
  • API key: the server's API token (the field is masked). The README says to use the API token, never the admin token.
  • Timeout: 1 to 3600 seconds, 600 by default.

What you cannot change

  • No http://, not even http://localhost.
  • The certificate is always checked: the panel shows "Verify TLS: Always on", with nothing to tick.
  • Redirects are never followed.

Click Save. The change applies at once and is kept across restarts. If you type an http:// address, Slicer refuses it before saving anything. Restore defaults clears what you saved.

A server on your own computer follows the same rule: the client does not accept the server's own self-signed certificate, so you reach it through a public address, for example a tailscale serve address (https://<name>.<tailnet>.ts.net), or a reverse proxy with a Let's Encrypt or institutional certificate.

Is the server reachable? There is no "Test connection" button. The panel shows a line "Server: online" or "Server: offline" at the top, refreshed when you open the module and after each save. It only asks the server's /health page, which needs no key: "online" does not prove that your key is accepted. A wrong key shows up at the first run (see If something goes wrong).

The key is stored in clear text

Slicer saves the key in its own settings file for your user, as plain text. The masked field only hides it on screen. Anyone who can read your Slicer settings can read the key.

HTTPS has no fallback

There is no setting, flag or file that relaxes the HTTPS rule or the certificate check. An http:// address saved by an older version of the client is ignored at start-up.

Run a tool

  1. Choose a tool in the module list. It builds its form from the server on opening. If the server cannot be reached, the panel says it could not load the tool and offers a Retry button.
  2. Fill the form. What you provide depends on the tool; the field names come from the server, so read each tool's own Guide page.
  3. Press Apply. The panel checks the form first (unknown argument, missing file, missing required field) before anything is sent.
  4. Watch the progress and cancel if you need to.

What you can give as input

  • A file is sent as it is, same name and same bytes.
  • A folder is packed into an archive that keeps its file and sub-folder names, then sent.
  • A node of the Slicer scene (a volume, a model, a region of interest) is exported to a temporary file, named after the tool and the argument, not after the node. AutoCrop3D, for instance, takes its region of interest from the scene this way.
  • A hosted test file is a sample the server offers for the tool. Picking one downloads it first (in the background, the Slicer window stays usable), then uses it as input. A second pick of the same entry in the same session reuses the download.
  • A model chosen on the server is picked by name from a list the server publishes. Only the name travels; the model file is never sent from your computer. If the list is empty and the argument has no other way to be given, the panel shows a warning to ask the server maintainer.

Large inputs are sent in parts and checked part by part. If the server publishes a size plan for a cohort folder, the panel splits it into batches, each one an ordinary run.

Progress, cancelling, lost connection

  • The panel reports the server's own phases: request received, preparing the input files, waiting for the GPU, running on the server, packaging the results, finished. An elapsed time runs next to it. A queued run shows "queued".
  • Cancel stops the run on the server as well. There is one Cancel per run; with several runs it reads "Cancel all", and a cohort reads "Cancel the cohort". A cancelled run is not reported as an error.
  • If the connection drops while the server is working, the panel reconnects to the progress stream by itself and picks up where it left off, without repeating what it already showed. This is the detached mode, on by default: the request ends as soon as the inputs are staged and the result arrives on the progress stream, so the timeout in the settings no longer caps how long a run may last.
Stopping for review runs the blocking way

If you arm a "stop after" step (see Quality review), the run does not use the detached mode: the server returns the review material in the answer to the original request. There the timeout from Server Tools Settings applies, and a lost connection loses the answer.

Get the results

  • When the run ends, the panel downloads the result (in parallel ranges), checks the archive, and unpacks it into the output folder. By default that folder is "Slicer Output" in your Documents.
  • An archive is refused before anything is written if it holds absolute paths, .., links, more than 100 000 entries or more than 20 GB.
  • The check box "Load the results into the scene when done" imports what the tool produced: volumes, label maps, models or landmarks, depending on the tool. At most 12 items are loaded by default; beyond that the panel tells you there are too many to load at once.
  • Some tools add their own options or messages: ALI summarizes its run report and asks to confirm above 20 landmark files; VFACE has a "Load the heat maps" box; AutoMatrix has a "Use the mirror matrix" box. CNE loads nothing in the scene and shows a summary in the status bar.
  • The server's copy of the result is deleted after your download.

Quality review with VISU

Some tools can stop after a step so that you check the intermediate result. The form then shows a "Quality control" section with a multiple choice stop_after; nothing is ticked by default. Tools that call other tools offer it, for example ALI for intraoral scans or VFACE.

  1. Stop. The server pauses after the step you ticked. The panel shows "Stopped after <step>, waiting for your review", downloads what was produced so far, and opens VISU on it.
  2. Review. VISU shows one patient at a time: scan, masks, surfaces and landmarks together. The arrow keys go to the previous or next case. Use Flag to mark a patient, and Go to next flagged to jump. Read the line "Drawn on <scan>" (it says which scan the landmarks are drawn on, and whether it was found next to the points or assumed).
  3. Correct. For landmarks, you can drag points and Save: only the points you moved are rewritten, matched by name. Undo my changes and Revert to what is on disk restore them. A registration adjustment is saved as a separate transform file next to the scene, never merged into the tool's own transform.
  4. Continue. Only the files whose content changed are sent back, then the server resumes the run.
  5. Go back. When an earlier step can be corrected (landmarks or a registration), the flag reads "Go back and edit this patient". Once you have flagged some, the green button reads "Go back to <step> for N patient(s)": your corrections are written, the flagged patients are redone from that step, and everyone else keeps the result they already have.

If VISU cannot be found, or the stop produced nothing to look at, the panel says so and resumes the run immediately, so that nothing stays paused on the server with your data in it.

VISU also works on any folder

You can open VISU on any folder a tool wrote, with no server involved: it pairs the scan, the masks, the surfaces and the landmarks of each patient by file name. The only thing it fetches from a server is hosted sample datasets.

What leaves your machine

Nothing is de-identified

No de-identification tool exists in VISOR today. What you select is sent to the server as it sits on disk: file names, DICOM headers and every identifier they carry. A de-identification pipeline is specified in the client repository but its README states it is not implemented, and a search of the code finds no implementation.

  • The notice. After you save a server address that is not this computer, Slicer shows once per server: "Files are uploaded unmodified. This client does not de-identify anything... De-identify your data before selecting it, or confine use to data that carries no protected health information." It is a warning, not a check: it does not stop anything.
  • Folders keep their names. A folder is packed with its original file and sub-folder names. A scene node is exported under a generic name, so its node name does not leave.
  • CNE sends clinical notes. The text model runs on the server: the notes go up and the extractions come back. The legacy CNE page, which says nothing leaves your machine, does not apply to VISOR.
  • Transport only. HTTPS protects the transfer. There is no encryption of the files beyond it on the client side.
  • The Medical Data Anonymizer still exists, but it handles text documents on this machine and is not part of what gets sent.
  • Point the client only at a server your institution controls, and check that the agreement with whoever operates it covers the data you send. The README asks for the same.

The security picture, including what the server does and does not protect, is in VISOR security.

If something goes wrong

For most failures, Slicer shows the server's own message. Here is what each means.

"The server URL must start with https://"

You typed an http:// address, or Slicer found one from an older version. Use the public https:// address; there is no way around the rule, including for a server on your own computer.

401: authentication failed

The key is wrong or missing. The panel can still say "Server: online" because the health page needs no key. Re-enter the key in Server Tools Settings and Save.

503 during a maintenance window

While the server is being updated, it refuses new work with a 503 and a Retry-After: 10 header, for at most 300 seconds. The client does not read that header: you see the server's message, or "Server error (503)". Wait and press Apply again. Reading results already under way is not blocked.

422: invalid arguments

The server names the offending argument, for example an option outside the accepted list. Fix the field it names. A "400" with a file-type message means the file extension is not accepted by that tool.

413: file too large

The server refuses an upload above its limit, 500 MB per file by default. For a large cohort, give a folder rather than one huge archive so that it can be split into batches.

500: "The tool failed on the server"

This is all the client shows for a crash inside a tool, on purpose: the details may contain server internals. Ask whoever runs the server to read its log.

  • Timeouts. The timeout in Server Tools Settings (600 s by default) applies to requests that stay open. In detached mode, which is the default, a long run is not cut by it. The server has no run time limit by default.
  • Waiting in a queue. A run can wait for the GPU: the panel reads "Waiting for the GPU", and you can cancel while it waits. The server also limits how many runs execute at once, so a fifth run may wait before it even appears as queued.
  • Server offline. If the tool list cannot be loaded, the panel says so and shows Retry. Check the address and "Server: online" in Server Tools Settings.
  • A change in config.py has no effect. What you saved in Server Tools Settings always wins over the compiled-in defaults.
