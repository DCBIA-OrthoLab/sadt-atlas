AREG_IOS — register two scans of the same patient

AREG_IOS superimposes two intraoral scans of the same patient taken at two different times — before and after treatment, say — without you having to draw the stable region by hand. It processes a whole batch of patients at once, not one scan at a time.

When to use it

Whenever you want to compare T1 and T2 of the same arch — measuring tooth movement, an arch change under treatment — and drawing the stable region by hand, scan after scan, would take too long across your series. If you only have one patient and would rather keep control over the registration region yourself, FlexReg is the interactive tool for that; AREG_IOS is its automatic, batch counterpart.

Two modes, one per arch

Butterfly (upper arch): the module predicts the stable palatal patch itself, with a network, and uses it as the registration anchor. MGL (lower arch): there's no palate down there, so the module builds a band along the mucogingival line instead, from landmarks it places automatically.

What you need, what you get

To provide

  • Two folders of scans, T1 and T2, in .vtk, .vtp, .stl or .obj
  • Filenames that literally contain T1 or T2, plus an arch marker (Upper/Lower, U/L, Maxilla/Mandible): matching is done on these words
  • The palatal patch model, downloaded once, for Butterfly mode
  • For MGL: a band width in mm, or your own mucogingival landmarks if you already have them

What comes out

  • Per patient: the T1 scan with the registration region marked on it, and the T2 scan registered onto T1
  • In Butterfly, if the lower arch is provided as a pair, it automatically follows the upper arch's registration
  • A transform matrix (.tfm) per patient, but only in some cases — see below
  • Your original files are never modified

Automatic or semi-automatic

This is the second choice to make, independent of which arch you're registering. Auto starts from raw scans: the module segments the teeth and orients the scans itself before registering, so there's nothing to prepare. Semi-auto assumes your scans are already segmented (tooth IDs already assigned) and already share a common orientation; pick it when that work is already done, since it skips straight to registration. In MGL mode, segmentation is still required either way — without tooth IDs, the mucogingival landmarks can't be placed.

Step by step

  1. Pick the regime. Auto for raw scans, semi-auto if they're already segmented and oriented.
  2. Pick the arch. Butterfly for the upper arch, MGL for the lower.
  3. Point to the two input folders, T1 and T2. AREG_IOS pairs up patients on its own from the filenames.
  4. For MGL, set the band width (0 to 20 mm), or point to a folder of mucogingival landmarks if you already have them — otherwise they're placed automatically.
  5. For Butterfly, download the palatal patch model if you haven't already.
  6. Point to an output folder that already exists, then run. A progress bar tracks patients as they complete.

Time and hardware

Butterfly mode needs a compatible graphics card: the palatal patch prediction has no CPU fallback, unlike some other tools in the suite. Without a GPU, this mode simply won't run — use MGL on machines that don't have one. MGL mode doesn't call that network at all; it relies on landmark placement and a geometric band construction instead, both lighter. Either way, processing runs folder by folder, so total time mostly scales with how many patients are in the batch.

If something goes wrong

No compatible graphics card

In Butterfly mode, the palatal patch inference requires a CUDA GPU, full stop. On a machine without a compatible GPU, this mode fails outright. Use MGL on those machines, or process the upper arch elsewhere.

File naming: order matters

Put the arch marker before the timepoint marker in the filename (P001_Upper_T1.vtk), not after (P001_T1_Upper.vtk): in the wrong order, one of the output matrices won't be found — with no blocking error, the run finishes but an expected file is simply missing. Also avoid the same words (Upper, Lower, U, L, Mx, Md…) in parent folder names: they're read from the full path and can throw off the upper/lower sorting for the whole batch.

A failed orientation silently breaks the patch

If the canonical orientation step can't be computed — for instance because the reference teeth weren't identified — processing doesn't stop: the network still runs, on a badly oriented scan, and nothing flags it. Always check the resulting patch visually before trusting it.

MGL never produces a transform

Whichever regime you pick, auto or semi-auto, MGL mode writes no .tfm file at all. You get the registered surfaces, but not the transform that produced them.

Output folder and file formats

The output folder must already exist: AREG_IOS doesn't create missing subfolders. And your files keep their original extension on write even though the content is always rewritten in VTK format — a .stl or .obj coming out is not a strictly valid STL or OBJ file, so keep it for Slicer rather than handing it to another program.

What happens next

The registered T2 scan overlays directly onto T1 in the scene: that's your basis for measuring change between the two timepoints. The marked region on T1 (palatal patch or mucogingival band) is only a registration aid, not a segmentation to interpret on its own — and as noted above, check it before trusting the result.

Further reading

On AREG_IOS itself

  • Hutin et al., ShapeMI 2023 (LNCS 14350) — AReg IOS: Automatic Registration on IntraOralScans. The module's paper: a network isolates the stable palatal region, then an ICP registers the two scans on it.

Around the method

  • Vasilakos et al., Scientific Reports 2017 — Assessment of different techniques for 3D superimposition of serial digital maxillary dental casts on palatal structures. How the various palatal regions compare as superimposition references.
  • Aliaga-Del Castillo et al., Orthod Craniofac Res 2022 — Comparison and reproducibility of three methods for maxillary digital dental model registration in open bite patients. Three registration methods compared on open-bite patients — the case where the choice of region matters most.
  • NA-MIC Project Week 36, 2022 — ALIIOS — Automatic Landmarks Identification for Intra Oral Scans. ALI_IOS, the network that supplies the mucogingival landmarks, has no publication: this project page is its only public description.

The tool's full bibliography — what was found, and what was looked for without success — is in its sources.
