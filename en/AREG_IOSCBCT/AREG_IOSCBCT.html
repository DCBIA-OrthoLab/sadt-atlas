AREG_IOSCBCT — full pipeline

Multimodal registration: placing an Intra Oral Scan into the frame of a CBCT from the same patient. The CLI is entirely geometric — it loads no weights at all.

unpublished areg_ioscbct Slicer's Python no network in the CLI Bibliography

Nothing to do with AREG_IOS, which is longitudinal (T1 → T2, same modality): here the two point clouds come from different sensors, and there is no common "stable patch".

Two successive matching steps, no network inside the CLI:

  1. 12 occlusal landmarks predicted on both sides by two different networks (ALI_CBCT on the volume, ALI_IOS on the mesh) → rigid Procrustes transform (vtkLandmarkTransform) that serves as pre-alignment;
  2. ICP of the IOS surface onto an isosurface of the CBCT extracted by marching cubes at threshold 400.

The CLI itself is therefore entirely geometric. The intelligence lies upstream, in the modules the orchestrator stacks in front of it.

1. Place in the chain

AREG_IOSCBCT/AREG_IOSCBCT.py is called only by AREG/AREG_Method/IOSCBCT.py, which defines three modes. It calls nothing itself.

The 12 shared landmarks

Identical on both sides, this is the pivot of the whole registration:

LL1O LL3O LL6O LR1O LR3O LR6O UL1O UL3O UL6O UR1O UR3O UR6O

Suffix O = occlusal point of the tooth. On the CBCT side they are passed to ALI_CBCT as lm_type, on the IOS side to ALI_IOS as teeth with lm_type='O', image_size=224, blur_radius=0, faces_per_pixel=1 (IOSCBCT.py:335 and IOSCBCT.py:839).

3. Matching the files

getPatients() (AREG_IOSCBCT.py:339) scans the four folders and builds a <patient_id>_<timepoint> key.

Expected extensions: IOS .vtk only, CBCT .nii.gz only, landmarks .json.

Each patient must supply seven entries: ios_upper, ios_lower, cbct, ios_lm_upper, ios_lm_lower, cbct_lm_upper, cbct_lm_lower. A missing key raises a KeyError in the main loop, caught by the per-patient try/except → the patient is simply skipped with an error log.

The same identifier normalization is reimplemented on the widget side in Review._normalisedId() (AREG/AREG_Method/Review.py:210), specifically to find the original CBCT matching a registered IOS whose name has been normalized.

4. Matching the two modalities

Short answer to the three possible hypotheses: shared landmarks for the pre-alignment, then ICP onto a surface extracted from the CBCT by thresholding. There is no tooth segmentation on the CBCT side, and the IOS-side segmentation only serves to let ALI_IOS aim its cameras tooth by tooth.

4.1 The CBCT surface

load_data() (AREG_IOSCBCT.py:315):

image = sitk.ReadImage(scan_path)
ijk_to_lps = np.eye(4)
ijk_to_lps[:3, :3] = direction @ np.diag(spacing)
ijk_to_lps[:3, 3]  = origin
vol = pv.wrap(sitk.GetArrayFromImage(image).transpose(2, 1, 0))
cbct_raw_mesh = vol.contour(isosurfaces=[400])
cbct_surface  = cbct_raw_mesh.transform(ijk_to_lps, inplace=False)
  • GetArrayFromImage gives (z,y,x), the transpose(2,1,0) puts it back into (x,y,z) so that pv.wrap produces an ImageData with unit spacing in index space;
  • contour(isosurfaces=[400]) = marching cubes at value 400. Implicit unit: HU if the CBCT is calibrated. This threshold is hard-coded and captures bone and enamel, undistinguished;
  • the ijk_to_lps matrix, rebuilt by hand, brings the isosurface back into physical LPS coordinates.

This is consistent with the rest: ALI_CBCT and ALI_IOS both write "coordinateSystem": "LPS" (ALI_CBCT/ALI_CBCT_utils/io.py:36, ALI_IOS/ALI_IOS_utils/io.py:85), and the .vtk files are in LPS. No flip is therefore needed, and none is done.

4.2 Matching landmarks by label

_pair_landmarks() (AREG_IOSCBCT.py:54) keeps only the labels present on both sides, in the order of the IOS labels, and logs which ones are missing from the CBCT.

Important fix

vtkLandmarkTransform requires as many source points as target points; with lists of different sizes it writes an error to stderr and returns the identity, so the pre-alignment used to disappear with nothing to say so. And matching two partial lists by position paired points that had nothing to do with each other.

4.3 The rigid pre-alignment

align_by_landmarks() (AREG_IOSCBCT.py:108):

landmark_transform = vtk.vtkLandmarkTransform()
landmark_transform.SetSourceLandmarks(points_moving)   # IOS
landmark_transform.SetTargetLandmarks(points_fixed)    # CBCT
landmark_transform.SetModeToRigidBody()                # 6 dof, no scaling

Two safeguards, both falling back to the identity (a fresh vtk.vtkMatrix4x4()) with an explicit warning:

SafeguardConstantRationale in the code
Number of pairsMIN_LANDMARK_PAIRS = 3one point = pure translation, two points leave a rotation free around the axis
RMS residualMAX_LANDMARK_RESIDUAL_MM = 10.0, overridable via the environment variable AREG_MAX_LANDMARK_RESIDUALa rigid transform preserves distances: a large residual proves the two sets do not describe the same anatomy

_alignment_residual() (AREG_IOSCBCT.py:67) applies the matrix to every moving landmark and computes the RMS of the differences.

Returns the transformed mesh, the matrix, and the transformed IOS landmarks — the latter are what end up in the output json.

4.4 The ICP

run_icp_point_to_plane() (AREG_IOSCBCT.py:163), called with max_dist=1.0 (the default value of 1.5 is never used).

ParameterValueEffect
max_iterations2000
max_dist1.0 mmfarther correspondences rejected (valid_mask)
rmse_threshold1e-8convergence on the change in inlier RMSE
fitness_threshold1e-8convergence on the change in inlier rate
Extra stop condition< 3 valid correspondences
Structurescipy.spatial.cKDTree on the fixed points, built once outside the loop
Querykdtree.query(..., k=1, workers=-1)parallelized across all cores; this is the dominant cost

At each iteration: nearest-neighbor correspondences, filtering by max_dist, then rigid estimation via SVD of Kabsch on the recentered centroids, with determinant correction (Vt[-1,:] *= -1 if det(R) < 0) to forbid reflections. The transformation is composed on the left (transformation = delta @ transformation) and reapplied to the original points on every round, which avoids error accumulation.

The function does not do what its name says

It is called run_icp_point_to_plane; it does compute fixed_normals via compute_normals(inplace=True) on a copy of the fixed mesh — and never uses them. The criterion minimized is ‖R·s + t − d‖², i.e. classic point-to-point. The normals are computed then discarded on every call, twice per patient, on a marching-cubes isosurface that can run to hundreds of thousands of faces.

What the ICP actually registers: the full IOS mesh (every vertex is a moving point) against the entire isosurface at 400 — alveolar bone, enamel, cortical bone, artifacts, thresholding noise. There is no restriction to teeth, no mask, no weighting. What makes the result usable is solely the combination of a good landmark pre-alignment + a 1 mm correspondence window, which in effect eliminates everything that is not right under the occlusal surface.

Unconstrained occlusion

Both arches are registered independently against the same isosurface, with two separate matrices mat_icp_upper and mat_icp_lower — the relative occlusion is not constrained.

5. Outputs

<pid> is the normalized identifier (P1, not P_0001): the output names therefore do not resemble the input names, hence _matchAcrossNaming() in AREG/AREG_Method/Review.py:226.

The output json files are a questionable choice: the container comes from the CBCT (display, ids, order) but the coordinates come from the IOS. _write_positions() (AREG_IOSCBCT.py:81) matches by label, and drops CBCT control points that have no IOS counterpart rather than leaving them at their original position. The previous version indexed by position: a CBCT with one landmark against six on the IOS side wrote the coordinates of UL1O under the label UR6O.

No .tfm is produced

Neither the landmark matrix nor the ICP matrix is written to disk; only the transformed geometries are. This is acknowledged at the widget level: the review page ioscbct_registration is of type VIEW, not REGISTRATION, with the text "This step writes no matrix, so the result cannot be moved here" (AREG/AREG_Method/Review.py:680) — so the operator cannot correct the registration with the mouse the way they can for AREG_IOS or AREG_CBCT.

If no patient could be registered, main() raises a RuntimeError (AREG_IOSCBCT.py:577): the try/except/continue loop otherwise exited with code 0 with an empty output folder, and Slicer reported the pipeline as successful.

7. Pitfalls and fragile points

The 400 threshold is hard-coded

And is never exposed. On a CBCT not calibrated in HU, or with a different reconstruction, the isosurface captures something else and the ICP registers against noise. This is the parameter most likely to need changing from one center to another.

  • run_icp_point_to_plane is point-to-point. The normals are computed and discarded. Either the name is wrong or the implementation is incomplete — either way, a maintainer counting on point-to-plane (better convergence on smooth surfaces, less tangential slippage) will be disappointed.
  • Two modalities, one single CBCT per patient key, but both arches mandatory. A patient for which only the upper arch was scanned raises a KeyError and disappears from the run with a simple log line.
  • The CBCT must be .nii.gz. NumberScan on the widget side, though, counts .nrrd .nii .gipl and their .gz variants (IOSCBCT.py:32): the progress bar can announce patients the CLI will never see.
  • Timepoints limited to T0–T2 by [Tt]([0-2]) — see the TIMEPOINT-SUFFIX comment at AREG_IOSCBCT.py:372 and the central note in AREG_CBCT/AREG_CBCT_utils/utils.py:83.
  • Identifier collision after normalization: P001 and P1 become the same key, hence the same patient. Nothing detects this in getPatients; only the widget, later, warns that there are several candidates (Review.py:243).
  • Dead code: load_data() computes lm_cbct_U/L and lm_ios_U/L via get_landmarks() (positional indexing, no labels), and all four are immediately overwritten by _pair_landmarks() (AREG_IOSCBCT.py:507). Only cbct_surface is used. Likewise: DisplayAREGIOSCBCT is defined twice in AREG/AREG_Method/Progress.py (lines 135 and 182), the second one shadowing the first; and PatientScanLandmark (IOSCBCT.py:40) is called nowhere.
  • DisplayAREGIOSCBCT(0) is instantiated with nb_progress_total = 0 in all three modes: self.progress / 0 → ZeroDivisionError if the progress bar is updated. It is only updated under the condition progress == 200 and updateProgessBar == False, which explains why this goes unnoticed.
  • fitness and inlier_rmse are read after the ICP loop. With max_iterations = 0 (impossible here, but fragile) or an exit at the first break on < 3 correspondences, they are defined — but the code does not guard against it.
  • pyvista is installed in Slicer's Python, pinned to version 0.47.3. This is a heavy dependency that is only there for this module (pv.wrap, contour, transform, read, save) and could be replaced with direct VTK, which is already present.
The pre-alignment can silently be the identity

It is logged as a warning, never as an error: an entire run can have benefited from no pre-alignment at all and still output files. Check the Skipping the pre-alignment log lines before relying on a batch.

8. Literature

Unpublished

No paper covers AREG_IOSCBCT as implemented here. The lineage published by the group covers CBCT orientation and registration (Automated Orientation and Registration of CBCT Scans, LNCS 2023) and longitudinal IOS registration (AReg IOS, LNCS 2023); the landmark modules it consumes each have their own (ALI_CBCT). The multimodal IOS↔CBCT part appears to be an internal, unpublished assembly.

The methodological neighborhood in the literature — for comparison, not as a description of this code:

  • Novel Procedure for Automatic Registration between CBCT and Intraoral Scan Data Supported with 3D Segmentation: same problem, but with tooth segmentation on both sides, then RANSAC + ICP. Reported error 0.234 ± 0.019 mm. AREG_IOSCBCT explicitly takes the lighter path: landmarks instead of volumetric segmentation, thresholded isosurface instead of segmented teeth.
  • Automatic multimodal registration of CBCT and intraoral scans: a systematic review and meta-analysis: systematic review, places geometric approaches (reliable, low-cost) against learned approaches.
  • Fully automatic integration of dental CBCT images and full-arch intraoral impressions: variant with tooth-by-tooth identification and stitching-error correction.
