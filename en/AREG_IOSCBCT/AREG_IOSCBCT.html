AREG_IOSCBCT: full pipeline

Multimodal registration: placing an intraoral scan into the frame of a CBCT from the same patient. The tool itself is entirely geometric and loads no weights. This page explains how, step by step, with the maths; the files, lines and pitfalls are on the code page.

Code (developers) Guide unpublished areg_ioscbct Slicer's Python no network in the CLI VISOR Bibliography

Overview: what goes in, what comes out

Nothing to do with AREG_IOS, which is longitudinal (T1 to T2, same modality): here the two data sets come from different machines, and there is no common stable patch. A CBCT is a volume of grey values, an intraoral scan (IOS) a surface of triangles. The tool works in two stages: a rough placement from 12 occlusal landmarks predicted on both sides, then an ICP of the mesh onto a surface extracted from the CBCT.

What it is
Inputper patient: an upper and a lower intraoral mesh (.vtk), one CBCT (.nii.gz), and a landmark file for each arch on each side
Idea12 matching points give a rigid pre-alignment, then the ICP slides the crowns onto the CBCT surface
Outputthe two arches moved into the CBCT frame, and the CBCT landmark files re-written with the mesh points

Everything numbered below describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, has its own page: AREG_IOSCBCT on VISOR.

1. Place in the chain

The tool is called only by the AREG widget, which defines three modes. So this is an orchestrator with a thin terminal tool: the real pipeline is the list of steps the widget builds in front of it.

ModeSteps stacked before the registration
Registrationnone: you supply the meshes, the CBCTs and both landmark folders
Semi-Automatedcrown segmentation, then the CBCT landmarks, then the IOS landmarks
Fully-Automatednine steps, see the sequence below

The two modalities are prepared separately, then brought into contact at the last moment.

a raw CBCT and a raw intra-oral scan: two modalities, prepared apart, brought into contact only at the end

CBCT path

  1. MRI2CBCT_resample_cbct_mri resamples it isotropically: spacing=[0.3,0.3,0.3], center=True <out>/CBCT Resampled/CBCT
  2. PRE_ASO_CBCT pre-orients it, with the PreASO models predicted <out>/PRE ASO CBCT
  3. ALI_CBCT places the orientation landmarks: N S Ba RPo… or IF ANS PNS UR1O UR6O UL6O, depending on the reference predicted same folder
  4. SEMI_ASO_CBCT orients it onto a gold file, suffix Or <out>/Oriented CBCT
  5. ALI_CBCT runs a second time, for the 12 shared landmarks predicted the occlusal point of each tooth

IOS path

  1. CrownSegmentationcli labels the crowns: Universal_ID, model=latest, suffix=Seg predicted <out>/Seg IOS
  2. PRE_ASO_IOS pre-orients the mesh onto a gold file the oriented arch
  3. ALI_IOS places the same 12 landmarks: lm_type='O', image_size=224, blur_radius=0, faces_per_pixel=1 predicted the occlusal point of each tooth

Where the two paths meet

  1. AREG_IOSCBCT itself: Procrustes, then ICP, on the 12 matched landmarks, computed, no network at all the arch, in the CBCT’s frame

Steps 2, 3, 5, 7 and 8 contain a network; the final CLI contains none: it is pure geometry. Semi mode skips steps 1–4 and 6, taking an already oriented CBCT and an already oriented arch. The numbers are the module’s own, which is why they interleave: the two paths run apart, so a continuous count would suggest an order that does not exist.

In the codeThe widget calls, their arguments and the folders they write

The 12 shared landmarks

Identical on both sides, they are the pivot of the whole registration: LL1O LL3O LL6O LR1O LR3O LR6O UL1O UL3O UL6O UR1O UR3O UR6O. The suffix O means the occlusal point of the tooth (first, third and sixth tooth of each quadrant). On the CBCT they are predicted by ALI_CBCT, an agent that walks through the volume; on the mesh by ALI_IOS, which photographs each tooth from virtual cameras. The registration tool itself loads no weights.

In the codeThe parameters passed to both networks and the weights they use

2. Where it runs

It is a true Slicer command-line module running in Slicer’s own Python, with no GPU and no conda environment. It takes five arguments: the mesh folder, the CBCT folder, the two landmark folders and the output folder. The only step outside Slicer’s Python is the crown segmentation.

In the codeHow the command is launched and which libraries Slicer must hold

3. Matching the files

A patient is recognised by letters stuck to digits followed by a time point T0, T1 or T2; underscores and leading zeros are dropped, so P_0001, P001 and P00001 are the same patient P1. The arch is read from a delimited u/upper or l/lower token. Each patient must bring seven entries: the upper and the lower mesh, the CBCT, and an IOS and a CBCT landmark file for each arch. A patient missing one is skipped with a log line; a T3 never matches and the patient is ignored.

In the codeThe four regular expressions and the seven keys

4. Matching the two modalities

Short answer to the three possible hypotheses: shared landmarks for the pre-alignment, then ICP onto a surface extracted from the CBCT by a threshold. There is no tooth segmentation on the CBCT side, and the IOS-side segmentation only lets ALI_IOS aim its cameras tooth by tooth.

4.1 The CBCT surface

The volume becomes a surface: voxels brighter than a level L are separated from the others by a closed skin of triangles (the marching-cubes contour), which takes bone and enamel alike. The surface is then put back into the physical coordinates of the scan (LPS), the frame in which both ALI tools write their points, so no flip is needed. The level is read off each scan.

400 is only the fallback, used when the crowns are no brighter than their surround, and an environment variable can set the level by hand. The comment above the constant gives the reason for the change: on one patient a fixed 400 moved the arch 2.2 mm away from its landmarks (the authors’ measurement, not re-run here).

In the codeThe loader, the array transposition and the level code

4.2 Matching landmarks by label

Only the labels present on both sides are kept, in the order of the mesh labels, and the missing ones are logged. Pairing by position was an earlier bug: it tied together points that had nothing to do with each other, and the VTK landmark filter, given lists of different lengths, silently returns the identity.

In the codeThe pairing function and the fix that made it label-based

4.3 The rigid pre-alignment

A rigid fit (6 degrees of freedom, no scaling) moves the IOS landmarks onto the CBCT ones. It is refused, and the identity used, with fewer than 3 pairs (one point is a pure translation, two leave a rotation free) or when the residual is above 10 mm: a rigid transform preserves distances, so a large residual proves the two sets do not describe the same anatomy.

Before that fit, a landmark whose neighbourhood in the scan never reaches the contour level is set aside: it is not on a tooth, and in a closed bite it usually landed on the opposing arch. The pairs are then trimmed one per round, never below 4. A set that is nearly in a line only triggers a warning.

In the codeThe fit, the safeguards and the trimming, with their constants

4.4 The ICP

The ICP is a real point-to-plane ICP. Only the crowns of the mesh move through it (the gingiva has no counterpart in a CBCT), against the CBCT surface cropped to a box 25 mm around the arch’s landmarks. A correspondence is kept within 1 mm and when the normals agree.

Each round is a linear least-squares step; if the system is degenerate, or the rotation would exceed 0.5 rad, a plain point-to-point step (the Procrustes fit) is used instead. The ICP stops when the largest shift of any point stays under a thousandth of a millimetre for 3 rounds, or after 300 rounds. An arch that matched under 5% of its points raises an error and nothing is written for that patient. Both arches are registered independently against the same surface, so their relative occlusion is not constrained.

In the codeEvery parameter of the ICP, the two steps and the line numbers

5. Outputs

For each patient: the upper and lower mesh, registered (landmark transform, then ICP), and the two CBCT landmark files with each position replaced by that of the registered mesh landmark of the same label. Names use the normalised identifier, so they do not resemble the input names. Neither matrix is written to disk, so the review page of the widget can only view the result. If no patient could be registered, the run fails instead of finishing with an empty folder.

In the codeThe writers, the naming and the review-page limit

6. What is predicted vs. what is computed

BlockNature
CBCT resampling and orientationgeometric, except the CBCT pre-orientation, a network
CBCT landmarks (two passes)network (ALI_CBCT, reinforcement agents)
Mesh crown segmentationnetwork (DentalModelSeg)
Mesh landmarksnetwork (ALI_IOS, multi-view)
CBCT surfacegeometric, marching cubes at a level read off the scan
Pre-alignmentgeometric, rigid fit, trimmed
ICPgeometric, point-to-plane least squares, KD-tree

In other words: the registration tool learns and predicts nothing. It consumes two sets of landmarks predicted elsewhere and a contoured surface.

7. Pitfalls and fragile points

  • The pre-alignment can silently be the identity: the skip is only a log line (details).
  • The relative occlusion of the two arches is not constrained, since each is registered alone (details).
  • No transform file is written, so the result cannot be corrected by hand afterwards (details).
  • Both arches are mandatory: a patient with only one arch is skipped with a single log line. Only .vtk meshes and .nii.gz CBCTs are read.
  • Time points are limited to T0 to T2, and _T10 to _T29 are misread as T1 or T2; P001 and P1 become the same patient without any warning.
  • Some dead code and a heavy dependency (pyvista, used only here) remain (details).

The contour level, once said to be hard-coded at 400, is read off the scan in this version (details).

8. Literature

No paper covers AREG_IOSCBCT as implemented here. The lineage published by the group covers CBCT orientation and registration (Automated Orientation and Registration of CBCT Scans, LNCS 2023) and longitudinal IOS registration (AReg IOS, LNCS 2023); the landmark modules it consumes each have their own (ALI_CBCT). The multimodal IOS to CBCT part appears to be an internal, unpublished assembly.

The methodological neighbourhood in the literature, for comparison, not as a description of this code:

  • Novel Procedure for Automatic Registration between CBCT and Intraoral Scan Data Supported with 3D Segmentation: same problem, but with tooth segmentation on both sides, then RANSAC + ICP. Reported error 0.234 ± 0.019 mm. AREG_IOSCBCT takes the lighter path: landmarks instead of volumetric segmentation, a thresholded surface instead of segmented teeth.
  • Automatic multimodal registration of CBCT and intraoral scans: a systematic review and meta-analysis: places geometric approaches (reliable, low-cost) against learned approaches.
  • Fully automatic integration of dental CBCT images and full-arch intraoral impressions: variant with tooth-by-tooth identification and stitching-error correction.
