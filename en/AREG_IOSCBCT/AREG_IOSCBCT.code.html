AREG_IOSCBCT, legacy: the code

For developers: what the legacy Slicer module AREG_IOSCBCT does in the code (SlicerAutomatedDentalTools at 3c67957), with file:line references, signatures, arguments, environment and the pitfalls. The readable explanation of the same pipeline, with the maths, is on the atlas page. The VISOR port has its own code page.

Code Atlas (explanation) unpublished areg_ioscbct Slicer's Python no network in the CLI VISOR Guide Bibliography

Nothing to do with AREG_IOS, which is longitudinal (T1 → T2, same modality): here the two point clouds come from different sensors, and there is no common "stable patch".

Two successive matching steps, no network inside the CLI:

  1. 12 occlusal landmarks predicted on both sides by two different networks (ALI_CBCT on the volume, ALI_IOS on the mesh) → rigid Procrustes transform (vtkLandmarkTransform) that serves as pre-alignment;
  2. ICP of the IOS surface onto an isosurface of the CBCT extracted by marching cubes at a level read off the scan (400 only as a fallback; see 4.1).

The CLI itself is therefore entirely geometric. The intelligence lies upstream, in the modules the orchestrator stacks in front of it.

Two code bases

Everything numbered below describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, has its own page: AREG_IOSCBCT on VISOR. The notes that open some boxes below (“Legacy only”, “Also true in VISOR”) compare with that port at SADT-VISOR 6ba2a78; in them ioscbct/ stands for SADT-VISOR tools/AREG/AREG_IOSCBCT/src/sadt_areg_ioscbct/.

1. Place in the chain

Plain-language explanation and maths: atlas page.

AREG_IOSCBCT/AREG_IOSCBCT.py is called only by AREG/AREG_Method/IOSCBCT.py, which defines three modes. It calls nothing itself.

ModeClassSteps stacked before AREG_IOSCBCT
RegistrationReg_IOSCBCT (IOSCBCT.py:383)none: the user supplies IOS, CBCT and both landmark folders
Semi-AutomatedSemi_IOSCBCT (IOSCBCT.py:149)CrownSegmentationcli → ALI_CBCT → ALI_IOS
Fully-AutomatedAuto_IOSCBCT (IOSCBCT.py:460)8 steps, see the full sequence

So this is indeed an orchestrator with a thin terminal CLI. The real pipeline is the list of processes built by Process().

Full sequence of the Fully-Automated mode

Plain-language explanation and maths: atlas page.

IOSCBCT.py:580. The two modalities are prepared separately, then brought back into contact at the last moment.

a raw CBCT and a raw intra-oral scan: two modalities, prepared apart, brought into contact only at the end

CBCT path

  1. MRI2CBCT_resample_cbct_mri resamples it isotropically: spacing=[0.3,0.3,0.3], center=True <out>/CBCT Resampled/CBCT
  2. PRE_ASO_CBCT pre-orients it, with the PreASO models predicted <out>/PRE ASO CBCT
  3. ALI_CBCT places the orientation landmarks: N S Ba RPo… or IF ANS PNS UR1O UR6O UL6O, depending on the reference predicted same folder
  4. SEMI_ASO_CBCT orients it onto a gold file, suffix Or <out>/Oriented CBCT
  5. ALI_CBCT runs a second time, for the 12 shared landmarks predicted the occlusal point of each tooth

IOS path

  1. CrownSegmentationcli labels the crowns: Universal_ID, model=latest, suffix=Seg predicted <out>/Seg IOS
  2. PRE_ASO_IOS pre-orients the mesh onto a gold file the oriented arch
  3. ALI_IOS places the same 12 landmarks: lm_type='O', image_size=224, blur_radius=0, faces_per_pixel=1 predicted IOSCBCT.py:327-337, :838-848

Where the two paths meet

  1. AREG_IOSCBCT itself: Procrustes, then ICP, on the 12 matched landmarks, computed, no network at all the arch, in the CBCT’s frame

Steps 2, 3, 5, 7 and 8 contain a network; the final CLI contains none: it is pure geometry. Semi mode skips steps 1–4 and 6, taking an already oriented CBCT and an already oriented arch. The numbers are the module’s own, which is why they interleave: the two paths run apart, so a continuous count would suggest an order that does not exist.

Semi mode skips 1–4 and 6: it segments the IOS, then runs the two ALI steps directly and the registration. Its IOS_folder points to <out>/Seg IOS/liste_csv_file_Seg, the subfolder that CrownSegmentationcli creates from the basename of the csv it was given (IOSCBCT.py:359).

The 12 shared landmarks

Plain-language explanation and maths: atlas page.

Identical on both sides, this is the pivot of the whole registration:

LL1O LL3O LL6O LR1O LR3O LR6O UL1O UL3O UL6O UR1O UR3O UR6O

Suffix O = occlusal point of the tooth. On the CBCT side they are passed to ALI_CBCT as lm_type, on the IOS side to ALI_IOS as teeth with lm_type='O', image_size=224, blur_radius=0, faces_per_pixel=1 (IOSCBCT.py:327-337 and IOSCBCT.py:838-848).

The two network families are therefore:

3. Matching the files

Plain-language explanation and maths: atlas page.

Each patient must supply seven entries: ios_upper, ios_lower, cbct, ios_lm_upper, ios_lm_lower, cbct_lm_upper, cbct_lm_lower. A missing key raises a KeyError in the main loop, caught by the per-patient try/except → the patient is skipped, with the error and its traceback in the log (AREG_IOSCBCT.py:1304).

The same identifier normalization is reimplemented on the widget side in Review._normalisedId() (AREG/AREG_Method/Review.py:243), specifically to find the original CBCT matching a registered IOS whose name has been normalized.

4. Matching the two modalities

Plain-language explanation and maths: atlas page.

Short answer: shared landmarks for the pre-alignment, then ICP onto a surface extracted from the CBCT by thresholding. There is no tooth segmentation on the CBCT side, and the IOS-side segmentation lets ALI_IOS aim its cameras tooth by tooth, and its tooth labels (Universal_ID) also pick the crowns that drive the ICP (AREG_IOSCBCT.py:545-576,750-754, see 4.4).

4.1 The CBCT surface

Plain-language explanation and maths: atlas page.

load_data() (AREG_IOSCBCT.py:969-1004, abridged):

image = sitk.ReadImage(scan_path)
image_array = sitk.GetArrayFromImage(image)
ijk_to_lps = np.eye(4)
ijk_to_lps[:3, :3] = direction @ np.diag(spacing)
ijk_to_lps[:3, 3] = origin
level = surface_threshold(image_array, ijk_to_lps, all_landmarks, patient_id)
vol = pv.wrap(image_array.transpose(2, 1, 0))
cbct_raw_mesh = vol.contour(isosurfaces=[level])
cbct_surface = cbct_raw_mesh.transform(ijk_to_lps, inplace=False)
  • GetArrayFromImage gives (z,y,x), the transpose(2,1,0) puts it back into (x,y,z) so that pv.wrap produces an ImageData with unit spacing in index space;
  • contour(isosurfaces=[level]) = marching cubes at a level measured on the scan (see the box below). The isosurface captures bone and enamel, undistinguished;
  • the ijk_to_lps matrix, rebuilt by hand, brings the isosurface back into physical LPS coordinates.

This is consistent with the rest: ALI_CBCT and ALI_IOS both write "coordinateSystem": "LPS" (ALI_CBCT/ALI_CBCT_utils/io.py:39, ALI_IOS/ALI_IOS_utils/io.py:74), and the .vtk files are in LPS. No flip is therefore needed, and none is done.

The level is read off the scan, not hard-coded

An earlier version of this page described a fixed level of 400. At 3c67957 load_data contours at surface_threshold(...) (AREG_IOSCBCT/AREG_IOSCBCT.py:986-1002): half-way between the enamel plateau read at the CBCT landmarks and the soft tissue around the arch, both measured over the landmarks of both arches together (AREG_IOSCBCT.py:847-893,940-966,986-990), 400 only when the crowns are no brighter than their surround (AREG_IOSCBCT.py:952-960), and the environment variable AREG_CBCT_SURFACE_THRESHOLD overrides it (AREG_IOSCBCT.py:92,943-950). The comment above the constant gives the reason: on one patient a fixed 400 moved the arch 2.2 mm away from its landmarks (AREG_IOSCBCT.py:73-80, the authors' measurement, not re-run here).

4.2 Matching landmarks by label

Plain-language explanation and maths: atlas page.

_pair_landmarks() (AREG_IOSCBCT.py:203-213) keeps only the labels present on both sides, in the order of the IOS labels, and logs which ones are missing from the CBCT.

Important fix

Also true in VISOR, and enforced. The two landmark sets are intersected by label and at least 3 common labels are required (SADT-VISOR ioscbct/pipeline.py:136-155; see AREG_IOSCBCT on VISOR); align_by_landmarks raises on sets of different sizes instead of returning the identity (ioscbct/geometry.py:34-51). Legacy: _pair_landmarks, AREG_IOSCBCT.py:203-213@3c67957.

vtkLandmarkTransform requires as many source points as target points; with lists of different sizes it writes an error to stderr and returns the identity, so the pre-alignment used to disappear with nothing to say so. And matching two partial lists by position paired points that had nothing to do with each other.

4.3 The rigid pre-alignment

Plain-language explanation and maths: atlas page.

align_by_landmarks() (AREG_IOSCBCT.py:399):

landmark_transform = vtk.vtkLandmarkTransform()
landmark_transform.SetSourceLandmarks(points_moving)   # IOS
landmark_transform.SetTargetLandmarks(points_fixed)    # CBCT
landmark_transform.SetModeToRigidBody()                # 6 dof, no scaling

Two safeguards, both falling back to the identity (a fresh vtk.vtkMatrix4x4()) with an explicit warning:

SafeguardConstantRationale in the code
Number of pairsMIN_LANDMARK_PAIRS = 3one point = pure translation, two points leave a rotation free around the axis
RMS residualMAX_LANDMARK_RESIDUAL_MM = 10.0, overridable via the environment variable AREG_MAX_LANDMARK_RESIDUALa rigid transform preserves distances: a large residual proves the two sets do not describe the same anatomy

_alignment_residual() (AREG_IOSCBCT.py:226) applies the matrix to every moving landmark and computes the RMS of the distances to their counterparts.

Before and around that fit, _fit_rigid_without_outliers() (AREG_IOSCBCT.py:331) decides which pairs count (the VISOR port has the same rules, see the table on the VISOR code page):

  • a landmark the scan says is not on a tooth is set aside first, whatever the others look like: the brightest voxel within 2 voxels (ENAMEL_PROBE_RADIUS_VOXELS, :97) is under the contour level (_landmarks_on_enamel, :896), provided 3 pairs remain;
  • the rest is trimmed one pair per round: the pair whose removal gives the best fit is dropped if it sits more than LANDMARK_OUTLIER_FLOOR_MM = 3.0 from where the others put it and the fit without it is at most LANDMARK_OUTLIER_IMPROVEMENT = 0.75 times the residual, never below MIN_LANDMARK_PAIRS_AFTER_TRIM = 4 pairs (:142-149, :331-397);
  • a set that is nearly in a line only gets a warning, under MIN_LANDMARK_SPREAD_RATIO = 0.10 (:49).

The residual that is compared with 10 mm is the one over the pairs actually fitted, and the transformed landmarks and the list of kept labels come back with the matrix, to be checked after the ICP (_report_landmark_drift, :240, warning above MAX_ICP_LANDMARK_DRIFT_MM = 1.0).

4.4 The ICP

Plain-language explanation and maths: atlas page.

Corrected: a point-to-plane ICP capped at 300 iterations (3c67957)

An earlier version of this section described a point-to-point ICP (Kabsch/SVD on centroids), up to 2000 iterations, stopping on a change of 1e-8 in RMSE and fitness, on the whole IOS mesh against the whole isosurface. Read against 3c67957, none of that holds: the step is point-to-plane (_point_to_plane_step, AREG_IOSCBCT.py:579), the cap is ICP_MAX_ITERATIONS = 300 (:188; the comment above it says 2000 was the old cap), the stop test is on the shift of the points (:180-181), the moving points are the crowns and the target is cropped around the arch (:545, :485). The Procrustes step is only the fallback (:609).

run_icp_point_to_plane() (AREG_IOSCBCT.py:719) is called once per arch with max_dist=1.0 (the default of 1.5 is never used), on a copy of the CBCT surface cropped around that arch's landmarks (:1239-1255). It runs _icp_run() (:627) once per reading of the CBCT normals and keeps the better one.

ParameterValueEffect

The transformation is composed on the left (transformation = delta @ transformation) and reapplied to the original points on every round, which avoids accumulating error. The linearised system is built from, for each correspondence (p, q, n), the residual (p - q)·n + w·(p x n) + t·n (docstring of _point_to_plane_step, :579-590).

Unconstrained occlusion

Also true in VISOR. Each mesh gets its own landmarks, its own pre-alignment and its own ICP, and its own matrix (ioscbct/dispatch.py:238-258); nothing constrains the relative occlusion. A mesh without landmarks fails alone (ioscbct/dispatch.py:240-246,262-264). Legacy: two matrices, AREG_IOSCBCT.py:1246-1253@3c67957.

Both arches are registered independently against the same isosurface, with two separate matrices mat_icp_upper and mat_icp_lower: the relative occlusion is not constrained.

5. Outputs

Plain-language explanation and maths: atlas page.

save_registered_ios() (AREG_IOSCBCT.py:804) and apply_matrix_and_save_landmarks() (AREG_IOSCBCT.py:810), all within <output> (= <folder_output>/Registered IOS in the Semi and Auto modes):

FileContent

<pid> is the normalized identifier (P1, not P_0001): the output names therefore do not resemble the input names, hence _matchAcrossNaming() in AREG/AREG_Method/Review.py:259.

The output json files are a questionable choice: the container comes from the CBCT (display, ids, order) but the coordinates come from the IOS. _write_positions() (AREG_IOSCBCT.py:282) matches by label, and drops CBCT control points that have no IOS counterpart rather than leaving them at their original position. The previous version indexed by position: a CBCT with one landmark against six on the IOS side wrote the coordinates of UL1O under the label UR6O.

No .tfm is produced

Legacy (3c67957); half true in VISOR. VISOR still writes no .tfm, but it does write the composed 4x4 matrix of each mesh as a numpy file, <stem>_<suffix>_matrix.npy (ioscbct/dispatch.py:258; the composition is refinement @ matrix, ioscbct/pipeline.py:212). The Slicer review page quoted below is legacy only.

Neither the landmark matrix nor the ICP matrix is written to disk; only the transformed geometries are. This is acknowledged at the widget level: the review page ioscbct_registration is of type VIEW, not REGISTRATION, with the text "This step writes no matrix, so the result cannot be moved here" (AREG/AREG_Method/Review.py:794-803), so the operator cannot correct the registration with the mouse the way they can for AREG_IOS or AREG_CBCT.

If no patient could be registered, main() raises a RuntimeError (AREG_IOSCBCT.py:1312): the try/except/continue loop otherwise exited with code 0 with an empty output folder, and Slicer reported the pipeline as successful.

7. Pitfalls and fragile points

Plain-language explanation and maths: atlas page.

Corrected: the isosurface level is read off the scan (3c67957)

An earlier version of this callout said that the 400 threshold is hard-coded and never exposed. At 3c67957 it is neither: the level is the half-way point between enamel and soft tissue measured on the scan, 400 is the fallback, and AREG_CBCT_SURFACE_THRESHOLD overrides it (AREG_IOSCBCT/AREG_IOSCBCT.py:92,847-966). The sensitivity to the reconstruction still applies in the fallback case, which the log reports as a warning.

In VISOR the same rule is kept (SADT-VISOR ioscbct/volume.py:96-117,148-175) and the fallback is 400 (ioscbct/volume.py:36), but the explicit override is gone: see the finding on the level on AREG_IOSCBCT on VISOR.

  • run_icp_point_to_plane is point-to-plane, as its name says. The normals are used: the CBCT normals decide which correspondences are kept and give the tangent planes of the step. An earlier version of this page said the function was point-to-point with the normals computed and discarded; that does not match 3c67957 (AREG_IOSCBCT.py:579-608,688-692). The Procrustes step (:609) is the fallback for a degenerate system.
  • Two modalities, one single CBCT per patient key, but both arches mandatory. A patient for which only the upper arch was scanned raises a KeyError ('ios_lower') and drops out of the run: the error is logged with its traceback (AREG_IOSCBCT.py:1303-1305) and the other patients go on.
  • The CBCT must be .nii.gz. NumberScan on the widget side, though, counts .nrrd .nii .gipl and their .gz variants (IOSCBCT.py:25): the progress bar can announce patients the CLI will never see.
  • Timepoints limited to T0–T2 by [Tt]([0-2]): see the TIMEPOINT-SUFFIX comment at AREG_IOSCBCT.py:1068 and the central note in AREG_CBCT/AREG_CBCT_utils/utils.py:56; _T10 to _T29 are read as T1 or T2.
  • Identifier collision after normalization: P001 and P1 become the same key, hence the same patient. Nothing detects this in getPatients; only the widget, later, warns that there are several candidates (Review.py:280).
  • Half-dead code: load_data() reads lm_cbct_u/l and lm_ios_u/l through get_landmarks() (positional indexing, no labels, AREG_IOSCBCT.py:971-974), and main() immediately overwrites all four with the label-matched arrays from _pair_landmarks() (AREG_IOSCBCT.py:1204-1207). It is not all waste: load_data() uses the CBCT arrays to read the contour level and to judge which landmarks sit on enamel (:988-999), and returns that verdict as on_enamel, which main() hands to align_by_landmarks (:1217-1226); the four returned arrays are the unused part. Likewise PatientScanLandmark (IOSCBCT.py:33) is called nowhere in this module (the only other definition is in ASO_Method/CBCT.py).
  • DisplayAREGIOSCBCT(0) (defined once, Progress.py:127) is instantiated with nb_progress_total = 0 in all three modes: self.progress / 0 → ZeroDivisionError if the progress bar is updated. It is only updated under the condition is_event(progress, PATIENT_DONE) and updateProgressBar == False (Progress.py:141; PATIENT_DONE = 200, ADT/ADTLib/progress_protocol.py:36), which explains why this goes unnoticed.
  • fitness and inlier_rmse are read after the ICP loop. With max_iterations = 0 (impossible here, but fragile) or an exit at the first break on < 3 correspondences, they are defined, but the code does not guard against it.
  • pyvista is installed in Slicer's Python, pinned to version 0.47.3. This is a heavy dependency that is only there for this module (pv.wrap, contour, transform, read, save) and could be replaced with direct VTK, which is already present.
The pre-alignment can silently be the identity

Legacy (3c67957); softened in VISOR. The legacy pre-alignment is skipped with a log line (AREG_IOSCBCT.py:416,425@3c67957). VISOR puts the verdict in the report, per mesh: prealignment.accepted and reason (ioscbct/geometry.py:293-294,306-307,319-321). A refused pre-alignment is still not an error: the mesh is written if the ICP holds, and an ICP that matches under 5% of the arch is refused (ioscbct/pipeline.py:192-202).

It is logged as a warning, never as an error: an entire run can have benefited from no pre-alignment at all and still output files. Check the Skipping the pre-alignment log lines before relying on a batch.

8. Literature

Plain-language explanation and maths: atlas page.

Unpublished

No paper covers AREG_IOSCBCT as implemented here. The lineage published by the group covers CBCT orientation and registration (Automated Orientation and Registration of CBCT Scans, LNCS 2023) and longitudinal IOS registration (AReg IOS, LNCS 2023); the landmark modules it consumes each have their own (ALI_CBCT). The multimodal IOS↔CBCT part appears to be an internal, unpublished assembly.

The methodological neighborhood in the literature, for comparison, not as a description of this code:

  • Novel Procedure for Automatic Registration between CBCT and Intraoral Scan Data Supported with 3D Segmentation: same problem, but with tooth segmentation on both sides, then RANSAC + ICP. Reported error 0.234 ± 0.019 mm. AREG_IOSCBCT explicitly takes the lighter path: landmarks instead of volumetric segmentation, thresholded isosurface instead of segmented teeth.
  • Automatic multimodal registration of CBCT and intraoral scans: a systematic review and meta-analysis: systematic review, places geometric approaches (reliable, low-cost) against learned approaches.
  • Fully automatic integration of dental CBCT images and full-arch intraoral impressions: variant with tooth-by-tooth identification and stitching-error correction.
