AMASSS

AMASSS cuts a head scan into anatomical structures with one network per structure, one voxel at a time. This page explains how a run goes in the legacy Slicer module, step by step, with the maths of the parts that are computation rather than learning: how the scan is normalised, how the network’s patches are blended, how masks are merged and surfaces built. Where the code does something worth checking, a link leads to the code page.

Code (developers) Gillot 2022 · PLOS ONE AMASSS_CLI Slicer's Python, no conda VISOR Bibliography

Overview: what goes in, what comes out

AMASSS takes a 3D head scan (CBCT) and cuts it into anatomical structures: lower jaw, upper jaw, cranial base, upper airway, neck vertebrae, skin and three registration masks. It uses one network per structure: each network answers one question for every voxel, “is this voxel part of my structure?”. The module is a Slicer widget that starts a command-line program in Slicer’s own Python.

InWhat happensOut
a scan (.nii, .nii.gz, .nrrd...) or a folder of them, and the structures wantedeach scan is converted, each structure is predicted by its own network, one structure after the other, and the masks are assembledone binary mask per structure and/or one merged label map per scan, optional 3D surfaces (.vtk)

This page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The server port is AMASSS on VISOR.

1. Where it sits in the chain

AMASSS is both a module of its own and a building block: AREG_CBCT uses it twice, first for registration masks (one file per structure) and afterwards for deliverable segmentations, and VFACE uses it inside its asymmetry-analysis chain. All of them run the same command-line program. AMASSS calls nothing else. Its one external dependency is the pip package nnU-Net.

An important distinction for AREG: the three mask structures (CBMASK, MANDMASK, MAXMASK) are not post-processing of the cranial base, mandible and maxilla. They are separately trained models, on other data and at a different resolution.

In the codeThe caller table with file and line

2. Files involved

Two parts: a Slicer widget that collects the choices, and a command-line program that does all the work (model lookup, inference, assembly). Both run in Slicer’s Python: no conda environment. A graphics card is not required, but on a batch the CPU is unusable in practice, because single-core resampling dominates. The program receives its twelve arguments by position.

In the codeThe file table and the twelve positional arguments in order

3. Inputs and preprocessing

3.1 File discovery

A file or a folder is accepted; a folder is walked recursively, because AREG writes its registered scans into sub-folders. Files kept have a volume extension. Two kinds of name are skipped: any name containing MASK, and, unless the input is a segmentation, any name containing the prediction ID, which is the output of an earlier run (re-segmenting it would give an empty mask).

3.2 Conversion

Each scan is copied into one folder under a numbered name (p_000, p_001...), in discovery order. A .nii.gz is copied as is; everything else is re-read and rewritten, because nnU-Net picks its reader from the file extension. The voxel type is left alone, since nnU-Net casts to float itself.

3.3 What AMASSS no longer does

No intensity normalisation, windowing or resampling is written in this repository: the old windowing function is an empty shell that nothing calls. All the effective preprocessing is nnU-Net’s own, described by the plan of each model: resampling to the target spacing, then intensity normalisation.

In the codeThe discovery filters, the conversion function and the dead windowing function

4. The models

4.1 The bundle and its discovery

For each requested structure the program looks, inside the model folder, for a model folder with a trained checkpoint of a single fold. A structure with no checkpoint is declared unavailable and the run goes on with the others. The “Download latest models” button fetches the archive (about 2 GB) once; the same archive is the one AREG and VFACE download automatically.

4.2 What the bundle actually contains

Nine folders, one per structure, each with a single trained fold. They fall in two families: full-field models (mandible, maxilla, cranial base, cervical vertebra, upper airway, skin) at 0.4 mm isotropic with 128-voxel patches, and the three registration masks at 0.3 mm with larger patches in two directions. All nine share one architecture: a plain convolutional 3D U-Net configured by nnU-Net, with six stages and no residual blocks.

Each model is binary: it only knows background and one structure. The final value of a structure in a merged volume is assigned by the program, not by the model.

Three codes have no model in the bundle: root canal, teeth and mandibular canal. The last two are disabled in the panel; root canal is not, and is even checked by default (see pitfalls).

4.4 Inference

The program does not write a sliding window of its own: nnU-Net handles it from the patch size of each model’s plan. The only parameters the program chooses are a step of 0.5 (patches overlap by half), Gaussian weighting on, and test-time mirroring off.

The loop is per structure, not per scan: all the scans go through one model before the next model is loaded, so a checkpoint is loaded S times instead of N × S. The model path is explicit, since a process-wide environment variable would let two runs overwrite each other’s path. A structure that fails is recorded and the run continues; it fails only if all of them fail.

5. The algorithmic core (not learned)

5.1 GPU resampling

According to the code comment, single-core resampling costs about seven times as much as the network, so the program substitutes a torch resampler that runs on the graphics card. The numerical difference is accepted on purpose: the input goes from third-order to first-order interpolation, because torch has no 3D cubic interpolation. If the card runs out of memory, the structure is replayed with the slower resampler.

In the codeThe resampler substitution, its safeguards and the memory fallback

5.2 Assembly and writing

For each scan, the prediction of each structure is read back and turned into a binary mask (any value above zero). Then the masks are written one per structure, merged, or both. A merged map needs at least two structures. The order is a priority order: the last structure written overwrites the previous ones on shared voxels. The list includes a code that exists in no dictionary, which is dead.

Each mask is cast to 16-bit integers and given the scan’s spacing, direction and origin. Its geometry is checked and resampled by nearest neighbour only if it differs, which does not happen in the normal case.

In the codeThe assembly function, the merge order and the geometry check

5.3 Post-processing: what’s no longer there

No hole filling, no connected-component selection and no morphology is applied. Two functions for it remain and nothing calls them. The earlier version cleaned every structure except two and cropped the skin; the nnU-Net port removed these calls, so cleanup now relies on nnU-Net’s own post-processing, if the bundle ships one.

5.4 VTK surface generation

Two modes: merged, one file with all the labels appended, and separate, one file per structure. Each cell gets one constant colour from the structure’s colour. Meshes are written in the image’s own coordinates, with no flip between LPS and RAS.

In the codeThe surface function, smoothing and the two modes

6. Post-processing and outputs

Names are built from the scan name and the prediction ID: one file per structure, one merged file, and a .vtk file if surfaces are requested. With the per-scan folder option, everything goes into a result folder named after the scan; otherwise directly into the output folder. The temporary folder is wiped at both the start and the end of a run, and the input copies are deleted as soon as inference finishes.

On the widget side, the surfaces are loaded into the scene at the end, but only for a single-file input saved next to the original, with the surface box checked.

8. Environment

Everything runs in Slicer’s Python. The libraries are installed when you press Predict, after a confirmation. Versions are mostly unpinned; NumPy is pinned to 1.26.4, because the torch build used here is built against NumPy 1.x and NumPy 2 breaks its import. No WSL, no conda: unlike the IOS modules (FlexReg, AREG_IOS, ALI_IOS), AMASSS uses no external environment. The table of versions is on the code page.

9. Pitfalls and fragile points

Each point is checked in the code and described, with its evidence, on the code page.

  • The small-field option does nothing: ticking it only changes the list of boxes. Evidence.
  • DICOM input is ignored: the panel offers it but the program has no conversion. Evidence.
  • Root canal is checked by default although no model exists. Evidence.
  • The temporary folder is shared and wiped, so two concurrent runs erase each other’s work. Evidence.
  • The link between case number and file is kept only in memory; a crash leaves anonymous predictions. Evidence.
  • The structure code is re-read from the file name when making separate surfaces, so an underscore in the prediction ID or the scan name raises an error. Evidence.
  • The widget and the program count scans differently (extensions, skipped names). Evidence.
  • The widget’s cleanup removes a path relative to Slicer’s working folder, unrelated to the temporary folder. Evidence.
  • Dead code: several functions and widget parts do nothing. Evidence.
  • The paper and the code diverge: the paper describes a MONAI UNETR, the code runs nnU-Net. Evidence.

10. Literature

The 2022 PLOS ONE paper (Gillot et al.) describes a MONAI UNETR model with a 128-voxel crop, a transformer encoder and a convolutional decoder. The code that runs today is a purely convolutional nnU-Net v2 network, in the legacy and in VISOR. The comparison is on the code page; the references are in SOURCES.md.
