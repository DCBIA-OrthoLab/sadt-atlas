ADTLib

Not a tool: no interface, no pipeline, no model. ADTLib is the code the twenty modules import, and almost every one of its files exists because the same function had been copied between two and fifteen times. Each module header records how many copies it replaced and what the copies had started to disagree about — that count is the point of this page.

Note

This page describes ADT/ADTLib on upstream/main, and it is the only page of this atlas that documents code no user ever opens. It is here because module behaviour now depends on it: a reader chasing what AREG does with a surface ends up in ADTLib/io/surface.py, not in AREG/.

1. Where it sits

Under everything, and inside no pipeline. ADTLib is declared first in the extension's CMakeLists.txt — "Shared code, declared before the modules that import it" — and the twenty tool directories import from it. It has no Process of its own, nothing to run, and nothing to download.

Its own measure of itself, from the module headers: twenty-one modules, about 3 300 lines, replacing copies that together ran to several thousand. The header of theming.py alone accounts for 1 926 lines of duplicate, and env/conda.py for 656 across forty functions.

2. How a module reaches it

Slicer puts each extension's qt-scripted-modules directory on sys.path, so a plain import ADTLib works from any module of the extension and from a scripted CLI. A third route matters more than it looks: once the modules publish Slicer's module search paths into the shapeaxi Conda environment, ADTLib is importable there too. That is what ADTLib.env.install_pytorch relies on — it is never imported by a widget, it is run as python -m ADTLib.env.install_pytorch by the Conda interpreter.

Pitfall

ADTLib/__init__.py and io/__init__.py must stay free of imports. They run in the lean Conda environment too, which has neither vtk, nor qt, nor slicer. A single import of one of those at package level would break every submodule import on that route. Submodules that need them import them themselves. package_root() exists for the same reason: it returns the directory that has to be on PYTHONPATH for the Conda side to find the package.

3. The shared contract

Three modules carry what the tools promise each other, rather than what they compute.

ModuleWhat it replacedWhat it settles
method.pysix Method(ABC) declarations, 934 lines mostly contract rather than codea core (Process, TestProcess, NumberScan, search) plus three mixins — landmarks, checkboxes, DICOM — because the six did not overlap at random: measured side by side, three clusters stood out sharply
requests.pynothing; it names what was never written down473 kwargs["..."] accesses with no list anywhere. Each family now declares its fields, an unknown key is rejected at construction, and a missing one is MISSING — raising the same KeyError as before, at the same place, rather than becoming a silent empty value
progress_protocol.pythree undocumented conventions on one channelsee below
Defect confirmed in the code

Slicer multiplies <filter-progress> by a hundred, and that factor is written down nowhere. It produced three conventions in one repository: a CLI printing the fraction 0.42 makes 42 appear and the bar advances — the intended use; a CLI printing the integer 2 makes 200 appear, which no bar can represent, so the interfaces compare against 200 to learn that one more patient is done, and the CLI sends it as a pulse 0 → 2 → 0 because Slicer only notifies the widget when the value changes; and AMASSS, receiving both, guessed at run time which one it held (if progress > 1: progress /= 100). The three are now named, with the constants carrying the value as the interface sees it, since that is where the comparison happens.

4. The environment

Four modules, and the only part of ADTLib that reaches outside the process.

ModuleWhat it replaced
env/conda.pysix copies of each function — forty functions, 656 lines — drifted into three shapes, one still holding an unreachable return in check_lib_wsl that read two names nothing had bound
env/deps.pynine copies of check_lib_installed under three incompatible answers to the same question: AREG and FlexReg wrote if required_version: pass, true as soon as the library was installed at all — the constraint was decoration
env/cuda.pythe architecture-list problem: a torch wheel carries compiled kernels for a fixed list of architectures
env/install_pytorch.pythe pytorch3d wheel tag, computed from the installed torch rather than left to pip
Pitfall

A pytorch3d wheel whose tag does not match the installed torch crashes with undefined symbol on import, not at install time. The tag 0.7.9+pt2110cu128 means torch 2.11.0 and CUDA 12.8; the index is ImageMindAnalytics.github.io/pytorch3d-wheels, because PyPI publishes no wheel for modern combinations and the historical fbaipublicfiles index stopped at Python 3.9 / torch 2.0. torch is installed here too, since computing the tag from whatever torch happens to be present only works if that torch has a wheel at all: condaCreateEnv(["torch>=2.8,<2.13", …]) resolved to 2.12.1+cu130 on 2026-09-16, a combination the index does not publish.

7. What the tests pin down

ADTLib ships 22 tests in ADT/Testing/Python/, up from two. They are the closest thing to a specification this shared layer has, and several were written because grepping was not enough.

test_pip_requirements.py says why in its own header: every (library, version) pair the repository hands to pip must parse, because f'{lib}=={version}' is correct only while every entry carries a bare version — and three modules had quietly gained a constraint with an operator, producing dicom2nifti==>=2.6.2, which pip refuses outright. The defect is invisible on a machine that already has the library, so no amount of running the module locally shows it. The test walks the source rather than a hand-written list, so a list that gains a constraint tomorrow is covered without anyone remembering.

The others name behaviours the tool pages describe: test_ali_cbct_bounds.py, test_ali_cbct_budget.py, test_ali_progress_contract.py, test_aso_cbct_report_is_not_landmarks.py, test_aso_ios_landmark_intersection.py, test_areg_review_skips_the_report.py, test_output_folder_survives_mode_switch.py, plus the unit tests of the shared modules themselves — test_fs, test_labels, test_naming, test_surface, test_requests, test_progress_protocol, test_deps, test_cuda_channel, test_context_managers, test_button_style.

Verified

Run under a plain PythonSlicer, the suite reports 188 tests and 4 errors. The four are ModuleNotFoundError: torch in the ALI_CBCT tests, which reach ADTLib/env/cuda.py's preferred_device() at import time. They are a property of the environment, not of the code: no torch, no device probe.

8. Reading this layer

Two habits make it legible. First, every module header states what it replaced and what the copies disagreed about — that is where the reasoning lives, not in this page. Second, the line that recurs across those headers is what was left out: the variants that genuinely diverge stay in their tool. TestScan and TestModel are not in method.py because their arities plainly differ from one tool to the next — up to four arguments in AREG — and getModelUrl returns a per-tool selection. Lifting them would have meant inventing a contract none of the six actually honoured.
