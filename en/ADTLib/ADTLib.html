ADTLib

Not a tool: no interface, no pipeline, no model. ADTLib is the code the twenty modules import, and almost every one of its files exists because the same function had been copied between two and fifteen times. Each module header records how many copies it replaced and what the copies had started to disagree about: that count is the point of this page. The file-level details are on the code page.

Shared code Code (developers)

This page describes ADT/ADTLib on upstream/main, and it is the only page of this atlas that documents code no user ever opens. It is here because module behaviour now depends on it: a reader chasing what AREG does with a surface ends up in the shared surface reader, not in AREG/. Evidence.

Overview: what modules take from it

AreaWhat a module getsWhat it replaced

1. Where it sits

Under everything, and inside no pipeline. ADTLib is declared first in the extension’s build file, “Shared code, declared before the modules that import it”, and the twenty tool directories import from it. It has no processing of its own, nothing to run, and nothing to download.

Its own measure of itself, from the module headers: twenty-one modules, about 3 300 lines, replacing copies that together ran to several thousand. The header of the theming module alone accounts for 1 926 lines of duplicate, and the conda helpers for 656 across forty functions.

In the codeThe declaration order in the build file and the line counts quoted by the module headers

2. How a module reaches it

Slicer puts each extension’s scripted-modules directory on the import path, so a plain import ADTLib works from any module of the extension and from a command-line module. A third route matters more than it looks: once the modules publish Slicer’s module search paths into the shapeaxi Conda environment, ADTLib is importable there too. That is what the PyTorch installer relies on: it is never imported by a panel, it is run as a module by the Conda interpreter.

A consequence: the package’s top-level files must stay free of imports, because they also run in the lean Conda environment, which has neither vtk, nor Qt, nor Slicer. Evidence.

In the codeThe three import routes and the package-root helper

3. The shared contract

Three modules carry what the tools promise each other, rather than what they compute.

ModuleWhat it replacedWhat it settles
methodSix method declarations, 934 lines mostly contract rather than codeA core (process, test process, scan counting, file search) plus three mixins, for landmarks, checkboxes and DICOM, because the six did not overlap at random: measured side by side, three clusters stood out sharply
requestsNothing; it names what was never written down473 reads of a request key with no list anywhere. Each family now declares its fields, an unknown key is rejected at construction, and a missing one raises the same error as before, at the same place, rather than becoming a silent empty value
progress protocolThree undocumented conventions on one channelSee the animation below

That factor of 100 is written down nowhere, and it produced three conventions in one repository. A tool printing the fraction makes the bar advance, the intended use. A tool printing the integer 2 makes 200 appear, so the interfaces compare against 200 to learn that one more patient is done, and the tool sends it as a pulse 0, 2, 0 because Slicer only notifies the panel when the value changes. AMASSS, receiving both, guessed at run time which one it held. The three are now named, with constants carrying the value as the interface sees it, since that is where the comparison happens. Evidence.

4. The environment

Four modules, and the only part of ADTLib that reaches outside the process.

ModuleWhat it replaced
conda helpersSix copies of each function, forty functions, 656 lines, drifted into three shapes, one still holding an unreachable return that read two names nothing had bound
library checksNine copies of the installed-library test under three incompatible answers to the same question: AREG and FlexReg answered true as soon as the library was installed at all, so a version constraint was decoration
CUDAThe architecture-list problem: a torch wheel carries compiled kernels for a fixed list of architectures
PyTorch installerThe pytorch3d wheel tag, computed from the installed torch rather than left to pip

Why the tag is computed: a pytorch3d wheel whose tag does not match the installed torch crashes with an undefined symbol error on import, not at install time. The tag 0.7.9+pt2110cu128 means torch 2.11.0 and CUDA 12.8, and PyPI publishes no wheel for modern combinations, so a dedicated index is used. Evidence.

7. What the tests pin down

ADTLib ships 22 tests, up from two. They are the closest thing to a specification this shared layer has, and several were written because grepping was not enough. One checks that every library and version the repository hands to pip parses: three modules had quietly gained a constraint with an operator, producing a requirement that pip refuses outright. The defect is invisible on a machine that already has the library, so no amount of running the module locally shows it. The test walks the source rather than a hand-written list, so a list that gains a constraint tomorrow is covered.

The others name behaviours the tool pages describe (ALI bounds, budget and progress contract, the ASO and AREG report rules, the output folder surviving a mode switch), plus the unit tests of the shared modules themselves. Run under a plain PythonSlicer, the suite reports 188 tests and 4 errors, all four a missing torch in the ALI_CBCT tests: a property of the environment, not of the code. Evidence.

In the codeThe test file names and the exact result of the run

8. Reading this layer

Two habits make it legible. First, every module header states what it replaced and what the copies disagreed about: that is where the reasoning lives, not in this page. Second, the line that recurs across those headers is what was left out: the variants that genuinely diverge stay in their tool. The test methods and the model-selection function are not in the shared method class because their arities plainly differ from one tool to the next; lifting them would have meant inventing a contract none of the six actually honoured.

9. Known problems

  • The package’s top-level files must stay free of imports, or every submodule import breaks in the lean Conda environment. Evidence.
  • The progress factor of 100 is documented nowhere, and produced three conventions. Evidence.
  • A pytorch3d wheel that does not match the installed torch crashes at import, not at install. Evidence.
