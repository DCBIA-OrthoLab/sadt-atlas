AREG_IOS

AREG_IOS puts a follow-up intraoral scan (T2) in the same position as the baseline scan (T1) of the same patient, using a patch of the arch that treatment does not move: the palate, predicted by a network, or a band along the mucogingival line. This page explains the method step by step, with the maths; developers will find the code, with file and line references, on the code page.

Code (developers) Hutin 2023 · LNCS 14350 AREG_IOS conda env: shapeaxi VISOR Bibliography

Everything on this page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, has its own page: AREG_IOS on VISOR. Where the two differ, the difference is named in the text as “Legacy only” or “also true in VISOR”. The code, with file and line references, is on the code page.

Overview: what goes in, what comes out

A patient’s teeth are scanned with an intraoral scanner twice: at the start (T1) and later (T2). To compare them, the two meshes must be put in the same position, which can only be done on a part of the mouth that treatment does not move. AREG_IOS picks such a patch and finds the rigid motion that makes the T2 patch coincide with the T1 patch. On the upper arch the patch is the palate, predicted by a network (the Butterfly patch); on the lower arch, which has no plateau, it is a band along the mucogingival line (the MGL mode), built from landmarks.

What it takes and gives
Inputa T1 and a T2 mesh per patient (.vtk, .vtp, .stl, .obj) with the jaw in the name and a tooth number on every vertex, oriented; the automatic mode prepares these two requirements
Methodmark the patch on each mesh, then rigid ICP between the two patches (section 6)
Outputthe T1 and the T2 moved onto it, both carrying the patch as a 0/1 array, and, in the automatic palate mode only, a transform file

1. Position in the chain

AREG_IOS is a command-line program. Its only caller in the repository is the AREG module; it calls no other module itself. Everything it needs (tooth labels, orientation, landmarks) is produced upstream by the steps the orchestrator stacks ahead of it. Upstream preprocessing depends on the mode; the program then produces either a palatal patch predicted by a network or an MGL band computed, before the rigid ICP.

AREG modeSteps stacked before AREG_IOS
Automatic, palate (Butterfly)crown segmentation of T1 and T2, then orientation of T1 and T2
Semi-automatic, palatenothing: the scans must already carry their tooth numbers and be oriented
Automatic, lower arch (MGL)crown segmentation of T1 and T2, then ALI_IOS on T1 and T2 for the landmarks
Semi-automatic, lower arch (MGL)the same: ALI places nothing without tooth labels, so MGL also segments

Butterfly or MGL is a choice in the widget. Conceptually upstream, FlexReg produces exactly the same input: an array of 0/1 points named Butterfly or Bottom_MGL. A scan patched by hand in FlexReg passes unchanged into the ICP of AREG_IOS.

2. Files involved

The program is made of a main file (the Butterfly loop, the MGL loop, the writing of the transforms), the palate inference with its post-processing, the network (renderer and UNet), the dataset (pairing, canonical orientation, normalisation), the MGL band, the ICP wrapper, and a few helpers. Unlike FlexReg, it does not go through Slicer’s command-line mechanism: it runs as a program in a conda environment, with its arguments passed by position, which is why their order matters. The palate network needs a GPU; the MGL band runs on the CPU.

3. Inputs and preprocessing

3.1 T1/T2 pairing

The program lists the meshes of both folders, keeps the four supported formats, and sorts them into upper and lower arches by looking for letters in the name (Lower, _L, Md and similar, or Upper, _U, Mx and similar). A T1 and a T2 are paired by literally removing the characters T1 or T2 from the name and comparing what is left; an upper arch is matched to its lower arch the same way. The MGL variant searches recursively, because the crown segmentation writes into a subfolder, and pairs lower arches alone. The assumptions are strict: the name must contain T1 or T2 and an arch marker, and a _T4 pairs with nothing. VISOR no longer needs T1 or T2 in the name, but a mesh still has to name its jaw (details).

3.2 Canonical orientation (Butterfly only)

Before the network sees a mesh, the mesh is put in a standard frame: the centroids of four teeth (3, 8, 9 and 14 in Universal numbering, the two upper first molars and the two upper central incisors; the incisors are averaged to a midpoint) are brought onto a fixed reference triangle by two rotations and a translation. The same idea exists in FlexReg, on different teeth. The result is an occlusal plane at about z = 0, with +y towards the front and +x towards the patient’s left. As a consequence the seven cameras, which sit at z of about +0.9, look at the arch from the palate side. (That last point is deduced from the geometry of the target, not claimed by the code.)

If the orientation fails, the prediction goes on with the mesh as it is. A failed orientation stops nothing: an unlabelled scan still goes to the network in some arbitrary frame and the patch will be silently wrong. VISOR does the same but writes a note in the report (details). Only the network is fed the oriented surface; the patch array is written on the raw surface, which shares the same vertex order, so the ICP runs in the coordinates of the input file (details).

3.3 Normalization

Point normals are then computed with no splitting of vertices, which is mandatory because otherwise the order and count of the vertices would change. Each normal is mapped to a colour, (normal × 0.5 + 0.5) × 255, then back to the unit range: the round trip through 8-bit integers is deliberate, because training saw the same quantisation. These colours, one per vertex, are the only texture the network gets.

In the codeThe pairing functions, the three tensors and their shapes

4. The model: MonaiUNetHRes

The weights are a single checkpoint of the AREG release v1.0.0, loaded from a Lightning file. The network is an ordinary 2D UNet; everything three-dimensional about it lives in the rendering that feeds it. The “HRes” in its name does not correspond to anything in the code.

4.1 Architecture

One class holds both the renderer and the network: a 2D UNet from MONAI with five levels (16 to 256 channels), 4 channels in (the colour image of the normals plus a depth channel) and 2 out (background, patch), applied to every view at once. The loss used in training is not used at inference.

4.2 The multi-view rendering

Seven cameras, clustered close together at height 0.9 above the arch and all looking at the origin: one straight above, four shifted by 0.2 along the two horizontal axes, two on diagonals. Despite the name of the variable, this is not an icosphere: it is a single occlusal view, slightly shifted seven times, which only makes sense because the scan was just put in the standard frame. Each view is rendered at 320 × 320 pixels with one triangle kept per pixel, and for each pixel the program also keeps the index of the triangle it shows, or −1 if it shows nothing. That pixel-to-triangle link is the pivot of the whole mechanism: it is what lets a 2D labelling be projected back onto the mesh without any ray casting.

4.3 From the 2D prediction to the per-vertex label

Three things follow from how this is coded, all facts about the code and not conjectures. First, empty pixels are zeroed before the softmax, so they become 0.5 and 0.5 instead of 0: they give a half vote to both classes, which does not change the winner but dilutes the real votes, and the pixels with index −1 write into the last triangle of the mesh. Second, the addition does not really accumulate: when several pixels of one view land on the same triangle, which is the general case, only one contribution survives. The sum across the seven views does work. Third, the vote only labels the first vertex of each triangle, so the patch comes out full of holes by construction, and it is the cleaning that repairs them (Evidence). VISOR fixes the first point and keeps the other two.

4.4 Post-processing

The cleaning first removes islands of fewer than 200 vertices, then closes the patch. Connectivity is that of the triangles around each vertex. It is all done vertex by vertex in plain Python, which makes it the dominant cost after the network. One more call in the legacy removes islands of a label, 33, that never occurs in the array: it does nothing (Evidence).

5. MGL mode: lower arch

The palate gives a stable plateau on the upper arch; the mandible has none, so the substitute is the mucogingival line. This mode is the command-line port of path C of FlexReg and involves no AREG network at all: the palate checkpoint is not even loaded.

5.1 The landmarks

Two ALI_IOS runs (T1 then T2) place 13 landmarks along the mucogingival line of the lower arch, unless the user supplied a landmark folder. Both time points write into the same temporary folder, and the program finds each scan’s file by its name.

5.2 DropDoubtfulLandmarks

ALI writes, in the description of a point it obtained in a degraded way (cameras aimed from an arch fit, a forced point, a fallback), how it did so. Any point carrying such a description is dropped, unless fewer than three points would remain. The code justifies this with a measurement on 364 predictions, not published elsewhere: 4.2 mm median deviation from the neighbours’ curve for such points against 1.2 mm for the rest. Legacy only: VISOR builds the band from every predicted landmark (details).

5.3 MGLPatch

The band is a geodesic distance, not a straight one: a band on the cheek side cannot leak through to the tongue side where the ridge is thinner than the band is wide. Crowns are then removed (lower-tooth labels), if the mesh is labelled. A height of 0 builds no band: the patch is the 13 snapped landmarks alone, a deliberate control case. The result is the array Bottom_MGL, the same name as in FlexReg. FlexReg has a richer version (a local frame at each landmark, asymmetric heights, a preview); AREG_IOS has the simplified one: a symmetric band of constant height. They are two separate files that diverged, not a shared module.

5.4 The MGL loop

For each lower pair the program builds the patch on T1 and on T2, runs the ICP and writes both meshes. If no pair goes through, an error is raised with the first cause, so that a run that “succeeded” while leaving the output folder empty no longer sends the user looking in the wrong place.

In the codeThe ALI_IOS command line, the filter, the band functions and the FlexReg differences

6. The ICP

The step is identical in both modes; only the array changes. The program extracts, from each mesh, a cloud made only of the isolated vertices whose array value is 1, then runs a rigid ICP from the T2 cloud onto the T1 cloud: six degrees of freedom, no scaling, at most 1000 iterations, starting by matching the centres. No tooth enters the matching: teeth are precisely what moves between T1 and T2.

The resulting matrix is applied to the full T2 mesh. The wrapper around the ICP returns its source unmoved instead of the result, which is harmless here because only one method is ever chained.

In the codeThe exact ICP call and the point-cloud extraction

7. Post-processing and outputs

Four mesh files can be written: the T1 unchanged but carrying the patch array; the T2 registered; for the palate, when a lower arch exists, the lower T1 copied unchanged and the lower T2 with the upper arch’s matrix applied; and, in the automatic mode only, two transform files: a copy of the orientation transform of the T1, and the composed transform of the T2. The composition chains the ICP matrix with the inverse of the orientation matrix and then inverts the whole, following the ITK convention (fixed → moving). Unlike FlexReg there is no flip between RAS and LPS anywhere: surfaces are read and written as they are.

Legacy only: in the semi-automatic mode no transform is written at all, and the MGL mode never writes one, whatever the mode (details). VISOR always writes one.

10. Environment

The program runs in the conda environment shared with ALI, ASO, FlexReg and DOCShapeAXI. The environment is created with the imaging library first, then torch and everything built on it (PyTorch3D, MONAI) are installed afterwards, with torch kept inside a supported range. On Windows, conda runs inside WSL, with a few system libraries. The palate network asks for a GPU unconditionally. At the start of the program a check removes a broken torchvision file and reinstalls torchvision if the torch and torchvision pair is not in its table; for recent torch versions the table has no entry, so nothing is touched, which is the desirable behaviour but by accident (details).

11. Pitfalls and fragile points

Each point is checked in the code and written up, with its evidence, on the code page; the list also appears in the findings. Most are legacy only and absent from VISOR, as marked.

  • The vote is partly wrong: duplicate triangles do not accumulate and only the first corner of a triangle is labelled. Still true in VISOR. Evidence.
  • A cleaning call does nothing (a label that never occurs). Legacy only. Evidence.
  • The jaw is read from the whole path, so a folder named with _U or Md misclassifies every arch, and the case rules differ between the widget and the program. Legacy only. Evidence.
  • The pairing has two errors: an empty lower list is taken as present, and a loop continues where it should stop, so one T1 can pair with several T2. Legacy only. First, second.
  • The orientation transform of the T1 is often not found, because it is looked up under a name that depends on the arch marker coming before the time point. The failure is a warning. Legacy only. Evidence.
  • A failed orientation is silent: the patch is predicted anyway and is probably wrong. Also true in VISOR, which writes a note in the report. Evidence.
  • The platform test looks for the wrong capitalisation, so the WSL branch is probably never taken. Legacy only. Evidence.
  • The module description file is out of date and ignores four parameters. Legacy only. Evidence, and.
  • The patch height is clamped to 0 to 20 mm by the widget; VISOR has no maximum. Evidence.

12. Literature

The published foundation is AReg IOS: Automatic Registration on IntraOral Scans (Hutin, Anchling, Cevidanes et al., Lecture Notes in Computer Science, 2023, MICCAI): crown segmentation by DentalModelSeg, initial alignment via shared centroids, palatal ROI segmented by multi-view 3D shape analysis, then ICP.

Two discrepancies between the paper and this repository's code:

  • the paper describes an initial alignment by shared crown centroids; in the code, that role is played by upstream PRE_ASO_IOS plus VTK's StartByMatchingCentroidsOn(): there is no centroid-alignment step inside AREG_IOS itself;
  • the MGL path doesn't exist in the paper. It's a later internal development, unpublished to date, and the figures cited in its code (4.2 mm vs 1.2 mm over 364 predictions) aren't sourced anywhere else than in the comments.
