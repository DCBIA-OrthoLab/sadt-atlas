FlexReg

Patient-by-patient registration of Intra Oral Scans, with a registration patch built by hand (palatal butterfly, free curve, or mucogingival band) instead of being predicted by a network — the interactive counterpart to AREG_IOS.

unpublished FlexReg_CLI conda env: shapeaxi Bibliography

1. Position in the chain

Nothing in the repository calls FlexReg: it is a terminal tool, driven by the operator. It does, however, call two pretrained networks, and it produces the input to AREG_IOS — both tools read exactly the same point array.

CalledWhenWhy
dentalmodelseg (ShapeAXI / DentalModelSeg)if the mesh has no Universal_ID arraysegment and number the crowns
ALI_IOS (weights Lower_MG_*.pth)lower-arch mode onlyplace the 13 mucogingival landmarks

Downstream, AREG_IOS.py:191 does vtkMeshTeeth(list_teeth=[1], property="Butterfly") and AREG_IOS.py:205 the same on MGL_ARRAY_NAME: a patch built in FlexReg is directly consumable by AREG_IOS, and vice versa. The difference is where the patch comes from: AREG_IOS has it predicted by a network (PredPatch.py, a multi-view MonaiUNetHRes), FlexReg builds it geometrically.

Non-obvious point

The CLI does not run inside the conda environment. It goes through slicer.cli.run(slicer.modules.flexreg_cli, ...) (FlexReg.py:939), so inside Slicer's own Python — hence why ensureBooted installs torch inside Slicer itself. Only dentalmodelseg and ALI_IOS go through conda run -n shapeaxi.

setup_cli_command() (FlexReg.py:1027), which would launch the CLI via conda, is never called anywhere: dead code.

3. Inputs and preprocessing

Pitfall — file conversion

ensureVtkInput() (FlexReg.py:3454) converts a .stl to .vtk before any operation. This is not cosmetic: dental_model_seg.py does os.remove(args.stl) and would destroy the source file if it were handed the .stl directly.

LPS ↔ RAS flip. The CLI reads the .vtk (LPS), applies Scale(-1,-1,1) to work in RAS like Slicer, and flips back before writing (FlexReg_CLI.py:39). All internal computation is therefore in RAS.

Canonical framing — the key preprocessing step, orientation.py:

  1. centroids of teeth Universal_ID 3, 5, 12, 14 (UR6, UR4, UL4, UL6);
  2. local basis on each side: normal of the plane through the three points (cross product of two vectors toward the midpoint), then the perpendicular direction;
  3. two successive rotations, axis = cross product, angle = arccos of the dot product, via RotationMatrix (Rodrigues);
  4. translation to make the centroids coincide.

The target is [[-0.5,-0.5,0], [0,0,0], [0.5,-0.5,0]]: right molar at x<0, left molar at x>0, premolars at the origin. Result: occlusal plane ≈ z=0, +y = anterior, +x = left side. No scaling — this is a rigid 3-point registration.

Direct consequence: the entire butterfly computation that follows is a 2D calculation in the XY plane, with the z component simply ignored.

4. The models

4.1 Crown segmentation — DentalModelSeg predicted

checkSegmentation() (FlexReg.py:3657) does not test for the array's presence: it attempts the orientation above and reads the exception.

  • ToothNoExist → the mesh is segmented but one of the 4 reference teeth is missing → message, stop.
  • NoSegmentationSurf → no segmentation array → shapeaxi_conda().
conda run -n shapeaxi python -m CrownSegmentationcli \
  <surf> None <out> 1 latest 0 Universal_ID 0 None <vtk_folder> <dentalmodelseg_path>

Arguments in order: surface, input csv, output folder, overwrite=1, latest model, crownsegmentation=0, array name Universal_ID, fdi=0, suffix, vtk folder, path to the dentalmodelseg executable (located via a which inside the env).

What can be verified from this repository stops at the command line above and its effect: the output is a point array Universal_ID in universal 1–32 numbering, written into the input file (overwrite=1).

The architecture and the latest weights live in the pip package shapeaxi, outside the repository: not determinable here. By lineage (DentalModelSeg descends from Fly-by-CNN) one would expect a multi-view render followed by a per-view 2D segmentation and a voted reprojection onto the vertices, but neither the number of cameras, their placement, nor the render resolution can be verified from this repository — and the neighboring example is a caution: in PredPatch.py, the buffer named ico_verts does not hold an icosphere but 7 cameras clustered at z=0.9.

Pitfall — do not assume

Do not assume a sphere of cameras without having read it.

downloadModel() (FlexReg.py:3629) downloads a Fly-by-CNN .pth (07-21-22_val-loss0.169.pth, release 3.0) — never called, dead code. The model actually used is the latest one bundled inside dentalmodelseg.

4.2 Mucogingival landmarks — ALI_IOS predicted

computeMGLLandmarks() (FlexReg.py:2517):

conda run -n shapeaxi python -m ALI_IOS \
  <scan> <models> None None "LL6MG LL5MG … L0MG … LR6MG" <out> 224 0 1 <log>

Positional arguments: input, dir_models, lm_type=None, teeth=None, teeth_mg=<13 names>, output_dir, image_size=224, blur_radius=0, faces_per_pixel=1, log_path.

ALI_IOS is likewise multi-view (PyTorch3D rendering): it places one camera per tooth based on the segmentation, renders the view at 224×224, and the network outputs a heatmap whose peak gives the point's position. A landmark is placed only if its tooth carries a label in Universal_ID / PredictedID — hence FlexReg's error message pointing back to the segmentation when ALI has placed only k of the 13 points.

The weights are looked for in <Documents>/SlicerDownloads/ALI/ALI_IOS/Models/Prediction, named Lower_MG_*.pth (hasMGLModel, FlexReg.py:2587); otherwise a folder picker opens.

5. The algorithmic core

5.1 Path A — the Butterfly patch (upper arch) computed

make_butterfly.py. No network, purely geometric.

a) Four centroids. The operator picks 4 teeth (anterior L/R, posterior L/R); vtkMeanTeeth averages the vertices carrying that Universal_ID.

b) Three families of parameters applied to these centroids:

ParameterEffectDetail
shift_lr, shift_aptranslates the whole patchthe same vector is added to all 4 centroids; since the landmarks are affine combinations with weights summing to 1, the shift carries through the interpolation and the shape is unchanged
adjust (mm)lengthens / shortensoffset in ±y, sign flipped on the posterior teeth: a positive adjust pushes both ends outward
ratiowidth is preservedreparameterized as r = (1-ratio)/2, then landmark = (1-r)·own_centroid + r·opposite_centroid. ratio=1 → landmark on its own centroid (maximal patch); ratio=0 → landmark halfway (degenerate patch)

Watch the vocabulary: the UI says top/bot, the CLI says anterior/posterior. lineedit_teeth_left_top → tooth_anterior_left.

c) The outline, four pieces:

  • anterior segment and posterior segment (Segment2D, step of 0.01);
  • two quadratic Béziers, right and left, control points (posterior_landmark, posterior_midpoint, anterior_landmark), then reflected across the chord (sym = 2·proj − bezier) so they bulge toward the outside of the arch instead of the center. This is what gives the butterfly its shape.

d) Marking. torch.cdist between the outline points and the vertices projected onto XY; every vertex within radius = 0.7 mm is set to 1.

e) Filling. Dilation() (propagation.py:73): a geodesic flood fill over the mesh, not a morphological dilation. It starts at the vertex closest to the barycenter of the 4 landmarks, propagates neighbor by neighbor (GetPointCells / GetCellPoints), and stops at the outline, already set to 1. Batched by nmb_treatment = 1000 on GPU.

f) Writing. The array is named Butterfly{index}: each patch has its own index, which allows them to be accumulated. At the end of the CLI, all the Butterfly1..N arrays are merged by torch.logical_or into a single array Butterfly (FlexReg_CLI.py:229) — that is the one the ICP and AREG_IOS read. The result is written back into the input file.

The delete mode renumbers the arrays above the deleted index and then drops the last one, rather than leaving a gap.

Real-time preview. butterfly_preview.py replays the exact same outline in pure numpy (CPU) and replaces the flood fill with a point-in-polygon test (matplotlib.path.Path, with a numpy crossing-number fallback). Orientation and centroids are cached per scan (prepare), so only the outline is recomputed on each joystick move. Constants: CELL = 1.0 mm for the height map, LIFT = 0.4 mm above the teeth, NB_POINTS = 120 samples per edge.

5.2 Path B — the drawn patch computed

draw() (FlexReg.py:4239), type="curve". A Slicer curve constrained to the surface (SetAndObserveSurfaceConstraintNode) plus a midpoint, serialized into strings and passed to the CLI. draw.py interpolates linearly between consecutive points (step 0.2, closed loop), marks vertices within 1.1 mm, then runs exactly the same Dilation() from the midpoint. The only difference from the butterfly is how the outline is obtained.

The curve is drawn on the model recentered facing the camera; before sending it to the CLI, moveCurve() applies the inverse of the recentering matrix to bring it back into the file's coordinates.

5.3 Path C — the MGL patch (lower arch) computed

The palate provides a stable plateau on the upper arch; the mandible has none. The substitute chosen is the mucogingival line. This whole block is computed inside the widget, in numpy/scipy — no GPU, no CLI (mgl_patch.py).

a) Cleaning up ALI's predictions. DoubtfulLandmarks() reads the description that ALI writes into the json when it forced a point (top-k pixels, fallback to the tooth, missing tooth). Per the code's comment, measured on 364 predictions: a 4.2 mm median deviation from the neighbors' curve, against 1.2 mm for the rest. These points are discarded by default, and the spline bridges the gap — unless fewer than 3 points would remain. Then CanonicalLandmarks (old annotation naming → canonical, detected by the presence of an LL7MG or LR7MG) and RecentreNames (the count stays anchored on the midline when a point is missing partway along the arch).

b) Local frame. LocalFrames(): the apical axis is the third component of the SVD of the centered landmarks (the normal of the point ribbon, independent of the scan's orientation in world space); the tangent is np.gradient along the arch; buccal is their cross product, flipped wherever it points inward. OrientApical fixes the sign based on the crowns.

c) Building the band, on every compute():

  1. operator offsets (buccal / apical / tangential) applied to the landmarks;
  2. vtkParametricSpline running through them, SAMPLES_PER_SEGMENT = 25;
  3. each sample is snapped onto the mesh (vtkPointLocator) — an interpolated spline drifts off the surface in interdental concavities;
  4. Dijkstra (scipy.sparse.csgraph) on the edge graph weighted by real length, multi-source from these vertices, limit = max height, min_only=True, return_predecessors=True → the band grows along the surface, never through it (a vestibular patch cannot come out on the lingual side, where the ridge is thin);
  5. height interpolated linearly between landmarks (np.interp) and asymmetric: heights on the crown side, heights_down on the vestibular side, with the side decided by the sign of the apical component. The height used is that of the seed from which the vertex was reached, so two segments of different heights coexist without a step;
  6. the crowns (Universal_ID 18–31, LOWER_TOOTH_LABELS) are removed — they move between T1 and T2;
  7. the landmarks themselves always stay in the patch.

Bounds: MIN_HEIGHT = 0.0, MAX_HEIGHT = 5.0, DEFAULT_HEIGHT = 2.5 mm. Zero height everywhere ⇒ only the 13 points remain: this is the deliberate control case, to measure what the band adds over the points alone.

The edge graph is built with np.unique(np.sort(edges)) before the coo_matrix: without this deduplication, interior edges shared by two triangles would be summed by the sparse matrix, doubling their length and halving the patch's reach.

Output array: Bottom_MGL (MGL_ARRAY_NAME), previewed in Bottom_MGLPreview.

WriteLandmarks() writes the edited landmarks in LPS, like the training annotations: the resulting file can be fed straight back into the corpus.

5.4 The registration computed

Reg.run() (FlexReg.py:1276) relaunches the same CLI with type = "icp" (upper) or "icp_mgl" (lower). T2 is the moving scan (lineedit), T1 the fixed one (path_reg).

patch_array = "Bottom_MGL" if args.type == "icp_mgl" else "Butterfly"
option = vtkMeshTeeth(list_teeth=[1], property=patch_array)
icp = ICP([vtkICP()], option=option)
output_icp = icp.run(modelNode, modelNodeT1)

vtkMeshTeeth does not build a mesh despite its name: it extracts a point cloud containing only the vertices whose patch array equals 1. The ICP therefore runs only on the patch, never on the teeth.

icp.GetLandmarkTransform().SetModeToRigidBody()   # 6 dof, no scaling
icp.SetMaximumNumberOfIterations(1000)
icp.StartByMatchingCentroidsOn()                  # initialization

Standard vtkIterativeClosestPointTransform: nearest-neighbor matching, rigid least-squares estimation, iteration. No learning at this stage.

The 4×4 matrix is then applied to the entire T2 mesh, and to the opposite arch if one is supplied (lower_arch), so it follows the same movement.

6. Post-processing and outputs

The mesh. Patch type → rewritten into the input file. ICP type → written into path_output as <T2 name without extension><suffix>.vtk, after flipping back to LPS.

The transform, the delicate step (FlexReg_CLI.py:186):

flip = np.diag([-1, -1, 1, 1])
composed = flip @ matrix_array @ flip     # RAS -> LPS by conjugation
composed_inv = np.linalg.inv(composed)    # ITK convention: fixed -> moving
sitk_tfm = sitk.AffineTransform(3)
sitk_tfm.SetMatrix(composed_inv[:3, :3].flatten())
sitk_tfm.SetTranslation(composed_inv[:3, 3])

File <T2 name><suffix>.tfm, reusable by the other modules in the repository.

The See button. Runs the exact same registration into a tempfile.mkdtemp(prefix="FlexReg_see_") that is deleted as soon as it's displayed (discardTempFolder). The resulting node is marked SetSaveWithScene(False) and renamed ... (preview, not saved): the file behind it is about to disappear.

The display. Custom layout 501, T1 in [255,51,200]/256 and T2 in [102,102,255]/256 in the third 3D view.

Pitfall — numpy

numpy must not be touched: Slicer's scipy is compiled against its own numpy, and swapping numpy out under a live session leaves the next scipy import reading a mix of the two (No module named 'numpy.strings'), which used to kill the MGL preview.

9. Pitfalls and fragile points

The CLI requires CUDA

Dilation, drawPatch, and the final merge of the arrays all call .cuda() with no CPU fallback. The MGL patch, on the other hand, is computed on the widget side and does without it — hence the while args.type != "icp_mgl" that skips the merge for the lower arch.

The input file gets overwritten

In patch mode, and the automatic segmentation overwrites it too (overwrite=1). A .stl handed to dentalmodelseg is simply deleted outright — that's the whole reason ensureVtkInput() exists.

Confirmed bug — vtkICP.__call__

vtkICP.__call__ returns source unchanged instead of the transformed mesh. Harmless here because list_icp only contains one method, but a multi-step chain would not work as written.

Segmentation detection works through an exception

A mesh segmented under an array name other than Universal_ID will trigger a full re-segmentation.

Confirmed bug — GetLabelSurface

GetLabelSurface (vtkSegTeeth.py:29) loops over the arrays and does continue when it finds the preferred one, instead of break: the name returned is that of the last array in the list, not necessarily the preferred one. Harmless as long as automatic_property stays False, which is the case everywhere in FlexReg.

Dead code: downloadModel(), setup_cli_command() / find_cli_parameters().

Patch decided in projected 2D

The butterfly patch is decided in projected 2D: on an arch strongly tilted after orientation, the outline can catch vertices that are far apart in z.

10. Literature

The published foundation is AReg IOS: Automatic Registration on IntraOral Scans (Hutin, Anchling, Cevidanes et al., Lecture Notes in Computer Science, 2023): crown segmentation by DentalModelSeg, initial alignment by shared centroids, palatal ROI segmented by multi-view 3D shape analysis, then ICP. FlexReg is its "the operator draws the ROI instead of having it predicted" counterpart.

No paper deals specifically with FlexReg or with the MGL variant — the latter appears to be an in-house development that remains unpublished to date. The figures quoted in the code (4.2 mm vs 1.2 mm on 364 predictions) are not sourced anywhere outside the comments.
