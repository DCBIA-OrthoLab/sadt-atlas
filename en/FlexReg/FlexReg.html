FlexReg: patch-based registration

Patient-by-patient registration of intraoral scans, with a registration patch built by hand (palatal butterfly, free curve, or mucogingival band) instead of being predicted by a network: the interactive counterpart to AREG_IOS. This page explains how, step by step, with the maths; the files, lines and pitfalls are on the code page.

Code (developers) Guide unpublished FlexReg_CLI conda env: shapeaxi VISOR Bibliography

Overview: what goes in, what comes out

Between two visits the teeth can move, and the gums too; the palate hardly does. FlexReg registers the second scan onto the first by looking only at a patch of the palate (upper arch) or of the mucogingival line (lower arch), so the teeth themselves are free to have moved. Unlike AREG_IOS, which has the patch predicted by a network, FlexReg builds it geometrically, by hand.

What it is
Inputtwo intraoral scans of a patient (T1, the fixed one, and T2, the moving one), .vtk or .stl
Idealabel the crowns, orient the arch, draw a patch (butterfly, free curve or band), then register T2 onto T1 on the patch with a rigid ICP
Outputthe registered mesh and a .tfm transform; the patch itself is stored in the mesh as a 0/1 array, which AREG_IOS reads

Everything numbered below describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, is described on its own page, FlexReg on VISOR. It keeps the patch preview in Slicer and does the rest on the server; it does not carry the free curve, the patch deletion, the mucogingival patch computation or the automatic crown segmentation.

1. Position in the chain

Nothing in the repository calls FlexReg: it is a terminal tool, driven by the operator. It does call two pretrained networks, and it produces the input to AREG_IOS: both tools read exactly the same point array. A patch built in FlexReg is directly usable by AREG_IOS, and the other way round; the difference is where the patch comes from.

2. Files involved

The widget (about 4150 lines, mostly user interface) drives a command-line tool that builds the patch and runs the ICP. The geometric core (orientation, patch, geodesic fill, ICP) is a small library; the preview and the mucogingival band live in the widget. The command-line tool needs CUDA; it runs in Slicer’s own Python, not in conda.

In the codeEvery file with its role and where it runs

3. Inputs and preprocessing

An .stl is first converted to .vtk, because the segmentation tool would otherwise delete the source file. The computation then runs in RAS: the mesh, in LPS, is mirrored in x and y on reading and flipped back before writing.

Canonical framing is the key preprocessing step. The centroids of teeth 3, 5, 12 and 14 (UR6, UR4, UL4, UL6; the tooth numbers follow the Universal system, 1 to 16 along the upper arch from the right third molar, 17 to 32 along the lower arch from the left third molar) are brought onto a fixed triangle by two rotations and a translation, with no scaling: the occlusal plane ends up near z = 0, +y points to the front and +x to the patient’s left. This oriented copy only serves to draw the patch (the patch is written back into the original mesh); it is not the RAS frame used for the registration. Everything the butterfly does next is a 2D calculation in the XY plane, with z ignored (the drawn patch, below, measures in 3D).

In the codeThe file conversion, the flip and the orientation algorithm

4. The models

4.1 Crown segmentation: DentalModelSeg predicted

The widget does not test whether the tooth-label array exists: it tries the orientation and reads the error. A missing array launches the segmentation, and a missing reference tooth stops with a message. The output is a point array with the universal tooth numbers 1 to 32, written into the input file. Its architecture lives in a package outside the repository, so what happens inside it is not described here.

In the codeThe command, its arguments and the dead download code

4.2 Mucogingival landmarks: ALI_IOS predicted

For the lower arch, ALI_IOS places 13 landmarks along the mucogingival line, one camera per tooth. A landmark is placed only if its tooth carries a label, hence the message that points back to the segmentation when only some of the 13 points were placed.

In the codeThe command, the positional arguments and where the weights are looked for

5. The algorithmic core

5.1 Path A: the Butterfly patch (upper arch) computed

No network, purely geometric. The operator picks four teeth (anterior left and right, posterior left and right); the tool averages their vertices into four centroids, derives four corners, outlines the patch, marks it and fills it.

The patch is written under the name Butterfly followed by an index, so patches can accumulate; at the end of the run all of them are merged by a logical OR into the single Butterfly array that the ICP and AREG_IOS read, and the result is written back into the input file. The widget’s preview replays the same outline on the CPU and replaces the flood fill by a point-in-polygon test.

In the codeThe three families of parameters, the code of each step and the preview constants

5.2 Path B: the drawn patch computed

The operator draws a closed curve on the surface plus a midpoint. The tool interpolates it linearly, marks the vertices within 1.1 mm (measured in 3D, with no projection onto the flat view) and runs exactly the same geodesic fill from the midpoint. Only the way the outline is obtained differs from the butterfly.

In the codeThe drawing, the serialisation and the undo of the recentering

5.3 Path C: the MGL patch (lower arch) computed

The palate gives a stable plateau on the upper arch; the lower arch has none, so the stand-in is the mucogingival line. The whole block is computed inside the widget, with no GPU and no command-line step. First the predicted landmarks that ALI_IOS marked as doubtful (forced out of the top pixels, fall-back to the tooth, arch fit, off the aim, extrapolated) or gave with a confidence under 0.785 are discarded, unless fewer than 3 points would remain: the code’s comment measures the doubtful ones on 364 predictions at a median 4.2 mm from the curve of their neighbours against 1.2 mm for the rest. A local frame is built from the landmarks (apical, tangent and buccal axes), then the band is grown.

Each of the two heights is bounded between 0 and 5 mm (2.5 by default); with both at zero everywhere only the 13 points remain, the deliberate control case. The result is stored in the array Bottom_MGL.

In the codeThe cleanup, the frame, the seven-step band construction and the constants

5.4 The registration computed

The same command-line tool is run again in registration mode. T2 is the moving scan, T1 the fixed one. The ICP extracts from both meshes only the points where the patch array equals 1, so it runs on the patch only, never on the teeth. Its matrix is then applied to the entire T2 mesh, and to the opposite arch if one is supplied so that it follows the same movement.

In the codeThe call, the VTK settings and the option object

6. Post-processing and outputs

A patch mode rewrites the mesh into the input file. A registration writes <T2 name><suffix>.vtk into the output folder, after flipping back to LPS, and a .tfm reusable by the other modules.

The preview button runs the same registration into a temporary folder that is deleted as soon as the result is displayed, and marks the node “preview, not saved”.

In the codeThe matrix code, the temporary folder and the display layout

MGL bandcomputed geometric, spline + shortest paths, on the CPU

No part of FlexReg learns anything: the two networks it calls are pretrained and act only as landmark providers.

8. Environment

The command-line tool runs in Slicer’s own Python, where the widget adds only torch; the two networks run in a shared conda environment (Python 3.12, with prebuilt pytorch3d wheels). The checks run once, at the moment an action needs them, and cost about 7.6 s. On Windows, conda goes through WSL.

In the codeThe packages, the probes and their measured cost

9. Pitfalls and fragile points

  • The command-line tool requires CUDA, with no CPU fallback; the same is true in VISOR for the patch fill (details).
  • In patch mode the input file is overwritten, and a .stl handed to the segmentation is deleted (details).
  • The ICP wrapper returns the source unchanged instead of the moved mesh: harmless with a single method (details).
  • Segmentation is detected through an exception: a mesh labelled under another array name is re-segmented (details).
  • The patch is decided in a 2D projection, so on a strongly tilted arch the outline can catch vertices far apart in height (details).
  • numpy must not be touched in Slicer’s Python, and some download code is never called (details).

10. Literature

The published foundation is AReg IOS: Automatic Registration on IntraOral Scans (Hutin, Anchling, Cevidanes et al., Lecture Notes in Computer Science, 2023): crown segmentation by DentalModelSeg, initial alignment by shared centroids, palatal ROI segmented by multi-view 3D shape analysis, then ICP. FlexReg is its "the operator draws the ROI instead of having it predicted" counterpart.

No paper deals specifically with FlexReg or with the MGL variant: the latter appears to be an in-house development that remains unpublished to date. The figures quoted in the code (4.2 mm vs 1.2 mm on 364 predictions) are not sourced anywhere outside the comments.
