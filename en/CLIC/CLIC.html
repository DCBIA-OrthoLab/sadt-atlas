CLIC

CLIC segments a CBCT slice by slice with a Mask R-CNN and classifies each detected instance as a buccal, bicortical, or palatal impacted canine — classification and localization come out of the same network pass.

unpublished clic_runner.py conda env: clic_env Python 3.9 Bibliography

Classification and Localization of Impacted Canines. 2D slice-by-slice instance segmentation of a CBCT by a torchvision Mask R-CNN, whose predicted class encodes the intraosseous position of the impacted canine: buccal, bicortical, palatal.

The module's name promises two tasks; the code has only one network. There is no separate classification network, no separate localization network, and no coordinate-regression head. Classification is the instance label (pr["labels"]); localization is the mask (pr["masks"]) — both come out of the same Mask R-CNN pass. Everything below follows from that.

1. Where it sits in the pipeline

Standalone in both directions: no module in the repository calls CLIC, and CLIC calls no other module in the repository. It calls nothing but its own runner:

CalledWhenHow
CLIC/runner/clic_runner.pyonce per scanCondaSetUpCall.condaRunFilePython(runner, ["--params_json=…"], "clic_env")
release CLIC_model/final_model.pthDownload Model buttonrequests.get, written to ~/Documents/CLIC_Models

It starts from the raw CBCT. No prior segmentation, no landmarks, no orientation: the module reads a .nii/.nii.gz and outputs a label map. It does not depend on AMASSS, ASO, or ALI in any way.

No Slicer CLI, no .xml, no MedX_Method-like layer: the widget writes a parameters JSON to slicer.app.temporaryPath and launches the runner as a standalone Python script inside the conda environment.

The widget imports CondaSetUp at module level (CLIC/CLIC.py:18) without declaring it in parent.dependencies: without SlicerConda installed, CLIC does not load at all, with no helpful message.

It always instantiates CondaSetUpCall() (CLIC/CLIC.py:62), never CondaSetUpCallWsl: unlike MedX, DOCShapeAXI, and the others, CLIC has no WSL path. On Windows it will call SlicerConda's Unix path, and the argument order of condaRunFilePython differs between the two classes ((file, args, env) on the Unix side, (file, env, args) on the WSL side) — the args list would go out as the environment name. The module is effectively Linux-only, despite the README.

Pitfall

No WSL path: CondaSetUpCallWsl is never instantiated. On Windows, the argument order of condaRunFilePython expected by the Unix path (used by mistake) is not that of the WSL path — the argument list would go out as the environment name. CLIC is effectively Linux-only.

3. Inputs and preprocessing

3.1 Scan collection

_collect_scans() (CLIC/CLIC.py:316) accepts .nii, .nii.gz, .nrrd, .mha, .mhd, and follows a two-step rule:

  1. if there are subfolders containing at least one valid file, it returns the list of these subfolders;
  2. otherwise, the list of valid files in the folder.

Case 1 produces directory Paths, passed as-is as input_path to the runner, which does nib.load(str(inp)): immediate failure. The nominal case is therefore a flat folder of .nii.gz.

Furthermore the runner only uses nibabel: .nrrd, .mha, .mhd are accepted by the widget's filter and unreadable by the runner.

Pitfall

The widget's selection filter accepts .nrrd, .mha, and .mhd in addition to .nii/.nii.gz, but the runner can only load with nibabel: these three formats pass the filter and fail to load.

3.2 The actual volume preprocessing

It fits in three lines (CLIC/runner/clic_runner.py:88):

sl = _norm(vol[..., z])                                    # min-max of the slice
t  = torch.from_numpy(sl).unsqueeze(0).repeat(3, 1, 1).float().to(device)
pr = model([t])[0]

In other words:

  • slicing into axial slices along the 3rd axis of the nibabel array, in the file's storage order — not according to a recomputed anatomical orientation. No RAS/LPS reorientation is done, the code never looks at nii.affine except to rewrite it;
  • per-slice min-max normalization (_norm, CLIC/runner/clic_runner.py:53): (x - min) / (max - min), and a constant slice becomes zero. No Hounsfield windowing, no percentile clipping, no volumetric statistics: each slice has its own contrast, a slice that contains only air is stretched across the full dynamic range;
  • replication into 3 channels to match the RGB input of the ImageNet backbone;
  • no crop, no ROI, no explicit resampling, no voxel rescaling.

The only resizing comes from torchvision itself: the GeneralizedRCNNTransform embedded in the model standardizes with the ImageNet means ([0.485,0.456,0.406] / [0.229,0.224,0.225]) and resizes so that the short side is 800 px, capped at 1333 px on the long side. This is a torchvision default, not a choice made in the repository — a 512×512 CBCT is thus upscaled to 800×800 before the backbone.

4. The model

4.1 Architecture

_blank_model(nc) (CLIC/runner/clic_runner.py:44), called with nc = 4:

m = maskrcnn_resnet50_fpn(weights=None)
m.roi_heads.box_predictor  = FastRCNNPredictor(in_f, nc)
m.roi_heads.mask_predictor = MaskRCNNPredictor(in_fm, 256, nc)
  • backbone: ResNet-50 + FPN (_resnet_fpn_extractor, 5 levels);
  • RPN then ROI heads: box head (FastRCNNPredictor: cls_score 4 classes, bbox_pred 16 outputs) and mask head (MaskRCNNPredictor, hidden layer 256, 4 output channels, 28×28 masks per ROI);
  • weights=None but weights_backbone keeps its default ResNet50_Weights.IMAGENET1K_V1: building the model downloads the ImageNet weights for ResNet-50 (then load_state_dict overwrites them). First run offline = failure. Useful side effect: since is_trained is True, the normalization is FrozenBatchNorm2d rather than BatchNorm2d, which must match the training model so that the state_dict keys line up.
Pitfall

weights_backbone keeps its default ResNet50_Weights.IMAGENET1K_V1 even when weights=None: simply building the model triggers a download of the ImageNet weights for ResNet-50. First run offline = failure, before even reaching final_model.pth.

4 classes = background + 3. The label-to-name mapping exists only in the widget, in _legend() (CLIC/CLIC.py:361):

predicted the network only outputs integers 1/2/3; the name and color below are a widget convention, absent from the runner.

LabelMeaningColor
1Buccalgreen (0,1,0)

The runner does not know these names: it writes the integers 1, 2, 3.

4.2 The weights

Hardcoded URL (CLIC/CLIC.py:333):

https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/CLIC_model/final_model.pth

Destination ~/Documents/CLIC_Models/final_model.pth. The runner does not look for this name: it takes sorted(model_dir.glob("*.pth"))[0] (CLIC/runner/clic_runner.py:76), the first .pth in alphabetical order. Two models in the folder, and the filename decides. Unhandled IndexError if the folder is empty.

The file is a bare state_dict (model.load_state_dict(torch.load(...))), not a Lightning checkpoint: no hyperparameters, no classes, no version. The training set, the number of annotated slices, and the metrics cannot be determined from the repository.

4.3 What the network literally outputs

network for each slice, model([t])[0] returns the standard torchvision dictionary:

KeyShapeContent
boxes(N,4)boxes x1,y1,x2,y2 in the resized frame, mapped back to the original size by the transform
labels(N,)integer 1..3
scores(N,)class score, decreasing
masks(N,1,H,W)per-pixel probability, float in [0,1]

with torchvision's default upstream thresholds: box_score_thresh=0.05, box_nms_thresh=0.5, box_detections_per_img=100.

4.4 From network outputs to the label map

Two thresholds, both hardcoded (CLIC/runner/clic_runner.py:93):

keep = pr["scores"] >= 0.7                     # confiance d'instance
for mk, lb in zip((pr["masks"][keep] > .5).squeeze(1).cpu().numpy(),
                  pr["labels"][keep].cpu().numpy()):
    seg[..., z][mk] = int(lb)
  • 0.7 on the instance score;
  • 0.5 on the mask probability, which binarizes it;
  • the assignment is an overwrite, not a vote: if two instances overlap, the one processed last (hence the lowest score, since torchvision sorts by decreasing score) wins the pixel. A buccal/palatal conflict on the same voxel is settled by the lowest score;
  • nothing restricts the number of instances per slice, neither to one canine nor to two.

No 3D consistency is enforced. Each slice is classified independently; there is no inter-slice smoothing, no connected-component analysis, no majority vote across the stack. Two neighboring slices can carry two different classes for the same tooth. Anyone who wants "the patient's class" has to aggregate it themselves — the module does not produce it.

Pitfall

Overlap between two instances is settled by overwrite, not by vote: the instance processed last — hence at the lowest score, since torchvision sorts by decreasing score — wins the pixel. And since nothing enforces consistency between neighboring slices, two adjacent slices can classify the same tooth differently.

5. The algorithmic core

There is no non-learned part, apart from thresholding: no ICP, no morphology, no component extraction, no measurement. The entire runner is: load the model, loop over Z, threshold, write. The entire decision is inside the Mask R-CNN.

6. Post-processing and outputs

out_dir  = out_root / inp.stem
out_path = out_dir / f"{inp.stem}_{suffix}.nii.gz"
nib.save(nib.Nifti1Image(seg.astype(np.int16), nii.affine, nii.header), out_path)
  • a subfolder per scan, named after the scan;
  • suffix from suffixLineEdit, default "seg";
  • Path.stem on X.nii.gz is X.nii: the folder is called X.nii and the file X.nii_seg.nii.gz. Ugly but without functional consequence;
  • affine and header are taken from the input volume: the label map overlays without registration. The original header describes a floating-point data type while the data is int16; Nifti1Image adjusts the header's dtype on write;
  • the type is int16 with values 0/1/2/3.
Note

The X.nii_seg.nii.gz naming comes from Path.stem on X.nii.gz, which only strips one extension and returns X.nii. Ugly, but without functional consequence.

On the widget side, loading the result goes through the ui_q queue: the "segmentation" action calls slicer.util.loadSegmentation(path) then _legend(), which colors the segments by index order (cols.get(i+1, …)) and not by label value. If a class is absent from the volume, the colors shift. _legend() also draws three vtkTextActors in the Red/Yellow/Green views, marked with an _leg attribute so they can be removed on the next refresh.

_ensure_env() (CLIC/CLIC.py:158) is replayed on every click on Predict: both pip install calls run again, even when everything is already in place (pip returns quickly but still queries the network). self._env_ready is set and never read back.

The second pip install passes "'numpy<2.0'" — single quotes included inside the string. Depending on how SlicerConda assembles the command (shell=True with a string on the Unix side), the argument may arrive correctly unquoted or not. Failure detection, meanwhile, looks for "error" or "failed" in the returned output: any pip warning containing those words fails the preparation step.

The conda patch

CLICWidget.__init__ (CLIC/CLIC.py:62–112) hot-patches SlicerConda's getCondaExecutable and getCondaPath:

  1. fixes a duplicated /bin/bin/ in the path;
  2. otherwise, shutil.which("conda");
  3. otherwise, hardcoded /home/luciacev/anaconda3/bin/conda.

And fixed_getCondaPath returns /home/luciacev/anaconda3 as soon as this folder exists, even before considering the user-configured path. A path from one specific development machine is thus versioned in the repository and takes priority over the SlicerConda configuration. To be treated as debt, not as intended behavior.

Pitfall

fixed_getCondaPath returns /home/luciacev/anaconda3 as soon as this folder exists on the machine, even before looking at the user's SlicerConda configuration — a development-machine path is versioned and takes priority.

9. Pitfalls and fragile points

Confirmed bug

The runner emits its markers via logger.info, with the formatter '%(name)s - %(levelname)s - (%(filename)s:%(lineno)d) - %(message)s' (CLIC/runner/clic_runner.py:39). The received lines look like CLIC_runner - INFO - (clic_runner.py:60) - [SEG] /path, so the tests ln.startswith("[PROGRESS]") and ln.startswith("[SEG]") (CLIC/CLIC.py:268) are never true. Consequence: the progress bar stays at zero and the produced segmentation is never loaded into Slicer — it is nonetheless correctly written to disk. Minimal fix: parse with "[SEG]" in ln and cut from the marker onward.

Pitfall

With no output folder chosen, the widget still writes the "output_dir" key in the JSON, as None. On the runner side, P.get("output_dir", inp.parent) then returns None — the key exists, so the default does not apply — and Path(None) raises a TypeError: the runner crashes.

  • The progress bar and the automatic loading of the result are broken. The runner emits its markers via logger.info, with the formatter '%(name)s - %(levelname)s - (%(filename)s:%(lineno)d) - %(message)s' (CLIC/runner/clic_runner.py:39). The received lines look like CLIC_runner - INFO - (clic_runner.py:60) - [SEG] /path, so the tests ln.startswith("[PROGRESS]") and ln.startswith("[SEG]") (CLIC/CLIC.py:268) are never true. Consequences: the bar stays at zero and the produced segmentation is never loaded into Slicer — it is nonetheless correctly written to disk. The switch from print to logging broke the protocol still described in the runner's header (CLIC/runner/clic_runner.py:12-16). Minimal fix: parse with "[SEG]" in ln and cut from the marker onward.
  • Nothing is incremental anyway. condaRunFilePython does a subprocess.run(...).stdout and returns f"Result: {result.stdout}": all the output arrives in one block, at the end of the scan. Even with the markers fixed, progress would jump from 0 to 100% per scan.
  • The Cancel button does nothing: _on_cancel (CLIC/CLIC.py:288) just writes a log line. It touches neither cancel_evt nor the subprocess.
  • With no output folder chosen, the runner crashes. The widget always writes the "output_dir" key in the JSON, as None if the operator has chosen nothing; P.get("output_dir", inp.parent) then returns None — the default does not apply, since the key exists — and Path(None) raises a TypeError. The Save Predictions in Input Folder checkbox in the .ui is connected to nothing.
  • self.output_dir is not converted to str for the JSON: it's already a string on the _browse side, and so is model_folder — consistent, except that input_path is a Path explicitly converted. Worth watching in case of a rewrite.
  • The waiting loop blocks Slicer: _on_predict runs in a while not cancel_evt.wait(0.05) with processEvents(), the worker thread waits for the subprocess. The UI stays responsive, but the Predict button is the only exit point.
  • Per-slice normalization: the class predicted on a slice depends on the recomputed local contrast, not on Hounsfield units. Two acquisitions with different fields of view do not present the same image to the network.
  • The .ui declares two QTextEdit widgets named logTextEdit (CLIC/Resources/UI/CLIC.ui:343 and 353): childWidgetVariables keeps only one, the other stays empty on screen.
  • Dead code: _clean_env() (CLIC/CLIC.py:39), initializeParameterNode (pass), _updateAllLabelsColor, _updateDynamicWidgetsColor, _updateMRMLNodeComboBoxColor, the glob, subprocess, urllib.request, Optional imports, CLIC/testing/test_CanineSegmentation.py (empty file), and the unused torch import in MedX_CLI/MedX_Dashboard/MedX_Dashboard.py — mentioned here because the same copy-paste turns up in several modules.
  • CLIC/__pycache__/CLIC.cpython-312.pyc is checked into the repository.

10. Literature

No paper covers CLIC. The corresponding work is announced under the title Interpretable Deep Learning for the Detection and Classification of Impacted Canines and severity of root resorption (Tulissi, Cevidanes, Prieto), presented at NA-MIC Project Week 43 (Montreal, 2025) — a project in progress, not a publication. The original code comes from the personal repository ashmoy/maskRcnn, which is also where the test scans cited by the README come from (MN138.nii, UM06.nii).

Not to be confused with the neighboring work below, which did not produce this code:

  • buccal/palatal localization of impacted canines is traditionally done on panoramic radiographs, with an image-classification CNN (not a Mask R-CNN on CBCT);
  • several teams publish 3D segmentation of impacted canines on CBCT (volumetric U-Net/nnU-Net), without classifying cortical position.

CLIC's specificity — a bicortical class in addition to the buccal/palatal pair, predicted slice by slice in 2D on CBCT — is not described in any of these papers. Do not present their numbers as belonging to this module.
