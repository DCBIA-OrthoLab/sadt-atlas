CLIC

CLIC finds impacted canines on a CBCT and says whether each lies on the cheek side, the palate side or across the bone. This page explains how, step by step, with the maths: what goes in, what each step does to it, and what comes out. The files, lines and pitfalls are on the code page; the VISOR port is on its own page.

Code (developers) unpublished VISOR clic_runner.py conda env: clic_env Python 3.9 Bibliography

Overview: what goes in, what comes out

CLIC looks for impacted canines in a CBCT scan. It reads the scan slice by slice; on each slice a trained network outlines the canines it finds and, in the same pass, says where each lies relative to the bone: on the cheek side (buccal), on the palate side (palatal) or across the bone (bicortical). The name promises two tasks, but there is one network: the outline is the localisation and the class is the classification.

CLIC, legacy module
Inputone CBCT as a NIfTI file, or a folder of them, picked in the Slicer panel
Methodper slice: rescale the grey values, give the slice to a Mask R-CNN, keep the confident detections, paint them into a label volume
Outputone label map per scan, on the same grid as the scan: 0 background, 1 buccal, 2 bicortical, 3 palatal
Wherethe panel runs in Slicer; the computation runs in a separate conda environment on the user’s machine, on the graphics card when there is one

This page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957). The VISOR port, which runs the same network on a server, has its own page. File names, line numbers and every pitfall are on the code page.

In the codeWhich code base this describes, and where the VISOR port is

1. Where it sits in the pipeline

CLIC is standalone in both directions: no other module calls it and it calls no other module. It starts from the raw CBCT, with no earlier segmentation, landmarks or orientation, and it does not depend on AMASSS, ASO or ALI. It uses only its own runner script, started once per scan, and a weights file that the panel can download from a GitHub release.

In the codeWhat the widget calls and how, with the conda arguments

2. Files involved

Three files make up the module: the Slicer panel and its interface, and a runner script that holds all the processing. The panel writes the parameters to a small file, starts the runner inside a conda environment and reads its output. The panel needs the SlicerConda helper to load at all, and it only knows the Linux-style way of calling conda, so the module is effectively Linux-only.

In the codeThe file table with line counts, the CondaSetUp import and the missing WSL path

3. Inputs and preprocessing

Two things happen before the network: the panel collects the scans, and the runner prepares each slice.

3.1 Scan collection

The panel accepts a file or a folder and filters on NIfTI, NRRD and MetaImage extensions. The runner can only read NIfTI, so the other formats pass the filter and fail later. If the chosen folder contains sub-folders with scans, the panel returns the sub-folders instead of the files, which the runner cannot load either: the working case is a flat folder of .nii.gz files.

In the codeThe collector function, its two-step rule and the resulting failure

3.2 The actual volume preprocessing

The runner cuts the volume into axial slices along the third array axis, in the order stored in the file, with no reorientation. Each slice is then handled on its own.

This rescaling has a consequence: there is no Hounsfield window and no volume-wide statistic, so each slice has its own contrast, and a slice containing only air is stretched over the full range like any other. After it, the slice is copied to three identical channels to match the colour input of the network’s ImageNet backbone. There is no crop, no region of interest and no resampling by the module. Inside the network, torchvision enlarges the picture so that its short side is 800 pixels (at most 1333 on the long side) and standardises it with the ImageNet mean and spread: a 512 by 512 scan is therefore enlarged to 800 by 800.

In the codeThe three lines of the loop, the normalisation function and torchvision’s transform

4. The model

Everything for one slice, in order. Click a box to read its section.

In the codeHow the model is built, loaded and fed

4.1 Architecture

The network is a Mask R-CNN: a ResNet-50 backbone with a feature pyramid looks at the picture, a proposal stage suggests candidate regions, and for each region two heads predict a class (with a box) and a mask. It is built with four classes: background and the three canine positions. The names and colours (1 buccal, green; 2 bicortical, yellow; 3 palatal, brown) live only in the panel, which uses them to colour the result; the runner just writes the integers 1, 2 and 3.

In the codeThe model builder, its heads, the backbone download and the class table

4.2 The weights

The weights are not in the repository: the panel can download them from a GitHub release into the user’s documents folder. The runner does not look for that name: it takes the first .pth file of the chosen folder in alphabetical order, so with two models in the folder the file name decides. The file is a bare weights dictionary: it carries no hyperparameters, no class count and no training information, so the training set and the metrics cannot be determined from the repository.

In the codeThe download address, the glob and the load call

4.3 What the network literally outputs

For each slice the network returns a list of candidates. Each candidate has a box, a class from 1 to 3, a confidence score and a mask: a picture the size of the slice holding, per pixel, a probability between 0 and 1. torchvision applies its own first filter before the tool does anything (a very low score cut, a removal of overlapping boxes and at most 100 candidates per slice), and sorts the candidates by decreasing score.

In the codeThe dictionary keys, shapes and torchvision’s default thresholds

4.4 From network outputs to the label map

Two thresholds, both written into the script, turn candidates into labels. Then the masks are painted in order.

Because the candidates arrive sorted by decreasing score, the one painted last is the one with the lowest score: an overlap between a buccal and a palatal candidate is settled in favour of the less confident one. Nothing limits the number of candidates per slice, and no 3D consistency is enforced: each slice is classified alone, with no smoothing between slices, no connected-component analysis and no vote. Two neighbouring slices can therefore carry two different classes for the same tooth, and anyone who wants one class per patient has to aggregate it themselves.

In the codeThe two thresholds in the loop and the overwrite pitfall

5. The algorithmic core

There is no non-learned core beyond the thresholds: no registration, no morphology, no component extraction and no measurement. The whole runner is: load the model, loop over the slices, threshold, write. The whole decision is inside the Mask R-CNN.

In the codeThe full runner outline

6. Post-processing and outputs

The runner writes a sub-folder named after the scan, and inside it the label map, named from the scan and the suffix typed in the panel (seg by default). Because the extension is stripped only once, a scan X.nii.gz gives the folder X.nii and the file X.nii_seg.nii.gz: ugly, but without consequence. The label map is stored as 16-bit integers with values 0 to 3 and takes the affine and header of the input scan, so it overlays the scan without any registration.

In Slicer, the panel loads the result as a segmentation and colours the segments in order of creation, not by label value, so if a class is absent from the volume the colours shift. It also draws three small text legends in the Red, Yellow and Green views.

8. Environment

The module creates its own conda environment, clic_env, with Python 3.9 and a few scientific packages, then installs PyTorch through pip from the wheel channel that matches the machine’s graphics card, and finally installs a NumPy older than version 2. This preparation is replayed on every click on Predict, which is slow but harmless. The GPU is optional: without one the runner uses the processor.

The conda patch

The panel patches SlicerConda’s way of locating the conda program, because the Slicer nightly it was written for kept one conda path for the whole machine without checking that it still existed. The patch fixes a doubled folder in the path, checks the file is really there and otherwise searches the system path. It is meant to be removed once the nightly includes the fix that is already in the 5.12 release.

In the codeThe environment table with lines, the pip calls and the patch itself

9. Known issues

  • The progress bar never moves and the result is never loaded into Slicer, although it is written to disk: the runner’s log lines no longer start with the markers the panel looks for. See the bug.
  • Even with the markers fixed, all output of a scan would arrive in one block at the end of the scan, so progress would jump from 0 to 100 percent. See the list.
  • The Cancel button only writes a line to the log. See the list.
  • With no output folder chosen the runner crashes. See the pitfall.
  • Building the network may fetch the ResNet-50 backbone from the internet; the first run offline fails. See the pitfall.
  • Overlaps are settled by order, and neighbouring slices are not made consistent. See the pitfall.
  • NRRD and MetaImage pass the file filter but cannot be read. See the pitfall.
  • The module has no Windows path and is effectively Linux-only. See the pitfall.
  • Per-slice rescaling means the same tooth can look different to the network on two scans with different fields of view. See the list.

10. Literature

No paper covers CLIC. The work is announced as Interpretable Deep Learning for the Detection and Classification of Impacted Canines and severity of root resorption (Tulissi, Cevidanes, Prieto), presented at NA-MIC Project Week 43 (Montreal, 2025): a project in progress, not a publication. The original code comes from a personal repository, ashmoy/maskRcnn. Mask R-CNN itself is described by He et al. (2017) and implemented in torchvision.
