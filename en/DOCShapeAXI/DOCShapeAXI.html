DOCShapeAXI

DOCShapeAXI classifies a 3D surface, such as an airway or a jaw joint, with a two-branch network (a point cloud and many pictures of the surface), then always shows where on the surface the network looked. This page explains how, step by step, with the maths. The details a developer needs (files, lines, arguments, pitfalls) are on the code page.

Prieto 2024 · SPIE Code (developers) VISOR DOCShapeAXI_CLI conda env: shapeaxi Bibliography

Dental Oral and Craniofacial Shape Analysis eXplainability and Interpretability. A single user action: pick a data type, an input folder, an output folder. Everything else, which checkpoint, which architecture, how many classes, is inferred from the data type.

This page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, is described on DOCShapeAXI on VISOR; the points where it differs are named in the text.

Overview: what goes in, what comes out

DOCShapeAXI
Inputa folder of .vtk surfaces that are already segmented elsewhere, and a data type: mandibular condyle, nasopharynx airway obstruction, or alveolar bone defect in cleft
Ideathe network sees each surface as a cloud of points and as 42 pictures taken from around it, merges what both tell it, and gives a class (or an obstruction ratio); a second pass, always run, paints on the surface how much each part weighed
Outputa table with one class per surface, and a copy of each surface carrying one “where it looked” map per class

1. Place in the pipeline

Standalone: nothing in the repository calls DOCShapeAXI. The input meshes are assumed to be already segmented and extracted elsewhere (AMASSS for condyles, airway segmentation, etc.); the module does not produce its own surfaces.

The command runs in a conda environment called shapeaxi, which is shared with FlexReg, ALI, AREG and ASO: any version change there ripples through all of them. If the checkpoint is not on disk, the command downloads it from the main branch of a GitHub repository, so an installed version can fetch weights published after it.

In the codeThe calls the module makes, how they are chained, and the model_path.json download

2. Files involved

The module is a 830-line Slicer panel (conda handling, model choice, progress bar), a 307-line command that does the prediction and the explanation, a small JSON of five checkpoint URLs, and an installer that picks the right PyTorch3D wheel. Most of the real work lives in the shapeaxi package outside the repository; its architecture was read from the installed package and checked against the settings stored in the condyle checkpoint itself.

In the codeThe file table with line counts and where each part runs

3. Inputs and preprocessing

3.1 The list of surfaces

The command lists the input folder, keeps the .vtk files, and writes their names, one per line, in a CSV in the output folder. That CSV is regenerated only if it does not exist yet: adding surfaces to the input folder without emptying the output folder will not get them processed.

3.2 Geometric normalization

Before anything else, every surface is put at a standard size and position.

All absolute-scale information is lost: a small condyle and a large condyle of the same shape are identical to the network. A scale factor learned at training time is stored in the checkpoint, but the installed package never forwards it to this step, so it is silently ignored at inference. This is a bug of the package, not of the repository, and it is detailed on the code page.

In the codeThe transform chain and the shapeaxi bug that drops the learned scale factor

3.3 What the network receives

For every surface: the points, the triangles, and the surface normals encoded as colours (each component of the unit normal mapped from [-1, 1] to [0, 1]). No scalar of the mesh is read: only the geometry and the normals go in. One surface is processed at a time, so meshes of different sizes need no padding.

4. The models

4.1 The decision table

The data type chosen in the panel, through one word of its label, selects the checkpoint, the network class and the number of classes:

4.2 The architecture actually used

This is not a PointNet, nor the ResNet-18 of the original ShapeAXI paper. The network has two branches, merged late. The values given here were confirmed from the settings stored in the condyle checkpoint, not only from the source.

Branch A, the point cloud. 4096 points are sampled uniformly on the surface. An encoder runs four stages of attention in which each point only looks at its 128 nearest neighbours (256 attention heads), subsampling randomly between stages. An attention pooling then reduces the 128 remaining tokens to one vector of 256 numbers.

Branch B, the pictures. Cameras stand on the vertices of a subdivided icosahedron, 42 of them. Each picture is rendered with ambient light only, so the surface colour (the normal) is not shaded, and carries a depth channel besides its three colour channels. The same EfficientNet-B0 (from MONAI) is applied to each of the 42 pictures; attention across the pictures and an attention pooling give a second vector of 256 numbers. The rendering is redone on every pass: there is no image cache.

Fusion. The two vectors are joined (512 numbers) and one linear layer gives one score per class. For regression, the layer has one output.

In the codeThe layers, the sizes, the rendering settings and how the checkpoint confirms them

4.3 What the network outputs, and how a class is derived

For classification only the highest score is kept: the probabilities are computed then discarded, so no confidence measure leaves the module. For regression the raw value is written as it is (an obstruction ratio, on a 0 to 100 scale at training time). A training detail visible in the upstream code: the target is not one-hot but soft probabilities, Gaussians centred on 12.5, 37.5, 62.5 and 87.5. The four severity classes are therefore quartiles of a continuous quantity, which is why a regression model exists on the same airway data.

In the codeThe prediction call, softmax then argmax, and the soft-label detail

5. The explainability mechanism

This is the module’s most distinctive part, and it runs systematically after prediction: neither an option nor a checkbox. In VISOR it can be switched off.

One map per class. The network is asked, for each class in turn, which parts of the pictures pushed that class’s score. This is done on the last block of the image branch only: the saliency describes only the multi-view branch. The point-cloud branch, which contributes half of the merged vector, appears nowhere in the map.

Back on the mesh. Each pixel of each picture knows which triangle it shows, so its value can be carried to that triangle. Across the 42 pictures the aggregation is a maximum, not an average: a region seen once and judged salient keeps its value. The step from triangle to point is crude: the value of each triangle is written onto its first vertex; vertices that are never first in a triangle, and triangles never visible, stay at zero. The map is therefore scattered with zeros, which the median filter partly recovers.

The maps are stored as one array per class on a copy of the surface; the regression checkpoint has a single one with a different name. The file is rewritten at every class, so the final surface carries all the maps. In Slicer they are shown through the Models module, scalars, with a cold-to-hot colour table.

6. Post-processing and outputs

FileContent

a CSV of the surfacesthe list of .vtk files

an explainability folder, one sub-folder per taska copy of each surface plus the Grad-CAM arrays

The prediction columns accumulate on purpose: if the prediction CSV already exists, it is read back and used as a base, so an airway dataset ends up with a binary, a severity and a regression column side by side. Rerunning on the same folder overwrites the columns in place and never clears the old ones.

7. What is predicted vs. what is computed

BlockNature

Color-encoded normalscomputed geometric

Class or ratiopredicted point-cloud encoder, EfficientNet-B0, attention
Grad-CAM mappredicted derived from the network’s gradients (image branch only)
Triangle to vertex, highest across picturescomputed geometric
Median filter on the meshcomputed topological neighbourhood

Two sources of randomness at inference (the point sampling is not seeded) mean two runs can give slightly different maps and, in borderline cases, two different classes. This stays true in VISOR.

8. Environment

Legacy builds a conda environment called shapeaxi with Python 3.12 and PyTorch, then picks the PyTorch3D wheel that matches the installed PyTorch and CUDA, then installs shapeaxi. The order is forced: shapeaxi needs PyTorch3D, which is not on PyPI. A GPU is not mandatory, but the Grad-CAM call assumes GPU 0. The installer asks for shapeaxi 2.0.2 or later, whereas the command is written for the 1.x interface: that mismatch is the first thing to check if the module stops working.

9. Pitfalls and fragile points

Each point is checked in the code and described, with its evidence, on the code page.

  • shapeaxi version mismatch. The command is written for shapeaxi 1.x and the installer fetches 2.x; fixed in VISOR by pinning 1.1.1. Evidence.
  • The learned scale factor is ignored. The preprocessing is per subject, whatever the checkpoint says. Evidence.
  • The saliency covers only one of the two branches. A decision driven by the point cloud gives an uninformative map, with nothing to flag it. Evidence.
  • No confidence is reported. Only the highest class comes out. Evidence.
  • Unseeded sampling. Two runs can differ. Evidence.
  • Lenient checkpoint loading. Missing or extra weights pass silently. Evidence.
  • The download depends on the output folder existing. If it does not, the error appears later, at loading. Evidence.
  • The log file lives in the module’s own folder. A read-only install breaks it. Evidence.
  • Model selection goes through the words of the data-type label. Renaming the label breaks it. Evidence.

10. Literature

Three references, not to be confused with one another. The framework: ShapeAXI: Shape Analysis Explainability and Interpretability, Prieto et al., Proc. SPIE Medical Imaging, April 2024, DOI 10.1117/12.3007053, which reports 79.78% on condyles and 81.58% on cleft severity. The airway dataset: Mattos et al., J Dent 2025, which describes exactly this architecture (an ImageNet-pretrained EfficientNet-B0 branch with attention, a 4096-point branch with neighbour attention, and the Grad-CAM mechanism of section 5), with AUC 0.77 to 0.94 and R = 0.854 for the ratio. The origin of the Slicer module: lucieDLE/DOC-ShapeAXI. Nothing is published on the cleft dataset beyond the cleft severity experiment in the SPIE paper.

The code diverges from the SPIE paper: the paper describes a ResNet-18 and a binary condyle task, while the checkpoints distributed here are two-branch networks with four severity classes. Do not present the paper’s figures as those of the downloaded models. Details.
