CNE

A language-model (LLM) inference module that reads free-text clinical notes and extracts key–value pairs from them: it is neither a geometric tool nor an image-processing one, despite its place in a suite of dental tools.

unpublished VISOR CNE_CLI no conda: Slicer's Python Bibliography

Scope warning. Unlike AutoCrop3D and AutoMatrix, CNE is not a geometric utility: it touches no volume, no mesh, no coordinate. It is an LLM inference module that reads free-text clinical notes and writes key–value pairs. At the core of the module sits a quantized GGUF model loaded by llama-cpp-python inside Slicer's Python.

Two code bases

Everything numbered below describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, is described on its own page, CNE on VISOR. One consequence matters before you read on: where this page says the model runs locally, that is true of the legacy module only. With VISOR the note text is sent to the server (see Findings in VISOR).

0. The acronym

The repository never spells out the acronym in any documentation: the README contains no CNE section, and no longer documents the MedX it replaced either, neither name appears in it. The module's help text (CNE.py:157) says only "This tool helps to create summaries of clinical notes".

Two log lines, and only those, give the expansion: logger.info("CNE (Clinical Notes Extraction)") (CNE.py:342 and CNE.py:663), and the CLI publishes the same name to the Slicer supervisor: <filter-name>Clinical Notes Extraction</filter-name> (CNE_CLI.py:93). CNE = Clinical Notes Extraction, attested by the code and by nothing else.

1. Place in the pipeline

Terminal module. Nothing calls it, and it calls no other module in the repository. Declared in CMakeLists.txt:50-52 (CNE, CNE_CLI, CNE_Dashboard).

It replaces the "Summarization" half of MedX, which was disabled from the build in March 2026 with the comment "Replaced by CNE".

Two points worth knowing:

Gotcha (legacy only)

Legacy (3c67957); not present in VISOR: nothing is compiled or installed on the workstation, the server environment pins llama-cpp-python==0.3.35 from a prebuilt wheel index (SADT-VISOR tools/CNE/pyproject.toml:60-67; see CNE on VISOR). install_function (CNE.py:44) forces CC=gcc and CXX=g++ during installation and then restores the original values: this is for the case where pip has to compile llama-cpp-python from source. On Windows these values are unusable.

Gotcha (also true in VISOR, now reported)

Also true in VISOR: the pinned index is still the CPU one (SADT-VISOR tools/CNE/pyproject.toml:60-67). What changed is that the request is no longer silent: device is an explicit argument defaulting to cpu, and a cuda request met by a CPU build is written to the report as gpu_offload and warnings (src/sadt_cne/__init__.py:145-165,184-185; see CNE on VISOR). The extra index explicitly points to the CPU wheels. Yet the CLI requests n_gpu_layers=-1 with the comment "Use GPU if available" (CNE_CLI.py:164): with a CPU-only build this parameter has no effect. In practice inference runs on CPU, and a 7–8 B Q4-quantized model costs several tens of seconds per note there.

The CLI re-tests its three imports (llama_cpp, fitz, docx) at startup and calls sys.exit(1) if one is missing (CNE_CLI.py:101-117): redundant, but harmless since the CLI shares the widget's interpreter.

Corrected (legacy only)

Legacy (3c67957) download code. In VISOR nothing is downloaded by the client: the models are hosted on the server, and the data manifest stages only the TMJ bundle (VISOR-serve scripts/data-manifest.yml:687-695); see Findings in VISOR. This page used to record a confirmed bug here: the Ortho mode asked for model-q4_0.gguf, which did not exist in the repository, so the download returned HTTP 404 and failed with "Download failed or was cancelled". The code now asks for model-q4_k_m.gguf in DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho (CNE.py:518-519), and the TMJ file in DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ (CNE.py:525-526). Checked on 2026-11-09 with an HTTP HEAD request on both URLs: each answers 302 to the file, and the Ortho file is 4,920,738,880 bytes, hence the "approx. 4.9 GB" of the download dialog (CNE.py:521; the TMJ dialog says 4.4 GB, CNE.py:528, which was not measured).

Both Hugging Face repositories now carry a model card, which this page used to say they lacked (read through the Hugging Face API on 2026-11-09, not from the ADT repository). Each states its license (Llama 3.1 for Ortho, Apache 2.0 for TMJ), the base model, the method (LoRA, r = 32, alpha = 64, merged then quantized to Q4_K_M), that the training notes are annotated patient data that are not released, and that the sets were split by patient. The Ortho card says the model takes the raw note with no system prompt, which matches the code (§6), and lists orthodontic features (wire size and material, ligation, elastics, overjet, overbite, ...) as its schema. Neither card reports an evaluation. The TMJ card gives the file as 4.7 GB, while the download dialog says 4.4 GB (CNE.py:528).

5. Inputs and preprocessing

SUPPORTED_EXTENSIONS = (".txt", ".pdf", ".docx"). The scan is non-recursive: glob.glob(os.path.join(notesFolder_input, f"*{ext}")) (CNE_CLI.py:135), unlike every other module in the repository, which uses iglob(**, recursive=True). A folder made of per-patient subfolders will yield nothing.

Text extraction (CNE_CLI.py:75):

FormatExtractorDetail
.pdffitz.open then "\n".join(page.get_text() for page in doc)no OCR: a scanned PDF comes out empty
.docxdocx.Document, paragraph.texttables are lost (doc.paragraphs does not iterate over them)
.txtopen(..., encoding="utf-8")a file in cp1252 raises UnicodeDecodeError, caught by the loop and counted as a failure

clean_text() (CNE_CLI.py:42) is the only preprocessing step, and its motivation is stated in the code: normalize what varies between PDF/Word exports but never appeared in the plain-text training notes, smart apostrophes and quotes to ASCII, en dash and em dash to -, non-breaking space to a regular space, then collapsing of consecutive blank lines. Explicit goal: the model should see the same text regardless of the source format.

No anonymization, no PHI filtering. The repository's test notes are pseudonymized by hand (B_001, [DOCTOR], Dr. XXX) but nothing in the code guarantees this for the user's own data. The Medical_Data_Anonymizer_Module module exists separately and is not chained to CNE.

6. Inference

A single pass per file, with no chunking (CNE_CLI.py:194-203):

messages = []
if notesType.upper() == "TMJ":
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": clinical_text})

output = llm.create_chat_completion(messages=messages, max_tokens=500, temperature=0.1)

Worth noting:

Gotcha (also true in VISOR)

Also true in VISOR (SADT-VISOR tools/CNE/src/sadt_cne/extraction.py:51: SYSTEM_PROMPTS = {"TMJ": INSTRUCTION_TMJ, "Ortho": None}; see CNE on VISOR). Ortho mode sends no instruction. Only the raw note goes out as the user message; it is the fine-tuning of the Llama-Ortho model that is supposed to carry the task. TMJ mode, by contrast, keeps the instruction inherited from MedX.

  • create_chat_completion applies the chat template embedded in the GGUF. Both models are tagged conversational on Hugging Face, so the template does exist; it is neither visible nor controllable from the repository.
  • temperature=0.1 and no seed: the output is nearly deterministic but not exactly reproducible.
Gotcha (partly true in VISOR)

VISOR (SADT-VISOR tools/CNE/src/sadt_cne/): max_tokens defaults to 2048 instead of 500 (__init__.py:46-56), and an answer cut off by the limit is a failure of that note instead of being written (__init__.py:293-297). Still true: nothing checks the note's length against the window, and nothing checks max_tokens against it either (extraction.py:146-153 only rejects a negative window); an overflow raises inside llama.cpp and is caught per note (__init__.py:200-212; see CNE on VISOR). No guard on length. n_ctx is 6144 (TMJ) or 2048 (Ortho) and max_tokens=500 is taken out of that budget. A note exceeding the budget makes llama.cpp raise; the exception is caught per file, logged, and the file is added to failed_files. The Ortho budget is particularly tight: ~1,500 tokens of usable note. The test note TMJ_note1.txt is roughly 4,400 characters long, which passes in TMJ mode.

  • Model loading is wrapped by redirecting stderr to /dev/null via os.dup2 (CNE_CLI.py:159), to mask llama.cpp's chatter, which would otherwise pollute the error channel that Slicer interprets as a CLI failure.

7. Post-processing the response

The model is expected to answer in JSON; the code does not enforce this (no response_format, no GBNF grammar) and simply fishes out the JSON from the text (CNE_CLI.py:209-214):

start_idx = ai_response.find('{')
end_idx   = ai_response.rfind('}') + 1
data = json.loads(ai_response[start_idx:end_idx])
if "extraction" in data:
    data = data["extraction"]
for key, value in data.items():
    formatted_response += f"{key} : {value}\n"

So: first opening brace through last closing brace, unwrapping of a possible extraction level, then flattening into key : value lines. If the parse fails or there is no brace at all, the model's raw response is written as is. The output file does not say which of the two cases occurred.

Gotcha (partly corrected in VISOR)

VISOR: nested values are no longer written as a Python repr (extraction.py:318-328). The first-brace to last-brace slicing is kept (extraction.py:263-266), but when json.loads fails the answer is read as key: value lines, and if that fails too nothing is written and the note is reported as failed, instead of saving the raw text (extraction.py:278-301, __init__.py:299-305; see CNE on VISOR). Consequences: the naive find('{')…rfind('}') slicing breaks as soon as the response contains more than one JSON object, and a nested value (list, dict) is rendered by its Python repr in the text file.

8. Outputs

One text file per input note, in the output folder:

Extraction_<note name without extension>.txt

Content: key : value lines, or the model's raw response if the parse failed. No CSV, no json and no per-patient aggregation from the extraction itself: the table and the figure come from the Dashboard button (§8.1), which reads these files afterwards.

The output folder is created by os.makedirs(..., exist_ok=True) on the widget side (CNE.py:613).

8.1 The Dashboard

The "Dashboard" half of MedX was ported on 2026-10-12, so the earlier statement of this page that it "was not carried over" no longer holds. It is read from the code as follows:

  • Trigger. The Dashboard button (dashboardButton in CNE.ui, connected at CNE.py:234) runs onDashboardButton() (CNE.py:365). It checks the dependencies, refuses to run without an output folder, and launches CNE_Dashboard via CNELogic.dashboard() (CNE.py:629) with the output folder as both input and output. No model and no download are involved.
  • Reading. read_summaries() (display_figure.py:23) keeps only Extraction_*.txt files in the folder; the patient identifier is the note name minus the prefix. process_summaries() (display_figure.py:135) fills a dictionary of 54 keys seeded by initialize_key_value_summary() (dashboard_utils.py:332) and converts six numeric fields.
  • Computed, not predicted. Each panel is a deterministic aggregation computed in dashboard_utils.py (age groups, mean and SD of pain scores, maximum mouth opening parsed from strings such as "33 mm", headache and joint-pain locations by synonym lists, disc displacement left and right, muscle pain level). The figure is drawn by generate_dashboard_figure() (display_figure.py:164).
  • Outputs. dashboard.png and patient_data.csv (display_figure.py:714-716), plus a third file, dashboard_full_dataframe.csv (display_figure.py:183), written before the figure is drawn.
  • Fails loudly when the schema does not match. report_field_coverage() (display_figure.py:668) logs the expected keys that carry no value, and show_dashboard() (display_figure.py:694) raises if none carries one or if the folder holds no Extraction_*.txt.
Gotcha (legacy only)

Legacy (3c67957); there is no Dashboard in VISOR (see the first callout of §1 and CNE on VISOR). The dashboard is a TMJ dashboard. The expected keys are headache intensity, jaw clicking, disc displacement, maximum opening, sleep disorder and similar (dashboard_utils.py:339-396). They are the keys the TMJ model is supposed to return; nothing in the repository says the Ortho model writes them, and the Ortho mode has no instruction to impose them. On Ortho extractions the coverage check would most likely stop the run with the "keys do not match" error. This is an inference from the key list, not something run against Ortho output. The keys themselves are chosen by the model, not by the code (docstring of report_field_coverage, display_figure.py:668-679).

9. What is predicted vs. what is computed

BlockNatureWhere
PDF/Word text extractioncomputed PyMuPDF / python-docxCLI

All the clinical content of the output comes from the model. There is no rule, no dictionary of terms, no schema validation: whatever the model writes is what gets saved.

11. Gotchas and fragile points

  • The Dashboard expects the TMJ schema (§8.1).
  • The test files' output folder. copyTestFiles() (CNE.py:454) used to put a path that did not exist into the output field. It now creates the output folder (CNE.py:508), copies the notes again on every call without erasing the folder (dirs_exist_ok=True, CNE.py:505), and leaves an output folder already chosen by the user alone (CNE.py:328-330). Resources/testfiles/ still holds only the two input_ folders.
  • Non-recursive scan of the input folder (§5).
  • No length limit before the call: a note that is too long fails instead of being chunked, whereas MedX did chunk (§6). This is a functional regression of the replacement.
  • Ortho mode sends no system instruction (§6): if the model is not the one expected, there is no reason for the output to be JSON at all.
  • No constraint on output format: no GBNF grammar and no response_format, even though llama.cpp offers both. Post-processing is therefore a heuristic fishing operation (§7).
  • Radio button set to neither TMJ nor Ortho → notesType = "" (CNE.py:427) → in getModelPath, repo_id is never assigned and the UnboundLocalError surfaces as "Failed to load model". This case should not occur (setExclusive(True) and a default of TMJ), but nothing blocks it.
  • Inconsistent casing: notesType == "TMJ" sets n_ctx, while notesType.upper() == "TMJ" sets the instruction. A lowercase notesType would give the TMJ instruction with the 2048 context.
  • No provenance trail: the Extraction_*.txt file mentions neither the model, its version, nor the date. Two runs with different models produce indistinguishable files.
  • PHI: nothing anonymizes, nothing warns. Notes are read in the clear, passed through a local model (so no network exfiltration: that is the only safeguard, and it is structural rather than deliberate). Legacy module only (3c67957). With VISOR the notes are uploaded to a server as they are, and nothing de-identifies them first: see Findings in VISOR.
  • CLI metadata left at the template default: CNE_CLI.xml still describes "Apply a Gaussian blur to an image", attributes the module to "Andras Lasso (PerkLab)", and its <index> values are 0, 2, 3, 4, index 1 is missing.
  • onCliProgress (CNE.py:651) reads caller.GetProgress() and does nothing with it; it is not even connected to any observer. Dead code. Actual progress goes through the CLI's <filter-progress> tags, read by qSlicerCLIProgressBar.

12. Literature

No publication is cited in the repository for CNE, and the two DCBIA-OrthoLab/* Hugging Face model cards cite no paper (they point to a code repository, ortho-cde-llm-extraction, which was not read). The annotation corpus is not released and no evaluation is reported: both are not determinable from the repository.

What is verifiable:

  • The MedX → CNE lineage, documented only by the acknowledgement line of CNE_Dashboard.xml ("Ported from MedX_Dashboard, which CNE replaced without taking this half with it") and the comments in display_figure.py:35 and :675. The root CMakeLists.txt no longer mentions MedX and the README has no MedX or CNE section.
  • The base models: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • The fine-tuned repositories: DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho.
  • The engine: llama-cpp-python, llama.cpp (GGUF format, Q4_K_M quantization).
  • SlicerAutomatedDentalTools

Do not tie CNE to the general literature on clinical information extraction by LLM: nothing in the repository indicates that the models used here come from published work.
