CNE

CNE reads free-text clinical notes and writes the facts it finds in them (symptoms, diagnoses, scores) as a list of field : value lines. It is a language-model module: it touches no image and no mesh. This page explains the pipeline of the legacy Slicer module step by step; the code details are on the code page.

unpublished VISOR CNE_CLI no conda: Slicer's Python Bibliography Code (developers) Guide

CNE is not a geometric tool: it reads text and writes text. A quantised language model (GGUF format) is loaded by llama-cpp-python inside Slicer’s own Python. This page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port runs the same tool on a server and has its own page. One consequence matters before you read on: where this page says the model runs locally, that is true of the legacy module only. With VISOR the note text is sent to the server (known problems in VISOR).

Overview: what goes in, what comes out

CNE, legacy
Inputa folder of notes (.txt, .pdf, .docx), not searched recursively, and a choice between TMJ and Ortho
The modela quantised Qwen 2.5 7B (TMJ) or Llama 3.1 8B (Ortho), downloaded on first use and run on the processor
Outputone text file per note, field : value lines, in the output folder
Optionala Dashboard button that reads those files and draws a figure and two CSV tables

0. The acronym

CNE stands for Clinical Notes Extraction. The repository never says so in its documentation: only two log lines and the name the tool announces to Slicer give the expansion.

In the codeThe log lines and filter name that attest the expansion

1. Place in the pipeline

CNE is a terminal module: nothing calls it and it calls nothing. It replaces the summarisation half of MedX, which was disabled from the build in March 2026 with the comment “Replaced by CNE”. MedX itself left the tree on 2026-09-17 and lives on the archive/medx branch. The Dashboard half was ported into CNE on 2026-10-12 (section 8.1); VISOR has no Dashboard.

Compared with the MedX summariser it replaces:

  • Engine and model: llama.cpp and a quantised Llama or Qwen instead of PyTorch and a BART model.
  • No chunking: the whole note goes to the model in one message, where MedX cut it into pieces.
  • Decoding: temperature 0.1 and at most 500 tokens, instead of beam search with sampling.
  • No per-patient aggregation: one file gives one output.

The one instruction sentence of TMJ mode is the same sentence MedX used (MedX put it in front of the text, CNE sends it as a separate system message).

In the codeWhich build files declare it, the corrected survey, the full MedX comparison table

2. Files involved

Four parts: the widget (dependencies, model download, launching the job, the Dashboard button), the command-line job that reads notes and calls the model, the Dashboard job with its two helper files, and the interface file. Four sample notes ship in the repository. There is no conda environment: everything runs in Slicer’s Python.

In the codeFile table with the roles and where each runs

3. Dependencies, installed on demand

When Apply is clicked, the module checks five packages (the llama.cpp binding, a PDF reader, a Word reader, a plotting library and a table library) and, after confirmation, installs the missing ones into Slicer’s Python. The wheel index it points to is the processor-only build. The job asks for GPU layers anyway, which has no effect on that build: in practice inference runs on the processor, and a 7 to 8 billion parameter model is slow there (the time per note was not measured for this page).

4. The models

No weights ship in the repository. The first run downloads the model for the chosen mode into the Documents folder.

The Ortho download used to fail because it asked for a file that did not exist; this was corrected (details). Both Hugging Face repositories now carry a model card that states the license, the base model and the fine-tuning method, and says the training notes are patient data that are not released. Neither card reports an evaluation.

5. Inputs and preprocessing

The module looks for .txt, .pdf and .docx files in the chosen folder only: sub-folders are not searched, unlike every other module, so a folder organised by patient yields nothing. Text comes out of a PDF page by page with no OCR (a scanned PDF is empty), out of a Word file paragraph by paragraph (tables are lost), and out of a text file as UTF-8 (another encoding makes that note fail).

Nothing anonymises the notes. The test notes in the repository were pseudonymised by hand, and the separate MedicalDataAnonymizer module is not chained to CNE.

In the codeThe three extractors, the replacement table and the glob call

6. Inference

The model is called once per note, with no chunking. In TMJ mode the note is preceded by the instruction sentence; in Ortho mode the note goes alone, because the Ortho model is supposed to carry the task in its fine-tuning.

The answer is limited to 500 tokens and the temperature is 0.1 with no seed, so the output is nearly deterministic but not exactly reproducible. A note that leaves less than 500 tokens of room does not raise an error: the engine shortens the answer to what is left, so the JSON is cut off and the raw text is written (§7). Only a prompt that fills the whole window makes the engine raise; the error is caught for that note, logged, and the file is counted as failed. The model’s own chat template is applied, and cannot be seen or changed from the repository.

In the codeThe call, the TMJ and Ortho messages, the stderr redirection

7. Post-processing the response

Nothing forces the model to produce JSON, so the module fishes it out of the answer.

If the slice holds a wrapper called extraction, that level is removed; each field is then written as a field : value line, and a nested value appears as its Python representation. If the slice cannot be read, or the answer has no brace at all, the model’s raw answer is written as it is, and the file does not say which of the two cases happened.

In the codeThe slicing code and the partly corrected VISOR behaviour

8. Outputs

One text file per note, Extraction_<note name>.txt, holding field : value lines or the raw answer. No CSV, no JSON and no per-patient aggregation come from the extraction itself.

In the codeFile naming, output folder creation

8.1 The Dashboard

A button beside Run launches a second job that reads the Extraction_*.txt files of the output folder. It fills a table of 56 keys (the patient id and 55 fields the model is expected to return), converts six of them to numbers, and computes one deterministic summary per panel of the figure: age groups, mean and spread of pain scores, maximum mouth opening, where headaches and joint pain are, disc displacement, muscle pain. It writes dashboard.png and two CSV tables, and stops with an error when the files do not carry the expected fields. No model and no download are involved.

It is a TMJ dashboard: the expected fields are those the TMJ model is supposed to return. Nothing says the Ortho model writes them, so on Ortho extractions the coverage check would most likely stop the run (an inference from the field list, not run).

In the codeTrigger, readers, aggregation functions and the coverage check

PDF and Word text extractioncomputed PyMuPDF and python-docx

All the clinical content of the output comes from the model. There is no rule, no dictionary of terms and no schema check: whatever the model writes is what gets saved.

10. Environment

Slicer’s Python only, with five packages installed on the fly. A 7 to 8 billion parameter quantised model needs roughly 5 to 6 GB of memory on top of Slicer. The weights take about 4.4 GB (TMJ) or 4.9 GB (Ortho) on disk.

In the codeInterpreter, packages, GPU and weights locations

11. Known problems

  • The Dashboard expects the TMJ fields and would probably stop on Ortho extractions (details).
  • Ortho mode sends no instruction, so nothing makes the output JSON if the model is not the expected one (details).
  • No length guard: a note longer than the window fails instead of being cut into chunks, a regression from MedX (details).
  • The answer format is not constrained, and the first-brace to last-brace slice breaks on two objects (details).
  • The scan of the input folder is not recursive (all gotchas).
  • Output files record neither the model nor the date, so two runs with different models cannot be told apart (all gotchas).
  • Nothing anonymises the notes; the only safeguard is that the model runs locally, which is true of this legacy module only (all gotchas).
  • The processor-only build makes the GPU request pointless (details).

12. Literature

No publication is cited in the repository for CNE, and the two DCBIA-OrthoLab/* Hugging Face model cards cite no paper (they point to a code repository, ortho-cde-llm-extraction, which was not read). The annotation corpus is not released and no evaluation is reported: both are not determinable from the repository.

What is verifiable:

  • The MedX → CNE lineage, documented only by the acknowledgement line of CNE_Dashboard.xml ("Ported from MedX_Dashboard, which CNE replaced without taking this half with it") and the comments in the Dashboard code (see the code page). The root CMakeLists.txt no longer mentions MedX and the README has no MedX or CNE section.
  • The base models: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • The fine-tuned repositories: DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho.
  • The engine: llama-cpp-python, llama.cpp (GGUF format, Q4_K_M quantization).
  • SlicerAutomatedDentalTools

Do not tie CNE to the general literature on clinical information extraction by LLM: nothing in the repository indicates that the models used here come from published work.
