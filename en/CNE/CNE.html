CNE

A language-model (LLM) inference module that reads free-text clinical notes and extracts key–value pairs from them — it is neither a geometric tool nor an image-processing one, despite its place in a suite of dental tools.

unpublished CNE_CLI no conda — Slicer's Python Bibliography

Scope warning. Unlike AutoCrop3D and AutoMatrix, CNE is not a geometric utility: it touches no volume, no mesh, no coordinate. It is an LLM inference module that reads free-text clinical notes and writes key–value pairs. At the core of the module sits a quantized GGUF model loaded by llama-cpp-python inside Slicer's Python.

0. The acronym

The repository never spells out the acronym in any documentation: the README contains no CNE section (it still documents MedX, which CNE replaces, cf. CMakeLists.txt:42 "Replaced by CNE"). The module's help text (CNE.py:147) says only "This tool helps to create summaries of clinical notes".

Two log lines, and only those, give the expansion: logger.info("CNE (Clinical Notes Extraction)") (CNE.py:329 and CNE.py:606), and the CLI publishes the same name to the Slicer supervisor: <filter-name>Clinical Notes Extraction</filter-name> (CNE_CLI.py:91). CNE = Clinical Notes Extraction, attested by the code and by nothing else.

1. Place in the pipeline

Terminal module. Nothing calls it, and it calls no other module in the repository. Declared in CMakeLists.txt:51.

It replaces the "Summarization" half of MedX. MedX/ and MedX_CLI/ are still in the tree but disabled from the build (CMakeLists.txt:42-44); the "Dashboard" half of MedX (dashboard.png + patient_data.csv) has no equivalent in CNE and therefore disappears from the compiled extension.

The system instruction is copied verbatim from MedX: "Using the following note, extract structured key-value pairs about the patient's symptoms and diagnoses:" (CNE_CLI.py:22 vs MedX_Summarize.py:50).

No conda. The CLI is a scripted CLI, so it is launched by slicer.cli.run in Slicer's Python — it is in that same interpreter that llama-cpp-python is installed and the model is loaded into memory.

3. Dependencies, installed on demand

check_dependencies() (CNE.py:83) is called on clicking Apply, not on module load. It tests three imports and, if any are missing, asks for confirmation before slicer.util.pip_install:

Import testedPackage installedUse
llama_cppllama-cpp-python --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cpuinference
fitzpymupdfPDF text extraction
docxpython-docxWord text extraction

Two points worth knowing:

Gotcha

install_function (CNE.py:44) forces CC=gcc and CXX=g++ during installation and then restores the original values — this is for the case where pip has to compile llama-cpp-python from source. On Windows these values are unusable.

Gotcha

The extra index explicitly points to the CPU wheels. Yet the CLI requests n_gpu_layers=-1 with the comment "Use GPU if available" (CNE_CLI.py:162): with a CPU-only build this parameter has no effect. In practice inference runs on CPU, and a 7–8 B Q4-quantized model costs several tens of seconds per note there.

The CLI re-tests the three imports at startup and calls sys.exit(1) if one is missing (CNE_CLI.py:99-115) — redundant, but harmless since the CLI shares the widget's interpreter.

4. The models

No weights ship in the repository. getModelPath() (CNE.py:478) downloads the GGUF on demand, via urllib.request.urlretrieve with a QProgressDialog, into <Documents>/SlicerDownloads/CNE/model/.

Constructed URL: https://huggingface.co/{repo_id}/resolve/main/{fileName}.

Confirmed bug

The Ortho download is broken. Verified via the Hugging Face API: the repository dcbia/Meta-Llama-3.1-8B-Instruct-Ortho contains only .gitattributes and model-q4_k_m.gguf. The file model-q4_0.gguf requested by the code does not exist — the URL returns HTTP 404, while the q4_k_m URL returns 200. urlretrieve raises, the partial file is deleted, and the user sees "Download failed or was cancelled". TMJ mode, on the other hand, is correct (qwen-ft-q4_k_m.gguf → 200). Fix: model-q4_0.gguf → model-q4_k_m.gguf.

Both Hugging Face repositories have no model card: no license, no training set, no fine-tuning method published. The base architectures are identifiable from the tags (Llama-3.1-8B-Instruct and Qwen2 7B), with quantization Q4_K_M in both cases. What sets the two fine-tuned models apart — annotation corpus, learned output schema, protocol — is not determinable from the repository or from Hugging Face.

5. Inputs and preprocessing

SUPPORTED_EXTENSIONS = (".txt", ".pdf", ".docx"). The scan is non-recursive: glob.glob(os.path.join(notesFolder_input, f"*{ext}")) (CNE_CLI.py:133) — unlike every other module in the repository, which uses iglob(**, recursive=True). A folder made of per-patient subfolders will yield nothing.

Text extraction (CNE_CLI.py:73):

FormatExtractorDetail
.pdffitz.open then "\n".join(page.get_text() for page in doc)no OCR: a scanned PDF comes out empty
.docxdocx.Document, paragraph.texttables are lost (doc.paragraphs does not iterate over them)
.txtopen(..., encoding="utf-8")a file in cp1252 raises UnicodeDecodeError, caught by the loop and counted as a failure

clean_text() (CNE_CLI.py:40) is the only preprocessing step, and its motivation is stated in the code: normalize what varies between PDF/Word exports but never appeared in the plain-text training notes — smart apostrophes and quotes to ASCII, en dash and em dash to -, non-breaking space to a regular space, then collapsing of consecutive blank lines. Explicit goal: the model should see the same text regardless of the source format.

No anonymization, no PHI filtering. The repository's test notes are pseudonymized by hand (B_001, [DOCTOR], Dr. XXX) but nothing in the code guarantees this for the user's own data. The Medical_Data_Anonymizer_Module module exists separately and is not chained to CNE.

6. Inference

A single pass per file, with no chunking (CNE_CLI.py:192):

messages = []
if notesType.upper() == "TMJ":
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": clinical_text})

output = llm.create_chat_completion(messages=messages, max_tokens=500, temperature=0.1)

Worth noting:

Gotcha

Ortho mode sends no instruction. Only the raw note goes out as the user message; it is the fine-tuning of the Llama-Ortho model that is supposed to carry the task. TMJ mode, by contrast, keeps the instruction inherited from MedX.

  • create_chat_completion applies the chat template embedded in the GGUF. Both models are tagged conversational on Hugging Face, so the template does exist; it is neither visible nor controllable from the repository.
  • temperature=0.1 and no seed: the output is nearly deterministic but not exactly reproducible.
Gotcha

No guard on length. n_ctx is 6144 (TMJ) or 2048 (Ortho) and max_tokens=500 is taken out of that budget. A note exceeding the budget makes llama.cpp raise; the exception is caught per file, logged, and the file is added to failed_files. The Ortho budget is particularly tight: ~1,500 tokens of usable note. The test note TMJ_note1.txt is roughly 4,400 characters long, which passes in TMJ mode.

  • Model loading is wrapped by redirecting stderr to /dev/null via os.dup2 (CNE_CLI.py:155), to mask llama.cpp's chatter, which would otherwise pollute the error channel that Slicer interprets as a CLI failure.

7. Post-processing the response

The model is expected to answer in JSON; the code does not enforce this (no response_format, no GBNF grammar) and simply fishes out the JSON from the text (CNE_CLI.py:207):

start_idx = ai_response.find('{')
end_idx   = ai_response.rfind('}') + 1
data = json.loads(ai_response[start_idx:end_idx])
if "extraction" in data:
    data = data["extraction"]
for key, value in data.items():
    formatted_response += f"{key} : {value}\n"

So: first opening brace through last closing brace, unwrapping of a possible extraction level, then flattening into key : value lines. If the parse fails or there is no brace at all, the model's raw response is written as is. The output file does not say which of the two cases occurred.

Gotcha

Consequences: the naive find('{')…rfind('}') slicing breaks as soon as the response contains more than one JSON object, and a nested value (list, dict) is rendered by its Python repr in the text file.

8. Outputs

One text file per input note, in the output folder:

Extraction_<note name without extension>.txt

Content: key : value lines, or the model's raw response if the parse failed. No CSV, no json, no per-patient aggregation — MedX's dashboard was not carried over.

The output folder is created by os.makedirs(..., exist_ok=True) on the widget side (CNE.py:578).

9. What is predicted vs. what is computed

BlockNatureWhere
PDF/Word text extractioncomputed PyMuPDF / python-docxCLI
Typographic normalizationcomputed fixed replacement table, 7 entriesCLI
Key–value pair extractionpredicted LLM, Qwen-2.5-7B-TMJ or Llama-3.1-8B-Ortho, GGUF Q4CLI, in-process llama_cpp
Formattingcomputed find('{') / json.loads / flattening loopCLI

All the clinical content of the output comes from the model. There is no rule, no dictionary of terms, no schema validation: whatever the model writes is what gets saved.

11. Gotchas and fragile points

  • The Ortho model does not download: wrong file name, HTTP 404 (§4). Fix: model-q4_0.gguf → model-q4_k_m.gguf.
  • The test files' output folders do not exist. copyTestFiles() (CNE.py:409) copies input_<type> and output_<type>, but Resources/testfiles/ contains only the two input_ folders. The shutil.copytree of the output folder is skipped with a warning, and the UI ends up with an output path filled in that does not yet exist.
  • Non-recursive scan of the input folder (§5).
  • No length limit before the call: a note that is too long fails instead of being chunked, whereas MedX did chunk (§6). This is a functional regression of the replacement.
  • Ortho mode sends no system instruction (§6): if the model is not the one expected, there is no reason for the output to be JSON at all.
  • No constraint on output format: no GBNF grammar and no response_format, even though llama.cpp offers both. Post-processing is therefore a heuristic fishing operation (§7).
  • Radio button set to neither TMJ nor Ortho → notesType = "" (CNE.py:382) → in getModelPath, repo_id is never assigned and the UnboundLocalError surfaces as "Failed to load model". This case should not occur (setExclusive(True) and a default of TMJ), but nothing blocks it.
  • Inconsistent casing: notesType == "TMJ" sets n_ctx, while notesType.upper() == "TMJ" sets the instruction. A lowercase notesType would give the TMJ instruction with the 2048 context.
  • No provenance trail: the Extraction_*.txt file mentions neither the model, its version, nor the date. Two runs with different models produce indistinguishable files.
  • PHI: nothing anonymizes, nothing warns. Notes are read in the clear, passed through a local model (so no network exfiltration — that is the only safeguard, and it is structural rather than deliberate).
  • CLI metadata left at the template default: CNE_CLI.xml still describes "Apply a Gaussian blur to an image", attributes the module to "Andras Lasso (PerkLab)", and its <index> values are 0, 2, 3, 4 — index 1 is missing.
  • onCliProgress (CNE.py:594) reads caller.GetProgress() and does nothing with it; it is not even connected to any observer. Dead code. Actual progress goes through the CLI's <filter-progress> tags, read by qSlicerCLIProgressBar.

12. Literature

No publication is cited in the repository for CNE, and both dcbia/* Hugging Face repositories are published with no model card and no reference. The fine-tuning protocol, the TMJ/Ortho annotation corpus, and the evaluation are not determinable from the repository.

What is verifiable:

  • The MedX → CNE lineage, documented only by CMakeLists.txt:42 and the MedX section of README.md:425, which still describes the old BART pipeline and the vanished dashboard.
  • The base models: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • The fine-tuned repositories: dcbia/Qwen-2.5-7B-Instruct-TMJ, dcbia/Meta-Llama-3.1-8B-Instruct-Ortho.
  • The engine: llama-cpp-python, llama.cpp (GGUF format, Q4_K_M quantization).
  • SlicerAutomatedDentalTools

Do not tie CNE to the general literature on clinical information extraction by LLM: nothing in the repository indicates that the models used here come from published work.
