3. The pipeline

Plain-language explanation and maths: atlas page.

3.1 Loading the model packages

Plain-language explanation and maths: atlas page.

model is optional and hidden. When it is empty, run() uses <data_root>/Surg_Mov_Pred/models (__init__.py:19,22-34,71). load_model_packages then takes every stacking_package.pkl below it, in sorted order, and loads each with joblib (pipeline.py:162-195):

package_files = sorted(model.glob("**/stacking_package.pkl"))   # legacy: list(...), filesystem order
for pkl_path in package_files:
    package = joblib.load(pkl_path)        # {target_name, features_names, scaler, model}
    packages[package["target_name"]] = package

An unreadable package is logged and skipped; if none loads, RuntimeError (pipeline.py:180-192). The comment in layout.py:16-24 describes the shipped set: 112 packages, each asking for the same 145 columns, of which 28 carry the suffix _T0 (pre-operative state) and 25 the suffix _Total (the planned total movement). The table therefore holds the plan as well as the measurements, hence the label "Measurements and plan". The stacking regressors contain LightGBM sub-estimators, so lightgbm must be installed for joblib.load to succeed (pyproject.toml:18-20). The packages were pickled under scikit-learn 1.6.1 and are loaded under 1.7.2; the version warning is silenced on purpose, as upstream did (pipeline.py:101-115, README.md:72-75).

3.2 Reading the measurements

Plain-language explanation and maths: atlas page.

  • One file or a flat folder. A file is read by extension: .csv with read_csv, .xlsx with read_excel, .ods with read_excel(engine="odf") (pipeline.py:22,118-129). A folder is not walked recursively: its files with one of the three extensions, case ignored, are sorted and concatenated row-wise (:132-159). Legacy read only a folder, globbing lower- and upper-case extensions and deduplicating with set(), so the row order changed between runs (legacy SurgMovPred_CLI/SurgMovPred_CLI.py:151-157).
  • Patient identifier. find_id_column tries eight patterns in order (#, id, id patient, patient id, patient number, subject id, patient, subject, case-insensitive), then any column whose name contains both "patient" and "id" (pipeline.py:65-98). Without one, IDPatient is left empty with a warning (:303-312).
  • Column names are cleaned to the training-time form by clean_name: strip, drop quotes, backslashes and brackets, every run of characters other than letters, digits, underscore and apostrophe becomes one underscore, total becomes Total, a leading digit gets f_ (pipeline.py:27-50). A name that cannot be cleaned raises ValueError (:51-60); legacy returned 'f_unnamed', so two such columns shadowed each other (legacy SurgMovPred_CLI.py:63-66).

3.3 One target per package

Plain-language explanation and maths: atlas page.

The only tolerance is the missing _T0 suffix; any other missing column removes that target from the output with a warning (pipeline.py:224-236). An exception while predicting one target is logged and the loop goes on (:249-250). A blank cell is not filled in: it leaves the scaler as NaN and the model raises on it, so that target is dropped for every row (the packages hold an ElasticNetCV; a stand-in stack on a current scikit-learn raised ValueError: Input X contains NaN; the shipped packages were not run). If no target at all was predicted the run raises RuntimeError instead of writing tables without predictions (:252-264). Legacy wrote those tables.

3.4 Outputs

Plain-language explanation and maths: atlas page.

The predictions become one DataFrame, IDPatient is inserted as first column, and the table is written twice (pipeline.py:266,314-317,276-287):

output_dir/predictions_outputs.xlsx     df.to_excel(..., index=True)
output_dir/predictions_outputs.csv      df.to_csv(..., index=True)
columns:  <unnamed index 0..n-1>, IDPatient, <one column per predicted target>

run() returns {"excel": ..., "csv": ...}, a dict[str, Path], so the server hands both back as a set of files (VISOR-serve server/registry/schema_tool.py:99-103). The order of the target columns follows the sorted package paths, the same on every run. There is no JSON report.

The output is a dictionary with two files, predictions_outputs.xlsx and predictions_outputs.csv (pipeline.py:276-287), so the server hands them back as a set of files (VISOR-serve server/registry/schema_tool.py:100-103). Each has an IDPatient column and one column per predicted target, preceded by an unnamed index column (to_excel(index=True), pipeline.py:283-284; the same at :268-269 in the legacy CLI). The models are looked for under DATA/Surg_Mov_Pred/models (__init__.py:19). No resource, timeout or batch setting is declared for this tool, so the server defaults apply: no timeout (VISOR-serve server/config.py:77). A comment in the server's admission code records a timing of this tool: 4.60 s with one thread, 4.45 s with eight, 7.80 s with 56, on a machine with 28 physical cores, so it gets slower above eight threads (VISOR-serve server/execution/admission.py:406-421). The same comment gives this as the reason the server caps the threads it grants (:433-434).

8. Findings in VISOR

Plain-language explanation and maths: atlas page.

Unnamed index column in both tables

Both result files start with a column holding 0, 1, 2 and so on, before IDPatient (pipeline.py:283-284). The legacy CLI does the same (legacy SurgMovPred_CLI/SurgMovPred_CLI.py:268-269). Account for it when reading column positions.

Stale comments in the client

The client says output_kind "is file" (Remote SurgMovPredRemote/SurgMovPredRemote.py:44) and the base widget gives "SurgMovPred's single predictions_outputs.xlsx" as its example (Remote ServerToolsCore/ServerToolsCoreLib/base_widget.py:1390-1391). The tool returns two files, which the schema code publishes as a set of files (VISOR-serve server/registry/schema_tool.py:100-103). The panel still handles them, since it unpacks any zip it receives.

Stale data path in the README

The tool README gives the model folder as /DATA/SurgMovPred/models (README.md:45), while the code looks under Surg_Mov_Pred (__init__.py:19,34), the name the data manifest also uses (VISOR-serve scripts/data-manifest.yml:91). The code is the reference.

Still true from legacy: independent targets, nothing applied to the scene

Every target is a separate model.predict on the same row (pipeline.py:216-247), so the predicted displacements of points of one rigid segment are not constrained to agree with each other (legacy page, pitfalls). The output is the two tables only: no transform, no Slicer node, and the panel saves the archive rather than loading anything (RESULT_KIND = "save_as", Remote SurgMovPredRemote.py:46). Read in the code.

A skipped target is visible only in the server log

A package whose features are missing from the table is skipped with a logger.warning, and a target that fails to predict with logger.exception (pipeline.py:234-236,249-250). The run then succeeds with fewer columns. There is no report file, so the user sees the missing targets only by counting columns. The one guard is the all-or-nothing case (:252-264). Read in the code.

Verified: reproducible order and no silent empty result

Packages and tables are sorted, so two runs on the same input give the same rows and columns in the same order (pipeline.py:143-147,173); a run where no model predicts is an error, not two empty tables (:252-264); a bad column name is an error, not a shadowed feature (:51-60). Read in the code.
