SurgMovPred on VISOR

SurgMovPred predicts the post-operative movement of 28 landmark points from a table of measurements and a surgical plan. This page explains how, step by step, with the maths: what goes in, what each step does to it, and what comes out. The files, lines, arguments and findings are on the code page. The legacy Slicer module is on its own page.

Code (developers) VISOR 112 regressors CPU only Legacy page Guide (VISOR)

The file names, line numbers and every finding are on the code page. Repositories named here: the SADT-VISOR tool catalogue at 6ba2a78, VISOR-serve at e9a7e5d, the Slicer client AutomatedDentalToolsRemote at 19b95e8 and the legacy module SlicerAutomatedDentalTools at 3c67957. Everything was read in the code; nothing was run for this page.

Overview: what goes in, what comes out

SurgMovPred predicts how far the bones will be moved in an orthognathic operation. It reads a table with one row per patient (cephalometric measurements before the operation, plus the planned movement) and returns a table of predicted post-operative movements: 28 landmark points, each with four values. It does not read any scan or mesh, and it changes nothing in Slicer.

SurgMovPred on VISOR
Inputone CSV, XLSX or ODS table of measurements and plan, or a flat folder of such tables
Method112 trained models, one per target; each re-scales its 145 inputs and predicts with a stack of three regressors
Outputtwo tables with the same content, predictions_outputs.xlsx and .csv: patient identifier, then one column per predicted target
Whereon the server, on the processor only; the Slicer panel uploads the table and saves the two results

The algorithm is the legacy one, unchanged. What changed is the ordering, the error handling and the environment (What changed).

1. Position in the chain

SurgMovPred is a leaf: it calls no other tool and no other tool calls it, as in the legacy module. The Slicer panel is a thin client generated from the server’s description of the tool. The tool was packaged under the name Surg_Mov_Pred, and the server also accepts the old spelling. It is covered by automated tests in its repository, and its README reports that its output matched the previous server implementation on 101 patients and 112 models (read, not re-run for this page).

In the codeAPI name, tool folder, server declaration, provenance and test counts

1.1 What runs where

The server does everything: reading the table, cleaning the column names, running the 112 models on the processor and writing the two tables. The panel has one field, the measurements, uploads the table (a folder is zipped on the way out), then saves the returned archive next to the file you chose. Nothing is loaded into the Slicer scene.

2. Files involved

The tool is two small Python files (a run function and the pipeline), a layout file that hides the model argument and renames the field, the environment definition and the tests. The legacy module was a 878-line panel plus a 323-line command-line script.

In the codeThe file table with line counts

3. The pipeline

Once per run the tool loads all model files and reads the table. Then, for each of the 112 targets in turn, it finds the columns that model needs, scales them, predicts and keeps the result. At the end it assembles one table. Click a box to read its section.

In the codeThe function behind each box of the diagram

3.1 Loading the model packages

Each target has its own folder with one file, a package holding four things: the target’s name, the ordered list of the 145 input columns it expects, its fitted scaler and its fitted model. The tool loads every package found under the models folder, in sorted order, so the columns of the result come out in the same order on every run. A package that cannot be read is logged and skipped, and if none loads the run stops. All 112 packages expect the same 145 columns; 28 of them end in _T0 (the state before the operation) and 25 in _Total (the planned total movement), which is why the table must hold the plan as well as the measurements.

In the codeThe load loop, the package keys, the LightGBM requirement and the silenced version warning

3.2 Reading the measurements

A file is read according to its extension (CSV, XLSX, ODS); a folder is not searched recursively, and its tables are sorted and stacked one under the other. The patient identifier column is found by trying a list of usual names (#, id, patient id, and so on); without one, the identifier column of the output is left empty with a warning. Column names are cleaned to the spelling used when the models were trained: quotes and brackets are removed, anything that is not a letter, a digit, an underscore or an apostrophe becomes an underscore, and a name starting with a digit gets a prefix. A name that cannot be cleaned is an error.

In the codeThe reading code, the eight identifier patterns and the cleaning rules with lines

3.3 One target per package

For each package the tool looks for each required column in the table. The only tolerance is a missing _T0 suffix: a model that asks for X_T0 accepts a column named X. Any other missing column removes that target from the output, with a warning. A blank cell is not filled in: the model refuses it, the error is logged, and that target is left out for every patient. The columns are put in the order the model expects, scaled, and given to the model.

A failure while predicting one target is logged and the loop goes on. Only when no target at all was predicted does the run stop with an error, rather than write tables with no predictions.

In the codeThe loop with the feature resolution, the skip rules and the error cases

3.4 Outputs

The predictions become one table with the patient identifier as the first data column, written twice, as Excel and as CSV. Both start with an unnamed column numbering the rows, which matters when reading column positions. Both files are handed back to the client, and there is no report file.

In the codeThe two files, the column layout and the return value

4. What you can choose

  • The measurements: a single table, or a flat folder of tables. This is the only field shown in the panel.
  • Not offered: the models (the server’s own set is used), the output folder (set by the server) and any option on targets or thresholds. All 112 targets are always attempted.

6. Environment

The tool has its own Python environment on the server (Python 3.12 with pinned versions of numpy, pandas, scikit-learn, LightGBM and the spreadsheet readers) and no graphics-card software at all. The models are staged on the server as one archive of about 740 MB (706 MiB). Nothing is installed at run time.

In the codeThe pinned versions with lines, the models archive and the timing comment

7. What changed from the legacy logic

  • The tool runs on the server in its own environment, instead of inside Slicer’s Python with a package install at every Apply.
  • The input can be a file or a flat folder; the legacy took a folder only, and its folder reading had no stable order.
  • Models and tables are read in sorted order, so two runs give the same rows and columns in the same order.
  • A column name that cannot be cleaned is an error, instead of a shared placeholder name that made two columns collide.
  • A run where no model predicts is an error instead of two tables with no predictions.
  • Both output files are returned, and ODS files can be read because the reader is installed.

8. Known issues

  • Both result files start with an unnamed index column; see the finding.
  • Some comments in the client describe a single output file; see the finding.
  • The tool README gives a stale data folder name; see the finding.
  • Targets are predicted independently, so the movements of the points of one bone segment need not agree, and nothing is applied to the scene; see the finding.
  • A skipped target is visible only in the server log; see the finding.
  • On the positive side, the order is reproducible and an empty result is no longer silent; see the check.
