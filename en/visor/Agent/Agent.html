Agent on VISOR

Agent reads a sentence such as “segment the skull of these scans” and proposes which of the other tools to run, with which settings. A language model served by Ollama makes the choice, ordinary code checks every answer, and nothing runs unless asked. In VISOR there are two unrelated things called Agent: a new tool on the server, and AgentRemote, a copy of the legacy Slicer panel that still runs everything on the workstation. This page explains both, step by step. The details a developer needs are on the code page; the legacy module is on its own page.

The client README says it plainly: Medical Data Anonymizer, VISU and Agent “run on this machine and send nothing”. The panel’s help text still says the agent is “powered locally by the qwen3:8b model through Ollama”.

Ollama is a prerequisite nobody deploys. The server tool needs an Ollama endpoint: the one given as an argument, else the one named by the OLLAMA_HOST variable, else the machine’s own Ollama port. It never installs, starts or pulls a model, and nothing in VISOR-serve mentions Ollama, so the image does not carry one. Without a reachable endpoint the tool stops with a “service unavailable” answer. Evidence.

2. Files involved

The server tool is a small Python package of about a dozen short files, each with one job: reading the catalogue, ranking it, talking to the model, routing, writing the prompts, validating values, running the chosen tool, parsing the history, and describing the panel. It has no dependency outside the standard library. The client copy is the legacy widget plus its command-line module and a manifest.

In the codeFile list with line counts, for the server tool, the legacy module and the client copy

3. The server tool’s pipeline

Five computed steps prepare the question, one or two model calls answer it, and code checks every answer before it is used.

3.1 The catalogue

The legacy agent carried its own hand-written list of tools and arguments, which drifted away from the tools. The server tool takes the catalogue as an input: a saved JSON copy of what the server publishes if one is given, otherwise the server’s own live list, read without a token; with neither, it stops. The list is then checked: it must not be empty, two names must not be the same once case and separators are ignored, and every argument type must be a known one. For each argument the tool keeps its type, whether it is required, its description, its choices and its default. The arguments the model may fill are those that are neither the output folder nor hidden.

In the codeWhere the catalogue is read, what is refused, and what is kept for each argument

3.2 Choosing the candidates

The synonym table used by the ranking holds vocabulary, not tool names. The legacy ranking was a neural cross-encoder; when it failed it silently returned the first three tools of the file, whereas the server ranking stops with an error instead of guessing.

In the codeThe BM25 code, the field weights, the synonym table and the all-tools fallback

3.3 The first model call: which tool?

The model is shown the request and the candidates, each written out in full (the legacy cut descriptions at 140 characters). It must answer with one JSON object: a tool name, a confidence and a one-sentence reason, or no tool with a confidence of 0.2 or less when nothing fits. Reasoning blocks and code fences around the answer are stripped before it is read. Then the name is checked against the candidates:

  • no tool, or the word “null”: nothing is chosen;
  • a name found among the candidates, exactly or after normalising case and separators: chosen;
  • anything else: no tool, confidence capped at 0.2, and the invented name is recorded with a warning.
In the codeThe request sent to Ollama, the router prompt, the JSON extraction and the name check

3.4 The second model call: which values?

The second call asks for the values of the chosen tool’s fillable arguments, with their types, choices and defaults, and the folders the user gave. The prompt forbids inventing a value or a path. Defaults are not copied into the proposal, and required arguments still without a value are listed as missing, never guessed.

In the codeThe extraction prompt, the validation rules and the coercion of booleans, numbers and lists

3.5 What is launched

When all conditions hold, the chosen tool runs as an ordinary supervised call in its own environment, with named arguments, and its outputs land in a run/ folder inside Agent’s own output. What it returned is recorded in the decision file. If the tool is called outside a server, with no supervisor, asking to execute is an error. A model that picked Agent itself would be stopped by the supervisor’s cycle check, at run time.

In the codeThe gate in code, the supervised call, and the cycle refusal

3.6 Ask mode

In Ask mode, one model call with an advisor prompt and the candidate list, not constrained to JSON, produces a Markdown answer written to advice.md. Nothing is proposed or run, whatever execute says. Any other mode value is treated as Agent mode; the server validates the two allowed names before the tool is called.

In the codeThe advisor call, the mode test and the order of the checks

6. Environment

  • Python 3.11, with no dependency outside the standard library; the connection to Ollama uses plain HTTP.
  • An Ollama server with qwen3:8b (or the chosen tag) already pulled. It is not in the image and not in VISOR-serve.
  • No hosted data, no declared resources, 300 seconds allowed per model call.

The legacy module downloaded and started an Ollama binary itself and pulled the model on demand (the language model); the server tool does neither. The client copy still depends on a local Ollama and on the cross-encoder in Slicer’s Python.

8. Known problems

  • A server tool with no client, a client with no server tool. No panel can reach the server tool, and the client panel never contacts the server. Evidence.
  • Execution is off by default, with three refusals. This is a protection, not a problem. Evidence.
  • No check at startup that the called tool exists. The names come from the registry, and Agent itself is not excluded; a self-call would be refused at run time. Evidence.
  • Paths are still the model’s word. Nothing checks that a proposed path exists or is the right kind; the executed tool reports a wrong path. Evidence.
  • The client copy keeps the legacy defects: silent cross-encoder fallback, Slicer frozen during the job, module scripts that are no longer shipped. Evidence.
  • The client copy’s manifest is out of date: it lists MedX, which no longer exists, and cannot name MRI2CBCT. Evidence.
