Agent on VISOR: the code

For developers: what the VISOR server tool Agent and the client copy AgentRemote do in the code, with file:line references, signatures, arguments, environment, the differences from the legacy code and the findings. The readable explanation of the same pipeline, with the maths, is on the atlas page.

VISOR: partial Code Atlas (explanation) Legacy page Guide (VISOR)

State at the reference commits: SADT-VISOR 6ba2a78, VISOR-serve e9a7e5d, AutomatedDentalToolsRemote 19b95e8 (Remote); legacy is SlicerAutomatedDentalTools at 3c67957. A bare file name such as llm.py or routing.py is in SADT-VISOR tools/Agent/src/sadt_agent/; AgentRemote.py is in Remote AgentRemote/. Everything was read in the code: no Ollama was available, so nothing was run.

The client README says it plainly: Medical Data Anonymizer, VISU and Agent "run on this machine and send nothing" (AutomatedDentalToolsRemote README.md:28-30). The panel's help text still says the agent is "powered locally by the qwen3:8b model through Ollama" (AgentRemote.py:107).

Ollama is a prerequisite nobody deploys

The server tool needs an Ollama endpoint: the endpoint argument, else the OLLAMA_HOST variable, else the loopback address on Ollama's port 11434 (SADT-VISOR tools/Agent/src/sadt_agent/llm.py:38-39,51-59). It never installs, starts or pulls a model (llm.py:1-23), and a search of VISOR-serve for "ollama" finds nothing, so the image does not carry one. Without a reachable endpoint the tool raises ToolUnavailableError (llm.py:86-91), which the server answers with a 503 (VISOR-serve server/main.py:133-138).

3. The server tool's pipeline

Plain-language explanation and maths: atlas page.

3.1 The catalogue, read from GET /tools

Plain-language explanation and maths: atlas page.

The legacy agent carried its own hand-written manifest of tools and parameters, which drifted from the tools. The server tool takes the catalogue as an input (catalog.py:1-23,52-83):

  1. catalog_file, a JSON file holding what GET /tools returns, if given;
  2. otherwise <SADT_API>/tools, read with urllib and no token (catalog.py:86-100). SADT_API is the server's own address as seen from a tool (VISOR-serve server/config.py:75, server/execution/dispatch.py:575);
  3. neither: a CatalogError naming both, a 422.

normalise accepts a list or {"tools": [...]} and refuses anything else, an empty catalogue, two names that are the same once case and separators are ignored, an argument type outside path, str, int, float, bool and their lists, and non-list choices (catalog.py:103-223). For each argument it keeps type, required flag, description, choices, default and the presentation keys hidden, label, section. The arguments the model may fill are those that are neither output_dir nor hidden (fillable_arguments, catalog.py:250-262). Nothing in catalog.py removes Agent itself from the catalogue.

3.2 Choosing the candidates

Plain-language explanation and maths: atlas page.

Each tool becomes a bag of words from its name (weight 4), its description (3) and its arguments' names and descriptions (1), with a synonym table of vocabulary, not of tools (ranking.py:32-110,148-169). The request is scored with BM25:

idf  = log(1 + (N - df + 0.5) / (df + 0.5))
norm = K1 * (1 - B + B * len(doc) / avg_len)          # K1 = 1.2, B = 0.4
score += weight * idf * tf * (K1 + 1) / (tf + norm)   # ranking.py:183-219

In that sum tf is the document's weighted count of the term: each occurrence adds 4, 3 or 1 according to the field (ranking.py:156-168), and len(doc) is the sum of those weights (:194). weight is the weight of the request term: 1.0 for a word typed, 0.55 (SYNONYM_DISCOUNT, :43,171-180) for a word added from its synonym class (:207,215).

select_candidates keeps the top candidates (8 by default), but returns the whole catalogue when candidates is 0, covers the catalogue, or when no tool scores above zero (ranking.py:222-239). Whether it narrowed is recorded as candidates_narrowed in the report. The legacy cross-encoder, on failure, returned the first three tools in file order (legacy Agent_CLI/Agent_CLI_utils/utils.py:94).

3.3 Router call

Plain-language explanation and maths: atlas page.

One /api/chat POST with stream: false, keep_alive: "30m", format: "json" and options {temperature, seed} (llm.py:45,62-103). The system prompt asks for one JSON object {"tool", "confidence", "reason"}, a tool chosen only from the CANDIDATES list, and null with confidence 0.2 or less when nothing fits (prompts.py:15-30). The candidates are written out in full, without the legacy 140-character truncation (prompts.py:1-8,67-103). parse_json_object strips <think> blocks and code fences, then takes the first balanced object (llm.py:131-181). choose_tool then checks the name (routing.py:22-55):

  • null, "null" or "None": no tool;
  • a name found among the candidates, exactly or after normalisation (catalog.find_tool, catalog.py:236-247): chosen;
  • anything else: no tool, confidence capped at 0.2, and the name recorded as rejected_tool_name with a warning (__init__.py:197-222).

3.4 Extraction call and validation

Plain-language explanation and maths: atlas page.

A second call asks for {"extracted": {...}, "confidence", "notes"}, with the fillable arguments of the chosen tool, their types, choices and defaults, and the folders (routing.py:58-84, prompts.py:32-48,105-140). The prompt forbids inventing a value or a path. validation.validate then (validation.py:39-77):

  • drops any name the tool does not take, and says so;
  • treats null as "not stated";
  • coerces booleans from true/yes/y/1/on and their opposites, integers and floats, lists, and checks choices (validation.py:80-209); a failure is an error in the decision and the value is dropped.

Any error multiplies the extraction confidence by 0.6, as in legacy (routing.py:78-83). Defaults are not copied into the proposal, and required arguments still absent are listed in missing_required (catalog.py:265-271, __init__.py:224-232).

3.5 What is launched

Plain-language explanation and maths: atlas page.

allowed, reason = routing.can_execute(decision)     # __init__.py:234
if not execute:          -> executed: false, proposal only
elif not allowed:        -> executed: false, execution_refused: reason
else:
    parameters = dict(values); parameters["output_dir"] = output_dir / "run"
    produced = supervisor.run(tool_name, **parameters)          # execution.py:58-70

can_execute refuses when no tool was chosen, when missing_required is not empty, and when the router's confidence is below EXECUTE_MIN_CONFIDENCE = 0.5 (routing.py:19,104-125). The chosen tool then runs as an ordinary supervised call in its own venv, with named arguments, its outputs under run/ inside the Agent's output folder; what it returned is recorded under execution in routing.json (__init__.py:245-252, execution.py:75-85). Without a supervisor (the tool called outside a server), execute raises SupervisorRequired (execution.py:51-56). The supervisor refuses a cycle by name, so a model that picks Agent itself would end in "Supervised call cycle" (VISOR-serve server/execution/runner.py:1814-1817). Read in the code.

3.6 Ask mode

Plain-language explanation and maths: atlas page.

With mode = "Ask (Interactive)", one call with the advisor prompt and the candidate list, not in JSON format, and the Markdown answer is written to advice.md (__init__.py:161-188, routing.py:87-101, prompts.py:50-63). Nothing is proposed or run, whatever execute says. Any other mode value is treated as Agent mode (__init__.py:161-167); the server validates the Literal before run() is called.

4. Arguments and schema

Signature of the server tool, SADT-VISOR tools/Agent/src/sadt_agent/__init__.py:35-51. sup is injected by the runner and never sent by a client; output_dir is removed from the published schema and filled by the server with the job's output/ (VISOR-serve server/registry/conventions.py:36). The tool's layout file hides history, endpoint, temperature, seed and timeout_seconds, and shows execute only in Agent mode (layout.py:19-50). Output: the output folder holds routing.json, Agent_report.json, advice.md in Ask mode, and run/ with the chosen tool's own outputs when it was executed (__init__.py:25-27, execution.py:41). The return type is a path, so the server hands it back as a zip.

8. Findings in VISOR

Plain-language explanation and maths: atlas page.

A server tool with no client, a client with no server tool

The server tool is not reachable from any panel, and the client panel never contacts the server. Nothing in AutomatedDentalToolsRemote builds a request for Agent, and AgentRemote.py does not import ServerToolsCoreLib. The two share a name and a model tag, nothing else.

Execution is off by default, with three refusals

execute defaults to false (__init__.py:43). When it is true, the run is still refused if no tool was chosen, if a required argument is missing, or if the confidence is below 0.5 (routing.py:104-125). The source comment calls that threshold a floor against a model admitting it is guessing, not a quality bar (routing.py:16-19).

No check at startup that the called tool exists

The call is written supervisor.run(...) instead of sup.run(...) on purpose, so that the schema generator does not record a fixed dependency (execution.py:9-29,68-70). The names that reach it come from the catalogue, so a name is only as good as the registry it was read from. The catalogue does not exclude Agent; a self-call would be refused by the supervisor's cycle check (VISOR-serve server/execution/runner.py:1814-1817), at run time.

Paths are still the model's word

The only paths the model sees are folders, and it is told to use them verbatim (prompts.py:32-48), but nothing checks that a proposed path exists or is the right kind: the schema says path without saying file or folder, and the legacy extension check was dropped on purpose (validation.py:9-17). The executed tool is what reports a wrong path. On a server, those paths are also server paths, not the user's. Read in the code.

The client copy keeps the legacy defects

AgentRemote and Agent_CLIRemote are the legacy design, so the legacy findings (legacy pitfalls) still apply to them: the cross-encoder still falls back to the first k tools (Remote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:94); the job still runs synchronously on Slicer's thread (AgentRemote.py:767); module paths are still resolved through AGENT_CLI_TOOLS_DIR (utils.py:150-156), while the CLI modules the manifest names were deleted from the extension (Remote CMakeLists.txt:49-56). Read in the code, not run in Slicer.

The client copy's manifest is out of date

Agent_CLIRemote/manifest.yaml lists medx_dashboard and medx_summarize (lines 491 and 509) although MedX no longer exists in either repository (see MedX), and it cannot name MRI2CBCT, which is not built.
