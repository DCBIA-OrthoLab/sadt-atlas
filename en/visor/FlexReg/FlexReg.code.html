FlexReg on VISOR: the code

For developers: what the VISOR port of FlexReg does in the code, with file:line references, signatures, arguments, environment, the differences from the legacy code and the findings. The readable explanation of the same pipeline, with the maths, is on the atlas page. The legacy module has its own code page.

VISOR Code Atlas (explanation) Legacy page Guide (VISOR)

VISOR splits FlexReg in two. The server builds the palatal patch and registers one arch onto another; the Slicer panel only previews the outline of the patch while you move its corners. This page follows the port from the request to the files that come back: who calls it, which files carry it, each step of the server pipeline with the code that does it, the published arguments, the environment, what changed from the legacy module, and what the code review found. Everything here was read in the code at the commits below, not observed on a running server (no FlexReg environment was available to run the tests), and nothing here says that a given server is deployed.

References name the repository first: SADT-VISOR (tool code, tool/vface @ 6ba2a78), VISOR-serve (server, @ e9a7e5d), AutomatedDentalToolsRemote (Slicer client, @ 19b95e8) and legacy (SlicerAutomatedDentalTools @ 3c67957). A bare file name such as __init__.py, pipeline.py, layout.py, make_butterfly.py, orientation.py, propagation.py, ICP.py, vtkSegTeeth.py or util.py is in the SADT-VISOR package tools/FlexReg/src/sadt_flexreg/; FlexRegRemote.py and FlexRegLib/ are in the client folder FlexRegRemote/. In the column "Legacy", FlexReg_CLI.py and FlexReg.py are the legacy CLI and widget, and the other names are under FlexReg_CLI/FlexReg_Method/ or FlexReg/FlexReg_utils/. Server paths such as server/config.py are in VISOR-serve.

1. Position in the chain

Plain-language explanation and maths: atlas page.

FlexReg calls no other tool and no tool calls it. run() takes no supervisor argument (SADT-VISOR __init__.py:49-78), and the server hands a supervisor only to a tool that declares *, sup (VISOR-serve server/execution/runner.py:6-9). The consequence is the main difference with the legacy chain: the legacy widget ran dentalmodelseg when the arch had no tooth labels, and ALI_IOS for the lower arch. In VISOR the arch must arrive already labelled (a per-point Universal_ID array), for example from a Crown_Seg run, and nothing computes the mucogingival patch any more.

3. What runs where

Plain-language explanation and maths: atlas page.

ServerClient (Slicer)
Reading the surfaces (RAS), building the palatal patch (orientation, four tooth centroids, outline, geodesic fill), merging patch arrays, rigid ICP on the patch, writing the registered surface, the .tfm and the report (SADT-VISOR __init__.py:49-202)The patch preview: while a joystick is dragged, the outline of the patch is recomputed in Slicer and drawn in the scene, with no round trip (FlexRegRemote.py:156-193)
The only GPU step: the geodesic fill of the patch (propagation.py:31, 60, 66-68)The form, generated from the server's schema: vec2 arguments become joysticks (FlexRegRemote.py:21-24, 71)
The real patch, which the registration actually uses, computed once at ApplyThe preview library FlexRegLib, which needs vtk and numpy and no GPU (FlexRegRemote/CMakeLists.txt:6-23)

The preview draws the outline only (with_fill=False, FlexRegRemote.py:182-187): filling the patch is done by the server, by geodesic propagation from the middle point. The client library can also fill approximately with a point-in-polygon test, which it does not do in the panel (FlexRegLib/butterfly_preview.py:285-306). The preview is on by default ("Preview the patch while I drag", FlexRegRemote.py:105-114) and works only when the surfaces field points at a surface already in the Slicer scene: with a folder (batch), there is no preview (FlexRegRemote.py:220-231). The orientation and the centroids are cached per surface and per tooth set (prepare), and only the outline is recomputed on each pad move (FlexRegRemote.py:166-187). The contour node is kept out of the saved scene (SetSaveWithScene(False), FlexRegRemote.py:244).

The preview replays the server's outline with the same constants: the orientation target and teeth (FlexRegLib/butterfly_preview.py:28-29), the radius 0.7 (:30), the sign flip of the posterior adjustment (:35-40) and the mirrored Béziers (:54-66), against make_butterfly.py:77, 82-83, 110-111, 136-148 on the server. The four hidden tooth numbers still exist as widgets in the client (hidden rows are built, not rendered: ServerToolsCoreLib/formgen.py:2272-2278, 2366-2420), so the preview reads their defaults; being hidden, they are not sent, and the server applies the same defaults.

4. The pipeline, step by step

Plain-language explanation and maths: atlas page.

One call of run() handles one surface or a folder of them. The steps below are those of SADT-VISOR __init__.py:108-202, in order.

4.1 Checks before reading computed

Plain-language explanation and maths: atlas page.

The mode decides two flags: registering for Register and Patch and register, and the array to register on, Butterfly for the palate or Bottom_MGL for the mucogingival line (__init__.py:111-112; names at pipeline.py:26-27). A registration without a reference is refused before any file is read, and the reference is read once for the whole batch (__init__.py:117-121):

if registering and not str(reference):
    raise ToolInputError(
        "'{}' registers onto a reference surface: name one in 'reference'.".format(mode)
    )
target = read_surface(str(reference)) if registering else None

surfaces_in takes a file as is, or walks a folder recursively and keeps .vtk, .vtp, .stl, sorted so that two runs on the same folder name their outputs the same way (pipeline.py:98-120). A missing path or a folder with no surface is an input error.

4.2 Reading, and the coordinate flip computed

Plain-language explanation and maths: atlas page.

read_surface picks the reader by extension (vtkXMLPolyDataReader, vtkSTLReader, vtkPolyDataReader), refuses any other extension and an empty mesh by name, then scales by (-1, -1, 1) (pipeline.py:50-78). That flip turns the LPS file into the RAS frame the geometric core was written in; it is its own inverse, so the same function flips back on write (pipeline.py:34-47, 93). All the computation below happens in RAS.

4.3 The palatal patch ("butterfly") computed

Plain-language explanation and maths: atlas page.

Built only when the mode contains Patch and the patch is the palate (__init__.py:155-158), by build_butterfly, which calls the legacy butterflyPatch with index 1 and turns a missing tooth into an input error that names it (pipeline.py:123-162). Inside make_butterfly.py, purely geometric apart from the fill:

  1. Orientation. The surface is copied and oriented so that the centroids of teeth 3, 5, 12, 14 (UR6, UR4, UL4, UL6) land on [[-0.5,-0.5,0],[0,0,0],[0.5,-0.5,0]] (make_butterfly.py:82-83; orientation.py:42-115): occlusal plane near z = 0, +y anterior. These four teeth are fixed, whatever teeth drive the corners.
  2. Centroids. vtkMeanTeeth averages the vertices of the four chosen teeth in Universal_ID (make_butterfly.py:79, 84). The whole-patch shift and each corner's adjustment are added; the adjustment is negated on the posterior corners so that a positive value lengthens the patch at both ends (make_butterfly.py:106-111).
  3. Corners. Each corner is an affine combination of its own centroid and the opposite one (make_butterfly.py:94-97, 113-117): 
    ratio_anterior_right = (1 - ratio_anterior_right)/2
...
landmark_anterior_right = (1 - ratio_anterior_right) * c_ar + ratio_anterior_right * c_al
    ratio 1 puts the corner on its tooth, ratio 0 halfway across the arch. Because the weights sum to 1, the shift added to all four centroids comes out of the interpolation unchanged: the patch moves rigidly.
  4. Outline. An anterior and a posterior segment (step 0.01) and two quadratic Béziers through (posterior corner, posterior midpoint, anterior corner), reflected across their chord so they bulge outward (make_butterfly.py:123-151).
  5. Marking. Every vertex closer than radius = 0.7 to the outline, measured on V[:, :2] (the projection on the occlusal plane), is set to 1 (make_butterfly.py:77, 127-157).
  6. Fill. Dilation floods the mesh neighbour by neighbour from the vertex nearest the middle of the four corners, stopping at the marked outline, in batches of 1000 on CUDA (make_butterfly.py:159-161; propagation.py:65-98). The array Butterfly1 is added to the original surface, not to the oriented copy (make_butterfly.py:165-170).

4.4 Merging patch arrays computed

Plain-language explanation and maths: atlas page.

merge_patches ORs Butterfly1, Butterfly2, ... into one Butterfly array (int32) in numpy, and does nothing when there is no Butterfly1 (pipeline.py:165-188). It runs only right after a patch was built in this run (__init__.py:157). A mesh that already carries several numbered patches from the legacy module registers on their union only if a patch is built again here.

4.5 Registration on the patch computed

Plain-language explanation and maths: atlas page.

register refuses a moving surface without the patch array, then runs the legacy ICP restricted to the patch (pipeline.py:203-210):

if not source.GetPointData().HasArray(patch_array):
    raise ToolInputError(...)
option = vtkMeshTeeth(list_teeth=[1], property=patch_array)
result = ICP([vtkICP()], option=option).run(source, target)

vtkMeshTeeth keeps, in both meshes, only the points whose array equals 1, as a point cloud (ICP.py:70-72). vtkICP is a plain vtkIterativeClosestPointTransform (ICP.py:94-113):

icp.GetLandmarkTransform().SetModeToRigidBody()
icp.SetMaximumNumberOfIterations(1000)
icp.StartByMatchingCentroidsOn()

The resulting 4×4 matrix (RAS) is then applied to the whole moving mesh, teeth included (pipeline.py:211-224). The surfaces are the moving meshes, the reference the fixed one. See ICP in the glossary.

4.6 Transform and writing computed

Plain-language explanation and maths: atlas page.

The .tfm converts the RAS matrix to LPS by conjugation and inverts it, because a Slicer transform maps the space rather than the points (pipeline.py:227-246):

flip = np.diag([-1, -1, 1, 1])
composed = np.linalg.inv(flip @ matrix @ flip)
transform = sitk.AffineTransform(3)
transform.SetMatrix(composed[:3, :3].flatten())
transform.SetTranslation(composed[:3, 3])

The surface is flipped back to its input convention and written with vtkPolyDataWriter in binary, whatever the input extension (pipeline.py:81-95). The output path mirrors the input tree under output_dir: <relative path without extension><suffix><input extension>, and the transform <same stem><suffix>.tfm (__init__.py:150, 160-171). The input is never modified. A surface that raises an input error is recorded as failed and the loop goes on (__init__.py:177-181).

4.7 The report computed

Plain-language explanation and maths: atlas page.

FlexReg_report.json, at the root of output_dir (__init__.py:139, 168-199):

{"mode": ..., "patch": ...,
 "surfaces": {"<relative path>": {"patch": "Butterfly", "registered_on": "Butterfly",
                                   "transform": "<path>", "status": "ok", "output": "<path>"}
              | {"status": "failed", "error": "..."}},
 "summary": {"total": n, "processed": k, "failed": m}}

It is written before the final refusal "None of the N surface(s) could be processed", so a run where nothing worked still leaves its reasons (__init__.py:188-200). Progress is reported as "surface i of n", never with a file name (__init__.py:144-146).

9. Findings in VISOR

Plain-language explanation and maths: atlas page.

"Patch and register" patches only the moving surface, not the reference

The patch is built on surfaces only (SADT-VISOR __init__.py:155-157); the reference is read once and used as is (__init__.py:121). The ICP selects the points of the patch array in both meshes (ICP.py:70-72; pipeline.py:209-210). A reference without the Butterfly array fails with NoSegmentationSurf (vtkSegTeeth.py:59-61), and an all-zero array with ToothNoExist (vtkSegTeeth.py:75); neither is an input error, which matters for a batch: see the next finding. In practice, the reference must already carry its patch, for example from an earlier run in Patch mode on it. The docstring of reference does not say so (__init__.py:89-90), where the legacy widget did ("Create the patch on T1 and T2 before registration", legacy FlexReg.py:1116-1118).

Only input errors are reported per surface; other exceptions stop the whole batch

The loop catches ToolInputError only (SADT-VISOR __init__.py:177), and the report is written after the loop (__init__.py:191). Any other exception, such as the two raised by a reference without its patch, a tooth number outside 1 to 32 (util.py:143-151) or a missing GPU in Dilation (propagation.py:31), ends the run for every remaining surface and leaves no report. This is read from the code; it was not run.

"Mucogingival line" cannot be produced by anything in VISOR

The array Bottom_MGL (SADT-VISOR pipeline.py:27) is created by no file of the tool nor of the Slicer client; the legacy built it in the widget (legacy FlexReg_utils/mgl_patch.py:117). The panel still offers the choice (__init__.py:53; layout.py:95). Register with it fails per surface if the mesh lacks the array (pipeline.py:203-207). And Patch mode with the mucogingival line builds nothing: the construction is guarded by patch == "Palate (butterfly)" (__init__.py:155-157), so the surface is copied and reported as ok.

Without Universal_ID, the last array is used

When a mesh has no Universal_ID array, the tooth-label lookup falls back to GetLabelSurface, whose loop uses continue where break is needed and returns the last point-data array (SADT-VISOR sadt_flexreg/util.py:25-28, 32-44). The legacy fixed this in ADTLib (legacy FlexReg_CLI/FlexReg_Method/util.py:24-30). The Slicer preview takes the first single-component array instead (FlexRegLib/butterfly_preview.py:136-152), while its comment says the server picks it the same way: preview and server can use different arrays on the same arch.

The four orientation teeth are fixed

The arch is oriented on teeth 3, 5, 12 and 14, whatever teeth are chosen for the corners (SADT-VISOR make_butterfly.py:82-83); the client uses the same constants (AutomatedDentalToolsRemote FlexRegRemote/FlexRegLib/butterfly_preview.py:29). An arch missing one of them fails even if the four chosen teeth exist. The four tooth_* arguments are hidden in the panel (layout.py:101-104).

Joystick bounds are enforced by the server

Ratio in [0, 1], adjustment in [-5, 5] mm, translation in [-15, 15] mm (SADT-VISOR layout.py:24-28, 57-59, 81-83); a value outside is refused (VISOR-serve server/base.py:759-768). The comment in layout.py:22-23 still says a larger number typed in the box "still works": that is no longer true.

Output names can lie about the format

The output keeps the input extension (SADT-VISOR __init__.py:163) but is always written as a binary legacy VTK file (pipeline.py:90-94), so an .stl or .vtp input yields a file with that extension and a VTK content. Read from the code; what Slicer does with such a file was not checked. The legacy always wrote .vtk (legacy FlexReg_CLI.py:321).

Absolute server paths in the report; GPU assumed for every mode

The report stores the absolute server path of the output and of the transform (SADT-VISOR __init__.py:170, 175), although progress messages avoid file names on purpose (__init__.py:144-146). And since the tool declares no device, the server queues even Register for the GPU (VISOR-serve server/execution/dispatch.py:95-116).

The tool's documents misdescribe the legacy flip

The docstring of pipeline.py (SADT-VISOR pipeline.py:8-14), the README (tools/FlexReg/README.md:32-36) and the docstring of test_a_surface_leaves_in_the_convention_it_arrived_in (tests/test_run.py:62-65) say that the legacy CLI flipped to RAS on read and never flipped back. At 3c67957 it does flip back before writing (legacy FlexReg_CLI.py:295-305). The VISOR code is right; only the stated difference does not hold for that commit. Likewise the module docstring says curve and delete "stay in the Slicer module" (__init__.py:19): FlexRegRemote.py has neither.

The real patch construction has no test

The gpu marker is declared (SADT-VISOR tools/FlexReg/pyproject.toml:32-34) but no test uses it, and the test of a missing tooth replaces butterflyPatch with a fake (tests/test_run.py:336-349). The figures in the tool's README (patch on a 294,260-point arch) have no test behind them in the repository.
