FlexReg on VISOR

FlexReg registers an intraoral arch onto another by looking only at the palate, the part of the mouth that does not move between two visits. It first draws a butterfly-shaped patch on the palate, from four teeth, then slides the patch of one scan onto the patch of the other. This page explains how, step by step, with the maths. Where the code does something worth checking, a link leads to the code page. The legacy module is described on its own page.

VISOR Code (developers) Legacy page Guide (VISOR)

Overview: what goes in, what comes out

Between two visits the teeth can move, and so can the gums; the palate hardly does. FlexReg uses that: it marks a patch of the palate on each arch and registers the arches on that patch alone, so that the teeth themselves are free to have moved. The patch is built by geometry, with no network, from four teeth chosen on the arch.

What it is
Inputan intraoral surface (.vtk, .vtp or .stl) that already carries a tooth number on every point, or a folder of them; a reference arch to register onto
Ideafour tooth centroids give four corners; the corners give an outline; the outline is filled over the surface; a rigid ICP aligns the patch of one arch with the patch of the other
Outputthe registered surface, a .tfm transform Slicer can load, and FlexReg_report.json

Three modes: Patch builds the patch only, Register registers a surface that already has one, Patch and register does both.

1. Position in the chain

FlexReg calls no other tool and no tool calls it. In the legacy module the widget ran a crown segmentation when the arch had no tooth labels; in VISOR the arch must arrive already labelled, for example from a Crown_Seg run. Nothing computes the mucogingival patch any more.

In the codeThe state of the port, the calls, and what is expected upstream

2. Files involved

The tool is a plain Python package: its geometric core (orientation, patch, propagation, ICP, tooth selection) is the legacy code with renamed variables, and the new part is the entry point and the reading, merging, registering and writing functions around it. A small library in the Slicer client replays the outline for the preview.

In the codeEvery file with its size and role, on the server and in the client

3. What runs where

The server builds the real patch (the fill needs the GPU), registers and writes everything. The Slicer panel only previews the outline: while you drag a joystick, the outline is recomputed locally with the same constants and drawn in the scene, with no round trip. Filling the patch is left to the server. The preview only works when the surface is already in the Slicer scene, not for a folder.

4. The pipeline, step by step

One run handles one surface or a folder of them.

In the codeThe order of the calls in the entry point

4.1 Checks before reading computed

The mode decides whether to register and which array to register on: Butterfly for the palate, Bottom_MGL for the mucogingival line. A registration without a reference is refused before any file is read, and the reference is read once for the whole batch. A folder is walked recursively and sorted, so two runs name their outputs the same way.

In the codeThe refusal, the folder walk and the extensions

4.2 Reading, and the coordinate flip computed

The file is read by its extension and an empty mesh is refused by name. All the geometry was written in RAS while Slicer files are in LPS, so the surface is first mirrored in x and y (a half-turn about the vertical axis). The same operation flips it back before it is written. The matrix found later is converted the same way, see 4.6.

In the codeThe reader, the scale by (-1, -1, 1) and the empty-mesh check

4.3 The palatal patch (“butterfly”) computed

Built only when the mode contains Patch and the patch is the palate. The arch is first oriented in a canonical way, from the centroids of four fixed teeth (3, 5, 12, 14, that is UR6, UR4, UL4, UL6; the tooth numbers follow the Universal system, 1 to 16 along the upper arch from the right third molar, 17 to 32 along the lower arch from the left third molar): the occlusal plane lies near z = 0, +y points to the front and +x to the patient’s left. This oriented copy only serves to draw the patch (the patch is written back into the original surface); it is not the RAS frame used for the registration. The four teeth that drive the corners are then averaged to centroids; by default they are teeth 6, 11, 3 and 14, and a missing tooth is an input error that names it.

The patch array is written into the original surface, not into the oriented copy.

In the codeThe six steps with their constants, the guard and the line numbers

4.4 Merging patch arrays computed

When several numbered patches exist on a mesh (Butterfly1, Butterfly2, and so on), they are combined with a logical OR into a single Butterfly array. This runs only right after a patch was built in the same run.

In the codeThe merge function and when it is called

4.5 Registration on the patch computed

The moving surface must carry the patch array, or it is refused. The ICP keeps, in both arches, only the points where the array equals 1, and registers those; the matrix it finds is then applied to the whole moving mesh, teeth included. The surfaces you give are the moving ones and the reference is the fixed one.

In the codeThe call, the VTK settings and the refusal when the array is missing

4.6 Transform and writing computed

The surface is flipped back and written as a binary legacy VTK file, whatever the input extension; the output mirrors the input folder tree under the output folder, with the suffix. The input is never modified. A surface that raises an input error is recorded as failed and the run goes on.

In the codeThe matrix construction, the writer and the output names

4.7 The report computed

FlexReg_report.json lists, per surface, the patch used, the array registered on, the transform and output files and a status, and ends with a summary of totals. It is written before the final refusal “none of the surfaces could be processed”, so a run where nothing worked still leaves its reasons.

In the codeThe report structure and the progress messages

5. What you can choose

  • The surfaces: one labelled arch or a folder; a hosted test file is offered.
  • The mode: Patch, Register, or Patch and register (the default).
  • The patch: palate (butterfly) or mucogingival line; the second can only be registered if the array already exists.
  • The reference, to register onto; it must already carry its patch.
  • Four joysticks, one per corner: the ratio (0 to 1, from the middle to the tooth) and the adjustment (-5 to 5 mm along the arch), and a fifth joystick that shifts the whole patch by up to 15 mm.
  • The suffix of the output names (_Reg by default). The four tooth numbers exist but are hidden.

6. What is predicted vs computed

BlockNature
Tooth labelspredicted upstream, by whatever labelled the arch; not run by FlexReg
Orientation, centroids, corners, outlinecomputed geometric (also replayed in the client for the preview)
Patch fillcomputed geodesic flood fill, on the GPU
Merge of patch arrayscomputed logical OR
Registrationcomputed rigid ICP (VTK), limited to 1000 rounds, on the CPU
Mucogingival patchnot computed anywhere in VISOR

FlexReg on VISOR runs no network at all: the legacy module’s two predicted inputs, the crown segmentation and the mucogingival landmarks, are both outside the port.

7. Environment

The tool has its own Python environment with torch (for the fill only), vtk, numpy and SimpleITK. The server assumes the GPU for every mode, including plain registration. Nothing is installed in Slicer; the preview library needs only vtk and numpy.

In the codeThe pinned versions, the hosted test files, and the limits

8. What changed from the legacy logic

The geometry of the patch and of the registration is the same code. What changed is the wrapping.

  • A missing tooth is now an error that fails that surface; the legacy logged it, wrote the mesh with no patch, and looked successful.
  • Inputs: .vtk, .vtp and .stl are read directly.
  • Outputs go to a separate folder with a suffix; the legacy rewrote the input file in the patch modes.
  • Merging the numbered patches runs on the CPU and only after a patch was built.
  • Absent: the free-drawn patch, patch deletion, the mucogingival patch computation, the crown segmentation and moving the second arch along with the first.
  • Parameters are bounded joysticks, checked by the server; the legacy took typed numbers.
In the codeThe full table with legacy and VISOR references

9. Known issues in VISOR

  • “Patch and register” patches only the moving surface, so the reference must already carry its patch (details).
  • Only input errors are reported per surface; any other exception stops the whole batch and leaves no report (details).
  • The mucogingival line cannot be produced by anything in VISOR (details).
  • Without a tooth-label array, a wrong array can be picked silently (details).
  • The four orientation teeth are fixed, so an arch missing one of them fails even if the four chosen teeth exist (details).
  • An .stl or .vtp input yields a file with that extension but VTK content (details).
  • The real patch construction has no test (details).
