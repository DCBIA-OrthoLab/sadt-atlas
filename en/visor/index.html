VISOR: the next generation of the tools

The rest of this atlas reads the legacy extension, where every algorithm runs inside Slicer. VISOR is the new generation that moves the computation to a server: a thin Slicer client, a generic inference server that knows no dental tool, and a catalogue of tools, each in its own folder with its own Python environment. This page is the overview; the pages listed at the bottom go into the machinery.

audit snapshot · 2026-11-09 three repositories English only
Other languages

The French, Spanish, Italian, Korean, Portuguese and Thai versions of this site describe only the legacy code (SlicerAutomatedDentalTools, commit 3c67957). They have no VISOR pages. Whatever a translated tool page says about where a computation runs, or which environment it needs, is a legacy statement. The translations will be redone later.

1. What VISOR is

VISOR is three repositories that each own one layer. None of them is a fork of the legacy extension: the algorithms are ported ("a repackaging exercise, not a rewrite", SADT-VISOR CONTRIBUTING.md:309-315), the structure around them is new.

Remote, the clientAutomatedDentalToolsRemote, the client: a Slicer extension of 23 module folders, each a thin panel over the server. A panel is generated at run time from the server's tool descriptor, so a field added on the server appears in Slicer with no client release. Slicer installs nothing and downloads no model for a ported module.
VISOR-serve, the serverThe inference server: FastAPI, Python 3.13, no torch. It discovers tools, publishes their schema, queues and admits runs, and launches each one in the tool's own interpreter. It is meant to know no dental tool by name.
SADT-VISOR, the toolsThe catalogue: one isolated Python project per tool, 19 of them, each with its own .venv and committed uv.lock. A tool is one public function, run(); its schema is derived from the signature.

Code: client AutomatedDentalToolsRemote CMakeLists.txt:24-48, ServerToolsCoreLib/formgen.py:1-30; server VISOR-serve server/registry/__init__.py:114; catalogue SADT-VISOR README.md:3-5, 41-58.

2. Why it exists

Legacy puts everything in Slicer: the widget, the model download, and the Python environment each module builds for itself. Two consequences recur across the legacy pages of this atlas: a laptop without a GPU cannot run a segmentation, and tools that pin incompatible libraries have to live in separate conda environments created on the user's machine. SADT-VISOR's own README lists reproducible conflicts in the upstream pins: SurgMovPred asks for numpy==2.4.0 where AREG, MedX and CLIC need numpy<2.0.0, two conda environments are both named shapeaxi (Python 3.9 and 3.12), and torch is pinned to 2.2.0 in five modules and left unpinned in the others (SADT-VISOR README.md:10-28).

VISOR answers with two moves. The computation goes to one machine that has the GPU; and each tool keeps its versions, because "the versions are part of the science" (SADT-VISOR README.md:25-28). The disk cost of many environments is handled by building them so that identical wheels share inodes: scripts/audit.py measured, on the checkout that was read, 7 virtual environments present at 19.6 GB apparent and 8.3 GB unique (SADT-VISOR scripts/audit.py:201-204, run on 2026-11-09).

Nothing on this site claims that VISOR reproduces the legacy results bit for bit.

Where a Remote module differs from a pure panel

ALIRemote and AREGRemote send one request to a facade, and the server picks the engine (see facades). FlexRegRemote recomputes the outline of the patch locally, about 18 ms on a 294,000-point arch, so that the joysticks respond; the real patch is computed on the server at Apply (FlexRegRemote.py:14-18).

5. Security, in one sentence

Transport is HTTPS with a certificate verified by the client and a shared Bearer token on most routes; de-identification is specified but not implemented, and attestation and key exchange exist only in a separate research prototype, not in these three repositories. The details and the evidence are on the security page.
