BatchDentalSeg on VISOR

BatchDentalSeg labels the teeth and jaws of CT and CBCT scans in a batch, with one multi-label network that gives every voxel its label in a single pass. This page explains how a run goes in VISOR, step by step, with the maths of the parts that are computation rather than learning: how the scan is normalised, how the network’s patches are blended, how a label is chosen for each voxel. Where the code does something worth checking, a link leads to the code page. The legacy module is described on its own page.

Code (developers) VISOR Batch_Dental_Seg Legacy page Guide (VISOR) Bibliography

Overview: what goes in, what comes out

BatchDentalSeg takes CT or CBCT scans of the head and labels the teeth and jaws in each one. A single 3D network, chosen among four, gives every voxel its label in one pass; it is not one network per structure, as in AMASSS. In VISOR the scans go to a server, where nnU-Net is called once for each batch of scans the server hands to the tool (section 4 gives the batch size).

InWhat happensOut
a scan or a folder, the name of one of four hosted models, and the export formatsthe scans are converted, one nnU-Net pass labels every scan of the batch, and each label volume is put back on its scan’s grida label volume per scan, optionally one file per label, STL, OBJ, VTK surfaces, and BatchDentalSeg_report.json

1. Position in the chain

The tool is a leaf: it calls no other tool, and one tool calls it. VFACE uses it for its heat maps, asking for a model and the prediction ID. Not ported on purpose: the automatic crop, the memory guard, the mirror correction, the persistent queue and the glTF export; the server takes over admission and memory.

In the codeCallers, state of the port and the tool table

1.1 What runs where

  • On the server: reading and converting the scans, one nnU-Net call for the whole batch, putting the labels back on the scan grid, writing label volumes, per-label files, meshes and the report.
  • In Slicer: choosing the scan, the model name and the export formats, unpacking the results archive, and loading at most 12 results. Nothing about anatomy or models lives in the panel.
  • Nothing is installed in Slicer: no NNUNet extension, no torch, no model download. Model bundles are hosted on the server and published as names, so weights are never sent from the laptop.
In the codeThe where-it-runs table with file and line

2. Files involved

The tool is a plain package with one public function, the pipeline, a table of the four models and their labels, a wrapper around nnU-Net, a module for the memory-saving resampling, a mesh exporter and the panel layout. The server and the Slicer panel contribute the hidden arguments, the model menu, the memory limits for nnU-Net’s workers and the result loading.

In the codeFile table with line counts, and the files outside the tool

3. The pipeline

A straight line: the model is checked before any scan is read, every scan is converted into one folder, nnU-Net runs once over that folder, then each scan is written back on its own grid. Only the network step is learned. Each box of the diagram leads to its section.

In the codeThe orchestration function

3.1 Inputs and discovery

A single file is taken as is. A folder is walked recursively and files with a volume extension are kept, except those whose name looks like an earlier output of the tool (ending in the prediction ID, or in the prediction ID and a label name), so a folder can be re-run in place. The input tree is kept: each case is described in the report by its path relative to the input, never an absolute path.

In the codeDiscovery and the filter for earlier outputs

3.2 The model: one name, one bundle, one label table

The model name is looked up before any scan is read; an unknown name is refused with the list of known models, and an incomplete bundle is refused too. The name also selects the label table, so a caller cannot pair one bundle with another’s labels.

3.3 Conversion to the nnU-Net layout

Every scan is read and rewritten into one folder under a positional case id (case_0000, case_0001...), never renamed: nnU-Net picks its reader from the extension, so a renamed NRRD would be read wrong. The ids are positional because nnU-Net writes its output under the input’s id, and two scans called the same in different sub-folders would collide. A scan that cannot be read is recorded as failed and skipped.

No windowing or crop is written in this package. The only resampling it adds is the optional graphics-card one of 3.5, and the one that puts the result back on the scan’s grid (3.6); the rest of the preprocessing is nnU-Net’s, driven by each bundle’s plan. The legacy automatic crop is not ported on purpose, because it changes what the network sees.

Only the plan of DentalSegmentator can be read in the repositories (in the legacy one): percentiles −110 and 3067, mean 1274, standard deviation 558. The three other bundles bring their own plan file, so for them this recipe is assumed, not checked.

In the codeCase ids, conversion and unreadable scans

3.4 Inference: one call for the whole batch

nnU-Net is called once with the whole input folder it is given (a large cohort reaches the tool as several such folders), so the checkpoint is loaded once per run, not once per scan. The settings are the same as in the legacy: fold 0 (a single trained copy of the model; no ensemble), a step of 0.5 (each patch moves by at most half its size), Gaussian weighting (the bell-shaped weights below), no test-time mirroring (no averaging over flipped copies of the scan). The device falls back to the CPU, with a warning, when no card is visible. Progress has only two measurable ends: reading counts scans from 0 to 10 %, writing from 90 to 100 %, and in between one line says “segmenting N scan(s) in one pass”.

In the codeThe predictor options, the two inference paths and progress

3.5 GPU resampling and the per-class argmax

By default, on a graphics card (the code calls this a CUDA device, NVIDIA’s computing interface), the tool swaps nnU-Net’s resampling for a torch one. The input volume goes from cubic to linear interpolation, which the code names as the whole numerical difference.

It then goes further: the network’s output is resampled one class at a time, keeping a running maximum and its label, so that the full set of class scores is never in memory at once. According to the code’s own docstring, the result is identical (0 differing voxels out of 95 682 560 on a UniversalLab run) and the peak drops from about 30.6 to 1.25 GiB (gibibytes) of video memory; those numbers were not reproduced here.

In the codeThe resampler swap and the per-class running argmax

3.6 Back on the scan grid, and writing

For each scan, the prediction is read and put back on the source scan’s exact grid: if size and spacing match (within 0.0001) the geometry is simply copied, otherwise the label volume is resampled by nearest neighbour. The output tree mirrors the input tree. With NIfTI selected, the file is <base>_<ID> plus the compressed extension; with the per-label option, one binary file per label present, named after the label. No cleanup, island removal or hole filling is applied: the volume is nnU-Net’s output on the scan’s grid.

In the codeGeometry restoration and the output table

3.7 Surfaces

Nothing happens unless a mesh format is requested. Each present label gets one surface, built once and written in every requested format, so ticking STL and OBJ together costs one marching-cubes pass. The mask is contoured, the mesh is smoothed with a windowed sinc filter (30 iterations, pass band 0.05; a filter that moves each vertex toward the average of its neighbours while shrinking the shape as little as possible. Feature-edge smoothing is off on purpose, because on a raw marching-cubes mesh every voxel step is a sharp edge), and optionally decimated (off by default, to match the legacy STL export). STL and VTK are written in binary, OBJ as text. No explicit RAS or LPS flip is applied, unlike the legacy VTK export.

In the codeThe mesh writer, the smoothing and decimation filters

3.8 Report and cleanup

BatchDentalSeg_report.json holds the model and its full label table, the settings used, and one entry per case with its status and the files produced. The case ids are positional and the inputs are relative paths, so the report names no absolute path. The work folder is removed first, then the report is written; if the inference call raises, the folder is removed and the whole batch fails, with no report written.

6. Environment

The tool runs in its own virtual environment, built from a lock file; nothing is installed in Slicer. The versions follow the server image: Python 3.11, torch 2.8.0, nnU-Net 2.8.1, SimpleITK, NumPy and VTK. Models are staged by the server’s setup script, one folder per bundle, and the tool never downloads anything during a run. Only two of the manifest’s files carry a checksum. The table is on the code page.

8. Findings in VISOR

Each point is checked in the code and described, with its evidence, on the code page; the list also appears in the findings.

  • VFACE asks for surfaces and gets label volumes: its call leaves the export format at NIfTI, so it finds no mesh and no heat map can be drawn. Evidence.
  • The tool’s README is out of date on mesh exports and memory. Evidence.
  • A scan named ..._Seg is invisible in a folder with the default prediction ID. Evidence.
  • GPU resampling is on by default and changes the numbers slightly. Evidence.
  • cuDNN autotuning is not switched off (cuDNN is NVIDIA’s library for the network’s convolutions; autotuning lets it pick a different algorithm from one run to the next), so two runs of one scan may not give bit-identical masks. Evidence.
  • An empty export list gives “ok” with no file when the tool is called directly. Evidence.
  • Per-label files need NIfTI: with meshes only, nothing is written for them. Evidence.
  • The label table travels with the result, but Slicer does not read it. Evidence.
  • Progress has two ends because the whole folder goes through one call. Evidence.
  • Verified good point: an unreadable scan does not stop the batch. Evidence.
