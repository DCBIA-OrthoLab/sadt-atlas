Packaging and deployment

How VISOR-serve is built into one container, where models and configuration live outside it, what every setting defaults to, which scripts stand a server up and keep it current, what the benchmarks published with the repository measured and what they did not, and what a dated inspection of a running instance found. The server is a Docker image with one Python 3.13 API environment that never loads torch, and one hardlinked virtual environment per tool.

Note

Citations are file:line in VISOR-serve at commit e9a7e5d, which is main (e91557e) plus one commit that touches only server/deployment.toml (it declares the VFACE data folder). The tools themselves are in SADT-VISOR at 6ba2a78. “Legacy” on this site means the Slicer modules of SlicerAutomatedDentalTools; nothing below applies to them. What section 7 says about a running instance comes from an inspection dated 2026-10-20, not from the code. Transport protection, tokens and the data-handling claims are on the security page; the shape of the whole system is on the architecture page.

1. The image

There is one container for all tools. docker/Dockerfile (232 lines) builds it in stages. The runtime stage starts from python:3.13-slim (:76), installs the one system library no lockfile can supply, libgomp1 (:86), copies uv 0.12.3 (:89) and builds the API environment at /opt/sadt/.venv from server/requirements-api.txt, which lists only fastapi, uvicorn[standard], python-multipart and pydantic-settings (:105-108). The server process therefore imports no torch, no nnU-Net and no MONAI. Each tool's own interpreter is installed by uv itself (:75), so tools can sit on different Python versions.

  • Tools are baked in. Each packaged tool is a folder /tools/<name>/ holding .venv, src/ and .schema.json; tools in a group folder (tools/ALI/ALI_CBCT) are found because discovery goes two levels deep (registry/__init__.py:114). The naming/ package is copied to /naming because tools depend on it by path (Dockerfile:122). The two in-process fixtures Example_Tool and Test_Tool are in the image: COPY server/ takes server/tools/ and .dockerignore:18-30 explains that the exclusion was removed, so that a fresh deployment can prove auth, upload, run and result before any model is downloaded. The running instance serves both (23 entries).
  • One uv sync layer, on purpose. Every tool's uv sync --frozen --no-install-project --no-dev --all-extras runs in a single RUN (:152), with UV_LINK_MODE=hardlink and the uv cache on the image's own filesystem (:96-101). Split across layers, overlayfs copies files up and the hardlinks break; the Dockerfile's own comment measures the eleven torch tools at about 26 GB shared against about 63 GB duplicated (:131-134). --all-extras is deliberate: a tool such as Crown_Seg keeps its engine behind an extra, and without it the image imports and then answers 503 on the first real request.
  • verify_dedup.py. Nothing observable fails when the links silently turn into copies, so docker/verify_dedup.py checks it: for files that belong to the same distribution at the same version (read from each environment's RECORD), a second inode means a copy. It exits non-zero on any, uses only the standard library, and is shipped in the image at /opt/sadt/verify_dedup.py (Dockerfile:200). The test fixtures are numpy_old (1.26.4, Python 3.12), numpy_new (2.5.2, Python 3.13) and numpy_twin.
  • Schemas are generated at build time by running each tool's describe.py with that tool's own interpreter (:177-188); a tool that cannot describe itself is reported and not served. At startup a stale schema is regenerated and cached in SCHEMA_CACHE_DIR (/var/cache/sadt), because /tools is read-only to the server.
  • Not in the image: models and test files (section 2), the per-site deployment.toml (section 4; the image carries a default copy that a mount replaces), the job scratch space /jobs and the API token.
  • Process. USER sadt, not root (:227); the code in /tools is root-owned and read-only to the server so that third-party code cannot rewrite its own virtual environment; CMD is uvicorn main:app --host 0.0.0.0 --port 8000 with no --reload and no --workers, hence one process and one admission queue (:232). There is no HEALTHCHECK in the Dockerfile or in docker-compose.yml.

The environment the image sets (Dockerfile:202-216) is SADT_DISPATCH_MODE=subprocess, TOOLS_DIR=/tools, RUNNER_PATH=/opt/sadt/server/execution/runner.py, DESCRIBE_PATH=/tools/scripts/describe.py, SCHEMA_CACHE_DIR=/var/cache/sadt, DEPLOYMENT_CONFIG=/opt/sadt/server/deployment.toml, DATA_DIR=/DATA, TEMP_DIR=/jobs and PYTHONDONTWRITEBYTECODE=1. The SADT_DISPATCH_MODE default in config.py:37 is inprocess, marked temporary; the image overrides it, so what the container runs is always the subprocess path.

The compose file defines several services. The one that is a real deployment is inference-venvs (profile venvs, docker-compose.yml:200): it builds docker/Dockerfile with a named build context tools=${TOOLS_CONTEXT:-docker/fixtures}, so without TOOLS_CONTEXT it builds the small fixtures, not the real tools. It sets shm_size: 8gb (nnU-Net passes data between export workers through shared memory; the default 64 MB fails with a message that names the wrong resource), reserves all GPUs and restarts unless-stopped. The other services are inference (a prebuilt GPU image from a container registry, with ./server mounted, pip run at each start and uvicorn --reload), inference-cpu, and the test / test-gpu services. docker-compose.dev.yml is an overlay that mounts server/ and each tool's src/ from a SADT-VISOR checkout, read-only.

Pitfall

Documentation inside the repository still describes older images. The Dockerfile comment at :193-195 says server/tools/ is excluded by .dockerignore, which is no longer true (.dockerignore:18-30). The comments at :11-12 and :217 still count fifteen tools or upstreams; there are 19 packaged tools. docker/README.md:45-48 says a tool nested one level deeper “is NOT discovered by the server today”, yet discovery is two levels deep and five served tools (ALI_CBCT, ALI_IOS, AREG_CBCT, AREG_IOS, AREG_IOSCBCT) live in group folders. docker/README.md:4 places runner.py at /opt/sadt/runner.py; it is server/execution/runner.py.

2. Models and test files

Weights are never in the image and never uploaded from a laptop. They live in a DATA/ directory mounted read-only at /DATA: DATA/<slug>/models/<name> and DATA/<slug>/testfiles/<name>, optionally one level deeper as a scope (DATA/AREG/testfiles/CBCT_T1). LocalDataStore reads it; a different backend can be plugged in through the abstract DataStore class (DATA_BACKEND, config.py:31).

  • Which folder. The slug is the tool's declared data_dir; if none, the literal tool name when that folder exists; otherwise the name without underscores, so Batch_Dental_Seg reads DATA/BatchDentalSeg (deployment.data_slug, registry/deployment.py:311-325). Five tools share two folders through data_dir = "AREG" (three tools) or "ALI" (two).
  • Which arguments are filled from it. By naming convention (registry/conventions.py): model, *_model and *_reference are published as a name chosen from DATA/<tool>/models/, never as an upload, so weights cannot be sent from a client. A file upload on such a field is a 400 (main.py:1269-1278). Any other path may be uploaded or filled from testfiles/.
  • What the API offers. GET /tools/{tool}/data lists models and test files; GET|HEAD /tools/{tool}/testfiles/{name} serves a test file. There is no route that serves a model (download_testfile only reads testfiles). A test-file folder is zipped on the fly and sent with Accept-Ranges: none; otherwise the client probes, sees ranges and splits a 339 MB cohort into 43 parts, the server building the same archive 43 times: 39.1 s ranged against 1.5 s whole (main.py:794-806).
  • Filling it. scripts/data-manifest.yml says what exists, where it comes from and where it goes; scripts/fetch_data.py (standard library only) downloads it, setup-models.sh and setup-testfiles.sh are wrappers, and --list prints sizes per tool without downloading. An entry has a name, a url, an optional sha256 (a mismatch discards the file; when absent the script prints the hash it got, to be pasted into the manifest), an optional size, extract: true to unpack a zip and keep the folder, and dest to rename or to group several archives into one bundle folder. The manifest comment puts the whole set at about 29 GB across 14 tools, 12 GB of it ALI's CBCT models.

A value is read from the environment (names are the field names) or from a .env file in the working directory (config.py:23); unknown keys are ignored. Compose and the scripts add their own variables, read from a .env beside docker-compose.yml (.env.example): API_TOKEN (compose default dev-token, docker-compose.yml:208), DEVICE (compose default cuda, :209), HOST_PORT, VENVS_HOST_PORT (default 8001), BIND_ADDR, TOOLS_CONTEXT and SADT_AUTO_UPDATE (section 5).

Pitfall

The compose default ${API_TOKEN:-dev-token} means an installation that does not write a .env runs with a token that is public, because it is in a versioned file. The port mapping "${BIND_ADDR:+${BIND_ADDR:-}:}${VENVS_HOST_PORT:-8001}:8000" (docker-compose.yml:224) publishes on every interface when BIND_ADDR is unset. The path through scripts/server_ctl.py generates a token and defaults BIND_ADDR to 127.0.0.1 (server_ctl.py:368,398); starting compose by hand does not.

4. deployment.toml

server/deployment.toml holds what is specific to one installation. It is read once at startup, mounted read-only into the container over the image's copy so that changing a line does not mean rebuilding the image (docker-compose.yml:215-220). Each [tools.<name>] table may contain exactly these keys (_TOOL_KEYS, registry/deployment.py:69): server_selectable, max_upload_mb, data_dir, hidden, timeout_seconds, dispatch, batch, width_from. server_selectable takes model, testfile or none, with a scope written testfile:Sub_folder (:53, SCOPE_SEPARATOR). An unreadable file or an unknown key is fatal (DeploymentConfigError); the refusal of a value the server does not know carries the marker DEPLOYMENT-CONFIG-AHEAD-OF-SERVER (:66), because the file is mounted and can be newer than the image.

What the file at e9a7e5d actually declares (292 lines, 14 sections, none with a timeout or an upload limit):

A facade (ALI, AREG) has no folder and no interpreter. Its schema is composed at startup from the dispatch table: a leading mode argument, then the union of the targets' arguments, each visible only in the modes that have it (registry/facade.py:49-98). The same argument name must have the same type, accepted extensions and required-ness in every target, otherwise the facade is skipped with a warning; it is fatal only if its name collides with a tool already served (facade.py:282-295).

The file is not empty, whatever its header says

server/README.md:540 says deployment.toml “is therefore an empty file of comments today”, and the first lines of the file itself say “this file has no entries” (server/deployment.toml:1-4). Both are false at this commit: the file has 14 sections, which is what makes the AREG and ALI facades, the VFACE data folder and the per-tool batch and width declarations work.

Automatic update. SADT_AUTO_UPDATE is off (default), notify or apply (server_ctl.py:838-850). apply waits until /status reports no running and no waiting run, closes the door through POST /maintenance with a 60 s lease that it renews (:911, GATE_LEASE_SECONDS), runs git pull --ff-only (:1178), relaunches with up -d --force-recreate (:1205, never restart) and reopens. It refuses a change to a lockfile, a pyproject.toml, server/requirements* or docker/, since those need a new image (:522-524). The unit's own header warns that the machine “will execute code pulled from a public repository” and that no commit in these repositories is signed today; turning it to apply is described as a decision for whoever is accountable for the machine.

7. What an inspection of a running instance found

A dated observation, not a property of the code

One running instance was inspected on 2026-10-20 (a report kept outside the repositories). What it found about that machine may no longer be true. This section keeps what the code explains; the details that identify the machine or its network are deliberately left out. The only check made while writing this page was an unauthenticated GET /health and GET /tools: they answered {"status":"ok"} and 23 entries.

  • What the code predicts, it did. GET /health and GET /tools answered without a token, GET /status refused a request without one (401). The catalogue had 23 entries, 19 of them from a schema. The startup log held no skip, error or traceback; its only warnings were the ignored schema keys of ALI_CBCT, ALI_IOS and ASO, explained on the architecture page.
  • Plain HTTP, straight from the container. The Slicer client of AutomatedDentalToolsRemote requires HTTPS with a publicly signed certificate and has no fallback (security page), so it cannot connect to an instance exposed that way; a script that calls the API directly can.
  • No .env. The instance had been started without one, so it ran with the compose defaults described in section 3, the token included.

The report then lists what can stop an unattended run. Each point below is checked against the code; the report marks the first four as derived from the code, the configuration and the log, not from a real run.

  1. No timeout. TOOL_TIMEOUT_SECONDS is 0 and deployment.toml sets none (config.py:77): four blocked runs freeze the server without any of them failing.
  2. An unmeasured tool runs alone. A tool whose cost has never been measured reserves the whole budget (execution/admission.py:22-33). On that instance most tools had no measured cost yet, so the announced max_parallel_jobs: 4 overstated the real throughput.
  3. Reservations follow the worst recent run. The learned cost is the maximum of the last COST_WINDOW = 20 runs (config.py:106), so a tool whose memory use varies a lot between inputs reserves its worst case and serialises.
  4. No VRAM figure. On that instance /status returned vram_bytes: null and a card with free_bytes: null: the probe, which shells out to nvidia-smi (resources.py:193), returned nothing, and /status tolerates that by design (main.py:470-474). Admission then works on cores and RAM.
  5. A failed run still teaches the cost table. The measurement is kept before the error branch, on purpose, because an out-of-memory run is the most useful measurement (execution/dispatch.py:800-803). A bench that fails for an unrelated reason can therefore inflate later reservations.
  6. No healthcheck in the Dockerfile or in compose: restart: unless-stopped relaunches a dead container, nothing detects a live but stuck one.
  7. An operator's SIGKILL looks like an out-of-memory death. A SIGKILL with no result.json is read as the kernel's out-of-memory kill (execution/dispatch.py:930-949), so the run is started again.

8. The benchmarks published with the server

benchmarks/ is a re-runnable harness (python -m benchmarks.run --campaign b1..b5 [--dry-run]), configured by config.yaml. Three execution paths exist: local (the tool in its own interpreter, no HTTP, with four documented differences in NOTES-local-path.md), loopback (the HTTP API on the same machine) and lan, which is never measured: server.lan_base_url is null (config.yaml:22). The harness's HTTP client speaks the Slicer client's protocol: 8 MB parts, four concurrent transfers, a SHA-256 per part, gzip, X-Result-Delivery: reference, ranged downloads. Statistics are the median with the full range, never the mean; repetition 1 of each configuration is discarded as warm-up but kept in the raw file with warmup: true; a failed run is a record, never removed.

Pitfall

Read these numbers for what they are. They were measured from 2026-08-25 on a single machine (Xeon w7-3555, 28 cores, 125 GiB, RTX 6000 Ada 48 GB, driver 595.84, 1 Gb/s Ethernet, Ubuntu 22.04.5), on a single card, with MAX_CONCURRENT_GPU_JOBS=1 (benchmarks/README.md:338), that is, before the admission engine replaced that counter (commit 89393b5, 2026-09-21). They were taken on loopback or local only, so the transfer times are those of localhost, not of a network. Their records point to tool and server trees marked -dirty, from August. They do not describe the current scheduler.

Pitfall

Byte-for-byte parity between the local path and the HTTP path is established for one tool, AREG_IOSCBCT, in one session (n = 1 pair). It is not established in general. The control shows that most of these tools do not even reproduce themselves byte for byte on the same path, because their reports carry durations or paths, and a byte comparison does not tell a report from data. Neither “parity reached” nor “parity lost” can be written from this table. The repository's README says the harness reproduces every runtime number of the accompanying paper; that holds for B1, B3 and B4, which have summaries, while B2 and B5 have to be read from the raw files.
