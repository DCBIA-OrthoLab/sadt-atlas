VISOR architecture

How the pieces fit: what stays in Slicer, what the server does before a tool ever runs, and how a tool declares itself so that nobody writes its interface by hand. A run, from upload to result, is on its own page; so are the image, security and tests. Citations read repository path:line and refer to the commits of the overview: VISOR-serve is e9a7e5d, SADT-VISOR is 6ba2a78, Remote is AutomatedDentalToolsRemote 19b95e8.

VISOR-serve e9a7e5d SADT-VISOR 6ba2a78 Remote 19b95e8

1. The shape of it

Two machines, one boundary. On the clinician's side, Slicer holds a Remote module whose panel was built by formgen from the server's tool descriptor. On the server side, a single FastAPI process validates the request, finds the tool in its registry, waits for room in its resource budget, and starts the tool in a subprocess that uses the tool's own interpreter. The server process contains no torch; the heavy libraries live only in the environments of the tools.

Code: the container is Python 3.13 with only the API requirements installed in /opt/sadt/.venv, tools under /tools/<name>/.venv (VISOR-serve docker/Dockerfile, detailed on the deployment page); SchemaTool.invoke always dispatches and SchemaTool.run raises RuntimeError (VISOR-serve server/registry/schema_tool.py:812-844); Popen(..., start_new_session=True) is at server/execution/dispatch.py:649.

2. Three rules that decide everything else

1. One tool, one folder, one venv

A tool is a directory with its own interpreter and lockfile. The server never imports it. Only the two fixtures, Example_Tool and Test_Tool, are Python classes loaded in-process.

2. Discovery is declared

A folder is a tool because its pyproject.toml says [tool.sadt] tool = true, optionally with name. The scan goes two levels deep, so group folders such as tools/ALI/ work.

3. Tools call tools through the supervisor

Never by import. A tool names the other by string, the schema publishes that name under calls, and the server checks at startup that every name is a tool it serves.

Code: rule 1 VISOR-serve server/registry/schema_tool.py:812-844, SADT-VISOR README.md:3-8 ("no HTTP, FastAPI, authentication or storage" in the tool repository); rule 2 server/registry/__init__.py:114-185, SADT-VISOR CONTRIBUTING.md:50-59; rule 3 server/registry/__init__.py:353, and the rule that the call must live in the tool's own src/, never in a shared package, otherwise calls comes out empty and the startup check verifies nothing (SADT-VISOR CONTRIBUTING.md:481-507).

3. The registry

At startup _build_registry assembles the table of served tools, in this order: packaged tools, in-process fixtures, the check of deployment.toml against what loaded, transitive stop points, facades, the check of supervised calls, and finally the refusal to start if packaged tools exist on disk but none loaded (VISOR-serve server/registry/__init__.py:521-605). Facades come after the stop points because a facade copies its targets' arguments.

What a failure costs

A tool that cannot load is skipped, written into FAILED_TOOLS, and announced in a full-width banner in the log, at startup and again at the end. A request for it then answers "failed to load at server startup", not "Unknown tool" (VISOR-serve server/registry/__init__.py:76-92, 521-605, 626). Four conditions stop the server instead:

Fatal conditionWhy it is fatalCode
UnknownSupervisedCalla sup.run("X") names a tool that is not served: the chain would start, run for an hour and then fail on a name that was wrong at deploy timeserver/registry/__init__.py:349-353
NoToolsLoadedpackaged tools exist on disk and none loaded: the deployment is broken, not one toolserver/registry/__init__.py:345, 472
FacadeError on a served namea facade declared in deployment.toml carries the name of a tool already servedserver/registry/facade.py:292
Unreadable deployment.tomlan unknown key or value raises DeploymentConfigError; a value from a newer file carries the marker DEPLOYMENT-CONFIG-AHEAD-OF-SERVERserver/registry/deployment.py:66-82
A stale source_hash is not fatal, whatever docs/INTERNALS.md says

VISOR-serve docs/INTERNALS.md lists "a stale source_hash" among the failures that stop the server. The code does the opposite: resolve_schema compares the cached schema's hash with the hash of the tool's src/ and, on a mismatch, regenerates the schema with the tool's own describe.py run in the tool's interpreter (server/registry/schema_tool.py:234-266). Only a describe.py that returns a schema whose hash still does not match raises SchemaError, and discovery catches that and records it as a single failed tool (server/registry/__init__.py:214-228). The docstring of that function, "the one failure that takes the server with it" (:219), is out of date too (docs/INTERNALS.md:45-50).

The regenerated schema is cached in SCHEMA_CACHE_DIR/<folder>.schema.json (default server/.schema-cache; /var/cache/sadt in the image) because the tool folders are read-only for the server (server/registry/schema_tool.py:224-227, 269-278; server/config.py:73). source_hash is a sha256 over the sorted <relative path>\0<sha256 of content>\n of every file under src/, without __pycache__ and *.pyc; the server and describe.py compute it independently and must agree byte for byte (server/registry/schema_hash.py:71; SADT-VISOR scripts/describe.py:1081-1095).

4. From the signature of run() to the schema

A tool publishes no interface by hand. scripts/describe.py (1,197 lines) reads the signature of run(), its annotations and the Args: block of its docstring, plus the AST for supervised calls, and prints a .schema.json. It has to be run with the tool's own interpreter and stays compatible with Python 3.9 so that it can run in old environments. For anything it cannot represent it prints a message on stderr and exits with code 2, so a schema that is "almost right" is never emitted (SADT-VISOR scripts/describe.py:1-18, 1185-1187).

No Optional, no union, no None default, no *args, no positional-only argument; every argument is annotated and documented. required comes only from the absence of a default. A path that was not provided travels as the empty string, which must stay a string: Path("") would be ., the current directory. Code: SADT-VISOR scripts/describe.py:36-46, 217-229, 287-296, 807-841, 1019-1036; server side VISOR-serve server/registry/schema_tool.py:67-86, 640-679.

What an argument can carry

The server reads these keys per argument: type, required, default, description, extensions, choices, section, ui, groups, visible_when, options_when, label, hidden, option_help, min_selected, select_all, x_range, y_range, x_labels, y_labels, x_label, y_label, section_columns, cell (VISOR-serve server/registry/schema_tool.py:134-147). The ones a tool author writes in an optional layout.py are the eighteen LAYOUT_KEYS of describe.py; a layout that names an argument or an option the signature does not publish is refused (SADT-VISOR scripts/describe.py:118-150, 901). At the top of the schema: name, description, arguments, returns, source_hash, supervisor, calls, injected_layout, quality_controls (server/registry/schema_tool.py:162-165), plus review_kind and case_input when the tool declares them (describe.py:1177-1182). returns becomes an output_kind: path, dict[str, path] or a list of paths give files; text and JSON give text (schema_tool.py:99-109).

A warning that is logged for keys the server does use

describe.py emits review_kind and case_input (SADT-VISOR scripts/describe.py:1177-1182), and SchemaTool reads both (VISOR-serve server/registry/schema_tool.py:762, 766), but neither is in _TOP_LEVEL_KEYS (:162-165). The check at :690-697 therefore logs "ignoring unknown schema key(s)" for every tool that declares them: ALI_CBCT and ALI_IOS (REVIEW_KIND = "landmarks") and ASO (CASE_INPUT = "input"). The values are consumed (the kind of a stop point, and the replay of corrected cases), so the message is wrong, not the behaviour. A cosmetic defect, but anyone reading the startup log will see it.

Arguments the server adds or fills

  • output_dir is removed from the published schema and filled with the job's own output/; a tool never chooses where it writes (server/registry/schema_tool.py:157, 741; server/execution/dispatch.py:393-441).
  • device is injected from settings.DEVICE when the caller does not choose (dispatch.py:431-432).
  • An undeclared hosted model argument receives the folder DATA/<tool>/models/, the folder and not a bundle (dispatch.py:433-440); this is why deployment.toml sets many server_selectable values to none.
  • keep_intermediate, added when the tool calls other tools: a multichoice, all unchecked, with select-all, in the section "Intermediate results". stop_after, added when there are stop points: a multichoice, all unchecked, in "Quality control". A tool never declares either (server/registry/schema_tool.py:340-522).

The supervisor parameter is invisible to the schema

A run() receives the supervisor through a keyword-only parameter named sup with no annotation; data_root works the same way. describe.py ignores both on purpose and publishes "supervisor": true instead (SADT-VISOR scripts/describe.py:71-81, 731-752). The missing annotation is the marker.

Documentation behind the code

Three statements about the schema in the repositories' own documents no longer hold. The header of schema_tool.py says a schema cannot express extensions, choices, a section, a label or visible_when (:28-33); all five are in _ARGUMENT_KEYS. SADT-VISOR CONTRIBUTING.md:154-169 and docs/SERVER_CONTRACT.md:41-48 speak of "six" layout keys and say options_when is not emitted; LAYOUT_KEYS has eighteen and includes it. CONTRIBUTING.md and README.md do not mention vec2, nor that every argument needs a line in Args:.

5. What deployment.toml declares

Everything specific to one deployment lives in server/deployment.toml, read once at startup. Per tool, the only keys accepted are server_selectable, max_upload_mb, data_dir, hidden, timeout_seconds, dispatch, batch and width_from (VISOR-serve server/registry/deployment.py:69-70). A value of server_selectable is model, testfile or none, with an optional scope written testfile:Sub_folder (deployment.py:53). The file is mounted into the container, so it can be newer than the server image.

The file at e9a7e5d has 292 lines and 14 [tools.X] sections:

The file is not "empty"

VISOR-serve server/README.md:540 calls deployment.toml "an empty file of comments today", and its own first lines say it "has no entries" (server/deployment.toml:1-4). It has fourteen sections. The conventions of the previous section cover the generic case; these sections are the exceptions that were needed.

6. Facades: ALI and AREG

ALI and AREG each became several engines (ALI_CBCT and ALI_IOS; AREG_CBCT, AREG_IOS and AREG_IOSCBCT), but the Slicer panel still asks for "ALI" or "AREG". A facade reconciles the two. It is not a folder and not an interpreter: folder is None and run() raises RuntimeError (VISOR-serve server/registry/facade.py:68, 80-81). Its schema is composed at startup from the dispatch table of deployment.toml: a leading mode argument, then the union of the targets' arguments, each visible only in the modes that have it, and optional unless every target requires it (facade.py:42, 98). If two targets declare the same argument with a different (type, accepts, required), the facade is skipped with a warning; it is fatal only if its name is already a served tool (facade.py:282-295).

At run time _run_tool removes mode, resolves the target (422 when the mode is missing or unknown), drops the arguments the target does not declare, and then performs an ordinary run of the target: its own validation, admission and job directory. Nothing downstream knows a facade was involved (VISOR-serve server/main.py:1888-1917). The dispatch tables are "CBCT"→AREG_CBCT, "IOS"→AREG_IOS, "IOS to CBCT"→AREG_IOSCBCT and "CBCT"→ALI_CBCT, "IOS"→ALI_IOS (server/deployment.toml:193, 210). Between them the two facades publish 11 arguments (ALI) and 31 (AREG), counted on a live instance.

Stale example in a docstring

The module docstring of facade.py:14 still shows a mode named "CBCT to IOS"; the mode that exists is "IOS to CBCT".

7. The call graph that actually exists

The calls field of each schema lists the tools named in sup.run("X", …). The matrix below is that field for the six tools that call another one, checked against the sup.run sites in SADT-VISOR tools/ (for example tools/ALI/ALI_IOS/src/sadt_ali_ios/dispatch.py:229, tools/ASO/src/sadt_aso/dispatch.py:537, tools/VFACE/src/sadt_vface/tools.py:145-359). Twelve tools call nobody; Agent calls tools too but declares none (see the callout below).

Reading it: VFACE fans out to six tools; each AREG engine calls the tools whose output it needs (CBCT segmentation, orientation, tooth numbering, landmarks); and ALI_IOS calls Crown_Seg when the mesh has no tooth labels, so Crown_Seg is reached from all three IOS-related engines (SADT-VISOR tools/ALI/ALI_IOS/src/sadt_ali_ios/dispatch.py:229). The deepest chain has four levels. A chain can go up to ten (MAX_SUPERVISOR_DEPTH), a cycle is refused by name at the first call, and a tool may appear twice on different branches (next section).

docs/TOOL_GRAPH.md is out of date

VISOR-serve docs/TOOL_GRAPH.md draws the AREG engines and ASO, marks ALI_IOS as a leaf (:27), omits VFACE, and states that the deepest real chain has three levels, AREG_IOSCBCT → ASO → ALI_CBCT (:53). In the code ALI_IOS calls Crown_Seg and the deepest chain has four levels, through VFACE. Agent is outside the graph by construction: it calls tools through supervisor.run(…), not sup.run(…), so that describe.py, which insists on a literal name, does not fail on it (SADT-VISOR tools/Agent/src/sadt_agent/execution.py:9-30, 70). The startup check therefore does not cover it; only a check at run time remains.

Stop points follow the same graph. Every called tool is a possible stop, and a stop is named by its path (ALI_CBCT or ASO/ALI_CBCT) (VISOR-serve server/registry/__init__.py:389, 425). No served tool calls declareQualityControl, so all the stop points that exist are the boundaries of calls (grep over SADT-VISOR tools/*/src). How a run stops, is corrected and resumes is on the run page.

8. What stays on the client

The client repository has 23 module folders. Fifteen of them front a server tool: AMASSS, ALI, ASO, AREG, AutoMatrix, AutoCrop3D, FlexReg, BATCHDENTALSEG, DOCShapeAXI, CLIC, CNE, VFACE, GreedyReg, SurgMovPred and Crown_Seg (Remote CMakeLists.txt:24-48). Every one of them inherits ServerToolWidgetBase, which does the common work:

  • The panel. At setup it calls GET /health then GET /tools, finds its own tool (exact name, then ignoring case and separators), and formgen turns the schema into widgets: scalars, choices, multichoices, vec2 joysticks, and file rows that accept a file or a folder. A module only declares what a schema cannot say, through FILE_INPUTS, RESULT_KIND, SCENE_INPUTS and a few hooks (Remote ServerToolsCoreLib/base_widget.py:359-368; formgen.py:1-30).
  • Packing. Before the request, each file input is packed: a file is sent as is, a folder is zipped, a node picked in the scene is exported to disk, and a hosted model or test file travels as a name only. A folder flagged by the server's batch plan is cut into lots, each a normal run (slicer_io.split_cohort, ServerToolsCoreLib/slicer_io.py:208).
  • Loading results. When the zip comes back, the module unpacks it and loads what its _LOADABLE table names into the scene (base_widget.py:1427): volumes, label maps, models, *.mrk.json markups. Some read a small report to word the final message (for example run_report.json for ALI).

Little else happens on the client, and the exceptions are those the table of the overview points out. FlexRegRemote recomputes the outline of the patch locally so the joysticks respond (about 18 ms on a 294,000-point arch; the real patch is computed on the server at Apply) and shows it as a node that is not saved in the scene (Remote FlexRegRemote/FlexRegRemote.py:14-18). The two local modules, Medical_Data_Anonymizer_ModuleRemote (text only, Presidio and spaCy) and AgentRemote (Ollama), do not import the server library at all.

MRI2CBCT is not delivered

MRI2CBCTRemote and MRI2CBCT_CLIRemote stay in the tree but have no add_subdirectory (Remote CMakeLists.txt:31-32), and the extension description says "MRI2CBCT is temporarily not shipped until it is ported to the server" (:10). SADT-VISOR has no MRI2CBCT tool. What is left is the legacy local code (slicer.cli.run, a pip_install of torch), unreachable from a built extension. See the VISOR page of MRI2CBCT and its legacy page for that code.

9. The supervisor: sup

A tool whose run() declares a keyword-only sup (no annotation) receives a supervisor object, the class _Supervisor in runner.py (VISOR-serve server/execution/runner.py:1140, 1685). It has eight members:

MemberWhat it isLine
run(tool, **params)runs another tool, blocking, and returns what its run() returnedrunner.py:1808
outthe job's output/ directory:1785
tmpscratch under the job, removed with it:1789
datapaththe read-only DATA root, so a tool can name a neighbour's model folder; None if the deployment publishes none:1804
channels(wanted)how many parallel workers the budget affords this run:2134
declareQualityControl(name)declares a stop point:2214
progress(fraction, message)writes a progress line:2235
log(message)writes to the job log:2242

Nesting. sup.run re-enters runner.py with the sibling's interpreter, as a subprocess of the parent: no new HTTP request, no new admission. The call's folder is <job>/sup/NN_<tool>/ with a two-digit counter, and its output_dir is imposed, never the parent's, otherwise keep_intermediate would find nothing to copy (runner.py:1808-1840). A call to a tool that is already running above it is refused by name, listing the chain; the backstop is MAX_SUPERVISOR_DEPTH = 10 (runner.py:196, 1810-1818). The same tool on two different branches is not a cycle.

Deadline. When a timeout is configured, the server converts it into an absolute monotonic instant, passed down as SADT_SUPERVISOR_DEADLINE; each level gives its child only what remains (VISOR-serve server/execution/dispatch.py:552-561; runner.py:201). With no timeout configured, which is the default, there is no deadline.

Process group. The top-level process starts with start_new_session=True and its group id is written to disk. A nested call does not start a new session: it inherits the group, so the server's SIGTERM on cancellation reaches every level (server/execution/dispatch.py:649, 713-745; runner.py:2063).

The documents count the members wrong

The docstring of the class says "six members" (runner.py:1686), VISOR-serve docs/INTERNALS.md:80 says "five members, frozen" and server/README.md:652 "five members", and SADT-VISOR scripts/run_tool.py implements a local supervisor with five (run, out, tmp, progress, log; run_tool.py:300-364) that has no cycle check, no depth limit and no declareQualityControl. The server has eight, listed above. server/README.md:660 also says "five deep is the backstop"; the constant is 10.
