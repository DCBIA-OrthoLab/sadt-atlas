AREG_IOS with VISOR

What changes when you run AREG_IOS through a VISOR server from 3D Slicer: what to provide, what is the same, what is different. The legacy module has its own page.

VISOR Legacy page Atlas (VISOR)

AREG_IOS registers a follow-up intraoral scan (T2) onto the baseline scan (T1) of the same patient, on a patch that treatment does not move: the palate, or a band along the mucogingival line. With VISOR the registration is computed on a server, including the network that predicts the palatal patch: in Slicer you fill a form, send the folders and get the results back. This page was written from the VISOR code (SADT-VISOR 6ba2a78, VISOR-serve e9a7e5d, AutomatedDentalToolsRemote 19b95e8); the details are on the Atlas page.

What changes in the panel

  • Open AREG Remote (category “Automated Dental Tools Remote”) and pick IOS in the first field, Mode.
  • Automation: Fully-Automated (the default) labels the teeth and orients the scans on the server; Semi-Automated expects scans that already carry tooth labels and a common orientation.
  • Registration patch replaces the two modes of the legacy module: Palate (upper arch) predicts the palatal patch and registers the upper arch, the lower arch following; Mucogingival line (lower arch) registers the lower arch alone.
  • No model to download and no graphics card needed on your machine. The patch model, the orientation reference and the crown model are chosen by the server, and their fields are hidden.
  • For the mucogingival patch, Mucogingival landmarks (your own 13 landmarks per lower scan, optional: otherwise the server predicts them) and Patch height (mm).

What you provide

  • T1 and T2: one folder each, or the hosted test cohorts. Formats .vtk .vtp .stl .obj. Because the two time points are two folders, the file names no longer have to contain T1 or T2.
  • Each mesh must still say its arch in its name, as a separate word (U, Upper, Maxilla, L, Lower, Mandible…). A mesh that does not is reported and left out, not guessed. The arch is read from the file name only, so the folder names no longer matter.
  • The patient is recognised from the sub-folder path plus the rest of the name, which must match between T1 and T2.

What stays the same

A rigid ICP on a stable patch, the same two patches, and the other arch carried along by the palatal registration. Your inputs are not modified.

What is different in the results

  • A transform file (.tfm) is written for every patient, in both modes and for both patches. When the server oriented your scans first, the transform is composed with that orientation so that it refers to the scans you sent.
  • The output keeps your folder structure. With the palate patch it also holds the lower arch of each time point, moved with the upper one; with the mucogingival patch only the lower arch comes back. AREG_report.json lists for each patient what was done. A failed canonical orientation of the palatal patch is written there as a note, instead of only in a log.
  • The mucogingival band is built without three refinements of the legacy module (the filter on doubtful landmarks, the restriction to landmarks present at both time points, and the landmark-based start of the ICP), and it excludes lower teeth 18 to 31 where the legacy excluded 17 to 32. Compare a few cases before mixing legacy and VISOR results in one study.
  • The palatal network runs on the server's GPU, or on its CPU when it has none.
Type a patch height for the mucogingival patch

The field Patch height (mm) starts at 0, and 0 does not mean “use the default”: it means no band at all, so the registration uses only about 13 landmark points. The legacy module started at 5 mm. Type a height (5 is the engine's own default) before you press Apply. There is no maximum, so keep it within the attached gingiva. The value used is written in the report. Observed by calling the VISOR tool: a run without a height reaches the engine with 0.
