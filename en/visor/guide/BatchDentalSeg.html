BatchDentalSeg with VISOR

What changes when you run BatchDentalSeg through a VISOR server from 3D Slicer: what to provide, what is the same, what is different. The legacy module has its own page.

VISOR Legacy page Atlas (VISOR)

Through VISOR, the module is BatchDentalSegmentator Remote: the segmentation runs on a server. Using VISOR explains how to connect Slicer to a server; this page covers what is specific to BatchDentalSeg.

What changes in the panel

  • No extension to install, no weights to download, no memory settings: the computation and the memory are the server's. The auto-crop, the "Free memory" button, the UniversalLab left/right correction button and the saved queue do not exist in the remote module.
  • The model is picked from the list of models hosted on the server. The names are DentalSegmentator, PediatricDentalSeg, NasoMaxillaDentSeg and UniversalLab; you cannot send your own weights.
  • Input: one scan or a folder, or a test file the server hosts. A folder is searched recursively and may contain NRRD, NIfTI or GIPL files. A big cohort is cut into batches by the panel (by default at most 400 MB or 25 files per batch).
  • Output formats are chips: NIFTI (the label volume), STL, OBJ, VTK (one mesh per structure) and VTK (merged) (one mesh with a Label value per cell). At least one must be selected. glTF is no longer offered. "One binary file per structure" works only together with NIFTI.
  • Hidden: the device, GPU resampling, tile overlap and mesh reduction. The panel always asks for the GPU with the defaults (the tool falls back to the CPU, with a warning, if the server has no card).

What stays the same

The four models, their structures and their label numbers, a single fold with no ensemble, no morphological cleanup of the network's output, and the result placed back on the original grid of your scan.

What is different in the results

  • The label volume is named <scan>_Seg plus the extension (the identifier is editable), not <scan>_Segmentation.nii.gz, and the extension is compressed (.nii comes back as .nii.gz, .gipl as .gipl.gz).
  • The label volume is no longer always written: it is only there if NIFTI is selected.
  • A BatchDentalSeg_report.json accompanies the results. It lists each scan (case_0000, ... in order, not by patient name), whether it worked, and the table of label numbers for the model.
  • A scan that cannot be read is reported as failed and the others are still segmented.
  • Meshes are built differently from the legacy ones: by default the VISOR mesh is smoothed with 30 iterations and not reduced, where the legacy VTK was smoothed with 60 iterations and reduced by 40 %. Do not expect files identical to the legacy ones.
  • The panel loads at most 12 results into the scene. Label volumes are loaded as plain label maps; the report is not used to name or color the segments.
A scan named ..._Seg inside a folder is ignored

With the default identifier, a file such as patient_Seg.nii.gz found in a folder is taken for an earlier result and skipped, with no message. Rename it, or select that file on its own: a single file is always processed. (Reference: SADT-VISOR sadt_batchdentalseg/pipeline.py:72-107.)

Resampling on the GPU

By default the server resamples the scan on the GPU, which changes the numbers very slightly compared with nnU-Net's own resampling. The report field gpu_resampling says whether it was requested on a GPU. Because the setting is hidden in the panel, ask the server administrator if you need the exact nnU-Net pipeline.
