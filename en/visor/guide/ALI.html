ALI with VISOR

What changes when you run ALI through a VISOR server from 3D Slicer: what to provide, what is the same, what is different. The legacy module has its own page.

VISOR Legacy page Atlas (VISOR)

Through a VISOR server the analysis runs on the server, not on your computer. The module in Slicer is called ALIRemote. It is a panel that sends your scans to the server and brings back the landmark files. How to connect and what the server does with your data is in Using VISOR; this page is only what changes for ALI compared with the legacy module. It is written from the code of the server and of the panel, not from a session on a live server. The details, with the code references, are in ALI on VISOR.

What changes in the panel

  • One window, a choice at the top. The first field is the Mode, CBCT or IOS. It plays the role of the data type in the legacy window. The list of points that follows changes with it (119 points for a CBCT, 153 for an intraoral scan).
  • No models to download. The trained weights are kept on the server. The model, the device and the search settings are not shown in the panel.
  • The input. A file or a folder. A folder is zipped and sent for you. The panel can also offer the test files the server hosts.
  • The points are picked in tabs, one tab per group. If you tick nothing, the CBCT run places all 119.
  • The result comes back as an archive. The panel unpacks it, saves it to the folder you chose and, with the box "Load the predicted landmarks into the scene" ticked (the default), loads the files in Slicer.

What stays the same

The landmark names, the two ways of working (a volume walked by an agent, a surface photographed from several sides), the .mrk.json format, and your original files left untouched. The points still arrive locked, as the legacy files did: unlock a point in the Markups module before moving it.

What is different in the files and in the results

  • One file per scan with all the groups together, named <scan>_lm_Pred.mrk.json, where the legacy module wrote one file per group (CBCT) or per jaw and per network (IOS). The folder layout of your input is reproduced in the result.
  • A report comes with it: run_report.json lists, scan by scan, the points placed and the points that did not converge.
  • Supported intraoral formats are .vtk and .stl. Meshes that already carry tooth numbers are processed first; a mesh without them goes through the server's crown segmentation (Crown_Seg), then follows.
  • The landmark files show up when loaded. The legacy files were written with their display switched off, so opening one directly showed nothing; the server's files are written visible.
  • Intraoral results are not identical to the legacy ones. On the mesh the developers compared, 54 of 73 points came out exactly the same and the others fell on the correct tooth (VISOR README, SADT-VISOR tools/ALI/README.md:213-226). The mucogingival points go through fewer correction steps than in the latest legacy module.
  • DICOM. The server converts a DICOM series itself, nothing is written in your folder.
  • Time. The server notes 128 s for 119 landmarks on one scan with 8 agents at once on an RTX 6000 Ada card (a measure written in the server's configuration, not rerun here). The server's default configuration sets no time limit on a run.
The end-of-run message says "0 scan(s), 0 landmark(s) written"

Whatever happened. The panel looks for the list of scans under a name that the server no longer uses (ALIRemote.py:216 in AutomatedDentalToolsRemote 19b95e8, against cases in the server report). Read the files that were loaded and the run_report.json in the result folder instead; the failures are listed there, and the panel message never lists them.

Choosing the folder of a single DICOM series

If you point to the folder that holds exactly one DICOM series, the result file is named ._lm_Pred.mrk.json, a hidden file, and will not show in a normal file listing. Put the series in a sub-folder of the folder you choose, or show hidden files. The cause was checked in the code (the two naming functions were run); a full run on a real series was not repeated.

CBCT stored in another orientation

The legacy module turns every CBCT to a standard orientation (LPS) before the search. The server version does not. The effect on the placed points has not been measured, so look at the landmarks on the scan before using them, particularly if your volume does not come from a DICOM export.
