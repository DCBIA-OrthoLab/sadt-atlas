DOCShapeAXI with VISOR

What changes when you run DOCShapeAXI through a VISOR server from 3D Slicer: what to provide, what is the same, what is different. The legacy module has its own page.

VISOR Legacy page Atlas (VISOR)

With a VISOR server the classification and the explainability maps are computed on the server, and the DOCShapeAXI panel is a form that sends your meshes there. Details of the code are on the Atlas page; connecting and running in general are in Using VISOR. Your meshes are uploaded: what protects them is on Security and privacy in VISOR.

What changes in the panel

  • There is no data-type list any more. You pick a checkpoint by its file name, and the name decides the anatomy, the task and the number of classes: condyles_4_class.ckpt (condyle, 4 stages), cleft_4_class.ckpt (cleft bone defect, 4 stages), and for the airway airways_2_class.ckpt (obstruction yes or no), airways_4_class.ckpt (4 stages) and airways_4_regress.ckpt (a continuous ratio).
  • For the airway, the three results are no longer chained in one run: one run gives one checkpoint, so you run it once per checkpoint you want.
  • Nothing is installed or downloaded in Slicer: the checkpoints are on the server.
  • You provide a .vtk surface or a folder of them (subfolders are searched).
  • A switch turns the explainability maps on or off. Off, you only get the report with the predictions, no surfaces, several times faster. On by default.
  • No test surface is hosted for this tool, because nothing public is an airway, a condyle or a cleft.

What is different in the results

  • There is no csv. The predictions are in DOCShapeAXI_report.json: for each surface, the path relative to your input and either a class (an integer) or, for the ratio, a score. The report also names the anatomy, the task, the number of classes and the network.
  • The meshes carrying the explainability maps are written directly in the output folder, with the suffix _pred added to their names, not in an explainability subfolder. The panel can load up to 12 of them into the scene when the run ends. The maps are read as in the legacy guide, Reading the result.
  • Still true: no confidence score, the map describes only the multi-view branch, and nothing is seeded, so two runs can differ.
  • The status bar line built by the panel may show "?" where the anatomy and the checkpoint should be. The information is in the report.
Give each surface a distinct file name

Surfaces are searched in subfolders but the results are written side by side. Two files called surface.vtk in different subfolders are written to the same place: one replaces the other, and the run is then likely to stop with an error after all the computation is done. This is deduced from the code, not tested.

A new server may refuse its first run

The network needs a small image-model file (an EfficientNet backbone) that the tool will not download in the middle of a request. If it has not been put in place on the server, the run fails after your meshes have been uploaded, with a message naming the missing file. That is a server setup problem: send the message to whoever runs the server.
