GreedyReg with VISOR

What changes when you run GreedyReg through a VISOR server from 3D Slicer: what to provide, what is the same, what is different. The legacy module has its own page.

VISOR Legacy page Atlas (VISOR)

Through a VISOR server the module is called GreedyReg Remote. You choose two folders in Slicer; they are sent to the server, which pairs the scans by patient, registers each T2 onto its T1 with Greedy, and sends the results back to a folder you choose. Nothing is installed or downloaded on your computer, and there is no Greedy binary to fetch. The panel is built from what the server publishes. Only part of the legacy module exists there: the folder-to-folder Greedy registration. There is no Manual Alignment, no Distant Registration and no mask creation in the scene. The module's own help text still mentions landmark modes; the server tool does not have them.

What you provide

  • T1 and T2: one folder of scans for each timepoint (T1 is the fixed image, T2 the moving one). A folder must hold a single timepoint. Patients are paired by name up to the timepoint word, so P1_T1_scan.nii.gz pairs with P1_T2.nii.gz, and names no longer need to start with letters then digits (01_T1.nii.gz and Patient-01.nii.gz are read as 01 and Patient_01). Sub-folders are searched. Scans can be .nii.gz, .nii, .nrrd, .gipl or .gipl.gz; avoid .nrrd.gz, which is found but has no ITK reader.
  • Advanced, optional: masks (one per patient; the metric is computed inside it; it must be in the space of T1, and nothing checks that) and initial transforms (one .mat per patient, for scans too far apart for the search; otherwise the search starts from the identity).
  • Options: metric NCC (default), NMI or SSD; transform Rigid (default, 6 degrees of freedom) or Affine (12); output suffix (registered by default). Then an output folder.

What stays the same

  • The same Greedy command and the same resampling of T2 into the T1 grid. A multi-segment mask is still flattened (any value above zero), and an identity start is still nudged by a thousandth of a unit so Greedy does not read it as "no initialisation".
  • The matrix produced is in Greedy's own format, not a Slicer transform. AutoMatrix on VISOR accepts this plain 4x4 file, but takes the matrix as written, with no conversion: check the result before relying on it.
  • Each Greedy call is limited to 10 minutes, as before.

What is different

  • Results go to the output folder you choose, never into the T2 folder: <patient>_registered.nii.gz (with the default suffix), <patient>_transform.mat and GreedyReg_report.json. The input sub-folder layout is kept. If a folder holds both a patient's scan and an earlier result for that patient, the scan is used.
  • The report lists patients present in one folder only, masks and initial transforms that matched nobody, and for each patient status and, if it failed, the reason.
  • A failing patient does not stop the others. If none is registered the run ends with an error and no report.
  • Defaults: the metric is NCC, where the legacy panel started on NMI.
  • The Slicer panel loads up to 12 registered volumes into the scene, with the CT-AAA rendering preset; it does not load the .mat files.
Give two folders, even for one pair

The client says that two files make one pair, but the pairing walks folders: tested on 2026-11-09 with a/P1_T1.nii.gz and b/P1_T2.nii.gz, nothing was paired, and the tool's error is "No patient appears in both the T1 and the T2 folder". Put each scan in its own folder. A test through a server was not made.

The hosted test cohort: pick its T1 and T2 sub-folders

The test file a server offers for GreedyReg, CBCT_T1_T2_pair, holds a T1 and a T2 folder. Given as a whole for T1 and T2, it is refused ("The T1 folder holds scans from more than one timepoint"); its T1 and T2 sub-folders pair. Checked on 2026-11-09 on the file names of a staged copy; whether the panel lets you pick a sub-folder of a hosted file was not checked. The masks and initial-transform rows offer hosted test files too: give your own.

The final status line is not reliable

When the run ends, Slicer shows "GreedyReg finished in ? mode: N pair(s) registered." The report has no mode, and N counts failed patients too. Read GreedyReg_report.json (summary.registered and summary.failed) instead.

A slow pair fails after ten minutes per step

A registration is two Greedy steps and each is cut at 600 s, so one pair can take up to twenty minutes. The server sets no limit on the whole run. A pair cut short appears as failed in the report with the exception text as its reason.
