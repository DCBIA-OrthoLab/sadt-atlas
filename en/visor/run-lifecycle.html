A run, step by step

What happens between a click in Slicer and the files coming back: the routes the server exposes, the fifteen stages one POST /run/{tool} goes through, the phases a watcher sees, how a run is admitted, detached, cancelled, paused and rewound, and which HTTP status each failure ends in. Every claim cites the line it was read from.

VISOR-serve e9a7e5d implemented, 857 test functions in server/tests read on 2026-11-09 Architecture Deployment Security
Note

This page describes VISOR, the server generation, not the legacy Slicer code that the rest of this site documents. Citations are file:line followed by the repository: VISOR-serve at commit e9a7e5d (lines of server/main.py unless a path is given), AutomatedDentalToolsRemote (the Slicer client) at 19b95e8, SADT-VISOR (the tools) at 6ba2a78. The repositories carry their own documentation, and several pages of it are older than the code; where the two disagree this page follows the code and says so in a callout. What the transport and the stored data are protected by is on the security page; how the pieces fit is on the architecture page.

1. The routes

Eighteen route handlers are declared in main.py, and two of them answer without a token. The decorators are the only authority: docs/ARCHITECTURE.md:34-42 lists five, server/README.md:49 onward lists more but not all. “Gate” in the table is the maintenance.require_accepting dependency: while an operator has closed the door with POST /maintenance, the route answers 503 with Retry-After: 10 (wire/maintenance.py:113-146). Reads, cancellation and deletion are deliberately not gated, so a run that is already going can always be watched and collected.

2. The happy path, from submission to cleanup

One run, on the blocking path (the client keeps one HTTP request open for the whole run). The detached variant is in section 4. The three columns of the diagram are three different processes: the Slicer module, the FastAPI process, and a separate Python interpreter that belongs to the tool.

  1. Upload by parts. The client sends large inputs through POST /uploads and PUT /uploads/{id}/parts/{n}: parts of 8 MB by default, clamped by the server to 1–64 MB (wire/transfer.py:204-215), four connections in parallel, a SHA-256 of each part in X-Part-SHA256, up to four tries per part (AutomatedDentalToolsRemote ServerToolsCoreLib/transfer.py:62-67, 309). On the blocking path a file below two parts, 16 MB, goes inline in the form instead; on the detached path, the client's default, every file goes through /uploads (client client.py:1106-1121). On the server the session lives on disk, the blob is pre-sized with os.truncate and each part is written at its offset with os.pwrite: nothing is reassembled, and at run time the blob is renamed into the work directory rather than copied (claim_upload, wire/transfer.py:279).
  2. The run is registered before the form is read. run_tool (main.py:1806) takes X-Run-Id and opens the run directory first, because the client opens its event stream from another thread and the two cannot be ordered. A malformed id is 400, a taken one 409 (wire/runs.py:178-213).
  3. Tool and mode. _run_tool (main.py:1833) resolves the tool (404 if unknown), reads the form, unpacks __uploads__. If the tool is a facade (ALI, AREG), it removes the mode field, replaces the facade by its target and drops any argument the target does not declare; a missing or unknown mode is 422 (main.py:1888-1917).
  4. Staging. Each input is written to TEMP_DIR/<mkdtemp>/<argument>/<safe name>.<ext>. The patient's file name is kept, filtered to [A-Za-z0-9_.-] (_safe_stem, main.py:1105), and the phase is staging with the message “input k of n”, never the file name. Refused here: an unknown argument (422), a file sent to a scalar argument (400), a forbidden extension (400), a size over the limit (413), an empty file or a truncated .gz (400, _reject_a_truncated_gzip, :1172). A .zip given to a path argument is extracted by the server, with zip-slip, absolute members and symbolic links refused and a 2000 MB ceiling on the extracted size (file_utils.py:125, config.py:241).
  5. Hosted files. A model or test file chosen by name is resolved through the data store (404 if absent). DATA_DIR is read-only, so an archive for a folder argument is extracted into the work directory.
  6. Validation, off the event loop. tool.invoke runs in a worker thread under a CapacityLimiter of MAX_CONCURRENT_TOOLS (4; main.py:183-187, :2081-2083). SchemaTool.invoke validates against the published schema (422 on ToolArgumentError), turns multichoice fields into lists and calls dispatch.dispatch.
  7. Dispatch. dispatch (execution/dispatch.py:1080) checks that the tool has an interpreter, creates TEMP_DIR/job_<uuid>/{input,output}, completes the parameters (output_dir is always the job's own, device is injected from the settings, an unnamed model argument receives the tool's models folder), writes job.json and computes the timeout: deployment_config.timeout_seconds(tool.name) or None (dispatch.py:1137).
  8. Admission. The run asks for room in a budget of bytes and cores (section 5). If it has to wait, the phase becomes queued_gpu, once; the client can still cancel.
  9. The tool starts. Popen([venv/python, runner.py, --job job.json]) with stdout and stderr to files, cwd the job directory and start_new_session=True (dispatch.py:618). The environment is the server's, without API_TOKEN, with thread caps (OMP_NUM_THREADS, MKL_, OPENBLAS_, NUMEXPR_, VECLIB_, ITK_GLOBAL_DEFAULT_NUMBER_OF_THREADS) and the variables SADT_API, SADT_JOB_ID, SADT_JOB_DIR, SADT_PROGRESS_FILE and SADT_SUPERVISOR_DEADLINE (_child_environment, dispatch.py:540). The process-group id is written to disk; the phase is running.
  10. The runner. runner.py is executed by the tool's own interpreter, uses only the standard library (Python 3.9 to 3.13), imports the single package under the tool's src/, converts arguments by annotation, calls run(), samples peak VRAM, RSS and cores with _TreeSampler (runner.py:405) and writes result.json atomically: {"result", "peak_vram_bytes", "peak_rss_bytes", "peak_cpu_cores", "channels", "vram_source"} or {"error": {"type", "message"}}.
  11. The result is read. No result.json after exit code 0 is a ToolExecutionError; an error becomes a ToolFailure(type, message). The measurements feed the cost table and an event carrying measured.
  12. Packaging. _finish_run (main.py:2200) sets the phase packaging. An output that is files becomes a zip named {tool}_{stem}.zip at compression level 1, members that are already compressed (.gz, .zip, .xlsx and the like) being stored (file_utils.py:199-251, config.py:252). A text output is answered as {"result": ...}.
  13. Delivery. Two ways. By default the file is streamed with FileResponse and removed in a background task after the response. If the client sent X-Result-Delivery: reference and the file is at least RESULT_REFERENCE_MIN_MB (16; config.py:249), the file is moved (renamed) into the result store and the answer is {"result_ref": {result_id, filename, media_type, size}} (wire/transfer.py:325-349); the client then fetches GET /results/{id} with Range, four connections, checks the CRC of every zip member, and finishes with DELETE /results/{id} (client client.py:1696-1773).
  14. The run record. _tracked_run (main.py:1610) writes done and schedules runs.discard as a background task, so the directory outlives the end of the stream.
  15. Cleanup. Staged inputs go in the finally of _run_tool; the work directory and outputs in background tasks after the stream; any error discards immediately. Results and unfinished uploads are swept by a reaper every 60 s once idle for 900 s (config.py:245-246, _reaper_loop main.py:63-81). The server log records endpoint, tool, status, duration and size, and never file content, argument values or progress messages (_log_served, main.py:351-371).
Verified

The process model is the point of the design: the server never imports a tool. SchemaTool.invoke always goes through dispatch (registry/schema_tool.py:812-822) and SchemaTool.run raises RuntimeError (:840-844). Only the two fixtures, Example_Tool and Test_Tool, are imported in-process. The tool's interpreter, torch and VRAM therefore disappear with the process when the run ends.

3. Phases, states and the event stream

A run has a phase (what it is doing) and a state (what a watcher should conclude). Phases are received, staging, queued_gpu, running, packaging, done, failed, cancelled, paused (wire/runs.py:73-81). States are pending (received, staging, queued_gpu), running (running, packaging), done, failed, cancelled (the three terminal ones) and paused, which is not terminal (:83-93).

GET /runs/{id}/events is a Server-Sent Events stream. It starts at the first event, including those written before the watcher connected, because the watcher is opened from a second thread and cannot be ordered against the POST (main.py:1004-1048). The file is polled every 0.25 s from a worker thread (RUN_EVENT_POLL_SECONDS, config.py:275) and each frame is data: {json}. The stream ends on a terminal event, or when the run directory has disappeared.

An event is {seq, at, state, phase, fraction, message, depth}, plus tool (the name of a nested call, [A-Za-z0-9_-]{1,64}), result (only ever written by the server) and measured (vram_bytes, ram_bytes, cpu_cores, channels) (_normalised, wire/runs.py:473-539). seq is the line number at read time and is never stored. message is cut to 200 characters with no line break. A line written by a tool is always read as running: only the server can declare done, failed or cancelled.

On disk, TEMP_DIR/runs/<run_id>/ holds events.jsonl, meta.json, pgid, cancel and, when stopped, paused.json. Appends take no lock: each record is a single write() under MAX_RECORD_BYTES (4096), atomic with O_APPEND on POSIX (wire/runs.py:137). The stream is capped at MAX_RUN_EVENTS = 2000 events; past the cap one “not reported” event is delivered and nothing more, terminal events never being cut (_capped, wire/runs.py:611-635).

Progress from a tool. A tool reports progress by appending {"fraction": ..., "message": ...} to the file named by SADT_PROGRESS_FILE; sup.progress(fraction, message) writes to the same file (runner._append_progress, runner.py:1058). The fraction is a number between 0 and 1 or absent, and the client does not invent one.

Pitfall

After a failure the run directory is removed at once: _tracked_run writes failed and calls runs.discard in the same breath (main.py:1636-1642). A watcher that had not yet read the terminal event then finds the directory gone, and its stream just ends: EventReader.read sets finished on the missing file and returns nothing (wire/runs.py:567-578). The failure itself is still reported by the POST. After a success the directory survives the end of the response.

4. Detached mode

With X-Run-Delivery: detached the server answers 202 as soon as the inputs are staged, and the run continues as a background task; its terminal event carries the result_ref (_detach main.py:1401, _detached_run :1354). It requires X-Run-Id (otherwise 400) and refuses any file in the body (400): every input must have arrived through /uploads. The run directory is not deleted at the end, because the client has not yet read the terminal event; it expires after RUN_TTL_SECONDS = 900 s of inactivity, refreshed on each read (config.py:263).

The reason is a timeout. The comment above the header says it plainly: the Slicer client's POST read timeout is 600 s with a ceiling of one hour, the server is sized for cohorts that take longer, and a disconnect never stopped a run, it only discarded the answer (main.py:157-160). Detached, the client holds no long request: it waits on the event stream, which reconnects and de-duplicates on seq. The client turns it on by default (DETACHED_RUNS = True, config.py:90 of the Remote extension) and falls back to the blocking path when it asks for stop_after, because the checkpoint record is delivered in the POST body only (client.py:1094-1106).

Defect confirmed in the code

main.py:2332 raises ToolExecutionError, a name that main.py never imports: the module imports dispatch and uses dispatch.ToolFailure and dispatch.RunCancelled by attribute (the only occurrence of the bare name in the file is that raise). The branch is “detached run, and storing the result by reference failed with OSError”. It raises a NameError instead of the intended message, so the failure report would be wrong. The branch is rare, and no test was run against it for this page.

5. Admission: a budget, not a counter

A run does not take a slot, it reserves room. The admission code in execution/admission.py keeps a Budget (:239) of bytes of RAM, bytes of VRAM and cores, and a queue of runs waiting for room in it.

  • FIFO per process. Tickets are served in order; only the run at the head can be admitted. The module states the trade: head-of-line blocking in return for a predictable order (admission.py:239-251). reserve(candidates) tries shapes of decreasing width and takes the first that fits (:446-530).
  • Three safety rules. A tool whose cost has never been measured reserves the whole budget and runs alone. A request larger than the budget still runs, alone, when the machine is empty. The memory actually free on the card is also checked (admission.py:22-33). A safety margin of 1.3 is applied (SAFETY_MARGIN, :49).
  • Where the budget comes from. resources.py reads the cgroup (v2, then v1) before the kernel, and nvidia-smi for free VRAM. The share is SADT_RESOURCE_SHARE = 0.75 (config.py:219); the budget is cut into per-job shares by SADT_EXPECTED_CLIENTS = 4 (config.py:234); SADT_CPU_BUDGET, SADT_RAM_BUDGET, SADT_VRAM_BUDGET and the *_PER_JOB forms override them and accept values such as 75%, 8 or 16GB (config.py:213-237). Expected clients is a declaration: there is one shared token and no client identity, so the server cannot count workstations.
  • A floor on cores. SADT_MIN_CPUS_PER_JOB = 4 (config.py:161): below it a run waits rather than being admitted starved.
  • GPU or not. A run is assumed to want the card unless it declares a device that resolves to cpu or mps (dispatch.uses_the_gpu, :95).
  • Learned costs. execution/costs.py keeps the maximum of the last COST_WINDOW = 20 runs of each tool, per resource, and fits a line fixed + marginal × width as soon as two distinct widths have been seen (_fit :429, _predict :404). “Measured at 0” and “never measured” are distinct (vram_known). A reading of the whole card is learned only from a run that was alone (dispatch._keep_measurements, :826-914). The table lives in SCHEMA_CACHE_DIR.
  • Width and channels. A tool that declares num_workers or batch_size (CHANNEL_ARGUMENTS, concurrency.py:145) can run several items at once; width_from in deployment.toml says which argument to count. The tool asks sup.channels(wanted) and is given min(affordable, wanted, SADT_CHANNELS, ceiling), never below 1 (runner.py:2134). SADT_MAX_CHANNELS = 0 means no ceiling (config.py:130). A run that opens only one channel keeps its whole reservation.
  • Memory retries. If a run dies of out-of-memory (OutOfMemoryError, CudaOutOfMemoryError, MemoryError, or SIGKILL without a result.json, _out_of_memory dispatch.py:933) it is started again, up to MEMORY_RETRIES = 2 times, with the reservation multiplied by MEMORY_RETRY_GROWTH = 1.5 each time, unless it already holds the whole machine. The job is reset and a queued_gpu event reads “out of memory; waiting for more room (try N)” (dispatch.py:1158-1228). This is what makes the 20-run window safe: a peak that has aged out of the window is recovered by the retry.
  • Nested calls skip admission. A tool called with sup.run is a subprocess of its parent, which holds the reservation. The byte budget is therefore divided downward among the channels of each level (concurrency.child_budget, runner._child_channel_budget :1493).
  • The queue is per process. The singleton is created by budget() (admission.py:541-553) behind a threading.Condition: uvicorn --workers N would create N budgets. The image starts one worker (docker/Dockerfile:232).
  • Two limits stack. The CapacityLimiter (4 threads) counts admission waits; the budget counts bytes. A fifth concurrent run waits before it is visible as queued_gpu.

A tool runs other tools through the supervisor, the sup object a run() receives when it declares a keyword-only parameter named sup with no annotation (_takes_supervisor, runner.py:1140; class _Supervisor, :1685). sup.run(tool, **params) re-enters runner.py with the sibling's interpreter, in the same process group: no HTTP call, no new admission. The sibling runs in <job>/sup/NN_<tool>/ with its own forced output_dir (runner.py:1808-1963). A tool already running above the caller is refused by name, listing the chain; the backstop is MAX_SUPERVISOR_DEPTH = 10 (runner.py:196). The deepest chain actually declared by the served tools is four levels, VFACE → AREG_CBCT → ASO → ALI_CBCT.

Pitfall

Stale documentation about the supervisor. The supervisor has eight members: run (runner.py:1808), out (:1785), tmp (:1789), datapath (:1804), channels (:2134), declareQualityControl (:2214), progress (:2235) and log (:2242). docs/INTERNALS.md:80 says “five members, frozen”, server/README.md:652 “five members”, and server/README.md:660 calls five levels the backstop where the code says ten.

Pitfall

MAX_CONCURRENT_GPU_JOBS no longer exists in config.py: the admission module says it “counted jobs, and a count cannot describe a card” (admission.py:3) and server/README.md:693 says so. It is still described as a working setting by MIGRATING_A_TOOL.md:104, RUN_PROGRESS.md:173, benchmarks/README.md:154, CLAUDE.md:467 and the client's ServerToolsCoreLib/config.py:36 (AutomatedDentalToolsRemote). The published benchmarks were measured with it set to 1; see the benchmark section.

6. Cancellation and timeouts

Cancel. DELETE /runs/{id} (main.py:1050) does two things because neither covers the whole window. It writes the cancel marker, which is seen during staging and while waiting for admission; and, if a process-group id has been recorded, it sends SIGTERM to the group (dispatch.kill_process_group, :745, which refuses a pgid of 1 or less), which is what stops a two-hour nnU-Net. The worker that holds the process handle polls the marker every RUN_CANCEL_POLL_SECONDS = 1.0 s (config.py:278) and applies TERM, then KILL after 10 s (_KILL_GRACE_SECONDS, dispatch.py:63; _kill_group :713). The blocked POST answers 499. A nested call shares its parent's process group, so one TERM reaches every level. Because the pgid goes through the disk, a cancel works from another worker process.

Timeouts. A run has no timeout by default. TOOL_TIMEOUT_SECONDS = 0 (config.py:77) and no section of server/deployment.toml sets timeout_seconds. When one is set, per tool in deployment.toml or globally, it is converted to an absolute monotonic instant passed down as SADT_SUPERVISOR_DEADLINE (dispatch.py:552-561), and each nested level gives its child only what is left (runner._remaining_seconds, :1726). On expiry the run ends with a ToolExecutionError that names both settings, and the answer is 500. The repository advises an orchestrating tool to be given at least 1.2 times the sum of the timeouts of the tools it calls (docs/INTERNALS.md:112, server/deployment.toml.example:86).

A run that hangs keeps its reservation until it is cancelled. The comment next to the setting gives the reason for the default: “a cohort legitimately takes hours” (config.py:77).

7. Quality control: stop, review, resume, rewind

A server run can stop part-way so that a person looks at what a stage produced, corrects it, and lets the run go on. It is the server-side counterpart of the review pauses of the legacy modules (AREG_CBCT has one); the mechanism is entirely different. The tool does not know it was paused.

  1. Arming. The server adds a multichoice argument stop_after to every tool that has stop points, all unchecked, in the section “Quality control” (registry/schema_tool.py:340-500). Its options are the names of the calls the tool makes plus any declared points, qualified for nested chains such as ASO/ALI_CBCT (_stop_points, registry/__init__.py:389). The kind of each point (view, landmarks, …) is read from the callee's review_kind and published as option_kind in GET /tools (main.py:633); absent means view.
  2. The stop. The armed names reach the runner as the JSON variable SADT_STOP_AFTER (runner.py:121); each child gets only the entries that concern it. After the call, QualityControlStop (runner.py:167) is raised and caught at the top of main() (:2486); stopped.json is written (cumulative: stopped_after and passed_stops, _record_stop, :920), everything the chain produced is collected whatever keep_intermediate says, and result.json says {"quality_control": true, "stopped_after", "produced"}.
  3. The server keeps the job. It does not delete the job directory (dispatch._kept_if_paused, :1045), writes paused.json (runs.pause), sets the phase paused and answers 200 with {quality_control, stopped_after, produced, result_ref}, the outputs being a zip by reference (_finish_stopped_run, main.py:2147-2197).
  4. Review, on the client. The Remote base widget unzips the checkpoint, computes a content digest, and opens the VISU module (REVIEW_MODULE = "VISU", base_widget.py:2290, _reviewCheckpoint :2292) through open_for_review(folder, on_continue, rewind, origin) (VISU/VISU.py:491). VISU knows nothing of the server: it receives a folder and a callback. Only landmarks and registration checkpoints are editable (EDITABLE_KINDS, base_widget.py:2328); a review is saved as visu-review.json beside the data (VISULib/review.py:20). If VISU is missing or the folder is empty, the run is resumed at once rather than left paused on the server.
  5. Resume. On “Continue” the client sends back only the files whose content digest changed, one zip per step, named after the step (01_ALI_CBCT, up to four levels: 01_Mid/01_Leaf), to POST /runs/{id}/resume (main.py:1750; step name checked against _RESUME_SLOT, :1442; extension checked against what the step produced, _checked_correction :1463). The pause is cleared, the run goes through the admission queue like any other, and the tool is called again from the top: every call already made answers from its memo (memo.json, runner._memo :1965), until the sequence diverges.
  6. Rewind. POST /runs/{id}/rewind with the field to (a published step name, ALI_CBCT or ASO/ALI_CBCT) goes back to a checkpoint already passed. It starts nothing and deletes no memo: runner.rewind_to (runner.py:971) removes to and everything after it from passed_stops, so the next resume stops there again with that step's output intact. If the step wrote a case report (run_report.json), the replay is limited to the cases that were corrected, by hard links (dispatch.narrow_to_cases, :959, driven by the schema's case_input); any doubt means a full replay, slower and never wrong.

No served tool declares a point of its own with sup.declareQualityControl (searched in SADT-VISOR tools/*/src at 6ba2a78: no occurrence outside the runner). All existing stop points are call boundaries: any called tool can be a stop. A paused run lives PAUSED_RUN_TTL_SECONDS = 4 h and, at expiry, reap_expired reads paused.json to delete the job directory and the retained inputs (wire/runs.py:242-313).

Pitfall

QUALITY_CONTROL.md is behind the code on three points. It lists “rewind to an earlier stop for flagged patients” as to build (QUALITY_CONTROL.md:174); it is implemented (main.py:1685, runner.rewind_to). It says the kind of a stop is “declared; not yet read by the server” (:173); the server reads it and publishes option_kind. And its diagram shows rewind to=01_ALI_CBCT patients=[...] followed by “drop the memo of 01_ALI_CBCT and after” (:130-131); the real route takes to and files, and drops no memo.
