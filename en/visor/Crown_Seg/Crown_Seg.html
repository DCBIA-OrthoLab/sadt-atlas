Crown_Seg: tooth numbering, VISOR only

Crown_Seg writes the dental number of every tooth of an intraoral surface scan into a per-vertex array, so that the landmark and registration tools that follow can find the teeth. It has no page of its own in the legacy atlas because the legacy repository has no such tool: the work was done by an external Slicer command-line module, called from four modules. VISOR makes it a tool of its own, called by three other tools. This page explains it step by step; the details a developer needs are on the code page.

VISOR only SADT-VISOR 6ba2a78 VISOR-serve e9a7e5d Remote 19b95e8 Code (developers)

No legacy module. The legacy repository (SlicerAutomatedDentalTools at 3c67957) contains no Crown_Seg module. What it contains are calls to the CrownSegmentationcli module of the separate SlicerDentalModelSeg extension, and a small copy of the same call inside the ALI_IOS command line. The exact correspondence is in Legacy counterpart. How VISOR runs a tool on a server is described in Architecture. Evidence.

Overview: what goes in, what comes out

InOut
One intraoral surface mesh (.vtk or .stl), or a folder of them, and the tooth-numbering system to use (Universal or FDI)A copy of each mesh as .vtk with a per-vertex array of tooth numbers (Universal 1 to 32, gum 33, or the FDI equivalent), and a run_report.json that says what happened to each mesh

3. Files involved

There is no legacy file to compare with: the legacy work lived in an external extension (see Legacy counterpart). The tool is two main files: one that holds the argument defaults and the call, and a longer one that holds everything else (constants, the shapeaxi import and its repair, device choice, checkpoint search, discovery, the two branches, the call to shapeaxi and the report), plus a layout file, an errors file, and 8 test files.

In the codeThe file table with line counts and the client panel

4. The pipeline

4.1 What the tool does around the engine

  1. Checkpoint first. The weights are found before anything is created, so a refused request leaves the output folder as it found it.
  2. Discovery. One .vtk or .stl, or a folder walked recursively and sorted; nothing found is refused.
  3. Sorting. With skip segmented on (the default), each mesh is opened and only the names of its point arrays are read. If one of PredictedID, UniversalID, Universal_ID or FDI_ID is there, the mesh goes to the copy branch.
  4. Copy branch. Each labelled mesh is written as .vtk in the output folder, an .stl being converted. The labels are not touched.
  5. Segment branch. The remaining meshes are listed in a small work table, the device is resolved to the GPU or the CPU, and shapeaxi is called once for the whole list.

If shapeaxi cannot be imported, the run goes on for the copy branch and records that the engine was unavailable; a mesh that needed the network then has no output and is marked failed.

In the codeThe exact options passed to shapeaxi, the import repair and the order of the steps

4.2 Inside shapeaxi

The network is shapeaxi’s tooth segmentation network, with 34 output classes. Each surface is loaded one at a time and rendered from several views; for each pixel the network returns scores for the classes, together with the face of the mesh that the pixel shows.

That gives one label per face, and each face’s label is then given to its first vertex. The labels are then cleaned.

The cleaning removes islands first for the gum label (33), with a threshold of 500, then for every label, with 200, then closes each label with a dilation followed by an erosion, two iterations each. The result is written to a predictable path, which Crown_Seg recomputes instead of reading shapeaxi’s output, and each mesh is marked segmented if its file exists and failed otherwise.

In the codeThe network class, the data loader, the post-processing calls and the output path rule

4.3 Tooth numbering: Universal and FDI

Universal valueFDI valueTeeth
1 to 818 down to 11upper right, third molar to central incisor
9 to 1621 up to 28upper left, central incisor to third molar
17 to 2438 down to 31lower left, third molar to central incisor
25 to 3241 up to 48lower right, central incisor to third molar
33 (gum)0gum

shapeaxi writes the converted integers back under the same array name. Because the two systems share most of their range, an FDI array called Universal_ID would be read without error as other teeth: FDI 18 is the upper right third molar, Universal 18 a lower left molar. Crown_Seg therefore names the array after the numbering: left empty, the array name becomes Universal_ID or FDI_ID. Every downstream reader looks for Universal names only, so an FDI mesh is refused by ALI_IOS, ASO or AREG_IOS instead of being misread. All legacy callers asked for Universal numbers; FDI output is new in practice, and Universal remains the default.

5. What you can choose

SettingDefaultWhat it does
MeshesrequiredA file or a folder; .vtk and .stl only, folders searched recursively.
SuffixSegAdded to each output name.
Tooth numberingUniversalUniversal or FDI.
Skip segmentedonPass a mesh that already carries a label array through unchanged.

Four more settings are technical and hidden from the clinician: the model (empty means the tool’s own folder), the array name (empty follows the numbering), the device (cuda by default, falling back to the CPU with a warning when no card is visible) and the number of data-loading workers (at least 1).

Outputs. The tool returns its output folder. Two trees can appear: a mesh segmented by the network lands under a folder named after the work table, and a mesh that already carried labels is copied beside its relative path. The caller is expected to read run_report.json rather than guess. It lists, per mesh, a status (segmented, already segmented, engine unavailable or failed), the input and the produced file, plus a summary of the counts and the duration. The run as a whole fails only when no mesh at all was produced. shapeaxi prints the path of every mesh it saves, and that path carries the patient’s file name, so its output is swallowed.

8. Known problems

  • FDI numbering over a mesh that is already labelled: the copy keeps its Universal integers, while the report announces FDI. Evidence.
  • Four names recognised here, three downstream: a mesh that only has FDI_ID passes Crown_Seg and is refused by the next tool. Evidence.
  • Meshes in .vtp or .obj are invisible to Crown_Seg, although AREG_IOS accepts them. Evidence.
  • Two output trees: read the report instead of globbing. Evidence.
  • The tool graph in the server docs is out of date. Evidence.
  • Some documentation disagrees with the code (the model is said to be required, a folder name, a test count). Evidence.
  • What the tool protects: nothing is left behind by a refused request, the input is never modified, file names stay out of the logs. Evidence.
  • Reproducibility: the raw prediction is bit-identical to a reference port, the post-processed array varies from run to run. Evidence.
