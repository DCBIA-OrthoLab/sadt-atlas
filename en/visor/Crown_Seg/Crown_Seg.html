Crown_Seg: tooth numbering, VISOR only

Crown_Seg writes the dental number of every tooth of an intraoral surface scan into a per-vertex array, so that the landmark and registration tools that follow can find the teeth. It has no page of its own in the legacy atlas because the legacy repository has no such tool: the work was done by an external Slicer command-line module, called from four modules. VISOR makes it a tool of its own, called by three other tools.

VISOR only SADT-VISOR 6ba2a78 VISOR-serve e9a7e5d Remote 19b95e8
No legacy module

The legacy repository (SlicerAutomatedDentalTools at 3c67957) contains no Crown_Seg module and no file with “crown” or “dentalmodelseg” in its path (git ls-tree on that commit, observed). What it contains are calls to the CrownSegmentationcli module of the separate SlicerDentalModelSeg extension, and a small copy of the same call inside the ALI_IOS command line. The exact correspondence is in Legacy counterpart. How VISOR runs a tool on a server is described in Architecture.

Paths: SADT-VISOR cs/ is tools/Crown_Seg/src/sadt_crownseg/, ali_ios/ is tools/ALI/ALI_IOS/src/sadt_ali_ios/, and VISOR-serve paths start at server/ unless they name docs/ or scripts/. “Observed” marks what was re-run while writing this page; everything else was read in the code.

4. The pipeline

4.1 What the tool does around the engine

  1. Checkpoint first: find_checkpoint accepts a .pth file, or a folder searched recursively for a file whose name carries val-loss; none or two is a ToolInputError naming them (cs/pipeline.py:186-262). Empty model means <data_root>/Crown_Seg/models (cs/__init__.py:18-29,104). This happens before anything is created (cs/pipeline.py:407-413).
  2. Discovery: one .vtk or .stl, or a folder walked recursively and sorted; nothing found is a 422 (cs/pipeline.py:292-320). The input root, used to mirror the tree, is the folder or the single file's parent (:323-330).
  3. Sorting: with skip_segmented (default true), is_segmented opens each mesh and reads only the names of its point arrays; any of PredictedID, UniversalID, Universal_ID, FDI_ID sends it to the copy branch (cs/pipeline.py:56,267-289,449-451).
  4. Copy branch: each labelled mesh is written as .vtk polydata to <output>/<relative folder>/<base>_<suffix>.vtk, an .stl being converted (cs/pipeline.py:480-487,594-613). The labels are not touched.
  5. Segment branch: the remaining paths go into .crownseg_work/crownseg_input.csv under a surf header, the device is resolved to cuda:0 or cpu (:170-178), and shapeaxi is called once for the whole list with this namespace (cs/pipeline.py:336-366,508-531):
Namespace(surf=None, csv=csv_path, model=checkpoint, suffix=suffix, out=output_dir,
          num_workers=max(1, num_workers), crown_segmentation=0, array_name=array_name,
          fdi=1 if numbering == "FDI" else 0, overwrite=0, device=device,
          vtk_folder=input_root)
with contextlib.redirect_stdout(io.StringIO()):
    dental_model_seg.main(args)

Before the call, _import_dental_model_seg imports shapeaxi lazily and, when saxi_nets lacks DentalModelSeg (every 2.0.x release, according to the comment), points it at saxi_nets_lightning.DentalModelSeg (cs/pipeline.py:105-167). If the import fails, the run goes on for the copy branch and records engine_available: false with the error (cs/pipeline.py:466-472); a mesh that needed the network then has no output and is failed.

4.2 Inside shapeaxi

Read in shapeaxi 2.0.2's dental_model_seg.py (an installed copy; identical, for these functions, to the ShapeAXI checkout 2b34042):

  • the network is saxi_nets_lightning.DentalModelSeg(custom_model=args.model, device=device), with out_channels = 34 (:23,26);
  • each surface is loaded through SaxiDataset with UnitSurfTransform(), batch size 1, persistent_workers=True (:82-84), which is why num_workers must be at least 1;
  • the network returns per-view predictions and the face each pixel shows; the softmax of the predictions masked to visible pixels is summed per face, the arg-max gives one label per face, and each face's label is given to its first vertex (:91-111);
  • post-processing: RemoveIslands for the gum label 33 with a threshold of 500, then for every label with 200, then a closing per label, DilateLabel then ErodeLabel, two iterations each (:118-130);
  • ConvertFDI if fdi == 1 (:52,225-236, next section);
  • with overwrite=0 and a csv input, the result goes to <out>/<csv stem>_<suffix>/<input path without vtk_folder>_<suffix>.vtk (:154-176). Crown_Seg recomputes this path rather than parsing shapeaxi's output (cs/pipeline.py:369-381), then marks each mesh segmented if the file exists and failed otherwise (:533-546).

4.3 Tooth numbering: Universal and FDI

The network always predicts Universal numbers: 1 to 32 for the teeth, 33 for the gum. With numbering = "FDI", shapeaxi's ConvertFDI maps every value through one look-up table (shapeaxi 2.0.2 dental_model_seg.py:225-236):

LUT = [0, 18,17,16,15,14,13,12,11, 21,22,23,24,25,26,27,28,
          38,37,36,35,34,33,32,31, 41,42,43,44,45,46,47,48, 0]
labels = LUT[labels]          # index = Universal value, entry = FDI value
Universal valueFDI valueTeeth
1 to 818 down to 11upper right, third molar to central incisor
9 to 1621 up to 28upper left, central incisor to third molar
17 to 2438 down to 31lower left, third molar to central incisor

00–

shapeaxi writes the converted integers back under the same array name (vtk_id.SetName(args.array_name), :233-235). Because the two systems share most of their range, an FDI array called Universal_ID would be read without error as other teeth: FDI 18 is the upper right third molar, Universal 18 a lower left molar; FDI 33 is a lower left canine, Universal 33 the gum (comment at cs/pipeline.py:62-80). Crown_Seg therefore names the array after the numbering: array_name left empty becomes Universal_ID or FDI_ID (array_name_for, cs/pipeline.py:58-85; cs/__init__.py:44,106). Every downstream reader looks for Universal names only, so an FDI mesh is refused by ALI_IOS, ASO or AREG_IOS instead of being misread (see Findings). All legacy callers passed fdi 0; FDI output is new in practice, and Universal remains the default (cs/__init__.py:46).

Outputs. The tool returns the output folder, so there are no named outputs. Two trees can appear, depending on what happened to each mesh: a mesh segmented by the network is written under <output>/crownseg_input_<suffix>/<relative path without extension>_<suffix>.vtk (cs/pipeline.py:369-381,514), and a mesh that already carried labels is copied, converted to .vtk, to <output>/<relative folder>/<base>_<suffix>.vtk (cs/pipeline.py:480-487,594-613). The caller is expected to read run_report.json rather than guess. The scratch folder .crownseg_work/ is removed in a finally (cs/pipeline.py:87,435-439), and the checkpoint is resolved before it exists, so a refused request leaves the output folder as it found it (cs/pipeline.py:407-413).

run_report.json. tool, checkpoint (by name), array_name, suffix, numbering, device, cases (per mesh: status, input, produced, and error on failure), segmented_meshes, engine_available, engine_error, a summary with the counts of total, segmented, already_segmented, engine_unavailable and failed, and duration_seconds (cs/pipeline.py:556-590). A mesh that shapeaxi wrote nothing for is a failed case; the run as a whole fails only when no mesh at all was produced (cs/pipeline.py:540-551).

Privacy of the logs. shapeaxi prints the path of every mesh it saves, and the path carries the patient's file name: its standard output is swallowed (cs/pipeline.py:341-345,365-366), and the paths of the output are recomputed rather than parsed from it (cs/pipeline.py:369-381).

8. Findings in VISOR

FDI numbering over a mesh that is already labelled

With numbering = "FDI" and skip_segmented on, a mesh that already carries a label array is copied unchanged (cs/pipeline.py:480-487; _write_as_vtk converts the file format, not the labels), while the report states array_name = "FDI_ID" and numbering = "FDI" (cs/pipeline.py:556-561). The copy keeps its Universal integers under their Universal name, so the report announces a numbering the file does not hold. Observed: a synthetic mesh carrying a Universal_ID array was passed through segment_crowns with fdi=True and array_name="FDI_ID"; the report read numbering: "FDI" and array_name: "FDI_ID", and the output file held only Universal_ID with its original value. The segmentation engine is not installed in the environment used, so the case status read engine_unavailable instead of already_segmented; the copy path is the same. The tests do not cover this crossing (tests/test_run.py:488-503).

Four names recognised here, three downstream

Crown_Seg treats a mesh as segmented if it holds any of PredictedID, UniversalID, Universal_ID or FDI_ID (cs/pipeline.py:56). ALI_IOS, ASO and AREG_IOS read only the first three (ali_ios/surface.py:19, SADT-VISOR tools/ASO/src/sadt_aso/markups.py:19, AREG_IOS/src/sadt_areg_ios/surfaces.py:39). A mesh that has only FDI_ID therefore passes Crown_Seg and is refused by the next tool: intended (the tool's own comment says so, cs/pipeline.py:64-80), but with no symptom before that next tool. The comment of ALI_IOS saying that these are “the same three names CrownSeg writes and recognizes” (ali_ios/surface.py:18) is inexact. Read in code.

Meshes in .vtp or .obj are invisible to Crown_Seg

Crown_Seg discovers .vtk and .stl only (cs/pipeline.py:51,292-320), while AREG_IOS accepts .vtk .vtp .stl .obj as input (AREG_IOS/src/sadt_areg_ios/surfaces.py:35) and, in Fully-Automated mode, hands its folder to Crown_Seg (dispatch.py:172-173). A folder holding only such meshes is refused (“No surface mesh found in the input”, cs/pipeline.py:314-319); in a mixed folder they are left out of Crown_Seg's output, which is the folder AREG_IOS continues with. The legacy ALI_IOS copy of the call did read .vtp (segmentation.py:33-56). Read in code; not run.

Two output trees: read the report

A segmented mesh lands under crownseg_input_<suffix>/, a mesh that was already labelled lands beside its relative path, so a glob over one tree misses the other (cs/pipeline.py:369-381,480-487). ALI_IOS reads cases[key].produced from run_report.json instead (ali_ios/dispatch.py:240-252), which is what the report is for. A mesh of a degraded installation carries the status engine_unavailable yet is copied with its produced path (cs/pipeline.py:495-505), so a client that filtered on already_segmented alone would skip it. Read in code.

The tool graph in the server docs is out of date

VISOR-serve docs/TOOL_GRAPH.md:27-28,43 lists ALI_IOS as a leaf. The schema that ALI_IOS publishes declares calls = ['Crown_Seg'] (observed with scripts/describe.py in the ALI_IOS environment), because its dispatch calls Crown_Seg through a module constant (ali_ios/dispatch.py:58,229). The document says it is generated from those schemas and checked at boot; the copy in the repository is older than the code.

Documentation that disagrees with the code

The README says that the model is a required argument (README.md:33), and so does the docstring of the pipeline (cs/pipeline.py:16-23); the argument is optional, with an empty default that resolves to the tool's own folder (cs/__init__.py:41, comment at cs/__init__.py:35-40). The README also names the folder DATA/CrownSeg/testfiles (README.md:178) while the code and the manifest use DATA/Crown_Seg, and it counts 176 tests (README.md:225,232) where 162 test functions are defined in tests/ (a def test_ count; parametrisation may explain the gap). AREG never passes device to Crown_Seg, unlike ALI_IOS (SADT-VISOR tools/AREG/AREG_IOS/src/sadt_areg_ios/tools.py:113-130), so on a CPU-only server the default cuda falls back to the CPU with a warning, or is replaced by the server's DEVICE. Read in code.

What the tool protects

The checkpoint is resolved before any file is created, so a refused request leaves nothing behind (cs/pipeline.py:407-413); a folder that holds two checkpoints is refused with both named, so the vintage of the weights is never silent (cs/pipeline.py:244-251); shapeaxi's standard output, which carries file names, is swallowed (cs/pipeline.py:365); the scratch folder is removed in a finally (cs/pipeline.py:435-439); the input is never modified. Read in code.

Reproducibility

The tool's README reports that the raw prediction PredictedID is bit-identical to a reference port, and that the post-processed Universal_ID varies from run to run, including between two runs of the same code (826 to 2,607 points of 294,260). This is the README's measurement (SADT-VISOR tools/Crown_Seg/README.md:176-209, section “Validated against”), not re-run here.
