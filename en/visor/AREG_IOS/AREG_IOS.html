AREG_IOS on VISOR

AREG_IOS puts two intraoral scans of the same patient, taken at different times, in the same position, using a part of the mouth that treatment does not move. This page explains how, step by step, with the maths: what goes in, what each step does to it, and what comes out. Where the code does something worth checking, a link leads to the code page. The legacy module is on its own page.

VISOR Code (developers) AREG_IOS reached as AREG, mode IOS torch 2.11, pytorch3d, GPU or CPU Legacy page Guide (VISOR) Bibliography

Overview: what goes in, what comes out

A patient’s teeth are scanned with an intraoral scanner twice: at the start (T1) and later (T2). To compare them, the two meshes must be put in the same position, and that can only be done on a part of the mouth that treatment does not move. AREG_IOS picks such a patch and finds the rigid motion (a rotation and a translation) that makes the T2 patch coincide with the T1 patch. On the upper arch the patch is the palate, found by a network; on the lower arch, which has no such plateau, it is a band along the mucogingival line, built from 13 landmarks.

What it takes and gives
Inputa T1 and a T2 intraoral mesh per patient (.vtk, .vtp, .stl, .obj), each naming its jaw in the file name; in Semi-Automated mode, meshes that already carry a tooth number on every vertex and are already oriented
PatchPalate (upper arch, the lower arch follows) or Mucogingival (lower arch alone)
Methodmark the patch on each mesh, then rigid ICP between the two patches (section 3.5)
Outputthe T1 and the T2 moved onto it, both carrying the patch as a 0/1 array, a transform file (.tfm) and a report (AREG_report.json)

Unlike AREG_CBCT, this engine holds a network of its own, for the palatal patch. The tooth labels, the orientation and the mucogingival landmarks come from three other tools it calls.

1. Position in the chain

A client never names AREG_IOS. The Slicer module sends a request to the server tool AREG with the mode “IOS”, and the server hands it to this engine. The engine owns the pairing, the palatal network, the mucogingival band and the ICP. In Fully-Automated mode it asks Crown_Seg for tooth labels and ASO for the orientation; for the mucogingival patch without landmarks it asks ALI_IOS. Nothing calls AREG_IOS back.

What has been checked. The engine is implemented and tested: 63 automated tests pass, with the network replaced by a stub. The AREG documentation states that the IOS engine is unvalidated, since it needs pytorch3d and a segmented lower arch. The engine’s own notes report that two identical runs of the ICP differ by about 0.19 mm on average and 0.38 mm at most on one pair of scans; this was not re-measured here. No timeout, width or memory limit is declared.

In the codeFacade, schema, who calls whom, with files and lines

2. Files involved

The engine is split by job: the published form, a dispatcher that checks every rule and drives the run, the three calls to other tools, the pipeline (pairing, the two ways to paint a patch, writing), the network with its cameras and renderer, the palate predictor, the orientation, the cleaning of the patch on the mesh graph, the mucogingival band, the reading of landmark files, the ICP with the transform writing, and the reading and writing of meshes. The heavy libraries (torch, monai, pytorch3d) are only imported inside functions, so the form can be published on a machine that lacks them.

3.1 Inputs and pairing

Each input becomes a folder under a scratch folder (a single file is linked into a folder of its own). Meshes are found recursively. The jaw is read on whole words of the file name: u, up, upper, maxilla, max or mx for the upper arch; l, low, lower, mandible, mand or md for the lower. The key of a patient is the relative folder plus the file stem without the jaw words and the time-point words, so P1_T1_U.vtk and P1_T2_Upper.vtk share the key P1.

A subject is kept only if the arch the patch lives on exists at both time points; with the palate, the opposite arch also travels along when both times have it. Nothing is guessed. What does not pair is listed in the report under three reasons: meshes with no jaw in their name, patients without that arch, and patients present at one time point only. When nothing pairs at all, the run stops with an error that gives the naming rule.

In the codeFolder handling, the jaw and key rules, the pairing functions and the report block

3.2 Labels and orientation: the supervised calls

Before any mesh is read, the engine refuses what cannot work: an unknown patch, the palate with no checkpoint, the mucogingival patch with neither landmarks nor a way to ask ALI_IOS, a negative height, or Fully-Automated without the other tools or a reference.

In Fully-Automated mode the two time points each go through two tools, in this order: Crown_Seg puts a tooth number on every vertex (a mesh that already has them passes untouched), then ASO orients each jaw onto a reference. ASO’s transforms for the upper arches of the T2 are kept, because they are composed into the transform written at the end, so that it refers to the mesh you sent. In Semi-Automated mode none of this happens: the meshes must already carry labels and be oriented.

For the mucogingival patch without a landmark folder, ALI_IOS is asked, for the T1 and for the T2, for its Mucogingival network alone, which keeps it from also running its occlusal and cervical passes.

3.3 The palatal patch: the network inside the engine

The network is loaded once per run. For each mesh the engine goes through five steps: orient the mesh into a standard frame, scale it into the unit sphere and turn the surface normals into colours, render seven views and let a network label each pixel, let the pixels vote for the triangles they show, then clean the result. The mesh is first triangulated if it holds anything else, because the face list is read as triangles.

Standard frame. The centroids of four teeth (3, 8, 9 and 14 in Universal numbering: the two upper first molars and the two upper central incisors) are brought onto a fixed reference triangle by two rotations and a translation. This frame is only used to render: the patch is written on the mesh as you sent it. If the tooth labels are missing, the prediction goes on without the standard frame and the report carries a note.

The surface normals, mapped to colours (normal × 0.5 + 0.5), are the only texture the network sees. Each view is that colour image plus a depth map: four channels.

ElementValue in VISOR
Networka 2D UNet (MONAI), 4 channels in, 2 out (background or patch), applied to every view
Viewsseven cameras clustered at height 0.9: one straight above the origin, four shifted by 0.2 along the two horizontal axes, two on diagonals; all look at the origin
Image320 × 320 pixels, one triangle kept per pixel, a plain ambient light
Training coderemoved: this is inference only

Two legacy defects are fixed: pixels that show no triangle no longer vote, and the device is no longer hard-coded to a GPU. Two are kept: several pixels of one view that show the same triangle do not add up, and only the first corner of each triangle receives its label (details). That second point leaves holes in the patch, which the cleaning repairs.

Before the closing, any island of either class under 200 points is absorbed by what surrounds it. The result is stored on the mesh as a 0/1 point array named Butterfly.

3.4 The mucogingival band

On the lower arch there is no plateau, so the patch is built from the 13 landmarks ALI places along the mucogingival line. This needs no network and no GPU. At least 3 landmarks are needed; missing ones are noted. The steps are: order the landmarks along the arch; draw a smooth curve through them (a spline, sampled at 300 points); snap each sample to its nearest vertex; grow a band of the chosen height around those vertices; then remove the vertices that carry a lower-crown label, if the mesh is labelled.

A height of 0 builds no curve and no band: the patch is only the 13 snapped landmarks (and this is the panel’s default). Each time point builds its band from its own landmarks. Three steps of the legacy module are not in the port: dropping the landmarks ALI marked as doubtful, restricting both bands to the landmarks found at both times, and starting the ICP from the paired landmarks (details). The result is the point array Bottom_MGL.

In the codeThe landmark order, the band functions, the file matching and the exact steps

3.5 The ICP

The vertices labelled 1 on each mesh become a point cloud of their own (an empty cloud is an error). The T2 cloud is moved onto the T1 cloud by the ICP of the visualisation toolkit: rigid body (six degrees of freedom), at most 1000 iterations, starting by matching the two centres.

A matrix with a non-finite entry is refused. The matrix is then applied to the whole T2 mesh, not only to its patch.

In the codeThe patch clouds and the exact ICP call

3.6 Outputs, transform and report

The tool returns one folder, archived and sent back. Under each patient’s relative folder: the T1 mesh carrying the patch array, the T2 mesh moved onto the T1 (patch array too), a transform file named <patient>_<suffix>_transform.tfm, and, for the palate, an untouched copy of the other T1 arch and the other T2 arch moved by the same matrix. With the mucogingival patch only the lower arch is written. A .vtp input stays .vtp; anything else is written as .vtk.

The transform. The ICP gives a matrix that moves points, while a .tfm is read the other way, so the inverse is written. When ASO oriented the meshes first, its own transform for the T2 upper arch is composed in, so that the file relates the mesh you sent to the registered result. The report says which case applies. AREG_report.json lists, per patient, whether it worked, on which patch and jaw, the direction of the transform and any note, plus the subjects that did not pair and a summary count.

6. Environment

The engine runs in a Python environment of its own, built from a lock file, with the deep-learning libraries pinned to one exact version of torch because pytorch3d is built against it (this is why the CBCT and IOS engines are separate). The palate network uses a GPU when the server has one and falls back to the CPU otherwise. The mucogingival patch needs neither pytorch3d nor a GPU. The server holds the palate checkpoint and the orientation reference; no time limit is set.

8. Findings in VISOR

Each point is checked in the code and written up, with its evidence, on the code page; the list also appears in the findings.

  • The default patch height is 0, which means no band. The form says 0 uses the engine’s default, the code does the opposite, so a mucogingival registration launched with the defaults uses about 13 points. Evidence.
  • The mucogingival path is behind the legacy: three refinements are absent. Evidence.
  • Duplicate faces lose votes in the palate network, as in the legacy. Evidence.
  • Fully-Automated orients each jaw on its own, so the occlusion captured in the scan may not be what is carried to the other arch. Evidence.
  • No maximum on the patch height. Evidence.
  • The scratch folder is not removed when a run fails in an unexpected way. Not triggered. Evidence.
  • A failed orientation is written in the report, and a transform is always written. Evidence, evidence.
  • Crown_Seg is not told which device to use; an asymmetry, not a fault. Evidence.

9. Literature

The method (a palatal patch predicted by a multi-view network, then ICP) is the one published for the legacy module; the bibliography of the tool is on its sources page and in section 12 of the legacy page. The port adds no publication of its own.
