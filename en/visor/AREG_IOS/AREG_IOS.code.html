AREG_IOS on VISOR: the code

For developers: what the VISOR port of AREG_IOS does in the code, with file:line references, signatures, arguments, environment, the differences from the legacy code and the findings. The readable explanation of the same pipeline, with the maths, is on the atlas page. The legacy module is on its own page.

Code Atlas (explanation) VISOR AREG_IOS reached as AREG, mode IOS torch 2.11, pytorch3d, GPU or CPU Legacy page Guide (VISOR) Bibliography

AREG_IOS registers a follow-up intraoral scan (T2) onto the baseline scan (T1) of the same patient by a rigid ICP on a patch that treatment does not move: the palate on the upper arch, or a band along the mucogingival line on the lower arch. In VISOR the whole computation runs on a server, including the network that finds the palatal patch; Slicer only shows the form, sends the folders and opens what comes back. This page describes that port, read at SADT-VISOR 6ba2a78 (branch tool/vface), VISOR-serve e9a7e5d and AutomatedDentalToolsRemote 19b95e8. The legacy module it is compared with is SlicerAutomatedDentalTools 3c67957, described on its own page; legacy paths below are at that commit.

Abbreviations used on this page: ios/ is SADT-VISOR tools/AREG/AREG_IOS/src/sadt_areg_ios/, common/ is SADT-VISOR tools/AREG/common/src/sadt_areg_common/, and server/ paths are in VISOR-serve. “Observed” marks what was executed (tests, scripts/describe.py, short Python probes) during the study of the port; everything else was read in the code.

1. Position in the chain

Plain-language explanation and maths: atlas page.

A client never names AREG_IOS: the Slicer module sends AREG with mode = "IOS", and the server swaps the facade for this engine. The engine owns the pairing, the palatal network, the mucogingival band and the ICP; tooth labels, orientation and the mucogingival landmarks come from three other tools it calls through the supervisor.

3.1 Inputs and pairing

Plain-language explanation and maths: atlas page.

As in the CBCT engine, each input becomes a directory under <output_dir>/.areg_work/, a single file being linked into a folder of its own (ios/dispatch.py:311-329,368-374). Meshes are .vtk .vtp .stl .obj (ios/surfaces.py:35,48-49), read with all their point arrays (ios/surfaces.py:52-76).

discover walks one time-point folder recursively and files every mesh under a key and a jaw (ios/pipeline.py:38-59). The key is the relative folder plus patient_stem with the jaw tokens dropped as well as the time-point tokens, so P1_T1_U.vtk and P1_T2_Upper.vtk share the key P1. The jaw is read on whole tokens of the base name: u up upper maxilla max mx for the upper arch, l low lower mandible mandibule mand md for the lower (ios/surfaces.py:113-130, common/catalogs.py:175-180). A file left by a previous run with the same suffix is skipped (ios/pipeline.py:53-54).

pair keeps a subject only if the arch the patch lives on exists at both time points, and with the palate it also carries the opposite arch when both times have it (ios/pipeline.py:81-116). Nothing is guessed: what does not pair is listed in the report under three reasons.

"unmatched": {
  "registered_jaw": "Upper",
  "meshes_without_a_jaw_in_their_name": [...],
  "patients_without_a_upper_arch": [...],
  "patients_present_at_only_one_timepoint": [...]}     # pipeline.py:72-78

When no subject pairs at all, the run stops with an error that gives the naming rule and the counts (ios/dispatch.py:189-197).

3.2 Labels and orientation: the supervised calls

Plain-language explanation and maths: atlas page.

main resolves two hosted bundles before anything else: registration_model left empty becomes DATA/AREG/models/AREG_model, ios_reference left empty becomes DATA/AREG/models/IOS_Gold_files (ios/dispatch.py:87-97,457-459). _check_ios then refuses, before a file is read: an unknown patch; the palate with no checkpoint found; the mucogingival patch with no landmarks and no supervisor to reach ALI_IOS; a negative height; Fully-Automated without a supervisor or without a reference (ios/dispatch.py:100-139). Fully-Automated requires Crown_Seg and ASO for both patches.

In Fully-Automated mode the two time points go through two calls each, in this order (ios/dispatch.py:168-183, ios/tools.py:83-130):

t1 = sup.run("Crown_Seg", meshes=<T1 folder>, suffix="Seg" [, model=crown_model])
t2 = sup.run("Crown_Seg", meshes=<T2 folder>, suffix="Seg" [, model=crown_model])
t1 = sup.run("ASO", input=t1, reference=<IOS_Gold_files>, modality="IOS",
             automation="Fully-Automated", output_suffix="Or")
t2 = sup.run("ASO", input=t2, reference=..., modality="IOS", ...)
prior_transforms = _collect_transforms(t2, suffix="Or")    # upper arches only

Crown_Seg is left at skip_segmented's default, so a mesh that already carries labels passes through untouched (ios/tools.py:113-122); no device is sent. ASO is called with its defaults for the teeth and the occlusion (see the findings). _collect_transforms indexes the .tfm files ASO wrote for the upper arches of T2 by patient key (ios/dispatch.py:257-279); they are composed into the transform written at the end, so that it refers to the mesh the caller sent (3.6).

For the mucogingival patch without mgl_landmarks, ALI_IOS is asked, for T1 and for T2, for its Mucogingival network alone, and both results are copied into one folder, .areg_work/mgl_predicted (ios/dispatch.py:213-229):

sup.run("ALI_IOS", input=<folder>, networks=["Mucogingival"] [, model=mgl_model])

Naming that network alone keeps ALI from also running its occlusal and cervical passes (ios/tools.py:140-145).

3.3 The palatal patch: the network inside the engine

Plain-language explanation and maths: atlas page.

PatchPredictor is built once per run, so the checkpoint is loaded once for the whole batch (ios/butterfly.py:96-107, ios/dispatch.py:199-206). The device is cuda when a card is visible, otherwise cpu with a warning (ios/butterfly.py:41-54); the report records the device and the checkpoint's file name. The checkpoint is the single .ckpt or .pth found under the bundle folder; zero or several are refused, naming the candidates (ios/butterfly.py:57-93). It is loaded with map_location set to that device and must hold model.* weights (ios/net.py:188-214).

For each mesh (ios/butterfly.py:109-141):

  1. Triangulate if the mesh holds anything but triangles, because the face tensor is read as reshape(-1, 4), which reads wrong indices silently otherwise (ios/postprocess.py:22-50).
  2. Orient into the canonical frame: the centroids of teeth 3, 8, 9 and 14 (UR6, UR1, UL1, UL6 in Universal numbering) are aligned onto a fixed reference triangle; the two incisors are averaged into one midpoint, so the triangle has three points (ios/orientation.py:29-30,111-146). This needs a tooth-label array, Universal_ID, PredictedID or UniversalID (ios/surfaces.py:39,103-110). If it fails, the prediction goes on with the mesh as it is and a note is kept for the report (ios/butterfly.py:117-131). The orientation is used for rendering only: the patch array is written on the original mesh.
  3. Normalise: centre on the bounding box, scale into the unit sphere, compute point normals; the normals mapped to RGB (n * 0.5 + 0.5) are the only texture the network sees (ios/surfaces.py:159-192, ios/butterfly.py:169-190).
  4. Render and segment seven views (below), then vote the per-pixel probabilities back onto faces and vertices.
  5. Clean: islands of either class under 200 points are absorbed by their surround, then the patch is closed, dilation 2 then erosion 2 (ios/postprocess.py:192-204).

As in the legacy, each view rasterises twice: once through the renderer with the camera's R and T, once through the rasteriser alone to get zbuf and pix_to_face (ios/net.py:171-172). The vote (ios/butterfly.py:143-166):

logits, _views, pixel_to_face = self.model((vertices, faces, colors))
probabilities = softmax(logits * (pixel_to_face >= 0), dim=2)
face_votes = torch.zeros(2, n_faces)
for view_faces, view_probabilities in zip(pixel_to_face, probabilities):   # 7 views
    hit = view_faces >= 0                       # background pixels left out
    face_votes[:, view_faces[hit]] += view_probabilities[:, hit]
face_labels = torch.argmax(face_votes, dim=0)
vertex_labels[faces[0, :, 0]] = face_labels      # first corner of each face
return (vertex_labels >= 1)

Two legacy defects are fixed: background pixels (index -1, which addressed the last face) no longer vote, and the device is no longer hard-coded to CUDA (ios/butterfly.py:11-23). Two are kept: repeated faces in one view do not accumulate, and only the first corner of each face receives the label; see the findings. The result is the point array Butterfly, 0 or 1 (ios/butterfly.py:39,138-141).

3.4 The mucogingival band

Plain-language explanation and maths: atlas page.

On the lower arch there is no plateau, so the patch is built from the 13 landmarks ALI places along the mucogingival line, LL6MG to LR6MG through L0MG, or the same names without MG (ios/mgl.py:46-52). It needs no network and no GPU (ios/mgl.py:15-18). Landmark files are Slicer markups (.json, .mrk.json); each scan finds its file by a key that keeps the time point, by equality or prefix of tokens, and an ambiguity is an error that names the candidates (ios/landmarks.py:68-160, ios/pipeline.py:136-157).

build_patch (ios/mgl.py:182-239):

  1. order the landmarks along the arch; at least 3 are needed, missing ones are noted (ios/mgl.py:79-96);
  2. with a height of 0: snap the landmarks themselves to their nearest vertices, and stop there, no curve and no band (ios/mgl.py:204-207);
  3. otherwise: sample a parametric spline through them at 300 points (vtkParametricSpline, which passes through its points; only the docstring calls it a B-spline, ios/mgl.py:99-115), snap each sample to its nearest vertex, and grow a band around those seeds by Dijkstra, reaching height mm on each side (a half-height, ios/mgl.py:59), measured along the mesh edges, never through space, so the band cannot jump to the lingual side (ios/mgl.py:99-163,208-210);
  4. remove the vertices that carry a lower crown label, 18 to 31, if the mesh is labelled (ios/mgl.py:72,166-179,212-216);
  5. write the result as the point array Bottom_MGL; an empty band is an error for that patient (ios/mgl.py:57,218-227).

Each time point builds its band from its own landmarks; the legacy restriction to landmarks common to both times, the filter on doubtful landmarks and the landmark-based start of the ICP are not in the port (section 7).

3.5 The ICP

Plain-language explanation and maths: atlas page.

The patch is predicted on each time point (ios/pipeline.py:192-193), then the ICP runs on the two patch clouds, T2 onto T1 (ios/pipeline.py:195-198). patch_cloud turns each painted mesh into a vertex-only cloud of the points whose array value is 1, and refuses an empty one (ios/butterfly.py:193-224). icp.align then runs the same vtk filter as the legacy:

icp = vtk.vtkIterativeClosestPointTransform()
icp.SetSource(t2_patch); icp.SetTarget(t1_patch)
icp.GetLandmarkTransform().SetModeToRigidBody()     # 6 degrees of freedom
icp.SetMaximumNumberOfIterations(1000)
icp.StartByMatchingCentroidsOn()

A matrix with a non-finite entry is refused (ios/icp.py:36-56). The legacy vtkICP.__call__ returned its source unmoved, harmless with a single method; the port has one alignment and no list to compose (ios/icp.py:8-14). The matrix moves the T2 mesh's points onto T1; the whole T2 mesh, not only its patch, is transformed with it (ios/pipeline.py:206).

3.6 Outputs, transform and report

Plain-language explanation and maths: atlas page.

The tool returns one path, so there are no named outputs: the output folder is archived. Under each patient's relative folder (ios/pipeline.py:200-233,253-258):

<output_dir>/<relative folder>/
    <T1 stem>_<suffix>.vtk|.vtp       # T1, carrying Butterfly or Bottom_MGL
    <T2 stem>_<suffix>.vtk|.vtp       # T2 moved onto T1, patch array too
    <other arch T1>_<suffix>           # palate only: untouched copy
    <other arch T2>_<suffix>           # palate only: moved by the same matrix
    <patient>_<suffix>_transform.tfm
AREG_report.json

A .vtp input stays .vtp; anything else is written as binary legacy .vtk, since .stl cannot hold the label array (ios/surfaces.py:79-100). The stem is that of the file actually registered, which in Fully-Automated mode is the labelled and oriented copy (ios/pipeline.py:253-258). With the mucogingival patch only the lower arch is written: the upper arch is not carried (ios/pipeline.py:13-17).

The transform (ios/icp.py:88-112). The ICP matrix moves points; a .tfm is consumed the other way, so the inverse is written, as the CBCT engine does. When ASO oriented the meshes first, ASO's transform for the upper arch of T2 is composed in, matrix @ inv(prior), so the file relates the mesh the caller sent to the registered result; matrix_of reads ASO's transform with its centre of rotation (ios/icp.py:63-85). The report says which case applies (ios/pipeline.py:240-244).

AREG_report.json (ios/dispatch.py:155-232,376-381,410-412, ios/pipeline.py:235-250):

{"modality": "IOS", "automation": "...", "output_suffix": "Reg",

A patient fails alone on a registration, surface, patch or landmark error, with its reason (ios/dispatch.py:238-254).

8. Findings in VISOR

Plain-language explanation and maths: atlas page.

The default patch height is 0, which means no band

run() publishes mgl_patch_height: float = 0.0 and documents it as “0 uses the engine's default” (SADT-VISOR ios/__init__.py:36,65-66). The code does the opposite: only None is replaced by the 5.0 mm default (ios/dispatch.py:395-397), and a height of 0 builds no curve and no band, only the snapped landmarks, which the ICP then uses alone (ios/mgl.py:196-211; the check says “0 registers on the landmarks alone, without any band”, ios/dispatch.py:119-123). Observed: calling run() with the mucogingival patch and no height hands the engine (_run_ios, stubbed) mgl_patch_height = 0.0, in the tool's environment. So a mucogingival registration launched with the panel's defaults registers on about 13 points, not on a band of 5 mm. The report states it (mgl_patch_height_mm, ios/dispatch.py:232); the panel does not. Legacy: default 5.0 (AREG/AREG.py:42-44,870-882).

The MGL port is behind the legacy at 3c67957

Three steps that the legacy module has at 3c67957 are absent from VISOR (grep over tools/AREG/AREG_IOS/src, observed): the doubtful-landmark filter, the restriction to landmarks common to both time points, and the landmark-based start of the ICP; see What changed from the legacy logic. The lower teeth kept out of the band are 18 to 31 in VISOR against 17 to 32 in the legacy, and the VISOR comment calls its range the upstream one, “verbatim” (ios/mgl.py:66-72), which 3c67957 contradicts (mgl_patch.py:47-55, where 17 and 32 are listed on purpose). The chronology of the two histories was not established, so this may be a port of an earlier version.

Duplicate faces lose votes in the palate network

In face_votes[:, view_faces[hit]] += view_probabilities[:, hit] (ios/butterfly.py:157) an indexed addition does not accumulate repeated indices. Observed with torch in the tool's environment: adding ones to the same column three times in one indexed operation leaves 1. The legacy has the same accumulation (AREG_IOS/AREG_IOS_utils/PredPatch.py:59-60); VISOR fixed the background pixels but not this. The vote is then written on the first corner of each face only (ios/butterfly.py:161-166), which is why the patch has holes that the morphological closing repairs (ios/postprocess.py:192-204).

Fully-Automated orients each jaw on its own

The call to ASO sends no ios_occlusion (ios/tools.py:96-102), and ASO's default is “Orient each jaw independently” (SADT-VISOR tools/ASO/src/sadt_aso/__init__.py:63-65). The registration then moves the other arch with the registered arch's matrix “so the captured occlusion survives” (ios/pipeline.py:13-15,209-224), but if the two jaws were oriented separately, the occlusion captured in the scan is not what is carried. The legacy passed occlusion = "true" when the folder held lower arches (AREG/AREG_Method/IOS.py:621,633). Read in code; no run compared the two outputs, so the size of the effect is unknown.

No maximum on the patch height

The check refuses a negative height and nothing else (ios/dispatch.py:119-123). The legacy widget kept the value in [0, 20] mm, (AREG/AREG.py:42-44,870-882). Read in code.

The scratch folder is not removed when a run fails

register removes .areg_work/ after the engine returns, with no try/finally (ios/dispatch.py:348-413, shutil.rmtree at line 408; the engine runs at lines 385-403). An exception that is not caught per patient would leave the copies of the inputs and the labelled and oriented meshes in the archived output folder. AREG_IOSCBCT has the finally. Read in code; not triggered.

A failed orientation is written in the report

The patch is still predicted, but notes in the patient's entry say that it was predicted without the canonical orientation, with the reason (ios/butterfly.py:117-131, ios/pipeline.py:247-249). Read in code.

A transform is always written

Every registered patient gets a .tfm, in both modes and for both patches, with a sentence in the report saying which way it maps (ios/pipeline.py:226-244). Read in code.

Crown_Seg is not told which device to use

label_crowns sends only meshes, suffix and an optional model (ios/tools.py:124-130). Crown_Seg then uses its own default, with the server's device setting applied when the caller names none, and falls back to the CPU with a warning when no card is visible; see Crown_Seg on VISOR. Not a fault, an asymmetry with ALI_IOS, which passes its device on. Read in code.

9. Literature

Plain-language explanation and maths: atlas page.

The method (a palatal patch predicted by a multi-view network, then ICP) is the one published for the legacy module; the bibliography of the tool is on its sources page and in section 12 of the legacy page. The port adds no publication of its own.
