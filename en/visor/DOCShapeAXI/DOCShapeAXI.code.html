DOCShapeAXI on VISOR: the code

For developers: what the VISOR port of DOCShapeAXI does in the code, with file:line references, signatures, arguments, environment, the differences from the legacy code and the findings. The readable explanation of the same pipeline, with the maths, is on the atlas page.

VISOR Code Atlas (explanation) Legacy page Guide (VISOR)

References on this page name a repository, then a path inside it, then a line: SADT-VISOR is the tool catalogue (commit 6ba2a78), VISOR-serve the server (e9a7e5d), Remote the Slicer client (AutomatedDentalToolsRemote 19b95e8), legacy SlicerAutomatedDentalTools at 3c67957. A bare path such as catalog.py:50 is in SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/. Everything was read in the code; nothing on this page was run, except the two checks named where they appear (the shapeaxi 1.0.10 against 1.1.1 file comparison, and a small CPU test of repeated indices). Overview of the stack: VISOR.

1. Position in the chain

Plain-language explanation and maths: atlas page.

  • State: ported, implemented in code, with tests in the tool (SADT-VISOR tools/DOCShapeAXI/tests/test_run.py, 91 test functions, not run for this page). A server set up only with the VISOR-serve staging scripts cannot run it: the EfficientNet backbone it requires is not staged by any of them (see Findings in VISOR).
  • API name DOCShapeAXI (SADT-VISOR tools/DOCShapeAXI/pyproject.toml:57-59); modules __init__.py, catalog.py, engine.py, pipeline.py.
  • Client panel DOCShapeAXIRemote, a thin panel (Remote DOCShapeAXIRemote/DOCShapeAXIRemote.py:63,67,69; built, CMakeLists.txt:34). It loads the .vtk and .vtp results as models, at most 12 (:82,88-92).
  • Calls / called by: nothing; no sup argument (__init__.py:18-25), and no other tool names DOCShapeAXI.
  • Hosted data: the five checkpoints are in the data manifest (VISOR-serve scripts/data-manifest.yml:597-614). There is no test surface, deliberately: nothing public is an airway, a condyle or a cleft (:616-622). The manifest header still says "NOT PORTED YET" (:595), which is wrong: the tool and its client exist.

3. The pipeline

Plain-language explanation and maths: atlas page.

3.1 One checkpoint name decides the analysis

Plain-language explanation and maths: atlas page.

Legacy asked the caller for data_type, task, model, nn and num_classes as separate positional arguments (legacy DOCShapeAXI_CLI/DOCShapeAXI_CLI.py:299-307), so a two-class checkpoint could be run with a four-class scale. VISOR takes one argument, model, and looks its base name up in a table (catalog.py:50-71, __init__.py:54). An unknown name is a ValueError listing the five known ones (catalog.py:74-88); the lookup happens before the file's existence is checked (__init__.py:54-57).

File nameAnatomyTaskClassesNetwork
airways_2_class.ckptNasopharynx airway obstructionbinary2SaxiMHAFBClassification
airways_4_class.ckptNasopharynx airway obstructionseverity4SaxiMHAFBClassification
airways_4_regress.ckptNasopharynx airway obstructionregression1SaxiMHAFBRegression

The table is keyed by the file name as staged: cleft_4_class.ckpt, where the legacy panel's lookup returned clefts_4_class (comment at catalog.py:44-49; legacy page, models).

3.2 Surfaces, device and network

Plain-language explanation and maths: atlas page.

  • Discovery: a single .vtk, or a folder walked recursively, hidden files skipped, sorted (pipeline.py:22,40-64). Nothing found is a ValueError, "DOCShapeAXI reads surfaces, not volumes" (__init__.py:59-64). The mount point given to shapeaxi is the input folder, or the file's folder for a single file (:71).
  • Device: cuda falls back to cpu with a warning when no card is visible (pipeline.py:67-72).
  • Network: load_network checks that the class named by the catalogue exists in shapeaxi.saxi_nets_lightning, then that the EfficientNet backbone is staged, then allowlists the classes the checkpoint pickles, and loads it (pipeline.py:130-151):
network_class = getattr(saxi_nets_lightning, network_name, None)   # else ValueError
check_backbone_is_staged()      # <torch hub dir>/checkpoints/efficientnet-b0-355c32eb.pth, else FileNotFoundError
allow_checkpoint_globals()      # shapeaxi transform classes + torchvision Compose
model = network_class.load_from_checkpoint(checkpoint, strict=False)
model.eval(); model.to(device)

The allowlist exists because torch 2.6 made weights_only=True the default and these checkpoints carry their training transforms in hyper_parameters (pipeline.py:108-127). strict=False is kept from legacy (legacy DOCShapeAXI_CLI.py:135,201).

3.3 Prediction pass

Plain-language explanation and maths: atlas page.

The file list is a pandas DataFrame built in memory (legacy wrote a CSV into the output folder with mode 'a', DOCShapeAXI_CLI.py:111-118), fed to shapeaxi's SaxiDataset with EvalTransform(scale_factor), the scale factor being read from the checkpoint's hyperparameters (engine.py:11-34); shapeaxi 1.1.1 then ignores it (see the check below). Then, one surface at a time (engine.py:37-64):

mesh = model.create_mesh(vertices, faces, normals)
points = model.sample_points_from_meshes(mesh, model.hparams.sample_levels[0])
views, _ = model.render(mesh)
output = model(points, views)
if not analysis.is_regression:
    output = torch.argmax(softmax(output).detach(), dim=1, keepdim=True)
predictions.append(float(output.reshape(-1)[0].cpu()))

Each prediction is recorded with the surface's path relative to the mount point and either class (an integer) or score (a float, regression) (__init__.py:81-90). The sampling of points and the rendering are shapeaxi's; neither the tool nor legacy fixes a random seed (no seed or manual_seed in the tool's sources).

3.4 Explanation pass (Grad-CAM)

Plain-language explanation and maths: atlas page.

Only when explain is true (__init__.py:92-95). The dataset is rebuilt and each surface is rendered again; then for each class k in range(analysis.classes) (engine.py:67-114):

cam = LayerGradCam(model, model.convnet.module._blocks[-1], device_ids=[0])
attribution = cam.attribute(inputs=(points, views), target=k, attr_dim_summation=False)
attribution = attribution.sum(dim=1).cpu().detach()
scaled = scale_attribution(attribution.numpy(), (224, 224))   # resize, clip 1/99 percentiles, rescale to [-1, 1]
projected = gradcam_process(_Namespace(device, target_class=k), scaled, faces, per_face, vertices)
surface.GetPointData().AddArray(projected)                    # array grad_cam_target_class_<k>
post_process.MedianFilter(surface, projected)
  • Resize: torch.nn.functional.interpolate, bilinear, align_corners=False, instead of legacy's cv2.resize; the comment says a test pins the two to 1e-5 (pipeline.py:163-184, pyproject.toml:45-51).
  • Normalisation: clip to the 1st and 99th percentiles, then map to [-1, 1]; a flat map becomes zeros rather than NaN (pipeline.py:186-199).
  • Which layer: the last block of the 2D EfficientNet branch, as in legacy (DOCShapeAXI_CLI.py:150-151): the map explains the multi-view branch, not the point-cloud branch.
  • Projection: gradcam_process is shapeaxi's (saxi_gradcam.py:112-144 in 1.0.10 and in 1.1.1, the same code). Faces start at 0 and take maximum(old, new) view after view, so on the mesh a face holds max(0, max over views) and the range is [0, 1]; the value goes to the face's first vertex, and vertices that are nobody's first vertex are reset to 0 (:134). Inside one view, pixels showing the same face share an index and the write that stays is not defined (the last one on the CPU, not the maximum); background pixels carry index -1 and write onto the last face. The CPU test and the details are on the legacy code page, section 5d; nothing was run on the GPU.
  • Median filter: post_process.MedianFilter (post_process.py:294-308) replaces every vertex, filled or empty, by the median of its neighbours, itself excluded (utils.py:363-376), not only the empty ones.
  • Array names: the class index is always passed as target_class, which names the array (engine.py:104-106,117-129). Legacy set it only when num_classes > 1 (DOCShapeAXI_CLI.py:171-174), so the regression checkpoint now also gets a per-class name, grad_cam_target_class_0. Read in the code.
  • Writing: once per surface after all classes, flat in output_dir under the input's base name (engine.py:111-113); legacy wrote inside the class loop, into <out>/explainability/<task>/ (DOCShapeAXI_CLI.py:153,185-186).

3.5 Outputs and the report

Plain-language explanation and maths: atlas page.

The written surfaces are renamed with output_suffix before the extension (__init__.py:118-133), so P01.vtk becomes P01_pred.vtk. DOCShapeAXI_report.json is always written (:97-110):

{
  "model": "condyles_4_class.ckpt", "anatomy": "Mandibular condyle", "task": "severity",
  "classes": 4, "network": "SaxiMHAFBClassification", "device": "cuda",
  "explained": true, "surfaces": 2,
  "predictions": [ {"surface": "left/P01.vtk", "class": 2},
                   {"surface": "right/P01.vtk", "class": 0} ]
}

The values are illustrative, the keys are the code's. This example is also the collision of the findings: both surfaces would be written to the same output_dir/P01.vtk. run() returns {"outputs": {...}, "predictions": [...], "report": path} although it is annotated -> Path (__init__.py:25,112-115). There is no CSV.

8. Findings in VISOR

Plain-language explanation and maths: atlas page.

The EfficientNet backbone is a prerequisite nobody stages

shapeaxi builds an EfficientNet-B0 around every checkpoint. The tool refuses to let it be downloaded in the middle of a request, and instead raises FileNotFoundError unless efficientnet-b0-355c32eb.pth is already under <torch hub dir>/checkpoints/ (SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/pipeline.py:80-105, called from load_network at :146; README.md:112-121). Neither the data manifest nor any script of VISOR-serve mentions this file (searched for "efficientnet" in the three repositories: only the tool's own README.md, pipeline.py and tests/test_run.py do). A deployment that follows the usual staging steps therefore fails at its first call, after the surfaces have been uploaded. Read in the code; whether a given server has the file in its cache was not checked.

The status line shows question marks

The client builds its summary from report.get("data_type") and report.get("checkpoint") (Remote DOCShapeAXIRemote/DOCShapeAXIRemote.py:122-130). The report written by the tool has neither key: it has model, anatomy, task, classes and network (SADT-VISOR __init__.py:97-110). The panel's summary will read "?" in place of the anatomy and of the checkpoint, while task and the surface count are filled. Read in the code, not run in Slicer.

The client describes a prediction table and a task selector that do not exist

The client's comments say the result is a "prediction table" in CSV form (DOCShapeAXIRemote.py:76-86) and that a task argument narrows itself to the anatomy through an options_when rule (:12-17). The tool writes no CSV (__init__.py:97-110), and its schema has six arguments, none called task, with no options_when (output of scripts/describe.py). The task is chosen by picking the checkpoint file, so a user must know what airways_2_class.ckpt and airways_4_regress.ckpt mean.

Two inputs with the same file name collide on output

Surfaces are found recursively but written flat: a/s.vtk and b/s.vtk both go to output_dir/s.vtk (engine.py:111-112), so the second replaces the first, while the report keeps them apart by relative path (__init__.py:84). The renaming step then moves s.vtk to s_pred.vtk once per entry (__init__.py:128-132): the second move finds no file, which would end the run in a FileNotFoundError after all the computation; with an empty output_suffix the overwrite is silent. CLIC and CNE reproduce the input tree to avoid exactly this. Read in the code, not run.

Still true from legacy: unseeded sampling, saliency of one branch only

No seed is set anywhere in the tool's sources and there is no seed argument, so the random point sampling inside shapeaxi (engine.py:54,92) is not fixed from one run to the next, as in legacy (legacy page, pitfalls). The Grad-CAM layer is the last block of the 2D views branch (engine.py:82-83), so the map says nothing about the point-cloud branch. Read in the code.

Comments that disagree with the pins

The comment above the captum pin speaks of 0.9.0 while the pin is captum==0.8.0 (pyproject.toml:39-44). The data manifest still labels the tool "NOT PORTED YET" (data-manifest.yml:595). Neither changes what runs.

Verified: the legacy shapeaxi mismatch is fixed here

Legacy code is written for the shapeaxi 1.x API while its installer asks for 2.0.2 or later (legacy ADT/ADTLib/env/install_pytorch.py:385). VISOR pins shapeaxi==1.1.1, with the reason in the comment (pyproject.toml:18-30), and resolves the network classes from saxi_nets_lightning, where they live (pipeline.py:135-145). The checkpoint is no longer copied into the output folder. shapeaxi 1.1.1's EvalTransform does not honour scale_factor either: UnitSurfTransform.__call__ never forwards it (saxi_transforms.py:48-57), identical in 1.0.10 and 1.1.1 (the two packages differ only in __about__.py, compared file by file for this pass; downloaded 1.1.1 from the package index).
