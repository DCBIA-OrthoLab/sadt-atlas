DOCShapeAXI on VISOR

DOCShapeAXI looks at a 3D surface, such as an airway or a jaw joint, and answers a clinical question about its shape: which severity class it belongs to, or how obstructed it is. It then shows where on the surface the network looked. This page explains how, step by step, with the maths. Where the code does something worth checking, a link leads to the code page. The legacy module is on its own page.

VISOR Code (developers) 5 checkpoints, 2 network classes Legacy page Guide (VISOR)

Overview: what goes in, what comes out

DOCShapeAXI
Inputone or several 3D surfaces (.vtk) that are already segmented elsewhere, for example an airway or a condyle, and the name of a trained network file (a checkpoint)
Ideathe network sees each surface in two ways at once, as a cloud of points and as many pictures taken from around it; the two views of the shape are merged into a class or a score; then a second pass shows which parts of the surface weighed most
Outputfor each surface, a class (or a number for the regression checkpoint) in a JSON report, and optionally a copy of the surface carrying one “where it looked” map per class

The networks and the Grad-CAM method are the legacy ones: nothing is trained in VISOR. What changed is everything around them: the checkpoint name now tells the tool which analysis to run, there is no CSV any more, and the explanation pass can be switched off (What changed).

1. Where it runs

In VISOR, Slicer keeps only a panel. It sends the surfaces and the checkpoint name to a server, which does all the work and sends one archive back. DOCShapeAXI calls no other tool, and no other tool calls it. The tool is implemented and tested, but a server prepared only with the standard staging scripts cannot run it yet: one image backbone that the network needs is not put in place by any of them (Known issues).

2. Files involved

The tool is four short Python modules (the catalogue of checkpoints, the network and the two passes, the discovery and loading helpers, and the entry point that ties them together), a pinned environment, and tests. Legacy had a 830-line panel plus a 310-line command; only the computation was ported. The full table, with line counts and the files on the server and client sides, is on the code page.

3. The pipeline

3.1 One checkpoint name decides the analysis

Legacy asked the caller for five separate settings, so a two-class checkpoint could be run with a four-class scale. VISOR takes one thing, the checkpoint name, and looks it up in a fixed table of five. An unknown name is refused with the list of the known ones.

3.2 Surfaces, device and network

  • Surfaces: a single file, or a folder searched through all its sub-folders, in a fixed order. Finding nothing is an error (“DOCShapeAXI reads surfaces, not volumes”).
  • Device: the graphics card if there is one, otherwise the processor, with a warning.
  • Network: the tool loads the network named by the table, checks that the image backbone it needs is already on the server (it refuses to download it in the middle of a request), then loads the checkpoint.
In the codeThe loading sequence, the allowlist of classes the checkpoint may rebuild, and strict=False

3.3 Prediction pass

Each surface goes through the network one at a time. The file list is built in memory, and shapeaxi puts every surface at a standard size and position before it is looked at; whether the checkpoint’s own scale factor is honoured by the pinned shapeaxi was not checked. Then the network receives two inputs made from the same surface, and each is turned into one 256-number vector.

Besides the pictures, the network samples 4096 points at random on the surface. A first branch processes this cloud with attention restricted to the nearest neighbours of every point; a second branch runs an image network (EfficientNet-B0) on each picture, then attention across the pictures.

The class is the highest score; the other scores are not returned, so the report carries no measure of confidence. The point sampling is random and no seed is set, so two runs on the same surface can differ slightly.

In the codeThe calls of the prediction loop, how a class or a score is recorded, and the missing seed

3.4 Explanation pass (Grad-CAM)

Only when explain is on. The surface is rendered again and, for each class in turn, the network is asked which parts of the pictures pushed that class’s score. This is done on the image branch only: the map says nothing about the point-cloud branch.

The result is stored on the surface as one named array of numbers per class. The regression checkpoint has one class, so one array. In Slicer these arrays can be shown as colours on the surface.

In the codeThe Grad-CAM calls, the resize, the percentile clipping, the array names and where the surfaces are written

3.5 Outputs and the report

The written surfaces get the chosen suffix (by default _pred) added to their name, so that P01.vtk becomes P01_pred.vtk. A JSON report is always written. It names the checkpoint, the anatomy, the task, the number of classes, the device, whether the explanation was done, and, for each surface, its path and its class or score. There is no CSV any more.

In the codeThe report keys, the example report and the return value of the tool

4. What you can choose

  • Surfaces: one .vtk file, or a folder.
  • Checkpoint: one of the five hosted files. Its name alone fixes the anatomy, the task, the number of classes and the network.
  • Explain: on by default. Turned off, the run is several times faster and only the report is written.
  • Suffix: added to the name of each written surface.
  • Device: filled in by the server, not shown in the panel.

6. Environment

The tool runs in a Python environment of its own on the server, with pinned versions: Python 3.11, shapeaxi 1.1.1 (all five checkpoints carry settings that shapeaxi 2.x rejects), PyTorch3D for the pictures, and Captum for Grad-CAM. Having one environment per tool is what lets DOCShapeAXI sit on older libraries next to Crown_Seg on newer ones. The image backbone (a 20 MB file) must be placed in the server’s PyTorch cache beforehand. Legacy installed a shared conda environment from the panel instead.

8. Known issues in VISOR

Each point below is read in the code and described, with its evidence, on the code page; the list also appears in the findings.

  • A prerequisite nobody stages. The image backbone file is not put in place by any staging script, so a standard server fails at its first call. Evidence.
  • The status line shows question marks. The panel reads two keys that the report does not have. Evidence.
  • The client describes things that do not exist. A prediction table and a task selector are mentioned in its comments; the tool has neither. Evidence.
  • Two inputs with the same file name collide. They are written to the same output file. Evidence.
  • Still true from legacy. Unseeded point sampling, and a saliency map for one branch only. Evidence.
  • Comments that disagree with the pins. Harmless, but they mislead. Evidence.
