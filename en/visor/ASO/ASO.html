ASO on VISOR

ASO turns a scan so that it sits in the same pose as a reference case. This page explains how, step by step, with the maths: which landmarks are used, how three of them give a first rotation, how a rigid ICP refines it, and what is written. Where the code does something worth checking, a link leads to the code page. The legacy module is on its own page.

VISOR Atlas (explanation) Code (developers) Legacy page Guide (VISOR)

Overview: what goes in, what comes out

A scan can be in any pose in its file: head tilted, centred anywhere. Every downstream tool (registration, mirroring, measurements) wants it in a known pose. ASO finds the rotation that brings the scan onto a reference patient who is already oriented, using a few anatomical points that both share.

CBCTIntraoral scan (IOS)
Inputa head scan (a file, a folder, a DICOM series), optionally with landmark filestooth meshes, upper and lower, optionally with landmark files
Points usedlandmarks supplied, or found by ALI_CBCT (seven by default)landmarks supplied, or the centroid of three or four labelled teeth
Methoda first alignment from three landmarks, then a rigid ICPthe same, on the tooth points
Outputthe oriented scan or mesh, the moved landmarks, the transform file (.tfm), and ASO_report.json saying what was used and what failed

1. Status and position in the chain

implemented and tested ASO is one tool of the VISOR server (a program the server runs on request), replacing the legacy widget and its four command-line modules. It has no front-end wrapper of its own and no network of its own: the only learned step of an ASO run is ALI_CBCT’s. It was tested against its own tests; its output was not compared numerically with the legacy ASO.

ASO calls ALI_CBCT only (through the supervisor, the part of the server that lets one tool run another, for the scans that need predicted landmarks) and is called by AREG_CBCT, AREG_IOS, AREG_IOSCBCT and VFACE.

3. The principle, the modes and the call to ALI_CBCT

The target is not an analytic frame such as “the occlusal plane is z = 0”. It is a reference case: an already-oriented patient’s landmarks for a CBCT, two labelled meshes and their landmarks for an intraoral scan. The choice of frame is therefore in the data: according to comments in the code, the two published CBCT references (each one a bundle: a folder of files hosted on the server) carry different landmark sets (Frankfurt plane: Ba, S, N, RPo, LPo, ROr, LOr; Occlusal plane: ANS, IF, PNS, UL6O, UR1O, UR6O). This page could not read the bundles themselves, so it relies on those comments; if they are right, the landmarks asked for decide the reference. If none or several fit, the run is refused with the list of what each carries. The reference scan is never read, only its landmarks.

The estimation has two stages for a CBCT, and the same two stages for an intraoral scan after a jaw alignment on the tooth centroids (section 5.2). The two stages are a coarse alignment built from three landmarks (a translation and two rotations about hand-built axes, never a least-squares fit), then a rigid ICP that re-pairs points by nearest neighbour.

Who decides between prediction and supplied landmarks

The legacy had two buttons, Semi and Fully. In VISOR the choice is made on the data:

ModalityDecision
CBCTper patient: a landmark folder given by the caller wins over everything; else Fully-Automated forces the prediction; else the prediction runs only for a patient with no landmark file beside the scan. It needs a supervisor; Fully-Automated without landmarks and without a supervisor is refused before any reading.
IOSper jaw: tooth centroids when forced by Fully-Automated or when the jaw has no landmark file; otherwise the landmarks.

The call to ALI_CBCT is a single one for the whole batch, with the landmarks asked for by name (seven agents instead of fifty-eight). The default seven are Ba, S, N, RPo, LPo, ROr and LOr, the set of the Frankfurt reference. How ALI places a point is on ALI on VISOR.

4. CBCT, step by step

4.1 Input, DICOM and patients

A single file, a folder or a zip is accepted. A DICOM series is detected and converted in the job’s scratch folder; nothing is written into the input. Files are grouped by patient: the name is cut at known markers (_scan, _Or, _lm and a few more) at word boundaries, so _OR no longer catches _ORTHO. Several landmark files of one patient are merged in memory, where the legacy wrote a merged file into the input and deleted the sources. At least 3 requested landmarks must exist in the reference before anything is registered.

In the codeDiscovery, DICOM, the patient name, the minimum check

4.2 Recentering

This is the whole of what the legacy pre-orientation step still did, now applied to every scan in both modes. Supplied landmarks are moved by the same offset. The order matters: recentre first, predict second.

In the codeThe recentering code and why the order matters

4.3 Landmarks from ALI_CBCT predicted

For the patients that need it, one call to ALI_CBCT over the folder of recentred scans, with the landmarks asked for by name. ALI_CBCT keeps its own constants and finds its own weights; ASO passes none of the legacy hard-coded parameters. ALI writes one file per scan, which is matched back to the patient.

In the codeThe call to ALI_CBCT and how results are collected

4.4 Registration computed

Per patient, in order:

  1. Usable landmarks. Requested, present in the patient’s file and in the reference; the others are listed in the report with the reason.
  2. Outliers. The distances and directions between landmarks are compared with the reference’s, for the labels both files share. A landmark is dropped if it disagrees by more than 15 mm or 0.4 rad too often. Fewer than 3 left: this patient fails.
  3. Best triplet. See below.
  4. Coarse alignment. A translation onto the first landmark, a rotation aligning first with second, then a rotation about that axis aligning first with third (maths in 4.5).
  5. ICP. A rigid ICP, 1000 iterations; its translation is set to zero.
  6. Composition. The rotations are composed, the recentering is added, and the whole is inverted for the transform file.
In the codeEach registration step with its constants and lines

4.5 The orientation, written out

Notation: p→A is landmark A on the scan being oriented, q→A the same landmark on the reference, and (A, B, C) the triplet the search kept. The formulas are the legacy ones, and the VISOR code computes the same quantities.

1. Translation onto the first landmark: computed, then thrown away. In CBCT it is left out of the matrix, because the volume was recentred on the origin first. In IOS it is kept: two meshes share no origin.

t→=q→A−p→A

2. First rotation. Both vectors are folded before the angle is taken. Each is first divided by its largest component, a positive scaling that cancels. Two guards are new in VISOR: the cosine is clipped to [−1, 1] before the arccosine, and coincident landmarks give no rotation instead of an undefined one.

3. Second rotation.

4. The rotation matrix is the quaternion form of Rodrigues’ formula. A zero-length axis gives the identity instead of a matrix of undefined values.

The matrix, written out from those four numbers:

R=[α2+β2−γ2−δ22(βγ+αδ)2(βδ−αγ)2(βγ−αδ)α2+γ2−β2−δ22(γδ+αβ)2(βδ+αγ)2(γδ−αβ)α2+δ2−β2−γ2]

5. Composition. The translation of step 1 never enters the product, and the ICP translation column is set to zero, so in CBCT the composite is a pure rotation about the origin; the recentering translation is added only to the transform written to disk.

M=RicpR2R1 (Ricp[0:3,3]=0)

This is a search followed by a nearest-neighbour ICP, not a least-squares fit over the landmarks; the legacy page writes out what such a fit would compute (its section 4.5).

4.6 Resampling and outputs

Three files per patient, in a copy of the input folders: the oriented volume (the input’s family of format, compressed), the landmarks moved by the coarse matrix and the ICP (written in LPS, display on), and the transform file mapping the oriented scan back to the original (recentering included). A report, ASO_report.json, lists per case the status, the landmarks used and dropped, and the products or the reason for failure.

In the codeResampling, the three files, the report keys

5. Intraoral scans, step by step

5.1 Patients and jaws

Each mesh is paired with an optional landmark file by patient and jaw, both read from the file name. A file with no jaw token is skipped and counted in a warning: the legacy silently treated it as the lower jaw. The reference is read once for the whole cohort.

In the codeThe IOS pipeline with its lines

5.2 Tooth centroids

For a jaw without a landmark file, or every jaw in Fully-Automated mode, the mesh must carry tooth labels, or the run is refused (Crown_Seg can put them there beforehand).

Then the same triplet search and a rigid ICP of 100 iterations are run on the same teeth’s centroids, this time with the translation. The two point sets must have the same keys, or the jaw fails naming the missing teeth. The final matrix is the ICP composed after the coarse alignment, as in the legacy. What differs is inside the fine registration: VISOR multiplies the ICP matrix after the triplet matrix (the order in which they are applied), the legacy multiplied them the other way round.

In the codeThe centroids, the jaw alignment, the registration and the composition order

5.3 Supplied landmarks

For a jaw with a landmark file: the points are named by tooth and type (for example the occlusal point of a tooth), selected in both files, and fed to the same triplet search and ICP. A missing point is named in the error.

In the codeKey construction and selection

5.4 Occlusion

Three choices: the jaws are oriented independently, or one jaw drives the other. With a driving jaw, it is registered first and its matrix is applied unchanged to the other jaw, which preserves the bite. One argument replaces the two legacy check boxes that could contradict each other.

In the codeDriving jaw and matrix reuse

5.5 Outputs

Per jaw: the oriented mesh (a .vtp stays .vtp; other formats are written as .vtk), the landmarks (only if a file was supplied, rewritten from the caller’s own file with the display switched on), and the transform as the inverted matrix, same convention as the legacy with a new file name. The report adds, per jaw, whether it was registered on tooth centroids, on landmarks, or from the other jaw’s transform.

In the codeWriters and the transform code

6. What you can choose

  • Scans: a file or folder; the type (CBCT or IOS) is always chosen, never deduced from the extension.
  • CBCT landmarks: 115 to choose from, the seven Frankfurt ones by default.
  • IOS teeth and landmark types: 32 teeth (six by default) and 8 types (the occlusal point by default), jaws upper and lower.
  • Occlusion: independent, upper drives lower, or lower drives upper.
  • Landmark folder (Advanced): wins over everything.
  • Output suffix: Or by default.
  • Hidden in the panel: the reference, the Mode override, the landmark model, DICOM detection and the triplet limit and seed.

8. Environment

ASO has an environment of its own on the server, without torch, pytorch3d or conda; the only GPU use of an ASO run is ALI_CBCT’s prediction. The reference bundles and test files are hosted on the server. Versions and limits are on the code page.

10. Known issues in VISOR

Each point is checked in the code and described, with its evidence, on the code page.

  • A misnamed landmark file is silently replaced by a prediction, even in Semi-Automated. The evidence, on the code page.
  • The report does not record the triplet limit or the seed, though the documentation says it does. The evidence, on the code page.
  • A triplet limit of 0 or less loses the whole CBCT batch with a misleading message (reachable only by a direct call). The evidence, on the code page.
  • IOS with an unusual tooth count fails late, after the mesh was read. The evidence, on the code page.
  • The coordinate system of a landmark file is never checked. The evidence, on the code page.
  • Silent choices: only the first scan of a patient folder is kept; output suffixes other than Or are not recognised when names are cut. The evidence, on the code page.
  • Some documents no longer match the code. The evidence, on the code page.
