ASO on VISOR: the code

For developers: what the VISOR port of ASO does in the code, with file:line references, signatures, arguments, environment, the differences from the legacy code and the findings. The readable explanation of the same pipeline, with the maths, is on the atlas page. The two 3D viewers are on the atlas page.

VISOR Code Atlas (explanation) Legacy page Guide (VISOR)

VISOR runs the dental tools on a server: Slicer keeps only a panel that sends the data and loads the results (see Architecture). This page describes the VISOR port of ASO, read in the code of the repositories named below and compared with the legacy Slicer module at 3c67957, which has its own page. "Run for this page" marks what was executed while checking it; everything else was read in the code. Abbreviations: ASO/ = SADT-VISOR 6ba2a78, tools/ASO/src/sadt_aso/; other tools/… paths are in SADT-VISOR too; VISOR-serve = VISOR-serve e9a7e5d, files under server/; Remote = AutomatedDentalToolsRemote 19b95e8; legacy = SlicerAutomatedDentalTools 3c67957, where ASO_CBCT_utils/, SEMI_ASO_CBCT/ and PRE_ASO_CBCT/ live under ASO_CBCT/, ASO_IOS_utils/ and PRE_ASO_IOS/ under ASO_IOS/, and ASO_Method/ under ASO/.

In one paragraph: ASO turns a scan so that it lands in the frame of a reference case hosted on the server. For a CBCT it recentres the volume on the physical origin, gets landmarks (supplied, found beside the scan, or predicted by ALI_CBCT through the supervisor), chooses the best three of them, builds a coarse rotation from that triplet, refines it with a rigid ICP and resamples the volume (section 4). For an intraoral mesh it does the same on tooth centroids or on supplied landmarks, without ever segmenting (section 5). There is no network in ASO itself: the only learned step of an ASO run is ALI_CBCT's.

1. Status and position in the chain

Plain-language explanation and maths: atlas page.

implemented and tested ASO is one server tool, ASO, in SADT-VISOR tools/ASO: a single run() (ASO/__init__.py:24-72) replaces the legacy widget and its four command-line modules (PRE_ASO_CBCT, SEMI_ASO_CBCT, PRE_ASO_IOS, SEMI_ASO_IOS). It has no facade. The Slicer panel is ASORemote (122 lines), which draws the form from the schema the server publishes and adds only the loading of results (Remote ASORemote/ASORemote.py:80-122). The tool has its own environment, Python 3.11 and no torch (tools/ASO/pyproject.toml:8-21).

Tests run when this page was written: 205 passed, 5 skipped (pytest in tools/ASO); not re-run for the latest revision of this page, and the same holds for the "Run for this page" scenarios below. SADT-VISOR/PROVENANCE.md (ASO row) records one end-to-end run through a real supervisor, on the real bundle and a real card (not rerun here), an upstream starting commit "unrecorded", and no numerical comparison with the pre-port ASO; the tool README says that comparison "is still owed" (tools/ASO/README.md:278). So the port is implemented and tested against its own tests, not compared with the legacy output.

3. The principle, the modes and the call to ALI_CBCT

Plain-language explanation and maths: atlas page.

The target is not an analytic frame but a reference case: an already-oriented patient's landmarks for a CBCT, two labelled meshes and their landmark files for an intraoral scan. The two published CBCT references carry disjoint landmark sets, "Frankfurt Horizontal + Midsagittal has Ba/S/N/RPo/LPo/ROr/LOr, Occlusal + Midsagittal has ANS/IF/PNS/UL6O/UR1O/UR6O" (comment, ASO/dispatch.py:309-312), so the landmarks asked for decide the reference: choose_reference keeps the only bundle carrying all of them, and refuses with the list of what each bundle carries if none or several fit (:305-371). An IOS reference is the one bundle holding meshes (:337-345). The reference scan is never read, only its landmarks (ASO/cbct/pipeline.py:256-273). The content of the hosted bundles was not available to read for this page.

The estimation is the legacy two-stage scheme in both modalities: a coarse alignment built from three landmarks (a translation and two rotations about hand-built axes, never a least-squares fit), then a rigid vtkIterativeClosestPointTransform that re-pairs points by nearest neighbour.

Who decides between prediction and supplied landmarks

Plain-language explanation and maths: atlas page.

The legacy had two buttons, Semi and Fully. In VISOR automation still exists in the signature (Semi-Automated by default) but the panel hides it (ASO/layout.py:61) and the code treats it as an override. The decision is made on the data (ASO/dispatch.py:649-668):

ModalityDecision
CBCTper patient: a landmarks folder given by the caller wins over everything; else Fully-Automated forces the prediction; else the prediction runs only for a patient with no markups file beside the scan. It runs only if a supervisor exists (:651-668). Fully-Automated without landmarks and without a supervisor is refused before any reading (:256-269, SupervisorRequired).
IOSper jaw: forced centroids with Fully-Automated, or when the jaw has no landmarks file; otherwise the landmarks (ASO/ios/pipeline.py:432-439)

The call is a single one for the whole batch: sup.run("ALI_CBCT", input=<recentered scans>, landmarks=[the requested names], model=… only if landmark_model is set) (ASO/dispatch.py:537-542). No output_dir is passed (the supervisor decides where the callee writes), nor device, seed or num_workers. The landmarks are asked for by name, not by region, so seven agents run instead of fifty-eight (comment :521-523). The default seven are Ba, S, N, RPo, LPo, ROr, LOr (ASO/__init__.py:51, default of cbct_landmarks; ASO/catalogs.py:51), the set of the Frankfurt reference. The three AREG callers do not pass cbct_landmarks, so they use these seven and need a reference that carries them (ASO/dispatch.py:361-371, :435-459); VFACE passes its own list for each frame (tools/VFACE/src/sadt_vface/tools.py:136). The results are read back by walking ALI's output folder and keying each file by patient_stem (_collect, :563-596).

4. CBCT, step by step

Plain-language explanation and maths: atlas page.

4.1 Input, DICOM and patients

Plain-language explanation and maths: atlas page.

A single file is linked into a folder of its own; a folder is used as is; a .zip has already been extracted by the server (_as_directory, ASO/dispatch.py:902-926). DICOM is detected (dicom.holds_a_series, ASO/cbct/dicom.py:34-57) or forced by the hidden dicom_input; the series are converted under .aso_work/dicom_nifti, GDCM first and dicom2nifti in an empty staging folder as a fallback (:60-151; ASO/dispatch.py:612-613). Nothing is written into the input.

discover (ASO/cbct/pipeline.py:199-229) groups files by patient. The patient name is cut at token boundaries before one of the known markers _lm_Pred, _Scanreg, _MERGED, _scan, _Scan, _Or, _OR, _lm (:34-36, patient_stem :99-129), so _OR no longer catches _ORTHO; _T1 and _T2 are deliberately kept. The key is the path relative to the input. Files that look like an earlier ASO output are used only if a patient has nothing else (:132-146). Several markups files of one patient are merged in memory (load_landmarks, :232-253), where the legacy MergeJson wrote a _MERGED file into the input and deleted the sources.

Before any registration, at least 3 requested landmarks must exist in the reference (_check_selection_against_reference, ASO/dispatch.py:435-459; called at :629).

4.2 Recentering

Plain-language explanation and maths: atlas page.

The whole of what the legacy PRE_ASO_CBCT still did, now applied to every scan in both modes (ASO/dispatch.py:707-731):

center = np.array(image.TransformContinuousIndexToPhysicalPoint(
    (np.array(image.GetSize()) / 2.0).tolist()))
translation = sitk.TranslationTransform(3)
translation.SetOffset((-center).tolist())
resampler.SetTransform(translation.GetInverse())
resampler.SetOutputOrigin((np.array(image.GetOrigin()) - center).tolist())   # ASO/cbct/pipeline.py:276-299

Same size, spacing and direction, only the origin moves: the volume ends up centred on the physical origin, which is what lets the rotation be applied about the origin later. A scan to be predicted is written to .aso_work/centered/<key> for ALI_CBCT (prepare, :302-313); supplied landmarks are shifted by the same offset (center_landmarks, :316-326; ASO/dispatch.py:756). The order matters and is commented in the code: ALI's voxel-to-millimetre conversion takes the absolute value of the origin, so recentering first and predicting second is not the same as the reverse (ASO/dispatch.py:20-27).

4.3 Landmarks from ALI_CBCT predicted

Plain-language explanation and maths: atlas page.

For the patients that need it (section 3), one sup.run("ALI_CBCT", …) over the folder of recentred scans, the landmarks asked by name (ASO/dispatch.py:513-553). ALI_CBCT keeps its own constants (field of view 64³, one voxel per step, spawn radius 10: tools/ALI/ALI_CBCT/src/sadt_ali_cbct/agent.py:39-41) and finds its own weights; ASO passes none of the legacy hard-coded parameters. ALI writes one file per scan, which _collect keys back to the patient (:563-596). How ALI places a point is described on ALI on VISOR.

4.4 Registration computed

Plain-language explanation and maths: atlas page.

register (ASO/cbct/icp.py:100-180), per patient:

  1. Usable landmarks: requested, present in the patient's file and in the reference; others are listed in landmarks_dropped with the reason (:121-128).
  2. Outliers: distance and direction tables of the landmarks both files share, thresholds 15 mm, 0.4 rad and 0.1 rad (:32-34); a landmark is dropped if its total count exceeds the number of shared labels, or its angular count alone exceeds half of it (landmarks_to_remove, :64-97). Fewer than 3 left: RegistrationError, this patient fails (:134-138).
  3. Best triplet: every ordered triplet is tried when there are at most max_triplets of them (7 landmarks give 210, 14 give 2184), otherwise a sample from default_rng(seed); the winner is the triplet whose coarse alignment leaves the smallest mean distance (best_triplet, ASO/geometry.py:323-381). Deterministic, where the legacy drew from the global generator.
  4. Coarse alignment (_Alignment and init_icp, ASO/geometry.py:237-320): a translation onto the first landmark, a rotation aligning first→second, then a rotation about that axis aligning first→third. The component-wise absolute values of the legacy are kept: 
    angle, axis = _angle_and_axis(self._pairs(first, second),
                              _scaled(np.absolute(moved[second] - moved[first])))
self.axis = np.absolute(self.aligned[second] - self.aligned[first])   # ASO/geometry.py:266-275
    In CBCT the translation is computed and not put in the matrix, because both volumes already sit on the origin (include_translation=False, ASO/cbct/icp.py:145-150).
  5. ICP: vtkIterativeClosestPointTransform, rigid body, 1000 iterations, start by matching centroids; its translation is set to zero (_icp_matrix, :199-212; :155).
  6. Composition: 
    rotations = sitk.CompositeTransform(3)
for step in reversed(transform_steps[1:]):      # skips the coarse translation
    rotations.AddTransform(step)
full = sitk.CompositeTransform(rotations)
full.AddTransform(pre_transform)                # the recentering
resample_transform=rotations.GetInverse(), full_transform=full.GetInverse()   # ASO/cbct/icp.py:162-174

The structure is the legacy one (TransformList walked backwards from index 1, then the PRE_ASO transform added, then the inverse: legacy SEMI_ASO_CBCT/SEMI_ASO_CBCT.py and ASO_CBCT_utils/utils.py, see the legacy page). The difference is where the recentering comes from: the legacy read it from a .tfm produced by PRE_ASO_CBCT (identity if absent), VISOR computes it in the same run.

4.5 The orientation, written out

Plain-language explanation and maths: atlas page.

Notation: p→A is landmark A on the scan being oriented, q→A the same landmark on the reference; (A,B,C) is the triplet the search kept. The formulas are the legacy ones, and the VISOR code computes the same quantities.

The translation superimposes the first landmarks so the rotations can be computed; in CBCT it is then left out of the matrix (include_translation=False, ASO/geometry.py:313-318; ASO/cbct/icp.py:148-150) and out of the composite (transform_steps[1:], :165), because the volume was recentred on the origin first. In IOS it is kept: two meshes share no origin (ASO/ios/icp.py:89-97).

The bars are a component-wise absolute value, not a norm (np.absolute, ASO/geometry.py:232, :267). Both vectors are folded into the positive octant before the angle is taken, so a landmark pair pointing one way and its reference counterpart pointing the opposite way give the same vector. VISOR keeps this on purpose: the port reproduces the legacy result.

θ1=arccos(v→2⋅v→1∥v→2∥∥v→1∥) , a→1=v→2×v→1

Each vector is first divided by its largest component (_scaled, ASO/geometry.py:132-153), a positive scaling that cancels in the quotient and in the cross product. Two guards are new in VISOR: the cosine is clipped to [-1, 1] before arccos, and coincident landmarks give no rotation instead of NaN (:156-170).

The axis of the second rotation is not a cross product but the first→second direction just aligned, itself folded by np.absolute (self.axis, ASO/geometry.py:275); its angle comes from the third landmark (finish, :277-290). The axis is the folded copy, so the roll keeps what the first rotation did only when the rotated vector has no negative component (or no positive one); otherwise it turns about a vector that points elsewhere. The angle is the unsigned arccos, applied counterclockwise about the axis.

R=[α2+β2−γ2−δ22(βγ+αδ)2(βδ−αγ)2(βγ−αδ)α2+γ2−β2−δ22(γδ+αβ)2(βδ+αγ)2(γδ−αβ)α2+δ2−β2−γ2]

rotation_matrix (ASO/geometry.py:101-129) writes exactly these nine terms, with the minus on the vector part; a zero-length axis returns the identity instead of a matrix of NaN.

The ICP translation column is set to zero (ASO/cbct/icp.py:155), so in CBCT the composite is a pure rotation about the origin; the recentering translation is added only to the transform written to disk (:168-170). This is a search followed by a nearest-neighbour ICP, not a least-squares (Kabsch) fit over the landmarks; the legacy page writes out what such a fit would compute (its section 4.5).

4.6 Resampling and outputs

Plain-language explanation and maths: atlas page.

The recentred volume is resampled onto its own grid (same size and spacing), linear, background 0, with the rotations only (ASO/cbct/pipeline.py:357-362): the volume turns inside its box, and what leaves the box is lost, as in the legacy. Three files per patient, in a copy of the input tree, written unconditionally into the job's own folder (:364-374):

FileContent
<patient>_<suffix><ext>oriented volume; the extension of the input family, compressed (.nii → .nii.gz, .gipl → .gipl.gz; compressed_extension, SADT-VISOR naming/src/sadt_naming/__init__.py:77-79)
<patient>_lm_<suffix>.mrk.jsonthe landmarks moved by the coarse matrix and the ICP, written from scratch in LPS with the display switched on (ASO/markups.py:67-86, :142-160)
<patient>_<suffix>_transform.tfmfull_transform: oriented → original, recentering included

ASO_report.json at the root (ASO/dispatch.py:52, :155-161, :929-935): modality, automation, output_suffix, reference, requested_landmarks, reference_landmarks, landmark_source, unmatched_markups, per case status, landmarks_used, landmarks_dropped, produced or the failure reason, and summary.

5. Intraoral scans, step by step

Plain-language explanation and maths: atlas page.

5.1 Patients and jaws

Plain-language explanation and maths: atlas page.

discover (ASO/ios/pipeline.py:122-180) pairs each mesh with an optional landmark file by patient and jaw, both read from the file name with the shared vocabulary sadt_naming.JAW_TOKENS (:38, patient_and_jaw :47-110). A jaw token may come first (Upper_gold.vtk). A file with no jaw token raises JawError, is skipped and counted in a warning (:43, :147-152): the legacy defaulted to Lower. Meshes are read once per run through a cache, the reference once for the cohort (FileCache, :251-280).

5.2 Tooth centroids

Plain-language explanation and maths: atlas page.

For a jaw without a landmark file, or every jaw in Fully-Automated (_fully_automated_matrix, ASO/ios/pipeline.py:442-476):

  1. The mesh must carry a label array (Universal_ID, PredictedID or UniversalID, ASO/markups.py:19); otherwise segment_unlabelled raises "Segment it first, or use the semi-automated mode with landmark files" (ASO/ios/pipeline.py:367-382). If no mesh of the batch is labelled, the whole request is refused naming Crown_Seg (ASO/dispatch.py:868-895).
  2. Coarse alignment on the 3 or 4 ticked teeth of the jaw (pre_icp.align, ASO/ios/pre_icp.py:20-47): centroids of the vertices carrying each label (mean_teeth, ASO/ios/icp.py:32-49), sorted into left, middle, right by Universal number, the two middle teeth of four averaged; the plane of the three points is turned onto the reference's, then the in-plane direction, then the centroids are made to coincide.
  3. Fine registration on the same teeth' centroids: triplet search, coarse alignment with its translation, rigid ICP of 100 iterations (register, ASO/ios/icp.py:61-98, :106-119). The two point sets must have the same keys, or the jaw fails naming the missing teeth (:72-79); the legacy silently subsampled the longer one.
  4. The matrix is fine @ coarse (ASO/ios/pipeline.py:476). Inside register the ICP is composed after the coarse alignment, M_icp @ M_init, where the legacy built M_init @ M_icp (ASO/ios/icp.py:11-15, :98).

5.3 Supplied landmarks

Plain-language explanation and maths: atlas page.

For a jaw with a landmark file (_semi_automated_matrix, ASO/ios/pipeline.py:479-499): the keys are built as <tooth><type> from ios_teeth × ios_landmark_types, split by jaw (ASO/catalogs.py, landmark_keys_by_jaw; called at ASO/dispatch.py:826), selected in both files, missing ones named in the error (select_keys, ASO/ios/icp.py:52-58), then the same register as above. Landmark files are read as .mrk.json or .json, positions taken as written (ASO/markups.py:23, :35-64).

5.4 Occlusion

Plain-language explanation and maths: atlas page.

ios_occlusion has three values (DRIVING_JAW, ASO/catalogs.py:127-131). With Upper drives Lower or Lower drives Upper, the driving jaw is registered first and its matrix is applied to the other jaw unchanged, which preserves the bite (_ordered_jaws and _matrix_for, ASO/ios/pipeline.py:390-415). One argument replaces the two legacy check boxes that could contradict each other.

5.5 Outputs

Plain-language explanation and maths: atlas page.

Per jaw (_write_jaw, ASO/ios/pipeline.py:502-545): the oriented mesh <stem>_<suffix>.vtk (a .vtp stays .vtp; .stl, .obj and .off are written as binary .vtk, ASO/ios/surfaces.py:67-88); the landmarks, only if a file was supplied, rewritten from the caller's own file with positions matched by label and the display forced on (rewrite_landmarks, ASO/markups.py:89-119); and the transform:

inverted = np.linalg.inv(matrix)
transform = sitk.AffineTransform(3)
transform.SetMatrix(inverted[:3, :3].flatten().tolist())
transform.SetTranslation(inverted[:3, 3].tolist())        # ASO/ios/pipeline.py:548-554
# written as <patient>_<Upper|Lower>_<suffix>.tfm      # :540-544

Same convention as the legacy saveMatrixAsTfm (inverted, affine, no LPS/RAS conjugation: legacy ASO_IOS_utils/utils.py:172-184); the name is new. The report adds per case jaws, each with status and registered_on ("tooth centroids", "landmarks" or "the Upper jaw's transform") or a reason (:342-350).

Outputs

  • ASO_report.json at the root; the tool returns one path, no named outputs

10. Findings in VISOR

Plain-language explanation and maths: atlas page.

Pitfall · a misnamed landmark file is silently replaced by a prediction

With a supervisor (which the server supplies to a tool that asks for one), a patient with no markups file matched to its scan is sent to prediction, even in Semi-Automated: _needs_prediction returns not patients[key]["markups"] (ASO/dispatch.py:651-661), the orphan list is emptied once any patient is predicted (:684-685), and the report says landmark_source is ALI_CBCT or mixed. Run for this page with the helpers of tools/ASO/tests/test_run.py: a scan P1_CBCT.nii.gz with a file P1.mrk.json (a name that does not pair), Semi-Automated, a fake supervisor: landmark_source = ALI_CBCT, unmatched_markups = [], the case oriented with status ok. Without a supervisor the same input fails and names the file (landmark_source = alongside the scans, unmatched_markups = ['P1.mrk.json']). The hand-placed points are ignored without a warning; the panel hides automation, so the user cannot force a strict Semi run.

Pitfall · the report does not record max_triplets or seed

The run() docstring says the report records them (ASO/__init__.py:119-121); no key of that name is written anywhere in the tool's sources (the report is built in ASO/dispatch.py at :155-161, :616-617, :670, :694, :819, :823, :931). The tool README repeats the claim (tools/ASO/README.md:166). Read in code.

Pitfall · max_triplets of 0 or less loses the whole CBCT batch with a misleading message

The sample is empty and best_triplet raises "Need at least three landmarks…" (ASO/geometry.py:353-357, :378-379); only RegistrationError is caught per CBCT patient (ASO/dispatch.py:797), so the ValueError ends the whole run. Run for this page: two valid patients, Semi-Automated, max_triplets=0: orient raises that ValueError and no patient is oriented. The argument is hidden, so only a direct API call reaches it (the hiding rule is the technical-arguments list in VISOR-serve server/registry/conventions.py:48-54, which names seed and max_triplets; layout.py has no entry for them).

Pitfall · IOS with an unusual tooth count fails late

Read in code, not run. Without a landmark file, a jaw is registered on tooth centroids, which needs exactly 3 or 4 teeth (ASO/ios/pre_icp.py:26-29). The upstream check outside Fully-Automated mode only requires teeth times types of at least 3 per jaw (ASO/dispatch.py:494-506), so 5 ticked teeth pass and each jaw then fails after its mesh was read.

Pitfall · the coordinate system of a landmark file is never checked

Also true in the legacy. load_landmarks reads each position as written (ASO/markups.py:35-64); the only occurrence of coordinateSystem in the tool is the "LPS" it writes (:75). A file exported in RAS is read with x and y inverted. Read in code.

Note · silent choices

When several scans share a patient folder, only the first, in sorted order, is kept, with no mention in the report (ASO/cbct/pipeline.py:219-228; read in code, not run). The suffixes _Or and _OR are hard-coded when patient names are cut (:34-36), whereas the output detection takes the caller's suffix (:132-146). Run for this page: on a folder holding P1.nii.gz and P1_Reo.nii.gz, discover with output_suffix="Reo" returns two patients, P1 and P1_Reo (the earlier output, which would be oriented again), where with Or and P1_Or.nii.gz it returns P1 alone.

Note · documents that no longer match the code

The tool README says "the server does not implement supervisors yet" (tools/ASO/README.md:111); it does (VISOR-serve execution/runner.py:1685) and ASO uses one. VISOR-serve server/base.py:208 speaks of 130 landmarks for ASO where the signature has 115. A docstring of the Remote client says the mode is "asked for, never guessed" (ASORemote/ASORemote.py:75-77), whereas automation is hidden (ASO/layout.py:61); modality is the one asked for. segment_unlabelled still describes crown segmentation as "not implemented yet" (ASO/ios/pipeline.py:367-376), while Crown_Seg now exists as a server tool; ASO simply does not call it.

Verified · no GPU, no network, no torch in ASO itself

The ASO environment declares neither torch nor pytorch3d (tools/ASO/pyproject.toml:8-21). The only GPU use of an ASO run is the prediction of ALI_CBCT, in Fully-Automated CBCT without supplied landmarks (tools/ALI/ALI_CBCT/src/sadt_ali_cbct/__init__.py:94, device = "cuda" by default).

Verified · a reproducible orientation

The triplet search is exhaustive up to max_triplets and seeded beyond it, with a local generator (ASO/geometry.py:323-391); the legacy used the global np.random, so the same request could orient differently from one run to the next. The tool's tests compare the ported geometry with the legacy functions (tools/ASO/tests/test_geometry_equivalence.py, part of the 205 tests run for this page).
