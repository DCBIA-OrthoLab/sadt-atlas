AMASSS on VISOR

How AMASSS runs in VISOR (client and server), what changed from the legacy Slicer module, and what the code of the port does: one binary nnU-Net v2 network per anatomical structure, now predicted side by side on a server. The legacy module is described on its own page.

VISOR sadt_amasss Legacy page Guide (VISOR) Bibliography

VISOR runs AMASSS on a server: Slicer only sends the scans and receives the segmentations. This page follows a run from the panel to the report: what runs where, which files do what, each step of the pipeline with the code that performs it, the arguments the server publishes, and how the port differs from the legacy module. Everything here was read in the code, not observed on a running server, and nothing here says that a given server is deployed.

References name the repository first: SADT-VISOR (tool code, tool/vface @ 6ba2a78), VISOR-serve (server, @ e9a7e5d), AutomatedDentalToolsRemote (Slicer client, @ 19b95e8) and legacy (SlicerAutomatedDentalTools @ 3c67957). A bare file name such as pipeline.py, catalog.py, layout.py, nnunet_runner.py, vtk_export.py, progress.py, errors.py or __init__.py is in the SADT-VISOR package tools/AMASSS/src/sadt_amasss/; AMASSS_CLI.py (AMASSS_CLI/) and AMASSS.py (AMASSS/) are legacy files. The AMASSS folder is identical on the SADT-VISOR main branch and at 6ba2a78 (no diff on tools/AMASSS).

Three paths reach the tool. A clinician fills the AMASSSRemote panel; AREG_CBCT asks for registration masks (CBMASK, MANDMASK, MAXMASK) before it registers; VFACE asks for the bone masks its regions and heat maps are keyed on. Both callers send the same fixed options, read in code:

sup.run("AMASSS", scans=..., model=..., structures=list(...),
        merge=["SEPARATE"], prediction_ID="seg", generate_surface=False)

One binary file per structure, because the caller then looks each region's mask up by name, and a merged volume would make every region resolve to the same file (AREG_CBCT tools.py:127-136; VFACE tools.py:149-153). A sup.run starts AMASSS as its own process in its own virtual environment, the same way the server starts it for a clinician (see Architecture). The callers are described on their own pages: AREG_CBCT on VISOR, VFACE on VISOR.

3. The pipeline at a glance

run() (__init__.py:20-109) turns the two list arguments into codes and calls segment() (pipeline.py:280-376), which checks the arguments, finds the scans and the models, then hands over to _run() (pipeline.py:379-558) for three phases that share the progress bar: reading (0 to 10 %), predicting (10 to 90 %), writing (90 to 100 %) (pipeline.py:391-395, 471, 492).

  1. Check arguments (pipeline.py:299-327): None takes the defaults, an empty list is refused, an unknown structure code or merge mode raises ToolInputError. §4
  2. Discover scans (pipeline.py:88-132): a file is taken as is, a folder is walked. §4
  3. Resolve models (pipeline.py:135-170): one model folder per requested code, or the code is listed as missing. §5
  4. Convert every scan once into a single nnU-Net input folder (pipeline.py:384-424). §4
  5. Predict: one predict_folder per structure, several at once (pipeline.py:426-488). §5
  6. Assemble each scan's outputs (pipeline.py:490-522, 561-657). §6
  7. Surfaces when generate_surface is true (vtk_export.py). §6.3
  8. Report and removal of the working folder (pipeline.py:362-369, 531-558). §6.4

4. Inputs: checks, discovery and conversion

4.1 From the panel's lists to codes

structures and merge are published as lists of fixed options (list[Literal[...]], __init__.py:28-31), which the schema generator turns into a multi-select (SADT-VISOR scripts/describe.py:240). catalog._codes_from() (catalog.py:108-135) accepts four shapes: None (the defaults), a single string, an iterable of codes or display names, and the old {name: bool} dictionary. The string branch exists because a bare string would otherwise be iterated character by character, so that no code matches; the comment records that merge once shipped that way and every run returned a report with no segmentation (catalog.py:115-126). Display names of the old schema ("Cranial base", "One merged segmentation file") are still translated (catalog.py:46-50, 102-105).

# pipeline.py:302-327 (shortened)
structures = tuple(DEFAULT_STRUCTURES if structures is None else structures)
merge = tuple(DEFAULT_MERGE_MODES if merge is None else merge)
prediction_ID = (prediction_ID or "Pred").strip() or "Pred"
unknown = [code for code in structures if code not in STRUCTURE_CODES]
if unknown:        raise ToolInputError("Unknown structure code(s): ...")
if not structures: raise ToolInputError("Select at least one structure to segment.")
if not merge:      raise ToolInputError("Select at least one output form ...")
unknown_merge = [code for code in merge if code not in MERGE_MODES]

The panel enforces the same minimum before the request leaves: min_selected = 1 on both lists (layout.py:47, 55).

4.2 Scan discovery

discover_scans() (pipeline.py:88-132): a path that does not exist raises FileNotFoundError; a file is returned as a one-element list with no filtering (:102-103); a folder is walked recursively with os.walk (:107). A file is kept if its name ends with one of the volume extensions of sadt_naming:

# SADT-VISOR naming/src/sadt_naming/__init__.py:36
VOLUME = (".nii.gz", ".nrrd.gz", ".gipl.gz", ".nii", ".nrrd", ".gipl")

and if is_previous_output() (pipeline.py:69-85) does not recognise it as an AMASSS result: a base name containing _<prediction_ID>_, or ending with _MERGED, with _<CODE> for one of the nine codes, or with _Seg / _SegOut. Only the number of skipped files is logged, never their names (:116-123). No file left: FileNotFoundError("No scan found ...") (:125-131), where the legacy called sys.exit(1). The list is sorted (:132), so case numbers follow the path order. The consequence for real patient names is in Findings.

4.3 Conversion to the nnU-Net input folder

Each readable scan is written once into .amasss_work/nnunet_input/ under a case name that carries no patient metadata, its position in the sorted list (pipeline.py:387-420):

# pipeline.py:396, 412
case_id = f"p_{index:03d}"
_convert_to_nifti(scan_path, os.path.join(nnunet_input, f"{case_id}_0000.nii.gz"))

# pipeline.py:191-194
image = sitk.ReadImage(scan_path)
sitk.WriteImage(image, destination)

The conversion is a real read and write for every format, .nii.gz included; the voxel type is left alone because nnU-Net's reader casts to float32 itself (pipeline.py:177-190). No intensity normalisation, windowing or resampling is written in the package: all of it is nnU-Net's, driven by each model's plans.json (resampling to the target spacing, then CTNormalization), as in the legacy (legacy §3). A scan that cannot be read is marked failed with "Unreadable input: ..." and logged by position ("scan 3 of 40"), not by name (pipeline.py:413-419); if none is readable the run stops with ToolInputError (:422-424). The index from p_NNN back to the file lives only in memory, in scan_records (:390-420).

5. Models and inference

5.1 The bundle and its lookup

The server hands the hidden model argument the whole DATA/AMASSS/models/ folder (layout.py:26-32). resolve_models() descends into it when it holds a single wrapping folder (for instance AMASSS_Models/) and none of the code folders directly (pipeline.py:143-153), then calls find_model_folder() for each requested code (nnunet_runner.py:50-72):

<bundle>/<CODE>/**/<Dataset...>__nnUNetPlans__3d_fullres/fold_0/checkpoint_final.pth

A candidate is accepted only once its fold_0/checkpoint_final.pth exists, so a half-copied bundle makes a structure unavailable rather than crashing the run. A code with no usable folder is logged and listed in the report's structures_without_model; only when no requested code has a model does the run fail, with ModelNotFoundError (pipeline.py:155-170). The README gives the shipped bundle as AMASSS_Models/, 2.1 GB (tools/AMASSS/README.md:48). The layout and the lookup are those of the legacy CLI (legacy AMASSS_CLI.py:87-109); what the bundle holds (nine binary PlainConvUNet models, two resolution families) is surveyed on the legacy page, legacy §4. The code does not say whether the server's copy is byte-identical to the archive the legacy widget downloads.

catalog.py is the single table every other file reads. Label values are those of the legacy LABELS["LARGE"], kept because AREG and existing datasets depend on them (catalog.py:52-64). The colours are new for labels 3 and 7 to 9 (catalog.py:67-80). TEETH, RC and MCAN are left out on purpose: no model ships for them (catalog.py:13-18).

5.3 Prediction: one model per structure, several at once

Predicting per structure over the whole folder loads each checkpoint once, not once per scan and structure (pipeline.py:384-386; nnunet_runner.py:198-203). That part is the legacy's design. What is new is that the structures overlap. The comment gives the reason measured on this pipeline: one nnU-Net call is a third inference and two thirds preprocessing on a single core, so a run left the card idle 78 % of its length (pipeline.py:428-434). Threads, not processes, because torch releases the GIL in its kernels and a process pool would need one CUDA context each (:436-439).

# pipeline.py:442, 446-453, 461-482 (shortened)
width = _channels_for(sup, len(models), num_workers)
def predict(item):
    code, model_folder = item
    structure_output = os.path.join(work_dir, f"pred_{code}")
    nnunet_runner.predict_folder(model_folder, nnunet_input, structure_output, device,
                                 tile_step_size=tile_step_size, gpu_resampling=gpu_resampling)
    return code, structure_output
progress.set_width(width)
with futures.ThreadPoolExecutor(max_workers=width) as pool:
    running = {pool.submit(predict, item): item[0] for item in models.items()}
    for future in futures.as_completed(running):
        progress.report(done, len(models), "structure", start=0.1, end=0.9)
        ...  # a failure goes to failed_structures, the others continue
progress.set_width(None)

Where the width comes from. _channels_for() (pipeline.py:235-277) asks the supervisor for one channel per structure that has a model; the server answers with what the run's reserved share can pay for, at least one (VISOR-serve server/execution/runner.py:2134-2148). A positive num_workers is a ceiling on the ask, never a floor; without a supervisor (a test, a direct call) the width is 1 unless num_workers names a number (pipeline.py:261-271). If asking fails, the run continues one structure at a time (:272-277). On the server side, width_from = "structures" makes admission reserve as many channels as structures ticked, not as many as scans (VISOR-serve server/deployment.toml:162-179); the reservation only exists because the schema declares num_workers (VISOR-serve server/execution/concurrency.py:145; comment at pipeline.py:243-250). progress.set_width() declares the width around this phase only, so the server learns what one channel costs from the real peak (progress.py:41-57).

5.4 The nnU-Net predictor

_build_predictor() (nnunet_runner.py:75-117) sets the same options as the legacy BuildPredictor() (legacy AMASSS_CLI.py:112-137), with the step size now an argument:

# nnunet_runner.py:85-96, 116
options = {
    "tile_step_size": float(tile_step_size),   # 0.5 by default: 50 % overlap
    "use_gaussian": True,                      # gaussian weighting of the patches
    "use_mirroring": False,                    # = --disable_tta, no test-time mirroring
    "device": torch.device(device),
    "verbose": False, "verbose_preprocessing": False, "allow_tqdm": False,
}
# perform_everything_on_device / _on_gpu: whichever the installed nnU-Net declares
...
torch.backends.cudnn.benchmark = False

The last line has no legacy counterpart. The comment explains it: nnUNetPredictor.__init__ turns cuDNN autotuning on, autotuning picks a convolution by timing, so the result depended on how busy the card was; seven runs of one scan gave three different masks, and with structures now overlapping that would become the normal case (nnunet_runner.py:104-115). The sliding window itself, its patch size and the Gaussian weighting are nnU-Net's, from the model's plans; the tile_step_size docstring records that 0.7 moves the mask (Dice 0.995 against 0.5), which is why it stays at nnU-Net's default (__init__.py:72-74).

predict_folder() (nnunet_runner.py:190-236) loads fold 0 from an explicit path (initialize_from_trained_model_folder(model_folder, use_folds=(0,), checkpoint_name="checkpoint_final.pth"), no nnUNet_results variable), then:

  • with GPU resampling in force: predict_from_files_sequential, everything in this process, because spawned workers would each need their own CUDA context (:216-227);
  • on CPU, or with gpu_resampling=False: predict_from_files with two preprocessing and two export processes (:228-236). The legacy always used the sequential call (legacy AMASSS_CLI.py:232-237).

resolve_device() falls back to CPU with a warning when CUDA is requested and no card is visible (nnunet_runner.py:37-47).

5.5 GPU resampling

_enable_gpu_resampling() (nnunet_runner.py:128-187) is the legacy EnableGpuResampling() (legacy AMASSS_CLI.py:148-201) made optional. nnU-Net resolves its two resampling functions by name from the configuration dictionary, so rewriting the names redirects both ends without monkeypatching:

# nnunet_runner.py:165-185 (shortened)
if any(configuration.get(key) != "resample_data_or_seg_to_shape" for key in _RESAMPLING_KEYS):
    return False          # a bundle asking for another resampler is left alone
for key in ("resampling_fn_data", "resampling_fn_probabilities"):
    configuration[key] = resample_torch_fornnunet.__name__
    configuration[f"{key}_kwargs"] = {"is_seg": False, "device": torch.device(device), "mode": "linear"}
for key in _RESAMPLING_KEYS:   # both are @property @lru_cache
    getattr(type(configuration_manager), key).fget.cache_clear()

It applies only on CUDA and only if nnU-Net ships the torch resampler (:145-158). The numerical difference is the input data's interpolation, order 3 to order 1, torch having no 3D cubic mode (:171-174). The docstring puts resampling at roughly seven times the network's time, and the argument's at roughly seven times less resampling time on the GPU (nnunet_runner.py:131-133; __init__.py:75-78). Unlike the legacy, an out-of-memory error is not retried on the CPU path: see Findings.

6. Assembly, outputs and the report

6.1 Per-scan assembly

Once every structure has run, each readable scan is assembled in turn (pipeline.py:490-522) by _assemble_scan_outputs() (pipeline.py:561-657): read pred_<CODE>/p_NNN.nii.gz for each predicted structure (a missing file is logged by case id and skipped, :581-588), binarise with array > 0 (:590), then write:

  • SEPARATE when requested, or whenever only one structure was produced: one binary file per structure (:599-606);
  • MERGED when requested and at least two structures exist: painted in MERGING_ORDER, where a later structure overwrites an earlier one on shared voxels (:625-633; order at catalog.py:87-97).
# pipeline.py:626-630 ; catalog.py:87-97
merged = np.zeros(shape, dtype=np.int16)
for code in MERGING_ORDER:   # SKIN, CV, UAW, CB, MAX, MAND, CBMASK, MANDMASK, MAXMASK
    if code in masks:
        merged = np.where(masks[code] == 1, LABELS[code], merged)

_write_segmentation() (pipeline.py:216-228) casts to int16, copies the reference scan's spacing, origin and direction, and passes through _match_reference_geometry() (:197-213), which resamples with nearest neighbour only if the geometry differs, a no-op in the normal case. It writes with useCompression=True.

6.2 File names and extensions

base is the scan name without its volume extension (sadt_naming.split_extension); the output extension is the compressed form of the input's (pipeline.py:570-576):

# SADT-VISOR naming/src/sadt_naming/__init__.py:60, 77-79
_COMPRESSED = {".nii": ".nii.gz", ".gipl": ".gipl.gz", ".nrrd.gz": ".nrrd"}
def compressed_extension(extension): return _COMPRESSED.get(extension.lower(), extension)

The comment gives the reason: a label volume compresses about a hundredfold, and a nine-structure run on a 0.33 mm CBCT wrote 1.75 GB uncompressed against 14 MB compressed (pipeline.py:571-575). A .nrrd.gz input becomes .nrrd written with compression.

With the callers' prediction_ID="seg", AREG_CBCT and VFACE therefore receive <base>_seg_SegOut/<base>_seg_CBMASK.nii.gz and the like.

6.3 Surfaces

When generate_surface is true, vtk_export.py builds one mesh per structure (separate) or one per label appended into a single file (merged). The geometry is meant to be the legacy's; two stages were replaced after the module docstring reports them identical, points, cells and triangles, on a real mandible (vtk_export.py:7-20):

# vtk_export.py:83-118 (shortened)
image = _image_from_mask(mask, reference)      # numpy buffer straight to vtkImageData, no temp .nrrd
contour = vtk.vtkFlyingEdges3D(); contour.SetValue(0, 0.5)   # replaces vtkDiscreteMarchingCubes
smoother = vtk.vtkSmoothPolyDataFilter(); smoother.SetNumberOfIterations(max(0, int(smoothing)))
reduction = min(max(int(decimation), 0), 99) / 100.0
if reduction > 0:
    decimator = vtk.vtkDecimatePro(); decimator.SetTargetReduction(reduction)
    decimator.PreserveTopologyOn(); decimator.SetFeatureAngle(60)

Decimation is new: 90 % by default, which the comment says moves a cranial-base surface by 0.059 mm on average, against 1.6 million triangles for a cranial base without it (vtk_export.py:99-109; __init__.py:63-69). Each cell gets one flat colour from LABEL_COLORS (:120-129), the writer is binary, about a third the size of ASCII and exact (:139-151), and meshes are built in a thread pool of the same width as the inference, then written in the run's order (:155-176; pipeline.py:505-509). The structure code is passed in, no longer parsed back out of the file name (vtk_export.py:29-32, 179-205); an unknown label in a merged volume is skipped with a warning (:244-249). Meshes are in the image's physical frame (spacing and origin, vtk_export.py:60-61), with no LPS/RAS flip; the direction matrix is not applied, as in the legacy (legacy §5.4). surface_smoothing and surface_decimation are hidden technical arguments.

structures_without_model, structures_failedno model folder; prediction raised (with the message)

A scan whose assembly raises is recorded as failed and the batch continues (pipeline.py:512-520); a scan with no segmentation written can never count as processed (:648-657). The run raises only if every structure failed (:484-488) or no scan was processed (:524-529). The working folder, with the NIfTI copies and every pred_<CODE>/, is removed in a finally block (:362-366), and the report is written after it (:368-369).

Cohorts. A cohort can be split by the panel: once model and output_dir are set aside, scans is the only required path, so it is the axis the server publishes for batching (VISOR-serve server/registry/conventions.py:158-190, 193-216). The panel splits a folder by its top-level entries, sorted by name, at 25 entries or 400 MB, whichever binds first (ServerToolsCoreLib/slicer_io.py:208-245; defaults VISOR-serve server/config.py:192, 196), sends one run per batch into batch_NN/ folders, then folds them back into the output folder, keeping the first file when two batches wrote the same name (base_widget.py:2161-2226). For AMASSS that name collision hits the report: see Findings.

Resources and time limits. deployment.toml declares no timeout_seconds and no max_upload_mb for AMASSS, so the server defaults apply: no time limit (TOOL_TIMEOUT_SECONDS = 0), upload cap 500 MB, and a cohort is split into batches of at most 400 MB or 25 files (VISOR-serve server/config.py:77, 240, 192, 196). The one AMASSS entry is width_from = "structures": the parallel width reserved is the number of structures ticked, not the number of scans (VISOR-serve server/deployment.toml:162-179).

The tool has its own virtual environment, built by uv from its lockfile; nothing is installed into Slicer. The pins are those of the stack the server already ran, not upstream's torch 2.2.0 / nnunetv2 2.8.0, because no AMASSS result had been produced on the latter (tools/AMASSS/pyproject.toml:5-10; README.md:73-85).

Models are expected under the server's DATA/AMASSS/models/; the test scan used for validation is DATA/AMASSS/testfiles/MG_test_scan.nii.gz (README.md:105-107). Tests and validation. tests/test_run.py has 61 test functions (counted with grep); the CI suite stubs nnunet_runner.predict_folder and runs without checkpoints, and the real-model test needs SADT_AMASSS_MODELS and SADT_AMASSS_SCAN (tests/data/README.md). Those figures are the README's; they were not reproduced for this page. See also Tests and provenance.

11. Findings in VISOR

Scans are skipped silently when their name looks like an output

When scans is a folder, a file is left out if its name (without extension) contains _<prediction_ID>_, ends with _MERGED, ends with one of the nine structure codes (_MAND, _MAX, _CB, _CV, _UAW, _SKIN, _CBMASK, _MANDMASK, _MAXMASK) or ends with _Seg or _SegOut (SADT-VISOR pipeline.py:69-85, applied at pipeline.py:111-113). A patient file called P01_CB.nii.gz or P01_Seg.nii.gz is therefore ignored. Only a count is logged, never the names (pipeline.py:119-123); if every file is ignored, the run stops with "No scan found" (pipeline.py:128-131). A single file passed as scans is never filtered (pipeline.py:102-103). The legacy also skipped some names (any name with MASK, any _<ID>_: legacy AMASSS_CLI.py:770-777), but not these suffixes.

A split cohort keeps the report of its first batch only

When the panel splits a cohort, every batch writes AMASSS_report.json at the root of its own batch_NN/ folder (SADT-VISOR pipeline.py:368). The client merges batch reports only for a module that names its report in RUN_REPORT (AutomatedDentalToolsRemote ServerToolsCoreLib/base_widget.py:1493, 1559-1562, 2192); AMASSSRemote does not (AMASSSRemote/AMASSSRemote.py:63-98), unlike AutoCrop3D, ALI, CNE, AutoMatrix, GreedyReg and DOCShapeAXI. When the batch folders are folded back, a name already present is kept and the later one dropped with a log warning (base_widget.py:2205-2226). The report left in the output folder therefore describes the first batch (25 entries at most), while the masks of every batch are there. Read in code, not observed.

Disk footprint: nothing is cleaned until the end

The tool keeps, for the whole run, an NIfTI copy of every scan (nnunet_input, SADT-VISOR pipeline.py:387-388, 412) and one pred_<CODE> folder per structure (pipeline.py:448). They are removed only by the rmtree of pipeline.py:366. The legacy removed nnunet_input right after inference and each scan's predictions right after its assembly (legacy AMASSS_CLI.py:872, 651-656). On a large cohort the peak disk use under output_dir is therefore higher than the legacy's; whether that is intended is not stated in the code.

GPU resampling lowers the input interpolation order, by default

gpu_resampling defaults to true. When it applies, the input data is resampled with torch in linear mode instead of nnU-Net's cubic spline: the code comment says this is the whole numerical difference with a stock nnU-Net run (SADT-VISOR nnunet_runner.py:171-179). It is ignored on CPU, and left alone if the model plans request another resampler (nnunet_runner.py:128-187). The report records the value requested on a CUDA device; a bundle whose plans opt out is only mentioned in the log (pipeline.py:534-538). The argument is hidden in the panel. The legacy CLI does the same substitution, without a way to turn it off (legacy AMASSS_CLI.py:148-201, 239-240).

No GPU memory retry

The legacy retried an out-of-memory structure with scipy resampling (legacy AMASSS_CLI.py:240-251). VISOR has no such handler: the structure goes to structures_failed in the report (SADT-VISOR pipeline.py:475-478, 550), the run continues with the others, and fails only if all of them fail (pipeline.py:484-488). With several structures now resident on the card at once (§5.3), the width the server grants is what keeps memory in bounds.

What the panel loads into the scene

Results are loaded only when the run produced 12 loadable files or fewer; above that, nothing is loaded and a dialog points to the folder (AutomatedDentalToolsRemote AMASSSRemote/AMASSSRemote.py:82; ServerToolsCoreLib/base_widget.py:1596-1602). The patterns are *.nii.gz, *.nii, *.nrrd, *.nrrd.gz as label maps and *.vtk as models (AMASSSRemote.py:92-98): a .gipl input, whose masks come back as .gipl.gz (SADT-VISOR naming/src/sadt_naming/__init__.py:60), produces files that are saved but not loaded.

Verified: no shared working folder between runs

Each run works under its own <output_dir>/.amasss_work and removes it once inference has started, whether it succeeds or fails (SADT-VISOR pipeline.py:59-62, 330-331, 342-366). The folder is created before the scans and models are looked up (pipeline.py:331-336), so a run that finds no scan leaves it behind, empty. The two legacy bugs about a shared and wiped temporary folder (legacy §6 and legacy §9) do not apply.

Verified: structured report and early validation

The report lists the structures without a model, the structures that failed, and a status, an error and a duration per scan (SADT-VISOR pipeline.py:497-558). Unknown structure or merge values are refused before any inference (pipeline.py:306-327). The legacy CLI checks neither: an unknown structure becomes a missing model, and an unknown merge mode is caught scan by scan, after inference (AMASSS_CLI.py:723-732, 623-627). cuDNN autotuning is switched off (nnunet_runner.py:116); the code comment gives the reason, autotuning made the same scan give different masks depending on the load of the card (nnunet_runner.py:104-115).

Verified: no file name in logs or progress

The tool names a scan by its position in the batch or by its case id, in the log and in the progress messages the server stores and shows (SADT-VISOR pipeline.py:116-118, 414-417, 584-587; progress.py:13-15, 100). The legacy logged the path of an unreadable scan (legacy AMASSS_CLI.py:713). The file name is still in the report's cases[].input (pipeline.py:399), which goes back to the caller with the results.

Models are never sent by the clinician

A model is published as a name, never as a file argument, so weights cannot be uploaded from a laptop (VISOR-serve server/registry/conventions.py:14-16), and the argument is hidden in the AMASSS panel (SADT-VISOR layout.py:32). See Security and privacy.
