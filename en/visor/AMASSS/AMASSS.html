AMASSS on VISOR

AMASSS cuts a head scan into anatomical structures with one network per structure, one voxel at a time. This page explains how a run goes in VISOR, step by step, with the maths of the parts that are computation rather than learning: how the scan is normalised, how the network’s patches are blended, how masks are merged and surfaces built. Where the code does something worth checking, a link leads to the code page. The legacy module is described on its own page.

Code (developers) VISOR sadt_amasss Legacy page Guide (VISOR) Bibliography

Overview: what goes in, what comes out

AMASSS takes a 3D head scan (CBCT) and cuts it into anatomical structures: lower jaw, upper jaw, cranial base, upper airway, neck vertebrae, skin and three registration masks. It does so with one network per structure: each network answers one question for every voxel, “is this voxel part of my structure?”.

InWhat happensOut
a scan (.nii.gz, .nrrd, .gipl...) or a folder of them, and the list of structures wantedeach scan is converted, then each structure is predicted by its own network (several at once on the server), and the masks are assembledone binary mask per structure and/or one merged label map per scan, optional 3D surfaces (.vtk), and AMASSS_report.json

The networks are the legacy ones; nothing is trained here. What changed is where the work runs, how several structures are predicted side by side, and how a run is reported.

1. Status and position in the chain

The pipeline, a run report and a test suite exist in the port. Not ported: DICOM input, the small-field option, the teeth, root canal and mandibular canal models, and the option to save into a per-scan folder. Three paths reach the tool: a clinician fills the Slicer panel; AREG_CBCT asks for registration masks (CBMASK, MANDMASK, MAXMASK) before it registers; VFACE asks for the bone masks its regions and heat maps are keyed on. Both tools ask for one file per structure, because they look each mask up by name. AMASSS calls no other tool.

In the codeCallers, state of the port, and what each side runs

What runs where

  • On the server: reading and converting the scans, one prediction per structure, merging, optional surfaces, the report, and the work folder.
  • In Slicer: choosing the scan (a file, or a folder zipped before upload), the structures and the merge mode; receiving a zip of the results and unpacking it; loading the results into the scene when there are 12 or fewer; splitting a large cohort into batches.
  • Nothing is installed in Slicer and no model is downloaded: the models are hosted on the server.
In the codeThe where-it-runs table with file and line

2. Files involved

The tool is a plain Python package with no knowledge of the server: it receives paths and returns a path. Its parts are a public entry point, the pipeline itself, a wrapper around nnU-Net, the table of structures, the surface exporter, a progress reporter and the layout of the panel. The server and the Slicer panel add the rest: hidden arguments, upload, cohort splitting and loading.

4. Inputs: checks, discovery and conversion

4.1 From the panel's lists to codes

The structures and the merge forms are chosen from fixed lists. An unknown structure or merge form is refused before any inference, and an empty choice is refused too: the panel enforces the same minimum before the request leaves.

4.2 Scan discovery

A single file is taken as is. A folder is walked, and files are kept if they carry a volume extension and do not look like an earlier AMASSS result (a name containing the prediction ID, ending in _MERGED, in a structure code, in _Seg or _SegOut). The list is sorted, so case numbers follow the path order. Skipped files are counted, never named in the log.

4.3 Conversion to the nnU-Net input folder

Each readable scan is read and rewritten once into a private folder, under a case name that carries no patient information (p_000, p_001...). The voxel type is left alone because nnU-Net casts to float itself. No normalisation, windowing or resampling is done here: all of it belongs to nnU-Net and is driven by each model’s plan (section 5.4). A scan that cannot be read is marked failed and the run goes on.

In the codeArgument checks, discovery, case naming and conversion

5. Models and inference

5.1 The bundle and its lookup

The server hands the tool the whole folder of models. For each requested structure the tool looks for one model folder holding the trained checkpoint (a single fold). A structure with no usable folder is listed in the report as having no model, and the run fails only if none of the requested structures has one. The bundle holds nine binary networks, in two families: full-field models (mandible, maxilla, cranial base, cervical vertebra, upper airway, skin) and the three registration masks, trained separately at a finer resolution.

5.2 Structures, labels and colours

One table gives every structure its label value (used in the merged volume) and its colour. The label values are the legacy ones, kept because AREG and existing datasets depend on them. The three masks are separately trained models used by AREG, not a post-processing of the cranial base, mandible and maxilla.

5.3 Prediction: one model per structure, several at once

The loop is per structure over the whole folder, so each model is loaded once, not once per scan. What is new is that structures overlap: one nnU-Net call is a third inference and two thirds preprocessing on a single core, so a run used to leave the graphics card idle most of the time. The tool runs structures side by side in threads. The server decides the width from the room it reserved, at most one channel per structure; a number given by the user is a ceiling, never a floor.

In the codeThe thread pool, the width the server grants and the progress counting

5.4 The nnU-Net predictor

The network is a 3D convolutional U-Net, chosen and configured by nnU-Net from each model’s plan. Two steps of the predictor are pure computation, and they are the ones that decide what the network sees and how its answers are put together.

Test-time mirroring is off and Gaussian weighting is on. One setting has no legacy counterpart: the tool switches off cuDNN autotuning, because autotuning picks a convolution by timing it, so the same scan gave different masks depending on how busy the card was. The step is kept at nnU-Net’s default of 0.5: the code records that 0.7 moves the mask.

In the codePredictor options, cuDNN autotuning and the fold loading

5.5 GPU resampling

nnU-Net spends most of its time resampling, around seven times what the network itself takes, according to the code comment. On a graphics card the tool replaces that step with a torch version, which makes the run much faster. The price is a small numerical difference in how the input is interpolated. It applies only on a CUDA device, and the setting is hidden in the panel. Unlike the legacy, an out-of-memory error is not retried on the CPU path.

In the codeThe resampler substitution and the safeguards

6. Assembly, outputs and the report

6.1 Per-scan assembly

Once every structure has run, each scan is assembled in turn: the prediction of each structure is read back and turned into a binary mask (any value above zero), then written as one file per structure, as one merged label map, or both. A merged map needs at least two structures; with one, the separate file is written anyway.

Each mask is cast to 16-bit integers, given the scan’s spacing, origin and direction, and written compressed. Its geometry is checked against the scan and resampled by nearest neighbour only if it differs, which does not happen in the normal case.

In the codeThe assembly function and the merge order

6.2 File names and extensions

Every scan gets its own result folder, named after the scan and the prediction ID. Inside are one file per structure (<base>_<ID>_<CODE>), the merged map (<base>_<ID>_MERGED), and the surfaces if requested. The output uses the compressed form of the input’s extension: a label volume compresses about a hundredfold, and a nine-structure run on a 0.33 mm scan wrote 1.75 GB uncompressed against 14 MB compressed. AMASSS_report.json sits at the root of the output folder. AREG_CBCT and VFACE, which use the prediction ID seg, receive files such as <base>_seg_SegOut/<base>_seg_CBMASK.nii.gz.

In the codeExtensions, the naming helper and the output table

6.3 Surfaces

Each triangle gets one flat colour from the structure’s colour; the writer is binary, about a third the size of text and exact. Meshes are in the image’s own coordinates, with no flip between LPS and RAS, as in the legacy. The smoothing and decimation settings are hidden in the panel.

In the codeThe contour, smoothing, decimation and writer in the code

6.4 The report and the cleanup

AMASSS_report.json lists the options of the run, the structures requested, predicted, without a model and failed, and for each scan a status, an error, the files produced and a duration. A scan whose assembly fails is recorded and the batch goes on; the run fails only if every structure failed or no scan was processed. The private work folder is removed whatever happens, then the report is written.

9. Environment

The tool has its own virtual environment on the server, built from a lock file; nothing is installed into Slicer. It uses Python 3.11 with pinned versions of torch, nnU-Net, SimpleITK, NumPy and VTK. The versions are those of the stack the server already ran, and the models are expected under the server’s data folder. The exact table, the test suite and the validation figures are on the code page.

11. Findings in VISOR

Each point is checked in the code and described, with its evidence, on the code page; the list also appears in the findings.

  • Scans can be skipped silently when their name looks like an output, for example P01_CB.nii.gz. Evidence.
  • A split cohort keeps the report of its first batch only, while the masks of every batch are present. Evidence.
  • Nothing is cleaned until the end, so peak disk use is higher than the legacy’s. Evidence.
  • GPU resampling lowers the input interpolation order by default. Evidence.
  • No retry after a GPU memory failure: the structure is reported failed. Evidence.
  • The panel loads results into the scene only up to 12 files; a .gipl input gives masks that are saved but not loaded. Evidence.
  • Verified good points: no shared working folder between runs (evidence), a structured report and early validation (evidence), no file names in logs (evidence), and models never sent by the clinician (evidence).
