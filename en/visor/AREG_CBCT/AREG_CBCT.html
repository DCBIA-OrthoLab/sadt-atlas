AREG_CBCT on VISOR

AREG_CBCT puts two CBCT scans of the same patient, taken at different times, in the same position, so that what changed between them can be compared. This page explains how, step by step, with the maths: what goes in, what each step does to it, and what comes out. Where the code does something worth checking, a link leads to the code page. The legacy module is on its own page.

VISOR Code (developers) AREG_CBCT reached as AREG, mode CBCT engine CPU only, elastix Legacy page Guide (VISOR) Bibliography

Overview: what goes in, what comes out

A patient is scanned twice: once at the start (T1, the baseline) and once later (T2, the follow-up). To see what treatment or growth really changed, the two scans must first be put in the same position. AREG_CBCT finds the rigid motion (a rotation and a translation, six numbers) that brings T2 onto T1. It does not use the whole head for that, only a bone region that should not have changed: the cranial base, the mandible or the maxilla. Whatever differs elsewhere then shows up as a true difference.

What it takes and gives
Inputa T1 and a T2 CBCT of the same patient, as files, as folders, or as DICOM series; in Semi-Automated mode, also the masks of the T1
Methoda masked T1 is compared with the T2 by mutual information, and an optimiser searches the six numbers of the motion, from coarse to fine (section 3.3)
Outputfor each ticked region: the T2 moved onto the T1 (written on the grid of the original T2), the transform file (.tfm), and a report (AREG_report.json) that says what worked and what did not
ModesSemi-Automated (you provide the masks), Fully-Automated (the masks are predicted by AMASSS), Oriented + Fully-Automated (the T1 is also put in a standard orientation first, by ASO)

The engine itself learns nothing and uses no GPU. The two networks involved, for the masks and for the orientation landmarks, live in other tools that the engine calls (section 3.2).

1. Position in the chain

A client never names AREG_CBCT. The Slicer module sends a request to a server tool called AREG with the mode “CBCT”; the server hands it to this engine. The engine does the pairing and the registration. It asks AMASSS for the masks and, in the oriented mode, ASO for the orientation (which in turn asks ALI_CBCT for landmarks). Each tool runs in its own environment, and nothing calls AREG_CBCT back: it is the root of its own graph.

What has been checked. The engine is implemented and tested: 101 automated tests pass, among them elastix on a synthetic phantom. The authors state that the whole chain has not been run end to end with the real tools, and that nothing was compared with the pre-port implementation. No timeout, width or memory limit is declared for this engine.

2. Files involved

The engine is small. One part publishes the form (the arguments and their types), one part checks every combination of arguments and drives the run, and three parts compute: pairing and mask lookup, the registration with elastix, and the resampling and writing. What the three AREG engines share, such as the naming rules and the list of file extensions, sits in a package with no dependency at all.

3.1 Inputs, DICOM and pairing

Each input becomes a folder: a folder is used as it is, and a single file is linked into a folder of its own, so that the other time point is never mistaken for a neighbour. DICOM series are converted in a scratch folder and the input is never touched. If the folder sent is a whole cohort with T1/ and T2/ inside, the engine descends into them; a folder that mixes the two time points is refused rather than paired by chance.

The T1 and the T2 of a patient are matched through a patient key: the file name without its extension, without the suffixes a previous run leaves behind (_Scanreg, _seg, _Or and similar), and without the time-point words t1, t2, t0. Only those whole words count, so P1_T1_scan.nii.gz and P1_T2.nii.gz both give P1, while P001_T3 stays P001_T3 and pairs with nothing. A subject found at one time point only is listed as unmatched in the report, and a run in which nothing pairs stops with an error that spells out the naming rule.

3.2 Orientation and masks: the two calls to other tools

Before any scan is read, the engine refuses what cannot work: no region ticked, Semi-Automated without masks, an automatic mode on a server without the other tools, or the oriented mode without a reference.

Orientation (Oriented mode only). The T1 alone is sent to ASO, which finds seven landmarks on it through ALI_CBCT (Ba, S, N, RPo, LPo, ROr, LOr, the Frankfurt set) and rotates the scan onto a reference. The T2 is never oriented. The oriented T1 replaces the original for the rest of the run.

Masks (both automatic modes). One call to AMASSS on the T1 returns the masks of the ticked regions together with any structure you asked to get back (cranial base, cervical vertebrae, mandible, maxilla, skin, upper airway). Only the T1 is segmented.

Finding the mask of a region. Folders of masks are tried in order (yours first, then the T1 folder or the AMASSS output) and the first one that holds a mask for the patient wins. A file is a mask of a region only if its name contains a segmentation word and a region word, both as whole words:

RegionWords that name it
Cranial basecb, cbmask, cranialbase, cranial
Mandiblemand, md, mandmask, mandible
Maxillamax, mx, maxmask, maxilla

A patient with no mask for a region fails for that region only, with a reason that gives the naming rule.

3.3 The registration

For one patient and one region the engine reads the T1, the mask and the T2, applies the mask to the T1, lets elastix search the motion, and writes the T2 moved onto the T1. The scene below replays these steps on a published test set; the cards after it explain what each step computes.

The settings are the ones a registration of the same patient needs and nothing else: a rigid motion with six degrees of freedom, Mattes mutual information on 64 grey-level bins, three resolution levels, a conjugate-gradient optimiser (step from 2.0 down to 0.001), and a regular grid of sample points with a single thread so that two runs give the same transform. Elastix starts from the geometric centre of the two images. Elastix also receives no separate mask: the zeroed voxels are the mask.

A problem with one region does not stop the others. A mask of the wrong size, a label the mask does not hold, or an elastix error marks that region as failed, with its reason, and the loop goes on. A patient is reported “ok” as soon as one region was registered.

In the codeThe register function, the masking rules, the full parameter table and the matrix conversion

3.4 Outputs and the report

The tool returns one folder, archived and sent back. For every region and patient it holds the registered T2 (on the T2 grid, as 16-bit integers, in the same file format as the input in compressed form) and a transform file named <patient>_<REGION>_Reg_transform.tfm, which maps points of the T1 frame to the T2 frame, in the ITK (LPS) convention. The suffix Reg can be changed. The structures you ticked come back under Segmentations/.

AREG_report.json lists, per patient and per region, whether it worked, which mask was used, the direction of the transform and any note, plus the subjects that did not pair and a summary of how many patients were registered or failed.

6. Environment

The engine runs on the CPU, in a Python environment of its own built from a lock file, with elastix as its one heavy dependency (elastix is checked once before any scan is read, so a batch of 40 patients does not fail 40 times). The models it needs are held by the server: the AMASSS bundle, and the two orientation references. No GPU is needed by the engine; AMASSS and ALI_CBCT, reached in the automatic modes, run in their own environments. No time limit is set.

8. Findings in VISOR

Each point is checked in the code and written up, with its evidence, on the code page; the list also appears in the findings.

  • The elastix transform is now exact. The centre of rotation is read and applied, and the unit tests recover a known transform. Evidence.
  • Unpaired subjects are reported instead of vanishing. Evidence.
  • Oriented mode with the Occlusal reference should end in a refusal, because the call to ASO sends no landmark list and the two references carry different landmarks. Read in the code, not run. Evidence.
  • The scratch folder is not removed when a run fails in an unexpected way, so copies of the inputs could end up in the archive. Not triggered. Evidence.
  • A declared dependency is never used: the engine lists torch, which none of its modules imports. Evidence.
  • A docstring promises a mask rule the code does not have. Harmless in the automatic modes; a Semi-Automated folder of masks with unusual names finds no mask. Evidence.

9. Literature

The method is the one published for the legacy module (voxel-based rigid registration on a masked stable region); the bibliography of the tool, with the points where the code departs from the paper, is on its sources page and in section 12 of the legacy page. The port adds no publication of its own.
