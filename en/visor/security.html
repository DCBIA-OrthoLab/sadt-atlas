Security and privacy in VISOR

What the VISOR stack protects today, what it only specifies, and what it does not have. The server checks one shared Bearer token and refuses hostile archives and paths; the client insists on a verified HTTPS connection. Nothing de-identifies the files before they leave the workstation, the server speaks plain HTTP, and attestation and key exchange exist only in a separate research prototype.

VISOR-serve e9a7e5d AutomatedDentalToolsRemote 19b95e8 SADT-VISOR 6ba2a78 volume_crypto d975dab (prototype)
How to read this page

Every statement about code is cited as repository file:line, with the repositories abbreviated VISOR-serve (the server), Remote (AutomatedDentalToolsRemote, the Slicer client), SADT-VISOR (the tools) and volume_crypto (a separate prototype), at the commits above. Implemented and tested means that code exists and a test in the repository targets it; the VISOR-serve and Remote tests were not run for this page, so it does not mean that they pass today. The legacy extension described by the rest of this atlas (commit 3c67957) has no server at all and none of what follows applies to it.

2. Authentication: one shared token

Every route that does work depends on verify_token: the scheme must be Bearer, and the credential is compared to API_TOKEN with secrets.compare_digest, a constant-time comparison; anything else is a 401 (VISOR-serve server/wire/security.py:13-31). The tests feed it malformed and wrong headers and check that the token is never echoed back (server/tests/test_security.py:43,50). The routes concerned include /status (main.py:447), /maintenance (:518), /uploads (:833), /results/{id} (:918), /runs/{id} (:990) and POST /run/{tool} (:1806).

There is one token for everybody. The configuration says it itself: "there is one shared API token and no client identity anywhere" (VISOR-serve server/config.py:226-227). The server cannot tell ten workstations from one clicking ten times, and nothing expires, rotates or revokes the token. The client keeps it in clear in Slicer's native settings file (qt.QSettings, Remote .../settings_qt.py:63-66).

Routes without a token

GET /health (main.py:422, returns {"status":"ok"}) and GET /tools (main.py:551) answer without credentials. The second returns the schema of every registered tool: names, arguments, types, extensions. This is on purpose, the test calls the two routes "deliberately unauthenticated" and checks that /run is not (test_security.py:59-63), and the server's own audit lists it as a medium-severity gap (VISOR-serve SECURITY.md, table of section 2, row 6).

The default token and the network exposure

API_TOKEN has no default in the server's settings (server/config.py:27), but the compose file supplies one: API_TOKEN=${API_TOKEN:-dev-token} (VISOR-serve docker-compose.yml:86,115,208). The client ships the same value as its default (Remote .../config.py:21), next to a placeholder server address, https://set-your-server.invalid, so nothing is sent before a server is configured. The install helper does better: scripts/server_ctl.py up generates secrets.token_urlsafe(32) (:396), writes it to .env with mode 0600 (:335) and keeps it on later runs.

The published port follows BIND_ADDR: unset, it is published on every interface (docker-compose.yml:35, and the comment at :23-27 explains that this is meant for a lab server behind a TLS terminator); server_ctl.py writes BIND_ADDR=127.0.0.1 for a local install (:368,398).

Verified in the compose file

Started with docker compose up and no API_TOKEN in the environment, the server runs with the token dev-token, and with no BIND_ADDR it listens on every interface. The generated token and the loopback binding come from server_ctl.py only.

3. Transport: strict client, plain-HTTP server

Client. require_https refuses every URL that is not https://, http://localhost included (Remote ServerToolsCore/ServerToolsCoreLib/tls.py:68-82). The certificate is verified against the certifi bundle, named explicitly so that no environment variable can swap the authorities (tls.py:84-93); there is no custom CA, no pinning, and never verify=False (tls.py:15-19). The deploy path built on urllib also refuses every redirect, since a redirect is how https:// would turn into http:// (tls.py:96-103), and the requests session mounts an adapter that refuses http:// (client.py:607,663). The old VerifyTls setting is no longer read back, so a machine that once stored False does not keep verification off (settings_qt.py:51-57).

Server. It speaks plain HTTP: uvicorn.run(app, host="0.0.0.0", port=8000) (VISOR-serve server/main.py:2368) and the image runs uvicorn without any certificate option (docker/Dockerfile:232). server/README.md:138-155 shows a self-signed certificate "for local development only" passed to uvicorn by hand. .env.example states the consequence: exposing the port is "only acceptable behind a TLS terminator".

Verified: the two ends only meet through a terminator

The client refuses plain HTTP and, by its own docstring, the self-signed certificate that a server presents on its own port, "including when it runs on this very machine" (tls.py:21-26). A Slicer client therefore cannot talk to a bare container: it needs a terminator with a publicly signed certificate in front. Whether one stands in front of a given instance is a fact of that deployment, not of the repositories.

4. Files and archives

extract_zip (VISOR-serve server/file_utils.py:125-174) examines every member before extracting anything: the resolved target must stay under the extraction root (os.path.commonpath, :159), a symbolic-link member is refused (:163), and only then does extractall run (:172). Tests cover zip slip, an absolute member and a symbolic link (server/tests/test_security.py:211,221,229).

Identifiers and names are treated as hostile too. Upload and result ids are secrets.token_urlsafe(24) (wire/transfer.py:176); malformed ids never build a path, and upload names such as ../, a NUL byte or $(whoami) stay inside the work directory (test_security.py:112,147,176); an unknown result id does not reveal whether it ever existed (:273). Limits: MAX_UPLOAD_MB 500 (HTTP 413 above), MAX_EXTRACTED_MB 2000, transfer and run directories expire after 900 s, and a run paused at a quality-control point keeps its data up to 4 h (server/config.py:240,241,245,263,271). Temporary directories are removed even when the tool raises (file_utils.py:20-81). The default tool timeout is zero, meaning none (config.py:77).

The cap the comment promises and the code does not apply

The cap on decompressed size is enforced only if the caller passes max_total_bytes (default None, file_utils.py:125-130). The folder argument of a normal run does (main.py:291-296, with _MAX_EXTRACTED_BYTES from MAX_EXTRACTED_MB, :113). The sum is taken over member.file_size, the size the archive declares (file_utils.py:167).

The resume path skips the extraction cap

The resume path unpacks the uploaded archive with file_utils.extract_zip(landed, destination) and no max_total_bytes (VISOR-serve server/main.py:1594), while the comment two lines above says it "refuses zip slip, symlink members and anything over MAX_EXTRACTED_MB before a byte is written" (:1592-1593). On that path only the path checks apply; the 2000 MB cap does not. Whether a declared size that lies about the real one could be exploited was not tested.

The client protects itself the same way against a misbehaving server. Before writing a byte of a result, checkpoint or hosted test file, it refuses an archive over UNZIP_MAX_MEMBERS = 100 000 members or UNZIP_MAX_BYTES = 20 GiB (Remote .../config.py:97-98, slicer_io.py:276-282).

5. The maintenance gate

The server can be told to stop accepting new work while it is updated. The updater runs on the host, not in the container, which only has server/ mounted, so it reaches in through POST /maintenance (token required, VISOR-serve main.py:518-548), body {accepting, seconds, reason}.

  • The closure is a deadline, not a flag: close() caps it at MAX_CLOSE_SECONDS = 300 and the gate reopens on its own when the monotonic clock passes it (wire/maintenance.py:38,51-66,80-89). The state is in memory, so a restart reopens it. With no seconds, the route asks for 60 s (main.py:540).
  • While closed, require_accepting answers 503 with Retry-After (maintenance.py:113-146) on exactly four routes: POST /uploads (main.py:833), POST /run/{tool} (:1806), POST /runs/{id}/rewind (:1685) and POST /runs/{id}/resume (:1750). Following a run, fetching a result and cancelling stay available.
  • /status reports the gate and carries no progress message, because a message can name a file and so a patient (main.py:455-467).
Limit of the gate

The route is protected by the same shared token as everything else. Anyone who holds it can refuse new runs for up to 300 s at a time, and again as soon as the window ends. The cap prevents a permanent lock-out, not a repeated one. This follows from the code; it was not tried on a live server.

6. De-identification: specified, not built

Remote DEIDENTIFICATION_SPEC.md (version 1.0, July 2026) specifies a client-side pipeline: three barriers (ingestion, transformation, verification) through a single choke point in the client, a step-by-step pipeline for DICOM and volumes, the leaks specific to Slicer (node names, the local DICOM database, logs, .mrml and .mrb files), a declarative profile per tool and a roadmap. It opens by saying that there is no de-identification processing today and that the server comment which claims otherwise "describes an intention, not a reality". Its principles are fail-closed, one choke point, and a proof per upload, and never a tick box that says "I anonymised".

Nothing of it is implemented. The client README says so in as many words: "There is no de-identification in the current client. Files are streamed to the server as they are on disk, with their names, their DICOM headers and whatever identifiers they contain" (Remote README.md:30-35). A search of Remote, VISOR-serve and SADT-VISOR for de-identification libraries (dicognito, pydicom) and for anonymisation code found none outside the specification, the upload notice and the text module below; pydicom appears only as a version pin in MRI2CBCTRemote, a module that is not built. The server has no gate either: the only trace is the header of main.py, which states that de-identification "happens on the client side before upload" (main.py:4-5).

The client warns the user, once per host

When the user saves a server that is not the local machine, the client shows a dialog that begins "Files are uploaded unmodified. This client does not de-identify anything" (Remote .../settings_qt.py:101-132, called from ServerToolsSettings.py:145 and SlicerCloud.py:1059). It is skipped for loopback and tracked per host (settings_qt.py:73-88). The header comment of main.py:4-5 is therefore false for the current client; the spec and SECURITY.md:130 both say as much.

Not to be confused: Medical Data Anonymizer

The Remote extension contains Medical_Data_Anonymizer_ModuleRemote (768 lines). It anonymises text documents (DOCX, PDF, TXT, CSV, XML, ODT) with Presidio, on the local machine, and sends nothing (Remote README.md:24-30). It is not the pipeline of the specification, it does not touch DICOM files or volumes, and it is not placed in the upload path of any other tool. The legacy module is described on its own page, the Remote module on its VISOR page; the same distinction holds for both.

7. Attestation and key exchange: not in VISOR

Absent from the three VISOR repositories

VISOR-serve, AutomatedDentalToolsRemote and SADT-VISOR contain no attestation, no key exchange and no application-level encryption of the files. A search for attestation, TEE, nonce, ECDH, X25519, HPKE, enclave and key exchange in them, and in the two legacy/ trees, finds only unrelated hits (the shell command tee, a recommendation to prefer ECDHE in a TLS configuration, the DICOM "Confidentiality Profile"). Protection of data in transit is TLS alone, section 3.

The protocol exists in a separate research prototype, volume_crypto (branch crypto/two-machine-chain, commit d975dab), a repository of its own with no reference to VISOR-serve or to the Remote extension in its code. It is not deployed anywhere known to this atlas and is not connected to the VISOR server. What follows describes what that prototype does, no more.

What the code does

  • Measurement. measure_code is a cumulative SHA-256 over files (name and content), documented as real, not simulated (voltcrypt/attestation.py:66-82). The measured set is a manifest: the protocol modules, the module that handles plain data, the runner and the announced policy (cryptoserve/measure.py:41-53,123-142), so that changing one line of any of them changes the digest and the client refuses to release the key.
  • Evidence. A record with version, kind, measurement, ephemeral public key, client nonce, report_data = SHA-512(public key || nonce), policy and date, signed with Ed25519 (attestation.py:98-134).
  • Verification order (attestation.py:162-206): signature first, then version, then the nonce (no replay), then the link between report_data and the public key presented (no relay of another server's evidence), then measurement and policy (debug off, swap off).
  • Key release. The client generates its own ephemeral X25519 pair, derives a wrapping key with HKDF-SHA256 (info = a version label, the ephemeral key and the recipient key) and seals the volume key with AES-256-GCM, with the job id and the nonce as authenticated data (voltcrypt/keyexchange.py:65-117). The docstring calls it a simplified equivalent of HPKE (RFC 9180): it is not standard HPKE.
  • Plain data. The server's private X25519 key is generated at start-up and never written (cryptoserve/enclave.py). Plain text is confined to one function in cryptoserve/boundary.py, guarded by an import test.
  • A real tool. A runner launches <tool>/.venv/bin/python <runner> --job job.json, the same contract as VISOR-serve (cryptoserve/runners/subprocess_tool.py).

Its trust root is simulated

Declared by the prototype itself

The header of voltcrypt/attestation.py:3-24 is a boxed warning, "simulated trust root": the signing key is a software Ed25519 key on the server's disk, which a server administrator can read to forge a false attestation. cryptoserve/enclave.py:32-43 announces "tee": "SIMULATED, aucune protection materielle" and "gpu_confidential": False, and debug: False and swap: False are constants chosen by the server, not read from hardware. The prototype guards against a server modified by mistake (wrong version, corrupted file, wrong machine), not against a malicious server. The hardware root (HardwareRoot in cryptoserve/roots.py) raises NotImplementedError: no AMD SEV-SNP, Intel TDX or NVIDIA confidential-computing device is used; they appear in comments only.

Other declared limits: the transport is plain HTTP with no TLS and no client authentication (PIPELINE.md, "Limites"); memory wiping is not guaranteed in Python; the --trust-on-first-use mode accepts whatever measurement the server announces, which the runbook forbids for real measurements; the result is re-encrypted with the volume key, a simplification.

Tests and evidence. The suite was run for this page: 155 passed, 3 skipped (they need a GPU and a served tool), 26 subtests, in 15.7 s. It includes refusal tests (replayed nonce, forged signature, relay attack, key never in the clear in the packet, key bound to the job, modified server refused) and a protocol state-machine. The repository's own README still says 158 tests. The end-to-end record committed at d975dab (evidence/endtoend.json) runs BatchDentalSeg behind the gate on a 138.9 MB scan: 78.9 s from the client's side, 78.3 s of it with the plain data resident while the tool runs; the working tree held an uncommitted rerun on a 98.6 MB scan (61.4 s). The adversary run recorded in evidence/adversary_twomachine.json targets the address of the machine that also hosts VISOR, so "two physical machines" is not established.

8. What is missing

  • No identity per user. One shared token (section 2). The client also calls GET /clients/me to ask how the server will run its cohort batches (Remote .../client.py:809, in batch_policy), and the route does not exist in VISOR-serve: no /clients route is defined under server/. The client treats any non-success answer as "no policy" and keeps its own concurrency (client.py:799-818), so nothing breaks, but the per-workstation identity this route suggests is not there.
  • No audit trail. No module records who ran what; logs are deliberately poor. The header of main.py claims the server never logs contents, argument values or patient metadata (:5-6); that claim was not checked on every logger call.
  • No encryption at rest. Temporary files are in clear in TEMP_DIR until the request is served; a run paused at a quality-control point holds them up to 4 h.
  • No rate limiting or lockout on token attempts.
  • No de-identification (section 6) and no TLS in the server (section 3).
  • Not reviewed: the execution of tool subprocesses (server/execution/) and the environment they inherit, which may be a security surface of its own.

What the server's SECURITY.md is

VISOR-serve SECURITY.md (522 lines, "Version 1.0, July 2026") is titled "Security and HIPAA compliance report". It is an audit and a set of recommendations, not a description of the implementation: it targets OIDC and JWT, envelope encryption at rest, a key vault, an audit trail, rate limiting, mTLS and phased roadmap. It says of the server it audited that it is "non conforme HIPAA en l'état" (SECURITY.md:11), for four structural reasons that are still true in the code: the shared static token, no persistent audit trail, de-identification assumed but not verified, and temporary files in clear. Its table of twelve gaps (:67-84) is the part that tells the state of the system; everything it phrases as a target ("il faut", "recommandé") is specified or recommended only. The report is written in French, contains leftover citation tags (cite index=, lines 48-52) and cites an "autumn 2026 Unified Agenda" inside a document dated July 2026. Treat it as a reading list of what is missing, not as a statement of compliance.

The assumption behind the design

The report's central argument is that data truly de-identified on the client would take the server out of HIPAA scope. That requires a provable de-identification, which section 6 shows is not available. Until it is, the server has to be treated as one that receives patient identifiers, over a token shared by every user.
