AutoMatrix on VISOR

AutoMatrix applies registration transforms to scans, segmentations and landmark files, a whole folder at a time. This page explains how, step by step: how files and transforms find each other, which way each one moves, and where the result lands. Files, lines, arguments and findings are on the code page. The legacy module is on its own page.

VISOR Atlas (explanation) Code (developers) Legacy page Guide (VISOR)

Overview: what goes in, what comes out

A registration tool (AREG, GreedyReg, FlexReg) finds a transform: how to move one scan onto another. AutoMatrix takes that file and applies it to other files of the same patient: a scan, a segmentation, or a set of landmark points. Nothing is predicted: it is geometry.

InOut
scans and segmentations (.nii.gz, .nrrd, .gipl), landmarks (.mrk.json), or a folder of themthe same files moved by their transform, with a suffix (Reg by default), in a copy of the input folders
transforms (.tfm, .mat, .h5, .hdf5, .txt), or a folder of thema report, AutoMatrix_report.json: what was paired, what failed, what had no partner

1. Position in the chain

AutoMatrix is the only tool of its group that another VISOR tool calls: VFACE calls it in two ways: to mirror (the scans of an asymmetry study, and its landmarks), and to move landmarks by each patient’s registration transform, one call per region. It calls nothing itself. Its transforms usually come from a registration, or from the hosted mirror matrix. The computation runs on the server, on the CPU, with no network and no weights.

4. The pipeline, step by step

One call applies every patient’s transforms to every file of that patient.

4.1 Discovery and the patient key computed

Files are searched in the folder and its subfolders, hidden files are skipped, and every file is keyed with the same function. If there is no file at all, or no transform at all, the run stops before reading anything.

In the codeDiscovery, the vocabulary of dropped words

4.2 The fallback pairing computed

After the normal rule, a second chance can only add pairs, never change one. Each rule used is recorded in the report. In order:

  1. With the option “same transform for every patient” and exactly one transform, that transform goes to every patient.
  2. Patients still unpaired are keyed again with the cuts of the legacy module, and matched against transforms nobody else took.
  3. One patient and one transform, still unpaired: the transform is applied.

Files without a transform, and transforms without a file, are listed in the report rather than ignored.

In the codeThe three fallback rules, with the lines

4.3 Reading a transform computed

The transform is read with ITK (the open-source imaging toolkit that SimpleITK wraps, the library doing the reading and resampling here). If ITK refuses the file but it holds a plain 4×4 matrix (four lines of four numbers, which is what Greedy writes under a .mat name), it is turned into an affine transform (a linear map plus a shift): the first three numbers of the first three rows form a matrix A, the last number of each row a translation t. Otherwise the error names the file. With several transforms for one patient, each is applied to the original file; none is composed with another.

T(x)=Ax+t
  • Tthe transform
  • xa point in millimetres
  • Athe 3×3 part of the matrix (rotation, scaling, reflection)
  • tthe translation, the last number of each of the first three rows
In the coderead_transform and the 4x4 text fallback

4.4 Landmarks: points through the inverse computed

In a landmark file, every group of points is moved. A point with no status counts as defined; any other status is left where it was. The frame declared in the file is not read: the points are moved as they are written.

In the codePoints through the inverse, with the lines

4.5 Images: interpolation and output box computed

Scan or segmentation? The choice sets the interpolation. By default it is read off the voxels: a floating-point image is a scan; so is one with a negative value, a value above 1000, or more than 128 distinct values; anything else is a label map. The answer is recorded per file.

Where the result lands. If a reference image is given, its grid is used. If not (the default, since the reference is hidden), the output has the input’s size, spacing and direction, and its origin is moved by the transform.

In the codeScan or label map, the interpolator, the output grid

4.6 Names, failures, report computed

The output mirrors the input folders. The name is the original name, then the suffix, then the transform’s name when that option is on or when the patient has several transforms (so two transforms never write the same file). For example p1.nii.gz with p1_CBReg_matrix.tfm and p1_MANDReg_matrix.tfm gives p1_Reg_p1_CBReg_matrix.nii.gz and p1_Reg_p1_MANDReg_matrix.nii.gz (run on 2026-11-09). A file that fails is recorded with its error and the others go on. If nothing was written, the run stops with the first reasons; otherwise AutoMatrix_report.json lists, per patient, the transforms, the files moved, the failures, and then the unpaired files and transforms.

In the codeNames, failures and the report fields

5. What you can choose

  • Files and transforms: a file or a folder for each (both required).
  • Same transform for every patient: off by default; needs exactly one transform.
  • Include the transform name: off by default, forced on when a patient has several transforms.
  • Output suffix: Reg by default, may be empty.
  • Hidden in the panel: how to resample (automatic by default) and the reference volume.
  • Use the mirror matrix (Slicer panel): fills Transforms with the hosted mirror file and ticks the same-transform option.

6. What is predicted vs computed

BlockNature
Pairingcomputed file-name rules
Scan or segmentationcomputed three value tests and a count of distinct values
Resampling, landmark pointscomputed SimpleITK
The transforms themselvescomputed upstream, by a registration (AREG, GreedyReg, FlexReg), or the fixed mirror matrix

Nothing in AutoMatrix is predicted.

9. Known issues in VISOR

Each point is checked in the code and described, with its evidence, on the code page; the list also appears in the findings.

  • The status line always says “0 file(s) written” in Slicer, and unpaired files are never signalled. Evidence.
  • Without a reference, the output box follows the transform: a reflection, such as the mirror matrix, leaves the box empty. A fix exists on a branch that is not merged. Evidence.
  • The list of produced files stays empty for volumes. Evidence.
  • An uninvertible transform does not stop the run: the landmarks fail, the volume is written. Evidence.
  • Documentation of the Remote module contradicts the code. Evidence.
  • The declared frame of a landmark file is not read. Evidence.
  • The README and the data manifest are out of date on this tool. Evidence.
