AutoMatrix on VISOR: the code

For developers: what the VISOR port of AutoMatrix does in the code, with file:line references, signatures, arguments, environment, the differences from the legacy module and the findings. The readable explanation of the same pipeline, with the maths, is on the atlas page.

VISOR Code Atlas (explanation) Legacy page Guide (VISOR)

In VISOR, AutoMatrix is a Python package that runs on the server: Slicer sends the files and the transforms, the server pairs them by patient, resamples the volumes, moves the landmark points and sends the results back. The transform convention is the legacy one (the volume is resampled through the transform, points move through its inverse); what changed is the pairing rule, the output grid when no reference is given, the formats, and a report of what was paired and what failed. This page follows the port from the request to the files that come back: position, files, each step with the code that does it, the published arguments, the environment, the differences with the legacy module and the findings. It describes the port in SADT-VISOR (branch tool/vface, 6ba2a78, 2026-09-30), served by VISOR-serve (e9a7e5d) and driven from Slicer by the AutomatedDentalToolsRemote extension (19b95e8). The port was made from an upstream state older than 3c67957 (the AutoMatrix and Automatrix_CLI files changed between b1ae78c and 3c67957), so a few details of the legacy page, which reads 3c67957, may differ from what the port started from. Nothing here claims a deployed server: it is read from the code, and the behaviours marked "run on 2026-11-09" were reproduced by calling the package's run() in its own virtual environment on synthetic volumes.

How references read on this page

SADT-VISOR AutoMatrix/pipeline.py:127 is tools/AutoMatrix/src/sadt_automatrix/pipeline.py in SADT-VISOR at 6ba2a78; a bare pipeline.py, __init__.py or layout.py is the same package, and a bare README.md, pyproject.toml or tests/… is under tools/AutoMatrix/. 1. Position in the chain

Plain-language explanation and maths: atlas page.

AutoMatrix is the only tool of this group that another VISOR tool calls: VFACE drives it through the supervisor in two ways: the mirror call (on the scans of an asymmetry study, SADT-VISOR tools/VFACE/src/sadt_vface/dispatch.py:161, and on its landmark folders, :232) and the call that moves landmarks by each patient's registration transform (one call per region, :253-261). It calls nothing itself. Its inputs are typically the outputs of a registration (AREG, GreedyReg, FlexReg) or the hosted mirror matrix.

4. The pipeline, step by step

Plain-language explanation and maths: atlas page.

One call of run() applies every patient's transforms to every file of that patient (SADT-VISOR AutoMatrix/__init__.py:68-185).

4.1 Discovery and the patient key computed

Plain-language explanation and maths: atlas page.

_walk takes a file as itself or walks a folder recursively, skips hidden files, and keys every file with the same function (__init__.py:267-298). Accepted: images .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl, landmarks .mrk.json, transforms .tfm .mat .h5 .hdf5 .txt (pipeline.py:45-67). The key is the shared patient_stem plus the transform and region vocabulary (pipeline.py:27-42):

PATIENT_TOKENS_TO_DROP = (
    "transform", "matrix", "warp", "reg", "cbreg", "mandreg", "maxreg",
    "cb", "mand", "max", "md", "mx",
)
def patient_of(filename: str) -> str:
    return pairing.patient_stem(filename, also_drop=PATIENT_TOKENS_TO_DROP)

So C_0001_CB_Reg_transform.tfm keys to C_0001, like its scan (run on 2026-11-09). No file at all, or no transform at all, is a ValueError before anything is read (__init__.py:72-84).

4.2 The fallback pairing computed

Plain-language explanation and maths: atlas page.

_pair_like_legacy runs after the normal rule and can only add pairs, never change one (__init__.py:188-264):

  1. With same_transform_for_every_patient and exactly one transform, that transform goes to every patient, recorded as "asked to share one transform" (:215-220).
  2. Patients left unpaired are keyed again with the legacy substring cuts, which differ on the two sides on purpose (pipeline.py:200-237), and matched against transforms nobody else took: "legacy file names" (__init__.py:222-249).
  3. One patient and one transform, still unpaired: applied, "the only transform, applied to every patient" (:258-262).

Each rule used is recorded in paired_by (__init__.py:110-111). Files without a transform and transforms without a file are listed in the report (:105-106).

4.3 Reading a transform computed

Plain-language explanation and maths: atlas page.

sitk.ReadTransform first; if ITK refuses it, a plain 4×4 matrix written as four lines of four numbers, which is what Greedy writes under a .mat name, becomes an AffineTransform; otherwise a RuntimeError that names the file and quotes ITK (pipeline.py:138-180):

try:
    return sitk.ReadTransform(path)
except RuntimeError as itk_error:
    matrix = _read_plain_matrix(path)
    ...
    affine = sitk.AffineTransform(3)
    affine.SetMatrix([value for row in matrix[:3] for value in row[:3]])
    affine.SetTranslation([row[3] for row in matrix[:3]])
    return affine

The transform is read per file (__init__.py:311). With several transforms for one patient, each is applied to the original file; none is composed with another (__init__.py:130-143).

4.4 Landmarks: points through the inverse computed

Plain-language explanation and maths: atlas page.

A .mrk.json has its points moved by transform.GetInverse(), in every markup group; a point whose positionStatus is absent counts as defined, any other status is left where it was; coordinateSystem is not read (pipeline.py:71-104). The reason is the resampler's convention: ResampleImageFilter maps each output point through the transform to find where to read the input, so the content of the image moves by the inverse, and points have to follow the same way (docstring pipeline.py:3-6, 74-78). The output is <stem>[_<tail>].mrk.json and is listed in both outputs (with points_moved) and produced (__init__.py:327-333).

4.5 Images: interpolation and output grid computed

Plain-language explanation and maths: atlas page.

The interpolator is nearest neighbour for a segmentation and linear for a scan (pipeline.py:120-125). Which one a file is comes from content; with the default Automatic, from the voxels (__init__.py:350-354; pipeline.py:264-296): a floating-point image is a scan, a negative value or a value above 1000 is a scan, and more than 128 distinct values, counted chunk by chunk, is a scan; anything else is a label map. The answer is recorded per file as detected.

The output grid (pipeline.py:127-133):

if reference is not None:
    resampler.SetReferenceImage(reference)
else:
    resampler.SetSize(image.GetSize())
    resampler.SetOutputSpacing(image.GetSpacing())
    resampler.SetOutputDirection(image.GetDirection())
    resampler.SetOutputOrigin(transform.TransformPoint(image.GetOrigin()))

Without a reference, which is the default since reference is hidden, the grid keeps the input's size, spacing and direction and its origin is moved by the transform. For a translation this keeps the content in the box; for a reflection it does not (see the findings). Outside the input, voxels are 0 (pipeline.py:125).

4.6 Names, failures, report computed

Plain-language explanation and maths: atlas page.

The output mirrors the input tree (__init__.py:323-325). The tail is output_suffix, then the transform's full stem when name_output_after_transform is on or the patient has more than one transform; parts are joined with _, an empty suffix adds nothing, and compound extensions are kept (__init__.py:141, 301-303, 317-322, 335-342). Example run on 2026-11-09: p1.nii.gz with p1_CBReg_matrix.tfm and p1_MANDReg_matrix.tfm gives p1_Reg_p1_CBReg_matrix.nii.gz and p1_Reg_p1_MANDReg_matrix.nii.gz. A file that fails is recorded in cases[patient].failed with its exception, and the loop goes on (__init__.py:144-155). If nothing was written, ValueError with the first five failures or the two unpaired counts, and no report (:164-184). Otherwise AutoMatrix_report.json:

{"tool": "AutoMatrix", "content": ..., "reference": <file name or null>, "output_suffix": ...,
 "cases": {"<patient>": {"transforms": [...],
                         "outputs": [{"file", "detected"} | {"file", "points_moved"}],
                         "produced": [...], "failed"?: [...]}},
 "without_a_transform": [...], "transforms_without_a_file": [...], "paired_by"?: {...},
 "summary": {"cases", "files_written"}, "duration_seconds": ...}

9. Findings in VISOR

Plain-language explanation and maths: atlas page.

The status line always says "0 file(s) written"

AutoMatrixRemote._summarize reads report.get("written") and report.get("skipped") (AutomatedDentalToolsRemote AutoMatrixRemote/AutoMatrixRemote.py:227-235). The report written by the tool has neither key: it carries summary.files_written and the lists without_a_transform and transforms_without_a_file (SADT-VISOR AutoMatrix/__init__.py:105-106,158-161). Run on 2026-11-09: the report of a run that wrote one file held summary.files_written = 1 and no written key, so, reading the code of _summarize, the message is AutoMatrix: 0 file(s) written. whatever happened, and unpaired files are never signalled in Slicer. No test covers _summarize (nothing in test_automatrix_client.py names it). AutoCrop3DRemote reads the right keys (AutoCrop3DRemote.py:119-120).

Without a reference the output box follows the transform

With no reference (the default, and the hidden argument), the output keeps the input size and direction and takes the origin transform.TransformPoint(origin) (SADT-VISOR AutoMatrix/pipeline.py:133). The legacy grid was the image's own (Automatrix_CLI.py:279@3c67957). Run on 2026-11-09 on a 20×20×20 volume of 1 mm voxels with its origin at -10 mm on each axis, holding a 10×10×10 block (1000 non-zero voxels) at indices 2 to 11, resampled as a segmentation: a translation of (5,0,0) moved the origin to -5 and kept 200 of the 1000 voxels; a reflection diag(-1,1,1) (a substitute for the hosted mirror file, whose content was not downloaded) moved the origin from -10 to +10 and kept none; the same reflection with the volume as its own reference kept all 1000. This is the path of the "Use the mirror matrix" box and of VFACE's mirror (SADT-VISOR tools/VFACE/src/sadt_vface/tools.py:179-187, no reference). Tests pin the translation behaviour (tests/test_run_options.py:265-277, tests/test_resample.py:108-115), and one relies on it (tests/test_resample.py:44-53).

Not delivered. A fix exists on the branch fix/automatrix-mirrors-into-an-empty-box (commit ce4f6fb, 2026-09-28, local and origin): it keeps the input origin unless the transform is a pure translation. That branch is not an ancestor of tool/vface (6ba2a78), so the behaviour described above is the one in this tree.

produced stays empty for volumes

Each case starts with "produced": [] (SADT-VISOR AutoMatrix/__init__.py:127-128) and the only append is in the landmark branch (:332). Run on 2026-11-09 with a volume: outputs held the file and produced was []. The comment at :125-126 says produced is the flat list every tool of the catalogue answers; AutoCrop3D fills it for its volumes (SADT-VISOR tools/AutoCrop3D/src/sadt_autocrop3d/__init__.py:236). The consequence for clients that read it was not traced.

An uninvertible transform does not stop the run

For a transform that cannot be inverted the landmark file of that patient fails and is listed in cases[patient].failed, while the patient's volume is written (SADT-VISOR AutoMatrix/__init__.py:144-155). Run on 2026-11-09 with a zero displacement field stored as .h5: GetInverse raised Unable to create inverse!, the volume was written and files_written was 1. The run raises only when nothing at all was written (:164), and in that case no report is written, because the report is saved after that check (:184). The Slicer panel does not show failed (see the status-line finding).

Documentation of the Remote module contradicts the code

AutomatedDentalToolsRemote AutoMatrixRemote/AutoMatrixRemote.py:16-19 says the server still applies a matrix whose name contains "mirror" in the scan's own space; the port does not (SADT-VISOR AutoMatrix/README.md:89-92, tests/test_run_options.py:311-331). AutoMatrixRemote.py:12-15 says "nothing is hidden" while reference and content are hidden (layout.py:28,43). The client test builds its schema by hand with hidden: False everywhere and other section names (test_automatrix_client.py:72-186), so test_nothing_is_marked_hidden (:255-257) checks that copy, not the server's schema. The comment in SADT-VISOR AutoMatrix/layout.py:22-27 says VFACE passes "None" at all eight of its call sites; the two AutoMatrix wrappers of SADT-VISOR tools/VFACE/src/sadt_vface/tools.py:179-187,205-212 pass no reference and are called from three places in dispatch.py (:161,232,257). Passing "None" and passing nothing come to the same, so this is a comment that cannot be matched to the count, not a proven contradiction.

coordinateSystem of a landmark file is not read

Points are moved as they are written, whatever frame the file declares, and the output keeps the declaration (SADT-VISOR AutoMatrix/pipeline.py:71-104, no read of the field). Points whose status is neither absent nor "defined" stay at their old coordinates in a file reported as transformed (:95-96). Both behaviours are those of the legacy CLI (legacy page). Read in code.

What the VISOR README and manifest say

VISOR-serve scripts/data-manifest.yml:730 still reads "NOT PORTED YET (test data only)" although the tool's source is mounted in VISOR-serve docker-compose.dev.yml:51; SADT-VISOR AutoMatrix/README.md:111-113 speaks of 1.4 GB of models while the manifest lists test archives (data-manifest.yml:731-751).
