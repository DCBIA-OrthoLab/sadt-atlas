VFACE on VISOR

VFACE decides whether a face is skeletally asymmetric, from a CBCT scan alone. It orients the scan, mirrors it, registers the mirror back onto the original region by region, measures how far each landmark has moved from its own reflection, and classifies the result with three small models. This page explains how, step by step, with the maths. Where the code does something worth checking, a link leads to the code page. The legacy module is on its own page.

VISOR Code (developers) branch tool/vface only Legacy page Guide (VISOR) Bibliography

A patient is compared against themselves. In an asymmetry assessment there is no second scan: the baseline is oriented, mirrored across the mid-sagittal plane, registered back onto itself region by region, and what is measured is how far each landmark has moved from its own reflection. A longitudinal study is the same chain with a real follow-up scan in the mirror’s place. VFACE itself learns nothing and runs no network: every model it needs belongs to another tool, except the classifier, which it reads with LightGBM.

The VFACE tool exists only on a feature branch of the tool catalogue and its server section only on a feature branch of the server, so a server built from the main branches does not publish it (details). Everything below was read in the code; nothing on this page comes from a run, and nothing here says that a server is deployed.

Overview: what goes in, what comes out

VFACE

OutputExcel tables of measurements per region and a table of features; a classification per patient (asymmetric or not, mandible involved or not, maxilla involved or not); optionally surfaces coloured by signed distance (heat maps); a JSON report listing everything that was skipped

The six calls

Every call names its tool by string and sends that tool’s published argument names, not VFACE’s own vocabulary. A test reads the six published forms and checks that every argument sent exists.

3. The pipeline

The chain, as the dispatcher states it: resample, orient (per frame), segment (per frame), the second scan, register (per region), landmarks, measure, classify.

3.2 Everything is checked before a volume is read

Before the first scan is touched, the tool fills the empty bundle arguments, rejects an unknown mode, study, output or region by name, and refuses a mode whose tools cannot be reached or whose bundle is missing. The code’s own rule: a request that cannot work has to come back in a second, not after an hour. Without a supervisor (a direct call, a test), a missing tool is refused with advice on the mode that works without it.

In the codeThe table of required tools and bundles per condition, and how the refusal is raised

3.3 Bundles the deployment resolves

Seven arguments are filled from the server’s data folder when the caller leaves them empty: the segmentation models, the classifier, the two gold-standard cases for orientation, the mirror matrix, the default measurement lists and the feature template. The server’s own convention would otherwise hand each of them the whole models folder, which holds six bundles at once. The landmark models are left out on purpose, since ALI_CBCT finds its own weights; the surface models are left out too, and nothing else fills them (known issues).

In the codeThe bundle table in the code and where each name is resolved

3.4 The chain, step by step

The default request: full pipeline, asymmetry assessment, measurements and classification, three regions.

a folder of raw CBCT scans, one per patient, sub-folders included

Preparation

  1. resample to 0.3 mm isotropic, centred, folder tree kept
  2. ASO ×2, Fully-Automated: Frankfort + mid-sagittal (7 landmarks), then occlusal + mid-sagittal (6 landmarks)
  3. AMASSS ×2: CBMASK and MANDMASK on the CB frame, MAXMASK on the MAX frame

Second scan

  1. AutoMatrix ×2 applies the mirror to the oriented scans of each frame: this is where the “T2” comes from

Registration

  1. AREG_CBCT ×3, Semi-Automated, one region per call, on the masks of step 3

Measurements

  1. pad the CB-frame scans by 30 mm, then ALI_CBCT places every landmark the lists name
  2. derive those landmarks into the MAX frame by a rigid transform
  3. AutoMatrix ×2 mirrors the landmarks of each frame
  4. AutoMatrix ×3 moves them by each patient's matrix, one call per region
  5. AQ3DC ×3 measures distances and angles
  6. signed features, one row per patient
  7. three LightGBM models

Progress is reported at fixed waypoints, so that the events of a whole chain land in one place: resample 2 %, orient 10, segment 30, second scan 45, register 55, landmarks 75, measure 90, classify 97.

In the codeThe output folder of each step, the count of server calls and the progress waypoints

3.5 Resample

The legacy full pipeline began by calling MRI2CBCT’s resampling command with every MRI-specific input switched off. VISOR has no MRI2CBCT tool, so the few lines that were actually reached are copied into VFACE.

The grid size is kept and the spacing changes. An unreadable volume is recorded in the report and the cohort continues; a cohort where nothing could be resampled is refused. Output paths keep each scan’s folder, where the legacy flattened them.

In the codeThe copied resampling code with its lines, the default value and the failure rules

3.6 Orientation into two frames

A scan is oriented twice, and every later step works in one frame or the other. The mandible is worked in the cranial-base frame, because it is measured by how it sits relative to the skull; only the maxilla gets the occlusal frame.

FrameReference caseLandmarks usedRegions worked in it
Cranial baseFrankfurt horizontal and mid-sagittal planeBa, LPo, N, RPo, S, LOr, ROrcranial base, mandible
Maxillaryocclusal and mid-sagittal planeANS, IF, PNS, UL6O, UR1O, UR6Omaxilla

Each frame is one ASO call in fully automatic mode, which for a CBCT means that ASO predicts its landmarks through ALI_CBCT and then registers on them. Both frames are oriented whatever regions were asked for, because the landmarks are predicted in the cranial-base frame and derived into the maxillary one. In the two modes that skip the orientation, a scan whose name carries neither suffix, or both, is left out and listed in the report.

In the codeThe frame table with file:line, the suffixes and how scans without a frame are handled

3.7 Registration masks

One AMASSS call per frame, for the structures of the regions that frame holds, so the cranial-base frame asks for the cranial-base and mandible masks in one pass. A frame that no requested region registers on gets no call at all. The structures are the mask variants, not the anatomical ones: a registration handed a segmentation where it expects a mask would run, produce a transform and report success on the wrong anatomy. One binary file is written per structure, so a region’s mask can be looked up by name.

In the codeThe structure names, the merge setting and the rule for a frame without a region

3.8 The second scan: where the two studies part

The mirror is a single transform applied with the same value for every patient, because it is a reflection of the frame and not something fitted per patient. It is valid only because the orientation has already put the mid-sagittal plane where the reflection expects it. A longitudinal study without a follow-up folder, or an asymmetry assessment without a mirror bundle, is refused with a message naming the other study.

In the codeThe mirror call, the content settings for scans and landmarks, and the refusals

3.9 Registration, one region per call

For each requested region, AREG_CBCT registers the second scan of that region’s frame onto the baseline of the same frame, on that region’s mask. It is used in its semi-automatic mode because the scans are already oriented and segmented: asking it to orient again would orient the mirror independently of the original, and a mirror is only a mirror while it shares the original’s frame.

AREG_CBCT groups its results by region, so the folder it returns holds no transform itself; VFACE steps one level down when exactly one sub-folder holds one, and otherwise refuses with the list of what it found. In that folder AREG_CBCT writes both the registered scan and its transform: the landmark step uses the transforms, the heat-map step the scans.

In the codeHow the region folder is found, the file names and the refusal message

3.10 Landmarks: found once, then derived and moved

Which landmarks. Only those the measurement lists name, collected into one set: ALI_CBCT runs one search agent per landmark, at about a minute each, so a whole region catalogue would cost hours.

Padding. The cranial-base scans are copied with 30 mm of room on each side before the search, filled with the scan’s own darkest value; the origin moves with the padding, so the points come back in the original scan’s space. The reason: ALI’s agent refuses any position outside the unpadded size, which made it give up on a point one or two voxels from the border, such as the menton.

Derivation into the maxillary frame. Both orientations come from the same centred scan, so a point’s position in the maxillary frame follows from its position in the cranial-base frame through the two orientation transforms, without a second search. A patient missing one of the two transforms is skipped and recorded; if no patient can be derived, the run stops.

The compared set. For an asymmetry assessment, the baseline’s own landmarks mirrored by AutoMatrix; for a longitudinal study, landmarks predicted by ALI_CBCT on the padded follow-up. Then each region’s compared set is moved by that region’s registration, one AutoMatrix call per region, so that each patient’s matrix is paired with that patient by name.

Coordinates. The landmarks travel as .mrk.json markups between ALI_CBCT, AutoMatrix and VFACE, and the transforms are applied to the stored positions directly. No RAS/LPS conversion appears in VFACE; the frame convention is the one the callees write, which this page did not re-read.

In the codeThe padding code, the derivation snippet with its lines and the rule that pairs files by patient

3.11 Measurements (AQ3DC)

The lists. The measurements come from Excel workbooks, one per region, matched to the region by their file name; every sheet is read. A row names a kind of measurement and its landmarks, and the timepoint sits on each point, not on the row: that is what makes “the distance between a landmark and its own mirror” expressible.

KindPoints
Distance between two pointstwo points, both at T1, both at T2, or one at each
Distance from a point to a linethree points, same timepoint
Angle between two linesfour points, same timepoint
Angle between a T1 line and a T2 linefour points, two at each timepoint

Each row gives right-left, front-back and up-down components with a sign meaning (which way a positive number points), a 3D distance, and yaw, pitch and roll for angles. The sign meanings are the clinical content and are reproduced from the legacy tables, dental and skeletal apart. A patient present at only one timepoint, a missing landmark or a degenerate measurement is skipped and recorded in the report.

In the codeThe spelling of each kind in the list, the arithmetic with its lines and the sign tables

3.12 Feature table and classification

Signed features. Each row’s magnitude and label are turned back into a signed number; which label counts as negative depends on whether the row is dental or skeletal. The vertical axis keeps both legacy conventions, which are opposite. A template workbook then names the columns of the feature table, and one row per patient is filled from the right region’s table; a column naming a landmark the run never produced is left empty.

Three models from the classifier bundle, all required:

ModelQuestionAsked ofOutput column
symmetrysymmetric or notevery patientAsymmetry
mandibleis the mandible involvedpatients read as asymmetricMand
maxillais the maxilla involvedpatients read as asymmetricMax

Each model picks its own columns by name, never by the table’s order, and a missing feature is refused by name: the template and the bundle must come from the same training run. A failing sub-model leaves “False” in its column and is recorded. A missing template or bundle leaves the measurements and the feature table in the result and says so in the report instead of failing the run.

In the codeThe sign code, the model files with their labels, and the partial-failure rules

3.13 Heat maps

For each region, Batch_Dental_Seg is asked for surfaces twice: on the oriented baseline of that region’s frame, and on the registered scans. Surfaces are paired by patient, and each pair gives one map, the baseline surface carrying its signed distance to the other. Large pairs are thinned out first (by half above a million points, by 70 % above two million) and the distance is carried back onto every original point.

Maps are written as legacy VTK files that every Slicer in use reads. A run that draws no map at all is refused.

In the codeThe decimation thresholds, the filter settings and the pairing code

4. What you can choose

  • CBCT volumes: a folder, searched through its sub-folders (required).
  • Starting from: full pipeline, file already oriented, or file already registered.
  • Study: asymmetry assessment (the default) or longitudinal study; the latter shows a second folder for the follow-up scans.
  • What to produce: measurements and classification, measurements and heat maps, or heat maps only.
  • Regions to measure: cranial base, mandible and maxilla, all three by default.
  • Transforms, for a run starting from registered files: one sub-folder per region.
  • Everything else (the reference cases, the models, the measurement lists, the classifier) is filled in by the server and hidden in the panel.

6. Environment

VFACE runs in a Python environment of its own on the server, with pinned versions: Python 3.11, SimpleITK, NumPy, SciPy, VTK, pandas, openpyxl, LightGBM, joblib and scikit-learn (the three models are LightGBM’s scikit-learn wrappers, and unpickling one imports it; the legacy never installed it). There is no GPU and no PyTorch in VFACE: every network belongs to a tool it calls, each with its own environment, so a full run needs the six tools built and served on the same server. No time limit is declared, so the server defaults apply.

In the codeVersions with their line numbers, the data folders, the limits and the tests

8. Known issues in VISOR

Each point is read in the code and described, with its evidence, on the code page; the list also appears in the findings.

  • Never run with its six real tools. Only simulated callees and the arithmetic are tested; nothing is validated clinically. Evidence.
  • Heat maps: the surface tool is not asked for surfaces. It writes only volumes by default, so no pair is found and the run is refused. Evidence.
  • Heat maps have no surface bundle on this deployment. A request for them is refused. Evidence.
  • A longitudinal study is also classified. The models were trained to read a patient against their mirror, so the answer has no stated meaning there. Evidence.
  • A cohort is split on the baseline folder only. The follow-up folder is not split with it. Evidence.
  • Error advice names fields that do not exist. Evidence.
  • The data manifest still says “not ported yet” and lists fewer bundles than the tool uses. Evidence.
  • Comments miscount the tools. Six are called, not seven; the nesting cap is ten, not five. Evidence.

9. Literature

The bibliography is the tool’s, on SOURCES; the legacy page discusses it in its literature section. One point carries over unchanged: the published work describes an unsupervised clustering of the measurements, while the code, legacy and VISOR alike, reads them with three supervised LightGBM classifiers. The VISOR README does not cite a publication.
