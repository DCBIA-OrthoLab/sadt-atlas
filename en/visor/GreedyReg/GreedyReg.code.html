GreedyReg on VISOR: the code

For developers: what the VISOR port of GreedyReg does in the code, with file:line references, signatures, arguments, environment, the differences from the legacy code and the findings. The readable explanation of the same pipeline, with the maths, is on the atlas page. The legacy module has its own code page.

VISOR Code Atlas (explanation) Legacy page Guide (VISOR)

In VISOR, GreedyReg is a Python package that runs on the server: Slicer sends the two folders of scans, the server pairs them by patient, runs Greedy twice per pair (an affine search, then a resampling of T2 into T1) and sends the results back. Greedy is no longer a downloaded binary but the picsl_greedy package, and the command it receives is the legacy one, flag for flag. This page describes the port in SADT-VISOR (branch tool/vface, 6ba2a78, 2026-09-30), served by VISOR-serve (e9a7e5d) and driven from Slicer by the AutomatedDentalToolsRemote extension (19b95e8); the legacy module is described on its own page. It is a partial port. What exists is the core of GreedyReg_CLI: pair the scans of two folders by patient, optionally restrict the metric with a mask and start from an initial transform, run Greedy, resample. The manual mode, the mask creation in the scene, the binary download and the Distant (landmark) mode are not in the server tool: run() has no argument for any of them (SADT-VISOR GreedyReg/__init__.py:38-52), and no landmark mode exists anywhere in SADT-VISOR (checked with git log --all -S"Landmark + Greedy"). The README's own "Not ported" list names only the stdout progress protocol and the nibabel install guard (README.md:60-64). Nothing here claims a deployed server.

1. Position in the chain

Plain-language explanation and maths: atlas page.

GreedyReg calls no tool and no tool calls it: there is no sup.run in the package and no other tool of SADT-VISOR names it (grep over tools/*/src). Its natural upstream is a segmentation that gives the mask of a stable structure, typically the cranial base from AMASSS (the docstring says so, __init__.py:64-67), but the clinician brings that mask as a file: the tool does not fetch it. In the legacy module the Distant mode called ALI_CBCT for landmarks; that path does not exist in VISOR (the calls: ["ALI_CBCT"] entry exists only in the client test fixture).

4. The pipeline, step by step

Plain-language explanation and maths: atlas page.

One call of run() registers a whole cohort, patient by patient, in SADT-VISOR GreedyReg/__init__.py:88-190.

4.1 Pairing T1 with T2 computed

Plain-language explanation and maths: atlas page.

The choices are checked first, so a bad metric is one error, not one per patient (__init__.py:92; pipeline.py:47-55). Then pairing.pair(t1, t2, output_suffix) (__init__.py:102). The shared rule walks both folders recursively, accepts .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl (pairing.py:36), and keys each file by patient_stem: the extension, any suffix a previous ASO, AMASSS, ALI or AREG run left, and the timepoint token are removed, and the sub-folder is kept as a prefix (pairing.py:175-211, 232-276). Files that look like an earlier output of this run's suffix are skipped (pairing.py:214-229). Examples run on 2026-11-09: 01_T1.nii.gz gives 01, Patient-01.nii.gz gives Patient_01, C_0001_T1_Or.nii.gz gives C_0001.

A folder that holds two timepoints is refused, so that T1 is never paired against T1 (pairing.py:336-358):

for label, root in (("T1", t1_root), ("T2", t2_root)):
    found = timepoints_in(root, accept)
    if len(found) > 1:
        raise ToolInputError(
            f"The {label} folder holds scans from more than one timepoint ..."

No patient in both folders is a ValueError that lists up to ten keys on each side (__init__.py:112-122); the server turns it into a 422.

4.2 Masks and initial transforms computed

Plain-language explanation and maths: atlas page.

_discover_masks keys a mask like its scan, and drops structure tokens (the AREG region tokens and mask tokens) only from a file whose name says it is a mask, so that P1_T1_MAND_seg.nii.gz keys to P1 while a patient called MD_01 keeps its name (__init__.py:28-35, 207-228). _discover_transforms keys .mat files the same way and drops transform, so the transforms of one run can be fed back as the start of the next (__init__.py:231-248). Masks and transforms that match no patient are listed in the report (__init__.py:131-135).

4.3 The start of the search computed

Plain-language explanation and maths: atlas page.

With a given transform, Greedy starts from it as is (-ia, __init__.py:261-262). Otherwise the tool writes the legacy identity with a nudged x translation (pipeline.py:101-114, legacy GreedyReg_CLI.py:86-90):

matrix = np.eye(4)
matrix[0, 3] = 0.001

The docstring gives the reason: Greedy reads an exact identity as "no initialisation given" (pipeline.py:102-106; a Greedy behaviour, not checked here). A mask is binarised above zero to float32 with the mask's own affine, in the scratch folder (pipeline.py:117-126; __init__.py:267-271). Nothing checks that the mask is in the space of T1.

4.4 The two Greedy calls computed

Plain-language explanation and maths: atlas page.

The affine search, built argument by argument as in the legacy buildRegistrationCommand (pipeline.py:74-94; legacy GreedyReg_CLI.py:104-125):

-d 3 -a -m NCC 4x4x4 | NMI | SSD
-i <T1> <T2> -o <patient>_transform.mat
-n 100x100x50x25 -e 0.5 -search 100 10 20
-dof 6 | 12 -ia <init> [-gm <mask>]

T1 is the fixed image, T2 the moving one. -n is the multi-resolution schedule and -search the random search that precedes it; neither is exposed (pipeline.py:78-81). An unknown metric is refused where the legacy CLI fell through to SSD (pipeline.py:58-71; legacy GreedyReg_CLI.py:107-112). Then the resampling of T2 into the grid of T1 (pipeline.py:97-98):

-d 3 -rf <T1> -rm <T2> <patient>_<suffix>.nii.gz -r <patient>_transform.mat

Each call runs in a child interpreter that hands the joined arguments to Greedy3D().execute, bounded by CASE_TIMEOUT_SECONDS = 600; a non-zero exit becomes a RuntimeError carrying Greedy's own message (pipeline.py:136-165):

_CHILD = """
import sys
from picsl_greedy import Greedy3D
Greedy3D().execute(" ".join(sys.argv[1:]), out=sys.stdout)
"""
finished = subprocess.run(
    [sys.executable, "-c", _CHILD, *[str(part) for part in command]],
    capture_output=True, text=True, timeout=timeout,
)

The comment explains the child process: an in-process call would have dropped the legacy 600 s bound, and the server sets no time limit of its own (pipeline.py:129-135).

4.5 Outputs and report computed

Plain-language explanation and maths: atlas page.

Per pair, under the zipped output folder and mirroring the input tree: <patient>_<suffix>.nii.gz (always .nii.gz) and <patient>_transform.mat, Greedy's text matrix, not a .tfm (__init__.py:254-259). Each case records status, the file names, the mask and initial transform used, transform_maps: "the T2 image -> the T1 frame (what greedy -r consumes)" and produced relative to the output folder (__init__.py:143, 261-286). A failure records reason, the exception type and text (__init__.py:157-167); the per-patient scratch is removed in every case (:168-170). At the end, summary and duration_seconds (:173-178), and the report is written only if at least one pair registered (:180-189). Progress is "patient i of n", never a file name (:141).

9. Findings in VISOR

Plain-language explanation and maths: atlas page.

The Slicer client describes a tool the server does not have

AutomatedDentalToolsRemote GreedyRegRemote/GreedyRegRemote.py:11-24 (docstring) and :50-57 (help text) describe a mode argument with Greedy, Landmark and Landmark + Greedy, a landmark_model and a second tool reached through the supervisor. The server tool has none of it: its run() takes t1, t2, output_dir, masks, initial_transforms, metric, transform_type, output_suffix (SADT-VISOR GreedyReg/__init__.py:38-52) and a search for mode or "landmark" in the package finds nothing. The comment at GreedyRegRemote.py:76-77 names an init argument; the argument is initial_transforms. The hand-written schema of the client test carries mode, init, region and landmark_model (test_greedyreg_client.py:90-260) and a calls entry for ALI_CBCT, so those 22 tests check the fixture, not the server. No branch of SADT-VISOR contains a landmark mode (git log --all -S"Landmark + Greedy" is empty). The Remote README.md:202,1056-1076 repeats the old three-mode description. Whether the Landmark mode is planned or abandoned is not known.

The final status line reads a field that does not exist

_summarize formats {mode} from report.get("mode") and counts len(report["cases"]) (AutomatedDentalToolsRemote GreedyRegRemote/GreedyRegRemote.py:133-138). The report has no mode (its keys are listed under Arguments and schema), so the status-bar message reads "GreedyReg finished in ? mode: N pair(s) registered." And cases also holds failed patients (SADT-VISOR GreedyReg/__init__.py:166-171), so N counts them. summary.registered is the right number.

Two files do not make a pair

The client says that two files are one pair (GreedyRegRemote.py:75-77) and the fixture describes t2 accordingly. pairing.pair walks folders (os.walk, pairing.py:232-276): run on 2026-11-09 with a/P1_T1.nii.gz and b/P1_T2.nii.gz it matched nothing, which the tool turns into No patient appears in both the T1 and the T2 folder (SADT-VISOR GreedyReg/__init__.py:112-122). A single uploaded file reaches run() as that file's path (VISOR-serve server/main.py:1288-1296). The tool's tests use folders only. A run through a server was not made.

The hosted test cohort is refused as offered

The only test file the server hosts for GreedyReg is CBCT_T1_T2_pair (VISOR-serve scripts/data-manifest.yml:756-781), and every path argument offers it (VISOR-serve server/registry/conventions.py:236-240, no [tools.GreedyReg] section to narrow it). Its root holds a T1/ and a T2/ folder (checked on a staged copy). pairing.pair refuses a folder that holds more than one timepoint (pairing.py:336-358), and GreedyReg does not descend into T1/ by itself, unlike AREG_CBCT which calls pairing.timepoint_root. Run on 2026-11-09 on the staged copy's file names: The T1 folder holds scans from more than one timepoint (T1, T2); pointing at T1/ and T2/ pairs C_0001. Whether the panel lets one pick a sub-folder of a hosted test file was not checked. The same convention offers hosted test files for masks and initial_transforms, which are the clinician's own files.

Only the Greedy calls are bounded, not the run

Each Greedy call is limited to 600 s (SADT-VISOR GreedyReg/pipeline.py:136,145) and a pair makes two (SADT-VISOR GreedyReg/__init__.py:273,276), so a pair can take up to 1200 s. There is no bound on the number of pairs and the server sets none (TOOL_TIMEOUT_SECONDS = 0, VISOR-serve server/config.py:77). VISOR-serve CLAUDE.md:896 speaks of a bound "per pair"; the code bounds each call.

No report when nothing was registered

If every pair fails, the tool raises (SADT-VISOR GreedyReg/__init__.py:180-187) before the line that writes GreedyReg_report.json (:189). The reasons then travel only in the error message. A failed patient's reason is the exception text (:167).

The produced .mat is not a Slicer transform; the mask's space is not checked

<patient>_transform.mat is what Greedy writes with -o (SADT-VISOR GreedyReg/pipeline.py:86; __init__.py:255); nothing in the package converts it to a .tfm, and the client does not load it (GreedyRegRemote.py:97-104). A multi-label mask is flattened by > 0 and nothing checks that it lies in the space of T1 (pipeline.py:117-126). Both points are those of the legacy module (legacy page), carried over unchanged. Read in code.

Defaults that differ from the legacy module

The metric default is NCC where the legacy combo started with NMI (SADT-VISOR GreedyReg/__init__.py:49, GreedyReg.py:575@3c67957), the transform is Rigid by default, and the suffix is configurable (output_suffix) where the legacy CLI wrote _registered (GreedyReg_CLI.py:168@3c67957).

Greedy is assumed to use the GPU

The tool declares no device argument, so the server's admission treats every run as a GPU run (VISOR-serve server/execution/dispatch.py:95-116), while Greedy runs on the CPU. A GreedyReg run can therefore wait for a GPU slot it does not use. Read in code.

Pairing and failures are explicit

Unmatched patients, unused masks and unused initial transforms are reported (SADT-VISOR GreedyReg/__init__.py:108,131-132); one failing patient costs one patient; the metric and the transform type are validated twice (pipeline.py:47-55). The 189 tests of the package passed on 2026-11-09, with Greedy stubbed.
