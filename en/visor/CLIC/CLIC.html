CLIC on VISOR

In VISOR, CLIC runs entirely on the server: the Slicer panel uploads CBCT scans and gets back one label map per scan plus a JSON report. The network and the slice-by-slice method are the legacy ones; how scans are found, how the checkpoint is chosen, how outputs are named and how a failed scan is handled have changed. The legacy Slicer module is described on its own page.

VISOR 1 network Legacy page Guide (VISOR)

References on this page name a repository, then a path inside it, then a line: SADT-VISOR is the tool catalogue (commit 6ba2a78), VISOR-serve the server (e9a7e5d), Remote the Slicer client (AutomatedDentalToolsRemote 19b95e8), legacy SlicerAutomatedDentalTools at 3c67957. A bare path such as pipeline.py:36 is in SADT-VISOR tools/CLIC/src/sadt_clic/. Everything was read in the code; nothing on this page was run. Overview of the stack: VISOR.

1. Position in the chain

  • State: ported, implemented in code and covered by tests in the tool (SADT-VISOR tools/CLIC/tests/, not run for this page). Nothing here says a given server is running it.
  • API name CLIC, declared by [tool.sadt] tool = true, name = "CLIC" (SADT-VISOR tools/CLIC/pyproject.toml:24-26). The server discovers every tool folder that carries this table; there is no hard-coded list (Architecture).
  • Client panel CLICRemote, a thin panel generated from the server's tool description (Remote CLICRemote/CLICRemote.py:44,53), built with the extension (Remote CMakeLists.txt:35).
  • Calls / called by: nothing on either side. run() has no sup argument, so there is no sup.run (SADT-VISOR __init__.py:76-88), and no other tool names CLIC. The schema nevertheless carries "supervisor": true, because data_root is an injected argument (output of SADT-VISOR scripts/describe.py on tools/CLIC).
  • Hosted data: DATA/CLIC/models/final_model.pth (176 MB) and the test scan MG_test_scan.nii.gz are in the data manifest (VISOR-serve scripts/data-manifest.yml:630-641). The scan is a whole-head CBCT with no known impacted canine (SADT-VISOR tools/CLIC/README.md:116-120): it proves the round trip, not the classification.

3. The pipeline

3.1 Finding the scans

scans is a single file or a folder. A folder is walked recursively with os.walk, hidden files are skipped, and only names ending in .nii or .nii.gz (case-insensitive) are kept, as file paths, sorted (pipeline.py:58-79). The legacy collector also advertised .nrrd, .mha and .mhd, which nibabel does not read, and returned sub-folders instead of files (legacy §3.1).

SCAN_EXTENSIONS = (".nii", ".nii.gz")                 # pipeline.py:36
found = discover_scans(str(scans))                    # __init__.py:115
if not found:
    raise ValueError("No .nii or .nii.gz scan found in '...'. "
                     "CLIC reads NIfTI volumes; NRRD and MetaImage are not supported.")

An empty result is a ValueError (__init__.py:116-123), which the server turns into a 422 carrying the message (VISOR-serve server/execution/runner.py:243-244). Only the base name of the input is quoted, not its full path.

3.2 Choosing and loading the checkpoint

model is optional. When it is empty the tool looks in <data_root>/CLIC/models (_own_models, __init__.py:30-37) and takes the single .pth there; none or several is a refusal that names the candidates (_sole_checkpoint, :40-61). A named folder gets the same rule, a named file is used as is (_resolve_checkpoint, :64-73).

The class count is not assumed. It is read from the shape of the classification head in the state dict, background included, and both heads are rebuilt to that size before the weights are loaded (pipeline.py:96-144):

state = torch.load(checkpoint_path, map_location=device, weights_only=True)
classes = class_count(state)       # roi_heads.box_predictor.cls_score.bias .shape[0]
model = maskrcnn_resnet50_fpn(weights=None)
model.roi_heads.box_predictor  = FastRCNNPredictor(box_features, classes)
model.roi_heads.mask_predictor = MaskRCNNPredictor(mask_features, 256, classes)
model.load_state_dict(state)
model.to(device).eval()

The published checkpoint has four classes (background, buccal, bicortical, palatal), which is what catalogs.CLASSES = len(LABELS) + 1 expects (catalogs.py:23-40). A malformed or missing head is a ValueError naming the key (pipeline.py:109-123). resolve_device keeps cuda when a card is visible and otherwise falls back to cpu with a warning (pipeline.py:82-93).

3.3 The slice loop

Each scan is read with nibabel as float32 (__init__.py:216-219); a volume that is not 3D fails that scan only. The label volume is an int16 array of the same shape. The loop runs over the third array axis as stored in the file, with no reorientation, exactly as the legacy runner did:

for index in range(volume.shape[2]):                          # pipeline.py:170
    image = normalise(volume[..., index])                     # min-max to [0, 1]
    tensor = torch.from_numpy(image).unsqueeze(0).repeat(3, 1, 1).float().to(device)
    with torch.no_grad():
        predicted = model([tensor])[0]                        # one slice per call
    keep = predicted["scores"] >= score_threshold             # default 0.7
    masks = (predicted["masks"][keep] > MASK_BINARY_THRESHOLD).squeeze(1)   # 0.5
    for mask, label in zip(masks.cpu().numpy(), predicted["labels"][keep].cpu().numpy()):
        labels[..., index][mask] = int(label)                 # last one wins
        detections += 1
  • Normalisation: per slice, (x - min) / (max - min); a flat slice (range ≤ 1e-8) becomes zeros rather than NaNs (pipeline.py:147-154). The legacy _norm is the same (legacy CLIC/runner/clic_runner.py:44-46).
  • Resizing and ImageNet standardisation happen inside torchvision's GeneralizedRCNNTransform, as in legacy (legacy §4.1); the tool does not resample anything itself.
  • Thresholds: score_threshold is an argument (default DEFAULT_SCORE_THRESHOLD = 0.7, pipeline.py:41); the mask threshold stays a constant, MASK_BINARY_THRESHOLD = 0.5 (:44).
  • Overlap: masks are written in the order the network returns them, so where two overlap the last one overwrites; there is no vote and no 3D consistency between slices (pipeline.py:180-182).

3.4 Outputs and the report

Each scan is keyed by its path relative to the input root, and the output tree mirrors the input tree. The .nii.gz or .nii extension is stripped before the suffix is added (__init__.py:223-231):

input   scans/site_A/P01.nii.gz
output  output_dir/site_A/P01_seg.nii.gz          # affine and header copied from the input

A single file is its own root, so its result lands directly in output_dir (__init__.py:163-165). The label map keeps the input's affine and header (nib.Nifti1Image(labels, image.affine, image.header), :231), so scan and segmentation open aligned. Then CLIC_report.json is written next to the results (:201), with this shape (keys from __init__.py:133-155,188-189,233-249):

{
  "tool": "CLIC", "model": "final_model.pth", "classes": 4,
  "labels": {"Buccal": 1, "Bicortical": 2, "Palatal": 3},
  "label_colors": {"Buccal": [0.0, 1.0, 0.0], "Bicortical": [1.0, 1.0, 0.0], "Palatal": [0.6, 0.4, 0.2]},
  "device": "cuda", "score_threshold": 0.7,
  "cases": {
    "site_A/P01.nii.gz": {"input": "site_A/P01.nii.gz", "status": "ok", "slices": 512,
                          "detections": 37, "labels_present": [3], "detected": ["Palatal"],
                          "produced": ["site_A/P01_seg.nii.gz"]},
    "site_B/P02.nii.gz": {"input": "site_B/P02.nii.gz", "status": "failed", "reason": "ValueError: ..."}
  },
  "summary": "1/2 scan(s) segmented", "duration_seconds": 41.3
}

The values in the example (slice count, detection count, duration) are illustrative; the keys are those of the code. When the checkpoint has another class count, labels and label_colors are null and a labels_note says why: an unnamed integer is preferred to a wrong name (__init__.py:146-154, catalogs.py:43-58). A scan with no detection gets "note": "no detection cleared the score threshold" (:245-249).

3.5 Failures, progress and logs

  • One scan fails, one scan is lost. Any exception inside _segment_one is recorded in that scan's entry as status: failed with reason, and the loop continues (__init__.py:173-186). The run raises only when no scan was written, listing every reason (:191-199); the report is then not written.
  • Progress: progress.report(index, total, "scan") before each scan (__init__.py:170) appends a JSON line to the file named by SADT_PROGRESS_FILE (progress.py:3,21,89-103). Messages give a position, never a file name, because file names are patient metadata (progress.py:13-15).
  • Logs: the failure log line also names the position, not the file (__init__.py:183), since a failed run's stderr is kept in the server's log.

8. Findings in VISOR

The backbone download is still reachable

The tool builds the network with maskrcnn_resnet50_fpn(weights=None) (SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:136), as legacy did. In the pinned torchvision 0.26.0 (pyproject.toml:14), weights_backbone defaults to ResNet50_Weights.IMAGENET1K_V1 (torchvision/models/detection/mask_rcnn.py:416) and resnet50(weights=weights_backbone) is called (:490,502), which fetches the file through load_state_dict_from_url (torchvision/models/_api.py:91); the checkpoint is loaded over it afterwards (pipeline.py:142). The test that forbids network calls only searches the tool's own sources for strings (tests/test_device_and_contract.py:163-175) and cannot see this call. The torchvision lines were read in an installed copy of torchvision 0.26.0; nothing was run, and whether a given server already holds the ResNet-50 file in its torch cache was not checked.

A scan with no detection is a success

A volume where nothing clears the threshold is written as an all-zero label map with "note": "no detection cleared the score threshold" (__init__.py:245-249). The "nothing written" guard counts written scans, not detections (:191-199), so a batch where every scan is empty is a successful run. The source comment says this is also what a wrong checkpoint looks like (:246-248).

The client neither shows nor merges the report

CLIC_report.json carries the label table, what was detected and which scans failed (__init__.py:133-155,173-186), but the panel has no RUN_REPORT (Remote CLICRemote/CLICRemote.py:53-72; base default empty, ServerToolsCore/ServerToolsCoreLib/base_widget.py:1493), unlike CNE and DOCShapeAXI. A scan that failed is visible only by opening the JSON. A folder larger than one batch (25 entries or 400 MB by default, VISOR-serve server/config.py:192,196) is sent as several runs whose folders are folded back into the output folder at the end; the merged report is written only for a panel that declares RUN_REPORT (base_widget.py:2192), and when two batches produce the same file name the first is kept (:2205-2224). For CLIC the final CLIC_report.json is therefore the one of a single batch. Read in the code, not run.

Server comments describe another CLIC

VISOR-serve comments describe a CLIC that "batches slices inside one forward" (server/execution/admission.py:146) with a batch_size = 4 argument (server/execution/runner.py:1251,1271-1272), and quote memory measurements of CLIC at widths 1 to 45 (server/execution/costs.py:470-477). The packaged tool has no batch_size argument, runs one slice per model([tensor]) call (pipeline.py:170-176) and never calls progress.set_width, which is only defined (progress.py:41). Those comments and figures therefore describe another version of the tool; do not read "four slices per pass" as a property of this code.

Overlaps are still resolved by order, slice by slice

Where two kept masks overlap on a slice, the one the network returned last overwrites the other, and each slice is decided alone: there is no vote between classes and no 3D consistency, so one canine can carry two labels on neighbouring slices (pipeline.py:170-182, same as legacy clic_runner.py:84-87). Read in the code.

Verified: the other legacy defects are gone

Checkpoint choice refuses ambiguity, the class count is read, loading is weights_only=True, outputs are named correctly and keyed by relative path so two homonymous scans no longer overwrite each other (SADT-VISOR __init__.py:40-73,223-231, pipeline.py:96-144). The label table is in the report, not only in the widget.
