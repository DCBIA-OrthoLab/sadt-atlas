CLIC on VISOR

CLIC finds impacted canines on a CBCT and says whether each lies on the cheek side, the palate side or across the bone. This page explains how, step by step, with the maths: what goes in, what each step does to it, and what comes out. The files, lines, arguments and findings are on the code page. The legacy Slicer module is on its own page.

Code (developers) VISOR 1 network Legacy page Guide (VISOR)

Where this page names a repository it means the SADT-VISOR tool catalogue at 6ba2a78, the VISOR-serve server at e9a7e5d, the Slicer client AutomatedDentalToolsRemote at 19b95e8, and the legacy module SlicerAutomatedDentalTools at 3c67957. The file names, line numbers and every finding are on the code page. Everything here was read in the code; nothing was run for this page.

Overview: what goes in, what comes out

CLIC looks for impacted canines in a CBCT scan. It does not look at the whole volume at once: it reads the scan slice by slice, and on each slice a trained network outlines the canines it finds and, in the same pass, says where each one lies relative to the bone: on the cheek side (buccal), on the palate side (palatal) or across the bone (bicortical). There is one network and no separate classifier: outline and class come out together.

CLIC on VISOR
Inputone CBCT as a NIfTI file (.nii or .nii.gz), or a folder of them, searched recursively
Methodper slice: rescale the grey values, give the slice to a Mask R-CNN, keep the confident detections, paint them into a label volume
Outputone label map per scan, on the same grid as the scan: 0 is background, 1 buccal, 2 bicortical, 3 palatal; plus CLIC_report.json, a summary of what was found and what failed
Whereon the server only; the Slicer panel uploads the scans and loads the label maps

The network and the slice-by-slice method are the legacy ones; nothing is retrained. What changed is how scans are found, how the weights file is chosen, how outputs are named and how a failed scan is handled (What changed).

1. Position in the chain

CLIC is standalone. No other tool prepares its input and no other tool reads its output, so it can be run on any NIfTI CBCT, whatever was done to it before. In VISOR the panel in Slicer is generated from the server’s description of the tool; it uploads the scans, waits, and downloads one archive with the label maps and the report. The tool is covered by automated tests in its repository (not run for this page); whether a particular server is running it is not something this page can say.

In the codeAPI name, hosted weights, what the schema declares, who calls whom

1.1 What runs where

The server does everything that matters: it reads the scans, runs the network on the graphics card when one is available, applies the thresholds and writes the files. The Slicer side only chooses the scans and an output folder, shows progress, unpacks the archive and, if asked, displays up to twelve of the label maps with a volume-rendering preset. The report is written by the server but the panel does not display it.

2. Files involved

The tool is small: one main file that organises a run, one that holds the image processing, a table of class names and colours, and a progress writer. The client panel is about eighty lines. The lines and the tests are listed on the code page.

3. The pipeline

A run has four levels: once per run, the tool finds the scans and loads the network; once per scan, it reads the volume; once per slice, it prepares the picture, runs the network and paints the result; at the end it writes the files. Click a box to read its section.

In the codeThe function behind each box of the diagram

3.1 Finding the scans

A single file is used as it is. A folder is searched recursively; hidden files are skipped and only names ending in .nii or .nii.gz are kept. The old module also let other formats through that its network code could not read; this one refuses them up front, with a message. If nothing is found the request is refused with a readable error.

In the codeExtensions, the walk, the error raised when nothing is found

3.2 Choosing and loading the checkpoint

The weights file is not chosen by the user. When none is named, the tool takes the single .pth in its models folder on the server; zero or several files is a refusal that names the candidates, so that a stray second file cannot silently change the results. The network is a Mask R-CNN: a ResNet-50 backbone with a feature pyramid looks at the picture, proposes candidate regions, and for each region predicts a class, a box and a mask. The number of classes is not assumed but read from the weights file, and the output layers are built to that size before the weights are loaded. The published weights have four classes: background and the three canine positions.

Weights are loaded in a mode that cannot run code embedded in the file. If a graphics card is visible the network runs on it; otherwise it falls back to the processor, with a warning.

In the codeThe checkpoint rules, class count, load call and device choice

3.3 The slice loop

Each scan is read as a stack of numbers and cut along its third array axis, in the order stored in the file; the tool does not reorient the scan. A volume that is not three-dimensional fails that scan only.

Before the network, each slice is rescaled and copied to three identical channels (the network was designed for colour pictures). Inside the network the picture is also enlarged so that its short side is 800 pixels and standardised with the ImageNet mean and spread; this is done by torchvision, the tool does nothing there.

Because every slice is rescaled on its own, a slice that is nearly empty is stretched to the full range just like a slice of bone: the network never sees absolute Hounsfield values. This is the legacy behaviour, kept.

Each slice is decided alone. Nothing links the result of one slice to its neighbours, so the same canine can carry two labels on two adjacent slices, and nothing turns the result into one answer per patient.

In the codeThe loop, the three thresholds, the overwrite rule and the normalisation function

3.4 Outputs and the report

The output folder mirrors the input folder: a scan site_A/P01.nii.gz gives site_A/P01_seg.nii.gz, so two patients with a file of the same name in different folders do not overwrite each other. The label map copies the scan’s geometry, so it opens aligned on the scan. It also reuses the scan’s header, so the file is saved in the scan’s own data type (a scan stored as floating point numbers gives a floating point label map); the values are still 0 to 3. The report lists, for every scan, whether it succeeded, how many slices were read, how many detections were kept and which classes appear, plus the class names, the colours and the threshold used. A scan with no detection is written as an empty label map and noted as such.

In the codeOutput naming, the report keys with an example, the note on empty scans

3.5 Failures, progress and logs

One bad scan does not stop the others: it is recorded as failed, with a reason, and the loop goes on. The run fails only if no scan at all could be written. Progress is reported as a position (scan 3 of 12), never as a file name, because file names can be patient information; the logs follow the same rule.

In the codeThe exception handling, the progress file and the log lines

4. What you can choose

  • The scans: one file or a folder of NIfTI volumes.
  • The score threshold: 0.7 by default. Raising it keeps only the most confident detections; lowering it keeps more, with more false ones.
  • The output suffix: seg by default; it is added to the scan name.
  • Not offered: the weights file (the server’s own), the device (the server’s setting, with a processor fallback) and the output folder (set by the server). The mask threshold of 0.5 is fixed.

6. Environment

The tool has its own Python environment on the server (Python 3.11, with pinned versions of torch, torchvision, nibabel and numpy), built from a lock file when the server image is built. Nothing is installed on the workstation. The weights file is about 176 MB and is staged on the server in advance.

7. What changed from the legacy logic

The network, the per-slice rescaling, the three channels, the slice axis and the thresholds are the same. Around them:

  • One run handles all scans in one process, instead of one process per scan started by the Slicer panel.
  • Only NIfTI is accepted, and a request with no NIfTI is refused with a clear message.
  • The weights file must be the only .pth of the folder; the old code silently took the first by alphabetical order.
  • The class count is read from the weights instead of being fixed at four, and the class names are in the tool and in the report instead of only in the panel.
  • Outputs mirror the input folders and are named X_seg.nii.gz, where the old code wrote X.nii_seg.nii.gz.
  • A failed scan is recorded in the report, and progress goes through a progress file the client can read, instead of text markers that never matched.
  • The weights are loaded in the safe mode, and there is no model download button.

8. Known issues

  • Building the network may still try to fetch the ResNet-50 backbone from the internet before the weights are loaded over it; see the finding.
  • A scan where nothing is detected counts as a success, which is also what a wrong weights file looks like; see the finding.
  • The panel does not display the report, so a failed scan is visible only by opening the JSON; see the finding.
  • Some server comments describe a CLIC that batches several slices per pass, which this tool does not do; see the finding.
  • Overlaps are still settled by order, slice by slice; see the finding.
  • On the positive side, the other legacy defects were checked and are gone; see the check.
