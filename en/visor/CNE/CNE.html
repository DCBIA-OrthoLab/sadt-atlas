CNE on VISOR

In VISOR, CNE runs on the server: the Slicer panel uploads the clinical notes, the server reads them and runs the language model, and the extractions come back as files. The clinical text therefore leaves the workstation, which the legacy module never did. The prompts and context windows are the legacy ones; reading the notes, parsing the answer and naming the outputs have changed. The legacy Slicer module is described on its own page.

Overview of the stack: VISOR.

1. Position in the chain

  • State: ported, implemented in code, with tests in the tool (SADT-VISOR tools/CNE/tests/test_run.py, 130 test functions, not run for this page). The Dashboard is not ported. Only the TMJ model is staged on the server's data manifest.
  • API name CNE (SADT-VISOR tools/CNE/pyproject.toml:35-37), code in __init__.py, extraction.py, readers.py, dependencies.py, layout.py.
  • Client panel CNERemote, a thin panel (Remote CNERemote/CNERemote.py:57,61-62; built, CMakeLists.txt:36). It reads CNE_report.json after a run and shows a one-line summary in the status bar (:75-103).
  • Calls / called by: nothing. No sup argument, no sup.run (__init__.py:46-56), and no other tool names CNE.
  • Hosted data: one bundle, DATA/CNE/models/TMJ/qwen-ft-q4_k_m.gguf (4,683,073,408 bytes) and one synthetic TMJ test note (VISOR-serve scripts/data-manifest.yml:687-701).

3. The pipeline

3.1 Checking the folders and finding the notes

A missing notes path is a FileNotFoundError (__init__.py:97-100). If notes is a folder and output_dir is the same folder (symlinks resolved), the run is refused, because the extractions would be read back as notes by the next run (:106-110,320-324). The tool then creates output_dir itself (:116); legacy relied on the panel to create it.

Discovery is recursive and returns files sorted by relative path (readers.py:92-123). It keeps .txt, .pdf and .docx without regard to case (:33,78-81), skips names starting with ~$ (Word lock files) or a dot, and folders named __MACOSX (:60-61,84-90,117-118). The output folder is excluded when it sits inside the input (__init__.py:118). Nothing found is a 422 naming the three extensions (:119-126); legacy exited with status 0 in that case (legacy CNE_CLI/CNE_CLI.py:137-141).

3.2 Choosing and loading the model

model is required. A .gguf file is used as is; a folder must hold exactly one .gguf, searched recursively, or the run is refused with the candidates named (extraction.py:89-128). If the model's path names one note type and notes_type is the other, a warning goes into the report; it is not a refusal (model_type_hint, extraction.py:131-143; __init__.py:132-142).

CONTEXT_TOKENS = {"TMJ": 6144, "Ortho": 2048}                # extraction.py:49
SYSTEM_PROMPTS = {"TMJ": INSTRUCTION_TMJ, "Ortho": None}      # extraction.py:51

window = context_for(notes_type, context_tokens)              # 0 means the type's default
offloading = wants_gpu and supports_gpu_offload()             # asked before the 4.4 GB load
engine = load_model(model_file, window, seed, -1 if wants_gpu else 0)   # __init__.py:144-165

load_model builds one llama_cpp.Llama(model_path, n_ctx, n_gpu_layers, seed, verbose=False) for the whole batch (extraction.py:193-203). Its loader chatter is captured with contextlib.redirect_stderr and logged at debug level (:63-86), where legacy redirected the process's file descriptor 2 with os.dup2 and no finally (legacy CNE_CLI.py:157-171). Every import of llama_cpp goes through engine_module(), which first tries to open the CUDA runtime from the venv (extraction.py:167-177, dependencies.py:65); on the CPU build that is a no-op. A device = "cuda" request on a build without GPU support adds a warning and gpu_offload: false to the report (__init__.py:145-165,184).

3.3 Reading a note

All three go through the same normalisation of quotes, dashes and non-breaking spaces, ported from the legacy table (readers.py:47-55,64). PyMuPDF and python-docx are imported only when a note of that format is read (dependencies.py:39); a missing package fails those notes with ToolUnavailableError, not the run. Then looks_empty refuses a text with no letter or digit, which is what an image-only PDF gives; there is no OCR (readers.py:254-264, __init__.py:276-285).

3.4 Asking the model

messages = []
if SYSTEM_PROMPTS[notes_type]:                       # TMJ only
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": text})   # extraction.py:156-164

output = model.create_chat_completion(messages=messages,
                                      max_tokens=max_tokens, temperature=temperature)
content, finish_reason = choice["message"]["content"], choice.get("finish_reason")   # :206-223
if finish_reason == "length":   # cut off at max_tokens
    raise ValueError("the model's answer was cut off ...")                          # __init__.py:293-297

The TMJ instruction is the legacy string verbatim: "Using the following note, extract structured key-value pairs about the patient's symptoms and diagnoses:" (extraction.py:41-44). Ortho gets no system message, as in legacy. The tool does not compare the note's length with the window: context_for only rejects a negative value (extraction.py:146-153), and any error raised by llama.cpp is caught for that note (__init__.py:200-212).

3.5 Reading the answer and writing it

  1. JSON first: the slice from the first { to the last } is parsed; a dict under "extraction" is unwrapped (extraction.py:261-275). The slicing is the legacy one.
  2. Then key: value lines: keys are lowercase words and underscores, at least 60 % of the non-empty lines must match, and a repeated key keeps its first value (extraction.py:230-235,278-301). The source says the published TMJ fine-tune answers in this form, 46 fields and no JSON (:244-245).
  3. Otherwise nothing is written and the note fails (__init__.py:299-305). Legacy wrote the raw answer.

Two files are written per note under the mirrored tree (__init__.py:240-266,307-317): the JSON, canonical, and a key : value text where a list is joined with commas and a nested dict stays JSON (extraction.py:304-328).

input   notes/P01/B_001.txt
output  output_dir/P01/Extraction_B_001.txt.json
        output_dir/P01/Extraction_B_001.txt.txt

plan_outputs checks that no two notes map to the same pair before anything runs (__init__.py:240-266). CNE_report.json carries tool, notes_type, model, system_prompt (a flag), context_tokens, max_tokens, temperature, seed, device, gpu_offload, warnings, and per note input, the reader and encoding, characters, finish_reason, answer_characters, status, fields, the two output paths or a reason; then summary and duration_seconds (__init__.py:171-187,213-216,272-317). The answer text itself is not put in the report or the logs.

3.6 Failures

Each note is in its own try: a failure is logged with the note's relative path and recorded in the report, and the loop continues (__init__.py:191-213). If no note was written the run raises: a 503 (ToolUnavailableError) when every failure was a missing reader, otherwise a 422 (ValueError) listing each note's reason (:218-232); the report is then not written. Note that this per-note log line names the file, unlike CLIC's progress messages.

8. Findings in VISOR

The text of the notes is sent to the server

The legacy statement that CNE keeps clinical text on the machine ("no network exfiltration", legacy page §11, and the legacy Guide's "Nothing leaves your machine") does not hold for VISOR. The VISOR panel uploads the notes you select to a tool server where the model runs (Remote README.md:24-35; CNERemote/CNERemote.py:57 and the server-side notes argument, Arguments and schema). The Remote README says in so many words that there is no de-identification in the current client (README.md:32), and the VISOR security page lists the de-identification of uploaded files as specified only (De-identification, Transport). What the tool itself does with the text: it runs llama.cpp in-process and contains no network call (grep for urllib, requests, http and socket in tools/CNE/src/sadt_cne/ finds none), and the server writes the answer to the job folder. The legacy finding stays true of the legacy module only.

The client says "automatic", but nothing matches the model to the note type

The Remote README ("leave Model on automatic and the server uses the model fine-tuned for that note type", README.md:611-613) and the docstring of CNERemote/CNERemote.py:15-18 ("the model field defaults to (automatic)") are out of date. model is a required argument of the tool (__init__.py:49), and the client adds its "(automatic)" entry only to optional arguments (Remote ServerToolsCore/ServerToolsCoreLib/base_widget.py:1074-1076, rationale at formgen.py:107-109): the Model field lists the hosted bundles and sends the one selected. Nothing derives the model from notes_type (resolve_model_file takes a path, extraction.py:89-128); a mismatch between the two is only a warning (next callout). Read in the code, not run in Slicer.

Only the TMJ model is hosted

The data manifest stages one bundle, TMJ/qwen-ft-q4_k_m.gguf (VISOR-serve scripts/data-manifest.yml:687-692). notes_type = "Ortho" is accepted by the tool but no Ortho model is hosted, and a model whose path names the other type is only a warning in the report, not a refusal (__init__.py:133-139, extraction.py:131-144). The manifest comment that the Ortho repository "answers 404 today" (data-manifest.yml:682-686, repeated in SADT-VISOR tools/CNE/README.md:205-208) is out of date: on 2026-11-09 an HTTP HEAD request on the old dcbia/ Ortho URL answered 307 (a redirect to the DCBIA-OrthoLab/ organisation), and one on DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho/.../model-q4_k_m.gguf answered 302 to a download (status codes only, nothing downloaded). The TMJ URL in the manifest also still uses the old dcbia/ name and answers 307.

CPU, whatever some comments say

The pinned wheel index for llama-cpp-python is the CPU one (SADT-VISOR tools/CNE/pyproject.toml:60-67). Three comments disagree with it: the same file's header speaks of a "CUDA 12.4 wheel index below" (:8-23); the published description of device says "it needs the CUDA build of llama.cpp, which this tool pins" (__init__.py:82-84); and VISOR-serve's compose file says CNE cannot run in the CPU service because it ships the CUDA build (docker-compose.yml:105-110). The code is the CPU build, so a cuda request is reported as ignored. The tool's README agrees with the code (SADT-VISOR tools/CNE/README.md:154-165). Do not read "CNE needs a GPU" anywhere.

No guard on the length of a note

The legacy concern about long notes (legacy page, §11) is only half closed. A cut-off answer is now refused (__init__.py:293-297) and max_tokens defaults to 2048 instead of 500. But nothing compares the note with the context window or checks that max_tokens leaves room in it: context_for only rejects a negative value (extraction.py:146-153). With the Ortho default the answer budget alone equals the window (2048 and 2048, :49, __init__.py:51). What llama.cpp does then was not checked; whatever it raises fails that one note (__init__.py:200-212). Read in the code.

Output names changed

Files are Extraction_<note file name>.json and .txt, not Extraction_<stem>.txt (__init__.py:240-266). Anything that reads the legacy names, such as the legacy Dashboard (Extraction_*.txt), would not find the same files.

Verified: the silent legacy failures are closed

An image-only PDF, a truncated answer and an answer that is neither JSON nor fields now fail the note instead of writing a plausible file (__init__.py:276-305); homonymous notes of different formats no longer overwrite each other (:240-266); the TMJ/tmj spelling split is gone (extraction.py:49-51); a GPU request that cannot be honoured is reported (__init__.py:145-165). Read in the code.
