CNE on VISOR

CNE reads free-text clinical notes and writes down the facts it finds in them (symptoms, diagnoses, scores) as a list of field : value lines. A language model does the reading; everything around it decides what the model is shown and which of its answers are kept. In VISOR the model runs on a server, so the notes are uploaded, which the legacy module never did. This page explains the steps and the few calculations in them; the details a developer needs are on the code page, and the legacy module has its own page.

Overview: what goes in, what comes out

CNE
Inputone note, or a folder of notes (.txt, .pdf, .docx), sub-folders included
What you choosethe type of note (TMJ or Ortho), the model file, and how long an answer may be
The modela quantised language model run on the server’s processor; the one hosted is a Qwen 2.5 7B fine-tuned on TMJ notes
Outputfor each note, a JSON file and a text file of field : value lines, plus one run report

The model alone decides which fields exist and what their values are. Nothing checks an extraction against the note it came from; the tool only controls what the model is shown and which answers are written down.

1. Where it runs

Slicer keeps only a small panel (CNERemote). It uploads the notes to a server, waits, then downloads one archive and unpacks it into the chosen folder. The model is loaded and run on the server, in an environment of its own, and nothing is loaded into the Slicer scene: the results are text. CNE calls no other tool and no tool calls CNE.

Because the model runs on the server, the text of the notes leaves the workstation. The legacy module kept it on the machine. Nothing de-identifies the notes before they are sent (known problems).

1.1 What runs where

  • Server: publishes the form the panel shows, reads the three note formats, runs the model, writes the results. The model is loaded once per call, which is why a whole folder of notes is sent in a single call.
  • Slicer: shows the generated form, uploads the notes, unpacks the archive, and prints a one-line summary in the status bar (how many notes were extracted, with which model type, and how many warnings). Nothing is installed or downloaded on the workstation.

2. Files involved

The tool is five small source files: the entry point that runs the loop over the notes, the model code (prompts, loading, parsing), the readers for the three formats, a loader for optional packages, and the layout of the panel. Of the legacy module, only the inference was ported; the panel, the model download and the Dashboard were not.

3. The pipeline

Once per run the tool checks the folders, lists the notes, chooses the model file and loads it. Then, note by note, it reads the text, asks the model, and decides whether the answer can be kept. Each box is a link to its step.

3.1 Checking the folders and finding the notes

The tool first checks that the notes exist and that the results will not be written into the notes folder, otherwise the next run would read its own results as notes. It then lists the .txt, .pdf and .docx files in the folder and its sub-folders, whatever the case of the extension, skipping Word lock files and hidden files. If it finds none, the run stops with an error that names the three extensions; the legacy module just ended quietly.

In the codeFolder checks, recursive discovery, skipped names, error codes

3.2 Choosing and loading the model

The model is one quantised file in the GGUF format, run by llama.cpp. A file is used as it is; a folder must contain exactly one. Each type of note has its own context window, the amount of text (note and answer together, counted in tokens) that the model can hold at once: 6144 for TMJ, 2048 for Ortho. If the path of the model names the other type of note, a warning goes into the report but the run continues. The model is loaded once for the whole batch, since loading 4.4 GB is the slow part, and if a GPU is requested from a processor-only build the run goes on without it and says so in the report.

In the codeModel resolution, the window table, loading and the CPU build

3.3 Reading a note

A text file is decoded as UTF-8, then Windows-1252, then Latin-1, whichever works first. A PDF gives its text layer page by page. A Word file gives its headers and footers, then its body in reading order with tables, one table row per line. Then every note goes through the same cleaning step.

A text with no letter and no digit, which is what a scanned PDF gives, is refused by name: there is no OCR.

In the codeThe three readers, the replacement table, the empty-text check

3.4 Asking the model

The note is sent as a chat. For TMJ notes a system prompt comes first: “Using the following note, extract structured key-value pairs about the patient’s symptoms and diagnoses”. Ortho notes get none, because their model was fine-tuned to answer from the note alone. The answer is limited to 2048 tokens by default, the sampling temperature is 0 and a fixed seed is used, so the same note should give the same answer. If the model stops because it reached the limit, the answer is incomplete and the note fails.

With the Ortho defaults the answer limit alone equals the whole window (2048 and 2048). The tool never compares a note with the window: if the model engine refuses a note that is too long, only that note fails.

In the codeThe messages, the call, the cut-off check, and the missing length guard

3.5 Reading the answer and writing it

The model is expected to answer in JSON, but nothing forces it to. The tool tries two readings, in this order, and writes nothing if both fail.

A field that appears twice keeps its first value. For each note two files are written in a folder tree that mirrors the notes: a JSON file, which is the canonical result, and a text file of field : value lines for reading, where a list is joined by commas. For B_001.txt they are Extraction_B_001.txt.json and Extraction_B_001.txt.txt. The run report lists, for each note, how it was read, how long the note and the answer were, whether it succeeded, how many fields it gave, and why it failed if it did. The text of the answer itself is not put in the report or in the logs.

In the codeThe parsing code, the output planner, the report fields

3.6 Failures

Each note is handled on its own. A failure (empty text, an answer cut off, an answer that is neither JSON nor fields, an error in the model engine) is logged with the note’s path, recorded with its reason, and the loop goes on. The whole run fails only if no note at all was written; it then ends with an error listing the reason for each note, and no report is written.

4. What you can choose

  • Notes: a note or a folder of notes. Required.
  • Note type: TMJ or Ortho. It selects the system prompt and the context window together.
  • Model: a model file, or a folder holding exactly one. The list shows the hosted models; there is no “automatic” choice, so the model is not derived from the note type.
  • Answer limit: the longest answer per note, 2048 tokens by default.
  • Temperature: 0 by default, which means no randomness.
  • Context window: 0 means the default of the note type.
  • Hidden settings: a random seed and the device (processor by default); the server fills in its own device.
  • Output folder: filled in by the server, and refused if it is the notes folder.

There is no time limit, and a call is limited by the 500 MB upload cap of the server.

6. Environment

Everything runs in the tool’s own environment on the server: Python 3.11, the processor build of llama-cpp-python, and one reader each for PDF and Word. Nothing is installed in Slicer. The legacy module installed the packages into Slicer’s own Python and downloaded a 4.4 or 4.9 GB model into the user’s Documents folder.

7. What changed from the legacy logic

The TMJ prompt, the absence of a prompt for Ortho and the two default windows are unchanged. Around them:

  • Where: on the server instead of inside Slicer on the workstation.
  • Finding notes: recursive and not case-sensitive; finding nothing is an error instead of a quiet success.
  • Reading: three text encodings instead of one; Word tables, headers and footers are read; a scanned PDF is refused instead of sending an empty text to the model; a missing reader package fails only the notes of that format.
  • Generation: answer limit 2048 instead of 500, temperature 0 instead of 0.1, a seed, and a cut-off answer fails the note instead of being written.
  • Reading the answer: JSON, then field lines, otherwise nothing is written, where the legacy module saved the raw answer.
  • Outputs: a JSON file and a text file per note, with the full note name so that a .txt, a .pdf and a .docx of the same name no longer overwrite each other, and a run report.
  • GPU: asked for only on request, and the report says whether layers were really offloaded.
  • Not ported: the Dashboard, and the download of models by the client.

8. Known problems

  • The notes are uploaded to the server as they are, with no de-identification, so the legacy statement that clinical text stays on the machine does not hold for VISOR (details).
  • The panel and the README speak of an “automatic” model, but nothing derives the model from the note type (details).
  • Only the TMJ model is hosted, and a model of the wrong type is only a warning (details).
  • The engine is the processor build, whatever some comments say; a GPU request is reported as ignored (details).
  • Nothing compares a note with the context window, and the Ortho defaults leave no room (details).
  • Output files are named differently from the legacy ones, so tools that read the old names would not find them (details).
  • Fixed: scanned PDFs, cut-off answers, unreadable answers, same-named notes and silent GPU requests no longer produce a plausible file (details).
