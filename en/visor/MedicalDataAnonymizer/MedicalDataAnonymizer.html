MedicalDataAnonymizer: not ported to VISOR

There is no server-side Medical Data Anonymizer. The VISOR client extension ships an older copy of the legacy module, which runs inside Slicer on text documents, and which does not de-identify the files VISOR uploads. The module itself is described on its legacy page.

VISOR: local copy only Legacy page Guide (VISOR)

State at the reference commits: SADT-VISOR 6ba2a78, VISOR-serve e9a7e5d, AutomatedDentalToolsRemote 19b95e8; legacy is SlicerAutomatedDentalTools at 3c67957. MDA-Remote below stands for AutomatedDentalToolsRemote Medical_Data_Anonymizer_ModuleRemote/Medical_Data_Anonymizer_ModuleRemote.py. Everything was read in the code; nothing was run.

What runs where

Everything runs in the Slicer process, as in the legacy module: install_dependencies pip-installs presidio-analyzer, presidio-anonymizer, pandas, python-docx, pdfplumber, odfpy, lxml, langdetect and reportlab into Slicer's Python, then downloads the spaCy model en_core_web_lg (MDA-Remote:392-441). Nothing is sent to a server and nothing is hosted.

How the copy differs from the legacy module

The shipped copy is an older revision of the module, not a port: 768 lines against 774 in the legacy file at 3c67957 (Medical_Data_Anonymizer_Module/Medical_Data_Anonymizer_Module.py). Since then the legacy file has switched to ADTLib.logging_setup instead of a local logger, given the widget a separate Logic object, and renamed variables. The copy's module category is "Automated Dental Tools Remote" instead of "Automated Dental Tools" (MDA-Remote:41). The detection logic is the same in both: the findings of the legacy page about the fixed language, the mapping file and the silent failure hold for the copy, at these lines.

Not the de-identification of what VISOR uploads

This module anonymises text documents that you point it at. It is not placed in the upload path of any other panel, and no code of ServerToolsCore, SlicerCloud or ServerToolsSettings mentions Presidio or anonymisation. The client README states that there is no de-identification in the current client: files are streamed "as they are on disk, with their names, their DICOM headers and whatever identifiers they contain" (README.md:32-35), and the client shows the same warning once for each remote server, "Files are uploaded unmodified" (ServerToolsCore/ServerToolsCoreLib/settings_qt.py:101-127). The pipeline that would de-identify uploads is specified and not implemented: read De-identification in VISOR before treating any module as a safeguard for uploaded data.
