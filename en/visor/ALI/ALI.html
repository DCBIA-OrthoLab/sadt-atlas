ALI on VISOR

ALI places anatomical points, called landmarks, on a 3D scan automatically. This page explains how, step by step, with the maths: what goes in, what each step does to it, and what comes out. Where the code does something worth checking, a link leads to the code page. The legacy module is on its own page.

VISOR Code (developers) Legacy page Guide (VISOR)

Overview: what goes in, what comes out

ALI takes a 3D image of a patient and returns a list of 3D points, each with a name: for example the tip of a tooth, or a point on the skull base. Other tools use these points to orient a scan or to register two scans (see ASO and AREG_IOSCBCT). It works on two kinds of image, which need two different methods, so the tool has two modes:

Mode CBCTMode IOS
Inputa CBCT volume (the head scan), or a folder of them, or a DICOM seriesan intraoral surface mesh of the teeth (.vtk or .stl) with a tooth number on every vertex, or a folder of them
Points offered119 landmarks, in 4 groups153 tooth landmarks: Occlusal 84, Cervical 56, Mucogingival 13
Ideaan agent walks through the volume, one step at a time, until it reaches the pointthe tooth is photographed from fixed virtual cameras, a network labels the pixels of each picture, and the labelled pixels are projected back onto the mesh
Outputone file per scan holding all its points, in the format Slicer reads (.mrk.json, coordinates in LPS), plus run_report.json, a summary of what was found and what was not

The networks and their trained weights are the legacy ones: nothing is trained in VISOR. What changed is everything around them: where the work runs, how the input is read, how a run is bounded and reported (What changed).

1. Where it runs

In VISOR, Slicer keeps only a panel (ALIRemote). It sends the scan to a server, waits, then downloads a zip and loads the points into the scene. All the computation happens on the server, in a Python environment of its own for each mode. The tool the user picks is called ALI and asks one question first, the mode; behind it two separate server tools do the work, ALI_CBCT and ALI_IOS. Other server tools, such as ASO or VFACE, do not go through the panel: they ask ALI for the landmarks they need.

StepLegacy moduleVISOR
Where the maths runson the user's machine, inside Slicer or a conda environmenton the server only. The panel uploads the scan (a folder is zipped), downloads the result and loads it
Weightsdownloaded by the widgetalready on the server, shared by both modes; the panel does not ask for them
Tooth labels for IOSthe module runs the tooth segmentation itselfmeshes that already have labels run first; the others go through a separate tool, Crown_Seg, and follow
Resultfiles written beside the scansa zip with the point files and the run report

What has been checked. The automated tests pass for both modes (60 for ALI_CBCT, 190 for ALI_IOS, see the code page for what they cover). The VISOR authors report that CBCT landmarks are identical to the previous server implementation on one real scan, for the seven landmarks ASO uses, and that the crown networks match the legacy code on one mesh. They also state that accuracy against annotated scans is not established. Nothing here was re-measured on a full set of scans.

2. Mode CBCT: an agent walks to the landmark

The idea comes from reinforcement learning, but at run time there is no learning: a trained network is simply used as a compass. For each landmark there is one agent, which is a position in the volume. At every step the network looks at a small cube of the image around the agent and says which of six one-voxel moves brings it closest to the landmark. The agent moves, looks again, and repeats until it starts going in circles, which means it has arrived. It does this twice, first on a coarse grid (1 mm voxels) to get close, then on a fine grid (0.3 mm voxels) to be precise.

2.1 Reading the input

A single file must be a volume (NIfTI, NRRD or GIPL); a surface is refused with a message pointing to ALI_IOS. A folder is searched recursively and each scan is identified by its path inside the folder, so two patients with a file of the same name in different subfolders do not collide. A folder of DICOM slices is recognised as such, converted to one NIfTI per series in a temporary place, and never modified.

2.2 Preparing the volume

Two operations, once per scan, before any agent moves.

In the codePercentiles, bins, interpolation and the files they write

2.3 What the agent sees

The volume is padded by 33 voxels on every side, so the cube still has data when the agent is near the border.

2.4 The decision

The network is a 3D DenseNet followed by a small decision head. The order of the six moves is part of the trained weights: reordering them would make the agent walk the wrong way. The head ends in a ReLU, inherited from the legacy training: if all six scores are negative before it, all become 0 and the agent takes the first move. This is kept on purpose, because the published weights were trained that way (finding). One network exists per landmark and per scale, loaded for each (scan, landmark) pair and released afterwards: a broken weight file or a memory error costs one landmark, not the scan.

2.5 The search

Rules around the walk: a move that would leave the volume is refused and the agent respawns at a random position (anywhere on the coarse grid; within 10 voxels of where the fine search began on the fine grid); after three exits the landmark is declared not found.

The budget is counted in steps, not in seconds: 900 network evaluations per landmark by default, search and final averaging together; running out records the landmark as not found. A time limit was dropped on purpose, because the result then depended on how busy the graphics card was (running four landmarks at a time once lost one that a quieter run found).

A landmark does not depend on the others. Every random choice comes from a generator started from the run seed and the landmark’s name, so asking for 7 landmarks or for 119 gives the same coordinates for the 7: this is what lets ASO ask for just the ones it needs. Landmarks are searched in parallel, at most 8 at once; the VISOR authors measured 358.7 s with one worker and 128.0 s with eight on the reference scan with 119 landmarks, the same 114 placed each time (their figure, not rerun here).

In the codeThe agent loop, bounds, memory, respawn and budget in the code

2.6 From voxels to millimetres, and the output

The absolute value is inherited from the legacy code. It is right when the origin is negative on all three axes, which is what an LPS-oriented volume usually has. VISOR no longer reorients the volume to LPS before the search, as the legacy did after September 2026, so a volume stored in another orientation may give mirrored coordinates (finding). Whether this changes real predictions was not measured: it needs a scan stored in another orientation and the full weights.

The result is one file per scan with all the landmarks of all the requested groups, in a copy of the input folder tree, and a run report. The report lists the mode, the groups and landmarks requested, the landmarks that have no trained model, and, for each scan, the landmarks found, the ones not found and why. The run fails only if no scan produced any landmark.

Which landmarks run is decided by the groups ticked and the names listed. Naming landmarks replaces the groups instead of narrowing them. A landmark is searched only if it has a trained network at both scales.

In the codeThe coordinate conversion, the markups writer, the report keys and the weight discovery

3. Mode IOS: look at the tooth, then project back

A mesh has no volume to walk through, so ALI_IOS turns the problem into one on ordinary pictures. For each tooth, virtual cameras take a few pictures of it from fixed directions. A 2D network colours each pixel of each picture with the class “this is landmark type 1”, “type 2”, “type 3” or “background”. The pixels of a class are traced back to the triangles of the mesh they show, and the landmark is the centre of those triangles, moved onto the surface.

3.1 The input and the tooth labels

Everything depends on knowing which vertices belong to which tooth. A mesh must therefore carry a tooth-number array (Universal numbering: 2 to 15 for the upper jaw, 18 to 31 for the lower jaw). With the server, a batch runs in two passes: first the meshes that already have labels, so that their landmarks are written before any segmentation time is spent; then the others, which the separate Crown_Seg tool labels, and which go through the same method. Either pass can fail without sinking the other; the run fails only if neither produced anything. A mesh Crown_Seg could not label is listed as not processed, with the reason.

In the codeLabel array names, the two passes and the Crown_Seg call

3.2 The unit sphere and the picture

The result is converted back to the mesh’s own millimetres at the end. The network does not see colours or textures but the shape: each surface normal, a unit vector with components in [-1, 1], is displayed as a colour, and the depth is a fourth channel. A picture is 224×224 pixels with a 90-degree field of view, and each pixel shows exactly one triangle, so every pixel can be traced back to the triangle it comes from.

In the codeThe scaling functions, the renderer settings and the texture

3.3 The cameras

The occlusal table is copied from the legacy code including a flaw: two of its direction vectors are not of length 1. It is kept deliberately, because the trained weights saw exactly these views (finding). The drawing is a schematic side view, not the real directions.

In the codeThe three camera tables and the Mucogingival frame

3.4 The network and the decision

A 2D UNet reads the pictures of a tooth. The occlusal and cervical networks take the pictures one by one (4 channels in: colour and depth; 4 classes out); the mucogingival network stacks its three pictures into one input (12 channels, 3 classes out). Class 0 is background; classes 1, 2 and 3 are the landmark types, in the order of the catalogue. For each pixel, the class is the one with the highest raw score zc:

The legacy code rounded the O and C scores to integers before this choice; VISOR does not, so the O and C results are not guaranteed identical to the legacy ones. The network is loaded once per network and jaw, not once per tooth.

In the codeNetwork construction, loading and the argmax code

3.5 From pixel to 3D point

Background pixels are dropped. For O and C, only the triangles that belong to the tooth being processed are kept; Mucogingival points lie on the gum, so they keep everything.

In the codeThe sequential float32 centroid and the octree snap

3.6 The Mucogingival path

It runs on the lower jaw only, is off by default, and covers teeth 19 to 31. Three behaviours are fixed in the code with no option. Missing teeth are always estimated: their cameras are aimed from a curve fitted through the teeth that are present, and the point is marked in its description. Forced points: if the network sees no pixel of class 1, the 50 most likely pixels stand in for it, and the point is marked “forced” with a confidence. No last resort: if nothing lands on the mesh, no point is written. The notes also go into the run report. The legacy module had a long refinement stack on top of this (levelling, smoothing, gap filling, and more); VISOR has none of it.

In the codeThe MG options, the forced pixels and the report entries

3.7 Output

One file per mesh, <name>_lm_Pred.mrk.json, with every network and jaw together, in a copy of the input folder tree. If the user names landmarks, only the networks needed to produce them run, and the others are removed from the files and from the report. The report adds the networks used, the weight files it could not recognise, the jaws without a model, the landmarks marked as doubtful, and which meshes were segmented on the fly.

In the codeFile naming, weight discovery by file name and the report keys

4. What you can choose

The Slicer panel is drawn from the server's description of the tool, so it shows only what the tool allows.

SettingWhat it doesShown in the panel
ModeCBCT or IOSyes, first field
Inputa file, or a folder of files; the form can also offer hosted test filesyes
Landmarkswhich points to place; naming them replaces the groupsyes, tabbed check boxes by group
Regions (CBCT) / networks (IOS)whole groups; Mucogingival is off by defaultno, hidden
Model, device, search steps, seed, workerstechnical settings: the weight folder, GPU or CPU, the 900-step budget, the random seed, the parallel widthno, hidden

With nothing ticked, a CBCT run searches all 119 landmarks. The legacy IOS settings for the list of teeth and the rendering parameters are gone: every labelled tooth is processed, and the rendering is fixed. Two server limits apply: a global upload cap of 500 MB, and no time limit.

When the run ends, the panel unzips the result, reads the report, loads every point file into the scene and shows a summary. Because of a bug the summary currently always reads “0 scan(s), 0 landmark(s) written” although the files load correctly (finding).

5. What is predicted and what is computed

Only three blocks are trained networks. Everything else is geometry or bookkeeping, and can be reasoned about without any model.

Nothing is trained in VISOR: the port does inference only and dropped the legacy training code.

Each mode runs in its own isolated Python environment on the server, so that the two sets of libraries (they need different versions of PyTorch) never meet. The details are on the code page.

7. Known issues in VISOR

These are the points a user or a developer should know. Each one is checked in the code and described, with its evidence, on the code page; the list also appears in the findings.

  • A DICOM series folder gives a hidden output file. When the input is the folder of one series, the output is named ._lm_Pred.mrk.json, so downstream tools that match files by name will not pair it with the scan. Evidence.
  • No reorientation to LPS. A CBCT stored in another orientation may give mirrored coordinates. The effect on real predictions was not measured. Evidence.
  • The panel's summary is wrong. It always reads zero scans and zero landmarks. The files themselves load correctly. Evidence.
  • ReLU on the last layer. Kept from the legacy because the weights were trained with it. Evidence.
  • Mucogingival refinement not ported. Accuracy on a set of scans was not measured. Evidence.
  • Two scans of the same name overwrite each other (a.nii.gz and a.nrrd in one folder). Evidence.

8. Literature

The networks are the published ones: ALI_CBCT follows Gillot et al. 2023 (agents on a multi-scale volume, scales 1 mm and 0.3 mm), ALI_IOS the CLIP 2022 paper for the occlusal model (unit sphere, five views per tooth, patch segmentation). The Mucogingival path is unpublished, as on the legacy side. The bibliography is the tool's own: ALI sources; the legacy page discusses each paper against the code in its section 8.
