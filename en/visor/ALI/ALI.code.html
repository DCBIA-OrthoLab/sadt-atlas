ALI on VISOR: the code

For developers: what the VISOR port of ALI does in the code, with file:line references, signatures, arguments, environment, the differences from the legacy code and the findings. The readable explanation of the same pipeline, with the maths, is on the atlas page.

VISOR Code Atlas (explanation) Legacy page Guide (VISOR)

VISOR runs the dental tools on a server: Slicer keeps only a panel that sends the data and loads the results (see Architecture). This page describes the VISOR port of ALI, read in the code of the repositories named below and compared with the legacy Slicer module at 3c67957, which has its own page. "Run for this page" marks what was executed while checking it; everything else was read in the code. Abbreviations used for the references:

  • CB/ = SADT-VISOR 6ba2a78, tools/ALI/ALI_CBCT/src/sadt_ali_cbct/; IO/ = SADT-VISOR, tools/ALI/ALI_IOS/src/sadt_ali_ios/; CM/ = SADT-VISOR, tools/ALI/common/src/sadt_ali_common/;
  • VISOR-serve = VISOR-serve e9a7e5d, files under server/ unless the path starts with scripts/; Remote = AutomatedDentalToolsRemote 19b95e8;
  • legacy = SlicerAutomatedDentalTools 3c67957; a legacy path such as ALI_CBCT_utils/agent.py lives under ALI_CBCT/, and ALI_IOS_utils/ under ALI_IOS/.

In one paragraph: the tool a user picks is a facade named ALI with two modes. Mode CBCT runs ALI_CBCT, one reinforcement-learning agent per landmark walking a volume voxel by voxel at 1 mm then 0.3 mm (section 3). Mode IOS runs ALI_IOS, which renders each tooth of a labelled intraoral mesh from fixed cameras, segments the renders with a 2D UNet and projects the mask back onto the mesh (section 4). Both write one .mrk.json per scan plus a run_report.json. The networks and their weights are the legacy ones; what changed is around them, and several later legacy fixes (DICOM reorientation, the step-budget guards, the whole Mucogingival refinement stack) were never carried over (section 8).

1. Status and position in the chain

Plain-language explanation and maths: atlas page.

implemented and tested The port is two server tools, not one: ALI_CBCT and ALI_IOS, split from a single ALI tool on 2026-08-17 (SADT-VISOR commit 2ac7d9d). 3. ALI_CBCT: agents inside the volume

Plain-language explanation and maths: atlas page.

3.1 Input and DICOM

Plain-language explanation and maths: atlas page.

detect() (CB/dispatch.py:80-135) decides what was sent. A single file must end in one of .nii .nii.gz .nrrd .nrrd.gz .gipl .gipl.gz (CM/discovery.py:22); a surface is refused by name ("run ALI_IOS on surfaces", :102-106). A folder is walked recursively; a folder mixing volumes and surfaces is refused rather than half processed (:115-125). Each scan is keyed by its path relative to the input (CM/discovery.py:33-45), so two patients called scan.nii.gz in different subfolders no longer collide. A .zip never reaches this code: the server extracts it before run() (:89-91).

DICOM is detected, not declared. Every directory that holds files but no volume or surface is asked to GDCM (_dicom_directories, CB/dispatch.py:60-77; CB/preprocess.py:130-143), and each series found is written as one NIfTI under the job's scratch folder, never in the input:

destination_root = os.path.join(work_dir, "dicom_converted")
key = scan_key(directory, root)
destination = os.path.join(destination_root, f"{key.replace(os.sep, '_')}.nii.gz")
...
converted.append((destination, f"{key}.nii.gz"))      # CB/dispatch.py:152-164

When the input is the series folder, key is ".": see the first finding in section 9. Everything intermediate lives in <output_dir>/.ali_work/ and is removed in a finally before the report is written (CB/dispatch.py:196, :249-253).

3.2 Preprocessing

Plain-language explanation and maths: atlas page.

Per scan, in its own scratch folder .ali_work/preprocessed/<key> (CB/engine.py:276-298, :816):

  1. Histogram clamp, correct_histogram (CB/preprocess.py:39-86): a 1000-bin histogram, normalised cumulative, intensities clipped between the 1 % and 99 % points (the first bin edge whose cumulative share passes the threshold, so the limits are approximate, :66-77) and inside [-1500, 4000], written as int16 with spacing, origin and direction kept. A constant volume is passed through with a warning instead of dividing by zero (:59-64). Same percentiles as the legacy call (ALI_CBCT/ALI_CBCT.py:202).
  2. Isotropic resampling, set_spacing (CB/preprocess.py:89-127), once per spacing in SCALE_SPACINGS = (1.0, 0.3) (CB/catalog.py:69), into <stem>_sp1.nii.gz and <stem>_sp0-3.nii.gz. New size size × spacing / wanted, origin shifted so the physical centre stays put, linear interpolation always, direction copied from the input (:115, :120).

The scratch folder is deleted as soon as the scan is done (CB/engine.py:910): one run never reads another run's resamples.

3.3 The environment

Plain-language explanation and maths: atlas page.

Environment (CB/environment.py) holds one scan at both spacings. load_images (:63-79) reads each resample as stored, with no reorientation, pads it by padding = 64/2 + 1 = 33 voxels on every side (CB/engine.py:371-374) and keeps the origin reversed to the array's (z, y, x) order. The agent sees only this:

crop = self._crop((np.asarray(center) + self.padding).tolist(), crop_size)
return self._rescale(crop(self.data[scale_key]["image"])).type(torch.float32)
# _rescale = ScaleIntensity(minv=-1.0, maxv=1.0)       # CB/environment.py:49, :102-103

A 64×64×64-voxel cube around the agent, rescaled per crop to [-1, 1]: a 64 mm side at the coarse scale, 19.2 mm at the fine one.

3.4 The agent and its network

Plain-language explanation and maths: atlas page.

The network is the legacy one, layer for layer (CB/brain.py:63-107): a monai 3D DenseNet (growth rate 34, blocks 6-12-24-16, 1024 features) followed by a decision head 1024-512-256-128-6. Output: six scores, one per move in MOVEMENT_MATRIX, whose order "is part of the weights' contract" (CB/agent.py:23-34). The prediction is a direction, not a position: predict returns the argmax of the six (CB/brain.py:138-145). The head still ends in a ReLU (:90), see Findings.

def forward(self, x):
    x = nn.functional.relu(self.fc0(x))
    x = nn.functional.relu(self.fc1(x))
    x = nn.functional.relu(self.fc2(x))
    return nn.functional.relu(self.fc3(x))            # CB/brain.py:86-90

One network per scale. A Brain is built, loaded with torch.load(..., weights_only=True) (CB/brain.py:123-136) and released for each (scan, landmark) pair (_walk_one, CB/engine.py:377-425). A broken checkpoint or an out-of-memory loses one landmark, not the scan (:405-410).

3.5 The search, step by step

Plain-language explanation and maths: atlas page.

  1. Start at scale 0 (1 mm), at the centre of the volume (CB/agent.py:275-279).
  2. Step: one forward pass, one move of one voxel (SPEED_PER_SCALE = (1, 1), :40), one unit off the budget (_step, :201-217).
  3. Bounds: a move is kept only if every coordinate stays in [0, size) of the unpadded volume (:135-141). Otherwise the short memory is cleared and the agent respawns: anywhere in the volume at scale 0, within 10 voxels of where the scale started at scale 1, drawn from a generator seeded by the run seed and the landmark name (:148-177, rng_for :54-68). Three exits and the landmark is not found (_MAX_ATTEMPTS = 3, :45, :294-295).
  4. Convergence: the new position is compared with the last 10 positions before being remembered (:179-185, :213-217). Circling means arrived.
  5. Change of scale: position multiplied by the spacing ratio (1/0.3), attempts reset; each scale has its own memory (:114, :187-199).
  6. Focus at the fine scale: six restarts at 4 voxels along ±x, ±y, ±z, each walked until it circles; the answer is the mean of the six landings, which is what makes it sub-voxel (:219-246).

The budget is counted in steps, not seconds: 900 forward passes per landmark by default, or search_steps (CB/engine.py:55, :81-92). The same counter feeds the search and the six Focus walks; running out raises NotFound, recorded per scan in landmarks_failed (CB/agent.py:238-243, :283-287; CB/engine.py:399-404). The engine's comment on why: a wall clock made the outcome depend on how busy the card was, "four agents wide dropped C4" (CB/agent.py:257-270).

Width. Landmarks are walked in a pool of processes (spawn), sized once per run by sup.channels() and capped at 8 (CB/engine.py:76, :301-338, :607, :619-626); each worker keeps the scan it loaded until the scan changes. Because each agent's randomness is derived from its landmark's name and the environment is read-only during a search, the width cannot move a coordinate (comment at CB/engine.py:841-854). The comments in VISOR-serve deployment.toml:93-103 report, on the reference scan with 119 landmarks, 358.7 s at width 1 and 128.0 s at width 8, 114 landmarks placed at every width (measured by the VISOR authors, not rerun).

3.6 Output and report

Plain-language explanation and maths: atlas page.

The fine-scale voxel position is converted back to millimetres in one place, the parent process (CB/engine.py:893-904):

physical_origin = abs(reference["origin"] / spacing)
coordinates = (np.asarray(position) - physical_origin) * spacing
return np.array([coordinates[2], coordinates[1], coordinates[0]])   # CB/environment.py:116-118

The abs() is the legacy formula; it is right only for a volume whose origin is negative on all three axes, and VISOR no longer reorients to LPS first (Findings). Then one file per scan, all regions together, in a copy of the input tree:

destination = os.path.join(output_dir, os.path.dirname(key),
    f"{scan_stem(os.path.basename(scan_path))}_lm_{prediction_ID}{MARKUPS_EXTENSION}")
# scan_stem("patient01.nii.gz") == "patient01"      # CB/engine.py:152-158, :916-921

The writer, shared by both engines (CM/markups.py:104-129), puts every point in coordinateSystem: "LPS" (:26), locked (:96), with display.visibility: true (:41) and an empty description for CBCT points (CB/engine.py:921 passes none). run_report.json (CB/engine.py:685-722, CB/dispatch.py:248-266) records mode, device, seed, regions, landmarks_selected, landmarks_requested, landmarks_without_model, landmarks_ungrouped, per-scan cases (status, landmarks_found, landmarks_failed with the reason, produced), summary, dicom_series_converted, model_bundle and durations. The run fails only if no scan produced a landmark (:644-650).

3.7 Weights and selection

discover_weights (CB/engine.py:165-224) walks the bundle recursively and keeps the legacy layout, read from folder names:

<bundle>/…/<LANDMARK>/<1 | 0-3>/<anything>.pth
             ^ alias-folded       ^ scale key = str(spacing) with "." → "-"

Three differences with the legacy GetBrain: a landmark needs a checkpoint at both scales or is dropped (:219-224); two bundles under one folder holding the same landmark are an error, not a silent overwrite (:198-211); aliases such as UR3OI → UR3OIP are folded (CB/catalog.py:52-57). Selection (requested_landmarks, :227-273): a non-empty landmarks list replaces the regions; otherwise every catalogue landmark of the ticked regions runs, plus any bundle landmark of those regions the catalogue does not know (reported as landmarks_ungrouped). Naming neither a region nor a landmark is an error (CB/dispatch.py:224-232). The local copy of DATA/ALI/models used for this page holds 22 landmark folders, not the full bundle.

4. ALI_IOS: rendering, one tooth at a time

Plain-language explanation and maths: atlas page.

4.1 Input, tooth labels and the Crown_Seg pass

Plain-language explanation and maths: atlas page.

Accepted: .vtk and .stl (CM/discovery.py:23; reader IO/surface.py:33-59), alone or in a folder walked recursively; volumes are refused by name (IO/dispatch.py:105-142). Everything depends on a tooth-label array, looked for under PredictedID, UniversalID or Universal_ID (IO/surface.py:19, :62-69), in Universal numbering: 2 to 15 upper, 18 to 31 lower (IO/engine.py:312-316).

With a supervisor (every run through the server), identify splits the batch (IO/dispatch.py:486-500) and runs it in two passes:

  1. Pass 1: the labelled meshes, at once, so their landmarks are on disk before any segmentation is spent (:534-538).
  2. Crown_Seg: the unlabelled meshes are linked under their keys into .ali_work/to_segment/ and handed over in one call (_segment, :193-266): 
    produced = sup.run(CROWN_TOOL, meshes=staged_root, model=model_path, device=device)   # :229-237
    model is the folder ALI_IOS was given, DATA/ALI/models, where Crown_Seg looks for its own checkpoint (docstring :206-213). Each returned <stem>_Seg.vtk is renamed to the input's name so the landmark file keeps the patient's name (_rename_to_input, :284-305).
  3. Pass 2: the newly labelled meshes (:572). Either pass may fail without sinking the other; the run fails only if neither produced anything (:511-532, :574-586). A mesh Crown_Seg could not label is reported as unprocessed with the reason.

4.2 Unit sphere and texture

Plain-language explanation and maths: atlas page.

scale_to_unit (IO/surface.py:72-103) centres a copy of the mesh on its bounding-box midpoint and scales it by 1 / ||max − centre||; upscale (:106-108) reverses it at the end. The texture is the per-point normal mapped into [0, 1]: (normal * 0.5 + 0.5) (:122-128). The renderer is the legacy one (IO/render.py:115-145):

cameras = FoVPerspectiveCameras(znear=0.01, zfar=10, fov=90)
RasterizationSettings(image_size=224, blur_radius=0, faces_per_pixel=1)
HardPhongShader(..., lights=PointLights(...))

The three rasterisation settings are constants (IO/render.py:79-81), no longer arguments: hard rasterisation, one face per pixel, which is what makes pix_to_face a lookup table from pixel to face.

4.3 The cameras

Plain-language explanation and maths: atlas page.

NetworkRadius (unit sphere)Views per toothDirections
O (occlusal)0.25fixed table: occlusal axis plus four tilts, per jaw (IO/render.py:39-54)
C (cervical)0.312fixed table: around the crown, horizontal and tilted by 0.5 (:56-73)
MG (mucogingival)0.23computed per tooth: buccal normal and ±0.35 rad (:171-318)

Radii from CAMERA_RADIUS (IO/catalog.py:54). The O table is copied "byte for byte INCLUDING their inconsistencies" (IO/render.py:8-12): four of the five vectors of each jaw (all but the axis) are divided by the norm of another vector, so they are not unit length (0.913, 0.913, 0.791, 0.791; the file itself says “several”), kept because the shipped weights were trained on these views. Those four cameras stand at 0.913 or 0.791 times the radius from the tooth. For each direction, render_views (:366-414) places the camera at centre + direction × radius, renders once with its R and T, and keeps both the image (normal RGB plus depth, 4 channels) and the pix_to_face of that same rasterisation. The MG frame (mg_frame, :211-250) uses the arch tangent from the neighbouring teeth and an aim point offset by MG_AIM_OFFSET (IO/catalog.py:96).

4.4 The network and the decoding

Plain-language explanation and maths: atlas page.

A monai 2D UNet, channels (16, 32, 64, 128, 256, 512), strides (2, 2, 2, 2, 2), 4 residual units; O and C take one image per camera as a batch (4 channels in, 4 classes out), MG stacks its three views into one 12-channel input (3 classes out) (IO/engine.py:160-186). Loaded with weights_only=True, once per (network, jaw), not once per tooth (:344-353). Class 0 is background; classes 1, 2, 3 are the landmark types in catalogue order. Decoding is an argmax on the raw logits for every network:

classes = torch.argmax(predictions, dim=1)
hits = (classes == channel).nonzero(as_tuple=False)
picked = pix_to_face[hits[:, 0], 0, hits[:, 1], hits[:, 2], 0].long()
return picked[picked >= 0].tolist()                 # IO/engine.py:216-226

The legacy cast O and C logits to int16 before the argmax; VISOR does not, so its O and C results differ from the legacy ones (section 8).

4.5 From pixel to 3D point

Plain-language explanation and maths: atlas page.

  1. The faces under the pixels of the class, background pixels (-1) dropped (IO/engine.py:226).
  2. O and C only: keep the faces that touch the tooth's own label (faces_on_tooth, IO/surface.py:180-211; called at IO/engine.py:465). MG keeps every face: its point lies on the gum.
  3. The mean of the vertices of those faces: the three corners of the triangle of each pixel are added, so a face hit by several pixels counts several times (the list of faces keeps its repeats, IO/engine.py:224, :272-276). The sum is accumulated sequentially in float32 so the result is bit-identical to the legacy loop (_landmark_position, IO/engine.py:229-278).
  4. Snapped onto the nearest mesh vertex (FindClosestPoint returns a point id) with vtkOctreePointLocator (:277), then upscale back to the mesh's millimetres.

4.6 The Mucogingival path

Plain-language explanation and maths: atlas page.

MG runs on the lower jaw only (NETWORK_JAWS, IO/catalog.py:48), off by default, on all 13 teeth 19 to 31 whatever the labels say (IO/engine.py:324-332). Three behaviours are fixed in code, with no option:

  • missing teeth are estimated when at least 4 teeth are present and they span at least 4 numbers, otherwise nothing is estimated and the missing ones are skipped (IO/render.py:347-348): cameras aimed from a quadratic fit of the arch through the teeth present (render.estimate_missing_teeth, IO/render.py:320-363; IO/engine.py:354-358), the point noted "cameras aimed from an arch fit, tooth not segmented" (:567-570);
  • forced points: if class 1 wins no pixel, the 50 most likely pixels stand in for it, noted forced (confidence 0.xyz) (MG_FORCE_TOPK, :472, :538-552);
  • no last resort: if nothing lands on the mesh, no point is written (:563-565).

Notes go into the point's description and into the report's landmarks_degraded (IO/engine.py:414-419). The legacy refinement stack (arch levelling, arch scale, refine, smooth, snap, line completion, gap filling, patch picking) has no counterpart: one pass per tooth.

4.7 Output, weights and filtering

Plain-language explanation and maths: atlas page.

One file per mesh, <stem>_lm_Pred.mrk.json, in a copy of the input tree, every network and jaw together (IO/engine.py:420-426). An O network always predicts its three types; when landmarks names some, only the networks needed run (IO/catalog.py:288-297) and the unrequested points are removed from the files and the report afterwards (_keep_only, IO/dispatch.py:348-384). Weights are found by file-name tokens: a network token (O, C, MG) and a jaw token are both required, and a conflict between two files is an error (discover_weights, IO/engine.py:72-127). The report (:684-710, IO/dispatch.py:598-626) adds to the CBCT keys networks, models_unrecognized, per-case jaws_without_model and landmarks_degraded, and segmented_on_the_fly.

  • CBCT: .nii, .nii.gz, .nrrd, .nrrd.gz, .gipl, .gipl.gz, a folder (recursive) or a DICOM series folder (converted by the server, CB/dispatch.py:60-77, :139-166); .zip is unpacked by the server first
  • IOS: .vtk and .stl (legacy also took .vtp .obj .off, ALI_IOS.py:120); tooth labels in PredictedID, UniversalID or Universal_ID (IO/surface.py:19)
  • A folder mixing volumes and surfaces is refused by name

Outputs

  • One <stem>_lm_Pred.mrk.json per scan, in a copy of the input tree, all landmarks of the scan in one file (CB/engine.py:916-921; IOS IO/engine.py:420-426)
  • run_report.json: mode, per-scan cases, summary, landmarks without a model, landmarks that did not converge, run time
  • The tool returns one path, no named outputs (returns "path")

What the client does with it. ALIRemote draws the form from GET /tools, adds one check box, "Load the predicted landmarks into the scene" (ALIRemote.py:131-136), shows an input volume with the CT-AAA preset (:107), then on the result unzips the archive, reads run_report.json, loads every .mrk.json it finds and shows a summary (handleResult, :142-159; the text comes from _summarize, :197-219).

Resources declared in VISOR-serve deployment.toml: both tools use data_dir = "ALI"; ALI_CBCT counts its width on the requested landmarks (width_from = "landmarks", :131-150), ALI_IOS on nothing declared (width_from = false, :152-160). Neither declares a timeout_seconds nor a max_upload_mb: the global timeout is 0, meaning none, and the global upload cap is 500 MB (VISOR-serve config.py:77, :240). ALI_CBCT caps its own agent width at 8 (CB/engine.py:76, :322), although a comment in deployment.toml:118-122 says nothing inside the tool caps it.

9. Findings in VISOR

Plain-language explanation and maths: atlas page.

Confirmed bug · a DICOM series folder gives a hidden output file

Select the folder of one DICOM series as the input (the case the panel invites) and the scan key becomes ".": _dicom_directories includes the root itself (CB/dispatch.py:70-77), scan_key is os.path.relpath(root, root) (CM/discovery.py:43), the converted file is named ..nii.gz (CB/dispatch.py:156, :164) and scan_stem("..nii.gz") is "." (CB/engine.py:152-158). The output is ._lm_Pred.mrk.json, a hidden file. Run for this page: scan_key and scan_stem return exactly those values. A complete run on a real series was not repeated here. Downstream tools that match files by name prefix will not pair such a file with a scan.

Pitfall · no reorientation to LPS

The legacy reorients every volume to LPS before the agents walk it, and says why in a comment: a volume stored in another orientation "reaches them mirrored" (ALI_CBCT_utils/environment.py:66-72). VISOR does not. Run for this page against the real Environment.physical_position (CB/environment.py:108-118): on a volume with identity direction and origin (-30,-25,-20), voxel (5,20,10) maps to (-25,-5,-10), the true point; on a volume with direction diag(-1,-1,1) and origin (30,25,-20), the function still returns (-25,-5,-10) while the true physical point is (25,5,-10), x and y inverted. No VISOR test mentions direction or orientation (grep -i over ALI_CBCT/tests: no hit). What this does to a real prediction was not measured: that needs a scan stored in a non-LPS orientation and the full weights. The published test scan is stored in LPS, so it cannot show the problem.

Confirmed bug · ReLU on the last layer, kept from the legacy

The decision head ends in a ReLU (CB/brain.py:90; legacy ALI_CBCT_utils/brain.py:35): the six scores are ≥ 0, and if all pre-activations are negative they are all 0 and argmax returns 0, "up". Not to be "fixed" without retraining: the published weights were trained with this head.

Confirmed bug · the Slicer panel reports "0 scan(s), 0 landmark(s) written"

ALIRemote._summarize reads report.get("scans") (Remote ALIRemote/ALIRemote.py:216), but both engines write the per-scan records under cases (CB/engine.py:708, IO/engine.py:704). Nothing between them renames the key (the report merge in ServerToolsCore/ServerToolsCoreLib/base_widget.py:119 is generic). The end-of-run message therefore always says no scan and no landmark, and never lists the landmarks that did not converge (ALIRemote.py:216-232). Run for this page: _summarize, extracted from the module, given a report with one case holding two found landmarks and one failed, prints "0 scan(s), 0 landmark(s) written." and no failure. The result files themselves load correctly (_findMarkupFiles walks the folder). Two related remnants: configureFields looks for a prediction_ID field that the facade no longer publishes (ALIRemote.py:129), and the client test fixture still declares cbct_regions and prediction_ID and no mode (ALIRemote/Testing/Python/test_ali_client.py:101, :409).

Pitfall · the Mucogingival refinement stack is not ported

See What changed from the legacy logic. For the 13 mucogingival landmarks, the legacy at 3c67957 places each point, then smooths, snaps, completes and fills the line; VISOR places each one in a single pass and always estimates absent teeth (IO/engine.py:354-358). The VISOR README reports one labelled lower arch: 13 landmarks out of 13, none forced, 12 identical to upstream and one 0.179 mm apart, and states that accuracy is not established for lack of annotated scans (tools/ALI/README.md:292-300). What the missing steps cost on a set of scans was not measured.

Pitfall · two scans of the same stem overwrite each other

The output path is dirname(key)/<stem>_lm_Pred.mrk.json where the stem drops the extension (CB/engine.py:916-921), so a.nii.gz and a.nrrd in the same folder write the same file with no error. Run for this page: scan_stem returns a for both names; the overwrite itself was not run.

Note · only Mucogingival points carry a description

O and C points, and every ALI_CBCT point, have an empty description whatever their quality: notes are filled only by the MG path (IO/engine.py:567-575, written by :426) and ALI_CBCT passes none (CB/engine.py:921). The run report's landmarks_degraded (IO/engine.py:414-419) is the other place an MG doubt is recorded.

Note · noise in the IOS run report

ALI_IOS is handed the whole models folder, which also holds the CBCT checkpoints (VISOR-serve scripts/data-manifest.yml:121-130), and lists every .pth whose name lacks a network token (O, C, MG) or a jaw token under models_unrecognized (IO/engine.py:98-111, :703). On a full bundle that is a long list of CBCT file names in every IOS report. Not a failure; not measured on the full bundle.

Note · dead duplicate in ALI_CBCT

CB/engine.py:644-650 and :651-657 are the same block (compute processed, raise "ALI produced no landmarks for any scan" if empty) twice in a row. No effect.

Verified · the O camera table is reproduced on purpose

Two O directions are divided by the norm of a different vector (np.array([0.5, 0.0, 1.0]) / _norm([0.5, 0.5, 1.0])), so they have a length of 0.913 or 0.791 instead of 1 (calculated: 1.118/1.2247 and 1.118/1.414). The port keeps them deliberately, because the weights were trained on these views (IO/render.py:8-12, table :39-54; legacy ALI_IOS_utils/model.py:66-77).

Verified · independent landmarks, bounded searches

A landmark's result depends only on the scan, the weights and the seed, never on which other landmarks were requested (CB/agent.py:54-68; this is what lets ASO ask for 7 and a standalone run ask for 119). Move bounds are tested coordinate by coordinate (CB/agent.py:135-141) and both the search and the refinement stop on the same step counter (CB/agent.py:238-243, :272-286). The weights are loaded with weights_only=True (CB/brain.py:133-135).

10. Literature

The networks are the published ones: ALI_CBCT follows Gillot et al. 2023 (agents on a multi-scale volume, scales 1 mm and 0.3 mm, CB/catalog.py:69), ALI_IOS the CLIP 2022 paper for the O model (unit sphere, five views per tooth, patch segmentation, IO/surface.py:72, IO/render.py:39-54). The Mucogingival path is unpublished, as on the legacy side. The bibliography is the tool's own: ALI sources; the legacy page discusses each paper against the code in its section 8.
