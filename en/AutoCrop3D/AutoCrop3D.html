AutoCrop3D

Batch-crops a folder of volumes to a ROI box (.mrk.json) by extracting indices in the original grid — no interpolation, no network, no conda.

unpublished autocrop3d_cli no conda no GPU purely computational Bibliography

1. Position in the pipeline

Nothing in the repository calls AutoCrop3D, and AutoCrop3D calls nothing but Slicer. It is declared in CMakeLists.txt:39 and that's it.

In practice it sits upstream of the segmenters (AMASSS, BATCHDENTALSEG) or downstream of them: the "generate VTK" mode only triggers if the output file name contains seg, which presupposes it's being handed labelmaps already produced elsewhere.

No model, no .pth, no download: verified by grepping torch|conda|\.pth|monai|nnunet across all of AutoCrop3D/ — zero hits outside a vtkPolyData named model.

3. What defines the crop box

A markups ROI json file (.mrk.json), read as follows (AutoCrop3D_CLI.py:70):

ROI = json.load(open(ROI_Path))['markups'][0]
ROI_Center = np.array(ROI['center'])
ROI_Size   = np.array(ROI['size'])
Lower = ROI_Center - ROI_Size / 2
Upper = ROI_Center + ROI_Size / 2

Three fields of the json are ignored, and that's the main source of surprises:

  • coordinateSystem. The test file ROI.mrk.zip (in AutoCrop3D/Crop_Volumes_UI/Testing/Test_data/) declares "coordinateSystem": "LPS", which is the repository's convention (every markups writer hardcodes "LPS": ALI_CBCT, ASO_CBCT, AREG_CBCT, FlexReg, VFACE). center is therefore in LPS, exactly what SimpleITK's TransformPhysicalPointToContinuousIndex expects. But the field is never read: a ROI saved in RAS would give a center whose x and y have the opposite sign, with no message at all.
  • orientation (the box's 3×3 matrix). Ignored: the box is assumed to be aligned with the LPS axes. In the test file it's diag(-1,-1,1), a 180° rotation around z — no effect on a centered box. A genuinely rotated ROI would be silently treated as its own axis-aligned bounding box. That's exactly the reason the "tilted images" checkbox exists (§5).
  • Neither segmentation nor a computed bounding box: the box comes solely from this json. There is no code anywhere that derives a ROI from a labelmap.
Pitfall

coordinateSystem: a ROI saved in RAS would give a center whose x and y have the opposite sign, with no message at all.

orientation: a genuinely rotated ROI would be silently treated as its own axis-aligned bounding box.

On the volume side, Search accepts .nii.gz, .nii, .nrrd.gz, .nrrd, .gipl.gz, .gipl (AutoCrop3D_CLI.py:48), via a glob.iglob(**, recursive=True) followed by an endswith.

4. How the box is applied — index extraction, no resampling

This is the key point: no interpolation. The physical → index conversion followed by the crop (AutoCrop3D_CLI.py:77):

Lower = np.array(img.TransformPhysicalPointToContinuousIndex(Lower)).astype(int)
Upper = np.array(img.TransformPhysicalPointToContinuousIndex(Upper)).astype(int)
for i in range(3):
    if Lower[i] > Upper[i]:
        Lower[i], Upper[i] = Upper[i], Lower[i]
Lower = [max(0, l) for l in Lower]
Upper = [min(img_size[i], u) for i, u in enumerate(Upper)]
img_roi = img[Lower[0]:Upper[0], Lower[1]:Upper[1], Lower[2]:Upper[2]]

The swap is not cosmetic. TransformPhysicalPointToContinuousIndex applies the inverse of the direction matrix. On a volume whose direction cosines are negative on some axis (common in CBCT), the physical "lower" corner becomes the largest index: without the swap, the slice would be empty. This is the correct handling of direction.

What SimpleITK indexing preserves. Verified: slicing a sitk.Image keeps spacing and direction identical and recomputes the origin of the extracted corner. On a 50×60×70 volume, spacing 0.3, origin (10,20,30), direction diag(-1,-1,1), img[5:20,5:20,5:20] gives an origin of (8.5, 18.5, 31.5) — a shift of -5·0.3 on x and y (negative direction), +5·0.3 on z. The voxel values are bit-for-bit identical to the input.

Verified

Slicing a sitk.Image keeps spacing and direction identical and only recomputes the origin of the extracted corner. The voxel values are bit-for-bit identical to the input.

"Keep the same size as input" mode (box_Size == 'True', AutoCrop3D_CLI.py:107): an empty image is created with the original geometry (sitk.Image(...) + CopyInformation), the extracted block is pasted back at the same index location, and CopyInformation is reapplied. The geometry is strictly identical to the input, with everything outside the ROI set to 0. Note the axis inversion of GetArrayFromImage (z,y,x), correctly handled by the code.

What happens to any associated transforms: nothing. No vtkMRMLTransformNode, no .tfm read or written, no HardenTransform. The geometry is carried entirely by the header (origin/spacing/direction), and the crop offset is absorbed by the origin.

Note

Practical consequence: a registration matrix computed on the full volume remains valid as-is on the cropped volume, since the physical coordinates haven't moved.

5. The alternative path — Slicer's Crop Volume module

processCropVolume() (AutoCrop3D.py:915), activated by the "Use module 'Crop Volume' for tilted images" checkbox (commit 9d2bbe8). It runs inside the widget, not in the CLI:

cropVolumeLogic = slicer.modules.cropvolume.logic()
parameters = slicer.vtkMRMLCropVolumeParametersNode()
parameters.SetInputVolumeNodeID(inputVolume.GetID())
parameters.SetROINodeID(roiNode.GetID())
parameters.SetOutputVolumeNodeID(outputVolume.GetID())
cropVolumeLogic.Apply(parameters)

Only the three IDs are set: interpolation, isotropy, and spacing scale stay at the vtkMRMLCropVolumeParametersNode's default values. With interpolation on, Crop Volume resamples in the ROI's own coordinate frame, which is precisely what lets it handle a rotated ROI — at the cost of modifying the voxel values, unlike the CLI path. The two paths therefore do not produce the same file, and that's intentional.

optionCheckBox() hides "Keep the same size" in this mode, since Crop Volume has no equivalent.

This path loads the ROI and the volume as MRML nodes (loadMarkups, loadVolume), so it, and it alone, reads coordinateSystem and orientation — Slicer takes care of that when parsing the json.

6. Batch mode and patient ↔ ROI pairing

Two regimes, discriminated by len(ROIList['.mrk.json']) > 1 (AutoCrop3D_CLI.py:53):

  • a single ROI → applied to every volume found;
  • several ROIs → ChangeKeyDict builds {basename.split('_')[0]: path} and each volume looks up its key; on failure → logger.warning('No ROI for patient:') and continue.

Both sides compute the key differently:

SideRuleExample MA_0001_T1_Scan.nii.gz / MA_0001_ROI.mrk.json
volumechain of .split() on _Scan _scan _Seg _seg _Or _OR _MAND _MD _MAX _MX _CB _lm _T2 _T1 _Cl then .split('.')[0]MA_0001
ROIbasename.split('_')[0]MA

A patient name containing an underscore therefore breaks the pairing. With names that have no underscore (MA0001_…), everything works fine.

Progress is a simple open(logPath,'r+').write(str(index)) on every file; the widget doesn't read the content, only the st_mtime (AutoCrop3D.py:574).

7. Generating a VTK mesh from a segmentation

Triggered by if "seg" in ScanOutPath.lower() (AutoCrop3D_CLI.py:151) — the test is against the full output path, so a parent folder named Segmentations/ is enough to trigger it on every file. The failure is swallowed by a bare except: pass.

convertNiftiToVTK (GenerateVTKfromSeg.py:16):

  1. padding(): sitk.ConstantPad(img, [50,50,10], [0,0,0]). The actual signature verified: ConstantPad(image, padLowerBound, padUpperBound, constant) — the third argument being zero means that only the lower bound gets padded.
    Confirmed bug

    The comment "add 50 pixels around each dimension" is wrong: a structure that touches the crop's upper face will stay open.

    The temporary file is named image_padded.nii.gz and is written into the process's current directory, not into a tempdir.
  2. vtkNIFTIImageReader → vtkDiscreteMarchingCubes(GenerateValues(100, 1, 100)) → vtkSmoothPolyDataFilter (5 iterations, feature angle 120°, relaxation 0.6).
  3. Coloring: color_tup = LABEL_COLORS[label] with label = np.max(img_arr), the same color for every cell.
    Confirmed bug

    The comment "coloring according to labels" does not describe the code.

    And LABEL_COLORS only holds keys 1–6: a labelmap with more than 6 classes raises a KeyError swallowed by the caller's except: pass, so no VTK and no message.
  4. present_labels is computed and then never used — dead code.

VTK's NIfTI reader applies neither qform nor sform (the code doesn't even retrieve them), and the 50/50/10-voxel padding is never compensated for. A deduction, not tested here: the resulting mesh does not line up with the cropped volume in Slicer.

10. Environment

Nothing to install. The module uses only what Slicer already ships with: SimpleITK, numpy, vtk, qt. pip_install is imported in AutoCrop3D.py:11 but never called. No CUDA, no WSL, no conda.

11. Pitfalls and fragile points

Pitfall — ROI folder with a single file

A ROI folder containing exactly one file → crash. ROI_dict is only built if len(ROIList) > 1; otherwise ROI_Path stays the folder, and json.load(open(ROI_Path)) raises IsADirectoryError. The Crop Volume path, by contrast, tests os.path.isdir and handles it fine.

Pitfall — inconsistent extensions between widget and CLI

The widget and the CLI don't look for the same extensions. CheckInput (AutoCrop3D.py:808) only looks for .nii.gz, .nrrd.gz, .gipl.gz. A folder of uncompressed .nii or .nrrd files is rejected by the UI ("Wrong type of patient file detected") even though the CLI handles them perfectly well. And since nbFiles comes from that same list, the progress bar's denominator is wrong as soon as a mix of extensions is present.

Pitfall — ignored ROI fields

The ROI's coordinateSystem and orientation are ignored by the CLI path (§3). A rotated box or a ROI saved in RAS: wrong result, silently.

Pitfall — index truncation

.astype(int) truncates toward zero, so Upper loses up to one voxel per axis. No clinical consequence, but the crop is not symmetric around the requested center.

Pitfall — no intersection check

No check that the ROI intersects the volume. The clamping constrains Lower ≥ 0 and Upper ≤ size but nothing prevents Lower > Upper after the clamp: this yields a zero-size image and the write fails inside the try/except that logs Lower/Upper.

Pitfall — overly broad path replacement

.replace(basename, filename) replaces every occurrence in the joined path (AutoCrop3D_CLI.py:129): a folder sharing the file's name would get renamed too.

Pitfall — Crop Volume clears the scene

Crop Volume path: slicer.mrmlScene.Clear(0) on every patient (AutoCrop3D.py:998) — clears the entire scene, including any data the user had loaded into it.

Pitfall — MRML access off the main thread

Crop Volume path: slicer.util.saveNode called from a threading.Thread (AutoCrop3D.py:979), meaning MRML access off the main thread. The following while thread.is_alive(): processEvents() effectively serializes execution, which masks the problem without fixing it.

Pitfall — partial suffix

Crop Volume path: the suffix is only applied to .nii.gz files. A .nrrd comes out with no suffix, at the same relative name.

Pitfall — inoperative unit test

The unit test tests nothing. test_AutoCrop3D1 is defined twice: a class method that contains only a docstring (called by runTest), then a module-level function (AutoCrop3D.py:1097) which holds the actual test and is never executed.

Dead code

Dead code: CropCBCT.py (flagged in its own docstring), Autofill() which still contains absolute paths from a development machine, registerSampleData() which references AutoCrop3D2.png — a file absent from the repository.

12. Literature

No paper covers AutoCrop3D. It's a batch-processing utility written for the lab (Jeanne Claret, UoM/DCBIA), documented only by the README.md:336 section and by the help of Slicer's Crop Volume module, whose semantics it reuses:

  • Crop Volume — Slicer documentation
  • Crop Volume Sequence — Slicer documentation (cited by the README as the limitation AutoCrop3D works around: files too heavy to load as a sequence)
  • SlicerAutomatedDentalTools

The CLI's documentation-url points to https://github.com/Jeanneclre/DCBIA-code, a personal repository that is not the project's own.
