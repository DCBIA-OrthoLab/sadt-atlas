AutoCrop3D

Batch-crops a folder of volumes to a ROI box (.mrk.json) by extracting indices in the original grid: no interpolation, no network, no conda.

unpublished autocrop3d_cli no conda no GPU purely computational VISOR Bibliography
Two code bases

Everything numbered below describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, is described in VISOR: how this tool runs now.

VISOR references read SADT-VISOR AutoCrop3D/pipeline.py:272: that is tools/AutoCrop3D/src/sadt_autocrop3d/pipeline.py at 6ba2a78. VISOR-serve is e9a7e5d, AutomatedDentalToolsRemote is 19b95e8. Legacy lines are written AutoCrop3D_CLI.py:63@3c67957; a bare legacy line number on this page is also read at 3c67957. Legacy paths are relative to AutoCrop3D/: the CLI and its helpers are in Crop_Volumes_CLI/, the widget AutoCrop3D.py in Crop_Volumes_UI/.

1. Position in the pipeline

Nothing in the repository calls AutoCrop3D, and AutoCrop3D calls nothing but Slicer. It is declared in CMakeLists.txt:41 and that's it.

In practice it sits upstream of the segmenters (AMASSS, BATCHDENTALSEG) or downstream of them: the "generate VTK" mode only triggers if the output file name contains seg, which presupposes it's being handed labelmaps already produced elsewhere.

3. What defines the crop box

A markups ROI json file (.mrk.json), read as follows (AutoCrop3D_CLI.py:63-68):

ROI = json.load(open(roi_path))['markups'][0]
roi_center = np.array(ROI['center'])
roi_size = np.array(ROI['size'])

lower = roi_center - roi_size / 2
upper = roi_center + roi_size / 2

Three fields of the json are ignored, and that's the main source of surprises:

  • coordinateSystem. The test file ROI.mrk.zip (in AutoCrop3D/Crop_Volumes_UI/Resources/testfiles/AutoCrop3D/) declares "coordinateSystem": "LPS", which is the repository's convention (every markups writer hardcodes "LPS": ALI_CBCT, ASO_CBCT, AREG_CBCT, FlexReg, VFACE). center is therefore in LPS, exactly what SimpleITK's TransformPhysicalPointToContinuousIndex expects. But the field is never read: a ROI saved in RAS would give a center whose x and y have the opposite sign, with no message at all.
  • orientation (the box's 3×3 matrix). Ignored: the box is assumed to be aligned with the LPS axes. In the test file it's diag(-1,-1,1), a 180° rotation around z: no effect on a centered box. A genuinely rotated ROI would be silently treated as its own axis-aligned bounding box. That's exactly the reason the "tilted images" checkbox exists (§5).
  • Neither segmentation nor a computed bounding box: the box comes solely from this json. There is no code anywhere that derives a ROI from a labelmap.
Pitfall

Legacy (3c67957); half corrected in VISOR. The legacy CLI reads only center and size (AutoCrop3D_CLI.py:63-65@3c67957). The VISOR port reads coordinateSystem: an RAS ROI is converted and an unknown value is an error (SADT-VISOR AutoCrop3D/pipeline.py:194-201). It still ignores orientation, but says so: a rotated box sets roi_orientation_ignored in the report and logs a warning (SADT-VISOR AutoCrop3D/pipeline.py:203-211, SADT-VISOR AutoCrop3D/__init__.py:242).

coordinateSystem: a ROI saved in RAS would give a center whose x and y have the opposite sign, with no message at all.

orientation: a genuinely rotated ROI would be silently treated as its own axis-aligned bounding box.

On the volume side, Search accepts .nii.gz, .nii, .nrrd.gz, .nrrd, .gipl.gz, .gipl (AutoCrop3D_CLI.py:41), via a glob.iglob(**, recursive=True) followed by an endswith.

4. How the box is applied: index extraction, no resampling

This is the key point: no interpolation. The physical → index conversion followed by the crop (AutoCrop3D_CLI.py:70-80, slice at :96-98):

lower = np.array(img.TransformPhysicalPointToContinuousIndex(lower)).astype(int)
upper = np.array(img.TransformPhysicalPointToContinuousIndex(upper)).astype(int)
for i in range(3):
    if lower[i] > upper[i]:
        lower[i], upper[i] = upper[i], lower[i]
lower = [max(0, l) for l in lower]
upper = [min(img_size[i], u) for i, u in enumerate(upper)]
img_roi = img[lower[0]:upper[0], lower[1]:upper[1], lower[2]:upper[2]]

The swap is not cosmetic. TransformPhysicalPointToContinuousIndex applies the inverse of the direction matrix. On a volume whose direction cosines are negative on some axis (common in CBCT), the physical "lower" corner becomes the largest index: without the swap, the slice would be empty. This is the correct handling of direction.

What SimpleITK indexing preserves. Verified: slicing a sitk.Image keeps spacing and direction identical and recomputes the origin of the extracted corner. On a 50×60×70 volume, spacing 0.3, origin (10,20,30), direction diag(-1,-1,1), img[5:20,5:20,5:20] gives an origin of (8.5, 18.5, 31.5): a shift of -5·0.3 on x and y (negative direction), +5·0.3 on z. The voxel values are bit-for-bit identical to the input.

Verified

Also true in VISOR (SADT-VISOR AutoCrop3D/pipeline.py:301 slices the same way). The VISOR README claims byte-identical output against the legacy CLI on one test scan (SADT-VISOR AutoCrop3D/README.md:204-221); that comparison was not replayed here.

Slicing a sitk.Image keeps spacing and direction identical and only recomputes the origin of the extracted corner. The voxel values are bit-for-bit identical to the input.

"Keep the same size as input" mode (original_size=='True', read from the box_Size argument, AutoCrop3D_CLI.py:35,100-110): an empty image is created with the original geometry (sitk.Image(...) + CopyInformation), the extracted block is pasted back at the same index location, and CopyInformation is reapplied. The geometry is strictly identical to the input, with everything outside the ROI set to 0. Note the axis inversion of GetArrayFromImage (z,y,x), correctly handled by the code.

What happens to any associated transforms: nothing. No vtkMRMLTransformNode, no .tfm read or written, no HardenTransform. The geometry is carried entirely by the header (origin/spacing/direction), and the crop offset is absorbed by the origin.

Note

Practical consequence: a registration matrix computed on the full volume remains valid as-is on the cropped volume, since the physical coordinates haven't moved.

5. The alternative path: Slicer's Crop Volume module

processCropVolume() (AutoCrop3D.py:723-808), activated by the "Use module 'Crop Volume' for tilted images" checkbox (commit 9d2bbe8). It runs inside the widget, not in the CLI:

crop_volume_logic= slicer.modules.cropvolume.logic()

parameters = slicer.vtkMRMLCropVolumeParametersNode()
parameters.SetInputVolumeNodeID(input_volume.GetID())
parameters.SetROINodeID(roi_node.GetID())
parameters.SetOutputVolumeNodeID(output_volume.GetID())

slicer.mrmlScene.AddNode(parameters)

crop_volume_logic.Apply(parameters)

(AutoCrop3D.py:769-778.)

Only the three IDs are set: interpolation, isotropy, and spacing scale stay at the vtkMRMLCropVolumeParametersNode's default values. With interpolation on, Crop Volume resamples in the ROI's own coordinate frame, which is precisely what lets it handle a rotated ROI: at the cost of modifying the voxel values, unlike the CLI path. The two paths therefore do not produce the same file, and that's intentional.

optionCheckBox() (AutoCrop3D.py:331-339) unchecks and hides "Keep the same size" in this mode, since Crop Volume has no equivalent.

This path loads the ROI and the volume as MRML nodes (loadMarkups, loadVolume, AutoCrop3D.py:761,764), so it, and it alone, reads coordinateSystem and orientation: Slicer takes care of that when parsing the json.

6. Batch mode and patient ↔ ROI pairing

Two regimes, discriminated by len(roi_list['.mrk.json']) >1 (AutoCrop3D_CLI.py:46,56):

  • a single ROI → applied to every volume found;
  • several ROIs → ChangeKeyDict builds {basename.split('_')[0]: path} (FilesType.py:75-78) and each volume looks up its key; on failure → logger.warning('No ROI for patient:') and continue (AutoCrop3D_CLI.py:57-61).

Both sides compute the key differently:

SideRuleExample MA_0001_T1_Scan.nii.gz / MA_0001_ROI.mrk.json
volumechain of .split() (AutoCrop3D_CLI.py:52) on _Scan _scan _Seg _seg _Or _OR _MAND _MD _MAX _MX _CB _lm _T2 _T1 _Cl then .split('.')[0]MA_0001
ROIbasename.split('_')[0] (FilesType.py:77)MA

A patient name containing an underscore therefore breaks the pairing. With names that have no underscore (MA0001_…), everything works fine.

Progress is a simple open(args.logPath,'r+') then write(str(index)) on every file (AutoCrop3D_CLI.py:140-141); the widget doesn't read the content, only the modification time (os.path.getmtime, AutoCrop3D.py:394).

7. Generating a VTK mesh from a segmentation

Triggered by if "seg" in scan_out_path.lower() (AutoCrop3D_CLI.py:143): the test is against the full output path, so a parent folder named Segmentations/ is enough to trigger it on every file. A failure is caught by except Exception and only logged at debug level (AutoCrop3D_CLI.py:144-147).

convertNiftiToVTK (GenerateVTKfromSeg.py:15):

  1. padding(): sitk.ConstantPad(input_image, padding_size, [0]*input_image.GetDimension()) with padding_size = [50, 50, 10] (GenerateVTKfromSeg.py:83-85). The actual signature verified: ConstantPad(image, padLowerBound, padUpperBound, constant), the third argument being zero means that only the lower bound gets padded.
    Confirmed bug

    Legacy only (3c67957); not present in VISOR. The legacy pads [50, 50, 10] voxels with ConstantPad(img, padding_size, [0]*dim), lower bound only (GenerateVTKfromSeg.py:83-85@3c67957). The port pads both bounds, with a margin in millimetres converted per axis (SADT-VISOR AutoCrop3D/pipeline.py:415-426, :462).

    The comment "add 50 pixels around each dimension" is wrong: a structure that touches the crop's upper face will stay open.

    The temporary file is named image_padded.nii.gz and is written into the process's current directory, not into a tempdir (GenerateVTKfromSeg.py:87-88).
  2. vtkNIFTIImageReader → vtkDiscreteMarchingCubes(GenerateValues(100, 1, 100)) → vtkSmoothPolyDataFilter (5 iterations, feature angle 120°, relaxation 0.6) (GenerateVTKfromSeg.py:38-55).
  3. Coloring: color_tup = LABEL_COLORS[label] with label = np.max(img_arr), the same color for every cell.
    Confirmed bug

    Legacy only (3c67957); not present in VISOR. The legacy takes label = np.max(img_arr) once and applies LABEL_COLORS[label] to every cell (GenerateVTKfromSeg.py:33,66@3c67957). The port colours each cell from its own label (SADT-VISOR AutoCrop3D/pipeline.py:544-585); the six-colour table is the same (:359-366) and a label beyond it gets a generated hue (:369-384).

    The comment "coloring according to labels" does not describe the code.

    And LABEL_COLORS only holds keys 1–6 (GenerateVTKfromSeg.py:6-13): a labelmap whose highest label is above 6, or an empty crop (maximum 0), raises a KeyError caught by the caller's except Exception and logged at debug level only, so no VTK and no visible message.
  4. present_labels is computed (GenerateVTKfromSeg.py:28-31) and then never used: dead code.

VTK's NIfTI reader applies neither qform nor sform (the code doesn't even retrieve them), and the 50/50/10-voxel padding is never compensated for. A deduction, not tested here: the resulting mesh does not line up with the cropped volume in Slicer.

10. Environment

Nothing to install. The module uses only what Slicer already ships with: SimpleITK, numpy, vtk, qt. pip_install was imported but never called when this page was written; checked again on 2026-10-12, the import has been removed. No CUDA, no WSL, no conda.

11. Pitfalls and fragile points

Pitfall: ROI folder with a single file

Legacy only (3c67957); not present in VISOR. Legacy: the table is built only if more than one ROI is found, then json.load(open(roi_path)) receives the folder (AutoCrop3D_CLI.py:46,56,63@3c67957). VISOR: a file, or a folder holding exactly one ROI, is applied to every scan (SADT-VISOR AutoCrop3D/__init__.py:342-343).

A ROI folder containing exactly one file → crash. ROI_dict is only built if len(ROIList) > 1; otherwise ROI_Path stays the folder, and json.load(open(ROI_Path)) raises IsADirectoryError. The Crop Volume path, by contrast, tests os.path.isdir and handles it fine.

Pitfall: inconsistent extensions between widget and CLI

Legacy only (3c67957); not present in VISOR. There is no hand-written panel any more: one tuple serves discovery (SADT-VISOR AutoCrop3D/pipeline.py:26). A .nrrd.gz is still discovered but refused with a named per-file error (SADT-VISOR AutoCrop3D/pipeline.py:37, SADT-VISOR AutoCrop3D/__init__.py:210-215). Legacy lines: the panel list is AutoCrop3D.py:641,656-659@3c67957, the CLI list AutoCrop3D_CLI.py:41@3c67957.

The widget and the CLI don't look for the same extensions. CheckInput (AutoCrop3D.py:641@3c67957) only looks for .nii.gz, .nrrd.gz, .gipl.gz. A folder of uncompressed .nii or .nrrd files is rejected by the UI ("Wrong type of patient file detected") even though the CLI handles them perfectly well. And since nbFiles comes from that same list, the progress bar's denominator is wrong as soon as a mix of extensions is present.

Pitfall: ignored ROI fields

Legacy (3c67957); half corrected in VISOR. coordinateSystem is read and orientation is flagged in the report, see the first Pitfall of section 3 (SADT-VISOR AutoCrop3D/pipeline.py:194-211).

The ROI's coordinateSystem and orientation are ignored by the CLI path (§3). A rotated box or a ROI saved in RAS: wrong result, silently.

Pitfall: index truncation

Also true in VISOR (SADT-VISOR AutoCrop3D/pipeline.py:272-273): the port keeps the truncation on purpose, and says why in its docstring (:261-264). Legacy: AutoCrop3D_CLI.py:70-71@3c67957.

.astype(int) truncates toward zero, so upper loses up to one voxel per axis. No clinical consequence, but the crop is not symmetric around the requested center.

Pitfall: no intersection check

Legacy only (3c67957); not present in VISOR. Legacy: clamping at AutoCrop3D_CLI.py:78-80@3c67957, slice at :96-98, failure swallowed at :128-138. VISOR: an empty index range raises The ROI does not overlap this volume (SADT-VISOR AutoCrop3D/pipeline.py:294-300); a partial overlap is cropped and flagged clamped_to_the_volume (SADT-VISOR AutoCrop3D/pipeline.py:280). A scan that fails is listed in failed and the others go on (SADT-VISOR AutoCrop3D/__init__.py:142-149).

No check that the ROI intersects the volume. The clamping constrains Lower ≥ 0 and Upper ≤ size but nothing prevents Lower > Upper after the clamp: this yields a zero-size image and the write fails inside the try/except that logs lower/upper.

Pitfall: overly broad path replacement

Legacy only (3c67957); not present in VISOR. The port builds the path with os.path.relpath and pathlib (SADT-VISOR AutoCrop3D/__init__.py:223-225, :277-286) and the name in SADT-VISOR AutoCrop3D/pipeline.py:332-344.

.replace(basename, filename) replaces every occurrence in the joined path (AutoCrop3D_CLI.py:122,124@3c67957): a folder sharing the file's name would get renamed too.

Pitfall: Crop Volume clears the scene

Legacy only (3c67957); not present in VISOR. The Crop Volume path is not ported: it needs a running Slicer and has no headless equivalent (SADT-VISOR AutoCrop3D/README.md:159-177; AutomatedDentalToolsRemote AutoCrop3DRemote/AutoCrop3DRemote.py:9-11). The server never touches a scene.

Crop Volume path: slicer.mrmlScene.Clear(0) on every patient (AutoCrop3D.py:808@3c67957), clears the entire scene, including any data the user had loaded into it.

Pitfall: MRML access off the main thread

Legacy only (3c67957); not present in VISOR. Same reason: the Crop Volume path is not ported (SADT-VISOR AutoCrop3D/README.md:159-177).

Crop Volume path: slicer.util.saveNode called from a threading.Thread (AutoCrop3D.py:706@3c67957, the thread is started at :787), meaning MRML access off the main thread. The following while thread.is_alive(): processEvents() effectively serializes execution, which masks the problem without fixing it.

Pitfall: partial suffix

Legacy only (3c67957); not present in VISOR. Legacy: replace('.nii.gz', ...) at AutoCrop3D.py:699@3c67957. VISOR applies the suffix to any extension, keeping a compound one (SADT-VISOR AutoCrop3D/pipeline.py:332-344; a.nii gives a_cropped.nii).

Crop Volume path: the suffix is only applied to .nii.gz files. A .nrrd comes out with no suffix, at the same relative name.

Pitfall: inoperative unit test

Legacy only (3c67957); not present in VISOR. The VISOR package has its own suite, SADT-VISOR AutoCrop3D/tests/test_run.py: 103 tests passed on 2026-11-09 (its README says 102, README.md:200, one test behind).

The unit test tests nothing. test_AutoCrop3D1 is defined twice: a class method that contains only a docstring (AutoCrop3D.py:977-987, called by runTest at :975), then a module-level function (AutoCrop3D.py:988) which holds the actual test and is never executed.

Dead code

Legacy only (3c67957); not present in VISOR. CropCBCT.py is not ported (SADT-VISOR AutoCrop3D/README.md:179-180). Correction: an earlier version of this callout also named Autofill(); no such function exists at 3c67957 (git grep Autofill is empty), so it was removed.

Dead code: CropCBCT.py (flagged in its own docstring, CropCBCT.py:13@3c67957) and registerSampleData() (AutoCrop3D.py:90-132@3c67957) which references AutoCrop3D2.png, a file absent from the repository.

12. Literature

No paper covers AutoCrop3D. It's a batch-processing utility written for the lab (Jeanne Claret, UoM/DCBIA), documented only by the README.md:331 section and by the help of Slicer's Crop Volume module, whose semantics it reuses:

  • Crop Volume: Slicer documentation
  • Crop Volume Sequence, Slicer documentation (cited by the README as the limitation AutoCrop3D works around: files too heavy to load as a sequence)
  • SlicerAutomatedDentalTools

The CLI's documentation-url points to https://github.com/Jeanneclre/DCBIA-code, a personal repository that is not the project's own.
