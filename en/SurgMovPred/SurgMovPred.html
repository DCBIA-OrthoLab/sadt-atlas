SurgMovPred

A spreadsheet of cephalometric measurements goes in, a spreadsheet of predicted bone displacements comes out: 112 stacked scikit-learn regressors, one per target, no neural network, no image, and no mesh.

unpublished SurgMovPred_CLI no conda — Slicer's own Python Bibliography

Prediction of the surgical movements of an orthognathic surgery from a spreadsheet of cephalometric measurements. No neural network, no image, no mesh: 112 stacked scikit-learn regressors, one per value to predict, applied row by row to an Excel/CSV file.

1. Position in the pipeline

Isolated tool. Nothing in the repository calls it, and it calls nothing in the repository: it reads no volume, no mesh, no landmarks. Its input is a folder of spreadsheets, its output another spreadsheet.

CalledHow
SurgMovPred_CLIslicer.cli.run(slicer.modules.surgmovpred_cli, …) (SurgMovPred.py:842)

The module isn't wired into the MRML scene: no vtkMRMLNode is created, read or transformed. It's a launch interface sitting on top of a pandas script.

Pitfall

Copy-paste leftovers from the CNE module (clinical-note summarization), not to be mistaken for the actual pipeline: the helpText says "This tool helps to create summaries of clinical notes", the parameterNodeWrapper is documented with notesFolder_input / modelType / notesType, and process() still names its arguments notesFolder_input / notesFolder_output (SurgMovPred.py:236, SurgMovPred.py:815).

3. Input and preprocessing

Accepted format. load_data_from_directory() (SurgMovPred_CLI.py:141) collects every *.csv, *.xlsx, *.ods file in the folder (extension in lowercase and uppercase), reads them (read_csv, read_excel, read_excel(engine='odf')) and concatenates them (pd.concat(..., ignore_index=True)). No recursion into subfolders. For an Excel workbook, only the first sheet is read — the official test file contains seven (all_data, demographics, Invivo_ceph, surgical_mov, dolp_ceph_T0, dolp_ceph_T1, dolp_ceph_total), and it's all_data that sits in first position.

Column-name normalization, clean_name() (SurgMovPred_CLI.py:39), applied on input to fall back onto the spelling used at training time:

  1. removal of ", \, [, ];
  2. any character outside [0-9a-zA-Z_'] becomes _ — the apostrophe is deliberately kept (code comment: for Jarabak's and SM_A'_CP);
  3. collapsing of repeated _, trimmed at both ends;
  4. "total" → "Total";
  5. f_ prefix if the name starts with a digit.

This cleanup explains the actual feature names: SM-A-FH   (with two trailing spaces, in the test file) becomes SM_A_FH, Jarabak's ratio   becomes Jarabak's_ratio, FMA(MP-FH) Ang_2D becomes FMA_MP_FH_Ang_2D.

Patient identifier. find_id_column() (SurgMovPred_CLI.py:81) tests 8 case-insensitive patterns (#, id, patient id, patient number, subject, …) then, as a last resort, any column containing both "patient" and "id". In the test file, the column is #. On failure, the output column IDPatient is filled with pd.NA with a plain warning.

Value normalization. Each model package carries its own StandardScaler computed (centering + scaling, with_mean=True, with_std=True), applied right before prediction (SurgMovPred_CLI.py:237). No imputation: a missing value propagates as NaN all the way to the output.

Tolerance on the _T0 suffix (SurgMovPred_CLI.py:223): if the model expects X_T0 and the column is named X, it is accepted.

Note

This is the only leniency; any other missing feature makes the entire model get skipped with a warning, and the corresponding column is absent from the result.

4. The models

The weights are not in the repository. onDownloadDefaultModel() (SurgMovPred.py:782) downloads and unzips:

https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/SurgMovPred/all_models.zip
  -> Documents/SlicerDownloads/SurgMovPred/Models/all_models/

706 MB, 112 folders, one stacking_package.pkl of ~13 MB each. load_all_model_packages() does a recursive Path.glob("**/stacking_package.pkl") and indexes by package['target_name']: pointing the selector at all_models/ loads all 112 models, pointing at a subfolder loads only one. The CLI's help text mentions saved_models/class_1, saved_models/class_None folders — this hierarchy by skeletal class does not exist in the published archive, which is flat.

4.1 Contents of a package

Each .pkl is a four-key joblib dict, used as-is by SurgMovPred_CLI.py:212:

KeyContent
target_nametarget name, e.g. Mx_ALL_APoint_P-/A+_Pred (raw form, with -, /, +)
features_namesordered list of 145 feature names
scalerfitted sklearn.preprocessing.StandardScaler
modelfitted sklearn.ensemble.StackingRegressor
Verified

This information was read directly from all_models/Mn_MB_Genioplasty_Total_Pred/stacking_package.pkl and all_models/Mx_ALL_APoint_P-_A_Pred/stacking_package.pkl (pickle-stream inspection, without execution). The 145 features are identical in both packages; nothing formally guarantees the same holds for the other 110, but their near-identical sizes (13.17–13.19 MB) strongly suggest it.

4.2 The architecture

No network. A stacking ensemble of three base regressors and one linear meta-regressor, serialized with _sklearn_version = 1.6.1:

RoleEstimatorParameters readable in the pickle
base multitask_elasticnetElasticNetCVgrid of l1_ratio, n_alphas, eps, selection='cyclic'
base lgbmlightgbm.sklearn.LGBMRegressorboosting_type='gbdt', objective='regression', num_leaves=31
base gaussian_processGaussianProcessRegressorkernel Product(ConstantKernel, RBF), optimizer='fmin_l_bfgs_b', normalize_y
metaLinearRegressionstack_method='predict', passthrough=False

passthrough=False means the meta-model sees only the three base models' predictions, not the 145 original features. stack_method='predict': one scalar value per base model, hence a three-input linear regression.

The file's dominant weight (13 MB for 145 features) comes from the GaussianProcessRegressor, which keeps its training matrix, and from the LightGBM booster.

Training is not in the repository: no script, no dataset, no metrics, no seed. Not determinable from the repository: cohort size, validation protocol, per-target performance.

4.3 The 145 features

Four families, reconstructed from features_names and cross-checked against the all_data sheet of the test file:

FamilyCountExamples
Point positions relative to the three reference planes — FH (Frankfort horizontal), MSP (midsagittal plane), CP (coronal plane) ~76 SM_A_FH, SM_GoL_MSP, SM_PNS_CP, SM_CoR_FH
Soft-tissue points, marked by the apostrophe ~20 SM_N'_FH, SM_Sn'_MSP, SM_ULip'_FH, SM_Pg'_MSP
Classic 2D cephalometric measurements ~12 SNA, SM_ANB_signed, SM_Witts, LAFH, Jarabak's_ratio, UAFH_LAFH, FMA_MP_FH_Ang_2D, IMPA_L1_MP_Ang_2D, U1_to_SN_Ang_2D, SM_Mx_Width, SM_Mn_Width, OP_to_FH_Ang_2D
Occlusal/dental measurements, in two sets suffixed _T0 and _Total 2 × ~18 MxMn_Overjet_R_T0 / MxMn_Overjet_R_Total, MxMn_Molar_Relationship_L_T0, Mn_Gonions_to_Midline_Distances_R_Total

What exactly the two _T0 / _Total sets mean is documented nowhere in the repository. The naming (T0 = before, Total = total variation) and the fact that both are on the input side suggest the model receives the pre-surgical state and the targeted occlusal outcome, in order to infer the bone displacements to be carried out — this is an inference, not a claim made by the code.

The columns Gender, Surg, Genio, 3piece, assymetry, Skl_Cl_2 from the test file do not appear among the 145 features of the two inspected packages: they are read and then ignored.

4.4 What is predicted

112 targets = 28 structures × 4 components.

Components, based on target names: P-/A+ (posterior negative / anterior positive), R-/L+ (right negative / left positive), Down+ (vertical, down positive), and Total. The first three are therefore the signed components of a displacement vector in the cephalometric frame (CP, MSP, FH), the fourth very likely its magnitude — inferred from the naming, the unit (mm) is written nowhere.

The 28 structures:

SegmentPoints
Maxilla, Mx_ALL_* (10)APoint, ANS, PNS, U3CanineTip L/R, U6MesialCuspTip L/R, UpperIncisorTip L/R, UpperIncisorTipMidpoint
Mandible, Mn_ALL_* (17)BPoint, Gnathion, Menton, Pogonion, Gonion L/R, ChinSideCut L/R, MandibleBackCut L/R, L3CanineTip L/R, L6MesialCuspTip L/R, LowerIncisorTip L/R, LowerIncisorTipMidpoint
Genioplasty, Mn_MB_Genioplasty (1)—

ALL designates the entire bone segment (maxilla or mandible mobilized as a block), MB the genioplasty segment. What is predicted, then, is the displacement of landmark points rigidly attached to each segment, predicted, not a rigid transform: nothing forces the maxilla's 10 points to be consistent with one another (see §7).

5. The core processing

predict_all_targets() (SurgMovPred_CLI.py:194), in full:

for target_name, pack in packages.items():
    X_target = df_cleaned[[feature_source[f] for f in pack['features_names']]]
    X_target.columns = pack['features_names']
    X_scaled = pack['scaler'].transform(X_target)
    predictions_by_target[target_name] = pack['model'].predict(
        pd.DataFrame(X_scaled, columns=..., index=df_cleaned.index))

No post-correction, no bounding, no inter-target consistency, no confidence interval — the GaussianProcessRegressor can produce a standard deviation, it isn't asked to. Each target is handled independently, with a try/except per target: a target that crashes doesn't interrupt the others, its column simply disappears.

All 112 models are loaded into memory at once (load_all_model_packages), i.e. ~1.5 GB of RAM before the data is even read.

6. Outputs

save_results() writes two files, same content, into the output folder:

FileContent
predictions_outputs.xlsxone row per input patient, IDPatient column then one column per predicted target
predictions_outputs.csvsame

index=True in both cases: the pandas index (0, 1, 2…) becomes an unnamed column. Column names are the packages' raw target_name, so with / and + (Mx_ALL_APoint_P-/A+_Pred).

Pitfall

There is no reapplication of the result whatsoever. Nothing builds a matrix, moves a mesh, creates a Slicer node, or opens a view: the prediction stops at the spreadsheet. The question "how is the prediction reapplied to produce a visualizable result" has no answer in this repository — it's up to the operator to carry the values into their planning software.

7. What is predicted vs. what is computed

BlockNatureWhere
Column-name cleanup, ID detectioncomputed deterministic (regex)CLI
Standardizationcomputed learned StandardScalerCLI
Prediction of the 112 displacementspredicted stacking ElasticNetCV + LightGBM + GP, meta LinearRegressionCLI, CPU
Consolidation into a single segment transformnonexistent—
Pitfall

The maxilla's 10 points are predicted by 40 independent models. Nothing guarantees that the predicted displacements are compatible with a rigid-body movement of the maxillary block; a post-processing step (a least-squares rigid fit on the predicted points) would be the natural complement, and it does not exist.

8. Environment

Everything runs inside Slicer's Python. check_dependencies() (SurgMovPred.py:156) is called on every click of Apply:

Confirmed bug

pip_install("numpy==2.4.0") runs unconditionally, on every click of Apply. Replacing numpy under a live Slicer session is exactly what breaks scipy's import elsewhere in the extension (Slicer's scipy is compiled against its numpy). By far the most dangerous point in the module, triggered by the main button.

Installation happens without conda, without GPU, without torch.

The CLI silences scikit-learn's InconsistentVersionWarning (SurgMovPred_CLI.py:19): the packages were serialized with scikit-learn 1.6.1 and are unpickled with whatever version happens to be installed. The comment accepts the risk ("models are tested for compatibility before being shipped").

9. Pitfalls and fragile points

  • pip_install("numpy==2.4.0") on every run. Replacing numpy under a live Slicer session is exactly what breaks scipy's import elsewhere in the extension (Slicer's scipy is compiled against its numpy). By far the most dangerous point in the module, and it's triggered by the main button.
  • Inoperative "test files" button: DownloadTestFiles() (SurgMovPred.py:763) does download TestFiles.zip, but only fills in the input/output fields if os.path.exists(.../V_FACE/DefaultList) — a copy-paste leftover from the VFACE module. Without VFACE's test data, the archive is downloaded and then ignored.
  • .ods advertised, odfpy not installed by check_dependencies (it is, however, installed by the Anonymizer module, which can mask the problem on a machine where both have been used).
  • A missing feature = a model silently skipped. The log says "Model 'X' skipped: missing N input feature(s)", but the output file itself simply ends up with one fewer column. A poorly named spreadsheet can produce a predictions_outputs.xlsx with zero prediction columns and no failure.
  • Blind concatenation of the input files: two spreadsheets with different columns give NaN, and model.predict on NaN raises — the error is caught per target, so the result comes out partial without much of it being visible.
  • Only one Excel sheet is read. A workbook whose first sheet isn't the data sheet produces an empty result.
  • 1.5 GB of models loaded systematically, even for a single row to predict, even if the operator only cares about one target.
  • No uncertainty on output even though one of the three base models is a Gaussian process.
  • No rigid consistency between the points of a given segment (§7).
  • The helpText, the parameter node's docstring, and process()'s argument names describe an entirely different tool (clinical-note summarization).

10. Literature

No paper covers SurgMovPred. Neither the repository, nor the release, nor the README cites any reference, and a search on the module's name returns nothing. The module isn't even listed in the extension's README.

The published context, not to be confused with a description of this code:

  • Machine-learning-based approach for predicting postoperative skeletal changes for orthognathic surgical planning (PubMed 35132764) — the problem posed is the same (predicting post-operative skeletal displacements from pre-operative measurements), but nothing indicates this is the work behind these weights.
  • Oliveira, Cevidanes, Bianchi et al., Artificial intelligence as a prediction tool for orthognathic surgery assessment, Orthodontics & Craniofacial Research, 2024 — same team (UNC/Pacific), but a different target: predicting the need for surgery from lateral cephalograms, not the movements themselves.
  • Prediction of orthognathic surgery plan from 3D cephalometric analysis via deep learning (PMC10024836) — same goal, deep-learning approach; SurgMovPred, meanwhile, is a classic tabular model.

The underlying tools, for their part, are documented: StackingRegressor and LightGBM.

Detailed bibliography, retrieved files, and links to visit: SOURCES.html — including the NA-MIC Project Week 45 (Boston, 2026) page devoted to this module, the only primary source found (2026_Buisson_NAMIC_PW45_surgery_movement.html).
