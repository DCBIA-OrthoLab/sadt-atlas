SurgMovPred

SurgMovPred predicts the post-operative movement of 28 landmark points from a table of measurements and a surgical plan. This page explains how, step by step, with the maths: what goes in, what each step does to it, and what comes out. The files, lines and pitfalls are on the code page; the VISOR port is on its own page.

Code (developers) unpublished SurgMovPred_CLI no conda: Slicer's own Python Bibliography VISOR

Overview: what goes in, what comes out

SurgMovPred predicts how far the bones will be moved in an orthognathic operation. It reads a table with one row per patient (cephalometric measurements before the operation, plus the planned movement) and writes a table of predicted post-operative movements: 28 landmark points, each with four values. It reads no scan or mesh and changes nothing in the Slicer scene.

SurgMovPred, legacy module
Inputa folder of CSV, XLSX or ODS tables, picked in the Slicer panel
Method112 trained models, one per target; each re-scales its 145 inputs and predicts with a stack of three regressors
Outputtwo tables with the same content, predictions_outputs.xlsx and .csv
Whereinside Slicer’s own Python, on the processor

This page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957). The VISOR port, which runs the same algorithm on a server, has its own page. File names, line numbers and pitfalls are on the code page.

1. Position in the pipeline

SurgMovPred is an isolated tool: nothing in the repository calls it and it calls nothing. Its input is a folder of spreadsheets and its output is another spreadsheet. The module is not wired into the Slicer scene: it is a launch interface on top of a pandas script.

In the codeThe pipeline diagram in the code, build state and leftover argument names

2. Files involved

The module is a Slicer panel (three folder selectors and four buttons) and a command-line script that holds all the processing. Only three folders are passed to the script: the input, the models and the output. Nothing else is configurable: no threshold, no choice of targets, no skeletal-class option.

In the codeThe file table and the parameters declared in the XML

3. Input and preprocessing

The script reads every spreadsheet in the input folder and stacks them one under the other (no sub-folders; for an Excel workbook only the first sheet is read). It then cleans the column names to the spelling used at training time, finds the patient identifier column by trying a list of usual names, and, right before prediction, scales the inputs.

Each model carries its own scaler, fitted on its training data. There is no imputation: a blank cell stays blank through the scaling, and the model then refuses it. The error is caught and logged, and that target disappears from the result for every patient, not only for the row with the blank. The only leniency about column names is the _T0 suffix: if the model expects X_T0 and the table has X, it is accepted. Any other missing column makes the whole model be skipped, with a warning, and its column is absent from the result.

In the codeThe reading function, the five cleaning rules, the identifier patterns and the scaler line

4. The models

The weights are not in the repository: the panel can download one archive of 112 model folders (about 740 MB) from a GitHub release. Pointing the model selector at the top folder loads all 112 models; pointing at a sub-folder loads only that one. All 112 are held in memory at once (about 1.5 GB), even for a single patient.

In the codeThe download address, the recursive search and the folder hierarchy that does not exist

4.1 Contents of a package

Each model file holds four things: the target’s name, the ordered list of 145 input columns, a fitted scaler and a fitted stacking model. These were read directly from two of the packages, without running them; the VISOR layout file says the same of the whole shipped set.

In the codeThe key table and the verification that was done

4.2 The architecture

There is no neural network. Each target is predicted by a stack of three base regressors, whose estimates are combined by a linear regression. The three are an ElasticNetCV (a linear model with a penalty chosen by cross-validation), a LightGBM (many small decision trees added one after the other) and a Gaussian process (a smooth curve fitted through the training points). Why these three were chosen is written nowhere in the repository: the training code is not there.

In the codeThe estimators and their readable parameters

4.3 The 145 features

The 145 inputs fall in four groups. 78 are positions of points measured against three reference planes (Frankfort horizontal, midsagittal and coronal); 24 of these are soft-tissue points, marked by an apostrophe in their names. 14 are other cephalometric measurements: angles, ratios and widths. The last 53 are occlusal measurements given twice: 28 as the state before the operation (names ending in _T0) and 25 as the planned total movement (ending in _Total), most of them in both sets. What the two sets mean exactly is documented nowhere in the repository; the reading that the model receives both the starting state and the planned outcome is an inference from the names.

In the codeThe family table with examples and the columns that are read and then ignored

4.4 What is predicted

112 targets are 28 structures times 4 components. Three components are the signed directions of a displacement (posterior or anterior, right or left, down), and the fourth is very likely its magnitude; the unit is written nowhere. The structures are points attached to a bone segment: 10 on the maxilla, 17 on the mandible and one for the genioplasty. What is predicted is thus the movement of each point on its own, not a rigid transform of the segment.

In the codeThe list of the 28 structures and the naming of the components

5. The core processing

For every package the script takes the model’s columns, scales them and predicts. There is no post-correction, no bounding, no consistency between targets and no confidence interval, although one of the three base regressors could give one. Each target has its own protection: a target that crashes does not stop the others, its column simply disappears.

In the codeThe full prediction loop

6. Outputs

The script writes two files with the same content: a table with the patient identifier, then one column per predicted target, named as in the model file. Both start with an unnamed numbering column. Nothing is reapplied to a scan, a mesh or the Slicer scene: the prediction stops at the spreadsheet, and the operator carries the values into their planning software.

8. Environment

Everything runs in Slicer’s own Python, with no conda, no graphics card and no torch. Every click on Apply checks and installs the needed Python packages, and forces a fixed numpy version, whatever the other modules of the extension need; the code page gives the details. On macOS an extra library is downloaded for LightGBM.

In the codeThe package list, the numpy pin and the macOS step

9. Known issues

  • The numpy version is set to 2.4.0 on every Apply, in the same Python that other modules of the extension set to numpy 1.26.4. See the details.
  • The test-files button downloads a table archive and then ignores it unless another module’s data is present; it also downloads the models. See the list.
  • ODS files are advertised but the reader package is not installed by the module. See the list.
  • A missing input column silently removes a target from the result. See the list.
  • Spreadsheets with different columns are concatenated blindly (a blank cell then drops the whole target), and only the first Excel sheet is read. See the list.
  • Targets are predicted independently, so the points of one bone segment need not move consistently. See the pitfall.
  • No uncertainty is given, and nothing is applied to the scene. See the pitfall.
