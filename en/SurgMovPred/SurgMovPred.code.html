SurgMovPred, legacy: the code

For developers: what the legacy SurgMovPred module does in the code, with file:line references, code, arguments, environment and pitfalls. The readable explanation with the maths is on the atlas page.

Code Atlas (explanation) unpublished SurgMovPred_CLI no conda: Slicer's own Python Bibliography VISOR

Prediction of the surgical movements of an orthognathic surgery from a spreadsheet of cephalometric measurements. No neural network, no image, no mesh: 112 stacked scikit-learn regressors, one per value to predict, applied row by row to an Excel/CSV file.

Two code bases

Everything numbered below describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The VISOR port, which runs the same tool on a server, is described on its VISOR page. The port is on the main branch of SADT-VISOR and keeps the same algorithm.

1. Position in the pipeline

Plain-language explanation and maths: atlas page.

Isolated tool. Nothing in the repository calls it, and it calls nothing in the repository: it reads no volume, no mesh, no landmarks. Its input is a folder of spreadsheets, its output another spreadsheet.

CalledHow
SurgMovPred_CLIslicer.cli.run(slicer.modules.surgmovpred_cli, …) (SurgMovPred.py:847)

The module isn't wired into the MRML scene: no vtkMRMLNode is created, read or transformed. It's a launch interface sitting on top of a pandas script.

Build state (legacy only)

The module is built with the extension: the root CMakeLists.txt has add_subdirectory(SurgMovPred) and add_subdirectory(SurgMovPred_CLI) (CMakeLists.txt:60-61), and SurgMovPred/CMakeLists.txt calls slicerMacroBuildScriptedModule with the icon and SurgMovPred.ui. The interface text now describes this tool: the helpText says "Predicts surgical movement targets from a table of patient measurements" (SurgMovPred.py:233) and the parameter node documents inputFolder, modelPath and outputFolder (SurgMovPred.py:250). The notes-summarization wording copied from CNE/MedX is gone.

Legacy (3c67957). The module was not always in the tree: commit 34d496f (2026-09-17, "Drop MedX and SurgMovPred, kept on archive branches, from the working tree") removed it, and dbc9810 and 7947b68 (2026-10-12) restored it. The branch archive/surgmovpred, local and on origin, points at fbfa0fb, the parent of the removal; fbfa0fb is an ancestor of 3c67957. The VISOR client builds its own module instead: VISOR:AutomatedDentalToolsRemote CMakeLists.txt:45 adds SurgMovPredRemote.

Remaining leftover (legacy only)

SurgMovPredLogic.process() still names its arguments notesFolder_input / notesFolder_output (SurgMovPred.py:815); its docstring now says so and defers the renaming, because every caller passes them positionally.

Legacy (3c67957); not present in VISOR, which has no SurgMovPredLogic: the entry point is run(measurements, output_dir, model) (VISOR:SADT-VISOR tools/Surg_Mov_Pred/src/sadt_surgmovpred/__init__.py:37-46).

3. Input and preprocessing

Plain-language explanation and maths: atlas page.

Accepted format. load_data_from_directory() (SurgMovPred_CLI.py:143) collects every *.csv, *.xlsx, *.ods file in the folder (extension in lowercase and uppercase), reads them (read_csv, read_excel, read_excel(engine='odf')) and concatenates them (pd.concat(..., ignore_index=True)). No recursion into subfolders. For an Excel workbook, only the first sheet is read: the official test file contains seven (all_data, demographics, Invivo_ceph, surgical_mov, dolp_ceph_T0, dolp_ceph_T1, dolp_ceph_total), and it's all_data that sits in first position. A file that cannot be read is logged and skipped (SurgMovPred_CLI.py:181-182); the run fails only if no file at all could be read (:184-185).

Column-name normalization, clean_name() (SurgMovPred_CLI.py:41), applied on input to fall back onto the spelling used at training time:

  1. removal of ", \, [, ];
  2. any character outside [0-9a-zA-Z_'] becomes _, the apostrophe is deliberately kept (code comment: for Jarabak's and SM_A'_CP);
  3. collapsing of repeated _, trimmed at both ends;
  4. "total" → "Total";
  5. f_ prefix if the name starts with a digit.

This cleanup explains the actual feature names: SM-A-FH   (with two trailing spaces, in the test file) becomes SM_A_FH, Jarabak's ratio   becomes Jarabak's_ratio, FMA(MP-FH) Ang_2D becomes FMA_MP_FH_Ang_2D.

Patient identifier. find_id_column() (SurgMovPred_CLI.py:83) tests 8 case-insensitive patterns (#, id, patient id, patient number, subject, …) then, as a last resort, any column containing both "patient" and "id". In the test file, the column is #. On failure, the output column IDPatient is filled with pd.NA with a plain warning.

Value normalization. Each model package carries its own StandardScaler computed (centering + scaling, with_mean=True, with_std=True), applied right before prediction (SurgMovPred_CLI.py:239). No imputation: a missing value reaches the scaler as NaN and leaves it as NaN, and model.predict then raises (SurgMovPred_CLI.py:243), so the target is dropped for all rows (see the note below). Evidence: the packages hold an ElasticNetCV (strings of the pickle), and a stand-in stack of ElasticNetCV + GaussianProcessRegressor + LinearRegression, run on a current scikit-learn, raised ValueError: Input X contains NaN. The real packages were not run.

Tolerance on the _T0 suffix (SurgMovPred_CLI.py:225): if the model expects X_T0 and the column is named X, it is accepted.

Note

This is the only leniency; any other missing feature makes the entire model get skipped with a warning, and the corresponding column is absent from the result.

Also true in VISOR: same _T0 tolerance and same skip (VISOR:SADT-VISOR tools/Surg_Mov_Pred/src/sadt_surgmovpred/pipeline.py:229,235). One difference: if no model at all can predict, VISOR raises an error instead of writing tables without predictions (pipeline.py:260).

A blank cell removes the whole target

All rows go to model.predict in one call (SurgMovPred_CLI.py:243), so one NaN in any row of the columns a model needs makes that call raise; the try/except at :245-246 logs it and the target gets no column, for every patient. This also happens when spreadsheets with different columns are concatenated (:187). VISOR runs the same code (pipeline.py:243-250). Evidence as in section 3: the pickle holds an ElasticNetCV, and a stand-in stack raised on NaN; the shipped packages were not run.

4. The models

Plain-language explanation and maths: atlas page.

The weights are not in the repository. onDownloadDefaultModel() (SurgMovPred.py:782) downloads and unzips:

https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/SurgMovPred/all_models.zip
  -> Documents/SlicerDownloads/SurgMovPred/Models/all_models/

About 740 MB (740 183 656 bytes, i.e. 706 MiB; the size is from the same release file in the VISOR data manifest, VISOR-serve scripts/data-manifest.yml:96-98), 112 folders, one stacking_package.pkl of ~13 MB each. load_all_model_packages() does a recursive Path.glob("**/stacking_package.pkl") and indexes by package['target_name']: pointing the selector at all_models/ loads all 112 models, pointing at a subfolder loads only one. The CLI's help text and a comment (SurgMovPred_CLI.py:284, SurgMovPred_CLI.py:320) mention saved_models/class_1, saved_models/class_None folders: this hierarchy by skeletal class does not exist in the published archive, which is flat.

4.1 Contents of a package

Plain-language explanation and maths: atlas page.

Each .pkl is a four-key joblib dict, used as-is by SurgMovPred_CLI.py:214-216:

KeyContent
target_nametarget name, e.g. Mx_ALL_APoint_P-/A+_Pred (raw form, with -, /, +)
features_namesordered list of 145 feature names
scalerfitted sklearn.preprocessing.StandardScaler
modelfitted sklearn.ensemble.StackingRegressor
Verified

This information was read directly from all_models/Mn_MB_Genioplasty_Total_Pred/stacking_package.pkl and all_models/Mx_ALL_APoint_P-_A_Pred/stacking_package.pkl (pickle-stream inspection, without execution). The 145 features are identical in both packages; nothing formally guarantees the same holds for the other 110, but their near-identical sizes (13.17–13.19 MB) strongly suggest it.

VISOR's layout file says the same of the shipped set: each of the 112 packages asks for the same 145 columns (VISOR:SADT-VISOR tools/Surg_Mov_Pred/src/sadt_surgmovpred/layout.py:18-23). That count is a code comment; the packages were not unpickled again for this page.

4.2 The architecture

Plain-language explanation and maths: atlas page.

No network. A stacking ensemble of three base regressors and one linear meta-regressor, serialized with _sklearn_version = 1.6.1:

RoleEstimatorParameters readable in the pickle
base multitask_elasticnetElasticNetCVgrid of l1_ratio, n_alphas, eps, selection='cyclic'
base lgbmlightgbm.sklearn.LGBMRegressorboosting_type='gbdt', objective='regression', num_leaves=31
base gaussian_processGaussianProcessRegressorkernel Product(ConstantKernel, RBF), optimizer='fmin_l_bfgs_b', normalize_y
metaLinearRegressionstack_method='predict', passthrough=False

passthrough=False means the meta-model sees only the three base models' predictions, not the 145 original features. stack_method='predict': one scalar value per base model, hence a three-input linear regression.

The file's dominant weight (13 MB for 145 features) comes from the GaussianProcessRegressor, which keeps its training matrix, and from the LightGBM booster.

Training is not in the repository: no script, no dataset, no metrics, no seed. Not determinable from the repository: cohort size, validation protocol, per-target performance.

4.3 The 145 features

Plain-language explanation and maths: atlas page.

Four groups, counted by reading the 145 names in Mn_ALL_BPoint_Down_Pred/stacking_package.pkl (strings of the pickle, nothing run) and cross-checked against the all_data sheet of the test file:

GroupCountExamples
Point positions relative to the three reference planes: FH (Frankfort horizontal, 26), MSP (midsagittal plane, 30), CP (coronal plane, 22). 24 of them are soft-tissue points, marked by an apostrophe, and are part of this count. 78 SM_A_FH, SM_GoL_MSP, SM_PNS_CP, SM_N'_FH, SM_Sn'_MSP
Other cephalometric measurements: angles, ratios and widths 14 SNA, SM_ANB_signed, SM_Witts, LAFH, Jarabak's_ratio, UAFH_LAFH, FMA_MP_FH_Ang_2D, SM_Mx_Width
Occlusal and dental measurements, suffix _T0 28 MxMn_Overjet_R_T0, MxMn_Molar_Relationship_L_T0
Occlusal and dental measurements, suffix _Total 25 MxMn_Overjet_R_Total, Mn_Gonions_to_Midline_Distances_R_Total

78 + 14 + 28 + 25 = 145. 24 base names exist in both the _T0 and the _Total set; 4 exist only as _T0 (the two molar relationships and the two left-side midline distances of the lower canines and first molars) and 1 only as _Total (the left upper canine vertical distance). VISOR's layout.py:19-22 says 82 landmark-to-plane distances, 28 _T0 and 25 _Total: the 82 is the 78 above plus the four other SM_ names (SM_ANB_signed, SM_Witts, SM_Mx_Width, SM_Mn_Width), which this page counts among the 14.

What exactly the two _T0 / _Total sets mean is documented nowhere in the repository. The naming (T0 = before, Total = total variation) and the fact that both are on the input side suggest the model receives the pre-surgical state and the targeted occlusal outcome, in order to infer the bone displacements to be carried out: this is an inference, not a claim made by the code.

The columns Gender, Surg, Genio, 3piece, assymetry, Skl_Cl_2 from the test file do not appear among the 145 features of the two inspected packages: they are read and then ignored.

4.4 What is predicted

Plain-language explanation and maths: atlas page.

112 targets = 28 structures × 4 components.

Components, based on target names: P-/A+ (posterior negative / anterior positive), R-/L+ (right negative / left positive), Down+ (vertical, down positive), and Total. The first three are therefore the signed components of a displacement vector in the cephalometric frame (CP, MSP, FH), the fourth very likely its magnitude: inferred from the naming, the unit (mm) is written nowhere.

The 28 structures:

SegmentPoints
Maxilla, Mx_ALL_* (10)APoint, ANS, PNS, U3CanineTip L/R, U6MesialCuspTip L/R, UpperIncisorTip L/R, UpperIncisorTipMidpoint
Mandible, Mn_ALL_* (17)BPoint, Gnathion, Menton, Pogonion, Gonion L/R, ChinSideCut L/R, MandibleBackCut L/R, L3CanineTip L/R, L6MesialCuspTip L/R, LowerIncisorTip L/R, LowerIncisorTipMidpoint
Genioplasty, Mn_MB_Genioplasty (1)–

ALL designates the entire bone segment (maxilla or mandible mobilized as a block), MB the genioplasty segment. What is predicted, then, is the displacement of landmark points rigidly attached to each segment, predicted, not a rigid transform: nothing forces the maxilla's 10 points to be consistent with one another (see §7).

5. The core processing

Plain-language explanation and maths: atlas page.

predict_all_targets() (SurgMovPred_CLI.py:196), in full:

for target_name, pack in packages.items():
    X_target = df_cleaned[[feature_source[f] for f in pack['features_names']]]
    X_target.columns = pack['features_names']
    X_scaled = pack['scaler'].transform(X_target)
    predictions_by_target[target_name] = pack['model'].predict(
        pd.DataFrame(X_scaled, columns=..., index=df_cleaned.index))

No post-correction, no bounding, no inter-target consistency, no confidence interval: the GaussianProcessRegressor can produce a standard deviation, it isn't asked to. Each target is handled independently, with a try/except per target: a target that crashes doesn't interrupt the others, its column simply disappears.

All 112 models are loaded into memory at once (load_all_model_packages), i.e. ~1.5 GB of RAM before the data is even read.

6. Outputs

Plain-language explanation and maths: atlas page.

save_results() writes two files, same content, into the output folder:

FileContent
predictions_outputs.xlsxone row per input patient, IDPatient column then one column per predicted target
predictions_outputs.csvsame

index=True in both cases: the pandas index (0, 1, 2…) becomes an unnamed column. Column names are the packages' raw target_name, so with / and + (Mx_ALL_APoint_P-/A+_Pred).

The panel's helpText says the module "writes one result table per input file" (SurgMovPred.py:235-237). The CLI does not: it concatenates all input files first (SurgMovPred_CLI.py:187) and writes one table (:264-269).

Pitfall

There is no reapplication of the result whatsoever. Nothing builds a matrix, moves a mesh, creates a Slicer node, or opens a view: the prediction stops at the spreadsheet. The question "how is the prediction reapplied to produce a visualizable result" has no answer in this repository: it's up to the operator to carry the values into their planning software.

Also true in VISOR: the tool returns the two tables only (VISOR:SADT-VISOR tools/Surg_Mov_Pred/src/sadt_surgmovpred/pipeline.py:276-287), and its client saves the result without loading anything (RESULT_KIND = "save_as", VISOR:AutomatedDentalToolsRemote SurgMovPredRemote/SurgMovPredRemote.py:46).

7. What is predicted vs. what is computed

Plain-language explanation and maths: atlas page.

BlockNatureWhere
Column-name cleanup, ID detectioncomputed deterministic (regex)CLI
Standardizationcomputed learned StandardScalerCLI
Prediction of the 112 displacementspredicted stacking ElasticNetCV + LightGBM + GP, meta LinearRegressionCLI, CPU
Consolidation into a single segment transformnonexistent–
Pitfall

The maxilla's 10 points are predicted by 40 independent models. Nothing guarantees that the predicted displacements are compatible with a rigid-body movement of the maxillary block; a post-processing step (a least-squares rigid fit on the predicted points) would be the natural complement, and it does not exist.

Also true in VISOR: each target is its own model.predict call (VISOR:SADT-VISOR tools/Surg_Mov_Pred/src/sadt_surgmovpred/pipeline.py:216-247).

8. Environment

Plain-language explanation and maths: atlas page.

Everything runs inside Slicer's Python. check_dependencies() (SurgMovPred.py:153) is called on every click of Apply:

ItemValue
Packagespandas, joblib, openpyxl, scikit-learn, lightgbm
Missing from the listodfpy, yet needed by read_excel(engine='odf') for the advertised .ods files
numpyslicer.util.pip_install("numpy==2.4.0") unconditional, on every Apply
macOSensure_mac_openmp() downloads libomp.dylib from mac.r-project.org and drops it into Slicer's cli-modules folder, then loads it with RTLD_GLOBAL: LightGBM needs it
CompilationCC=gcc / CXX=g++ forced during pip_install, restored afterward
Unconditional numpy pin that other modules undo (legacy only)

Legacy (3c67957); not present in VISOR, where the tool has its own virtual environment pinned to numpy 2.2.6 and no install happens at run time (VISOR:SADT-VISOR tools/Surg_Mov_Pred/pyproject.toml:14; the 2.4.0 pin was deliberately not adopted, VISOR:SADT-VISOR tools/Surg_Mov_Pred/README.md:76-80).

onApplyButton calls check_dependencies() first (SurgMovPred.py:412), and that function runs slicer.util.pip_install("numpy==2.4.0") on every click, before looking at what is installed (SurgMovPred.py:171). Other modules of the same extension push numpy the other way: AMASSS installs 1.26.4 when numpy is missing or 2.x (AMASSS/AMASSS.py:53,74-76), VFACE does the same when torch needs numpy 1.x (VFACE/VFACE.py:107,148-158), and MRI2CBCT installs 1.26.4 whenever the version differs (MRI2CBCT/MRI2CBCT.py:625-626, MRI2CBCT_core/requirements.py:21). In one Slicer session, using SurgMovPred and one of those modules moves numpy between 2.4.0 and 1.26.4.

Not proved here: that this breaks scipy or another package. The code shows the conflict of pins, not a failure; the VISOR README only says upstream pins 2.4.0 "because Slicer's shared interpreter needs it for other reasons" (VISOR:SADT-VISOR tools/Surg_Mov_Pred/README.md:78-79).

Installation happens without conda, without GPU, without torch.

The CLI silences scikit-learn's InconsistentVersionWarning (SurgMovPred_CLI.py:19): the packages were serialized with scikit-learn 1.6.1 and are unpickled with whatever version happens to be installed. The comment accepts the risk ("models are tested for compatibility before being shipped").

9. Pitfalls and fragile points

Plain-language explanation and maths: atlas page.

  • pip_install("numpy==2.4.0") on every run. Other modules of the extension install numpy 1.26.4 (AMASSS, VFACE, MRI2CBCT), so the version can swing between the two within one Slicer session. Whether that breaks anything was not tested (details).
  • "Test files" button half-inoperative: DownloadTestFiles() (SurgMovPred.py:763) does download TestFiles.zip, but only fills in the input/output fields if os.path.exists(.../V_FACE/DefaultList) (:773), a copy-paste leftover from the VFACE module. Without VFACE's test data, the archive is downloaded and then ignored. The same button then calls onDownloadDefaultModel() (:780), so it also downloads the 740 MB of models and fills the model field.
  • .ods advertised, odfpy not installed by check_dependencies (it is, however, installed by the Anonymizer module, Medical_Data_Anonymizer_Module.py:411, which can mask the problem on a machine where both have been used).
  • A missing feature = a model silently skipped. The log says "Model 'X' skipped: missing N input feature(s)", but the output file itself simply ends up with one fewer column. A poorly named spreadsheet can produce a predictions_outputs.xlsx with zero prediction columns and no failure.
  • Blind concatenation of the input files: two spreadsheets with different columns give NaN in the columns one of them lacks, and model.predict on NaN raises; the error is caught per target, so those targets vanish for every patient (note) and the result comes out partial without much of it being visible.
  • Only one Excel sheet is read. A workbook whose first sheet isn't the data sheet produces an empty result.
  • 1.5 GB of models loaded systematically, even for a single row to predict, even if the operator only cares about one target.
  • No uncertainty on output even though one of the three base models is a Gaussian process.
  • No rigid consistency between the points of a given segment (§7).
  • process() still names its arguments notesFolder_input / notesFolder_output (SurgMovPred.py:815), a leftover from the clinical-notes tool; the helpText and the parameter node's docstring were rewritten and no longer carry it.

10. Literature

Plain-language explanation and maths: atlas page.

No paper covers SurgMovPred. Neither the repository, nor the release, nor the README cites any reference, and a search on the module's name returns nothing. The module isn't even listed in the extension's README.

The published context, not to be confused with a description of this code:

  • Machine-learning-based approach for predicting postoperative skeletal changes for orthognathic surgical planning (PubMed 35132764): the problem posed is the same (predicting post-operative skeletal displacements from pre-operative measurements), but nothing indicates this is the work behind these weights.
  • Oliveira, Cevidanes, Bianchi et al., Artificial intelligence as a prediction tool for orthognathic surgery assessment, Orthodontics & Craniofacial Research, 2024, same team (UNC/Pacific), but a different target: predicting the need for surgery from lateral cephalograms, not the movements themselves.
  • Prediction of orthognathic surgery plan from 3D cephalometric analysis via deep learning (PMC10024836): same goal, deep-learning approach; SurgMovPred, meanwhile, is a classic tabular model.

The underlying tools, for their part, are documented: StackingRegressor and LightGBM.

Detailed bibliography, retrieved files, and links to visit: SOURCES.html, including the NA-MIC Project Week 45 (Boston, 2026) page devoted to this module, the only primary source found (2026_Buisson_NAMIC_PW45_surgery_movement.html).
