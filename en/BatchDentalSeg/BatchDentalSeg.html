BatchDentalSeg

BatchDentalSeg labels the teeth and jaws of CT and CBCT scans in a batch, with one multi-label network that gives every voxel its label in a single pass. This page explains the module step by step, with the maths of the parts that are computation rather than learning: how the scan is normalised, how the network’s patches are blended, how the memory is estimated, how a scan is cropped and how left and right are corrected. Where the code does something worth checking, a link leads to the code page.

Code (developers) Dot 2024 · J Dent BATCHDENTALSEG nnUNetv2_predict no conda: Slicer's Python + nnunetv2 VISOR Bibliography

Overview: what goes in, what comes out

BatchDentalSeg takes CT or CBCT scans of the head and labels the teeth and jaws in each one. A single 3D network looks at the whole scan and gives every voxel a label in one pass: it is not one network per structure, as in AMASSS. The module itself is a queue around that network: it chooses the model, guards the memory, restores the geometry and writes the exports.

InWhat happensOut
a folder of scans (.nii, .nii.gz, .gipl, .gipl.gz), and one of four modelseach scan goes through nnU-Net, one scan at a time; the label map is put back on the scan’s own grida label map per scan (<scan>_Segmentation.nii.gz), and optionally STL, OBJ, VTK, glTF or one NIfTI file per segment

This page describes the legacy Slicer module (SlicerAutomatedDentalTools at 3c67957, 2026-10-26). The server port is BatchDentalSeg on VISOR.

1. Where it sits in the pipeline

No other module of the repository calls BatchDentalSeg, and it calls none: it is a terminal tool. It depends on an external Slicer extension, NNUNet, for installing nnU-Net, checking the model folder and running the prediction as a child process. It is a batch variant of DentalSegmentator, from which it reuses the widget, the icons and the weight download.

In the codeThe table of classes called from the NNUNet extension

2. Files involved

Most of the code is one widget file of about 3000 lines: the interface, the queue, the model choice, the memory guard, the crop, the labels and the exports. A small queue file keeps the list of scans on disk, and a checker downloads and refreshes the DentalSegmentator weights. Everything runs in Slicer’s Python; nnU-Net itself is launched as a child process, one scan at a time. The weights arrive at run time.

In the codeThe file table with line counts, and what the build file installs

3. Inputs, folder traversal, naming

3.1 What is accepted

A folder is listed without going into sub-folders, for four patterns: .nii, .nii.gz, .gipl, .gipl.gz. NRRD, Slicer’s default format, is not recognised.

3.2 The queue

One entry is one scan, not one folder, so several folders with different models can be stacked in the same session. A scan is skipped if its result already exists or if it is already queued. The state of the queue is rewritten after each scan, so a session killed mid-inference resumes where it stopped. Every five scans (by default) a clean-up releases the graphics card and the memory.

3.3 What the network actually sees

The widget preprocesses nothing: it exports the scan as a NIfTI file and everything else is nnU-Net’s. nnU-Net reorders the scan along the axes the plan asks for, crops it to the region that is not zero, normalises the intensities and only then resamples it to the plan’s spacing (the order of nnU-Net’s own code, checked in version 2.8.1; the version a legacy install runs is not recorded). The normalisation shown below is the one DentalSegmentator’s plan declares; for the three other models see section 4.3.

Only the plan of DentalSegmentator can be read in the repositories (in the legacy one): percentiles −110 and 3067, mean 1274, standard deviation 558. The three other bundles bring their own plan file, so for them this recipe is assumed, not checked.

The only preprocessing written in this repository is the optional automatic crop (section 5.2), reserved for a replay after a memory failure.

In the codeThe glob, the queue item, persistence and the clean-up cycle

4. The four models

4.1 What the combo box selects

The four entries run the same code: a prediction request is built with fold 0 and the chosen device, and only the weights folder and the label table change. The three variants (pediatric, naso-maxilla and universal) are downloaded as three files each; DentalSegmentator comes as the zip of the latest release of its repository. The downloads have no checksum and no resume, so an interrupted download leaves a truncated checkpoint that the next run takes for a complete one.

In the codeThe four branches, the download paths and the checkpoint check

4.2 nnU-Net, verified in the code

It is really nnU-Net v2: the command it builds names the dataset, the trainer, the plan and the configuration (3D full resolution), one fold (a single trained copy of the model), a step of 0.5 (each patch moves by at most half its size), no test-time mirroring (no averaging over flipped copies of the scan). The only setting the interface offers is the device (cuda, cpu or mps). Fold 0 only, never an ensemble.

In the codeThe command line, the defaults and the process-wide environment variables

4.3 Architecture and plan: what is verifiable

Only the DentalSegmentator bundle ships its plan files in the repository: a plain convolutional 3D U-Net with six stages (32 features at the first, 320 at the last), patches of 128 × 160 × 112 voxels, a spacing of about 0.45 × 0.31 × 0.45 mm, a batch of 2 and CT normalisation. The plans of the other three models arrive with their download, so nothing more can be said about them from the code.

In the codeThe plan summary and the format notes

4.4 The labels produced, per model

A table in the widget decides the values written into the output file. The first two models share the same five labels and differ only in what they were trained on (permanent against mixed dentition).

ModelLabelsWhat they are
DentalSegmentator51 Upper skull (maxilla included), 2 Mandible, 3 Upper teeth, 4 Lower teeth, 5 Mandibular canal; permanent dentition
PediatricDentalsegmentator5the same table; mixed dentition
NasoMaxillaDentSeg61 Upper skull, 2 Mandible, 3 Maxilla, 4 Upper teeth, 5 Lower teeth, 6 Mandibular canal
UniversalLabDentalsegmentator551 to 32 the permanent teeth one by one (Universal numbering), 33 to 52 the primary teeth, 53 Mandible, 54 Maxilla, 55 Mandibular canal; no “Upper skull”

The UniversalLab model does not segment the cranial vault, contrary to its description in the interface and to the README (see pitfalls).

In the codeThe label function, the segment tags and the UniversalLab numbering

5. The non-learned core

5.1 Label map reconstruction and geometry restoration

The segmentation is turned into one label map in a single export, then remapped to the official values with a lookup table in one pass. The earlier version rasterised the full volume once per segment: 55 times for UniversalLab on a full-mouth CBCT.

In the codeThe single export and the lookup table

5.2 Automatic crop (replay after memory failure)

The cropped sub-volume keeps its spacing and axes, only its origin moves, and nothing is interpolated. After the prediction, the label map is pasted back into an array of the original size by a simple offset, so the output is always on the grid of the scan as acquired.

In the codeThe crop function, its constants and the paste-back

5.3 Memory guard: three lines of defense

The code comment gives the real case: a scan filled 114 GB on a 125 GB machine, was killed by the system, and left its workers alive holding the memory. Hence three lines of defence, one per moment of the process: an estimate before launching, a monitor during the run, and a recovery after it.

During the run, memory is sampled every 3 seconds and two consecutive overruns are needed to kill the process, so that a transient spike does not condemn a good scan. The whole process tree is killed, not only the direct child, because nnU-Net starts workers of its own, and orphan processes are swept up.

In the codeThe estimate, the sampler, the process-tree kill and the stray sweep

5.4 Fallback completion detection

When nnU-Net prints its “done” line, a timer watches the output file’s size, and two equal readings force the finish even if the process never signalled it; it gives up after 60 seconds. Each scan also has a watchdog (60 minutes by default) that marks it failed and moves on.

In the codeThe fallback timer and the per-scan watchdog

5.5 Mirror correction (UniversalLab only)

If one of the four incisors is missing, the correction is refused. The result goes into a new node, <name>_Mirrored, and the original is kept.

In the codeThe mirror function, the label dictionary and the plane computation

5.6 Missing post-processing

No morphological cleanup is applied: what comes out is nnU-Net’s raw output, with its own internal post-processing if the bundle ships one. Two island-removal functions exist but nothing calls them.

In the codeThe dead functions and what is left

6. Outputs

Whatever formats are ticked, the module always writes <scan>_Segmentation.nii.gz, a label map on the geometry of the original volume. This is also the file the queue looks for to decide that a scan is already done. Other formats go into the same folder:

  • STL, OBJ: one file per segment.
  • VTK per label: one file per label, cleaned, smoothed (60 windowed-sinc iterations), reduced by 40 % and flipped from RAS to LPS.
  • VTK merged: one file with every label, built the same way, with a constant label array.
  • NIfTI per segment: one binary file per segment, not to be confused with the label map above.
  • glTF: through the SlicerOpenAnatomy extension, with an adjustable decimation (0.9 by default).

A mesh export failure does not fail the scan: the NIfTI is already written, and the scan is marked done with a warning.

In the codeThe output table with every function and filter

7. What is predicted vs what is computed

BlockNature
Reordering, crop to non-zero, intensity normalisation, resampling (in this order)computed deterministic, driven by the plan
Segmentationpredicted 3D U-Net, one fold, no mirroring at test time
Automatic cropcomputed air threshold and bounding box
Restoration onto the original gridcomputed an index offset, no interpolation
Label map reconstructioncomputed one export and a lookup table
Mirror correctioncomputed a sagittal plane through the incisors
Meshescomputed marching cubes, smoothing, decimation
Memory estimate and guardcomputed arithmetic on the scan and the plan

The only learning is that of the four checkpoints, outside this repository.

In the codeThe same table with where each block runs

8. Environment

Libraries are installed once per session, at the first Apply: torch (the build matching the detected driver, no version pinned), NumPy below 2 because current torch wheels are built against NumPy 1, psutil, and nnU-Net through the NNUNet extension, which must be installed by hand. No conda, no WSL. A graphics card is optional, but the fallback message speaks of about an hour per scan on the CPU.

In the codeThe install sequence step by step

9. Pitfalls and fragile points

Each point is checked in the code and described, with its evidence, on the code page.

  • NasoMaxillaDentSeg segments are renamed wrongly: the last four get the wrong name, colour and opacity, and the mandibular canal can be lost from the output. Evidence.
  • UniversalLab is described as segmenting the cranial vault in the interface and README, but it has no such label. Evidence.
  • Downloading the DentalSegmentator weights wipes out the other three models. Evidence.
  • The release is resolved fragilely and no download is checked: the first asset of the latest release, no checksum. Evidence.
  • NRRD is not read and sub-folders are not walked; two scans of the same name overwrite the same result. Evidence.
  • A single fold, never an ensemble: extra folds in a bundle are ignored. Evidence.
  • The environment variables that point nnU-Net at the model are set for the whole Slicer process, harmless here only because the queue is sequential. Evidence.
  • Dead code: the island-removal and post-processing functions are never called. Evidence.
  • The install list is incomplete in the build file: only part of the model folder is listed. Evidence.
In the codeEvery pitfall with file and line

10. Literature

DentalSegmentator is published: Dot G. et al., DentalSegmentator: robust open source deep learning-based CT and CBCT image segmentation, Journal of Dentistry 147:105130, 2024 (doi:10.1016/j.jdent.2024.105130). It uses nnU-Net v2, with 470 CT and CBCT scans from 7 institutions for training and a hold-out test of 256 scans, with a Dice of 92.2 ± 6.3 % internally and 94.2 ± 7.4 % externally. On this model, code and paper agree. The methodological foundation is Isensee et al., nnU-Net, Nature Methods 18(2):203-211, 2021.

The three variants are not attached to any publication in the repository. The README announces 513 CBCT scans in mixed dentition for two of them and 135 scans for the third, with no reference and no test set: these figures are internal claims until a publication covers them. The full text of the references is on the code page and in SOURCES.md.
