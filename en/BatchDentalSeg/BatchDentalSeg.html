BatchDentalSeg

Queue that drives nnUNetv2_predict over a batch of CT/CBCT scans, with four interchangeable weight bundles — DentalSegmentator and its three variants — plus all the guard-rail, geometry-restoration, and export work around them.

Dot 2024 · J Dent BATCHDENTALSEG nnUNetv2_predict no conda — Slicer's Python + nnunetv2 Bibliography

Batch dento-maxillofacial segmentation of CT/CBCT scans. The module is not a network: it is a queue and an orchestrator around nnUNetv2_predict, with four interchangeable weight bundles. All the learning happens outside this repository; what is written here is the model choice, the memory guard-rails, the geometry restoration, and the exports.

1. Where it sits in the pipeline

No other module in the repository calls BatchDentalSeg, and BatchDentalSeg does not call any other module in the repository. It is a terminal tool. It does, however, depend on an external Slicer extension, NNUNet (SlicerNNUNetLib), from which it uses three classes.

CalledOriginRole
SlicerNNUNetLib.InstallLogicNNUNet extensionsetupPythonRequirements(): installs nnunetv2 in Slicer's Python
SlicerNNUNetLib.ParameterNNUNet extensionvalidates the model directory tree and builds the command line
SlicerNNUNetLib.SegmentationLogicNNUNet extensionwrites the volume as NIfTI into a temporary folder, launches nnUNetv2_predict as a QProcess, reloads the segmentation
OpenAnatomyExportSlicerOpenAnatomy extensionglTF export only; installed on the fly if absent

The module is a batch variant of DentalSegmentator (extension gaudot/SlicerDentalSegmentator), from which it reuses the widget, the icons, and the weight-download mechanism. The contributors declared in BATCHDENTALSEG.py:30 mix the original team (Dot, Gajny, Fenioux, Pelletier) with the UoM addition (Tulissi).

Everything runs inside Slicer's Python. nnUNetv2_predict is launched as a child process (QProcess), one scan at a time — unlike AMASSS, which calls the nnU-Net Python API in-process.

Resources/ML is not listed in MODULE_PYTHON_RESOURCES of CMakeLists.txt: in an installed extension, the folder is created entirely at runtime. The .pth files are .gitignored.

3. Inputs, folder traversal, naming

3.1 What is accepted

listVolumes() (Queue.py:28) does a non-recursive glob over four patterns: *.nii, *.nii.gz, *.gipl, *.gipl.gz. Subfolders are not visited, and NRRD is not recognized — Slicer's default format, and a format the repository's other modules commonly produce.

volumeStem() strips the compound suffix: case01.nii.gz → case01 (a Path.stem would leave case01.nii).

3.2 The queue

One entry = one scan, not one folder (QueueItem, Queue.py:52): inputPath, outputDir, model, device, status, error, durationSec, autoCrop. Several folders with different models can therefore be stacked in the same session.

addFolder() skips a scan if <outputDir>/<stem>_Segmentation.nii.gz already exists (the Skip scans already segmented checkbox, checked by default) or if it is already in the queue.

Persistence: the state is rewritten after each scan into <outputDir>/.batchdentalseg_queue.json. On reload, a scan left in running (Slicer killed mid-inference) is rewound to pending and the index goes back to it.

isChunkBoundary(): every chunkSize scans (default 5), _coolDown() does a deep cleanup — removes orphan nodes, torch.cuda.empty_cache() + ipc_collect(), gc.collect().

3.3 What the network actually sees

The widget does not preprocess anything. SegmentationLogic._prepareInferenceDir() does a slicer.util.exportNode(volumeNode, <tmp>/input/volume_0000.nii.gz), and all of the preprocessing is nnU-Net's: transposition per transpose_forward, resampling to the plan's spacing, CTNormalization (clip to the 0.5% / 99.5% percentiles of the training set, then standardization by its mean and standard deviation).

The only preprocessing written in this repository is the automatic crop (§5.2), and it is optional, reserved for replay after a memory failure.

4. The four models

4.1 What the combo box selects

onApplyClickedForVolume() (SegmentationWidget.py:1729) is an if/elif with four near-identical branches. Each builds the same object:

Parameter(folds="0", modelPath=basePath, device=self.deviceComboBox.currentText)
Name in the combo boxFolder under Resources/MLWeight origin
DentalSegmentatorDataset111_453CT/nnUNetTrainer__nnUNetPlans__3d_fullreszip of the latest release of gaudot/SlicerDentalSegmentator, resolved via the GitHub API
PediatricDentalsegmentatorDataset001_380CT/...3 files from releases/download/PEDIATRICDENTALSEG_MODEL
NasoMaxillaDentSegDataset001_max4/...releases/download/NASOMAXILLADENTSEG_MODEL
UniversalLabDentalsegmentatorDataset002_380CT/...releases/download/UNIVERSALLAB_MODEL

The last three follow the same pattern: if <basePath>/fold_0/checkpoint_final.pth is missing, three files are downloaded (checkpoint_final.pth, dataset.json, plans.json) via slicer.util.downloadFile. No checksum, no versioning, no resume: an interrupted download leaves a truncated checkpoint that the code will consider present on the next run.

DentalSegmentator goes through a separate path, PythonDependencyChecker: Github().get_repo("gaudot/SlicerDentalSegmentator"), then the first asset of the first release listed, streamed down and unzipped. The URL used is stored in Resources/ML/download_info.json, and a more recent release triggers an update prompt. The file committed in the repository points to Dataset111_453CT_v100.zip.

4.2 nnU-Net, verified in the code

Yes, this is nnU-Net v2, not just in name. The proof is in the call chain: Parameter.asArgList() literally builds

nnUNetv2_predict -i <tmp>/input -o <tmp>/output
  -d Dataset111_453CT -tr nnUNetTrainer -p nnUNetPlans -c 3d_fullres
  -f 0 -npp 1 -nps 1 -step_size 0.5 -device cuda -chk checkpoint_final.pth --disable_tta

-d, -tr, -p, -c are inferred from folder names: the parent folder gives the Dataset…, and the configuration folder's name is split on __ into (trainer, plan, configuration). Hence the requirement Dataset<id>/<trainer>__<plan>__<conf>/fold_<i>/checkpoint_final.pth.

Parameters not exposed to the user, default values from SlicerNNUNetLib.Parameter: stepSize = 0.5, disableTta = True (no mirror augmentation at test time), folds = "0" (a single fold, never an ensemble), nProcessPreprocessing = nProcessSegmentationExport = 1, forced to 0 on macOS (nnU-Net hangs on write there because of multiprocessing).

The only setting the UI offers is the device: cuda / cpu / mps. If unavailable, only one question is asked for the whole queue (_deviceFallbackAccepted), and in Unattended mode the CPU fallback is accepted automatically.

nnUNet_raw, nnUNet_preprocessed, and nnUNet_results are all pointed at the model folder — three process-level environment variables, written by SegmentationLogic._startInferenceProcess. Since os.environ is global, two concurrent inferences in the same Slicer session would step on each other; here the queue is strictly sequential, so the issue does not arise.

4.3 Architecture and plan — what is verifiable

Only Dataset111_453CT (DentalSegmentator) has its JSON files in the repository. Summary from plans.json:

UNet_class_name = PlainConvUNet     base/max features = 32 / 320
n_conv_per_stage encoder [2,2,2,2,2,2]  decoder [2,2,2,2,2]
pool_op_kernel_sizes = [1,1,1], 4 x [2,2,2], [2,2,1]   conv_kernel 6 x [3,3,3]
patch_size = [128, 160, 112]    spacing = [0.4492, 0.3120, 0.4492] mm
transpose_forward = transpose_backward = [1, 0, 2]     batch_size = 2, batch_dice
normalization_schemes = CTNormalization
foreground intensities: median 1317, mean 1274, s 558, p0.5 -110, p99.5 3067

This plans.json is in the nnU-Net format predating 2.4 (flat UNet_class_name / pool_op_kernel_sizes fields, no architecture block), whereas the AMASSS bundles use the newer format. Both remain readable by current nnunetv2.

The plans of the other three models cannot be determined from the repository: they arrive with the download. Everything known about them comes from the dictionaries hard-coded in the widget (§4.4) and from the README.

4.4 The labels produced, per model

_get_active_label_map() (SegmentationWidget.py:1847) is the reference table: it decides the values written into the output NIfTI.

DentalSegmentator and PediatricDentalsegmentator — 5 labels identical, confirmed by the dataset.json of bundle 111: 1 Upper Skull (maxilla included), 2 Mandible, 3 Upper Teeth, 4 Lower Teeth, 5 Mandibular canal. What distinguishes them is therefore not the output but the training data: permanent dentition (453CT, 7 institutions) versus mixed dentition (380CT). The code treats them in a rigorously identical way — same label table, same colors, same post-processing; only _modelBasePath differs.

NasoMaxillaDentSeg — 6 labels, the maxilla detached from the skull: 1 Upper Skull, 2 Mandible, 3 Maxilla, 4 Upper Teeth, 5 Lower Teeth, 6 Mandibular canal.

UniversalLabDentalsegmentator — 55 labels: the 32 permanent teeth numbered one by one (1 = upper right 3rd molar → 32 = lower right 3rd molar, going around the upper arch then the lower arch), then 20 primary teeth (33 → 52), then Mandible = 53, Maxilla = 54, Mandibular canal = 55. No "Upper Skull": this model does not segment the cranial vault, contrary to what its UI description shows and to what the README says.

Pitfall

The description shown in the UI for UniversalLabDentalsegmentator and the repository's README announce a segmentation of the cranial vault. The actual model has no "Upper Skull" label: it only numbers the teeth, plus mandible/maxilla/canal.

Values are set on each segment via a LabelValue tag (_segmentLabelValue), which takes priority over the name when present.

5. The non-learned core

5.1 Label map reconstruction and geometry restoration

_buildLabelArray() (SegmentationWidget.py:1912):

a single ExportSegmentsToLabelmapNode, with the explicit list of segmentId (which pins down the correspondence "exported value i+1 ↔ segIds[i]"), then a numpy LUT that remaps to the official values in one pass (lut[exported]). The earlier version rasterized the full extent of the volume once per segment: 55 rasterizations of a full-mouth CBCT for UniversalLab.

5.2 Automatic crop (replay after memory failure)

Optional, triggered by Retry failed after explicit confirmation. _applyAutoCrop() (SegmentationWidget.py:1017):

  • air/tissue threshold scale-tolerant: if array.min() < −800, we are in Hounsfield units and the threshold is −500; otherwise min + 0.15 × (p99.5 − min);
  • bounding box of the voxels above the threshold, expanded by _CROP_MARGIN_MM = 15.0 mm converted to voxels per axis;
  • if more than _CROP_MIN_GAIN = 0.85 of the voxels are kept, the crop is abandoned: gaining less than 15% is not worth the risk;
  • the sub-volume keeps its spacing and axes, only the origin moves (ijkToRas.MultiplyPoint([i0,j0,k0,1])). Nothing is interpolated.

_restoreCropToOriginalGrid() pastes the label map back into an array of the original size by a simple index offset: the output is therefore always on the grid of the scan as acquired.

5.3 Memory guard — three lines of defense

The code comment gives the real case: a scan filled 114 GB on a 125 GB machine, got killed by the OOM killer, and left its multiprocessing workers alive holding the memory.

a) A priori estimate, _estimatePeakRamGb() (SegmentationWidget.py:1161). Since the physical volume of the field of view is independent of spacing, the number of resampled voxels equals fovMm3 / targetVoxelMm3. The peak is reached in convert_predicted_logits_to_segmentation_with_correct_shape, where, per class, the following coexist: the sliding-window accumulator (torch.half on the resampled grid, 2 bytes), its float64 copy (data = data.astype(float) on the whole 4D array at once, 8 bytes), and reshaped_final (torch.half on the original grid, 2 bytes). Hence logitsGb = (10 × C × Vresampled + 2 × C × Voriginal) / 2³⁰, plus 8 × (Voriginal + Vresampled) for the float64 transients of skimage.resize, plus _RAM_FIXED_OVERHEAD_GB = 4.0 (torch, weights, workers). The spacing and the label count are read from the same configuration folder, so as not to cross one model's spacing with another model's label count.

Budget = free RAM × ramLimitSpinBox (default 85%). Above it, the scan is marked failed with the reason, without ever starting nnU-Net.

b) Monitoring during execution: _onMemCheck samples every _RAM_SAMPLE_MS = 3000 ms; it takes _RAM_CONSECUTIVE_HITS = 2 consecutive overruns to kill (a transient spike must not condemn a good scan).

c) Memory recovery: _killInferenceTree() kills the entire tree — QProcess.kill() only reaches the direct child, yet nnU-Net does multiprocessing. _reclaimStrayProcesses() sweeps processes whose command line contains nnunetv2_predict, nnunetv2/inference, or nnunet and that no longer belong to anyone. The Free memory button does this by hand.

5.4 Fallback completion detection

_checkInferenceCompletionFallback() (SegmentationWidget.py:2514): when the "done with volume" line appears in nnU-Net's output, a timer checks the output file's size every 1.5 s; two consecutive equal readings ⇒ forced finalization, even if the QProcess's finished signal never arrived. Gives up after 40 attempts (60 s).

Additional guard-rail: a per-scan watchdog (itemTimeoutSpinBox, default 60 min) marks the scan as failed and moves to the next one. _finishCurrentItem is the single exit point, guarded by _itemFinalized against double advancement.

5.5 Mirror correction (UniversalLab only)

onResolveMirroring() (SegmentationWidget.py:1308), a button visible only for UniversalLab. The network regularly confuses left and right; the correction is purely geometric:

  1. reconstruction of the official label map (§5.1), then the RAS R coordinate of each foreground voxel in numpy (m00·x + m01·y + m02·z + m03) — the previous version called vtkMatrix4x4.MultiplyPoint once per voxel and per label;
  2. sagittal plane = average of the R centroids of the four central incisors (labels 8, 9, 24, 25); if one is missing, the correction is refused;
  3. for each lateralized label, the voxels on the wrong side of the plane receive the value of the symmetric label (a table built by substituting left ↔ right in the name); {53, 54, 55} are protected.

The result goes into a new node <name>_Mirrored, the original is kept.

5.6 Missing post-processing

Pitfall

_postProcessSegments() only logs two lines; _keepLargestIsland() and _removeSmallIsland() (which would use _minimumIslandSize_mm3 = 60) are never called anywhere — dead code inherited from upstream DentalSegmentator. No morphological cleanup is therefore applied: what comes out is nnU-Net's raw output, with its own internal post-processing if present in the bundle.

6. Outputs

onInferenceFinished always writes, regardless of which formats are checked, <outputFolder>/<stem>_Segmentation.nii.gz: a label map with the values from _get_active_label_map, on the geometry (spacing, origin, IJKToRAS) of the original volume — uncropped if a crop took place. This is the file expectedOutputPath() looks for to decide a scan has already been processed.

Additional formats, checkboxes, all written into the same folder:

FormatFunctionNamingDetails
STL, OBJExportSegmentsClosedSurfaceRepresentationToFilesone file per segmentsmoothing 1.0, no merging
VTK (per label)_exportVTKPerLabel<segNodeName>_<labelName>.vtkclean → vtkWindowedSincPolyDataFilter (60 it., passBand 0.05, smoothing of boundaries/sharp edges/non-manifold) → cell normals → vtkQuadricDecimation 40% → flip RAS→LPS (Scale(-1,-1,1)), binary
VTK (merged)_exportMergedVTK<segNodeName>_merged.vtkvtkDiscreteMarchingCubes one contour per present label, same smoothing chain, then per-label thresholding, 40% decimation, constant Label cell array, concatenation, LPS flip
NIfTI (checkbox)ExportSegmentsBinaryLabelmapRepresentationToFilesone binary .nii.gz per segmentnot to be confused with the label map above
glTFOpenAnatomyExportadjustable decimation factor (default 0.9); installs SlicerOpenAnatomy if needed

The mesh file names derive from the segmentation node's name, <stem>_Segmentation, not from the scan's name: segment names are sanitized by re.sub(r"[^0-9A-Za-z_-]+", "_", ...).

A mesh export failure does not fail the scan: the NIfTI is already written, the scan is marked done with an export warning.

Verified — fixed in the code

A bug that was fixed, documented in the code of _exportMergedVTK: vtkDiscreteMarchingCubes.SetValue takes a contour index, not a label value. Passing the label as the index left index 0 at contour value 0.0, so the background was contoured, smoothed, and normal-computed before being discarded.

The only learning is that of the four checkpoints, outside this repository.

8. Environment

Installed once per session, on the first Apply, by _runSetupThenStartQueue() (SegmentationWidget.py:1651):

  1. pip install light-the-torch, then python -m light_the_torch install torch torchvision — ltt picks the CUDA wheel matching the detected driver, no version is pinned;
  2. pip install numexpr>=2.10.2;
  3. pip install numpy<2.0 numexpr>=2.10.2 psutil, via PipRunner, a QProcess that returns control to the UI;
  4. SlicerNNUNetLib.InstallLogic().setupPythonRequirements(): nnunetv2, outside this repository;
  5. PythonDependencyChecker.downloadWeightsIfNeeded(): DentalSegmentator weights only.

numpy<2.0 for the same reason as in AMASSS: current torch wheels are compiled against numpy 1.x.

The NNUNet extension must be installed manually: its absence is detected (import SlicerNNUNetLib) and produces a message asking to install it and restart. SlicerOpenAnatomy, on the other hand, installs itself on the first glTF export.

No conda environment, no WSL. GPU is optional (cpu, mps available), at the cost of "about an hour per scan" according to the fallback message.

9. Pitfalls and fragile points

Confirmed bug — NasoMaxillaDentSeg

The segment names and the label table diverge for NasoMaxillaDentSeg. _get_active_label_map gives Maxilla = 3, Upper Teeth = 4, Lower Teeth = 5, Mandibular canal = 6, while _updateSegmentationDisplay (SegmentationWidget.py:2385) renames Segment_1..6 using the list ["Upper Skull", "Mandible", "Upper Teeth", "Lower Teeth", "Mandibular canal", "Maxilla "].

The first effect is visible on screen, before any question of export: the list is not in the order of the table, so the last four segments get the wrong name, the wrong color, and the wrong opacity.

SegmentActual structureDisplayed name
Segment_3Maxilla"Upper Teeth"
Segment_4Upper Teeth"Lower Teeth"
Segment_5Lower Teeth"Mandibular canal"
Segment_6Mandibular canal"Maxilla" (with a trailing space)

The fix is to reorder the list — and the accompanying colors and opacities lists — to match _get_active_label_map, rather than just removing the space.

But the renaming happens before the LabelValue tags are set, and _segmentLabelValue then falls back on the name: Segment_3, which actually carries label 3 (maxilla), is renamed "Upper Teeth" and exported with value 4. Worse, "Maxilla " has a trailing space: the lookup in the table fails, Segment_6 (the mandibular canal) is logged as "unexpected segment" and lost from the NIfTI. The two lists, however, correspond perfectly for the other three models.

  • The four branches of onApplyClickedForVolume are copy-pasted: the UniversalLab branch still names its variable pediatricCheckpoint and logs "Downloading pediatricdentalseg model…". Cosmetic, but misleading when reading logs.
Pitfall

Downloading the DentalSegmentator weights wipes out the other three models: downloadWeights() does shutil.rmtree(self.destWeightFolder) on Resources/ML, which also holds Dataset001_380CT, Dataset001_max4, and Dataset002_380CT. And areWeightsMissing() tests rglob("dataset.json") anywhere under Resources/ML: if only the pediatric model is present, the checker believes DentalSegmentator is installed.

Pitfall

Fragile release resolution: assets[0] among all the assets of all the releases, via an unauthenticated GitHub client (60 requests/h per IP). An asset added at the head of the latest release changes the downloaded model. And no integrity check on the three checkpoints downloaded one by one: a truncated file is indistinguishable from a complete one.

  • NRRD is not recognized and subfolders are not traversed (listVolumes), whereas the repository's other modules readily produce NRRD and folder trees. Name collision is possible: two scans from different folders sharing the same base name overwrite the same <stem>_Segmentation.nii.gz.
  • A single fold, never an ensemble (folds="0"): a bundle that shipped fold_1..4 would see them ignored.
  • os.environ['nnUNet_results'] is rewritten at every scan by SegmentationLogic: harmless here (sequential queue), dangerous if another nnU-Net inference runs in the same Slicer session.
  • Dead code: _saveSegmentationAsNifti, _postProcessSegments, _keepLargestIsland, _removeSmallIsland, onExportClicked (the corresponding button is not wired into the batch layout).
Pitfall

Resources/ML is not installed by CMake: in a packaged extension, the repository's dataset.json / plans.json are not there, and the a priori memory estimate (§5.3) returns None as long as the weights are not downloaded — it then lets the scan through.

10. Literature

DentalSegmentator is published:

Dot G., Chaurasia A., Dubois G., Savoldelli C., Haghighat S., Azimian S., Rahbar Taramsari A., Sivaramakrishnan G., Issa J., Dubey A., Schouman T., Gajny L. DentalSegmentator: robust open source deep learning-based CT and CBCT image segmentation. Journal of Dentistry 147:105130, 2024. doi:10.1016/j.jdent.2024.105130 — PMID 38878813

nnU-Net v2 (v2.2 per the Zenodo notice for the weights), 470 CT and CBCT scans from 7 institutions for training, 5 structures, tested hold-out on 256 scans (133 internal, 123 external): DSC 92.2 ± 6.3% internal, 94.2 ± 7.4% external. The dataset.json shipped here announces numTraining = 453, consistent with the corpus described.

Verified

On this model, code and paper agree. The weights are also published under CC-BY-4.0 on Zenodo (concept DOI 10.5281/zenodo.10829674) — but this module fetches them from GitHub releases, not from Zenodo.

The methodological foundation:

Isensee F., Jaeger P.F., Kohl S.A.A., Petersen J., Maier-Hein K.H. nnU-Net: a self-configuring method for deep learning-based biomedical image segmentation. Nature Methods 18(2):203-211, 2021. doi:10.1038/s41592-020-01008-z

The three variants are not attached to any publication in the repository. The repository's README announces 513 CBCT scans in mixed dentition for PediatricDentalSegmentator and UniversalLabDentalSegmentator, and 135 scans for NasoMaxillaDentalSegmentator, with no reference and no test set. These figures cannot be verified anywhere in the code: the corresponding dataset.json files only arrive with the weight download. To be treated as internal claims until a publication covers them.
