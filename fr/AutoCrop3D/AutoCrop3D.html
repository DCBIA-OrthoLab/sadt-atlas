AutoCrop3D

AutoCrop3D recadre par lots un dossier de volumes selon une boîte dessinée dans Slicer, en extrayant des voxels de la grille d'origine : pas d'interpolation, pas de réseau, pas de conda. Cette page explique comment, pas à pas. Les fichiers, les lignes et les pièges sont sur la page de code.

non publié Atlas (explication) Code (développeurs) pas de conda pas de GPU purement computationnel VISOR Bibliographie

Deux bases de code. Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, est décrit dans VISOR : comment cet outil tourne aujourd'hui. Là où VISOR diffère, une phrase le dit.

Vue d'ensemble : ce qui entre, ce qui sort

Le clinicien dessine une boîte (une région d'intérêt) dans Slicer et l'enregistre dans un fichier. AutoCrop3D ne garde que les voxels situés dans cette boîte, pour chaque volume d'un dossier. Rien n'est prédit : c'est de la géométrie, et les voxels qui restent sont les voxels d'origine.

EntréeSortie
un dossier de volumes (.nii.gz, .nii, .nrrd, .gipl et leurs formes compressées), segmentations comprisespour chaque volume, le même volume réduit à la boîte, nommé avec un suffixe (cropped par défaut), dans une copie des dossiers d'entrée
un fichier de boîte, ou un dossier avec une boîte par patient (.mrk.json)pour une segmentation, une surface (.vtk) à côté

1. Place dans le pipeline

Rien dans le dépôt n'appelle AutoCrop3D, et il n'appelle rien d'autre que Slicer. Rien dans le code ne le lie aux segmenteurs (AMASSS, BATCHDENTALSEG) : sa place relève donc de l'usage, pas du code. L'étape de surface ne démarre que si le nom de sortie contient seg, il est donc fait pour recevoir des segmentations produites ailleurs. Pas de modèle, pas de téléchargement.

2. Fichiers en jeu

Un panneau dans Slicer (vérifie l'entrée, propose le second chemin), un module en ligne de commande (un programme que Slicer exécute en arrière-plan) qui fait tout le recadrage, un petit utilitaire d'appariement, et le constructeur de surface. La liste des fichiers et l'endroit où chacun s'exécute sont sur la page de code. Le module en ligne de commande s'exécute dans le Python propre de Slicer : rien à installer.

3. Ce qui définit la boîte de recadrage

La boîte est un fichier de ROI markups (.mrk.json). Seuls son centre et sa taille sont lus. Les coins sont le centre moins et plus la moitié de la taille, sur chaque axe. La boîte ne vient pas d'une segmentation : rien dans le module ne dérive une boîte d'une carte de labels.

Deux choses dans le fichier sont ignorées par le chemin par défaut : le système de coordonnées dans lequel il a été enregistré, et sa rotation. Une boîte enregistrée en RAS aurait ses deux premières coordonnées à l'envers, sans message ; une boîte tournée est traitée comme sa propre boîte englobante alignée sur les axes. C'est pourquoi un second chemin existe pour les boîtes inclinées (section 5). VISOR lit le système de coordonnées et signale une rotation.

4. Comment la boîte est appliquée : extraction par index, sans rééchantillonnage

Le point clé : aucune interpolation. Les coins sont convertis en positions de voxel et le bloc qui les sépare est copié tel quel.

Conserver la taille d'origine est une option : le bloc recadré est recollé au même endroit dans un volume vide ayant la géométrie de l'original, tout ce qui est hors de la boîte mis à zéro. Aucun fichier de transformation n'est lu ni écrit ; la géométrie vit dans l'en-tête de l'image.

5. Le chemin alternatif : le module Crop Volume de Slicer

Une case à cocher, « Use module Crop Volume for tilted images », confie le travail au module propre à Slicer. Il s'exécute dans le panneau de Slicer, pas dans le module en ligne de commande. Avec l'interpolation activée, Crop Volume rééchantillonne dans le repère propre de la boîte, ce qui lui permet de gérer une boîte tournée, au prix d'un changement des valeurs de voxel. Les deux chemins ne produisent pas le même fichier, à dessein. Il charge la boîte et le volume comme nœuds de la scène, si bien que lui seul lit le système de coordonnées et la rotation. VISOR ne porte pas ce chemin.

6. Mode batch et appariement patient ↔ boîte

Avec un seul fichier de boîte, il est appliqué à chaque volume. Avec plusieurs, chaque volume cherche sa boîte par une clé de patient construite à partir du nom de fichier ; un volume sans boîte est sauté avec un avertissement. Le problème est que les deux côtés calculent la clé par des règles différentes : le nom du volume passe par une chaîne de coupes qui retirent des mots comme Scan ou T1, tandis que le nom de la boîte est coupé à son premier tiret bas.

Un nom de patient contenant un tiret bas casse donc l'appariement. Avec des noms sans tiret bas, tout fonctionne.

7. Générer un maillage VTK à partir d'une segmentation

Quand le nom de sortie contient seg, la carte de labels recadrée est aussi transformée en surface : une marge de voxels vides est ajoutée, marching cubes extrait le contour, et le contour est lissé (5 passes). La marge legacy est de 50, 50 et 10 voxels, mais seulement du côté inférieur de chaque axe, si bien qu'une structure qui touche la face supérieure du recadrage y reste ouverte.

Marching cubes est appelé sur une plage fixe de 100 valeurs de label (1 à 100) quels que soient les labels présents, si bien qu'un label supérieur à 100 n'est jamais contouré ; VISOR demande les labels réellement présents. Chaque cellule du maillage reçoit la même couleur, prise sur le plus grand label (la table contient six couleurs). Le maillage n'est pas replacé dans l'espace du patient, on s'attend donc à ce qu'il ne s'aligne pas sur le volume recadré dans Slicer (une déduction, non testée). VISOR complète des deux côtés en millimètres, colore chaque label et replace le maillage dans l'espace du patient.

10. Environnement

Rien à installer : le module utilise ce que Slicer fournit déjà (SimpleITK, numpy, VTK, Qt). Pas de CUDA, pas de WSL, pas de conda.

11. Pièges et points fragiles

Chaque point est vérifié dans le code et décrit, avec sa preuve, sur la page de code.

  • Le système de coordonnées et la rotation de la boîte sont ignorés : résultat faux, en silence. Preuve.
  • Un dossier contenant une seule boîte plante. Preuve.
  • Le panneau Slicer et le module en ligne de commande cherchent des extensions différentes, si bien qu'un dossier de fichiers non compressés est refusé. Preuve.
  • La troncature perd jusqu'à un voxel du côté supérieur de chaque axe. Preuve.
  • Aucune vérification que la boîte rencontre le volume : un recadrage vide échoue dans une erreur avalée. Preuve.
  • Un remplacement de nom trop large peut renommer un dossier qui porte le même nom que le fichier. Preuve.
  • Crop Volume vide toute la scène à chaque patient. Preuve.
  • La scène est modifiée depuis un autre thread sur ce chemin. Preuve.
  • Le suffixe n'est appliqué qu'à .nii.gz sur ce chemin. Preuve.
  • Le test unitaire ne teste rien. Preuve.
  • Du code mort subsiste dans le module. Preuve.
  • L'étape de surface ne complète que le côté inférieur, et colore toutes les cellules de la même façon. Marge, couleur.
