AutoCrop3D, legacy : le code

Pour les développeurs : ce que fait le module AutoCrop3D legacy dans le code, avec des références file:line, des blocs de code, l'étape VTK, l'environnement et les pièges. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, est décrit dans VISOR : comment cet outil tourne aujourd'hui.

Les références VISOR se lisent SADT-VISOR AutoCrop3D/pipeline.py:272 : c'est tools/AutoCrop3D/src/sadt_autocrop3d/pipeline.py à 6ba2a78. VISOR-serve est e9a7e5d, AutomatedDentalToolsRemote est 19b95e8. Les lignes legacy s'écrivent AutoCrop3D_CLI.py:63@3c67957 ; un numéro de ligne legacy nu sur cette page se lit lui aussi à 3c67957. Les chemins legacy sont relatifs à AutoCrop3D/ : le CLI et ses aides sont dans Crop_Volumes_CLI/, le widget AutoCrop3D.py dans Crop_Volumes_UI/.

1. Place dans le pipeline

Explication en langage courant et maths : page de l'atlas.

Rien dans le dépôt n'appelle AutoCrop3D, et AutoCrop3D n'appelle rien d'autre que Slicer. Il est déclaré dans le CMakeLists.txt:41 racine (la racine du dépôt, pas AutoCrop3D/) et c'est tout.

En pratique, il se place en amont des segmenteurs (AMASSS, BATCHDENTALSEG) ou en aval d'eux : le mode « générer un VTK » ne se déclenche que si le nom du fichier de sortie contient seg, ce qui suppose qu'on lui donne des labelmaps déjà produits ailleurs.

Pas de modèle, pas de .pth, pas de téléchargement : vérifié par un grep de torch|conda|\.pth|monai|nnunet dans tout AutoCrop3D/, zéro résultat hors d'un vtkPolyData nommé model.

3. Ce qui définit la boîte de recadrage

Explication en langage courant et maths : page de l'atlas.

Un fichier json de ROI markups (.mrk.json), lu comme suit (AutoCrop3D_CLI.py:63-68) :

ROI = json.load(open(roi_path))['markups'][0]
roi_center = np.array(ROI['center'])
roi_size = np.array(ROI['size'])

lower = roi_center - roi_size / 2
upper = roi_center + roi_size / 2

Trois champs du json sont ignorés, et c'est la principale source de surprises :

  • coordinateSystem. Le fichier de test ROI.mrk.zip (dans AutoCrop3D/Crop_Volumes_UI/Resources/testfiles/AutoCrop3D/) déclare "coordinateSystem": "LPS", qui est la convention du dépôt (chaque écrivain de markups code en dur "LPS" : ALI_CBCT, ASO_CBCT, AREG_CBCT, FlexReg, VFACE). center est donc en LPS, exactement ce qu'attend TransformPhysicalPointToContinuousIndex de SimpleITK. Mais le champ n'est jamais lu : un ROI enregistré en RAS donnerait un centre dont x et y ont le signe opposé, sans aucun message.
  • orientation (la matrice 3×3 de la boîte). Ignoré : la boîte est supposée alignée sur les axes LPS. Dans le fichier de test, c'est diag(-1,-1,1), une rotation de 180° autour de z : aucun effet sur une boîte centrée. Un ROI réellement tourné serait silencieusement traité comme sa propre boîte englobante alignée sur les axes. C'est exactement la raison d'être de la case « tilted images » (§5).
  • Ni segmentation ni boîte englobante calculée : la boîte vient uniquement de ce json. Il n'y a nulle part de code qui dérive un ROI d'un labelmap.
Piège

Legacy (3c67957) ; à moitié corrigé dans VISOR. Le CLI legacy ne lit que center et size (AutoCrop3D_CLI.py:63-65@3c67957). Le portage VISOR lit coordinateSystem : un ROI en RAS est converti et une valeur inconnue est une erreur (SADT-VISOR AutoCrop3D/pipeline.py:194-201). Il ignore toujours orientation, mais le dit : une boîte tournée met roi_orientation_ignored dans le rapport et journalise un avertissement (SADT-VISOR AutoCrop3D/pipeline.py:203-211, SADT-VISOR AutoCrop3D/__init__.py:242).

coordinateSystem : un ROI enregistré en RAS donnerait un centre dont x et y ont le signe opposé, sans aucun message.

orientation : un ROI réellement tourné serait silencieusement traité comme sa propre boîte englobante alignée sur les axes.

Côté volume, Search accepte .nii.gz, .nii, .nrrd.gz, .nrrd, .gipl.gz, .gipl (AutoCrop3D_CLI.py:41), via un glob.iglob(**, recursive=True) suivi d'un endswith.

4. Comment la boîte est appliquée : extraction par index, sans rééchantillonnage

Explication en langage courant et maths : page de l'atlas.

C'est le point clé : aucune interpolation. La conversion physique → index suivie du recadrage (AutoCrop3D_CLI.py:70-80, découpe à :96-98) :

lower = np.array(img.TransformPhysicalPointToContinuousIndex(lower)).astype(int)
upper = np.array(img.TransformPhysicalPointToContinuousIndex(upper)).astype(int)
for i in range(3):
    if lower[i] > upper[i]:
        lower[i], upper[i] = upper[i], lower[i]
lower = [max(0, l) for l in lower]
upper = [min(img_size[i], u) for i, u in enumerate(upper)]
img_roi = img[lower[0]:upper[0], lower[1]:upper[1], lower[2]:upper[2]]

Le swap n'est pas cosmétique. TransformPhysicalPointToContinuousIndex applique l'inverse de la matrice de direction. Sur un volume dont les cosinus directeurs sont négatifs sur un axe (c'est-à-dire sur certains scans), le coin physique « inférieur » devient le plus grand index : sans le swap, la découpe serait vide. C'est la bonne gestion de direction.

Ce que l'indexation SimpleITK préserve. Vérifié : découper un sitk.Image garde spacing et direction identiques et recalcule l'origine du coin extrait. Sur un volume 50×60×70, espacement 0.3, origine (10,20,30), direction diag(-1,-1,1), img[5:20,5:20,5:20] donne une origine de (8.5, 18.5, 31.5) : un décalage de -5·0.3 sur x et y (direction négative), +5·0.3 sur z. Les valeurs des voxels sont identiques bit pour bit à l'entrée.

Vérifié

Vrai aussi dans VISOR (SADT-VISOR AutoCrop3D/pipeline.py:301 découpe de la même façon). Le README de VISOR affirme une sortie identique à l'octet près à celle du CLI legacy sur un scan de test (SADT-VISOR AutoCrop3D/README.md:204-221) ; cette comparaison n'a pas été rejouée ici.

Découper un sitk.Image garde spacing et direction identiques et ne recalcule que l'origine du coin extrait. Les valeurs des voxels sont identiques bit pour bit à l'entrée.

Mode « Keep the same size as input » (original_size=='True', lu dans l'argument box_Size, AutoCrop3D_CLI.py:35,100-110) : une image vide est créée avec la géométrie d'origine (sitk.Image(...) + CopyInformation), le bloc extrait est recollé au même emplacement d'index, et CopyInformation est réappliqué. La géométrie est strictement identique à l'entrée, avec tout ce qui est hors du ROI mis à 0. Noter l'inversion des axes de GetArrayFromImage (z,y,x), correctement gérée par le code.

Ce qu'il advient des transformations associées : rien. Pas de vtkMRMLTransformNode, pas de .tfm lu ou écrit, pas de HardenTransform. La géométrie est portée entièrement par l'en-tête (origine/espacement/direction), et le décalage du recadrage est absorbé par l'origine.

Note

Conséquence pratique : une matrice de recalage calculée sur le volume complet reste valable telle quelle sur le volume recadré, puisque les coordonnées physiques n'ont pas bougé. Cela découle de la façon dont l'origine est recalculée ; aucun recalage n'a été exécuté pour le vérifier.

5. Le chemin alternatif : le module Crop Volume de Slicer

Explication en langage courant et maths : page de l'atlas.

processCropVolume() (AutoCrop3D.py:723-808), activé par la case « Use module 'Crop Volume' for tilted images » (commit 9d2bbe8). Il s'exécute dans le widget, pas dans le CLI :

crop_volume_logic= slicer.modules.cropvolume.logic()

parameters = slicer.vtkMRMLCropVolumeParametersNode()
parameters.SetInputVolumeNodeID(input_volume.GetID())
parameters.SetROINodeID(roi_node.GetID())
parameters.SetOutputVolumeNodeID(output_volume.GetID())

slicer.mrmlScene.AddNode(parameters)

crop_volume_logic.Apply(parameters)

(AutoCrop3D.py:769-778.)

Seuls les trois ID sont définis : l'interpolation, l'isotropie et l'échelle d'espacement restent aux valeurs par défaut du vtkMRMLCropVolumeParametersNode. Avec l'interpolation activée, Crop Volume rééchantillonne dans le repère propre du ROI, ce qui est précisément ce qui lui permet de gérer un ROI tourné : au prix d'une modification des valeurs des voxels, contrairement au chemin du CLI. Les deux chemins ne produisent donc pas le même fichier, et c'est voulu.

optionCheckBox() (AutoCrop3D.py:331-339) décoche et masque « Keep the same size » dans ce mode, puisque Crop Volume n'a pas d'équivalent.

Ce chemin charge le ROI et le volume comme nœuds MRML (loadMarkups, loadVolume, AutoCrop3D.py:761,764), si bien que lui seul lit coordinateSystem et orientation : Slicer s'en charge en analysant le json.

6. Mode batch et appariement patient ↔ ROI

Explication en langage courant et maths : page de l'atlas.

Deux régimes, distingués par len(roi_list['.mrk.json']) >1 (AutoCrop3D_CLI.py:46,56) :

  • un seul ROI → appliqué à chaque volume trouvé ;
  • plusieurs ROI → ChangeKeyDict construit {basename.split('_')[0]: path} (FilesType.py:75-78) et chaque volume cherche sa clé ; en cas d'échec → logger.warning('No ROI for patient:') et continue (AutoCrop3D_CLI.py:57-61).

Les deux côtés calculent la clé différemment :

CôtéRègleExemple MA_0001_T1_Scan.nii.gz / MA_0001_ROI.mrk.json
volumechaîne de .split() (AutoCrop3D_CLI.py:52) sur _Scan _scan _Seg _seg _Or _OR _MAND _MD _MAX _MX _CB _lm _T2 _T1 _Cl puis .split('.')[0]MA_0001
ROIbasename.split('_')[0] (FilesType.py:77)MA

Un nom de patient contenant un tiret bas casse donc l'appariement. Avec des noms sans tiret bas (MA0001_…), tout fonctionne bien.

La progression est un simple open(args.logPath,'r+') puis write(str(index)) à chaque fichier (AutoCrop3D_CLI.py:140-141) ; le widget ne lit pas le contenu, seulement l'heure de modification (os.path.getmtime, AutoCrop3D.py:394).

7. Générer un maillage VTK à partir d'une segmentation

Explication en langage courant et maths : page de l'atlas.

Déclenché par if "seg" in scan_out_path.lower() (AutoCrop3D_CLI.py:143) : le test porte sur le chemin de sortie complet, si bien qu'un dossier parent nommé Segmentations/ suffit à le déclencher sur chaque fichier. convertNiftiToVTK (GenerateVTKfromSeg.py:15):

La signature réelle, vérifiée : ConstantPad(image, padLowerBound, padUpperBound, constant), le troisième argument étant nul, ce qui signifie que seule la borne inférieure est complétée.

    Legacy uniquement (3c67957) ; absent de VISOR. Le legacy complète de [50, 50, 10] voxels avec ConstantPad(img, padding_size, [0]*dim), borne inférieure seulement (GenerateVTKfromSeg.py:83-85@3c67957). Le portage complète les deux bornes, avec une marge en millimètres convertie par axe (SADT-VISOR AutoCrop3D/pipeline.py:415-426, :462).

    Le commentaire « add 50 pixels around each dimension » est faux : une structure qui touche la face supérieure du recadrage restera ouverte.

    Le fichier temporaire s'appelle image_padded.nii.gz et est écrit dans le répertoire courant du processus, pas dans un dossier temporaire (GenerateVTKfromSeg.py:87-88).
  2. vtkNIFTIImageReader → vtkDiscreteMarchingCubes(GenerateValues(100, 1, 100)) → vtkSmoothPolyDataFilter (5 itérations, angle de crête 120°, relaxation 0.6) (GenerateVTKfromSeg.py:38-55).

    Bug confirmé

    Legacy uniquement (3c67957) ; absent de VISOR. Le legacy prend label = np.max(img_arr) une seule fois et applique LABEL_COLORS[label] à chaque cellule (GenerateVTKfromSeg.py:33,66@3c67957).     Le commentaire « coloring according to labels » ne décrit pas le code.

    Et LABEL_COLORS ne contient que les clés 1–6 (GenerateVTKfromSeg.py:6-13) : un labelmap dont le plus grand label dépasse 6, ou un recadrage vide (maximum 0), lève une KeyError attrapée par le except Exception de l'appelant et journalisée au seul niveau debug, donc ni VTK ni message visible.

Le lecteur NIfTI de VTK n'applique ni qform ni sform (le code ne les récupère même pas), et le padding de 50/50/10 voxels n'est jamais compensé. Une déduction, non testée ici : le maillage obtenu ne s'aligne pas sur le volume recadré dans Slicer.

10. Environnement

Explication en langage courant et maths : page de l'atlas.

Rien à installer. Le module n'utilise que ce que Slicer fournit déjà : SimpleITK, numpy, vtk, qt. pip_install était importé mais jamais appelé quand cette page a été écrite ; revérifié le 2026-10-12, l'import a été retiré. Pas de CUDA, pas de WSL, pas de conda.

11. Pièges et points fragiles

Explication en langage courant et maths : page de l'atlas.

Piège : dossier de ROI avec un seul fichier

Legacy uniquement (3c67957) ; absent de VISOR. Legacy : la table n'est construite que si plus d'un ROI est trouvé, puis json.load(open(roi_path)) reçoit le dossier (AutoCrop3D_CLI.py:46,56,63@3c67957). VISOR : un fichier, ou un dossier contenant exactement un ROI, est appliqué à chaque scan (SADT-VISOR AutoCrop3D/__init__.py:342-343).

Un dossier de ROI contenant exactement un fichier → plantage. ROI_dict n'est construit que si len(ROIList) > 1 ; sinon ROI_Path reste le dossier, et json.load(open(ROI_Path)) lève IsADirectoryError. Le chemin Crop Volume, lui, teste os.path.isdir et le gère très bien.

Piège : extensions incohérentes entre le widget et le CLI

Legacy uniquement (3c67957) ; absent de VISOR. Il n'y a plus de panneau écrit à la main : un seul tuple sert à la découverte (SADT-VISOR AutoCrop3D/pipeline.py:26). Un .nrrd.gz est toujours découvert mais refusé avec une erreur nommée par fichier (SADT-VISOR AutoCrop3D/pipeline.py:37, SADT-VISOR AutoCrop3D/__init__.py:210-215). Lignes legacy : la liste du panneau est AutoCrop3D.py:641,656-659@3c67957, la liste du CLI AutoCrop3D_CLI.py:41@3c67957.

Le widget et le CLI ne cherchent pas les mêmes extensions. CheckInput (AutoCrop3D.py:641@3c67957) ne cherche que .nii.gz, .nrrd.gz, .gipl.gz. Un dossier de fichiers .nii ou .nrrd non compressés est rejeté par l'interface (« Wrong type of patient file detected ») alors que le CLI les gère parfaitement. Et comme nbFiles vient de cette même liste, le dénominateur de la barre de progression est faux dès qu'un mélange d'extensions est présent.

Piège : champs du ROI ignorés

Legacy (3c67957) ; à moitié corrigé dans VISOR. coordinateSystem est lu et orientation est signalé dans le rapport, voir le premier Piège de la section 3 (SADT-VISOR AutoCrop3D/pipeline.py:194-211).

Le coordinateSystem et l'orientation du ROI sont ignorés par le chemin du CLI (§3). Une boîte tournée ou un ROI enregistré en RAS : résultat faux, en silence.

Piège : troncature de l'index

Vrai aussi dans VISOR (SADT-VISOR AutoCrop3D/pipeline.py:272-273) : le portage garde la troncature à dessein, et en donne la raison dans sa docstring (:261-264). Legacy : AutoCrop3D_CLI.py:70-71@3c67957.

.astype(int) tronque vers zéro, si bien que upper perd jusqu'à un voxel par axe. Aucune conséquence clinique, mais le recadrage n'est pas symétrique autour du centre demandé.

Piège : aucune vérification d'intersection

Legacy uniquement (3c67957) ; absent de VISOR. Legacy : écrêtage à AutoCrop3D_CLI.py:78-80@3c67957, découpe à :96-98, échec avalé à :128-138. VISOR : une plage d'index vide lève The ROI does not overlap this volume (SADT-VISOR AutoCrop3D/pipeline.py:294-300) ; un recouvrement partiel est recadré et signalé clamped_to_the_volume (SADT-VISOR AutoCrop3D/pipeline.py:280). Un scan qui échoue est listé dans failed et les autres continuent (SADT-VISOR AutoCrop3D/__init__.py:142-149).

Aucune vérification que le ROI recoupe le volume. L'écrêtage impose Lower ≥ 0 et Upper ≤ size mais rien n'empêche Lower > Upper après l'écrêtage : cela donne une image de taille nulle et l'écriture échoue dans le try/except qui journalise lower/upper.

Piège : remplacement de chemin trop large

Legacy uniquement (3c67957) ; absent de VISOR. Le portage construit le chemin avec os.path.relpath et pathlib (SADT-VISOR AutoCrop3D/__init__.py:223-225, :277-286) et le nom dans SADT-VISOR AutoCrop3D/pipeline.py:332-344.

.replace(basename, filename) remplace chaque occurrence dans le chemin joint (AutoCrop3D_CLI.py:122,124@3c67957) : un dossier portant le même nom que le fichier serait renommé lui aussi.

Piège : Crop Volume vide la scène

Legacy uniquement (3c67957) ; absent de VISOR. Le chemin Crop Volume n'est pas porté : il exige un Slicer en cours d'exécution et n'a pas d'équivalent sans interface (SADT-VISOR AutoCrop3D/README.md:159-177 ; AutomatedDentalToolsRemote AutoCrop3DRemote/AutoCrop3DRemote.py:9-11). Le serveur ne touche jamais à une scène.

Chemin Crop Volume : slicer.mrmlScene.Clear(0) à chaque patient (AutoCrop3D.py:808@3c67957), vide toute la scène, y compris les données que l'utilisateur y avait chargées.

Piège : accès MRML hors du thread principal

Legacy uniquement (3c67957) ; absent de VISOR. Même raison : le chemin Crop Volume n'est pas porté (SADT-VISOR AutoCrop3D/README.md:159-177).

Chemin Crop Volume : slicer.util.saveNode appelé depuis un threading.Thread (AutoCrop3D.py:706@3c67957, le thread est démarré à :787), c'est-à-dire un accès MRML hors du thread principal. Le while thread.is_alive(): processEvents() qui suit sérialise de fait l'exécution, ce qui masque le problème sans le corriger.

Piège : suffixe partiel

Legacy uniquement (3c67957) ; absent de VISOR. Legacy : replace('.nii.gz', ...) à AutoCrop3D.py:699@3c67957. VISOR applique le suffixe à toute extension, en conservant une extension composée (SADT-VISOR AutoCrop3D/pipeline.py:332-344 ; a.nii donne a_cropped.nii).

Chemin Crop Volume : le suffixe n'est appliqué qu'aux fichiers .nii.gz. Un .nrrd ressort sans suffixe, avec le même nom relatif.

Piège : test unitaire inopérant

Legacy uniquement (3c67957) ; absent de VISOR. Le paquet VISOR a sa propre suite, SADT-VISOR AutoCrop3D/tests/test_run.py : 103 tests réussis le 2026-11-09 (son README en annonce 102, README.md:200, un test de retard).
