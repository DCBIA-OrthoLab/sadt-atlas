CLIC

CLIC trouve les canines incluses sur un CBCT et dit si chacune se situe du côté de la joue, du côté du palais ou à cheval sur l'os. Cette page explique comment, pas à pas, avec les maths : ce qui entre, ce que chaque étape lui fait et ce qui sort. Les fichiers, les lignes et les pièges sont sur la page de code ; le portage VISOR est sur sa propre page.

Code (développeurs) non publié VISOR clic_runner.py env conda : clic_env Python 3.9 Bibliographie

Vue d'ensemble : ce qui entre, ce qui sort

CLIC recherche les canines incluses dans un scan CBCT. Il lit le scan coupe par coupe ; sur chaque coupe, un réseau entraîné délimite les canines qu'il trouve et, dans la même passe, dit où chacune se situe par rapport à l'os : du côté de la joue (vestibulaire), du côté du palais (palatine) ou à travers l'os (bicorticale). Le nom promet deux tâches, mais il n'y a qu'un seul réseau : le contour est la localisation et la classe est la classification.

CLIC, module legacy

Méthodepar coupe : remettre à l'échelle les valeurs de gris, donner la coupe à un Mask R-CNN, garder les détections confiantes, les peindre dans un volume d'étiquettes

Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957). Le portage VISOR, qui exécute le même réseau sur un serveur, a sa propre page. Les noms de fichiers, les numéros de ligne et chaque piège sont sur la page de code.

Dans le codeQuelle base de code est décrite ici, et où se trouve le portage VISOR

1. Situation dans la chaîne

CLIC est autonome dans les deux sens : aucun autre module ne l'appelle et il n'en appelle aucun. Il part du CBCT brut, sans segmentation, repères ni orientation préalables, et ne dépend ni d'AMASSS, ni d'ASO, ni d'ALI. Il n'utilise que son propre script d'exécution, lancé une fois par scan, et un fichier de poids que le panneau peut télécharger depuis une release GitHub.

Dans le codeCe que le widget appelle et comment, avec les arguments conda

2. Fichiers en jeu

Trois fichiers composent le module : le panneau Slicer et son interface, et un script d'exécution qui contient tout le traitement. Le panneau écrit les paramètres dans un petit fichier, lance le script dans un environnement conda et lit sa sortie. Le panneau a besoin de l'utilitaire SlicerConda pour se charger. Il utilise la propre classe conda de SlicerConda et n'a pas de chemin WSL ; savoir s'il fonctionne sous Windows dépend de la version de SlicerConda, et cela n'a pas été essayé.

Dans le codeLe tableau des fichiers avec leurs nombres de lignes, l'import de CondaSetUp et le chemin WSL manquant

3. Entrées et prétraitement

Deux choses se passent avant le réseau : le panneau rassemble les scans, et le script prépare chaque coupe.

3.1 Collecte des scans

Le panneau accepte un fichier ou un dossier et filtre sur les extensions NIfTI, NRRD et MetaImage. Le script ne sait lire que le NIfTI : les autres formats passent donc le filtre et échouent plus tard. Si le dossier choisi contient des sous-dossiers de scans, le panneau renvoie les sous-dossiers au lieu des fichiers, que le script ne peut pas charger non plus : le cas qui fonctionne est un dossier à plat de fichiers .nii.gz.

Dans le codeLa fonction de collecte, sa règle en deux temps et l'échec qui en résulte

3.2 Le prétraitement réel du volume

Le script découpe le volume en coupes axiales le long du troisième axe du tableau, dans l'ordre stocké dans le fichier, sans réorientation. Chaque coupe est ensuite traitée isolément.

Cette remise à l'échelle a une conséquence : il n'y a ni fenêtre de Hounsfield ni statistique sur tout le volume, donc chaque coupe a son propre contraste, et une coupe ne contenant que de l'air est étirée sur toute la plage comme les autres. Ensuite, la coupe est copiée sur trois canaux identiques pour correspondre à l'entrée couleur du réseau de base ImageNet (backbone). Le module n'effectue ni recadrage, ni région d'intérêt, ni rééchantillonnage. À l'intérieur du réseau, torchvision agrandit l'image de sorte que son petit côté fasse 800 pixels (1333 au plus sur le grand côté) et la standardise avec la moyenne et l'écart d'ImageNet : un scan de 512 par 512 est donc agrandi à 800 par 800.

Dans le codeLes trois lignes de la boucle, la fonction de normalisation et la transformation de torchvision

4. Le modèle

Tout ce qui concerne une coupe, dans l'ordre. Cliquez sur une boîte pour lire sa section.

Dans le codeComment le modèle est construit, chargé et alimenté

4.1 Architecture

Le réseau est un Mask R-CNN : un backbone ResNet-50 avec une pyramide de caractéristiques regarde l'image, une étape de propositions suggère des régions candidates, et pour chaque région deux têtes prédisent une classe (avec une boîte) et un masque. Il est construit avec quatre classes : le fond et les trois positions de canine. Les noms et les couleurs (1 vestibulaire, vert ; 2 bicorticale, jaune ; 3 palatine, marron) n'existent que dans le panneau, qui s'en sert pour colorer le résultat ; le script se contente d'écrire les entiers 1, 2 et 3.

Dans le codeLe constructeur du modèle, ses têtes, le téléchargement du backbone et la table des classes

4.2 Les poids

Les poids ne sont pas dans le dépôt : le panneau peut les télécharger depuis une release GitHub dans le dossier de documents de l'utilisateur. Le script ne cherche pas ce nom : il prend le premier fichier .pth du dossier choisi dans l'ordre alphabétique, donc avec deux modèles dans le dossier, c'est le nom du fichier qui décide. Le fichier est un simple dictionnaire de poids : il ne contient ni hyperparamètres, ni nombre de classes, ni information d'entraînement, si bien que le jeu d'entraînement et les métriques ne peuvent pas être déterminés à partir du dépôt.

Dans le codeL'adresse de téléchargement, le glob et l'appel de chargement

4.3 Ce que le réseau produit littéralement

Pour chaque coupe, le réseau renvoie une liste de candidats. Chaque candidat a une boîte, une classe de 1 à 3, un score de confiance et un masque : une image de la taille de la coupe contenant, pour chaque pixel, une probabilité entre 0 et 1. torchvision applique son propre premier filtre avant que l'outil ne fasse quoi que ce soit (une coupure de score très basse, une suppression des boîtes qui se chevauchent et au plus 100 candidats par coupe), et trie les candidats par score décroissant.

Dans le codeLes clés du dictionnaire, les formes et les seuils par défaut de torchvision

4.4 Des sorties du réseau à la carte de labels

Deux seuils, tous deux écrits dans le script, transforment les candidats en étiquettes. Puis les masques sont peints dans l'ordre.

Comme les candidats arrivent triés par score décroissant, celui peint en dernier est celui qui a le score le plus bas : un chevauchement entre un candidat vestibulaire et un candidat palatin est tranché en faveur du moins confiant. L'outil n'ajoute aucune limite propre au nombre de candidats par coupe (torchvision en garde au plus 100), et aucune cohérence 3D n'est imposée : chaque coupe est classée seule, sans lissage entre coupes, sans analyse de composantes connexes et sans vote. Deux coupes voisines peuvent donc porter deux classes différentes pour la même dent, et quiconque veut une seule classe par patient doit l'agréger lui-même.

Dans le codeLes deux seuils dans la boucle et le piège de l'écrasement

5. Le cœur algorithmique

Il n'y a pas de cœur non appris au-delà des seuils : pas de recalage, pas de morphologie, pas d'extraction de composantes et pas de mesure. Tout le script se résume à : charger le modèle, boucler sur les coupes, seuiller, écrire. Toute la décision est à l'intérieur du Mask R-CNN.

Dans le codeLe plan complet du script d'exécution

6. Post-traitement et sorties

Le script écrit un sous-dossier nommé d'après le scan, et dedans la carte d'étiquettes, nommée d'après le scan et le suffixe saisi dans le panneau (seg par défaut). Comme l'extension n'est retirée qu'une seule fois, un scan X.nii.gz donne le dossier X.nii et le fichier X.nii_seg.nii.gz : laid, mais sans conséquence. La carte d'étiquettes contient les entiers 0 à 3 (le script la construit en entiers 16 bits) et reprend l'affine et l'en-tête du scan d'entrée, donc elle se superpose au scan sans aucun recalage. Comme l'en-tête du scan est réutilisé, le fichier est enregistré dans le type de données propre au scan : pour un scan stocké en nombres à virgule flottante, la carte d'étiquettes est aussi en virgule flottante, avec les mêmes valeurs 0 à 3.

Le panneau est écrit pour charger le résultat comme une segmentation et colorer les segments dans l'ordre de création, pas selon la valeur de l'étiquette : si une classe est absente du volume, les couleurs se décalent ; il dessine aussi trois petites légendes textuelles dans les vues Rouge, Jaune et Verte. Aujourd'hui, cette étape n'est pas atteinte, car le panneau ne reconnaît jamais la ligne de sortie du script (voir les problèmes connus ci-dessous).

Dans le codeLes lignes d'enregistrement, la règle de nommage et la routine de légende

8. Environnement

Le module crée son propre environnement conda, clic_env, avec Python 3.9 et quelques paquets scientifiques, puis installe PyTorch par pip depuis le canal de wheels qui correspond à la carte graphique de la machine, et enfin installe un NumPy antérieur à la version 2 (ce dernier appel met son argument entre guillemets d'une façon qui ne fonctionne qu'avec l'ancien SlicerConda ; voir la page de code). Cette préparation est rejouée à chaque clic sur Predict, ce qui est lent mais inoffensif. Le GPU est optionnel : sans lui, le script utilise le processeur.

Le correctif conda

Le panneau corrige à la volée la façon dont SlicerConda localise le programme conda, parce que le Slicer nightly pour lequel il a été écrit gardait un seul chemin conda pour toute la machine sans vérifier qu'il existait encore. Le correctif supprime un dossier doublé dans le chemin, vérifie que le fichier est bien là et cherche sinon dans le chemin système. Il est destiné à être retiré dès que le nightly inclura le correctif déjà présent dans la version 5.12.

Dans le codeLe tableau de l'environnement avec les lignes, les appels pip et le correctif lui-même

9. Problèmes connus

  • La barre de progression ne bouge jamais et le résultat n'est jamais chargé dans Slicer, bien qu'il soit écrit sur disque : les lignes de journal du script ne commencent plus par les marqueurs que cherche le panneau. Voir le bug.
  • Même avec les marqueurs corrigés, toute la sortie d'un scan arriverait en un seul bloc à la fin du scan, si bien que la progression sauterait de 0 à 100 pour cent. Voir la liste.
  • Le bouton Cancel se contente d'écrire une ligne dans le journal. Voir la liste.
  • Sans dossier de sortie choisi, le script plante. Voir le piège.
  • La construction du réseau peut aller chercher le backbone ResNet-50 sur internet ; la première exécution hors ligne échoue. Voir le piège.
  • Les chevauchements sont tranchés par l'ordre, et les coupes voisines ne sont pas rendues cohérentes. Voir le piège.
  • NRRD et MetaImage passent le filtre de fichiers mais ne peuvent pas être lus. Voir le piège.
  • L'étape NumPy de la préparation de l'environnement peut échouer avec un SlicerConda récent, ce qui arrêterait Predict avant le démarrage du script. Voir la section sur l'environnement.
  • Le module n'a pas de chemin WSL ; savoir s'il fonctionne sous Windows dépend de la version de SlicerConda et n'a pas été essayé. Voir le piège.
  • La remise à l'échelle par coupe fait que la même dent peut sembler différente au réseau sur deux scans de champs de vue différents. Voir la liste.

10. Littérature

Aucun article ne couvre CLIC. Le travail est annoncé sous le titre Interpretable Deep Learning for the Detection and Classification of Impacted Canines and severity of root resorption (Tulissi, Cevidanes, Prieto), présenté à la NA-MIC Project Week 43 (Montréal, 2025) : un projet en cours, pas une publication. Le code d'origine vient d'un dépôt personnel, ashmoy/maskRcnn. Mask R-CNN lui-même est décrit par He et al. (2017) et implémenté dans torchvision.
