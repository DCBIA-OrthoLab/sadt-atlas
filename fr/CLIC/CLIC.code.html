CLIC, legacy : le code

Pour les développeurs : ce que fait le module CLIC legacy dans le code, avec des références file:line, du code, des arguments, l'environnement et des pièges. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas.

Code Atlas (explication) non publié VISOR clic_runner.py env conda : clic_env Python 3.9 Bibliographie

Classification and Localization of Impacted Canines. Segmentation d'instances 2D coupe par coupe d'un CBCT par un Mask R-CNN torchvision, dont la classe prédite encode la position intra-osseuse de la canine incluse : vestibulaire, bicorticale, palatine.

Le nom du module promet deux tâches ; le code n'a que un seul réseau. Il n'y a ni réseau de classification distinct, ni réseau de localisation distinct, ni tête de régression de coordonnées. La classification est le label d'instance (pr["labels"]) ; la localisation est le masque (pr["masks"]) : les deux sortent de la même passe de Mask R-CNN. Tout ce qui suit en découle.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, est décrit sur sa propre page, CLIC sur VISOR. Les encadrés ci-dessous qui ne tiennent plus dans VISOR le disent dans leur titre.

1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

Autonome dans les deux sens : aucun module du dépôt n'appelle CLIC, et CLIC n'appelle aucun autre module du dépôt. Il n'appelle que son propre runner :

AppeléQuandComment
CLIC/runner/clic_runner.pyune fois par scanCondaSetUpCall.condaRunFilePython(runner, ["--params_json=…"], "clic_env")
release CLIC_model/final_model.pthbouton Download Modelrequests.get, écrit dans ~/Documents/CLIC_Models

Il part du CBCT brut. Pas de segmentation préalable, pas de landmarks, pas d'orientation : le module lit un .nii/.nii.gz et produit une carte de labels. Il ne dépend en aucune façon d'AMASSS, d'ASO ni d'ALI.

Pas de CLI Slicer, pas de .xml, pas de couche de type MedX_Method : le widget écrit un JSON de paramètres dans slicer.app.temporaryPath et lance le runner comme script Python autonome dans l'environnement conda.

Le widget importe CondaSetUp au niveau du module (CLIC/CLIC.py:18) sans le déclarer dans parent.dependencies : sans SlicerConda installé, CLIC ne se charge pas du tout, sans message utile.

Il instancie toujours CondaSetUpCall() (CLIC/CLIC.py:70), jamais CondaSetUpCallWsl : contrairement à DOCShapeAXI et aux modules qui passent par init_conda() (ADT/ADTLib/env/conda.py:46-59, qui renvoie CondaSetUpCallWsl() sous Windows), CLIC n'a pas de chemin WSL. Cela ne le rend pas pour autant Linux seulement. L'appel en CLIC/CLIC.py:269-273 est condaRunFilePython(file, [args], env), qui est l'ordre d'arguments de la classe native ; l'ordre inversé (file, env, args) n'appartient qu'à CondaSetUpCallWsl. Dans SlicerConda à ba426f4 (CondaSetUp/CondaSetUp.py, 2026-10-16), le condaRunFilePython natif (:1746) a une branche platform.system()=="Windows" (:1762). Le SlicerConda plus ancien qui est livré dans l'extension de Slicer 5.12.3 exécute condaRunCommand via executable="/bin/bash" (:1586 du CondaSetUp.py installé), que Windows n'a pas. Le dépôt ne fige aucune version de SlicerConda, et rien n'a été exécuté sous Windows, donc savoir si CLIC y fonctionne n'est démontré dans aucun sens.

Piège · Legacy uniquement

Legacy (3c67957) ; absent de VISOR : le panneau VISOR est un client léger qui envoie les scans à un serveur et n'exécute aucun environnement conda sur le poste (Remote CLICRemote/CLICRemote.py:44,53 ; voir CLIC sur VISOR). Pas de chemin WSL : CondaSetUpCallWsl n'est jamais instancié, et init_conda() n'est pas utilisé. L'ordre des arguments en CLIC/CLIC.py:269-273 correspond à la classe native, donc l'affirmation antérieure selon laquelle la liste d'arguments partirait comme nom d'environnement ne tient pas (cet ordre est celui de la classe WSL). Que la classe native fonctionne sous Windows dépend de la version de SlicerConda (voir section 2) ; non essayé sous Windows, donc « Linux seulement » n'est pas démontré.

3. Entrées et prétraitement

Explication en langage courant et maths : page de l'atlas.

3.1 Collecte des scans

Explication en langage courant et maths : page de l'atlas.

_collect_scans() (CLIC/CLIC.py:439) accepte .nii, .nii.gz, .nrrd, .mha, .mhd, et suit une règle en deux temps :

  1. s'il y a des sous-dossiers contenant au moins un fichier valide, elle renvoie la liste de ces sous-dossiers ;
  2. sinon, la liste des fichiers valides du dossier.

Le cas 1 produit des Path de répertoires, passés tels quels comme input_path au runner, qui fait nib.load(str(inp)) : échec immédiat. Le cas nominal est donc un dossier plat de .nii.gz.

De plus, le runner n'utilise que nibabel : .nrrd, .mha, .mhd sont acceptés par le filtre du widget et illisibles pour le runner.

Piège · Legacy uniquement

Legacy (3c67957) ; absent de VISOR : l'outil ne lit que .nii et .nii.gz (SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:36), ignore les autres fichiers, et refuse une requête sans aucun NIfTI avec un message lisible (__init__.py:115-123 ; voir CLIC sur VISOR). Le filtre de sélection du widget accepte .nrrd, .mha et .mhd en plus de .nii/.nii.gz, mais le runner ne sait charger qu'avec nibabel : ces trois formats passent le filtre et échouent au chargement.

3.2 Le prétraitement réel du volume

Explication en langage courant et maths : page de l'atlas.

Il tient en trois lignes (CLIC/runner/clic_runner.py:80-83) :

sl = _norm(vol[..., z])                                    # min-max of the slice
t  = torch.from_numpy(sl).unsqueeze(0).repeat(3, 1, 1).float().to(device)
pr = model([t])[0]

En d'autres termes :

  • découpage en coupes axiales le long du 3e axe du tableau nibabel, dans l'ordre de stockage du fichier, et non selon une orientation anatomique recalculée. Aucune réorientation RAS/LPS n'est faite, le code ne regarde jamais nii.affine sauf pour le réécrire ;
  • normalisation min-max par coupe (_norm, CLIC/runner/clic_runner.py:44) : (x - min) / (max - min), et une coupe constante devient nulle. Pas de fenêtrage Hounsfield, pas d'écrêtage par percentiles, pas de statistiques volumiques : chaque coupe a son propre contraste, une coupe qui ne contient que de l'air est étirée sur toute la dynamique ;
  • réplication en 3 canaux pour correspondre à l'entrée RGB du backbone ImageNet ;
  • pas de recadrage, pas de ROI, pas de rééchantillonnage explicite, pas de remise à l'échelle des voxels.

Le seul redimensionnement vient de torchvision lui-même : le GeneralizedRCNNTransform intégré au modèle standardise avec les moyennes ImageNet ([0.485,0.456,0.406] / [0.229,0.224,0.225]) et redimensionne de sorte que le petit côté fasse 800 px, plafonné à 1333 px sur le grand côté. C'est une valeur par défaut de torchvision, pas un choix fait dans le dépôt : un CBCT de 512×512 est donc agrandi à 800×800 avant le backbone.

Explication en langage courant et maths : page de l'atlas.

4.1 Architecture

Explication en langage courant et maths : page de l'atlas.

_blank_model(nc) (CLIC/runner/clic_runner.py:35-41), appelé avec nc = 4 :

m = maskrcnn_resnet50_fpn(weights=None)
m.roi_heads.box_predictor  = FastRCNNPredictor(in_f, nc)
m.roi_heads.mask_predictor = MaskRCNNPredictor(in_fm, 256, nc)
  • backbone : ResNet-50 + FPN (_resnet_fpn_extractor, 5 niveaux) ;
  • RPN puis têtes ROI : tête de boîtes (FastRCNNPredictor : cls_score 4 classes, bbox_pred 16 sorties) et tête de masques (MaskRCNNPredictor, couche cachée 256, 4 canaux de sortie, masques 28×28 par ROI) ;
  • weights=None mais weights_backbone garde sa valeur par défaut ResNet50_Weights.IMAGENET1K_V1 : construire le modèle télécharge les poids ImageNet de ResNet-50 (puis load_state_dict les écrase). Premier lancement hors ligne = échec. Effet de bord utile : comme is_trained vaut True, la normalisation est FrozenBatchNorm2d et non BatchNorm2d, ce qui doit correspondre au modèle d'entraînement pour que les clés du state_dict s'alignent.
Piège (aussi vrai dans VISOR)

Aussi vrai dans VISOR : SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:136 appelle toujours maskrcnn_resnet50_fpn(weights=None), voir Constats dans VISOR. weights_backbone garde sa valeur par défaut ResNet50_Weights.IMAGENET1K_V1 même quand weights=None : le simple fait de construire le modèle déclenche un téléchargement des poids ImageNet de ResNet-50. Premier lancement hors ligne = échec, avant même d'atteindre final_model.pth.

4 classes = fond + 3. La correspondance label-nom n'existe que dans le widget, dans _legend() (CLIC/CLIC.py:354-358) :

prédit le réseau ne sort que des entiers 1/2/3 ; le nom et la couleur ci-dessous sont une convention du widget, absente du runner.

4.2 Les poids

Explication en langage courant et maths : page de l'atlas.

URL codée en dur (CLIC/CLIC.py:326-329) :

https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/CLIC_model/final_model.pth

Destination ~/Documents/CLIC_Models/final_model.pth. Le runner ne cherche pas ce nom : il prend sorted(model_dir.glob("*.pth"))[0] (CLIC/runner/clic_runner.py:67), le premier .pth par ordre alphabétique. Deux modèles dans le dossier, et c'est le nom de fichier qui décide. IndexError non gérée si le dossier est vide.

Dans VISOR, le checkpoint n'est pas téléchargé par l'outil ni choisi par ordre de tri : c'est l'unique .pth hébergé sur le serveur, et en avoir plusieurs est un refus (SADT-VISOR tools/CLIC/src/sadt_clic/__init__.py:40-73).

Le fichier est un state_dict nu (model.load_state_dict(torch.load(...))), pas un checkpoint Lightning : pas d'hyperparamètres, pas de classes, pas de version. Le jeu d'entraînement, le nombre de coupes annotées et les métriques ne peuvent pas être déterminés depuis le dépôt.

4.3 Ce que le réseau produit littéralement

Explication en langage courant et maths : page de l'atlas.

réseau pour chaque coupe, model([t])[0] renvoie le dictionnaire standard de torchvision :

CléFormeContenu
boxes(N,4)boîtes x1,y1,x2,y2 dans le repère redimensionné, ramenées à la taille d'origine par la transformation
labels(N,)entier 1..3
scores(N,)score de classe, décroissant
masks(N,1,H,W)probabilité par pixel, flottant dans [0,1]

avec les seuils amont par défaut de torchvision : box_score_thresh=0.05, box_nms_thresh=0.5, box_detections_per_img=100.

4.4 Des sorties du réseau à la carte de labels

Explication en langage courant et maths : page de l'atlas.

Deux seuils, tous deux codés en dur (CLIC/runner/clic_runner.py:84-87) :

keep = pr["scores"] >= 0.7                     # confiance d'instance
for mk, lb in zip((pr["masks"][keep] > .5).squeeze(1).cpu().numpy(),
                  pr["labels"][keep].cpu().numpy()):
    seg[..., z][mk] = int(lb)
  • 0.7 sur le score d'instance ;
  • 0.5 sur la probabilité du masque, ce qui la binarise ;
  • l'affectation est un écrasement, pas un vote : si deux instances se chevauchent, celle traitée en dernier (donc la plus faible en score, puisque torchvision trie par score décroissant) gagne le pixel. Un conflit vestibulaire/palatin sur le même voxel est donc tranché par le score le plus bas ;
  • l'outil n'ajoute aucune limite propre au nombre d'instances par coupe, ni pour une canine ni pour deux (torchvision en garde au plus 100 par coupe, box_detections_per_img).

Aucune cohérence 3D n'est imposée. Chaque coupe est classée indépendamment ; pas de lissage inter-coupes, pas d'analyse de composantes connexes, pas de vote majoritaire sur la pile. Deux coupes voisines peuvent porter deux classes différentes pour la même dent. Quiconque veut « la classe du patient » doit l'agréger lui-même : le module ne la produit pas.

Piège (aussi vrai dans VISOR)

Aussi vrai dans VISOR (SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:178-182 : la même boucle, le même écrasement ; voir CLIC sur VISOR). Le chevauchement entre deux instances est tranché par écrasement, pas par vote : l'instance traitée en dernier, donc au score le plus bas puisque torchvision trie par score décroissant, gagne le pixel. Et comme rien n'impose de cohérence entre coupes voisines, deux coupes adjacentes peuvent classer différemment la même dent.

5. Le cœur algorithmique

Explication en langage courant et maths : page de l'atlas.

Il n'y a pas de partie non apprise, hormis le seuillage : pas d'ICP, pas de morphologie, pas d'extraction de composantes, pas de mesure. Tout le runner est : charger le modèle, boucler sur Z, seuiller, écrire. Toute la décision est dans le Mask R-CNN.

Le correctif conda

Explication en langage courant et maths : page de l'atlas.

CLICWidget.__init__ applique à chaud un correctif à getCondaExecutable de SlicerConda :

  1. corrige un /bin/bin/ dupliqué dans le chemin ;
  2. le renvoie si le fichier est réellement sur le disque ;
  3. sinon, shutil.which("conda") ;
  4. sinon, garde le chemin d'origine et journalise un avertissement.

Le correctif existe parce que le SlicerConda livré avec le nightly 5.13 garde un seul chemin conda pour toute la machine et le distribue sans vérifier qu'il est toujours sur le disque : une autre installation de Slicer l'écrase, et ce module exécute alors un conda qui n'est pas là. Le code le dit, et dit ce qui le rend redondant : la branche déjà présente dans la release 5.12 indexe le chemin par installation et le protège par executableExists(). Il est destiné à être retiré une fois que le nightly embarquera cette version.

Corrigé depuis la rédaction de cette page (legacy uniquement)

Legacy uniquement : VISOR n'a ni environnement conda ni correctif SlicerConda à corriger (CLIC sur VISOR). Cet état des lieux, daté de septembre 2026, notait ici un défaut : fixed_getCondaPath renvoyait /home/<developer>/anaconda3 dès que ce dossier existait sur la machine, avant même de regarder la configuration SlicerConda de l'utilisateur, un chemin de machine de développement, versionné et prioritaire. Revérifié le 2026-10-12 : il a disparu. fixed_getCondaPath n'existe plus, et aucun chemin codé en dur ne subsiste dans CLIC/CLIC.py. Il ne reste que le correctif de getCondaExecutable ci-dessus, qui se replie sur shutil.which.

9. Pièges et points fragiles

Explication en langage courant et maths : page de l'atlas.

Bug confirmé · Legacy uniquement

Legacy (3c67957) ; absent de VISOR : la progression passe par un fichier de progression désigné par SADT_PROGRESS_FILE et écrit par l'outil (SADT-VISOR tools/CLIC/src/sadt_clic/progress.py:21,60-103, appelé en __init__.py:170), et les résultats reviennent dans une archive que le client peut charger comme cartes de labels (Remote CLICRemote/CLICRemote.py:67-72 ; voir CLIC sur VISOR). Le runner émet ses marqueurs via logger.info, avec le formateur '%(name)s - %(levelname)s - (%(filename)s:%(lineno)d) - %(message)s' (ADT/ADTLib/logging_setup.py:21). Les lignes reçues ressemblent à CLIC_runner - INFO - (clic_runner.py:51) - [SEG] /path, donc les tests ln.startswith("[PROGRESS]") et ln.startswith("[SEG]") (CLIC/CLIC.py:277,279) ne sont jamais vrais. Conséquence : la barre de progression reste à zéro et la segmentation produite n'est jamais chargée dans Slicer, elle est pourtant correctement écrite sur disque. Correctif minimal : analyser avec "[SEG]" in ln et couper à partir du marqueur.

Piège · Legacy uniquement

Legacy (3c67957) ; absent de VISOR : le serveur remplit lui-même output_dir et l'outil le crée (SADT-VISOR tools/CLIC/src/sadt_clic/__init__.py:112-113 ; voir CLIC sur VISOR). Sans dossier de sortie choisi, le widget écrit quand même la clé "output_dir" dans le JSON, valant None. Côté runner, P.get("output_dir", inp.parent) renvoie alors None, la clé existe, donc la valeur par défaut ne s'applique pas, et Path(None) lève une TypeError : le runner plante.

  • La barre de progression et le chargement automatique du résultat sont cassés. Le runner émet ses marqueurs via logger.info, avec le formateur '%(name)s - %(levelname)s - (%(filename)s:%(lineno)d) - %(message)s' (ADT/ADTLib/logging_setup.py:21). Les lignes reçues ressemblent à CLIC_runner - INFO - (clic_runner.py:51) - [SEG] /path, donc les tests ln.startswith("[PROGRESS]") et ln.startswith("[SEG]") (CLIC/CLIC.py:277,279) ne sont jamais vrais. Conséquences : la barre reste à zéro et la segmentation produite n'est jamais chargée dans Slicer, elle est pourtant correctement écrite sur disque. Le passage de print à logging a cassé le protocole toujours décrit dans l'en-tête du runner (CLIC/runner/clic_runner.py:12-16). Correctif minimal : analyser avec "[SEG]" in ln et couper à partir du marqueur.
  • Rien n'est incrémental de toute façon. condaRunFilePython fait un subprocess.run(...).stdout et renvoie f"Result: {result.stdout}" : toute la sortie arrive en un seul bloc, à la fin du scan. Même avec les marqueurs corrigés, la progression sauterait de 0 à 100 % par scan.
  • Le bouton Cancel ne fait rien : _on_cancel (CLIC/CLIC.py:296) se contente d'écrire une ligne de journal. Il ne touche ni cancel_evt ni le sous-processus.
  • Sans dossier de sortie choisi, le runner plante. Le widget écrit toujours la clé "output_dir" dans le JSON, valant None si l'opérateur n'a rien choisi ; P.get("output_dir", inp.parent) renvoie alors None, la valeur par défaut ne s'applique pas puisque la clé existe, et Path(None) lève une TypeError. La case Save Predictions in Input Folder du .ui n'est reliée à rien.
  • self.output_dir n'est pas converti en str pour le JSON : c'est déjà une chaîne côté _browse, tout comme model_folder, de façon cohérente, sauf que input_path est un Path explicitement converti. À surveiller en cas de réécriture.
  • La boucle d'attente bloque Slicer : _on_predict s'exécute dans un while not cancel_evt.wait(0.05) avec processEvents(), le thread de travail attend le sous-processus. L'interface reste réactive, mais le bouton Predict est l'unique point de sortie.
  • Normalisation par coupe : la classe prédite sur une coupe dépend du contraste local recalculé, pas des unités Hounsfield. Deux acquisitions de champs de vue différents ne présentent pas la même image au réseau.
  • Le .ui déclare deux widgets QTextEdit nommés logTextEdit (CLIC/Resources/UI/CLIC.ui:343 et 353) : childWidgetVariables n'en garde qu'un, l'autre reste vide à l'écran.
  • Code mort : _clean_env() (CLIC/CLIC.py:47, jamais appelée), initializeParameterNode (:427, pass), _updateAllLabelsColor, _updateDynamicWidgetsColor, _updateMRMLNodeComboBoxColor (:396-425, qui ne s'appellent qu'elles-mêmes), CLIC/testing/test_CanineSegmentation.py (un fichier vide), et l'import torch inutilisé dans MedX_CLI/MedX_Dashboard/MedX_Dashboard.py, mentionné ici parce que le même copier-coller se retrouve dans plusieurs modules. La liste antérieure nommait aussi des imports inutilisés de glob, subprocess, urllib.request et Optional et un fichier CLIC/__pycache__ versionné : ni l'un ni l'autre n'est présent à 3c67957.

10. Littérature

Explication en langage courant et maths : page de l'atlas.

Aucun article ne couvre CLIC. Le travail correspondant est annoncé sous le titre Interpretable Deep Learning for the Detection and Classification of Impacted Canines and severity of root resorption (Tulissi, Cevidanes, Prieto), présenté à la NA-MIC Project Week 43 (Montréal, 2025) : un projet en cours, pas une publication. Le code d'origine vient du dépôt personnel ashmoy/maskRcnn, d'où viennent aussi les scans de test cités par le README (MN138.nii, UM06.nii).

À ne pas confondre avec les travaux voisins ci-dessous, qui n'ont pas produit ce code :

  • la localisation vestibulaire/palatine des canines incluses se fait traditionnellement sur des radiographies panoramiques, avec un CNN de classification d'images (pas un Mask R-CNN sur CBCT) ;
  • plusieurs équipes publient une segmentation 3D de canines incluses sur CBCT (U-Net volumétrique/nnU-Net), sans classer la position corticale.

La spécificité de CLIC, une classe bicorticale en plus de la paire vestibulaire/palatine, prédite coupe par coupe en 2D sur CBCT, n'est décrite dans aucun de ces articles. Ne pas présenter leurs chiffres comme appartenant à ce module.
