MedX

Extraction d'indicateurs cliniques de DTM à partir de notes en texte libre par un modèle de langage exécuté en local (un BART-large-CNN fine-tuné), puis agrégation de la cohorte en un seul panneau de figures : du texte de bout en bout ; aucune image médicale n'entre dans ce module, quoi que son nom puisse laisser croire. Cette page explique le pipeline pas à pas ; les détails du code sont sur la page de code.

Gaydamour 2025 · CLIP, LNCS medx_summarize medx_dashboard env conda : summaries Bibliographie VISOR : non porté, module retiré Code (développeurs) Guide

MedX n'est plus dans l'arborescence legacy : il a été retiré le 2026-09-17 (commit 34d496f) et conservé sur la branche archive/medx, dont le dernier commit est fbfa0fb. Tout ce qui suit décrit ce code archivé ; sa compilation avait déjà été désactivée le 2026-03-18, quand il a été remplacé par CNE. Il n'existe aucun portage VISOR ; ce qui reste de MedX dans VISOR est une coquille vide.

1. Sa place dans la chaîne

MedX est autonome : aucun autre module ne l'appelle et il n'appelle aucun autre module (le catalogue d'outils de l'Agent liste les deux tâches, mais seulement à titre de description). Les deux chemins sont indépendants, chacun avec son propre bouton et sa propre tâche. Le dashboard lit ce que le summarizer a écrit, mais rien ne les enchaîne : l'opérateur relance le dashboard à la main. Aucun des deux chemins n'appelle un modèle de langage via le réseau ; le seul trafic sortant est le téléchargement des poids depuis une release GitHub.

Dans le codeLes deux tâches, la façon dont chacune est lancée, la vérification de l'absence de réseau

2. Fichiers en jeu

Un widget avec une feuille de style sombre et la gestion de conda, deux petits fichiers de méthode, la tâche de summarization avec son module d'aide (lecture, découpage, chargement du modèle), et la tâche de dashboard avec un fichier d'analyse et de figure et un fichier de fonctions d'agrégation. Le summarizer tourne dans un environnement conda à part, le dashboard dans le Python de Slicer. Un GPU est utilisé s'il est présent et n'est pas requis.

Dans le codeLe tableau des fichiers, le lancement conda et la CLI qui n'est jamais exécutée

3. Entrées et prétraitement

Trois étapes transforment un dossier de notes en morceaux que le modèle peut lire : regrouper par patient, extraire le texte, découper en chunks.

3.1 Regroupement par patient

Le dossier est lu sans descendre dans les sous-dossiers. Tout ce qui précède le premier tiret bas dans un nom de fichier est l'identifiant du patient, et les notes d'un même patient sont concaténées en un seul texte avant que le modèle ne les voie. La barre de progression, en revanche, divise le nombre de patients terminés par le nombre de fichiers qu'elle trouve dans tous les sous-dossiers ; dès qu'un patient a plus d'une note, ou qu'il y a des sous-dossiers, elle ne peut pas atteindre 100 %. Les notes d'un patient sont jointes sans rien entre elles.

Dans le codeLe code de regroupement et le décalage de progression

3.2 Extraction du texte

Un PDF donne le texte de ses pages, un fichier Word donne ses paragraphes, un fichier texte est lu tel quel. Le seul nettoyage réécrit deux caractères : l'apostrophe typographique et le tiret demi-cadratin deviennent des caractères simples.

Dans le codeLes extracteurs et la fonction de nettoyage

3.3 Découpage en chunks : la partie la plus soignée

Le texte est d'abord découpé en paragraphes : à une ligne vide, au début d'un élément numéroté ou à puce, et à quatre en-têtes de section (examen clinique, évaluation clinique, examen radiographique, évaluation radiographique), qui ne sont isolés que s'ils sont écrits en majuscules. Les morceaux sont ensuite recollés par deux règles. Un élément numéroté ou à puce se colle toujours au morceau qui le précède. Un paragraphe de moins de 150 caractères absorbe le morceau qui vient après lui : un titre court prend donc le texte qui le suit, et un paragraphe court est joint à ce qui suit, pas à ce qui précède. Un en-tête de section ouvre toujours un nouveau paragraphe.

Quand une section est trop grande pour un chunk, elle est coupée paragraphe par paragraphe, et un paragraphe encore trop grand est coupé phrase par phrase. Un paragraphe ordinaire qui ne tient pas dans ce qui reste du chunk est coupé tout de suite phrase par phrase. 3 500 caractères font environ 850 à 950 tokens (une estimation faite sur les notes de test de CNE, pas une mesure avec le vrai tokenizer), plus environ 20 pour la phrase d'instruction, donc sous la limite de 1 024 du modèle ; tout ce qui dépasse cette limite est tronqué sans avertissement.

Dans le codeLes deux fonctions de découpage, les expressions régulières et les arguments de taille

4. Le modèle

4.1 Ce qui est réellement chargé

Le modèle et son tokenizer sont chargés avec les appels standard de la bibliothèque et rien d'autre : pas d'adaptateur ni de quantification, bien que l'environnement installe des paquets pour les deux (des restes de l'entraînement).

Dans le codeLes lignes de chargement et les paquets inutilisés

4.2 Les poids

Les poids sont une archive de 1,51 GB d'une release GitHub. Sa configuration montre un fine-tune de facebook/bart-large-cnn, un encodeur et un décodeur de 12 couches chacun (environ 406 millions de paramètres, d'après la taille du fichier de poids), capable de lire au plus 1 024 positions, et non un modèle entraîné de zéro. Le bouton de téléchargement du widget ne télécharge en réalité rien ; l'archive doit être récupérée à la main (détails).

Dans le codeLe contenu de l'archive et les champs de configuration

4.3 Le prompt et la génération

Pour chaque chunk, une phrase est placée devant le texte : “Using the following note, extract structured key-value pairs about the patient’s symptoms and diagnoses”. BART n'est pas un modèle qui suit des instructions, donc la phrase n'aide que si le fine-tuning a utilisé le même préfixe, ce qui ne peut pas être vérifié depuis le dépôt. Le modèle écrit ensuite du texte libre : le format champ : valeur est une habitude apprise, jamais vérifiée ici.

La génération combine la beam search à quatre faisceaux et un échantillonnage aléatoire, ce qui rend la sortie différente à chaque exécution (aucune graine n'est fixée). Les résumés des chunks d'un patient sont joints par une ligne de 100 tirets.

Dans le codeLe prompt, le tableau complet de génération et les fonctions d'extraction mortes

5. Le cœur algorithmique : le dashboard

Aucun apprentissage ici : analyse de texte, comptage et dessin.

5.1 Du résumé texte au tableau

Le dashboard lit les fichiers se terminant par _summary.txt. Un dictionnaire de 56 champs, tous du texte vide au départ (l'intensité de la céphalée, le déplacement discal, le trouble du sommeil, l'usage ou non d'un CPAP, etc.), est le schéma cible du module, et le seul endroit où il est écrit. Chaque ligne d'un résumé est coupée à son deux-points ; une ligne qui ne donne pas exactement deux morceaux est ignorée, si bien qu'une valeur qui contient elle-même un deux-points est perdue, et un champ hors des 56 est ignoré.

Dans le codeLe code d'analyse et de fusion, les six champs numériques et la branche booléenne morte

5.2 Les agrégateurs

Chaque panneau a sa fonction, toutes procédant par recherche de motifs dans du texte libre suivie d'un comptage : groupes d'âge (étiquetés 12 à 19, 20 à 40 et plus de 40), trouble du sommeil ou non, sensibilité, moyenne et dispersion de cinq scores de douleur, ouverture maximale de la bouche lue dans des chaînes comme “33 mm” (ou dans n'importe quel nombre nu), localisation des céphalées et des douleurs articulaires (par listes de synonymes), six symptômes oui ou non, cinq niveaux de douleur musculaire, et mois écoulés depuis le début lus dans des phrases comme “1 year and 9 months ago”.

Les autres panneaux suivent leurs propres règles. Le camembert du sommeil compte toute valeur sauf “unknown”, champ vide compris, comme un trouble du sommeil. Le camembert de la sensibilité place un patient dans la part “unknown” quand aucun des trois champs n'est positif et qu'ils ne sont pas tous “false”. Les barres de scores et les barres d'ouverture de la bouche sont des moyennes sur les valeurs qui existent.

Deux fragilités en découlent. Certaines fonctions comparent le texte à true en minuscules tandis que d'autres le passent d'abord en minuscules, donc un modèle qui écrirait True mettrait silencieusement à zéro cinq des six donuts oui ou non, celui de la mâchoire étant le seul protégé (détails). Et le déplacement discal est calculé mais jamais dessiné.

Dans le codeLe tableau des fonctions, le bug de casse et le calcul mort

5.3 La figure

Une grande figure (22 par 14 pouces) dans une grille 2 par 2 : des camemberts pour l'âge, le trouble du sommeil et la sensibilité et deux petits donuts pour la migraine et la céphalée en haut à gauche, six donuts à droite, des diagrammes en barres des scores avec leur dispersion, de l'ouverture maximale et des localisations de céphalée en bas à gauche, puis la douleur musculaire, les zones de douleur articulaire, et l'âge face à la durée de la douleur en bas à droite.

Dans le codeLa spécification de la grille et une auto-affectation qui ne fait rien

6. Post-traitement et sorties

Le summarizer écrit un fichier texte par patient et un fichier journal qui contient le nombre de patients terminés. Le dashboard écrit dashboard.png, un tableau de 58 colonnes patient_data.csv (les 56 champs plus deux colonnes auxiliaires que le code de la figure ajoute), et le tableau de 56 colonnes dashboard_full_dataframe.csv, écrit avant que ces deux colonnes n'existent. Si la case est cochée, l'image est chargée dans Slicer comme si c'était un volume, dans la vue en coupe rouge, faute de visionneuse d'images.

8. Environnement

Le summarizer a besoin d'un environnement conda à lui (Python 3.12) avec les paquets de modèle de langage et de PDF ; sous Windows, conda passe par WSL. Le dashboard tourne dans le Python de Slicer et a besoin de numpy inférieur à 2, de pandas et de matplotlib.

Dans le codeLes listes de paquets, les vérifications d'environnement, l'arrêt du groupe de processus

9. Problèmes connus

  • Le bouton Download ne télécharge rien ; les poids doivent être récupérés à la main (détails).
  • Le résultat de la vérification de l'environnement est ignoré, si bien que la summarization démarre même sans conda (détails).
  • La barre de progression du dashboard ne bouge jamais (détails), et un dossier d'entrée vide provoque une division par zéro (détails).
  • La génération n'est pas reproductible : beam search et échantillonnage ensemble, sans graine (détails).
  • Le patient est tout ce qui précède le premier tiret bas, donc deux patients différents, ou un même patient sous deux noms, se mélangent facilement (tous les pièges).
  • Les valeurs contenant un deux-points sont perdues à l'analyse (tous les pièges).
  • Un commentaire dans le code du dashboard pointe vers des résumés d'un modèle Qwen 1.5B, et non vers le BART que le module livre (tous les pièges).
  • Un des agrégateurs est calculé et jamais dessiné, et quatre paquets installés ne sont jamais importés (tous les pièges).

10. Littérature

L'article correspondant est AI-Driven Multimodal TMJ Patient Modeling: From Unstructured Notes to Precision Treatment (2025, Springer LNCS). Il décrit le fine-tuning de BART et de DeepSeek-R1 sur 1 813 segments annotés tirés de 500 dossiers de DTM, pour extraire 56 indicateurs cliniques, le nombre exact de clés dans initialize_key_value_summary(), et alimenter un dashboard patient et cohorte. L'article conclut que BART bat DeepSeek sur la précision d'extraction des champs malgré un score ROUGE légèrement inférieur ; c'est cohérent avec le fait que le module livre un BART.

Écarts entre l'article et le code du dépôt :

  • l'article place la summarization dans un cadre multimodal (IRM et CBCT recalés) ; rien de cela n'est dans MedX, qui ne lit que du texte ;
  • les commentaires de développement pointent vers un Qwen 1.5B, un troisième modèle que le résumé de l'article ne mentionne pas ;
  • les métriques de l'article ne peuvent être reproduites par aucun script du dépôt (evaluate et scikit-learn sont installés mais inutilisés).
