Agent : pipeline complet

Un assistant en langage naturel qui choisit un module de l'extension, en extrait les paramètres, construit la ligne de commande et la lance. Aucun réseau de neurones médical n'est appelé ici : l'Agent ne fait que du routage et du remplissage de formulaire. Cette page explique comment, pas à pas ; les détails dont un développeur a besoin sont sur la page de code.

non publié Agent_CLI Python de Slicer qwen3:8b via Ollama cross-encoder MiniLM-L6 Code (développeurs) Bibliographie VISOR : partiel

Tout tourne en local : un modèle de langage de 8 milliards de paramètres servi par Ollama, plus un petit cross-encoder pour présélectionner les outils candidats.

Deux bases de code. Tout ce qui est décrit ici est le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). VISOR a un outil serveur appelé Agent, un routeur au-dessus d'un point d'accès Ollama externe, mais aucun client ne l'appelle : le panneau AgentRemote livré dans le client VISOR est une copie du widget legacy qui tourne toujours en local. Les deux sont décrits sur la page VISOR d'Agent. Preuve.

Vue d'ensemble : ce qui entre, ce qui sort

Agent (Automated)Ask (Interactive)
EntréeUne phrase tapée dans le chat, et les dossiers déposés sur le panneauLa même

1. Situation dans la chaîne

Personne n'appelle Agent. Aucun autre module de l'extension ne l'utilise : c'est un point d'entrée terminal. En sortie, trois choses sont appelées :

AppeléCommentOù
Agent_CLIL'exécuteur en ligne de commande de Slicerprocessus séparé, Python de Slicer
Le module cible (ALI_CBCT, AMASSS_CLI, ...)lancé comme processus enfant du panneauPython de Slicer
Ollamason client Python, en HTTP sur le port propre de la machineserveur local, installé et lancé par le module

L'inventaire des cibles est purement déclaratif : il vit dans manifest.yaml, un fichier YAML de 16 entrées. L'Agent ne découvre rien tout seul : il ne connaît que ce fichier.

2. Fichiers en jeu

Le panneau (chat, zone de dépôt, installation d'Ollama, confirmation, lancement, réparation) s'exécute dans Slicer. Un programme en ligne de commande séparé fait le routage et l'extraction et affiche du JSON, sans rien exécuter. Un fichier d'utilitaires contient le manifest, le cross-encoder, l'appel à Ollama, la recherche des chemins et la construction de la commande. Un validateur convertit et vérifie les valeurs, et le manifest liste les 16 outils adressables. Pas d'environnement conda ni de GPU obligatoire : tout tourne dans le Python de Slicer ; le seul GPU utilisé l'est indirectement, via le serveur Ollama.

3. Les modèles

3.1 Le modèle de langage, qwen3:8b via Ollama

Un seul modèle sert les trois appels, routage, extraction des paramètres et réparation : Qwen3 à 8 milliards de paramètres, exécuté par Ollama (donc llama.cpp en dessous) au format GGUF qu'impose Ollama. Il n'y a ni modèle spécialisé ni fine-tuning. Le nom du modèle est écrit à deux endroits du code et peut être remplacé par une variable d'environnement. Le tag par défaut pèse 5.2 GB (lu sur ollama.com, non déterminable à partir du dépôt).

Que cela tourne sur CPU ou sur GPU, c'est Ollama qui en décide, pas le module. Le code en tire une conséquence : sous Linux, un Ollama installé via snap est isolé dans un bac à sable, ne voit pas le GPU NVIDIA et se replie sur le CPU, à 80 à 90 secondes par réponse pour un modèle de 8B, un chiffre mesuré et écrit dans le code. Le module le détecte et avertit, sans pouvoir y remédier.

Quand aucun Ollama n'est trouvé, le module télécharge l'archive portable officielle dans un dossier à lui, si bien qu'aucun mot de passe root n'est demandé depuis le panneau. Seuls deux réglages d'appel sont utilisés : le modèle reste chargé 30 minutes au lieu de 5, et la réponse est contrainte au JSON pour le routeur, l'extraction et la réparation (pas pour le mode consultant). Ni température, ni graine, ni taille de contexte ne sont passées. Si le modèle n'est pas présent, il est téléchargé et l'appel rejoué.

Dans le codeLes constantes, le test snap, l'installeur d'Ollama et les deux réglages d'appel

3.2 Le cross-encoder : ms-marco-MiniLM-L-6-v2

C'est le seul vrai réseau de neurones chargé dans le processus : MiniLM, 6 couches, 22.7 millions de paramètres, entraîné sur la tâche de classement de passages MS MARCO, téléchargé depuis le Hugging Face Hub. Ce n'est pas un modèle d'embedding : la requête et le texte de l'outil sont passés ensemble dans le transformer, qui produit un nombre de pertinence non borné. Le programme en ligne de commande est un processus neuf à chaque message, donc le modèle est rechargé à chaque fois.

Si le chargement du cross-encoder échoue, le repli est brutal : les trois premiers outils du manifest, quelle que soit la question, et le chat n'en est pas informé (une ligne va seulement dans la sortie du programme). Le champ priority du manifest n'est jamais lu.

4. Routage

Deux étapes, et le modèle de langage n'intervient qu'à la seconde. L'étape 1 est le cross-encoder ci-dessus. À l'étape 2, le modèle reçoit la requête et les trois candidats, une ligne chacun (nom, description coupée à 140 caractères, 8 tags au plus), et doit répondre par un seul objet JSON : un nom d'outil, une confidence et une raison en une phrase. Trois choses sont à savoir :

  • Le contexte des dossiers n'est pas donné au routeur ; il n'est ajouté que plus tard, pour l'extraction.
  • L'historique de la conversation est injecté tel qu'il apparaît à l'écran, y compris les propres phrases du panneau comme « After reflection, I would like to run ... », si bien que le routeur JSON reçoit de la prose d'interface en guise de réponses antérieures.
  • La confidence et la raison ne servent à rien. La confidence est analysée et écrite, puis jamais relue : il n'existe aucun seuil nulle part, et la consigne « confidence at most 0.4 when nothing matches » n'est qu'une suggestion faite au modèle.

Le seul filet de sécurité est textuel : la réponse ne doit pas être null. Un nom d'outil qui n'est pas dans le manifest passe ce test, puis fait échouer le constructeur de commande ; l'erreur est attrapée et renvoyée sous forme de message d'erreur.

Dans le codeLe prompt du routeur, l'injection de l'historique et le code mort de la spécification d'outils

5. Extraction des paramètres

Un second appel au modèle, avec un outil déjà choisi. Les paramètres techniques (un dossier temporaire, un chemin de log) sont retirés de ce que voit le modèle et remplis ensuite par le panneau : on ne demande pas au modèle de les inventer. Le prompt liste chaque paramètre avec son type, son caractère requis ou non et la façon d'écrire une liste, puis impose sept règles, surtout : n'extraire que ce que la requête mentionne, ne pas inventer de valeurs, laisser absents les paramètres optionnels non mentionnés. La liste des paramètres requis que renvoie le modèle est ignorée : c'est le validateur qui compte.

Le validateur force aussi le texte « true » ou « false » en minuscules là où un outil compare l'argument brut. Le rapport de validation est par ailleurs presque entièrement jeté : ses erreurs et ses avertissements n'apparaissent nulle part.

Les chemins sont entièrement laissés au modèle. Les dossiers déposés sur le panneau sont ajoutés à la requête, avec la consigne de les tenir pour la source de vérité. Il n'y a ni correspondance heuristique, ni regard dans les dossiers, ni vérification d'existence : le modèle seul devine quel chemin déposé est le T1, lequel est le T2, lequel est le dossier du modèle. VISOR ne corrige que la partie virgule : l'outil serveur reçoit les dossiers sous forme de liste.

6. Construction et exécution de la commande

Oui, le module est réellement lancé. Le programme en ligne de commande ne fait que construire la commande : il fusionne les valeurs par défaut du manifest avec celles extraites et place devant l'interpréteur propre à Slicer et le chemin du script. Pour 14 des 16 outils, les valeurs sont simplement écrites l'une après l'autre dans l'ordre que le manifest déclare (style positionnel).

Le panneau exécute ensuite la commande, et seulement si rien de requis ne manque : une bulle de chat dit ce qu'il voudrait lancer, une boîte de dialogue Yes/No liste chaque paramètre, et sur Yes le module démarre. Si quelque chose de requis manque, rien n'est lancé : le panneau liste ce qui manque avec les valeurs déjà connues, et attend un message de suite. Le lancement est synchrone et se fait sur le thread de l'interface : Slicer est gelé pendant tout le travail, qui, pour une segmentation ou un recalage, se compte en dizaines de minutes.

7. La boucle de réparation

Ce chemin s'exécute dans le processus Slicer, pas dans le programme en ligne de commande. La correction repasse par le validateur et le constructeur de commande, une différence ancien-vers-nouveau est affichée, et une nouvelle confirmation Yes/No est requise ; une différence vide arrête la boucle. Un diagnostic à base de mots-clés, sans modèle, ajoute des indices pour un modèle Ollama manquant, un module Python manquant, une régression connue dans une version récente de transformers, un conflit numpy 2 avec les roues torch, et un échec de connexion à Ollama.

Dans le codeLe prompt de réparation, l'astuce de réimport et le diagnostic par mots-clés

8. Modules adressables, et leur état réel

Le manifest liste 16 outils. Sa liste de paramètres a été comparée, fichier par fichier, avec la vraie ligne de commande de chaque script cible. Seules 2 signatures sur 16 sont correctes : DOCShapeAXI et MRI2CBCT_resample. Deux autres (BatchDentalSeg et CLIC) sont des modules Slicer scriptés, pas des outils en ligne de commande, et ne peuvent pas être lancés ainsi. AMASSS refuse net (« Expected 13 arguments »). Les autres manquent chacun d'un à quatre paramètres.

Comme rien n'est nommé sur la ligne de commande, une liste trop courte ne lève pas d'erreur nette : sur AREG_IOS, par exemple, le chemin du fichier de log finit comme suffixe de nom de fichier. Absents du manifest, donc hors de portée de l'Agent : VFACE, GreedyReg, CNE, AREG_IOSCBCT, SurgMovPred et Medical_Data_Anonymizer.

Dans le codeLe tableau de 16 lignes avec les nombres de paramètres du manifest et réels pour chaque script

Les chemins des scripts ne se résolvent pas

Un problème plus fondamental que les signatures. Le manifest ne donne que des noms de scripts nus. La recherche de chemin regarde, dans l'ordre, dans un dossier désigné par la variable AGENT_CLI_TOOLS_DIR, dans un dossier « CLI files » à côté du manifest, dans le dossier du manifest lui-même, puis jusqu'à quatre niveaux au-dessus. Aucun n'existe dans ce dépôt, où chaque script vit dans le dossier de son propre module, si bien qu'aucun candidat ne correspond et que la fonction renvoie le premier « pour que le message d'erreur pointe vers un chemin déboguable ».

Le lancement lui-même ne lève pas d'exception (l'interpréteur de Slicer existe) : c'est Python qui s'arrête avec le code 2 sur un fichier introuvable, ce qui déclenche la boucle de réparation. Même avec les chemins résolus, certaines cibles échoueraient encore : DOCShapeAXI a besoin d'un paquet qui vit dans un environnement conda, alors que l'Agent lance tout avec le Python de Slicer.

9. Les deux modes

ModeCe que renvoie Agent_CLIExécution
Agent (Automated)Un objet JSON avec l'outil, sa confidence, les paramètres, ce qui manque et la commandeoui, après confirmation
Ask (Interactive)Texte libreaucune

En mode Ask, chaque ligne de candidat porte aussi la liste brute de ses paramètres, collée telle quelle dans le prompt système d'un « expert medical image analysis consultant ». La réponse n'est pas contrainte au JSON et est affichée une fois les caractères * et # retirés. Le README appelle ce mode « Consultant », l'interface dit « Ask (Interactive) », et le code ne teste que le nom Agent, si bien que toute autre valeur retombe dans le mode consultant.

10. Garde-fous

Ce qui existe :

  • Une confirmation obligatoire avant chaque exécution, listant tous les paramètres, et une seconde avant chaque tentative de réparation.
  • Rien n'est lancé tant qu'un paramètre requis manque.
  • Coercition de types, et vérifications des choix, des plages et de l'extension des noms qui ressemblent à des dossiers.
  • Les dossiers temporaires sont remplis par le panneau, pas par le modèle.
  • Bornes : 2 tentatives de réparation, un historique d'au plus 40 tours, et un attrape-tout global pour que la sortie du programme reste toujours du JSON analysable.

Ce qui n'existe pas :

  • Aucun seuil de confidence : un routage à 0.1 est traité comme un routage à 0.95.
  • Aucune vérification qu'un chemin existe : un chemin halluciné passe la validation et la confirmation (l'opérateur doit le repérer à l'œil) et n'échoue qu'au démarrage du module.
  • Les erreurs du validateur ne sont jamais affichées.
  • Aucune protection des dossiers de sortie : si le modèle choisit un dossier de données d'entrée comme sortie, rien ne l'en empêche.
  • Aucune liste blanche d'exécutables, mais la vraie protection est que le chemin du script vient du manifest, pas du modèle : le modèle contrôle les valeurs, pas le programme qui est lancé.

11. Environnement

Le panneau installe cinq paquets dans le Python de Slicer, dans un ordre qui compte : le client Python d'Ollama, un lecteur YAML pour le manifest, transformers antérieur à 4.53 (une régression casse l'import du cross-encoder), numpy antérieur à 2 (numpy 2 casse les roues torch) et, en dernier pour ne pas faire monter les versions épinglées, sentence-transformers. Le programme en ligne de commande s'exécute dans un processus séparé mais partage les paquets de Slicer. Aucun environnement conda n'est créé.

Le serveur Ollama est sondé sur son port local, démarré au besoin et attendu pendant une trentaine de secondes au plus tandis que l'interface reste vivante. Il est revérifié avant chaque message, parce qu'un serveur lancé par le module ne survit pas à un redémarrage de Slicer. Sous Windows, aucune fenêtre de console n'est affichée ; il n'y a pas de prise en charge de WSL, contrairement au reste du dépôt.

12. Pièges et points fragiles

  • Les scripts des modules sont introuvables, ce qui bloque tout l'outil. Preuve.
  • 14 signatures sur 16 sont fausses, et le décalage est silencieux. Preuve.
  • Le cross-encoder se replie silencieusement sur les trois premiers outils, est rechargé à chaque message, et garde un top 3 codé en dur. Preuve.
  • Slicer est gelé pendant tout le travail. Preuve.
  • La résolution des chemins est entièrement laissée au modèle. Preuve.
  • Un Ollama installé avec snap tourne sur CPU. Preuve.
  • Trois noms pour deux modes. Preuve.
  • Du code mort subsiste : un process() inutilisé, un constructeur de spécification d'outils inutilisé, un cache inutilisé du cross-encoder, et un fichier d'interface qu'un module en ligne de commande ne charge jamais. Preuve.
  • L'historique mélange la prose de l'interface et le contexte de routage, et quand une discussion sauvegardée est rechargée, l'historique est reconstruit en découpant le texte sur deux émojis, si bien qu'un message qui les contient le désynchronise (un chat en direct garde ses tours sous forme de liste).

14. Littérature

Aucun article, ni sur ce module ni sur l'approche. Une recherche de SlicerAutomatedDentalTools et d'agents LLM ne ramène que la documentation du dépôt et de la littérature générale sur les modèles de langage en dentisterie. Les seules vraies références externes sont celles des deux modèles utilisés, toutes deux génériques et non entraînées pour ce domaine. L'outil serveur VISOR suit la même approche ; son README fournit une section de provenance nommant les fichiers legacy dont il a été porté, pas une publication. Preuve.
