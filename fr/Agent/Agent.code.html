Agent, legacy : le code

Pour les développeurs : ce que fait le module Agent legacy dans le code, avec des références file:line, les prompts, la vérification du manifest, l'environnement et les constats. L'explication lisible du même pipeline se trouve sur la page de l'atlas.

Agent_CLI Code Atlas (explication) Bibliographie VISOR : partiel

Tout tourne en local : un LLM de 8 milliards de paramètres servi par Ollama, plus un petit cross-encoder pour présélectionner les outils candidats.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). VISOR a un outil serveur appelé Agent, un routeur au-dessus d'un point d'accès Ollama externe, mais aucun client ne l'appelle : le panneau AgentRemote livré dans le client VISOR est une copie du widget legacy qui tourne toujours en local. Les deux sont décrits sur la page VISOR d'Agent.

3.1 Le LLM, qwen3:8b via Ollama

Explication en langage courant et maths : page de l'atlas.

Une seule constante, dupliquée aux deux bouts : DEFAULT_MODEL = "qwen3:8b" (utils.py:21) et MODEL_NAME = "qwen3:8b" (Agent.py:29). get_router_model() respecte une variable d'environnement ROUTER_MODEL qui permet de brancher n'importe quel modèle Ollama sans toucher au code.

Le même modèle sert les trois appels : routage, extraction des paramètres, réparation. Pas de modèle spécialisé, pas de fine-tuning.

Ollama installé via snap = CPU · Legacy uniquement

Legacy uniquement (3c67957) ; absent de VISOR. Il n'y a aucun test /snap/ dans la copie du client (aucune correspondance dans AutomatedDentalToolsRemote AgentRemote/AgentRemote.py), et l'outil serveur n'installe ni ne démarre Ollama : il lui faut un point d'accès joignable (SADT-VISOR tools/Agent/src/sadt_agent/llm.py:1-25, point d'accès résolu à :38-39).

Le module ne passe jamais de directive de périphérique. Le binaire Ollama décide, et le code en tire une conséquence explicite : sous Linux, un Ollama installé via snap est isolé dans un bac à sable, ne voit pas le GPU NVIDIA et se replie sur le CPU, 80–90 s par réponse pour un modèle de 8B, un chiffre mesuré et codé en dur dans le code (commentaire à Agent.py:1101-1103, repris dans la boîte de dialogue d'avertissement). Le module détecte /snap/ dans le realpath du binaire et avertit, sans pouvoir y remédier (le serveur snap occupe déjà le port 11434, et le supprimer demande sudo).

Quand aucun Ollama n'est trouvé, install_official_ollama() (Agent.py:111) télécharge l'archive portable officielle dans ~/.slicer_agent/ollama (modifiable via SLICER_AGENT_HOME) : ollama-linux-{amd64,arm64}.tgz, ollama-windows-{amd64,arm64}.zip, ou Ollama-darwin.zip, extraite avec ditto puis dé-quarantainée avec xattr. Ces archives embarquent les bibliothèques CUDA/Metal, d'où le choix délibéré de ne pas utiliser curl | sudo sh (pas de mot de passe root depuis l'interface) ni le paquet snap. LD_LIBRARY_PATH est pointé sur <install>/lib/ollama pour que le binaire trouve ses propres bibliothèques (Agent.py:67).

Seulement deux réglages d'appel, dans chat_with_auto_pull (utils.py:96) :

  • keep_alive="30m" au lieu des 5 minutes par défaut, pour ne pas recharger 5 GB en VRAM entre deux messages ;
  • format="json" pour le routeur, l'extraction et la réparation (une contrainte de grammaire côté Ollama) : pas pour le mode consultant.

Aucun temperature, seed, num_ctx ni think n'est passé. Comme qwen3 est un modèle à raisonnement hybride, le mode consultant peut donc laisser fuir du texte de raisonnement selon la version d'Ollama ; le seul post-traitement est output.replace("*","").replace("#","") (Agent_CLI.py:215), qui retire le markdown en retirant les caractères.

Si le modèle n'est pas présent, chat_with_auto_pull intercepte le message not found, exécute ollama.pull(model, stream=True) en affichant la progression, puis rejoue la conversation. Toute autre erreur est relancée telle quelle.

3.2 Le cross-encoder : ms-marco-MiniLM-L-6-v2

Explication en langage courant et maths : page de l'atlas.

C'est le seul vrai réseau de neurones chargé dans le processus. CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") (utils.py:53), via sentence-transformers, donc des poids transformers/safetensors téléchargés depuis le Hugging Face Hub et mis en cache dans ~/.cache/huggingface.

MiniLM, 6 couches, 22.7 M de paramètres, distillé de MiniLM-L12-H384-uncased, entraîné sur MS MARCO Passage Ranking. Ce n'est pas un modèle d'embedding : il n'y a ni vecteurs ni similarité cosinus. La requête et le document sont concaténés et passés ensemble dans le transformer, qui produit un seul scalaire de pertinence non borné (typiquement de −10 à +10). Le périphérique est celui que sentence-transformers choisit de lui-même, d'après la roue torch installée.

Le cache _cross_encoder_model ne sert à rien en pratique : Agent_CLI.py est un processus neuf à chaque requête, si bien que le modèle est rechargé à chaque message. Le commentaire du code l'admet.

Repli silencieux du cross-encoder · legacy et copie du client ; pas l'outil serveur

Legacy (3c67957) ; absent de l'outil serveur VISOR. Le classeur du serveur est BM25 et ne restreint la liste que lorsqu'il a un signal : sans recouvrement entre la requête et un outil quelconque, tous les outils sont affichés (SADT-VISOR tools/Agent/src/sadt_agent/ranking.py:222-239). Le repli du cross-encoder est toujours vrai dans la copie du client (AutomatedDentalToolsRemote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:94 ; legacy Agent_CLI/Agent_CLI_utils/utils.py:94).

Si le chargement échoue, le repli est brutal : scripts[:k], c'est-à-dire les trois premiers outils du manifest (ali_cbct, ali_ios, amasss_cli) quelle que soit la question (utils.py:94). La seule trace est une ligne affichée dans la sortie du CLI (utils.py:93) ; le chat n'en est pas informé.

4. Routage

Explication en langage courant et maths : page de l'atlas.

Deux étapes, et le LLM n'intervient qu'à la seconde.

Étape 1, présélection par cross-encoder. cross_encoder_retrieve_candidates(manifest, prompt, k=3) construit un document par outil :

docs.append(f"{s['name']}: {s['description']} (tags: {tags})")
scores = model.predict([(user_text, doc) for doc in docs])
ranked = sorted(zip(scores, scripts), reverse=True)
return [s for _, s in ranked[:k]]

16 paires notées, triées par ordre décroissant, top-3 codé en dur (k=3 n'est jamais paramétré). Le champ priority du manifest (valeurs de 1 à 23, avec des trous) n'est jamais lu : la ligne qui le lirait est mise en commentaire (utils.py:216). Le bon outil, s'il est classé 4e, est perdu définitivement ; le LLM ne le verra jamais.

Étape 2, choix par le LLM. Le prompt système (Agent_CLI.py:105) :

You are a tool router. Output ONLY one JSON object.
Schema:
{"tool": string|null, "confidence": number, "reason": string}

Rules:
- Choose tool ONLY from the candidate list provided by the user message.
- If none match, set tool = null and confidence <= 0.4.
- Do not invent tool names.
- Keep reason short (max 1 sentence).

Le message de l'utilisateur est USER_REQUEST: <prompt> suivi de CANDIDATES (choose exactly one name from this list): et du bloc construit par build_candidates_block : une ligne par candidat, i) name — description (truncated to 140 characters) | tags: t1, t2, … (8 max).

Trois choses à noter :

  • Le contexte des dossiers n'est pas donné au routeur. folders_context n'est ajouté qu'au prompt d'extraction.
  • L'historique de la conversation est injecté entre le tour système et le tour utilisateur (*history), et il contient les bulles de chat brutes du widget (« After reflection, I would like to run … »). Le routeur JSON reçoit donc de la prose d'interface en guise de tours « assistant ».
  • confidence et reason ne servent à rien. confidence est analysé, arrondi, sérialisé dans le JSON de sortie sous le nom tool_confidence… et jamais relu par le widget. Aucun seuil nulle part. La consigne « confidence ≤ 0.4 » n'est pas une contrainte, juste une suggestion faite au modèle.

Le seul filet de sécurité est textuel : if selected_tool and selected_tool != "null" and selected_tool != "None". Un nom d'outil halluciné qui n'est pas dans le manifest passe ce test, puis fait échouer build_cli_args avec une KeyError, attrapée par le try global de main() et renvoyée sous la forme {"error": …}.

tools = build_tool_spec(manifest) (Agent_CLI.py:72) est calculé puis jamais utilisé : du code mort, tout comme la gestion de l'« ancienne structure » (patterns, defaults) qu'aucune entrée du manifest actuel n'utilise.

5. Extraction des paramètres

Explication en langage courant et maths : page de l'atlas.

Un second appel au LLM, avec un outil déjà choisi, dans extract_parameters (utils.py:220).

Masquage des paramètres techniques. Les paramètres nommés temp_fold, tmp_folder, temp_folder, log_path ou logPath sont retirés de la spécification avant de construire le prompt : inutile de demander au modèle d'inventer un dossier temporaire. Ils sont réinjectés ensuite avec la valeur input.temp_folder, c'est-à-dire le slicer.util.tempDirectory() créé par le widget à chaque clic (Agent_CLI.py:153), et retirés de missing_required.

Le prompt d'extraction (parameter_extraction_improved.py:40) liste chaque paramètre sous la forme - name (type) [REQUIRED|optional] (encode: …): description, puis impose sept règles : mise en forme des listes selon encode (comma_no_brackets, space_separated, comma_separated, python_literal), booléens et nombres en JSON brut, « si le nom contient folder ou dir, donner un dossier sans nom de fichier », et surtout :

7. ONLY extract parameters mentioned in the user request
   - Do NOT invent values
   - Leave unmentioned optional parameters absent

Sortie obligatoire : {"extracted": {...}, "confidence": 0.0-1.0, "missing_required": [...], "notes": "..."}. Le missing_required produit par le modèle est ignoré : c'est le validateur qui compte.

La résolution des chemins est entièrement déléguée au LLM · en partie corrigé dans VISOR

La partie chemin est aussi vraie dans VISOR ; la partie virgule est corrigée. L'outil serveur reçoit folders sous forme de liste, si bien qu'une virgule dans un nom de dossier ne le coupe plus (SADT-VISOR tools/Agent/src/sadt_agent/__init__.py:40,124). Le modèle reste le seul à décider quel chemin va dans quel argument : validation.py vérifie les types et choices d'après le schéma publié, pas qu'un chemin existe (validation.py:1-30).

Le widget passe la liste des éléments déposés dans la zone de dépôt, joints par des virgules (Agent.py:770) ; le CLI la redécoupe sur , et l'enveloppe :

FOLDERS_CONTEXT:
<one path per line>

Rules:
- Treat FOLDERS_CONTEXT as the source of truth for paths.
- If a required path parameter is missing, try to infer it from FOLDERS_CONTEXT.
- If multiple candidates exist, pick the most specific match and explain briefly in 'reason'.

Ce bloc est concaténé au prompt de l'utilisateur, pas passé séparément. Il n'y a ni correspondance heuristique, ni inspection du contenu des dossiers, ni vérification d'existence : c'est au modèle de deviner lequel des chemins déposés est le T1, lequel est le T2, lequel est le dossier du modèle. Un chemin contenant une virgule est coupé en deux par le split(",").

La validation (parameter_validator.py) enchaîne six passes : champs requis manquants, coercition de types (bool/int/float/list/path/string), syntaxe des chemins, choices, min/max, paramètres hors spécification. Deux détails utiles :

  • encode: lower_str_bool force la chaîne "true"/"false" en minuscules, parce que plusieurs CLI comparent l'argument brut sans .lower() : str(True) donnerait "True" et ne correspondrait jamais.
  • _check_paths ne vérifie que deux choses : que Path(str(value)) ne lève pas d'exception (c'est presque toujours le cas) et qu'un paramètre dont le nom contient folder/dir ne se termine pas par une extension connue. L'existence du chemin n'est jamais testée.

Le résultat de la validation est presque entièrement jeté : errors et warnings n'apparaissent nulle part. Leur seul effet est final_confidence = confidence * 0.6 quand c'est invalide, et cette confidence n'est lue par personne. Seuls params et missing_required survivent.

6. Construction et exécution de la commande

Explication en langage courant et maths : page de l'atlas.

Oui, le module est réellement lancé. Sans ambiguïté.

Le CLI ne fait que construire la commande. build_cli_args (utils.py:350) fusionne les valeurs par défaut du manifest avec les paramètres extraits, puis :

return [sys.executable, tool_path] + cli

sys.executable est l'interpréteur du processus Agent_CLI, c'est-à-dire le Python de Slicer. Pour cli_style: positional (14 outils sur 16), les valeurs sont concaténées dans l'ordre de déclaration du manifest : positional_order est pris en charge mais aucune entrée ne le définit. Pour tout autre cli_style, l'exécution tombe dans la branche --flag value, qui itère sur merged : des paramètres hallucinés hors spécification sont donc bien émis.

La liste est renvoyée au widget dans le champ command du JSON. C'est AgentWidget qui l'exécute, et seulement si missing_required == [] :

  1. une bulle de chat, « After reflection, I would like to run X » ;
  2. QMessageBox.question listant key=value pour chaque paramètre (Agent.py:841 ; l'étape de réparation redemande, :938) ;
  3. sur Yes → runToolWithRepair → subprocess.run(cli_args, capture_output=True).

Si missing_required n'est pas vide, l'agent ne lance rien : il affiche la liste de ce qui manque avec les valeurs déjà connues, et attend un message de suite (que l'historique de la conversation lui permettra de raccrocher).

Slicer est gelé pendant le travail · legacy et copie du client ; pas l'outil serveur

Legacy (3c67957) ; absent de l'outil serveur VISOR. L'outil serveur exécute l'outil choisi via le superviseur, seulement quand execute vaut true (SADT-VISOR tools/Agent/src/sadt_agent/execution.py:70). Le gel est toujours vrai dans la copie du client (AutomatedDentalToolsRemote AgentRemote/AgentRemote.py:767 ; legacy Agent/Agent.py:898).

subprocess.run est synchrone et s'exécute sur le thread de l'interface : Slicer est gelé pendant toute la durée du travail, qui, pour une segmentation AMASSS ou un recalage AREG, se compte en dizaines de minutes.

7. La boucle de réparation

Explication en langage courant et maths : page de l'atlas.

Sur un code de retour non nul, runToolWithRepair (Agent.py:880) demande au LLM de corriger les paramètres, au plus MAX_REPAIR_ATTEMPTS = 2 fois. build_repair_prompt (utils.py:282) envoie les définitions des paramètres, les valeurs utilisées, la commande complète et les 2000 derniers caractères de stderr, et lui demande de ne renvoyer que les paramètres à changer.

Ce chemin s'exécute dans le processus Slicer, pas dans le CLI : _proposeRepair ajoute le dossier Agent_CLI à sys.path et réimporte Agent_CLI_utils pour ne pas dupliquer la logique. La correction repasse par ParameterValidator puis build_cli_args, un diff old -> new est affiché, et une nouvelle confirmation Yes/No est requise. Si le diff est vide, la boucle s'arrête.

_suggestFixFor (Agent.py:1240) complète cela par un diagnostic sans LLM, à base de mots-clés : modèle Ollama manquant, ModuleNotFoundError, NameError: name 'nn' is not defined (une régression connue dans transformers>=4.53.0, huggingface/transformers#43784), Numpy is not available (conflit d'ABI numpy 2 avec les roues torch), ou un échec de connexion à Ollama.

Les chemins des scripts ne se résolvent pas

Un problème plus fondamental que les signatures. Le manifest ne donne que des noms nus (path: "ALI_CBCT.py"). resolve_tool_path (utils.py:143) cherche, dans l'ordre : $AGENT_CLI_TOOLS_DIR/<name>, <manifest_dir>/CLI files/<name>, <manifest_dir>/<name>, puis <ancestor>/CLI files/<name> en remontant de 4 niveaux.

Sans AGENT_CLI_TOOLS_DIR, l'Agent ne peut lancer aucun module · vrai pour la copie du client

Vrai aussi pour la copie du client ; sans objet pour l'outil serveur. L'extension qui livre AgentRemote n'a pas non plus un tel dossier, et son résolveur lit toujours AGENT_CLI_TOOLS_DIR (AutomatedDentalToolsRemote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:154 ; les modules CLI ont été supprimés, CMakeLists.txt:49-56). L'outil serveur ne lance rien par chemin.

Il n'existe aucun dossier CLI files nulle part dans SlicerAutomatedDentalTools. Le commentaire du code cite l'organisation AI_Agent/Agent_CLI/ + .../CLI files/, celle du dépôt d'origine dont Agent_CLI a été extrait. Ici, chaque script vit dans le dossier de son propre module (ALI_CBCT/ALI_CBCT.py, …). Aucun candidat ne correspond, et la fonction renvoie candidates[0] « pour que le message d'erreur pointe vers un chemin déboguable », soit <Agent_CLI>/CLI files/ALI_CBCT.py.

subprocess.run ne lève pas d'exception (l'exécutable, sys.executable, existe) ; c'est Python qui s'arrête avec le code 2 sur un fichier introuvable, ce qui déclenche la boucle de réparation qui, puisqu'elle corrige des paramètres, ne peut structurellement rien y faire.

Et même avec les chemins résolus, certaines cibles échoueraient encore : DOCShapeAXI_CLI.py importe shapeaxi, un paquet qui vit dans un environnement conda que son module Slicer invoque via conda run -n … ou CondaSetUpCall. (MRI2CBCT n'est plus un exemple : son nnunetv2 tourne désormais dans le Python même de Slicer.) L'Agent, lui, lance tout avec sys.executable, c'est-à-dire le Python de Slicer, jamais conda.

10. Garde-fous

Explication en langage courant et maths : page de l'atlas.

Ce qui existe :

  • Une confirmation modale obligatoire avant chaque exécution, listant tous les paramètres, et une seconde avant chaque tentative de réparation.
  • Blocage sur les paramètres requis manquants : rien n'est lancé tant que missing_required n'est pas vide.
  • Coercition de types et vérifications choices / min / max / extension sur les dossiers.
  • Masquage des dossiers temporaires, remplis à partir de slicer.util.tempDirectory() plutôt que par le modèle.
  • Bornage : MAX_REPAIR_ATTEMPTS = 2, historique tronqué à MAX_HISTORY_ENTRIES = 40 tours.
  • try global dans main() : stdout reste toujours du JSON analysable, la trace d'appels va sur stderr.

Ce qui n'existe pas :

  • Aucun seuil de confidence. tool_confidence et parameters_confidence sont calculés et sérialisés, puis ignorés. Un routage à 0.1 est traité comme un routage à 0.95.
  • Aucune vérification d'existence des chemins. Un chemin halluciné passe la validation, passe la confirmation (l'opérateur doit le repérer à l'œil dans la boîte de dialogue), et n'échoue qu'au lancement du module cible.
  • Les erreurs du validateur ne sont jamais affichées. errors, warnings et extra_params sont produits puis jetés.
  • Aucune protection des dossiers de sortie. Si le modèle choisit un dossier de données d'entrée comme output_folder, rien ne l'en empêche. Plusieurs CLI du dépôt écrasent leur fichier d'entrée.
  • Les paramètres hors spécification ne sont pas filtrés en mode --flag.
  • log_path reçoit un dossier, pas un fichier : les noms log_path et logPath figurent dans la liste des paramètres remplacés par input.temp_folder. Les CLI qui ouvrent ce chemin en écriture échoueront.
  • Aucune liste blanche d'exécutables. subprocess.run prend la liste exactement telle qu'elle est construite. La vraie protection est que tool_path vient du manifest, pas du LLM : le modèle contrôle les valeurs, pas le binaire.

11. Environnement

Explication en langage courant et maths : page de l'atlas.

CheckDependencies (Agent.py:1018) exécute un slicer.util.pip_install dans le Python de Slicer, dans cet ordre, qui compte :

PaquetRaison de l'épinglage
ollamaclient python seulement : pip ne fournit pas le serveur
pyyamllecture du manifest
transformers<4.53.0régression NameError: name 'nn' is not defined dans integrations/accelerate.py, casse l'import du cross-encoder

Agent_CLI.py s'exécute dans un processus séparé mais partage les site-packages de Slicer, d'où l'installation côté widget. Aucun environnement conda n'est créé ni utilisé.

Le serveur Ollama est vérifié par une simple sonde de socket sur 127.0.0.1:11434 (_ollama_responding, délai de 0.5 s), relancé si besoin via Popen([binary, "serve"]) avec une attente allant jusqu'à ~30 s par pas de 500 ms tout en gardant l'interface vivante. ensure_agent_ollama_running() est rappelé avant chaque message (Agent.py:752), parce qu'un serveur lancé par le module ne survit pas à un redémarrage de Slicer.

Windows : CREATE_NO_WINDOW pour ne pas faire clignoter une fenêtre de console. Pas de WSL, contrairement au reste du dépôt.

12. Pièges et points fragiles

Explication en langage courant et maths : page de l'atlas.

  • resolve_tool_path ne trouve rien dans ce dépôt (§8). C'est le bloquant numéro un. Corrections possibles : créer un dossier CLI files avec des liens, définir AGENT_CLI_TOOLS_DIR, ou mettre des chemins relatifs au dépôt dans le manifest et étendre la recherche.
  • 14 signatures sur 16 sont fausses, et le décalage est silencieux.
  • batchdentalseg et clic ne sont pas des CLI. cli_style: ui_module n'est géré nulle part : il tombe dans la branche --flag, qui produit une commande incapable de fonctionner sur un module Slicer scripté.
  • input.folders.split(",") casse tout chemin contenant une virgule, aussi bien pour la liste de dossiers que pour le join(",") côté widget.
  • Le cross-encoder est rechargé à chaque message (processus neuf), et son échec dégrade vers les trois premiers outils du manifest sans que l'opérateur en soit informé.
  • k=3 est codé en dur. 16 outils, 3 candidats : un mauvais score du cross-encoder ne peut pas être rattrapé par le LLM.
  • priority est inerte, ce qui rend trompeur le classement du manifest.
  • subprocess.run bloque le thread de l'interface pendant toute l'exécution du module.
  • L'historique mélange la prose de l'interface et le contexte de routage : les bulles de chat sont renvoyées telles quelles en tours assistant à un routeur contraint au JSON.
  • OnRetrieveButton reconstruit l'historique en découpant sur l'émoji 👨: / 🤖: (Agent.py:1003-1004), seulement quand un fichier de discussion sauvegardé est rechargé : un message contenant ces caractères désynchronise l'alternance. L'historique envoyé au CLI pendant un chat en direct est une liste de tours, pas du texte découpé sur des émojis (Agent.py:736-743).
  • Détection du thème par échantillonnage de pixel (widget.grab(), luminance du pixel (5,5)), parce que QPalette renvoie les couleurs du thème clair même sous un thème sombre dans Slicer (Agent.py:649). Ça marche, mais dépend du moment du premier rendu, d'où le QTimer.singleShot(0, ...) dans setup.
  • Code mort : AgentLogic.process(), build_tool_spec() (et tout le support de patterns/defaults autour), ValidationReport, positional_order, le champ examples du manifest, _cross_encoder_model, Agent_CLI/Resources/UI/Agent_CLI.ui.
  • extract_parameters renvoie 4 valeurs alors que son annotation en déclare 3.
