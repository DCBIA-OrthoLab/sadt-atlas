SurgMovPred

SurgMovPred prédit le mouvement postopératoire de 28 points landmarks à partir d'un tableau de mesures et d'un plan chirurgical. Cette page explique comment, pas à pas, avec les maths : ce qui entre, ce que chaque étape lui fait, et ce qui sort. Les fichiers, les lignes et les pièges sont sur la page de code ; le portage VISOR est sur sa propre page.

Code (développeurs) non publié SurgMovPred_CLI pas de conda : le Python propre de Slicer Bibliographie VISOR

Vue d'ensemble : ce qui entre, ce qui sort

SurgMovPred prédit de combien les os seront déplacés lors d'une opération orthognathique. Il lit un tableau avec une ligne par patient (mesures céphalométriques avant l'opération, plus le mouvement prévu) et écrit un tableau de mouvements postopératoires prédits : 28 points landmarks, chacun avec quatre valeurs. Il ne lit ni scan ni maillage et ne change rien dans la scène Slicer.

SurgMovPred, module legacy
Entréeun dossier de tableaux CSV, XLSX ou ODS, choisi dans le panneau Slicer
Méthode112 modèles entraînés, un par cible ; chacun remet à l'échelle ses 145 entrées et prédit avec un empilement de trois régresseurs
Sortiedeux tableaux au même contenu, predictions_outputs.xlsx et .csv
Oùdans le Python propre de Slicer, sur le processeur

Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957). Le portage VISOR, qui exécute le même algorithme sur un serveur, a sa propre page. Les noms de fichiers, les numéros de ligne et les pièges sont sur la page de code.

1. Place dans le pipeline

SurgMovPred est un outil isolé : rien dans le dépôt ne l'appelle et il n'appelle rien. Son entrée est un dossier de tableurs et sa sortie est un autre tableur. Le module n'est pas branché sur la scène Slicer : c'est une interface de lancement posée sur un script pandas.

Dans le codeLe schéma du pipeline dans le code, l'état de la compilation et les noms d'arguments restants

2. Fichiers en jeu

Le module est un panneau Slicer (trois sélecteurs de dossier et quatre boutons) et un script en ligne de commande qui contient tout le traitement. Seuls trois dossiers sont transmis au script : l'entrée, les modèles et la sortie. Rien d'autre n'est configurable : ni seuil, ni choix des cibles, ni option de classe squelettique.

Dans le codeLe tableau des fichiers et les paramètres déclarés dans le XML

3. Entrée et prétraitement

Le script lit chaque tableur du dossier d'entrée et les empile les uns sous les autres (pas de sous-dossiers ; pour un classeur Excel, seule la première feuille est lue). Il nettoie ensuite les noms de colonnes pour retrouver l'orthographe utilisée à l'entraînement, trouve la colonne de l'identifiant du patient en essayant une liste de noms usuels, et, juste avant la prédiction, met les entrées à l'échelle.

Chaque modèle porte son propre scaler, ajusté sur ses données d'entraînement. Il n'y a pas d'imputation : une cellule vide reste vide à travers la mise à l'échelle, puis le modèle la refuse. L'erreur est interceptée et consignée, et cette cible disparaît du résultat pour tous les patients, pas seulement pour la ligne qui contient la cellule vide. La seule indulgence sur les noms de colonnes est le suffixe _T0 : si le modèle attend X_T0 et que le tableau a X, elle est acceptée. Toute autre colonne manquante fait ignorer le modèle entier, avec un avertissement, et sa colonne est absente du résultat.

Dans le codeLa fonction de lecture, les cinq règles de nettoyage, les motifs d'identifiant et la ligne du scaler

4. Les modèles

Les poids ne sont pas dans le dépôt : le panneau peut télécharger une archive de 112 dossiers de modèles (environ 740 MB) depuis une release GitHub. Pointer le sélecteur de modèle sur le dossier du haut charge les 112 modèles ; pointer sur un sous-dossier n'en charge qu'un. Les 112 sont gardés en mémoire d'un coup (environ 1,5 GB), même pour un seul patient.

Dans le codeL'adresse de téléchargement, la recherche récursive et la hiérarchie de dossiers qui n'existe pas

4.1 Contenu d'un paquet

Chaque fichier de modèle contient quatre éléments : le nom de la cible, la liste ordonnée des 145 colonnes d'entrée, un scaler ajusté et un modèle de stacking ajusté. Ils ont été lus directement dans deux des paquets, sans les exécuter ; le fichier de disposition de VISOR dit la même chose de l'ensemble livré.

Dans le codeLa table des clés et la vérification effectuée

4.2 L'architecture

Il n'y a pas de réseau de neurones. Chaque cible est prédite par un stack de trois régresseurs de base, dont les estimations sont combinées par une régression linéaire. Ces trois régresseurs sont un ElasticNetCV (un modèle linéaire dont la pénalité est choisie par validation croisée), un LightGBM (de nombreux petits arbres de décision ajoutés les uns après les autres) et un processus gaussien (une courbe lisse ajustée à travers les points d'entraînement). Le dépôt n'écrit nulle part pourquoi ces trois-là ont été choisis : le code d'entraînement n'y figure pas.

Dans le codeLes estimateurs et leurs paramètres lisibles

4.3 Les 145 features

Les 145 entrées se répartissent en quatre groupes. 78 sont des positions de points mesurées par rapport à trois plans de référence (horizontal de Francfort, médio-sagittal et coronal) ; 24 d'entre elles sont des points des tissus mous, repérés par une apostrophe dans leur nom. 14 sont d'autres mesures céphalométriques : angles, rapports et largeurs. Les 53 dernières sont des mesures occlusales fournies deux fois : 28 comme état avant l'opération (noms finissant par _T0) et 25 comme mouvement total prévu (finissant par _Total), la plupart dans les deux jeux. Le dépôt ne documente nulle part ce que signifient exactement les deux jeux ; l'idée que le modèle reçoit à la fois l'état de départ et le résultat prévu est une déduction tirée des noms.

Dans le codeLa table des familles avec des exemples et les colonnes lues puis ignorées

4.4 Ce qui est prédit

112 cibles correspondent à 28 structures multipliées par 4 composantes. Trois composantes sont les directions signées d'un déplacement (postérieur ou antérieur, droite ou gauche, bas), et la quatrième est très probablement sa norme ; l'unité n'est écrite nulle part. Les structures sont des points rattachés à un segment osseux : 10 sur le maxillaire, 17 sur la mandibule et un pour la génioplastie. Ce qui est prédit, c'est donc le mouvement de chaque point pris isolément, et non une transformation rigide du segment.

Dans le codeLa liste des 28 structures et le nommage des composantes

5. Le traitement central

Pour chaque paquet, le script prend les colonnes du modèle, les met à l'échelle et prédit. Il n'y a ni post-correction, ni borne, ni cohérence entre cibles, ni intervalle de confiance, bien que l'un des trois régresseurs de base pourrait en fournir un. Chaque cible a sa propre protection : une cible qui plante n'arrête pas les autres, sa colonne disparaît simplement.

Dans le codeLa boucle de prédiction complète

6. Sorties

Le script écrit deux fichiers de même contenu : une table avec l'identifiant du patient, puis une colonne par cible prédite, nommée comme dans le fichier de modèle. Les deux commencent par une colonne de numérotation sans nom. Rien n'est réappliqué à un scan, à un maillage ou à la scène Slicer : la prédiction s'arrête au tableur, et l'opérateur reporte les valeurs dans son logiciel de planification.

Dans le codeLa fonction de sauvegarde, la table des fichiers et la réapplication manquante

8. Environnement

Tout s'exécute dans le Python propre à Slicer, sans conda, sans carte graphique et sans torch. Chaque clic sur Apply vérifie et installe les paquets Python nécessaires, et force une version de numpy fixe, quels que soient les besoins des autres modules de l'extension ; la page de code donne le détail. Sous macOS, une bibliothèque supplémentaire est téléchargée pour LightGBM.

Dans le codeLa liste des paquets, l'épinglage de numpy et l'étape macOS

9. Problèmes connus

  • La version de numpy est fixée à 2.4.0 à chaque Apply, dans le même Python où d'autres modules de l'extension fixent numpy à 1.26.4. Voir le détail.
  • Le bouton des fichiers de test télécharge une archive de tables puis l'ignore, sauf si les données d'un autre module sont présentes ; il télécharge aussi les modèles. Voir la liste.
  • Les fichiers ODS sont annoncés, mais le module n'installe pas le paquet de lecture correspondant. Voir la liste.
  • Une colonne d'entrée manquante retire silencieusement une cible du résultat. Voir la liste.
  • Les tableurs aux colonnes différentes sont concaténés à l'aveugle (une cellule vide fait alors tomber toute la cible), et seule la première feuille Excel est lue. Voir la liste.
  • Les cibles sont prédites indépendamment, si bien que les points d'un même segment osseux ne bougent pas forcément de façon cohérente. Voir le piège.
  • Aucune incertitude n'est fournie, et rien n'est appliqué à la scène. Voir le piège.
