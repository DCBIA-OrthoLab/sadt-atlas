SurgMovPred, legacy : le code

Pour les développeurs : ce que fait le module legacy SurgMovPred dans le code, avec des références file:line, du code, les arguments, l'environnement et les pièges. L'explication lisible avec les maths se trouve sur la page de l'atlas.

Code Atlas (explication) non publié SurgMovPred_CLI pas de conda : le Python propre de Slicer Bibliographie VISOR

Prédiction des mouvements chirurgicaux d'une chirurgie orthognathique à partir d'un tableur de mesures céphalométriques. Pas de réseau de neurones, pas d'image, pas de maillage : 112 régresseurs scikit-learn empilés, un par valeur à prédire, appliqués ligne par ligne à un fichier Excel/CSV.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, est décrit sur sa page VISOR. Le portage se trouve sur la branche main de SADT-VISOR et conserve le même algorithme.

1. Place dans le pipeline

Explication en langage courant et maths : page de l'atlas.

Outil isolé. Rien dans le dépôt ne l'appelle, et il n'appelle rien dans le dépôt : il ne lit aucun volume, aucun maillage, aucun landmark. Son entrée est un dossier de tableurs, sa sortie un autre tableur.

AppeléComment
SurgMovPred_CLIslicer.cli.run(slicer.modules.surgmovpred_cli, …) (SurgMovPred.py:847)

Le module n'est pas branché sur la scène MRML : aucun vtkMRMLNode n'est créé, lu ou transformé. C'est une interface de lancement posée sur un script pandas.

État de la compilation (legacy uniquement)

Le module est compilé avec l'extension : le CMakeLists.txt racine contient add_subdirectory(SurgMovPred) et add_subdirectory(SurgMovPred_CLI) (CMakeLists.txt:60-61), et SurgMovPred/CMakeLists.txt appelle slicerMacroBuildScriptedModule avec l'icône et SurgMovPred.ui. Le texte de l'interface décrit désormais cet outil : le helpText dit "Predicts surgical movement targets from a table of patient measurements" (SurgMovPred.py:233) et le nœud de paramètres documente inputFolder, modelPath et outputFolder (SurgMovPred.py:250). La formulation de résumé de notes copiée de CNE/MedX a disparu.

Legacy (3c67957). Le module n'a pas toujours été dans l'arborescence : le commit 34d496f (2026-09-17, "Drop MedX and SurgMovPred, kept on archive branches, from the working tree") l'a retiré, et dbc9810 et 7947b68 (2026-10-12) l'ont restauré. La branche archive/surgmovpred, locale et sur origin, pointe sur fbfa0fb, le parent du retrait ; fbfa0fb est un ancêtre de 3c67957. Le client VISOR construit à la place son propre module : VISOR:AutomatedDentalToolsRemote CMakeLists.txt:45 ajoute SurgMovPredRemote.

Reste à nettoyer (legacy uniquement)

SurgMovPredLogic.process() nomme encore ses arguments notesFolder_input / notesFolder_output (SurgMovPred.py:815) ; sa docstring le dit désormais et reporte le renommage, parce que tous les appelants les passent par position.

Legacy (3c67957) ; absent de VISOR, qui n'a pas de SurgMovPredLogic : le point d'entrée est run(measurements, output_dir, model) (VISOR:SADT-VISOR tools/Surg_Mov_Pred/src/sadt_surgmovpred/__init__.py:37-46).

3. Entrée et prétraitement

Explication en langage courant et maths : page de l'atlas.

Format accepté. load_data_from_directory() (SurgMovPred_CLI.py:143) collecte tous les fichiers *.csv, *.xlsx, *.ods du dossier (extension en minuscules et en majuscules), les lit (read_csv, read_excel, read_excel(engine='odf')) et les concatène (pd.concat(..., ignore_index=True)). Pas de récursion dans les sous-dossiers. Pour un classeur Excel, seule la première feuille est lue : le fichier de test officiel en contient sept (all_data, demographics, Invivo_ceph, surgical_mov, dolp_ceph_T0, dolp_ceph_T1, dolp_ceph_total), et c'est all_data qui est en première position. Un fichier illisible est consigné dans le journal et ignoré (SurgMovPred_CLI.py:181-182) ; l'exécution n'échoue que si aucun fichier n'a pu être lu (:184-185).

Normalisation des noms de colonnes, clean_name() (SurgMovPred_CLI.py:41), appliquée à l'entrée pour retomber sur l'orthographe utilisée à l'entraînement :

  1. suppression de ", \, [, ] ;
  2. tout caractère hors de [0-9a-zA-Z_'] devient _, l'apostrophe est volontairement conservée (commentaire du code : pour Jarabak's et SM_A'_CP) ;
  3. fusion des _ répétés, nettoyés aux deux extrémités ;
  4. "total" → "Total";
  5. préfixe f_ si le nom commence par un chiffre.

Ce nettoyage explique les vrais noms de features : SM-A-FH   (avec deux espaces à la fin, dans le fichier de test) devient SM_A_FH, Jarabak's ratio   devient Jarabak's_ratio, FMA(MP-FH) Ang_2D devient FMA_MP_FH_Ang_2D.

Identifiant du patient. find_id_column() (SurgMovPred_CLI.py:83) teste 8 motifs insensibles à la casse (#, id, patient id, patient number, subject, …) puis, en dernier recours, toute colonne contenant à la fois « patient » et « id ». Dans le fichier de test, la colonne est #. En cas d'échec, la colonne de sortie IDPatient est remplie de pd.NA avec un simple avertissement.

Normalisation des valeurs. Chaque paquet de modèle embarque son propre StandardScaler calculé (centrage + mise à l'échelle, with_mean=True, with_std=True), appliqué juste avant la prédiction (SurgMovPred_CLI.py:239). Pas d'imputation : une valeur manquante arrive au scaler sous forme de NaN et en ressort NaN, et model.predict lève alors une exception (SurgMovPred_CLI.py:243), si bien que la cible est abandonnée pour toutes les lignes (voir la note ci-dessous). Preuve : les paquets contiennent un ElasticNetCV (chaînes du pickle), et un empilement de substitution ElasticNetCV + GaussianProcessRegressor + LinearRegression, exécuté sur un scikit-learn récent, a levé ValueError: Input X contains NaN. Les vrais paquets n'ont pas été exécutés.

Tolérance sur le suffixe _T0 (SurgMovPred_CLI.py:225) : si le modèle attend X_T0 et que la colonne s'appelle X, elle est acceptée.

Note

C'est la seule indulgence ; toute autre feature manquante fait ignorer le modèle entier avec un avertissement, et la colonne correspondante est absente du résultat.

Aussi vrai dans VISOR : même tolérance sur _T0 et même abandon (VISOR:SADT-VISOR tools/Surg_Mov_Pred/src/sadt_surgmovpred/pipeline.py:229,235). Une différence : si aucun modèle ne peut prédire, VISOR lève une erreur au lieu d'écrire des tableaux sans prédictions (pipeline.py:260).

Une cellule vide supprime toute la cible

Toutes les lignes vont à model.predict en un seul appel (SurgMovPred_CLI.py:243), donc un seul NaN dans une ligne quelconque des colonnes dont un modèle a besoin fait lever une exception à cet appel ; le try/except en :245-246 la consigne et la cible n'a plus de colonne, pour tous les patients. Cela arrive aussi quand on concatène des tableurs de colonnes différentes (:187). VISOR exécute le même code (pipeline.py:243-250). Preuve comme en section 3 : le pickle contient un ElasticNetCV, et un empilement de substitution a levé une exception sur NaN ; les paquets livrés n'ont pas été exécutés.

Environ 740 MB (740 183 656 octets, soit 706 MiB ; la taille vient du même fichier de release dans le manifeste de données de VISOR, VISOR-serve scripts/data-manifest.yml:96-98), 112 dossiers, un stacking_package.pkl d'environ 13 MB chacun. load_all_model_packages() fait un Path.glob("**/stacking_package.pkl") récursif et indexe par package['target_name'] : pointer le sélecteur sur all_models/ charge les 112 modèles, pointer sur un sous-dossier n'en charge qu'un. 4.2 L'architecture

Explication en langage courant et maths : page de l'atlas.

Aucun réseau. Un ensemble en stacking de trois régresseurs de base et d'un méta-régresseur linéaire, sérialisé avec _sklearn_version = 1.6.1 :

RôleEstimateurParamètres lisibles dans le pickle
base multitask_elasticnetElasticNetCVgrille de l1_ratio, n_alphas, eps, selection='cyclic'
base lgbmlightgbm.sklearn.LGBMRegressorboosting_type='gbdt', objective='regression', num_leaves=31
base gaussian_processGaussianProcessRegressornoyau Product(ConstantKernel, RBF), optimizer='fmin_l_bfgs_b', normalize_y
métaLinearRegressionstack_method='predict', passthrough=False

passthrough=False signifie que le méta-modèle ne voit que les prédictions des trois modèles de base, pas les 145 features d'origine. stack_method='predict' : une valeur scalaire par modèle de base, donc une régression linéaire à trois entrées.

L'essentiel du poids du fichier (13 MB pour 145 features) vient du GaussianProcessRegressor, qui conserve sa matrice d'entraînement, et du booster LightGBM.

L'entraînement n'est pas dans le dépôt : ni script, ni jeu de données, ni métriques, ni graine. Impossible à déterminer à partir du dépôt : taille de la cohorte, protocole de validation, performance par cible.

4.3 Les 145 features

Explication en langage courant et maths : page de l'atlas.

Quatre groupes, comptés en lisant les 145 noms de Mn_ALL_BPoint_Down_Pred/stacking_package.pkl (chaînes du pickle, rien d'exécuté) et recoupés avec la feuille all_data du fichier de test :

GroupeNombreExemples
Positions de points par rapport aux trois plans de référence : FH (horizontale de Francfort, 26), MSP (plan médio-sagittal, 30), CP (plan coronal, 22). 24 d'entre eux sont des points de tissus mous, marqués par une apostrophe, et font partie de ce décompte. 78 SM_A_FH, SM_GoL_MSP, SM_PNS_CP, SM_N'_FH, SM_Sn'_MSP
Autres mesures céphalométriques : angles, rapports et largeurs 14 SNA, SM_ANB_signed, SM_Witts, LAFH, Jarabak's_ratio, UAFH_LAFH, FMA_MP_FH_Ang_2D, SM_Mx_Width
Mesures occlusales et dentaires, suffixe _T0 28 MxMn_Overjet_R_T0, MxMn_Molar_Relationship_L_T0
Mesures occlusales et dentaires, suffixe _Total 25 MxMn_Overjet_R_Total, Mn_Gonions_to_Midline_Distances_R_Total

78 + 14 + 28 + 25 = 145. 24 noms de base existent à la fois dans l'ensemble _T0 et dans l'ensemble _Total ; 4 n'existent que sous _T0 (les deux relations molaires et les deux distances à la ligne médiane, côté gauche, des canines inférieures et des premières molaires) et 1 seulement sous _Total (la distance verticale de la canine supérieure gauche). Le layout.py:19-22 de VISOR dit 82 distances point-plan, 28 _T0 et 25 _Total : le 82 est les 78 ci-dessus plus les quatre autres noms en SM_ (SM_ANB_signed, SM_Witts, SM_Mx_Width, SM_Mn_Width), que cette page compte parmi les 14.

Ce que signifient exactement les deux ensembles _T0 / _Total n'est documenté nulle part dans le dépôt. La nomenclature (T0 = avant, Total = variation totale) et le fait que les deux soient du côté entrée suggèrent que le modèle reçoit l'état préchirurgical et le résultat occlusal visé, afin d'en déduire les déplacements osseux à effectuer : c'est une déduction, pas une affirmation du code.

Les colonnes Gender, Surg, Genio, 3piece, assymetry, Skl_Cl_2 du fichier de test n'apparaissent pas parmi les 145 features des deux paquets inspectés : elles sont lues puis ignorées.

4.4 Ce qui est prédit

Explication en langage courant et maths : page de l'atlas.

112 cibles = 28 structures × 4 composantes.

Composantes, d'après les noms de cibles : P-/A+ (postérieur négatif / antérieur positif), R-/L+ (droite négatif / gauche positif), Down+ (vertical, bas positif), et Total. Les trois premières sont donc les composantes signées d'un vecteur de déplacement dans le repère céphalométrique (CP, MSP, FH), la quatrième très probablement son amplitude : déduit des noms, l'unité (mm) n'est écrite nulle part.

Les 28 structures :

SegmentPoints
Maxillaire, Mx_ALL_* (10)APoint, ANS, PNS, U3CanineTip L/R, U6MesialCuspTip L/R, UpperIncisorTip L/R, UpperIncisorTipMidpoint
Mandibule, Mn_ALL_* (17)BPoint, Gnathion, Menton, Pogonion, Gonion L/R, ChinSideCut L/R, MandibleBackCut L/R, L3CanineTip L/R, L6MesialCuspTip L/R, LowerIncisorTip L/R, LowerIncisorTipMidpoint
Génioplastie, Mn_MB_Genioplasty (1)–

ALL désigne le segment osseux entier (maxillaire ou mandibule mobilisé en bloc), MB le segment de génioplastie. Ce qui est prédit, c'est donc le déplacement de points de repère rigidement attachés à chaque segment, prédit, pas une transformation rigide : rien n'oblige les 10 points du maxillaire à être cohérents entre eux (voir §7).

5. Le traitement central

Explication en langage courant et maths : page de l'atlas.

predict_all_targets() (SurgMovPred_CLI.py:196), en entier :

for target_name, pack in packages.items():
    X_target = df_cleaned[[feature_source[f] for f in pack['features_names']]]
    X_target.columns = pack['features_names']
    X_scaled = pack['scaler'].transform(X_target)
    predictions_by_target[target_name] = pack['model'].predict(
        pd.DataFrame(X_scaled, columns=..., index=df_cleaned.index))

Aucune post-correction, aucune borne, aucune cohérence entre cibles, aucun intervalle de confiance : le GaussianProcessRegressor peut produire un écart type, on ne le lui demande pas. Chaque cible est traitée indépendamment, avec un try/except par cible : une cible qui plante n'interrompt pas les autres, sa colonne disparaît simplement.

Les 112 modèles sont chargés en mémoire d'un coup (load_all_model_packages), soit ~1,5 GB de RAM avant même que les données soient lues.

index=True dans les deux cas : l'index pandas (0, 1, 2…) devient une colonne sans nom. Les noms de colonnes sont les target_name bruts des paquets, donc avec / et + (Mx_ALL_APoint_P-/A+_Pred).

Le helpText du panneau dit que le module « writes one result table per input file » (SurgMovPred.py:235-237). La CLI ne le fait pas : elle concatène d'abord tous les fichiers d'entrée (SurgMovPred_CLI.py:187) et écrit un seul tableau (:264-269).

Piège

Il n'y a aucune réapplication du résultat. Rien ne construit de matrice, ne déplace de maillage, ne crée de nœud Slicer ni n'ouvre de vue : la prédiction s'arrête au tableur. La question « comment la prédiction est-elle réappliquée pour produire un résultat visualisable » n'a aucune réponse dans ce dépôt : c'est à l'opérateur de reporter les valeurs dans son logiciel de planification.

Aussi vrai dans VISOR : l'outil ne renvoie que les deux tableaux (VISOR:SADT-VISOR tools/Surg_Mov_Pred/src/sadt_surgmovpred/pipeline.py:276-287), et son client enregistre le résultat sans rien charger (RESULT_KIND = "save_as", VISOR:AutomatedDentalToolsRemote SurgMovPredRemote/SurgMovPredRemote.py:46).

Tout tourne dans le Python de Slicer. check_dependencies() (SurgMovPred.py:153) est appelée à chaque clic sur Apply :

Legacy (3c67957) ; absent de VISOR, où l'outil a son propre environnement virtuel épinglé sur numpy 2.2.6 et où aucune installation n'a lieu à l'exécution (VISOR:SADT-VISOR tools/Surg_Mov_Pred/pyproject.toml:14 ; l'épinglage 2.4.0 n'a volontairement pas été adopté, VISOR:SADT-VISOR tools/Surg_Mov_Pred/README.md:76-80).

onApplyButton appelle d'abord check_dependencies() (SurgMovPred.py:412), et cette fonction exécute slicer.util.pip_install("numpy==2.4.0") à chaque clic, avant de regarder ce qui est installé (SurgMovPred.py:171). D'autres modules de la même extension poussent numpy dans l'autre sens : AMASSS installe 1.26.4 quand numpy est absent ou en 2.x (AMASSS/AMASSS.py:53,74-76), VFACE fait de même quand torch a besoin de numpy 1.x (VFACE/VFACE.py:107,148-158), et MRI2CBCT installe 1.26.4 dès que la version diffère (MRI2CBCT/MRI2CBCT.py:625-626, MRI2CBCT_core/requirements.py:21). Dans une même session Slicer, utiliser SurgMovPred et l'un de ces modules fait passer numpy de 2.4.0 à 1.26.4 et inversement.

Non démontré ici : que cela casse scipy ou un autre paquet. Le code montre le conflit d'épinglages, pas une panne ; le README de VISOR dit seulement que l'amont épingle 2.4.0 « because Slicer's shared interpreter needs it for other reasons » (VISOR:SADT-VISOR tools/Surg_Mov_Pred/README.md:78-79).

L'installation se fait sans conda, sans GPU, sans torch.

La CLI fait taire l'InconsistentVersionWarning de scikit-learn (SurgMovPred_CLI.py:19) : les paquets ont été sérialisés avec scikit-learn 1.6.1 et sont désérialisés avec la version qui se trouve être installée. Le commentaire accepte le risque (« models are tested for compatibility before being shipped »).

9. Pièges et points fragiles

Explication en langage courant et maths : page de l'atlas.

  • pip_install("numpy==2.4.0") à chaque exécution. D'autres modules de l'extension installent numpy 1.26.4 (AMASSS, VFACE, MRI2CBCT), donc la version peut osciller entre les deux au sein d'une même session Slicer. Si cela casse quelque chose n'a pas été testé (détails).
  • Bouton « Test files » à moitié inopérant : DownloadTestFiles() (SurgMovPred.py:763) télécharge bien TestFiles.zip, mais ne remplit les champs d'entrée/sortie que if os.path.exists(.../V_FACE/DefaultList) (:773), un reste de copier-coller du module VFACE. Sans les données de test de VFACE, l'archive est téléchargée puis ignorée. Le même bouton appelle ensuite onDownloadDefaultModel() (:780), donc il télécharge aussi les 740 MB de modèles et remplit le champ du modèle.
  • .ods annoncé, odfpy non installé par check_dependencies (il l'est pourtant par le module Anonymizer, Medical_Data_Anonymizer_Module.py:411, ce qui peut masquer le problème sur une machine où les deux ont été utilisés).
  • Une feature manquante = un modèle ignoré en silence. Le journal dit « Model 'X' skipped: missing N input feature(s) », mais le fichier de sortie se retrouve simplement avec une colonne de moins. Un tableur mal nommé peut produire un predictions_outputs.xlsx sans aucune colonne de prédiction et sans aucun échec.
  • Concaténation aveugle des fichiers d'entrée : deux tableurs de colonnes différentes donnent NaN dans les colonnes qui manquent à l'un d'eux, et model.predict sur NaN lève une exception ; l'erreur est interceptée par cible, donc ces cibles disparaissent pour tous les patients (note) et le résultat sort partiel sans que grand-chose ne le montre.
  • Une seule feuille Excel est lue. Un classeur dont la première feuille n'est pas la feuille de données produit un résultat vide.
  • 1,5 GB de modèles chargés systématiquement, même pour une seule ligne à prédire, même si l'opérateur ne s'intéresse qu'à une seule cible.
  • Aucune incertitude en sortie alors que l'un des trois modèles de base est un processus gaussien.
  • Aucune cohérence rigide entre les points d'un même segment (§7).
  • process() nomme encore ses arguments notesFolder_input / notesFolder_output (SurgMovPred.py:815), un reste de l'outil de notes cliniques ; le helpText et la docstring du nœud de paramètres ont été réécrits et n'en portent plus la trace.

10. Littérature

Explication en langage courant et maths : page de l'atlas.

Aucun article ne couvre SurgMovPred. Ni le dépôt, ni la release, ni le README ne citent de référence, et une recherche sur le nom du module ne renvoie rien. Le module n'est même pas listé dans le README de l'extension.

Le contexte publié, à ne pas confondre avec une description de ce code :

  • Machine-learning-based approach for predicting postoperative skeletal changes for orthognathic surgical planning (PubMed 35132764) : le problème posé est le même (prédire les déplacements squelettiques postopératoires à partir de mesures préopératoires), mais rien n'indique que ce soit le travail derrière ces poids.
  • Oliveira, Cevidanes, Bianchi et al., Artificial intelligence as a prediction tool for orthognathic surgery assessment, Orthodontics & Craniofacial Research, 2024, même équipe (UNC/Pacific), mais une cible différente : prédire le besoin de chirurgie à partir de téléradiographies de profil, pas les mouvements eux-mêmes.
  • Prediction of orthognathic surgery plan from 3D cephalometric analysis via deep learning (PMC10024836) : même objectif, approche par apprentissage profond ; SurgMovPred, lui, est un modèle tabulaire classique.

Les outils sous-jacents, eux, sont documentés : StackingRegressor et LightGBM.
