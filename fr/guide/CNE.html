CNE : extraire des informations de notes cliniques

Le nom ne le dit pas : CNE ne touche aucune image, aucun volume, aucun maillage. C'est un outil de lecture : il prend des notes cliniques en texte libre et en tire des informations structurées, sous forme de paires clé/valeur, à l'aide d'un modèle de langage (LLM) qui tourne localement dans Slicer.

Deux façons de le lancer

Cette page décrit le module Slicer legacy. Pour l'utiliser via un serveur VISOR : voir CNE avec VISOR et, pour le flux de travail général, Utiliser VISOR. Notez qu'avec un serveur VISOR vos notes sont envoyées à ce serveur.

Quand s'en servir

À chaque fois que vous avez un lot de notes en texte libre, consultations TMJ ou Ortho, et que vous voulez en tirer rapidement les faits clés (symptômes, diagnostics) au lieu de les lire une à une. CNE traite un dossier entier de notes d'un coup, avec un modèle différent selon que les notes sont TMJ ou Ortho.

Rien ne quitte votre machine (module legacy uniquement)

Cela vaut pour le module Slicer legacy uniquement, pas pour VISOR. Dans le module legacy, le modèle tourne dans le Python propre à Slicer, sur votre ordinateur. Les notes ne sont envoyées à aucun service en ligne pendant l'extraction : la seule étape qui touche le réseau est le téléchargement unique du modèle. Avec un serveur VISOR, le texte de vos notes est envoyé à ce serveur : voir CNE avec VISOR.

Ce qu'il vous faut, ce que vous obtenez

À fournir

  • Un dossier de notes, placées directement dedans (pas de sous-dossiers) : .txt, .pdf ou .docx
  • Le type de note : TMJ ou Ortho, chacun avec son propre modèle
  • Le modèle correspondant, téléchargé une seule fois (quelques Go)

Ce qui sort

  • Un fichier texte par note, Extraction_<note name>.txt, dans le dossier de sortie
  • Des lignes key : value qui résument la note
  • Pas de tableau récapitulatif issu de l'extraction elle-même : un fichier par note, à vérifier un par un. Le bouton Dashboard (plus bas) construit ensuite un tableau et une figure

Étapes

  1. Choisissez le type de note. TMJ ou Ortho : cela décide du modèle utilisé et de la longueur de note qu'il peut absorber d'un seul coup.
  2. Téléchargez le modèle correspondant. Au premier clic sur « Apply », le module installe ce qui manque (après votre confirmation), puis récupère le modèle sur Hugging Face. À faire une seule fois par type de note.
  3. Désignez le dossier des notes. Les fichiers doivent se trouver directement à la racine du dossier choisi, pas rangés dans des sous-dossiers par patient.
  4. Indiquez un dossier de sortie.
  5. Lancez, puis attendez. Les notes sont traitées l'une après l'autre ; comptez plusieurs dizaines de secondes par note.

Le bouton Dashboard

À côté de Run, le module a un bouton Dashboard. Il dessine une image de synthèse (dashboard.png) et écrit le tableau à partir duquel elle est dessinée (patient_data.csv), d'après les fichiers Extraction_*.txt déjà présents dans votre dossier de sortie. Il n'extrait rien et n'a besoin d'aucun modèle : lancez d'abord l'extraction, puis appuyez sur Dashboard avec le même dossier de sortie sélectionné. Les pourcentages et les moyennes sont calculés sur toutes les notes du dossier, pour des éléments comme les tranches d'âge, les scores de douleur, l'ouverture buccale, les localisations des céphalées et le déplacement discal.

Le Dashboard est conçu pour les notes TMJ

Il cherche les champs qu'écrit le modèle TMJ (céphalée, claquement de la mâchoire, déplacement discal, ouverture maximale...). Les extractions faites en mode Ortho listent à la place des constats orthodontiques (taille du fil, élastiques, overjet...), et elles arrêteraient donc très probablement le Dashboard sur une erreur indiquant que les clés ne correspondent pas. C'est une déduction tirée des listes de champs dans le code et sur les fiches de modèle, non testée sur une sortie Ortho.

La première fois, le module peut demander l'autorisation d'installer matplotlib et pandas, dont le Dashboard a besoin et que Slicer ne fournit pas.

Combien de temps, combien de mémoire

Même si le module mentionne l'usage d'une carte graphique, l'installation ne met en place que des paquets pour CPU : en pratique, l'extraction tourne toujours sur CPU. Comptez environ une minute par note selon sa longueur ; sur un lot de plusieurs dizaines de notes, mieux vaut lancer l'exécution et revenir plus tard. Le modèle chargé demande environ 5 à 6 Go de RAM en plus de ce que Slicer utilise déjà, et son téléchargement fait plusieurs gigaoctets, une seule fois par type de note.

Vérifier le résultat

Tout le contenu clinique du fichier de sortie vient du modèle : aucune règle, aucun dictionnaire de termes, aucun contrôle de schéma ne le soutient. Le module attend une réponse JSON mais ne l'impose pas techniquement : il cherche simplement la première accolade ouvrante et la dernière accolade fermante dans la réponse. Si la sortie du modèle est mal formée, son texte brut atterrit tel quel dans le fichier, sans aucune indication que la mise en forme a échoué. Vérifiez chaque fichier produit avant de vous y fier.

Si ça coince

Notes rangées dans des sous-dossiers par patient

CNE ne regarde que les fichiers placés directement dans le dossier que vous avez choisi, pas ce qui se trouve dans les sous-dossiers. Un dossier organisé avec un sous-dossier par patient ne produira aucune sortie, sans aucun message d'erreur.

PDF numérisé

L'extraction de texte des PDF ne fait pas d'OCR : si votre PDF est en réalité une image numérisée, le texte extrait est vide et la note ne peut rien produire.

Tableaux dans un .docx

Seul le texte des paragraphes est lu dans un document Word ; le contenu des tableaux est ignoré. Si vos informations clés se trouvent dans un tableau, elles n'atteignent jamais le modèle.

Note trop longue

Il n'y a pas de découpage : une note plus longue que ce que le modèle peut lire en une seule passe échoue entièrement au lieu d'être traitée en morceaux. La marge est particulièrement serrée en mode Ortho.

Pas d'anonymisation

Les notes sont lues telles quelles, sans suppression des données personnelles. Si vos fichiers contiennent des informations identifiantes, passez-les d'abord par MedicalDataAnonymizer si nécessaire.

Comment citer

Le module n'a pas de publication, et les modèles qu'il exécute sont des fine-tunes du laboratoire déposés sans model card : ni jeu d'entraînement décrit, ni évaluation. Les lectures ci-dessous disent ce qu'on sait, en général, de la fiabilité de ce genre d'extraction.

Rien ne décrit le module lui-même, citez donc l'extension comme logiciel :

SlicerAutomatedDentalTools. DCBIA-OrthoLab. https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools

Ajoutez la date à laquelle vous l'avez consultée si le style de votre revue la demande.

Contexte, à ne pas citer pour l'outil

  • Wiest et al., npj Digital Medicine 2024: Privacy-preserving large language models for structured medical information retrieval. Exactement l'usage visé, extraire des champs structurés d'un compte rendu avec un modèle qui tourne en local, et ce que ça donne réellement.
  • Panchal et al., BMJ Health & Care Informatics 2026: Benchmarking large language models for de-identification of electronic health record notes. Une comparaison chiffrée de plusieurs modèles sur des notes cliniques : où ils se trompent, et sur quels types de champs.
  • Dorémus et al., JMIR 2025: Harnessing Moderate-Sized Language Models for Reliable Patient Data Deidentification in Emergency Department Records. Ce qu'on peut attendre d'un modèle de la taille de ceux employés ici, plutôt que d'un très gros modèle distant.

La bibliographie complète de l'outil, ce qui a été trouvé, et ce qui a été cherché sans rien trouver, est dans ses sources.
