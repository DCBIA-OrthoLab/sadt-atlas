MRI2CBCT

MRI2CBCT place une IRM de l'articulation de la mâchoire sur le CBCT du même patient. Il prédit la base du crâne sur les deux scans avec deux réseaux, puis aligne les deux surfaces prédites et vérifie le résultat. Cette page explique comment, pas à pas, avec les maths : ce qui entre, ce que chaque étape en fait, et ce qui sort. Les fichiers, les lignes et les pièges sont sur la page de code. Il n'y a pas de portage VISOR : voir ce qui existe.

Code (développeurs) Leroux 2024 · version antérieure, CLIP, LNCS 15196 3 CLI MRI2CBCT_* + 4 empruntés Python de Slicer, pas de conda Bibliographie VISOR : non porté

Vue d'ensemble : ce qui entre, ce qui sort

MRI2CBCT place une IRM de l'articulation de la mâchoire (l'articulation temporo-mandibulaire) sur le CBCT du même patient. Le module apparie un dossier d'IRM avec un dossier de CBCT, oriente chaque CBCT, prédit la base du crâne sur les deux scans avec deux réseaux, puis aligne les deux surfaces prédites. Les images elles-mêmes ne sont jamais comparées : seuls les deux masques de la base du crâne sont utilisés. Quand le résultat sort tourné dans le mauvais sens, une échelle de récupération essaie d'autres possibilités. L'ensemble de l'exécution est lancé par un seul bouton Run et peut s'interrompre après n'importe quelle étape pour que le clinicien la vérifie.

Entréeun dossier d'IRM et un dossier de CBCT, appariés par identifiant de patient

Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, la version réécrite). Il n'y a pas de portage VISOR : voir ce qui existe de MRI2CBCT dans VISOR. Les noms de fichiers, les numéros de ligne et les pièges sont sur la page de code.

Dans le codeQuelle base de code cette page décrit

1. Situation dans la chaîne

Sept étapes sont enchaînées par le panneau : trois petits programmes qui lui sont propres (préparer, segmenter l'IRM, recaler) et quatre empruntés à ASO, ALI et AMASSS (les autres outils du laboratoire : ASO oriente un CBCT, ALI y trouve des landmarks, AMASSS le segmente). Rien d'autre n'appelle les trois nouveaux programmes. La liste des étapes est construite une seule fois et le panneau exécute ce qu'elle renvoie ; les programmes empruntés reçoivent de nouveaux dossiers sous la sortie pour ne pas reprendre de fichiers périmés. Le module ne dépend plus de SlicerNNUNet : nnU-Net est installé avec pip.

Dans le codeLe tableau de ce qui est appelé, comment et quand, avec les lignes

2. Fichiers en jeu

Un fichier de panneau, plus un paquet sans dépendance à Slicer qui porte la logique : le plan des sept étapes, l'appariement, la préparation de l'IRM, l'inférence du réseau IRM, le recalage avec son échelle, les conversions entre repères de coordonnées, et la configuration de l'environnement et des modèles. Tout s'exécute dans le Python de Slicer. Les trois nouveaux programmes ont chacun besoin du manifeste écrit par le premier et des fichiers laissés par les étapes précédentes, donc ils ne sont pas utilisables seuls.

Dans le codeLe tableau des fichiers, les trois programmes et leurs arguments

3. Ordre du pipeline, et ce qui est réellement obligatoire

L'ordre est le suivant : apparier les patients, éventuellement rééchantillonner et séparer la gauche de la droite, orienter le CBCT, prédire la base du crâne sur le CBCT, la prédire sur l'IRM, recaler. Les étapes 1 à 6 sont toutes obligatoires, car le recalage (étape 7) lit les fichiers qu'elles laissent derrière elles ; seuls le rééchantillonnage et la séparation gauche-droite à l'intérieur de la première étape sont des options, toutes deux activées par défaut. Cinq pauses de revue facultatives sont désactivées par défaut. Cliquez sur une boîte pour lire sa section.

Dans le codeLe tableau des étapes avec leur statut, leur raison et leurs codes de sortie

4. Appariement et préparation de l'IRM

Avant l'exécution de tout réseau, le module doit décider quelle IRM appartient à quel CBCT et ce que contient chaque fichier IRM.

4.1 Appariement par identifiant de patient

La modalité vient du dossier choisi par le clinicien, jamais du nom de fichier. L'identifiant du patient est constitué des lettres initiales suivies d'un nombre (P01, B038) ; les zéros de tête et les majuscules ne comptent pas, donc P1 et p01 sont le même patient. Les dossiers sont parcourus récursivement. Un fichier ou un patient est écarté, avec un message, quand aucun identifiant ne peut être lu, quand il y a une IRM sans CBCT ou l'inverse, ou quand il y a plus d'un CBCT pour le même identifiant. Le panneau les liste et demande confirmation. Le panneau vérifie aussi si les deux dossiers ont été inversés, en ne regardant que les en-têtes de fichiers : une IRM a des voxels nettement non cubiques ou un petit champ, un CBCT a des voxels cubiques et un champ d'au moins 12 cm.

Dans le codeLa fonction d'appariement, l'expression régulière et la détection d'inversion avec leurs seuils

4.2 Préparation de chaque IRM

L'en-tête de l'IRM est conservé tel quel : la version précédente écrasait la matrice de direction, ce qui effaçait le seul enregistrement du sens dans lequel les coupes s'enchaînent. Pour chaque fichier, le module décide d'après sa taille et les intervalles entre coupes s'il contient une articulation ou les deux et, avec l'option activée, les sépare.

Le côté d'une coupe contenant une seule articulation se lit là où son en-tête la place : une coupe en position gauche-droite positive est dite gauche. Si les deux articulations ont été acquises en deux piles séparées par un intervalle, chaque pile est reconstruite à l'espacement d'acquisition (3,0 mm par défaut). Avec le rééchantillonnage activé, chaque articulation obtenue est ramenée à des voxels isotropes de 0,3 mm.

Dans le codeLa fonction de décision, la règle du côté, le test de l'intervalle et le rééchantillonneur

5. Orienter le CBCT (ASO)

Trois programmes empruntés à ASO et ALI mettent le CBCT dans une pose standard. Le premier centre le scan ; le deuxième place sept landmarks (Ba, LPo, N, RPo, S, LOr, ROr) avec les modèles entraînés d'ALI ; le troisième tourne le scan sur l'horizontale de Francfort et sur le plan médio-sagittal de référence calculés à partir de ces points. Le résultat est un CBCT orienté et la transformation qui ramène au scan d'origine. L'orientation compte ici pour une raison concrète : le CBCT est coupé en une moitié gauche et une moitié droite à la médiane de sa base du crâne (section 7), ce qui n'a de sens que lorsque la tête est en pose standard.

Dans le codeLes trois programmes, leurs arguments et les fichiers qu'ils écrivent

6. Les deux réseaux

Aucun des deux réseaux ne recale quoi que ce soit. Chacun produit un masque binaire de la base du crâne : AMASSS sur le CBCT orienté, et un nnU-Net entraîné pour l'occasion (appelé Dataset516) sur chaque articulation d'IRM préparée. Le recalage travaille ensuite sur les surfaces de ces deux masques. Le réseau IRM tourne sur la carte graphique quand il y en a une, sur le processeur sinon, et peut utiliser ses cinq folds ou seulement le premier sur un ordinateur sans carte. Toutes les articulations de tous les patients passent par un seul prédicteur en un seul appel. La façon dont le réseau IRM a été entraîné et évalué n'est documentée nulle part dans le dépôt.

Dans le codeLe tableau comparatif des deux réseaux, les variables d'environnement et la documentation manquante

7. Recalage

Pour chaque patient, le masque de base du crâne du CBCT est chargé une fois, avec la transformation d'orientation, et chaque articulation est recalée sur lui. Les images ne sont pas lues à ce stade : les seules entrées sont deux masques.

Dans le codeLa boucle de recalage et ses entrées

7.1 Surfaces

Chaque masque devient un nuage de points de surface avec leurs normales. Le masque IRM est d'abord nettoyé : il est seuillé, refusé s'il compte moins de 50 voxels, et réduit à sa plus grande composante connexe, car des îlots détachés auraient leurs normales inversées à l'étape suivante. La surface du CBCT est ensuite coupée au côté scanné pour une IRM d'une seule articulation, ce qui permet de recaler une coupe d'une articulation sur une tête entière.

Dans le codeLes fonctions de surface, le filtre de composantes, le nombre de points et le code de coupe par côté

7.2 Un tirage

Un tirage comprend trois étapes. Les deux nuages sont d'abord éclaircis sur une grille de 1,5 mm. Une recherche globale rapide apparie ensuite des descripteurs de forme locaux, de courtes listes de nombres qui décrivent la courbure de la surface autour d'un point (FPFH, calculés dans un voisinage de 7,5 mm), entre les deux nuages, et une boucle RANSAC (suppositions aléatoires répétées, chacune notée selon le nombre d'appariements qui s'y accordent) choisit trois appariements à la fois, garde la pose qui s'accorde le mieux et s'arrête à 0,999 de confiance ou après quatre millions d'essais. Enfin, un ICP point-à-plan affine cette pose. La recherche globale est là parce que l'ICP seul est local et s'est une fois fixé sur un retournement de 172 degrés pour un patient. Les tirages sont indépendants et tournent en parallèle dans des processus séparés.

Dans le codeLe tableau des paramètres, le pool de workers et le réglage des threads

7.3 Le verdict

Un court test, qui n'a besoin d'aucune transformation de référence, attribue à chaque articulation une étiquette, dans cet ordre : FLIP si la rotation dépasse 90 degrés (le seul critère qui ait détecté les échecs gauche-droite ; la fitness ne le faisait pas), FLAG si la fitness est inférieure à 0,75, SMALL si le masque IRM est plus petit que 11,21 cm³ (un avertissement : selon le commentaire du code lui-même, tous les retournements venaient de ce groupe), sinon OK.

Dans le codeLa fonction d'étiquetage avec ses seuils et la statistique de cohorte citée dans le commentaire

7.4 L'échelle FLIP

Quand la meilleure pose du barreau 0 (le premier recalage, 50 tirages) est un retournement, le module gravit les barreaux 1 à 4 d'une échelle de remèdes de plus en plus drastiques, et s'arrête au premier qui donne une pose qui n'est pas un retournement et dont la fitness est d'au moins 0,75 :

  1. Barreau 1, plus de tirages : 100 de plus, on garde la meilleure pose réussie parmi les 150.
  2. Barreau 2, rotation de 180 degrés : on tourne la pose retournée de 180 degrés autour de chacun des trois axes, passant par le centre de la surface IRM, et on affine chacune par ICP.
  3. Barreau 3, l'autre côté : pour une IRM d'une seule articulation, on coupe le CBCT à la moitié opposée et on recale de nouveau avec 50 tirages, car l'étiquette de côté peut être fausse. Si cela fonctionne, l'articulation est rebaptisée de l'autre côté.
  4. Barreau 4, miroir : on réfléchit la surface IRM de gauche à droite et on recale de nouveau avec 50 tirages ; cela répare un fichier dont la latéralité est fausse.

Si aucun barreau ne réussit, le cas reste non résolu : la meilleure pose du barreau 0 est écrite avec le suffixe _FLAGGED.

Le recalage ne regarde jamais les intensités de l'image : tout ce que les deux segmentations manquent ou inventent, le recalage l'hérite. C'est l'inverse de la version précédente, où la segmentation du CBCT n'était qu'un masque et où l'appariement se faisait sur les intensités.

Dans le codeLe code de l'échelle avec les matrices de rotation et de miroir et les règles d'acceptation

8. Sorties, et le repère dans lequel elles sont

Tout est écrit dans le repère du CBCT d'origine, pas dans celui du CBCT orienté : la transformation finale compose le recalage avec l'inverse de la transformation d'orientation. Par patient, le module écrit l'IRM recalée sur le CBCT, son masque de base du crâne, le fichier de transformation (IRM vers CBCT, dans la convention d'ITK), et, une fois par patient, le masque de base du crâne du CBCT ; un fichier summary.csv contient une ligne par articulation avec l'étiquette, la fitness, la rotation, le volume du masque et le barreau qui l'a résolue. Par défaut, les volumes gardent les voxels propres de l'IRM et seules leur position et leur direction sont réécrites : rien n'est interpolé et l'IRM s'ouvre par-dessus le CBCT dans n'importe quelle visionneuse ; une option rééchantillonne plutôt sur la grille du CBCT. Un patient en échec produit une ligne marquée comme échouée et les autres continuent.

Dans le codeLe tableau des fichiers, les conversions de repère et les lignes d'échec

9. Le panneau

Le panneau affiche une ligne d'installation unique (paquets et modèles, environ 5 GB d'après sa propre estimation), les trois dossiers et un bouton pour utiliser un patient d'exemple, les options (rééchantillonner à 0,3 mm, séparer gauche et droite avec l'espacement d'acquisition, et des choix avancés : les cinq folds ou un seul, mettre le résultat sur la grille du CBCT, garder le dossier intermédiaire, nombre de workers de recalage), et les pauses de revue. À une pause, le panneau charge l'image avec le masque dessiné en contour dans une disposition à quatre vues, un élément par patient ou par articulation, et la première pause propose un bouton pour échanger la gauche et la droite d'un patient. À la fin, un message liste le verdict de chaque articulation.

11. Problèmes connus

  • Un recalage faible (fitness inférieure à 0,75, mais pas un retournement) garde un nom de fichier propre ; seul le tableau récapitulatif le signale. Voir le piège.
  • Un retournement non résolu écrit la meilleure pose des 50 premiers tirages, pas la meilleure trouvée par les barreaux suivants. Voir le piège.
  • Le côté vient de l'endroit où l'en-tête place la coupe : un fichier mal centré reçoit donc le mauvais côté sans aucun message. Voir le piège.
  • Un dossier de sortie placé à l'intérieur d'un dossier d'entrée est relu à l'exécution suivante. Voir le piège.
  • Le journal d'exécution ne survit pas à une exécution réussie. Voir la note.
  • Seule la surface de l'IRM est nettoyée pour ne garder que sa plus grande composante connexe. Voir la note.

12. Environnement

Tout tourne dans le Python de Slicer, sans conda. La carte graphique est facultative pour le réseau IRM. À la première utilisation, le panneau installe les paquets Python et télécharge les modèles dans les dossiers que les modules empruntés utilisent déjà, de sorte que rien n'est récupéré deux fois ; les versions, la gestion de numpy et les chemins figurent sur la page de code.

Dans le codeLe tableau d'environnement avec les versions, les chemins et les variables de remplacement

12.1 Open3D sous Linux

Open3D, la bibliothèque derrière le recalage, demande une installation particulière sous Linux, que le panneau effectue. L'étape de recalage échoue aussitôt avec un message clair si Open3D est absent, alors que le panneau lui-même s'ouvre sans lui ; les détails sont sur la page de code.

13. Littérature

L'article lié depuis cet outil (Leroux et al., CLIP 2024) décrit la séquence antérieure : orientation automatique, rééchantillonnage, inversion de l'IRM, normalisation et recalage rigide par information mutuelle. Ce n'est plus ce que fait le code : le recalage actuel est une recherche globale sur deux surfaces prédites et n'utilise aucune intensité. Aucun document du dossier ne décrit l'appariement de descripteurs, le RANSAC ou l'échelle, et les commentaires du code citent des scripts extérieurs au dépôt ; c'est une question à poser aux mainteneurs. La seule évaluation numérique publiée est antérieure à la réécriture : rien de publié ne mesure donc la version actuelle.
