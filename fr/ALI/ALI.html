ALI

ALI place automatiquement des points anatomiques, appelés landmarks, sur un scan 3D. Cette page explique comment, pas à pas, avec les maths : ce qui entre, ce que chaque étape lui fait, et ce qui sort. Le module est un répartiteur entre deux programmes distincts : ALI_CBCT, où un agent marche dans un volume de tête, et ALI_IOS, où une dent est photographiée par des caméras virtuelles. Là où le code fait quelque chose qui mérite d'être vérifié, un lien mène vers la page de code. Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26) ; le portage serveur est ALI sur VISOR.

Code (développeurs) Gillot 2023 · Orthod Craniofac Res ALI_CBCT ALI_IOS CBCT : Python Slicer, IOS : env conda shapeaxi VISOR Bibliographie

Vue d'ensemble : ce qui entre, ce qui sort

ALI prend une image 3D d'un patient et renvoie une liste de points 3D, chacun avec un nom : la pointe d'une dent, un point de la base du crâne. Le module affiché dans Slicer ne calcule rien lui-même. Il demande seulement quel type d'image vous avez et confie le travail à l'un de deux programmes distincts, qui ne partagent aucun code. D'autres outils utilisent ensuite ces points pour orienter un scan ou pour recaler deux scans.

Les coordonnées sont écrites en LPS. Les deux programmes tournent dans des environnements Python différents : ALI_CBCT dans celui de Slicer, ALI_IOS dans un environnement conda séparé, parce qu'il a besoin d'une bibliothèque graphique que Slicer ne fournit pas.

1. Situation dans la chaîne

ALI est un fournisseur de landmarks pour la plus grande partie de la boîte à outils. Les modules qui l'appellent, et pourquoi :

  • ALI lui-même, utilisé directement, pour les deux modes.
  • ASO demande à ALI_CBCT des landmarks pour orienter un scan.
  • AREG_IOSCBCT demande aux deux 12 points occlusaux sur le CBCT et sur le maillage, pour recaler l'un sur l'autre.
  • GreedyReg (recalage distant) demande à ALI_CBCT un recalage par landmarks.
  • FlexReg demande à ALI_IOS les 13 points mucogingivaux du patch inférieur.

Quand un maillage n'a pas d'étiquettes de dents, ALI_IOS a d'abord besoin d'une segmentation des couronnes. Il peut la lancer lui-même ou la recevoir du widget : deux voies vers le même résultat.

Dans le codeLes appelants, avec fichier et ligne, et les autres outils qui appellent ALI

2. Fichiers en jeu

Deux programmes et un widget qui choisit entre eux. ALI_CBCT tourne dans le Python propre à Slicer, donc sans environnement supplémentaire. ALI_IOS a besoin de pytorch3d, qui n'existe pas dans Slicer : il passe par un environnement conda partagé avec plusieurs autres outils. Ni l'un ni l'autre n'exige une carte graphique, mais les deux sont beaucoup plus lents sans.

3. ALI_CBCT : des agents dans le volume

L'idée vient de l'apprentissage par renforcement, mais à l'exécution rien n'est appris : un réseau entraîné sert de boussole. Pour chaque landmark il y a un agent, c'est-à-dire une position dans le volume. À chaque pas, le réseau regarde un petit cube de l'image autour de l'agent et dit lequel des six déplacements d'un voxel le rapproche le plus du landmark. L'agent bouge, regarde de nouveau, et recommence jusqu'à tourner en rond, ce qui signifie qu'il est arrivé. Il fait cela sur une grille grossière, puis de nouveau sur une grille fine, et moyenne six derniers essais.

3.1 Prétraitement

Deux opérations, une fois par scan, avant qu'aucun agent ne bouge.

Les fichiers écrits pour chaque grille portent le nom du scan et sont réutilisés s'ils existent déjà : un cache, donc aussi un piège si l'entrée change sans changer de nom. Au chargement, le volume est en outre réorienté en LPS et complété de 33 voxels de marge de chaque côté, pour que le cube que regarde l'agent contienne toujours des données, même au bord.

Dans le codePercentiles, classes, interpolation, fichiers de cache et marge ajoutée au chargement

3.2 L'environnement

L'« environnement » est un patient : l'image à chacune des deux grilles. Il répond à une seule question de l'agent, qu'y a-t-il autour de cette position ?, et il y répond par un cube.

Dans le codeLa classe de l'environnement et l'appel de découpe

3.3 L'agent et son réseau

Le réseau est un DenseNet 3D (un réseau convolutif qui lit le petit cube 3D) suivi d'une petite tête de décision (les dernières couches, qui transforment ce que le DenseNet a trouvé en six scores). Ce n'est pas une heatmap : il ne dit pas où est le point, il dit dans quel sens avancer. Il y a un agent par landmark, et un réseau par landmark et par grille : le programme reconstruit les réseaux et relit leurs poids pour chaque scan et chaque landmark. La tête se termine par une ReLU, une opération qui ramène chaque score négatif à 0, donc si les six scores sont négatifs avant elle, tous deviennent 0 et l'agent prend le premier déplacement (voir problèmes connus).

Dans le codeLa définition du réseau, l'ordre des déplacements et la ReLU

3.4 La recherche

Règles autour de la marche : un déplacement qui sortirait de la zone où un cube entier peut encore être lu (un voxel au-delà de chaque face du scan) est refusé, et l'agent réapparaît à une position aléatoire (n'importe où à l'échelle grossière ; à moins de 10 voxels de l'endroit où l'échelle a commencé à l'échelle fine). Un agent qui tourne sur un terrain où il est déjà passé pendant 64 pas de suite réapparaît aussi. Après trois réapparitions, le landmark est abandonné. Le nombre de pas est lui aussi borné : le module legacy arrête une recherche après 1000 pas par défaut, avec une garde de 900 s.

Dans le codeLa boucle de l'agent, la mémoire, la réapparition, le budget de pas et la moyenne finale dans le code

3.5 Sortie

La valeur absolue suppose que l'origine est négative sur les trois axes, ce qui est vrai pour un volume LPS centré sur l'origine. Comme le module legacy réoriente d'abord chaque volume en LPS, les dégâts sont limités (problèmes connus).

Les points sont regroupés par famille anatomique (CB, U, L, CI) et un fichier est écrit par groupe, coordonnées en LPS. Le champ de description de chaque point est toujours vide.

Dans le codeLa conversion des coordonnées et l'écriture des markups

3.6 Poids

Les réseaux entraînés sont trouvés par l'organisation de leurs dossiers : un dossier par landmark, un sous-dossier par grille (1 mm et 0.3 mm). Le module télécharge huit archives (base du crâne, mandibule, dents inférieures et supérieures), et ASO et GreedyReg récupèrent les mêmes poids depuis une autre release.

Dans le codeLa découverte des poids et les huit archives

4. ALI_IOS : rendu multi-vues

Le maillage est ramené dans une sphère unité. Autour de chaque dent, quelques caméras virtuelles prennent des images. Un réseau 2D étiquette chaque pixel, et les pixels de la classe landmark sont rattachés aux triangles du maillage, dont le centre est le landmark. Le réseau est la seule partie entraînée ; tout le reste est de la géométrie.

4.1 Entrées

Cinq formats de maillage sont lus. Mais tout dépend d'un tableau d'étiquettes de dents sur le maillage : il donne le centre de chaque dent, et donc l'endroit où va la caméra. Sans lui, aucune dent n'est trouvée. Si le scan n'en a pas, une segmentation des couronnes est lancée d'abord, sur une copie du fichier ; elle ne déplace pas les points, donc les landmarks restent valides dans le fichier d'origine.

Nivellement (réseau mucogingival seulement). Ses caméras sont construites autour d'un axe vertical supposé être Z, donc le plan occlusal est ajusté sur les dents inférieures et le scan est incliné pour amener la normale de ce plan sur Z. Sous 12 degrés d'inclinaison, le scan est laissé tel quel, et les landmarks sont ramenés par la rotation inverse avant d'être écrits.

Dans le codeLa recherche des étiquettes, l'appel de segmentation, la mise à l'échelle et le nivellement

4.2 Les caméras

Le rendu est dur : un triangle par pixel, 224 par 224 pixels, de sorte que chaque pixel peut être rattaché au triangle qu'il montre. Ce que voit le réseau n'est pas une photo en couleur : chaque normale de surface est transformée en couleur, et la profondeur est ajoutée comme quatrième canal.

Les caméras occlusales (O) utilisent une table de directions dont quatre des cinq lignes sont normalisées par le mauvais vecteur (les longueurs sont 0.913, 0.913, 0.791 et 0.791, pas 1), si bien que ces quatre caméras sont un peu plus près de la dent que ne le dit le rayon. C'est sans conséquence tant que les poids ont été entraînés avec la même table, et VISOR la conserve volontairement (détails).

Les caméras mucogingivales (MG) sont les seules adaptatives. La direction de l'arcade au niveau d'une dent est prise à partir de ses deux voisines ; le côté de la joue est la perpendiculaire horizontale à celle-ci. Les caméras ne regardent pas le centre de la dent mais un point décalé d'un écart typique pour cette dent, la médiane sur 155 scans d'entraînement, de sorte que le point gingival tombe dans l'image. Les trois caméras sont la direction du côté de la joue et deux autres tournées de ±0.35 rad autour de l'axe vertical, chacune abaissée de 0.15 du rayon.

Dans le codeLes réglages du rendu, les tables de directions et les caméras MG adaptatives

4.3 Le réseau

Un UNet 2D de la bibliothèque MONAI est chargé pour chaque dent. Pour les réseaux occlusal et cervical, chaque caméra est une image indépendante et obtient sa propre carte de quatre classes. Pour le réseau mucogingival, les trois vues sont empilées en 12 canaux et le réseau produit une seule carte de trois classes, lue dans le repère de la première caméra. C'est une segmentation par pixel, pas une heatmap : la classe 1 est le landmark, les autres portent les points secondaires (vestibulaire mésial et distal pour O, vestibulaire pour C).

Une différence entre les voies est un problème connu : pour O et C, les scores sont tronqués en entiers avant le choix de la classe la plus probable, ce qui fusionne des classes proches et retombe sur le fond en cas d'égalité. La voie mucogingivale utilise les scores bruts, et VISOR les utilise partout.

Dans le codeLes paramètres du réseau, le traitement par lots et les décodeurs

4.4 Du pixel au point 3D

Pour O et C, seuls les triangles qui touchent la dent (au moins un coin porte son numéro) sont conservés. Pour MG il n'y a pas un tel filtre, car le point gingival est sur la gencive, pas sur la couronne ; à la place, par défaut, seuls les triangles proches du point visé par les caméras sont conservés (à moins de la moitié de la distance entre dents voisines), afin que le point gingival d'une voisine vu sur la même image ne soit pas moyenné. Le point est ensuite remis à l'échelle des coordonnées du fichier.

Dans le codeLes filtres pixel vers face et l'accrochage par octree

4.5 Points forcés et champ de description

Pour le réseau mucogingival, trois garde-fous évitent qu'un point manque. Si la classe landmark ne gagne aucun pixel, les 50 pixels où elle est la plus probable tiennent lieu de prédiction. Une dent absente de la segmentation peut recevoir un point par un ajustement polynomial de l'arcade, mais cette option est désactivée par défaut, car de tels points tombent à 4 à 21 mm d'écart, d'après le code. Si rien ne tombe sur le maillage, le point est ancré sur la dent elle-même.

Ces trois-là ne font partie que de la voie mucogingivale. La ligne de commande a huit étapes de plus, toutes activées par défaut : l'échelle vient des premières molaires ; chaque dent est regardée deux fois, la seconde visant l'endroit où le premier regard a trouvé le point (la première réponse est gardée si la seconde la déplace de plus de 3 mm) ; le point d'une voisine dans l'image est écarté ; un point manquant est reconstruit à partir de la courbe que dessinent ses voisines ; la ligne est toujours complétée à 13 points, ceux qui sont extrapolés étant marqués ; chaque point est tiré de 30 % vers la courbe de ses voisines ; chaque point est remis sur le maillage ; et la bande gingivale et les landmarks sont peints dans le fichier du scan. VISOR n'en garde aucune.

Chaque dégradation est écrite dans le champ description du point. FlexReg et AREG_IOS le lisent : toute description non vide est traitée comme douteuse et le point est ignoré, de sorte que la courbe passe par-dessus le trou. Les points des réseaux occlusal et cervical, et tous les points CBCT, ont une description vide quelle que soit leur qualité.

Dans le codeLes options, les valeurs par défaut, l'ajustement de l'arcade et chaque valeur de description

4.6 Sortie et poids

Un fichier par patient, mâchoire et réseau, dans les coordonnées du maillage d'entrée. Les poids sont trouvés à partir du seul nom de fichier (mâchoire, puis réseau, puis n'importe quoi, puis .pth). Le module télécharge une archive qui contient les poids historiques plus celui du mucogingival, dans le dossier que FlexReg attend.

Dans le codeLe nom de sortie, le nommage des poids et le téléchargement

6. Environnement

ALI_CBCT utilise le Python de Slicer plus quelques bibliothèques installées. ALI_IOS utilise un environnement conda partagé avec AREG, ASO, FlexReg et DOCShapeAXI, avec pytorch3d choisi pour correspondre au PyTorch installé. Ni l'un ni l'autre n'exige de GPU. Sous Windows, conda est atteint via WSL. Les versions exactes sont listées sur la page de code.

Dans le codeLes versions, les vérifications d'installation et le paquet patché

7. Pièges et points fragiles

Chaque point est vérifié dans le code et décrit, avec sa preuve, sur la page de code ; la liste figure aussi dans les constats.

  • La dernière couche du réseau est une ReLU, donc une sortie entièrement négative fait toujours prendre le premier déplacement à l'agent. Preuve.
  • La conversion en millimètres utilise une valeur absolue qui n'est juste que pour une origine négative ; réorienter d'abord en LPS limite les dégâts. Preuve.
  • Les scores O et C sont tronqués en entiers avant l'argmax, ce qui fusionne des classes proches. Preuve.
  • Les images O et C sont rattachées aux triangles sans la pose de la caméra qui a servi à les rendre, si bien qu'un pixel peut être rattaché au mauvais triangle. Preuve.
  • La voie DICOM du widget est cassée : cocher DICOM dans le panneau se termine par une erreur, alors que la ligne de commande elle-même convertit le DICOM. Preuve.
  • Le manifeste de l'Agent (la liste qui permet à un pipeline distant d'appeler l'outil) est incomplet : pour ali_ios, une valeur manque et chaque valeur suivante se décale d'un cran. Preuve.
  • Un cache silencieux entre les exécutions : les fichiers rééchantillonnés sont réutilisés s'ils existent et ne sont jamais nettoyés. Preuve.
  • Deux façons de lancer ALI_IOS ne peuvent pas fonctionner ensemble sur une même installation : AREG l'appelle dans le Python de Slicer, où pytorch3d est absent. Preuve.
  • Les landmarks R, RIP et OIP n'ont aucun modèle : les sélectionner seuls fait échouer la CLI. Preuve.
  • Les noms de sortie MG entrent en collision avec les noms d'entraînement d'autres dents ; traduire sur l'ensemble des étiquettes, jamais étiquette par étiquette. Preuve.
  • D'autres points fragiles (les deux étapes IOS lancées l'une après l'autre d'une façon qui peut démarrer la mauvaise, du calcul inutilisé, la liste de modèles vide, l'ancien test non borné de Focus et des bornes) sont décrits un par un sur la page de code. Tous les pièges.

8. Littérature

Les deux programmes ont chacun leur article, et le code correspond à ce qu'ils décrivent, avec une réserve pour ALI_IOS. ALI_CBCT : Gillot, Baquero, Cevidanes et al., Orthodontics & Craniofacial Research, 2023, qui reformule la détection comme la navigation d'un agent virtuel dans un volume multi-échelle ; le code fait exactement cela, avec les mêmes deux grilles. ALI_IOS : Baquero, Gillot, Prieto, Cevidanes, CLIP 2022 : la sphère unité, les cinq vues par dent, la segmentation par vue et la moyenne décrivent à la lettre le réseau occlusal. La voie mucogingivale n'est pas publiée. Les chiffres de précision rapportés sont ceux des articles et n'ont pas été remesurés.
