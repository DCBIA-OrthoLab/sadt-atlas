ALI, legacy : le code

Pour les développeurs : ce que fait le module Slicer legacy dans le code, avec des références file:line, des signatures, des tableaux et des pièges. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. ALI ne calcule rien lui-même : c'est un widget de dispatch qui choisit entre deux backends sans code commun, ALI_CBCT (agents de renforcement qui se déplacent dans un volume) et ALI_IOS (rendu multi-vues et segmentation par pixel sur maillage), pour poser des landmarks anatomiques en LPS.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui fait tourner le même outil sur un serveur, est décrit dans ALI sur VISOR. Les notes ajoutées aux encadrés disent si chaque constat reste valable dans VISOR ; elles citent SADT-VISOR à 6ba2a78, avec CB/ pour tools/ALI/ALI_CBCT/src/sadt_ali_cbct/ et IO/ pour tools/ALI/ALI_IOS/src/sadt_ali_ios/. Chaque file:line ci-dessous a été relu à 3c67957 (ALI_CBCT.py fait 371 lignes, ALI_IOS.py 1133, ALI.py 2224) ; quand un encadré décrit une révision antérieure, il le dit.

3. ALI_CBCT : des agents dans le volume

Explication en langage courant et maths : page de l'atlas.

3.1 Prétraitement

Deux étapes, toutes deux écrites dans temp_fold et jamais nettoyées :

  1. Fenêtrage d'histogramme, CorrectHisto(scan, out, 0.01, 0.99) (preprocess.py:14) : histogramme à 1000 classes, cumul normalisé, écrêté aux percentiles 1 % et 99 %, borné strictement à [-1500, 4000] HU. Sortie en int16, spacing/origin/direction conservés. Attention : la signature par défaut dit max_porcent=0.95, mais l'appel passe 0.99.
  2. Rééchantillonnage isotrope, un fichier par échelle : SetSpacing (itk, interpolation linéaire, plus proche voisin si seg/Seg figure dans le nom) pour chaque sp de spacing = [1, 0.3] mm. La nouvelle taille est size * spacing / sp et l'origine est recentrée sur la même boîte physique.
Piège · Legacy uniquement

Les fichiers sont nommés <stem>_sp<1|0-3><suffixes> et réutilisés s'ils existent déjà : c'est un cache, et donc aussi un piège si l'entrée change sans changer de nom.

Legacy (3c67957) : toujours vrai, ALI_CBCT/ALI_CBCT.py:199 et :215 sautent un fichier qui existe. Absent de VISOR : chaque scan reçoit son propre dossier de travail, supprimé une fois le scan terminé (SADT-VISOR CB/engine.py:910), si bien qu'une exécution ne lit jamais les fichiers d'une autre.

Au chargement (environment.py:72) : sitk.DICOMOrient(img, "LPS"), sans cela, les agents, qui ne lisent jamais que le tableau brut et jamais les cosinus directeurs, marchent dans un volume en miroir. Puis EnsureChannelFirst + BorderPad(padding) avec padding = agent_FOV/2 + 1 = [33,33,33], de sorte que tout crop 64³ soit valide où que l'agent se trouve.

Le tableau est stocké dans l'ordre numpy (z,y,x) et l'origin est inversée pour suivre ce même ordre, mais pas le spacing, qui reste en (x,y,z). Cela est sans effet uniquement parce que le rééchantillonnage rend le spacing isotrope.

3.2 L'environnement

Environment (environment.py:17) est un patient : un dictionnaire {scale_key: {image, spacing, origin, size}} plus la liste des landmarks prédits. Une instance par patient, avec toutes les échelles gardées en mémoire.

GetZone(scale, center, crop_size) est la seule chose que l'agent voit jamais du monde :

cropTransform = SpatialCrop(center.tolist() + self.padding, crop_size)
rescale = ScaleIntensity(minv=-1.0, maxv=1.0, factor=None)
crop = rescale(cropTransform(self.data[scale]["image"])).type(torch.float32)

Un cube de 64×64×64 voxels centré sur l'agent, renormalisé crop par crop dans [-1,1] (min/max locaux, pas une normalisation globale). À l'échelle 1, il couvre un côté de 64 mm, à l'échelle 0-3 19,2 mm.

3.3 L'agent et son réseau

Un agent par landmark (agent.py:149), instancié une fois puis réutilisé pour chaque patient. Un nouveau Brain est construit et ses poids rechargés pour chaque paire (patient, landmark) (ALI_CBCT.py:123) : 2 DenseNet reconstruits et 2 fichiers .pth relus par point et par scan.

Le réseau, DNet (brain.py:39) :

self.featNet = DenseNet(spatial_dims=3, in_channels=1, out_channels=1024,
                        growth_rate=34, block_config=(6, 12, 24, 16))
self.dens = DN(in_channels=1024, out_channels=6)   # MLP 1024-512-256-128-6

Un DenseNet-121 3D de monai (taux de croissance 34 au lieu de 32), suivi d'un MLP à 4 couches. Entrée [1, 1, 64, 64, 64], sortie de 6 scores, un par déplacement : Up / Down / Back / Front / Left / Right, c'est-à-dire ±1 voxel le long de chacun des trois axes du tableau (constants.py:29).

Ce n'est pas une heatmap : c'est un classifieur de direction. La prédiction du réseau ne dit pas où se trouve le point, elle dit dans quelle direction faire un pas. Predict prend l'argmax des 6 scores (brain.py:157).

Bug confirmé · Aussi vrai dans VISOR

Notez que DN.forward applique un relu à la dernière couche aussi. Les scores sont donc ≥ 0, et si toutes les pré-activations sont négatives, les 6 sortent à 0 et argmax renvoie systématiquement 0 (« Up »). Le softmax mis en commentaire juste en dessous laisse penser que ce n'était pas l'intention.

Aussi vrai dans VISOR : la tête portée se termine de la même façon (SADT-VISOR CB/brain.py:90 ; legacy ALI_CBCT_utils/brain.py:35 à 3c67957).

Un réseau par échelle : Brain en instancie un par scale_key, et LoadModels charge <label>/1/*.pth puis <label>/0-3/*.pth.

3.4 La recherche

Agent.Search() (agent.py:345):

  1. échelle 0 (1 mm), position au centre du volume ;
  2. boucle : PredictAction() → Move() d'un pas de speed_per_scale[scale] = 1 voxel ;
  3. critère d'arrêt = oscillation. Visited() vérifie si la position courante figure parmi les 10 dernières positions (shortmem_size = 10). Dès que l'agent repasse sur ses pas, il est considéré comme arrivé ;
  4. UpScale() : passe à l'échelle 0-3, position convertie par le rapport des spacings, mémoire à court terme vidée, et la recherche repart ;
  5. à l'échelle finale, Visited() met fin à la recherche.

Budget et réapparition à 3c67957 (commit b87c02f, 2026-09-18). Une recherche s'arrête après max_steps passes avant, 1000 par défaut (ALI_SEARCH_MAX_STEPS, ALI_CBCT_utils/agent.py:27, :58-60, boucle :377), avec un garde-fou de 900 s (ALI_SEARCH_TIME_GUARD, :33, :380-391). Une recherche qui tourne en rond sur un terrain connu pendant 64 pas de suite réapparaît ailleurs (Cycling, :43, :402-412, :471-491). Sortir de la zone où un crop entier peut encore être lu la fait aussi réapparaître (Move, :279-289 : un voxel au-delà de chaque face du scan, environment.py:246-272). Les deux sortes de réapparition comptent comme une tentative, et le landmark est abandonné à la troisième (search_atempt > 2, :421-428) ; épuiser le budget renvoie aussi -1 (:446-453). Une réapparition est aléatoire : n'importe où à l'échelle 0, dans un rayon de spawn_radius = 10 voxels de l'endroit où l'échelle a commencé aux échelles suivantes (:244-259) ; elle utilise le np.random global, sans graine. VISOR : 900 pas, pas de garde-fou temporel, pas de règle des 64 pas, un générateur à graine par landmark (SADT-VISOR CB/engine.py:55, CB/agent.py:54-68).

Le raffinement final, Focus() (agent.py:305) : à partir de la position trouvée, six re-départs à 4 voxels (1,2 mm à l'échelle finale) le long de ±x, ±y, ±z ; chacun marche de nouveau jusqu'à Visited() ; la position retenue est la moyenne des six arrivées. C'est ce qui rend le résultat sub-voxel. Les six sondes partent dans l'ordre +x, -x, +y, -y, +z, -z (:306-330), chacune bornée par son propre max_steps (:331) ; la règle des 64 pas de la recherche ne s'applique pas ici, et un pas hors de la zone lisible fait réapparaître la sonde à une position aléatoire (Move).

Note · Remplacé : Focus est borné à 3c67957

Une révision antérieure de cette page disait que Focus n'avait aucune borne. À 3c67957, il en a une : chacune des six sondes s'arrête après max_steps (SearchStepBudget(), 1000 par défaut), journalise un avertissement et garde sa dernière position (legacy ALI_CBCT_utils/agent.py:325-341, commit b87c02f, 2026-09-18). VISOR est borné aussi, plus strictement : le raffinement puise dans le même compteur de pas que la recherche et lève NotFound quand il est épuisé (SADT-VISOR CB/agent.py:238-243).

3.5 Sortie

SavePredictedLandmarks(scale_keys[-1], output_dir) (environment.py:109) reconvertit l'indice en coordonnée physique :

physical_origin = abs(ref_origin / ref_spacing)
real_label_pos  = (pos - physical_origin) * ref_spacing
real_label_pos  = [real_label_pos[2], real_label_pos[1], real_label_pos[0]]  # back to x,y,z
Bug confirmé · Aussi vrai dans VISOR, et n'est plus atténué

Le abs() suppose que l'origin est négative sur les trois axes : vrai pour un volume LPS centré sur l'origine, faux en général.

Legacy (3c67957) : ALI_CBCT_utils/environment.py:115, mais chaque volume est d'abord réorienté en LPS (:72), ce qui limite les dégâts. VISOR : la même ligne (SADT-VISOR CB/environment.py:116) sans réorientation, voir Constats dans VISOR.

4.1 Entrées

.vtk, .vtp, .stl, .obj, .off. Mais tout dépend d'un tableau de labels de dents, cherché sous PredictedID, predictedId ou Universal_ID (surface.py:137) : c'est lui qui donne le centroïde de chaque dent, donc la position de la caméra. Sans tableau, RI est mis à zéro et aucun label n'est trouvé.

Si le scan n'en a pas, SegmentSurface (segmentation.py:72) appelle dentalmodelseg sur une copie (un .stl passé à shapeaxi avec --overwrite 1 est supprimé par dental_model_seg.py), via un csv (passer un seul fichier à --surf fait planter shapeaxi sur un attribut qu'il ne définit pas). La segmentation ne déplace pas les points, 5e-5 mm mesurés sur 118k points d'après le commentaire, donc les landmarks restent valables dans le fichier d'origine.

Mise à l'échelle canonique, ScaleSurf (surface.py:24) : centrage sur le milieu de la boîte englobante, puis scale = 1 / ||max - center||. Tout le pipeline travaille à l'intérieur de cette sphère unité ; Upscale inverse le processus à la fin.

Mise à niveau (MG uniquement), LowerArchMatrix (orientation.py:89) : les caméras MG sont construites autour d'un axe vertical supposé être Z. Le plan occlusal est ajusté par SVD sur les centroïdes des dents 18–31 (au moins 4 dents, étalées sur ≥ 4 labels), avec le signe fixé pour que les couronnes pointent vers le haut, puis une rotation minimale (Rodrigues) amène la normale sur +Z. En dessous de MAX_TILT_DEGREES = 12°, le scan est laissé strictement intact : envoyer un scan déjà à niveau dans un repère fixe le ferait pivoter dans le plan et dégraderait la prédiction. Les landmarks repassent par inv(matrix) avant d'être écrits.

4.2 Les caméras

GenPhongRenderer (render.py:10-35):

cameras = FoVPerspectiveCameras(znear=0.01, zfar=10, fov=90)
raster_settings = RasterizationSettings(image_size=224, blur_radius=0, faces_per_pixel=1)

image_size / blur_radius / faces_per_pixel sont des arguments positionnels du CLI, mais tous les appelants passent 224 / 0 / 1 (IOS.py:280, IOSCBCT.py:333, FlexReg.py:2323). blur_radius = 0 plus faces_per_pixel = 1 signifie une rastérisation dure, une face par pixel : c'est ce qui rend pix_to_face utilisable comme table de correspondance pixel-face.

La texture n'est pas une couleur : TexturesVertex(verts_features=CN) où CN est la normale par sommet remappée en RGB ((n*0.5+0.5)*255, surface.py:101). Le réseau voit donc une carte de normales éclairée en Phong, plus le z-buffer en 4e canal.

Une caméra est placée par dent, à radius de son centroïde :

ModèleRayonCamérasGéométrie
O (occlusal)0.25dic_cam['O'], axe occlusal + 4 inclinaisons
C (cervical)0.312dic_cam['C'], couronne vestibulaire/linguale
MG (mucogingival)0.23calculées à la volée, voir ci-dessous

Les directions de dic_cam['O'] sont mal normalisées : np.array([0.5,0,1.0]) / linalg.norm([0.5,0.5,1.0]) divise par la norme d'un vecteur différent (model.py:66). Les caméras ne sont donc pas sur la sphère de rayon radius. Sans conséquence tant que les poids ont été entraînés avec la même table.

À 3c67957, la table se trouve à ALI_IOS_utils/model.py:66-77. VISOR la reproduit volontairement, parce que les poids livrés ont été entraînés sur ces vues (SADT-VISOR IO/render.py:9-12, table en :39-54). Quatre des cinq lignes par mâchoire (toutes sauf la ligne de l'axe) ont une longueur de 0,913, 0,913, 0,791 et 0,791 au lieu de 1 (calculé : 1,118/1,2247 pour les deux inclinaisons en x et 1,118/1,414 pour les deux en y), si bien que ces quatre caméras se tiennent plus près que le rayon.

Les caméras MG, la seule partie adaptative (agent.py:119-263) :

  • tangente à l'arcade : la différence entre les centroïdes des dents label-1 et label+1 (les labels inférieurs 18→31 se suivent le long de l'arcade), aplatie en z ;
  • normale vestibulaire : perpendiculaire horizontale à la tangente, retournée si elle pointe vers l'intérieur. La direction radiale (centre de la dent − centre du maillage) utilisée par la version précédente est décalée de 35° sur les dents 19/30 et de 53° sur la dent 31 : les caméras regardaient le long de l'arcade et le point tombait hors du rendu ;
  • point visé : non pas le centroïde de la dent mais centroid + b·normal + t·tangent, z += v, avec (b,t,v) lus dans MG_AIM_OFFSET (model.py:35), la médiane par dent sur 155 scans d'entraînement, dispersion 0,02–0,03 ;
  • trois caméras : la normale vestibulaire, plus deux tournées de ±0,35 rad dans le plan horizontal (les composantes x et y sont tournées, donc autour de l'axe vertical ; le commentaire du code l'appelle l'axe Y), placées à radius du point visé et abaissées de 0.15·radius.

4.3 Le réseau

Un monai.networks.nets.UNet 2D, chargé pour chaque dent (net.load_state_dict dans la boucle, ALI_IOS.py:714) :

O / CMG

Une différence structurelle : pour O/C, chaque caméra est un échantillon indépendant et chaque vue produit sa propre carte ; pour MG, les trois vues sont empilées en canaux et le réseau produit une seule carte, interprétée dans le repère de la caméra 0 (l'indexation tens_pix_to_face_model[0,0,0,y,x] vise la première caméra après le permute(1,0,4,2,3)).

Ce n'est pas une heatmap au sens de la régression gaussienne : c'est une segmentation par pixel. La classe 1 est le landmark (MG, ou O), 2 et 3 portent MB/DB (modèle O) ou CB (modèle C) : voir MODELS_DICT et dic_label (model.py:51).

Le décodage de la sortie est l'endroit où les deux chemins divergent (ALI_IOS.py:722-739) :

# MG: argmax on the raw logits
pred_data = torch.argmax(images_pred.detach().cpu().float(), dim=1)...
# O / C: cast to int16 BEFORE the argmax
pred_data = images_pred.detach().cpu().unsqueeze(0).type(torch.int16)
pred_data = torch.argmax(pred_data, dim=2).unsqueeze(2)
Bug confirmé · Legacy uniquement

Le commentaire du code MG explique pourquoi le second est faux : tronquer les logits en entiers fusionne des classes proches, et en cas d'égalité, argmax retombe sur l'indice 0 (le fond). Le correctif n'a été appliqué qu'à MG.

Legacy (3c67957) : toujours vrai, ALI_IOS/ALI_IOS.py:738-739 (cast) contre :731-736 (MG, logits bruts). Absent de VISOR : chaque réseau est décodé par un argmax sur les logits bruts (SADT-VISOR IO/engine.py:199-216). 4.4 Du pixel au point 3D

  1. index = (pred_data == 1.).nonzero() : les pixels de la classe cible ;
  2. tens_pix_to_face[...] : la face rendue sous chacun de ces pixels ;
  3. filtrage, et il diffère :
    • O/C : RemoveExtraFaces ne garde que les faces dont au moins un sommet porte l'Universal_ID de la dent (surface.py:159) ;
    • MG : pas de filtrage par dent, seulement face >= 0 (ALI_IOS.py:635). Le point mucogingival se trouve sur la gencive, pas sur la couronne ; RemoveExtraFaces les éliminerait tous. Puis, avec --pick_patch (actif par défaut), PickNearAim garde les faces dont le centre est à moins de la moitié du pas médian entre dents du point visé par la caméra (ALI_IOS.py:639-651, pick_patch.py:63-103) ;
  4. les 3 sommets de chaque face retenue, moyennés : la liste contient une face par pixel, donc une face vue par plusieurs pixels compte plusieurs fois (all_verts, ALI_IOS.py:498-506 ; une somme Python séquentielle pour O et C, V[0][all_verts].mean pour MG) ;
  5. vtkOctreePointLocator.FindClosestPoint : le point moyen est aligné sur un sommet existant, la moyenne d'un patch courbe tombe sous la surface ;
  6. Upscale(pos, mean_arr, scale_factor) : retour aux coordonnées du fichier.

7. Pièges et points fragiles

  • Focus() n'avait aucune protection dans la révision sur laquelle cette page a été écrite. Remplacé : borné à 3c67957 (agent.py:325-341) et dans VISOR (CB/agent.py:238-243), voir la note en 3.4.
  • Move() teste mal ses bornes : if new_pos.all() > 0 and (...), .all() renvoie un booléen, comparé à 0. Le test vérifie « aucune coordonnée n'est nulle », pas « aucune coordonnée n'est négative » (agent.py:242). Remplacé : depuis 7d901e4 (2026-09-18), le legacy teste la zone échantillonnée avec marge coordonnée par coordonnée (ALI_CBCT_utils/agent.py:114, :279-284), et VISOR teste >= 0 et < size (CB/agent.py:135-141).
  • Le cast int16 avant argmax est toujours là sur les modèles O et C. Le commentaire du code MG explique précisément pourquoi c'est faux. Legacy uniquement : toujours là à 3c67957 (ALI_IOS.py:738-739), absent de VISOR (IO/engine.py:216).
  • get_view_rasterize pour non-MG rastérise sans R/T : renderer.rasterizer(meshes.clone()) (agent.py:364 à 3c67957) ne passe pas les matrices utilisées par le rendu juste au-dessus, donc pix_to_face vient de la caméra par défaut, pas de celle qui a produit l'image. Le chemin MG a été écrit explicitement pour corriger cela (« with the SAME R,T so pix_to_face stays aligned », agent.py:267). C'est le code upstream d'origine, et il n'a jamais été rejoué pour O/C. Legacy uniquement : toujours en ALI_IOS_utils/agent.py:364 à 3c67957 ; VISOR rastérise une fois par vue, avec R et T (IO/render.py:402-412).
  • val_pred / post_pred (ALI_IOS.py:724-728) : un AsDiscrete(argmax=True, to_onehot=4) est calculé sur chaque vue puis jamais lu. Calcul mort sur chaque dent.
  • Collisions de noms MG. Six des 13 noms de sortie sont le nom d'entraînement d'une dent différente : LR1MG est la sortie de la dent 26 et le nom d'entraînement de la dent 25 (model.py:25). Toute traduction entre les deux conventions doit être décidée sur l'ensemble des labels, jamais label par label.
  • Le chemin DICOM du widget est cassé. Auto_CBCT n'implémente ni NumberScanDCM, ni TestScanDCM, ni getTestFileListDCM : les versions de base renvoient None. Cocher « DICOM » donne nb_patient = None, puis une TypeError au téléchargement des fichiers de test et une division par None dans OnEndProcess. Le CLI lui-même sait convertir.
  • Le manifeste d'Agent est incomplet. ali_cbct déclare 6 paramètres pour 10 positionnels attendus, ali_ios en déclare 6 pour 10 et omet teeth_mg (indice 4) : les valeurs suivantes se décalent d'un cran (manifest.yaml:48).
  • temp_fold n'est jamais nettoyé par ALI_CBCT, et les fichiers rééchantillonnés sont réutilisés tels quels s'ils existent : un cache silencieux entre deux exécutions. Legacy uniquement : à 3c67957, la réutilisation est en ALI_CBCT.py:199, :215 ; VISOR supprime un dossier de travail par scan (CB/engine.py:910).
  • Auto_IOS.getALIModelList renvoie super().getALIModelList(), une méthode abstraite vide → None (IOS.py:159-160).
  • slicer.modules.ali_ios est appelé par AREG via slicer.cli.run (IOSCBCT.py:341), donc dans le Python de Slicer, où pytorch3d et shapeaxi ne sont pas installés. Le widget ALI, lui, ne l'appelle jamais que par conda run. Les deux chemins ne peuvent pas fonctionner ensemble sur la même installation.
  • SURFACE_LANDMARKS (ALI.py:137) propose R, RIP, OIP, qui n'ont aucune entrée dans MODELS_DICT : les sélectionner seuls fait échouer le CLI avec « No matching models found. »
  • onPredictButton enchaîne mal les deux processus IOS : le if "CrownSegmentationcli" et le if "ALI_IOS" qui suit ne sont pas mutuellement exclusifs, et le else placé après se rattache au second (ALI.py:992-1011). Quand une segmentation est nécessaire, ALI_IOS est relancé depuis onProcessUpdate ; sinon depuis onPredictButton. Deux points d'entrée pour la même étape.
