FlexReg, legacy : le code

Pour les développeurs : ce que fait le module Slicer legacy FlexReg dans le code (SlicerAutomatedDentalTools à 3c67957), avec des références file:line, des signatures, des arguments, l'environnement et les pièges. L'explication lisible du même pipeline, avec les maths, est sur la page de l'atlas. Le portage VISOR a sa propre page de code.

Code Atlas (explication) non publié FlexReg_CLI env conda : shapeaxi VISOR Guide Bibliographie
Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, est décrit sur sa propre page, FlexReg sur VISOR. Le portage VISOR garde l'aperçu du patch dans Slicer et fait le reste sur le serveur ; il ne reprend ni la courbe libre, ni la suppression de patch, ni le calcul du patch mucogingival, ni la segmentation automatique des couronnes.

1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

Rien dans le dépôt n'appelle FlexReg : c'est un outil terminal, piloté par l'opérateur. Il appelle en revanche deux réseaux préentraînés, et il produit l'entrée d'AREG_IOS : les deux outils lisent exactement le même tableau de points.

AppeléQuandPourquoi
dentalmodelseg (ShapeAXI / DentalModelSeg)si le maillage n'a pas de tableau Universal_IDsegmenter et numéroter les couronnes
ALI_IOS (poids Lower_MG_*.pth)mode arcade inférieure seulementplacer les 13 repères mucogingivaux

En aval, AREG_IOS.py:364 fait vtkMeshTeeth(list_teeth=[1], property="Butterfly") et AREG_IOS.py:378 la même chose sur MGL_ARRAY_NAME : un patch construit dans FlexReg est directement consommable par AREG_IOS, et inversement. La différence est l'origine du patch : AREG_IOS le fait prédire par un réseau (PredPatch.py, un MonaiUNetHRes multi-vues), FlexReg le construit géométriquement.

3. Entrées et prétraitement

Explication en langage courant et maths : page de l'atlas.

Piège : conversion de fichier (legacy uniquement)

ensureVtkInput() (FlexReg.py:3199) convertit un .stl en .vtk avant toute opération. Ce n'est pas cosmétique : dental_model_seg.py fait os.remove(args.stl) et détruirait le fichier source si on lui passait directement le .stl (FlexReg.py:3409).

Legacy (3c67957) ; absent de VISOR : read_surface lit directement .vtk, .vtp et .stl, selon l'extension, et refuse un maillage vide (SADT-VISOR sadt_flexreg/pipeline.py:50-78) ; aucune segmentation n'est lancée, donc aucun fichier source n'est supprimé.

LPS ↔ RAS inversion. Le CLI lit le .vtk (LPS), applique Scale(-1,-1,1) pour travailler en RAS comme Slicer, et rétablit avant d'écrire (FlexReg_CLI.py:228, 297). Tout le calcul interne est donc en RAS.

Cadrage canonique, l'étape de prétraitement clé, orientation.py :

  1. centroïdes des dents Universal_ID 3, 5, 12, 14 (UR6, UR4, UL4, UL6) ;
  2. base locale de chaque côté : normale du plan passant par les trois points (produit vectoriel de deux vecteurs vers le milieu), puis la direction perpendiculaire ;
  3. deux rotations successives, axe = produit vectoriel, angle = arccos du produit scalaire, via RotationMatrix (Rodrigues) ;
  4. translation pour faire coïncider les centroïdes.

La cible est [[-0.5,-0.5,0], [0,0,0], [0.5,-0.5,0]] : molaire droite en x<0, molaire gauche en x>0, prémolaires à l'origine. Résultat : plan occlusal ≈ z=0, +y = antérieur, +x = côté gauche. Pas de mise à l'échelle : c'est un recalage rigide sur 3 points.

Conséquence directe : tout le calcul du butterfly qui suit est un calcul 2D dans le plan XY, la composante z étant simplement ignorée.

5. Le cœur algorithmique

Explication en langage courant et maths : page de l'atlas.

5.1 Chemin A : le patch Butterfly (arcade supérieure) calculé

Explication en langage courant et maths : page de l'atlas.

make_butterfly.py. Aucun réseau, purement géométrique.

a) Quatre centroïdes. L'opérateur choisit 4 dents (antérieures G/D, postérieures G/D) ; vtkMeanTeeth fait la moyenne des sommets qui portent cet Universal_ID.

b) Trois familles de paramètres appliquées à ces centroïdes :

ParamètreEffetDétail
shift_lr, shift_aptranslate tout le patchle même vecteur est ajouté aux 4 centroïdes ; comme les repères sont des combinaisons affines dont les poids somment à 1, le décalage se transmet à travers l'interpolation et la forme est inchangée
adjust (mm)allonge / raccourcitdécalage en ±y, signe inversé sur les dents postérieures : un ajustement positif pousse les deux extrémités vers l'extérieur
ratiola largeur est préservéereparamétré en r = (1-ratio)/2, puis landmark = (1-r)·own_centroid + r·opposite_centroid. ratio=1 → repère sur son propre centroïde (patch maximal) ; ratio=0 → repère à mi-chemin (patch dégénéré)

Attention au vocabulaire : l'interface dit top/bot, le CLI dit anterior/posterior. lineedit_teeth_left_top → tooth_anterior_left.

c) Le contour, en quatre morceaux :

  • segment antérieur et segment postérieur (Segment2D, pas de 0.01) ;
  • deux Béziers quadratiques, droite et gauche, points de contrôle (posterior_landmark, posterior_midpoint, anterior_landmark), puis réfléchis par rapport à la corde (sym = 2·proj − bezier) pour qu'ils bombent vers l'extérieur de l'arcade au lieu du centre. C'est ce qui donne au butterfly sa forme.

d) Marquage. torch.cdist entre les points du contour et les sommets projetés sur XY ; tout sommet à moins de radius = 0.7 mm est mis à 1.

e) Remplissage. Dilation() (propagation.py:56) : un remplissage géodésique par diffusion sur le maillage, pas une dilatation morphologique. Il part du sommet le plus proche du barycentre des 4 repères, se propage de voisin en voisin (GetPointCells / GetCellPoints), et s'arrête au contour, déjà mis à 1. Traité par lots de nmb_treatment = 1000 sur GPU.

f) Écriture. Le tableau s'appelle Butterfly{index} : chaque patch a son propre indice, ce qui permet de les accumuler. À la fin du CLI, tous les tableaux Butterfly1..N sont fusionnés par torch.logical_or en un seul tableau Butterfly (FlexReg_CLI.py:277) : c'est celui que lisent l'ICP et AREG_IOS. Le résultat est réécrit dans le fichier d'entrée.

Le mode delete renumérote les tableaux au-dessus de l'indice supprimé puis retire le dernier, plutôt que de laisser un trou.

Aperçu en temps réel. butterfly_preview.py rejoue le même contour en numpy pur (CPU) et remplace le remplissage par diffusion par un test point-dans-polygone (matplotlib.path.Path, avec un repli numpy par nombre de croisements). L'orientation et les centroïdes sont mis en cache par scan (prepare), donc seul le contour est recalculé à chaque mouvement de joystick. Constantes : CELL = 1.0 mm pour la carte de hauteur, LIFT = 0.4 mm au-dessus des dents, NB_POINTS = 120 échantillons par arête.

5.2 Chemin B : le patch dessiné calculé

Explication en langage courant et maths : page de l'atlas.

draw() (FlexReg.py:3972), type="curve". Une courbe Slicer contrainte à la surface (SetAndObserveSurfaceConstraintNode) plus un point médian, sérialisés en chaînes et passés au CLI. draw.py interpole linéairement entre les points consécutifs (pas de 0.2, boucle fermée), marque les sommets à moins de 1.1 mm (torch.cdist sur les points 3D, draw.py:34-35 : pas de projection sur XY, contrairement au butterfly), puis exécute exactement le même Dilation() depuis le point médian. La seule différence avec le butterfly est la façon d'obtenir le contour.

La courbe est dessinée sur le modèle recentré face à la caméra ; avant de l'envoyer au CLI, moveCurve() applique l'inverse de la matrice de recentrage pour la ramener dans les coordonnées du fichier.

5.3 Chemin C : le patch MGL (arcade inférieure) calculé

Explication en langage courant et maths : page de l'atlas.

Le palais offre un plateau stable sur l'arcade supérieure ; la mandibule n'en a pas. Le substitut choisi est la ligne mucogingivale. Tout ce bloc est calculé dans le widget, en numpy/scipy : ni GPU, ni CLI (FlexReg/FlexReg_utils/mgl_patch.py, appelé mgl_patch.py ci-dessous ; AREG_IOS/AREG_IOS_utils/mgl_patch.py est un fichier distinct).

a) Nettoyage des prédictions d'ALI. DoubtfulLandmarks() lit la description que ALI écrit dans le json quand il a forcé un point (top-k pixels, repli sur la dent, dent manquante). D'après le commentaire du code, mesuré sur 364 prédictions : une déviation médiane de 4,2 mm par rapport à la courbe des voisins, contre 1,2 mm pour le reste. Les marques testées sont forced, fallback, arch fit, off the aim et extrapolated, plus toute confidence sous MIN_CONFIDENCE = 0.785 (mgl_patch.py:144-162). Ces points sont écartés par défaut, et la spline comble le vide : sauf s'il resterait moins de 3 points. Viennent ensuite CanonicalLandmarks (ancienne nomenclature d'annotation → canonique, détectée par la présence d'un LL7MG ou LR7MG) et RecentreNames (le compte reste ancré sur la ligne médiane quand un point manque en cours d'arcade).

b) Repère local. LocalFrames() : l'axe apical est la troisième composante de la SVD des repères centrés (la normale du ruban de points, indépendante de l'orientation du scan dans l'espace monde) ; la tangente est np.gradient le long de l'arcade ; la direction vestibulaire est leur produit vectoriel, inversé partout où il pointe vers l'intérieur. OrientApical fixe le signe à partir des couronnes.

c) Construction de la bande, à chaque compute() :

  1. décalages de l'opérateur (vestibulaire / apical / tangentiel) appliqués aux repères ;
  2. vtkParametricSpline passant par eux, SAMPLES_PER_SEGMENT = 25 ;
  3. chaque échantillon est ramené sur le maillage (vtkPointLocator) : une spline interpolée dérive hors de la surface dans les concavités interdentaires ;
  4. Dijkstra (scipy.sparse.csgraph) sur le graphe des arêtes pondéré par la longueur réelle, multi-source à partir de ces sommets, limit = hauteur maximale, min_only=True, return_predecessors=True → la bande croît le long de la surface, jamais à travers (un patch vestibulaire ne peut pas ressortir du côté lingual, où la crête est mince) ;
  5. hauteur interpolée linéairement entre les repères (np.interp) et asymétrique : heights côté couronne, heights_down côté vestibulaire, le côté étant décidé par le signe de la composante apicale. La hauteur utilisée est celle de la graine depuis laquelle le sommet a été atteint, donc deux segments de hauteurs différentes coexistent sans marche. Le côté est le signe du sommet moins sa graine, projeté sur l'axe apical (below, mgl_patch.py:510-513), et un sommet est gardé si distance <= allowed et allowed > 0 (:513-516), donc une hauteur de 0 ne garde rien, pas même la courbe. Les deux hauteurs valent 2,5 mm par défaut (mgl_patch.py:120 ; curseurs « Upper extension » et « Lower extension », FlexReg.py:1867-1868, 1966-1972), donc la bande n'est symétrique que par défaut ;
  6. les couronnes (Universal_ID 17–32, LOWER_TOOTH_LABELS = range(17, 33), troisièmes molaires comprises, mgl_patch.py:130-134) sont retirées : elles bougent entre T1 et T2 ;
  7. les repères eux-mêmes restent toujours dans le patch.

Bornes : MIN_HEIGHT = 0.0, MAX_HEIGHT = 5.0, DEFAULT_HEIGHT = 2.5 mm. Hauteur nulle partout ⇒ il ne reste que les 13 points : c'est le cas témoin voulu, pour mesurer ce que la bande apporte par rapport aux seuls points.

Le graphe des arêtes est construit avec np.unique(np.sort(edges)) avant la coo_matrix : sans cette déduplication, les arêtes intérieures partagées par deux triangles seraient additionnées par la matrice creuse, doublant leur longueur et divisant par deux la portée du patch.

Tableau de sortie : Bottom_MGL (MGL_ARRAY_NAME), prévisualisé dans Bottom_MGLPreview.

WriteLandmarks() écrit les repères édités en LPS, comme les annotations d'entraînement : le fichier obtenu peut être réinjecté tel quel dans le corpus.

5.4 Le recalage calculé

Explication en langage courant et maths : page de l'atlas.

Reg.run() (FlexReg.py:1060) relance le même CLI avec type = "icp" (arcade supérieure) ou "icp_mgl" (arcade inférieure). T2 est le scan mobile (lineedit), T1 le scan fixe (path_reg).

patch_array = "Bottom_MGL" if args.type == "icp_mgl" else "Butterfly"
option = vtkMeshTeeth(list_teeth=[1], property=patch_array)
icp = ICP([vtkICP()], option=option)
output_icp = icp.run(modelNode, modelNodeT1)

Malgré son nom, vtkMeshTeeth ne construit pas de maillage : il extrait un nuage de points qui ne contient que les sommets dont le tableau du patch vaut 1. L'ICP ne tourne donc que sur le patch, jamais sur les dents.

icp.GetLandmarkTransform().SetModeToRigidBody()   # 6 dof, no scaling
icp.SetMaximumNumberOfIterations(1000)
icp.StartByMatchingCentroidsOn()                  # initialization

vtkIterativeClosestPointTransform standard : appariement au plus proche voisin, estimation rigide par moindres carrés, itération. Aucun apprentissage à ce stade.

La matrice 4×4 est ensuite appliquée à tout le maillage T2, ainsi qu'à l'arcade opposée si elle est fournie (lower_arch), pour qu'elle suive le même mouvement.

6. Post-traitement et sorties

Explication en langage courant et maths : page de l'atlas.

Le maillage. type patch → réécrit dans le fichier d'entrée. type ICP → écrit dans path_output sous la forme <T2 name without extension><suffix>.vtk, après retour en LPS.

La transformation, l'étape délicate (FlexReg_CLI.py:100-106) :

flip = np.diag([-1, -1, 1, 1])
composed = flip @ matrix_array @ flip     # RAS -> LPS by conjugation
composed_inv = np.linalg.inv(composed)    # ITK convention: fixed -> moving
sitk_tfm = sitk.AffineTransform(3)
sitk_tfm.SetMatrix(composed_inv[:3, :3].flatten())
sitk_tfm.SetTranslation(composed_inv[:3, 3])

Fichier <T2 name><suffix>.tfm, réutilisable par les autres modules du dépôt.

Le bouton See. Lance le recalage exactement identique dans un tempfile.mkdtemp(prefix="FlexReg_see_") supprimé dès l'affichage (discardTempFolder). Le nœud obtenu est marqué SetSaveWithScene(False) et renommé ... (preview, not saved) : le fichier qui le porte est sur le point de disparaître.

L'affichage. Disposition personnalisée 501, T1 en [255,51,200]/256 et T2 en [102,102,255]/256 dans la troisième vue 3D.

9. Pièges et points fragiles

Le CLI exige CUDA (aussi vrai dans VISOR, pour l'étape du patch uniquement)

Dilation, drawPatch et la fusion finale des tableaux appellent toutes .cuda() sans repli sur le CPU. Le patch MGL, lui, est calculé côté widget et s'en passe, d'où le while args.type != "icp_mgl" qui saute la fusion pour l'arcade inférieure (FlexReg_CLI.py:267-292, .cuda() aux lignes 272 et 286).

Aussi vrai dans VISOR pour le patch : Dilation appelle .cuda() sans repli (SADT-VISOR sadt_flexreg/propagation.py:31, 60, 66-68), appelée depuis make_butterfly.py:161. Plus vrai pour le reste : la fusion des tableaux Butterfly se fait en numpy (pipeline.py:165-188), drawPatch n'est pas appelée, le saut de boucle icp_mgl a disparu, et le chemin de recalage n'importe aucun torch (pipeline.py:191-224).

Le fichier d'entrée est écrasé (Legacy uniquement)

En mode patch, et la segmentation automatique l'écrase aussi (overwrite=1). Un .stl confié à dentalmodelseg est tout simplement supprimé : c'est la raison d'être de ensureVtkInput().

Références Legacy : FlexReg_CLI.py:314-315 (les modes patch écrivent dans args.lineedit), FlexReg.py:3481 (indicateur overwrite de la segmentation).

Legacy (3c67957) ; absent de VISOR : l'entrée n'est jamais modifiée ; les sorties vont sous output_dir avec un suffixe (SADT-VISOR sadt_flexreg/__init__.py:160-163), et aucune segmentation n'est lancée.

Bug confirmé : vtkICP.__call__ (aussi vrai dans VISOR)

vtkICP.__call__ renvoie source inchangé au lieu du maillage transformé. Sans conséquence ici, car list_icp ne contient qu'une seule méthode, mais une chaîne de plusieurs étapes ne fonctionnerait pas telle qu'elle est écrite.

Aussi vrai dans VISOR : return source, VTKMatrixToNumpy(...) (SADT-VISOR sadt_flexreg/ICP.py:113 ; legacy FlexReg_CLI/FlexReg_Method/ICP.py:104). Toujours sans conséquence, car register applique lui-même la matrice renvoyée (pipeline.py:218-224).

La détection de la segmentation passe par une exception (Legacy uniquement)

Un maillage segmenté sous un nom de tableau autre que Universal_ID déclenche une re-segmentation complète.

Legacy (3c67957) ; absent de VISOR : il n'y a pas de re-segmentation. Ce que fait VISOR à la place est différent et plus discret : voir « Without Universal_ID, the last array is used » dans Constats dans VISOR.

Code mort : downloadModel(), setup_cli_command() / find_cli_parameters().

Patch décidé en 2D projeté (aussi vrai dans VISOR)

Le patch butterfly est décidé en 2D projeté : sur une arcade fortement inclinée après l'orientation, le contour peut attraper des sommets très éloignés en z.

Aussi vrai dans VISOR : les distances utilisent V[:,:2] (SADT-VISOR sadt_flexreg/make_butterfly.py:127, 133, 147, 159 ; legacy make_butterfly.py:114, 120, 134, 146), et l'aperçu Slicer fait de même côté client (FlexRegLib/butterfly_preview.py).

10. Littérature

Explication en langage courant et maths : page de l'atlas.

Le fondement publié est AReg IOS: Automatic Registration on IntraOral Scans (Hutin, Anchling, Cevidanes et al., Lecture Notes in Computer Science, 2023) : segmentation des couronnes par DentalModelSeg, alignement initial par centroïdes partagés, ROI palatine segmentée par analyse de forme 3D multi-vues, puis ICP. FlexReg en est la version « l'opérateur dessine la ROI au lieu de la faire prédire ».

Aucun article ne traite spécifiquement de FlexReg ni de la variante MGL : cette dernière semble être un développement interne resté inédit à ce jour. Les chiffres cités dans le code (4,2 mm contre 1,2 mm sur 364 prédictions) ne sont sourcés nulle part en dehors des commentaires.
