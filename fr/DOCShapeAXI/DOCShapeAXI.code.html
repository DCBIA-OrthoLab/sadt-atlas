DOCShapeAXI, legacy : le code

Pour les développeurs : ce que fait le module Slicer legacy dans le code, avec des références file:line, des signatures, des tableaux et des pièges. L'explication lisible du même pipeline, avec les maths, est sur la page de l'atlas.

Code Atlas (explication) Prieto 2024 · SPIE DOCShapeAXI_CLI env conda : shapeaxi VISOR Bibliographie

Dental Oral and Craniofacial Shape Analysis eXplainability and Interpretability. Une seule action de l'utilisateur : choisir un type de données, un dossier d'entrée, un dossier de sortie. Tout le reste, quel checkpoint, quelle architecture, combien de classes, est déduit du type de données.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, est décrit sur sa propre page, DOCShapeAXI sur VISOR. Les encadrés ci-dessous qui ne valent plus dans VISOR le disent dans leur titre.

3. Entrées et prétraitement

Explication en langage courant et maths : page de l'atlas.

3.1 Le CSV

Le CLI liste à plat args.input_dir, garde les fichiers .vtk, et écrit <output_dir>/files_<data_type>.csv avec l'en-tête surf et un nom de fichier par ligne (csv_edit, DOCShapeAXI_CLI.py:105). Les chemins sont relatifs ; SaxiDataset les joint avec mount_point = input_dir.

data_type contient des espaces (« Mandibular Condyle »), donc le csv s'appelle files_Mandibular Condyle.csv. Le csv n'est régénéré que s'il n'existe pas déjà (DOCShapeAXI_CLI.py:285) : ajouter des maillages au dossier d'entrée sans vider le dossier de sortie ne les fera pas traiter.

3.2 Normalisation géométrique

Explication en langage courant et maths : page de l'atlas.

EvalTransform → UnitSurfTransform → utils.GetUnitSurf → ScaleSurf:

  1. centre = milieu de la boîte englobante (pas le centroïde) ;
  2. translater les points vers ce centre ;
  3. facteur d'échelle 1 / ||bounds_max - center||, appliqué uniformément.

Le maillage tient donc dans la sphère unité, indépendamment de sa taille réelle. Toute information d'échelle absolue est perdue : un petit condyle et un grand condyle de même forme sont identiques pour le réseau.

Bug confirmé (paquet shapeaxi, tel qu'installé pour le module legacy)

Daté : ceci a été lu dans shapeaxi 1.0.10 (la copie installée dans l'environnement shapeaxi de Slicer 5.12.3) et dans la 1.1.1 (téléchargée pour cette passe ; hors __about__.py, les deux paquets sont identiques octet pour octet), et la transformation est la même en 2.0.2 et 2.0.3. L'outil VISOR construit son jeu de données de la même façon, en passant scale_factor à EvalTransform dans les deux passes (SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/engine.py:25-28), contre un shapeaxi==1.1.1 épinglé (pyproject.toml:30). La 1.1.1 ignore aussi la valeur : son saxi_transforms.py est identique à celui de la 1.0.10 (DOCShapeAXI sur VISOR). À savoir : saxi_predict lit model.hparams.scale_factor (0.0507 dans le checkpoint des condyles) et le passe à EvalTransform(scale_factor) (DOCShapeAXI_CLI.py:209), mais UnitSurfTransform.__call__ (saxi_transforms.py:48-57) appelle utils.GetUnitSurf(surf) sans le transmettre quand l'entrée est un vtkPolyData. Le facteur d'échelle appris à l'entraînement est donc silencieusement ignoré à l'inférence, remplacé par une normalisation par sujet. C'est un bug du paquet shapeaxi, pas du dépôt, mais il modifie bien le prétraitement réel. saxi_gradcam, d'ailleurs, construit son jeu de données avec EvalTransform() sans argument : les deux passes finissent cohérentes entre elles.

3.3 Ce que renvoie le DataLoader

SaxiDataset(..., CN=True, class_column=None, scalar_column=None) → (V, F, CN) par sujet :

  • V : sommets (1, Nv, 3) après normalisation ;
  • F : triangles (1, Nf, 3) ;
  • CN : normales encodées en couleur, utils.ComputeNormals puis GetColorArray(surf,"Normals") divisé par 255 → (1, Nv, 3) dans [0,1].

Aucun scalaire du maillage n'est jamais lu (surf_property=None) : seules la géométrie et les normales entrent. batch_size=1, pas de remplissage, donc des maillages de tailles différentes passent sans problème.

4.2 L'architecture réellement utilisée

Explication en langage courant et maths : page de l'atlas.

Ce n'est pas un PointNet, ni le fly-by-CNN ResNet-18 du papier ShapeAXI d'origine. SaxiMHAFBClassification (MHA Fly-By) a deux branches fusionnées tardivement.

Vérifié (checkpoints legacy ; mêmes fichiers dans VISOR)

Le manifeste de données de VISOR-serve liste les mêmes cinq checkpoints de la même release shapeaxi-ckpt-v1 (scripts/data-manifest.yml:597-614) et le catalogue de l'outil s'appuie sur les mêmes classes de réseau (catalog.py:24-25,50-71). Les valeurs ci-dessous n'ont pas été remesurées sur les copies de VISOR (DOCShapeAXI sur VISOR). Les valeurs ci-dessous (K=128, 256 têtes, 42 vues, image_size=224…) ont été confirmées par une lecture antérieure des hyper_parameters et du buffer ico_verts du checkpoint condyles_4_class.ckpt. Cette lecture n'a pas été refaite pour cette passe (aucun .ckpt n'est sur la machine) ; les mêmes nombres sont aussi les valeurs par défaut du code (saxi_nets_lightning.py:2392-2405, shapeaxi 1.0.10).

Branche A : nuage de points.

  • sample_points_from_meshes(X_mesh, 4096) (pytorch3d) : échantillonnage uniforme de 4096 points sur la surface ;
  • MHAEncoder : Linear(3→256), puis 4 étages avec sample_levels = [4096, 2048, 512, 128]. À chaque étage, MHA_KNN (attention multi-têtes restreinte aux K=128 plus proches voisins, 256 têtes) puis un FeedForward résiduel (caché 64). Entre les étages, sous-échantillonnage aléatoire jusqu'au niveau suivant, en reportant les indices pour cumuler un poids par point d'origine (x_w) ;
  • Linear(256→256), FeedForward, puis SelfAttention (attention additive Linear(256→64) → tanh → Linear(64→1) → sigmoid, normalisée puis somme pondérée) qui réduit les 128 tokens à un seul vecteur de 256.

Branche B : multi-vues.

  • caméras aux sommets d'un icosaèdre subdivisé (subdivision_level=2, radius=1.35 : la valeur par défaut de --radius, saxi_nets_lightning.py:2396 ; le rayon utilisé est self.hparams.radius, :2371, lu dans le checkpoint, et aucun checkpoint n'était disponible pour le relire). Le buffer ico_verts du checkpoint a la forme (42, 3) : 42 vues par sujet ;
  • rendu pytorch3d : FoVPerspectiveCameras, look_at_rotation vers l'origine, AmbientLights (pas d'ombrage directionnel), HardPhongShader, RasterizationSettings(image_size=224, blur_radius=0, faces_per_pixel=1, max_faces_per_bin=200000) ;
  • chaque vue est un tenseur à 4 canaux : RVB (les normales encodées en couleur posées en TexturesVertex) plus le z-buffer. D'où in_channels=4 ;
  • TimeDistributed(EfficientNetBN('efficientnet-b0', spatial_dims=2, in_channels=4, num_classes=256)) de MONAI : les 42 vues sont aplaties dans la dimension de lot, passent dans le même CNN, puis sont remises en forme (1, 42, 256) ;
  • FeedForward, nn.MultiheadAttention(256, 256 heads, batch_first=True) en auto-attention sur les 42 vues, puis SelfAttention → un vecteur de 256.

Fusion. torch.cat([x_points, x_views], dim=1) → 512, puis fc = Linear(512, num_classes). Pour la régression, Linear(512, 1) et une perte MSE.

Le rendu est refait à chaque passe : il n'y a pas de cache d'images.

4.3 Ce que le réseau produit littéralement, et comment une classe en est déduite

x = model(X_pc, X_views)                       # (1, num_classes), raw logits
if args.nn == 'SaxiMHAFBClassification':
    x = softmax(x).detach()
    x = torch.argmax(x, dim=1, keepdim=True)   # the class integer
predictions.append(x)

(DOCShapeAXI_CLI.py:230-235)

  • classification : seul l'argmax est conservé. Les probabilités softmax sont calculées puis jetées ; aucune mesure de confiance ne sort du module ;
  • régression : la valeur brute de Linear(512,1) est écrite telle quelle (ratio d'obstruction, sur une échelle de 0 à 100 à l'entraînement) ;
  • le softmax n'a de toute façon aucun effet sur l'argmax.

Un détail d'entraînement visible dans le code amont : en classification, la cible n'est pas un one-hot mais des probabilités de classe douces (soft_class_probabilities : des gaussiennes centrées sur [12.5, 37.5, 62.5, 87.5] avec widths = 12.5). Les 4 classes de sévérité sont donc en réalité des quartiles d'une grandeur continue sur une échelle de 0 à 100, ce qui explique pourquoi un modèle de régression existe sur le même jeu de données des voies aériennes.

5. Le mécanisme d'explicabilité

Explication en langage courant et maths : page de l'atlas.

Note (legacy uniquement)

Legacy (3c67957) ; absent de VISOR : explain: bool = True est un argument qui peut être désactivé (SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/__init__.py:22,93-95 ; voir DOCShapeAXI sur VISOR). C'est la partie la plus distinctive du module, et elle s'exécute systématiquement après la prédiction : ni option ni case à cocher (saxi_gradcam, DOCShapeAXI_CLI.py:129).

a) La couche ciblée.

target_layer = getattr(model.convnet.module, '_blocks')
mv_cam = LayerGradCam(model, target_layer[-1], device_ids=[0])

model.convnet.module est l'EfficientNet-B0 ; _blocks[-1] est son dernier bloc MBConv.

Piège (aussi vrai dans VISOR)

Aussi vrai dans VISOR : LayerGradCam(model, blocks[-1]) sur model.convnet.module._blocks (SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/engine.py:82-83 ; voir DOCShapeAXI sur VISOR). Conséquence majeure : la saillance ne décrit que la branche multi-vues. La branche nuage de points, qui contribue à la moitié du vecteur fusionné, n'apparaît nulle part dans la carte. Le x_w (poids par point) que l'encodeur est capable de produire n'est ni récupéré ni écrit.

b) Une carte par classe. Une boucle for class_idx in range(num_classes) avec mv_cam.attribute(inputs=(X_pc, X_views), target=class_idx, attr_dim_summation=False) : Captum rétropropage le logit de la classe class_idx jusqu'aux activations du bloc, multiplie par les gradients moyennés, et renvoie un tenseur à la résolution de la carte d'activation (7×7 pour EfficientNet-B0 en 224×224), pour les 42 vues à la fois. attr_dim_summation=False garde la dimension des canaux, qui est écrasée juste après par mv_att.sum(dim=1).

c) Remise à l'échelle (scale_cam_image, DOCShapeAXI_CLI.py:46, adaptée de pytorch-grad-cam) : cv2.resize vers 224×224, écrêtage aux 1er et 99e centiles, puis une remise à l'échelle affine dans [-1, 1]. L'écrêtage par centiles évite qu'un pixel aberrant n'écrase toute la dynamique ; la sortie est donc signée, pas une probabilité. La remise à l'échelle divise par max - min de la carte écrêtée sans garde (DOCShapeAXI_CLI.py:58) : une carte dont toutes les valeurs sont égales donne 0/0, donc la surface recevrait des valeurs NaN. VISOR ajoute la garde (SADT-VISOR pipeline.py:192-197).

d) Reprojection sur le maillage (gradcam_process, dans shapeaxi ; lu dans la 1.0.10 saxi_gradcam.py:112-144, identique dans la 1.1.1), le cœur du mécanisme :

P_faces = torch.zeros(1, F.shape[1])
V_gcam  = -1 * torch.ones(V.shape[1])
for pf, gc in zip(PF.squeeze(), GCAM):          # one view at a time
    P_faces[:, pf] = torch.maximum(P_faces[:, pf], gc)
faces_pid0 = F[0, :, 0].to(torch.int64)
V_gcam[faces_pid0] = P_faces
V_gcam[V_gcam < 0] = 0
  • PF est le pix_to_face du rastériseur : pour chaque pixel de chaque vue, l'indice du triangle visible, ou -1 sur le fond (saxi_nets_lightning.py:2455-2456). La valeur du pixel est reportée sur la face ;
  • les faces démarrent à 0 et la mise à jour est maximum(old, new), donc d'une vue à l'autre l'agrégation est un maximum, pas une moyenne, et une valeur négative ne survit jamais : sur le maillage la plage est [0, 1], donc la valeur d'une face est max(0, max over views), pas max s. Une région vue une fois et jugée saillante garde sa valeur ;
  • à l'intérieur d'une vue, de nombreux pixels montrent la même face. P_faces[:, pf] = ... assigne alors par un indice répété, et PyTorch ne dit pas quelle écriture est conservée : ce n'est pas un maximum sur les pixels. Essayé sur CPU avec torch 2.12.1 (indices [0,0,0,1,-1,-1], valeurs [.9,.1,.5,.3,.8,.2]) : la face 0 a fini à 0.5, le dernier de ses trois pixels, pas à 0.9. Non essayé sur GPU, où l'ordre n'est pas garanti ;
  • pour les pixels -1, la même indexation écrit sur la dernière face du maillage (indice négatif de Python), dans chaque vue ; la valeur de cette face est ce que le fond y a écrit. Le même test a montré la dernière face écrasée (0.2). Une seule face sur tout le maillage ;
  • le passage face vers sommet est grossier : la valeur de chaque face est écrite sur son premier sommet (F[0,:,0]) ; un sommet qui est le premier sommet de plusieurs faces garde l'une de leurs valeurs (indice répété encore). Les sommets jamais utilisés comme premier point d'un triangle restent à -1, puis sont remis à 0 par la dernière ligne. La carte est donc parsemée de zéros structurels ;
  • les faces qui ne sont jamais rastérisées (intérieur, occlusions permanentes) restent à 0.

Note de version. shapeaxi 2.0.2 et 2.0.3, ce que l'installeur récupère aujourd'hui (shapeaxi>=2.0.2), ont la même fonction sans la dernière ligne (saxi_gradcam.py:31-62 dans la 2.0.2 : pas de V_gcam[V_gcam<0]=0), donc les sommets qui ne sont le premier sommet de personne resteraient à -1 là-bas. Ce module ne peut de toute façon pas tourner sur la 2.x (voir le bug ci-dessous), donc le comportement décrit ici est celui de la 1.x pour laquelle la commande a été écrite.

e) Lissage et écriture.

surf.GetPointData().AddArray(mv_att_upscaled)
psp.MedianFilter(surf, mv_att_upscaled)
utils.WriteSurf(surf, out_surf_path)

MedianFilter (post_process.py:294-308) remplace chaque sommet, les remplis comme les vides, par la médiane de ses voisins topologiques, le sommet lui-même exclu (utils.py:363-376) : il comble beaucoup des trous laissés par le report du « premier sommet » et lisse aussi les valeurs qui étaient là (1 passe, en place ; la médiane est prise sur une copie, donc l'ordre des sommets n'importe pas). Il modifie le vtkDataArray déjà ajouté au maillage, c'est donc bien la version filtrée qui est écrite.

Le nom du tableau est fixé dans gradcam_process :

Le fichier est réécrit à chaque itération de classe, en accumulant les tableaux : le .vtk final porte les N cartes. C'est ce que le README vous fait sélectionner dans le module Models → Scalars → Active Scalar, avec la table ColdToHotRainbow.

Une version antérieure de cette page affirmait ici que gradcam_save() (DOCShapeAXI_CLI.py:65) appelle shutil.copy alors que shutil n'est jamais importé. C'est faux à 3c67957 : import shutil est à la ligne 4 du fichier, et l'appel à la ligne 80. Ce qui reste vrai, c'est que la fonction n'est jamais appelée. Divergence code / papier (vraie aussi dans VISOR)

Aussi vrai dans VISOR : l'outil charge les mêmes réseaux SaxiMHAFBClassification et SaxiMHAFBRegression (SADT-VISOR catalog.py:24-25,50-71 ; voir DOCShapeAXI sur VISOR). Le code diverge de l'article. L'article décrit un rendu multi-vues sur une subdivision d'icosaèdre traité par un ResNet-18 plus une attention additive, avec les condyles traités comme une classification binaire. Les checkpoints distribués ici sont des modèles SaxiMHAFB* : EfficientNet-B0 sur 42 vues plus une seconde branche nuage de points avec attention KNN, absente de l'article, avec un checkpoint condyles_4_class à 4 classes de sévérité. Ne pas présenter les chiffres de l'article SPIE comme ceux des modèles téléchargés.

2. Le jeu de données des voies aériennes. Explainable Artificial Intelligence to Quantify Adenoid Hypertrophy-related Upper Airway Obstruction using 3D Shape Analysis, Mattos et al., J Dent 2025. Celui-ci décrit exactement l'architecture du code : une branche multi-vues EfficientNet-B0 préentraînée sur ImageNet + attention multi-têtes, une branche nuage de 4096 points avec attention KNN, et l'explicabilité par « SurfGradCAM », le mécanisme du §5. Les trois tâches (4 classes, binaire, régression du ratio d'obstruction) correspondent aux trois checkpoints airways_*. AUC 0,77–0,94, R = 0,854 pour le ratio.

3. L'origine du module Slicer : lucieDLE/DOC-ShapeAXI, cité par le README.md du dépôt.
