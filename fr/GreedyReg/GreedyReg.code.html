GreedyReg, legacy : le code

Pour les développeurs : ce que fait le module Slicer legacy GreedyReg dans le code (SlicerAutomatedDentalTools à 3c67957), avec les références file:line, les signatures, les arguments, l'environnement et les pièges. L'explication lisible du même pipeline, avec les maths, est sur la page de l'atlas. Le portage VISOR a sa propre page de code.

Code Atlas (explication) Venet 2019 · arXiv GreedyReg_CLI env conda : aucun (Python de Slicer) VISOR Guide Bibliographie
Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute une partie de cet outil sur un serveur, est décrit dans VISOR : comment cet outil tourne aujourd'hui. C'est un portage partiel : seul le recalage Greedy de dossier à dossier y existe. Le mode manuel et le mode Distant (par landmarks) des sections 4.1 et 4.3 n'ont pas d'équivalent dans l'outil serveur.

Les références VISOR se lisent SADT-VISOR GreedyReg/pipeline.py:74 : c'est tools/GreedyReg/src/sadt_greedyreg/pipeline.py à 6ba2a78. VISOR-serve est e9a7e5d, AutomatedDentalToolsRemote est 19b95e8. Les lignes legacy s'écrivent GreedyReg_CLI.py:41@3c67957 ; un numéro de ligne legacy nu sur cette page se lit aussi à 3c67957. GreedyReg.py est le widget (GreedyReg/GreedyReg.py), Logic.py est GreedyReg/GreedyReg_Method/Logic.py, GreedyReg_CLI.py est GreedyReg_CLI/GreedyReg_CLI.py.

Recalage de scans CBCT T1/T2 en appelant le binaire greedy d'ITK-SNAP comme sous-processus. Aucun réseau n'est entraîné ni appelé dans le chemin principal : le seul réseau utilisé par le module sert à l'initialisation « distante », et c'est ALI_CBCT, emprunté tel quel.

4. Les trois modes, et ce qui les distingue vraiment

Explication en langage courant et maths : page de l'atlas.

ModeCe qui est calculéQui le calculeSortie
Manual Alignment rien : l'opérateur déplace un vtkMRMLLinearTransformNode widget matrice dans la scène, utilisée comme -ia
Automatic Registration affine ou rigide, par optimisation d'une métrique d'intensité calculé binaire greedy, via le CLI .nii.gz recalé + .mat
Distant Registration rigide en forme close (SVD/Kabsch) sur 3 à 5 landmarks prédits prédit calculé widget + ALI_CBCT seulement une matrice, à affiner ensuite
Piège de vocabulaire

Legacy uniquement (3c67957) ; absent de VISOR. L'outil serveur n'a pas de mode Distant (SADT-VISOR GreedyReg/__init__.py:38-52). La dernière phrase ci-dessous est aussi propre au module legacy : avec VISOR, les scans sont envoyés à un serveur et tout le recalage s'y déroule.

Le mot « Distant » ne désigne pas un calcul à distance. Le panneau s'intitule « Distant Registration (Large Misalignment) » : il vise deux scans qui partent éloignés géométriquement (un grand désalignement initial). Tout s'exécute en local. Pas de réseau, pas de socket, pas de chiffrement, pas d'attestation : le module ne contient aucune requête sortante en dehors de urllib.request.urlretrieve vers SourceForge (le binaire greedy) et vers les releases GitHub du dépôt (poids d'ALI). Le seul contact avec l'extérieur est donc le téléchargement d'outils, jamais l'envoi de données de patients.

4.1 Mode manuel

Explication en langage courant et maths : page de l'atlas.

Deux ensembles de commandes agissent sur le même nœud de transformation :

  • six curseurs ctkSliderWidget (rotations ±180°, translations ±200 mm), composés dans cet ordre : Translate puis RotateX, RotateY, RotateZ (GreedyReg.py:1135-1140) ;
  • « Center T2 on T1 » : une translation pure entre les centres des deux volumes, calculée en IJK puis convertie en RAS par GetIJKToRASMatrix (Logic.py:383-396) ;
  • les poignées natives de Slicer (SetEditorScalingEnabled(False) → jamais de mise à l'échelle) ;
  • un prototype assumé, « Sensitivity Demo » : une roue Qt rattachée aux vues Red/Yellow/Green. L'axe de rotation dépend de la vue (Red→Z, Yellow→X, Green→Y), un glissement hors de la roue translate dans le plan de coupe (0,5 mm/pixel × gain), et la taille de la roue suit le zoom (baseFov / fovMean, borné à 0.55-1.90). Le commentaire en GreedyReg.py:503 en donne la raison : les poignées natives recalculent leur delta à partir de la position brute de la souris, donc amortir la matrice après coup n'a aucun effet visible.

Le volume mobile n'est pas durci avant l'export : slicer.util.exportNode(node, path) vaut par défaut world=False (vérifié dans slicer/util.py), donc la transformation manuelle n'arrive à greedy que par le fichier -ia. Voir le §9 pour le problème de convention que cela soulève.

4.2 Mode automatique

Explication en langage courant et maths : page de l'atlas.

onRunRegistration() (GreedyReg.py:1147) construit une arborescence dans tempfile.mkdtemp() : T1/, T2/, INIT/, MASK/, OUTPUT/, exporte les deux volumes sous l'identifiant factice CASE0001, écrit l'init, puis appelle le CLI en mode lot à une seule paire. Il n'existe pas de chemin de code dédié au cas unique : c'est un lot sur un dossier contenant un seul fichier.

Un QTimer d'1 s interroge le cliNode ; à la fin, le volume recalé est chargé depuis le dossier temporaire. Ce dossier n'est jamais supprimé (pas de rmtree dans le widget) : les résultats survivent jusqu'au nettoyage du système, et c'est aussi de cela que dépend le bouton « Save Registered Volume », puisqu'il s'agit d'un simple shutil.copy.

4.3 Mode Distant

Explication en langage courant et maths : page de l'atlas.

onRunDistantRegistration() (GreedyReg.py:1347):

  1. une seule région est retenue, par ordre de priorité base du crâne > mandibule > maxillaire (_selectedDistantRegion, GreedyReg.py:1338) : cocher plusieurs cases n'additionne pas leurs landmarks, la première trouvée l'emporte ;
  2. les deux volumes sont exportés en .nii.gz dans un dossier temporaire ;
  3. une file de tâches pour ALI est construite : une tâche par (scan × sous-dossier de modèle), exécutées en série en chaînant des observateurs ModifiedEvent (GreedyReg.py:1440) ;
  4. les fichiers json de sortie sont relus, les coordonnées converties LPS → RAS ([-x, -y, z], Logic.py:534) ;
  5. si ≥ 3 landmarks sont communs aux deux scans, rigidFromLandmarks() (Logic.py:537) calcule une transformation rigide par SVD ; sinon, un échec explicite.

Régions et landmarks (REGION_CONFIG, Logic.py:24-34) :

RégionLandmarksDossiers de poids
MANDMASKRGo, LGo, Gn, Me, PogLower_Bones_1, Lower_Bones_2
MAXMASKA, ANS, LOr, ROr, PNSUpper_Bones_v2
CBMASKS, N, RPo, LPoCranial_Base

Les poids viennent de la release v0.1-v2.0_models du dépôt, un .zip par dossier, extrait dans Documents/SlicerDownloads/GreedyReg/ALIModels/<folder>/ (Logic.py:43,412).

Le réseau appelé. ALI_CBCT ne produit pas de heatmap : c'est de l'apprentissage par renforcement. Un agent par landmark navigue dans le volume, observe un cube de agent_FOV = [64,64,64] voxels, et choisit un déplacement dans MOVEMENTS ; le réseau DNet (une couche de transition à 1024 canaux, out_channels = len(MOVEMENTS["id"])) est rechargé pour chaque landmark à partir des fichiers .pth du dossier (ALI_CBCT/ALI_CBCT.py:138 ; les fichiers sont collectés en ALI_CBCT/ALI_CBCT_utils/io.py:79-80). Paramètres imposés par GreedyReg (Logic.py:473-492) : spacing = [1, 0.3] mm (recherche grossière puis fine), speed_per_scale = [1,1], spawn_radius = 10, DCMInput = false.

Le calcul rigide (Logic.py:537) est un Kabsch classique calculé : centrage, H = movingᵀ·fixed, SVD, R = vt.T @ U.T (soit R = V·Uᵀ dans la notation usuelle, avec H = U·S·Vᵀ), correction de réflexion si det(R) < 0, t = c_fixed − R·c_moving. La matrice obtenue va donc du mobile vers le fixe, en RAS : exactement la convention d'un nœud de transformation Slicer, où elle est placée telle quelle.

Vérifié

Legacy uniquement (3c67957) ; absent de VISOR. Le mode est absent de l'outil serveur (SADT-VISOR GreedyReg/__init__.py:38-52).

Le message de fin est honnête : « Distant registration complete! Now run Automatic Registration to refine. » (GreedyReg.py:1407). Ce mode ne recale pas, il initialise.

5. La ligne de commande greedy

Explication en langage courant et maths : page de l'atlas.

buildRegistrationCommand() (GreedyReg_CLI.py:104-125) produit toujours exactement ceci, sans autre option exposée que la métrique et le nombre de degrés de liberté :

greedy -d 3 -a \
  -m NMI | -m NCC 4x4x4 | -m SSD \
  -i <T1.nii.gz> <T2.nii.gz> \
  -o <ID>_warp.mat \
  -n 100x100x50x25 \
  -e 0.5 \
  -search 100 10 20 \
  -dof 6|12 \
  -ia <init.mat> \
  [-gm <binarized mask>]
OptionValeurSignification (docs de greedy)
-d 3fixedimension de l'image
-afixemode affine/rigide. Le mode difféomorphe de Greedy, qui est son mode par défaut et sa raison d'être, n'est jamais utilisé ici
-m NMIindice 0 (défaut de l'interface)information mutuelle normalisée, pour des intensités hétérogènes
-m NCC 4x4x4indice 1corrélation croisée locale, rayon en voxels : 4x4x4 donne une fenêtre de 9x9x9
-m SSDindice 2somme des différences au carré, même modalité
-i fixed movingT1 puis T2ordre fixe : -i <fixed> <moving>
-o<ID>_warp.matmatrice affine 4×4 (texte)
-n 100x100x50x25fixe4 niveaux de pyramide multi-résolution, 100/100/50/25 itérations du plus grossier au plus fin (le défaut de greedy est 100x100, 2 niveaux)
-e 0.5fixepas de temps, sans effet en mode affine : la doc de greedy dit clairement que « -s and -e have no effect » pour -a. Ligne morte
-search 100 10 20fixerecherche aléatoire sur 100 transformations rigides avant l'optimisation : σ_angle = 10°, σ_offset = 20 (en voxels d'après la prose de la doc, en unités physiques d'après son texte d'usage, l'ambiguïté est dans greedy, pas ici)
-dof 6 / 12liste déroulante « Rigid »/« Affine »6 = rigide, 12 = affine complet. -dof 7 (rigide + échelle uniforme) n'est pas proposé
-iatoujours fournimatrice d'initialisation. Jamais -ia-identity, jamais -ia-image-centers
-gmsi un masque est donnémasque du volume fixe : les gradients de la métrique ne sont calculés qu'à l'intérieur

Puis un second appel, toujours exécuté, en mode rééchantillonnage :

greedy -d 3 -rf <T1> -rm <T2> <ID>_registered.nii.gz -r <ID>_warp.mat

-rf fixe l'espace de référence (le volume fixe), -rm la paire entrée/sortie. Le volume de sortie est donc le T2 d'origine rééchantillonné dans la grille de T1, avec une interpolation linéaire (le défaut de -ri). Chaque appel est plafonné à timeout = 600 s (GreedyReg_CLI.py:128-142).

6. Entrées, appariement, masques, initialisation

Explication en langage courant et maths : page de l'atlas.

Piège

Legacy uniquement (3c67957) ; absent de VISOR. Le portage apparie selon la règle commune de sadt_areg_common.pairing : récursive, casse conservée, jetons de point temporel retirés, sorties antérieures exclues (SADT-VISOR AREG/common/src/sadt_areg_common/pairing.py:175-276). Exécuté le 2026-11-09 : 01_T1.nii.gz donne 01, Patient-01.nii.gz donne Patient_01. Les patients présents d'un seul côté sont signalés sous unmatched, et l'absence totale de paire est une ValueError (SADT-VISOR GreedyReg/__init__.py:102-122). Legacy : GreedyReg_CLI.py:41,44-53@3c67957.

Appariement. ID_PATTERN = ^([A-Za-z]+\d+) appliqué au nom de fichier, mis en majuscules (GreedyReg_CLI.py:41,50-52). A01_t1.nii.gz → identifiant A01. Une paire existe quand le même identifiant se trouve à la fois dans le dossier T1 et dans le dossier T2 ; les masques (.nii/.nii.gz) et les inits (.mat) sont facultatifs et appariés par le même identifiant. Un fichier nommé 01_T1.nii.gz (chiffres d'abord) ou Patient-01.nii.gz n'est jamais apparié, silencieusement.

findBatchPairs() dans le widget (Logic.py:306) duplique cette logique pour l'étiquette « Found N pairs » ; le commentaire avertit que les deux implémentations doivent rester synchronisées.

Masque. Exporté depuis un vtkMRMLSegmentationNode ou une labelmap en .nii.gz, puis binarisé côté CLI : (get_fdata() > 0).astype(np.float32) (GreedyReg_CLI.py:96-101). Tous les segments d'une segmentation multi-étiquettes sont donc fusionnés en un seul masque. C'est le seul vrai usage de nibabel, avec la réécriture de l'affine du lot distant.

Piège

Aussi vrai dans VISOR (SADT-VISOR GreedyReg/pipeline.py:101-114, matrix[0, 3] = 0.001 en :111) : le portage garde volontairement le coup de pouce et sa raison (SADT-VISOR tools/GreedyReg/README.md, « Kept deliberately »). Legacy : GreedyReg_CLI.py:86-93@3c67957 pour l'init par défaut du CLI ; l'init manuelle du widget reçoit le même coup de pouce quand sa translation est nulle (Logic.py:279-283@3c67957).

Initialisation. Sans fichier d'init, writeIdentityInit() (GreedyReg_CLI.py:86-93) écrit l'identité avec matrix[0,3] = 0.001 : une translation d'un micron. Le commentaire explique pourquoi : « so Greedy doesn't treat it as identity. » Ce comportement n'est documenté nulle part du côté de greedy ; c'est un contournement empirique, et il faut le traiter comme tel.

Aucun prétraitement d'intensité : ni normalisation, ni recadrage, ni rééchantillonnage préalable, ni conversion d'orientation. Les fichiers NIfTI sont passés tels quels, et greedy travaille dans l'espace physique RAS des en-têtes.

7. Mode lot

Explication en langage courant et maths : page de l'atlas.

Deux lots indépendants, qui ne font pas la même chose.

Lot automatique (GreedyReg.py:1477-1544). Le widget ne boucle pas : il lance un seul GreedyReg_CLI sur les dossiers, et c'est le CLI qui itère (main(), GreedyReg_CLI.py:145-194), en émettant des balises <filter-progress> / <filter-comment> lues par l'infrastructure CLI de Slicer. Le dossier de sortie est le dossier T2 lui-même. Le dossier de masques, si le champ est rempli, est transmis (_batchAutoMaskEdit en GreedyReg.py:1480, maskFolder=maskFolder en :1515) et binarisé par le CLI (GreedyReg_CLI.py:96-101, 177-179) ; aucune init n'est transmise (initFolder="") : le lot part toujours de l'identité décalée. Premier cas qui échoue → sys.exit(1) → tout le lot s'arrête (GreedyReg_CLI.py:186-188).

Lot Distant (GreedyReg.py:1545). Ici, le widget boucle cas par cas, avec une file de tâches ALI par paire. Le résultat n'est pas un volume recalé mais un en-tête réécrit (GreedyReg.py:1630-1638) :

new_affine = moving_img.affine.copy()
new_affine[:3, :3] = R @ moving_img.affine[:3, :3]
new_affine[:3, 3] = R @ moving_img.affine[:3, 3] + t
aligned_img = nib.Nifti1Image(moving_img.get_fdata(), new_affine, moving_img.header)
Vérifié

Legacy uniquement (3c67957) ; absent de VISOR. Le mode Distant est absent. Dans le portage, Greedy rééchantillonne l'image mobile dans l'image fixe (SADT-VISOR GreedyReg/pipeline.py:97-98, appelé en SADT-VISOR GreedyReg/__init__.py:276) et les sorties vont dans un output_dir séparé. Legacy : GreedyReg.py:1637@3c67957.

Les voxels ne bougent pas, seule l'affine voxel→monde change. C'est correct : l'affine NIfTI est en RAS, comme la matrice Kabsch. Sortie : <ID>_t2_aligned.nii.gz, écrite dans le dossier T2. Greedy n'est pas appelé du tout dans ce lot.

Explication en langage courant et maths : page de l'atlas.

Format de transformation, et la conversion qui n'existe pas. <ID>_warp.mat est un simple fichier texte de quatre lignes, dans la convention propre à greedy : une matrice 4×4 qui envoie les coordonnées RAS du volume fixe vers les coordonnées RAS du volume mobile ([ras(moving);1] = M · [ras(fixed);1], docs de greedy, section « Affine mode »).

Le bouton « Save Transform Matrix » fait un simple shutil.copy de ce fichier (GreedyReg.py:1229-1241).

Piège

Aussi vrai dans VISOR pour la partie « pas de .tfm » : la sortie est <patient>_transform.mat, le fichier brut écrit par -o (SADT-VISOR GreedyReg/pipeline.py:86, SADT-VISOR GreedyReg/__init__.py:255), rien ne le convertit, et le client Slicer ne charge pas les fichiers .mat (AutomatedDentalToolsRemote GreedyRegRemote/GreedyRegRemote.py:97-104). L'affirmation sur LPS et RAS concerne le format de greedy et n'a pas été revérifiée. Un lecteur existe dans VISOR : AutoMatrix accepte une matrice 4x4 brute par un repli et en fait une transformation affine telle quelle, sans changement de convention (AutoMatrix, VISOR ; SADT-VISOR AutoMatrix/pipeline.py:138-164) ; la justesse du mouvement obtenu pour une matrice Greedy n'a pas été testée.

Il n'existe, nulle part dans le module, aucune conversion vers .tfm ou vers quoi que ce soit d'ITK. Qui reprend ce code doit savoir que :

  • ce n'est pas un fichier de transformation ITK (TxtTransform), donc il ne se charge pas comme transformation dans Slicer malgré son extension .mat ;
  • une transformation ITK/Slicer sur disque est en LPS, celle-ci est en RAS : elle demande une conjugaison par diag(-1,-1,1,1), en plus d'une éventuelle inversion ;
  • la conversion attendue passe par c3d_affine_tool (recommandé par la doc de greedy), ou par le même code que FlexReg_CLI.py:100-105@3c67957, qui fait exactement cela pour ses propres matrices.

Comparé à FlexReg, qui produit un .tfm SimpleITK réutilisable, consommé par d'autres modules du dépôt, GreedyReg est une impasse : personne ne consomme sa matrice.

9. Convention d'initialisation : très probablement inversée

Explication en langage courant et maths : page de l'atlas.

Le mode manuel écrit la matrice du nœud de transformation Slicer, telle quelle, dans <ID>_init.mat (Logic.py:279-286).

  • Cette matrice est une MatrixTransformToParent appliquée au volume mobile : elle envoie les coordonnées propres du volume mobile vers les coordonnées du monde, c'est-à-dire mobile → fixe.
  • -ia attend une matrice de même nature que celle produite par -o, c'est-à-dire fixe → mobile.
Piège probable, non confirmé

Legacy uniquement (3c67957) ; absent de VISOR. Le mode manuel est absent. Un fichier initial_transforms est transmis tel quel à -ia (SADT-VISOR GreedyReg/pipeline.py:91, SADT-VISOR GreedyReg/__init__.py:261-265) ; cette page n'a pas testé son sens.

Les deux sont inverses l'une de l'autre. Le pré-alignement manuel est donc très probablement transmis à greedy à l'envers (rotation transposée, translation de signe opposé). Le reste du dépôt connaît cette convention : FlexReg_CLI.py:100-105@3c67957 inverse explicitement, avec le commentaire « ITK convention: fixed -> moving. »

Pourquoi cela ne se voit pas toujours : -search 100 10 20 échantillonne 100 transformations rigides aléatoires avant l'optimisation, et la pyramide à 4 niveaux pardonne beaucoup. Un mauvais point de départ ralentit la convergence et la fragilise, il ne l'empêche pas. À vérifier par un test simple (une translation pure de 20 mm selon X, en comparant l'init écrite et la matrice renvoyée) avant de corriger.

13. Littérature

Explication en langage courant et maths : page de l'atlas.

Le moteur est publié, le module ne l'est pas.

  • greedy : un outil de Paul Yushkevich (PICSL, UPenn), livré avec ITK-SNAP. La référence habituelle pour le citer est Venet, Pati, Yushkevich, Bakas, Accurate and Robust Alignment of Variable-Stained Histologic Images Using a General-Purpose Greedy Diffeomorphic Registration Tool (arXiv:1904.11929). Documentation : greedy.readthedocs.io, code : pyushkevich/greedy. À noter : l'article et l'outil portent sur le recalage difféomorphe ; GreedyReg n'utilise que le mode affine/rigide (-a), qui n'en est que l'étape d'initialisation.
  • ALI_CBCT : Gillot et al., Automatic landmark identification in cone-beam computed tomography, Orthodontics & Craniofacial Research, 2023, des agents virtuels naviguant dans un espace volumétrique multi-échelle, erreur moyenne rapportée de 1,54 ± 0,87 mm sur 32 landmarks. Dépôt d'origine : Maxlo24/ALI_CBCT.
  • GreedyReg lui-même : aucune publication. L'approche, « pré-alignement manuel puis affine fondé sur l'intensité, avec un masque », est celle du panneau Registration d'ITK-SNAP, dont ce module est une transposition dans Slicer ; c'est la seule filiation que le code peut revendiquer.

Bibliographie complète : SOURCES.html, références vérifiées, fichiers récupérés dans ce dossier (l'article de greedy, l'article d'ALI_CBCT), et une distinction détaillée entre ce que décrit l'article de greedy et ce que ce module exécute réellement.
