AutoMatrix

AutoMatrix applique une ou plusieurs transformations à un dossier de volumes et de fichiers de landmarks. Cette page explique comment, étape par étape : dans quel sens chaque fichier se déplace, comment un fichier trouve sa matrice et où atterrit le résultat. Les fichiers, les lignes, les blocs de code et les pièges sont sur la page de code.

non publié Atlas (explication) Code (développeurs) sans conda sans GPU purement calculatoire VISOR Bibliographie

Deux bases de code. Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, est décrit dans VISOR : comment cet outil tourne maintenant. Là où VISOR diffère, une phrase le dit.

Vue d'ensemble : ce qui entre, ce qui sort

Un module de recalage trouve une transformation : comment déplacer un scan sur un autre. AutoMatrix prend ce fichier et l'applique aux autres fichiers du patient. Ni réseau, ni conda, ni GPU : c'est une transformation lue dans un fichier, un rééchantillonneur et un appariement de noms de fichiers.

EntréeSortie
volumes (.nii, .nii.gz, .nrrd) et fichiers de landmarks (.mrk.json), ou un dossier qui en contientles mêmes fichiers déplacés par leur transformation, avec un suffixe (_apply proposé), dans une copie des dossiers d'entrée
transformations (.tfm, .mat, .h5, .txt), ou un dossier qui en contientaucun fichier de transformation : AutoMatrix consomme des transformations et n'en écrit aucune

1. Place dans le pipeline

Aucun module n'appelle AutoMatrix. Il consomme les fichiers de transformation produits par les modules de recalage :

ProducteurFichier produitType de transformation
AREG_CBCTune matrice par patient et par région (_matrix.tfm)affine ou rigide
SEMI_ASO_CBCT<patient>_<name>_transform.tfmune composite de plusieurs transformations
MRI2CBCT_REGISTER<id>_<side>_MRI_transform.tfmaffine, déjà convertie entre RAS et LPS et inversée
Revue et VFACErecalage plus un ajustement manuelune composite
FlexReg<T2><suffix>.tfmaffine, déjà convertie et inversée

La case « From AReg » du panneau code en dur la convention de nommage d'AREG_CBCT (ci-dessous).

2. Fichiers en jeu

Un widget (sélecteurs, validation, miroir, barre de progression), un assistant qui construit les paramètres du module en ligne de commande, une copie du code d'appariement utilisée seulement pour compter, et le module en ligne de commande qui fait tout le travail. Le module s'exécute dans le Python propre de Slicer. Une partie du module vit désormais dans la couche partagée ADTLib.

3. Formats de transformation lus, et ceux qui ne le sont pas

Le panneau annonce .npy, .h5, .tfm, .mat et .txt. Le module en ligne de commande les confie tous à ITK, qui ne connaît que ses propres formats de transformation. Testé avec SimpleITK 2.5.5 de Slicer 5.12 :

ExtensionRésultat réel
.tfm, .txtlu seulement s'il s'agit d'un fichier texte de transformation ITK ; une matrice 4×4 brute est rejetée
.h5, .hdf5lu (mais la recherche dans un dossier ne liste que .h5 : un .hdf5 n'est lu que s'il est donné comme fichier unique)
.matlu (format Matlab)
.npyéchoue : chaque fichier .npy est journalisé puis ignoré

VISOR ne liste plus .npy et accepte un .txt contenant une simple matrice 4×4.

4. La convention de transformation : le point qui casse tout

4.1 Sens de la transformation

ITK (la boîte à outils d'imagerie derrière SimpleITK, qui lit ici les transformations et rééchantillonne les images) va de la sortie vers l'entrée : une transformation donnée à un rééchantillonneur (l'étape qui écrit une nouvelle image sur une grille choisie) associe un point de sortie au point d'entrée où lire. Le contenu visible se déplace donc de l'inverse de la transformation. Le code s'en sert des deux côtés, de façon cohérente : le volume est rééchantillonné avec T telle quelle, et chaque point de landmark est déplacé par l'inverse explicite.

Si une transformation ne peut pas être inversée (un champ de déplacement dense ou une B-spline : les deux lèvent une erreur à l'inversion dans SimpleITK 2.5.5 de Slicer 5.12, essayé le 2026-11-10), le fichier de landmarks de ce patient est ignoré avec un avertissement alors que son volume est tout de même transformé : les deux sorties peuvent se désynchroniser sans bruit.

Dans le codeLe rééchantillonneur et l'inverse explicite, avec les lignes

4.2 RAS / LPS : où se fait l'inversion d'axes, nulle part

Il n'y a pas de flip dans AutoMatrix, et c'est correct. Les fichiers de transformation ITK et la lecture et l'écriture des images sont en LPS, et les fichiers de landmarks du dépôt sont codés en dur en LPS, comme l'est l'écriture par défaut de Slicer. Un point peut donc être donné directement à la transformation. Le point fragile est que le champ coordinateSystem d'un fichier de landmarks n'est jamais lu : un fichier qui déclare du RAS serait déplacé avec x et y du mauvais signe, sans aucun message. Les modules qui produisent les matrices font eux-mêmes la conversion ; AutoMatrix consomme le résultat.

Dans le codeOù chaque module code le LPS en dur

4.3 Composition

Il n'y en a pas. Quand un patient a plusieurs matrices, chacune est appliquée au fichier d'origine, indépendamment, ce qui donne une sortie par matrice. La seule composition est celle qu'ITK a déjà faite : un .tfm contenant plusieurs transformations est relu comme une composite et appliqué en bloc.

Dans le codeLa boucle qui applique chaque matrice à l'original

4.4 Harden

Aucune. L'ancienne version attachait la transformation à un nœud de scène et la « durcissait » ; ce bloc a disparu, et le code qui exportait le nœud est mort.

6. Rééchantillonnage et image de référence

Plus proche voisin pour une carte de labels, linéaire sinon. Dans le module legacy, l'utilisateur le déclare avec une case à cocher ; rien n'est détecté. VISOR le détecte fichier par fichier.

La grille de sortie est choisie dans cet ordre : (1) pour une transformation composite, la référence est devinée d'après le nom de la matrice, ce qui marche parce qu'ASO_CBCT écrit le scan orienté à côté de sa matrice ; (2) une matrice dont le nom contient mirror utilise l'image d'entrée comme sa propre référence ; (3) un fichier de référence donné par l'utilisateur impose sa géométrie ; (4) sinon, l'image d'entrée elle-même.

Dans le codeL'interpolateur et le choix de la grille parmi quatre

7. Mode miroir

Le bouton miroir télécharge une petite matrice depuis une release du dépôt propre du laboratoire et remplit le champ de matrice avec elle. Son contenu est une transformation affine dont la matrice est diag(-1, 1, 1), sans translation.

Son déterminant vaut −1, ce qu'un rééchantillonneur gère sans difficulté pour un volume. Le mode force le suffixe sur _mir et décoche « Add the matrix name ». Dans VISOR, une réflexion appliquée sans référence laisse la boîte de sortie vide (voir la carte de la grille là-bas).

Dans le codeLe téléchargement et le contenu du fichier

8. Appariement fichier ↔ matrice

Une clé patient est construite à partir de chaque nom de fichier, et un scan rencontre la matrice de même clé. Si le chemin de matrice est un fichier unique, il est attaché à chaque patient. La clé vient d'une chaîne de coupes qui n'est pas la même des deux côtés.

Dans le codeGetPatients et les deux listes de jetons

Le chemin « From AReg »

Une table codée en dur associe un suffixe de fichier de landmarks à un nom de matrice AREG_CBCT, en contournant tout l'appariement. Elle est morte et cassée : ses deux lettres de mâchoire sont inversées par rapport au reste du dépôt, elle lit un paramètre que le module en ligne de commande n'a pas, et la case est masquée, donc le chemin n'est jamais pris. VISOR l'a supprimée.

Dans le codeLa table des suffixes et les trois problèmes

9. Sorties

Le nom de sortie est le nom du fichier, puis le suffixe (_apply proposé), puis, quand « Add the matrix name » est coché (il l'est par défaut), le nom entier de la matrice. Pour patient1_MAXReg_matrix.tfm, cela donne patient1_T1_MA_apply_patient1_MAXReg_matrix.nii.gz, et non ce que promettait l'ancien README. Décocher l'option avec plusieurs matrices par patient fait que les sorties s'écrasent les unes les autres ; VISOR force le nom dans ce cas. Les dossiers d'entrée sont reproduits dans le dossier de sortie. Aucun .tfm n'est jamais produit.

11. Environnement

Rien à installer : SimpleITK, numpy, VTK et Qt sont déjà dans Slicer. Ni conda, ni CUDA. Le seul accès réseau est le téléchargement de la matrice miroir, et seulement si la case Mirror est cochée.

12. Pièges et points fragiles

Chaque point est vérifié dans le code et décrit, avec sa preuve, sur la page de code.

  • .npy ne fonctionne pas, bien qu'annoncé. Preuve.
  • Les maillages ne fonctionnent plus, bien qu'annoncés. Preuve.
  • Une matrice texte 4×4 brute est rejetée par le lecteur legacy. Preuve.
  • Le repère des landmarks n'est jamais lu. Preuve.
  • Pas de composition : N matrices donnent N fichiers, pas une chaîne. Preuve.
  • Les sorties s'écrasent les unes les autres si le nom de la matrice n'est pas ajouté. Preuve.
  • Une matrice sans point temporel ne trouve aucun scan, en silence. Preuve.
  • Le miroir se fait par rapport à l'origine du système de coordonnées, et non à la ligne médiane du patient. Preuve.
  • Une matrice non inversible laisse un volume sans ses landmarks. Preuve.
  • Deux copies du code d'appariement ont déjà divergé. Preuve.
  • « From AReg » est mort et cassé. Preuve.
  • La progression passe par un protocole indirect fragile. Preuve.
  • Le widget a plusieurs autres défauts (une division par zéro sur un dossier vide, une validation fausse, du code mort). Résumé.
