AutoMatrix, legacy : le code

Pour les développeurs : ce que fait le module AutoMatrix legacy dans le code, avec des références file:line, des blocs de code, les formats réellement lus, les règles d'appariement et les pièges. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, est décrit dans VISOR : comment cet outil tourne aujourd'hui.

Les références VISOR se lisent SADT-VISOR AutoMatrix/pipeline.py:127 : c'est tools/AutoMatrix/src/sadt_automatrix/pipeline.py à 6ba2a78. VISOR-serve est e9a7e5d, AutomatedDentalToolsRemote est 19b95e8. Les lignes legacy s'écrivent Automatrix_CLI.py:279@3c67957 ; un numéro de ligne legacy nu sur cette page se lit lui aussi à 3c67957. Automatrix_CLI.py est Automatrix_CLI/Automatrix_CLI.py ; AutoMatrix.py, AutoMatrix.ui et AutoMatrix_Method/ se trouvent sous AutoMatrix/.

Application par lots d'une ou plusieurs transformations ITK à un dossier de volumes et de fichiers de landmarks. Pas de réseau, pas de conda, pas de GPU : sitk.ReadTransform + sitk.ResampleImageFilter, et un appariement fichier ↔ matrice par découpage des noms. Tout l'intérêt de cette page tient aux conventions de transformation et à l'écart entre ce que promet l'interface et ce que fait réellement le CLI.

3. Formats de transformation lus, et ceux qui ne le sont pas

Explication en langage courant et maths : page de l'atlas.

L'interface (AutoMatrix.py:829,832) et le README (README.md:416-418) annoncent .npy, .h5, .tfm, .mat, .txt. GetPatients les collecte tous. Le CLI fait ensuite, sans distinction (Automatrix_CLI.py:257-261) :

try:
    tfm = sitk.ReadTransform(matrix)
except Exception as e:
    logger.error(f"ERROR reading transform {matrix}: {e}")

sitk.ReadTransform ne connaît que les classes TransformIO d'ITK. Testé avec le SimpleITK 2.5.5 de Slicer 5.12 :

Legacy (3c67957) ; changé dans VISOR. La liste legacy porte encore .npy (Automatrix_CLI.py:110@3c67957) et l'échec de lecture est journalisé puis sauté (:258-261). Le portage ne le liste plus : les transformations sont .tfm .mat .h5 .hdf5 .txt (SADT-VISOR AutoMatrix/pipeline.py:46), et un dossier ne contenant que d'autres fichiers est refusé par une ValueError (SADT-VISOR AutoMatrix/__init__.py:79-84 ; ce message nomme quatre extensions et omet .hdf5). Un .npy n'est toujours pas lu, mais rien ne l'annonce.

La prise en charge de .npy est donc cassée : chaque fichier .npy produit une ligne d'erreur et est sauté. C'est une régression introduite par le passage au CLI (commit 7bc362b) : la version widget lisait np.load(matrix) et construisait un vtkMRMLTransformNode (la branche extension_mat == ".npy", visible avec git show 7bc362b^:AutoMatrix/AutoMatrix.py).

Faux dans VISOR. Un .txt contenant une matrice 4x4 simple est lu par un repli quand sitk.ReadTransform le refuse (SADT-VISOR AutoMatrix/pipeline.py:138-180). Exécuté le 2026-11-09 : une matrice de quatre lignes dans P1_matrix.txt a produit un volume transformé.

Même histoire pour les « matrices texte » : ce n'est pas un format de matrice, c'est le format texte d'ITK.

Une lecture réussie renvoie un sitk.Transform dont le type concret est préservé : isinstance(tfm, sitk.CompositeTransform) fonctionne, vérifié.

4. La convention de transformation : le point qui casse tout

Explication en langage courant et maths : page de l'atlas.

4.1 Sens de la transformation

Explication en langage courant et maths : page de l'atlas.

ITK est fixe → mobile : un sitk.Transform passé à un rééchantillonneur fait correspondre au point physique de sortie le point physique d'entrée où échantillonner. Le contenu visible se déplace donc selon T⁻¹.

Le code exploite cela des deux côtés, et c'est cohérent :

  • Volumes (Automatrix_CLI.py:182) : resampler.SetTransform(transform), la transformation est passée telle quelle, le contenu se déplace selon T⁻¹.
  • Landmarks (Automatrix_CLI.py:149,156) : 
    tfm_inverted = transform.GetInverse()
point['position'] = list(tfm_inverted.TransformPoint(point['position']))
    T⁻¹ est explicitement appliquée au point, qui se déplace donc comme le contenu du volume.
Vérifié

Vrai aussi dans VISOR (SADT-VISOR AutoMatrix/pipeline.py:121 passe la transformation au rééchantillonneur ; :83 et :99 l'inversent pour les points).

À retenir : le même .tfm appliqué à un scan et à ses landmarks les déplace du même mouvement. C'est la propriété qui rend le module utilisable, et c'est aussi le seul endroit du code où une inversion apparaît.

Piège

Legacy (3c67957) ; changé dans VISOR. Legacy : avertissement et return, pas de fichier (Automatrix_CLI.py:148-152@3c67957). VISOR : la RuntimeError n'est plus avalée (SADT-VISOR AutoMatrix/pipeline.py:74-78,83) ; elle est consignée sous cases[patient].failed (SADT-VISOR AutoMatrix/__init__.py:144-155) et le volume de ce patient est quand même écrit, si bien que les deux sorties peuvent toujours diverger, mais le rapport le dit. Un champ de déplacement nul lève sur GetInverse() (exécuté le 2026-11-09). L'exécution n'échoue que si rien du tout n'a été écrit (:164). Le panneau Slicer n'affiche pas les échecs, voir les constats dans la section VISOR.

GetInverse() peut lever RuntimeError (transformation non inversible : champ de déplacement dense, B-spline ; les deux lèvent RuntimeError depuis GetInverse() dans SimpleITK 2.5.5, exécuté le 2026-11-10). Le cas est attrapé et le fichier de landmarks est simplement sauté avec un avertissement : le volume correspondant, lui, aura été transformé. Les deux sorties peuvent donc se désynchroniser en silence.

4.2 RAS / LPS : où se fait l'inversion d'axes, nulle part

Explication en langage courant et maths : page de l'atlas.

Il n'y a pas d'inversion d'axes dans AutoMatrix. C'est correct, et voici pourquoi :

  • Les fichiers .tfm d'ITK sont en LPS par construction.
  • sitk.ReadImage / WriteImage travaillent en LPS. Les deux côtés s'accordent, rien à faire pour les volumes.
  • Les fichiers .mrk.json du dépôt sont codés en dur en LPS, partout : ALI_CBCT/ALI_CBCT_utils/io.py:39, ALI_IOS/ALI_IOS_utils/io.py:74, FlexReg/FlexReg_utils/mgl_patch.py:222, VFACE/VFACE_utils/functionaq3dc.py:1724, et, puisque ASO_CBCT et AREG_CBCT réexportent désormais WriteJson au lieu d'avoir le leur, ADTLib/io/landmarks.py:92. C'est aussi le défaut de Slicer à l'écriture. Donc point['position'] est déjà en LPS, et l'appliquer directement à une transformation ITK est correct.
Piège

Vrai aussi dans VISOR (SADT-VISOR AutoMatrix/pipeline.py:71-104 ne le lit jamais). Exécuté le 2026-11-09 : un fichier déclarant RAS avec un point de contrôle [1,2,3] et une translation (5,0,0) est ressorti avec x = -4 en déclarant toujours RAS. Legacy : Automatrix_CLI.py:154-156@3c67957.

Le point fragile est que le champ coordinateSystem n'est jamais lu. FlexReg le lit bel et bien (FlexReg.py:2221) ; AutoMatrix non. Un json déclarant "coordinateSystem": "RAS", ce qu'écrivent d'anciennes annotations ou d'autres outils, sera transformé avec x et y de signe faux, sans message. Le fichier de sortie conservera même son coordinateSystem: RAS d'origine, puisque le json est relu et réécrit tel quel.

Pour mémoire, les modules qui produisent les matrices font eux-mêmes l'inversion d'axes : FlexReg_CLI.py:100-105 calcule flip @ matrix_array @ flip avec flip = np.diag([-1, -1, 1, 1]) puis inverse, avant d'écrire le .tfm (:107-109). AutoMatrix consomme le résultat de ce travail et n'a donc plus rien à refaire.

6. Rééchantillonnage et image de référence

Explication en langage courant et maths : page de l'atlas.

resampler.SetInterpolator(sitk.sitkNearestNeighbor if is_seg else sitk.sitkLinear)

(Automatrix_CLI.py:183-187.) L'interpolateur vient de la case « Check this box if using segmentations » (is_seg, :206). Plus proche voisin pour un labelmap, linéaire sinon : c'est correct, et c'est à l'utilisateur de le déclarer, rien n'est détecté automatiquement.

La grille de sortie est choisie ainsi (Automatrix_CLI.py:165-175 et :276-279), par priorité décroissante :

  1. Transformation composite → la référence est devinée d'après le chemin de la matrice : matrix.replace("_transform.tfm", ".nii.gz"), avec repli sur .nii. Ce n'est pas un bug : ASO_CBCT écrit <patient>_<add>_transform.tfm et <patient>_<add>.nii.gz dans le même dossier, si bien que le scan orienté placé à côté de la matrice est exactement la bonne grille. Si le fichier est absent, un avertissement est émis et l'image d'entrée sert de repli.
  2. Nom de matrice contenant mirror (insensible à la casse) → la référence est forcée à l'image d'entrée, le fichier de référence de l'interface est ignoré. Aiguillage fondé sur le nom du fichier.
  3. Fichier de référence fourni (reference_file != "None", valeur par défaut du champ, AutoMatrix.ui:257 ; lu en Automatrix_CLI.py:209-216) → sa géométrie est imposée à toutes les sorties.
  4. Sinon, l'image d'entrée elle-même : taille, espacement, origine et direction inchangés. Une transformation qui déplace du contenu hors du champ de vue le fait disparaître, remplacé par DefaultPixelValue = 0.
Bug confirmé

Legacy (3c67957) ; l'inverse dans VISOR. À 3c67957, la branche est inatteignable, car l'appelant fournit l'image elle-même quand il n'y a pas de référence (Automatrix_CLI.py:279@3c67957). Dans le portage, cette branche est le chemin par défaut : sans référence, on garde la taille, l'espacement et la direction de l'entrée, avec une origine déplacée en transform.TransformPoint(origin) (SADT-VISOR AutoMatrix/pipeline.py:127-133, verrouillé par un test, tests/test_run_options.py:265-277). Voir le constat « Without a reference the output box follows the transform » dans la section VISOR.

La branche reference is None de ResampleImage (Automatrix_CLI.py:186-194@3c67957) est inatteignable : l'appelant passe toujours une référence. Elle est aussi fausse : elle fait new_origin = transform.TransformPoint(image.GetOrigin()) alors que la convention du rééchantillonneur demanderait T⁻¹.

Explication en langage courant et maths : page de l'atlas.

Piège

Constat legacy (3c67957) ; une seconde conséquence dans VISOR. Dans le portage, une réflexion appliquée sans référence laisse la boîte de sortie vide, car l'origine passe elle aussi par la réflexion (SADT-VISOR AutoMatrix/pipeline.py:133). Exécuté le 2026-11-09 avec une matrice de réflexion diag(-1,1,1) sur un cube de 20 voxels centré sur l'origine : l'origine de sortie est passée de -10 à +10 et aucun des 1000 voxels non nuls n'est resté ; avec le volume comme sa propre référence, les 1000 sont restés. Détails et correctif non fusionné dans la section VISOR.

C'est diag(-1, 1, 1) en LPS, centrée sur l'origine : une réflexion par rapport au plan x_LPS = 0. Comme x_LPS pointe vers la gauche du patient, il s'agit bien d'un échange gauche/droite, mais par rapport au plan sagittal de l'origine du repère monde, et non au plan sagittal propre du patient. Un patient qui n'est pas centré ressort translaté en plus d'être mis en miroir, ce qu'un recalage ultérieur doit corriger.

Le déterminant vaut −1. Pour un volume, ResampleImageFilter s'en accommode sans problème. Pour un maillage, il inverserait l'orientation des faces et les normales : sans objet ici, puisque les maillages ne sont plus traités.

Le mode force ComboBoxMatrix sur « File », le suffixe sur _mir, et décoche checkBoxMatrixName (AutoMatrix.py:319-321).

12. Pièges et points fragiles

Explication en langage courant et maths : page de l'atlas.

Résumé

Legacy (3c67957) ; statut dans VISOR, puce par puce. Toujours vrai : pas de composition, coordinateSystem jamais lu, landmarks non définis laissés dans l'ancien repère (SADT-VISOR AutoMatrix/pipeline.py:95-96, exécuté le 2026-11-09 : un point undefined est resté à [7,7,7]), .npy et maillages non pris en charge (plus annoncés). Plus vrai : .txt avec une matrice 4x4 brute (accepté par un repli), écrasement quand l'option de nom est désactivée, troncature par .split(extension_scan)[0] (remplacée par Path et relpath, SADT-VISOR AutoMatrix/__init__.py:323-342). Legacy uniquement : OnEndProcess, CheckGoodEntre, onPredictButton, « From AReg », le code mort et les métadonnées XML.

  • .npy ne fonctionne pas (§3), bien qu'annoncé par l'interface et le README.
  • Les maillages ne fonctionnent plus (§5), bien qu'annoncés par l'interface et le README. Régression due au commit 7bc362b.
  • .txt n'accepte pas une matrice 4×4 brute (§3), seulement le format texte d'ITK.
  • Le coordinateSystem des landmarks n'est jamais lu (§4.2).
  • Pas de composition : N matrices pour un patient donnent N fichiers, pas une chaîne (§4.3).
  • Sorties écrasées si checkBoxMatrixName est décochée avec plusieurs matrices (§9).
  • OnEndProcess divise par self.nb_scans (AutoMatrix.py:745-747@3c67957) sans garde-fou : un dossier d'entrée vide provoque un ZeroDivisionError à la fin du traitement.
  • CheckGoodEntre est logiquement fausse (AutoMatrix.py:808@3c67957) : le test d'extension est len(dico['.vtk'])==0 and len(dico['.vtp']) and len(dico['.stl']) and …, où seul le premier terme est une comparaison. Les autres sont des entiers évalués comme des booléens, si bien que l'avertissement « Folder empty or wrong type » ne se déclenche que dans une conjonction improbable. Un dossier réellement vide passe la validation.
  • onPredictButton ne s'arrête pas sur erreur : TestProcess renvoie un tuple (ok, out), donc la vérification isinstance(error, str) en AutoMatrix.py:581@3c67957 est toujours fausse, et le traitement démarre même avec des champs vides.
  • .split(extension_scan)[0] coupe à la première occurrence : un chemin dont un dossier contient la même sous-chaîne que l'extension serait tronqué.
  • Landmarks non defined laissés dans l'ancien repère, mêlés à des points transformés dans le même fichier (§5).
  • Le chemin « From AReg », mort et cassé (§8).
  • Code mort : saveOutput / UpdateProgressBar / UpdateTime du widget, AutoMatrixLogic.process, la branche ResampleImage avec reference is None, registerSampleData qui référence des fichiers .png manquants.
  • Les métadonnées de Automatrix_CLI.xml sont toujours celles du modèle Slicer (FirstName LastName (Institution), NIH grant NXNNXXNNNNNN-NNXN).

13. Littérature

Explication en langage courant et maths : page de l'atlas.

Aucun article ne couvre AutoMatrix : c'est un utilitaire d'application par lots écrit pour le laboratoire (Gaëlle Leroux, UoM/DCBIA). Le contenu scientifique se trouve entièrement dans les modules qui produisent les matrices, AREG, ASO, MRI2CBCT, FlexReg, et il est traité dans leurs pages respectives.

Pour la convention des transformations, la référence à jour est la documentation d'ITK / Slicer plutôt qu'un article :

  • Coordinate systems : guide développeur de Slicer
  • SimpleITK : Transforms and Resampling
  • SlicerAutomatedDentalTools
  • DCBIA_Apply_matrix : le dépôt d'origine, qui héberge toujours la matrice miroir et les jeux de test cités par le README
