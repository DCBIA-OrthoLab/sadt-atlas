CNE

Un module d'inférence par modèle de langage (LLM) qui lit des notes cliniques en texte libre et en extrait des paires clé–valeur : ce n'est ni un outil géométrique ni un traitement d'image, malgré sa place dans une suite d'outils dentaires.

non publié CNE_CLI pas de conda : Python de Slicer Bibliographie

Avertissement de périmètre. Contrairement à AutoCrop3D et AutoMatrix, CNE n'est pas un utilitaire géométrique : il ne touche ni volume, ni maillage, ni coordonnée. C'est un module d'inférence LLM qui lit des notes cliniques en texte libre et écrit des paires clé–valeur. Le cœur du module est un modèle quantifié GGUF chargé par llama-cpp-python dans le Python de Slicer.

0. L'acronyme

Le dépôt n'explicite l'acronyme nulle part dans une documentation : le README ne contient aucune section CNE, et ne documente pas davantage le MedX qu'il remplace, aucun des deux noms n'y figure. L'aide du module (CNE.py:157) dit seulement « This tool helps to create summaries of clinical notes ».

En revanche deux lignes de log, et elles seules, donnent l'expansion : logger.info("CNE (Clinical Notes Extraction)") (CNE.py:342 et CNE.py:663), et le CLI publie le même nom au superviseur Slicer : <filter-name>Clinical Notes Extraction</filter-name> (CNE_CLI.py:93). CNE = Clinical Notes Extraction, attesté par le code et par rien d'autre.

1. Situation dans la chaîne

Module terminal. Rien ne l'appelle, il n'appelle aucun autre module du dépôt. Déclaré en CMakeLists.txt:50-52 (CNE, CNE_CLI, CNE_Dashboard).

Il remplace la moitié « Summarization » de MedX, désactivée du build en mars 2026 avec le commentaire « Replaced by CNE ».

Corrigé depuis la rédaction de cette fiche

Ce relevé, daté de septembre 2026, consignait ici deux choses qui ont changé depuis. MedX/ et MedX_CLI/ ne sont plus du tout dans l'arbre : ils en ont été retirés le 2026-09-17, le jour même où cette fiche a été écrite , et conservés sur la branche archive/medx. Et la moitié « Dashboard » (dashboard.png + patient_data.csv), dont cette fiche disait qu'elle n'avait pas d'équivalent et disparaissait de l'extension compilée, a été portée dans CNE le 2026-10-12 : CNE_Dashboard et CNE_CLI_utils la dessinent à partir des fichiers Extraction_*.txt qu'écrit CNE, par un bouton à côté de Run (CNE.py:234, CNE.py:365 ; §8.1). Le 2026-10-16, les deux dépôts de modèles sont passés de dcbia/... à DCBIA-OrthoLab/... et le téléchargement Ortho a été réparé (§4).

3. Dépendances, installées à la demande

check_dependencies() (CNE.py:83) est appelé au clic sur Apply, pas au chargement du module. Il teste cinq imports (CNE.py:93-110) et, s'il en manque, demande confirmation avant slicer.util.pip_install :

Import testéPaquet installéUsage
llama_cppllama-cpp-python --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cpuinférence
fitzpymupdfextraction de texte PDF
docxpython-docxextraction de texte Word
matplotlibmatplotlibfigure du Dashboard (CNE.py:102-107)
pandaspandastableau du Dashboard (CNE.py:109-110)

Deux points à connaître :

Piège

install_function (CNE.py:44) force CC=gcc et CXX=g++ pendant l'installation puis restaure les valeurs d'origine : c'est pour le cas où pip doit compiler llama-cpp-python depuis les sources. Sur Windows ces valeurs sont inutilisables.

Piège

L'index supplémentaire pointe explicitement vers les wheels CPU. Or le CLI demande n_gpu_layers=-1 avec le commentaire « Use GPU if available » (CNE_CLI.py:164) : avec une build CPU-only ce paramètre est sans effet. En pratique l'inférence tourne sur CPU, et un modèle 7–8 B quantifié Q4 y coûte plusieurs dizaines de secondes par note.

Le CLI re-teste ses trois imports (llama_cpp, fitz, docx) au démarrage et sys.exit(1) si l'un manque (CNE_CLI.py:101-117) : redondant, mais sans danger puisque le CLI partage l'interpréteur du widget.

Cette fiche consignait ici un bug confirmé : le mode Ortho demandait model-q4_0.gguf, qui n'existait pas dans le dépôt, si bien que le téléchargement renvoyait HTTP 404 et échouait avec « Download failed or was cancelled ». Le code demande maintenant model-q4_k_m.gguf dans DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho (CNE.py:518-519), et le fichier TMJ dans DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ (CNE.py:525-526). Vérifié le 2026-11-09 par une requête HTTP HEAD sur les deux URL : chacune répond 302 vers le fichier, et le fichier Ortho fait 4 920 738 880 octets, d'où les « approx. 4.9 GB » de la boîte de dialogue de téléchargement (CNE.py:521 ; celle du TMJ annonce 4,4 Go, CNE.py:528, non mesuré).

Les deux dépôts Hugging Face portent maintenant une model card, que cette fiche disait absente (lue par l'API Hugging Face le 2026-11-09, pas depuis le dépôt ADT). Chacune indique sa licence (Llama 3.1 pour Ortho, Apache 2.0 pour TMJ), le modèle de base, la méthode (LoRA, r = 32, alpha = 64, fusionné puis quantifié en Q4_K_M), que les notes d'entraînement sont des données patients annotées non diffusées, et que les jeux ont été séparés par patient. La carte Ortho dit que le modèle reçoit la note brute sans prompt système, ce qui concorde avec le code (§6), et cite des caractéristiques orthodontiques (taille et matériau du fil, ligature, élastiques, overjet, overbite, ...) comme schéma. Aucune des deux cartes ne rapporte d'évaluation. La carte TMJ donne le fichier à 4,7 Go, alors que la boîte de dialogue annonce 4,4 Go (CNE.py:528).

5. Entrées et prétraitements

SUPPORTED_EXTENSIONS = (".txt", ".pdf", ".docx"). Le balayage est non récursif : glob.glob(os.path.join(notesFolder_input, f"*{ext}")) (CNE_CLI.py:135), contrairement à tous les autres modules du dépôt qui utilisent iglob(**, recursive=True). Un dossier de sous-dossiers par patient ne donnera rien.

Extraction du texte (CNE_CLI.py:75) :

FormatExtracteurDétail
.pdffitz.open puis "\n".join(page.get_text() for page in doc)pas d'OCR : un PDF scanné ressort vide
.docxdocx.Document, paragraph.textles tableaux sont perdus (doc.paragraphs ne les parcourt pas)
.txtopen(..., encoding="utf-8")un fichier en cp1252 lève UnicodeDecodeError, attrapé par la boucle et compté en échec

clean_text() (CNE_CLI.py:42) est le seul prétraitement, et il est motivé dans le code : normaliser ce qui varie entre exports PDF/Word mais n'apparaissait jamais dans les notes texte d'entraînement, apostrophes et guillemets typographiques vers ASCII, tiret demi-cadratin et cadratin vers -, espace insécable vers espace, puis effondrement des lignes vides consécutives. Objectif explicite : que le modèle voie le même texte quel que soit le format source.

Aucune anonymisation, aucun filtrage PHI. Les notes de test du dépôt sont pseudonymisées à la main (B_001, [DOCTOR], Dr. XXX) mais rien dans le code ne le garantit pour les données de l'utilisateur. Le module Medical_Data_Anonymizer_Module existe séparément et n'est pas chaîné à CNE.

6. L'inférence

Une seule passe par fichier, aucun découpage (CNE_CLI.py:194-203) :

messages = []
if notesType.upper() == "TMJ":
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": clinical_text})

output = llm.create_chat_completion(messages=messages, max_tokens=500, temperature=0.1)

À noter :

Piège

Le mode Ortho n'envoie aucune instruction. Seule la note brute part comme message utilisateur ; c'est le fine-tuning du modèle Llama-Ortho qui est censé porter la tâche. Le mode TMJ, lui, conserve l'instruction héritée de MedX.

  • create_chat_completion applique le chat template embarqué dans le GGUF. Les deux modèles sont tagués conversational sur Hugging Face, donc le template existe ; il n'est ni visible ni contrôlable depuis le dépôt.
  • temperature=0.1 et pas de seed : la sortie est quasi déterministe mais pas reproductible à l'identique.
Piège

Pas de garde sur la longueur. n_ctx vaut 6144 (TMJ) ou 2048 (Ortho) et max_tokens=500 est prélevé dessus. Une note dépassant le budget fait lever llama.cpp ; l'exception est attrapée par fichier, journalisée, et le fichier est ajouté à failed_files. Le budget Ortho est particulièrement serré : ~1500 tokens de note utile. La note de test TMJ_note1.txt fait environ 4 400 caractères, ce qui passe en TMJ.

  • Le chargement du modèle est encadré par une redirection de stderr vers /dev/null via os.dup2 (CNE_CLI.py:159), pour masquer le bavardage de llama.cpp qui sinon polluerait le canal d'erreur que Slicer interprète comme un échec du CLI.

7. Post-traitement de la réponse

Le modèle est censé répondre en JSON ; le code ne le lui impose pas (pas de response_format, pas de grammaire GBNF) et se contente de repêcher le JSON dans le texte (CNE_CLI.py:209-214) :

start_idx = ai_response.find('{')
end_idx   = ai_response.rfind('}') + 1
data = json.loads(ai_response[start_idx:end_idx])
if "extraction" in data:
    data = data["extraction"]
for key, value in data.items():
    formatted_response += f"{key} : {value}\n"

Donc : première accolade ouvrante jusqu'à la dernière fermante, déballage d'un éventuel niveau extraction, puis aplatissement en lignes clé : valeur. Si le parse échoue ou s'il n'y a pas d'accolade, la réponse brute du modèle est écrite telle quelle. Le fichier de sortie ne dit pas dans lequel des deux cas on se trouve.

Piège

Conséquences : le découpage naïf find('{')…rfind('}') casse dès que la réponse contient plusieurs objets JSON, et une valeur imbriquée (liste, dict) est rendue par son repr Python dans le fichier texte.

8. Sorties

Un fichier texte par note d'entrée, dans le dossier de sortie :

Extraction_<nom de la note sans extension>.txt

Contenu : des lignes clé : valeur, ou la réponse brute du modèle en cas d'échec de parse. Ni CSV, ni json, ni agrégation par patient dans l'extraction elle-même : le tableau et la figure viennent du bouton Dashboard (§8.1), qui relit ces fichiers ensuite.

Le dossier de sortie est créé par os.makedirs(..., exist_ok=True) côté widget (CNE.py:613).

8.1 Le Dashboard

La moitié « Dashboard » de MedX a été portée le 2026-10-12 : l'affirmation antérieure de cette fiche, selon laquelle elle « n'a pas été reprise », ne tient plus. Elle se lit ainsi dans le code :

  • Déclenchement. Le bouton Dashboard (dashboardButton dans CNE.ui, connecté en CNE.py:234) lance onDashboardButton() (CNE.py:365). Il vérifie les dépendances, refuse de tourner sans dossier de sortie, et lance CNE_Dashboard via CNELogic.dashboard() (CNE.py:629) avec le dossier de sortie comme entrée et comme sortie. Aucun modèle, aucun téléchargement n'intervient.
  • Lecture. read_summaries() (display_figure.py:23) ne garde que les fichiers Extraction_*.txt du dossier ; l'identifiant du patient est le nom de la note moins le préfixe. process_summaries() (display_figure.py:135) remplit un dictionnaire de 54 clés initialisé par initialize_key_value_summary() (dashboard_utils.py:332) et convertit six champs numériques.
  • Calculé, pas prédit. Chaque panneau est une agrégation déterministe calculé dans dashboard_utils.py (tranches d'âge, moyenne et écart type des scores de douleur, ouverture buccale maximale lue dans des chaînes comme « 33 mm », localisations des céphalées et des douleurs articulaires par listes de synonymes, déplacement discal gauche et droit, niveau de douleur musculaire). La figure est dessinée par generate_dashboard_figure() (display_figure.py:164).
  • Sorties. dashboard.png et patient_data.csv (display_figure.py:714-716), plus un troisième fichier, dashboard_full_dataframe.csv (display_figure.py:183), écrit avant que la figure soit dessinée.
  • Échoue bruyamment quand le schéma ne correspond pas. report_field_coverage() (display_figure.py:668) journalise les clés attendues qui ne portent aucune valeur, et show_dashboard() (display_figure.py:694) lève une erreur si aucune n'en porte ou si le dossier ne contient aucun Extraction_*.txt.
Piège

Le tableau de bord est un tableau de bord TMJ. Les clés attendues sont l'intensité des céphalées, les claquements de la mâchoire, le déplacement discal, l'ouverture maximale, les troubles du sommeil et similaires (dashboard_utils.py:339-396). Ce sont les clés que le modèle TMJ est censé renvoyer ; rien dans le dépôt ne dit que le modèle Ortho les écrit, et le mode Ortho n'a aucune instruction pour les imposer. Sur des extractions Ortho, le contrôle de couverture arrêterait très probablement l'exécution avec l'erreur « keys do not match ». C'est une inférence tirée de la liste de clés, pas quelque chose d'exécuté sur une sortie Ortho. Les clés elles-mêmes sont choisies par le modèle, pas par le code (docstring de report_field_coverage, display_figure.py:668-679).

Tout le contenu clinique de la sortie vient du modèle. Il n'y a aucune règle, aucun dictionnaire de termes, aucune validation de schéma : ce que le modèle écrit est ce qui est sauvegardé.

11. Pièges et points fragiles

  • Le Dashboard attend le schéma TMJ (§8.1).
  • Le dossier de sortie des fichiers de test. copyTestFiles() (CNE.py:454) mettait un chemin inexistant dans le champ de sortie. Il crée désormais le dossier de sortie (CNE.py:508), recopie les notes à chaque appel sans effacer le dossier (dirs_exist_ok=True, CNE.py:505), et laisse tranquille un dossier de sortie déjà choisi par l'utilisateur (CNE.py:328-330). Resources/testfiles/ ne contient toujours que les deux dossiers input_.
  • Balayage non récursif du dossier d'entrée (§5).
  • Aucune limite de longueur avant l'appel : une note trop longue échoue au lieu d'être découpée, alors que MedX découpait (§6). C'est une régression fonctionnelle du remplacement.
  • Le mode Ortho n'envoie aucune instruction système (§6) : si le modèle n'est pas celui attendu, la sortie n'a aucune raison d'être du JSON.
  • Aucune contrainte de format de sortie : pas de grammaire GBNF ni de response_format, alors que llama.cpp les propose. Le post-traitement est donc un repêchage heuristique (§7).
  • Radio button ni TMJ ni Ortho → notesType = "" (CNE.py:427) → dans getModelPath, repo_id n'est jamais affecté et l'UnboundLocalError remonte en « Failed to load model ». Le cas ne devrait pas arriver (setExclusive(True) et défaut TMJ), mais rien ne le bloque.
  • Casse incohérente : notesType == "TMJ" fixe n_ctx, notesType.upper() == "TMJ" fixe l'instruction. Un notesType en minuscules donnerait l'instruction TMJ avec le contexte de 2048.
  • Aucune trace de provenance : le fichier Extraction_*.txt ne mentionne ni le modèle, ni sa version, ni la date. Deux exécutions avec des modèles différents produisent des fichiers indistinguables.
  • PHI : rien n'anonymise, rien n'avertit. Les notes sont lues en clair, passent par un modèle local (donc pas d'exfiltration réseau : c'est le seul garde-fou, et il est structurel plutôt que délibéré).
  • Métadonnées du CLI restées au gabarit : CNE_CLI.xml décrit encore « Apply a Gaussian blur to an image », attribue le module à « Andras Lasso (PerkLab) », et ses <index> valent 0, 2, 3, 4, l'index 1 manque.
  • onCliProgress (CNE.py:651) lit caller.GetProgress() et n'en fait rien ; elle n'est d'ailleurs connectée à aucun observateur. Code mort. L'avancement réel passe par les balises <filter-progress> du CLI, lues par le qSlicerCLIProgressBar.

12. Littérature

Aucune publication n'est citée dans le dépôt pour CNE, et les deux model cards Hugging Face DCBIA-OrthoLab/* ne citent aucun article (elles renvoient à un dépôt de code, ortho-cde-llm-extraction, qui n'a pas été lu). Le corpus d'annotations n'est pas diffusé et aucune évaluation n'est rapportée : les deux sont non déterminables depuis le dépôt.

Ce qui est vérifiable :

  • La lignée MedX → CNE, documentée uniquement par la ligne de remerciements de CNE_Dashboard.xml (« Ported from MedX_Dashboard, which CNE replaced without taking this half with it ») et les commentaires de display_figure.py:35 et :675. Le CMakeLists.txt racine ne mentionne plus MedX et le README n'a aucune section MedX ni CNE.
  • Les modèles de base : Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • Les dépôts fine-tunés : DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho.
  • Le moteur : llama-cpp-python, llama.cpp (format GGUF, quantification Q4_K_M).
  • SlicerAutomatedDentalTools

Ne pas rattacher CNE à la littérature générale sur l'extraction d'information clinique par LLM : rien dans le dépôt n'indique que les modèles utilisés ici proviennent d'un travail publié.
