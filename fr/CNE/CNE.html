CNE

CNE lit des notes cliniques en texte libre et écrit les faits qu'il y trouve (symptômes, diagnostics, scores) sous forme de lignes champ : valeur. C'est un module de modèle de langage : il ne touche ni image ni maillage. Cette page explique pas à pas le pipeline du module Slicer legacy ; les détails du code sont sur la page de code.

non publié VISOR CNE_CLI pas de conda : le Python de Slicer Bibliographie Code (développeurs) Guide

CNE n'est pas un outil géométrique : il lit du texte et écrit du texte. Un modèle de langage quantifié (format GGUF) est chargé par llama-cpp-python dans le Python même de Slicer. Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR exécute le même outil sur un serveur et a sa propre page. Une conséquence compte avant de poursuivre : là où cette page dit que le modèle tourne en local, cela n'est vrai que du module legacy. Avec VISOR, le texte de la note est envoyé au serveur (problèmes connus dans VISOR).

Vue d'ensemble : ce qui entre, ce qui sort

CNE, legacy
Entréeun dossier de notes (.txt, .pdf, .docx), parcouru sans récursivité, et un choix entre TMJ et Ortho
Le modèleun Qwen 2.5 7B (TMJ) ou un Llama 3.1 8B (Ortho) quantifié, téléchargé au premier usage et exécuté sur le processeur
Sortieun fichier texte par note, des lignes champ : valeur, dans le dossier de sortie
Optionnelun bouton Dashboard qui lit ces fichiers et dessine une figure et deux tableaux CSV

0. L'acronyme

CNE signifie Clinical Notes Extraction. Le dépôt ne le dit jamais dans sa documentation : seules deux lignes de journal et le nom que l'outil annonce à Slicer donnent le développement.

Dans le codeLes lignes de journal et le nom de filtre qui attestent le développement

1. Place dans le pipeline

CNE est un module terminal : rien ne l'appelle et il n'appelle rien. Il remplace la moitié de résumé de MedX, qui a été retirée du build en mars 2026 avec le commentaire « Replaced by CNE ». MedX lui-même a quitté l'arborescence le 2026-09-17 et vit sur la branche archive/medx. La moitié Dashboard a été portée dans CNE le 2026-10-12 (section 8.1) ; VISOR n'a pas de Dashboard.

Comparé au résumeur de MedX qu'il remplace :

  • Moteur et modèle : llama.cpp et un Llama ou un Qwen quantifié au lieu de PyTorch et d'un modèle BART.
  • Pas de découpage : la note entière va au modèle en un seul message, là où MedX la découpait en morceaux.
  • Décodage : température 0,1 et au plus 500 tokens, au lieu d'une recherche en faisceau avec échantillonnage.
  • Pas d'agrégation par patient : un fichier donne une sortie.

La seule phrase d'instruction du mode TMJ est la même phrase que celle de MedX (MedX la plaçait devant le texte, CNE l'envoie comme message système séparé).

Dans le codeQuels fichiers de build le déclarent, le relevé corrigé, le tableau de comparaison complet avec MedX

2. Fichiers en jeu

Quatre parties : le widget (dépendances, téléchargement du modèle, lancement du travail, bouton Dashboard), le travail en ligne de commande qui lit les notes et appelle le modèle, le travail Dashboard avec ses deux fichiers auxiliaires, et le fichier d'interface. Quatre notes d'exemple sont livrées dans le dépôt. Il n'y a pas d'environnement conda : tout s'exécute dans le Python de Slicer.

Dans le codeLe tableau des fichiers avec leurs rôles et l'endroit où chacun s'exécute

3. Dépendances, installées à la demande

Au clic sur Apply, le module vérifie cinq paquets (la liaison llama.cpp, un lecteur de PDF, un lecteur de Word, une bibliothèque de tracé et une bibliothèque de tableaux) et, après confirmation, installe ceux qui manquent dans le Python de Slicer. L'index de wheels vers lequel il pointe est le build processeur seul. Le travail demande quand même des couches GPU, ce qui n'a aucun effet sur ce build : en pratique l'inférence tourne sur le processeur, et un modèle de 7 à 8 milliards de paramètres y est lent (le temps par note n'a pas été mesuré pour cette page).

Dans le codeLes cinq imports, les options d'installation, le forçage du compilateur, la demande de GPU

4. Les modèles

Aucun poids n'est livré dans le dépôt. La première exécution télécharge le modèle du mode choisi dans le dossier Documents.

Les deux dépôts Hugging Face portent désormais une carte de modèle qui indique la licence, le modèle de base et la méthode d'affinage, et précise que les notes d'entraînement sont des données de patients non publiées. Aucune carte ne rapporte d'évaluation.

5. Entrées et prétraitement

Le module cherche des fichiers .txt, .pdf et .docx dans le dossier choisi seulement : les sous-dossiers ne sont pas parcourus, contrairement à tous les autres modules, donc un dossier organisé par patient ne donne rien. Le texte sort d'un PDF page par page sans OCR (un PDF numérisé est vide), d'un fichier Word paragraphe par paragraphe (les tableaux sont perdus), et d'un fichier texte en UTF-8 (un autre encodage fait échouer cette note).

Rien n'anonymise les notes. Les notes de test du dépôt ont été pseudonymisées à la main, et le module MedicalDataAnonymizer, séparé, n'est pas chaîné à CNE.

Dans le codeLes trois extracteurs, la table de remplacement et l'appel glob

6. Inférence

Le modèle est appelé une fois par note, sans découpage. En mode TMJ, la note est précédée de la phrase d'instruction ; en mode Ortho, la note part seule, car le modèle Ortho est censé porter la tâche dans son affinage.

La réponse est limitée à 500 tokens et la température est de 0,1 sans seed, donc la sortie est presque déterministe mais pas exactement reproductible. Une note qui laisse moins de 500 tokens de place ne lève pas d'erreur : le moteur raccourcit la réponse à ce qui reste, si bien que le JSON est coupé et que le texte brut est écrit (§7). Seul un prompt qui remplit toute la fenêtre fait lever une exception au moteur ; l'erreur est attrapée pour cette note, journalisée, et le fichier est compté comme échoué. Le modèle de conversation propre au modèle est appliqué, et ne peut être ni vu ni modifié depuis le dépôt.

Dans le codeL'appel, les messages TMJ et Ortho, la redirection de stderr

7. Post-traitement de la réponse

Rien n'oblige le modèle à produire du JSON, donc le module le repêche dans la réponse.

Si la tranche contient une enveloppe appelée extraction, ce niveau est retiré ; chaque champ est alors écrit comme une ligne champ : valeur, et une valeur imbriquée apparaît sous sa représentation Python. Si la tranche ne peut pas être lue, ou si la réponse n'a aucune accolade, la réponse brute du modèle est écrite telle quelle, et le fichier ne dit pas lequel des deux cas s'est produit.

Dans le codeLe code de découpage et le comportement en partie corrigé de VISOR

8. Sorties

Un fichier texte par note, Extraction_<note name>.txt, contenant des lignes champ : valeur ou la réponse brute. Ni CSV, ni JSON, ni agrégation par patient ne viennent de l'extraction elle-même.

Dans le codeLe nommage des fichiers, la création du dossier de sortie

8.1 Le Dashboard

Un bouton à côté de Run lance un second travail qui lit les fichiers Extraction_*.txt du dossier de sortie. Il remplit un tableau de 56 clés (l'identifiant du patient et 55 champs que le modèle est censé renvoyer), en convertit six en nombres, et calcule un résumé déterministe par panneau de la figure : classes d'âge, moyenne et dispersion des scores de douleur, ouverture buccale maximale, localisation des céphalées et des douleurs articulaires, déplacement du disque, douleur musculaire. Il écrit dashboard.png et deux tableaux CSV, et s'arrête avec une erreur quand les fichiers ne portent pas les champs attendus. Aucun modèle et aucun téléchargement ne sont en jeu.

C'est un dashboard TMJ : les champs attendus sont ceux que le modèle TMJ est censé renvoyer. Rien ne dit que le modèle Ortho les écrit, donc sur des extractions Ortho la vérification de couverture arrêterait très probablement l'exécution (une inférence tirée de la liste des champs, non exécutée).

Dans le codeLe déclenchement, les lecteurs, les fonctions d'agrégation et la vérification de couverture

10. Environnement

Le Python de Slicer seulement, avec cinq paquets installés à la volée. Un modèle quantifié de 7 à 8 milliards de paramètres demande environ 5 à 6 Go de mémoire en plus de Slicer. Les poids occupent environ 4,4 Go (TMJ) ou 4,9 Go (Ortho) sur disque.

Dans le codeL'interpréteur, les paquets, le GPU et l'emplacement des poids

11. Problèmes connus

  • Le Dashboard attend les champs TMJ et s'arrêterait probablement sur des extractions Ortho (détails).
  • Le mode Ortho n'envoie aucune instruction, donc rien ne garantit que la sortie soit du JSON si le modèle n'est pas celui attendu (détails).
  • Aucune garde de longueur : une note plus longue que la fenêtre échoue au lieu d'être découpée, une régression par rapport à MedX (détails).
  • Le format de réponse n'est pas contraint, et la tranche de la première à la dernière accolade casse sur deux objets (détails).
  • Le parcours du dossier d'entrée n'est pas récursif (tous les pièges).
  • Les fichiers de sortie n'enregistrent ni le modèle ni la date, donc deux exécutions avec des modèles différents ne se distinguent pas (tous les pièges).
  • Rien n'anonymise les notes ; la seule protection est que le modèle tourne en local, ce qui n'est vrai que de ce module legacy (tous les pièges).
  • Le build processeur seul rend la demande de GPU inutile (détails).

12. Littérature

Aucune publication n'est citée dans le dépôt pour CNE, et les deux cartes de modèle Hugging Face DCBIA-OrthoLab/* ne citent aucun article (elles renvoient vers un dépôt de code, ortho-cde-llm-extraction, qui n'a pas été lu). Le corpus d'annotation n'est pas publié et aucune évaluation n'est rapportée : les deux sont indéterminables à partir du dépôt.

Ce qui est vérifiable :

  • La filiation MedX → CNE, documentée uniquement par la ligne de remerciements de CNE_Dashboard.xml (« Ported from MedX_Dashboard, which CNE replaced without taking this half with it ») et par les commentaires du code du Dashboard (voir la page de code). Le CMakeLists.txt racine ne mentionne plus MedX et le README n'a aucune section MedX ni CNE.
  • Les modèles de base : Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • Les dépôts affinés : DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho.
  • Le moteur : llama-cpp-python, llama.cpp (format GGUF, quantification Q4_K_M).
  • SlicerAutomatedDentalTools

Ne pas rattacher CNE à la littérature générale sur l'extraction d'informations cliniques par LLM : rien dans le dépôt n'indique que les modèles utilisés ici proviennent de travaux publiés.

Ce qui a été cherché pour arriver à cette conclusion, et le voisinage rassemblé en chemin : SOURCES.md.
