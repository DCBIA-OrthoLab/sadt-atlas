AREG_IOSCBCT, legacy : le code

Pour les développeurs : ce que fait dans le code le module Slicer legacy AREG_IOSCBCT (SlicerAutomatedDentalTools à 3c67957), avec des références file:line, les signatures, les arguments, l'environnement et les pièges. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. Le portage VISOR a sa propre page de code.

Code Atlas (explication) non publié areg_ioscbct Python de Slicer pas de réseau dans le CLI VISOR Guide Bibliographie

Rien à voir avec AREG_IOS, qui est longitudinal (T1 → T2, même modalité) : ici les deux nuages de points viennent de capteurs différents, et il n'y a pas de « zone stable » commune.

Deux étapes d'appariement successives, aucun réseau dans le CLI :

  1. 12 landmarks occlusaux prédits des deux côtés par deux réseaux différents (ALI_CBCT sur le volume, ALI_IOS sur le maillage) → transformation rigide de Procrustes (vtkLandmarkTransform) qui sert de pré-alignement ;
  2. ICP de la surface IOS sur une isosurface du CBCT extraite par marching cubes à un niveau lu dans le scan (400 seulement en repli ; voir 4.1).

Le CLI lui-même est donc entièrement géométrique. L'intelligence se situe en amont, dans les modules que l'orchestrateur empile devant lui.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, a sa propre page : AREG_IOSCBCT sur VISOR. Les notes qui ouvrent certains encadrés ci-dessous (« Legacy uniquement », « Aussi vrai dans VISOR ») comparent avec ce portage à SADT-VISOR 6ba2a78 ; dans ces notes, ioscbct/ désigne SADT-VISOR tools/AREG/AREG_IOSCBCT/src/sadt_areg_ioscbct/.

Séquence complète du mode entièrement automatique

Explication en langage courant et maths : page de l'atlas.

IOSCBCT.py:580. Les deux modalités sont préparées séparément, puis remises en contact au dernier moment.

un CBCT brut et un scan intra-oral brut : deux modalités, préparées à part, mises en contact seulement à la fin

Chemin CBCT

  1. MRI2CBCT_resample_cbct_mri le rééchantillonne de façon isotrope : spacing=[0.3,0.3,0.3], center=True <out>/CBCT Resampled/CBCT
  2. PRE_ASO_CBCT le pré-oriente, avec les modèles PreASO prédit <out>/PRE ASO CBCT
  3. ALI_CBCT place les landmarks d'orientation : N S Ba RPo… ou IF ANS PNS UR1O UR6O UL6O, selon la référence prédit même dossier
  4. SEMI_ASO_CBCT l'oriente sur un fichier de référence, suffixe Or <out>/Oriented CBCT
  5. ALI_CBCT tourne une seconde fois, pour les 12 landmarks communs prédit le point occlusal de chaque dent

Chemin IOS

  1. CrownSegmentationcli étiquette les couronnes : Universal_ID, model=latest, suffix=Seg prédit <out>/Seg IOS
  2. PRE_ASO_IOS pré-oriente le maillage sur un fichier de référence l'arcade orientée
  3. ALI_IOS place les mêmes 12 landmarks : lm_type='O', image_size=224, blur_radius=0, faces_per_pixel=1 prédit IOSCBCT.py:327-337, :838-848

Où les deux chemins se rejoignent

  1. AREG_IOSCBCT lui-même : Procrustes, puis ICP, sur les 12 landmarks appariés, calculé, aucun réseau l'arcade, dans le repère du CBCT

Les étapes 2, 3, 5, 7 et 8 contiennent un réseau ; le CLI final n'en contient aucun : c'est de la pure géométrie. Le mode semi saute les étapes 1–4 et 6⟧, en prenant un CBCT déjà orienté et une arcade déjà orientée. Les numéros sont ceux du module lui-même, ce qui explique qu'ils s'entrelacent : les deux chemins s'exécutent séparément, donc une numérotation continue suggérerait un ordre qui n'existe pas.

Le mode semi saute 1–4 et 6 : il segmente l'IOS, puis lance directement les deux étapes ALI et le recalage. Son IOS_folder pointe vers <out>/Seg IOS/liste_csv_file_Seg, le sous-dossier que CrownSegmentationcli crée à partir du nom de base du csv qu'on lui a donné (IOSCBCT.py:359).

Les 12 landmarks communs

Explication en langage courant et maths : page de l'atlas.

Identiques des deux côtés, c'est le pivot de tout le recalage :

LL1O LL3O LL6O LR1O LR3O LR6O UL1O UL3O UL6O UR1O UR3O UR6O

Le suffixe O = point occlusal de la dent. Côté CBCT, ils sont passés à ALI_CBCT comme lm_type, côté IOS à ALI_IOS comme teeth avec lm_type='O', image_size=224, blur_radius=0, faces_per_pixel=1 (IOSCBCT.py:327-337 et IOSCBCT.py:838-848).

4. Appariement des deux modalités

Explication en langage courant et maths : page de l'atlas.

En bref : des landmarks communs pour le pré-alignement, puis un ICP sur une surface extraite du CBCT par seuillage. Il n'y a aucune segmentation des dents côté CBCT, et la segmentation côté IOS permet à ALI_IOS de viser avec ses caméras dent par dent, et ses étiquettes de dents (Universal_ID) choisissent aussi les couronnes qui pilotent l'ICP (AREG_IOSCBCT.py:545-576,750-754, voir 4.4).

4.1 La surface du CBCT

Explication en langage courant et maths : page de l'atlas.

load_data() (AREG_IOSCBCT.py:969-1004, abrégé) :

image = sitk.ReadImage(scan_path)
image_array = sitk.GetArrayFromImage(image)
ijk_to_lps = np.eye(4)
ijk_to_lps[:3, :3] = direction @ np.diag(spacing)
ijk_to_lps[:3, 3] = origin
level = surface_threshold(image_array, ijk_to_lps, all_landmarks, patient_id)
vol = pv.wrap(image_array.transpose(2, 1, 0))
cbct_raw_mesh = vol.contour(isosurfaces=[level])
cbct_surface = cbct_raw_mesh.transform(ijk_to_lps, inplace=False)
  • GetArrayFromImage donne (z,y,x), le transpose(2,1,0) le remet en (x,y,z) pour que pv.wrap produise une ImageData à spacing unitaire dans l'espace des indices ;
  • contour(isosurfaces=[level]) = marching cubes à un niveau mesuré sur le scan (voir l'encadré ci-dessous). L'isosurface capte l'os et l'émail, sans distinction ;
  • la matrice ijk_to_lps, reconstruite à la main, ramène l'isosurface dans les coordonnées physiques LPS.

C'est cohérent avec le reste : ALI_CBCT et ALI_IOS écrivent tous deux "coordinateSystem": "LPS" (ALI_CBCT/ALI_CBCT_utils/io.py:39, ALI_IOS/ALI_IOS_utils/io.py:74), et les fichiers .vtk sont en LPS. Aucune bascule n'est donc nécessaire, et aucune n'est faite.

Le niveau est lu sur le scan, il n'est pas codé en dur

Une version antérieure de cette page décrivait un niveau fixe de 400. À 3c67957, load_data contourne à surface_threshold(...) (AREG_IOSCBCT/AREG_IOSCBCT.py:986-1002) : à mi-chemin entre le plateau de l'émail lu aux landmarks du CBCT et les tissus mous autour de l'arcade, tous deux mesurés sur les landmarks des deux arcades ensemble (AREG_IOSCBCT.py:847-893,940-966,986-990), 400 seulement quand les couronnes ne sont pas plus brillantes que leur entourage (AREG_IOSCBCT.py:952-960), et la variable d'environnement AREG_CBCT_SURFACE_THRESHOLD le remplace (AREG_IOSCBCT.py:92,943-950). Le commentaire au-dessus de la constante en donne la raison : sur un patient, un 400 fixe éloignait l'arcade de 2,2 mm de ses landmarks (AREG_IOSCBCT.py:73-80, mesure des auteurs, non refaite ici).

4.2 Apparier les landmarks par étiquette

Explication en langage courant et maths : page de l'atlas.

_pair_landmarks() (AREG_IOSCBCT.py:203-213) ne garde que les étiquettes présentes des deux côtés, dans l'ordre des étiquettes de l'IOS, et journalise celles qui manquent au CBCT.

Correction importante

Également vrai dans VISOR, et appliqué. Les deux jeux de landmarks sont croisés par étiquette et au moins 3 étiquettes communes sont exigées (SADT-VISOR ioscbct/pipeline.py:136-155 ; voir AREG_IOSCBCT sur VISOR) ; align_by_landmarks lève une erreur sur des jeux de tailles différentes au lieu de renvoyer l'identité (ioscbct/geometry.py:34-51). Legacy : _pair_landmarks, AREG_IOSCBCT.py:203-213@3c67957.

vtkLandmarkTransform exige autant de points source que de points cible ; avec des listes de tailles différentes, il écrit une erreur sur stderr et renvoie l'identité, si bien que le pré-alignement disparaissait sans rien dire. Et apparier deux listes partielles par position associait des points qui n'avaient rien à voir entre eux.

4.3 Le pré-alignement rigide

Explication en langage courant et maths : page de l'atlas.

align_by_landmarks() (AREG_IOSCBCT.py:399):

landmark_transform = vtk.vtkLandmarkTransform()
landmark_transform.SetSourceLandmarks(points_moving)   # IOS
landmark_transform.SetTargetLandmarks(points_fixed)    # CBCT
landmark_transform.SetModeToRigidBody()                # 6 dof, no scaling

Deux garde-fous, qui se replient tous deux sur l'identité (une nouvelle vtk.vtkMatrix4x4()) avec un avertissement explicite :

Garde-fouConstanteJustification dans le code
Nombre de pairesMIN_LANDMARK_PAIRS = 3un point = translation pure, deux points laissent une rotation libre autour de l'axe
Résidu RMSMAX_LANDMARK_RESIDUAL_MM = 10.0, modifiable via la variable d'environnement AREG_MAX_LANDMARK_RESIDUALune transformation rigide conserve les distances : un grand résidu prouve que les deux jeux ne décrivent pas la même anatomie

_alignment_residual() (AREG_IOSCBCT.py:226) applique la matrice à chaque landmark mobile et calcule le RMS des distances à leurs homologues.

Avant et autour de cet ajustement, _fit_rigid_without_outliers() (AREG_IOSCBCT.py:331) décide quelles paires comptent (le portage VISOR a les mêmes règles, voir le tableau sur la page de code VISOR) :

  • un landmark que le scan dit hors d'une dent est écarté en premier, quels que soient les autres : le voxel le plus brillant dans un rayon de 2 voxels (ENAMEL_PROBE_RADIUS_VOXELS, :97) est sous le niveau de contour (_landmarks_on_enamel, :896), à condition qu'il reste 3 paires ;
  • le reste est élagué une paire par tour : la paire dont le retrait donne le meilleur ajustement est écartée si elle se trouve à plus de LANDMARK_OUTLIER_FLOOR_MM = 3.0 de l'endroit où les autres la placent et que l'ajustement sans elle vaut au plus LANDMARK_OUTLIER_IMPROVEMENT = 0.75 fois le résidu, jamais en dessous de MIN_LANDMARK_PAIRS_AFTER_TRIM = 4 paires (:142-149, :331-397) ;
  • un jeu presque aligné sur une droite ne déclenche qu'un avertissement, sous MIN_LANDMARK_SPREAD_RATIO = 0.10 (:49).

Le résidu comparé à 10 mm est celui sur les paires effectivement ajustées, et les landmarks transformés ainsi que la liste des étiquettes conservées reviennent avec la matrice, pour être contrôlés après l'ICP (_report_landmark_drift, :240, avertissement au-dessus de MAX_ICP_LANDMARK_DRIFT_MM = 1.0).

4.4 L'ICP

Explication en langage courant et maths : page de l'atlas.

Corrigé : un ICP point-plan plafonné à 300 itérations (3c67957)

Une version antérieure de cette section décrivait un ICP point-point (Kabsch/SVD sur les centroïdes), jusqu'à 2000 itérations, s'arrêtant sur une variation de 1e-8 du RMSE et de la fitness, sur tout le maillage IOS contre toute l'isosurface. Relu contre 3c67957, rien de cela ne tient : l'étape est point-plan (_point_to_plane_step, AREG_IOSCBCT.py:579), le plafond est ICP_MAX_ITERATIONS = 300 (:188 ; le commentaire au-dessus dit que 2000 était l'ancien plafond), le test d'arrêt porte sur le déplacement des points (:180-181), les points mobiles sont les couronnes et la cible est recadrée autour de l'arcade (:545, :485). L'étape de Procrustes n'est que le repli (:609).

run_icp_point_to_plane() (AREG_IOSCBCT.py:719) est appelé une fois par arcade avec max_dist=1.0 (la valeur par défaut de 1.5 n'est jamais utilisée), sur une copie de la surface du CBCT recadrée autour des landmarks de cette arcade (:1239-1255). Il lance _icp_run() (:627) une fois par lecture des normales du CBCT et garde la meilleure.

La transformation est composée à gauche (transformation = delta @ transformation) et réappliquée aux points d'origine à chaque tour, ce qui évite d'accumuler l'erreur. Le système linéarisé est construit à partir, pour chaque correspondance (p, q, n), du résidu (p - q)·n + w·(p x n) + t·n (docstring de _point_to_plane_step, :579-590).

Occlusion non contrainte

Également vrai dans VISOR. Chaque maillage a ses propres landmarks, son propre pré-alignement, son propre ICP et sa propre matrice (ioscbct/dispatch.py:238-258) ; rien ne contraint l'occlusion relative. Un maillage sans landmarks échoue seul (ioscbct/dispatch.py:240-246,262-264). Legacy : deux matrices, AREG_IOSCBCT.py:1246-1253@3c67957.

Les deux arcades sont recalées indépendamment contre la même isosurface, avec deux matrices distinctes mat_icp_upper et mat_icp_lower : l'occlusion relative n'est pas contrainte.

Les fichiers json de sortie sont un choix discutable : le conteneur vient du CBCT (affichage, identifiants, ordre) mais les coordonnées viennent de l'IOS. _write_positions() (AREG_IOSCBCT.py:282) apparie par étiquette, et supprime les points de contrôle du CBCT qui n'ont pas d'équivalent IOS plutôt que de les laisser à leur position d'origine. La version précédente indexait par position : un CBCT avec un seul landmark face à six côté IOS écrivait les coordonnées de UL1O sous l'étiquette UR6O.

Aucun .tfm n'est produit

Legacy (3c67957) ; à moitié vrai dans VISOR. VISOR n'écrit toujours pas de .tfm, mais il écrit bien la matrice 4x4 composée de chaque maillage sous forme de fichier numpy, <stem>_<suffix>_matrix.npy (ioscbct/dispatch.py:258 ; la composition est refinement @ matrix, ioscbct/pipeline.py:212). La page de revue de Slicer citée ci-dessous est legacy uniquement.

Ni la matrice des landmarks ni la matrice de l'ICP ne sont écrites sur disque ; seules les géométries transformées le sont. C'est reconnu au niveau du widget : la page de revue ioscbct_registration est de type VIEW, pas REGISTRATION, avec le texte "This step writes no matrix, so the result cannot be moved here" (AREG/AREG_Method/Review.py:794-803), si bien que l'opérateur ne peut pas corriger le recalage à la souris comme il le peut pour AREG_IOS ou AREG_CBCT.

Si aucun patient n'a pu être recalé, main() lève une RuntimeError (AREG_IOSCBCT.py:1312) : la boucle try/except/continue sortait sinon avec le code 0 et un dossier de sortie vide, et Slicer déclarait le pipeline réussi.

7. Pièges et points fragiles

Explication en langage courant et maths : page de l'atlas.

Corrigé : le niveau de l'isosurface est lu sur le scan (3c67957)

Une version antérieure de cet encadré disait que le seuil de 400 est codé en dur et jamais exposé. À 3c67957, il n'est ni l'un ni l'autre : le niveau est le point à mi-chemin entre l'émail et les tissus mous mesurés sur le scan, 400 est le repli, et AREG_CBCT_SURFACE_THRESHOLD le remplace (AREG_IOSCBCT/AREG_IOSCBCT.py:92,847-966). La sensibilité à la reconstruction s'applique toujours dans le cas du repli, que le journal signale par un avertissement.

Dans VISOR, la même règle est conservée (SADT-VISOR ioscbct/volume.py:96-117,148-175) et le repli est 400 (ioscbct/volume.py:36), mais le remplacement explicite a disparu : voir le constat sur le niveau dans AREG_IOSCBCT sur VISOR.

  • run_icp_point_to_plane est point-plan, comme son nom l'indique. Les normales sont utilisées : les normales du CBCT décident quelles correspondances sont gardées et donnent les plans tangents de l'étape. Une version antérieure de cette page disait que la fonction était point-point, avec des normales calculées puis jetées ; cela ne correspond pas à 3c67957 (AREG_IOSCBCT.py:579-608,688-692). L'étape de Procrustes (:609) est le repli pour un système dégénéré.
  • Deux modalités, un seul CBCT par clé de patient, mais les deux arcades obligatoires. Un patient dont seule l'arcade supérieure a été scannée lève une KeyError ('ios_lower') et sort de l'exécution : l'erreur est journalisée avec sa trace (AREG_IOSCBCT.py:1303-1305) et les autres patients continuent.
  • Le CBCT doit être en .nii.gz. NumberScan, côté widget, compte pourtant .nrrd .nii .gipl et leurs variantes .gz (IOSCBCT.py:25) : la barre de progression peut annoncer des patients que le CLI ne verra jamais.
  • Temps limités à T0–T2 par [Tt]([0-2]) : voir le commentaire TIMEPOINT-SUFFIX à AREG_IOSCBCT.py:1068 et la note centrale dans AREG_CBCT/AREG_CBCT_utils/utils.py:56 ; de _T10 à _T29, ils sont lus comme T1 ou T2.
  • Collision d'identifiants après normalisation : P001 et P1 deviennent la même clé, donc le même patient. Rien ne le détecte dans getPatients ; seul le widget, plus tard, avertit qu'il y a plusieurs candidats (Review.py:280).
  • Code à moitié mort : load_data() lit lm_cbct_u/l et lm_ios_u/l par get_landmarks() (indexation positionnelle, sans étiquettes, AREG_IOSCBCT.py:971-974), et main() écrase aussitôt les quatre avec les tableaux appariés par étiquette de _pair_landmarks() (AREG_IOSCBCT.py:1204-1207). Tout n'est pas perdu : load_data() utilise les tableaux CBCT pour lire le niveau de contour et juger quels landmarks sont sur l'émail (:988-999), et renvoie ce verdict sous le nom on_enamel, que main() passe à align_by_landmarks (:1217-1226) ; la partie inutilisée, ce sont les quatre tableaux renvoyés. De même, PatientScanLandmark (IOSCBCT.py:33) n'est appelé nulle part dans ce module (l'autre définition est dans ASO_Method/CBCT.py).
  • DisplayAREGIOSCBCT(0) (défini une fois, Progress.py:127) est instancié avec nb_progress_total = 0 dans les trois modes : self.progress / 0 → ZeroDivisionError si la barre de progression est mise à jour. Elle n'est mise à jour que sous la condition is_event(progress, PATIENT_DONE) and updateProgressBar == False (Progress.py:141 ; PATIENT_DONE = 200, ADT/ADTLib/progress_protocol.py:36), ce qui explique que cela passe inaperçu.
  • fitness et inlier_rmse sont lus après la boucle de l'ICP. Avec max_iterations = 0 (impossible ici, mais fragile) ou une sortie au premier break sur < 3 correspondances, ils sont définis, mais le code ne s'en prémunit pas.
  • pyvista est installé dans le Python de Slicer, épinglé à la version 0.47.3. C'est une dépendance lourde qui n'est là que pour ce module (pv.wrap, contour, transform, read, save) et qui pourrait être remplacée par du VTK direct, déjà présent.
Le pré-alignement peut silencieusement être l'identité

Legacy (3c67957) ; adouci dans VISOR. Le pré-alignement legacy est sauté avec une ligne de journal (AREG_IOSCBCT.py:416,425@3c67957). VISOR met le verdict dans le rapport, par maillage : prealignment.accepted et reason (ioscbct/geometry.py:293-294,306-307,319-321). Un pré-alignement refusé n'est toujours pas une erreur : le maillage est écrit si l'ICP tient, et un ICP qui apparie moins de 5 % de l'arcade est refusé (ioscbct/pipeline.py:192-202).

C'est journalisé comme un avertissement, jamais comme une erreur : une exécution entière peut s'être passée de tout pré-alignement et produire quand même des fichiers. Vérifiez les lignes de journal Skipping the pre-alignment avant de vous fier à un lot.

8. Littérature

Explication en langage courant et maths : page de l'atlas.

Non publié

Aucun article ne couvre AREG_IOSCBCT tel qu'il est implémenté ici. La lignée publiée par le groupe couvre l'orientation et le recalage de CBCT (Automated Orientation and Registration of CBCT Scans, LNCS 2023) et le recalage longitudinal d'IOS (AReg IOS, LNCS 2023) ; les modules de landmarks qu'il consomme ont chacun le leur (ALI_CBCT). La partie multimodale IOS↔CBCT semble être un assemblage interne, non publié.

Le voisinage méthodologique dans la littérature, pour comparaison, et non comme description de ce code :

  • Novel Procedure for Automatic Registration between CBCT and Intraoral Scan Data Supported with 3D Segmentation : même problème, mais avec segmentation des dents des deux côtés, puis RANSAC + ICP. Erreur rapportée : 0,234 ± 0,019 mm. AREG_IOSCBCT prend explicitement la voie plus légère : des landmarks au lieu d'une segmentation volumétrique, une isosurface seuillée au lieu de dents segmentées.
  • Automatic multimodal registration of CBCT and intraoral scans: a systematic review and meta-analysis : revue systématique, qui oppose les approches géométriques (fiables, peu coûteuses) aux approches apprises.
  • Fully automatic integration of dental CBCT images and full-arch intraoral impressions : variante avec identification dent par dent et correction des erreurs d'assemblage.
