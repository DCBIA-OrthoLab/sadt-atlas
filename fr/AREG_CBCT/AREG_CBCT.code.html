AREG_CBCT, legacy : le code

Pour les développeurs : ce que fait le module Slicer legacy dans le code, avec des références file:line, des signatures, les arguments exacts, l'environnement, les pauses de revue et les pièges. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. Le portage VISOR a sa propre page.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, a sa propre page : AREG_CBCT sur VISOR. Les notes qui ouvrent certains encadrés ci-dessous (« Legacy uniquement », « Aussi vrai dans VISOR ») comparent avec ce portage à SADT-VISOR 6ba2a78 ; dans ces notes, cbct/ désigne SADT-VISOR tools/AREG/AREG_CBCT/src/sadt_areg_cbct/ et common/ désigne SADT-VISOR tools/AREG/common/src/sadt_areg_common/.

1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

AREG/AREG.py est un widget unique qui pilote trois modalités : CBCT (AREG/AREG_Method/CBCT.py), IOS (AREG/AREG_Method/IOS.py) et IOS sur CBCT (AREG/AREG_Method/IOSCBCT.py). Il ne calcule rien lui-même : chaque Method.Process() renvoie une liste de dictionnaires d'étapes, et le widget les exécute l'une après l'autre.

Une étape a toujours la forme suivante :

{"Process": slicer.modules.areg_cbct,   # Slicer CLI module
 "Parameter": {...},                    # dict passed as-is to slicer.cli.run
 "Module": "AREG_CBCT for Mandible",    # label shown in the UI
 "ReviewId": "cbct_registration",       # optional review pause
 "ReviewFolder": ".../Mandible",
 "ReviewReferenceFolder": "<T1 folder>",
 "Display": DisplayAREGCBCT(nb_scan)}   # progress translation -> progress bar

Appels sortants du mode CBCT, dans l'ordre d'exécution :

Rien dans le dépôt n'appelle AREG : c'est un outil terminal. Ses fichiers .tfm sont en revanche réutilisés par AutoMatrix et les modules d'analyse.

3. Les trois modes et la chaîne exacte

Explication en langage courant et maths : page de l'atlas.

Le mode est choisi par CbModeType ; SwitchType() (AREG.py:1093) instancie la classe correspondante. Les trois partagent la même fin de chaîne, centrer T2, lancer AREG par région, AMASSS final, et ne diffèrent qu'en amont :

ModeClasseEn amontMasques T1
Semi-AutomatedSemi_CBCT (CBCT.py:27)aucunfournis par l'opérateur (champ « T1 Masks »)
Fully-AutomatedAuto_CBCT (CBCT.py:445)aucunAMASSS CBMASK/MANDMASK/MAXMASK, écrits dans le dossier T1 d'entrée prédit
Orientation & RegistrationOr_Auto_CBCT (CBCT.py:613)PRE_ASO → ALI_CBCT → SEMI_ASO sur T1, dans <T1 folder>OrAMASSS sur <T1 folder>Or prédit

La région de référence est un choix de l'opérateur, pas quelque chose d'inféré : les cases « Regions of Reference for Registration », Cranial Base, Mandible, Maxilla (CBCT.py:194-200), sont traduites en CB / MAND / MAX par TranslateModels. Cocher deux régions lance deux recalages indépendants, chacun avec son propre dossier de sortie.

La chaîne du mode Orientation & Registration, étape par étape

Explication en langage courant et maths : page de l'atlas.

T1 et T2 : deux CBCT du même patient

Préparation : ce mode uniquement

  1. PRE_ASO recentre le T1 : pas de réseau, une translation <T1 folder>Or
  2. ALI_CBCT place les landmarks d'orientation prédit CBCT.py:758-769
  3. SEMI_ASO oriente le T1 sur le gold standard <T1 folder>Or

Segmentation : ce que le recalage aura le droit de voir

  1. AMASSS prédit CBMASK, MANDMASK, MAXMASK sur le T1 orienté prédit <base>_seg_<STRUCT>.nii.gz, à côté des scans

Recalage : une fois par région cochée

  1. centrer le T2 mobile T2_Center
  2. masquer le T1 fixe : elastix ne voit rien à l'extérieur fixed_image_masked
  3. une passe elastix : information mutuelle de Mattes, 3 niveaux de pyramide, 1500 itérations chacun une transformation rigide
  4. MatrixRetrieval la convertit en Euler3DTransform <pat>_<REG>Reg_matrix.tfm
  5. rééchantillonner le T2 : sur sa propre grille, pas celle du T1 Registered/<Region>/<pat>_OutReg/

Fin

  1. AMASSS s'exécute de nouveau pour les segmentations finales, deux fois, sur le dossier d'entrée, puis récursivement sur l'arborescence de sortie, avec genVtk=True <Region>/<pat>_OutReg/

Les étapes 4 à 10 forment la fin de chaîne que les trois modes partagent. Les deux autres ne diffèrent qu'en amont : Fully-Automated saute 1–3 et laisse AMASSS prédire les masques sur le T1 tel que fourni ; Semi-Automated saute entièrement 1–4 et prend les masques dans le champ « T1 Masks » de l'opérateur. Cocher deux régions de référence lance deux recalages indépendants, chacun avec son propre dossier de sortie.

4. Entrées, appariement, prétraitement

Explication en langage courant et maths : page de l'atlas.

Formats. .nii.gz, .nii, .nrrd, .nrrd.gz, .gipl, .gipl.gz. Pour une entrée DICOM, convertdicom2nifti (utils.py:601) convertit un sous-dossier par patient avec sitk.ImageSeriesReader, en se rabattant sur dicom2nifti, vers <folder>/NIFTI/<patient>.nii.gz.

Appariement T1/T2 : GetPatients (utils.py:80). L'identifiant du patient est ce qui reste du nom de fichier après une chaîne d'appels split() sur une liste fixe de marqueurs (_Scan, _Or, _MAND, _CB, _lm, _T2, _T1, _Cl…). Ensuite :

  • un fichier image dont le nom contient mask, seg ou pred → segmentation ;
  • sinon → scanT1 / scanT2 ;
  • si segmentationType est donné, une seconde passe cherche dans mask_folder_t1 (ou dans le dossier T1 par défaut) les fichiers dont le nom contient cb, mand/md ou max/mx selon la région, et le premier trouvé l'emporte. Cette passe ne vérifie jamais que le fichier est bien un masque : un scan nommé P1_T1_MAX.nii.gz serait pris pour la segmentation.
Piège

Legacy uniquement (3c67957) ; faux dans VISOR. La recherche legacy est un test de sous-chaîne sur le nom de base en minuscules (AREG_CBCT/AREG_CBCT_utils/utils.py:116-120@3c67957). VISOR exige un jeton de segmentation (mask, seg, pred, segmentation) et un jeton de région, tous deux comme jetons entiers du nom (SADT-VISOR common/pairing.py:376-404, common/catalogs.py:117-125). Observé : avec P1_T1_MAX.nii.gz et P1_T1_MAX_seg.nii.gz dans un même dossier, le masque du maxillaire trouvé est le fichier _seg.

La recherche de masque par mot-clé (cb, mand/md, max/mx) ne vérifie jamais que le fichier trouvé est réellement une segmentation : un scan nommé P1_T1_MAX.nii.gz serait pris silencieusement pour la segmentation.

T2 est lu avec segmentationType=None : seule l'image fixe est masquée, jamais la mobile.

Centrage de T2 : pre_aso_cbct. Malgré son nom et son paramètre model_folder qui pointe vers Models/Orientation/PreASO, ce CLI n'utilise aucun réseau : il calcule T = -physical_center_of_the_image (ASO_CBCT/PRE_ASO_CBCT/PRE_ASO_CBCT.py:100-104), rééchantillonne avec l'inverse et écrit la TranslationTransform en .tfm à côté. Une prédiction de direction par un DenseNet a existé, commentée, puis a été retirée (commit 4296774). Les arguments model_folder et SmallFOV sont morts, mais les poids PreASO sont quand même téléchargés.

Masquage de l'image fixe, MaskedImage (utils.py:465) :

fixed_seg_sitk.SetOrigin(fixed_image_sitk.GetOrigin())   # origin forced
fixed_image_masked = applyMask(fixed_image_sitk, fixed_seg_sitk, label=SegLabel)
sitk.WriteImage(sitk.Cast(fixed_image_masked, sitk.sitkInt16),
                os.path.join(temp_folder, "fixed_image_masked.nii.gz"))

applyMask binarise si un label est demandé, sinon passe le masque tel quel à sitk.Mask (tout voxel non nul est conservé). Le fichier temporaire porte toujours le même nom : le dossier temporaire est unique pour tout le lot (CBCT.py:302 (:515 en mode Orientation)), donc chaque patient écrase le précédent, sans danger en séquentiel, fatal si le CLI était un jour parallélisé.

Piège

Legacy uniquement (3c67957) ; absent de VISOR. Legacy : utils.py:465-476@3c67957. VISOR masque l'image fixe en mémoire et le dit dans la docstring de register (SADT-VISOR cbct/elastix.py:198-201).

Le dossier temporaire de masquage est unique pour tout le lot et le fichier s'appelle toujours fixed_image_masked.nii.gz : chaque patient écrase le précédent, sans danger en séquentiel, fatal si le CLI était un jour parallélisé.

SegLabel vaut en pratique toujours None : la liste déroulante LabelSelectcomboBox est masquée en dur (AREG.py:684) et SegmentationLabels reste [0], que le CLI retraduit en None. GetSegmentationLabel (CBCT.py:173), qui lisait les labels présents dans le masque, n'est appelée nulle part : code mort.

5. Le cœur algorithmique : le recalage

Explication en langage courant et maths : page de l'atlas.

Tout se passe dans VoxelBasedRegistration (utils.py:479) :

  1. lire le T2 mobile en itk.F ;
  2. masquer le T1 fixe (ci-dessus), le relire en itk.F ;
  3. un seul ElastixReg(fixed_image_masked, moving_image, initial_transform=None) ;
  4. MatrixRetrieval → transformation SimpleITK ;
  5. ComputeFinalMatrix([t]) → Euler3DTransform;
  6. rééchantillonner T2.

La bibliothèque est itk-elastix (itk.ElastixRegistrationMethod), pas SimpleITK ni ANTs. Les paramètres, tous rendus explicites dans make_rigid_param_map_deterministic (utils.py:408), se superposent à la carte "rigid" par défaut d'elastix :

Il n'y a plus d'étape grossière. Le paramètre ApproxReg derrière la case « Include Approximation Step » descend jusqu'à VoxelBasedRegistration(approx=...) et n'y est jamais lu : ElastixApprox et make_rigid_param_map_stochastic (échantillonneur RandomCoordinate, 10000 échantillons, AdaptiveStochasticGradientDescent, 2 niveaux, sur les images non masquées) ont été supprimés par le commit 350a8de le 2025-09-23, avec l'usage de initial_transform dans ElastixReg (utils.py:454), appelé partout avec None. Le seul « du grossier au fin » qui reste est la pyramide à 3 niveaux ; le pré-alignement grossier est désormais assuré par le centrage de T2 par PRE_ASO et par AutomaticTransformInitialization.

Récupération de la matrice, MatrixRetrieval (utils.py:711), lit TransformParameters : 3 angles puis 3 translations, réordonnés en sitk.Euler3DTransform. ComputeFinalMatrix (utils.py:732) compose la liste (rotations multipliées, translations additionnées) : avec une liste à un seul élément, c'est une simple copie directe. Le code de composition n'est donc jamais exercé, et l'addition des translations ne serait de toute façon valable que si les rotations intermédiaires étaient l'identité.

Rééchantillonnage, ResampleImage (utils.py:353) : interpolation linéaire, DefaultPixelValue = 0, et SetReferenceImage(image) où image est l'image mobile elle-même. Le volume recalé garde donc la grille de T2 (taille, espacement, origine), pas celle de T1. Sortie convertie en int16.

La seconde parcourt récursivement l'arborescence <Region>/<patient>_OutReg/ et ignore ses propres sorties grâce au suffixe _seg_.

ALI_CBCT (mode Orientation uniquement, CBCT.py:758-769) :

Agents de renforcement multi-échelles (1 mm puis 0,3 mm), champ de vue de 64³ voxels, un réseau DNet = DenseNet 3D MONAI (growth_rate=34, blocs (6,12,24,16)) suivi d'un MLP à 6 sorties = les 6 directions de déplacement (brain.py:39) prédit. La liste des landmarks dépend du plan de référence : IF ANS PNS UR1O UR6O UL6O (occlusal) ou N S Ba RPo LPo LOr ROr (Francfort).

SEMI_ASO_CBCT : gold_folder = <model_folder_2>/<reference>, output_folder = <T1 folder>Or, add_inname = "Or". Alignement par vtkIterativeClosestPointTransform, rigide, sur les landmarks (1000 itérations, StartByMatchingCentroidsOn), après avoir écarté les landmarks aberrants calculé.

7. Sorties

Explication en langage courant et maths : page de l'atlas.

Écrit par AREG_CBCT.py:47-53 :

<output>/<Cranial Base|Mandible|Maxilla>/<patient>_OutReg/
    <patient>_<CB|MAND|MAX>Scan<add_name>.nii.gz    # registered T2, int16
    <patient>_<CB|MAND|MAX><add_name>_matrix.tfm    # the transform

Le nom du sous-dossier vient de translate() (utils.py:595) : CB → Cranial Base. add_name est concaténé sans séparateur.

Conventions du .tfm : sitk.WriteTransform d'une Euler3DTransform, donc LPS et convention ITK (la transformation envoie l'espace de sortie vers l'espace d'entrée). Aucune inversion n'est nécessaire nulle part dans le CLI, tout y est SimpleITK/elastix ; le seul endroit de la chaîne CBCT qui conjugue par diag(-1,-1,1,1) est la correction manuelle, qui part d'une matrice Slicer en RAS (Review.py:597).

Le .tfm de centrage écrit par PRE_ASO à côté du T2 centré n'est pas composé avec celui d'AREG : pour ramener le T2 d'origine sur T1, il faut chaîner les deux fichiers à la main.

8. Pauses de revue et navigation dans le lot

Explication en langage courant et maths : page de l'atlas.

Ajouté par le commit 2609bc4 (« Pause VFACE at chosen steps »… et AREG avant lui). Dans « Review and manual adjustment », l'opérateur coche les étapes où l'exécution doit s'arrêter ; la sélection est stockée dans QSettings sous AREG/ReviewSteps (AREG.py:2122).

Les points d'arrêt disponibles en CBCT (getReviewSteps, CBCT.py:254), et ce qu'ils permettent (CATALOGUE, Review.py:676) :

IdAprèsNature
cbct_landmarks_orientationALI_CBCT (mode Orientation)modifiable : les points peuvent être déplacés et sont réécrits

Mécanique de la pause. markProcessesForReview (AREG.py:2237) pose ReviewPause=True sur les étapes dont le ReviewId est coché. À la fin d'une exécution du CLI, enterReviewPause (AREG.py:2250) renvoie True et diffère beginReview via QTimer.singleShot(0, ...), ce qui est obligatoire : cela se passe dans un callback d'observateur VTK, où la boucle d'événements Qt ne tourne pas et où charger un volume remplirait le tube stdout que Slicer ne vide plus.

ReviewSession.build (Review.py:143) construit la file : un élément par patient trouvé dans ReviewFolder, restreint aux patients de cette exécution (runPatientIds() lit le dossier T1 d'entrée, alors qu'un dossier de sortie réutilisé contient les résultats de mois de travail). Pour AREG, ReviewFolder est limité à <output>/<Region> : sinon la pause de la mandibule montrerait aussi la base du crâne, et l'ajustement de l'opérateur se fondrait dans la matrice arrivée la première.

Pour cbct_registration, le scan recalé est chargé par-dessus le T1 (foregroundOpacity=0.5) et rattaché à un vtkMRMLLinearTransformNode avec ses poignées d'interaction (Review.py:505). À la sortie, _saveAdjustment (Review.py:565) convertit le déplacement RAS en LPS (flip @ ras @ flip), l'inverse, et écrit sitk.CompositeTransform([original, nudge.GetInverse()]) dans le .tfm existant : ce qui le consomme en aval applique une seule matrice par patient et ne peut pas les chaîner. Le scan est ensuite figé et réécrit sur place (Review.py:628). Si la matrice est l'identité à 1e-9 près, rien n'est écrit.

Navigation dans le lot :

  • Patient précédent / suivant (AREG.py:2416) : parcourent la file sans jamais faire avancer l'exécution ; saveEdits() est appelé avant chaque changement, donc les corrections sont conservées.
  • Signaler (AREG.py:2430) : marque un patient « à refaire ». Le bouton n'apparaît que s'il existe une étape corrigeable plus en arrière.
  • Revenir en arrière (AREG.py:2437) : previousCorrectableStep() (AREG.py:2524) remonte executed_steps jusqu'à la dernière étape de type LANDMARKS ou REGISTRATION, les étapes en lecture seule sont sautées. Les étapes intermédiaires sont rejouées pour les seuls patients signalés : restrictStepToPatients (Review.py:846) construit un dossier temporaire qui ne contient que ces patients, par liens symboliques (un CBCT pèse 200 Mo), en conservant l'arborescence, puis réécrit la clé d'entrée de l'étape (t1_folder, t2_folder, input, inputVolume… : INPUT_KEYS, Review.py:836). Les étapes restreintes sont insérées en tête de list_Processes_Parameters. Les liens sont supprimés à la fin de l'exécution par clearReviewTempFolders.
  • Étape suivante (AREG.py:2494) : enregistre le patient courant, journalise combien de patients ont été acceptés sans être ouverts, et reprend l'exécution.

ReviewMatrixFolder et ReviewKind sont lus par Review.build mais définis nulle part : des points d'extension inutilisés (la matrice est donc toujours cherchée dans ReviewFolder lui-même).

11. Pièges et points fragiles

Explication en langage courant et maths : page de l'atlas.

Les suffixes _T1 / _T2. Le commit 05d1fec a marqué chaque occurrence avec le mot-clé TIMEPOINT-SUFFIX. La note de référence se trouve au-dessus de GetPatients (utils.py:56-79).

Piège

Aussi vrai dans VISOR, mais plus silencieux. Observé sur 6ba2a78 : P001_T3.nii.gz garde l'identifiant P001_T3 et P001_T10.nii.gz n'est pas coupé en P001 ; seuls t1, t2 et t0 sont des jetons de point temporel (SADT-VISOR common/catalogs.py:148). L'orphelin est listé sous unmatched dans AREG_report.json (cbct/dispatch.py:259-260) et une exécution où rien ne s'apparie s'arrête avec une erreur qui énonce la règle (cbct/dispatch.py:261-268). Côté legacy : ADT/ADTLib/naming.py:34-47@3c67957.

Le problème : l'identifiant du patient est ce qui reste du nom après découpage sur une liste fixe de marqueurs, et les seuls points temporels de cette liste sont _T1 et _T2. Un P001_T3.nii.gz garde l'identifiant P001_T3, ne s'apparie avec rien, et la paire est écartée silencieusement : aucune exception. Le vrai point temporel ne vient pas du nom mais de l'argument time_point, c'est-à-dire du dossier ; seule l'extraction de l'identifiant est en cause.

Les occurrences, dans le périmètre d'AREG, à 3c67957. La chaîne par défaut est ADT/ADTLib/naming.py:34-47 (patient_id) ; les occurrences ci-dessous l'appellent ou portent une chaîne à elles :

Il n'a pas été fait volontairement : la réponse actuellement supportée est de renommer les entrées.

Bug confirmé

Legacy uniquement (3c67957) ; corrigé dans VISOR. VISOR lit CenterOfRotationPoint et le pose sur la transformation SimpleITK (SADT-VISOR cbct/elastix.py:212-240) ; la docstring du module rapporte 8,371 mm d'erreur quand le centre est abandonné contre 0,025 mm quand il est respecté, sur un fantôme (cbct/elastix.py:8-17, mesure des auteurs, non rejouée ici). Numéros de ligne à 3c67957 : MatrixRetrieval est en utils.py:711-729 et l'appel à ResampleImage en utils.py:568-570, pas 689.

Le centre de rotation d'elastix est perdu. MatrixRetrieval ne lit que TransformParameters et jamais CenterOfRotationPoint. Une EulerTransform d'elastix vaut R·(x − c) + t + c ; la sitk.Euler3DTransform reconstruite a son centre à l'origine et vaut R·x + t. Les deux ne coïncident que si c est l'origine ou si R = I. Comme AutomaticTransformInitialization est actif et que le centre de rotation est dérivé de l'image fixe (T1, qui n'est centrée qu'en mode Orientation), l'écart (I − R)·c est en général non nul. Et l'écart ne se limite pas au .tfm : le volume de sortie n'est pas l'image résultat d'elastix, il est reconstruit par ResampleImage(sitk.ReadImage(moving_image_path), transform) (utils.py:569) à partir de cette même matrice. Le .tfm et le volume recalé sont donc cohérents entre eux, mais tous deux s'écartent de ce qu'elastix a réellement optimisé.

CenterOfRotationPoint n'apparaît nulle part dans le dépôt (vérifié par grep), et la seconde copie de MatrixRetrieval que portait MRI2CBCT_CLI/MRI2CBCT_CLI_utils/AREG_MRI.py a quitté l'arborescence avec la réécriture de MRI2CBCT (PR ADT #277) : ce module est désormais le seul à présenter cet écart.

Note

Legacy uniquement (3c67957). L'hypothèse portait sur un écart que VISOR n'a plus. VISOR applique le centre de rotation, ne pré-centre pas T2, et laisse elastix partir du centre géométrique des deux images (SADT-VISOR cbct/elastix.py:106-107) ; en mode orienté, seul T1 est orienté, jamais T2 (cbct/dispatch.py:226-228).

Une hypothèse à tester plutôt qu'à croire : si le module donne encore des résultats corrects en pratique, c'est probablement parce que les volumes arrivent déjà près de l'origine, PRE_ASO recentre T2 et ASO oriente T1, si bien que c ≈ 0 et que (I − R)·c reste petit. Le résultat dépend alors d'un centrage préalable qui n'est garanti nulle part. Mesurez l'écart sur un cas réel avant de tirer des conclusions.

Autres points :

  • ApproxReg / « Include Approximation Step » ne fait rien depuis septembre 2025. La case reste cochée par défaut dans l'interface.
  • Le dossier <T2 folder>_Center est créé à côté du dossier d'entrée de l'utilisateur, comme <T1 folder>Or. PRE_ASO saute les fichiers déjà présents : une seconde exécution avec des entrées modifiées réutilise les anciens.
  • En mode Fully-Auto, AMASSS écrit les masques dans le dossier T1 d'entrée. À la pause cbct_registration, comme ReviewReferenceFolder est ce même dossier, tous les masques du patient sont chargés dans la scène avec le scan.
  • Le fichier fixed_image_masked.nii.gz est réécrit pour chaque patient dans le même dossier temporaire.
  • SwitchType (AREG.py:1093) réaffiche le sélecteur NIFTI/DCM après que SwitchModeCBCT l'a masqué : le résultat net est que l'entrée DICOM n'est proposée qu'en mode Orientation, l'inverse de ce que SwitchModeCBCT semble vouloir. Et dans ce mode, DCMInput est passé à l'étape AREG dont les dossiers contiennent déjà du NIfTI.
  • startStep est appelé deux fois pour la première étape CBCT (AREG.py:1789 puis AREG.py:1804) : executed_steps se retrouve avec un doublon, que previousCorrectableStep absorbe parce qu'il cherche la dernière occurrence.
  • Un .tfm corrigé manuellement devient une CompositeTransform, pas une Euler3DTransform : un consommateur en aval qui suppose une transformation simple pourrait échouer à la relire.
  • Code mort trouvé : TestReference (CBCT.py:57, qui appellerait NumberScan avec un seul argument et lèverait une TypeError), GetSegmentationLabel, getGPUUsage, GetMatrixPatients et ModifiedDictPatients (aucun appelant ne passe jamais matrix_folder ni todo_str), ElastixReg(initial_transform=...), et DisplayAREGIOSCBCT défini deux fois dans Progress.py (ligne 135).

12. Littérature

Explication en langage courant et maths : page de l'atlas.

L'article de référence est Anchling, Hutin, Huang, Barone, Roberts, Miranda, Gurgel, Al Turkestani, Tinawi, Bianchi, Yatabe, Ruellas, Prieto, Cevidanes, « Automated Orientation and Registration of Cone-Beam Computed Tomography Scans », LNCS 14242, 2023, p. 43-58 : Springer, PMC11104011. Précision rapportée : < 3° et < 2 mm par rapport aux experts, moins de 5 min par cas.

Le code diverge de l'article sur trois points vérifiés :

  1. l'article décrit un recalage en deux temps : « VBR entre les images entières, puis avec l'image masquée comme étape de raffinement », 10 000 itérations sur la passe masquée. Le code n'exécute plus qu'une seule passe masquée à 1500 itérations ;
  2. l'article rapporte SimpleElastix ; le code utilise itk-elastix (itk.ElastixRegistrationMethod) ;
  3. l'article obtient ses masques par AMASSS / UNETR MONAI ; AMASSS est aujourd'hui un nnU-Net v2.

Sur la question de fond, la superposition voxel à voxel sur la base du crâne, la référence historique du laboratoire est Cevidanes et al., Superimposition of 3D cone-beam CT models of orthognathic surgery patients (2005, PubMed 16227481).

À ne pas confondre avec Accuracy and Reproducibility of Voxel Based Superimposition…, PLOS One 2011, qui n'est pas du laboratoire : il est de Nada, Maal, Kuijpers-Jagtman et al. (Radboud UMC, Nimègue). C'est une validation indépendante de la méthode, ce qui lui donne plus de poids, pas moins, mais l'attribuer au groupe serait une erreur.
