AMASSS

AMASSS découpe un scan de la tête en structures anatomiques, avec un réseau par structure, un voxel à la fois. Cette page explique, étape par étape, le déroulement d'une exécution dans le module Slicer legacy, avec les maths des parties qui relèvent du calcul plutôt que de l'apprentissage : normalisation du scan, fusion des patchs du réseau, fusion des masques, construction des surfaces. Quand le code fait quelque chose qui mérite d'être vérifié, un lien mène à la page de code.

Code (développeurs) Gillot 2022 · PLOS ONE AMASSS_CLI Python de Slicer, pas de conda VISOR Bibliographie

Vue d'ensemble : ce qui entre, ce qui sort

AMASSS prend un scan 3D de la tête (CBCT) et le découpe en structures anatomiques : mandibule, maxillaire, base du crâne, voies aériennes supérieures, vertèbres cervicales, peau et trois masques de recalage. Il utilise un réseau par structure : chaque réseau répond à une seule question pour chaque voxel, « ce voxel fait-il partie de ma structure ? ». Le module est un widget Slicer qui lance un programme en ligne de commande dans le Python propre à Slicer.

EntréeCe qui se passeSortie
un scan (.nii, .nii.gz, .nrrd...) ou un dossier de scans, et les structures voulueschaque scan est converti, chaque structure est prédite par son propre réseau, une structure après l'autre, puis les masques sont assemblésun masque binaire par structure et/ou une carte de labels fusionnée par scan, des surfaces 3D optionnelles (.vtk)

Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage serveur est AMASSS sur VISOR.

1. Sa place dans la chaîne

AMASSS est à la fois un module à part entière et une brique : AREG_CBCT l'utilise deux fois, d'abord pour les masques de recalage (un fichier par structure) puis pour les segmentations livrables, VFACE l'utilise dans sa chaîne d'analyse d'asymétrie, et MRI2CBCT l'utilise une fois, pour la base du crâne du CBCT. Tous lancent le même programme en ligne de commande. AMASSS n'appelle aucun autre module. Outre nnU-Net (importé seulement au besoin), le programme importe torch, SimpleITK, VTK, cc3d, NumPy et la bibliothèque d'aide ADT partagée.

Une distinction importante pour AREG : les trois structures de masque (CBMASK, MANDMASK, MAXMASK) ne sont pas un post-traitement de la base du crâne, de la mandibule et du maxillaire. Ce sont des modèles entraînés séparément, à une autre résolution (0,3 mm au lieu de 0,4 mm) et avec un jeu d'entraînement de taille différente (50 contre 76 dans les descriptions des modèles).

2. Fichiers en jeu

Deux parties : un widget Slicer qui recueille les choix, et un programme en ligne de commande qui fait tout le travail (recherche des modèles, inférence, assemblage). Les deux s'exécutent dans le Python de Slicer : pas d'environnement conda. Une carte graphique n'est pas obligatoire, mais sur un lot le CPU est inutilisable en pratique, car le rééchantillonnage monocœur domine. Le programme reçoit ses douze arguments par position.

3. Entrées et prétraitement

3.1 Découverte des fichiers

Un fichier ou un dossier est accepté ; un dossier est parcouru récursivement, car AREG écrit ses scans recalés dans des sous-dossiers. Les fichiers retenus ont une extension de volume. Deux sortes de noms sont ignorées : tout nom contenant MASK et, sauf si l'entrée est une segmentation, tout nom contenant l'identifiant de prédiction entre tirets bas (_Pred_ par défaut), qui est la sortie d'une exécution précédente (la resegmenter donnerait un masque vide). Ces deux filtres s'appliquent à un dossier ; un fichier unique donné directement n'est jamais filtré.

3.2 Conversion

Chaque scan est copié dans un dossier sous un nom numéroté (p_001, p_002...), dans l'ordre de découverte. Un .nii.gz est copié tel quel ; tout le reste est relu puis réécrit, car nnU-Net choisit son lecteur d'après l'extension du fichier. Le type de voxel est laissé tel quel, puisque nnU-Net convertit lui-même en float.

3.3 Ce qu'AMASSS ne fait plus

Aucune normalisation d'intensité, aucun fenêtrage ni rééchantillonnage n'est écrit dans ce dépôt : l'ancienne fonction de fenêtrage est une coquille vide que rien n'appelle. Tout le prétraitement effectif est celui de nnU-Net, décrit par le plan de chaque modèle : recadrage sur la région non nulle, normalisation d'intensité, puis rééchantillonnage à l'espacement cible.

Dans le codeLes filtres de découverte, la fonction de conversion et la fonction de fenêtrage morte

4. Les modèles

4.1 Le bundle et sa découverte

Pour chaque structure demandée, le programme cherche, dans le dossier des modèles, un dossier de modèle contenant un checkpoint entraîné d'un seul fold. Une structure sans checkpoint est déclarée indisponible et l'exécution continue avec les autres. Le bouton « Download latest models » télécharge l'archive (environ 2 Go) une seule fois ; c'est la même archive qu'AREG et VFACE téléchargent automatiquement.

4.2 Ce que contient réellement le bundle

Neuf dossiers, un par structure, chacun avec un seul fold entraîné. Ils forment deux familles : les modèles plein champ (mandibule, maxillaire, base du crâne, vertèbre cervicale, voies aériennes supérieures, peau) à 0,4 mm isotrope avec des patchs de 128 voxels, et les trois masques de recalage à 0,3 mm avec un patch différent, non cubique (112 × 160 × 128 voxels). Les neuf partagent une seule architecture : un U-Net 3D convolutif simple configuré par nnU-Net, à six étages et sans blocs résiduels.

Chaque modèle est binaire : il ne connaît que le fond et une structure. La valeur finale d'une structure dans un volume fusionné est attribuée par le programme, pas par le modèle.

4.4 Inférence

Le programme n'écrit pas de fenêtre glissante à lui : nnU-Net la gère à partir de la taille de patch du plan de chaque modèle. Les seuls paramètres que choisit le programme sont un pas de 0,5 (le pas vaut au plus la moitié d'un patch, donc les patchs se recouvrent d'au moins la moitié), une pondération gaussienne activée et le miroir au moment du test désactivé.

La boucle est par structure, pas par scan : tous les scans passent dans un modèle avant que le suivant soit chargé, de sorte qu'un checkpoint est chargé S fois au lieu de N × S. Le chemin du modèle est explicite, car une variable d'environnement valable pour tout le processus laisserait deux exécutions écraser le chemin l'une de l'autre. Une structure qui échoue est consignée et l'exécution continue ; elle n'échoue que si toutes échouent.

5. Le cœur algorithmique (non appris)

5.1 Rééchantillonnage GPU

D'après le commentaire du code, le rééchantillonnage monocœur coûte environ sept fois plus que le réseau, donc le programme le remplace par un rééchantillonneur torch qui tourne sur la carte graphique. La différence numérique est acceptée volontairement : l'entrée passe d'une interpolation d'ordre trois à une interpolation d'ordre un, car torch n'a pas d'interpolation cubique 3D. Si la carte manque de mémoire, la structure est rejouée avec le rééchantillonneur plus lent.

Dans le codeLa substitution du rééchantillonneur, ses garde-fous et le repli mémoire

5.2 Assemblage et écriture

Pour chaque scan, la prédiction de chaque structure est relue et transformée en masque binaire (toute valeur supérieure à zéro). Puis les masques sont écrits un par structure, fusionnés, ou les deux. Une carte fusionnée demande au moins deux structures. L'ordre est un ordre de priorité : la dernière structure écrite écrase les précédentes sur les voxels communs. La liste comprend deux codes qui ne correspondent à rien, CAN (il n'existe dans aucun dictionnaire) et RC (canal radiculaire : pas de modèle, et pas de label dans le tableau, donc il retomberait sur le label de la mandibule) ; ce sont deux entrées mortes.

Chaque masque est converti en entiers 16 bits et reçoit l'espacement, la direction et l'origine du scan. Sa géométrie est vérifiée et rééchantillonnée au plus proche voisin seulement si elle diffère, ce qui n'arrive pas dans le cas normal.

Dans le codeLa fonction d'assemblage, l'ordre de fusion et la vérification de géométrie

5.3 Post-traitement : ce qui n'est plus là

Aucun comblement de trous, aucune sélection de composante connexe et aucune morphologie n'est appliqué. Deux fonctions pour cela subsistent et rien ne les appelle. La version précédente nettoyait toutes les structures sauf deux et recadrait la peau ; le portage nnU-Net a supprimé ces appels, si bien que le nettoyage repose désormais sur le post-traitement propre à nnU-Net, si l'archive en fournit un.

5.4 Génération des surfaces VTK

Deux modes : fusionné, un fichier avec tous les labels ajoutés, et séparé, un fichier par structure. Chaque cellule reçoit une couleur constante, celle de la structure. Les maillages sont écrits dans les coordonnées propres de l'image, sans inversion entre LPS et RAS.

Dans le codeLa fonction de surface, le lissage et les deux modes

6. Post-traitement et sorties

Les noms sont construits à partir du nom du scan et de l'identifiant de prédiction : un fichier par structure, un fichier fusionné, et un fichier .vtk si des surfaces sont demandées. Avec l'option de dossier par scan, tout va dans un dossier de résultat nommé d'après le scan ; sinon, directement dans le dossier de sortie. Le dossier temporaire est vidé au début et à la fin d'une exécution, et les copies d'entrée sont supprimées dès que l'inférence est terminée.

Côté widget, les surfaces sont chargées dans la scène à la fin, mais seulement pour une entrée à fichier unique enregistrée à côté de l'original, avec la case des surfaces cochée.

8. Environnement

Tout s'exécute dans le Python de Slicer. Les bibliothèques sont installées quand on appuie sur Predict, après une confirmation. Les versions sont pour la plupart non épinglées ; NumPy est épinglé à 1.26.4, parce que la build de torch utilisée ici est compilée contre NumPy 1.x et que NumPy 2 casse son import. Pas de WSL, pas de conda : contrairement aux modules IOS (FlexReg, AREG_IOS, ALI_IOS), AMASSS n'utilise aucun environnement externe. Le tableau des versions est sur la page de code.

9. Pièges et points fragiles

Chaque point est vérifié dans le code et décrit, avec sa preuve, sur la page de code.

  • L'option « petit champ » ne fait rien : la cocher ne change que la liste des cases. Preuve.
  • L'entrée DICOM est ignorée : le panneau la propose mais le programme n'a aucune conversion. Preuve.
  • Le canal radiculaire est coché par défaut alors qu'aucun modèle n'existe. Preuve.
  • Le dossier temporaire est partagé et vidé, si bien que deux exécutions simultanées effacent le travail l'une de l'autre. Preuve.
  • Le lien entre numéro de cas et fichier n'est gardé qu'en mémoire ; un plantage laisse des prédictions anonymes. Preuve.
  • Le code de la structure est relu dans le nom du fichier au moment de fabriquer les surfaces séparées, si bien qu'un tiret bas dans l'identifiant de prédiction ou dans le nom du scan provoque une erreur. Preuve.
  • Le widget et le programme ne comptent pas les scans de la même façon (extensions, noms ignorés). Preuve.
  • Le nettoyage du widget supprime un chemin relatif au dossier de travail de Slicer, sans rapport avec le dossier temporaire. Preuve.
  • Code mort : plusieurs fonctions et parties du widget ne font rien. Preuve.
  • L'article et le code divergent : l'article décrit un MONAI UNETR, le code exécute nnU-Net. Preuve.

10. Littérature

L'article PLOS ONE de 2022 (Gillot et al.) décrit un modèle MONAI UNETR avec un recadrage de 128 voxels, un encodeur transformer et un décodeur convolutif. Le code qui tourne aujourd'hui est un réseau nnU-Net v2 purement convolutif, dans le legacy comme dans VISOR. La comparaison est sur la page de code ; les références sont dans SOURCES.md.
