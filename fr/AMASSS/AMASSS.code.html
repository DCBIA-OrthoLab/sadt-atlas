AMASSS, legacy : le code

Pour les développeurs : ce que fait le module Slicer legacy dans le code, avec des références file:line, des signatures, des tableaux et des pièges. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. Segmentation automatique multi-structures de scans CBCT craniofaciaux : un réseau nnU-Net v2 binaire par structure anatomique, assemblés et fusionnés par la CLI.

Code Atlas (explication) Gillot 2022 · PLOS ONE AMASSS_CLI Python de Slicer, sans conda VISOR Bibliographie
Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui fait tourner le même outil sur un serveur, est décrit sur sa propre page, AMASSS sur VISOR.

1. Sa place dans la chaîne

AMASSS est à la fois un module terminal (le widget AMASSS) et une brique réutilisée par trois autres outils, qui appellent tous la même CLI par slicer.modules.amasss_cli.

AppelantFichierUsage
Widget AMASSSAMASSS.py:1659-1667segmentation pilotée par l'opérateur
AREG_CBCT (semi-auto, entièrement auto, orienté)AREG/AREG_Method/CBCT.py:337, 469, 554, 842, 920deux rôles distincts : masques de recalage avant AREG (469, 842: merge=SEPARATE, genVtk=False), puis segmentations livrables ensuite (337, 554, 920: genVtk=True, fusion selon la demande)
VFACEVFACE/VFACE_utils/createlistprocess.py:123 (module chargé), 471, 496 (les deux appels)masques de recalage (merge=SEPARATE, genVtk=False) dans la chaîne d'analyse d'asymétrie
MRI2CBCTMRI2CBCT/MRI2CBCT_core/plan.py:87-92une étape AMASSS_CLI demandant la base du crâne (CB) du CBCT, merge=MERGE, genVtk=False

AMASSS n'appelle aucun autre module et ne démarre aucun sous-processus conda. Ses dépendances ne se limitent pas à nnunetv2 (importé paresseusement dans les fonctions qui l'utilisent) : la CLI importe torch, cc3d, SimpleITK, vtk, numpy et l'ADTLib partagé en tête de fichier (AMASSS_CLI.py:5-26).

Une distinction importante pour AREG : les codes CBMASK / MANDMASK / MAXMASK ne sont pas des étapes de post-traitement appliquées aux segmentations CB / MAND / MAX, ce sont des modèles entraînés séparément, à une autre résolution et avec un jeu d'entraînement de taille différente (numTraining 50 contre 76 ; §4.2).

La CLI n'est pas lancée dans un environnement conda : slicer.cli.run la démarre dans le Python de Slicer, et depuis le portage de septembre 2026 (109e1ed) l'inférence nnU-Net s'exécute dans ce même processus, et plus dans un nnUNetv2_predict enfant.

CUDA n'est pas requis : ResolveDevice() (AMASSS_CLI.py:79) retombe sur le CPU en le journalisant. En pratique le CPU est inutilisable sur un lot (le rééchantillonnage scipy monocœur domine, cf. §5.1).

Les arguments sont positionnels et lus par indice dans sys.argv (AMASSS_CLI.py:937-957), sans argparse. L'ordre dans le XML fait donc foi : inputVolume (fichier ou dossier), modelDirectory, skullStructure (codes séparés par des virgules), merge (MERGE / SEPARATE / les deux, découpé sur [, ]+), genVtk, save_in_folder, output_folder, vtk_smooth, prediction_ID (par défaut Pred), temp_fold (vidé au démarrage), SegmentInput, DCMInput (jamais utilisé).

3. Entrées et prétraitement

Explication en langage courant et maths : page de l'atlas.

3.1 Découverte des fichiers

main() accepte un fichier ou un dossier, parcouru par un os.walk récursif (AMASSS_CLI.py:766) : nécessaire parce qu'AREG écrit ses scans recalés dans <output>/<Region>/<patient>_OutReg/. Extensions retenues : .nii, .nii.gz, .nrrd, .nrrd.gz. Deux filtres : tout nom contenant MASK est ignoré, et si isSegmentInput est faux, tout nom contenant _<prediction_ID>_ est ignoré aussi, c'est la sortie d'une exécution précédente, et la re-segmenter produirait un masque vide.

Piège · Legacy uniquement

Le widget, lui, compte les fichiers avec une liste d'extensions différente (.gipl inclus) et d'autres exceptions ["Seg","seg","Pred"] (AMASSS.py:637-641, AMASSS.py:1677) : le compteur « Number of scans to process » et ce que la CLI traite réellement peuvent diverger.

Legacy (3c67957) ; absent de VISOR : le serveur a une seule fonction de découverte (SADT-VISOR sadt_amasss/pipeline.py:88-132), et le panneau Slicer n'a aucun compteur propre à AMASSS.

3.2 Conversion

PrepareScanForNnunet() (AMASSS_CLI.py:555) copie chaque scan dans un unique dossier <temp>/nnunet_input/ sous le nom p_<NNN>_0000.nii.gz (NNN = indice à trois chiffres dans l'ordre de découverte, compté à partir de 001 : enumerate(..., start=1), AMASSS_CLI.py:685, 848 ; le portage VISOR compte à partir de 000). Un .nii.gz est copié tel quel ; tout le reste est relu et réécrit par SimpleITK. Ce n'est pas cosmétique : la version précédente faisait un shutil.copy d'un NRRD vers un nom .nii.gz, et le lecteur de nnU-Net choisit son format d'après l'extension, si bien que NRRD, le format par défaut de Slicer, était en pratique cassé. Le type de voxel est laissé intact, puisque nnU-Net convertit lui-même en float32.

3.3 Ce qu'AMASSS ne fait plus

Aucune normalisation d'intensité, aucun fenêtrage, aucun rééchantillonnage n'est écrit dans ce dépôt. CorrectHisto() (AMASSS_CLI.py:269) existe encore, avec un corps vidé : elle lit l'image, la convertit en float32 et la renvoie, sans percentiles, sans écrêtage, sans écriture, malgré sa signature (min_porcent, max_porcent, i_min, i_max). Elle n'est appelée nulle part : code mort.

Tout le prétraitement effectif est celui de nnU-Net, décrit par le plans.json de chaque modèle (§4.2), dans cet ordre : recadrage sur la région non nulle, CTNormalization (écrêtage aux percentiles 0.5 % / 99.5 % des intensités de l'avant-plan du jeu d'entraînement, puis centrage-réduction par la moyenne et l'écart type de ce même jeu), puis rééchantillonnage à l'espacement cible (nnU-Net lui-même, nnunetv2/preprocessing/preprocessors/default_preprocessor.py:65, 82, 88, dont le commentaire dit que la normalisation doit précéder le rééchantillonnage ; preprocessing/normalization/default_normalization_schemes.py:58-72 ; nnU-Net 2.8.1, lu dans le venv de l'outil VISOR : la bibliothèque n'est pas dans ce dépôt). Les valeurs propres à chaque modèle vivent dans le plans.json du bundle, pas dans le dépôt.

4. Les modèles

Explication en langage courant et maths : page de l'atlas.

4.1 Le bundle et sa découverte

FindModelFolder() (AMASSS_CLI.py:87) cherche, pour chaque code de structure :

<modelDirectory>/<CODE>/**/<Dataset...>__nnUNetPlans__3d_fullres/fold_0/checkpoint_final.pth

Un candidat n'est accepté qu'une fois le checkpoint fold_0 confirmé présent ; sinon la structure est déclarée indisponible et l'exécution continue avec les autres. La découverte a lieu une fois pour toute l'exécution.

Téléchargement : le bouton Download latest models télécharge MODEL_LINK, l'archive AMASSS_Models.zip (environ 2 GB), une seule fois, dans <Documents>/<Slicer>Downloads/AMASSS/Models, et renseigne le dossier des modèles (AMASSS.py:240-243, 681-695). Le commentaire du code note que l'ancien lien pointait vers la page web de la release et n'ouvrait qu'un onglet de navigateur. C'est la même archive qu'AREG (AREG_Method/CBCT.py:120, 619), VFACE (VFACE.py:988) et MRI2CBCT (MRI2CBCT_core/requirements.py:33) téléchargent automatiquement. ALI passe encore par un dépôt personnel, lucanchling/AMASSS_CBCT v1.0.2 (AMASSS_Models.zip + Masks_Models.zip, ALI_Method/CBCT.py:93-94, l'URL étant AMASSS_CBCT_UPSTREAM, ADT/ADTLib/model_registry.py:77). Le README pointe encore vers ALL_NEW_MODELS.zip et une ligne commentée vers ALL_MODELS.zip : des reliques de l'époque monai, ces archives contenaient des .pth bruts.

4.2 Ce que contient réellement le bundle

Examiné sur le bundle décompressé (AMASSS_Models.zip, hors du dépôt) : neuf dossiers, un par code, chacun contenant Dataset001_myseg/nnUNetTrainer__nnUNetPlans__3d_fullres/ avec dataset.json, plans.json et fold_0/checkpoint_final.pth. Un seul fold.

Deux familles, distinguées par leur plans.json : full-FOV (MAND, MAX, CB, CV, UAW, SKIN) à 0.4 mm isotrope, patch 128³, numTraining = 76 ; et masques (CBMASK, MANDMASK, MAXMASK) à 0.3 mm isotrope, patch 112 × 160 × 128, numTraining = 50.

Architecture, identique dans les deux familles (champ architecture du plans.json) :

dynamic_network_architectures.architectures.unet.PlainConvUNet
n_stages = 6            features_per_stage = [32, 64, 128, 256, 320, 320]
kernel_sizes = 6 x [3,3,3]          n_conv_per_stage = [2,2,2,2,2,2]
n_conv_per_stage_decoder = [2,2,2,2,2]
norm_op = InstanceNorm3d (eps 1e-5, affine)   conv_bias = True
Divergence code / papier (vraie aussi dans VISOR)

Aussi vrai dans VISOR : le portage charge des checkpoints nnU-Net v2 (checkpoint_final.pth, fold 0, *__nnUNetPlans__3d_fullres: SADT-VISOR sadt_amasss/nnunet_runner.py:33-34, 208-212), et ses dépendances ne contiennent aucun MONAI (tools/AMASSS/pyproject.toml:11-23).

Ce n'est pas un monai.networks.nets.UNet : ni channels, ni strides, ni num_res_units n'apparaissent nulle part. PlainConvUNet est le U-Net convolutif que nnU-Net configure lui-même, sans blocs résiduels ; les strides viennent du plan ([1,1,1] puis cinq × [2,2,2] pour full-FOV, dernier étage [1,2,2] pour les masques, à cause de l'anisotropie du patch). batch_size = 2, use_mask_for_norm = [false] partout. L'article PLOS ONE de 2022 décrit un modèle UNETR MONAI avec un recadrage 128³ (encodeur transformer + décodeur convolutif) ; le code qui tourne aujourd'hui est un PlainConvUNet nnU-Net v2 purement convolutif. Voir §10.

Chaque modèle est binaire. Les fichiers dataset.json déclarent seulement {background: 0, <one structure>: 1}, et pour les six modèles full-FOV le nom d'étiquette est resté "Skin" par copier-coller, même pour MAND ou CB. Ce nom n'est jamais lu : la sortie est binarisée par (arr > 0) (AMASSS_CLI.py:584) et c'est la CLI qui attribue la valeur finale.

4.4 Inférence

Aucun sliding_window_inference n'est écrit ici : nnU-Net gère lui-même la fenêtre glissante, à partir du patch_size de son plan. Le seul paramètre que choisit la CLI est le pas.

BuildPredictor() (AMASSS_CLI.py:112) fixe tile_step_size = 0.5 (le pas vaut au plus un demi-patch, donc au moins 50 % de recouvrement : nnU-Net le raccourcit pour que le dernier patch finisse au bord de l'image, nnunetv2/inference/sliding_window_prediction.py:30-54 ; codé en dur dans la signature), use_gaussian = True (pondération gaussienne des patchs, étalée sur un huitième du patch, logits pondérés divisés par la somme des poids : nnunetv2/inference/predict_from_raw_data.py:626-653), use_mirroring = False (l'équivalent de --disable_tta : pas d'augmentation miroir au moment du test), device issu de ResolveDevice(), et verbose / verbose_preprocessing / allow_tqdm mis à False. L'argument nommé perform_everything_on_device (renommé depuis perform_everything_on_gpu en cours de série 2.x) est choisi par introspection de la signature.

PredictFolder() (AMASSS_CLI.py:204) charge le checkpoint (initialize_from_trained_model_folder(..., use_folds=(0,), checkpoint_name="checkpoint_final.pth")) puis appelle predict_from_files_sequential sur le dossier entier. Trois choix structurants, tous commentés dans le code :

  1. Chemin de modèle explicite, pas de nnUNet_results. os.environ est global au processus : deux exécutions AMASSS simultanées s'écraseraient mutuellement leur chemin de modèle.
  2. Boucle par structure, pas par scan : tous les scans dans un seul dossier d'entrée, une prédiction de dossier par structure. Le checkpoint est chargé S fois au lieu de N × S.
  3. Version séquentielle : predict_from_files utilise spawn, et sous Slicer un worker réimporterait ce module et paierait de nouveau tout le coût d'import de torch ; il aurait aussi besoin de son propre contexte CUDA pour le rééchantillonnage GPU.

La progression est toujours comptée en pas scan × structure (AMASSS_CLI.py:674-677) pour ne pas changer l'échelle attendue par les widgets, même si le travail est regroupé par structure : la barre avance par pas de la taille de scan_count.

Une structure qui échoue est enregistrée dans failed_structures et l'exécution continue ; elle n'échoue que si toutes échouent.

5. Le cœur algorithmique (non appris)

Explication en langage courant et maths : page de l'atlas.

5.1 Rééchantillonnage GPU

EnableGpuResampling() (AMASSS_CLI.py:148) est la principale optimisation de la CLI. D'après le commentaire du code, le rééchantillonnage scipy monocœur coûte environ sept fois autant que le réseau.

Le mécanisme : nnU-Net résout ses fonctions de rééchantillonnage par nom, par recursive_find_resampling_fn_by_name, à partir du dictionnaire de configuration. Réécrire les deux noms redirige les deux bouts, sans monkeypatch :

configuration["resampling_fn_data"]          = "resample_torch_fornnunet"
configuration["resampling_fn_probabilities"] = "resample_torch_fornnunet"
configuration[f"{key}_kwargs"] = {"is_seg": False, "device": torch.device(device), "mode": "linear"}

Trois garde-fous : la substitution n'a lieu que si les deux clés valent exactement resample_data_or_seg_to_shape (un plan qui demande autre chose est laissé intact) ; PlansManager distribue une deepcopy, donc modifier le dictionnaire n'affecte ni les plans partagés ni une exécution concurrente ; les deux propriétés sont @property @lru_cache, d'où le getattr(manager_class, key).fget.cache_clear(), sans lequel une valeur lue avant le basculement survivrait. Différence numérique acceptée délibérément : les données passent de l'interpolation d'ordre 3 à l'ordre 1 (torch n'a pas d'interpolation cubique 3D) ; les probabilités étaient déjà d'ordre 1.

Repli automatique sur torch.cuda.OutOfMemoryError → empty_cache() puis rejeu de la structure avec le rééchantillonneur scipy (AMASSS_CLI.py:240-251) : la version cloud a un argument explicite gpu_resampling, ce qui est impossible ici puisque la liste de paramètres est figée par le XML et ses appelants.

5.2 Assemblage et écriture

AssembleScanOutputs() (AMASSS_CLI.py:573), par scan : lit p_<NNN>.nii.gz dans chaque dossier pred_<STRUCT> (absent → avertissement, structure ignorée), binarise avec (arr > 0), puis

  • SEPARATE si demandé ou s'il n'y a qu'une structure (un « fusionné » d'une seule structure est simplement cette structure) ;
  • MERGE si demandé et ≥ 2 structures : np.where(mask == 1, label, merged) dans l'ordre de merging_order = ["SKIN","CV","UAW","CB","MAX","MAND","CAN","RC","CBMASK","MANDMASK","MAXMASK"]. C'est un ordre de priorité : la dernière structure écrite écrase les précédentes sur les voxels communs. "CAN" n'existe dans aucun dictionnaire (le code du canal est MCAN), une entrée morte. "RC" est un code connu sans modèle et sans entrée dans LABELS["LARGE"] : .get(struct, 1) (AMASSS_CLI.py:612) ramènerait un code sans étiquette à l'étiquette 1, celle de la mandibule. Ni l'un ni l'autre ne peut correspondre à une prédiction en pratique, puisqu'aucun n'a de modèle.

SaveSeg() (AMASSS_CLI.py:522) convertit en int16, recopie explicitement l'espacement, la direction et l'origine du scan de référence, puis passe par MatchReferenceGeometry() (AMASSS_CLI.py:500), qui ne rééchantillonne (plus proche voisin) que si la géométrie diffère : sans effet dans le cas normal. La version précédente écrivait un volume temporaire et le relisait pour forcer la géométrie : deux allers-retours gzip d'un CBCT complet par structure, pour rien.

5.3 Post-traitement : ce qui n'est plus là

Aucun remplissage de trous, aucune sélection de composante connexe, aucune morphologie n'est appliquée. Deux fonctions subsistent, appelées nulle part :

  • CleanArray() (AMASSS_CLI.py:420) : dilatation binaire de rayon r, BinaryFillhole, érosion de rayon r, puis cc3d.connected_components et conservation de la plus grande composante ;
  • CropSkin() (AMASSS_CLI.py:487) : remplissage, érosion d'épaisseur thickness, différence des deux pour ne garder que la coque, puis la plus grande composante.

Dans la version monai, CleanArray(sep_arr, 2) était appliqué à toutes les structures sauf CV et RC, et CropSkin(sep_arr, 5) à la peau. Le portage nnU-Net a supprimé ces appels : le nettoyage repose désormais entièrement sur le post-traitement interne de nnU-Net (le postprocessing.pkl du bundle, s'il existe). cc3d est encore importé pour ces deux fonctions mortes, de même que Write() (AMASSS_CLI.py:285).

5.4 Génération des surfaces VTK

SavePredToVTK() (AMASSS_CLI.py:303), appelée depuis SaveSeg quand genVtk est vrai. Par étiquette : écrit un NRRD temporaire <temp>/temp.nrrd du masque binaire, vtkNrrdReader → vtkDiscreteMarchingCubes avec GenerateValues(1, 1, 1) (un seul contour de valeur 1, d'où le passage par un masque binaire plutôt que par la carte d'étiquettes) → vtkSmoothPolyDataFilter pendant vtk_smooth itérations (5 par défaut : le widget a un curseur, AMASSS.py:337, 858-863, 978 ; AREG, VFACE et MRI2CBCT passent 5, AREG_Method/CBCT.py:346, createlistprocess.py:463, plan.py:91) → vtkUnsignedCharArray "Colors", une couleur constante par cellule tirée de LABEL_COLORS.

Deux modes, choisis sur le suffixe _MERGED du nom de fichier : en mode fusionné, elle boucle sur np.unique(arr) et concatène avec vtkAppendPolyData en un seul .vtk ; en mode séparé, struct = base.split('_')[-1], le code de structure est ré-extrait du nom de fichier pour retrouver la couleur.

Les maillages sont écrits dans le système de coordonnées de l'image, sans inversion LPS/RAS : ce sont des vtkPolyData dérivés directement des indices du NRRD.

Bug confirmé · Legacy uniquement

Le dossier temporaire est vidé et recréé au démarrage et à la fin (AMASSS_CLI.py:808, AMASSS_CLI.py:887). nnunet_input est supprimé dès que l'inférence est finie, avant l'assemblage (AMASSS_CLI.py:872) : sinon un lot garderait une copie NIfTI complète de chaque CBCT jusqu'à la toute fin ; les prédictions d'un scan sont supprimées au fil de l'assemblage (AMASSS_CLI.py:651-656). temp_fold est inconditionnellement rmtree'd au démarrage (AMASSS_CLI.py:808), et le widget, AREG et VFACE passent tous <Documents>/Slicer_temp_AMASSS (AMASSS.py:982-992) : deux exécutions simultanées effacent le dossier de travail l'une de l'autre. Détails au §9.

Legacy (3c67957) ; absent de VISOR : le dossier de travail est <output_dir>/.amasss_work, propre à l'exécution et supprimé dans un bloc finally (SADT-VISOR sadt_amasss/pipeline.py:330-331, 362-366). VISOR fait aussi l'inverse de la seconde moitié de cet encadré : nnunet_input et chaque prédiction sont conservés jusqu'à cette suppression finale (voir Constats dans VISOR).

Côté widget, OnEndProcess() (AMASSS.py:1110) charge les fichiers .vtk du dossier de sortie dans la scène (opacité 0.1 pour la peau, 0.2 pour la mandibule/le maxillaire si un canal radiculaire est présent). Ce chargement n'a lieu que si vtk_output_folder n'est pas nul, donc seulement pour une entrée « fichier unique » enregistrée dans son dossier d'origine avec la case surface cochée (AMASSS.py:963-975). LOADED_VTK_FILES est une globale de module : les nœuds restent référencés pendant toute la session, même après la fermeture de la scène.

8. Environnement

Tout tourne dans le Python de Slicer. L'installation est déclenchée par le bouton Predict (AMASSS.py:869-890), pas à l'ouverture du module, et passe par une boîte de confirmation.

PaquetVersion figéeRaison lisible dans le code
torch, torchvision, torchaudionon figéele build CUDA est lu sur le GPU par torch_install_arguments() (ADTLib) ; une version figée avait signalé le build cu128 qu'exige une RTX série 50 (AMASSS.py:878-882)
nnunetv2>=2.8.0backend d'inférence
numpy1.26.4 (NUMPY_PINNED_VERSION)d'après le commentaire, torch 2.2.0 est compilé contre numpy 1.x ; numpy ≥ 2 casse tous les imports de torch avec _ARRAY_API not found
pydicom3.0.2ne pas rétrograder : pydicom 2.x casse dicomweb-client et highdicom, donc tous les modules DICOM de Slicer

itk, blosc2, einops, nibabelnon figéedépendances de nnU-Net

fix_numpy_version() (AMASSS.py:61) est rappelée après toutes les installations : pip résout chaque installation indépendamment, et nnunetv2 (qui exige numpy>=1.24) peut faire venir numpy 2.x en chemin.

check_lib_installed() ne rejette la famille torch que si deux de ses membres déclarent des builds +cuXXX différents, sur toutes les plateformes (AMASSS.py:80-113) ; le build CUDA à installer est lu sur le GPU par torch_install_arguments() sous Windows et ailleurs (AMASSS.py:170, 191).

Pas de WSL, pas de conda : contrairement aux modules IOS (FlexReg, AREG_IOS, ALI_IOS), AMASSS n'utilise aucun environnement externe.

9. Pièges et points fragiles

Bug confirmé : FOV réduit cassé · Legacy uniquement

highDefinition / « small FOV » ne fait plus rien de ce qu'il prétend. La case smallFOVCheckBox fait passer la liste de structures proposée à GROUPS_HD_SEG (AMASSS.py:252, AMASSS.py:769) : mandibule, maxillaire, dents, canal radiculaire, canal mandibulaire, dont trois n'ont aucun modèle. Le drapeau param["highDefinition"] n'est pas déclaré dans le XML, slicer.cli.run l'abandonne, et la CLI n'a de toute façon plus aucun chemin de code SMALL (l'espacement [0.16, 0.16, 0.32] et MODELS_GROUP["SMALL"] ont disparu avec le portage). Cocher la case ne change que la liste des cases à cocher.

Legacy (3c67957) ; absent de VISOR : il n'y a pas d'option small-FOV dans run() (SADT-VISOR sadt_amasss/__init__.py:20-42) ni dans le panneau Slicer (AutomatedDentalToolsRemote AMASSSRemote/AMASSSRemote.py:63-98).

Bug confirmé : entrée DICOM ignorée · Legacy uniquement

isDCMInput est lu puis ignoré (AMASSS_CLI.py:955, jamais utilisé ensuite) : le widget installe dicom2nifti (AMASSS.py:883) mais aucune conversion DICOM → NIfTI n'existe nulle part dans la CLI, alors que l'interface propose « DICOM Files » comme type d'entrée. Une entrée DICOM ne produit rien : aucun fichier n'a d'extension reconnue.

Legacy (3c67957) ; absent de VISOR en tant qu'option : run() n'a aucun argument DICOM (SADT-VISOR sadt_amasss/__init__.py:20-42) et discover_scans n'accepte que des fichiers de volume (pipeline.py:88-132). L'absence de toute conversion DICOM reste vraie.

Piège · Legacy uniquement

RC coché par défaut sans modèle disponible : DEFAULT_SELECT inclut « Root canal » (AMASSS.py:258), et le bundle publié n'a aucun dossier RC. Échec silencieux.

Legacy (3c67957) ; absent de VISOR : RC n'est pas dans le catalogue des structures et les structures par défaut sont MAND, MAX, CB, CV, UAW (SADT-VISOR sadt_amasss/catalog.py:37-41).

10. Littérature

AMASSS a été publié une fois :

Gillot M., Baquero B., Le C., Deleat-Besson R., Bianchi J., Ruellas A., …, Cevidanes L., Prieto J.C. Automatic multi-anatomical skull structure segmentation of cone-beam computed tomography scans using 3D UNETR. PLOS ONE 17(10):e0275033, 2022. doi:10.1371/journal.pone.0275033 , PMID 36223330, PMC9555672

Divergence code / papier (vraie aussi dans VISOR)

Aussi vrai dans VISOR (checkpoints nnU-Net v2, pas de MONAI : SADT-VISOR sadt_amasss/nnunet_runner.py:33-34, 208-212). Le code a divergé de l'article, complètement. L'article décrit un UNETR (encodeur transformer + décodeur convolutif, bibliothèque MONAI) : patchs 128³, feature_size=16, hidden_size=768, mlp_dim=3072, 12 têtes d'attention, 5 % de dropout, entraîné sur 618 CBCT de 7 centres pour cinq structures, avec un rééchantillonnage isotrope à 0.4 mm et un ajustement du contraste par histogramme cumulé aux percentiles 1 % / 99 %. Scores Dice rapportés : peau 0.971, mandibule 0.962, maxillaire 0.853, base du crâne 0.788, vertèbre cervicale 0.760.

C'est ce que faisait la version historique de la CLI, Create_UNETR(...), sliding_window_inference(input_img, [128,128,128], nbr_GPU_worker, net, overlap=precision/100, sw_device=DEVICE, ...), CorrectHisto + ScaleIntensityd(0,1) + Spacingd(pixdim=[0.4,0.4,0.4]) ou [0.16,0.16,0.32] en haute définition, puis CleanArray/CropSkin, lisible dans le dépôt jusqu'au commit 61bbb15 « ENH: AMASSS with nnunet. » L'espacement haute définition et le precision de l'interface étaient des paramètres du code, pas de l'article ; un Create_SwinUNETR(feature_size=48) y coexistait, commenté.

Rien de tout cela ne subsiste dans le code actuel : nnU-Net v2, PlainConvUNet, un réseau binaire par structure. L'espacement de 0.4 mm survit, mais vient du plans.json des poids ; la voie haute définition et le post-traitement morphologique ont disparu. Aucune publication ne décrit la version nnU-Net d'AMASSS : citer l'article PLOS ONE pour décrire le module tel qu'il tourne aujourd'hui revient à décrire une architecture qui n'est plus exécutée.
