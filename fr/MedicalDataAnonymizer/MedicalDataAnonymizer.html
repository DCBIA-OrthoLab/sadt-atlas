MedicalDataAnonymizer

Détection et remplacement d'entités sensibles dans des documents texte (DOCX, TXT, PDF, CSV, XML, ODT) via Microsoft Presidio ; le module ne touche jamais une image médicale : ce n'est pas un anonymiseur DICOM. Cette page explique le pipeline pas à pas ; les détails du code sont sur la page de code.

non publié pas de CLI (widget Slicer) thread de l'interface, pas de conda Bibliographie VISOR : copie locale uniquement Code (développeurs) Guide

Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). VISOR n'a aucun outil serveur pour lui : son extension cliente embarque une ancienne copie qui tourne dans Slicer et n'envoie rien, et ce n'est pas la dé-identification des fichiers que VISOR téléverse, qui est spécifiée et non construite (La dé-identification dans VISOR). Voir la page VISOR de ce module.

Vue d'ensemble : ce qui entre, ce qui sort

MedicalDataAnonymizer
Entréeun dossier de documents texte (Word, texte, PDF, CSV, XML, ODT), parcouru récursivement
DétectionMicrosoft Presidio : un modèle statistique anglais pour les noms, les lieux et les dates, et des motifs avec sommes de contrôle pour les numéros, les e-mails et les identifiants du même genre
Remplacementune des quatre méthodes : étiquette, suppression, hash ou astérisques
Sortieun document _anonymized reconstruit par entrée, tous dans un seul dossier à plat, plus file_mappings.csv

Le module n'anonymise que du texte. C'est une première passe sur du texte libre en anglais, pas un moyen de déclarer un jeu de données dé-identifié (section 7).

0. Ce que le module n'est pas

Le nom suggère un anonymiseur DICOM. Ce n'est rien de tel, et il en va de même pour la copie dans VISOR. Chercher “DICOM” ou “deface” dans tout le module ne donne rien, donc :

  • aucun tag DICOM n'est lu ni modifié : ni le nom ou l'identifiant du patient, ni les dates, ni l'établissement, ni les identifiants uniques, ni les tags privés ;
  • aucun defacing n'est jamais appliqué : le visage que l'on peut reconstruire à partir d'un CBCT ou d'un scanner n'est pas touché, et il n'y a aucun outil de defacing dans toute l'extension ;
  • les formats pris en charge ne couvrent aucun format d'image ou de maillage, ni un fichier de landmarks.

Quiconque décide si des données peuvent être partagées devrait d'abord lire la section 7.

Dans le codeLa recherche qui le prouve, et les formats pris en charge avec leur ligne

1. Place dans le pipeline

Un outil isolé sans tâche en ligne de commande : rien ne l'appelle, il n'appelle rien. Toute la logique est dans le widget, donc sur le thread principal de Slicer, si bien que l'interface se fige pendant le traitement et que seule la barre de progression est rafraîchie.

Dans le codeLe fichier unique, la classe de logique vide et le thread de l'interface

2. Entrées : extraction du texte, format par format

Le dossier est parcouru récursivement, en ignorant les fichiers de verrou Word. Chaque fichier est réduit à une chaîne de caractères avant l'analyse, et la sortie est reconstruite à partir de cette chaîne. Ce qui n'a pas été extrait n'est ni analysé ni reporté : cela disparaît.

  • Word : les paragraphes. Les tableaux, en-têtes, pieds de page, notes de bas de page, zones de texte, commentaires et métadonnées sont perdus.
  • Texte : lu tel quel.
  • PDF : la couche de texte ; un PDF scanné donne un texte vide.
  • CSV : chaque ligne est aplatie en une seule ligne de texte, donc la structure en colonnes est perdue.
  • XML : le contenu texte seulement ; les balises et les attributs ne sont jamais lus.
  • ODT : les paragraphes ; les tableaux, styles et métadonnées sont perdus.

Un contenu sensible dans une partie qui n'a pas été extraite n'est pas détecté, mais n'arrive pas non plus dans la sortie : il n'y a pas de fuite, mais une perte silencieuse de données. Les métadonnées de fichier, comme l'auteur d'un document Word, disparaissent aussi puisque les fichiers sont recréés.

Dans le codeLe tableau des formats avec les appels de bibliothèque et ce que chacun perd

3. Le moteur de détection

Aucun modèle n'est embarqué ; le module installe le modèle anglais de spaCy et construit les moteurs Presidio avec leurs réglages par défaut à chaque clic. Deux familles de recognizers travaillent côte à côte.

La famille statistique trouve les noms, les lieux et les dates. La famille à base de règles trouve les numéros de téléphone, les e-mails, les numéros de sécurité sociale américains, de permis de conduire et de compte bancaire, les licences médicales, les cartes de crédit, les adresses IP et les URL, à partir de motifs, de sommes de contrôle et de mots de contexte.

La langue est verrouillée sur l'anglais : un dossier de notes en français passe par un modèle anglais, avec la détection plus faible que l'on peut attendre, et le module n'en dit rien. Un détecteur de langue est installé mais jamais utilisé (détails).

Dans le codeLes deux appels de moteur, le téléchargement du modèle et la langue fixe

4. Entités et méthodes de remplacement

Douze types d'entités peuvent être cochés et sept le sont par défaut : noms, numéros de téléphone, adresses e-mail, dates et heures, lieux, numéros de sécurité sociale et numéros de licence médicale. Les cinq autres (permis de conduire, carte de crédit, compte bancaire, adresse IP, URL) sont désactivés. Les noms, dates et lieux viennent du modèle statistique (prédit) ; les autres viennent de règles (calculé).

Le hash est un simple SHA-256 du texte détecté. Dans Presidio 2.2.355, le même nom donne toujours le même condensat, ce qui assure la cohérence, mais sans sel ni clé un hash sur un espace aussi petit que les noms, les dates de naissance ou les numéros de sécurité sociale peut être inversé en essayant tous les candidats. À traiter comme un pseudonyme public, pas comme une protection. Le module n'épingle pas la version de Presidio, et 2.2.366 sale chaque span haché avec 32 octets aléatoires, si bien que là les condensats d'un même nom diffèrent d'une occurrence à l'autre.

Dans le codeLe tableau des entités avec les valeurs par défaut et les configurations d'opérateurs

5. Sorties et table de correspondance

Tout est écrit à plat dans le dossier de sortie : les sous-dossiers ne sont pas reproduits, et deux fichiers de même nom dans des sous-dossiers différents font que le second écrase le premier. Les fichiers Word, texte et PDF sont reconstruits dans leur propre format (le PDF en un seul bloc sans pagination), un fichier ODT devient un fichier texte, et un fichier XML devient du texte brut sous un nom en .xml.

La table de correspondance file_mappings.csv liste le nom d'origine, le nom produit et un UUID par fichier. Ce n'est pas une table de ré-identification : elle ne contient aucun lien entre un nom détecté et son remplacement, et l'UUID est généré puis n'est utilisé nulle part. Elle se trouve à côté des documents anonymisés, donc partager le dossier de sortie partage la liste des noms de fichiers d'origine.

7. Limites : ce qui N'EST PAS supprimé

La section la plus utile pour décider si un jeu de données peut être partagé.

  1. Toutes les images : rien dans un fichier image ou dans son en-tête n'est lu ni modifié.
  2. Noms de fichiers et de dossiers : le nom d'un patient dans un nom de fichier survit dans le nom de sortie et dans la table de correspondance, et la hiérarchie des dossiers est aplatie.
  3. Identifiants hospitaliers : les numéros de dossier, d'accession et de lit n'ont aucun recognizer.
  4. Tout ce qui n'est pas américain : seuls les numéros américains sont recherchés, pas un NIR français, un numéro NHS ou un passeport.
  5. Identifiants indirects : âges supérieurs à 89 ans, dates rares, professions ; les dates sont remplacées en bloc ou pas du tout.
  6. La langue : la détection s'effondre sur du texte non anglais, sans avertissement.
  7. Le seuil de 0,5 écarte les détections les moins sûres, mais lesquelles dépend des recognizers : les détections de noms, de lieux et de dates de spaCy reçoivent toutes le même score fixe (0,85 par défaut dans Presidio 2.2.355 et 2.2.366), donc un seuil de 0,5 ne sépare pas les noms rares des noms courants ; il agit surtout sur les recognizers à base de motifs.
  8. Le contenu qui n'a pas été extrait : tableaux, attributs, pages scannées, en-têtes.
  9. Échec silencieux, le constat le plus grave. Si l'analyse lève une erreur, quelle qu'elle soit, le module écrit un fichier _anonymized qui contient le texte d'origine inchangé, affiche “Complete!”, et laisse une ligne rouge dans la console Python. Rien ne compte les entités trouvées ni ne vérifie après coup (détails).

En pratique, la sortie est une première passe sur du texte libre en anglais, à relire, et elle demande de renommer les fichiers, un anonymiseur DICOM dédié pour les images, et du defacing si un volume couvre le visage.

8. Environnement

Tout tourne dans le Python de Slicer, installé par un seul bouton sans confirmation et sans versions épinglées, suivi du téléchargement du modèle spaCy anglais et d'une demande de redémarrage de Slicer. Pas de GPU, pas de conda, pas de tâche en ligne de commande ; le chargement des moteurs prend quelques secondes sur le thread de l'interface à chaque exécution. Les avertissements sont désactivés pour tout Slicer dès que le module se charge.

9. Problèmes connus

  • L'échec silencieux qui renvoie le texte d'origine (détails).
  • Le dossier de sortie à plat écrase sans message les fichiers de même nom (tous les pièges).
  • Les fichiers CSV sont restructurés, le XML se dégrade en texte brut et l'ODT est renommé en texte (tous les pièges).
  • L'UUID de la table de correspondance est généré et jamais appliqué (détails).
  • Tout tourne sur le thread de l'interface, si bien que Slicer paraît figé sur un gros dossier (tous les pièges).
  • Le README parle de conformité HIPAA et d'analyse par IA là où le code est un appel Presidio par défaut sur du texte anglais (tous les pièges).
  • Le module n'a aucun test et rien d'appelable par script (tous les pièges).

10. Littérature et références

Aucun article ne couvre ce module ; il n'y a pas non plus d'évaluation (rappel, précision) dans le dépôt, sur aucun corpus.

Les briques utilisées sont documentées :

  • Microsoft Presidio : le moteur de détection et d'anonymisation, avec la liste exacte de ses recognizers et opérateurs prédéfinis (replace, redact, hash, mask, encrypt, ce dernier, réversible avec une clé, n'est pas proposé par le module).
  • spaCy en_core_web_lg : le modèle de NER anglais utilisé par défaut.
  • HIPAA Safe Harbor, 45 CFR §164.514(b)(2) : les 18 catégories d'identifiants à supprimer. Utile comme grille de lecture pour §7 : les noms de fichiers, les identifiants de dossier médical et les identifiants d'image y figurent, et ce module ne les traite pas.

Bibliographie complète : SOURCES.html, recherche faite, résultat négatif sur le module lui-même. Le dossier contient la seule évaluation publiée de Presidio sur du texte clinique non structuré, et des liens vers les campagnes de dé-identification de texte i2b2/n2c2, qui ne décrivent pas ce code mais en fournissent la grille de lecture.
