MedicalDataAnonymizer, legacy : le code

Pour les développeurs : ce que fait le module Slicer legacy MedicalDataAnonymizer dans le code (SlicerAutomatedDentalTools à 3c67957), avec des références file:line, des blocs de code, les entités, l'environnement et l'échec silencieux confirmé. L'explication lisible du même pipeline se trouve sur la page de l'atlas.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). VISOR n'a aucun outil serveur pour lui. L'extension cliente VISOR embarque une ancienne copie du module qui tourne dans Slicer et n'envoie rien, et ce n'est pas la dé-identification des fichiers que VISOR téléverse (celle-là est spécifiée et non construite, voir La dé-identification dans VISOR). Détails sur la page VISOR de ce module.

Piège de vocabulaire · aussi vrai dans VISOR

Aussi vrai dans VISOR. La copie cliente ne traite que du texte (AutomatedDentalToolsRemote README.md:215), et la dé-identification d'images que le nom pourrait suggérer n'existe pas dans le client (README.md:31-34).

Le nom suggère un anonymiseur DICOM. Ce n'est rien de tel : MedicalDataAnonymizer dé-identifie des documents texte via Presidio + spaCy. Aucun tag DICOM (PatientName, PatientID, UID…) n'est lu ni modifié, et aucun defacing n'est jamais appliqué à une image : l'extension dans son ensemble ne contient aucun outil de defacing.

0. Ce que le module n'est pas

Explication en langage courant et maths : page de l'atlas.

Le nom suggère un anonymiseur DICOM. Ce n'est rien de tel, et on peut le vérifier avec une seule commande :

$ grep -rin "dicom\|pydicom\|deface" Medical_Data_Anonymizer_Module/
(no result)
$ grep -rlni "deface" --include="*.py" --include="*.md" .
(no result anywhere in the repository)

Conséquences directes :

  • aucun tag DICOM n'est jamais effacé ni remplacé : ni PatientName (0010,0010), ni PatientID (0010,0020), ni PatientBirthDate, ni StudyDate, ni InstitutionName, ni les UID, ni les tags privés, ni BurnedInAnnotation ;
  • aucun defacing : le visage reconstructible dans un CBCT ou un scanner n'est jamais altéré, par aucune méthode (ni masque facial, ni flou, ni retrait de surface). Il n'y a aucun outil de defacing dans toute l'extension ;
  • les formats pris en charge (.docx, .txt, .pdf, .csv, .xml, .odt, Medical_Data_Anonymizer_Module.py:514) ne couvrent ni .dcm, ni .nii.gz, ni .nrrd, ni .vtk, ni un .json de landmarks.

Un opérateur qui décide si des données peuvent être partagées devrait lire directement §7.

1. Place dans le pipeline

Explication en langage courant et maths : page de l'atlas.

Un outil isolé, sans CLI. Rien ne l'appelle, et il n'appelle rien d'autre dans le dépôt. Tout vit dans un seul fichier de 774 lignes, dont ~350 de feuilles de style Qt : Medical_Data_Anonymizer_Module.py.

Medical_Data_Anonymizer_ModuleLogic et …Test sont des classes vides (pass) : toute la logique vit dans le widget, donc sur le thread principal de Slicer, l'interface se fige pendant le traitement, seul slicer.app.processEvents() rafraîchit la barre de progression.

2. Entrées : extraction du texte, format par format

Explication en langage courant et maths : page de l'atlas.

Parcours récursif du dossier d'entrée (os.walk) ; les fichiers commençant par ~$ (fichiers de verrou Word) sont ignorés. Chaque fichier est réduit à une seule chaîne de caractères avant l'analyse :

FormatExtractionCe qui se perd en route
.docxpython-docx, "\n".join(p.text for p in doc.paragraphs)tableaux, en-têtes/pieds de page, notes de bas de page, zones de texte, commentaires, métadonnées du fichier
.txtlecture UTF-8 brute–
.pdfpdfplumber, page.extract_text() ; en cas d'exception, une seconde tentative via extract_tables()images, PDF scannés (pas d'OCR) → texte vide
.csvcsv.reader, chaque ligne aplatie par " ".join(row)la structure en colonnes
.xmlElementTree + extract_text_from_xml() récursive (texte + tail)balises et attributs : les valeurs d'attributs ne sont jamais lues
.odtodfpy, nœuds de texte de text.Ptableaux, styles, métadonnées

La perte n'est pas qu'une question de fidélité : les documents de sortie sont reconstruits à partir de cette chaîne. Ce qui n'a pas été extrait n'est pas anonymisé, mais n'est pas non plus reporté : cela disparaît. À l'inverse, un contenu sensible placé dans une partie non extraite (un tableau DOCX, un attribut XML) n'est ni détecté ni reporté : pas de fuite, mais une perte silencieuse de données.

Une exception notable : rien ne lit les métadonnées d'un fichier (l'auteur d'un DOCX, le Producer d'un PDF). Elles disparaissent aussi, puisque les fichiers sont recréés de zéro.

3. Le moteur de détection

Explication en langage courant et maths : page de l'atlas.

Aucun modèle dans le dépôt, aucun poids téléchargé par le module lui-même hormis le modèle spaCy. Deux moteurs Presidio sont instanciés à chaque clic sur « Anonymize Files » (…py:499-502), avec stderr court-circuité par une classe SuppressStderr :

analyzer = AnalyzerEngine()      # default config
anonymizer = AnonymizerEngine()

AnalyzerEngine() sans argument utilise la configuration NLP par défaut de Presidio, c'est-à-dire spaCy en_core_web_lg : le seul modèle que install_dependencies() télécharge (spacy.cli.download, …py:432).

Deux familles de recognizers se combinent : le NER statistique de spaCy (PERSON, LOCATION, DATE_TIME) et les recognizers à base de motifs et de sommes de contrôle (PHONE_NUMBER, EMAIL_ADDRESS, US_SSN, MEDICAL_LICENSE, US_DRIVER_LICENSE, CREDIT_CARD, US_BANK_NUMBER, IP_ADDRESS, URL).

Piège · aussi vrai dans VISOR

Aussi vrai dans VISOR (copie cliente). Même code dans la copie livrée : language='en' à AutomatedDentalToolsRemote Medical_Data_Anonymizer_ModuleRemote/Medical_Data_Anonymizer_ModuleRemote.py:716 et pip_install('langdetect') à :405 (legacy à 3c67957 : :724 et :413 ; la ligne citée dans cet encadré date d'une révision antérieure).

La langue est verrouillée sur l'anglais : analyzer.analyze(..., language='en') (…py:724), malgré le commentaire « with automatic language detection » et l'installation de langdetect, qui n'est jamais importé, une dépendance morte. Un dossier de notes en français passe par un modèle anglais, avec le rappel que l'on peut attendre.

Seuil de confiance : score_threshold, curseur 0,0–1,0, par défaut 0,5. Les détections sous le seuil sont écartées sans laisser de trace ; le test dans Presidio est result.score >= score_threshold (analyzer_engine.py, __remove_low_scores, identique en 2.2.355 et 2.2.366), donc un score égal au seuil est conservé.

Quatre méthodes, dans « Advanced Options » (…py:129-132) :

MéthodeImplémentationRésultat
replace (default)operators = {} → passé comme None → opérateur par défaut de Presidio<PERSON>, <DATE_TIME>, …

hashOperatorConfig("hash")SHA-256 sans sel du texte détecté dans presidio-anonymizer 2.2.355 ; en 2.2.366, un sel aléatoire de 32 octets est ajouté par span (operators/hash.py)

À propos de hash : le README parle de « cryptographic hashes for consistent anonymization ». L'affirmation de cohérence tient avec presidio-anonymizer 2.2.355 (le même nom donne toujours le même condensat), mais il n'y a ni sel ni clé : sur un espace de valeurs aussi petit qu'un nom, une date de naissance ou un numéro de sécurité sociale, le condensat peut être ré-identifié par force brute en quelques secondes. À traiter comme un pseudonyme public, pas comme une protection. Le module n'épingle pas la version (pip_install('presidio-anonymizer'), :407), et 2.2.366 sale chaque span avec os.urandom(32) sauf si un sel est fourni, ce que le module ne fait pas : avec cette version, le même nom reçoit chaque fois un condensat différent, et l'affirmation de cohérence est fausse.

5. Sorties et table de correspondance

Explication en langage courant et maths : page de l'atlas.

Écrits à plat dans le dossier de sortie : la hiérarchie de sous-dossiers de l'entrée n'est pas reproduite.

EntréeSortieNote
x.docxx_anonymized.docxdocument reconstruit, un paragraphe par ligne, sans mise en forme
x.txtx_anonymized.txt–
x.pdfx_anonymized.pdfrégénéré par reportlab, un seul bloc Preformatted
x.csvx_anonymized.csvvoir ci-dessous
x.xmlx_anonymized.xmltexte brut sous une extension .xml : plus aucune balise, et le commentaire du code l'admet (« XML anonymization is complex »)
x.odtx_anonymized.txtchangement d'extension

Le cas du CSV est le plus destructeur : le fichier a été lu en aplatissant chaque ligne avec des espaces, puis il est réécrit avec writer.writerow(line.split()) (…py:640). Toute cellule contenant une espace est éclatée sur plusieurs colonnes, et les cellules vides disparaissent : l'alignement des colonnes n'est pas préservé. Un CSV de mesures ressort inutilisable.

La table de correspondance, file_mappings.csv, écrite dans le dossier de sortie (…py:656) :

ColonneContenu
Original File Namenom du fichier source
Anonymized File Namenom produit, ou ERROR
UUIDuuid.uuid4() tiré par fichier, ou le message de l'exception en cas d'échec

Ce n'est pas une table de ré-identification des personnes : elle ne contient aucune correspondance entre un nom détecté et son remplacement. Et l'UUID est purement décoratif, il est généré (…py:539) puis jamais utilisé : il n'apparaît ni dans le contenu ni dans le nom du fichier de sortie. Il n'existe donc aucun mécanisme stable de pseudonymisation entre documents.

Ce fichier file_mappings.csv est écrit juste à côté des documents anonymisés : partager le dossier de sortie revient à partager la liste des noms de fichiers d'origine.

7. Limites : ce qui N'EST PAS supprimé

Explication en langage courant et maths : page de l'atlas.

La section la plus utile pour décider si un jeu de données peut être partagé.

Hors périmètre par construction

  1. Toutes les images. DICOM, NIfTI, NRRD, maillages : jamais lus, jamais modifiés. Aucun tag d'en-tête n'est nettoyé, aucun visage n'est effacé (§0).
  2. Noms de fichiers et de dossiers. Dupont_Jean_2019.docx devient Dupont_Jean_2019_anonymized.docx. Le nom du patient survit intact dans le nom du fichier, et il est recopié tel quel dans file_mappings.csv. La hiérarchie d'entrée, souvent tout aussi identifiante (.../Patients/Dupont_Jean/), est aplatie, et si deux sous-dossiers contiennent chacun un fichier de même nom, le second écrase silencieusement le premier.

Angles morts de la détection

  1. Identifiants hospitaliers. Aucun recognizer pour un MRN, un numéro de dossier, un numéro d'accession, un identifiant d'étude, un numéro de lit. Ils ne figurent dans aucune des douze entités proposées, et Presidio n'en a aucun par défaut.
  2. Tout ce qui n'est pas américain. Les entités sélectionnables sont US_SSN, US_DRIVER_LICENSE, US_BANK_NUMBER : un NIR français, un numéro NHS, un numéro de passeport ou un ITIN ne sont pas recherchés.
  3. Les identifiants indirects de HIPAA ne sont pas traités : âge supérieur à 89 ans, dates rares, professions, appartenance à un petit groupe. Presidio ne fait aucune généralisation de dates : DATE_TIME est remplacé en bloc ou pas du tout.
  4. La langue. L'analyse est verrouillée sur l'anglais (§3) : sur un corpus non anglophone, le rappel de PERSON/LOCATION/DATE_TIME s'effondre, sans le moindre avertissement.
  5. Le seuil de 0,5 écarte les détections qui obtiennent un score inférieur. Lesquelles dépend des recognizers : les entités spaCy (noms, lieux, dates) reçoivent toutes un score fixe (ner_strength / default_score = 0,85 dans les sources de Presidio 2.2.355 et 2.2.366), donc 0,5 ne filtre pas les noms rares ou non anglo-saxons ; il agit sur les recognizers à base de motifs. Non testé sur une installation réelle.
  6. Le contenu qui n'a pas été extrait (tableaux DOCX, attributs XML, PDF scannés, en-têtes et pieds de page) n'est pas analysé. Il ne fuit pas dans la sortie, mais si le destinataire reçoit aussi les originaux, l'anonymisation ne l'a jamais couvert.

Échec silencieux : le constat le plus grave

  1. anonymize_text_presidio() se termine par (…py:757-759) :

    Bug confirmé : échec silencieux · aussi vrai dans VISOR

    Aussi vrai dans VISOR (copie cliente). La copie livrée a le même repli (AutomatedDentalToolsRemote Medical_Data_Anonymizer_ModuleRemote/Medical_Data_Anonymizer_ModuleRemote.py:750-751) et le même message « Complete! » (:673) ; legacy :758-759 et :680.

    except Exception as e:
    logger.error(f"Error in Presidio anonymization: {e}")
    return text  # Return original text if anonymization fails

    Toute erreur d'analyse (une entité non reconnue par la version de Presidio installée, un modèle spaCy manquant, un texte trop long) produit un fichier _anonymized contenant le texte d'origine intact, avec un statut « Complete! » dans l'interface et une seule ligne rouge dans la console Python. Il n'y a aucune vérification a posteriori, aucun décompte d'entités détectées, aucun rapport. Un document non anonymisé est indiscernable d'un document propre sans le lire.

Conclusion pratique. La sortie de ce module ne suffit pas à elle seule pour déclarer un jeu de données dé-identifié. C'est une première passe sur du texte libre en anglais, à relire, et elle doit être complétée par : le renommage des fichiers, un anonymiseur DICOM dédié pour les images, et le defacing si les volumes couvrent le visage.

8. Environnement

Explication en langage courant et maths : page de l'atlas.

Tout tourne dans le Python de Slicer, installé par le bouton « Install Dependencies » (…py:147, gestionnaire :400), sans confirmation et sans versions épinglées :

presidio-analyzer, presidio-anonymizer, pandas, python-docx, pdfplumber,
odfpy, lxml, langdetect, reportlab    then    spacy.cli.download("en_core_web_lg")

Notes:

  • spacy n'est pas dans la liste pip_install : il est seulement importé (…py:417). Cela fonctionne parce que presidio-analyzer l'installe comme dépendance ; si cet import échoue, tout le bloc tombe dans l'except et affiche « Error installing dependencies. »
  • Un redémarrage de Slicer est demandé après l'installation (boîte de dialogue), ce qui est cohérent avec le chargement d'un modèle spaCy.
  • lxml est installé mais inutilisé (le code utilise xml.etree.ElementTree) ; langdetect est installé et jamais importé.
  • os.environ['PRESIDIO_SUPPRESS_WARNINGS'] = '1' et warnings.filterwarnings('ignore') sont posés au niveau du module, donc dès le chargement de l'extension : ils suppriment les avertissements pour tout Slicer, pas seulement ceux de Presidio.
  • Pas de GPU, pas de conda, pas de CLI : AnalyzerEngine() et le chargement de spaCy (quelques secondes) se font sur le thread de l'interface, à chaque exécution.

9. Pièges et points fragiles

Explication en langage courant et maths : page de l'atlas.

  • Échec silencieux qui renvoie le texte d'origine (§7.9).
  • Dossier de sortie aplati : collisions de noms, écrasement sans message.
  • CSV restructuré par line.split(), XML dégradé en texte brut, ODT renommé en .txt.
  • UUID généré mais jamais appliqué : la « table de correspondance » ne permet aucune ré-identification contrôlée.
  • file.replace(".docx", "_anonymized.docx") : str.replace remplace toutes les occurrences ; un nom contenant deux fois l'extension produit un résultat inattendu.
  • Le PDF de sortie n'a aucune pagination (un seul bloc Preformatted) : un long document peut déborder du cadre ou lever une exception reportlab, auquel cas le fichier est compté comme ERROR mais le traitement continue.
  • Tout tourne sur le thread de l'interface : sur un gros dossier, Slicer paraît figé.
  • Le README surestime le module : il parle de conformité HIPAA et d'« AI-powered text analysis » là où le code est un appel Presidio par défaut sur du texte anglais, sans validation.
  • Le README pointe vers Medical_Data_Anonymizer_Module/Resources/Icons/icon.png alors que le fichier réellement présent s'appelle Medical_Data_Anonymizer_Module.png.
  • Medical_Data_Anonymizer_ModuleLogic / …Test sont des coquilles vides : pas de tests, et rien d'appelable par script.

10. Littérature et références

Explication en langage courant et maths : page de l'atlas.

Aucun article ne couvre ce module ; il n'y a pas non plus d'évaluation (rappel, précision) dans le dépôt, sur aucun corpus.

Les briques utilisées sont documentées :

  • Microsoft Presidio : le moteur de détection et d'anonymisation, avec la liste exacte de ses recognizers et opérateurs prédéfinis (replace, redact, hash, mask, encrypt, ce dernier, réversible avec une clé, n'est pas proposé par le module).
  • spaCy en_core_web_lg : le modèle de NER anglais utilisé par défaut.
  • HIPAA Safe Harbor, 45 CFR §164.514(b)(2) : les 18 catégories d'identifiants à supprimer. Utile comme grille de lecture pour §7 : les noms de fichiers, les identifiants de dossier médical et les identifiants d'image y figurent, et ce module ne les traite pas.

Bibliographie complète : SOURCES.html, recherche faite, résultat négatif sur le module lui-même. Le dossier contient la seule évaluation publiée de Presidio sur du texte clinique non structuré, et des liens vers les campagnes de dé-identification de texte i2b2/n2c2, qui ne décrivent pas ce code mais en fournissent la grille de lecture.
