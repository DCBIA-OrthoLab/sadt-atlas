BatchDentalSeg, legacy : le code

Pour les développeurs : ce que fait le module Slicer legacy dans le code, avec des références file:line, des signatures, des tableaux et des pièges. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. File d'attente qui pilote nnUNetv2_predict sur un lot de scans CT/CBCT, avec quatre jeux de poids interchangeables, DentalSegmentator et ses trois variantes, plus tout le travail de garde-fous, de restauration de la géométrie et d'export qui les entoure.

Code Atlas (explication) Dot 2024 · J Dent BATCHDENTALSEG nnUNetv2_predict sans conda : le Python de Slicer + nnunetv2 VISOR Bibliographie

Segmentation dento-maxillo-faciale par lots de scans CT/CBCT. Le module n'est pas un réseau : c'est une file d'attente et un orchestrateur autour de nnUNetv2_predict, avec quatre jeux de poids interchangeables. Tout l'apprentissage se fait hors de ce dépôt ; ce qui est écrit ici, c'est le choix du modèle, les garde-fous mémoire, la restauration de la géométrie et les exports.

Deux bases de code

Tout ce qui est numéroté ci-dessous décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage VISOR, qui exécute le même outil sur un serveur, est décrit sur sa propre page, BatchDentalSeg sur VISOR.

1. Situation dans la chaîne

Aucun autre module du dépôt n'appelle BatchDentalSeg, et BatchDentalSeg n'appelle aucun autre module du dépôt. C'est un outil terminal. Il dépend en revanche d'une extension Slicer externe, NNUNet (SlicerNNUNetLib), dont il utilise trois classes.

AppeléOrigineRôle
SlicerNNUNetLib.InstallLogicExtension NNUNetsetupPythonRequirements() : installe nnunetv2 dans le Python de Slicer
SlicerNNUNetLib.ParameterExtension NNUNetvalide l'arborescence du dossier de modèle et construit la ligne de commande
SlicerNNUNetLib.SegmentationLogicExtension NNUNetécrit le volume en NIfTI dans un dossier temporaire, lance nnUNetv2_predict comme QProcess, recharge la segmentation
OpenAnatomyExportExtension SlicerOpenAnatomyexport glTF uniquement ; installée à la volée si absente

Le module est une variante par lots de DentalSegmentator (extension gaudot/SlicerDentalSegmentator), dont il reprend le widget, les icônes et le mécanisme de téléchargement des poids. Les contributeurs déclarés dans BATCHDENTALSEG.py:35-41 mêlent l'équipe d'origine (Dot, Gajny, Fenioux, Pelletier) et l'ajout de l'UoM (Tulissi).

3. Entrées, parcours des dossiers, nommage

Explication en langage courant et maths : page de l'atlas.

3.1 Ce qui est accepté

listVolumes() (Queue.py:28) fait un glob non récursif sur quatre motifs : *.nii, *.nii.gz, *.gipl, *.gipl.gz. Les sous-dossiers ne sont pas visités, et NRRD n'est pas reconnu : c'est le format par défaut de Slicer, et un format que les autres modules du dépôt produisent couramment.

volumeStem() retire le suffixe composé : case01.nii.gz → case01 (un Path.stem laisserait case01.nii).

Explication en langage courant et maths : page de l'atlas.

3.2 La file d'attente

Une entrée = un scan, pas un dossier (QueueItem, Queue.py:52) : inputPath, outputDir, model, device, status, error, durationSec, autoCrop. Plusieurs dossiers avec des modèles différents peuvent donc être empilés dans la même session.

addFolder() saute un scan si <outputDir>/<stem>_Segmentation.nii.gz existe déjà (la case Skip scans already segmented, cochée par défaut) ou s'il est déjà dans la file.

Persistance : l'état est réécrit après chaque scan dans <outputDir>/.batchdentalseg_queue.json. Au rechargement, un scan resté à running (Slicer tué en pleine inférence) est remis à pending et l'index revient dessus.

isChunkBoundary() : tous les chunkSize scans (5 par défaut), _coolDown() fait un nettoyage en profondeur, supprime les nœuds orphelins, torch.cuda.empty_cache() + ipc_collect(), gc.collect().

Explication en langage courant et maths : page de l'atlas.

3.3 Ce que le réseau voit réellement

Le widget ne prétraite rien. SegmentationLogic._prepareInferenceDir() fait un slicer.util.exportNode(volumeNode, <tmp>/input/volume_0000.nii.gz), et tout le prétraitement est celui de nnU-Net, dans cet ordre (nnunetv2 2.8.1, preprocessing/preprocessors/default_preprocessor.py, lu dans l'environnement de VISOR ; la version qu'exécute une installation legacy n'est pas consignée) : transposition selon transpose_forward (:56), recadrage sur la région non nulle (:65), normalisation (:82, commentée comme DEVANT précéder le rééchantillonnage), puis rééchantillonnage au spacing du plan (:88). CTNormalization est la définition standard de nnU-Net (preprocessing/normalization/default_normalization_schemes.py:58-72) : écrêtage aux percentiles 0,5 % / 99,5 % du plan sur le jeu d'entraînement, soustraction de leur moyenne, division par max(std, 1e-8). Le plan lu ici est celui de DentalSegmentator uniquement (plans.json : p0.5 −110, p99.5 3067, moyenne 1274, écart-type 558) ; que le même schéma s'applique aux trois autres modèles est supposé, non vérifié (§4.3).

Le seul prétraitement écrit dans ce dépôt est le recadrage automatique (§5.2), et il est facultatif, réservé au rejeu après un échec mémoire.

4.2 nnU-Net, vérifié dans le code

Oui, c'est bien nnU-Net v2, pas seulement de nom. La preuve est dans la chaîne d'appels : Parameter.asArgList() construit littéralement

nnUNetv2_predict -i <tmp>/input -o <tmp>/output
  -d Dataset111_453CT -tr nnUNetTrainer -p nnUNetPlans -c 3d_fullres
  -f 0 -npp 1 -nps 1 -step_size 0.5 -device cuda -chk checkpoint_final.pth --disable_tta

-d, -tr, -p, -c sont déduits des noms de dossiers : le dossier parent donne le Dataset…, et le nom du dossier de configuration est découpé sur __ en (trainer, plan, configuration). D'où l'exigence Dataset<id>/<trainer>__<plan>__<conf>/fold_<i>/checkpoint_final.pth.

Paramètres non exposés à l'utilisateur, valeurs par défaut de SlicerNNUNetLib.Parameter : stepSize = 0.5, disableTta = True (pas d'augmentation par miroir au moment du test), folds = "0" (un seul fold, jamais un ensemble), nProcessPreprocessing = nProcessSegmentationExport = 1, forcés à 0 sur macOS (nnU-Net s'y bloque à l'écriture à cause du multiprocessing).

Le placement des patchs et les poids gaussiens sont ceux de nnU-Net, pas ceux du module : le pas vaut au plus step_size fois le patch et est réduit pour que les patchs finissent au bord de l'image, d'où un recouvrement d'au moins la moitié pour 0,5 (nnunetv2 2.8.1, inference/sliding_window_prediction.py:30-54) ; les poids sont gaussiens avec un étalement d'un huitième du patch (:11-16, appelé en inference/predict_from_raw_data.py:626). Le label d'un voxel est l'argmax sur les labels (utilities/label_handling/label_handling.py:178), qui renvoie le premier maximum en cas d'égalité (comportement documenté de NumPy et de PyTorch).

Le seul réglage que propose l'interface est le périphérique : cuda / cpu / mps. S'il est indisponible, une seule question est posée pour toute la file (_deviceFallbackAccepted), et en mode Unattended le repli sur le CPU est accepté automatiquement.

nnUNet_raw, nnUNet_preprocessed et nnUNet_results pointent tous vers le dossier du modèle : trois variables d'environnement au niveau du processus, écrites par SegmentationLogic._startInferenceProcess. Comme os.environ est global, deux inférences simultanées dans la même session Slicer se marcheraient dessus ; ici la file est strictement séquentielle, donc le problème ne se pose pas.

Seul Dataset111_453CT (DentalSegmentator) a ses fichiers JSON dans le dépôt. Résumé tiré de plans.json :

Les plans des trois autres modèles ne peuvent pas être déterminés depuis le dépôt : ils arrivent avec le téléchargement. Tout ce qu'on en sait vient des dictionnaires codés en dur dans le widget (§4.4) et du README.

4.4 Les labels produits, par modèle

_get_active_label_map() (SegmentationWidget.py:1945) est la table de référence : elle décide des valeurs écrites dans le NIfTI de sortie.

DentalSegmentator et PediatricDentalsegmentator, 5 labels identiques, confirmés par le dataset.json du jeu 111 : 1 Upper Skull (maxillaire inclus), 2 Mandible, 3 Upper Teeth, 4 Lower Teeth, 5 Mandibular canal. Ce qui les distingue n'est donc pas la sortie mais les données d'entraînement : dentition permanente (453CT, 7 établissements) contre dentition mixte (380CT). Le code les traite de façon rigoureusement identique : même table de labels, mêmes couleurs, même post-traitement ; seul _modelBasePath diffère.

NasoMaxillaDentSeg, 6 labels, le maxillaire détaché du crâne : 1 Upper Skull, 2 Mandible, 3 Maxilla, 4 Upper Teeth, 5 Lower Teeth, 6 Mandibular canal.

UniversalLabDentalsegmentator, 55 labels : les 32 dents permanentes numérotées une à une (1 = 3e molaire supérieure droite → 32 = 3e molaire inférieure droite, en parcourant l'arcade supérieure puis l'inférieure), puis 20 dents temporaires (33 → 52), puis Mandible = 53, Maxilla = 54, Mandibular canal = 55. Pas de « Upper Skull » : ce modèle ne segmente pas la voûte crânienne, contrairement à ce qu'affiche sa description dans l'interface et à ce que dit le README. La numérotation n'est pas arbitraire : label par label, les valeurs 1–32 sont exactement le système de numérotation universel (1 = troisième molaire supérieure droite … 32 = troisième molaire inférieure droite) et 33–52 sont ses lettres A–T pour les dents temporaires, de sorte que l'équivalent FDI d'un label est fixé, la figure ci-dessous donne les deux.

Piège (le fait sur le modèle vaut dans VISOR, le texte de l'interface non)

La description affichée dans l'interface pour UniversalLabDentalsegmentator et le README du dépôt annoncent une segmentation de la voûte crânienne. Le modèle réel n'a pas de label « Upper Skull » : il ne numérote que les dents, plus mandibule/maxillaire/canal.

Legacy (3c67957) : la description indique « Segments: Upper Skull, Mandibular Canal, All teeth » (SegmentationWidget.py:68-72), et la table de labels n'a pas d'Upper Skull (SegmentationWidget.py:1949-1974). VISOR : la description du modèle a été corrigée (« Every tooth labelled individually in Universal numbering, deciduous teeth included, plus Mandible, Maxilla and Mandibular canal », SADT-VISOR sadt_batchdentalseg/catalogs.py:145-150) et la table de 55 labels n'a pas non plus d'Upper Skull (catalogs.py:47-103). Le README du client Slicer répète encore l'erreur (AutomatedDentalToolsRemote README.md:865-867).

Les valeurs sont posées sur chaque segment via une balise LabelValue (_segmentLabelValue), qui l'emporte sur le nom quand elle est présente.

5.2 Recadrage automatique (rejeu après échec mémoire)

Facultatif, déclenché par Retry failed après confirmation explicite. _applyAutoCrop() (SegmentationWidget.py:1029) :

  • seuil air/tissu tolérant à l'échelle : si array.min() < −800, on est en unités Hounsfield et le seuil est −500 ; sinon min + 0.15 × (p99.5 − min) ;
  • boîte englobante des voxels au-dessus du seuil, élargie de _CROP_MARGIN_MM = 15.0 mm convertis en voxels par axe ;
  • si plus de _CROP_MIN_GAIN = 0.85 des voxels sont conservés, le recadrage est abandonné : gagner moins de 15 % ne vaut pas le risque ;
  • le sous-volume garde son espacement et ses axes, seule l'origine bouge (ijkToRas.MultiplyPoint([i0,j0,k0,1])). Rien n'est interpolé.

_restoreCropToOriginalGrid() recolle la carte de labels dans un tableau de la taille d'origine par un simple décalage d'indices : la sortie est donc toujours sur la grille du scan tel qu'acquis.

Explication en langage courant et maths : page de l'atlas.

5.3 Garde mémoire : trois lignes de défense

Le commentaire du code donne le cas réel : un scan a rempli 114 Go sur une machine de 125 Go, a été tué par l'OOM killer et a laissé ses workers de multiprocessing en vie, qui retenaient la mémoire.

a) Estimation a priori, _estimatePeakRamGb() (SegmentationWidget.py:1173). Comme le volume physique du champ de vue est indépendant de l'espacement, le nombre de voxels rééchantillonnés vaut fovMm3 / targetVoxelMm3. Le pic est atteint dans convert_predicted_logits_to_segmentation_with_correct_shape, où coexistent, par classe : l'accumulateur de fenêtre glissante (torch.half sur la grille rééchantillonnée, 2 octets), sa copie float64 (data = data.astype(float) sur tout le tableau 4D d'un coup, 8 octets) et reshaped_final (torch.half sur la grille d'origine, 2 octets). D'où logitsGb = (10 × C × Vresampled + 2 × C × Voriginal) / 2³⁰, plus 8 × (Voriginal + Vresampled) pour les transitoires float64 de skimage.resize, plus _RAM_FIXED_OVERHEAD_GB = 4.0 (torch, poids, workers). Le spacing et le nombre de labels sont lus dans le même dossier de configuration, pour ne pas croiser l'espacement d'un modèle avec le nombre de labels d'un autre.

Budget = free RAM × ramLimitSpinBox (par défaut 85 %). Au-delà, le scan est marqué failed avec la raison, sans jamais démarrer nnU-Net, sauf si la case Skip scans too large for the free RAM (ramPreflightCheckBox, cochée par défaut, SegmentationWidget.py:446-447) est décochée : l'estimation est alors seulement journalisée (SegmentationWidget.py:1248-1253). Le budget s'applique à la mémoire disponible à cet instant (vm.available, SegmentationWidget.py:1243-1244), bien que le champ numérique soit libellé « % of system RAM ».

b) Surveillance pendant l'exécution : _onMemCheck échantillonne toutes les _RAM_SAMPLE_MS = 3000 ms ; il faut _RAM_CONSECUTIVE_HITS = 2 dépassements consécutifs pour tuer (un pic transitoire ne doit pas condamner un bon scan).

c) Récupération de la mémoire : _killInferenceTree() tue l'arbre entier, car QProcess.kill() n'atteint que l'enfant direct, or nnU-Net fait du multiprocessing. _reclaimStrayProcesses() balaie les processus dont la ligne de commande contient nnunetv2_predict, nnunetv2/inference ou nnunet et qui n'appartiennent plus à personne. Le bouton Free memory le fait à la main.

5.4 Détection de fin de repli

_checkInferenceCompletionFallback() (SegmentationWidget.py:2611) : quand la ligne « done with volume » apparaît dans la sortie de nnU-Net, un minuteur vérifie la taille du fichier de sortie toutes les 1,5 s ; deux lectures consécutives égales ⇒ finalisation forcée, même si le QProcess n'a jamais émis son signal finished. Abandonne après 40 tentatives (60 s).

Garde-fou supplémentaire : un chien de garde par scan (itemTimeoutSpinBox, 60 min par défaut ) marque le scan comme échoué et passe au suivant. _finishCurrentItem est le point de sortie unique, protégé par _itemFinalized contre une double avance.

Explication en langage courant et maths : page de l'atlas.

5.5 Correction du miroir (UniversalLab uniquement)

onResolveMirroring() (SegmentationWidget.py:1321), un bouton visible seulement pour UniversalLab. Le réseau confond régulièrement la gauche et la droite ; la correction est purement géométrique :

  1. reconstruction de la carte de labels officielle (§5.1), puis la coordonnée RAS R de chaque voxel de premier plan en numpy (m00·x + m01·y + m02·z + m03) : la version précédente appelait vtkMatrix4x4.MultiplyPoint une fois par voxel et par label ;
  2. plan sagittal = moyenne des centroïdes R des quatre incisives centrales (labels 8, 9, 24, 25) ; si l'une manque, la correction est refusée ;
  3. pour chaque label latéralisé, les voxels du mauvais côté du plan reçoivent la valeur du label symétrique (table construite en substituant left ↔ right dans le nom) ; {53, 54, 55} sont protégés.

Le résultat va dans un nouveau nœud <name>_Mirrored, l'original est conservé.

Explication en langage courant et maths : page de l'atlas.

5.6 Post-traitement absent

Piège (le code mort est legacy uniquement ; l'absence de nettoyage vaut aussi dans VISOR)

_postProcessSegments() ne journalise que deux lignes (SegmentationWidget.py:2526-2528) ; _keepLargestIsland() et _removeSmallIsland() (qui utiliseraient _minimumIslandSize_mm3 = 60) ne sont appelées nulle part : du code mort hérité de DentalSegmentator en amont. Aucun nettoyage morphologique n'est donc appliqué : ce qui sort est la sortie brute de nnU-Net, avec son propre post-traitement interne s'il figure dans le jeu.

Aussi vrai dans VISOR pour l'absence de nettoyage : la sortie de nnU-Net est remise sur la grille du scan et écrite telle quelle (SADT-VISOR sadt_batchdentalseg/pipeline.py:323-346) ; les fonctions d'îlots n'y existent pas.

Explication en langage courant et maths : page de l'atlas.

6. Sorties

onInferenceFinished écrit toujours, quels que soient les formats cochés, <outputFolder>/<stem>_Segmentation.nii.gz : une carte de labels avec les valeurs de _get_active_label_map, sur la géométrie (espacement, origine, IJKToRAS) du volume d'origine, non recadrée si un recadrage a eu lieu. C'est le fichier que cherche expectedOutputPath() pour décider qu'un scan a déjà été traité.

Formats supplémentaires, cases à cocher, tous écrits dans le même dossier :

Les noms des fichiers de maillage dérivent du nom du nœud de segmentation, <stem>_Segmentation, et non du nom du scan : les noms de segments sont assainis par re.sub(r"[^0-9A-Za-z_-]+", "_", ...).

Un échec d'export de maillage ne fait pas échouer le scan : le NIfTI est déjà écrit, le scan est marqué done avec un export warning.

Vérifié : corrigé dans le code (legacy uniquement)

Un bug qui a été corrigé, documenté dans le code de _exportMergedVTK (SegmentationWidget.py:2823-2832) : vtkDiscreteMarchingCubes.SetValue prend un indice de contour, pas une valeur de label. Passer le label comme indice laissait l'indice 0 à la valeur de contour 0.0, de sorte que le fond était contouré, lissé et traité pour ses normales avant d'être écarté.

Legacy (3c67957) ; absent de VISOR : VISOR construit une surface par label à partir d'un masque binaire (GenerateValues(1, 1, 1), SADT-VISOR sadt_batchdentalseg/mesh_export.py:78-80) et les fusionne avec vtkAppendPolyData (mesh_export.py:205-207, 226-235).

8. Environnement

Installé une fois par session, au premier Apply, par _runSetupThenStartQueue() (SegmentationWidget.py:1749) :

  1. pip install light-the-torch, puis python -m light_the_torch install torch torchvision : ltt choisit la roue CUDA qui correspond au pilote détecté, aucune version n'est figée ;
  2. pip install numexpr>=2.10.2;
  3. pip install numpy<2.0 numexpr>=2.10.2 psutil, via PipRunner, un QProcess qui rend la main à l'interface ;
  4. SlicerNNUNetLib.InstallLogic().setupPythonRequirements() : nnunetv2, hors de ce dépôt ;
  5. PythonDependencyChecker.downloadWeightsIfNeeded() : poids de DentalSegmentator uniquement.

numpy<2.0 pour la même raison que dans AMASSS : les roues torch actuelles sont compilées contre numpy 1.x.

L'extension NNUNet doit être installée à la main : son absence est détectée (import SlicerNNUNetLib) et produit un message demandant de l'installer et de redémarrer. SlicerOpenAnatomy, en revanche, s'installe toute seule au premier export glTF.

Pas d'environnement conda, pas de WSL. Le GPU est facultatif (cpu, mps disponibles), au prix d'« environ une heure par scan » selon le message de repli.

9. Pièges et points fragiles

Bug confirmé : NasoMaxillaDentSeg (legacy uniquement)

Legacy (3c67957) ; absent de VISOR. VISOR ne renomme aucun segment : la table est Upper Skull 1, Mandible 2, Maxilla 3, Upper Teeth 4, Lower Teeth 5, Mandibular canal 6 (SADT-VISOR sadt_batchdentalseg/catalogs.py:35-42) et c'est elle qui nomme les fichiers par label (pipeline.py:199-206). L'analyse legacy suit.

Les noms de segments et la table de labels divergent pour NasoMaxillaDentSeg. _get_active_label_map (SegmentationWidget.py:1977-1987) donne Maxilla = 3, Upper Teeth = 4, Lower Teeth = 5, Mandibular canal = 6, alors que _updateSegmentationDisplay (SegmentationWidget.py:2278, liste en SegmentationWidget.py:2482) renomme Segment_1..6 avec la liste ["Upper Skull", "Mandible", "Upper Teeth", "Lower Teeth", "Mandibular canal", "Maxilla "].

Le premier effet est visible à l'écran, avant toute question d'export : la liste n'est pas dans l'ordre de la table, si bien que les quatre derniers segments reçoivent le mauvais nom, la mauvaise couleur et la mauvaise opacité.

SegmentStructure réelleNom affiché
Segment_3Maxillaire"Upper Teeth"
Segment_4Upper Teeth"Lower Teeth"
Segment_5Lower Teeth"Mandibular canal"
Segment_6Mandibular canal"Maxilla" (avec une espace en fin de chaîne)

Le correctif consiste à réordonner la liste, ainsi que les listes colors et opacities qui l'accompagnent, pour qu'elles correspondent à _get_active_label_map, plutôt qu'à simplement retirer l'espace.

Mais le renommage a lieu avant la pose des balises LabelValue, et _segmentLabelValue se rabat alors sur le nom : Segment_3, qui porte en réalité le label 3 (maxillaire), est renommé « Upper Teeth » et exporté avec la valeur 4. Pis, "Maxilla " a une espace en fin de chaîne : la recherche dans la table échoue, Segment_6 (le canal mandibulaire) est journalisé comme « unexpected segment » et perdu dans le NIfTI. Les deux listes correspondent en revanche parfaitement pour les trois autres modèles.

  • Les quatre branches de onApplyClickedForVolume sont du copier-coller : la branche UniversalLab nomme encore sa variable pediatricCheckpoint et journalise « Downloading pediatricdentalseg model… ». Cosmétique, mais trompeur à la lecture des journaux.
Piège · Legacy uniquement

Télécharger les poids de DentalSegmentator efface les trois autres modèles : downloadWeights() fait shutil.rmtree(self.destWeightFolder) sur Resources/ML (PythonDependencyChecker.py:158-160), qui contient aussi Dataset001_380CT, Dataset001_max4 et Dataset002_380CT. Et getDatasetPath() cherche rglob("dataset.json") n'importe où sous Resources/ML (PythonDependencyChecker.py:123-127), puis areWeightsMissing() vérifie la présence de fold_*/*.pth à côté du premier trouvé (PythonDependencyChecker.py:78-96) : si seul le modèle pédiatrique est présent, le vérificateur croit DentalSegmentator installé.

Legacy (3c67957) ; absent de VISOR : rien n'est téléchargé pendant une exécution (SADT-VISOR sadt_batchdentalseg/pipeline.py:15-17) ; chaque jeu a son propre dossier (dest) dans le manifeste du serveur (VISOR-serve scripts/data-manifest.yml:542-586) et un jeu n'est accepté que s'il contient dataset.json, plans.json et fold_0/checkpoint_final.pth (nnunet_runner.py:57-73).

Piège (la résolution de release est legacy uniquement ; la faille d'intégrité n'est que partiellement comblée dans VISOR)

Résolution de release fragile : assets[0] parmi tous les assets de toutes les releases (PythonDependencyChecker.py:98-102), via un client GitHub non authentifié (60 requêtes/h par IP). Un asset ajouté en tête de la dernière release change le modèle téléchargé. Et aucun contrôle d'intégrité sur les trois checkpoints téléchargés un par un : un fichier tronqué est indiscernable d'un fichier complet.

Legacy (3c67957) ; absent de VISOR pour la résolution : le manifeste du serveur fige une URL par fichier, par tag de release (VISOR-serve scripts/data-manifest.yml:546-585). Seulement en partie corrigé pour l'intégrité : un sha256 n'est déclaré que pour deux fichiers de cet outil, le dataset.json et le plans.json de PediatricDentalSeg (data-manifest.yml:563, 568) ; les checkpoints et l'archive de DentalSegmentator ont une size et pas de hachage, et le script de récupération ne vérifie que lorsqu'un hachage est présent (VISOR-serve scripts/fetch_data.py:309-319). Un téléchargement va dans un dossier temporaire et n'est déplacé en place qu'une fois complet, si bien qu'un checkpoint tronqué n'est plus pris pour un checkpoint terminé (fetch_data.py:300-306).

  • NRRD n'est pas reconnu et les sous-dossiers ne sont pas parcourus (listVolumes), alors que les autres modules du dépôt produisent volontiers du NRRD et des arborescences de dossiers. Une collision de noms est possible : deux scans de dossiers différents portant le même nom de base écrasent le même <stem>_Segmentation.nii.gz.
  • Un seul fold, jamais un ensemble (folds="0") : un jeu qui livrerait fold_1..4 les verrait ignorés.
  • os.environ['nnUNet_results'] est réécrit à chaque scan par SegmentationLogic : sans danger ici (file séquentielle), dangereux si une autre inférence nnU-Net tourne dans la même session Slicer.
  • Code mort : _saveSegmentationAsNifti, _postProcessSegments, _keepLargestIsland, _removeSmallIsland, onExportClicked (le bouton correspondant n'est pas câblé dans la disposition par lots).
Piège (legacy uniquement ; corrigé : CMake liste bien une partie de Resources/ML)

Correction à 3c67957. MODULE_PYTHON_RESOURCES liste bien Resources/ML/download_info.json ainsi que le dataset.json et le plans.json de Dataset111_453CT (BATCHDENTALSEG/CMakeLists.txt:28-34), donc l'affirmation selon laquelle Resources/ML n'est pas installé était fausse pour ce commit. Les fichiers JSON des trois autres jeux ne sont pas listés.

Ce qui tient : l'estimation mémoire a priori (§5.3) renvoie None quand les fichiers de plans ou de jeu de données sont illisibles (SegmentationWidget.py:1173-1204), et le contrôle de RAM laisse alors passer le scan (SegmentationWidget.py:1239-1242).

Absent de VISOR : le client Slicer n'a pas de garde mémoire (le panneau fait 97 lignes, AutomatedDentalToolsRemote BATCHDENTALSEGRemote/BATCHDENTALSEGRemote.py:51-97) ; l'admission est faite par le serveur (VISOR-serve server/execution/admission.py:1-12).

10. Littérature

DentalSegmentator est publié :

Dot G., Chaurasia A., Dubois G., Savoldelli C., Haghighat S., Azimian S., Rahbar Taramsari A., Sivaramakrishnan G., Issa J., Dubey A., Schouman T., Gajny L. DentalSegmentator: robust open source deep learning-based CT and CBCT image segmentation. Journal of Dentistry 147:105130, 2024. doi:10.1016/j.jdent.2024.105130 , PMID 38878813

nnU-Net v2 (v2.2 d'après la notice Zenodo des poids), 470 scans CT et CBCT de 7 établissements pour l'entraînement, 5 structures, test en hold-out sur 256 scans (133 internes, 123 externes) : DSC 92,2 ± 6,3 % en interne, 94,2 ± 7,4 % en externe. Le dataset.json fourni ici annonce numTraining = 453, cohérent avec le corpus décrit.

Vérifié

Sur ce modèle, le code et l'article concordent. Les poids sont aussi publiés sous CC-BY-4.0 sur Zenodo (DOI de concept 10.5281/zenodo.10829674) , mais ce module les récupère depuis les releases GitHub, pas depuis Zenodo.

Legacy : le module les télécharge lui-même au premier Apply. VISOR : rien n'est récupéré pendant une exécution ; un script d'installation met en place la même archive de release amont (gaudot/SlicerDentalSegmentator, Dataset111_453CT_v100.zip, VISOR-serve scripts/data-manifest.yml:582-586), toujours depuis GitHub et non depuis Zenodo.

Le fondement méthodologique :

Isensee F., Jaeger P.F., Kohl S.A.A., Petersen J., Maier-Hein K.H. nnU-Net: a self-configuring method for deep learning-based biomedical image segmentation. Nature Methods 18(2):203-211, 2021. doi:10.1038/s41592-020-01008-z

Les trois variantes ne sont rattachées à aucune publication dans le dépôt. Ces chiffres ne peuvent être vérifiés nulle part dans le code : les fichiers dataset.json correspondants n'arrivent qu'avec le téléchargement des poids.
