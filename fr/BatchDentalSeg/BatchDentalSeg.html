BatchDentalSeg

BatchDentalSeg étiquette les dents et les mâchoires de scans CT et CBCT par lots, avec un seul réseau multi-labels qui donne à chaque voxel son label en une seule passe. Cette page explique le module pas à pas, avec les maths des parties qui relèvent du calcul plutôt que de l'apprentissage : comment le scan est normalisé, comment les patchs du réseau sont fondus, comment la mémoire est estimée, comment un scan est recadré et comment la gauche et la droite sont corrigées. Là où le code fait quelque chose qui mérite d'être vérifié, un lien mène à la page de code.

Code (développeurs) Dot 2024 · J Dent BATCHDENTALSEG nnUNetv2_predict sans conda : le Python de Slicer + nnunetv2 VISOR Bibliographie

Vue d'ensemble : ce qui entre, ce qui sort

BatchDentalSeg prend des scans CT ou CBCT de la tête et étiquette les dents et les mâchoires de chacun. Un seul réseau 3D regarde tout le scan et donne à chaque voxel un label en une passe : ce n'est pas un réseau par structure, comme dans AMASSS. Le module lui-même est une file d'attente autour de ce réseau : il choisit le modèle, garde la mémoire, restaure la géométrie et écrit les exports.

EntréeCe qui se passeSortie
un dossier de scans (.nii, .nii.gz, .gipl, .gipl.gz), et l'un des quatre modèleschaque scan passe par nnU-Net, un scan à la fois ; la carte de labels est remise sur la grille propre du scanune carte de labels par scan (<scan>_Segmentation.nii.gz), et en option STL, OBJ, VTK, glTF ou un fichier NIfTI par segment

Cette page décrit le module Slicer legacy (SlicerAutomatedDentalTools à 3c67957, 2026-10-26). Le portage serveur est BatchDentalSeg sur VISOR.

1. Situation dans la chaîne

Aucun autre module du dépôt n'appelle BatchDentalSeg, et il n'en appelle aucun : c'est un outil terminal. Il dépend d'une extension Slicer externe, NNUNet, pour installer nnU-Net, vérifier le dossier de modèle et lancer la prédiction comme processus enfant. C'est une variante par lots de DentalSegmentator, dont il reprend le widget, les icônes et le téléchargement des poids.

Dans le codeLe tableau des classes appelées depuis l'extension NNUNet

2. Fichiers en jeu

L'essentiel du code tient dans un fichier de widget d'environ 3000 lignes : l'interface, la file d'attente, le choix du modèle, la garde mémoire, le recadrage, les labels et les exports. Un petit fichier de file d'attente garde la liste des scans sur disque, et un vérificateur télécharge et rafraîchit les poids de DentalSegmentator. Tout s'exécute dans le Python de Slicer ; nnU-Net lui-même est lancé comme processus enfant, un scan à la fois. Les poids arrivent à l'exécution.

Dans le codeLe tableau des fichiers avec leur nombre de lignes, et ce qu'installe le fichier de build

3. Entrées, parcours des dossiers, nommage

3.1 Ce qui est accepté

Un dossier est listé sans descendre dans les sous-dossiers, pour quatre motifs : .nii, .nii.gz, .gipl, .gipl.gz. NRRD, le format par défaut de Slicer, n'est pas reconnu.

3.2 La file d'attente

Une entrée est un scan, pas un dossier, donc plusieurs dossiers avec des modèles différents peuvent être empilés dans la même session. Un scan est sauté si son résultat existe déjà ou s'il est déjà en file. L'état de la file est réécrit après chaque scan, si bien qu'une session tuée en pleine inférence reprend là où elle s'est arrêtée. Tous les cinq scans (par défaut), un nettoyage libère la carte graphique et la mémoire.

3.3 Ce que le réseau voit réellement

Le widget ne prétraite rien : il exporte le scan en fichier NIfTI et tout le reste est celui de nnU-Net. nnU-Net réordonne le scan selon les axes que demande le plan, le recadre sur la région non nulle, normalise les intensités et ne le rééchantillonne qu'ensuite à l'espacement du plan (l'ordre du code propre de nnU-Net, vérifié en version 2.8.1 ; la version qu'exécute une installation legacy n'est pas consignée). La normalisation montrée ci-dessous est celle que déclare le plan de DentalSegmentator ; pour les trois autres modèles, voir la section 4.3.

Seul le plan de DentalSegmentator peut être lu dans les dépôts (dans le dépôt legacy) : percentiles −110 et 3067, moyenne 1274, écart-type 558. Les trois autres jeux apportent leur propre fichier de plan, donc pour eux cette recette est supposée, non vérifiée.

Le seul prétraitement écrit dans ce dépôt est le recadrage automatique facultatif (section 5.2), réservé à un rejeu après un échec mémoire.

4. Les quatre modèles

4.1 Ce que sélectionne la liste déroulante

Les quatre entrées exécutent le même code : une requête de prédiction est construite avec le fold 0 et le périphérique choisi, et seuls le dossier de poids et la table de labels changent. Les trois variantes (pédiatrique, naso-maxillaire et universelle) sont téléchargées en trois fichiers chacune ; DentalSegmentator arrive sous forme du zip de la dernière release de son dépôt. Les téléchargements n'ont ni somme de contrôle ni reprise, si bien qu'un téléchargement interrompu laisse un checkpoint tronqué que l'exécution suivante prend pour complet.

Dans le codeLes quatre branches, les chemins de téléchargement et la vérification des checkpoints

4.2 nnU-Net, vérifié dans le code

C'est bien nnU-Net v2 : la commande qu'il construit nomme le jeu de données, le trainer, le plan et la configuration (3D pleine résolution), un fold (une seule copie entraînée du modèle), un pas de 0,5 (chaque patch avance d'au plus la moitié de sa taille), pas de miroir au moment du test (pas de moyenne sur des copies retournées du scan). Le seul réglage que propose l'interface est le périphérique (cuda, cpu ou mps). Fold 0 seulement, jamais un ensemble.

Dans le codeLa ligne de commande, les valeurs par défaut et les variables d'environnement à l'échelle du processus

4.3 Architecture et plan : ce qui est vérifiable

Seul le jeu DentalSegmentator livre ses fichiers de plan dans le dépôt : un U-Net 3D convolutif simple à six étages (32 caractéristiques au premier, 320 au dernier), des patchs de 128 × 160 × 112 voxels, un espacement d'environ 0,45 × 0,31 × 0,45 mm, un lot de 2 et la normalisation CT. Les plans des trois autres modèles arrivent avec leur téléchargement, donc on n'en peut rien dire de plus depuis le code.

Dans le codeLe résumé du plan et les notes de format

4.4 Les labels produits, par modèle

Une table du widget décide des valeurs écrites dans le fichier de sortie. Les deux premiers modèles partagent les mêmes cinq labels et ne diffèrent que par ce sur quoi ils ont été entraînés (dentition permanente contre dentition mixte).

5. Le cœur non appris

5.1 Reconstruction de la carte de labels et restauration de la géométrie

La segmentation est transformée en une seule carte de labels par un export unique, puis remappée vers les valeurs officielles par une table de correspondance en une passe. La version précédente rastérisait le volume entier une fois par segment : 55 fois pour UniversalLab sur un CBCT bouche entière.

Dans le codeL'export unique et la table de correspondance

5.2 Recadrage automatique (rejeu après échec mémoire)

Le sous-volume recadré garde son espacement et ses axes, seule son origine bouge, et rien n'est interpolé. Après la prédiction, la carte de labels est recollée dans un tableau de la taille d'origine par un simple décalage, de sorte que la sortie est toujours sur la grille du scan tel qu'acquis.

Dans le codeLa fonction de recadrage, ses constantes et le recollage

5.3 Garde mémoire : trois lignes de défense

Le commentaire du code donne le cas réel : un scan a rempli 114 Go sur une machine de 125 Go, a été tué par le système et a laissé ses workers en vie, qui retenaient la mémoire. D'où trois lignes de défense, une par moment du processus : une estimation avant le lancement, une surveillance pendant l'exécution et une récupération après.

Pendant l'exécution, la mémoire est échantillonnée toutes les 3 secondes et deux dépassements consécutifs sont nécessaires pour tuer le processus, afin qu'un pic transitoire ne condamne pas un bon scan. Tout l'arbre de processus est tué, pas seulement l'enfant direct, car nnU-Net démarre ses propres workers, et les processus orphelins sont balayés.

Dans le codeL'estimation, l'échantillonneur, l'arrêt de l'arbre de processus et le balayage des orphelins

5.4 Détection de fin de repli

Quand nnU-Net imprime sa ligne « done », un minuteur surveille la taille du fichier de sortie, et deux lectures égales forcent la fin même si le processus ne l'a jamais signalée ; il abandonne après 60 secondes. Chaque scan a aussi un chien de garde (60 minutes par défaut) qui le marque échoué et passe au suivant.

Dans le codeLe minuteur de repli et le chien de garde par scan

5.5 Correction du miroir (UniversalLab uniquement)

Si l'une des quatre incisives manque, la correction est refusée. Le résultat va dans un nouveau nœud, <name>_Mirrored, et l'original est conservé.

Dans le codeLa fonction miroir, le dictionnaire de labels et le calcul du plan

5.6 Post-traitement absent

Aucun nettoyage morphologique n'est appliqué : ce qui sort est la sortie brute de nnU-Net, avec son propre post-traitement interne si le jeu en livre un. Deux fonctions de suppression d'îlots existent mais rien ne les appelle.

Dans le codeLes fonctions mortes et ce qu'il en reste

6. Sorties

Quels que soient les formats cochés, le module écrit toujours <scan>_Segmentation.nii.gz, une carte de labels sur la géométrie du volume d'origine. C'est aussi le fichier que la file cherche pour décider qu'un scan est déjà fait. Les autres formats vont dans le même dossier :

  • STL, OBJ : un fichier par segment.
  • VTK par label : un fichier par label, nettoyé, lissé (60 itérations windowed-sinc), réduit de 40 % et inversé de RAS vers LPS.
  • VTK fusionné : un fichier avec tous les labels, construit de la même façon, avec un tableau de labels constant.
  • NIfTI par segment : un fichier binaire par segment, à ne pas confondre avec la carte de labels ci-dessus.
  • glTF : via l'extension SlicerOpenAnatomy, avec une décimation réglable (0,9 par défaut).

Un échec d'export de maillage ne fait pas échouer le scan : le NIfTI est déjà écrit, et le scan est marqué terminé avec un avertissement.

8. Environnement

Les bibliothèques sont installées une fois par session, au premier Apply : torch (la version qui correspond au pilote détecté, aucune version figée), NumPy en dessous de 2 parce que les roues torch actuelles sont compilées contre NumPy 1, psutil, et nnU-Net via l'extension NNUNet, qui doit être installée à la main. Ni conda, ni WSL. Une carte graphique est facultative, mais le message de repli parle d'environ une heure par scan sur le CPU.

9. Pièges et points fragiles

Chaque point est vérifié dans le code et décrit, avec sa preuve, sur la page de code.

  • Les segments de NasoMaxillaDentSeg sont mal renommés : les quatre derniers reçoivent le mauvais nom, la mauvaise couleur et la mauvaise opacité, et le canal mandibulaire peut être perdu dans la sortie. Preuve.
  • UniversalLab est décrit comme segmentant la voûte crânienne dans l'interface et le README, mais il n'a pas un tel label. Preuve.
  • Télécharger les poids de DentalSegmentator efface les trois autres modèles. Preuve.
  • La release est résolue de façon fragile et aucun téléchargement n'est vérifié : le premier asset de la dernière release, pas de somme de contrôle. Preuve.
  • NRRD n'est pas lu et les sous-dossiers ne sont pas parcourus ; deux scans de même nom écrasent le même résultat. Preuve.
  • Un seul fold, jamais un ensemble : les folds supplémentaires d'un jeu sont ignorés. Preuve.
  • Les variables d'environnement qui pointent nnU-Net vers le modèle sont posées pour tout le processus Slicer, sans danger ici seulement parce que la file est séquentielle. Preuve.
  • Code mort : les fonctions de suppression d'îlots et de post-traitement ne sont jamais appelées. Preuve.
  • La liste d'installation est incomplète dans le fichier de build : seule une partie du dossier de modèle est listée. Preuve.

10. Littérature

DentalSegmentator est publié : Dot G. et al., DentalSegmentator: robust open source deep learning-based CT and CBCT image segmentation, Journal of Dentistry 147:105130, 2024 (doi:10.1016/j.jdent.2024.105130). Il utilise nnU-Net v2, avec 470 scans CT et CBCT de 7 établissements pour l'entraînement et un test hold-out de 256 scans, avec un Dice de 92,2 ± 6,3 % en interne et 94,2 ± 7,4 % en externe. Sur ce modèle, le code et l'article concordent. Le fondement méthodologique est Isensee et al., nnU-Net, Nature Methods 18(2):203-211, 2021.

Les trois variantes ne sont rattachées à aucune publication dans le dépôt. Le README annonce 513 scans CBCT en dentition mixte pour deux d'entre elles et 135 scans pour la troisième, sans référence ni jeu de test : ces chiffres sont des affirmations internes tant qu'une publication ne les couvre pas. Le texte complet des références est sur la page de code et dans SOURCES.md.
