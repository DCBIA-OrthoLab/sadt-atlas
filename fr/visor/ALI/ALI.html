ALI sur VISOR

ALI place automatiquement des points anatomiques, appelés landmarks, sur un scan 3D. Cette page explique comment, pas à pas, avec les maths : ce qui entre, ce que chaque étape en fait et ce qui en sort. Quand le code fait quelque chose qui mérite d'être vérifié, un lien mène à la page de code. Le module legacy a sa propre page.

VISOR Code (développeurs) Page legacy Guide (VISOR)

Vue d'ensemble : ce qui entre, ce qui sort

ALI prend une image 3D d'un patient et renvoie une liste de points 3D, chacun avec un nom : par exemple la pointe d'une dent, ou un point de la base du crâne. D'autres outils utilisent ces points pour orienter un scan ou pour recaler deux scans (voir ASO et AREG_IOSCBCT). Il travaille sur deux sortes d'image, qui demandent deux méthodes différentes, si bien que l'outil a deux modes :

Les réseaux et leurs poids entraînés sont ceux du legacy : rien n'est entraîné dans VISOR. Ce qui a changé, c'est tout ce qui les entoure : l'endroit où le travail s'exécute, la façon dont l'entrée est lue, la façon dont une exécution est bornée et rapportée (Ce qui a changé).

1. Où il s'exécute

Dans VISOR, Slicer ne garde qu'un panneau (ALIRemote). Il envoie le scan à un serveur, attend, puis télécharge un zip et charge les points dans la scène. Tout le calcul se fait sur le serveur, dans un environnement Python propre à chaque mode. L'outil que choisit l'utilisateur s'appelle ALI et pose d'abord une question, le mode ; derrière lui, deux outils serveur distincts font le travail, ALI_CBCT et ALI_IOS. Les autres outils serveur, comme ASO ou VFACE, ne passent pas par le panneau : ils demandent à ALI les landmarks dont ils ont besoin.

Quelles parties font le travail

Chaque mode est un programme distinct, avec son propre environnement Python isolé. Ils ne partagent qu'un tout petit paquet d'aide. Pour chaque mode, un fichier d'entrée publie l'outil, et les autres fichiers contiennent les étapes décrites plus bas : lecture de l'entrée, préparation du scan, l'agent et son réseau (CBCT), le rendu des caméras et le réseau qui lit les images (IOS), la sortie et le rapport.

Ce qui a été vérifié. Les tests automatisés passent pour les deux modes (60 pour ALI_CBCT, 190 pour ALI_IOS ; voir la page de code pour ce qu'ils couvrent). Les auteurs de VISOR rapportent que les landmarks CBCT sont identiques à ceux de l'implémentation serveur précédente sur un scan réel, pour les sept landmarks qu'utilise ASO, et que les réseaux de couronnes, exécutés sur un maillage, s'accordent avec le code legacy sur la bonne dent à chaque fois : 54 des 73 landmarks sont identiques, et les 19 autres diffèrent parce que VISOR garde les scores bruts au lieu de les tronquer en entiers (avec cette troncature remise, 71 sur 73 sont identiques). Ils indiquent aussi que la précision par rapport à des scans annotés n'est pas établie. Rien de cela n'a été re-mesuré sur un ensemble complet de scans.

2. Mode CBCT : un agent marche jusqu'au landmark

L'idée vient de l'apprentissage par renforcement, mais à l'exécution il n'y a pas d'apprentissage : un réseau entraîné sert simplement de boussole. Pour chaque landmark il y a un agent, qui est une position dans le volume. À chaque pas, le réseau regarde un petit cube de l'image autour de l'agent et dit lequel des six déplacements d'un voxel le rapproche le plus du landmark. L'agent avance, regarde de nouveau, et recommence jusqu'à ce qu'il se mette à tourner en rond, ce qui signifie qu'il est arrivé. Il le fait deux fois, d'abord sur une grille grossière (voxels de 1 mm) pour s'approcher, puis sur une grille fine (voxels de 0,3 mm) pour être précis.

2.1 Lecture de l'entrée

Un fichier seul doit être un volume (NIfTI, NRRD ou GIPL) ; une surface est refusée avec un message qui renvoie à ALI_IOS. Un dossier est parcouru récursivement et chaque scan est identifié par son chemin dans le dossier, si bien que deux patients ayant un fichier de même nom dans des sous-dossiers différents n'entrent pas en collision. Un dossier de coupes DICOM est reconnu comme tel, converti en un NIfTI par série dans un emplacement temporaire, et jamais modifié.

2.2 Préparation du volume

Deux opérations, une fois par scan, avant qu'aucun agent ne bouge.

Dans le codePercentiles, classes, interpolation et fichiers qu'ils écrivent

2.3 Ce que voit l'agent

Le volume est rembourré de 33 voxels de chaque côté, pour que le cube contienne encore des données quand l'agent est près du bord. Le rembourrage ajoute seulement une marge autour des données : les positions de l'agent se comptent toujours à partir du coin du scan lui-même.

2.4 La décision

Le réseau est un DenseNet 3D (un réseau convolutif qui lit le petit cube 3D) suivi d'une petite tête de décision (les dernières couches, qui transforment ce que le DenseNet a trouvé en six scores). L'ordre des six déplacements fait partie des poids entraînés : les réordonner ferait marcher l'agent dans la mauvaise direction. La tête se termine par une ReLU, une étape qui met à 0 tout score négatif, héritée de l'entraînement du legacy : si les six scores sont négatifs avant elle, tous deviennent 0 et l'agent prend le premier déplacement. Cela est conservé volontairement, parce que les poids publiés ont été entraînés ainsi (constat). Il existe un réseau par landmark et par échelle, chargé pour chaque paire (scan, landmark) puis libéré : un fichier de poids cassé ou une erreur de mémoire coûte un landmark, pas le scan.

2.5 La recherche

Règles autour de la marche : un déplacement qui sortirait du volume est refusé et l'agent réapparaît à une position aléatoire (n'importe où sur la grille grossière ; à moins de 10 voxels de l'endroit où la recherche fine a commencé sur la grille fine) ; après trois sorties, le landmark est déclaré introuvable.

Le budget se compte en pas, pas en secondes : 900 évaluations du réseau par landmark par défaut, recherche et moyennage final ensemble ; l'épuiser enregistre le landmark comme introuvable. Une limite de temps a été abandonnée volontairement, parce que le résultat dépendait alors de l'occupation de la carte graphique (lancer quatre landmarks à la fois en a un jour fait perdre un que trouvait une exécution plus calme).

Un landmark ne dépend pas des autres. Chaque choix aléatoire vient d'un générateur initialisé à partir de la graine de l'exécution et du nom du landmark, si bien que demander 7 landmarks ou 119 donne les mêmes coordonnées pour les 7 : c'est ce qui permet à ASO de ne demander que ceux dont il a besoin. Les landmarks sont cherchés en parallèle, 8 à la fois au plus ; les auteurs de VISOR ont mesuré 358,7 s avec un seul worker et 128,0 s avec huit sur le scan de référence à 119 landmarks, les mêmes 114 étant placés à chaque fois (leur chiffre, non relancé ici).

Dans le codeLa boucle de l'agent, les bornes, la mémoire, la réapparition et le budget dans le code

2.6 Des voxels aux millimètres, et la sortie

La valeur absolue est héritée du code legacy. Elle est juste quand l'origine est négative sur les trois axes, ce qu'a d'ordinaire un volume orienté en LPS. VISOR ne réoriente plus le volume en LPS avant la recherche, comme le legacy le faisait après septembre 2026, si bien qu'un volume stocké dans une autre orientation peut donner des coordonnées en miroir (constat). Que cela change ou non les prédictions réelles n'a pas été mesuré : il faudrait un scan stocké dans une autre orientation et les poids complets.

Le résultat est un fichier par scan avec tous les landmarks de tous les groupes demandés, dans une copie de l'arborescence du dossier d'entrée, et un rapport d'exécution. Le rapport liste le mode, les groupes et les landmarks demandés, les landmarks qui n'ont pas de modèle entraîné et, pour chaque scan, les landmarks trouvés, ceux qui ne l'ont pas été et pourquoi. L'exécution n'échoue que si aucun scan n'a produit le moindre landmark.

Dans le codeLa conversion de coordonnées, l'écriture des markups et les clés du rapport

2.7 Les poids et les landmarks qui s'exécutent

Les réseaux entraînés se retrouvent grâce aux noms des dossiers qui les contiennent : un dossier par landmark, avec un sous-dossier pour chacune des deux échelles. Un landmark n'est cherché que s'il a un réseau entraîné aux deux échelles. Deux bundles de poids contenant le même landmark sont une erreur, pas un écrasement silencieux, et quelques noms de landmarks alternatifs sont traités comme un seul.

Les landmarks qui s'exécutent sont déterminés par les groupes cochés et les noms listés. Nommer des landmarks remplace les groupes au lieu de les restreindre.

3. Mode IOS : regarder la dent, puis reprojeter

Un maillage n'a pas de volume à parcourir, alors ALI_IOS ramène le problème à des images ordinaires. Pour chaque dent, des caméras virtuelles prennent quelques images d'elle depuis des directions fixes. Un réseau 2D colorie chaque pixel de chaque image avec la classe “ceci est un landmark de type 1”, “type 2”, “type 3” ou “fond”. Les pixels d'une classe sont remontés jusqu'aux triangles du maillage qu'ils montrent, et le landmark est la moyenne des coins de ces triangles, ramenée sur la surface.

3.1 L'entrée et les étiquettes de dents

Tout repose sur le fait de savoir quels sommets appartiennent à quelle dent. Un maillage doit donc porter un tableau de numéros de dents (numérotation universelle : 2 à 15 pour la mâchoire supérieure, 18 à 31 pour la mâchoire inférieure). Avec le serveur, un lot s'exécute en deux passes : d'abord les maillages qui ont déjà des étiquettes, pour que leurs landmarks soient écrits avant que du temps de segmentation soit dépensé ; puis les autres, que l'outil séparé Crown_Seg étiquette, et qui suivent la même méthode. Chaque passe peut échouer sans faire couler l'autre ; l'exécution n'échoue que si aucune des deux n'a rien donné. Un maillage que Crown_Seg n'a pas pu étiqueter est listé comme non traité, avec la raison.

Dans le codeLes noms de tableaux d'étiquettes, les deux passes et l'appel à Crown_Seg

3.2 La sphère unité et l'image

Le résultat est reconverti aux millimètres propres du maillage à la fin. La surface est peinte avec sa propre forme : chaque normale à la surface, un vecteur unité dont les composantes sont dans [-1, 1], devient une couleur, le moteur de rendu éclaire cette surface peinte, et la profondeur est ajoutée comme quatrième canal. Une image fait 224×224 pixels avec un champ de vue de 90 degrés, et chaque pixel montre exactement un triangle, si bien que chaque pixel peut être remonté jusqu'au triangle dont il vient.

Dans le codeComment la mise à l'échelle est faite, les réglages du moteur de rendu et la texture

3.3 Les caméras

La table occlusale est copiée du code legacy, défaut compris : quatre de ses cinq vecteurs de direction ne sont pas de longueur 1 (0,913, 0,913, 0,791 et 0,791, parce que chaque vecteur incliné est divisé par la longueur d'un autre vecteur). Ces quatre caméras se tiennent donc un peu plus près de la dent que ne le dit le rayon. Cela est conservé volontairement, parce que les poids entraînés ont vu exactement ces vues (constat).

Dans le codeLes trois tables de caméras et la façon dont les caméras Mucogingival sont visées

3.4 Le réseau et la décision

Un UNet 2D (un réseau convolutif qui donne une classe à chaque pixel) lit les images d'une dent. Les réseaux occlusal et cervical prennent les images une par une (4 canaux en entrée : couleur et profondeur ; 4 classes en sortie) ; le réseau mucogingival empile ses trois images en une seule entrée (12 canaux, 3 classes en sortie). La classe 0 est le fond ; les classes 1, 2 et 3 sont les types de landmarks, dans l'ordre du catalogue. Pour chaque pixel, la classe est celle dont le score brut zc est le plus élevé (argmax signifie “la classe dont le score est le plus grand”) :

Le code legacy arrondissait les scores O et C à des entiers avant ce choix ; VISOR ne le fait pas, si bien que les résultats O et C ne sont pas garantis identiques à ceux du legacy. Le réseau est chargé une fois par réseau et par mâchoire, et non une fois par dent.

Dans le codeComment le réseau est construit et chargé, et le choix de classe

3.5 Du pixel au point 3D

Les pixels de fond sont écartés. Pour O et C, seuls les triangles qui touchent la dent traitée sont gardés (au moins un coin porte son numéro) ; les points Mucogingival se trouvent sur la gencive, ils gardent donc tout.

Dans le codeComment la moyenne des coins est sommée, et le rattachement au sommet le plus proche

3.6 Le chemin Mucogingival

Il ne tourne que sur la mâchoire inférieure, est désactivé par défaut, et couvre les dents 19 à 31. Trois comportements sont fixés dans le code sans option. Les dents manquantes sont estimées dès qu'au moins quatre dents sont présentes et qu'elles couvrent au moins quatre numéros de dents : leurs caméras sont visées à partir d'une courbe ajustée sur les dents présentes, et le point est signalé dans sa description. Avec moins de dents, les manquantes sont ignorées. Points forcés : si le réseau ne voit aucun pixel de classe 1, les 50 pixels les plus probables la remplacent, et le point est signalé “forced” avec une confiance. Pas de dernier recours : si rien ne tombe sur le maillage, aucun point n'est écrit. Les annotations vont aussi dans le rapport d'exécution. Le module legacy avait par-dessus cela une longue pile de raffinement (mise à niveau, lissage, comblement des trous, et plus) ; VISOR n'en a rien.

Dans le codeLes options MG, les pixels forcés et les entrées du rapport

3.7 Sortie

Un fichier par maillage, <name>_lm_Pred.mrk.json, avec tous les réseaux et toutes les mâchoires ensemble, dans une copie de l'arborescence du dossier d'entrée. Si l'utilisateur nomme des landmarks, seuls les réseaux nécessaires pour les produire s'exécutent, et les autres sont retirés des fichiers et du rapport. Le rapport ajoute les réseaux utilisés, les fichiers de poids qu'il n'a pas pu reconnaître, les mâchoires sans modèle, les landmarks marqués comme douteux, et quels maillages ont été segmentés à la volée.

Sans rien de coché, une exécution CBCT cherche les 119 landmarks. Les réglages IOS du legacy pour la liste de dents et les paramètres de rendu ont disparu : toutes les dents étiquetées sont traitées, et le rendu est fixe. À cause d'un bug, le résumé affiche actuellement toujours “0 scan(s), 0 landmark(s) written” alors que les fichiers se chargent correctement (constat).

Environnement logiciel

Chaque mode s'exécute dans son propre environnement Python isolé sur le serveur, pour que les deux jeux de bibliothèques (qui demandent des versions différentes de PyTorch) ne se rencontrent jamais. Plus rien n'est installé dans Slicer. Une carte graphique est facultative : sans elle, le travail se rabat sur le processeur avec un avertissement.

7. Problèmes connus dans VISOR

Voici les points qu'un utilisateur ou un développeur devrait connaître. Chacun est vérifié dans le code et décrit, avec sa preuve, sur la page de code ; la liste figure aussi dans les constats.

  • Un dossier de série DICOM donne un fichier de sortie caché. Quand l'entrée est le dossier d'une seule série, la sortie s'appelle ._lm_Pred.mrk.json, si bien que les outils en aval qui associent les fichiers par nom ne l'apparieront pas au scan. Preuve.
  • Pas de réorientation en LPS. Un CBCT stocké dans une autre orientation peut donner des coordonnées en miroir. L'effet sur les prédictions réelles n'a pas été mesuré. Preuve.
  • Le résumé du panneau est faux. Il affiche toujours zéro scan et zéro landmark. Les fichiers eux-mêmes se chargent correctement. Preuve.
  • ReLU sur la dernière couche. Conservée du legacy parce que les poids ont été entraînés avec elle. Preuve.
  • Raffinement Mucogingival non porté. La précision sur un ensemble de scans n'a pas été mesurée. Preuve.
  • Deux scans de même nom s'écrasent mutuellement (a.nii.gz et a.nrrd dans un même dossier). Preuve.

8. Littérature

Les réseaux sont ceux qui ont été publiés : ALI_CBCT suit Gillot et al. 2023 (agents sur un volume multi-échelle, échelles 1 mm et 0,3 mm), ALI_IOS l'article CLIP 2022 pour le modèle occlusal (sphère unité, cinq vues par dent, segmentation par patchs). Le chemin Mucogingival n'est pas publié, comme du côté legacy. La bibliographie est celle de l'outil : sources d'ALI ; la page legacy discute chaque article au regard du code dans sa section 8.
