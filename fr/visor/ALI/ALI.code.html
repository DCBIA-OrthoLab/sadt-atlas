ALI sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR d'ALI dans le code, avec des références file:line, des signatures, des arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible du même pipeline, avec les maths, est sur la page de l'atlas.

VISOR Code Atlas (explication) Page Legacy Guide (VISOR)

VISOR exécute les outils dentaires sur un serveur : Slicer ne garde qu'un panneau qui envoie les données et charge les résultats (voir Architecture). Cette page décrit le portage VISOR d'ALI, lu dans le code des dépôts nommés ci-dessous et comparé au module Slicer legacy à 3c67957, qui a sa propre page. « Run for this page » marque ce qui a été exécuté pendant la vérification ; tout le reste a été lu dans le code. Abréviations utilisées pour les références :

  • CB/ = SADT-VISOR 6ba2a78, tools/ALI/ALI_CBCT/src/sadt_ali_cbct/ ; IO/ = SADT-VISOR, tools/ALI/ALI_IOS/src/sadt_ali_ios/ ; CM/ = SADT-VISOR, tools/ALI/common/src/sadt_ali_common/ ;
  • VISOR-serve = VISOR-serve e9a7e5d, fichiers sous server/ sauf si le chemin commence par scripts/ ; Remote = AutomatedDentalToolsRemote 19b95e8 ;
  • legacy = SlicerAutomatedDentalTools 3c67957 ; un chemin legacy comme ALI_CBCT_utils/agent.py se trouve sous ALI_CBCT/, et ALI_IOS_utils/ sous ALI_IOS/.

En un paragraphe : l'outil que choisit l'utilisateur est une façade nommée ALI à deux modes. Le mode CBCT exécute ALI_CBCT, un agent d'apprentissage par renforcement par landmark qui parcourt un volume voxel par voxel à 1 mm puis 0,3 mm (section 3). Le mode IOS exécute ALI_IOS, qui rend chaque dent d'un maillage intra-oral étiqueté depuis des caméras fixes, segmente les rendus avec un UNet 2D et reporte le masque sur le maillage (section 4). Les deux écrivent un .mrk.json par scan plus un run_report.json. Les réseaux et leurs poids sont ceux du legacy ; ce qui a changé est autour d'eux, et plusieurs correctifs legacy ultérieurs (réorientation DICOM, garde-fous du budget de pas, toute la pile de raffinement Mucogingival) n'ont jamais été repris (section 8).

1. Statut et place dans la chaîne

Explication en langage courant et maths : page de l'atlas.

implémenté et testé Le portage est constitué de deux outils serveur, pas d'un seul : ALI_CBCT et ALI_IOS, séparés d'un outil ALI unique le 2026-08-17 (commit SADT-VISOR 2ac7d9d). L'outil que voit l'utilisateur est la façade ALI : elle n'a aucun code propre, seulement dispatch = { "CBCT" = "ALI_CBCT", "IOS" = "ALI_IOS" } (VISOR-serve deployment.toml:205-210). Au démarrage, le serveur construit son formulaire à partir des deux cibles : d'abord un choix mode obligatoire, puis chaque argument des deux, chacun portant un visible_when sur mode si une seule cible l'a (VISOR-serve registry/facade.py:98, :155-166, :236-245). Le panneau Slicer est le module ALIRemote, dont le TOOL_NAME est "ALI", donc il parle à la façade (Remote ALIRemote/ALIRemote.py:92). Les autres outils serveur ne passent pas par la façade : ils appellent par son nom le moteur dont ils ont besoin via le superviseur, sup.run.

3. ALI_CBCT : des agents dans le volume

Explication en langage courant et maths : page de l'atlas.

3.1 Entrée et DICOM

Explication en langage courant et maths : page de l'atlas.

detect() (CB/dispatch.py:80-135) décide de ce qui a été envoyé. Un fichier unique doit se terminer par l'un de .nii .nii.gz .nrrd .nrrd.gz .gipl .gipl.gz (CM/discovery.py:22) ; une surface est refusée par son nom (« run ALI_IOS on surfaces », :102-106). Un dossier est parcouru récursivement ; un dossier mêlant volumes et surfaces est refusé plutôt que traité à moitié (:115-125). Chaque scan est identifié par son chemin relatif à l'entrée (CM/discovery.py:33-45), si bien que deux patients nommés scan.nii.gz dans des sous-dossiers différents n'entrent plus en collision. Un .zip n'atteint jamais ce code : le serveur l'extrait avant run() (:89-91).

DICOM est détecté, pas déclaré. Chaque répertoire qui contient des fichiers mais ni volume ni surface est soumis à GDCM (_dicom_directories, CB/dispatch.py:60-77 ; CB/preprocess.py:130-143), et chaque série trouvée est écrite comme un NIfTI sous le dossier de travail du job, jamais dans l'entrée :

destination_root = os.path.join(work_dir, "dicom_converted")
key = scan_key(directory, root)
destination = os.path.join(destination_root, f"{key.replace(os.sep, '_')}.nii.gz")
...
converted.append((destination, f"{key}.nii.gz"))      # CB/dispatch.py:152-164

Quand l'entrée est le dossier de la série, key vaut "." : voir le premier constat de la section 9. Tout ce qui est intermédiaire vit dans <output_dir>/.ali_work/ et est supprimé dans un finally avant l'écriture du rapport (CB/dispatch.py:196, :249-253).

3.2 Prétraitement

Explication en langage courant et maths : page de l'atlas.

Par scan, dans son propre dossier de travail .ali_work/preprocessed/<key> (CB/engine.py:276-298, :816) :

  1. Écrêtage d'histogramme, correct_histogram (CB/preprocess.py:39-86) : un histogramme de 1000 classes, cumulé et normalisé, des intensités écrêtées entre les points à 1 % et 99 % (la première borne de classe dont la part cumulée dépasse le seuil, donc les limites sont approximatives, :66-77) et dans [-1500, 4000], écrites en int16 avec espacement, origine et direction conservés. Un volume constant est transmis avec un avertissement au lieu d'une division par zéro (:59-64). Mêmes percentiles que l'appel legacy (ALI_CBCT/ALI_CBCT.py:202).
  2. Rééchantillonnage isotrope, set_spacing (CB/preprocess.py:89-127), une fois par espacement dans SCALE_SPACINGS = (1.0, 0.3) (CB/catalog.py:69), vers <stem>_sp1.nii.gz et <stem>_sp0-3.nii.gz. Nouvelle taille size × spacing / wanted, origine décalée pour que le centre physique reste en place, interpolation toujours linéaire, direction copiée de l'entrée (:115, :120).

Le dossier de travail est supprimé dès que le scan est terminé (CB/engine.py:910) : une exécution ne lit jamais les rééchantillonnages d'une autre.

3.3 L'environnement

Explication en langage courant et maths : page de l'atlas.

Environment (CB/environment.py) contient un scan aux deux espacements. load_images (:63-79) lit chaque rééchantillonnage tel que stocké, sans réorientation, le complète de padding = 64/2 + 1 = 33 voxels de chaque côté (CB/engine.py:371-374) et garde l'origine inversée dans l'ordre (z, y, x) du tableau. L'agent ne voit que ceci :

crop = self._crop((np.asarray(center) + self.padding).tolist(), crop_size)
return self._rescale(crop(self.data[scale_key]["image"])).type(torch.float32)
# _rescale = ScaleIntensity(minv=-1.0, maxv=1.0)       # CB/environment.py:49, :102-103

Un cube de 64×64×64 voxels autour de l'agent, remis à l'échelle pour chaque rognage dans [-1, 1] : un côté de 64 mm à l'échelle grossière, 19,2 mm à l'échelle fine.

3.4 L'agent et son réseau

Explication en langage courant et maths : page de l'atlas.

Le réseau est celui du legacy, couche pour couche (CB/brain.py:63-107) : un DenseNet 3D de monai (taux de croissance 34, blocs 6-12-24-16, 1024 caractéristiques) suivi d'une tête de décision 1024-512-256-128-6. Sortie : six scores, un par déplacement dans MOVEMENT_MATRIX, dont l'ordre « is part of the weights' contract » (CB/agent.py:23-34). La prédiction est une direction, pas une position : predict renvoie l'argmax des six (CB/brain.py:138-145). La tête se termine toujours par une ReLU (:90), voir Constats.

def forward(self, x):
    x = nn.functional.relu(self.fc0(x))
    x = nn.functional.relu(self.fc1(x))
    x = nn.functional.relu(self.fc2(x))
    return nn.functional.relu(self.fc3(x))            # CB/brain.py:86-90

Un réseau par échelle. Un Brain est construit, chargé avec torch.load(..., weights_only=True) (CB/brain.py:123-136) et libéré pour chaque paire (scan, landmark) (_walk_one, CB/engine.py:377-425). Un checkpoint cassé ou un manque de mémoire fait perdre un landmark, pas le scan (:405-410).

3.5 La recherche, pas à pas

Explication en langage courant et maths : page de l'atlas.

  1. Départ à l'échelle 0 (1 mm), au centre du volume (CB/agent.py:275-279).
  2. Pas : une passe avant, un déplacement d'un voxel (SPEED_PER_SCALE = (1, 1), :40), une unité retirée du budget (_step, :201-217).
  3. Limites : un déplacement n'est conservé que si chaque coordonnée reste dans [0, size) du volume sans marge (:135-141). Sinon la mémoire courte est effacée et l'agent réapparaît : n'importe où dans le volume à l'échelle 0, à moins de 10 voxels de l'endroit où l'échelle avait commencé à l'échelle 1, tiré d'un générateur initialisé par la graine de l'exécution et le nom du landmark (:148-177, rng_for :54-68). Trois sorties et le landmark n'est pas trouvé (_MAX_ATTEMPTS = 3, :45, :294-295).
  4. Convergence : la nouvelle position est comparée aux 10 dernières positions avant d'être mémorisée (:179-185, :213-217). Tourner en rond signifie être arrivé.
  5. Changement d'échelle : position multipliée par le rapport des espacements (1/0,3), tentatives remises à zéro ; chaque échelle a sa propre mémoire (:114, :187-199).
  6. Focus à l'échelle fine : six redémarrages à 4 voxels le long de ±x, ±y, ±z, chacun parcouru jusqu'à ce qu'il tourne en rond ; la réponse est la moyenne des six atterrissages, ce qui la rend sub-voxel (:219-246).

Le budget se compte en pas, pas en secondes : 900 passes avant par landmark par défaut, ou search_steps (CB/engine.py:55, :81-92). Le même compteur alimente la recherche et les six parcours Focus ; en cas d'épuisement, NotFound est levé, consigné par scan dans landmarks_failed (CB/agent.py:238-243, :283-287 ; CB/engine.py:399-404). Le commentaire du moteur explique pourquoi : une horloge murale faisait dépendre le résultat de l'occupation de la carte, « four agents wide dropped C4 » (CB/agent.py:257-270).

Largeur. Les landmarks sont parcourus dans un pool de processus (spawn), dimensionné une fois par exécution par sup.channels() et plafonné à 8 (CB/engine.py:76, :301-338, :607, :619-626) ; chaque worker garde le scan qu'il a chargé jusqu'à ce que le scan change. Comme l'aléa de chaque agent est dérivé du nom de son landmark et que l'environnement est en lecture seule pendant une recherche, la largeur ne peut déplacer aucune coordonnée (commentaire à CB/engine.py:841-854). Les commentaires de VISOR-serve deployment.toml:93-103 rapportent, sur le scan de référence avec 119 landmarks, 358,7 s en largeur 1 et 128,0 s en largeur 8, 114 landmarks placés à toute largeur (mesuré par les auteurs de VISOR, non relancé).

3.6 Sortie et rapport

Explication en langage courant et maths : page de l'atlas.

La position en voxels à l'échelle fine est reconvertie en millimètres à un seul endroit, le processus parent (CB/engine.py:893-904) :

physical_origin = abs(reference["origin"] / spacing)
coordinates = (np.asarray(position) - physical_origin) * spacing
return np.array([coordinates[2], coordinates[1], coordinates[0]])   # CB/environment.py:116-118

Le abs() est la formule legacy ; elle n'est juste que pour un volume dont l'origine est négative sur les trois axes, et VISOR ne réoriente plus d'abord en LPS (Constats). Puis un fichier par scan, toutes régions confondues, dans une copie de l'arborescence d'entrée :

destination = os.path.join(output_dir, os.path.dirname(key),
    f"{scan_stem(os.path.basename(scan_path))}_lm_{prediction_ID}{MARKUPS_EXTENSION}")
# scan_stem("patient01.nii.gz") == "patient01"      # CB/engine.py:152-158, :916-921

L'écrivain, partagé par les deux moteurs (CM/markups.py:104-129), met chaque point dans coordinateSystem: "LPS" (:26), verrouillé (:96), avec display.visibility: true (:41) et une description vide pour les points CBCT (CB/engine.py:921 n'en passe aucune). run_report.json (CB/engine.py:685-722, CB/dispatch.py:248-266) consigne mode, device, seed, regions, landmarks_selected, landmarks_requested, landmarks_without_model, landmarks_ungrouped, par scan cases (status, landmarks_found, landmarks_failed avec la raison, produced), summary, dicom_series_converted, model_bundle et les durées. L'exécution n'échoue que si aucun scan n'a produit de landmark (:644-650).

3.7 Poids et sélection

discover_weights (CB/engine.py:165-224) parcourt le lot récursivement et conserve la disposition legacy, lue dans les noms de dossiers :

<bundle>/…/<LANDMARK>/<1 | 0-3>/<anything>.pth
             ^ alias-folded       ^ scale key = str(spacing) with "." → "-"

Trois différences avec le GetBrain legacy : un landmark a besoin d'un checkpoint aux deux échelles ou il est écarté (:219-224) ; deux lots sous un même dossier contenant le même landmark sont une erreur, pas un écrasement silencieux (:198-211) ; des alias comme UR3OI → UR3OIP sont fusionnés (CB/catalog.py:52-57). Sélection (requested_landmarks, :227-273) : une liste landmarks non vide remplace les régions ; sinon chaque landmark du catalogue des régions cochées s'exécute, plus tout landmark du lot appartenant à ces régions que le catalogue ne connaît pas (signalé comme landmarks_ungrouped). Ne nommer ni région ni landmark est une erreur (CB/dispatch.py:224-232). La copie locale de DATA/ALI/models utilisée pour cette page contient 22 dossiers de landmarks, pas le lot complet.

4. ALI_IOS : rendu, une dent à la fois

Explication en langage courant et maths : page de l'atlas.

4.1 Entrée, labels de dents et passe Crown_Seg

Explication en langage courant et maths : page de l'atlas.

Acceptés : .vtk et .stl (CM/discovery.py:23 ; lecteur IO/surface.py:33-59), seuls ou dans un dossier parcouru récursivement ; les volumes sont refusés par leur nom (IO/dispatch.py:105-142). Tout dépend d'un tableau de labels de dents, cherché sous PredictedID, UniversalID ou Universal_ID (IO/surface.py:19, :62-69), en numérotation Universal : 2 à 15 en haut, 18 à 31 en bas (IO/engine.py:312-316).

Avec un superviseur (toute exécution passant par le serveur), identify divise le lot (IO/dispatch.py:486-500) et l'exécute en deux passes :

  1. Passe 1 : les maillages étiquetés, d'un coup, pour que leurs landmarks soient sur le disque avant qu'aucune segmentation soit dépensée (:534-538).
  2. Crown_Seg : les maillages non étiquetés sont liés sous leurs clés dans .ali_work/to_segment/ et transmis en un seul appel (_segment, :193-266) : 
    produced = sup.run(CROWN_TOOL, meshes=staged_root, model=model_path, device=device)   # :229-237
    model est le dossier qu'on a donné à ALI_IOS, DATA/ALI/models, où Crown_Seg cherche son propre checkpoint (docstring :206-213). Chaque <stem>_Seg.vtk renvoyé est renommé du nom de l'entrée pour que le fichier de landmarks garde le nom du patient (_rename_to_input, :284-305).
  3. Passe 2 : les maillages nouvellement étiquetés (:572). L'une ou l'autre passe peut échouer sans couler l'autre ; l'exécution n'échoue que si aucune des deux n'a rien produit (:511-532, :574-586). Un maillage que Crown_Seg n'a pas pu étiqueter est signalé comme non traité avec la raison.

4.2 Sphère unité et texture

Explication en langage courant et maths : page de l'atlas.

scale_to_unit (IO/surface.py:72-103) centre une copie du maillage sur le milieu de sa boîte englobante et la met à l'échelle par 1 / ||max − centre|| ; upscale (:106-108) fait l'opération inverse à la fin. La texture est la normale de chaque point ramenée dans [0, 1] : (normal * 0.5 + 0.5) (:122-128). Le moteur de rendu est celui du legacy (IO/render.py:115-145) :

cameras = FoVPerspectiveCameras(znear=0.01, zfar=10, fov=90)
RasterizationSettings(image_size=224, blur_radius=0, faces_per_pixel=1)
HardPhongShader(..., lights=PointLights(...))

Les trois réglages de rastérisation sont des constantes (IO/render.py:79-81), et non plus des arguments : rastérisation dure, une face par pixel, ce qui fait de pix_to_face une table de correspondance du pixel vers la face.

4.4 Le réseau et le décodage

Explication en langage courant et maths : page de l'atlas.

Un UNet 2D de monai, canaux (16, 32, 64, 128, 256, 512), pas (2, 2, 2, 2, 2), 4 unités résiduelles ; O et C prennent une image par caméra comme lot (4 canaux en entrée, 4 classes en sortie), MG empile ses trois vues en une entrée de 12 canaux (3 classes en sortie) (IO/engine.py:160-186). Chargé avec weights_only=True, une fois par (réseau, mâchoire), et non une fois par dent (:344-353). La classe 0 est le fond ; les classes 1, 2, 3 sont les types de landmarks dans l'ordre du catalogue. Le décodage est un argmax sur les logits bruts pour tous les réseaux :

classes = torch.argmax(predictions, dim=1)
hits = (classes == channel).nonzero(as_tuple=False)
picked = pix_to_face[hits[:, 0], 0, hits[:, 1], hits[:, 2], 0].long()
return picked[picked >= 0].tolist()                 # IO/engine.py:216-226

Le legacy convertissait les logits de O et C en int16 avant l'argmax ; VISOR ne le fait pas, si bien que ses résultats O et C diffèrent de ceux du legacy (section 8).

4.5 Du pixel au point 3D

Explication en langage courant et maths : page de l'atlas.

  1. Les faces sous les pixels de la classe, les pixels de fond (-1) écartés (IO/engine.py:226).
  2. O et C seulement : garder les faces qui touchent l'étiquette propre de la dent (faces_on_tooth, IO/surface.py:180-211 ; appelée à IO/engine.py:465). MG garde toutes les faces : son point se trouve sur la gencive.
  3. La moyenne des sommets de ces faces : les trois coins du triangle de chaque pixel sont ajoutés, si bien qu'une face touchée par plusieurs pixels compte plusieurs fois (la liste de faces garde ses répétitions, IO/engine.py:224, :272-276). La somme est accumulée séquentiellement en float32 pour que le résultat soit identique au bit près à la boucle du legacy (_landmark_position, IO/engine.py:229-278).
  4. Ramené sur le sommet le plus proche du maillage (FindClosestPoint renvoie un identifiant de point) avec vtkOctreePointLocator (:277), puis upscale pour revenir aux millimètres du maillage.

4.6 Le chemin Mucogingival

Explication en langage courant et maths : page de l'atlas.

MG ne tourne que sur la mâchoire inférieure (NETWORK_JAWS, IO/catalog.py:48), désactivé par défaut, sur les 13 dents 19 à 31 quelles que soient les étiquettes (IO/engine.py:324-332). Trois comportements sont fixés dans le code, sans option :

  • les dents manquantes sont estimées quand au moins 4 dents sont présentes et qu'elles couvrent au moins 4 numéros, sinon rien n'est estimé et les dents manquantes sont ignorées (IO/render.py:347-348) : caméras visées à partir d'un ajustement quadratique de l'arcade sur les dents présentes (render.estimate_missing_teeth, IO/render.py:320-363 ; IO/engine.py:354-358), le point étant annoté « cameras aimed from an arch fit, tooth not segmented » (:567-570) ;
  • points forcés : si la classe 1 ne l'emporte sur aucun pixel, les 50 pixels les plus probables la remplacent, avec l'annotation forced (confidence 0.xyz) (MG_FORCE_TOPK, :472, :538-552) ;
  • pas de dernier recours : si rien ne tombe sur le maillage, aucun point n'est écrit (:563-565).

Les annotations vont dans la description du point et dans landmarks_degraded du rapport (IO/engine.py:414-419). La pile de raffinement du legacy (mise à niveau de l'arcade, échelle de l'arcade, raffinement, lissage, ajustement à la surface, complétion de ligne, comblement des trous, choix de patchs) n'a pas d'équivalent : une seule passe par dent.

4.7 Sortie, poids et filtrage

9. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Bug confirmé · un dossier de série DICOM donne un fichier de sortie caché

Choisissez comme entrée le dossier d'une série DICOM (le cas que le panneau invite à faire) et la clé du scan devient "." : _dicom_directories inclut la racine elle-même (CB/dispatch.py:70-77), scan_key vaut os.path.relpath(root, root) (CM/discovery.py:43), le fichier converti s'appelle ..nii.gz (CB/dispatch.py:156, :164) et scan_stem("..nii.gz") vaut "." (CB/engine.py:152-158). La sortie est ._lm_Pred.mrk.json, un fichier caché. Exécuté pour cette page : scan_key et scan_stem renvoient exactement ces valeurs. Une exécution complète sur une vraie série n'a pas été refaite ici. Les outils en aval qui associent les fichiers par préfixe de nom n'apparieront pas un tel fichier à un scan.

Piège · pas de réorientation en LPS

Le legacy réoriente chaque volume en LPS avant que les agents le parcourent, et en donne la raison dans un commentaire : un volume stocké dans une autre orientation « leur arrive en miroir » (ALI_CBCT_utils/environment.py:66-72). VISOR ne le fait pas. Exécuté pour cette page sur le vrai Environment.physical_position (CB/environment.py:108-118) : sur un volume de direction identité et d'origine (-30,-25,-20), le voxel (5,20,10) devient (-25,-5,-10), le vrai point ; sur un volume de direction diag(-1,-1,1) et d'origine (30,25,-20), la fonction renvoie toujours (-25,-5,-10) alors que le vrai point physique est (25,5,-10), x et y inversés. Aucun test de VISOR ne mentionne la direction ou l'orientation (grep -i sur ALI_CBCT/tests : aucun résultat). Ce que cela fait à une vraie prédiction n'a pas été mesuré : il faudrait un scan stocké dans une orientation autre que LPS et les poids complets. Le scan de test publié est stocké en LPS, il ne peut donc pas montrer le problème.

Bug confirmé · ReLU sur la dernière couche, conservé du legacy

La tête de décision se termine par une ReLU (CB/brain.py:90 ; legacy ALI_CBCT_utils/brain.py:35) : les six scores sont ≥ 0, et si toutes les pré-activations sont négatives ils valent tous 0 et argmax renvoie 0, « up ». À ne pas « corriger » sans réentraîner : les poids publiés ont été entraînés avec cette tête.

Bug confirmé · le panneau Slicer affiche « 0 scan(s), 0 landmark(s) written »

ALIRemote._summarize lit report.get("scans") (Remote ALIRemote/ALIRemote.py:216), mais les deux moteurs écrivent les enregistrements par scan sous cases (CB/engine.py:708, IO/engine.py:704). Rien entre les deux ne renomme la clé (la fusion de rapports dans ServerToolsCore/ServerToolsCoreLib/base_widget.py:119 est générique). Le message de fin d'exécution dit donc toujours qu'il n'y a aucun scan et aucun landmark, et ne liste jamais les landmarks qui n'ont pas convergé (ALIRemote.py:216-232). Exécuté pour cette page : _summarize, extrait du module, auquel on donne un rapport contenant un cas avec deux landmarks trouvés et un en échec, affiche « 0 scan(s), 0 landmark(s) written. » et aucun échec. Les fichiers de résultat eux-mêmes se chargent correctement (_findMarkupFiles parcourt le dossier). Deux restes liés : configureFields cherche un champ prediction_ID que la façade ne publie plus (ALIRemote.py:129), et le jeu de test du client déclare encore cbct_regions et prediction_ID et pas de mode (ALIRemote/Testing/Python/test_ali_client.py:101, :409).

Piège · la pile de raffinement Mucogingival n'est pas portée

Voir Ce qui a changé par rapport à la logique du legacy. Pour les 13 landmarks mucogingivaux, le legacy à 3c67957 place chaque point, puis lisse, ajuste à la surface, complète et comble la ligne ; VISOR place chacun en une seule passe et estime toujours les dents absentes (IO/engine.py:354-358). Le README de VISOR rapporte une arcade inférieure étiquetée : 13 landmarks sur 13, aucun forcé, 12 identiques à l'amont et un à 0,179 mm, et indique que la précision n'est pas établie faute de scans annotés (tools/ALI/README.md:292-300). Ce que coûtent les étapes manquantes sur un ensemble de scans n'a pas été mesuré.

Piège · deux scans de même radical s'écrasent mutuellement

Le chemin de sortie est dirname(key)/<stem>_lm_Pred.mrk.json où le radical perd l'extension (CB/engine.py:916-921), si bien que a.nii.gz et a.nrrd dans le même dossier écrivent le même fichier sans aucune erreur. Exécuté pour cette page : scan_stem renvoie a pour les deux noms ; l'écrasement lui-même n'a pas été exécuté.

Note · seuls les points Mucogingival portent une description

Les points O et C, et tous les points d'ALI_CBCT, ont une description vide quelle que soit leur qualité : les annotations ne sont remplies que par le chemin MG (IO/engine.py:567-575, écrites par :426) et ALI_CBCT n'en passe aucune (CB/engine.py:921). Le landmarks_degraded du rapport d'exécution (IO/engine.py:414-419) est l'autre endroit où un doute sur MG est consigné.

Note · du bruit dans le rapport d'exécution IOS

ALI_IOS reçoit tout le dossier de modèles, qui contient aussi les checkpoints CBCT (VISOR-serve scripts/data-manifest.yml:121-130), et liste chaque .pth dont le nom n'a ni élément de réseau (O, C, MG) ni élément de mâchoire sous models_unrecognized (IO/engine.py:98-111, :703). Sur un bundle complet, cela fait une longue liste de noms de fichiers CBCT dans chaque rapport IOS. Ce n'est pas un échec ; non mesuré sur le bundle complet.

Note · doublon mort dans ALI_CBCT

CB/engine.py:644-650 et :651-657 sont le même bloc (calculer processed, lever « ALI produced no landmarks for any scan » s'il est vide) écrit deux fois de suite. Sans effet.

Vérifié · la table des caméras O est reproduite volontairement

Deux directions O sont divisées par la norme d'un autre vecteur (np.array([0.5, 0.0, 1.0]) / _norm([0.5, 0.5, 1.0])), si bien qu'elles ont une longueur de 0,913 ou 0,791 au lieu de 1 (calculé : 1,118/1,2247 et 1,118/1,414). Le portage les conserve délibérément, parce que les poids ont été entraînés sur ces vues (IO/render.py:8-12, table :39-54 ; legacy ALI_IOS_utils/model.py:66-77).

Vérifié · landmarks indépendants, recherches bornées

Le résultat d'un landmark ne dépend que du scan, des poids et de la graine, jamais des autres landmarks demandés (CB/agent.py:54-68 ; c'est ce qui permet à ASO d'en demander 7 et à une exécution autonome d'en demander 119). Les bornes de déplacement sont testées coordonnée par coordonnée (CB/agent.py:135-141) et la recherche comme le raffinement s'arrêtent sur le même compteur de pas (CB/agent.py:238-243, :272-286). Les poids sont chargés avec weights_only=True (CB/brain.py:133-135).

10. Littérature

Les réseaux sont ceux qui ont été publiés : ALI_CBCT suit Gillot et al. 2023 (agents sur un volume multi-échelle, échelles 1 mm et 0,3 mm, CB/catalog.py:69), ALI_IOS l'article CLIP 2022 pour le modèle O (sphère unité, cinq vues par dent, segmentation par patchs, IO/surface.py:72, IO/render.py:39-54).
