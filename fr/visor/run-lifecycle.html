Une exécution, pas à pas

Ce qui se passe entre un clic dans Slicer et le retour des fichiers : les routes exposées par le serveur, les quinze étapes que traverse un POST /run/{tool}, les phases que voit un observateur, comment une exécution est admise, détachée, annulée, mise en pause et rembobinée, et à quel statut HTTP aboutit chaque échec. Chaque affirmation cite la ligne où elle a été lue.

Note

Cette page décrit VISOR, la génération serveur, et non le code Slicer legacy que documente le reste de ce site. Les citations sont file:line suivies du dépôt : VISOR-serve au commit e9a7e5d (lignes de server/main.py sauf chemin indiqué), AutomatedDentalToolsRemote (le client Slicer) à 19b95e8, SADT-VISOR (les outils) à 6ba2a78. Les dépôts portent leur propre documentation, dont plusieurs pages sont plus anciennes que le code ; quand les deux divergent, cette page suit le code et le dit dans un encadré. Ce qui protège le transport et les données stockées est sur la page de sécurité ; la façon dont les pièces s'assemblent est sur la page d'architecture.

1. Les routes

Dix-huit gestionnaires de routes sont déclarés dans main.py, et deux d'entre eux répondent sans jeton. Les décorateurs sont la seule autorité : docs/ARCHITECTURE.md:34-42 en liste cinq, server/README.md:49 et suivantes en liste davantage mais pas toutes. « Gate » dans le tableau est la dépendance maintenance.require_accepting : tant qu'un opérateur a fermé la porte avec POST /maintenance, la route répond 503 avec Retry-After: 10 (wire/maintenance.py:113-146). Les lectures, l'annulation et la suppression ne sont volontairement pas soumises à ce verrou, de sorte qu'une exécution déjà en cours peut toujours être observée et récupérée.

Quatre noms sont réservés sur le fil. Le statut 499 signifie « l'exécution a été annulée » et n'est volontairement pas un code standard, pour qu'un client distingue une annulation d'un échec sans lire un message (:174).

Piège

Il n'y a ni GET /benchmarks, ni /benchmarks/view, ni aucune page HTML dans main.py. La clé de réglage SADT_BENCHMARK_DIR (config.py:172), un bloc de commentaires sur « the other two pages » (main.py:409-420), un import HTMLResponse inutilisé (main.py:26) et une description de GET /benchmarks/view dans CLAUDE.md:1192 sont des restes de routes qui n'ont jamais été fusionnées. Une recherche de ces routes dans main n'en trouve pas non plus.

2. Le chemin nominal, de la soumission au nettoyage

Une exécution, sur le chemin bloquant (le client garde une requête HTTP ouverte pendant toute l'exécution). La variante détachée est à la section 4. Les trois colonnes du schéma sont trois processus différents : le module Slicer, le processus FastAPI, et un interpréteur Python distinct qui appartient à l'outil.

  1. Envoi par parties. Le client envoie les grandes entrées par POST /uploads et PUT /uploads/{id}/parts/{n} : parties de 8 MB par défaut, bornées par le serveur entre 1 et 64 MB (wire/transfer.py:204-215), quatre connexions en parallèle, un SHA-256 de chaque partie dans X-Part-SHA256, jusqu'à quatre essais par partie (AutomatedDentalToolsRemote ServerToolsCoreLib/transfer.py:62-67, 309). Sur le chemin bloquant, un fichier de moins de deux parties, 16 MB, passe plutôt en ligne dans le formulaire ; sur le chemin détaché, celui par défaut du client, chaque fichier passe par /uploads (client client.py:1106-1121). Sur le serveur, la session vit sur disque, le blob est pré-dimensionné avec os.truncate et chaque partie est écrite à son décalage avec os.pwrite : rien n'est réassemblé, et à l'exécution le blob est renommé dans le dossier de travail plutôt que copié (claim_upload, wire/transfer.py:279).
  2. L'exécution est enregistrée avant la lecture du formulaire. run_tool (main.py:1806) prend X-Run-Id et ouvre d'abord le dossier de l'exécution, parce que le client ouvre son flux d'événements depuis un autre thread et que les deux ne peuvent pas être ordonnés. Un identifiant mal formé donne 400, un identifiant déjà pris 409 (wire/runs.py:178-213).
  3. Outil et mode. _run_tool (main.py:1833) résout l'outil (404 s'il est inconnu), lit le formulaire, déballe __uploads__. Si l'outil est une façade (ALI, AREG), il retire le champ mode, remplace la façade par sa cible et abandonne tout argument que la cible ne déclare pas ; un mode manquant ou inconnu donne 422 (main.py:1888-1917).
  4. Mise en place. Chaque entrée est écrite dans TEMP_DIR/<mkdtemp>/<argument>/<safe name>.<ext>. Le nom de fichier du patient est conservé, filtré à [A-Za-z0-9_.-] (_safe_stem, main.py:1105), et la phase est staging avec le message « input k of n », jamais le nom du fichier. Refusés ici : un argument inconnu (422), un fichier envoyé à un argument scalaire (400), une extension interdite (400), une taille au-dessus de la limite (413), un fichier vide ou un .gz tronqué (400, _reject_a_truncated_gzip, :1172). Un .zip donné à un argument path est extrait par le serveur, avec refus du zip-slip, des membres absolus et des liens symboliques, et un plafond de 2000 MB sur la taille extraite (file_utils.py:125, config.py:241).
  5. Fichiers hébergés. Un modèle ou un fichier de test choisi par son nom est résolu par le magasin de données (404 s'il est absent). DATA_DIR est en lecture seule, une archive pour un argument de dossier est donc extraite dans le dossier de travail.
  6. Validation, hors de la boucle d'événements. tool.invoke s'exécute dans un thread de travail sous un CapacityLimiter de MAX_CONCURRENT_TOOLS (4 ; main.py:183-187, :2081-2083). SchemaTool.invoke valide contre le schéma publié (422 sur ToolArgumentError), transforme les champs à choix multiples en listes et appelle dispatch.dispatch.
  7. Dispatch. dispatch (execution/dispatch.py:1080) vérifie que l'outil a un interpréteur, crée TEMP_DIR/job_<uuid>/{input,output}, complète les paramètres (output_dir est toujours celui de la tâche, device est injecté depuis les réglages, un argument de modèle sans nom reçoit le dossier de modèles de l'outil), écrit job.json et calcule le délai : deployment_config.timeout_seconds(tool.name) or None (dispatch.py:1137).
  8. Admission. L'exécution demande de la place dans un budget d'octets et de cœurs (section 5). Si elle doit attendre, la phase devient queued_gpu, une seule fois ; le client peut encore annuler.
  9. L'outil démarre. Popen([venv/python, runner.py, --job job.json]) avec stdout et stderr vers des fichiers, cwd le dossier de la tâche et start_new_session=True (dispatch.py:618). L'environnement est celui du serveur, sans API_TOKEN, avec des plafonds de threads (OMP_NUM_THREADS, MKL_, OPENBLAS_, NUMEXPR_, VECLIB_, ITK_GLOBAL_DEFAULT_NUMBER_OF_THREADS) et les variables SADT_API, SADT_JOB_ID, SADT_JOB_DIR, SADT_PROGRESS_FILE et SADT_SUPERVISOR_DEADLINE (_child_environment, dispatch.py:540). L'identifiant de groupe de processus est écrit sur disque ; la phase est running.
  10. Le runner. runner.py est exécuté par l'interpréteur propre à l'outil, n'utilise que la bibliothèque standard (Python 3.9 à 3.13), importe l'unique paquet sous le src/ de l'outil, convertit les arguments selon leur annotation, appelle run(), échantillonne le pic de VRAM, la RSS et les cœurs avec _TreeSampler (runner.py:405) et écrit result.json de façon atomique : {"result", "peak_vram_bytes", "peak_rss_bytes", "peak_cpu_cores", "channels", "vram_source"} ou {"error": {"type", "message"}}.
  11. Le résultat est lu. Pas de result.json après un code de sortie 0 donne une ToolExecutionError ; une error devient une ToolFailure(type, message). Les mesures alimentent la table des coûts et un événement portant measured.
  12. Empaquetage. _finish_run (main.py:2200) pose la phase packaging. Une sortie de type files devient un zip nommé {tool}_{stem}.zip au niveau de compression 1, les membres déjà compressés (.gz, .zip, .xlsx et assimilés) étant stockés tels quels (file_utils.py:199-251, config.py:252). Une sortie text est renvoyée sous la forme {"result": ...}.
  13. Livraison. Deux façons. Par défaut, le fichier est diffusé en flux avec FileResponse et supprimé dans une tâche d'arrière-plan après la réponse. Si le client a envoyé X-Result-Delivery: reference et que le fichier fait au moins RESULT_REFERENCE_MIN_MB (16 ; config.py:249), le fichier est déplacé (renommé) dans le magasin de résultats et la réponse est {"result_ref": {result_id, filename, media_type, size}} (wire/transfer.py:325-349) ; le client récupère alors GET /results/{id} avec Range, quatre connexions, vérifie le CRC de chaque membre du zip, et termine par DELETE /results/{id} (client client.py:1696-1773).
  14. L'enregistrement de l'exécution. _tracked_run (main.py:1610) écrit done et planifie runs.discard comme tâche d'arrière-plan, de sorte que le dossier survit à la fin du flux.
  15. Nettoyage. Les entrées mises en place partent dans le finally de _run_tool ; le dossier de travail et les sorties dans des tâches d'arrière-plan après le flux ; toute erreur supprime immédiatement. Les résultats et les envois inachevés sont balayés par un reaper toutes les 60 s une fois inactifs depuis 900 s (config.py:245-246, _reaper_loop main.py:63-81). Le journal du serveur enregistre le point d'accès, l'outil, le statut, la durée et la taille, et jamais le contenu des fichiers, les valeurs des arguments ni les messages de progression (_log_served, main.py:351-371).
Vérifié

Le modèle de processus est le cœur du design : le serveur n'importe jamais un outil. SchemaTool.invoke passe toujours par dispatch (registry/schema_tool.py:812-822) et SchemaTool.run lève RuntimeError (:840-844). Seules les deux fixtures, Example_Tool et Test_Tool, sont importées dans le processus. L'interpréteur de l'outil, torch et la VRAM disparaissent donc avec le processus à la fin de l'exécution.

3. Phases, états et flux d'événements

Une exécution a une phase (ce qu'elle fait) et un état (ce qu'un observateur doit en conclure). Les phases sont received, staging, queued_gpu, running, packaging, done, failed, cancelled, paused (wire/runs.py:73-81). Les états sont pending (received, staging, queued_gpu), running (running, packaging), done, failed, cancelled (les trois terminaux) et paused, qui n'est pas terminal (:83-93).

GET /runs/{id}/events est un flux Server-Sent Events. Il commence au premier événement, y compris ceux écrits avant la connexion de l'observateur, parce que l'observateur est ouvert depuis un second thread et ne peut pas être ordonné par rapport au POST (main.py:1004-1048). Le fichier est interrogé toutes les 0,25 s depuis un thread de travail (RUN_EVENT_POLL_SECONDS, config.py:275) et chaque trame est data: {json}. Le flux s'arrête sur un événement terminal, ou quand le dossier de l'exécution a disparu.

Un événement est {seq, at, state, phase, fraction, message, depth}, plus tool (le nom d'un appel imbriqué, [A-Za-z0-9_-]{1,64}), result (écrit uniquement par le serveur) et measured (vram_bytes, ram_bytes, cpu_cores, channels) (_normalised, wire/runs.py:473-539). seq est le numéro de ligne au moment de la lecture et n'est jamais stocké. message est coupé à 200 caractères sans saut de ligne. Une ligne écrite par un outil est toujours lue comme running : seul le serveur peut déclarer done, failed ou cancelled.

Sur disque, TEMP_DIR/runs/<run_id>/ contient events.jsonl, meta.json, pgid, cancel et, à l'arrêt, paused.json. Les ajouts ne prennent aucun verrou : chaque enregistrement est un seul write() sous MAX_RECORD_BYTES (4096), atomique avec O_APPEND sous POSIX (wire/runs.py:137). Le flux est plafonné à MAX_RUN_EVENTS = 2000 événements ; au-delà du plafond, un événement « not reported » est livré et rien de plus, les événements terminaux n'étant jamais coupés (_capped, wire/runs.py:611-635).

Progression d'un outil. Un outil signale sa progression en ajoutant {"fraction": ..., "message": ...} au fichier désigné par SADT_PROGRESS_FILE ; sup.progress(fraction, message) écrit dans le même fichier (runner._append_progress, runner.py:1058). La fraction est un nombre entre 0 et 1 ou est absente, et le client n'en invente pas.

Piège

Après un échec, le dossier de l'exécution est supprimé aussitôt : _tracked_run écrit failed et appelle runs.discard dans le même souffle (main.py:1636-1642). Un observateur qui n'avait pas encore lu l'événement terminal trouve alors le dossier disparu, et son flux s'arrête simplement : EventReader.read positionne finished sur le fichier manquant et ne renvoie rien (wire/runs.py:567-578). L'échec lui-même est toujours signalé par le POST. Après un succès, le dossier survit à la fin de la réponse.

4. Mode détaché

Avec X-Run-Delivery: detached, le serveur répond 202 dès que les entrées sont mises en place, et l'exécution continue comme tâche d'arrière-plan ; son événement terminal porte le result_ref (_detach main.py:1401, _detached_run :1354). Il exige X-Run-Id (sinon 400) et refuse tout fichier dans le corps (400) : chaque entrée doit être arrivée par /uploads. Le dossier de l'exécution n'est pas supprimé à la fin, parce que le client n'a pas encore lu l'événement terminal ; il expire après RUN_TTL_SECONDS = 900 s d'inactivité, rafraîchi à chaque lecture (config.py:263).

La raison est un délai d'attente. Le commentaire au-dessus de l'en-tête le dit clairement : le délai de lecture du POST du client Slicer est de 600 s avec un plafond d'une heure, le serveur est dimensionné pour des cohortes qui prennent plus longtemps, et une déconnexion n'a jamais arrêté une exécution, elle n'a fait que jeter la réponse (main.py:157-160). En mode détaché, le client ne garde aucune longue requête : il attend sur le flux d'événements, qui se reconnecte et dédoublonne sur seq. Le client l'active par défaut (DETACHED_RUNS = True, config.py:90 de l'extension Remote) et se rabat sur le chemin bloquant quand il demande stop_after, parce que l'enregistrement de checkpoint n'est livré que dans le corps du POST (client.py:1094-1106).

Défaut confirmé dans le code

main.py:2332 lève ToolExecutionError, un nom que main.py n'importe jamais : le module importe dispatch et utilise dispatch.ToolFailure et dispatch.RunCancelled par attribut (la seule occurrence du nom nu dans le fichier est ce raise). La branche est « exécution détachée, et le stockage du résultat par référence a échoué avec OSError ». Elle lève une NameError au lieu du message prévu, si bien que le rapport d'échec serait faux. La branche est rare, et aucun test n'a été lancé dessus pour cette page.

5. Admission : un budget, pas un compteur

Une exécution ne prend pas un emplacement, elle réserve de la place. Le code d'admission de execution/admission.py tient un Budget (:239) d'octets de RAM, d'octets de VRAM et de cœurs, et une file d'exécutions qui attendent de la place dedans.

  • FIFO par processus. Les tickets sont servis dans l'ordre ; seule l'exécution en tête peut être admise. Le module énonce le compromis : un blocage en tête de file en échange d'un ordre prévisible (admission.py:239-251). reserve(candidates) essaie des formes de largeur décroissante et prend la première qui tient (:446-530).
  • Trois règles de sécurité. Un outil dont le coût n'a jamais été mesuré réserve tout le budget et s'exécute seul. Une demande plus grande que le budget s'exécute tout de même, seule, quand la machine est vide. La mémoire réellement libre sur la carte est aussi vérifiée (admission.py:22-33). Une marge de sécurité de 1,3 est appliquée (SAFETY_MARGIN, :49).
  • D'où vient le budget. resources.py lit le cgroup (v2, puis v1) avant le noyau, et nvidia-smi pour la VRAM libre. La part est SADT_RESOURCE_SHARE = 0,75 (config.py:219) ; le budget est découpé en parts par tâche par SADT_EXPECTED_CLIENTS = 4 (config.py:234) ; SADT_CPU_BUDGET, SADT_RAM_BUDGET, SADT_VRAM_BUDGET et les formes *_PER_JOB les remplacent et acceptent des valeurs comme 75%, 8 ou 16GB (config.py:213-237). Les clients attendus sont une déclaration : il y a un jeton partagé et aucune identité de client, le serveur ne peut donc pas compter les postes de travail.
  • Un plancher sur les cœurs. SADT_MIN_CPUS_PER_JOB = 4 (config.py:161) : en dessous, une exécution attend plutôt que d'être admise affamée.
  • GPU ou non. On suppose qu'une exécution veut la carte, sauf si elle déclare un device qui se résout en cpu ou mps (dispatch.uses_the_gpu, :95).
  • Coûts appris. execution/costs.py garde le maximum des COST_WINDOW = 20 dernières exécutions de chaque outil, par ressource, et ajuste une droite fixe + marginal × largeur dès que deux largeurs distinctes ont été vues (_fit :429, _predict :404). « Mesuré à 0 » et « jamais mesuré » sont distincts (vram_known). Une lecture de la carte entière n'est apprise qu'à partir d'une exécution qui était seule (dispatch._keep_measurements, :826-914). La table vit dans SCHEMA_CACHE_DIR.
  • Largeur et canaux. Un outil qui déclare num_workers ou batch_size (CHANNEL_ARGUMENTS, concurrency.py:145) peut traiter plusieurs éléments à la fois ; width_from dans deployment.toml dit quel argument compter. L'outil demande sup.channels(wanted) et reçoit min(affordable, wanted, SADT_CHANNELS, ceiling), jamais moins de 1 (runner.py:2134). SADT_MAX_CHANNELS = 0 signifie aucun plafond (config.py:130). Une exécution qui n'ouvre qu'un canal garde toute sa réservation.
  • Nouvelles tentatives mémoire. Si une exécution meurt faute de mémoire (OutOfMemoryError, CudaOutOfMemoryError, MemoryError, ou SIGKILL sans result.json, _out_of_memory dispatch.py:933), elle est relancée, jusqu'à MEMORY_RETRIES = 2 fois, avec la réservation multipliée par MEMORY_RETRY_GROWTH = 1,5 à chaque fois, sauf si elle détient déjà toute la machine. La tâche est réinitialisée et un événement queued_gpu se lit « out of memory; waiting for more room (try N) » (dispatch.py:1158-1228). C'est ce qui rend sûre la fenêtre de 20 exécutions : un pic sorti de la fenêtre est rattrapé par la nouvelle tentative.
  • Les appels imbriqués sautent l'admission. Un outil appelé avec sup.run est un sous-processus de son parent, qui détient la réservation. Le budget d'octets est donc divisé vers le bas entre les canaux de chaque niveau (concurrency.child_budget, runner._child_channel_budget :1493).
  • La file est par processus. Le singleton est créé par budget() (admission.py:541-553) derrière un threading.Condition : uvicorn --workers N créerait N budgets. L'image démarre un seul worker (docker/Dockerfile:232).
  • Deux limites s'empilent. Le CapacityLimiter (4 threads) compte les attentes d'admission ; le budget compte les octets. Une cinquième exécution concurrente attend avant d'être visible comme queued_gpu.

Un outil lance d'autres outils par le superviseur, l'objet sup que reçoit un run() quand il déclare un paramètre nommé sup, réservé aux mots-clés et sans annotation (_takes_supervisor, runner.py:1140 ; classe _Supervisor, :1685). sup.run(tool, **params) rentre de nouveau dans runner.py avec l'interpréteur du voisin, dans le même groupe de processus : pas d'appel HTTP, pas de nouvelle admission. Le voisin s'exécute dans <job>/sup/NN_<tool>/ avec son propre output_dir forcé (runner.py:1808-1963). Un outil déjà en cours au-dessus de l'appelant est refusé par son nom, avec la liste de la chaîne ; le garde-fou est MAX_SUPERVISOR_DEPTH = 10 (runner.py:196). La chaîne la plus profonde réellement déclarée par les outils servis compte quatre niveaux, VFACE → AREG_CBCT → ASO → ALI_CBCT.

6. Annulation et délais d'attente

Annulation. DELETE /runs/{id} (main.py:1050) fait deux choses parce qu'aucune ne couvre toute la fenêtre. Il écrit le marqueur cancel, vu pendant la mise en place et pendant l'attente d'admission ; et, si un identifiant de groupe de processus a été enregistré, il envoie SIGTERM au groupe (dispatch.kill_process_group, :745, qui refuse un pgid de 1 ou moins), ce qui arrête un nnU-Net de deux heures. Le worker qui détient le descripteur du processus interroge le marqueur toutes les RUN_CANCEL_POLL_SECONDS = 1,0 s (config.py:278) et applique TERM, puis KILL au bout de 10 s (_KILL_GRACE_SECONDS, dispatch.py:63 ; _kill_group :713). Le POST bloqué répond 499. Un appel imbriqué partage le groupe de processus de son parent, donc un seul TERM atteint chaque niveau. Comme le pgid passe par le disque, une annulation fonctionne depuis un autre processus worker.

Délais d'attente. Une exécution n'a aucun délai par défaut. TOOL_TIMEOUT_SECONDS = 0 (config.py:77) et aucune section de server/deployment.toml ne fixe timeout_seconds. Quand un délai est fixé, par outil dans deployment.toml ou globalement, il est converti en instant monotone absolu transmis sous la forme SADT_SUPERVISOR_DEADLINE (dispatch.py:552-561), et chaque niveau imbriqué ne donne à son enfant que ce qu'il reste (runner._remaining_seconds, :1726). À l'expiration, l'exécution se termine par une ToolExecutionError qui nomme les deux réglages, et la réponse est 500. Le dépôt conseille de donner à un outil d'orchestration au moins 1,2 fois la somme des délais des outils qu'il appelle (docs/INTERNALS.md:112, server/deployment.toml.example:86).

7. Contrôle qualité : arrêter, relire, reprendre, rembobiner

Une exécution serveur peut s'arrêter en cours de route pour qu'une personne regarde ce qu'une étape a produit, le corrige, et laisse l'exécution continuer. C'est le pendant côté serveur des pauses de revue des modules legacy (AREG_CBCT en a une) ; le mécanisme est entièrement différent. L'outil ne sait pas qu'il a été mis en pause.

  1. Armement. Le serveur ajoute un argument à choix multiples stop_after à chaque outil qui a des points d'arrêt, tous décochés, dans la section « Quality control » (registry/schema_tool.py:340-500). Ses options sont les noms des appels que fait l'outil plus les points déclarés, qualifiés pour les chaînes imbriquées comme ASO/ALI_CBCT (_stop_points, registry/__init__.py:389). La nature de chaque point (view, landmarks, …) est lue dans le review_kind de l'appelé et publiée comme option_kind dans GET /tools (main.py:633) ; absente, elle vaut view.
  2. L'arrêt. Les noms armés parviennent au runner sous la forme de la variable JSON SADT_STOP_AFTER (runner.py:121) ; chaque enfant ne reçoit que les entrées qui le concernent. Après l'appel, QualityControlStop (runner.py:167) est levée et attrapée en haut de main() (:2486) ; stopped.json est écrit (cumulatif : stopped_after et passed_stops, _record_stop, :920), tout ce que la chaîne a produit est collecté quoi que dise keep_intermediate, et result.json dit {"quality_control": true, "stopped_after", "produced"}.
  3. Le serveur garde la tâche. Il ne supprime pas le dossier de la tâche (dispatch._kept_if_paused, :1045), écrit paused.json (runs.pause), pose la phase paused et répond 200 avec {quality_control, stopped_after, produced, result_ref}, les sorties étant un zip par référence (_finish_stopped_run, main.py:2147-2197).
  4. Revue, sur le client. Le widget de base de Remote décompresse le checkpoint, calcule une empreinte du contenu, et ouvre le module VISU (REVIEW_MODULE = "VISU", base_widget.py:2290, _reviewCheckpoint :2292) par open_for_review(folder, on_continue, rewind, origin) (VISU/VISU.py:491). VISU ne sait rien du serveur : il reçoit un dossier et un callback. Seuls les checkpoints landmarks et registration sont modifiables (EDITABLE_KINDS, base_widget.py:2328) ; une revue est enregistrée sous visu-review.json à côté des données (VISULib/review.py:20). Si VISU manque ou si le dossier est vide, l'exécution est reprise aussitôt plutôt que laissée en pause sur le serveur.
  5. Reprise. Sur « Continue », le client ne renvoie que les fichiers dont l'empreinte du contenu a changé, un zip par étape, nommé d'après l'étape (01_ALI_CBCT, jusqu'à quatre niveaux : 01_Mid/01_Leaf), vers POST /runs/{id}/resume (main.py:1750 ; nom d'étape vérifié contre _RESUME_SLOT, :1442 ; extension vérifiée contre ce que l'étape a produit, _checked_correction :1463). La pause est levée, l'exécution repasse par la file d'admission comme n'importe quelle autre, et l'outil est de nouveau appelé depuis le début : chaque appel déjà fait répond depuis sa mémoïsation (memo.json, runner._memo :1965), jusqu'à ce que la séquence diverge.
  6. Rembobinage. POST /runs/{id}/rewind avec le champ to (un nom d'étape publié, ALI_CBCT ou ASO/ALI_CBCT) revient à un checkpoint déjà passé. Il ne démarre rien et ne supprime aucune mémoïsation : runner.rewind_to (runner.py:971) retire to et tout ce qui le suit de passed_stops, de sorte que la reprise suivante s'arrête de nouveau là avec la sortie de cette étape intacte. Si l'étape a écrit un rapport de cas (run_report.json), la rediffusion est limitée aux cas qui ont été corrigés, par des liens physiques (dispatch.narrow_to_cases, :959, piloté par le case_input du schéma) ; au moindre doute, c'est une rediffusion complète, plus lente et jamais fausse.

Aucun outil servi ne déclare de point propre avec sup.declareQualityControl (recherché dans SADT-VISOR tools/*/src à 6ba2a78 : aucune occurrence hors du runner). Tous les points d'arrêt existants sont des frontières d'appel : tout outil appelé peut être un arrêt. Une exécution en pause vit PAUSED_RUN_TTL_SECONDS = 4 h et, à l'expiration, reap_expired lit paused.json pour supprimer le dossier de la tâche et les entrées conservées (wire/runs.py:242-313).
