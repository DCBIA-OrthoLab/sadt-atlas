VISOR : la prochaine génération des outils

Le reste de cet atlas lit l'extension legacy, où chaque algorithme s'exécute dans Slicer. VISOR est la nouvelle génération qui déplace le calcul vers un serveur : un client Slicer léger, un serveur d'inférence générique qui ne connaît aucun outil dentaire, et un catalogue d'outils, chacun dans son propre dossier avec son propre environnement Python. Cette page est la vue d'ensemble ; les pages listées en bas entrent dans la mécanique.

instantané d'audit · 2026-11-09 trois dépôts en anglais seulement
Autres langues

Les versions française, espagnole, italienne, coréenne, portugaise et thaïe de ce site décrivent uniquement le code legacy (SlicerAutomatedDentalTools, commit 3c67957). Elles n'ont pas de pages VISOR. Tout ce qu'une page d'outil traduite dit de l'endroit où s'exécute un calcul, ou de l'environnement dont il a besoin, est un énoncé sur le legacy. Les traductions seront refaites plus tard.

1. Ce qu'est VISOR

VISOR, ce sont trois dépôts qui possèdent chacun une couche. Aucun n'est un fork de l'extension legacy : les algorithmes sont portés (« a repackaging exercise, not a rewrite », SADT-VISOR CONTRIBUTING.md:309-315), la structure autour d'eux est nouvelle.

Remote, le clientAutomatedDentalToolsRemote, le client : une extension Slicer de 23 dossiers de modules, chacun un panneau léger au-dessus du serveur. Un panneau est généré à l'exécution à partir du descripteur d'outil du serveur : un champ ajouté sur le serveur apparaît donc dans Slicer sans nouvelle version du client. Slicer n'installe rien et ne télécharge aucun modèle pour un module porté.
VISOR-serve, le serveurLe serveur d'inférence : FastAPI, Python 3.13, sans torch. Il découvre les outils, publie leur schéma, met les exécutions en file et les admet, et lance chacune dans l'interpréteur propre à l'outil. Il est conçu pour ne connaître aucun outil dentaire par son nom.
SADT-VISOR, les outilsLe catalogue : un projet Python isolé par outil, 19 au total, chacun avec son propre .venv et son uv.lock versionné. Un outil est une fonction publique, run() ; son schéma est dérivé de la signature.

Code : client AutomatedDentalToolsRemote CMakeLists.txt:24-48, ServerToolsCoreLib/formgen.py:1-30 ; serveur VISOR-serve server/registry/__init__.py:114 ; catalogue SADT-VISOR README.md:3-5, 41-58.

2. Pourquoi il existe

Le legacy met tout dans Slicer : le widget, le téléchargement des modèles, et l'environnement Python que chaque module construit pour lui-même. Deux conséquences reviennent dans les pages legacy de cet atlas : un portable sans GPU ne peut pas lancer une segmentation, et les outils qui épinglent des bibliothèques incompatibles doivent vivre dans des environnements conda séparés créés sur la machine de l'utilisateur. Le README de SADT-VISOR liste des conflits reproductibles dans les versions épinglées en amont : SurgMovPred demande numpy==2.4.0 là où AREG, MedX et CLIC ont besoin de numpy<2.0.0, deux environnements conda s'appellent tous deux shapeaxi (Python 3.9 et 3.12), et torch est épinglé à 2.2.0 dans cinq modules et laissé libre dans les autres (SADT-VISOR README.md:10-28).

VISOR répond par deux mouvements. Le calcul va sur une seule machine qui a le GPU ; et chaque outil garde ses versions, parce que « the versions are part of the science » (SADT-VISOR README.md:25-28). Le coût disque de nombreux environnements est traité en les construisant de sorte que les wheels identiques partagent les mêmes inodes : scripts/audit.py a mesuré, sur le checkout lu, 7 environnements virtuels présents à 19,6 GB apparents et 8,3 GB uniques (SADT-VISOR scripts/audit.py:201-204, exécuté le 2026-11-09).

La vitesse, la précision et l'équivalence des sorties ne sont pas comparées ici. Les bancs d'essai du serveur (VISOR-serve benchmarks/) ont été mesurés avant la réécriture du moteur d'admission du 2026-09-21, et l'unique session de parité connue n'a trouvé des sorties identiques à l'octet que pour un outil sur six. Rien sur ce site n'affirme que VISOR reproduit les résultats du legacy bit pour bit.

« Servi » signifie que le dossier est dans le catalogue SADT-VISOR et que VISOR-serve le découvre et le charge ; une instance en service a listé les mêmes 23 noms le 2026-10-20. Cela ne veut pas dire un déploiement en production, ce que rien ici n'établit. « Module Slicer » est le dossier d'AutomatedDentalToolsRemote qui appelle l'outil. Là où un module Remote diffère d'un simple panneau

ALIRemote et AREGRemote envoient une requête à une façade, et le serveur choisit le moteur (voir façades). FlexRegRemote recalcule le contour de la zone en local, environ 18 ms sur une arcade de 294 000 points, pour que les joysticks répondent ; la vraie zone est calculée sur le serveur à l'Apply (FlexRegRemote.py:14-18).

5. Sécurité, en une phrase

Le transport est en HTTPS avec un certificat vérifié par le client et un jeton Bearer partagé sur la plupart des routes ; la désidentification est spécifiée mais non implémentée, et l'attestation et l'échange de clés n'existent que dans un prototype de recherche séparé, pas dans ces trois dépôts. Le détail et les preuves sont sur la page de sécurité.
