Empaquetage et déploiement

Comment VISOR-serve est construit en un seul conteneur, où vivent les modèles et la configuration en dehors de celui-ci, la valeur par défaut de chaque réglage, quels scripts montent un serveur et le tiennent à jour, ce que les benchmarks publiés avec le dépôt ont mesuré et ce qu'ils n'ont pas mesuré, et ce qu'une inspection datée d'une instance en fonctionnement a trouvé. Le serveur est une image Docker avec un seul environnement Python 3.13 pour l'API qui ne charge jamais torch, et un environnement virtuel par outil relié par des liens physiques.

Les outils eux-mêmes sont dans SADT-VISOR à 6ba2a78. « Legacy » sur ce site désigne les modules Slicer de SlicerAutomatedDentalTools ; rien de ce qui suit ne s'y applique. La protection du transport, les jetons et les affirmations sur le traitement des données sont sur la page de sécurité ; la forme de l'ensemble du système est sur la page d'architecture.

1. L'image

Il y a un seul conteneur pour tous les outils. docker/Dockerfile (232 lignes) le construit par étapes. L'étape d'exécution part de python:3.13-slim (:76), installe la seule bibliothèque système qu'aucun fichier de verrouillage ne peut fournir, libgomp1 (:86), copie uv 0.12.3 (:89) et construit l'environnement de l'API dans /opt/sadt/.venv à partir de server/requirements-api.txt, qui ne liste que fastapi, uvicorn[standard], python-multipart et pydantic-settings (:105-108). Le processus serveur n'importe donc ni torch, ni nnU-Net, ni MONAI. L'interpréteur propre à chaque outil est installé par uv lui-même (:75), si bien que les outils peuvent reposer sur des versions de Python différentes.

  • Les outils sont intégrés. Chaque outil empaqueté est un dossier /tools/<name>/ contenant .venv, src/ et .schema.json ; les outils d'un dossier de groupe (tools/ALI/ALI_CBCT) sont trouvés parce que la découverte descend sur deux niveaux (registry/__init__.py:114). Le paquet naming/ est copié dans /naming parce que les outils en dépendent par chemin (Dockerfile:122). Les deux fixtures en processus Example_Tool et Test_Tool sont dans l'image : COPY server/ emporte server/tools/ et .dockerignore:18-30 explique que l'exclusion a été retirée, pour qu'un déploiement neuf puisse prouver l'authentification, l'envoi, l'exécution et le résultat avant qu'aucun modèle ne soit téléchargé. L'instance en fonctionnement sert les deux (23 entrées).
  • Une seule couche uv sync, exprès. Le uv sync --frozen --no-install-project --no-dev --all-extras de chaque outil s'exécute dans un seul RUN (:152), avec UV_LINK_MODE=hardlink et le cache uv sur le système de fichiers propre de l'image (:96-101). Réparti sur plusieurs couches, overlayfs copie les fichiers vers le haut et les liens physiques se cassent ; le commentaire du Dockerfile lui-même mesure les onze outils torch à environ 26 GB partagés contre environ 63 GB dupliqués (:131-134). --all-extras est délibéré : un outil comme Crown_Seg garde son moteur derrière un extra, et sans lui l'image s'importe puis répond 503 à la première vraie requête.
  • verify_dedup.py. Rien d'observable n'échoue quand les liens se transforment silencieusement en copies, donc docker/verify_dedup.py le vérifie : pour des fichiers appartenant à la même distribution à la même version (lue dans le RECORD de chaque environnement), un second inode signifie une copie. Il sort avec un code non nul à la moindre, n'utilise que la bibliothèque standard, et est livré dans l'image à /opt/sadt/verify_dedup.py (Dockerfile:200). Les fixtures de test sont numpy_old (1.26.4, Python 3.12), numpy_new (2.5.2, Python 3.13) et numpy_twin.
  • Les schémas sont générés à la construction en exécutant le describe.py de chaque outil avec l'interpréteur propre à cet outil (:177-188) ; un outil qui ne peut pas se décrire est signalé et n'est pas servi. Au démarrage, un schéma périmé est régénéré et mis en cache dans SCHEMA_CACHE_DIR (/var/cache/sadt), parce que /tools est en lecture seule pour le serveur.
  • Pas dans l'image : les modèles et les fichiers de test (section 2), le deployment.toml propre à chaque site (section 4 ; l'image en porte une copie par défaut qu'un montage remplace), l'espace temporaire des jobs /jobs et le jeton d'API.
  • Processus. USER sadt, pas root (:227) ; le code de /tools appartient à root et est en lecture seule pour le serveur, pour que du code tiers ne puisse pas réécrire son propre environnement virtuel ; CMD est uvicorn main:app --host 0.0.0.0 --port 8000 sans --reload et sans --workers, donc un seul processus et une seule file d'admission (:232). Il n'y a aucun HEALTHCHECK dans le Dockerfile ni dans docker-compose.yml.

L'environnement que l'image définit (Dockerfile:202-216) est SADT_DISPATCH_MODE=subprocess, TOOLS_DIR=/tools, RUNNER_PATH=/opt/sadt/server/execution/runner.py, DESCRIBE_PATH=/tools/scripts/describe.py, SCHEMA_CACHE_DIR=/var/cache/sadt, DEPLOYMENT_CONFIG=/opt/sadt/server/deployment.toml, DATA_DIR=/DATA, TEMP_DIR=/jobs et PYTHONDONTWRITEBYTECODE=1. La valeur par défaut de SADT_DISPATCH_MODE dans config.py:37 est inprocess, marquée temporaire ; l'image la remplace, donc ce que le conteneur exécute est toujours le chemin par sous-processus.

Le fichier compose définit plusieurs services. Celui qui est un vrai déploiement est inference-venvs (profil venvs, docker-compose.yml:200) : il construit docker/Dockerfile avec un contexte de construction nommé tools=${TOOLS_CONTEXT:-docker/fixtures}, si bien que sans TOOLS_CONTEXT il construit les petites fixtures, pas les vrais outils. Il définit shm_size: 8gb (nnU-Net fait passer des données entre les workers d'export par la mémoire partagée ; les 64 MB par défaut échouent avec un message qui nomme la mauvaise ressource), réserve tous les GPU et redémarre unless-stopped. Les autres services sont inference (une image GPU précompilée issue d'un registre de conteneurs, avec ./server monté, pip exécuté à chaque démarrage et uvicorn --reload), inference-cpu, et les services test / test-gpu. docker-compose.dev.yml est une surcouche qui monte server/ et le src/ de chaque outil depuis une copie de travail de SADT-VISOR, en lecture seule.

Piège

La documentation à l'intérieur du dépôt décrit encore d'anciennes images. Le commentaire du Dockerfile à :193-195 dit que server/tools/ est exclu par .dockerignore, ce qui n'est plus vrai (.dockerignore:18-30). Les commentaires à :11-12 et :217 comptent encore quinze outils ou amonts ; il y a 19 outils empaquetés. docker/README.md:45-48 dit qu'un outil imbriqué un niveau plus bas « is NOT discovered by the server today », alors que la découverte descend sur deux niveaux et que cinq outils servis (ALI_CBCT, ALI_IOS, AREG_CBCT, AREG_IOS, AREG_IOSCBCT) vivent dans des dossiers de groupe. docker/README.md:4 place runner.py à /opt/sadt/runner.py ; il est à server/execution/runner.py.

2. Modèles et fichiers de test

Les poids ne sont jamais dans l'image et jamais envoyés depuis un portable. Ils vivent dans un répertoire DATA/ monté en lecture seule sur /DATA : DATA/<slug>/models/<name> et DATA/<slug>/testfiles/<name>, avec éventuellement un niveau de plus comme portée (DATA/AREG/testfiles/CBCT_T1). LocalDataStore le lit ; un autre backend peut être branché par la classe abstraite DataStore (DATA_BACKEND, config.py:31).

  • Quel dossier. Le slug est le data_dir déclaré de l'outil ; à défaut, le nom littéral de l'outil si ce dossier existe ; sinon le nom sans tirets bas, de sorte que Batch_Dental_Seg lit DATA/BatchDentalSeg (deployment.data_slug, registry/deployment.py:311-325). Cinq outils partagent deux dossiers par data_dir = "AREG" (trois outils) ou "ALI" (deux).
  • Quels arguments en sont remplis. Par convention de nommage (registry/conventions.py) : model, *_model et *_reference sont publiés comme un nom choisi dans DATA/<tool>/models/, jamais comme un envoi, de sorte que les poids ne peuvent pas être envoyés depuis un client. Un envoi de fichier sur un tel champ est une erreur 400 (main.py:1269-1278). Tout autre path peut être envoyé ou rempli depuis testfiles/.
  • Ce que l'API offre. GET /tools/{tool}/data liste les modèles et les fichiers de test ; GET|HEAD /tools/{tool}/testfiles/{name} sert un fichier de test. Il n'existe aucune route qui serve un modèle (download_testfile ne lit que testfiles). Un dossier de fichiers de test est zippé à la volée et envoyé avec Accept-Ranges: none ; sinon le client sonde, voit des plages et découpe une cohorte de 339 MB en 43 parties, le serveur construisant la même archive 43 fois : 39,1 s par plages contre 1,5 s en entier (main.py:794-806).
  • Le remplir. scripts/data-manifest.yml dit ce qui existe, d'où cela vient et où cela va ; scripts/fetch_data.py (bibliothèque standard seulement) le télécharge, setup-models.sh et setup-testfiles.sh en sont des enveloppes, et --list affiche les tailles par outil sans rien télécharger. Une entrée a un name, une url, un sha256 facultatif (une différence fait écarter le fichier ; en son absence le script affiche le hash obtenu, à coller dans le manifeste), une size facultative, extract: true pour décompresser un zip et garder le dossier, et dest pour renommer ou pour regrouper plusieurs archives dans un dossier de bundle. Le commentaire du manifeste chiffre l'ensemble à environ 29 GB pour 14 outils, dont 12 GB pour les modèles CBCT d'ALI.

Compose et les scripts ajoutent leurs propres variables, lues dans un .env à côté de docker-compose.yml (.env.example) : API_TOKEN (valeur par défaut de compose dev-token, docker-compose.yml:208), DEVICE (valeur par défaut de compose cuda, :209), HOST_PORT, VENVS_HOST_PORT (8001 par défaut), BIND_ADDR, TOOLS_CONTEXT et SADT_AUTO_UPDATE (section 5).

Piège

La valeur par défaut de compose ${API_TOKEN:-dev-token} signifie qu'une installation qui n'écrit pas de .env tourne avec un jeton public, parce qu'il est dans un fichier versionné. Le mappage de port "${BIND_ADDR:+${BIND_ADDR:-}:}${VENVS_HOST_PORT:-8001}:8000" (docker-compose.yml:224) publie sur toutes les interfaces quand BIND_ADDR n'est pas défini. Le chemin par scripts/server_ctl.py génère un jeton et met BIND_ADDR à 127.0.0.1 par défaut (server_ctl.py:368,398) ; lancer compose à la main ne le fait pas.

4. deployment.toml

server/deployment.toml contient ce qui est propre à une installation. Il est lu une fois au démarrage, monté en lecture seule dans le conteneur par-dessus la copie de l'image pour que changer une ligne n'oblige pas à reconstruire l'image (docker-compose.yml:215-220). Chaque table [tools.<name>] peut contenir exactement ces clés (_TOOL_KEYS, registry/deployment.py:69) : server_selectable, max_upload_mb, data_dir, hidden, timeout_seconds, dispatch, batch, width_from. server_selectable accepte model, testfile ou none, avec une portée écrite testfile:Sub_folder (:53, SCOPE_SEPARATOR). Un fichier illisible ou une clé inconnue est fatal (DeploymentConfigError) ; le refus d'une valeur que le serveur ne connaît pas porte la marque DEPLOYMENT-CONFIG-AHEAD-OF-SERVER (:66), parce que le fichier est monté et peut être plus récent que l'image.

Une façade (ALI, AREG) n'a ni dossier ni interpréteur. Son schéma est composé au démarrage à partir de la table dispatch : un argument mode en tête, puis l'union des arguments de ses cibles, chacun visible seulement dans les modes qui l'ont (registry/facade.py:49-98). Le même nom d'argument doit avoir le même type, les mêmes extensions acceptées et le même caractère obligatoire dans chaque cible, sinon la façade est sautée avec un avertissement ; c'est fatal seulement si son nom entre en collision avec un outil déjà servi (facade.py:282-295).

Le fichier n'est pas vide, quoi qu'en dise son en-tête

Les deux sont faux à ce commit : le fichier a 14 sections, ce qui fait fonctionner les façades AREG et ALI, le dossier de données de VFACE et les déclarations de lots et de largeur par outil.

5. Scripts et exploitation

Mise à jour automatique. SADT_AUTO_UPDATE vaut off (par défaut), notify ou apply (server_ctl.py:838-850). apply attend que /status ne signale ni exécution en cours ni exécution en attente, ferme la porte par POST /maintenance avec un bail de 60 s qu'il renouvelle (:911, GATE_LEASE_SECONDS), exécute git pull --ff-only (:1178), relance avec up -d --force-recreate (:1205, jamais restart) et rouvre. Il refuse un changement de fichier de verrouillage, de pyproject.toml, de server/requirements* ou de docker/, puisque ceux-là exigent une nouvelle image (:522-524). L'en-tête de l'unité elle-même avertit que la machine « will execute code pulled from a public repository » et qu'aucun commit de ces dépôts n'est signé aujourd'hui ; passer à apply y est décrit comme une décision qui revient à qui est responsable de la machine.

7. Ce que l'inspection d'une instance en fonctionnement a trouvé

Une observation datée, pas une propriété du code

Une instance en fonctionnement a été inspectée le 2026-10-20 (un rapport conservé hors des dépôts). Ce qu'il a trouvé sur cette machine n'est peut-être plus vrai. Cette section ne garde que ce que le code explique ; les détails qui identifient la machine ou son réseau sont volontairement omis. Les seules vérifications faites en écrivant cette page ont été un GET /health et un GET /tools sans authentification : ils ont répondu {"status":"ok"} et 23 entrées.

  • Ce que le code prédit, elle l'a fait. GET /health et GET /tools ont répondu sans jeton, GET /status a refusé une requête sans jeton (401). Le catalogue comptait 23 entrées, dont 19 issues d'un schéma. Le journal de démarrage ne contenait ni saut, ni erreur, ni traceback ; ses seuls avertissements concernaient les clés de schéma ignorées d'ALI_CBCT, ALI_IOS et ASO, expliquées sur la page d'architecture.
  • HTTP en clair, directement depuis le conteneur. Le client Slicer d'AutomatedDentalToolsRemote exige du HTTPS avec un certificat signé publiquement et n'a aucun repli (page de sécurité), donc il ne peut pas se connecter à une instance exposée ainsi ; un script qui appelle directement l'API le peut.
  • Pas de .env. L'instance avait été démarrée sans, donc elle tournait avec les valeurs par défaut de compose décrites en section 3, jeton compris.

Le rapport liste ensuite ce qui peut arrêter une exécution sans surveillance. Chaque point ci-dessous est vérifié par rapport au code ; le rapport marque les quatre premiers comme dérivés du code, de la configuration et du journal, pas d'une exécution réelle.

  1. Pas de délai d'expiration. TOOL_TIMEOUT_SECONDS vaut 0 et deployment.toml n'en définit aucun (config.py:77) : quatre exécutions bloquées gèlent le serveur sans qu'aucune d'elles n'échoue.
  2. Un outil non mesuré s'exécute seul. Un outil dont le coût n'a jamais été mesuré réserve tout le budget (execution/admission.py:22-33). Sur cette instance, la plupart des outils n'avaient pas encore de coût mesuré, donc le max_parallel_jobs: 4 annoncé surestimait le débit réel.
  3. Les réservations suivent la pire exécution récente. Le coût appris est le maximum des COST_WINDOW = 20 dernières exécutions (config.py:106), donc un outil dont l'usage mémoire varie beaucoup d'une entrée à l'autre réserve son pire cas et se sérialise.
  4. Aucune valeur de VRAM. Sur cette instance, /status a renvoyé vram_bytes: null et une carte avec free_bytes: null : la sonde, qui appelle nvidia-smi (resources.py:193), n'a rien renvoyé, et /status le tolère par conception (main.py:470-474). L'admission travaille alors sur les cœurs et la RAM.
  5. Une exécution échouée enseigne quand même la table des coûts. La mesure est conservée avant la branche d'erreur, exprès, parce qu'une exécution morte par manque de mémoire est la mesure la plus utile (execution/dispatch.py:800-803). Un banc qui échoue pour une raison sans rapport peut donc gonfler les réservations suivantes.
  6. Pas de healthcheck dans le Dockerfile ni dans compose : restart: unless-stopped relance un conteneur mort, rien ne détecte un conteneur vivant mais bloqué.
  7. Le SIGKILL d'un opérateur ressemble à une mort par manque de mémoire. Un SIGKILL sans result.json est lu comme le kill par manque de mémoire du noyau (execution/dispatch.py:930-949), donc l'exécution est relancée.

8. Les benchmarks publiés avec le serveur

benchmarks/ est un harnais relançable (python -m benchmarks.run --campaign b1..b5 [--dry-run]), configuré par config.yaml. Trois chemins d'exécution existent : local (l'outil dans son propre interpréteur, sans HTTP, avec quatre différences documentées dans NOTES-local-path.md), loopback (l'API HTTP sur la même machine) et lan, qui est jamais mesuré : server.lan_base_url vaut null (config.yaml:22). Le client HTTP du harnais parle le protocole du client Slicer : parties de 8 MB, quatre transferts simultanés, un SHA-256 par partie, gzip, X-Result-Delivery: reference, téléchargements par plages. Les statistiques sont la médiane avec l'étendue complète, jamais la moyenne ; la répétition 1 de chaque configuration est écartée comme échauffement mais conservée dans le fichier brut avec warmup: true ; une exécution échouée est un enregistrement, jamais supprimée.

La parité octet pour octet entre le chemin local et le chemin HTTP est établie pour un seul outil, AREG_IOSCBCT, dans une seule session (n = 1 paire). Elle n'est pas établie en général. Le témoin montre que la plupart de ces outils ne se reproduisent même pas octet pour octet sur le même chemin, parce que leurs rapports portent des durées ou des chemins, et qu'une comparaison d'octets ne distingue pas un rapport de données. On ne peut écrire ni « parité atteinte » ni « parité perdue » à partir de cette table. Le README du dépôt dit que le banc reproduit chaque chiffre de temps d'exécution de l'article qui l'accompagne ; c'est vrai pour B1, B3 et B4, qui ont des résumés, alors que B2 et B5 doivent être lus dans les fichiers bruts.
