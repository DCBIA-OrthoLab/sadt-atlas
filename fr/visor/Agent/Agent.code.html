Agent sur VISOR : le code

Pour les développeurs : ce que font dans le code l'outil serveur VISOR Agent et la copie cliente AgentRemote, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas.

VISOR : partiel Code Atlas (explication) Page legacy Guide (VISOR)

État aux commits de référence : SADT-VISOR 6ba2a78, VISOR-serve e9a7e5d, AutomatedDentalToolsRemote 19b95e8 (Remote) ; le legacy est SlicerAutomatedDentalTools à 3c67957. Un simple nom de fichier comme llm.py ou routing.py est dans SADT-VISOR tools/Agent/src/sadt_agent/ ; AgentRemote.py est dans Remote AgentRemote/. Tout a été lu dans le code : aucun Ollama n'était disponible, rien n'a donc été exécuté.

Ollama est un prérequis que personne ne déploie

L'outil serveur a besoin d'un point d'accès Ollama : l'argument endpoint, sinon la variable OLLAMA_HOST, sinon l'adresse de bouclage sur le port 11434 d'Ollama (SADT-VISOR tools/Agent/src/sadt_agent/llm.py:38-39,51-59). Sans point d'accès joignable, l'outil lève ToolUnavailableError (llm.py:86-91), que le serveur traduit par un 503 (VISOR-serve server/main.py:133-138).

3. Le pipeline de l'outil serveur

Explication en langage courant et maths : page de l'atlas.

3.1 Le catalogue, lu depuis GET /tools

Explication en langage courant et maths : page de l'atlas.

L'agent legacy portait son propre manifeste d'outils et de paramètres écrit à la main, qui dérivait par rapport aux outils. L'outil serveur prend le catalogue en entrée (catalog.py:1-23,52-83) :

  1. catalog_file, un fichier JSON contenant ce que renvoie GET /tools, s'il est donné ;
  2. sinon <SADT_API>/tools, lu avec urllib et sans jeton (catalog.py:86-100). SADT_API est l'adresse propre du serveur vue depuis un outil (VISOR-serve server/config.py:75, server/execution/dispatch.py:575) ;
  3. ni l'un ni l'autre : une CatalogError qui nomme les deux, un 422.

normalise accepte une liste ou {"tools": [...]} et refuse tout le reste, un catalogue vide, deux noms identiques une fois ignorées la casse et les séparateurs, un type d'argument hors de path, str, int, float, bool et leurs listes, et des choices qui ne sont pas une liste (catalog.py:103-223). Pour chaque argument, elle garde le type, l'indicateur d'obligation, la description, les choix, la valeur par défaut et les clés de présentation hidden, label, section. Les arguments que le modèle peut remplir sont ceux qui ne sont ni output_dir ni masqués (fillable_arguments, catalog.py:250-262). Rien dans catalog.py ne retire Agent lui-même du catalogue.

3.2 Choisir les candidats

Explication en langage courant et maths : page de l'atlas.

Chaque outil devient un sac de mots tiré de son nom (poids 4), de sa description (3) et des noms et descriptions de ses arguments (1), avec une table de synonymes de vocabulaire, non d'outils (ranking.py:32-110,148-169). La requête est notée avec BM25 :

idf  = log(1 + (N - df + 0.5) / (df + 0.5))
norm = K1 * (1 - B + B * len(doc) / avg_len)          # K1 = 1.2, B = 0.4
score += weight * idf * tf * (K1 + 1) / (tf + norm)   # ranking.py:183-219

Dans cette somme, tf est le décompte pondéré du terme dans le document : chaque occurrence ajoute 4, 3 ou 1 selon le champ (ranking.py:156-168), et len(doc) est la somme de ces poids (:194). weight est le poids du terme de la requête : 1,0 pour un mot tapé, 0,55 (SYNONYM_DISCOUNT, :43,171-180) pour un mot ajouté depuis sa classe de synonymes (:207,215).

select_candidates garde les candidates premiers (8 par défaut), mais renvoie tout le catalogue quand candidates vaut 0, couvre le catalogue, ou quand aucun outil ne marque plus de zéro (ranking.py:222-239). Le fait qu'il ait réduit ou non est enregistré comme candidates_narrowed dans le rapport. Le cross-encoder legacy, en cas d'échec, renvoyait les trois premiers outils dans l'ordre du fichier (legacy Agent_CLI/Agent_CLI_utils/utils.py:94).

3.3 Appel du routeur

Explication en langage courant et maths : page de l'atlas.

Un POST /api/chat avec stream: false, keep_alive: "30m", format: "json" et options {temperature, seed} (llm.py:45,62-103). Le prompt système demande un seul objet JSON {"tool", "confidence", "reason"}, un outil choisi seulement dans la liste CANDIDATES, et null avec une confiance de 0,2 ou moins quand rien ne convient (prompts.py:15-30). Les candidats sont écrits en entier, sans la troncature à 140 caractères du legacy (prompts.py:1-8,67-103). parse_json_object retire les blocs <think> et les clôtures de code, puis prend le premier objet équilibré (llm.py:131-181). choose_tool vérifie ensuite le nom (routing.py:22-55) :

  • null, "null" ou "None" : aucun outil ;
  • un nom trouvé parmi les candidats, exactement ou après normalisation (catalog.find_tool, catalog.py:236-247) : choisi ;
  • tout autre chose : aucun outil, confiance plafonnée à 0,2, et le nom enregistré comme rejected_tool_name avec un avertissement (__init__.py:197-222).

3.4 Appel d'extraction et validation

Explication en langage courant et maths : page de l'atlas.

Un second appel demande {"extracted": {...}, "confidence", "notes"}, avec les arguments remplissables de l'outil choisi, leurs types, choix et valeurs par défaut, et les dossiers (routing.py:58-84, prompts.py:32-48,105-140). Le prompt interdit d'inventer une valeur ou un chemin. validation.validate ensuite (validation.py:39-77) :

  • écarte tout nom que l'outil ne prend pas, et le dit ;
  • traite null comme « non indiqué » ;
  • convertit les booléens depuis true/yes/y/1/on et leurs contraires, les entiers et les flottants, les listes, et vérifie choices (validation.py:80-209) ; un échec est une erreur dans la décision et la valeur est écartée.

Toute erreur multiplie la confiance d'extraction par 0,6, comme dans le legacy (routing.py:78-83). Les valeurs par défaut ne sont pas copiées dans la proposition, et les arguments obligatoires encore absents sont listés dans missing_required (catalog.py:265-271, __init__.py:224-232).

3.5 Ce qui est lancé

Explication en langage courant et maths : page de l'atlas.

allowed, reason = routing.can_execute(decision)     # __init__.py:234
if not execute:          -> executed: false, proposal only
elif not allowed:        -> executed: false, execution_refused: reason
else:
    parameters = dict(values); parameters["output_dir"] = output_dir / "run"
    produced = supervisor.run(tool_name, **parameters)          # execution.py:58-70

can_execute refuse quand aucun outil n'a été choisi, quand missing_required n'est pas vide, et quand la confiance du routeur est sous EXECUTE_MIN_CONFIDENCE = 0.5 (routing.py:19,104-125). L'outil choisi s'exécute ensuite comme un appel supervisé ordinaire dans son propre venv, avec des arguments nommés, ses sorties sous run/ dans le dossier de sortie d'Agent ; ce qu'il a renvoyé est enregistré sous execution dans routing.json (__init__.py:245-252, execution.py:75-85). Sans superviseur (l'outil appelé hors d'un serveur), execute lève SupervisorRequired (execution.py:51-56). Le superviseur refuse un cycle par le nom : un modèle qui choisirait Agent lui-même finirait donc en « Supervised call cycle » (VISOR-serve server/execution/runner.py:1814-1817). Lu dans le code.

3.6 Mode Ask

Explication en langage courant et maths : page de l'atlas.

Avec mode = "Ask (Interactive)", un seul appel avec le prompt du conseiller et la liste des candidats, hors format JSON, et la réponse en Markdown est écrite dans advice.md (__init__.py:161-188, routing.py:87-101, prompts.py:50-63). Rien n'est proposé ni exécuté, quoi que dise execute. Toute autre valeur de mode est traitée comme le mode Agent (__init__.py:161-167) ; le serveur valide le Literal avant que run() soit appelé.

8. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Un outil serveur sans client, un client sans outil serveur

L'outil serveur n'est joignable depuis aucun panneau, et le panneau client ne contacte jamais le serveur. Rien dans AutomatedDentalToolsRemote ne construit de requête pour Agent, et AgentRemote.py n'importe pas ServerToolsCoreLib. Les deux partagent un nom et un tag de modèle, rien d'autre.

L'exécution est désactivée par défaut, avec trois refus

execute vaut faux par défaut (__init__.py:43). Quand il est vrai, l'exécution est quand même refusée si aucun outil n'a été choisi, si un argument obligatoire manque, ou si la confiance est sous 0,5 (routing.py:104-125). Le commentaire du code source appelle ce seuil un plancher contre un modèle qui avoue deviner, pas un critère de qualité (routing.py:16-19).

Aucune vérification au démarrage que l'outil appelé existe

L'appel est écrit supervisor.run(...) au lieu de sup.run(...) exprès, pour que le générateur de schéma n'enregistre pas de dépendance fixe (execution.py:9-29,68-70). Les noms qui y arrivent viennent du catalogue : un nom ne vaut donc que ce que vaut le registre où il a été lu. Le catalogue n'exclut pas Agent ; un appel à soi-même serait refusé par le contrôle de cycle du superviseur (VISOR-serve server/execution/runner.py:1814-1817), à l'exécution.

Les chemins restent la parole du modèle

Les seuls chemins que voit le modèle sont folders, et on lui dit de les utiliser tels quels (prompts.py:32-48), mais rien ne vérifie qu'un chemin proposé existe ou est du bon genre : le schéma dit path sans dire fichier ou dossier, et le contrôle d'extension du legacy a été abandonné exprès (validation.py:9-17). C'est l'outil exécuté qui signale un mauvais chemin. Sur un serveur, ces chemins sont aussi des chemins du serveur, pas ceux de l'utilisateur. Lu dans le code.

La copie cliente garde les défauts du legacy

AgentRemote et Agent_CLIRemote sont la conception legacy, donc les constats du legacy (pièges legacy) s'y appliquent toujours : le cross-encoder se rabat toujours sur les k premiers outils (Remote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:94) ; le job s'exécute toujours de façon synchrone sur le fil de Slicer (AgentRemote.py:767) ; les chemins de modules sont toujours résolus par AGENT_CLI_TOOLS_DIR (utils.py:150-156), alors que les modules CLI que nomme le manifeste ont été supprimés de l'extension (Remote CMakeLists.txt:49-56). Lu dans le code, pas exécuté dans Slicer.

Le manifeste de la copie cliente est périmé

Agent_CLIRemote/manifest.yaml liste medx_dashboard et medx_summarize (lignes 491 et 509) alors que MedX n'existe plus dans aucun des deux dépôts (voir MedX), et il ne peut pas nommer MRI2CBCT, qui n'est pas compilé.
