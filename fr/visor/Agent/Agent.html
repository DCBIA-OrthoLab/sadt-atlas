Agent sur VISOR

Agent lit une phrase comme « segmente le crâne de ces scans » et propose lequel des autres outils exécuter, avec quels réglages. Un modèle de langage servi par Ollama fait le choix, du code ordinaire vérifie chaque réponse, et rien ne s'exécute sans demande. Dans VISOR, deux choses sans rapport s'appellent Agent : un nouvel outil sur le serveur, et AgentRemote, une copie de l'ancien panneau Slicer qui exécute encore tout sur le poste de travail. Cette page explique les deux, pas à pas. Les détails dont un développeur a besoin sont sur la page de code ; le module legacy se trouve sur sa propre page.

État aux commits de référence : SADT-VISOR 6ba2a78, VISOR-serve e9a7e5d, AutomatedDentalToolsRemote 19b95e8 (Remote) ; le legacy est SlicerAutomatedDentalTools à 3c67957. Tout a été lu dans le code : aucun Ollama n'était disponible, rien n'a donc été exécuté.

Le README du client le dit sans détour : Medical Data Anonymizer, VISU et Agent « run on this machine and send nothing ». Le texte d'aide du panneau dit toujours que l'agent est « powered locally by the qwen3:8b model through Ollama ».

Ollama est un prérequis que personne ne déploie. L'outil serveur a besoin d'un point d'accès Ollama : celui donné en argument, sinon celui que nomme la variable OLLAMA_HOST, sinon le port Ollama de la machine elle-même. Il n'installe, ne démarre ni ne télécharge jamais de modèle, et rien dans VISOR-serve ne mentionne Ollama : l'image n'en porte donc pas. Sans point d'accès joignable, l'outil s'arrête sur une réponse « service unavailable ». Preuve.

2. Fichiers en jeu

L'outil serveur est un petit paquet Python d'une douzaine de fichiers courts, chacun avec une seule tâche : lire le catalogue, le classer, parler au modèle, router, écrire les prompts, valider les valeurs, exécuter l'outil choisi, analyser l'historique et décrire le panneau. Il n'a aucune dépendance hors de la bibliothèque standard. La copie cliente est le widget legacy plus son module en ligne de commande et un manifeste.

Dans le codeLa liste des fichiers avec nombres de lignes, pour l'outil serveur, le module legacy et la copie cliente

3. Le pipeline de l'outil serveur

Cinq étapes calculées préparent la question, un ou deux appels au modèle y répondent, et du code vérifie chaque réponse avant qu'elle soit utilisée.

3.1 Le catalogue

L'agent legacy portait sa propre liste d'outils et d'arguments écrite à la main, qui s'écartait peu à peu des outils. L'outil serveur prend le catalogue en entrée : une copie JSON enregistrée de ce que publie le serveur si elle est donnée, sinon la propre liste vivante du serveur, lue sans jeton ; sans l'une ni l'autre, il s'arrête. La liste est ensuite vérifiée : elle ne doit pas être vide, deux noms ne doivent pas être identiques une fois ignorées la casse et les séparateurs, et chaque type d'argument doit être connu. Pour chaque argument, l'outil garde son type, s'il est obligatoire, sa description, ses choix et sa valeur par défaut. Les arguments que le modèle peut remplir sont ceux qui ne sont ni le dossier de sortie ni masqués.

Dans le codeOù le catalogue est lu, ce qui est refusé, et ce qui est gardé pour chaque argument

3.2 Choisir les candidats

La table de synonymes utilisée par le classement contient du vocabulaire, pas des noms d'outils. Le classement legacy était un cross-encoder neuronal ; quand il échouait, il renvoyait en silence les trois premiers outils du fichier, alors que le classement du serveur s'arrête sur une erreur au lieu de deviner.

Dans le codeLe code BM25, les poids des champs, la table de synonymes et le repli sur tous les outils

3.3 Le premier appel au modèle : quel outil ?

Le modèle voit la requête et les candidats, chacun écrit en entier (le legacy coupait les descriptions à 140 caractères). Il doit répondre par un seul objet JSON : un nom d'outil, une confiance et une raison en une phrase, ou aucun outil avec une confiance de 0,2 ou moins quand rien ne convient. Les blocs de raisonnement et les clôtures de code autour de la réponse sont retirés avant qu'elle soit lue. Puis le nom est vérifié parmi les candidats :

  • aucun outil, ou le mot « null » : rien n'est choisi ;
  • un nom trouvé parmi les candidats, exactement ou après normalisation de la casse et des séparateurs : choisi ;
  • tout autre chose : aucun outil, confiance plafonnée à 0,2, et le nom inventé est enregistré avec un avertissement.
Dans le codeLa requête envoyée à Ollama, le prompt du routeur, l'extraction du JSON et la vérification du nom

3.4 Le second appel au modèle : quelles valeurs ?

Le second appel demande les valeurs des arguments remplissables de l'outil choisi, avec leurs types, choix et valeurs par défaut, et les dossiers donnés par l'utilisateur. Le prompt interdit d'inventer une valeur ou un chemin. Les valeurs par défaut ne sont pas copiées dans la proposition, et les arguments obligatoires encore sans valeur sont listés comme manquants, jamais devinés.

Dans le codeLe prompt d'extraction, les règles de validation et la conversion des booléens, des nombres et des listes

3.5 Ce qui est lancé

Quand toutes les conditions sont réunies, l'outil choisi s'exécute comme un appel supervisé ordinaire dans son propre environnement, avec des arguments nommés, et ses sorties atterrissent dans un dossier run/ à l'intérieur de la sortie d'Agent. Ce qu'il a renvoyé est enregistré dans le fichier de décision. Si l'outil est appelé hors d'un serveur, sans superviseur, demander l'exécution est une erreur. Un modèle qui choisirait Agent lui-même serait arrêté par le contrôle de cycle du superviseur, à l'exécution.

Dans le codeLa barrière en code, l'appel supervisé et le refus de cycle

3.6 Mode Ask

En mode Ask, un appel au modèle avec un prompt de conseiller et la liste des candidats, non contraint au JSON, produit une réponse en Markdown écrite dans advice.md. Rien n'est proposé ni exécuté, quoi que dise execute. Toute autre valeur de mode est traitée comme le mode Agent ; le serveur valide les deux noms permis avant que l'outil soit appelé.

Dans le codeL'appel du conseiller, le test du mode et l'ordre des contrôles

6. Environnement

  • Python 3.11, sans dépendance hors de la bibliothèque standard ; la connexion à Ollama utilise du HTTP simple.
  • Un serveur Ollama avec qwen3:8b (ou le tag choisi) déjà téléchargé. Il n'est pas dans l'image ni dans VISOR-serve.
  • Aucune donnée hébergée, aucune ressource déclarée, 300 secondes permises par appel au modèle.

Le module legacy téléchargeait et démarrait lui-même un binaire Ollama et téléchargeait le modèle à la demande (le modèle de langage) ; l'outil serveur ne fait ni l'un ni l'autre. La copie cliente dépend toujours d'un Ollama local et du cross-encoder dans le Python de Slicer.

8. Problèmes connus

  • Un outil serveur sans client, un client sans outil serveur. Aucun panneau ne peut joindre l'outil serveur, et le panneau client ne contacte jamais le serveur. Preuve.
  • L'exécution est désactivée par défaut, avec trois refus. C'est une protection, pas un problème. Preuve.
  • Aucune vérification au démarrage que l'outil appelé existe. Les noms viennent du registre, et Agent lui-même n'est pas exclu ; un appel à soi-même serait refusé à l'exécution. Preuve.
  • Les chemins restent la parole du modèle. Rien ne vérifie qu'un chemin proposé existe ou est du bon genre ; l'outil exécuté signale un mauvais chemin. Preuve.
  • La copie cliente garde les défauts du legacy : repli silencieux du cross-encoder, Slicer figé pendant le job, scripts de modules qui ne sont plus livrés. Preuve.
  • Le manifeste de la copie cliente est périmé : il liste MedX, qui n'existe plus, et ne peut pas nommer MRI2CBCT. Preuve.
