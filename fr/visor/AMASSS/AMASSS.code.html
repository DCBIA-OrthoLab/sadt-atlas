AMASSS sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR d'AMASSS dans le code, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible de la même chaîne, avec les maths, se trouve sur la page de l'atlas. Comment AMASSS s'exécute dans VISOR (client et serveur), ce qui a changé par rapport au module Slicer legacy, et ce que fait le code du portage : un réseau nnU-Net v2 binaire par structure anatomique, désormais prédit côte à côte sur un serveur. Le module legacy est décrit sur sa propre page.

Code Atlas (explication) VISOR sadt_amasss Page legacy Guide (VISOR) Bibliographie

VISOR exécute AMASSS sur un serveur : Slicer se contente d'envoyer les scans et de recevoir les segmentations. Cette page suit une exécution du panneau jusqu'au rapport : ce qui s'exécute où, quels fichiers font quoi, chaque étape de la chaîne avec le code qui l'effectue, les arguments que publie le serveur, et en quoi le portage diffère du module legacy. Tout ici a été lu dans le code, pas observé sur un serveur en marche, et rien ici ne dit qu'un serveur donné est déployé.

Les références nomment d'abord le dépôt : SADT-VISOR (code des outils, tools/AMASSS @ 6ba2a78), VISOR-serve (serveur, @ e9a7e5d), AutomatedDentalToolsRemote (client Slicer, @ 19b95e8) et legacy (SlicerAutomatedDentalTools @ 3c67957). Un nom de fichier nu comme pipeline.py, catalog.py, layout.py, nnunet_runner.py, vtk_export.py, progress.py, errors.py ou __init__.py se trouve dans le paquet SADT-VISOR tools/AMASSS/src/sadt_amasss/ ; AMASSS_CLI.py (AMASSS_CLI/) et AMASSS.py (AMASSS/) sont des fichiers legacy. Le dossier AMASSS est identique sur la branche main de SADT-VISOR et à 6ba2a78 (aucune différence sur tools/AMASSS).

3. La chaîne en un coup d'œil

run() (__init__.py:20-109) transforme les deux arguments de liste en codes et appelle segment() (pipeline.py:280-376), qui vérifie les arguments, trouve les scans et les modèles, puis passe la main à _run() (pipeline.py:379-558) pour trois phases qui partagent la barre de progression : lecture (0 à 10 %), prédiction (10 à 90 %), écriture (90 à 100 %) (pipeline.py:391-395, 471, 492).

  1. Vérifier les arguments (pipeline.py:299-327) : None prend les valeurs par défaut, une liste vide est refusée, un code de structure ou un mode de fusion inconnu lève ToolInputError. §4
  2. Découvrir les scans (pipeline.py:88-132) : un fichier est pris tel quel, un dossier est parcouru. §4
  3. Résoudre les modèles (pipeline.py:135-170) : un dossier de modèle par code demandé, sinon le code est listé comme manquant. §5
  4. Convertir chaque scan une fois dans un unique dossier d'entrée nnU-Net (pipeline.py:384-424). §4
  5. Prédire : un predict_folder par structure, plusieurs à la fois (pipeline.py:426-488). §5
  6. Assembler les sorties de chaque scan (pipeline.py:490-522, 561-657). §6
  7. Surfaces quand generate_surface est vrai (vtk_export.py). §6.3
  8. Rapport et suppression du dossier de travail (pipeline.py:362-369, 531-558). §6.4

4.1 Des listes du panneau aux codes

structures et merge sont publiés comme des listes d'options fixes (list[Literal[...]], __init__.py:28-31), que le générateur de schéma transforme en sélection multiple (SADT-VISOR scripts/describe.py:240). catalog._codes_from() (catalog.py:108-135) accepte quatre formes : None (les valeurs par défaut), une chaîne seule, un itérable de codes ou de noms d'affichage, et l'ancien dictionnaire {name: bool}. La branche de la chaîne existe parce qu'une chaîne nue serait sinon parcourue caractère par caractère, si bien qu'aucun code ne correspondrait ; le commentaire consigne que merge a un jour été livré ainsi et que chaque exécution renvoyait un rapport sans segmentation (catalog.py:115-126). Les noms d'affichage de l'ancien schéma ("Cranial base", "One merged segmentation file") sont encore traduits (catalog.py:46-50, 102-105).

# pipeline.py:302-327 (shortened)
structures = tuple(DEFAULT_STRUCTURES if structures is None else structures)
merge = tuple(DEFAULT_MERGE_MODES if merge is None else merge)
prediction_ID = (prediction_ID or "Pred").strip() or "Pred"
unknown = [code for code in structures if code not in STRUCTURE_CODES]

if not merge:      raise ToolInputError("Select at least one output form ...")

Le panneau impose le même minimum avant que la requête parte : min_selected = 1 sur les deux listes (layout.py:47, 55).

4.2 Découverte des scans

discover_scans() (pipeline.py:88-132) : un chemin qui n'existe pas lève FileNotFoundError ; un fichier est renvoyé comme liste d'un élément sans aucun filtrage (:102-103) ; un dossier est parcouru récursivement avec os.walk (:107). Un fichier est gardé si son nom se termine par l'une des extensions de volume de sadt_naming :

# SADT-VISOR naming/src/sadt_naming/__init__.py:36
VOLUME = (".nii.gz", ".nrrd.gz", ".gipl.gz", ".nii", ".nrrd", ".gipl")

et si is_previous_output() (pipeline.py:69-85) ne le reconnaît pas comme un résultat d'AMASSS : un nom de base contenant _<prediction_ID>_, ou se terminant par _MERGED, par _<CODE> pour l'un des neuf codes, ou par _Seg / _SegOut. Seul le nombre de fichiers ignorés est journalisé, jamais leurs noms (:116-123). Aucun fichier restant : FileNotFoundError("No scan found ...") (:125-131), là où le legacy appelait sys.exit(1). La liste est triée (:132), si bien que les numéros de cas suivent l'ordre des chemins. La conséquence pour de vrais noms de patients est décrite dans les Constats.

4.3 Conversion vers le dossier d'entrée nnU-Net

Chaque scan lisible est écrit une fois dans .amasss_work/nnunet_input/ sous un nom de cas qui ne porte aucune métadonnée de patient, sa position dans la liste triée (pipeline.py:387-420) :

# pipeline.py:396, 412
case_id = f"p_{index:03d}"
_convert_to_nifti(scan_path, os.path.join(nnunet_input, f"{case_id}_0000.nii.gz"))

# pipeline.py:191-194
image = sitk.ReadImage(scan_path)
sitk.WriteImage(image, destination)

La conversion est une vraie lecture suivie d'une vraie écriture pour chaque format, .nii.gz compris ; le type de voxel est laissé tel quel parce que le lecteur de nnU-Net convertit lui-même en float32 (pipeline.py:177-190). Aucune normalisation d'intensité, aucun fenêtrage ni aucun rééchantillonnage n'est écrit dans le paquet : tout cela relève de nnU-Net, piloté par le plans.json de chaque modèle, dans cet ordre : recadrage sur la région non nulle, CTNormalization, puis rééchantillonnage vers l'espacement cible (nnU-Net 2.8.1 tel que verrouillé dans le venv de l'outil, nnunetv2/preprocessing/preprocessors/default_preprocessor.py:65, 82, 88 ; le commentaire qui s'y trouve dit que la normalisation doit précéder le rééchantillonnage), comme dans le legacy (legacy §3). Un scan qui ne peut pas être lu est marqué failed avec "Unreadable input: ..." et journalisé par position (« scan 3 of 40 »), non par nom (pipeline.py:413-419) ; si aucun n'est lisible, l'exécution s'arrête avec ToolInputError (:422-424). L'index qui ramène de p_NNN au fichier n'existe qu'en mémoire, dans scan_records (:390-420).

5.1 Le bundle et sa recherche

Le serveur donne à l'argument caché model tout le dossier DATA/AMASSS/models/ (layout.py:26-32). resolve_models() y descend quand il contient un seul dossier englobant (par exemple AMASSS_Models/) et aucun des dossiers de codes directement (pipeline.py:143-153), puis appelle find_model_folder() pour chaque code demandé (nnunet_runner.py:50-72) :

<bundle>/<CODE>/**/<Dataset...>__nnUNetPlans__3d_fullres/fold_0/checkpoint_final.pth

Un candidat n'est accepté que lorsque son fold_0/checkpoint_final.pth existe, si bien qu'un bundle à moitié copié rend une structure indisponible au lieu de faire planter l'exécution. Un code sans dossier utilisable est journalisé et listé dans structures_without_model du rapport ; l'exécution n'échoue que si aucun code demandé n'a de modèle, avec ModelNotFoundError (pipeline.py:155-170). Le README donne le bundle livré comme AMASSS_Models/, 2,1 GB (tools/AMASSS/README.md:48). L'organisation et la recherche sont celles du CLI legacy (legacy AMASSS_CLI.py:87-109) ; ce que contient le bundle (neuf modèles PlainConvUNet binaires, deux familles de résolution) est passé en revue sur la page legacy, legacy §4. Le code ne dit pas si la copie du serveur est identique octet pour octet à l'archive que télécharge le widget legacy.

5.3 Prédiction : un modèle par structure, plusieurs à la fois

Prédire structure par structure sur tout le dossier charge chaque checkpoint une seule fois, et non une fois par scan et par structure (pipeline.py:384-386 ; nnunet_runner.py:198-203). Cette partie est la conception du legacy. Ce qui est nouveau, c'est que les structures se recouvrent dans le temps. Le commentaire donne la raison mesurée sur cette chaîne : un appel nnU-Net est un tiers d'inférence et deux tiers de prétraitement sur un seul cœur, si bien qu'une exécution laissait la carte inactive pendant 78 % de sa durée (pipeline.py:428-434). Des threads, pas des processus, parce que torch libère le GIL dans ses noyaux et qu'un pool de processus exigerait un contexte CUDA chacun (:436-439).

# pipeline.py:442, 446-453, 461-482 (shortened)
width = _channels_for(sup, len(models), num_workers)
def predict(item):
    code, model_folder = item
    structure_output = os.path.join(work_dir, f"pred_{code}")
    nnunet_runner.predict_folder(model_folder, nnunet_input, structure_output, device,
                                 tile_step_size=tile_step_size, gpu_resampling=gpu_resampling)
    return code, structure_output
progress.set_width(width)
with futures.ThreadPoolExecutor(max_workers=width) as pool:
    running = {pool.submit(predict, item): item[0] for item in models.items()}
    for future in futures.as_completed(running):
        progress.report(done, len(models), "structure", start=0.1, end=0.9)
        ...  # a failure goes to failed_structures, the others continue
progress.set_width(None)

D'où vient la largeur. _channels_for() (pipeline.py:235-277) demande au superviseur un canal par structure qui a un modèle ; le serveur répond avec ce que la part réservée de l'exécution peut payer, au moins un (VISOR-serve server/execution/runner.py:2134-2148). Un num_workers positif est un plafond sur la demande, jamais un plancher ; sans superviseur (un test, un appel direct) la largeur est de 1, sauf si num_workers nomme un nombre (pipeline.py:261-271). Si la demande échoue, l'exécution continue une structure à la fois (:272-277). Côté serveur, width_from = "structures" fait que l'admission réserve autant de canaux que de structures cochées, et non autant que de scans (VISOR-serve server/deployment.toml:162-179) ; la réservation n'existe que parce que le schéma déclare num_workers (VISOR-serve server/execution/concurrency.py:145 ; commentaire à pipeline.py:243-250). progress.set_width() déclare la largeur autour de cette phase seulement, pour que le serveur apprenne ce que coûte un canal à partir du pic réel (progress.py:41-57).

5.4 Le prédicteur nnU-Net

_build_predictor() (nnunet_runner.py:75-117) fixe les mêmes options que le BuildPredictor() du legacy (legacy AMASSS_CLI.py:112-137), le pas de la fenêtre étant désormais un argument :

# nnunet_runner.py:85-96, 116
options = {
    "tile_step_size": float(tile_step_size),   # 0.5 by default: 50 % overlap
    "use_gaussian": True,                      # gaussian weighting of the patches
    "use_mirroring": False,                    # = --disable_tta, no test-time mirroring
    "device": torch.device(device),
    "verbose": False, "verbose_preprocessing": False, "allow_tqdm": False,
}
# perform_everything_on_device / _on_gpu: whichever the installed nnU-Net declares
...
torch.backends.cudnn.benchmark = False

La dernière ligne n'a pas d'équivalent dans le legacy. Le commentaire l'explique : nnUNetPredictor.__init__ active l'autoréglage de cuDNN, l'autoréglage choisit une convolution en mesurant des temps, si bien que le résultat dépendait de l'occupation de la carte ; sept exécutions d'un même scan ont donné trois masques différents, et comme les structures se recouvrent désormais, cela deviendrait le cas normal (nnunet_runner.py:104-115). La fenêtre glissante elle-même, sa taille de patch et la pondération gaussienne sont celles de nnU-Net, tirées des plans du modèle ; la docstring de tile_step_size consigne que 0,7 déplace le masque (Dice 0,995 contre 0,5), ce qui explique qu'il reste à la valeur par défaut de nnU-Net (__init__.py:72-74).

Ce qui appartient à nnU-Net, pas à ce dépôt. Les formules de la page de l'atlas sont celles de nnU-Net (nnunetv2 2.8.1, tools/AMASSS/.venv/lib/python3.11/site-packages/nnunetv2/ ; le paquet n'est pas dans le dépôt, ce sont donc des références à la bibliothèque installée). Ordre du prétraitement : recadrage, normalisation, rééchantillonnage (preprocessing/preprocessors/default_preprocessor.py:65, 82, 88). CTNormalization : écrêtage aux percentiles 0,5 et 99,5 du premier plan d'entraînement, soustraction de la moyenne, division par l'écart type (preprocessing/normalization/default_normalization_schemes.py:58-72 ; les neuf fichiers de plans du bundle donnent les deux percentiles). Fenêtre glissante : le pas vaut au plus patch_size * tile_step_size et il est raccourci pour que le dernier patch se termine sur le bord de l'image, si bien qu'avec 0,5 le recouvrement est d'au moins un demi-patch (inference/sliding_window_prediction.py:30-54). Poids gaussiens d'écart d'un huitième du patch, les logits pondérés sont additionnés, puis divisés par la somme des poids (inference/predict_from_raw_data.py:626-653).

predict_folder() (nnunet_runner.py:190-236) charge le fold 0 depuis un chemin explicite (initialize_from_trained_model_folder(model_folder, use_folds=(0,), checkpoint_name="checkpoint_final.pth"), sans variable nnUNet_results), puis :

  • avec le rééchantillonnage sur GPU actif : predict_from_files_sequential, tout dans ce processus, parce que des workers lancés auraient chacun besoin de leur propre contexte CUDA (:216-227) ;
  • sur CPU, ou avec gpu_resampling=False : predict_from_files avec deux processus de prétraitement et deux d'export (:228-236). Le legacy utilisait toujours l'appel séquentiel (legacy AMASSS_CLI.py:233-238).

resolve_device() se rabat sur le CPU avec un avertissement quand CUDA est demandé et qu'aucune carte n'est visible (nnunet_runner.py:37-47).

5.5 Rééchantillonnage sur GPU

_enable_gpu_resampling() (nnunet_runner.py:128-187) est l'EnableGpuResampling() du legacy (legacy AMASSS_CLI.py:148-201) rendu facultatif. nnU-Net résout ses deux fonctions de rééchantillonnage par leur nom dans le dictionnaire de configuration, si bien que réécrire les noms redirige les deux bouts sans monkeypatching :

# nnunet_runner.py:165-185 (shortened)
if any(configuration.get(key) != "resample_data_or_seg_to_shape" for key in _RESAMPLING_KEYS):
    return False          # a bundle asking for another resampler is left alone
for key in ("resampling_fn_data", "resampling_fn_probabilities"):
    configuration[key] = resample_torch_fornnunet.__name__
    configuration[f"{key}_kwargs"] = {"is_seg": False, "device": torch.device(device), "mode": "linear"}
for key in _RESAMPLING_KEYS:   # both are @property @lru_cache
    getattr(type(configuration_manager), key).fget.cache_clear()

Il ne s'applique que sur CUDA et seulement si nnU-Net livre le rééchantillonneur torch (:145-158). La différence numérique est l'interpolation des données d'entrée, de l'ordre 3 à l'ordre 1, torch n'ayant pas de mode cubique 3D (:171-174). La docstring estime le rééchantillonnage à environ sept fois le temps du réseau, et celle de l'argument à environ sept fois moins de temps de rééchantillonnage sur le GPU (nnunet_runner.py:131-133 ; __init__.py:75-78). Contrairement au legacy, une erreur de mémoire insuffisante n'est pas retentée sur le chemin CPU : voir les Constats.

6.1 Assemblage par scan

Une fois que chaque structure a tourné, chaque scan lisible est assemblé à son tour (pipeline.py:490-522) par _assemble_scan_outputs() (pipeline.py:561-657) : lire pred_<CODE>/p_NNN.nii.gz pour chaque structure prédite (un fichier manquant est journalisé par identifiant de cas et ignoré, :581-588), binariser avec array > 0 (:590), puis écrire :

  • SEPARATE quand il est demandé, ou chaque fois qu'une seule structure a été produite : un fichier binaire par structure (:599-606) ;
  • MERGED quand il est demandé et qu'au moins deux structures existent : peint dans l'ordre de MERGING_ORDER, où une structure ultérieure écrase une structure antérieure sur les voxels communs (:625-633 ; ordre à catalog.py:87-97).
# pipeline.py:626-630 ; catalog.py:87-97
merged = np.zeros(shape, dtype=np.int16)
for code in MERGING_ORDER:   # SKIN, CV, UAW, CB, MAX, MAND, CBMASK, MANDMASK, MAXMASK
    if code in masks:
        merged = np.where(masks[code] == 1, LABELS[code], merged)

_write_segmentation() (pipeline.py:216-228) convertit en int16, copie l'espacement, l'origine et la direction du scan de référence, et passe par _match_reference_geometry() (:197-213), qui rééchantillonne au plus proche voisin seulement si la géométrie diffère, ce qui ne fait rien dans le cas normal. Il écrit avec useCompression=True.

6.3 Surfaces

Quand generate_surface est vrai, vtk_export.py construit un maillage par structure (séparé) ou un par étiquette ajouté dans un seul fichier (fusionné). La géométrie est censée être celle du legacy ; deux étapes ont été remplacées après que la docstring du module les a rapportées identiques, points, cellules et triangles, sur une vraie mandibule (vtk_export.py:7-20) :

# vtk_export.py:83-118 (shortened)
image = _image_from_mask(mask, reference)      # numpy buffer straight to vtkImageData, no temp .nrrd
contour = vtk.vtkFlyingEdges3D(); contour.SetValue(0, 0.5)   # replaces vtkDiscreteMarchingCubes
smoother = vtk.vtkSmoothPolyDataFilter(); smoother.SetNumberOfIterations(max(0, int(smoothing)))
reduction = min(max(int(decimation), 0), 99) / 100.0
if reduction > 0:
    decimator = vtk.vtkDecimatePro(); decimator.SetTargetReduction(reduction)
    decimator.PreserveTopologyOn(); decimator.SetFeatureAngle(60)

La décimation est nouvelle : 90 % par défaut, ce qui, dit le commentaire, déplace une surface de base du crâne de 0,059 mm en moyenne, contre 1,6 million de triangles pour une base du crâne sans elle (vtk_export.py:99-109 ; __init__.py:63-69). Chaque cellule reçoit une couleur plate issue de LABEL_COLORS (:120-129), l'écrivain est binaire, environ un tiers de la taille de l'ASCII et exact (:139-151), et les maillages sont construits dans un pool de threads de la même largeur que l'inférence, puis écrits dans l'ordre de l'exécution (:155-176 ; pipeline.py:505-509). Le code de la structure est transmis, il n'est plus relu à partir du nom de fichier (vtk_export.py:29-32, 179-205) ; une étiquette inconnue dans un volume fusionné est ignorée avec un avertissement (:244-249). Les maillages sont dans le repère physique de l'image (espacement et origine, vtk_export.py:60-61), sans bascule LPS/RAS ; la matrice de direction n'est pas appliquée, comme dans le legacy (legacy §5.4). Le lissage vient avant la décimation, et la docstring du module consigne que décimer d'abord a été mesuré et refusé parce que cela donne une autre surface (vtk_export.py:22-27). surface_smoothing et surface_decimation sont des arguments techniques masqués.

La géométrie du visualiseur 3D de la page de l'atlas. Elle n'a pas été produite par ce paquet : elle a été construite par le script propre à l'atlas amasss_mesh.py à partir d'une prédiction d'AMASSS sur le scan de test publié (marching cubes, petites composantes connexes écartées, environ 14 000 triangles par structure). Les couleurs et les valeurs d'étiquettes sont celles du catalogue (catalog.py:52-80) ; la peau et les trois masques de recalage sont laissés de côté.

11. Constats dans VISOR

Des scans sont ignorés en silence quand leur nom ressemble à une sortie

Quand scans est un dossier, un fichier est écarté si son nom (sans extension) contient _<prediction_ID>_, se termine par _MERGED, se termine par l'un des neuf codes de structures (_MAND, _MAX, _CB, _CV, _UAW, _SKIN, _CBMASK, _MANDMASK, _MAXMASK) ou se termine par _Seg ou _SegOut (SADT-VISOR pipeline.py:69-85, appliqué à pipeline.py:111-113). Un fichier de patient nommé P01_CB.nii.gz ou P01_Seg.nii.gz est donc ignoré. Seul un décompte est journalisé, jamais les noms (pipeline.py:119-123) ; si tous les fichiers sont ignorés, l'exécution s'arrête avec « No scan found » (pipeline.py:128-131). Un fichier unique passé comme scans n'est jamais filtré (pipeline.py:102-103). Le legacy ignorait aussi certains noms (tout nom avec MASK, tout _<ID>_ : legacy AMASSS_CLI.py:770-777), mais pas ces suffixes.

Une cohorte découpée ne garde que le rapport de son premier lot

Quand le panneau découpe une cohorte, chaque lot écrit AMASSS_report.json à la racine de son propre dossier batch_NN/ (SADT-VISOR pipeline.py:368). Le client ne fusionne les rapports de lots que pour un module qui nomme son rapport dans RUN_REPORT (AutomatedDentalToolsRemote ServerToolsCoreLib/base_widget.py:1493, 1559-1562, 2192) ; AMASSSRemote ne le fait pas (AMASSSRemote/AMASSSRemote.py:63-98), contrairement à AutoCrop3D, ALI, CNE, AutoMatrix, GreedyReg et DOCShapeAXI. Quand les dossiers de lots sont repliés, un nom déjà présent est conservé et le suivant écarté avec un avertissement dans le journal (base_widget.py:2205-2226). Le rapport laissé dans le dossier de sortie décrit donc le premier lot (25 entrées au plus), alors que les masques de tous les lots s'y trouvent. Lu dans le code, non observé.

Empreinte disque : rien n'est nettoyé avant la fin

L'outil garde, pendant toute l'exécution, une copie NIfTI de chaque scan (nnunet_input, SADT-VISOR pipeline.py:387-388, 412) et un dossier pred_<CODE> par structure (pipeline.py:448). Ils ne sont supprimés que par le rmtree de pipeline.py:366. Le legacy supprimait nnunet_input juste après l'inférence et les prédictions de chaque scan juste après son assemblage (legacy AMASSS_CLI.py:872, 651-656). Sur une grosse cohorte, le pic d'utilisation du disque sous output_dir est donc plus élevé que celui du legacy ; le code ne dit pas si c'est voulu.

Le rééchantillonnage sur GPU abaisse l'ordre d'interpolation de l'entrée, par défaut

gpu_resampling vaut vrai par défaut. Quand il s'applique, les données d'entrée sont rééchantillonnées avec torch en mode linéaire au lieu de la spline cubique de nnU-Net : le commentaire du code dit que c'est toute la différence numérique avec une exécution nnU-Net standard (SADT-VISOR nnunet_runner.py:171-179). Il est ignoré sur CPU, et laissé de côté si les plans du modèle demandent un autre rééchantillonneur (nnunet_runner.py:128-187). Le rapport enregistre la valeur demandée sur un périphérique CUDA ; un bundle dont les plans s'en désistent n'est mentionné que dans le journal (pipeline.py:534-538). L'argument est masqué dans le panneau. Le CLI legacy fait la même substitution, sans moyen de la désactiver (legacy AMASSS_CLI.py:148-201, 240-241).

Pas de nouvel essai en cas de manque de mémoire GPU

Le legacy retentait une structure en manque de mémoire avec un rééchantillonnage scipy (legacy AMASSS_CLI.py:240-251). VISOR n'a pas un tel gestionnaire : la structure va dans structures_failed du rapport (SADT-VISOR pipeline.py:475-478, 550), l'exécution continue avec les autres, et n'échoue que si toutes échouent (pipeline.py:484-488). Avec plusieurs structures désormais résidentes en même temps sur la carte (§5.3), c'est la largeur que le serveur accorde qui garde la mémoire dans ses bornes.

Ce que le panneau charge dans la scène

Les résultats ne sont chargés que si l'exécution a produit 12 fichiers chargeables ou moins ; au-delà, rien n'est chargé et une boîte de dialogue renvoie vers le dossier (AutomatedDentalToolsRemote AMASSSRemote/AMASSSRemote.py:82 ; ServerToolsCoreLib/base_widget.py:1596-1602). Les motifs sont *.nii.gz, *.nii, *.nrrd, *.nrrd.gz comme cartes d'étiquettes et *.vtk comme modèles (AMASSSRemote.py:92-98) : une entrée .gipl, dont les masques reviennent en .gipl.gz (SADT-VISOR naming/src/sadt_naming/__init__.py:60), produit des fichiers qui sont enregistrés mais non chargés.

Vérifié : pas de dossier de travail partagé entre exécutions

Chaque exécution travaille sous son propre <output_dir>/.amasss_work et le supprime une fois l'inférence commencée, qu'elle réussisse ou échoue (SADT-VISOR pipeline.py:59-62, 330-331, 342-366). Le dossier est créé avant la recherche des scans et des modèles (pipeline.py:331-336), si bien qu'une exécution qui ne trouve aucun scan le laisse derrière elle, vide. Les deux bugs du legacy sur un dossier temporaire partagé et vidé (legacy §6 et legacy §9) ne s'appliquent pas.

Vérifié : rapport structuré et validation précoce

Le rapport liste les structures sans modèle, les structures qui ont échoué, et un statut, une erreur et une durée par scan (SADT-VISOR pipeline.py:497-558). Les valeurs inconnues de structure ou de fusion sont refusées avant toute inférence (pipeline.py:306-327). Le CLI legacy ne vérifie ni l'une ni l'autre : une structure inconnue devient un modèle manquant, et un mode de fusion inconnu est attrapé scan par scan, après l'inférence (AMASSS_CLI.py:723-732, 623-627). L'autoréglage de cuDNN est désactivé (nnunet_runner.py:116) ; le commentaire du code en donne la raison, l'autoréglage faisait que le même scan donnait des masques différents selon la charge de la carte (nnunet_runner.py:104-115).

Vérifié : aucun nom de fichier dans les journaux ni dans la progression

L'outil désigne un scan par sa position dans le lot ou par son identifiant de cas, dans le journal et dans les messages de progression que le serveur stocke et affiche (SADT-VISOR pipeline.py:116-118, 414-417, 584-587 ; progress.py:13-15, 100). Le legacy journalisait le chemin d'un scan illisible (legacy AMASSS_CLI.py:713). Le nom de fichier reste dans cases[].input du rapport (pipeline.py:399), qui revient à l'appelant avec les résultats.

Les modèles ne sont jamais envoyés par le clinicien

Un modèle est publié comme un nom, jamais comme un argument fichier, si bien que des poids ne peuvent pas être envoyés depuis un portable (VISOR-serve server/registry/conventions.py:14-16), et l'argument est masqué dans le panneau AMASSS (SADT-VISOR layout.py:32). Voir Sécurité et confidentialité.

12. Littérature

La bibliographie est celle de l'outil, inchangée par le portage : l'article PLOS ONE de 2022 décrit un UNETR de MONAI, alors que le code legacy comme celui de VISOR exécutent des checkpoints nnU-Net v2 (nnunet_runner.py:33-34, 208-212 ; pas de MONAI dans tools/AMASSS/pyproject.toml:11-23). La divergence est discutée sur la page legacy, legacy §10, et les références se trouvent dans SOURCES.html.
