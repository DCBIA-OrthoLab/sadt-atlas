AutoMatrix sur VISOR

AutoMatrix applique des transformations de recalage à des scans, des segmentations et des fichiers de landmarks, un dossier entier à la fois. Cette page explique comment, étape par étape : comment les fichiers et les transformations se retrouvent, dans quel sens chacun se déplace, et où atterrit le résultat. Les fichiers, les lignes, les arguments et les constats sont sur la page de code. Le module legacy a sa propre page.

Vue d'ensemble : ce qui entre, ce qui sort

Un outil de recalage (AREG, GreedyReg, FlexReg) trouve une transformation : comment déplacer un scan sur un autre. AutoMatrix prend ce fichier et l'applique à d'autres fichiers du même patient : un scan, une segmentation, ou un ensemble de points de landmarks. Rien n'est prédit : c'est de la géométrie.

EntréeSortie
scans et segmentations (.nii.gz, .nrrd, .gipl), landmarks (.mrk.json), ou un dossier de ces fichiersles mêmes fichiers déplacés par leur transformation, avec un suffixe (Reg par défaut), dans une copie des dossiers d'entrée
transformations (.tfm, .mat, .h5, .hdf5, .txt), ou un dossier de ces fichiersun rapport, AutoMatrix_report.json : ce qui a été apparié, ce qui a échoué, ce qui n'avait pas de partenaire

1. Situation dans la chaîne

AutoMatrix est le seul outil de son groupe qu'un autre outil VISOR appelle : VFACE l'appelle de deux façons : pour faire un miroir (les scans d'une étude d'asymétrie, et ses landmarks), et pour déplacer des landmarks par la transformation de recalage de chaque patient, un appel par région. Il n'appelle rien lui-même. Ses transformations viennent en général d'un recalage, ou de la matrice miroir hébergée. Le calcul s'exécute sur le serveur, sur le CPU, sans réseau et sans poids.

4. Le pipeline, pas à pas

Un appel applique les transformations de chaque patient à chaque fichier de ce patient.

4.1 Découverte et clé patient calculé

Les fichiers sont cherchés dans le dossier et ses sous-dossiers, les fichiers cachés sont ignorés, et chaque fichier reçoit sa clé de la même fonction. S'il n'y a aucun fichier, ou aucune transformation, l'exécution s'arrête avant de rien lire.

Dans le codeLa découverte, le vocabulaire des mots écartés

4.2 L'appariement de secours calculé

Après la règle normale, une seconde chance peut seulement ajouter des paires, jamais en modifier une. Chaque règle utilisée est consignée dans le rapport. Dans l'ordre :

  1. Avec l'option « same transform for every patient » et exactement une transformation, cette transformation va à chaque patient.
  2. Les patients toujours sans paire reçoivent de nouveau une clé avec les coupes du module legacy, et sont appariés aux transformations que personne d'autre n'a prises.
  3. Un patient et une transformation, toujours sans paire : la transformation est appliquée.

Les fichiers sans transformation, et les transformations sans fichier, sont listés dans le rapport plutôt qu'ignorés.

Dans le codeLes trois règles de secours, avec les lignes

4.3 Lire une transformation calculé

La transformation est lue avec ITK (la boîte à outils d'imagerie libre que SimpleITK enveloppe, la bibliothèque qui fait ici la lecture et le rééchantillonnage). Si ITK refuse le fichier mais qu'il contient une simple matrice 4×4 (quatre lignes de quatre nombres, ce que Greedy écrit sous un nom .mat), elle est convertie en transformation affine (une application linéaire plus un décalage) : les trois premiers nombres des trois premières lignes forment une matrice A, le dernier nombre de chaque ligne une translation t. Sinon l'erreur nomme le fichier. Avec plusieurs transformations pour un patient, chacune est appliquée au fichier d'origine ; aucune n'est composée avec une autre.

T(x)=Ax+t
  • Tla transformation
  • xun point, en millimètres
  • Ala partie 3×3 de la matrice (rotation, mise à l'échelle, réflexion)
  • tla translation, le dernier nombre de chacune des trois premières lignes
Dans le coderead_transform et le repli sur un 4x4 texte

4.4 Points de repère : les points par l'inverse calculé

Dans un fichier de landmarks, chaque groupe de points est déplacé. Un point sans statut compte comme défini ; tout autre statut est laissé où il était. Le repère déclaré dans le fichier n'est pas lu : les points sont déplacés tels qu'ils sont écrits.

Dans le codeLes points par l'inverse, avec les lignes

4.5 Images : interpolation et boîte de sortie calculé

Scan ou segmentation ? Le choix détermine l'interpolation. Par défaut il est lu dans les voxels : une image en virgule flottante est un scan ; de même pour une image avec une valeur négative, une valeur supérieure à 1000, ou plus de 128 valeurs distinctes ; tout le reste est une carte de labels. La réponse est consignée par fichier.

Où atterrit le résultat. Si une image de référence est donnée, sa grille est utilisée. Sinon (le défaut, puisque la référence est masquée), la sortie a la taille, l'espacement et la direction de l'entrée, et son origine est déplacée par la transformation.

Dans le codeScan ou carte de labels, l'interpolateur, la grille de sortie

4.6 Noms, échecs, rapport calculé

La sortie reproduit les dossiers d'entrée. Le nom est le nom d'origine, puis le suffixe, puis le nom de la transformation quand cette option est activée ou quand le patient a plusieurs transformations (si bien que deux transformations n'écrivent jamais le même fichier). Par exemple p1.nii.gz avec p1_CBReg_matrix.tfm et p1_MANDReg_matrix.tfm donne p1_Reg_p1_CBReg_matrix.nii.gz et p1_Reg_p1_MANDReg_matrix.nii.gz (exécuté le 2026-11-09). Un fichier qui échoue est consigné avec son erreur et les autres continuent. Si rien n'a été écrit, l'exécution s'arrête avec les premières raisons ; sinon AutoMatrix_report.json liste, par patient, les transformations, les fichiers déplacés, les échecs, puis les fichiers et transformations sans paire.

5. Ce que vous pouvez choisir

  • Fichiers et transformations : un fichier ou un dossier pour chacun (les deux sont obligatoires).
  • Même transformation pour chaque patient : désactivé par défaut ; exige exactement une transformation.
  • Inclure le nom de la transformation : désactivé par défaut, forcé quand un patient a plusieurs transformations.
  • Suffixe de sortie : Reg par défaut, peut être vide.
  • Masqués dans le panneau : la méthode de rééchantillonnage (automatique par défaut) et le volume de référence.
  • Use the mirror matrix (panneau Slicer) : remplit Transforms avec le fichier miroir hébergé et coche l'option de transformation commune.

9. Problèmes connus dans VISOR

Chaque point est vérifié dans le code et décrit, avec sa preuve, sur la page de code ; la liste figure aussi dans les constats.

  • La ligne d'état dit toujours « 0 file(s) written » dans Slicer, et les fichiers sans paire ne sont jamais signalés. Preuve.
  • Sans référence, la boîte de sortie suit la transformation : une réflexion, comme la matrice miroir, laisse la boîte vide. Un correctif existe sur une branche non fusionnée. Preuve.
  • La liste des fichiers produits reste vide pour les volumes. Preuve.
  • Une transformation non inversible n'arrête pas l'exécution : les landmarks échouent, le volume est écrit. Preuve.
  • La documentation du module Remote contredit le code. Preuve.
  • Le repère déclaré d'un fichier de landmarks n'est pas lu. Preuve.
  • Le README et le manifeste de données sont périmés sur cet outil. Preuve.
