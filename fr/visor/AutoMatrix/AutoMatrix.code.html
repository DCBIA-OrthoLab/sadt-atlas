AutoMatrix sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR d'AutoMatrix dans le code, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le module legacy et les constats. L'explication lisible du même pipeline, avec les maths, est sur la page de l'atlas.

VISOR Code Atlas (explication) Page legacy Guide (VISOR)

Dans VISOR, AutoMatrix est un paquet Python qui s'exécute sur le serveur : Slicer envoie les fichiers et les transformations, le serveur les apparie par patient, rééchantillonne les volumes, déplace les points de repère et renvoie les résultats. La convention de transformation est celle du legacy (le volume est rééchantillonné à travers la transformation, les points se déplacent à travers son inverse) ; ce qui a changé, c'est la règle d'appariement, la grille de sortie quand aucune référence n'est donnée, les formats, et un rapport de ce qui a été apparié et de ce qui a échoué. Cette page suit le portage depuis la requête jusqu'aux fichiers qui reviennent : position, fichiers, chaque étape avec le code qui l'effectue, les arguments publiés, l'environnement, les différences avec le module legacy et les constats. Elle décrit le portage dans SADT-VISOR (branche tool/vface, 6ba2a78, 2026-09-30), servi par VISOR-serve (e9a7e5d) et piloté depuis Slicer par l'extension AutomatedDentalToolsRemote (19b95e8). Le portage a été fait à partir d'un état amont plus ancien que 3c67957 (les fichiers AutoMatrix et Automatrix_CLI ont changé entre b1ae78c et 3c67957), donc quelques détails de la page legacy, qui lit 3c67957, peuvent différer de ce dont le portage est parti. Rien ici ne prétend qu'un serveur est déployé : tout est lu dans le code, et les comportements marqués « run on 2026-11-09 » ont été reproduits en appelant le run() du paquet dans son propre environnement virtuel sur des volumes synthétiques.

4. Le pipeline, pas à pas

Explication en langage courant et maths : page de l'atlas.

Un appel de run() applique les transformations de chaque patient à chaque fichier de ce patient (SADT-VISOR AutoMatrix/__init__.py:68-185).

4.1 Découverte et clé patient calculé

Explication en langage courant et maths : page de l'atlas.

_walk prend un fichier tel quel ou parcourt un dossier récursivement, ignore les fichiers cachés, et attribue une clé à chaque fichier avec la même fonction (__init__.py:267-298). Acceptés : images .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl, points de repère .mrk.json, transformations .tfm .mat .h5 .hdf5 .txt (pipeline.py:45-67). La clé est le patient_stem partagé plus le vocabulaire des transformations et des régions (pipeline.py:27-42) :

PATIENT_TOKENS_TO_DROP = (
    "transform", "matrix", "warp", "reg", "cbreg", "mandreg", "maxreg",
    "cb", "mand", "max", "md", "mx",
)
def patient_of(filename: str) -> str:
    return pairing.patient_stem(filename, also_drop=PATIENT_TOKENS_TO_DROP)

Ainsi C_0001_CB_Reg_transform.tfm a pour clé C_0001, comme son scan (exécuté le 2026-11-09). Aucun fichier du tout, ou aucune transformation du tout, est une ValueError avant que rien ne soit lu (__init__.py:72-84).

4.2 L'appariement de secours calculé

Explication en langage courant et maths : page de l'atlas.

_pair_like_legacy s'exécute après la règle normale et peut seulement ajouter des paires, jamais en modifier une (__init__.py:188-264) :

  1. Avec same_transform_for_every_patient et exactement une transformation, cette transformation va à chaque patient, consignée comme « asked to share one transform » (:215-220).
  2. Les patients restés sans paire reçoivent de nouveau une clé avec les coupes de sous-chaînes legacy, qui diffèrent volontairement des deux côtés (pipeline.py:200-237), et sont appariés aux transformations que personne d'autre n'a prises : « legacy file names » (__init__.py:222-249).
  3. Un patient et une transformation, toujours sans paire : appliquée, « the only transform, applied to every patient » (:258-262).

Chaque règle utilisée est consignée dans paired_by (__init__.py:110-111). Les fichiers sans transformation et les transformations sans fichier sont listés dans le rapport (:105-106).

4.3 Lire une transformation calculé

Explication en langage courant et maths : page de l'atlas.

sitk.ReadTransform d'abord ; si ITK la refuse, une simple matrice 4×4 écrite sur quatre lignes de quatre nombres, ce que Greedy écrit sous un nom .mat, devient une AffineTransform ; sinon une RuntimeError qui nomme le fichier et cite ITK (pipeline.py:138-180) :

try:
    return sitk.ReadTransform(path)
except RuntimeError as itk_error:
    matrix = _read_plain_matrix(path)
    ...
    affine = sitk.AffineTransform(3)
    affine.SetMatrix([value for row in matrix[:3] for value in row[:3]])
    affine.SetTranslation([row[3] for row in matrix[:3]])
    return affine

La transformation est lue par fichier (__init__.py:311). Avec plusieurs transformations pour un patient, chacune est appliquée au fichier d'origine ; aucune n'est composée avec une autre (__init__.py:130-143).

4.4 Points de repère : les points par l'inverse calculé

Explication en langage courant et maths : page de l'atlas.

Un .mrk.json a ses points déplacés par transform.GetInverse(), dans chaque groupe de marqueurs ; un point dont le positionStatus est absent compte comme défini, tout autre statut est laissé où il était ; coordinateSystem n'est pas lu (pipeline.py:71-104). La raison est la convention du rééchantillonneur : ResampleImageFilter fait passer chaque point de sortie par la transformation pour trouver où lire l'entrée, donc le contenu de l'image se déplace par l'inverse, et les points doivent suivre le même sens (docstring pipeline.py:3-6, 74-78). La sortie est <stem>[_<tail>].mrk.json et figure à la fois dans outputs (avec points_moved) et dans produced (__init__.py:327-333).

4.5 Images : interpolation et grille de sortie calculé

Explication en langage courant et maths : page de l'atlas.

L'interpolateur est le plus proche voisin pour une segmentation et linéaire pour un scan (pipeline.py:120-125). Ce qu'est un fichier vient de content ; avec la valeur par défaut Automatic, des voxels (__init__.py:350-354 ; pipeline.py:264-296) : une image en virgule flottante est un scan, une valeur négative ou supérieure à 1000 en fait un scan, et plus de 128 valeurs distinctes, comptées morceau par morceau, en font un scan ; tout le reste est une carte de labels. La réponse est consignée par fichier sous detected.

La grille de sortie (pipeline.py:127-133) :

if reference is not None:
    resampler.SetReferenceImage(reference)
else:
    resampler.SetSize(image.GetSize())
    resampler.SetOutputSpacing(image.GetSpacing())
    resampler.SetOutputDirection(image.GetDirection())
    resampler.SetOutputOrigin(transform.TransformPoint(image.GetOrigin()))

Sans référence, ce qui est le cas par défaut puisque reference est masqué, la grille garde la taille, l'espacement et la direction de l'entrée, et son origine est déplacée par la transformation. Pour une translation, le contenu reste dans la boîte ; pour une réflexion, non (voir les constats). En dehors de l'entrée, les voxels valent 0 (pipeline.py:125).

4.6 Noms, échecs, rapport calculé

Explication en langage courant et maths : page de l'atlas.

La sortie reproduit l'arborescence d'entrée (__init__.py:323-325). La queue est output_suffix, puis le nom complet (stem) de la transformation quand name_output_after_transform est activé ou que le patient a plus d'une transformation ; les parties sont jointes par _, un suffixe vide n'ajoute rien, et les extensions composées sont conservées (__init__.py:141, 301-303, 317-322, 335-342). Exemple exécuté le 2026-11-09 : p1.nii.gz avec p1_CBReg_matrix.tfm et p1_MANDReg_matrix.tfm donne p1_Reg_p1_CBReg_matrix.nii.gz et p1_Reg_p1_MANDReg_matrix.nii.gz. Un fichier qui échoue est consigné dans cases[patient].failed avec son exception, et la boucle continue (__init__.py:144-155). Si rien n'a été écrit, ValueError avec les cinq premiers échecs ou les deux décomptes de non-appariés, et pas de rapport (:164-184). Sinon AutoMatrix_report.json :

9. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

La ligne d'état dit toujours « 0 file(s) written »

AutoMatrixRemote._summarize lit report.get("written") et report.get("skipped") (AutomatedDentalToolsRemote AutoMatrixRemote/AutoMatrixRemote.py:227-235). Le rapport écrit par l'outil n'a aucune de ces clés : il porte summary.files_written et les listes without_a_transform et transforms_without_a_file (SADT-VISOR AutoMatrix/__init__.py:105-106,158-161). Exécuté le 2026-11-09 : le rapport d'une exécution qui a écrit un fichier contenait summary.files_written = 1 et pas de clé written, donc, d'après le code de _summarize, le message est AutoMatrix: 0 file(s) written. quoi qu'il se soit passé, et les fichiers sans paire ne sont jamais signalés dans Slicer. Aucun test ne couvre _summarize (rien dans test_automatrix_client.py ne le nomme). AutoCrop3DRemote lit les bonnes clés (AutoCrop3DRemote.py:119-120).

Sans référence, la boîte de sortie suit la transformation

Sans reference (le défaut, et l'argument masqué), la sortie garde la taille et la direction de l'entrée et prend pour origine transform.TransformPoint(origin) (SADT-VISOR AutoMatrix/pipeline.py:133). La grille legacy était celle de l'image elle-même (Automatrix_CLI.py:279@3c67957). Exécuté le 2026-11-09 sur un volume de 20×20×20 en voxels de 1 mm avec son origine à -10 mm sur chaque axe, contenant un bloc de 10×10×10 (1000 voxels non nuls) aux indices 2 à 11, rééchantillonné comme une segmentation : une translation de (5,0,0) a déplacé l'origine à -5 et gardé 200 des 1000 voxels ; une réflexion diag(-1,1,1) (un substitut du fichier miroir hébergé, dont le contenu n'a pas été téléchargé) a déplacé l'origine de -10 à +10 et n'en a gardé aucun ; la même réflexion avec le volume comme propre référence les a gardés tous les 1000. C'est le chemin de la case « Use the mirror matrix » et du miroir de VFACE (SADT-VISOR tools/VFACE/src/sadt_vface/tools.py:179-187, sans reference). Des tests figent le comportement pour la translation (tests/test_run_options.py:265-277, tests/test_resample.py:108-115), et l'un d'eux s'appuie dessus (tests/test_resample.py:44-53).

Non livré. Un correctif existe sur la branche fix/automatrix-mirrors-into-an-empty-box (commit ce4f6fb, 2026-09-28, en local et sur origin) : il garde l'origine de l'entrée sauf si la transformation est une translation pure. Cette branche n'est pas un ancêtre de tool/vface (6ba2a78), donc le comportement décrit ci-dessus est celui de cet arbre.

produced reste vide pour les volumes

Chaque cas commence par "produced": [] (SADT-VISOR AutoMatrix/__init__.py:127-128) et le seul ajout se trouve dans la branche des points de repère (:332). Exécuté le 2026-11-09 avec un volume : outputs contenait le fichier et produced valait []. Le commentaire en :125-126 dit que produced est la liste plate que renvoie chaque outil du catalogue ; AutoCrop3D la remplit pour ses volumes (SADT-VISOR tools/AutoCrop3D/src/sadt_autocrop3d/__init__.py:236). La conséquence pour les clients qui la lisent n'a pas été retracée.

Une transformation non inversible n'arrête pas l'exécution

Pour une transformation qui ne peut pas être inversée, le fichier de points de repère de ce patient échoue et est listé dans cases[patient].failed, alors que le volume du patient est écrit (SADT-VISOR AutoMatrix/__init__.py:144-155). Exécuté le 2026-11-09 avec un champ de déplacement nul stocké en .h5 : GetInverse a levé Unable to create inverse!, le volume a été écrit et files_written valait 1. L'exécution ne lève une erreur que si rien du tout n'a été écrit (:164), et dans ce cas aucun rapport n'est écrit, car le rapport est enregistré après cette vérification (:184). Le panneau Slicer n'affiche pas failed (voir le constat sur la ligne d'état).

La documentation du module Remote contredit le code

AutomatedDentalToolsRemote AutoMatrixRemote/AutoMatrixRemote.py:16-19 dit que le serveur applique encore une matrice dont le nom contient « mirror » dans l'espace propre du scan ; le portage ne le fait pas (SADT-VISOR AutoMatrix/README.md:89-92, tests/test_run_options.py:311-331). AutoMatrixRemote.py:12-15 dit que « nothing is hidden » alors que reference et content sont masqués (layout.py:28,43). Le test client construit son schéma à la main avec hidden: False partout et d'autres noms de sections (test_automatrix_client.py:72-186), donc test_nothing_is_marked_hidden (:255-257) vérifie cette copie, pas le schéma du serveur. Le commentaire de SADT-VISOR AutoMatrix/layout.py:22-27 dit que VFACE passe "None" à ses huit sites d'appel ; les deux enveloppes d'AutoMatrix de SADT-VISOR tools/VFACE/src/sadt_vface/tools.py:179-187,205-212 ne passent aucun reference et sont appelées depuis trois endroits de dispatch.py (:161,232,257). Passer "None" et ne rien passer reviennent au même, donc c'est un commentaire qu'on ne peut pas faire correspondre au décompte, pas une contradiction prouvée.

Le coordinateSystem d'un fichier de points de repère n'est pas lu

Les points sont déplacés tels qu'ils sont écrits, quel que soit le repère que déclare le fichier, et la sortie conserve la déclaration (SADT-VISOR AutoMatrix/pipeline.py:71-104, aucune lecture du champ). Les points dont le statut n'est ni absent ni « defined » restent à leurs anciennes coordonnées dans un fichier signalé comme transformé (:95-96). Les deux comportements sont ceux du CLI legacy (page legacy). Lu dans le code.

Ce que disent le README et le manifeste de VISOR

VISOR-serve scripts/data-manifest.yml:730 indique encore « NOT PORTED YET (test data only) » alors que la source de l'outil est montée dans VISOR-serve docker-compose.dev.yml:51 ; SADT-VISOR AutoMatrix/README.md:111-113 parle de 1,4 GB de modèles alors que le manifeste liste des archives de test (data-manifest.yml:731-751). Les fichiers hébergés sont AutoMatrixRelease1 à 4 (247 961 348, 247 962 104, 254 256 972 et 787 127 578 octets) et Mirror (468 octets).

L'appariement, les noms et les échecs sont signalés

Une seule règle de nommage des deux côtés, avec les coupes legacy en seconde chance consignée (paired_by) ; les fichiers et transformations sans paire nommés dans le rapport ; un fichier en échec ne coûte que ce fichier (SADT-VISOR AutoMatrix/__init__.py:105-111,144-155) ; deux transformations d'un même patient n'écrivent jamais le même nom (tests/test_run_options.py:224-243). Les 234 tests du paquet ont réussi le 2026-11-09.
