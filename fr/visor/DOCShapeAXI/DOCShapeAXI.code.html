DOCShapeAXI sur VISOR : le code

L'explication lisible du même pipeline, avec les maths, est sur la page de l'atlas.

Les références de cette page nomment un dépôt, puis un chemin à l'intérieur, puis une ligne : SADT-VISOR est le catalogue d'outils (commit 6ba2a78), VISOR-serve le serveur (e9a7e5d), Remote le client Slicer (AutomatedDentalToolsRemote 19b95e8), legacy SlicerAutomatedDentalTools à 3c67957. Un chemin nu comme catalog.py:50 se trouve dans SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/. Tout a été lu dans le code ; rien sur cette page n'a été exécuté, sauf les deux vérifications nommées là où elles apparaissent (la comparaison fichier par fichier de shapeaxi 1.0.10 et 1.1.1, et un petit test CPU d'indices répétés). 1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

  • État : porté, implémenté dans le code, avec des tests dans l'outil (SADT-VISOR tools/DOCShapeAXI/tests/test_run.py, 91 fonctions de test, non exécutées pour cette page). Un serveur configuré seulement avec les scripts de déploiement de VISOR-serve ne peut pas l'exécuter : le backbone EfficientNet qu'il exige n'est déposé par aucun d'eux (voir Constatations dans VISOR).
  • Nom d'API DOCShapeAXI (SADT-VISOR tools/DOCShapeAXI/pyproject.toml:57-59) ; modules __init__.py, catalog.py, engine.py, pipeline.py.
  • Panneau client DOCShapeAXIRemote, un panneau fin (Remote DOCShapeAXIRemote/DOCShapeAXIRemote.py:63,67,69 ; construit, CMakeLists.txt:34). Il charge les résultats .vtk et .vtp comme modèles, 12 au plus (:82,88-92).
  • Appelle / appelé par : personne ; pas d'argument sup (__init__.py:18-25), et aucun autre outil ne nomme DOCShapeAXI.
  • Données hébergées : les cinq checkpoints sont dans le manifeste de données (VISOR-serve scripts/data-manifest.yml:597-614). Il n'y a pas de surface de test, volontairement : rien de public n'est une voie aérienne, un condyle ou une fente (:616-622). L'en-tête du manifeste dit encore "NOT PORTED YET" (:595), ce qui est faux : l'outil et son client existent.

3.1 Un nom de checkpoint décide de l'analyse

Explication en langage courant et maths : page de l'atlas.

Le legacy demandait à l'appelant data_type, task, model, nn et num_classes comme arguments positionnels séparés (legacy DOCShapeAXI_CLI/DOCShapeAXI_CLI.py:299-307), si bien qu'un checkpoint à deux classes pouvait être exécuté avec une échelle à quatre classes. VISOR prend un seul argument, model, et cherche son nom de base dans une table (catalog.py:50-71, __init__.py:54). Un nom inconnu est une ValueError qui liste les cinq connus (catalog.py:74-88) ; la recherche a lieu avant la vérification de l'existence du fichier (__init__.py:54-57).

3.2 Surfaces, périphérique et réseau

Explication en langage courant et maths : page de l'atlas.

  • Découverte : un seul .vtk, ou un dossier parcouru récursivement, fichiers cachés ignorés, trié (pipeline.py:22,40-64). Ne rien trouver est une ValueError, "DOCShapeAXI reads surfaces, not volumes" (__init__.py:59-64). Le point de montage donné à shapeaxi est le dossier d'entrée, ou le dossier du fichier pour un fichier unique (:71).
  • Périphérique : cuda se rabat sur cpu avec un avertissement quand aucune carte n'est visible (pipeline.py:67-72).
  • Réseau : load_network vérifie que la classe nommée par le catalogue existe dans shapeaxi.saxi_nets_lightning, puis que le backbone EfficientNet est déposé, puis autorise les classes que le checkpoint sérialise, et le charge (pipeline.py:130-151) :
network_class = getattr(saxi_nets_lightning, network_name, None)   # else ValueError
check_backbone_is_staged()      # <torch hub dir>/checkpoints/efficientnet-b0-355c32eb.pth, else FileNotFoundError
allow_checkpoint_globals()      # shapeaxi transform classes + torchvision Compose
model = network_class.load_from_checkpoint(checkpoint, strict=False)
model.eval(); model.to(device)

La liste d'autorisation existe parce que torch 2.6 a fait de weights_only=True la valeur par défaut et que ces checkpoints portent leurs transformations d'entraînement dans hyper_parameters (pipeline.py:108-127). strict=False est conservé du legacy (legacy DOCShapeAXI_CLI.py:135,201).

3.3 Passe de prédiction

Explication en langage courant et maths : page de l'atlas.

La liste de fichiers est un DataFrame pandas construit en mémoire (le legacy écrivait un CSV dans le dossier de sortie avec le mode 'a', DOCShapeAXI_CLI.py:111-118), donné au SaxiDataset de shapeaxi avec EvalTransform(scale_factor), le facteur d'échelle étant lu dans les hyperparamètres du checkpoint (engine.py:11-34) ; shapeaxi 1.1.1 l'ignore ensuite (voir la vérification ci-dessous). Puis, une surface à la fois (engine.py:37-64) :

mesh = model.create_mesh(vertices, faces, normals)
points = model.sample_points_from_meshes(mesh, model.hparams.sample_levels[0])
views, _ = model.render(mesh)
output = model(points, views)
if not analysis.is_regression:
    output = torch.argmax(softmax(output).detach(), dim=1, keepdim=True)
predictions.append(float(output.reshape(-1)[0].cpu()))

Chaque prédiction est consignée avec le chemin de la surface relatif au point de montage et soit class (un entier), soit score (un flottant, régression) (__init__.py:81-90). L'échantillonnage des points et le rendu sont ceux de shapeaxi ; ni l'outil ni le legacy ne fixent de graine aléatoire (aucun seed ni manual_seed dans les sources de l'outil).

3.4 Passe d'explication (Grad-CAM)

Explication en langage courant et maths : page de l'atlas.

Seulement quand explain est vrai (__init__.py:92-95). Le dataset est reconstruit et chaque surface est rendue de nouveau ; puis, pour chaque classe k dans range(analysis.classes) (engine.py:67-114) :

cam = LayerGradCam(model, model.convnet.module._blocks[-1], device_ids=[0])
attribution = cam.attribute(inputs=(points, views), target=k, attr_dim_summation=False)
attribution = attribution.sum(dim=1).cpu().detach()
scaled = scale_attribution(attribution.numpy(), (224, 224))   # resize, clip 1/99 percentiles, rescale to [-1, 1]
projected = gradcam_process(_Namespace(device, target_class=k), scaled, faces, per_face, vertices)
surface.GetPointData().AddArray(projected)                    # array grad_cam_target_class_<k>
post_process.MedianFilter(surface, projected)
  • Redimensionnement : torch.nn.functional.interpolate, bilinéaire, align_corners=False, à la place du cv2.resize du legacy ; le commentaire dit qu'un test cale les deux à 1e-5 près (pipeline.py:163-184, pyproject.toml:45-51).
  • Normalisation : écrêtage au 1er et au 99e percentiles, puis projection sur [-1, 1] ; une carte plate devient des zéros plutôt que NaN (pipeline.py:186-199).
  • Quelle couche : le dernier bloc de la branche EfficientNet 2D, comme dans le legacy (DOCShapeAXI_CLI.py:150-151) : la carte explique la branche multi-vues, pas la branche nuage de points.
  • Projection : gradcam_process est celui de shapeaxi (saxi_gradcam.py:112-144 dans 1.0.10 et dans 1.1.1, le même code). Les faces partent de 0 et prennent maximum(old, new) vue après vue, si bien que sur le maillage une face porte max(0, max over views) et la plage est [0, 1] ; la valeur va au premier sommet de la face, et les sommets qui ne sont le premier sommet de personne sont remis à 0 (:134). Dans une même vue, les pixels qui montrent la même face partagent un indice et l'écriture qui reste n'est pas définie (la dernière sur le CPU, pas le maximum) ; les pixels de fond portent l'indice -1 et écrivent sur la dernière face. Le test CPU et les détails sont sur la page de code legacy, section 5d ; rien n'a été exécuté sur le GPU.
  • Filtre médian : post_process.MedianFilter (post_process.py:294-308) remplace chaque sommet, rempli ou vide, par la médiane de ses voisins, lui-même exclu (utils.py:363-376), et pas seulement les vides.
  • Noms de tableaux : l'indice de classe est toujours passé comme target_class, qui nomme le tableau (engine.py:104-106,117-129). Le legacy ne le fixait que lorsque num_classes > 1 (DOCShapeAXI_CLI.py:171-174), donc le checkpoint de régression reçoit désormais lui aussi un nom par classe, grad_cam_target_class_0. Lu dans le code.
  • Écriture : une fois par surface après toutes les classes, à plat dans output_dir sous le nom de base de l'entrée (engine.py:111-113) ; le legacy écrivait dans la boucle des classes, dans <out>/explainability/<task>/ (DOCShapeAXI_CLI.py:153,185-186).

3.5 Sorties et rapport

Explication en langage courant et maths : page de l'atlas.

Les surfaces écrites sont renommées avec output_suffix avant l'extension (__init__.py:118-133), si bien que P01.vtk devient P01_pred.vtk. DOCShapeAXI_report.json est toujours écrit (:97-110) :

{
  "model": "condyles_4_class.ckpt", "anatomy": "Mandibular condyle", "task": "severity",
  "classes": 4, "network": "SaxiMHAFBClassification", "device": "cuda",
  "explained": true, "surfaces": 2,

                   {"surface": "right/P01.vtk", "class": 0} ]

Les valeurs sont illustratives, les clés sont celles du code. Cet exemple est aussi la collision des constatations : les deux surfaces seraient écrites dans le même output_dir/P01.vtk. run() renvoie {"outputs": {...}, "predictions": [...], "report": path} bien qu'il soit annoté -> Path (__init__.py:25,112-115). Il n'y a pas de CSV.

8. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Le backbone EfficientNet est un prérequis que personne ne dépose

shapeaxi construit un EfficientNet-B0 autour de chaque checkpoint. L'outil refuse de le laisser se télécharger au milieu d'une requête, et lève plutôt FileNotFoundError sauf si efficientnet-b0-355c32eb.pth est déjà sous <torch hub dir>/checkpoints/ (SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/pipeline.py:80-105, appelé depuis load_network en :146 ; README.md:112-121). Ni le manifeste de données ni aucun script de VISOR-serve ne mentionne ce fichier (recherche de "efficientnet" dans les trois dépôts : seuls le README.md, pipeline.py et tests/test_run.py de l'outil le font). Un déploiement qui suit les étapes habituelles de dépôt échoue donc à son premier appel, une fois les surfaces envoyées. Lu dans le code ; on n'a pas vérifié si un serveur donné a le fichier dans son cache.

La ligne d'état affiche des points d'interrogation

Le client construit son résumé à partir de report.get("data_type") et report.get("checkpoint") (Remote DOCShapeAXIRemote/DOCShapeAXIRemote.py:122-130). Le rapport écrit par l'outil n'a aucune de ces clés : il a model, anatomy, task, classes et network (SADT-VISOR __init__.py:97-110). Le résumé du panneau affichera "?" à la place de l'anatomie et du checkpoint, tandis que task et le nombre de surfaces sont renseignés. Lu dans le code, non exécuté dans Slicer.

Le client décrit une table de prédictions et un sélecteur de tâche qui n'existent pas

Les commentaires du client disent que le résultat est une "prediction table" au format CSV (DOCShapeAXIRemote.py:76-86) et qu'un argument task se restreint à l'anatomie par une règle options_when (:12-17). L'outil n'écrit aucun CSV (__init__.py:97-110), et son schéma a six arguments, dont aucun ne s'appelle task, sans options_when (sortie de scripts/describe.py). La tâche se choisit en prenant le fichier de checkpoint, donc l'utilisateur doit savoir ce que signifient airways_2_class.ckpt et airways_4_regress.ckpt.

Deux entrées de même nom de fichier entrent en collision en sortie

Les surfaces sont trouvées récursivement mais écrites à plat : a/s.vtk et b/s.vtk vont toutes deux vers output_dir/s.vtk (engine.py:111-112), si bien que la seconde remplace la première, alors que le rapport les distingue par chemin relatif (__init__.py:84). L'étape de renommage déplace ensuite s.vtk vers s_pred.vtk une fois par entrée (__init__.py:128-132) : le second déplacement ne trouve aucun fichier, ce qui terminerait l'exécution par une FileNotFoundError après tout le calcul ; avec un output_suffix vide, l'écrasement est silencieux. CLIC et CNE reproduisent l'arborescence d'entrée pour éviter exactement cela. Lu dans le code, non exécuté.

Toujours vrai depuis le legacy : échantillonnage sans graine, saillance d'une seule branche

Aucune graine n'est fixée dans les sources de l'outil et il n'y a pas d'argument seed, donc l'échantillonnage aléatoire de points dans shapeaxi (engine.py:54,92) n'est pas fixé d'une exécution à l'autre, comme dans le legacy (page legacy, pièges). La couche Grad-CAM est le dernier bloc de la branche de vues 2D (engine.py:82-83), donc la carte ne dit rien de la branche nuage de points. Lu dans le code.

Commentaires en désaccord avec les versions figées

Le commentaire au-dessus de la version figée de captum parle de 0.9.0 alors que la version figée est captum==0.8.0 (pyproject.toml:39-44). Le manifeste de données étiquette encore l'outil "NOT PORTED YET" (data-manifest.yml:595). Ni l'un ni l'autre ne change ce qui s'exécute.

Vérifié : l'incohérence de version de shapeaxi du legacy est corrigée ici

Le code legacy est écrit pour l'API shapeaxi 1.x alors que son installeur demande 2.0.2 ou plus (legacy ADT/ADTLib/env/install_pytorch.py:385). VISOR fige shapeaxi==1.1.1, avec la raison dans le commentaire (pyproject.toml:18-30), et résout les classes du réseau depuis saxi_nets_lightning, où elles se trouvent (pipeline.py:135-145). Le checkpoint n'est plus copié dans le dossier de sortie. L'EvalTransform de shapeaxi 1.1.1 ne respecte pas non plus scale_factor : UnitSurfTransform.__call__ ne le transmet jamais (saxi_transforms.py:48-57), identique dans 1.0.10 et 1.1.1 (les deux paquets ne diffèrent que par __about__.py, comparés fichier par fichier pour cette passe ; 1.1.1 téléchargé depuis l'index des paquets).
