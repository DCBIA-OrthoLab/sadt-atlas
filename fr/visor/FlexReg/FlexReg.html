FlexReg sur VISOR

FlexReg recale une arcade intra-orale sur une autre en ne regardant que le palais, la partie de la bouche qui ne bouge pas entre deux visites. Il trace d'abord un patch en forme de papillon sur le palais, à partir de quatre dents, puis fait glisser le patch d'un scan sur celui de l'autre. Cette page explique comment, pas à pas, avec les maths. Quand le code fait quelque chose qui mérite d'être vérifié, un lien mène à la page de code. Le module legacy est décrit sur sa propre page.

Vue d'ensemble : ce qui entre, ce qui sort

Entre deux visites, les dents peuvent bouger, et les gencives aussi ; le palais à peine. FlexReg s'en sert : il marque un patch du palais sur chaque arcade et recale les arcades sur ce seul patch, de sorte que les dents elles-mêmes sont libres d'avoir bougé. Le patch est construit par la géométrie, sans réseau, à partir de quatre dents choisies sur l'arcade.

Ce que c'est
Entréeune surface intra-orale (.vtk, .vtp ou .stl) qui porte déjà un numéro de dent sur chaque point, ou un dossier de telles surfaces ; une arcade de référence sur laquelle recaler
Idéequatre centroïdes de dents donnent quatre coins ; les coins donnent un contour ; le contour est rempli sur la surface ; un ICP rigide aligne le patch d'une arcade sur le patch de l'autre
Sortiela surface recalée, une transformation .tfm que Slicer peut charger, et FlexReg_report.json

Trois modes : Patch construit seulement le patch, Register recale une surface qui en a déjà un, Patch and register fait les deux.

1. Situation dans la chaîne

FlexReg n'appelle aucun autre outil et aucun outil ne l'appelle. Dans le module legacy, le widget lançait une segmentation des couronnes quand l'arcade n'avait pas d'étiquettes de dents ; dans VISOR, l'arcade doit arriver déjà étiquetée, par exemple à la suite d'une exécution de Crown_Seg. Plus rien ne calcule le patch mucogingival.

Dans le codeL'état du portage, les appels, et ce qui est attendu en amont

2. Fichiers en jeu

L'outil est un simple paquet Python : son cœur géométrique (orientation, patch, propagation, ICP, sélection des dents) est le code legacy avec des variables renommées, et la partie nouvelle est le point d'entrée et les fonctions de lecture, de fusion, de recalage et d'écriture qui l'entourent. Une petite bibliothèque dans le client Slicer rejoue le contour pour l'aperçu.

Dans le codeChaque fichier avec sa taille et son rôle, sur le serveur et dans le client

3. Ce qui s'exécute où

Le serveur construit le vrai patch (le remplissage a besoin du GPU), recale et écrit tout. Le panneau Slicer ne fait qu'un aperçu du contour : pendant que vous faites glisser un joystick, le contour est recalculé localement avec les mêmes constantes et dessiné dans la scène, sans aller-retour. Le remplissage du patch est laissé au serveur. L'aperçu ne fonctionne que si la surface est déjà dans la scène Slicer, pas pour un dossier.

Dans le codeCe que chaque côté calcule, et comment l'aperçu rejoue le serveur

4. Le pipeline, pas à pas

Une exécution traite une surface ou un dossier de surfaces.

Dans le codeL'ordre des appels dans le point d'entrée

4.1 Vérifications avant lecture calculé

Le mode décide s'il faut recaler et sur quel tableau : Butterfly pour le palais, Bottom_MGL pour la ligne mucogingivale. Un recalage sans référence est refusé avant la lecture du moindre fichier, et la référence est lue une seule fois pour tout le lot. Un dossier est parcouru récursivement et trié, de sorte que deux exécutions nomment leurs sorties de la même façon.

Dans le codeLe refus, le parcours du dossier et les extensions

4.2 Lecture, et inversion des coordonnées calculé

Le fichier est lu selon son extension et un maillage vide est refusé en le nommant. Toute la géométrie a été écrite en RAS alors que les fichiers Slicer sont en LPS, donc la surface est d'abord reflétée en x et en y (un demi-tour autour de l'axe vertical). La même opération la remet dans son état d'origine avant son écriture. La matrice trouvée plus tard est convertie de la même façon, voir 4.6.

Dans le codeLe lecteur, la mise à l'échelle par (-1, -1, 1) et la vérification du maillage vide

4.3 Le patch palatin (« papillon ») calculé

Construit seulement quand le mode contient Patch et que le patch est le palais. L'arcade est d'abord orientée de façon canonique, à partir des centroïdes de quatre dents fixes (3, 5, 12, 14, soit UR6, UR4, UL4, UL6 ; les numéros de dents suivent le système Universal, de 1 à 16 le long de l'arcade supérieure à partir de la troisième molaire droite, de 17 à 32 le long de l'arcade inférieure à partir de la troisième molaire gauche) : le plan occlusal se trouve près de z = 0, +y pointe vers l'avant et +x vers la gauche du patient. Cette copie orientée ne sert qu'à dessiner le patch (le patch est réécrit dans la surface d'origine) ; ce n'est pas le repère RAS utilisé pour le recalage. Les quatre dents qui pilotent les coins sont ensuite moyennées en centroïdes ; par défaut ce sont les dents 6, 11, 3 et 14, et une dent manquante est une erreur d'entrée qui la nomme.

Le tableau du patch est écrit dans la surface d'origine, non dans la copie orientée.

Dans le codeLes six étapes avec leurs constantes, la protection et les numéros de ligne

4.4 Fusion des tableaux de patch calculé

Quand plusieurs patchs numérotés existent sur un maillage (Butterfly1, Butterfly2, etc.), ils sont combinés par un OU logique en un seul tableau Butterfly. Cela ne s'exécute que juste après la construction d'un patch dans la même exécution.

Dans le codeLa fonction de fusion et le moment où elle est appelée

4.5 Recalage sur le patch calculé

La surface mobile doit porter le tableau du patch, sinon elle est refusée. L'ICP ne garde, dans les deux arcades, que les points où le tableau vaut 1, et recale ceux-là ; la matrice qu'il trouve est ensuite appliquée à tout le maillage mobile, dents comprises. Les surfaces que vous donnez sont les mobiles et la référence est la fixe.

Dans le codeL'appel, les réglages VTK et le refus quand le tableau est absent

4.6 Transformation et écriture calculé

La surface est remise dans son état d'origine et écrite comme un fichier VTK legacy binaire, quelle que soit l'extension d'entrée ; la sortie reproduit l'arborescence du dossier d'entrée sous le dossier de sortie, avec le suffixe. L'entrée n'est jamais modifiée. Une surface qui lève une erreur d'entrée est consignée comme échouée et l'exécution continue.

Dans le codeLa construction de la matrice, l'écriture et les noms de sortie

4.7 Le rapport calculé

FlexReg_report.json liste, par surface, le patch utilisé, le tableau sur lequel on a recalé, les fichiers de transformation et de sortie et un statut, et se termine par un récapitulatif des totaux. Il est écrit avant le refus final « none of the surfaces could be processed », de sorte qu'une exécution où rien n'a marché laisse tout de même ses raisons.

Dans le codeLa structure du rapport et les messages de progression

5. Ce que vous pouvez choisir

  • Les surfaces : une arcade étiquetée ou un dossier ; un fichier de test hébergé est proposé.
  • Le mode : Patch, Register, ou Patch and register (par défaut).
  • Le patch : palais (papillon) ou ligne mucogingivale ; la seconde ne peut être recalée que si le tableau existe déjà.
  • La référence, sur laquelle recaler ; elle doit déjà porter son patch.
  • Quatre joysticks, un par coin : le ratio (0 à 1, du milieu vers la dent) et l'ajustement (-5 à 5 mm le long de l'arcade), et un cinquième joystick qui décale tout le patch de 15 mm au plus.
  • Le suffixe des noms de sortie (_Reg par défaut). Les quatre numéros de dents existent mais sont cachés.

7. Environnement

L'outil a son propre environnement Python avec torch (pour le remplissage seulement), vtk, numpy et SimpleITK. Le serveur suppose le GPU pour tous les modes, recalage simple compris. Rien n'est installé dans Slicer ; la bibliothèque d'aperçu n'a besoin que de vtk et de numpy.

Dans le codeLes versions épinglées, les fichiers de test hébergés et les limites

8. Ce qui a changé par rapport à la logique du legacy

La géométrie du patch et du recalage est le même code. Ce qui a changé, c'est l'enrobage.

  • Une dent manquante est désormais une erreur qui fait échouer cette surface ; le legacy la journalisait, écrivait le maillage sans patch, et paraissait réussir.
  • Entrées : .vtk, .vtp et .stl sont lus directement.
  • Les sorties vont dans un dossier séparé avec un suffixe ; le legacy réécrivait le fichier d'entrée dans les modes Patch.
  • La fusion des patchs numérotés s'exécute sur le CPU et seulement après la construction d'un patch.
  • Absents : le patch dessiné à main levée, la suppression de patch, le calcul du patch mucogingival, la segmentation des couronnes et le déplacement de la seconde arcade avec la première.
  • Les paramètres sont des joysticks bornés, vérifiés par le serveur ; le legacy prenait des nombres saisis.

9. Problèmes connus dans VISOR

  • « Patch and register » ne pose un patch que sur la surface mobile, donc la référence doit déjà porter le sien (détails).
  • Seules les erreurs d'entrée sont signalées par surface ; toute autre exception arrête tout le lot et ne laisse aucun rapport (détails).
  • La ligne mucogingivale ne peut être produite par rien dans VISOR (détails).
  • Sans tableau d'étiquettes de dents, un mauvais tableau peut être choisi silencieusement (détails).
  • Les quatre dents d'orientation sont fixes, donc une arcade à laquelle il manque l'une d'elles échoue même si les quatre dents choisies existent (détails).
  • Une entrée .stl ou .vtp donne un fichier portant cette extension mais un contenu VTK (détails).
  • La vraie construction du patch n'a aucun test (détails).
