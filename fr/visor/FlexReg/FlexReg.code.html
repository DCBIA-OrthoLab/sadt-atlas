FlexReg sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR de FlexReg dans le code, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. Le module legacy a sa propre page de code.

VISOR Code Atlas (explication) Page legacy Guide (VISOR)

VISOR scinde FlexReg en deux. Le serveur construit le patch palatin et recale une arcade sur une autre ; le panneau Slicer ne fait qu'un aperçu du contour du patch pendant que vous déplacez ses coins. Cette page suit le portage de la requête jusqu'aux fichiers qui reviennent : qui l'appelle, quels fichiers le portent, chaque étape du pipeline serveur avec le code qui l'exécute, les arguments publiés, l'environnement, ce qui a changé par rapport au module legacy, et ce que la revue de code a trouvé. Tout ce qui figure ici a été lu dans le code aux commits ci-dessous, et non observé sur un serveur en marche (aucun environnement FlexReg n'était disponible pour lancer les tests), et rien ici n'affirme qu'un serveur donné soit déployé.

Les références nomment d'abord le dépôt : SADT-VISOR (code des outils, tool/vface @ 6ba2a78), VISOR-serve (serveur, @ e9a7e5d), AutomatedDentalToolsRemote (client Slicer, @ 19b95e8) et legacy (SlicerAutomatedDentalTools @ 3c67957). Un nom de fichier seul tel que __init__.py, pipeline.py, layout.py, make_butterfly.py, orientation.py, propagation.py, ICP.py, vtkSegTeeth.py ou util.py se trouve dans le paquet SADT-VISOR tools/FlexReg/src/sadt_flexreg/ ; FlexRegRemote.py et FlexRegLib/ se trouvent dans le dossier client FlexRegRemote/. Dans la colonne « Legacy », FlexReg_CLI.py et FlexReg.py sont le CLI et le widget legacy, et les autres noms sont sous FlexReg_CLI/FlexReg_Method/ ou FlexReg/FlexReg_utils/. Les chemins serveur tels que server/config.py se trouvent dans VISOR-serve.

1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

FlexReg n'appelle aucun autre outil et aucun outil ne l'appelle. run() ne prend aucun argument superviseur (SADT-VISOR __init__.py:49-78), et le serveur ne transmet un superviseur qu'à un outil qui déclare *, sup (VISOR-serve server/execution/runner.py:6-9). La conséquence est la principale différence avec la chaîne legacy : le widget legacy lançait dentalmodelseg quand l'arcade n'avait pas d'étiquettes de dents, et ALI_IOS pour l'arcade inférieure. Dans VISOR, l'arcade doit arriver déjà étiquetée (un tableau Universal_ID par point), par exemple à la suite d'une exécution de Crown_Seg, et plus rien ne calcule le patch mucogingival.

3. Ce qui s'exécute où

Explication en langage courant et maths : page de l'atlas.

ServeurClient (Slicer)
Lecture des surfaces (RAS), construction du patch palatin (orientation, quatre centroïdes de dents, contour, remplissage géodésique), fusion des tableaux de patch, ICP rigide sur le patch, écriture de la surface recalée, du .tfm et du rapport (SADT-VISOR __init__.py:49-202)L'aperçu du patch : pendant qu'on fait glisser un joystick, le contour du patch est recalculé dans Slicer et dessiné dans la scène, sans aller-retour (FlexRegRemote.py:156-193)
La seule étape GPU : le remplissage géodésique du patch (propagation.py:31, 60, 66-68)Le formulaire, généré à partir du schéma du serveur : les arguments vec2 deviennent des joysticks (FlexRegRemote.py:21-24, 71)
Le vrai patch, celui que le recalage utilise réellement, calculé une seule fois à ApplyLa bibliothèque d'aperçu FlexRegLib, qui a besoin de vtk et de numpy et d'aucun GPU (FlexRegRemote/CMakeLists.txt:6-23)

L'aperçu ne dessine que le contour (with_fill=False, FlexRegRemote.py:182-187) : le remplissage du patch est fait par le serveur, par propagation géodésique à partir du point central. La bibliothèque client peut aussi remplir approximativement avec un test point dans polygone, ce qu'elle ne fait pas dans le panneau (FlexRegLib/butterfly_preview.py:285-306). L'aperçu est activé par défaut (« Preview the patch while I drag », FlexRegRemote.py:105-114) et ne fonctionne que si le champ surfaces pointe vers une surface déjà présente dans la scène Slicer : avec un dossier (lot), il n'y a pas d'aperçu (FlexRegRemote.py:220-231). L'orientation et les centroïdes sont mis en cache par surface et par jeu de dents (prepare), et seul le contour est recalculé à chaque déplacement de pastille (FlexRegRemote.py:166-187). Le nœud de contour est exclu de la scène enregistrée (SetSaveWithScene(False), FlexRegRemote.py:244).

L'aperçu rejoue le contour du serveur avec les mêmes constantes : la cible d'orientation et les dents (FlexRegLib/butterfly_preview.py:28-29), le rayon 0.7 (:30), l'inversion de signe de l'ajustement postérieur (:35-40) et les courbes de Bézier en miroir (:54-66), face à make_butterfly.py:77, 82-83, 110-111, 136-148 sur le serveur. Les quatre numéros de dents cachés existent toujours comme widgets dans le client (les lignes cachées sont construites, non affichées : ServerToolsCoreLib/formgen.py:2272-2278, 2366-2420), si bien que l'aperçu lit leurs valeurs par défaut ; étant cachés, ils ne sont pas envoyés, et le serveur applique les mêmes valeurs par défaut.

4. Le pipeline, pas à pas

Explication en langage courant et maths : page de l'atlas.

Un appel de run() traite une surface ou un dossier de surfaces. Les étapes ci-dessous sont celles de SADT-VISOR __init__.py:108-202, dans l'ordre.

4.1 Vérifications avant lecture calculé

Explication en langage courant et maths : page de l'atlas.

Le mode décide de deux indicateurs : registering pour Register et Patch and register, et le tableau sur lequel recaler, Butterfly pour le palais ou Bottom_MGL pour la ligne mucogingivale (__init__.py:111-112 ; noms à pipeline.py:26-27). Un recalage sans référence est refusé avant la lecture du moindre fichier, et la référence est lue une seule fois pour tout le lot (__init__.py:117-121) :

if registering and not str(reference):
    raise ToolInputError(
        "'{}' registers onto a reference surface: name one in 'reference'.".format(mode)
    )
target = read_surface(str(reference)) if registering else None

surfaces_in prend un fichier tel quel, ou parcourt un dossier récursivement et garde les .vtk, .vtp, .stl, triés pour que deux exécutions sur le même dossier nomment leurs sorties de la même façon (pipeline.py:98-120). Un chemin manquant ou un dossier sans surface est une erreur d'entrée.

4.2 Lecture, et inversion des coordonnées calculé

Explication en langage courant et maths : page de l'atlas.

read_surface choisit le lecteur selon l'extension (vtkXMLPolyDataReader, vtkSTLReader, vtkPolyDataReader), refuse toute autre extension et un maillage vide, en le nommant, puis met à l'échelle (-1, -1, 1) (pipeline.py:50-78). Cette inversion fait passer le fichier LPS dans le repère RAS dans lequel le cœur géométrique a été écrit ; elle est sa propre inverse, donc la même fonction rétablit l'état d'origine à l'écriture (pipeline.py:34-47, 93). Tout le calcul ci-dessous se fait en RAS.

4.3 Le patch palatin (« papillon ») calculé

Explication en langage courant et maths : page de l'atlas.

Construit seulement quand le mode contient Patch et que le patch est le palais (__init__.py:155-158), par build_butterfly, qui appelle le butterflyPatch legacy avec l'indice 1 et transforme une dent manquante en erreur d'entrée qui la nomme (pipeline.py:123-162). Dans make_butterfly.py, purement géométrique à part le remplissage :

  1. Orientation. La surface est copiée puis orientée de sorte que les centroïdes des dents 3, 5, 12, 14 (UR6, UR4, UL4, UL6) tombent sur [[-0.5,-0.5,0],[0,0,0],[0.5,-0.5,0]] (make_butterfly.py:82-83 ; orientation.py:42-115) : plan occlusal près de z = 0, +y vers l'avant. Ces quatre dents sont fixes, quelles que soient les dents qui pilotent les coins.
  2. Centroïdes. vtkMeanTeeth fait la moyenne des sommets des quatre dents choisies dans Universal_ID (make_butterfly.py:79, 84). Le shift du patch entier et l'ajustement de chaque coin sont ajoutés ; l'ajustement est inversé sur les coins postérieurs de sorte qu'une valeur positive allonge le patch aux deux extrémités (make_butterfly.py:106-111).
  3. Coins. Chaque coin est une combinaison affine de son propre centroïde et du centroïde opposé (make_butterfly.py:94-97, 113-117) : 
    ratio_anterior_right = (1 - ratio_anterior_right)/2
...
landmark_anterior_right = (1 - ratio_anterior_right) * c_ar + ratio_anterior_right * c_al
    un ratio de 1 place le coin sur sa dent, un ratio de 0 à mi-chemin à travers l'arcade. Comme les poids ont pour somme 1, le décalage ajouté aux quatre centroïdes ressort de l'interpolation inchangé : le patch se déplace de façon rigide.
  4. Contour. Un segment antérieur et un segment postérieur (pas de 0.01) et deux courbes de Bézier quadratiques passant par (coin postérieur, milieu postérieur, coin antérieur), réfléchies par rapport à leur corde pour qu'elles bombent vers l'extérieur (make_butterfly.py:123-151).
  5. Marquage. Tout sommet situé à moins de radius = 0.7 du contour, mesuré sur V[:, :2] (la projection sur le plan occlusal), est mis à 1 (make_butterfly.py:77, 127-157).
  6. Remplissage. Dilation inonde le maillage de voisin en voisin à partir du sommet le plus proche du milieu des quatre coins, en s'arrêtant au contour marqué, par lots de 1000 sur CUDA (make_butterfly.py:159-161 ; propagation.py:65-98). Le tableau Butterfly1 est ajouté à la surface d'origine, non à la copie orientée (make_butterfly.py:165-170).

4.4 Fusion des tableaux de patch calculé

Explication en langage courant et maths : page de l'atlas.

merge_patches combine par OU Butterfly1, Butterfly2, ... en un seul tableau Butterfly (int32) en numpy, et ne fait rien quand il n'y a pas de Butterfly1 (pipeline.py:165-188). Il ne s'exécute que juste après la construction d'un patch dans cette exécution (__init__.py:157). Un maillage qui porte déjà plusieurs patchs numérotés issus du module legacy ne se recale sur leur union que si un patch est de nouveau construit ici.

4.5 Recalage sur le patch calculé

Explication en langage courant et maths : page de l'atlas.

register refuse une surface mobile sans le tableau du patch, puis lance l'ICP legacy restreint au patch (pipeline.py:203-210) :

if not source.GetPointData().HasArray(patch_array):
    raise ToolInputError(...)
option = vtkMeshTeeth(list_teeth=[1], property=patch_array)
result = ICP([vtkICP()], option=option).run(source, target)

vtkMeshTeeth ne garde, dans les deux maillages, que les points dont le tableau vaut 1, sous forme de nuage de points (ICP.py:70-72). vtkICP est un simple vtkIterativeClosestPointTransform (ICP.py:94-113) :

icp.GetLandmarkTransform().SetModeToRigidBody()
icp.SetMaximumNumberOfIterations(1000)
icp.StartByMatchingCentroidsOn()

La matrice 4×4 obtenue (RAS) est ensuite appliquée à tout le maillage mobile, dents comprises (pipeline.py:211-224). Les surfaces sont les maillages mobiles, la reference le maillage fixe. Voir ICP dans le glossaire.

4.6 Transformation et écriture calculé

Explication en langage courant et maths : page de l'atlas.

Le .tfm convertit la matrice RAS en LPS par conjugaison et l'inverse, parce qu'une transformation Slicer applique l'espace plutôt que les points (pipeline.py:227-246) :

flip = np.diag([-1, -1, 1, 1])
composed = np.linalg.inv(flip @ matrix @ flip)
transform = sitk.AffineTransform(3)
transform.SetMatrix(composed[:3, :3].flatten())
transform.SetTranslation(composed[:3, 3])

La surface est remise dans sa convention d'entrée et écrite avec vtkPolyDataWriter en binaire, quelle que soit l'extension d'entrée (pipeline.py:81-95). Le chemin de sortie reproduit l'arborescence d'entrée sous output_dir : <relative path without extension><suffix><input extension>, et la transformation <same stem><suffix>.tfm (__init__.py:150, 160-171). L'entrée n'est jamais modifiée. Une surface qui lève une erreur d'entrée est consignée comme échouée et la boucle continue (__init__.py:177-181).

4.7 Le rapport calculé

Explication en langage courant et maths : page de l'atlas.

FlexReg_report.json, à la racine de output_dir (__init__.py:139, 168-199) :

{"mode": ..., "patch": ...,
 "surfaces": {"<relative path>": {"patch": "Butterfly", "registered_on": "Butterfly",
                                   "transform": "<path>", "status": "ok", "output": "<path>"}
              | {"status": "failed", "error": "..."}},
 "summary": {"total": n, "processed": k, "failed": m}}

Il est écrit avant le refus final « None of the N surface(s) could be processed », de sorte qu'une exécution où rien n'a marché laisse tout de même ses raisons (__init__.py:188-200). La progression est signalée sous la forme « surface i sur n », jamais avec un nom de fichier (__init__.py:144-146).

9. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

« Patch and register » ne pose un patch que sur la surface mobile, pas sur la référence

Le patch est construit sur surfaces seulement (SADT-VISOR __init__.py:155-157) ; la référence est lue une fois et utilisée telle quelle (__init__.py:121). L'ICP sélectionne les points du tableau du patch dans les deux maillages (ICP.py:70-72 ; pipeline.py:209-210). Une référence sans le tableau Butterfly échoue avec NoSegmentationSurf (vtkSegTeeth.py:59-61), et un tableau entièrement nul avec ToothNoExist (vtkSegTeeth.py:75) ; ni l'une ni l'autre n'est une erreur d'entrée, ce qui compte pour un lot : voir le constat suivant. En pratique, la référence doit déjà porter son patch, par exemple à la suite d'une exécution antérieure en mode Patch sur elle. La docstring de reference ne le dit pas (__init__.py:89-90), alors que le widget legacy le disait (« Create the patch on T1 and T2 before registration », legacy FlexReg.py:1116-1118).

Seules les erreurs d'entrée sont signalées par surface ; toute autre exception arrête tout le lot

La boucle n'intercepte que ToolInputError (SADT-VISOR __init__.py:177), et le rapport est écrit après la boucle (__init__.py:191). Toute autre exception, comme les deux levées par une référence sans son patch, un numéro de dent hors de 1 à 32 (util.py:143-151) ou l'absence de GPU dans Dilation (propagation.py:31), met fin à l'exécution pour toutes les surfaces restantes et ne laisse aucun rapport. Cela est lu dans le code ; ce n'a pas été exécuté.

La « ligne mucogingivale » ne peut être produite par rien dans VISOR

Le tableau Bottom_MGL (SADT-VISOR pipeline.py:27) n'est créé par aucun fichier de l'outil ni du client Slicer ; le legacy le construisait dans le widget (legacy FlexReg_utils/mgl_patch.py:117). Le panneau propose encore ce choix (__init__.py:53 ; layout.py:95). Register avec lui échoue par surface si le maillage n'a pas le tableau (pipeline.py:203-207). Et le mode Patch avec la ligne mucogingivale ne construit rien : la construction est protégée par patch == "Palate (butterfly)" (__init__.py:155-157), donc la surface est copiée et déclarée ok.

Sans Universal_ID, le dernier tableau est utilisé

Quand un maillage n'a pas de tableau Universal_ID, la recherche des étiquettes de dents se rabat sur GetLabelSurface, dont la boucle utilise continue là où il faudrait break et renvoie le dernier tableau de données de points (SADT-VISOR sadt_flexreg/util.py:25-28, 32-44). Le legacy l'a corrigé dans ADTLib (legacy FlexReg_CLI/FlexReg_Method/util.py:24-30). L'aperçu Slicer prend à la place le premier tableau à une seule composante (FlexRegLib/butterfly_preview.py:136-152), alors que son commentaire dit que le serveur le choisit de la même façon : l'aperçu et le serveur peuvent utiliser des tableaux différents sur la même arcade.

Les quatre dents d'orientation sont fixes

L'arcade est orientée sur les dents 3, 5, 12 et 14, quelles que soient les dents choisies pour les coins (SADT-VISOR make_butterfly.py:82-83) ; le client utilise les mêmes constantes (AutomatedDentalToolsRemote FlexRegRemote/FlexRegLib/butterfly_preview.py:29). Une arcade à laquelle il manque l'une d'elles échoue même si les quatre dents choisies existent. Les quatre arguments tooth_* sont cachés dans le panneau (layout.py:101-104).

Les bornes des joysticks sont imposées par le serveur

Ratio dans [0, 1], ajustement dans [-5, 5] mm, translation dans [-15, 15] mm (SADT-VISOR layout.py:24-28, 57-59, 81-83) ; une valeur hors plage est refusée (VISOR-serve server/base.py:759-768). Le commentaire de layout.py:22-23 dit encore qu'un nombre plus grand saisi dans la case « still works » : ce n'est plus vrai.

Les noms de sortie peuvent mentir sur le format

La sortie garde l'extension d'entrée (SADT-VISOR __init__.py:163) mais est toujours écrite comme un fichier VTK legacy binaire (pipeline.py:90-94), donc une entrée .stl ou .vtp donne un fichier portant cette extension et un contenu VTK. Lu dans le code ; ce que Slicer fait d'un tel fichier n'a pas été vérifié. Le legacy écrivait toujours .vtk (legacy FlexReg_CLI.py:321).

Chemins serveur absolus dans le rapport ; GPU supposé pour tous les modes

Le rapport stocke le chemin serveur absolu de la sortie et de la transformation (SADT-VISOR __init__.py:170, 175), alors que les messages de progression évitent volontairement les noms de fichiers (__init__.py:144-146). Et comme l'outil ne déclare aucun device, le serveur met en file même Register pour le GPU (VISOR-serve server/execution/dispatch.py:95-116).

Les documents de l'outil décrivent mal l'inversion legacy

La docstring de pipeline.py (SADT-VISOR pipeline.py:8-14), le README (tools/FlexReg/README.md:32-36) et la docstring de test_a_surface_leaves_in_the_convention_it_arrived_in (tests/test_run.py:62-65) disent que le CLI legacy inversait vers RAS à la lecture et ne revenait jamais en arrière. À 3c67957, il revient bien en arrière avant l'écriture (legacy FlexReg_CLI.py:295-305). Le code VISOR est juste ; seule la différence annoncée ne tient pas pour ce commit. De même, la docstring du module dit que curve et delete « stay in the Slicer module » (__init__.py:19) : FlexRegRemote.py n'a ni l'un ni l'autre.

La vraie construction du patch n'a aucun test

Le marqueur gpu est déclaré (SADT-VISOR tools/FlexReg/pyproject.toml:32-34) mais aucun test ne l'utilise, et le test d'une dent manquante remplace butterflyPatch par un faux (tests/test_run.py:336-349). Les chiffres du README de l'outil (patch sur une arcade de 294,260 points) n'ont aucun test derrière eux dans le dépôt.
