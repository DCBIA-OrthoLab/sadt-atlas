CNE sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR de CNE dans le code, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le code legacy et les constatations. L'explication lisible du même pipeline, avec les petits calculs qu'il contient, est sur la page de l'atlas.

Les références de cette page nomment un dépôt, puis un chemin à l'intérieur, puis une ligne : SADT-VISOR est le catalogue d'outils (commit 6ba2a78), VISOR-serve le serveur (e9a7e5d), Remote le client Slicer (AutomatedDentalToolsRemote 19b95e8), legacy SlicerAutomatedDentalTools à 3c67957. Un chemin nu comme readers.py:41 se trouve dans SADT-VISOR tools/CNE/src/sadt_cne/. Tout a été lu dans le code ; rien sur cette page n'a été exécuté, sauf les vérifications de statut HTTP datées plus bas. Vue d'ensemble de la pile : VISOR.

3. Le pipeline

Explication en langage courant et maths : page de l'atlas.

3.1 Vérifier les dossiers et trouver les notes

Explication en langage courant et maths : page de l'atlas.

Un chemin notes manquant est une FileNotFoundError (__init__.py:97-100). Si notes est un dossier et que output_dir est le même dossier (liens symboliques résolus), l'exécution est refusée, parce que les extractions seraient relues comme des notes par l'exécution suivante (:106-110,320-324). L'outil crée ensuite lui-même output_dir (:116) ; le legacy comptait sur le panneau pour le créer.

La découverte est récursive et renvoie les fichiers triés par chemin relatif (readers.py:92-123). Elle garde .txt, .pdf et .docx sans tenir compte de la casse (:33,78-81), ignore les noms commençant par ~$ (fichiers de verrouillage Word) ou par un point, et les dossiers nommés __MACOSX (:60-61,84-90,117-118). Le dossier de sortie est exclu quand il se trouve dans l'entrée (__init__.py:118). Ne rien trouver est une erreur 422 qui nomme les trois extensions (:119-126) ; le legacy sortait avec le statut 0 dans ce cas (legacy CNE_CLI/CNE_CLI.py:137-141).

3.2 Choisir et charger le modèle

Explication en langage courant et maths : page de l'atlas.

model est obligatoire. Un fichier .gguf est utilisé tel quel ; un dossier doit contenir exactement un .gguf, cherché récursivement, sinon l'exécution est refusée avec les candidats nommés (extraction.py:89-128). Si le chemin du modèle nomme un type de note et que notes_type est l'autre, un avertissement va dans le rapport ; ce n'est pas un refus (model_type_hint, extraction.py:131-143 ; __init__.py:132-142).

CONTEXT_TOKENS = {"TMJ": 6144, "Ortho": 2048}                # extraction.py:49
SYSTEM_PROMPTS = {"TMJ": INSTRUCTION_TMJ, "Ortho": None}      # extraction.py:51

window = context_for(notes_type, context_tokens)              # 0 means the type's default
offloading = wants_gpu and supports_gpu_offload()             # asked before the 4.4 GB load
engine = load_model(model_file, window, seed, -1 if wants_gpu else 0)   # __init__.py:144-165

load_model construit un seul llama_cpp.Llama(model_path, n_ctx, n_gpu_layers, seed, verbose=False) pour tout le lot (extraction.py:193-203). Son bavardage de chargement est capturé avec contextlib.redirect_stderr et journalisé au niveau debug (:63-86), là où le legacy redirigeait le descripteur de fichier 2 du processus avec os.dup2 et sans finally (legacy CNE_CLI.py:157-171). Chaque import de llama_cpp passe par engine_module(), qui essaie d'abord d'ouvrir le runtime CUDA du venv (extraction.py:167-177, dependencies.py:65) ; sur le build CPU, c'est sans effet. Une requête device = "cuda" sur un build sans prise en charge GPU ajoute un avertissement et gpu_offload: false au rapport (__init__.py:145-165,184).

3.4 Interroger le modèle

Explication en langage courant et maths : page de l'atlas.

messages = []

    messages.append({"role": "system", "content": INSTRUCTION_TMJ})

L'instruction TMJ est la chaîne du legacy telle quelle : "Using the following note, extract structured key-value pairs about the patient's symptoms and diagnoses:" (extraction.py:41-44). Ortho ne reçoit aucun message système, comme dans le legacy. L'outil ne compare pas la longueur de la note à la fenêtre : context_for ne rejette qu'une valeur négative (extraction.py:146-153), et toute erreur levée par llama.cpp est attrapée pour cette note (__init__.py:200-212). Dans llama-cpp-python 0.3.36 (llama.py:1343-1358), le moteur ne lève une erreur que lorsque le prompt seul atteint n_ctx ; sinon max_tokens est ramené à n_ctx moins la longueur du prompt, la note n'est jamais tronquée, et une génération arrêtée par cette limite raccourcie signale finish_reason == "length", ce qui fait échouer la note (__init__.py:293-297). La version figée est 0.3.35, dont le code n'a pas été lu.

3.5 Lire la réponse et l'écrire

Explication en langage courant et maths : page de l'atlas.

  1. JSON d'abord : la portion allant du premier { au dernier } est analysée ; un dict sous "extraction" est déballé ; un résultat vide ou une valeur JSON qui n'est pas un objet est refusé (extraction.py:261-275). Le découpage est celui du legacy.
  2. Puis des lignes key: value : une clé commence par une lettre minuscule et contient des minuscules, des chiffres, des espaces et des tirets bas (jusqu'à 61 caractères, les espaces deviennent _, extraction.py:230,296), au moins 60 % des lignes non vides doivent correspondre, et une clé répétée garde sa première valeur (extraction.py:230-235,278-301). Le source dit que le fine-tune TMJ publié répond sous cette forme, 46 champs et pas de JSON (:244-245).
  3. Sinon rien n'est écrit et la note échoue (__init__.py:299-305). Le legacy écrivait la réponse brute.

Deux fichiers sont écrits par note dans l'arborescence recopiée (__init__.py:240-266,307-317) : le JSON, canonique, et un texte key : value où une liste est jointe par des virgules et un dict imbriqué reste du JSON (extraction.py:304-328).

input   notes/P01/B_001.txt
output  output_dir/P01/Extraction_B_001.txt.json
        output_dir/P01/Extraction_B_001.txt.txt

plan_outputs vérifie qu'aucune paire de notes ne correspond à la même paire de sorties avant que quoi que ce soit s'exécute (__init__.py:240-266). CNE_report.json porte tool, notes_type, model, system_prompt (un indicateur), context_tokens, max_tokens, temperature, seed, device, gpu_offload, warnings, et par note input, le lecteur et l'encodage, characters, finish_reason, answer_characters, status, fields, les deux chemins de sortie ou un reason ; puis summary et duration_seconds (__init__.py:171-187,213-216,272-317). Le texte de la réponse lui-même n'est mis ni dans le rapport ni dans les journaux.

3.6 Échecs

Explication en langage courant et maths : page de l'atlas.

Chaque note est dans son propre try : un échec est journalisé avec le chemin relatif de la note et consigné dans le rapport, et la boucle continue (__init__.py:191-213). Si aucune note n'a été écrite, l'exécution lève une erreur : un 503 (ToolUnavailableError) quand chaque échec était un lecteur manquant, sinon un 422 (ValueError) qui liste la raison de chaque note (:218-232) ; le rapport n'est alors pas écrit. Notez que cette ligne de journal par note nomme le fichier, contrairement aux messages de progression de CLIC.

8. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Le texte des notes est envoyé au serveur

L'affirmation du legacy selon laquelle CNE garde le texte clinique sur la machine ("no network exfiltration", page legacy §11, et le « Nothing leaves your machine » du Guide legacy) ne tient pas pour VISOR. Le panneau VISOR envoie les notes que vous sélectionnez vers un serveur d'outils où tourne le modèle (Remote README.md:24-35 ; CNERemote/CNERemote.py:57 et l'argument notes côté serveur, Arguments et schéma). Le README de Remote dit en toutes lettres qu'il n'y a pas de désidentification dans le client actuel (README.md:32), et la page de sécurité de VISOR ne donne la désidentification des fichiers envoyés que comme spécifiée (Désidentification, Transport). Ce que fait l'outil lui-même du texte : il exécute llama.cpp en processus et ne contient aucun appel réseau (un grep de urllib, requests, http et socket dans tools/CNE/src/sadt_cne/ n'en trouve aucun), et le serveur écrit la réponse dans le dossier du job. La constatation du legacy reste vraie pour le module legacy seul.

Le client dit "automatic", mais rien n'associe le modèle au type de note

Le README de Remote ("leave Model on automatic and the server uses the model fine-tuned for that note type", README.md:611-613) et la docstring de CNERemote/CNERemote.py:15-18 ("the model field defaults to (automatic)") sont périmés. model est un argument obligatoire de l'outil (__init__.py:49), et le client n'ajoute son entrée "(automatic)" qu'aux arguments facultatifs (Remote ServerToolsCore/ServerToolsCoreLib/base_widget.py:1074-1076, justification en formgen.py:107-109) : le champ Model liste les bundles hébergés et envoie celui qui est sélectionné. Rien ne déduit le modèle de notes_type (resolve_model_file prend un chemin, extraction.py:89-128) ; un décalage entre les deux n'est qu'un avertissement (encadré suivant). Lu dans le code, non exécuté dans Slicer.

Seul le modèle TMJ est hébergé

Le manifeste de données dépose un seul bundle, TMJ/qwen-ft-q4_k_m.gguf (VISOR-serve scripts/data-manifest.yml:687-692). notes_type = "Ortho" est accepté par l'outil mais aucun modèle Ortho n'est hébergé, et un modèle dont le chemin nomme l'autre type n'est qu'un avertissement dans le rapport, pas un refus (__init__.py:133-139, extraction.py:131-144). Le commentaire du manifeste selon lequel le dépôt Ortho "answers 404 today" (data-manifest.yml:682-686, répété dans SADT-VISOR tools/CNE/README.md:205-208) est périmé : le 2026-11-09, une requête HTTP HEAD sur l'ancienne URL Ortho dcbia/ a répondu 307 (une redirection vers l'organisation DCBIA-OrthoLab/), et une sur DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho/.../model-q4_k_m.gguf a répondu 302 vers un téléchargement (codes de statut seulement, rien n'a été téléchargé). L'URL TMJ du manifeste utilise elle aussi encore l'ancien nom dcbia/ et répond 307.

CPU, quoi que disent certains commentaires

L'index de wheels figé pour llama-cpp-python est celui du CPU (SADT-VISOR tools/CNE/pyproject.toml:60-67). Trois commentaires le contredisent : l'en-tête du même fichier parle d'un "CUDA 12.4 wheel index below" (:8-23) ; la description publiée de device dit "it needs the CUDA build of llama.cpp, which this tool pins" (__init__.py:82-84) ; et le fichier compose de VISOR-serve dit que CNE ne peut pas tourner dans le service CPU parce qu'il embarque le build CUDA (docker-compose.yml:105-110). Le code est le build CPU, donc une requête cuda est signalée comme ignorée. Le README de l'outil est d'accord avec le code (SADT-VISOR tools/CNE/README.md:154-165). Ne lisez nulle part « CNE a besoin d'un GPU ».

Aucune garde sur la longueur d'une note

La préoccupation du legacy sur les notes longues (page legacy, §11) n'est qu'à moitié close. Une réponse coupée est désormais refusée (__init__.py:293-297) et max_tokens vaut 2048 par défaut au lieu de 500. Mais rien ne compare la note à la fenêtre de contexte ni ne vérifie que max_tokens y laisse de la place : context_for ne rejette qu'une valeur négative (extraction.py:146-153). Avec la valeur par défaut d'Ortho, la limite de réponse seule égale la fenêtre (2048 et 2048, :49, __init__.py:51). Dans llama-cpp-python 0.3.36 (llama.py:1343-1358), le moteur ne lève une erreur que lorsque le prompt seul atteint n_ctx ; sinon il raccourcit max_tokens à n_ctx moins le prompt et la note n'est jamais coupée. Donc avec Ortho une note passe tant que la réponse se termine dans ce que la note laisse, et échoue (finish_reason == "length") quand ce n'est pas le cas ; tout ce que lève le moteur fait échouer cette seule note (__init__.py:200-212).

Les noms de sortie ont changé

Les fichiers sont Extraction_<note file name>.json et .txt, pas Extraction_<stem>.txt (__init__.py:240-266). Tout ce qui lit les noms du legacy, comme le Dashboard legacy (Extraction_*.txt), ne retrouverait pas les mêmes fichiers.

Vérifié : les échecs silencieux du legacy sont fermés

Un PDF fait d'images seulement, une réponse tronquée et une réponse qui n'est ni du JSON ni des champs font désormais échouer la note au lieu d'écrire un fichier plausible (__init__.py:276-305) ; les notes homonymes de formats différents ne s'écrasent plus (:240-266) ; la scission d'orthographe TMJ/tmj a disparu (extraction.py:49-51) ; une demande de GPU qui ne peut pas être satisfaite est signalée (__init__.py:145-165). Lu dans le code.
