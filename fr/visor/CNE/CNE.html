CNE sur VISOR

CNE lit des notes cliniques en texte libre et consigne les faits qu'il y trouve (symptômes, diagnostics, scores) sous la forme de lignes champ : valeur. Un modèle de langage fait la lecture ; tout ce qui l'entoure décide de ce que le modèle voit et de celles de ses réponses qui sont gardées. Dans VISOR, le modèle tourne sur un serveur, donc les notes sont envoyées, ce que le module legacy ne faisait jamais. Cette page explique les étapes et les quelques calculs qu'elles contiennent ; les détails dont un développeur a besoin sont sur la page de code, et le module legacy a sa propre page.

Le modèle seul décide quels champs existent et quelles sont leurs valeurs. Rien ne vérifie une extraction par rapport à la note dont elle vient ; l'outil contrôle seulement ce que le modèle voit et quelles réponses sont écrites.

1. Où il s'exécute

Slicer ne garde qu'un petit panneau (CNERemote). Il envoie les notes à un serveur, attend, puis télécharge une archive et la décompresse dans le dossier choisi. Le modèle est chargé et exécuté sur le serveur, dans un environnement propre, et rien n'est chargé dans la scène Slicer : les résultats sont du texte. CNE n'appelle aucun autre outil et aucun outil n'appelle CNE.

Comme le modèle tourne sur le serveur, le texte des notes quitte le poste de travail. Le module legacy le gardait sur la machine. Rien ne désidentifie les notes avant leur envoi (problèmes connus).

1.1 Ce qui s'exécute où

  • Serveur : publie le formulaire que montre le panneau, lit les trois formats de notes, exécute le modèle, écrit les résultats. Le modèle est chargé une fois par appel, c'est pourquoi un dossier entier de notes est envoyé en un seul appel.
  • Slicer : affiche le formulaire généré, envoie les notes, décompresse l'archive et affiche un résumé d'une ligne dans la barre d'état (combien de notes ont été extraites, avec quel type de modèle, et combien d'avertissements). Rien n'est installé ni téléchargé sur le poste de travail.
Dans le codeLe panneau, l'outil serveur, ce qui est hébergé, avec les fichiers et les lignes

2. Fichiers en jeu

L'outil tient en cinq petits fichiers sources : le point d'entrée qui exécute la boucle sur les notes, le code du modèle (prompts, chargement, analyse), les lecteurs des trois formats, un chargeur de paquets facultatifs, et la mise en page du panneau. Du module legacy, seule l'inférence a été portée ; le panneau, le téléchargement du modèle et le Dashboard ne l'ont pas été.

Dans le codeLa liste des fichiers avec le nombre de lignes, et les fichiers du serveur et du client qui concernent CNE

3. Le pipeline

Une fois par exécution, l'outil vérifie les dossiers, liste les notes, choisit le fichier de modèle et le charge. Ensuite, note par note, il lit le texte, interroge le modèle et décide si la réponse peut être gardée. Chaque boîte est un lien vers son étape.

3.1 Vérifier les dossiers et trouver les notes

L'outil vérifie d'abord que les notes existent et que les résultats ne seront pas écrits dans le dossier des notes, sinon l'exécution suivante relirait ses propres résultats comme des notes. Il liste ensuite les fichiers .txt, .pdf et .docx du dossier et de ses sous-dossiers, quelle que soit la casse de l'extension, en ignorant les fichiers de verrouillage de Word et les fichiers cachés. S'il n'en trouve aucun, l'exécution s'arrête avec une erreur qui nomme les trois extensions ; le module legacy se terminait simplement sans bruit.

Dans le codeLes vérifications de dossiers, la découverte récursive, les noms ignorés, les codes d'erreur

3.2 Choisir et charger le modèle

Le modèle est un fichier quantifié au format GGUF, exécuté par llama.cpp. Un fichier est utilisé tel quel ; un dossier doit en contenir exactement un. Chaque type de note a sa propre fenêtre de contexte, la quantité de texte (note et réponse ensemble, comptée en tokens) que le modèle peut tenir à la fois : 6144 pour TMJ, 2048 pour Ortho. Si le chemin du modèle nomme l'autre type de note, un avertissement va dans le rapport mais l'exécution continue. Le modèle est chargé une seule fois pour tout le lot, puisque charger 4.4 GB est la partie lente, et si un GPU est demandé à un build processeur seul l'exécution continue sans lui et le dit dans le rapport.

Dans le codeLa résolution du modèle, la table des fenêtres, le chargement et le build CPU

3.3 Lire une note

Un fichier texte est décodé en UTF-8, puis en Windows-1252, puis en Latin-1, selon le premier qui fonctionne. Un PDF donne sa couche de texte page par page. Un fichier Word donne ses en-têtes et pieds de page, puis son corps dans l'ordre de lecture avec les tableaux, une ligne de tableau par ligne. Ensuite chaque note passe par la même étape de nettoyage.

Un texte sans lettre ni chiffre, ce que donne un PDF numérisé, est refusé par son nom : il n'y a pas d'OCR.

Dans le codeLes trois lecteurs, la table de remplacement, la vérification du texte vide

3.4 Interroger le modèle

La note est envoyée sous forme de chat. Pour les notes TMJ, un prompt système vient en premier : “Using the following note, extract structured key-value pairs about the patient’s symptoms and diagnoses”. Les notes Ortho n'en reçoivent aucun, parce que leur modèle a été affiné pour répondre à partir de la seule note. La réponse est limitée à 2048 tokens par défaut, la température d'échantillonnage est 0 et une graine fixe est utilisée, donc la même note devrait donner la même réponse. Si le modèle s'arrête parce qu'il a atteint la limite, la réponse est incomplète et la note échoue.

Avec les valeurs par défaut d'Ortho, la limite de réponse égale toute la fenêtre (2048 et 2048), donc la réponse est limitée par ce que la note laisse : une note de 1,000 tokens laisse 1,048 à la réponse. L'outil ne compare jamais une note à la fenêtre. Quand la réponse atteint ce reste, le modèle signale une coupure et la note échoue ; quand le prompt seul remplit la fenêtre, le moteur le refuse et, là encore, seule cette note échoue.

Dans le codeLes messages, l'appel, le contrôle de coupure, et la garde de longueur manquante

3.5 Lire la réponse et l'écrire

Le modèle est censé répondre en JSON, mais rien ne l'y oblige. L'outil essaie deux lectures, dans cet ordre, et n'écrit rien si les deux échouent.

Un champ qui apparaît deux fois garde sa première valeur. Pour chaque note, deux fichiers sont écrits dans une arborescence qui reproduit celle des notes : un fichier JSON, qui est le résultat canonique, et un fichier texte de lignes champ : valeur pour la lecture, où une liste est jointe par des virgules. Pour B_001.txt, ce sont Extraction_B_001.txt.json et Extraction_B_001.txt.txt. Le rapport d'exécution liste, pour chaque note, comment elle a été lue, quelle était la longueur de la note et de la réponse, si elle a réussi, combien de champs elle a donnés, et pourquoi elle a échoué le cas échéant. Le texte de la réponse lui-même n'est mis ni dans le rapport ni dans les journaux.

Dans le codeLe code d'analyse, le planificateur de sorties, les champs du rapport

3.6 Échecs

Chaque note est traitée isolément. Un échec (texte vide, réponse coupée, réponse qui n'est ni du JSON ni des champs, erreur dans le moteur du modèle) est journalisé avec le chemin de la note, consigné avec sa raison, et la boucle continue. L'exécution entière n'échoue que si aucune note n'a été écrite ; elle se termine alors avec une erreur qui liste la raison de chaque note, et aucun rapport n'est écrit.

4. Ce que vous pouvez choisir

  • Notes : une note ou un dossier de notes. Obligatoire.
  • Type de note : TMJ ou Ortho. Il sélectionne ensemble le prompt système et la fenêtre de contexte.
  • Modèle : un fichier de modèle, ou un dossier qui en contient exactement un. La liste montre les modèles hébergés ; il n'y a pas de choix “automatic”, donc le modèle n'est pas déduit du type de note.
  • Limite de réponse : la réponse la plus longue par note, 2048 tokens par défaut.
  • Température : 0 par défaut, ce qui signifie aucun hasard.
  • Fenêtre de contexte : 0 signifie la valeur par défaut du type de note.
  • Réglages cachés : une graine aléatoire et le périphérique (processeur par défaut) ; le serveur renseigne son propre périphérique.
  • Dossier de sortie : renseigné par le serveur, et refusé si c'est le dossier des notes.

Il n'y a pas de limite de temps, et un appel est limité par le plafond d'envoi de 500 MB du serveur.

6. Environnement

Tout s'exécute dans l'environnement propre de l'outil sur le serveur : Python 3.11, le build processeur de llama-cpp-python, et un lecteur chacun pour PDF et Word. Rien n'est installé dans Slicer. Le module legacy installait les paquets dans le Python propre de Slicer et téléchargeait un modèle de 4.4 ou 4.9 GB dans le dossier Documents de l'utilisateur.

7. Ce qui a changé par rapport à la logique legacy

Le prompt TMJ, l'absence de prompt pour Ortho et les deux fenêtres par défaut sont inchangés. Autour d'eux :

  • Où : sur le serveur au lieu de l'intérieur de Slicer sur le poste de travail.
  • Trouver les notes : récursif et insensible à la casse ; ne rien trouver est une erreur au lieu d'un succès silencieux.
  • Lecture : trois encodages de texte au lieu d'un ; les tableaux, en-têtes et pieds de page Word sont lus ; un PDF numérisé est refusé au lieu d'envoyer un texte vide au modèle ; un paquet de lecture manquant ne fait échouer que les notes de ce format.
  • Génération : limite de réponse à 2048 au lieu de 500, température 0 au lieu de 0.1, une graine, et une réponse coupée fait échouer la note au lieu d'être écrite.
  • Lecture de la réponse : JSON, puis lignes de champs, sinon rien n'est écrit, là où le module legacy enregistrait la réponse brute.
  • Sorties : un fichier JSON et un fichier texte par note, avec le nom complet de la note pour qu'un .txt, un .pdf et un .docx du même nom ne s'écrasent plus, et un rapport d'exécution.
  • GPU : demandé seulement sur demande, et le rapport dit si des couches ont réellement été déchargées.
  • Non porté : le Dashboard, et le téléchargement des modèles par le client.

8. Problèmes connus

  • Les notes sont envoyées au serveur telles quelles, sans désidentification, donc l'affirmation du legacy selon laquelle le texte clinique reste sur la machine ne tient pas pour VISOR (détails).
  • Le panneau et le README parlent d'un modèle “automatic”, mais rien ne déduit le modèle du type de note (détails).
  • Seul le modèle TMJ est hébergé, et un modèle du mauvais type n'est qu'un avertissement (détails).
  • Le moteur est le build processeur, quoi que disent certains commentaires ; une demande de GPU est signalée comme ignorée (détails).
  • Rien ne compare une note à la fenêtre de contexte, et les valeurs par défaut d'Ortho ne donnent à la réponse que ce que la note laisse (détails).
  • Les fichiers de sortie sont nommés autrement que ceux du legacy, donc les outils qui lisent les anciens noms ne les trouveraient pas (détails).
  • Corrigé : les PDF numérisés, les réponses coupées, les réponses illisibles, les notes de même nom et les demandes de GPU silencieuses ne produisent plus de fichier plausible (détails).
