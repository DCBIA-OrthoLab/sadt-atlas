CLIC avec VISOR

Ce qui change quand vous lancez CLIC via un serveur VISOR depuis 3D Slicer : ce qu'il faut fournir, ce qui reste pareil, ce qui diffère. Le module legacy a sa propre page.

VISOR Page legacy Atlas (VISOR)

Avec un serveur VISOR, le calcul s'exécute sur le serveur, pas sur votre poste de travail, et le panneau CLIC est un formulaire qui y envoie vos scans. Le détail du code est sur la page de l'atlas ; la connexion et l'exécution en général sont dans Utiliser VISOR.

Ce qui change dans le panneau

  • Rien n'est installé dans Slicer : aucun environnement de calcul à construire, aucun modèle à télécharger. Le modèle entraîné est déjà sur le serveur, et vous ne le choisissez pas.
  • Vous fournissez un CBCT en .nii ou .nii.gz, un fichier ou un dossier. Les sous-dossiers sont parcourus, un dossier avec un sous-dossier par patient fonctionne donc. Les fichiers d'autres formats (.nrrd, .mha...) sont ignorés ; s'il ne reste rien de lisible, l'exécution est refusée avec un message qui le dit.
  • Les résultats arrivent dans le dossier de sortie que vous choisissez dans le panneau. Vous pouvez aussi modifier le seuil de score (0,7 par défaut : les détections en dessous ne sont pas peintes) et le suffixe ajouté aux noms de fichiers (seg par défaut). Le périphérique qui exécute le calcul est décidé par le serveur.
  • Le champ du scan peut proposer des fichiers de test hébergés sur le serveur. Celui qui est listé pour CLIC est un CBCT de tête entière sans canine incluse connue : il montre que l'aller-retour fonctionne, pas que la classification est juste.
  • Vos scans sont envoyés au serveur. Ce qui les protège pendant le transit, et ce qui ne les protège pas, est expliqué dans Sécurité et confidentialité dans VISOR.

Ce qui reste pareil

La méthode est inchangée : le volume est lu coupe par coupe, chaque coupe est classée seule, et les valeurs 1, 2 et 3 signifient vestibulaire, bicorticale et palatine. Des coupes voisines peuvent toujours être en désaccord sur la même dent, et rien ne vous donne une classe par patient.

Ce qui diffère dans les résultats

  • Les résultats reviennent dans une seule archive, décompressée dans votre dossier de sortie. L'arborescence de vos dossiers d'entrée est reproduite, et chaque fichier s'appelle <scan>_seg.nii.gz (le module legacy produisait X.nii_seg.nii.gz dans un dossier X.nii).
  • Le panneau peut charger jusqu'à 12 segmentations dans la scène à la fin de l'exécution, vous n'avez donc plus à les chercher et les charger vous-même.
  • Un fichier CLIC_report.json est écrit à côté. Il nomme les trois classes et dit, par scan, lesquelles ont été détectées et quels scans ont échoué. Le panneau ne l'affiche pas : ouvrez le fichier. Quand un grand dossier est envoyé en plusieurs lots, le rapport que vous obtenez à la fin ne décrit que l'un d'eux.
  • Si un scan d'un dossier est illisible, les autres sont tout de même traités.
Un résultat vide n'est pas une erreur

Quand rien ne franchit le seuil sur un scan, vous obtenez une segmentation entièrement à zéro et l'exécution est déclarée réussie, même si cela arrive sur chaque scan du dossier. Le rapport porte la note « no detection cleared the score threshold » pour chacun de ces scans. Un résultat vide peut être une vraie réponse ou un mauvais modèle : lisez donc le rapport avant de conclure qu'il n'y a pas de canine incluse.
