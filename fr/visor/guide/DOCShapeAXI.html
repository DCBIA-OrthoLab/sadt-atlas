DOCShapeAXI avec VISOR

Ce qui change quand vous lancez DOCShapeAXI via un serveur VISOR depuis 3D Slicer : ce qu'il faut fournir, ce qui reste pareil, ce qui diffère. Le module legacy a sa propre page.

VISOR Page legacy Atlas (VISOR)

Avec un serveur VISOR, la classification et les cartes d'explicabilité sont calculées sur le serveur, et le panneau DOCShapeAXI est un formulaire qui y envoie vos maillages. Le détail du code est sur la page de l'atlas ; la connexion et l'exécution en général sont dans Utiliser VISOR. Vos maillages sont envoyés : ce qui les protège est expliqué dans Sécurité et confidentialité dans VISOR.

Ce qui change dans le panneau

  • Il n'y a plus de liste de types de données. Vous choisissez un checkpoint par son nom de fichier, et le nom décide de l'anatomie, de la tâche et du nombre de classes : condyles_4_class.ckpt (condyle, 4 stades), cleft_4_class.ckpt (défaut osseux de fente, 4 stades), et pour les voies aériennes airways_2_class.ckpt (obstruction oui ou non), airways_4_class.ckpt (4 stades) et airways_4_regress.ckpt (un rapport continu).
  • Pour les voies aériennes, les trois résultats ne sont plus enchaînés en une seule exécution : une exécution donne un checkpoint, vous la lancez donc une fois par checkpoint voulu.
  • Rien n'est installé ni téléchargé dans Slicer : les checkpoints sont sur le serveur.
  • Vous fournissez une surface .vtk ou un dossier de surfaces (les sous-dossiers sont parcourus).
  • Un interrupteur active ou désactive les cartes d'explicabilité. Désactivé, vous n'obtenez que le rapport avec les prédictions, sans surfaces, plusieurs fois plus vite. Activé par défaut.
  • Aucune surface de test n'est hébergée pour cet outil, parce que rien de public n'est une voie aérienne, un condyle ou une fente.

Ce qui diffère dans les résultats

  • Il n'y a pas de csv. Les prédictions sont dans DOCShapeAXI_report.json : pour chaque surface, le chemin relatif à votre entrée et soit une class (un entier) soit, pour le rapport continu, un score. Le rapport nomme aussi l'anatomie, la tâche, le nombre de classes et le réseau.
  • Les maillages portant les cartes d'explicabilité sont écrits directement dans le dossier de sortie, avec le suffixe _pred ajouté à leurs noms, et non dans un sous-dossier explainability. Le panneau peut en charger jusqu'à 12 dans la scène à la fin de l'exécution. Les cartes se lisent comme dans le guide legacy, Lire le résultat.
  • Toujours vrai : pas de score de confiance, la carte ne décrit que la branche multi-vues, et rien n'est initialisé par une graine, donc deux exécutions peuvent différer.
  • La ligne de la barre d'état construite par le panneau peut afficher « ? » là où devraient figurer l'anatomie et le checkpoint. L'information est dans le rapport.
Donnez à chaque surface un nom de fichier distinct

Les surfaces sont cherchées dans les sous-dossiers mais les résultats sont écrits côte à côte. Deux fichiers appelés surface.vtk dans des sous-dossiers différents sont écrits au même endroit : l'un remplace l'autre, et l'exécution risque ensuite de s'arrêter avec une erreur une fois tout le calcul terminé. Cela est déduit du code, pas testé.

Un serveur neuf peut refuser sa première exécution

Le réseau a besoin d'un petit fichier de modèle d'image (un backbone EfficientNet) que l'outil ne téléchargera pas au milieu d'une requête. S'il n'a pas été mis en place sur le serveur, l'exécution échoue après l'envoi de vos maillages, avec un message qui nomme le fichier manquant. C'est un problème d'installation du serveur : envoyez le message à la personne qui l'administre.
