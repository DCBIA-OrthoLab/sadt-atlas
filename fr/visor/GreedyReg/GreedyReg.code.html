GreedyReg sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR de GreedyReg dans le code, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. Le module legacy a sa propre page de code.

VISOR Code Atlas (explication) Page legacy Guide (VISOR)

Dans VISOR, GreedyReg est un paquet Python qui s'exécute sur le serveur : Slicer envoie les deux dossiers de scans, le serveur les apparie par patient, lance Greedy deux fois par paire (une recherche affine, puis un rééchantillonnage de T2 dans T1) et renvoie les résultats. Greedy n'est plus un binaire téléchargé mais le paquet picsl_greedy, et la commande qu'il reçoit est celle du legacy, option pour option. Cette page décrit le portage dans SADT-VISOR (branche tool/vface, 6ba2a78, 2026-09-30), servi par VISOR-serve (e9a7e5d) et piloté depuis Slicer par l'extension AutomatedDentalToolsRemote (19b95e8) ; le module legacy est décrit sur sa propre page. C'est un portage partiel. Ce qui existe, c'est le cœur de GreedyReg_CLI : apparier les scans de deux dossiers par patient, restreindre éventuellement la métrique avec un masque et partir d'une transformation initiale, lancer Greedy, rééchantillonner. Le mode manuel, la création du masque dans la scène, le téléchargement du binaire et le mode Distant (repères) ne sont pas dans l'outil serveur : run() n'a d'argument pour aucun d'eux (SADT-VISOR GreedyReg/__init__.py:38-52), et aucun mode par repères n'existe nulle part dans SADT-VISOR (vérifié avec git log --all -S"Landmark + Greedy"). La liste « Not ported » du README ne nomme que le protocole de progression sur stdout et la protection d'installation de nibabel (README.md:60-64). Rien ici n'affirme qu'un serveur soit déployé.

1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

GreedyReg n'appelle aucun outil et aucun outil ne l'appelle : il n'y a pas de sup.run dans le paquet et aucun autre outil de SADT-VISOR ne le nomme (grep sur tools/*/src). Son amont naturel est une segmentation qui donne le masque d'une structure stable, typiquement la base du crâne issue d'AMASSS (la docstring le dit, __init__.py:64-67), mais le clinicien apporte ce masque sous forme de fichier : l'outil ne va pas le chercher. Dans le module legacy, le mode Distant appelait ALI_CBCT pour des repères ; ce chemin n'existe pas dans VISOR (l'entrée calls: ["ALI_CBCT"] n'existe que dans la fixture de test du client).

4. Le pipeline, pas à pas

Explication en langage courant et maths : page de l'atlas.

Un appel de run() recale toute une cohorte, patient par patient, dans SADT-VISOR GreedyReg/__init__.py:88-190.

4.1 Apparier T1 et T2 calculé

Explication en langage courant et maths : page de l'atlas.

Les choix sont vérifiés en premier, de sorte qu'une mauvaise métrique donne une seule erreur, non une par patient (__init__.py:92 ; pipeline.py:47-55). Puis pairing.pair(t1, t2, output_suffix) (__init__.py:102). La règle partagée parcourt les deux dossiers récursivement, accepte .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl (pairing.py:36), et indexe chaque fichier par patient_stem : l'extension, tout suffixe laissé par une exécution précédente d'ASO, d'AMASSS, d'ALI ou d'AREG, et le jeton de point temporel sont retirés, et le sous-dossier est conservé comme préfixe (pairing.py:175-211, 232-276). Les fichiers qui ressemblent à une sortie antérieure du suffixe de cette exécution sont ignorés (pairing.py:214-229). Exemples exécutés le 2026-11-09 : 01_T1.nii.gz donne 01, Patient-01.nii.gz donne Patient_01, C_0001_T1_Or.nii.gz donne C_0001.

Un dossier qui contient deux points temporels est refusé, afin que T1 ne soit jamais apparié à T1 (pairing.py:336-358) :

for label, root in (("T1", t1_root), ("T2", t2_root)):
    found = timepoints_in(root, accept)
    if len(found) > 1:
        raise ToolInputError(
            f"The {label} folder holds scans from more than one timepoint ..."

Aucun patient présent dans les deux dossiers est une ValueError qui liste jusqu'à dix clés de chaque côté (__init__.py:112-122) ; le serveur la transforme en 422.

4.2 Masques et transformations initiales calculé

Explication en langage courant et maths : page de l'atlas.

_discover_masks indexe un masque comme son scan, et retire les jetons de structure (les jetons de région d'AREG et les jetons de masque) seulement d'un fichier dont le nom dit que c'est un masque, de sorte que P1_T1_MAND_seg.nii.gz s'indexe en P1 alors qu'un patient appelé MD_01 garde son nom (__init__.py:28-35, 207-228). _discover_transforms indexe les fichiers .mat de la même façon et retire transform, de sorte que les transformations d'une exécution peuvent être réinjectées comme point de départ de la suivante (__init__.py:231-248). Les masques et transformations qui ne correspondent à aucun patient sont listés dans le rapport (__init__.py:131-135).

4.3 Le point de départ de la recherche calculé

Explication en langage courant et maths : page de l'atlas.

Avec une transformation donnée, Greedy part de celle-ci telle quelle (-ia, __init__.py:261-262). Sinon l'outil écrit l'identité legacy avec une translation en x légèrement décalée (pipeline.py:101-114, legacy GreedyReg_CLI.py:86-90) :

matrix = np.eye(4)
matrix[0, 3] = 0.001

La docstring en donne la raison : Greedy lit une identité exacte comme « no initialisation given » (pipeline.py:102-106 ; un comportement de Greedy, non vérifié ici). Un masque est binarisé au-dessus de zéro en float32 avec l'affine propre du masque, dans le dossier de travail (pipeline.py:117-126 ; __init__.py:267-271). Rien ne vérifie que le masque est dans l'espace de T1.

4.4 Les deux appels à Greedy calculé

Explication en langage courant et maths : page de l'atlas.

La recherche affine, construite argument par argument comme le buildRegistrationCommand legacy (pipeline.py:74-94 ; legacy GreedyReg_CLI.py:104-125) :

-d 3 -a -m NCC 4x4x4 | NMI | SSD   (4x4x4 is a radius: a 9x9x9 window)
-i <T1> <T2> -o <patient>_transform.mat
-n 100x100x50x25 -e 0.5 -search 100 10 20
-dof 6 | 12 -ia <init> [-gm <mask>]

T1 est l'image fixe, T2 l'image mobile. -n est le calendrier multi-résolution et -search la recherche aléatoire qui le précède ; aucun des deux n'est exposé (pipeline.py:78-81). Une métrique inconnue est refusée là où le CLI legacy retombait sur SSD (pipeline.py:58-71 ; legacy GreedyReg_CLI.py:107-112). Vient ensuite le rééchantillonnage de T2 dans la grille de T1 (pipeline.py:97-98) :

-d 3 -rf <T1> -rm <T2> <patient>_<suffix>.nii.gz -r <patient>_transform.mat

Chaque appel s'exécute dans un interpréteur enfant qui transmet les arguments joints à Greedy3D().execute, borné par CASE_TIMEOUT_SECONDS = 600 ; une sortie non nulle devient une RuntimeError qui porte le message propre de Greedy (pipeline.py:136-165) :

_CHILD = """
import sys
from picsl_greedy import Greedy3D
Greedy3D().execute(" ".join(sys.argv[1:]), out=sys.stdout)
"""
finished = subprocess.run(
    [sys.executable, "-c", _CHILD, *[str(part) for part in command]],
    capture_output=True, text=True, timeout=timeout,
)

Le commentaire explique le processus enfant : un appel dans le même processus aurait fait perdre la borne legacy de 600 s, et le serveur ne fixe aucune limite de temps de son côté (pipeline.py:129-135).

4.5 Sorties et rapport calculé

Explication en langage courant et maths : page de l'atlas.

Par paire, sous le dossier de sortie zippé et en reproduisant l'arborescence d'entrée : <patient>_<suffix>.nii.gz (toujours .nii.gz) et <patient>_transform.mat, la matrice texte de Greedy, non un .tfm (__init__.py:254-259). Chaque cas consigne status, les noms de fichiers, le masque et la transformation initiale utilisés, transform_maps: "the T2 image -> the T1 frame (what greedy -r consumes)" et produced relativement au dossier de sortie (__init__.py:143, 261-286). Un échec consigne reason, le type et le texte de l'exception (__init__.py:157-167) ; le dossier de travail du patient est supprimé dans tous les cas (:168-170). À la fin, summary et duration_seconds (:173-178), et le rapport n'est écrit que si au moins une paire a été recalée (:180-189). La progression est « patient i sur n », jamais un nom de fichier (:141).

9. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Le client Slicer décrit un outil que le serveur n'a pas

AutomatedDentalToolsRemote GreedyRegRemote/GreedyRegRemote.py:11-24 (docstring) et :50-57 (texte d'aide) décrivent un argument mode avec Greedy, Landmark et Landmark + Greedy, un landmark_model et un second outil atteint par le superviseur. L'outil serveur n'a rien de tout cela : son run() prend t1, t2, output_dir, masks, initial_transforms, metric, transform_type, output_suffix (SADT-VISOR GreedyReg/__init__.py:38-52) et une recherche de mode ou de « landmark » dans le paquet ne trouve rien. Le commentaire de GreedyRegRemote.py:76-77 nomme un argument init ; l'argument est initial_transforms. Le schéma écrit à la main du test client porte mode, init, region et landmark_model (test_greedyreg_client.py:90-260) et une entrée calls pour ALI_CBCT, donc ces 22 tests vérifient la fixture, non le serveur. Aucune branche de SADT-VISOR ne contient de mode par repères (git log --all -S"Landmark + Greedy" est vide). Le README.md:202,1056-1076 du Remote répète l'ancienne description à trois modes. On ignore si le mode Landmark est prévu ou abandonné.

La ligne d'état finale lit un champ qui n'existe pas

_summarize formate {mode} à partir de report.get("mode") et compte len(report["cases"]) (AutomatedDentalToolsRemote GreedyRegRemote/GreedyRegRemote.py:133-138). Le rapport n'a pas de mode (ses clés sont listées sous Arguments et schéma), donc le message de la barre d'état dit « GreedyReg finished in ? mode: N pair(s) registered. » Et cases contient aussi les patients en échec (SADT-VISOR GreedyReg/__init__.py:166-171), donc N les compte. summary.registered est le bon nombre.

Deux fichiers ne font pas une paire

Le client dit que deux fichiers forment une paire (GreedyRegRemote.py:75-77) et la fixture décrit t2 en conséquence. pairing.pair parcourt des dossiers (os.walk, pairing.py:232-276) : lancé le 2026-11-09 avec a/P1_T1.nii.gz et b/P1_T2.nii.gz, il n'a rien apparié, ce que l'outil transforme en No patient appears in both the T1 and the T2 folder (SADT-VISOR GreedyReg/__init__.py:112-122). Un fichier unique envoyé arrive à run() comme le chemin de ce fichier (VISOR-serve server/main.py:1288-1296). Les tests de l'outil n'utilisent que des dossiers. Aucun essai via un serveur n'a été fait.

La cohorte de test hébergée est refusée telle qu'elle est proposée

Le seul fichier de test que le serveur héberge pour GreedyReg est CBCT_T1_T2_pair (VISOR-serve scripts/data-manifest.yml:756-781), et chaque argument path le propose (VISOR-serve server/registry/conventions.py:236-240, pas de section [tools.GreedyReg] pour le restreindre). Sa racine contient un dossier T1/ et un dossier T2/ (vérifié sur une copie mise en place). pairing.pair refuse un dossier qui contient plus d'un point temporel (pairing.py:336-358), et GreedyReg ne descend pas de lui-même dans T1/, contrairement à AREG_CBCT qui appelle pairing.timepoint_root. Lancé le 2026-11-09 sur les noms de fichiers de la copie mise en place : The T1 folder holds scans from more than one timepoint (T1, T2) ; en pointant sur T1/ et T2/, on apparie C_0001. On n'a pas vérifié si le panneau permet de choisir un sous-dossier d'un fichier de test hébergé. La même convention propose des fichiers de test hébergés pour masks et initial_transforms, qui sont les propres fichiers du clinicien.

Seuls les appels à Greedy sont bornés, pas l'exécution

Chaque appel à Greedy est limité à 600 s (SADT-VISOR GreedyReg/pipeline.py:136,145) et une paire en fait deux (SADT-VISOR GreedyReg/__init__.py:273,276), donc une paire peut prendre jusqu'à 1200 s. Il n'y a aucune borne sur le nombre de paires et le serveur n'en fixe aucune (TOOL_TIMEOUT_SECONDS = 0, VISOR-serve server/config.py:77). VISOR-serve CLAUDE.md:896 parle d'une borne « per pair » ; le code borne chaque appel.

Pas de rapport quand rien n'a été recalé

Si chaque paire échoue, l'outil lève une erreur (SADT-VISOR GreedyReg/__init__.py:180-187) avant la ligne qui écrit GreedyReg_report.json (:189). Les raisons ne voyagent alors que dans le message d'erreur. La reason d'un patient en échec est le texte de l'exception (:167).

Le .mat produit n'est pas une transformation Slicer ; l'espace du masque n'est pas vérifié

<patient>_transform.mat est ce que Greedy écrit avec -o (SADT-VISOR GreedyReg/pipeline.py:86 ; __init__.py:255) ; rien dans le paquet ne le convertit en .tfm, et le client ne le charge pas (GreedyRegRemote.py:97-104). Un masque multi-étiquettes est aplati par > 0 et rien ne vérifie qu'il se trouve dans l'espace de T1 (pipeline.py:117-126). Ces deux points sont ceux du module legacy (page legacy), repris sans changement. Lu dans le code.

Valeurs par défaut qui diffèrent du module legacy

La métrique par défaut est NCC là où la liste legacy commençait par NMI (SADT-VISOR GreedyReg/__init__.py:49, GreedyReg.py:575@3c67957), la transformation est Rigid par défaut, et le suffixe est configurable (output_suffix) là où le CLI legacy écrivait _registered (GreedyReg_CLI.py:168@3c67957).

Greedy est supposé utiliser le GPU

L'outil ne déclare aucun argument device, donc l'admission du serveur traite chaque exécution comme une exécution GPU (VISOR-serve server/execution/dispatch.py:95-116), alors que Greedy s'exécute sur le CPU. Une exécution de GreedyReg peut donc attendre un créneau GPU qu'elle n'utilise pas. Lu dans le code.

L'appariement et les échecs sont explicites

Les patients non appariés, les masques inutilisés et les transformations initiales inutilisées sont signalés (SADT-VISOR GreedyReg/__init__.py:108,131-132) ; un patient en échec ne coûte qu'un patient ; la métrique et le type de transformation sont validés deux fois (pipeline.py:47-55). Les 189 tests du paquet ont réussi le 2026-11-09, avec Greedy remplacé par une doublure.
