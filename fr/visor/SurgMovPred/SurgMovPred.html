SurgMovPred sur VISOR

SurgMovPred prédit le mouvement postopératoire de 28 points de repère à partir d'un tableau de mesures et d'un plan chirurgical. Cette page explique comment, pas à pas, avec les maths : ce qui entre, ce que chaque étape en fait, et ce qui sort. Les fichiers, les lignes, les arguments et les constats sont sur la page de code. Le module Slicer legacy est sur sa propre page.

Code (développeurs) VISOR 112 régresseurs CPU seulement Page legacy Guide (VISOR)

Les noms de fichiers, les numéros de ligne et chaque constat sont sur la page de code. Dépôts nommés ici : le catalogue d'outils SADT-VISOR à 6ba2a78, VISOR-serve à e9a7e5d, le client Slicer AutomatedDentalToolsRemote à 19b95e8 et le module legacy SlicerAutomatedDentalTools à 3c67957. Tout a été lu dans le code ; rien n'a été exécuté pour cette page.

Vue d'ensemble : ce qui entre, ce qui sort

SurgMovPred prédit de combien les os seront déplacés lors d'une opération orthognathique. Il lit un tableau d'une ligne par patient (des mesures céphalométriques avant l'opération, plus le mouvement planifié) et renvoie un tableau de mouvements postopératoires prédits : 28 points de repère, chacun avec quatre valeurs. Il ne lit aucun scan ni maillage, et il ne change rien dans Slicer.

SurgMovPred sur VISOR
Entréeun tableau CSV, XLSX ou ODS de mesures et de plan, ou un dossier à plat de tels tableaux
Méthode112 modèles entraînés, un par cible ; chacun remet ses 145 entrées à l'échelle et prédit avec un empilement de trois régresseurs
Sortiedeux tableaux au même contenu, predictions_outputs.xlsx et .csv : identifiant du patient, puis une colonne par cible prédite
Oùsur le serveur, sur le processeur seulement ; le panneau Slicer envoie le tableau et enregistre les deux résultats

L'algorithme est celui du legacy, inchangé. Ce qui a changé, c'est l'ordre, la gestion des erreurs et l'environnement (Ce qui a changé).

1. Situation dans la chaîne

SurgMovPred est une feuille : il n'appelle aucun autre outil et aucun autre outil ne l'appelle, comme dans le module legacy. Le panneau Slicer est un client mince généré à partir de la description de l'outil par le serveur. L'outil a été empaqueté sous le nom Surg_Mov_Pred, et le serveur accepte aussi l'ancienne graphie. Il est couvert par des tests automatisés dans son dépôt, et son README rapporte que sa sortie correspondait à l'implémentation serveur précédente sur 101 patients et 112 modèles (lu, non relancé pour cette page).

Dans le codeNom dans l'API, dossier de l'outil, déclaration serveur, provenance et nombre de tests

1.1 Ce qui s'exécute où

Le serveur fait tout : lire le tableau, nettoyer les noms de colonnes, exécuter les 112 modèles sur le processeur et écrire les deux tableaux. Le panneau n'a qu'un champ, les mesures, envoie le tableau (un dossier est zippé à l'aller), puis enregistre l'archive renvoyée à côté du fichier que vous avez choisi. Rien n'est chargé dans la scène Slicer.

Dans le codeLes tâches du serveur et du client avec les lignes qui les décident

2. Fichiers en jeu

L'outil tient en deux petits fichiers Python (une fonction run et le pipeline), un fichier de mise en page qui cache l'argument model et renomme le champ, la définition de l'environnement et les tests. Le module legacy était un panneau de 878 lignes plus un script en ligne de commande de 323 lignes.

Dans le codeLe tableau des fichiers avec le nombre de lignes

3. Le pipeline

Une fois par exécution, l'outil charge tous les fichiers de modèles et lit le tableau. Puis, pour chacune des 112 cibles à tour de rôle, il trouve les colonnes dont ce modèle a besoin, les met à l'échelle, prédit et garde le résultat. À la fin, il assemble un tableau. Cliquez sur une case pour lire sa section.

Dans le codeLa fonction derrière chaque case du schéma

3.1 Chargement des paquets de modèles

Chaque cible a son propre dossier avec un fichier, un paquet qui contient quatre choses : le nom de la cible, la liste ordonnée des 145 colonnes d'entrée qu'elle attend, son scaler ajusté et son modèle ajusté. L'outil charge chaque paquet trouvé sous le dossier des modèles, dans l'ordre trié, de sorte que les colonnes du résultat sortent dans le même ordre à chaque exécution. Un paquet qui ne peut pas être lu est journalisé et ignoré, et si aucun ne se charge, l'exécution s'arrête. Les 112 paquets attendent les mêmes 145 colonnes ; 28 d'entre elles se terminent par _T0 (l'état avant l'opération) et 25 par _Total (le mouvement total planifié), c'est pourquoi le tableau doit contenir le plan autant que les mesures.

Dans le codeLa boucle de chargement, les clés des paquets, l'exigence de LightGBM et l'avertissement de version réduit au silence

3.2 Lecture des mesures

Un fichier est lu selon son extension (CSV, XLSX, ODS) ; un dossier n'est pas parcouru récursivement, et ses tableaux sont triés et empilés les uns sous les autres. La colonne d'identifiant du patient est trouvée en essayant une liste de noms usuels (#, id, patient id, etc.) ; sans elle, la colonne d'identifiant de la sortie reste vide avec un avertissement. Les noms de colonnes sont nettoyés vers la graphie utilisée à l'entraînement des modèles : les guillemets et les crochets sont supprimés, tout ce qui n'est ni une lettre, ni un chiffre, ni un tiret bas, ni une apostrophe devient un tiret bas, et un nom commençant par un chiffre reçoit un préfixe. Un nom qui ne peut pas être nettoyé est une erreur.

Dans le codeLe code de lecture, les huit motifs d'identifiant et les règles de nettoyage avec leurs lignes

3.3 Une cible par paquet

Pour chaque paquet, l'outil cherche chaque colonne requise dans le tableau. La seule tolérance est un suffixe _T0 manquant : un modèle qui demande X_T0 accepte une colonne nommée X. Toute autre colonne manquante retire cette cible de la sortie, avec un avertissement. Une cellule vide n'est pas remplie : le modèle la refuse, l'erreur est journalisée, et cette cible est laissée de côté pour tous les patients. Les colonnes sont mises dans l'ordre que le modèle attend, mises à l'échelle, et données au modèle.

Un échec pendant la prédiction d'une cible est journalisé et la boucle continue. Ce n'est que lorsqu'aucune cible n'a été prédite que l'exécution s'arrête avec une erreur, plutôt que d'écrire des tableaux sans prédictions.

Dans le codeLa boucle avec la résolution des variables, les règles d'omission et les cas d'erreur

3.4 Sorties

Les prédictions deviennent un tableau avec l'identifiant du patient comme première colonne de données, écrit deux fois, en Excel et en CSV. Les deux commencent par une colonne sans nom qui numérote les lignes, ce qui compte en lisant les positions des colonnes. Les deux fichiers sont rendus au client, et il n'y a pas de fichier de rapport.

Dans le codeLes deux fichiers, la disposition des colonnes et la valeur de retour

4. Ce que vous pouvez choisir

  • Les mesures : un seul tableau, ou un dossier à plat de tableaux. C'est le seul champ affiché dans le panneau.
  • Non proposés : les modèles (le jeu propre au serveur est utilisé), le dossier de sortie (fixé par le serveur) et toute option sur les cibles ou les seuils. Les 112 cibles sont toujours tentées.

6. Environnement

L'outil a son propre environnement Python sur le serveur (Python 3.12 avec des versions épinglées de numpy, pandas, scikit-learn, LightGBM et des lecteurs de tableurs) et aucun logiciel de carte graphique. Les modèles sont mis en place sur le serveur sous la forme d'une archive d'environ 740 MB (706 MiB). Rien n'est installé à l'exécution.

Dans le codeLes versions épinglées avec leurs lignes, l'archive des modèles et le commentaire de mesure de temps

7. Ce qui a changé par rapport à la logique legacy

  • L'outil s'exécute sur le serveur dans son propre environnement, au lieu de s'exécuter dans le Python de Slicer avec une installation de paquet à chaque Apply.
  • L'entrée peut être un fichier ou un dossier à plat ; le legacy ne prenait qu'un dossier, et sa lecture de dossier n'avait pas d'ordre stable.
  • Les modèles et les tableaux sont lus dans l'ordre trié, donc deux exécutions donnent les mêmes lignes et colonnes dans le même ordre.
  • Un nom de colonne qui ne peut pas être nettoyé est une erreur, au lieu d'un nom de remplacement partagé qui faisait entrer deux colonnes en collision.
  • Une exécution où aucun modèle ne prédit est une erreur au lieu de deux tableaux sans prédictions.
  • Les deux fichiers de sortie sont rendus, et les fichiers ODS peuvent être lus parce que le lecteur est installé.
Dans le codeLe tableau legacy contre VISOR avec les lignes

8. Problèmes connus

  • Les deux fichiers de résultat commencent par une colonne d'index sans nom ; voir le constat.
  • Certains commentaires du client décrivent un fichier de sortie unique ; voir le constat.
  • Le README de l'outil donne un nom de dossier de données périmé ; voir le constat.
  • Les cibles sont prédites indépendamment, donc les mouvements des points d'un même segment osseux n'ont pas à s'accorder, et rien n'est appliqué à la scène ; voir le constat.
  • Une cible ignorée n'est visible que dans le journal du serveur ; voir le constat.
  • Côté positif, l'ordre est reproductible et un résultat vide n'est plus silencieux ; voir la vérification.
