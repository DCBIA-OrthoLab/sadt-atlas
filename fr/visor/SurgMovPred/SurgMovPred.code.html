3. Le pipeline

Explication en langage courant et maths : page de l'atlas.

3.1 Chargement des paquets de modèles

Explication en langage courant et maths : page de l'atlas.

model est facultatif et caché. Quand il est vide, run() utilise <data_root>/Surg_Mov_Pred/models (__init__.py:19,22-34,71). load_model_packages prend alors chaque stacking_package.pkl en dessous, dans l'ordre trié, et charge chacun avec joblib (pipeline.py:162-195) :

package_files = sorted(model.glob("**/stacking_package.pkl"))   # legacy: list(...), filesystem order
for pkl_path in package_files:
    package = joblib.load(pkl_path)        # {target_name, features_names, scaler, model}
    packages[package["target_name"]] = package

Un paquet illisible est journalisé et ignoré ; si aucun ne se charge, RuntimeError (pipeline.py:180-192). Le commentaire de layout.py:16-24 décrit le jeu livré : 112 paquets, chacun demandant les mêmes 145 colonnes, dont 28 portent le suffixe _T0 (état préopératoire) et 25 le suffixe _Total (le mouvement total planifié). Le tableau contient donc le plan autant que les mesures, d'où le libellé « Measurements and plan ». Les régresseurs de stacking contiennent des sous-estimateurs LightGBM, donc lightgbm doit être installé pour que joblib.load réussisse (pyproject.toml:18-20). Les paquets ont été sérialisés sous scikit-learn 1.6.1 et sont chargés sous 1.7.2 ; l'avertissement de version est volontairement réduit au silence, comme l'a fait l'amont (pipeline.py:101-115, README.md:72-75).

3.2 Lecture des mesures

Explication en langage courant et maths : page de l'atlas.

  • Un fichier ou un dossier à plat. Un fichier est lu selon son extension : .csv avec read_csv, .xlsx avec read_excel, .ods avec read_excel(engine="odf") (pipeline.py:22,118-129). Un dossier n'est pas parcouru récursivement : ses fichiers portant l'une des trois extensions, casse ignorée, sont triés et concaténés ligne à ligne (:132-159). Le legacy ne lisait qu'un dossier, en cherchant les extensions en minuscules et en majuscules et en dédoublonnant avec set(), si bien que l'ordre des lignes changeait d'une exécution à l'autre (legacy SurgMovPred_CLI/SurgMovPred_CLI.py:151-157).
  • Identifiant du patient. find_id_column essaie huit motifs dans l'ordre (#, id, id patient, patient id, patient number, subject id, patient, subject, sans tenir compte de la casse), puis toute colonne dont le nom contient à la fois « patient » et « id » (pipeline.py:65-98). Sans aucune, IDPatient reste vide avec un avertissement (:303-312).
  • Les noms de colonnes sont nettoyés vers la forme de l'entraînement par clean_name : suppression des espaces aux extrémités, des guillemets, des barres obliques inverses et des crochets, toute suite de caractères autres que lettres, chiffres, tiret bas et apostrophe devient un seul tiret bas, total devient Total, un chiffre initial reçoit f_ (pipeline.py:27-50). Un nom qui ne peut pas être nettoyé lève ValueError (:51-60) ; le legacy renvoyait 'f_unnamed', si bien que deux telles colonnes se masquaient l'une l'autre (legacy SurgMovPred_CLI.py:63-66).

La seule tolérance est le suffixe _T0 manquant ; toute autre colonne manquante retire cette cible de la sortie avec un avertissement (pipeline.py:224-236). Une exception pendant la prédiction d'une cible est journalisée et la boucle continue (:249-250). Une cellule vide n'est pas remplie : elle arrive au scaler sous forme de NaN et le modèle lève une erreur dessus, de sorte que cette cible est abandonnée pour toutes les lignes (les paquets contiennent un ElasticNetCV ; un stack de substitution sur un scikit-learn actuel a levé ValueError: Input X contains NaN ; les paquets livrés n'ont pas été lancés). Si aucune cible n'a été prédite, l'exécution lève RuntimeError au lieu d'écrire des tableaux sans prédictions (:252-264). Le legacy écrivait ces tableaux.

3.4 Sorties

Explication en langage courant et maths : page de l'atlas.

Les prédictions deviennent un seul DataFrame, IDPatient est inséré en première colonne, et le tableau est écrit deux fois (pipeline.py:266,314-317,276-287) :

output_dir/predictions_outputs.xlsx     df.to_excel(..., index=True)
output_dir/predictions_outputs.csv      df.to_csv(..., index=True)
columns:  <unnamed index 0..n-1>, IDPatient, <one column per predicted target>

run() renvoie {"excel": ..., "csv": ...}, un dict[str, Path], de sorte que le serveur rend les deux comme un ensemble de fichiers (VISOR-serve server/registry/schema_tool.py:99-103). L'ordre des colonnes de cibles suit les chemins de paquets triés, le même à chaque exécution. Il n'y a pas de rapport JSON.

8. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Colonne d'index sans nom dans les deux tableaux

Les deux fichiers de résultat commencent par une colonne contenant 0, 1, 2 et ainsi de suite, avant IDPatient (pipeline.py:283-284). Le CLI legacy fait de même (legacy SurgMovPred_CLI/SurgMovPred_CLI.py:268-269). À prendre en compte en lisant les positions des colonnes.

Commentaires périmés dans le client

Le client dit que output_kind « is file » (Remote SurgMovPredRemote/SurgMovPredRemote.py:44) et le widget de base donne « SurgMovPred's single predictions_outputs.xlsx » comme exemple (Remote ServerToolsCore/ServerToolsCoreLib/base_widget.py:1390-1391). L'outil renvoie deux fichiers, que le code de schéma publie comme un ensemble de fichiers (VISOR-serve server/registry/schema_tool.py:100-103). Le panneau les gère quand même, puisqu'il décompresse tout zip qu'il reçoit.

Chemin de données périmé dans le README

Le README de l'outil donne le dossier des modèles comme /DATA/SurgMovPred/models (README.md:45), alors que le code cherche sous Surg_Mov_Pred (__init__.py:19,34), le nom que le manifeste de données utilise aussi (VISOR-serve scripts/data-manifest.yml:91). Le code fait référence.

Toujours vrai depuis le legacy : cibles indépendantes, rien d'appliqué à la scène

Chaque cible est un model.predict distinct sur la même ligne (pipeline.py:216-247), donc les déplacements prédits des points d'un même segment rigide ne sont pas contraints de s'accorder entre eux (page legacy, pièges). La sortie se résume aux deux tableaux : pas de transformation, pas de nœud Slicer, et le panneau enregistre l'archive plutôt que de rien charger (RESULT_KIND = "save_as", Remote SurgMovPredRemote.py:46). Lu dans le code.

Une cible ignorée n'est visible que dans le journal du serveur

Un paquet dont les variables manquent dans le tableau est ignoré avec un logger.warning, et une cible dont la prédiction échoue avec un logger.exception (pipeline.py:234-236,249-250). L'exécution réussit alors avec moins de colonnes. Il n'y a pas de fichier de rapport, donc l'utilisateur ne voit les cibles manquantes qu'en comptant les colonnes. La seule protection est le cas du tout ou rien (:252-264). Lu dans le code.

Vérifié : ordre reproductible et pas de résultat vide silencieux

Les paquets et les tableaux sont triés, donc deux exécutions sur la même entrée donnent les mêmes lignes et colonnes dans le même ordre (pipeline.py:143-147,173) ; une exécution où aucun modèle ne prédit est une erreur, non deux tableaux vides (:252-264) ; un mauvais nom de colonne est une erreur, non une variable masquée (:51-60). Lu dans le code.
