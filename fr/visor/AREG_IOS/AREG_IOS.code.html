AREG_IOS sur VISOR : le code

Pour les développeurs : ce que fait le port VISOR d'AREG_IOS dans le code, avec des références file:line, des signatures, des arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. Le module legacy a sa propre page.

Code Atlas (explication) VISOR AREG_IOS atteint comme AREG, mode IOS torch 2.11, pytorch3d, GPU ou CPU Page legacy Guide (VISOR) Bibliographie

AREG_IOS recale un scan intraoral de suivi (T2) sur le scan de référence (T1) du même patient par un ICP rigide sur une zone que le traitement ne déplace pas : le palais sur l'arcade supérieure, ou une bande le long de la ligne mucogingivale sur l'arcade inférieure. Dans VISOR, tout le calcul s'exécute sur un serveur, y compris le réseau qui trouve la zone palatine ; Slicer ne fait qu'afficher le formulaire, envoyer les dossiers et ouvrir ce qui revient. Cette page décrit ce port, lu à SADT-VISOR 6ba2a78 (branche tool/vface), VISOR-serve e9a7e5d et AutomatedDentalToolsRemote 19b95e8. Le module legacy auquel on le compare est SlicerAutomatedDentalTools 3c67957, décrit sur sa propre page ; les chemins legacy ci-dessous sont à ce commit.

Abréviations utilisées sur cette page : ios/ désigne SADT-VISOR tools/AREG/AREG_IOS/src/sadt_areg_ios/, common/ désigne SADT-VISOR tools/AREG/common/src/sadt_areg_common/, et les chemins server/ sont dans VISOR-serve. « Observé » marque ce qui a été exécuté (tests, scripts/describe.py, courtes sondes Python) pendant l'étude du port ; tout le reste a été lu dans le code.

1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

Un client ne nomme jamais AREG_IOS : le module Slicer envoie AREG avec mode = "IOS", et le serveur échange la facade contre ce moteur. Le moteur gère l'appariement, le réseau palatin, la bande mucogingivale et l'ICP ; les labels de dents, l'orientation et les landmarks mucogingivaux viennent de trois autres outils qu'il appelle via le superviseur.

3.1 Entrées et appariement

Explication en langage courant et maths : page de l'atlas.

Comme dans le moteur CBCT, chaque entrée devient un répertoire sous <output_dir>/.areg_work/, un fichier seul étant lié dans un dossier à lui (ios/dispatch.py:311-329,368-374). Les maillages sont .vtk .vtp .stl .obj (ios/surfaces.py:35,48-49), lus avec tous leurs tableaux de points (ios/surfaces.py:52-76).

discover parcourt récursivement un dossier de point temporel et range chaque maillage sous une clé et une mâchoire (ios/pipeline.py:38-59). La clé est le dossier relatif plus patient_stem, dont les jetons de mâchoire sont retirés comme les jetons de point temporel, de sorte que P1_T1_U.vtk et P1_T2_Upper.vtk partagent la clé P1. La mâchoire est lue sur des jetons entiers du nom de base : u up upper maxilla max mx pour l'arcade supérieure, l low lower mandible mandibule mand md pour l'inférieure (ios/surfaces.py:113-130, common/catalogs.py:175-180). Un fichier laissé par une exécution précédente avec le même suffixe est ignoré (ios/pipeline.py:53-54).

pair ne garde un sujet que si l'arcade sur laquelle se trouve la zone existe aux deux points temporels, et avec le palais elle emporte aussi l'arcade opposée quand les deux points temporels l'ont (ios/pipeline.py:81-116). Rien n'est deviné : ce qui ne s'apparie pas est listé dans le rapport sous trois raisons.

"unmatched": {
  "registered_jaw": "Upper",
  "meshes_without_a_jaw_in_their_name": [...],
  "patients_without_a_upper_arch": [...],
  "patients_present_at_only_one_timepoint": [...]}     # pipeline.py:72-78

Quand aucun sujet ne s'apparie, l'exécution s'arrête avec une erreur qui donne la règle de nommage et les comptes (ios/dispatch.py:189-197).

3.2 Labels et orientation : les appels supervisés

Explication en langage courant et maths : page de l'atlas.

main résout deux bundles hébergés avant toute chose : registration_model laissé vide devient DATA/AREG/models/AREG_model, ios_reference laissé vide devient DATA/AREG/models/IOS_Gold_files (ios/dispatch.py:87-97,457-459). _check_ios refuse ensuite, avant la lecture d'un fichier : une zone inconnue ; le palais sans checkpoint trouvé ; la zone mucogingivale sans landmarks et sans superviseur pour atteindre ALI_IOS ; une hauteur négative ; Fully-Automated sans superviseur ou sans référence (ios/dispatch.py:100-139). Fully-Automated exige Crown_Seg et ASO pour les deux zones.

En mode Fully-Automated, les deux points temporels passent par deux appels chacun, dans cet ordre (ios/dispatch.py:168-183, ios/tools.py:83-130) :

t1 = sup.run("Crown_Seg", meshes=<T1 folder>, suffix="Seg" [, model=crown_model])
t2 = sup.run("Crown_Seg", meshes=<T2 folder>, suffix="Seg" [, model=crown_model])
t1 = sup.run("ASO", input=t1, reference=<IOS_Gold_files>, modality="IOS",
             automation="Fully-Automated", output_suffix="Or")
t2 = sup.run("ASO", input=t2, reference=..., modality="IOS", ...)
prior_transforms = _collect_transforms(t2, suffix="Or")    # upper arches only

Crown_Seg est laissé au défaut de skip_segmented, si bien qu'un maillage qui porte déjà des labels passe sans être touché (ios/tools.py:113-122) ; aucun device n'est envoyé. ASO est appelé avec ses défauts pour les dents et l'occlusion (voir les constats). _collect_transforms indexe par clé de patient les fichiers .tfm qu'ASO a écrits pour les arcades supérieures du T2 (ios/dispatch.py:257-279) ; ils sont composés dans la transformation écrite à la fin, de sorte qu'elle se rapporte au maillage que l'appelant a envoyé (3.6).

Pour la zone mucogingivale sans mgl_landmarks, on demande à ALI_IOS, pour le T1 et pour le T2, son seul réseau Mucogingival, et les deux résultats sont copiés dans un même dossier, .areg_work/mgl_predicted (ios/dispatch.py:213-229) :

sup.run("ALI_IOS", input=<folder>, networks=["Mucogingival"] [, model=mgl_model])

Nommer ce seul réseau évite qu'ALI exécute aussi ses passes occlusale et cervicale (ios/tools.py:140-145).

3.3 La zone palatine : le réseau à l'intérieur du moteur

Explication en langage courant et maths : page de l'atlas.

PatchPredictor est construit une fois par exécution, si bien que le checkpoint est chargé une seule fois pour tout le lot (ios/butterfly.py:96-107, ios/dispatch.py:199-206). Le périphérique est cuda quand une carte est visible, sinon cpu avec un avertissement (ios/butterfly.py:41-54) ; le rapport note le périphérique et le nom de fichier du checkpoint. Le checkpoint est l'unique .ckpt ou .pth trouvé sous le dossier du bundle ; zéro ou plusieurs sont refusés, en nommant les candidats (ios/butterfly.py:57-93). Il est chargé avec map_location réglé sur ce périphérique et doit contenir des poids model.* (ios/net.py:188-214).

Pour chaque maillage (ios/butterfly.py:109-141) :

  1. Trianguler si le maillage contient autre chose que des triangles, car le tenseur de faces est lu comme reshape(-1, 4), ce qui lit sinon de mauvais indices en silence (ios/postprocess.py:22-50).
  2. Orienter dans le repère canonique : les centroïdes des dents 3, 8, 9 et 14 (UR6, UR1, UL1, UL6 en numérotation Universal) sont alignés sur un triangle de référence fixe ; les deux incisives sont moyennées en un seul point milieu, si bien que le triangle a trois points (ios/orientation.py:29-30,111-146). Cela exige un tableau de labels de dents, Universal_ID, PredictedID ou UniversalID (ios/surfaces.py:39,103-110). En cas d'échec, la prédiction continue avec le maillage tel quel et une note est gardée pour le rapport (ios/butterfly.py:117-131). L'orientation ne sert qu'au rendu : le tableau de zone est écrit sur le maillage d'origine.
  3. Normaliser : centrer sur la boîte englobante, mettre à l'échelle dans la sphère unité, calculer les normales aux points ; les normales converties en RVB (n * 0.5 + 0.5) sont la seule texture que voit le réseau (ios/surfaces.py:159-192, ios/butterfly.py:169-190).
  4. Rendre et segmenter sept vues (ci-dessous), puis reporter par vote les probabilités par pixel sur les faces et les sommets.
  5. Nettoyer : les îlots de l'une ou l'autre classe de moins de 200 points sont absorbés par leur entourage, puis la zone est fermée, dilatation 2 puis érosion 2 (ios/postprocess.py:192-204).

Comme dans le legacy, chaque vue est rastérisée deux fois : une fois par le moteur de rendu avec le R et le T de la caméra, une fois par le seul rastériseur pour obtenir zbuf et pix_to_face (ios/net.py:171-172). Le vote (ios/butterfly.py:143-166) :

logits, _views, pixel_to_face = self.model((vertices, faces, colors))
probabilities = softmax(logits * (pixel_to_face >= 0), dim=2)
face_votes = torch.zeros(2, n_faces)
for view_faces, view_probabilities in zip(pixel_to_face, probabilities):   # 7 views
    hit = view_faces >= 0                       # background pixels left out
    face_votes[:, view_faces[hit]] += view_probabilities[:, hit]
face_labels = torch.argmax(face_votes, dim=0)
vertex_labels[faces[0, :, 0]] = face_labels      # first corner of each face
return (vertex_labels >= 1)

Deux défauts legacy sont corrigés : les pixels de fond (indice -1, qui adressait la dernière face) ne votent plus, et le périphérique n'est plus codé en dur sur CUDA (ios/butterfly.py:11-23). Deux sont conservés : les faces répétées dans une même vue ne s'accumulent pas, et seul le premier coin de chaque face reçoit le label ; voir les constats. Le résultat est le tableau de points Butterfly, 0 ou 1 (ios/butterfly.py:39,138-141).

3.4 La bande mucogingivale

Explication en langage courant et maths : page de l'atlas.

Sur l'arcade inférieure il n'y a pas de plateau, donc la zone est construite à partir des 13 landmarks qu'ALI place le long de la ligne mucogingivale, LL6MG à LR6MG en passant par L0MG, ou les mêmes noms sans MG (ios/mgl.py:46-52). Elle n'a besoin ni de réseau ni de GPU (ios/mgl.py:15-18). Les fichiers de landmarks sont des markups Slicer (.json, .mrk.json) ; chaque scan trouve son fichier par une clé qui garde le point temporel, par égalité ou préfixe de jetons, et une ambiguïté est une erreur qui nomme les candidats (ios/landmarks.py:68-160, ios/pipeline.py:136-157).

build_patch (ios/mgl.py:182-239):

  1. ordonner les landmarks le long de l'arcade ; il en faut au moins 3, les manquants sont notés (ios/mgl.py:79-96) ;
  2. avec une hauteur de 0 : accrocher les landmarks eux-mêmes à leurs sommets les plus proches, et s'arrêter là, ni courbe ni bande (ios/mgl.py:204-207) ;
  3. sinon : échantillonner une spline paramétrique qui les traverse en 300 points (vtkParametricSpline, qui passe par ses points ; seule la docstring la qualifie de B-spline, ios/mgl.py:99-115), accrocher chaque échantillon à son sommet le plus proche, et faire croître une bande autour de ces germes par Dijkstra, jusqu'à height mm de chaque côté (une demi-hauteur, ios/mgl.py:59), mesurée le long des arêtes du maillage, jamais à travers l'espace, si bien que la bande ne peut pas sauter du côté lingual (ios/mgl.py:99-163,208-210) ;
  4. retirer les sommets qui portent un label de couronne inférieure, 18 à 31, si le maillage est étiqueté (ios/mgl.py:72,166-179,212-216) ;
  5. écrire le résultat comme tableau de points Bottom_MGL ; une bande vide est une erreur pour ce patient (ios/mgl.py:57,218-227).

Chaque point temporel construit sa bande à partir de ses propres landmarks ; la restriction legacy aux landmarks communs aux deux temps, le filtre sur les landmarks douteux et le départ de l'ICP à partir des landmarks ne sont pas dans le port (section 7).

3.5 L'ICP

Explication en langage courant et maths : page de l'atlas.

La zone est prédite sur chaque point temporel (ios/pipeline.py:192-193), puis l'ICP s'exécute sur les deux nuages de zone, T2 sur T1 (ios/pipeline.py:195-198). patch_cloud transforme chaque maillage peint en un nuage de sommets seuls, les points dont la valeur du tableau est 1, et refuse un nuage vide (ios/butterfly.py:193-224). icp.align exécute ensuite le même filtre vtk que le legacy :

icp = vtk.vtkIterativeClosestPointTransform()
icp.SetSource(t2_patch); icp.SetTarget(t1_patch)
icp.GetLandmarkTransform().SetModeToRigidBody()     # 6 degrees of freedom
icp.SetMaximumNumberOfIterations(1000)
icp.StartByMatchingCentroidsOn()

Une matrice contenant une entrée non finie est refusée (ios/icp.py:36-56). Le vtkICP.__call__ legacy renvoyait sa source sans la déplacer, sans conséquence avec une seule méthode ; le port a un seul alignement et aucune liste à composer (ios/icp.py:8-14). La matrice déplace les points du maillage T2 sur le T1 ; tout le maillage T2, pas seulement sa zone, est transformé avec elle (ios/pipeline.py:206).

3.6 Sorties, transformation et rapport

Explication en langage courant et maths : page de l'atlas.

L'outil renvoie un seul chemin, il n'y a donc pas de sorties nommées : le dossier de sortie est archivé. Sous le dossier relatif de chaque patient (ios/pipeline.py:200-233,253-258) :

<output_dir>/<relative folder>/
    <T1 stem>_<suffix>.vtk|.vtp       # T1, carrying Butterfly or Bottom_MGL
    <T2 stem>_<suffix>.vtk|.vtp       # T2 moved onto T1, patch array too
    <other arch T1>_<suffix>           # palate only: untouched copy
    <other arch T2>_<suffix>           # palate only: moved by the same matrix
    <patient>_<suffix>_transform.tfm
AREG_report.json

Une entrée .vtp reste .vtp ; tout le reste est écrit en .vtk legacy binaire, puisque .stl ne peut pas contenir le tableau de labels (ios/surfaces.py:79-100). Le nom sans extension est celui du fichier réellement recalé, qui en mode Fully-Automated est la copie étiquetée et orientée (ios/pipeline.py:253-258). Avec la zone mucogingivale, seule l'arcade inférieure est écrite : l'arcade supérieure n'est pas reportée (ios/pipeline.py:13-17).

La transformation (ios/icp.py:88-112). La matrice ICP déplace des points ; un .tfm est consommé dans l'autre sens, donc l'inverse est écrite, comme le fait le moteur CBCT. Quand ASO a d'abord orienté les maillages, la transformation d'ASO pour l'arcade supérieure du T2 est composée, matrix @ inv(prior), si bien que le fichier relie le maillage envoyé par l'appelant au résultat recalé ; matrix_of lit la transformation d'ASO avec son centre de rotation (ios/icp.py:63-85). Le rapport dit quel cas s'applique (ios/pipeline.py:240-244).

AREG_report.json (ios/dispatch.py:155-232,376-381,410-412, ios/pipeline.py:235-250):

8. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

La hauteur de patch par défaut est 0, ce qui veut dire aucune bande

run() publie mgl_patch_height: float = 0.0 et le documente comme « 0 utilise la valeur par défaut du moteur » (SADT-VISOR ios/__init__.py:36,65-66). Le code fait l'inverse : seul None est remplacé par la valeur par défaut de 5,0 mm (ios/dispatch.py:395-397), et une hauteur de 0 ne construit ni courbe ni bande, seulement les landmarks ramenés sur le maillage, que l'ICP utilise alors seuls (ios/mgl.py:196-211 ; le contrôle dit « 0 registers on the landmarks alone, without any band », ios/dispatch.py:119-123). Observé : appeler run() avec le patch mucogingival et sans hauteur transmet au moteur (_run_ios, remplacé par une doublure) mgl_patch_height = 0.0, dans l'environnement de l'outil. Un recalage mucogingival lancé avec les valeurs par défaut du panneau se fait donc sur environ 13 points, et non sur une bande de 5 mm. Le rapport l'indique (mgl_patch_height_mm, ios/dispatch.py:232) ; le panneau non. Legacy : valeur par défaut 5,0 (AREG/AREG.py:42-44,870-882).

Le portage MGL est en retard sur le legacy à 3c67957

Trois étapes que le module legacy possède à 3c67957 sont absentes de VISOR (grep sur tools/AREG/AREG_IOS/src, observé) : le filtre des landmarks douteux, la restriction aux landmarks communs aux deux temps, et le départ de l'ICP à partir des landmarks ; voir Ce qui a changé par rapport à la logique legacy. Les dents inférieures tenues hors de la bande vont de 18 à 31 dans VISOR contre 17 à 32 dans le legacy, et le commentaire de VISOR appelle sa plage celle d'upstream, « verbatim » (ios/mgl.py:66-72), ce que 3c67957 contredit (mgl_patch.py:47-55, où 17 et 32 sont listées exprès). La chronologie des deux historiques n'a pas été établie : il peut donc s'agir d'un portage d'une version antérieure.

Les faces en double perdent des votes dans le réseau du palais

Dans face_votes[:, view_faces[hit]] += view_probabilities[:, hit] (ios/butterfly.py:157), une addition indexée n'accumule pas les indices répétés. Observé avec torch dans l'environnement de l'outil : ajouter des uns trois fois à la même colonne dans une seule opération indexée laisse 1. Le legacy a la même accumulation (AREG_IOS/AREG_IOS_utils/PredPatch.py:59-60) ; VISOR a corrigé les pixels de fond, mais pas ceci. Le vote n'est ensuite écrit que sur le premier coin de chaque face (ios/butterfly.py:161-166), ce qui explique que le patch ait des trous que la fermeture morphologique répare (ios/postprocess.py:192-204).

Fully-Automated oriente chaque mâchoire séparément

L'appel à ASO n'envoie aucun ios_occlusion (ios/tools.py:96-102), et la valeur par défaut d'ASO est « Orient each jaw independently » (SADT-VISOR tools/ASO/src/sadt_aso/__init__.py:63-65). Le recalage déplace ensuite l'autre arcade avec la matrice de l'arcade recalée « so the captured occlusion survives » (ios/pipeline.py:13-15,209-224), mais si les deux mâchoires ont été orientées séparément, l'occlusion capturée dans le scan n'est pas ce qui est transporté. Le legacy passait occlusion = "true" quand le dossier contenait des arcades inférieures (AREG/AREG_Method/IOS.py:621,633). Lu dans le code ; aucune exécution n'a comparé les deux sorties, l'ampleur de l'effet est donc inconnue.

Aucun maximum sur la hauteur de patch

Le contrôle refuse une hauteur négative et rien d'autre (ios/dispatch.py:119-123). Le widget legacy gardait la valeur dans [0, 20] mm (AREG/AREG.py:42-44,870-882). Lu dans le code.

Le dossier de travail temporaire n'est pas supprimé quand une exécution échoue

register supprime .areg_work/ après le retour du moteur, sans try/finally (ios/dispatch.py:348-413, shutil.rmtree à la ligne 408 ; le moteur s'exécute aux lignes 385-403). Une exception non rattrapée par patient laisserait les copies des entrées et les maillages étiquetés et orientés dans le dossier de sortie archivé. AREG_IOSCBCT a le finally. Lu dans le code ; non déclenché.

Une orientation échouée est écrite dans le rapport

Le patch est quand même prédit, mais notes dans l'entrée du patient indique qu'il a été prédit sans l'orientation canonique, avec la raison (ios/butterfly.py:117-131, ios/pipeline.py:247-249). Lu dans le code.

Une transformation est toujours écrite

Chaque patient recalé obtient un .tfm, dans les deux modes et pour les deux patchs, avec une phrase dans le rapport qui dit dans quel sens elle applique (ios/pipeline.py:226-244). Lu dans le code.

Crown_Seg ne reçoit pas le périphérique à utiliser

label_crowns n'envoie que meshes, suffix et un model facultatif (ios/tools.py:124-130). Crown_Seg utilise alors sa propre valeur par défaut, avec le réglage de périphérique du serveur appliqué quand l'appelant n'en nomme aucun, et se rabat sur le CPU avec un avertissement quand aucune carte n'est visible ; voir Crown_Seg sur VISOR. Ce n'est pas une faute, c'est une asymétrie avec ALI_IOS, qui transmet son périphérique. Lu dans le code.
