MedicalDataAnonymizer : non porté sur VISOR

Il n'existe aucun Medical Data Anonymizer côté serveur. L'extension cliente VISOR embarque une ancienne copie du module legacy, qui s'exécute dans Slicer sur des documents texte, et qui ne dépersonnalise pas les fichiers que VISOR envoie. Le module lui-même est décrit sur sa page legacy.

VISOR : copie locale seulement Page legacy Guide (VISOR)

État aux commits de référence : SADT-VISOR 6ba2a78, VISOR-serve e9a7e5d, AutomatedDentalToolsRemote 19b95e8 ; legacy désigne SlicerAutomatedDentalTools à 3c67957. MDA-Remote ci-dessous désigne AutomatedDentalToolsRemote Medical_Data_Anonymizer_ModuleRemote/Medical_Data_Anonymizer_ModuleRemote.py. Tout a été lu dans le code ; rien n'a été exécuté.

Ce qui tourne où

Tout s'exécute dans le processus Slicer, comme dans le module legacy : install_dependencies installe par pip presidio-analyzer, presidio-anonymizer, pandas, python-docx, pdfplumber, odfpy, lxml, langdetect et reportlab dans le Python de Slicer, puis télécharge le modèle spaCy en_core_web_lg (MDA-Remote:392-441). Rien n'est envoyé à un serveur et rien n'est hébergé.

En quoi la copie diffère du module legacy

La copie livrée est une révision plus ancienne du module, non un portage : 768 lignes contre 774 dans le fichier legacy à 3c67957 (Medical_Data_Anonymizer_Module/Medical_Data_Anonymizer_Module.py). Depuis, le fichier legacy est passé à ADTLib.logging_setup au lieu d'un journal local, a donné au widget un objet Logic séparé, et a renommé des variables. La catégorie de module de la copie est « Automated Dental Tools Remote » au lieu de « Automated Dental Tools » (MDA-Remote:41). La logique de détection est la même dans les deux : les constats de la page legacy sur la langue fixe, le fichier de correspondance et l'échec silencieux valent pour la copie, à ces lignes.

Ce n'est pas la dépersonnalisation de ce que VISOR envoie

Ce module anonymise les documents texte que vous lui indiquez. Il n'est placé sur le chemin d'envoi d'aucun autre panneau, et aucun code de ServerToolsCore, SlicerCloud ou ServerToolsSettings ne mentionne Presidio ni l'anonymisation. Le README du client indique qu'il n'y a aucune dépersonnalisation dans le client actuel : les fichiers sont transmis en flux « as they are on disk, with their names, their DICOM headers and whatever identifiers they contain » (README.md:32-35), et le client affiche le même avertissement une fois pour chaque serveur distant, « Files are uploaded unmodified » (ServerToolsCore/ServerToolsCoreLib/settings_qt.py:101-127). Le pipeline qui dépersonnaliserait les envois est spécifié et non implémenté : lisez La dépersonnalisation dans VISOR avant de tenir un module pour une garantie sur les données envoyées.
