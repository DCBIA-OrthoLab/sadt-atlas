AREG_IOSCBCT sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR d'AREG_IOSCBCT dans le code, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. Le module legacy a sa propre page de code.

VISOR Code Atlas (explication) AREG_IOSCBCT accessible comme AREG, mode IOS to CBCT pas de torch, géométrie pure Page legacy Guide (VISOR) Bibliographie

AREG_IOSCBCT place un scan intraoral dans le repère d'un CBCT du même patient, pris lors de la même visite : un ajustement rigide sur des landmarks que les deux côtés partagent, puis un ICP du maillage contre une surface contourée à partir du CBCT. Dans VISOR, tout le calcul s'exécute sur un serveur, et les landmarks, quand vous ne les envoyez pas, viennent d'autres outils que le serveur appelle ; Slicer ne fait que montrer le formulaire, envoyer les dossiers et ouvrir ce qui revient. Cette page décrit ce portage, lu à SADT-VISOR 6ba2a78 (branche tool/vface), VISOR-serve e9a7e5d et AutomatedDentalToolsRemote 19b95e8. Le module legacy auquel il est comparé est SlicerAutomatedDentalTools 3c67957, décrit sur sa propre page ; les chemins legacy ci-dessous sont à ce commit, et AREG_IOSCBCT.py est AREG_IOSCBCT/AREG_IOSCBCT.py à cet endroit.

Abréviations utilisées sur cette page : ioscbct/ est SADT-VISOR tools/AREG/AREG_IOSCBCT/src/sadt_areg_ioscbct/, common/ est SADT-VISOR tools/AREG/common/src/sadt_areg_common/, et les chemins server/ sont dans VISOR-serve. « Observé » marque ce qui a été exécuté (tests, scripts/describe.py, courtes sondes Python lancées avec l'environnement propre de l'outil sur les fichiers de test publiés) ; tout le reste a été lu dans le code.

1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

Un client envoie AREG avec mode = "IOS to CBCT", et le serveur remplace la façade par ce moteur. Le moteur n'a pas de réseau propre et n'importe ni torch ni pytorch3d (ioscbct/__init__.py:9-14) : étiquettes de dents, landmarks et orientation sont tous demandés à d'autres outils, et ce qui reste dans le moteur est de la géométrie.

3.1 Les appels supervisés

Explication en langage courant et maths : page de l'atlas.

Le mode est vérifié en premier ; Registration est le défaut, et le seul qui n'a besoin d'aucun autre outil (ioscbct/__init__.py:46-48, ioscbct/dispatch.py:283-288). Dans les deux autres modes, main refuse aussitôt quand Crown_Seg, ALI_IOS et ALI_CBCT, plus ASO pour Fully-Automated, sont injoignables, et résout la référence d'orientation en DATA/AREG/models/CBCT_Gold_Frankfurt_Horizontal_Midsagittal_Plane quand aucune n'est nommée (ioscbct/dispatch.py:190-199,311-331). Puis, dans cet ordre (ioscbct/dispatch.py:332-339, ioscbct/tools.py:102-177) :

cbct = sup.run("ASO", input=cbct, reference=<Frankfurt>,          # Fully only
               modality="CBCT", automation="Fully-Automated" [, landmark_model])
ios  = sup.run("Crown_Seg", meshes=ios, suffix="Seg" [, model=crown_model])
ios_lm  = sup.run("ALI_IOS", input=ios, networks=["Occlusal"])          # unless sent
cbct_lm = sup.run("ALI_CBCT", input=cbct,
                  landmarks=["UR1O","UR3O","UR6O","UL1O","UL3O","UL6O",
                             "LR1O","LR3O","LR6O","LL1O","LL3O","LL6O"])   # unless sent

ALI_CBCT reçoit la demande de ces douze points par leur nom, et non par région, car une demande par région exécuterait tous les agents de toutes les régions qui en contiennent un (ioscbct/tools.py:122-137) ; ALI_IOS est sollicité pour son seul réseau occlusal (ioscbct/tools.py:140-156). Les maillages intraoraux sont étiquetés mais non orientés : ASO n'est appelé que sur le CBCT. Les jalons de progression sont 0,1, 0,3 et 0,5, et le recalage démarre à 0,6 (ioscbct/tools.py:129-130,148-149,167-168, ioscbct/dispatch.py:355).

3.2 Apparier les deux modalités

Explication en langage courant et maths : page de l'atlas.

Les deux modalités sont nommées selon des conventions différentes, donc patient_key ne garde que ce qu'elles partagent, les chiffres : les jetons de temps t0 t1 t2 sont retirés, puis tout caractère non numérique, puis les zéros de tête, de sorte que P001_T2_U.vtk et P_0001_T2.nii.gz donnent tous deux la clé 1 (ioscbct/pipeline.py:30-52). discover parcourt les deux dossiers dans l'ordre trié, garde tous les maillages (.vtk, .stl) d'une clé et le premier CBCT d'une clé, et signale une clé présente d'un seul côté (ioscbct/pipeline.py:55-106). La grossièreté de cette clé est le premier constat.

Les fichiers de landmarks sont lus comme des markups Slicer, ou comme un simple objet {label: [x, y, z]} (ioscbct/pipeline.py:109-133), indexés par leur chemin relatif au dossier (ioscbct/dispatch.py:87-108), restreints à la clé du patient (:111-135), et appariés à un maillage par son jeton de mâchoire (u upper l lower) ; un fichier unique sans jeton de mâchoire, ce qu'ALI_CBCT écrit pour un CBCT entier, sert les deux arcades, les étiquettes elles-mêmes (UR1O contre LR1O) les séparant (ioscbct/dispatch.py:138-175).

3.3 La surface du CBCT, et le niveau auquel elle est contourée

Explication en langage courant et maths : page de l'atlas.

Une fois par patient, tous les landmarks CBCT du patient fusionnés, volume.read lit le volume et renvoie la surface contourée et un verdict sur chaque landmark (ioscbct/dispatch.py:57-84, ioscbct/volume.py:148-175) :

array = sitk.GetArrayFromImage(image)
ijk_to_lps[:3, :3] = direction @ diag(spacing);  ijk_to_lps[:3, 3] = origin
level = surface_threshold(array, ijk_to_lps, landmark_positions)
on_enamel = landmarks_on_enamel(array, ijk_to_lps, landmarks, level)
surface = pv.wrap(array.transpose(2, 1, 0)).contour(isosurfaces=[level])
return surface.transform(ijk_to_lps, inplace=False), on_enamel

Le niveau est lu sur le scan, avec la même règle que le legacy à 3c67957 (ioscbct/volume.py:96-117) :

  • le plateau d'émail est la médiane, sur les landmarks CBCT, du voxel le plus brillant à moins de 2 voxels de chacun (PROBE_RADIUS_VOXELS = 2, ioscbct/volume.py:27,46-60,77-79,91) ;
  • le pourtour est la médiane des voxels compris entre -300 et 300 HU dans la boîte que couvrent les landmarks (SOFT_TISSUE_BAND, ioscbct/volume.py:32,85-92) ;
  • le niveau est à mi-chemin entre les deux ; 400 n'est que la valeur de repli, utilisée quand aucun landmark ne tombe dans le scan ou quand les couronnes ne sont pas plus brillantes que leur pourtour (FALLBACK_LEVEL = 400.0, ioscbct/volume.py:36,105-112) ;
  • un argument level explicite l'emporterait, mais aucun appelant n'en passe (ioscbct/volume.py:101-103, ioscbct/dispatch.py:77).

Observé sur le scan de test publié (P_0001_T2_Or.nii.gz et ses 12 landmarks CBCT, les fichiers dont est construit le visualiseur ci-dessous, passés dans volume.surface_threshold et volume.landmarks_on_enamel dans l'environnement de l'outil) : émail 2783, pourtour 146, niveau 1464, bien au-dessus du repli de 400 ; et UL3O lit 274 au plus brillant, sous le niveau, il est donc jugé ne pas reposer sur une dent.

Le même niveau juge ensuite chaque landmark : celui dont le voisinage ne l'atteint jamais n'est pas sur l'émail, ce qui, dans une occlusion fermée, signifie en général que le réseau l'a posé sur l'arcade antagoniste (ioscbct/volume.py:120-145). Le contour prend l'os et l'émail indistinctement au-dessus de ce niveau ; la transposition remet le tableau (k, j, i) de SimpleITK dans l'ordre (i, j, k) de pyvista, et ijk_to_lps ramène la surface en LPS, le repère que les deux outils ALI écrivent (ioscbct/volume.py:161-175).

3.4 L'ajustement sur les landmarks

Explication en langage courant et maths : page de l'atlas.

shared_landmarks intersecte les deux ensembles d'étiquettes, refuse moins de 3 étiquettes communes et signale les étiquettes écartées (ioscbct/pipeline.py:136-155). align_by_landmarks est l'ajustement rigide en forme fermée de vtkLandmarkTransform en mode RigidBody, IOS comme source et CBCT comme cible, et il lève une erreur sur des ensembles de tailles différentes au lieu de renvoyer l'identité (ioscbct/geometry.py:34-74). Autour, fit_rigid_without_outliers et prealign décident quelles paires comptent et si le résultat est accepté (ioscbct/geometry.py:168-321) :

RègleConstanteEffet
Moins de 3 pairesMIN_LANDMARK_PAIRS = 3identité, accepted: false, raison « too few pairs » (:289-294) ; atteignable seulement quand prealign est appelé seul, car via register_one l'étape d'appariement lève déjà ToolInputError sous 3 étiquettes communes (pipeline.py:145-149)
Landmark hors émailverdict de la 3.3écarté avant tout ajustement, pourvu qu'il reste 3 paires (:229-242)
Élagage des valeurs aberrantesLANDMARK_OUTLIER_FLOOR_MM = 3.0, LANDMARK_OUTLIER_IMPROVEMENT = 0.75, MIN_LANDMARK_PAIRS_AFTER_TRIM = 4une paire par tour : la paire dont le retrait donne le meilleur ajustement est écartée si elle est à plus de 3 mm et si l'ajustement sans elle vaut au plus 75 % du résidu ; jamais sous 4 paires (:244-275)
Résidu trop grandMAX_LANDMARK_RESIDUAL_MM = 10.0identité, accepted: false, raison « residual too large » (:301-307)
Landmarks presque alignésMIN_LANDMARK_SPREAD_RATIO = 0.10avertissement seulement ; la dispersion va dans le rapport (:199-209,309-321)

Un pré-alignement refusé n'est pas une erreur : l'ICP part alors de la pose que l'orientation a laissée, l'identité (ioscbct/geometry.py:278-285).

3.5 L'ICP

Explication en langage courant et maths : page de l'atlas.

register_one rogne la surface du CBCT à la boîte des landmarks CBCT de l'arcade plus 25 mm, déplace le maillage par le pré-alignement, puis exécute icp_point_to_plane (ioscbct/pipeline.py:158-212, ioscbct/geometry.py:395-450) :

  • points qui pilotent l'ajustement : les couronnes seulement (toute l'arcade, gencive comprise, se déplace quand même par la matrice qu'elles fixent, ioscbct/geometry.py:623-624), quand le maillage porte Universal_ID et que au moins 10 % de lui est de la couronne ; les étiquettes 0 et 33 sont de la gencive, qui n'a pas d'équivalent dans un CBCT (GINGIVA_LABELS, MIN_CROWN_SHARE, ioscbct/geometry.py:368-372,453-476) ;
  • correspondances : point CBCT le plus proche à moins de ICP_MAX_DIST_MM = 1.0, dont la normale s'accorde à celle du maillage à plus de 0,5, ce qui écarte l'arcade antagoniste en occlusion fermée (:338,343,543-555) ;
  • pas : point-à-plan, linéarisé en la rotation, résolu par moindres carrés ; un système de rang déficient ou une rotation de plus de 0,5 rad se rabat sur un pas de Procrustes point-à-point (:479-521,571-577) ;
  • arrêt : après 300 itérations, ou dès que le plus grand déplacement reste sous 0,001 mm pendant 3 itérations (:346-348,585-586) ;
  • signe des normales : l'exécution est faite avec les normales du CBCT lues dans les deux sens, et la lecture qui a la meilleure fitness, puis la plus faible RMSE, est conservée (:600-651) ;
  • plancher : un ICP qui a apparié moins de 5 % de l'arcade est une erreur pour ce maillage, de sorte qu'un maillage non recalé n'est jamais écrit sous un nom de maillage recalé (MIN_ICP_FITNESS = 0.05, ioscbct/pipeline.py:192-202) ;
  • dérive : la RMS des landmarks ajustés avant et après l'ICP va dans le rapport, avec un avertissement au-dessus de 1 mm (ioscbct/pipeline.py:215-244).

La matrice finale est refinement @ matrix, l'ICP composé après l'ajustement sur landmarks (ioscbct/pipeline.py:212). Sans surface (le volume n'a pas pu être contouré), le maillage est placé sur ses seuls landmarks et icp reste null dans le rapport (ioscbct/pipeline.py:184-185).

8. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Des patients et des temps qui ne diffèrent que par des lettres sont fusionnés

patient_key garde les chiffres et rien d'autre (ioscbct/pipeline.py:30-52). Observé à 6ba2a78 : A12_T1_Upper.vtk, B12_T1_Upper.vtk et P1_visit2_U.vtk donnent tous '12', tandis que P001_T2_U.vtk et P_0001_T2.nii.gz donnent tous deux '1', ce qui est voulu. Avec quatre maillages P001_T1_{U,L}.vtk et P001_T2_{U,L}.vtk à côté de trois CBCT P_0001_T1.nii.gz, P_0001_T2.nii.gz et Q001_T1.nii.gz, discover a renvoyé un seul patient '1' contenant les quatre maillages et le premier CBCT dans l'ordre de tri, et un unpaired vide : les deux autres CBCT ont disparu sans être signalés (setdefault, ioscbct/pipeline.py:74,81). Les fichiers de landmarks sont restreints à la clé du patient, puis appariés à un maillage par le seul jeton de mâchoire, le premier dans l'ordre de tri l'emportant : observé, l'ensemble de landmarks choisi pour P001_T2_L.vtk parmi P001_T1_L et P001_T2_L était celui de T1 (_for_patient et _match_landmarks, ioscbct/dispatch.py:111-175). L'outil est documenté comme non longitudinal (ioscbct/__init__.py:3-7) mais rien ne l'impose ni ne le signale.

Le niveau de l'isosurface ne peut plus être fixé

Le legacy acceptait AREG_CBCT_SURFACE_THRESHOLD (AREG_IOSCBCT.py:92,943-950@3c67957). VISOR garde la règle et la valeur de repli de 400, et l'avertissement qu'il journalise en se repliant conseille de « pass a level explicitly » (ioscbct/volume.py:96-112), mais le seul appelant ne le fait jamais : volume.read(scan_path, merged) (ioscbct/dispatch.py:77) et run() n'a pas un tel argument. Lu dans le code.

Sur le scan de test publié, le niveau est 1464, pas 400

Observé avec les propres fonctions de l'outil sur P_0001_T2_Or.nii.gz et ses 12 landmarks CBCT : émail 2783, tissu mou 146, niveau 1464 (ioscbct/volume.py:96-117). À ce niveau, UL3O (le plus brillant 274) est jugé hors émail, et l'ajustement sur landmarks de l'arcade supérieure se fait sans lui (ioscbct/geometry.py:229-236). « 400 » n'est donc que ce que VISOR utilise quand il ne peut pas lire un scan, et la surface que tout schéma dessine à 400 n'est pas celle sur laquelle l'ICP de VISOR recale. Le visualiseur en 3.4 le dit.

La documentation de max_dist est fausse

La docstring dit que 0 utilise 1,5, « which is upstream's » (ioscbct/__init__.py:83-85). Le code utilise ICP_MAX_DIST_MM = 1.0 (ioscbct/dispatch.py:352, ioscbct/geometry.py:338), avec un commentaire disant que la signature d'upstream dit 1,5 et que chaque site d'appel passe 1,0 (ioscbct/geometry.py:335-338). DEFAULT_MAX_DIST = 1.5 est le défaut de icp_point_to_point seule (ioscbct/geometry.py:25,77-78), une fonction qu'aucun module du moteur n'appelle (grep : seul tests/test_geometry.py le fait) ; le repli que l'ICP utilise réellement est _point_to_point_step, qui ne prend aucune distance (ioscbct/geometry.py:509-521,576-577). Le champ est masqué dans le panneau (ioscbct/layout.py:84), la phrase fausse n'atteint donc que les utilisateurs de l'API.

Un estimateur conservé décrit un upstream qui n'existe plus

La docstring de icp_point_to_point dit qu'elle a été renommée depuis le run_icp_point_to_plane d'upstream parce que cette fonction calcule du point-à-point (ioscbct/geometry.py:81-86), et le commentaire au-dessus des constantes de l'ICP dit qu'elle est gardée comme repli pour un système dégénéré (ioscbct/geometry.py:331-334). À 3c67957, le run_icp_point_to_plane d'upstream a un vrai pas point-à-plan (AREG_IOSCBCT.py:579-608,719), et dans VISOR le cas dégénéré se rabat sur _point_to_point_step, pas sur cette fonction. Sans conséquence, mais trompeur pour qui compare les deux bases de code. Lu dans le code.

Le verdict du pré-alignement est une donnée, pas une ligne de journal

Chaque maillage porte prealignment (accepté ou non, pourquoi, landmarks ajustés, résidu, dispersion) et les statistiques de l'ICP, dont la dérive des landmarks avant et après (ioscbct/pipeline.py:158-212). Un volume qui ne peut pas être contouré n'arrête pas l'exécution : les maillages sont placés sur leurs landmarks et le rapport dit que l'ICP n'a pas tourné (ioscbct/dispatch.py:57-84). Lu dans le code.

Le dossier de travail temporaire est toujours supprimé

Contrairement à AREG_CBCT et AREG_IOS, le moteur enveloppe son travail dans un try/finally qui supprime .areg_work/ (ioscbct/dispatch.py:306-358). Lu dans le code.
