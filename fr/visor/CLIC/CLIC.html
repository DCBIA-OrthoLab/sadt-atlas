CLIC sur VISOR

CLIC trouve les canines incluses sur un CBCT et dit si chacune se trouve côté joue, côté palais ou à cheval sur l'os. Cette page explique comment, pas à pas, avec les maths : ce qui entre, ce que chaque étape en fait et ce qui sort. Les fichiers, les lignes, les arguments et les constatations sont sur la page de code. Le module Slicer legacy a sa propre page.

Quand cette page nomme un dépôt, il s'agit du catalogue d'outils SADT-VISOR à 6ba2a78, du serveur VISOR-serve à e9a7e5d, du client Slicer AutomatedDentalToolsRemote à 19b95e8 et du module legacy SlicerAutomatedDentalTools à 3c67957. Les noms de fichiers, les numéros de ligne et toutes les constatations sont sur la page de code. Tout ici a été lu dans le code ; rien n'a été exécuté pour cette page.

Vue d'ensemble : ce qui entre, ce qui sort

CLIC cherche des canines incluses dans un scan CBCT. Il ne regarde pas tout le volume d'un coup : il lit le scan coupe par coupe, et sur chaque coupe un réseau entraîné dessine le contour des canines qu'il trouve et, dans la même passe, dit où chacune se situe par rapport à l'os : côté joue (buccale), côté palais (palatine) ou à cheval sur l'os (bicorticale). Il y a un seul réseau et aucun classifieur séparé : le contour et la classe sortent ensemble.

CLIC sur VISOR
Entréeun CBCT au format NIfTI (.nii ou .nii.gz), ou un dossier de CBCT, parcouru récursivement
Méthodepar coupe : remettre à l'échelle les niveaux de gris, donner la coupe à un Mask R-CNN, garder les détections sûres, les peindre dans un volume d'étiquettes
Sortieune carte d'étiquettes par scan, sur la même grille que le scan : 0 est le fond, 1 buccale, 2 bicorticale, 3 palatine ; plus CLIC_report.json, un résumé de ce qui a été trouvé et de ce qui a échoué
Oùsur le serveur uniquement ; le panneau Slicer envoie les scans et charge les cartes d'étiquettes

Le réseau et la méthode coupe par coupe sont ceux du legacy ; rien n'est réentraîné. Ce qui a changé, c'est la façon de trouver les scans, de choisir le fichier de poids, de nommer les sorties et de traiter un scan en échec (Ce qui a changé).

1. Situation dans la chaîne

CLIC est autonome. Aucun autre outil ne prépare son entrée et aucun autre outil ne lit sa sortie, donc on peut l'exécuter sur n'importe quel CBCT NIfTI, quoi qu'on lui ait fait subir avant. Dans VISOR, le panneau de Slicer est généré à partir de la description de l'outil par le serveur ; il envoie les scans, attend, et télécharge une archive avec les cartes d'étiquettes et le rapport. L'outil est couvert par des tests automatiques dans son dépôt (non exécutés pour cette page) ; savoir si un serveur donné l'exécute, cette page ne peut pas le dire.

Dans le codeNom d'API, poids hébergés, ce que déclare le schéma, qui appelle qui

1.1 Ce qui s'exécute où

Le serveur fait tout ce qui compte : il lit les scans, exécute le réseau sur la carte graphique quand il y en a une, applique les seuils et écrit les fichiers. Le côté Slicer se contente de choisir les scans et un dossier de sortie, d'afficher la progression, de décompresser l'archive et, si on le demande, d'afficher jusqu'à douze cartes d'étiquettes avec un préréglage de rendu volumique. Le rapport est écrit par le serveur, mais le panneau ne l'affiche pas.

2. Fichiers en jeu

L'outil est petit : un fichier principal qui organise une exécution, un qui contient le traitement d'image, une table de noms et de couleurs de classes, et un écrivain de progression. Le panneau client fait environ quatre-vingts lignes. Les lignes et les tests sont listés sur la page de code.

Dans le codeLa table des fichiers avec le nombre de lignes, et les autres dépôts concernés

3. Le pipeline

Une exécution a quatre niveaux : une fois par exécution, l'outil trouve les scans et charge le réseau ; une fois par scan, il lit le volume ; une fois par coupe, il prépare l'image, exécute le réseau et peint le résultat ; à la fin, il écrit les fichiers. Cliquez sur une boîte pour lire sa section.

Dans le codeLa fonction derrière chaque boîte du schéma

3.1 Trouver les scans

Un fichier seul est utilisé tel quel. Un dossier est parcouru récursivement ; les fichiers cachés sont ignorés et seuls les noms finissant par .nii ou .nii.gz sont gardés. L'ancien module laissait aussi passer d'autres formats que le code de son réseau ne savait pas lire ; celui-ci les refuse d'emblée, avec un message. Si rien n'est trouvé, la requête est refusée avec une erreur lisible.

Dans le codeLes extensions, le parcours, l'erreur levée quand rien n'est trouvé

3.2 Choisir et charger le checkpoint

Le fichier de poids n'est pas choisi par l'utilisateur. Quand aucun n'est nommé, l'outil prend l'unique .pth de son dossier de modèles sur le serveur ; zéro ou plusieurs fichiers est un refus qui nomme les candidats, pour qu'un second fichier égaré ne puisse pas changer les résultats en silence. Le réseau est un Mask R-CNN : un backbone ResNet-50 avec une pyramide de caractéristiques regarde l'image, propose des régions candidates, et pour chaque région prédit une classe, une boîte et un masque. Le nombre de classes n'est pas supposé mais lu dans le fichier de poids, et les couches de sortie sont construites à cette taille avant le chargement des poids. Les poids publiés ont quatre classes : le fond et les trois positions de la canine.

Les poids sont chargés dans un mode qui ne peut pas exécuter de code embarqué dans le fichier. Si une carte graphique est visible, le réseau s'exécute dessus ; sinon il se rabat sur le processeur, avec un avertissement.

Dans le codeLes règles du checkpoint, le nombre de classes, l'appel de chargement et le choix du périphérique

3.3 La boucle sur les tranches

Chaque scan est lu comme une pile de nombres et découpé selon son troisième axe de tableau, dans l'ordre stocké dans le fichier ; l'outil ne réoriente pas le scan. Un volume qui n'est pas tridimensionnel fait échouer ce scan seulement.

Avant le réseau, chaque coupe est remise à l'échelle et copiée sur trois canaux identiques (le réseau a été conçu pour des images en couleur). À l'intérieur du réseau, l'image est aussi agrandie pour que son petit côté mesure 800 pixels, et standardisée avec la moyenne et l'écart d'ImageNet ; c'est torchvision qui s'en charge, l'outil n'y fait rien.

Comme chaque coupe est remise à l'échelle isolément, une coupe presque vide est étirée sur toute la plage tout comme une coupe d'os : le réseau ne voit jamais de valeurs absolues en unités Hounsfield. C'est le comportement du legacy, conservé.

Chaque coupe est décidée isolément. Rien ne relie le résultat d'une coupe à celui de ses voisines, donc la même canine peut porter deux étiquettes sur deux coupes adjacentes, et rien ne ramène le résultat à une seule réponse par patient.

Dans le codeLa boucle, les trois seuils, la règle d'écrasement et la fonction de normalisation

3.4 Sorties et rapport

Le dossier de sortie reprend l'arborescence du dossier d'entrée : un scan site_A/P01.nii.gz donne site_A/P01_seg.nii.gz, si bien que deux patients ayant un fichier du même nom dans des dossiers différents ne s'écrasent pas. La carte d'étiquettes copie la géométrie du scan, donc elle s'ouvre alignée sur lui. Elle réutilise aussi l'en-tête du scan, si bien que le fichier est enregistré dans le type de données propre au scan (un scan stocké en nombres à virgule flottante donne une carte d'étiquettes en virgule flottante) ; les valeurs restent de 0 à 3. Le rapport indique, pour chaque scan, s'il a réussi, combien de coupes ont été lues, combien de détections ont été gardées et quelles classes apparaissent, ainsi que les noms des classes, les couleurs et le seuil utilisé. Un scan sans détection est écrit comme une carte d'étiquettes vide et noté comme tel.

Dans le codeLe nommage des sorties, les clés du rapport avec un exemple, la note sur les scans vides

3.5 Échecs, progression et journaux

Un mauvais scan n'arrête pas les autres : il est consigné comme en échec, avec une raison, et la boucle continue. L'exécution n'échoue que si aucun scan n'a pu être écrit. La progression est indiquée comme une position (scan 3 sur 12), jamais comme un nom de fichier, parce que les noms de fichiers peuvent être des informations sur le patient ; les journaux suivent la même règle.

Dans le codeLa gestion des exceptions, le fichier de progression et les lignes de journal

4. Ce que vous pouvez choisir

  • Les scans : un fichier ou un dossier de volumes NIfTI.
  • Le seuil de score : 0.7 par défaut. Le relever ne garde que les détections les plus sûres ; l'abaisser en garde davantage, avec plus de fausses.
  • Le suffixe de sortie : seg par défaut ; il est ajouté au nom du scan.
  • Non proposés : le fichier de poids (celui du serveur), le périphérique (réglage du serveur, avec repli sur le processeur) et le dossier de sortie (fixé par le serveur). Le seuil de masque de 0.5 est fixe.

6. Environnement

L'outil a son propre environnement Python sur le serveur (Python 3.11, avec des versions figées de torch, torchvision, nibabel et numpy), construit à partir d'un fichier de verrouillage lors de la construction de l'image du serveur. Rien n'est installé sur le poste de travail. Le fichier de poids fait environ 176 MB et est déposé à l'avance sur le serveur.

7. Ce qui a changé par rapport à la logique legacy

Le réseau, le redimensionnement par coupe, les trois canaux, l'axe des coupes et les seuils sont les mêmes. Autour d'eux :

  • Une exécution traite tous les scans dans un seul processus, au lieu d'un processus par scan lancé par le panneau Slicer.
  • Seul le NIfTI est accepté, et une requête sans NIfTI est refusée avec un message clair.
  • Le fichier de poids doit être le seul .pth du dossier ; l'ancien code prenait silencieusement le premier par ordre alphabétique.
  • Le nombre de classes est lu dans les poids au lieu d'être fixé à quatre, et les noms des classes sont dans l'outil et dans le rapport au lieu d'être seulement dans le panneau.
  • Les sorties reprennent l'arborescence des dossiers d'entrée et se nomment X_seg.nii.gz, là où l'ancien code écrivait X.nii_seg.nii.gz.
  • Un scan en échec est consigné dans le rapport, et la progression passe par un fichier de progression que le client peut lire, au lieu de marqueurs textuels qui ne correspondaient jamais.
  • Les poids sont chargés en mode sûr, et il n'y a pas de bouton de téléchargement du modèle.

8. Problèmes connus

  • La construction du réseau peut encore tenter de récupérer le backbone ResNet-50 sur internet avant que les poids soient chargés par-dessus ; voir la constatation.
  • Un scan où rien n'est détecté compte comme un succès, ce qui est aussi à quoi ressemble un mauvais fichier de poids ; voir la constatation.
  • Le panneau n'affiche pas le rapport, donc un scan en échec n'est visible qu'en ouvrant le JSON ; voir la constatation.
  • Certains commentaires du serveur décrivent un CLIC qui traite plusieurs coupes par passe, ce que cet outil ne fait pas ; voir la constatation.
  • Les chevauchements sont toujours réglés par l'ordre, coupe par coupe ; voir la constatation.
  • Côté positif, les autres défauts du legacy ont été vérifiés et ont disparu ; voir la vérification.
