CLIC sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR de CLIC dans le code, avec des références file:line, le code, les arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible du même pipeline, avec les maths, est sur la page de l'atlas.

Code Atlas (explication) VISOR 1 réseau Page legacy Guide (VISOR)

Les références de cette page nomment un dépôt, puis un chemin à l'intérieur, puis une ligne : SADT-VISOR est le catalogue d'outils (commit 6ba2a78), VISOR-serve le serveur (e9a7e5d), Remote le client Slicer (AutomatedDentalToolsRemote 19b95e8), legacy SlicerAutomatedDentalTools à 3c67957. Un chemin seul comme pipeline.py:36 est dans SADT-VISOR tools/CLIC/src/sadt_clic/. Tout a été lu dans le code ; rien sur cette page n'a été exécuté. Vue d'ensemble de la pile : VISOR.

1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

  • État : porté, implémenté dans le code et couvert par des tests dans l'outil (SADT-VISOR tools/CLIC/tests/, non exécutés pour cette page). Rien ici ne dit qu'un serveur donné l'exécute.
  • Nom d'API CLIC, déclaré par [tool.sadt] tool = true, name = "CLIC" (SADT-VISOR tools/CLIC/pyproject.toml:24-26). Le serveur découvre chaque dossier d'outil qui porte cette table ; il n'y a pas de liste codée en dur (Architecture).
  • Panneau client CLICRemote, un panneau mince généré à partir de la description d'outil du serveur (Remote CLICRemote/CLICRemote.py:44,53), construit avec l'extension (Remote CMakeLists.txt:35).
  • Appelle / appelé par : rien de part et d'autre. run() n'a pas d'argument sup, donc pas de sup.run (SADT-VISOR __init__.py:76-88), et aucun autre outil ne nomme CLIC. Le schéma porte néanmoins "supervisor": true, parce que data_root est un argument injecté (sortie de SADT-VISOR scripts/describe.py sur tools/CLIC).
  • Données hébergées : DATA/CLIC/models/final_model.pth (176 MB) et le scan de test MG_test_scan.nii.gz figurent dans le manifeste de données (VISOR-serve scripts/data-manifest.yml:630-641). Le scan est un CBCT de la tête entière sans canine incluse connue (SADT-VISOR tools/CLIC/README.md:116-120) : il prouve l'aller-retour, pas la classification.

3. Le pipeline

Explication en langage courant et maths : page de l'atlas.

3.1 Trouver les scans

Explication en langage courant et maths : page de l'atlas.

scans est un fichier unique ou un dossier. Un dossier est parcouru récursivement avec os.walk, les fichiers cachés sont ignorés, et seuls les noms se terminant par .nii ou .nii.gz (sans distinction de casse) sont conservés, comme chemins de fichiers, triés (pipeline.py:58-79). Le collecteur legacy annonçait aussi .nrrd, .mha et .mhd, que nibabel ne lit pas, et renvoyait des sous-dossiers au lieu de fichiers (legacy §3.1).

SCAN_EXTENSIONS = (".nii", ".nii.gz")                 # pipeline.py:36
found = discover_scans(str(scans))                    # __init__.py:115
if not found:
    raise ValueError("No .nii or .nii.gz scan found in '...'. "
                     "CLIC reads NIfTI volumes; NRRD and MetaImage are not supported.")

Un résultat vide est une ValueError (__init__.py:116-123), que le serveur transforme en 422 portant le message (VISOR-serve server/execution/runner.py:243-244). Seul le nom de base de l'entrée est cité, pas son chemin complet.

3.2 Choisir et charger le checkpoint

Explication en langage courant et maths : page de l'atlas.

model est optionnel. Quand il est vide, l'outil cherche dans <data_root>/CLIC/models (_own_models, __init__.py:30-37) et prend l'unique .pth qui s'y trouve ; aucun ou plusieurs est un refus qui nomme les candidats (_sole_checkpoint, :40-61). Un dossier nommé reçoit la même règle, un fichier nommé est utilisé tel quel (_resolve_checkpoint, :64-73).

Le nombre de classes n'est pas supposé. Il est lu dans la forme de la tête de classification du state dict, fond compris, et les deux têtes sont reconstruites à cette taille avant le chargement des poids (pipeline.py:96-144) :

state = torch.load(checkpoint_path, map_location=device, weights_only=True)
classes = class_count(state)       # roi_heads.box_predictor.cls_score.bias .shape[0]
model = maskrcnn_resnet50_fpn(weights=None)
model.roi_heads.box_predictor  = FastRCNNPredictor(box_features, classes)
model.roi_heads.mask_predictor = MaskRCNNPredictor(mask_features, 256, classes)
model.load_state_dict(state)
model.to(device).eval()

Le checkpoint publié a quatre classes (fond, buccal, bicortical, palatin), ce qu'attend catalogs.CLASSES = len(LABELS) + 1 (catalogs.py:23-40). Une tête mal formée ou absente est une ValueError qui nomme la clé (pipeline.py:109-123). resolve_device garde cuda quand une carte est visible et sinon se replie sur cpu avec un avertissement (pipeline.py:82-93).

3.3 La boucle sur les tranches

Explication en langage courant et maths : page de l'atlas.

Chaque scan est lu avec nibabel en float32 (__init__.py:216-219) ; un volume qui n'est pas 3D fait échouer ce scan seulement. Le volume de labels est un tableau int16 de même forme. La boucle parcourt le troisième axe du tableau tel qu'il est stocké dans le fichier, sans réorientation, exactement comme le faisait le runner legacy :

for index in range(volume.shape[2]):                          # pipeline.py:170
    image = normalise(volume[..., index])                     # min-max to [0, 1]
    tensor = torch.from_numpy(image).unsqueeze(0).repeat(3, 1, 1).float().to(device)
    with torch.no_grad():
        predicted = model([tensor])[0]                        # one slice per call
    keep = predicted["scores"] >= score_threshold             # default 0.7
    masks = (predicted["masks"][keep] > MASK_BINARY_THRESHOLD).squeeze(1)   # 0.5
    for mask, label in zip(masks.cpu().numpy(), predicted["labels"][keep].cpu().numpy()):
        labels[..., index][mask] = int(label)                 # last one wins
        detections += 1
  • Normalisation : par tranche, (x - min) / (max - min) ; une tranche plate (étendue ≤ 1e-8) devient des zéros plutôt que des NaN (pipeline.py:147-154). Le _norm legacy est identique (legacy CLIC/runner/clic_runner.py:44-46).
  • Le redimensionnement et la standardisation ImageNet se font à l'intérieur du GeneralizedRCNNTransform de torchvision, comme dans le legacy (legacy §4.1) ; l'outil ne rééchantillonne rien lui-même.
  • Seuils : score_threshold est un argument (par défaut DEFAULT_SCORE_THRESHOLD = 0.7, pipeline.py:41) ; le seuil du masque reste une constante, MASK_BINARY_THRESHOLD = 0.5 (:44).
  • Recouvrement : les masques sont écrits dans l'ordre où le réseau les renvoie, donc là où deux se recouvrent le dernier écrase l'autre ; il n'y a ni vote ni cohérence 3D entre les tranches (pipeline.py:180-182).

3.4 Sorties et rapport

Explication en langage courant et maths : page de l'atlas.

Chaque scan est identifié par son chemin relatif à la racine d'entrée, et l'arborescence de sortie reproduit celle d'entrée. L'extension .nii.gz ou .nii est retirée avant l'ajout du suffixe (__init__.py:223-231) :

input   scans/site_A/P01.nii.gz
output  output_dir/site_A/P01_seg.nii.gz          # affine and header copied from the input

Un fichier unique est sa propre racine, donc son résultat atterrit directement dans output_dir (__init__.py:163-165). La carte de labels conserve l'affine et l'en-tête de l'entrée (nib.Nifti1Image(labels, image.affine, image.header), :231), si bien que scan et segmentation s'ouvrent alignés. Réutiliser l'en-tête signifie aussi que le fichier est écrit dans le type de données du scan d'entrée, comme dans le legacy : labels est int16 en mémoire (pipeline.py:167), mais un scan float32 donne une carte de labels float32 sur disque (nibabel 5.4.2, vérifié sur l'appel legacy, qui a la même forme ; les valeurs restent de 0 à 3). Puis CLIC_report.json est écrit à côté des résultats (:201), avec cette forme (clés tirées de __init__.py:133-155,188-189,233-249) :

{
  "tool": "CLIC", "model": "final_model.pth", "classes": 4,
  "labels": {"Buccal": 1, "Bicortical": 2, "Palatal": 3},
  "label_colors": {"Buccal": [0.0, 1.0, 0.0], "Bicortical": [1.0, 1.0, 0.0], "Palatal": [0.6, 0.4, 0.2]},
  "device": "cuda", "score_threshold": 0.7,
  "cases": {
    "site_A/P01.nii.gz": {"input": "site_A/P01.nii.gz", "status": "ok", "slices": 512,
                          "detections": 37, "labels_present": [3], "detected": ["Palatal"],
                          "produced": ["site_A/P01_seg.nii.gz"]},
    "site_B/P02.nii.gz": {"input": "site_B/P02.nii.gz", "status": "failed", "reason": "ValueError: ..."}
  },
  "summary": "1/2 scan(s) segmented", "duration_seconds": 41.3
}

Les valeurs de l'exemple (nombre de tranches, nombre de détections, durée) sont illustratives ; les clés sont celles du code. Quand le checkpoint a un autre nombre de classes, labels et label_colors valent null et un labels_note dit pourquoi : un entier sans nom est préféré à un mauvais nom (__init__.py:146-154, catalogs.py:43-58). Un scan sans détection reçoit "note": "no detection cleared the score threshold" (:245-249).

3.5 Échecs, progression et journaux

Explication en langage courant et maths : page de l'atlas.

  • Un scan échoue, un scan est perdu. Toute exception dans _segment_one est consignée dans l'entrée de ce scan comme status: failed avec reason, et la boucle continue (__init__.py:173-186). L'exécution ne lève une erreur que si aucun scan n'a été écrit, en listant toutes les raisons (:191-199) ; le rapport n'est alors pas écrit.
  • Progression : progress.report(index, total, "scan") avant chaque scan (__init__.py:170) ajoute une ligne JSON au fichier désigné par SADT_PROGRESS_FILE (progress.py:3,21,89-103). Les messages donnent une position, jamais un nom de fichier, parce que les noms de fichiers sont des métadonnées de patient (progress.py:13-15).
  • Journaux : la ligne de journal de l'échec nomme elle aussi la position, pas le fichier (__init__.py:183), puisque le stderr d'une exécution échouée est conservé dans le journal du serveur.

8. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Le téléchargement du backbone reste possible

L'outil construit le réseau avec maskrcnn_resnet50_fpn(weights=None) (SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:136), comme le faisait le legacy. Dans torchvision 0.26.0, version figée (pyproject.toml:14), weights_backbone vaut par défaut ResNet50_Weights.IMAGENET1K_V1 (torchvision/models/detection/mask_rcnn.py:416) et resnet50(weights=weights_backbone) est appelé (:490,502), ce qui récupère le fichier par load_state_dict_from_url (torchvision/models/_api.py:91) ; le checkpoint est chargé par-dessus ensuite (pipeline.py:142). Le test qui interdit les appels réseau ne cherche des chaînes que dans les sources propres de l'outil (tests/test_device_and_contract.py:163-175) et ne peut pas voir cet appel. Les lignes de torchvision ont été lues dans une copie installée de torchvision 0.26.0 ; rien n'a été exécuté, et l'on n'a pas vérifié si un serveur donné détient déjà le fichier ResNet-50 dans son cache torch.

Un scan sans détection est un succès

Un volume où rien ne franchit le seuil est écrit comme une carte d'étiquettes entièrement nulle, avec "note": "no detection cleared the score threshold" (__init__.py:245-249). La garde « rien d'écrit » compte les scans écrits, pas les détections (:191-199), donc un lot où chaque scan est vide est une exécution réussie. Le commentaire du source dit que c'est aussi ce à quoi ressemble un mauvais checkpoint (:246-248).

Le client n'affiche ni ne fusionne le rapport

CLIC_report.json porte la table des étiquettes, ce qui a été détecté et quels scans ont échoué (__init__.py:133-155,173-186), mais le panneau n'a pas de RUN_REPORT (Remote CLICRemote/CLICRemote.py:53-72 ; valeur par défaut de la base vide, ServerToolsCore/ServerToolsCoreLib/base_widget.py:1493), contrairement à CNE et DOCShapeAXI. Un scan en échec n'est visible qu'en ouvrant le JSON. Un dossier plus grand qu'un lot (25 entrées ou 400 MB par défaut, VISOR-serve server/config.py:192,196) est envoyé en plusieurs exécutions dont les dossiers sont ramenés dans le dossier de sortie à la fin ; le rapport fusionné n'est écrit que pour un panneau qui déclare RUN_REPORT (base_widget.py:2192), et quand deux lots produisent le même nom de fichier, le premier est conservé (:2205-2224). Pour CLIC, le CLIC_report.json final est donc celui d'un seul lot. Lu dans le code, non exécuté.

Les commentaires du serveur décrivent un autre CLIC

Les commentaires de VISOR-serve décrivent un CLIC qui « batches slices inside one forward » (server/execution/admission.py:146) avec un argument batch_size = 4 (server/execution/runner.py:1251,1271-1272), et citent des mesures de mémoire de CLIC pour des largeurs de 1 à 45 (server/execution/costs.py:470-477). L'outil empaqueté n'a pas d'argument batch_size, traite une coupe par appel model([tensor]) (pipeline.py:170-176) et n'appelle jamais progress.set_width, qui est seulement défini (progress.py:41). Ces commentaires et ces chiffres décrivent donc une autre version de l'outil ; il ne faut pas lire « quatre coupes par passe » comme une propriété de ce code.

Les chevauchements sont toujours résolus par l'ordre, coupe par coupe

Là où deux masques retenus se chevauchent sur une coupe, celui que le réseau a renvoyé en dernier écrase l'autre, et chaque coupe est décidée isolément : il n'y a ni vote entre classes ni cohérence 3D, si bien qu'une même canine peut porter deux étiquettes sur des coupes voisines (pipeline.py:170-182, comme dans le legacy clic_runner.py:84-87). Lu dans le code.

Vérifié : les autres défauts du legacy ont disparu

Le choix du checkpoint refuse l'ambiguïté, le nombre de classes est lu, le chargement se fait en weights_only=True, les sorties sont nommées correctement et indexées par chemin relatif, si bien que deux scans homonymes ne s'écrasent plus (SADT-VISOR __init__.py:40-73,223-231, pipeline.py:96-144). La table des étiquettes est dans le rapport, pas seulement dans le widget.
