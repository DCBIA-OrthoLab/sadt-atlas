BatchDentalSeg sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR de BatchDentalSeg dans le code, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible du même pipeline, avec les maths, est sur la page de l'atlas. Comment BatchDentalSeg s'exécute dans VISOR (client et serveur), ce qui a changé par rapport au module Slicer legacy, et ce que fait le code du portage, étape par étape. Le module legacy est décrit sur sa propre page.

Code Atlas (explication) VISOR Batch_Dental_Seg Page legacy Guide (VISOR) Bibliographie

VISOR exécute BatchDentalSeg sur un serveur : Slicer envoie les scans et le nom d'un modèle hébergé, et reçoit des volumes de labels, des fichiers par label ou des maillages. Un réseau nnU-Net v2, choisi parmi quatre bundles, étiquette toutes les structures d'un scan en une seule passe, et un appel couvre tout le lot. Cette page dit ce qui s'exécute où, suit le pipeline du fichier d'entrée jusqu'au rapport d'exécution, liste les arguments que publie le serveur, et compare chaque étape avec le module legacy. Tout ici a été lu dans le code, pas observé sur un serveur en marche, et rien ici ne dit qu'un serveur donné est déployé.

Les références nomment d'abord le dépôt : SADT-VISOR (code des outils, tool/vface @ 6ba2a78), VISOR-serve (serveur, @ e9a7e5d), AutomatedDentalToolsRemote (client Slicer, @ 19b95e8) et legacy (SlicerAutomatedDentalTools @ 3c67957). Un nom de fichier seul comme pipeline.py, catalogs.py, layout.py, nnunet_runner.py, low_memory.py, mesh_export.py, progress.py ou __init__.py est dans le paquet SADT-VISOR tools/Batch_Dental_Seg/src/sadt_batchdentalseg/. SegmentationWidget.py, Queue.py et PythonDependencyChecker.py sont des fichiers legacy de BATCHDENTALSEG/BATCHDENTALSEGLib/ (le widget compte 3037 lignes à 3c67957).

3. Le pipeline

segment() (SADT-VISOR pipeline.py:216-398) est une ligne droite. Le bundle est vérifié avant qu'aucun scan ne soit lu, chaque scan est converti dans un seul dossier, nnU-Net s'exécute une seule fois sur ce dossier, puis chaque scan est réécrit sur sa propre grille. Seule l'étape du réseau est apprise.

Explication en langage courant et maths : page de l'atlas.

3.1 Entrées et découverte

discover_scans() (pipeline.py:87-107) prend un fichier tel quel, ou parcourt un dossier récursivement avec os.walk et garde les fichiers dont l'extension figure dans sadt_naming.VOLUME : .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl, comparées en minuscules (SADT-VISOR naming/src/sadt_naming/__init__.py:36). Dans un dossier, un fichier est ignoré quand il ressemble à une sortie précédente de cet outil :

def is_previous_output(filename, suffix):                      # pipeline.py:72-84
    base, _extension = split_scan_extension(os.path.basename(filename))
    if suffix and base.endswith(f"_{suffix}"):
        return True
    return any(base.endswith(f"_{suffix}_{name.replace(' ', '-')}")
               for model in catalogs.MODELS.values()
               for name in model.labels)

Avec prediction_ID = "Seg" par défaut, c'est tout nom de base qui se termine par _Seg ou par _Seg_<label> pour n'importe quel label de n'importe lequel des quatre modèles, si bien qu'on peut relancer un dossier sur place (voir le constat du §8 sur les scans dont le propre nom se termine ainsi). Aucun scan du tout lève ToolInputError (pipeline.py:243-248). L'arborescence d'entrée est conservée : input_root est le dossier, ou le parent d'un fichier unique (pipeline.py:250), et chaque cas est décrit dans le rapport par son chemin relatif à ce dossier, jamais par un chemin absolu (pipeline.py:264-265).

3.2 Le modèle : un nom, un bundle, une table de labels

resolve_model() (pipeline.py:110-133) s'exécute avant qu'aucun scan ne soit lu. Le nom du dossier du chemin model est cherché dans catalogs.MODELS ; un nom inconnu est refusé avec la liste des modèles connus. À l'intérieur du dossier, find_model_folder() parcourt l'arborescence à la recherche du répertoire qui contient dataset.json, plans.json et fold_0/checkpoint_final.pth, les trois vérifiés (nnunet_runner.py:57-73) : les quatre bundles n'ont pas la même organisation, DentalSegmentator arrivant sous forme de zip avec sa propre arborescence Dataset<n>/ (nnunet_runner.py:37-41). Un bundle incomplet est refusé avec la commande qui le place de nouveau (pipeline.py:126-132).

MODELS = {model.name: model for model in (                     # catalogs.py:126-152
    Model("DentalSegmentator",  _FIVE_LABELS,      "Adult dental CT/CBCT. ..."),
    Model("PediatricDentalSeg", _FIVE_LABELS,      "Paediatric dental CT/CBCT, ..."),
    Model("NasoMaxillaDentSeg", _NASO_LABELS,      "Six segments: the maxilla is separated ..."),

Comme la table des labels suit le nom du dossier, un appelant ne peut pas associer un bundle aux labels d'un autre : il n'y a pas de second argument où se tromper (catalogs.py:120-125). Les valeurs sont les entiers que le réseau émet, et le code les écrit sans les modifier.

3.3 Conversion vers l'organisation nnU-Net

Chaque scan est converti dans un seul dossier, <output_dir>/.batchdentalseg_work/nnunet_in/, sous un identifiant de cas positionnel (pipeline.py:256-277) :

case_id = f"case_{index:04d}"                                   # pipeline.py:275
_convert_to_nifti(scan, os.path.join(nnunet_input, f"{case_id}_0000.nii.gz"))

def _convert_to_nifti(scan_path, destination):                  # pipeline.py:140-149
    sitk.WriteImage(sitk.ReadImage(scan_path), destination)

Une lecture suivie d'une écriture, jamais un renommage : nnU-Net choisit son lecteur d'après l'extension, donc un NRRD renommé en .nii.gz serait mal lu. Le type des voxels est laissé tel quel ; nnU-Net convertit lui-même en float32 (pipeline.py:143-145). Les identifiants sont positionnels parce que nnU-Net écrit sa sortie sous l'identifiant de l'entrée, et deux scans nommés scan.nii.gz dans des sous-dossiers différents entreraient en collision (pipeline.py:256-259). Un scan illisible est consigné comme failed avec « could not be read » et ignoré ; l'exécution ne s'arrête que si aucun n'est lisible (pipeline.py:278-298).

Aucun fenêtrage d'intensité et aucun recadrage n'est écrit dans ce paquet. Les seuls rééchantillonnages qu'il ajoute sont celui, optionnel, du GPU (§3.5) et celui qui remet le résultat sur la grille du scan (§3.6, pipeline.py:152-171). Le reste du prétraitement est celui de nnU-Net, tiré du plans.json de chaque bundle, et s'exécute dans cet ordre (nnunetv2 2.8.1 tel qu'installé dans l'environnement de l'outil, nnunetv2/preprocessing/preprocessors/default_preprocessor.py) : transposition (:56), recadrage sur la région non nulle (:65), normalisation (:82, le commentaire au-dessus dit qu'elle DOIT précéder le rééchantillonnage), puis rééchantillonnage à l'espacement du plan (:88). Le recadrage automatique du legacy n'est pas porté, volontairement : en amont il ne s'appliquait qu'après un contrôle mémoire raté, et il change ce que le réseau voit (pipeline.py:18-21).

La normalisation est celle de nnU-Net, pas celle de ce dépôt. Pour un plan dont le schéma est CTNormalization : écrêter aux percentiles 0,5 et 99,5 du plan, soustraire la moyenne, diviser par max(std, 1e-8) (nnunetv2/preprocessing/normalization/default_normalization_schemes.py:58-72, chiffres tirés de foreground_intensity_properties_per_channel). Seul le plans.json de DentalSegmentator est lisible dans les dépôts (dans le legacy : CTNormalization, p0,5 −110, p99,5 3067, moyenne 1274, écart type 558). Les plans des trois autres bundles sont téléchargés avec les modèles, donc que ce schéma leur soit applicable est supposé, non vérifié.

3.4 Inférence : un appel pour tout le lot

predict_folder() (nnunet_runner.py:192-232) est appelée une seule fois avec le dossier d'entrée complet qu'elle reçoit (pipeline.py:302-306), donc le checkpoint est chargé une fois par appel, pas une fois par scan. Une cohorte plus grande qu'un lot du serveur (25 fichiers ou 400 MB, §4) parvient à l'outil sous la forme de plusieurs appels de ce type. Le prédicteur est construit par l'API Python de nnU-Net, avec le mot-clé renommé choisi par introspection :

options = {                                                     # nnunet_runner.py:86-95
    "tile_step_size": float(tile_step_size),   # argument, default 0.5
    "use_gaussian": True,
    "use_mirroring": False,                    # no test-time mirroring
    "device": torch.device(device),
    "verbose": False, "verbose_preprocessing": False, "allow_tqdm": False,
}
# + perform_everything_on_device (or _on_gpu) = device.startswith("cuda")   :97-100

predictor.initialize_from_trained_model_folder(                 # :204-208
    model_folder, use_folds=(0,), checkpoint_name="checkpoint_final.pth")

Le chemin du modèle est explicite : pas de variable d'environnement nnUNet_results, qui est globale au processus (nnunet_runner.py:202-203). device bascule de cuda à cpu avec un avertissement quand aucune carte n'est visible (nnunet_runner.py:46-54). Deux chemins suivent (nnunet_runner.py:210-232) :

  • rééchantillonnage GPU appliqué : predict_from_files_sequential, tout dans ce processus, parce que des workers lancés auraient chacun besoin de leur propre contexte CUDA ;
  • sinon (CPU, gpu_resampling=false, ou plans avec un autre rééchantillonneur) : predict_from_files avec 2 workers de prétraitement et 2 d'export. Ces workers sont la raison d'être du shm_size du conteneur (VISOR-serve docker-compose.yml:225-229).

Le placement et la pondération des patchs sont ceux de nnU-Net : le pas vaut au plus tile_step_size fois la taille du patch et est réduit pour que les patchs finissent exactement sur le bord de l'image, d'où un recouvrement d'au moins la moitié pour 0,5 (nnunetv2/inference/sliding_window_prediction.py:30-54) ; le poids gaussien a un écart d'un huitième du patch (sliding_window_prediction.py:11-16, appelé en predict_from_raw_data.py:626).

La progression n'a que deux extrémités mesurables : la lecture compte les scans de 0 à 10 %, l'écriture de 90 à 100 %, et entre les deux une ligne dit « segmenting N scan(s) in one pass » (pipeline.py:269-274, 301, 313 ; progress.py:89-103). Si l'appel d'inférence lève une exception, le dossier temporaire est supprimé et tout le lot échoue, sans qu'aucun rapport ne soit écrit (pipeline.py:302-309).

3.5 Rééchantillonnage GPU et argmax par classe

Avec gpu_resampling = true (le défaut) sur un périphérique CUDA, _enable_gpu_resampling() (nnunet_runner.py:124-189) réécrit les deux noms de rééchantillonneurs dans la configuration du prédicteur, seulement si les deux sont le resample_data_or_seg_to_shape d'origine de nnU-Net :

for key in ("resampling_fn_data", "resampling_fn_probabilities"):   # nnunet_runner.py:167-177
    configuration[key] = "resample_torch_fornnunet"
    configuration[f"{key}_kwargs"] = {"is_seg": False,
                                      "device": torch.device(device),
                                      "mode": "linear"}

Le volume d'entrée passe donc de l'ordre 3 de spline à l'ordre 1, ce que le code désigne comme toute la différence numérique (nnunet_runner.py:169-172). Le troisième rééchantillonneur, celui du masque de recadrage, est volontairement laissé sur scipy (nnunet_runner.py:110-116). Les propriétés en cache sont vidées pour que le remplacement prenne effet (:179-183).

La même fonction appelle ensuite low_memory.install(predictor) (nnunet_runner.py:185-188). Cela remplace de nouveau le rééchantillonneur de probabilités par un qui rééchantillonne la sortie du réseau une classe à la fois et conserve un maximum et un label courants, et cela remplace l'argmax de nnU-Net par un passe-plat, puisque ce qui arrive est déjà l'argmax :

for index in range(data.shape[0]):                              # low_memory.py:62-79
    one = resample_torch_fornnunet(data[index:index + 1].to(device), shape, ...)[0]
    ...
    higher = one > best
    best = torch.where(higher, one, best)
    labels = torch.where(higher, index, labels)
return labels.unsqueeze(0).cpu()                                 # :86

Les deux moitiés sont installées ensemble ou pas du tout : la fabrique qui construit un gestionnaire de labels neuf pour predict_from_files_sequential est aussi enveloppée sur l'instance (low_memory.py:100-151). D'après la docstring du module, l'arithmétique est la même que celle du chemin d'origine (0 voxel différent sur 95 682 560 lors d'une exécution UniversalLab) et le pic passe d'environ 30,6 à 1,25 GiB de VRAM (low_memory.py:14-26) ; ces chiffres n'ont pas été reproduits ici. Les égalités entre classes vont à l'indice le plus bas sur le chemin GPU, parce que le maximum courant n'est remplacé que par un score strictement supérieur (one > best, low_memory.py:75). Sur le chemin propre de nnU-Net, le label est predicted_probabilities.argmax(0) (nnunetv2/utilities/label_handling/label_handling.py:178), qui renvoie le premier maximum selon la convention de NumPy et de PyTorch (comportement documenté d'argmax, non testé ici).

3.6 De retour sur la grille du scan, et écriture

Pour chaque cas, la prédiction nnunet_out/<case_id>.nii.gz est lue ; une prédiction absente marque ce scan failed et la boucle continue (pipeline.py:312-321). Le volume de labels est alors remis sur la grille exacte du scan source :

if (mask.GetSize() == reference.GetSize()                       # pipeline.py:162-171
        and np.allclose(mask.GetSpacing(), reference.GetSpacing(), atol=1e-4)):
    mask.CopyInformation(reference)          # same grid: copy origin and direction
    return mask
return sitk.Resample(mask, reference, sitk.Transform(),
                     sitk.sitkNearestNeighbor, 0, mask.GetPixelID())

<ext> est l'extension d'entrée dans son écriture compressée : .nii devient .nii.gz, .gipl devient .gipl.gz, .nrrd.gz devient .nrrd (NRRD compresse à l'intérieur du fichier) ; .nii.gz, .gipl.gz et .nrrd sont conservés (SADT-VISOR naming/src/sadt_naming/__init__.py:58-60, 77-79 ; pipeline.py:327-328). 3.7 Surfaces

mesh_export.write() (mesh_export.py:177-236) ne fait rien si aucun format de maillage ne figure dans export_formats. Il construit la surface de chaque label présent une seule fois et l'écrit dans tous les formats demandés, si bien que cocher STL et OBJ ensemble ne coûte qu'une passe de marching cubes (:212-225).

smoother = vtk.vtkWindowedSincPolyDataFilter()                  # mesh_export.py:89-110
smoother.SetNumberOfIterations(max(0, int(smoothing)))          # write(smoothing=30)
smoother.SetPassBand(0.05)

smoother.SetFeatureEdgeSmoothing(False)
smoother.NonManifoldSmoothingOn()

Le lissage des arêtes vives est désactivé volontairement : sur un maillage brut de marching cubes, chaque marche de voxel est une arête vive, et protéger ces arêtes conserverait l'escalier (mesh_export.py:94-107). La décimation utilise vtkDecimatePro avec la topologie préservée et un angle caractéristique de 60 (:120-130) ; sa valeur par défaut de 0 a été choisie par parité avec l'export STL du module legacy, mesurée sur un label d'après la docstring (__init__.py:84-100). Aucune normale n'est écrite (:132-139). STL et VTK sont écrits en binaire, OBJ en texte, qui n'a pas de forme binaire (:45-49, 165-172). Le masque parvient à VTK par un NRRD temporaire au nom unique, supprimé après lecture (:66-118) ; mesh_export.py n'applique aucune transformation RAS ou LPS explicite, contrairement à l'export VTK du legacy, qui basculait en LPS (legacy SegmentationWidget.py:2958).

8. Constats dans VISOR

VFACE demande des surfaces et reçoit des volumes de labels

Le chemin des cartes de chaleur de VFACE appelle cet outil avec trois arguments seulement, scans, model et prediction_ID="Seg" (SADT-VISOR tools/VFACE/src/sadt_vface/tools.py:359-364), donc export_formats garde sa valeur par défaut ["NIFTI"] (SADT-VISOR __init__.py:22-24) et aucun maillage n'est écrit (pipeline.py:342-354 ; mesh_export.py:187-189). VFACE cherche ensuite uniquement des fichiers .vtk ou .vtp (heatmap.py:29, 194-204), n'en trouve aucun, et se termine par « No heat map could be drawn » (heatmap.py:246-251). Lu dans le code, non exécuté. Le déploiement lu ici ne publie de toute façon aucun surface_model pour VFACE (VISOR-serve server/deployment.toml:277-279), donc le chemin n'est pas atteignable depuis le panneau de ce serveur.

Le README de l'outil est périmé sur les exports de maillages et la mémoire

Le README de l'outil dit « No vtk: the mesh exports are not ported » et les liste comme non portés (tools/Batch_Dental_Seg/README.md:28, 95) ; la docstring de pipeline.py dit la même chose (SADT-VISOR pipeline.py:23-24). Le code dit le contraire : mesh_export.py écrit du STL, de l'OBJ et du VTK, export_formats est un argument (__init__.py:22-24) et vtk 9.6.2 est une dépendance (pyproject.toml:23). Seul glTF manque vraiment. Le README compte aussi 38 tests sans GPU (README.md:267) alors que le fichier a 55 fonctions de test. Son conseil de désactiver gpu_resampling pour UniversalLab sur une carte de moins d'environ 40 GiB (README.md:241-256, répété dans __init__.py:69-73) a été modifié pour la dernière fois dans le commit d2fb0d8 ; le rééchantillonneur par classe, que le code installe avec le rééchantillonneur GPU sur chaque bundle (nnunet_runner.py:185-188), est venu après, dans c8899c8, et sa docstring annonce un pic bien plus bas (low_memory.py:20-26). Le code fait référence ici ; le pic lui-même n'a pas été mesuré pour cette page.

Un scan nommé ..._Seg est invisible dans un dossier

Avec l'identifiant par défaut, patient_Seg.nii.gz dans un dossier est pris pour une sortie précédente et ignoré sans aucun message (SADT-VISOR pipeline.py:79-80, 104-105). Un fichier unique passé comme scans est traité même si son nom ressemble à une sortie (pipeline.py:96-97).

Le rééchantillonnage GPU est activé par défaut et change les chiffres

Quand il s'applique, le volume d'entrée est rééchantillonné sur le GPU en mode linéaire au lieu de la spline cubique de nnU-Net ; le code affirme que c'est toute la différence numérique et que gpu_resampling=false le désactive (SADT-VISOR nnunet_runner.py:167-177). Le rapport consigne la valeur demandée sur un périphérique CUDA, et false sur CPU ; un bundle dont les plans refusent n'est mentionné que dans le journal (pipeline.py:374-378 ; nnunet_runner.py:163-165). L'argument est masqué dans le panneau.

L'autoréglage de cuDNN n'est pas désactivé

BatchDentalSeg ne règle jamais torch.backends.cudnn.benchmark (aucune occurrence dans le paquet), et le prédicteur de nnU-Net le met à true sur CUDA (nnunetv2/inference/predict_from_raw_data.py:60-61, nnunetv2 tel qu'installé dans l'environnement de l'outil). AMASSS le désactive explicitement (SADT-VISOR AMASSS sadt_amasss/nnunet_runner.py:116). Le README de l'outil dit que nnU-Net sur CUDA n'est pas déterministe au bit près (README.md:113) : ne vous attendez pas à un masque identique au bit près entre deux exécutions du même scan.

Une liste d'export vide donne « ok » sans fichier (appel direct seulement)

Appelé directement en Python, run(..., export_formats=[]) signale chaque scan comme ok avec une liste produced vide et un résumé « 1/1 scan(s) segmented », et n'écrit rien (SADT-VISOR pipeline.py:342-355, 362-386 ; mesh_export.py:187-189) ; l'outil lui-même ne vérifie pas la liste. Une requête passant par le serveur est refusée avant l'exécution, puisque la disposition exige au moins un format (layout.py:31-33 ; VISOR-serve server/base.py:855-858), et le panneau en exige un aussi.

Les fichiers par label dépendent du format NIfTI

separate_segments découpe le volume de labels, donc il ne fonctionne que lorsque NIFTI est sélectionné : avec des maillages seulement, rien n'est écrit pour lui même si la case est cochée (SADT-VISOR pipeline.py:339-350).

La table des labels voyage avec le résultat, mais Slicer ne la lit pas

Le rapport contient la table labels complète (SADT-VISOR pipeline.py:364-371). Le panneau Slicer ne définit aucun RUN_REPORT (vide par défaut : ServerToolsCoreLib/base_widget.py:1493) et charge les volumes de labels avec un simple loadLabelVolume (slicer_io.py:560) ; un commentaire du module parle d'une table de couleurs (BATCHDENTALSEGRemote.py:79-82) mais aucun code n'en applique une.

Un seul appel d'inférence : la progression a deux extrémités

Le dossier entier passe par un seul appel nnU-Net, donc la barre couvre la lecture (0 à 10 %) et l'écriture (90 à 100 %) et dit « segmenting N scan(s) in one pass » entre les deux, sans inventer de valeurs intermédiaires (SADT-VISOR pipeline.py:269-274, 301). Une exception de cet appel fait échouer tout le lot après avoir nettoyé le dossier temporaire (pipeline.py:302-309).

Vérifié : un scan illisible n'arrête pas le lot

Un scan qui ne peut pas être lu est signalé failed (« could not be read ») et les autres sont segmentés ; l'exécution ne s'arrête avec une erreur d'entrée que si aucun n'est lisible (SADT-VISOR pipeline.py:273-298).

9. Littérature

Les réseaux sont de la famille DentalSegmentator ; la bibliographie est celle de l'outil et n'est pas répétée ici : Sources de BatchDentalSeg, et la section de littérature de la page legacy. Le manifeste pointe vers les mêmes URL de release que celles où le module legacy télécharge : les trois releases DCBIA-OrthoLab (VISOR-serve scripts/data-manifest.yml:542-581 ; legacy ADT/ADTLib/model_registry.py:59-64) et, pour DentalSegmentator, l'archive consignée dans le Resources/ML/download_info.json du legacy (data-manifest.yml:582-586). Le code ne permet pas de savoir si les fichiers derrière ces URL sont octet pour octet ceux qu'une installation legacy récupérait : aucun des deux côtés n'enregistre de hash pour un checkpoint.
