Crown_Seg sur VISOR : le code

Pour les développeurs : ce que fait l'outil VISOR Crown_Seg dans le code, avec des références file:line, les signatures, les arguments, l'environnement, la correspondance avec le legacy et les constatations. L'explication lisible du même pipeline, avec les maths, est sur la page de l'atlas.

VISOR uniquement Code Atlas (explication) SADT-VISOR 6ba2a78 VISOR-serve e9a7e5d Remote 19b95e8
Pas de module legacy

Le dépôt legacy (SlicerAutomatedDentalTools à 3c67957) ne contient aucun module Crown_Seg et aucun fichier dont le chemin contient “crown” ou “dentalmodelseg” (git ls-tree sur ce commit, observé). Il contient des appels au module CrownSegmentationcli de l'extension séparée SlicerDentalModelSeg, et une petite copie du même appel dans la ligne de commande d'ALI_IOS. La correspondance exacte est dans Équivalent legacy. La façon dont VISOR exécute un outil sur un serveur est décrite dans Architecture.

Chemins : SADT-VISOR cs/ est tools/Crown_Seg/src/sadt_crownseg/, ali_ios/ est tools/ALI/ALI_IOS/src/sadt_ali_ios/, et les chemins VISOR-serve commencent à server/ sauf s'ils nomment docs/ ou scripts/. “Observed” marque ce qui a été relancé pendant la rédaction de cette page ; tout le reste a été lu dans le code.

Explication en langage courant et maths : page de l'atlas.

4.1 Ce que fait l'outil autour du moteur

Explication en langage courant et maths : page de l'atlas.

  1. Checkpoint d'abord : find_checkpoint accepte un fichier .pth, ou un dossier parcouru récursivement à la recherche d'un fichier dont le nom contient val-loss ; aucun ou deux est une ToolInputError qui les nomme (cs/pipeline.py:186-262). Un model vide signifie <data_root>/Crown_Seg/models (cs/__init__.py:18-29,104). Cela se passe avant que quoi que ce soit soit créé (cs/pipeline.py:407-413).
  2. Découverte : un .vtk ou .stl, ou un dossier parcouru récursivement et trié ; ne rien trouver est un 422 (cs/pipeline.py:292-320). La racine d'entrée, utilisée pour recopier l'arborescence, est le dossier ou le parent du fichier unique (:323-330).
  3. Tri : avec skip_segmented (vrai par défaut), is_segmented ouvre chaque maillage et ne lit que les noms de ses tableaux de points ; l'un de PredictedID, UniversalID, Universal_ID, FDI_ID l'envoie dans la branche de copie (cs/pipeline.py:56,267-289,449-451).
  4. Branche de copie : chaque maillage étiqueté est écrit en polydata .vtk vers <output>/<relative folder>/<base>_<suffix>.vtk, un .stl étant converti (cs/pipeline.py:480-487,594-613). Les étiquettes ne sont pas touchées.
  5. Branche de segmentation : les chemins restants vont dans .crownseg_work/crownseg_input.csv sous un en-tête surf, le périphérique est résolu en cuda:0 ou cpu (:170-178), et shapeaxi est appelé une fois pour toute la liste avec ce namespace (cs/pipeline.py:336-366,508-531) :
Namespace(surf=None, csv=csv_path, model=checkpoint, suffix=suffix, out=output_dir,
          num_workers=max(1, num_workers), crown_segmentation=0, array_name=array_name,
          fdi=1 if numbering == "FDI" else 0, overwrite=0, device=device,
          vtk_folder=input_root)
with contextlib.redirect_stdout(io.StringIO()):
    dental_model_seg.main(args)

Avant l'appel, _import_dental_model_seg importe shapeaxi paresseusement et, quand saxi_nets n'a pas DentalModelSeg (toutes les versions 2.0.x, d'après le commentaire), le redirige vers saxi_nets_lightning.DentalModelSeg (cs/pipeline.py:105-167). Si l'import échoue, l'exécution continue pour la branche de copie et consigne engine_available: false avec l'erreur (cs/pipeline.py:466-472) ; un maillage qui avait besoin du réseau n'a alors pas de sortie et est failed.

4.2 Dans shapeaxi

Explication en langage courant et maths : page de l'atlas.

Lu dans dental_model_seg.py du checkout ShapeAXI 2b34042. Le fichier de verrouillage résout shapeaxi en 2.0.2, dont le source n'a pas été ouvert ici ; les lignes citées ci-dessous sont identiques dans les copies qui l'ont été (shapeaxi 1.0.10 et 2.0.3 installés, et 1.1.1 dans le cache uv) :

  • le réseau est saxi_nets_lightning.DentalModelSeg(custom_model=args.model, device=device), avec out_channels = 34 (:23,26) ;
  • chaque surface est chargée via SaxiDataset avec UnitSurfTransform(), taille de lot 1, persistent_workers=True (:82-84), ce qui explique pourquoi num_workers doit valoir au moins 1 ;
  • le réseau renvoie des prédictions par vue et la face que montre chaque pixel ; les prédictions sont multipliées par (PF >= 0) (zéro là où un pixel ne montre aucune face) puis passées dans le softmax (:97), si bien qu'un pixel sans face donne un 1/34 uniforme qui est ajouté à une entrée de la table des faces au lieu d'être ignoré (:103-104) ; la somme par face et l'arg-max (:106) donnent une étiquette par face, et l'étiquette de chaque face est donnée à son premier sommet (:107-108) ;
  • post-traitement : RemoveIslands pour l'étiquette de gencive 33 avec un seuil de 500, puis pour chaque étiquette avec 200, puis une fermeture par étiquette, DilateLabel puis ErodeLabel, deux itérations chacun (:118-130) ;
  • ConvertFDI si fdi == 1 (:52,225-236, section suivante) ;
  • avec overwrite=0 et une entrée csv, le résultat va dans <out>/<csv stem>_<suffix>/<input path without vtk_folder>_<suffix>.vtk (:154-176). Crown_Seg recalcule ce chemin plutôt que d'analyser la sortie de shapeaxi (cs/pipeline.py:369-381), puis marque chaque maillage segmented si le fichier existe et failed sinon (:533-546).

4.3 Numérotation des dents : Universal et FDI

Explication en langage courant et maths : page de l'atlas.

Le réseau prédit toujours des numéros Universal : 1 à 32 pour les dents, 33 pour la gencive. Avec numbering = "FDI", le ConvertFDI de shapeaxi fait passer chaque valeur par une seule table de correspondance (ShapeAXI 2b34042 dental_model_seg.py:225-236) :

LUT = [0, 18,17,16,15,14,13,12,11, 21,22,23,24,25,26,27,28,
          38,37,36,35,34,33,32,31, 41,42,43,44,45,46,47,48, 0]
labels = LUT[labels]          # index = Universal value, entry = FDI value

9 à 1621 en montant jusqu'à 28haut gauche, de l'incisive centrale à la troisième molaire
17 à 2438 en descendant jusqu'à 31bas gauche, de la troisième molaire à l'incisive centrale
25 à 3241 en montant jusqu'à 48bas droite, de l'incisive centrale à la troisième molaire

shapeaxi réécrit les entiers convertis sous le même nom de tableau (vtk_id.SetName(args.array_name), :233-235). Comme les deux systèmes partagent l'essentiel de leur plage, un tableau FDI appelé Universal_ID serait lu sans erreur comme d'autres dents : FDI 18 est la troisième molaire supérieure droite, Universal 18 une molaire inférieure gauche ; FDI 33 est une canine inférieure gauche, Universal 33 la gencive (commentaire en cs/pipeline.py:62-80). Crown_Seg nomme donc le tableau d'après la numérotation : array_name laissé vide devient Universal_ID ou FDI_ID (array_name_for, cs/pipeline.py:58-85 ; cs/__init__.py:44,106). Tout lecteur en aval ne cherche que des noms Universal, donc un maillage FDI est refusé par ALI_IOS, ASO ou AREG_IOS au lieu d'être mal lu (voir Constatations). Tous les appelants du legacy passaient fdi 0 ; la sortie FDI est nouvelle en pratique, et Universal reste la valeur par défaut (cs/__init__.py:46).

Sorties. L'outil renvoie le dossier de sortie, donc il n'y a pas de sorties nommées. Deux arborescences peuvent apparaître, selon ce qui est arrivé à chaque maillage : un maillage segmenté par le réseau est écrit sous <output>/crownseg_input_<suffix>/<relative path without extension>_<suffix>.vtk (cs/pipeline.py:369-381,514), et un maillage qui portait déjà des étiquettes est copié, converti en .vtk, vers <output>/<relative folder>/<base>_<suffix>.vtk (cs/pipeline.py:480-487,594-613). L'appelant est censé lire run_report.json plutôt que de deviner. Le dossier temporaire .crownseg_work/ est supprimé dans un finally (cs/pipeline.py:87,435-439), et le checkpoint est résolu avant qu'il existe, donc une requête refusée laisse le dossier de sortie comme elle l'a trouvé (cs/pipeline.py:407-413).

run_report.json. tool, checkpoint (par nom), array_name, suffix, numbering, device, cases (par maillage : status, input, produced, et error en cas d'échec), segmented_meshes, engine_available, engine_error, un summary avec les décomptes de total, segmented, already_segmented, engine_unavailable et failed, et duration_seconds (cs/pipeline.py:556-590). Un maillage pour lequel shapeaxi n'a rien écrit est un cas failed ; l'exécution dans son ensemble n'échoue que si aucun maillage n'a été produit (cs/pipeline.py:540-551).

Confidentialité des journaux. shapeaxi affiche le chemin de chaque maillage qu'il enregistre, et le chemin porte le nom de fichier du patient : sa sortie standard est avalée (cs/pipeline.py:341-345,365-366), et les chemins de sortie sont recalculés plutôt qu'analysés à partir d'elle (cs/pipeline.py:369-381).

8. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Numérotation FDI sur un maillage déjà étiqueté

Avec numbering = "FDI" et skip_segmented activé, un maillage qui porte déjà un tableau d'étiquettes est copié sans changement (cs/pipeline.py:480-487 ; _write_as_vtk convertit le format de fichier, pas les étiquettes), alors que le rapport indique array_name = "FDI_ID" et numbering = "FDI" (cs/pipeline.py:556-561). La copie garde ses entiers Universal sous leur nom Universal, donc le rapport annonce une numérotation que le fichier ne contient pas. Observé : un maillage synthétique portant un tableau Universal_ID a été passé dans segment_crowns avec fdi=True et array_name="FDI_ID" ; le rapport indiquait numbering: "FDI" et array_name: "FDI_ID", et le fichier de sortie ne contenait que Universal_ID avec sa valeur d'origine. Le moteur de segmentation n'est pas installé dans l'environnement utilisé, donc le statut du cas indiquait engine_unavailable au lieu de already_segmented ; le chemin de copie est le même. Les tests ne couvrent pas ce croisement (tests/test_run.py:488-503).

Quatre noms reconnus ici, trois en aval

Crown_Seg considère un maillage comme segmenté s'il contient l'un de PredictedID, UniversalID, Universal_ID ou FDI_ID (cs/pipeline.py:56). ALI_IOS, ASO et AREG_IOS ne lisent que les trois premiers (ali_ios/surface.py:19, SADT-VISOR tools/ASO/src/sadt_aso/markups.py:19, AREG_IOS/src/sadt_areg_ios/surfaces.py:39). Un maillage qui n'a que FDI_ID passe donc Crown_Seg et est refusé par l'outil suivant : voulu (le commentaire de l'outil le dit, cs/pipeline.py:64-80), mais sans aucun symptôme avant cet outil suivant. Le commentaire d'ALI_IOS disant que ce sont “the same three names CrownSeg writes and recognizes” (ali_ios/surface.py:18) est inexact. Lu dans le code.

Les maillages en .vtp ou .obj sont invisibles pour Crown_Seg

Crown_Seg ne découvre que .vtk et .stl (cs/pipeline.py:51,292-320), alors qu'AREG_IOS accepte .vtk .vtp .stl .obj en entrée (AREG_IOS/src/sadt_areg_ios/surfaces.py:35) et, en mode Fully-Automated, passe son dossier à Crown_Seg (dispatch.py:172-173). Un dossier qui ne contient que de tels maillages est refusé (“No surface mesh found in the input”, cs/pipeline.py:314-319) ; dans un dossier mixte, ils sont absents de la sortie de Crown_Seg, qui est le dossier avec lequel AREG_IOS continue. La copie legacy de l'appel dans ALI_IOS lisait bien .vtp (segmentation.py:33-56). Lu dans le code ; non exécuté.

Deux arborescences de sortie : lire le rapport

Un maillage segmenté atterrit sous crownseg_input_<suffix>/, un maillage déjà étiqueté atterrit à côté de son chemin relatif, si bien qu'un glob sur une arborescence rate l'autre (cs/pipeline.py:369-381,480-487). ALI_IOS lit plutôt cases[key].produced dans run_report.json (ali_ios/dispatch.py:240-252), ce à quoi sert le rapport. Un maillage d'une installation dégradée porte le statut engine_unavailable mais est copié avec son chemin produced (cs/pipeline.py:495-505), donc un client qui filtrerait sur already_segmented seul l'ignorerait. Lu dans le code.

Le graphe des outils dans la documentation du serveur est périmé

VISOR-serve docs/TOOL_GRAPH.md:27-28,43 liste ALI_IOS comme une feuille. Le schéma qu'ALI_IOS publie déclare calls = ['Crown_Seg'] (observé avec scripts/describe.py dans l'environnement d'ALI_IOS), parce que son dispatch appelle Crown_Seg via une constante de module (ali_ios/dispatch.py:58,229). Le document dit qu'il est généré à partir de ces schémas et vérifié au démarrage ; la copie du dépôt est plus ancienne que le code.

Documentation en désaccord avec le code

Le README dit que le modèle est un argument obligatoire (README.md:33), et la docstring du pipeline aussi (cs/pipeline.py:16-23) ; l'argument est facultatif, avec une valeur par défaut vide qui se résout vers le dossier propre de l'outil (cs/__init__.py:41, commentaire en cs/__init__.py:35-40). Le README nomme aussi le dossier DATA/CrownSeg/testfiles (README.md:178) alors que le code et le manifeste utilisent DATA/Crown_Seg, et il compte 176 tests (README.md:225,232) là où 162 fonctions de test sont définies dans tests/ (décompte de def test_ ; la paramétrisation peut expliquer l'écart). AREG ne passe jamais device à Crown_Seg, contrairement à ALI_IOS (SADT-VISOR tools/AREG/AREG_IOS/src/sadt_areg_ios/tools.py:113-130), donc sur un serveur sans GPU la valeur par défaut cuda se rabat sur le CPU avec un avertissement, ou est remplacée par le DEVICE du serveur. Lu dans le code.

Ce que l'outil protège

Le checkpoint est résolu avant la création de tout fichier, donc une requête refusée ne laisse rien derrière elle (cs/pipeline.py:407-413) ; un dossier qui contient deux checkpoints est refusé en nommant les deux, si bien que l'âge des poids n'est jamais silencieux (cs/pipeline.py:244-251) ; la sortie standard de shapeaxi, qui porte des noms de fichiers, est avalée (cs/pipeline.py:365) ; le dossier temporaire est supprimé dans un finally (cs/pipeline.py:435-439) ; l'entrée n'est jamais modifiée. Lu dans le code.

Reproductibilité

Le README de l'outil rapporte que la prédiction brute PredictedID est identique bit à bit à un portage de référence, et que le Universal_ID post-traité varie d'une exécution à l'autre, y compris entre deux exécutions du même code (de 826 à 2,607 points sur 294,260). C'est la mesure du README (SADT-VISOR tools/Crown_Seg/README.md:176-209, section “Validated against”), non relancée ici.
