AutoCrop3D sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR d'AutoCrop3D dans le code, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le module legacy et les constats. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas.

VISOR Code Atlas (explication) Page legacy Guide (VISOR)

Dans VISOR, AutoCrop3D est un paquet Python qui s'exécute sur le serveur : le côté Slicer ne fait que dessiner ou choisir la boîte, envoyer les fichiers et charger ce qui revient. Le recadrage lui-même est l'arithmétique legacy, conservée exprès ; ce qui a changé, c'est tout ce qui l'entoure, la façon d'apparier les scans aux ROI, ce qui est vérifié, ce qui est rapporté. Cette page suit le portage depuis la requête jusqu'aux fichiers qui reviennent : position, fichiers, chaque étape du recadrage et de la surface avec le code qui la fait, les arguments publiés, l'environnement, les différences avec le module legacy et les constats. Elle décrit le portage dans SADT-VISOR (branche tool/vface, 6ba2a78, 2026-09-30), servi par VISOR-serve (e9a7e5d) et piloté depuis Slicer par l'extension AutomatedDentalToolsRemote (19b95e8). Le portage a été fait à partir du commit upstream b1ae78c (2026-05-26, SADT-VISOR AutoCrop3D/README.md:15-16), qui précède l'état 3c67957 décrit sur la page legacy. Aucune affirmation n'est faite ici sur un serveur déployé : tout ce qui suit est lu dans le code, et la suite de tests de l'outil a été exécutée sur le paquet.

1. Situation dans la chaîne

Explication en langage courant et maths : page de l'atlas.

AutoCrop3D est un utilitaire en tête de chaîne : il réduit un CBCT, ou sa segmentation, à la région qu'un clinicien a dessinée, avant qu'un autre outil travaille dessus. Dans VISOR, il n'appelle rien et rien ne l'appelle. La ROI est dessinée dans Slicer, ce qui explique que le client garde cette partie.

4. Le pipeline, pas à pas

Explication en langage courant et maths : page de l'atlas.

Un appel de run() recadre chaque scan qu'il trouve (SADT-VISOR AutoCrop3D/__init__.py:76-167).

4.1 Trouver les scans et les ROI calculé

Explication en langage courant et maths : page de l'atlas.

_discover_scans prend un fichier, ou parcourt un dossier récursivement, garde .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl (pipeline.py:26), ignore les fichiers cachés, et met de côté les fichiers qui ressemblent à une sortie antérieure de cette exécution (pairing.is_previous_output, un jeton final entier, donc Cropped_01 n'est pas exclu) ; ceux-ci ne servent que si rien d'autre n'est trouvé (__init__.py:289-311). _discover_rois accepte trois formes : un fichier .mrk.json, un dossier qui en contient exactement un (les deux utilisés pour chaque scan), ou un dossier de plusieurs, appariés par patient (__init__.py:314-368). Deux ROI avec la même clé de patient sont refusées par leur nom plutôt que de laisser l'une l'emporter en silence (:345-367).

4.2 La clé de patient calculée

Explication en langage courant et maths : page de l'atlas.

Une seule fonction sert les scans et les ROI (pipeline.py:60-113). Elle découpe le nom en jetons et retire, comme jetons entiers et jamais le premier mot, le vocabulaire des découpages enchaînés du legacy plus les mots de ROI (pipeline.py:51-57, 97-108) :

IDENTITY_TOKENS_TO_DROP = frozenset({
    "scan", "scans", "seg", "segmentation", "segmentations", "or", "mand",
    "md", "max", "mx", "cb", "lm", "cl", "merged", "mask", "pred",
    "roi", "rois", "mrk", "crop", "cropped", "box", "bbox",
})

Le temps est conservé : P01_T1 et P01_T2 peuvent donc avoir deux boîtes, et un patient appelé MAX_01 reste MAX_01 (pipeline.py:75-81, 100-105). Exécuté le 2026-11-09 : Patient_01_Scan et Patient_01_ROI donnent tous deux Patient_01. Un scan dont la clé n'a pas de ROI lève _NoRoi et est listé dans without_a_roi (__init__.py:134-141, 206-208).

4.3 Lire la boîte calculé

Explication en langage courant et maths : page de l'atlas.

read_roi prend center et size du premier markup et refuse, par nom de fichier, un fichier qui n'est pas du JSON, n'a aucun markup ou n'a pas de boîte (pipeline.py:158-187). Puis le repère (pipeline.py:194-201) :

system = str(document.get("coordinateSystem", markup.get("coordinateSystem", "LPS"))).upper()
center = [float(value) for value in center]
if system in ("RAS", "0"):
    center = [-center[0], -center[1], center[2]]
elif system not in ("LPS", "1"):
    raise ValueError(...)

Le centre se retrouve en LPS, le repère des points physiques d'ITK. La taille est prise en valeur absolue (:215). Une rotation dans orientation n'est pas appliquée : la boîte reste alignée sur les axes, un avertissement est journalisé et roi_orientation_ignored est posé, mais seulement pour une vraie rotation ; une permutation signée des axes, qui envoie la boîte sur elle-même, ne compte pas (pipeline.py:203-211, 228-249).

4.4 De la boîte aux indices, et le recadrage calculé

Explication en langage courant et maths : page de l'atlas.

Les deux coins physiques passent par TransformPhysicalPointToContinuousIndex et sont tronqués vers zéro, exactement comme le faisait le .astype(int) du legacy ; les coins sont échangés par axe si besoin, puis bornés au volume (pipeline.py:269-283) :

lower_point = [c - s / 2.0 for c, s in zip(roi.center, roi.size)]
upper_point = [c + s / 2.0 for c, s in zip(roi.center, roi.size)]
lower = [int(value) for value in image.TransformPhysicalPointToContinuousIndex(lower_point)]
upper = [int(value) for value in image.TransformPhysicalPointToContinuousIndex(upper_point)]
...
clamped = any(lower[axis] < 0 or upper[axis] > size[axis] for axis in range(3))

Le recadrage est une tranche SimpleITK, image[lower[0]:upper[0], lower[1]:upper[1], lower[2]:upper[2]] : ni rééchantillonnage ni interpolation, avec origine, spacing et direction conservés, de sorte que le volume recadré se trouve exactement là où étaient ses voxels. Une plage vide est refusée avec "The ROI does not overlap this volume" (pipeline.py:286-301). Avec keep_original_size, le recadrage est recopié dans une image vide de la taille et de la géométrie d'origine, tout le reste à zéro (pipeline.py:304-329 ; numpy indexe en (z, y, x), les bornes sont en (x, y, z), :320-325).

4.5 Écrire et nommer calculé

Explication en langage courant et maths : page de l'atlas.

La sortie reproduit l'arborescence d'entrée sous output_dir (__init__.py:223-226, 277-286), et le nom garde les extensions composées : P1_scan.nii.gz avec le suffixe cropped donne P1_scan_cropped.nii.gz ; un suffixe vide n'ajoute rien (pipeline.py:332-344). Le format suit l'extension (sitk.WriteImage, __init__.py:226). Un .nrrd.gz est refusé pour ce scan seulement, avec la raison (__init__.py:210-214).

4.6 La surface d'une carte d'étiquettes recadrée calculé

Explication en langage courant et maths : page de l'atlas.

Construite quand surfaces vaut all, ou segmentations et que le nom de fichier contient un jeton entier parmi seg, segmentation, mask, pred, label, labels (__init__.py:246, 265-274 ; pipeline.py:124-134).

  1. Étiquettes. Les valeurs non nulles réellement présentes (pipeline.py:400-412). Aucune : aucun fichier n'est écrit, le rapport dit surface: null (pipeline.py:457-459 ; __init__.py:257-261).
  2. Marge. surface_padding_mm converti en voxels entiers par axe, au moins un, puis sitk.ConstantPad(image, margin, margin, 0) sur les deux bornes, de sorte qu'une structure qui touche la boîte est fermée (pipeline.py:415-426, 461-462).
  3. Marching cubes. Le volume rempli est écrit dans padded.nii.gz dans le dossier temporaire de l'exécution et relu avec vtkNIFTIImageReader ; vtkDiscreteMarchingCubes avec un contour par étiquette présente (pipeline.py:463-478).
  4. Lissage. vtkSmoothPolyDataFilter, surface_smoothing_iterations passes, angle de crête 120 et relaxation 0,6 comme constantes (pipeline.py:434-435, 480-485).
  5. Espace patient. Le lecteur NIfTI laisse le qform à l'appelant, la surface est donc déplacée par origin + direction @ diag(spacing / reader_spacing), une matrice 4×4 et aucun rééchantillonnage (pipeline.py:502-541). Le .vtk se superpose alors au volume recadré (tests/test_run.py:1242, réussi).
  6. Couleur et écriture. Chaque cellule reçoit la couleur de son étiquette : la table legacy de six entrées, puis une teinte en angle d'or pour les étiquettes supérieures (pipeline.py:359-384, 544-585). Écrit avec vtkPolyDataWriter à ses réglages par défaut sous le nom <stem>_<suffix>_vtk.vtk à côté du volume (pipeline.py:347-351, 491-494) ; le volume temporaire est supprimé dans un finally (:495-497).

Il est écrit avant la vérification finale. Si rien n'a été recadré, run() lève une ValueError qui dit pourquoi : soit tous les scans ont échoué (les cinq premières raisons), soit aucun scan n'a trouvé de ROI, avec jusqu'à huit clés de scan et clés de ROI côte à côte pour que l'écart se voie (__init__.py:162-194). Un échec sur un scan est enregistré et les autres continuent (:142-149).

9. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Chemins du serveur dans le rapport

Quand une surface est écrite, le rapport la désigne par un chemin absolu du serveur : entry["surface"] = str(surface_path) et la même chaîne ajoutée à produced (SADT-VISOR AutoCrop3D/__init__.py:253-255), alors que le commentaire juste au-dessus dit que le rapport doit rester relatif à output_dir parce qu'il voyage jusqu'au client (:231-232). L'entrée du volume est relative (:236). Le seul test de la règle vérifie produced[0] (tests/test_run.py:1424-1441), qui est le volume. Reproduit le 2026-11-09 en appelant run() sur une carte de labels synthétique nommée P1_Seg.nii.gz : produced contenait P1_Seg_cropped.nii.gz et un chemin absolu …/out/P1_Seg_cropped_vtk.vtk, et surface le même chemin absolu.

La règle de surface par défaut dépend du nom de fichier

Avec surfaces = "segmentations" par défaut, une surface n'est construite que si le nom de fichier contient un mot entier parmi seg, segmentation, mask, pred, label, labels (SADT-VISOR AutoCrop3D/pipeline.py:124-134). Vérifié le 2026-11-09 avec le is_segmentation_name du paquet : P1_Seg.nii.gz convient, Mandible.nii.gz non et n'a pas de surface sauf avec surfaces = "all". Le test legacy était une sous-chaîne seg n'importe où dans le chemin de sortie (AutoCrop3D_CLI.py:143@3c67957).

Une cohorte n'est pas découpée

scans et roi sont deux arguments path obligatoires, donc le serveur n'offre aucun axe de lot (VISOR-serve server/registry/conventions.py:158-190, le commentaire cite AutoCrop3D) et le dossier entier part en une seule requête, sous la limite d'envoi par défaut de 500 MB (VISOR-serve server/config.py:240). Le scan de test hébergé pèse à lui seul 98 611 496 octets (data-manifest.yml:792-794).

Tests client non enregistrés

AutomatedDentalToolsRemote AutoCrop3DRemote/Testing/Python/test_autocrop3d_client.py contient 15 tests, mais AutoCrop3DRemote/CMakeLists.txt n'a ni add_test ni add_subdirectory et Testing/ n'a pas de CMakeLists.txt, donc la suite n'est pas rattachée à ctest. Le CMakeLists.txt:29 racine ajoute bien le module. AutoMatrixRemote et GreedyRegRemote enregistrent les leurs (AutoMatrixRemote/CMakeLists.txt:34, GreedyRegRemote/CMakeLists.txt:34, chacun avec un add_subdirectory(Testing)).

Documentation périmée autour du portage

AutomatedDentalToolsRemote README.md:508-546 décrit encore l'ancien module : un chemin d'icône sous AutoCrop3D/ (le dossier est AutoCrop3DRemote), .nrrd.gz accepté (l'outil le refuse, pipeline.py:37), « Seg quelque part dans le nom » (désormais des mots entiers), une ROI créée par « Volume Rendering ». Le README du paquet annonce aussi 102 tests (README.md:200) alors que la suite en compte 103. Cette page suit le code.

Une ROI orientée est quand même recadrée comme une boîte alignée sur les axes

La rotation n'est pas appliquée ; le recadrage utilise le centre et la taille de la boîte le long des axes d'indices du volume, comme dans le CLI legacy, et le rapport le dit avec roi_orientation_ignored et un avertissement dans le journal (SADT-VISOR AutoCrop3D/pipeline.py:203-211). Le second moteur du module legacy pour les boîtes inclinées, Crop Volume de Slicer, n'a pas d'équivalent sans interface et n'est pas porté (README.md:159-177). La troncature des indices vers zéro est aussi conservée volontairement (pipeline.py:257-264, 272-273).

Treize défauts legacy corrigés, chacun avec un test

Le portage énumère ses treize corrections, chacune avec le nom de son test, dans SADT-VISOR AutoCrop3D/README.md:107-125 ; la suite est passée au vert (103 réussis, 2026-11-09). Le message du panneau Slicer pour les patients sans correspondance en nomme jusqu'à cinq (AutomatedDentalToolsRemote AutoCrop3DRemote/AutoCrop3DRemote.py:129-136).
