ASO sur VISOR : le code

Pour les développeurs : ce que fait le portage VISOR d'ASO dans le code, avec des références file:line, les signatures, les arguments, l'environnement, les différences avec le code legacy et les constats. L'explication lisible du même pipeline, avec les maths, se trouve sur la page de l'atlas. Les deux visionneuses 3D sont sur la page de l'atlas.

VISOR Code Atlas (explication) Page legacy Guide (VISOR)

VISOR exécute les outils dentaires sur un serveur : Slicer ne garde qu'un panneau qui envoie les données et charge les résultats (voir Architecture). Cette page décrit le portage VISOR d'ASO, lu dans le code des dépôts nommés ci-dessous et comparé au module Slicer legacy à 3c67957, qui a sa propre page. « Run for this page » marque ce qui a été exécuté pendant la vérification ; tout le reste a été lu dans le code. Abréviations : ASO/ = SADT-VISOR 6ba2a78, tools/ASO/src/sadt_aso/ ; les autres chemins tools/… sont aussi dans SADT-VISOR ; VISOR-serve = VISOR-serve e9a7e5d, fichiers sous server/ ; Remote = AutomatedDentalToolsRemote 19b95e8 ; legacy = SlicerAutomatedDentalTools 3c67957, où ASO_CBCT_utils/, SEMI_ASO_CBCT/ et PRE_ASO_CBCT/ se trouvent sous ASO_CBCT/, ASO_IOS_utils/ et PRE_ASO_IOS/ sous ASO_IOS/, et ASO_Method/ sous ASO/.

En un paragraphe : ASO tourne un scan pour qu'il tombe dans le repère d'un cas de référence hébergé sur le serveur. Pour un CBCT, il recentre le volume sur l'origine physique, obtient des landmarks (fournis, trouvés à côté du scan ou prédits par ALI_CBCT via le superviseur), en choisit les trois meilleurs, construit une rotation grossière à partir de ce triplet, l'affine par un ICP rigide et rééchantillonne le volume (section 4). Pour un maillage intraoral, il fait la même chose sur les centroïdes des dents ou sur des landmarks fournis, sans jamais segmenter (section 5). ASO lui-même n'a pas de réseau : la seule étape apprise d'une exécution d'ASO est celle d'ALI_CBCT.

3. Le principe, les modes et l'appel à ALI_CBCT

Explication en langage courant et maths : page de l'atlas.

La cible n'est pas un repère analytique mais un cas de référence : les landmarks d'un patient déjà orienté pour un CBCT, deux maillages étiquetés et leurs fichiers de landmarks pour un scan intraoral. Les deux références CBCT publiées portent des ensembles de landmarks disjoints, « Frankfurt Horizontal + Midsagittal has Ba/S/N/RPo/LPo/ROr/LOr, Occlusal + Midsagittal has ANS/IF/PNS/UL6O/UR1O/UR6O » (commentaire, ASO/dispatch.py:309-312), si bien que les landmarks demandés décident de la référence : choose_reference garde l'unique bundle qui les porte tous, et refuse avec la liste de ce que porte chaque bundle si aucun ou plusieurs conviennent (:305-371). Une référence IOS est l'unique bundle qui contient des maillages (:337-345). Le scan de référence n'est jamais lu, seulement ses landmarks (ASO/cbct/pipeline.py:256-273). Le contenu des bundles hébergés n'était pas disponible à la lecture pour cette page.

L'estimation est le schéma legacy en deux étapes dans les deux modalités : un alignement grossier construit à partir de trois landmarks (une translation et deux rotations autour d'axes construits à la main, jamais un ajustement par moindres carrés), puis un vtkIterativeClosestPointTransform rigide qui réapparie les points par plus proche voisin.

Qui décide entre prédiction et landmarks fournis

Explication en langage courant et maths : page de l'atlas.

Le legacy avait deux boutons, Semi et Fully. Dans VISOR, automation existe toujours dans la signature (Semi-Automated par défaut) mais le panneau le masque (ASO/layout.py:61) et le code le traite comme un forçage. La décision se prend sur les données (ASO/dispatch.py:649-668) :

ModalitéDécision
CBCTpar patient : un dossier landmarks donné par l'appelant l'emporte sur tout ; sinon Fully-Automated force la prédiction ; sinon la prédiction ne tourne que pour un patient sans fichier de markups à côté du scan. Elle ne tourne que s'il existe un superviseur (:651-668). Fully-Automated sans landmarks et sans superviseur est refusé avant toute lecture (:256-269, SupervisorRequired).
IOSpar mâchoire : centroïdes forcés avec Fully-Automated, ou quand la mâchoire n'a pas de fichier de landmarks ; sinon les landmarks (ASO/ios/pipeline.py:432-439)

L'appel est unique pour tout le lot : sup.run("ALI_CBCT", input=<recentered scans>, landmarks=[the requested names], model=… only if landmark_model is set) (ASO/dispatch.py:537-542). Aucun output_dir n'est passé (le superviseur décide où écrit l'appelé), ni device, seed ou num_workers. Les landmarks sont demandés par nom, pas par région, de sorte que sept agents tournent au lieu de cinquante-huit (commentaire :521-523). Les sept par défaut sont Ba, S, N, RPo, LPo, ROr, LOr (ASO/__init__.py:51, valeur par défaut de cbct_landmarks ; ASO/catalogs.py:51), l'ensemble de la référence Frankfurt. Les trois appelants AREG ne passent pas cbct_landmarks, ils utilisent donc ces sept et ont besoin d'une référence qui les porte (ASO/dispatch.py:361-371, :435-459) ; VFACE passe sa propre liste pour chaque repère (tools/VFACE/src/sadt_vface/tools.py:136). Les résultats sont relus en parcourant le dossier de sortie d'ALI et en indexant chaque fichier par patient_stem (_collect, :563-596).

4.1 Entrée, DICOM et patients

Explication en langage courant et maths : page de l'atlas.

Un fichier seul est lié dans un dossier à lui ; un dossier est utilisé tel quel ; un .zip a déjà été extrait par le serveur (_as_directory, ASO/dispatch.py:902-926). Le DICOM est détecté (dicom.holds_a_series, ASO/cbct/dicom.py:34-57) ou forcé par le dicom_input masqué ; les séries sont converties sous .aso_work/dicom_nifti, GDCM d'abord et dicom2nifti dans un dossier de transit vide en repli (:60-151 ; ASO/dispatch.py:612-613). Rien n'est écrit dans l'entrée.

discover (ASO/cbct/pipeline.py:199-229) regroupe les fichiers par patient. Le nom du patient est coupé aux frontières de jetons avant l'un des marqueurs connus _lm_Pred, _Scanreg, _MERGED, _scan, _Scan, _Or, _OR, _lm (:34-36, patient_stem :99-129), de sorte que _OR n'attrape plus _ORTHO ; _T1 et _T2 sont volontairement conservés. La clé est le chemin relatif à l'entrée. Les fichiers qui ressemblent à une sortie ASO antérieure ne sont utilisés que si un patient n'a rien d'autre (:132-146). Plusieurs fichiers de markups d'un même patient sont fusionnés en mémoire (load_landmarks, :232-253), là où le MergeJson legacy écrivait un fichier _MERGED dans l'entrée et supprimait les sources.

Avant tout recalage, au moins 3 landmarks demandés doivent exister dans la référence (_check_selection_against_reference, ASO/dispatch.py:435-459 ; appelé à :629).

4.2 Recentrage

Explication en langage courant et maths : page de l'atlas.

Tout ce que faisait encore le PRE_ASO_CBCT legacy, désormais appliqué à chaque scan dans les deux modes (ASO/dispatch.py:707-731) :

center = np.array(image.TransformContinuousIndexToPhysicalPoint(
    (np.array(image.GetSize()) / 2.0).tolist()))
translation = sitk.TranslationTransform(3)
translation.SetOffset((-center).tolist())
resampler.SetTransform(translation.GetInverse())
resampler.SetOutputOrigin((np.array(image.GetOrigin()) - center).tolist())   # ASO/cbct/pipeline.py:276-299

Même taille, même espacement, même direction, seule l'origine bouge : le volume se retrouve centré sur l'origine physique, ce qui permet d'appliquer ensuite la rotation autour de l'origine. Un scan à prédire est écrit dans .aso_work/centered/<key> pour ALI_CBCT (prepare, :302-313) ; les landmarks fournis sont décalés du même vecteur (center_landmarks, :316-326 ; ASO/dispatch.py:756). L'ordre compte et il est commenté dans le code : la conversion voxel vers millimètre d'ALI prend la valeur absolue de l'origine, donc recentrer d'abord et prédire ensuite n'est pas équivalent à l'inverse (ASO/dispatch.py:20-27).

4.3 Landmarks d'ALI_CBCT prédits

Explication en langage courant et maths : page de l'atlas.

Pour les patients qui en ont besoin (section 3), un seul sup.run("ALI_CBCT", …) sur le dossier des scans recentrés, les landmarks demandés par nom (ASO/dispatch.py:513-553). ALI_CBCT garde ses propres constantes (champ de vue 64³, un voxel par pas, rayon d'apparition 10 : tools/ALI/ALI_CBCT/src/sadt_ali_cbct/agent.py:39-41) et trouve ses propres poids ; ASO ne passe aucun des paramètres codés en dur du legacy. ALI écrit un fichier par scan, que _collect rattache au patient (:563-596). La façon dont ALI place un point est décrite sur ALI sur VISOR.

4.4 Recalage calculé

Explication en langage courant et maths : page de l'atlas.

register (ASO/cbct/icp.py:100-180), par patient :

  1. Landmarks utilisables : demandés, présents dans le fichier du patient et dans la référence ; les autres sont listés dans landmarks_dropped avec la raison (:121-128).
  2. Aberrants : tables de distances et de directions des landmarks que partagent les deux fichiers, seuils 15 mm, 0.4 rad et 0.1 rad (:32-34) ; un landmark est écarté si son compte total dépasse le nombre d'étiquettes partagées, ou si son seul compte angulaire en dépasse la moitié (landmarks_to_remove, :64-97). Moins de 3 restants : RegistrationError, ce patient échoue (:134-138).
  3. Meilleur triplet : tous les triplets ordonnés sont essayés quand il y en a au plus max_triplets (7 landmarks en donnent 210, 14 en donnent 2184), sinon un échantillon tiré de default_rng(seed) ; le gagnant est le triplet dont l'alignement grossier laisse la plus petite distance moyenne (best_triplet, ASO/geometry.py:323-381). Déterministe, là où le legacy tirait dans le générateur global.
  4. Alignement grossier (_Alignment et init_icp, ASO/geometry.py:237-320) : une translation sur le premier landmark, une rotation alignant premier→deuxième, puis une rotation autour de cet axe alignant premier→troisième. Les valeurs absolues composante par composante du legacy sont conservées : 
    angle, axis = _angle_and_axis(self._pairs(first, second),
                              _scaled(np.absolute(moved[second] - moved[first])))
self.axis = np.absolute(self.aligned[second] - self.aligned[first])   # ASO/geometry.py:266-275
    En CBCT, la translation est calculée et pas mise dans la matrice, car les deux volumes sont déjà sur l'origine (include_translation=False, ASO/cbct/icp.py:145-150).
  5. ICP : vtkIterativeClosestPointTransform, corps rigide, 1000 itérations, départ par mise en correspondance des centroïdes ; sa translation est mise à zéro (_icp_matrix, :199-212 ; :155).
  6. Composition : 
    rotations = sitk.CompositeTransform(3)
for step in reversed(transform_steps[1:]):      # skips the coarse translation
    rotations.AddTransform(step)
full = sitk.CompositeTransform(rotations)
full.AddTransform(pre_transform)                # the recentering
resample_transform=rotations.GetInverse(), full_transform=full.GetInverse()   # ASO/cbct/icp.py:162-174

La structure est celle du legacy (TransformList parcourue à rebours depuis l'indice 1, puis la transformation PRE_ASO ajoutée, puis l'inverse : legacy SEMI_ASO_CBCT/SEMI_ASO_CBCT.py et ASO_CBCT_utils/utils.py, voir la page legacy). La différence est l'origine du recentrage : le legacy le lisait dans un .tfm produit par PRE_ASO_CBCT (identité s'il est absent), VISOR le calcule dans la même exécution.

4.5 L'orientation, écrite en toutes lettres

Explication en langage courant et maths : page de l'atlas.

Notation: p→A est le landmark A sur le scan à orienter, q→A le même landmark sur la référence ; (A,B,C) est le triplet retenu par la recherche. Les formules sont celles du legacy, et le code VISOR calcule les mêmes quantités.

La translation superpose les premiers landmarks pour que les rotations puissent être calculées ; en CBCT elle est ensuite écartée de la matrice (include_translation=False, ASO/geometry.py:313-318 ; ASO/cbct/icp.py:148-150) et du composite (transform_steps[1:], :165), parce que le volume a d'abord été recentré sur l'origine. En IOS elle est conservée : deux maillages ne partagent aucune origine (ASO/ios/icp.py:89-97).

Les barres sont une valeur absolue composante par composante, pas une norme (np.absolute, ASO/geometry.py:232, :267). Les deux vecteurs sont repliés dans l'octant positif avant de prendre l'angle, si bien qu'une paire de landmarks orientée dans un sens et sa contrepartie de référence orientée dans le sens opposé donnent le même vecteur. VISOR le garde exprès : le portage reproduit le résultat du legacy.

θ1=arccos(v→2⋅v→1∥v→2∥∥v→1∥) , a→1=v→2×v→1

Chaque vecteur est d'abord divisé par sa plus grande composante (_scaled, ASO/geometry.py:132-153), une mise à l'échelle positive qui s'annule dans le quotient et dans le produit vectoriel. Deux garde-fous sont nouveaux dans VISOR : le cosinus est borné à [-1, 1] avant arccos, et des landmarks confondus ne donnent aucune rotation au lieu de NaN (:156-170).

L'axe de la seconde rotation n'est pas un produit vectoriel mais la direction premier→deuxième qui vient d'être alignée, elle-même repliée par np.absolute (self.axis, ASO/geometry.py:275) ; son angle vient du troisième landmark (finish, :277-290). L'axe est la copie repliée, donc le roulis ne conserve ce qu'a fait la première rotation que si le vecteur tourné n'a aucune composante négative (ou aucune positive) ; sinon il tourne autour d'un vecteur qui pointe ailleurs. L'angle est l'arccos non signé, appliqué dans le sens antihoraire autour de l'axe.

R=[α2+β2−γ2−δ22(βγ+αδ)2(βδ−αγ)2(βγ−αδ)α2+γ2−β2−δ22(γδ+αβ)2(βδ+αγ)2(γδ−αβ)α2+δ2−β2−γ2]

rotation_matrix (ASO/geometry.py:101-129) écrit exactement ces neuf termes, avec le moins sur la partie vectorielle ; un axe de longueur nulle renvoie l'identité au lieu d'une matrice de NaN.

La colonne de translation de l'ICP est mise à zéro (ASO/cbct/icp.py:155), donc en CBCT le composite est une pure rotation autour de l'origine ; la translation de recentrage n'est ajoutée qu'à la transformation écrite sur disque (:168-170). C'est une recherche suivie d'un ICP par plus proche voisin, pas un ajustement par moindres carrés (Kabsch) sur les landmarks ; la page legacy écrit ce que calculerait un tel ajustement (sa section 4.5).

5. Scans intraoraux, pas à pas

5.1 Patients et mâchoires

Explication en langage courant et maths : page de l'atlas.

discover (ASO/ios/pipeline.py:122-180) apparie chaque maillage à un fichier de landmarks facultatif par patient et mâchoire, tous deux lus dans le nom de fichier avec le vocabulaire partagé sadt_naming.JAW_TOKENS (:38, patient_and_jaw :47-110). 5.2 Centroïdes des dents

Explication en langage courant et maths : page de l'atlas.

Pour une mâchoire sans fichier de landmarks, ou toute mâchoire en Fully-Automated (_fully_automated_matrix, ASO/ios/pipeline.py:442-476) :

  1. Le maillage doit porter un tableau d'étiquettes (Universal_ID, PredictedID ou UniversalID, ASO/markups.py:19) ; sinon segment_unlabelled lève « Segment it first, or use the semi-automated mode with landmark files » (ASO/ios/pipeline.py:367-382). Si aucun maillage du lot n'est étiqueté, toute la requête est refusée en nommant Crown_Seg (ASO/dispatch.py:868-895).
  2. Alignement grossier sur les 3 ou 4 dents cochées de la mâchoire (pre_icp.align, ASO/ios/pre_icp.py:20-47) : centroïdes des sommets portant chaque étiquette (mean_teeth, ASO/ios/icp.py:32-49), triés en gauche, milieu, droite par numéro Universal, les deux dents du milieu étant moyennées quand il y en a quatre ; le plan des trois points est tourné sur celui de la référence, puis la direction dans le plan, puis les centroïdes sont amenés à coïncider.
  3. Recalage fin sur les centroïdes des mêmes dents : recherche du triplet, alignement grossier avec sa translation, ICP rigide de 100 itérations (register, ASO/ios/icp.py:61-98, :106-119). Les deux ensembles de points doivent avoir les mêmes clés, sinon la mâchoire échoue en nommant les dents manquantes (:72-79) ; le legacy sous-échantillonnait en silence le plus long.
  4. La matrice est fine @ coarse (ASO/ios/pipeline.py:476). Dans register, l'ICP est composé après l'alignement grossier, M_icp @ M_init, là où le legacy construisait M_init @ M_icp (ASO/ios/icp.py:11-15, :98).

5.3 Landmarks fournis

Explication en langage courant et maths : page de l'atlas.

Pour une mâchoire avec un fichier de landmarks (_semi_automated_matrix, ASO/ios/pipeline.py:479-499) : les clés sont construites en <tooth><type> à partir de ios_teeth × ios_landmark_types, réparties par mâchoire (ASO/catalogs.py, landmark_keys_by_jaw ; appelé à ASO/dispatch.py:826), sélectionnées dans les deux fichiers, celles qui manquent étant nommées dans l'erreur (select_keys, ASO/ios/icp.py:52-58), puis le même register que ci-dessus. Les fichiers de landmarks sont lus en .mrk.json ou .json, positions prises telles qu'écrites (ASO/markups.py:23, :35-64).

5.4 Occlusion

Explication en langage courant et maths : page de l'atlas.

ios_occlusion a trois valeurs (DRIVING_JAW, ASO/catalogs.py:127-131). Avec Upper drives Lower ou Lower drives Upper, la mâchoire directrice est recalée d'abord et sa matrice est appliquée telle quelle à l'autre mâchoire, ce qui préserve l'occlusion (_ordered_jaws et _matrix_for, ASO/ios/pipeline.py:390-415). Un seul argument remplace les deux cases à cocher legacy qui pouvaient se contredire.

10. Constats dans VISOR

Explication en langage courant et maths : page de l'atlas.

Piège · un fichier de landmarks mal nommé est remplacé en silence par une prédiction

Avec un superviseur (que le serveur fournit à un outil qui en demande un), un patient sans fichier de markups apparié à son scan est envoyé à la prédiction, même en Semi-Automated : _needs_prediction renvoie not patients[key]["markups"] (ASO/dispatch.py:651-661), la liste des orphelins est vidée dès qu'un patient est prédit (:684-685), et le rapport indique landmark_source valant ALI_CBCT ou mixed. Run for this page avec les helpers de tools/ASO/tests/test_run.py : un scan P1_CBCT.nii.gz avec un fichier P1.mrk.json (un nom qui ne s'apparie pas), Semi-Automated, un faux superviseur : landmark_source = ALI_CBCT, unmatched_markups = [], le cas orienté avec le statut ok. Sans superviseur, la même entrée échoue et nomme le fichier (landmark_source = alongside the scans, unmatched_markups = ['P1.mrk.json']). Les points placés à la main sont ignorés sans avertissement ; le panneau masque automation, l'utilisateur ne peut donc pas imposer une exécution Semi stricte.

Piège · le rapport n'enregistre ni max_triplets ni seed

La docstring de run() dit que le rapport les enregistre (ASO/__init__.py:119-121) ; aucune clé de ce nom n'est écrite nulle part dans les sources de l'outil (le rapport est construit dans ASO/dispatch.py à :155-161, :616-617, :670, :694, :819, :823, :931). Le README de l'outil répète l'affirmation (tools/ASO/README.md:166). Lu dans le code.

Piège · un max_triplets de 0 ou moins fait perdre tout le lot CBCT avec un message trompeur

L'échantillon est vide et best_triplet lève « Need at least three landmarks… » (ASO/geometry.py:353-357, :378-379) ; seule RegistrationError est interceptée par patient CBCT (ASO/dispatch.py:797), si bien que la ValueError met fin à toute l'exécution. Run for this page : deux patients valides, Semi-Automated, max_triplets=0 : orient lève cette ValueError et aucun patient n'est orienté. L'argument est masqué, donc seul un appel direct à l'API l'atteint (la règle de masquage est la liste des arguments techniques de VISOR-serve server/registry/conventions.py:48-54, qui nomme seed et max_triplets ; layout.py n'a aucune entrée pour eux).

Piège · l'IOS avec un nombre de dents inhabituel échoue tard

Lu dans le code, non exécuté. Sans fichier de landmarks, une mâchoire est recalée sur les centroïdes des dents, ce qui demande exactement 3 ou 4 dents (ASO/ios/pre_icp.py:26-29). Le contrôle amont hors mode Fully-Automated exige seulement que dents fois types fassent au moins 3 par mâchoire (ASO/dispatch.py:494-506) ; 5 dents cochées passent donc, et chaque mâchoire échoue ensuite après la lecture de son maillage.

Piège · le système de coordonnées d'un fichier de landmarks n'est jamais vérifié

Aussi vrai dans le legacy. load_landmarks lit chaque position telle qu'écrite (ASO/markups.py:35-64) ; la seule occurrence de coordinateSystem dans l'outil est le "LPS" qu'il écrit (:75). Un fichier exporté en RAS est lu avec x et y inversés. Lu dans le code.

Note · choix silencieux

Quand plusieurs scans partagent un dossier de patient, seul le premier, dans l'ordre trié, est conservé, sans mention dans le rapport (ASO/cbct/pipeline.py:219-228 ; lu dans le code, non exécuté). Les suffixes _Or et _OR sont codés en dur pour couper les noms de patients (:34-36), alors que la détection des sorties prend le suffixe de l'appelant (:132-146). Run for this page : sur un dossier contenant P1.nii.gz et P1_Reo.nii.gz, discover avec output_suffix="Reo" renvoie deux patients, P1 et P1_Reo (la sortie précédente, qui serait orientée à nouveau), alors qu'avec Or et P1_Or.nii.gz il renvoie P1 seul.

Note · des documents qui ne correspondent plus au code

Le README de l'outil dit « the server does not implement supervisors yet » (tools/ASO/README.md:111) ; il les implémente (VISOR-serve execution/runner.py:1685) et ASO en utilise un. VISOR-serve server/base.py:208 parle de 130 landmarks pour ASO là où la signature en a 115. Une docstring du client Remote dit que le mode est « asked for, never guessed » (ASORemote/ASORemote.py:75-77), alors que automation est masqué (ASO/layout.py:61) ; modality est celui qui est demandé. segment_unlabelled décrit encore la segmentation des couronnes comme « not implemented yet » (ASO/ios/pipeline.py:367-376), alors que Crown_Seg existe désormais comme outil serveur ; ASO ne l'appelle simplement pas.

Vérifié · ni GPU, ni réseau, ni torch dans ASO lui-même

L'environnement ASO ne déclare ni torch ni pytorch3d (tools/ASO/pyproject.toml:8-21). Le seul usage du GPU dans une exécution d'ASO est la prédiction d'ALI_CBCT, en CBCT Fully-Automated sans landmarks fournis (tools/ALI/ALI_CBCT/src/sadt_ali_cbct/__init__.py:94, device = "cuda" par défaut).

Vérifié · une orientation reproductible

La recherche du triplet est exhaustive jusqu'à max_triplets et à graine fixée au-delà, avec un générateur local (ASO/geometry.py:323-391) ; le legacy utilisait le np.random global, si bien que la même requête pouvait s'orienter différemment d'une exécution à l'autre. Les tests de l'outil comparent la géométrie portée aux fonctions legacy (tools/ASO/tests/test_geometry_equivalence.py, qui fait partie des 205 tests exécutés pour cette page).
