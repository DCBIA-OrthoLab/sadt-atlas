ADTLib : le code

Pour les développeurs : le code partagé que chaque module importe, avec les modules qu'il a remplacés, le nombre de copies, les défauts trouvés dans le code et ce que les tests verrouillent. La vue d'ensemble lisible, avec l'animation du protocole de progression, se trouve sur la page de l'atlas.

Code partagé Code Atlas (explication)
Note

Cette page décrit ADT/ADTLib sur upstream/main, et c'est la seule page de cet atlas qui documente du code qu'aucun utilisateur n'ouvre jamais. Elle est là parce que le comportement des modules en dépend désormais : un lecteur qui cherche ce qu'AREG fait d'une surface atterrit dans ADTLib/io/surface.py, pas dans AREG/.

1. Où il se situe

Explication en langage courant et maths : page de l'atlas.

Sous tout le reste, et dans aucune chaîne. ADTLib est déclaré en premier dans le CMakeLists.txt de l'extension, « Shared code, declared before the modules that import it », et les vingt répertoires d'outils importent depuis lui. Il n'a pas de Process propre, rien à lancer et rien à télécharger.

Sa taille, comptée sur l'arborescence : vingt et un fichiers, environ 3 100 lignes (3 144), qui remplacent des copies atteignant ensemble plusieurs milliers (les en-têtes donnent la taille des copies, pas celle du paquet). L'en-tête de theming.py représente à lui seul 1 926 lignes de doublon, et env/conda.py 656 réparties sur quarante fonctions.

2. Comment un module y accède

Explication en langage courant et maths : page de l'atlas.

Slicer place le répertoire qt-scripted-modules de chaque extension sur sys.path, si bien qu'un simple import ADTLib fonctionne depuis n'importe quel module de l'extension et depuis un CLI scripté. Une troisième voie compte plus qu'il n'y paraît : une fois que les modules publient les chemins de recherche de modules de Slicer dans l'environnement Conda shapeaxi, ADTLib est importable là aussi. C'est sur cela que repose ADTLib.env.install_pytorch : aucun widget ne l'importe jamais, il est lancé par l'interpréteur Conda avec python -m ADTLib.env.install_pytorch.

Piège

ADTLib/__init__.py et io/__init__.py doivent rester sans imports. Ils tournent aussi dans l'environnement Conda léger, qui n'a ni vtk, ni qt, ni slicer. Un seul import de l'un d'eux au niveau du paquet casserait l'import de chaque sous-module sur cette voie. Les sous-modules qui en ont besoin les importent eux-mêmes. package_root() existe pour la même raison : il renvoie le répertoire qui doit figurer dans PYTHONPATH pour que le côté Conda trouve le paquet.

3. Le contrat partagé

Explication en langage courant et maths : page de l'atlas.

Trois modules portent ce que les outils se promettent entre eux, plutôt que ce qu'ils calculent.

ModuleCe qu'il a remplacéCe qu'il tranche
method.pysix déclarations Method(ABC), 934 lignes qui sont surtout du contrat plutôt que du codeun noyau (Process, TestProcess, NumberScan, search) plus trois mixins : landmarks, cases à cocher, DICOM, car les six ne se recouvraient pas au hasard : mesurés côte à côte, trois groupes ressortaient nettement
requests.pyrien ; il nomme ce qui n'avait jamais été écrit473 accès kwargs["..."] sans aucune liste nulle part. Chaque famille déclare désormais ses champs, une clé inconnue est rejetée à la construction, et une clé absente vaut MISSING : elle lève la même KeyError qu'avant, au même endroit, au lieu de devenir une valeur vide silencieuse
progress_protocol.pytrois conventions non documentées sur un seul canalvoir ci-dessous
Défaut confirmé dans le code

Slicer multiplie <filter-progress> par cent, et ce facteur n'est écrit nulle part. Il a produit trois conventions dans un seul dépôt : un CLI qui affiche la fraction 0.42 fait apparaître 42 et la barre avance, c'est l'usage prévu ; un CLI qui affiche l'entier 2 fait apparaître 200, qu'aucune barre ne peut représenter, si bien que les interfaces comparent à 200 pour savoir qu'un patient de plus est terminé, et le CLI l'envoie sous forme d'impulsion 0 → 2 → 0 parce que Slicer ne prévient le widget que lorsque la valeur change ; et AMASSS, qui reçoit les deux, devinait à l'exécution laquelle il tenait (if progress > 1: progress /= 100). Les trois sont maintenant nommées, avec des constantes qui portent la valeur telle que l'interface la voit, puisque c'est là que se fait la comparaison.

Piège

Un wheel pytorch3d dont le tag ne correspond pas au torch installé plante avec undefined symbol à l'import, et non à l'installation. Le tag 0.7.9+pt2110cu128 signifie torch 2.11.0 et CUDA 12.8 ; l'index est ImageMindAnalytics.github.io/pytorch3d-wheels, car PyPI ne publie aucun wheel pour les combinaisons récentes et l'index historique fbaipublicfiles s'arrêtait à Python 3.9 / torch 2.0. torch est aussi installé ici, puisque calculer le tag à partir du torch présent ne marche que si ce torch a un wheel : condaCreateEnv(["torch>=2.8,<2.13", …]) a résolu en 2.12.1+cu130 le 2026-09-16, une combinaison que l'index ne publie pas.

7. Ce que les tests verrouillent

Explication en langage courant et maths : page de l'atlas.

ADTLib livre 22 tests dans ADT/Testing/Python/, contre deux auparavant. C'est ce qui se rapproche le plus d'une spécification pour cette couche partagée, et plusieurs ont été écrits parce que le grep ne suffisait pas.

test_pip_requirements.py en dit la raison dans son propre en-tête : chaque paire (library, version) que le dépôt confie à pip doit être analysable, car f'{lib}=={version}' n'est correct que tant que chaque entrée porte une version nue, et trois modules avaient discrètement gagné une contrainte avec opérateur, produisant dicom2nifti==>=2.6.2, que pip refuse net. Le défaut est invisible sur une machine qui a déjà la bibliothèque, si bien que lancer le module en local ne le montre jamais. Le test parcourt le code source plutôt qu'une liste écrite à la main, donc une liste qui gagnera une contrainte demain est couverte sans que personne ait à s'en souvenir.

Les autres nomment des comportements que décrivent les pages des outils : test_ali_cbct_bounds.py, test_ali_cbct_budget.py, test_ali_progress_contract.py, test_aso_cbct_report_is_not_landmarks.py, test_aso_ios_landmark_intersection.py, test_areg_review_skips_the_report.py, test_output_folder_survives_mode_switch.py, plus les tests unitaires des modules partagés eux-mêmes, test_fs, test_labels, test_naming, test_surface, test_requests, test_progress_protocol, test_deps, test_cuda_channel, test_context_managers, test_button_style.

Vérifié

Lancé le 2026-11-10 avec PythonSlicer -m unittest discover dans ADT/Testing/Python (Slicer 5.12.4, copie de l'arborescence 3c67957) : avec torch 2.2.0 disponible, 217 tests, tous réussis. Avec torch rendu non importable, la même exécution rapporte 192 tests : 188 réussis et 4 en erreur. Les quatre sont ModuleNotFoundError: torch à l'import des quatre fichiers de test d'ALI_CBCT, qui atteignent à l'import ADTLib/env/cuda.py et son preferred_device(). Elles tiennent à l'environnement, pas au code : sans torch, pas de sonde de périphérique.

8. Lire cette couche

Explication en langage courant et maths : page de l'atlas.

Deux habitudes la rendent lisible. D'abord, chaque en-tête de module dit ce qu'il a remplacé et sur quoi les copies divergeaient : c'est là que vit le raisonnement, pas sur cette page. Ensuite, la ligne qui revient dans ces en-têtes est ce qui a été laissé de côté : les variantes qui divergent vraiment restent dans leur outil. TestScan et TestModel ne sont pas dans method.py parce que leurs arités diffèrent nettement d'un outil à l'autre, jusqu'à quatre arguments dans AREG, et que getModelUrl renvoie une sélection propre à chaque outil. Les remonter aurait obligé à inventer un contrat qu'aucun des six ne respectait.
