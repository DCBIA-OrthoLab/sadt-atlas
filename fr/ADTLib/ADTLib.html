ADTLib

Ce n'est pas un outil : ni interface, ni chaîne, ni modèle. ADTLib est le code que les vingt modules importent, et presque chacun de ses fichiers existe parce que la même fonction avait été copiée entre deux et quinze fois. L'en-tête de chaque module consigne combien de copies il a remplacées et sur quoi elles avaient commencé à diverger : ce décompte est le propos de cette page. Le détail fichier par fichier se trouve sur la page de code.

Code partagé Code (développeurs)

Cette page décrit ADT/ADTLib sur upstream/main, et c'est la seule page de cet atlas qui documente du code qu'aucun utilisateur n'ouvre jamais. Elle est là parce que le comportement des modules en dépend désormais : un lecteur qui cherche ce qu'AREG fait d'une surface atterrit dans le lecteur de surfaces partagé, pas dans AREG/. Preuve.

1. Où il se situe

Sous tout le reste, et dans aucune chaîne. ADTLib est déclaré en premier dans le fichier de build de l'extension, « Shared code, declared before the modules that import it », et les vingt répertoires d'outils importent depuis lui. Il n'a pas de traitement propre, rien à lancer et rien à télécharger.

Sa taille, comptée sur l'arborescence : vingt et un fichiers, environ 3 100 lignes (3 144 comptées), qui remplacent des copies atteignant ensemble plusieurs milliers. L'en-tête du module de thème représente à lui seul 1 926 lignes de doublon, et les utilitaires conda 656 réparties sur quarante fonctions.

2. Comment un module y accède

Slicer place le répertoire de modules scriptés de chaque extension sur le chemin d'import, si bien qu'un simple import ADTLib fonctionne depuis n'importe quel module de l'extension et depuis un module en ligne de commande. Une troisième voie compte plus qu'il n'y paraît : une fois que les modules publient les chemins de recherche de modules de Slicer dans l'environnement Conda shapeaxi, ADTLib est importable là aussi. C'est sur cela que repose l'installeur de PyTorch : aucun panneau ne l'importe jamais, il est lancé comme module par l'interpréteur Conda.

Une conséquence : les fichiers de premier niveau du paquet doivent rester sans imports, car ils tournent aussi dans l'environnement Conda léger, qui n'a ni vtk, ni Qt, ni Slicer. Preuve.

3. Le contrat partagé

Trois modules portent ce que les outils se promettent entre eux, plutôt que ce qu'ils calculent.

ModuleCe qu'il a remplacéCe qu'il tranche
methodSix déclarations de méthode, 934 lignes qui sont surtout du contrat plutôt que du codeUn noyau (process, test process, comptage des scans, recherche de fichiers) plus trois mixins, pour les landmarks, les cases à cocher et le DICOM, car les six ne se recouvraient pas au hasard : mesurés côte à côte, trois groupes ressortaient nettement
requestsRien ; il nomme ce qui n'avait jamais été écrit473 lectures d'une clé de requête sans aucune liste nulle part. Chaque famille déclare désormais ses champs, une clé inconnue est rejetée à la construction, et une clé absente lève la même erreur qu'avant, au même endroit, au lieu de devenir une valeur vide silencieuse
protocole de progressionTrois conventions non documentées sur un seul canalVoir l'animation ci-dessous

Ce facteur 100 n'est écrit nulle part, et il a produit trois conventions dans un seul dépôt. Un outil qui affiche la fraction fait avancer la barre, c'est l'usage prévu. Un outil qui affiche l'entier 2 fait apparaître 200, si bien que les interfaces comparent à 200 pour savoir qu'un patient de plus est terminé, et l'outil l'envoie sous forme d'impulsion 0, 2, 0 parce que Slicer ne prévient le panneau que lorsque la valeur change. AMASSS, qui reçoit les deux, devinait à l'exécution laquelle il tenait. Les trois sont maintenant nommées, avec des constantes qui portent la valeur telle que l'interface la voit, puisque c'est là que se fait la comparaison. Preuve.

4. L'environnement

Quatre modules, et la seule partie d'ADTLib qui sorte du processus.

ModuleCe qu'il a remplacé
utilitaires condaSix copies de chaque fonction, quarante fonctions, 656 lignes, dérivées en trois formes, dont une contient encore un return inatteignable qui lisait deux noms que rien n'avait liés

Pourquoi le tag est calculé : un wheel pytorch3d dont le tag ne correspond pas au torch installé plante avec une erreur undefined symbol à l'import, et non à l'installation. Le tag 0.7.9+pt2110cu128 signifie torch 2.11.0 et CUDA 12.8, et PyPI ne publie aucun wheel pour les combinaisons récentes, d'où l'usage d'un index dédié. Preuve.

7. Ce que les tests verrouillent

ADTLib livre 22 tests, contre deux auparavant. C'est ce qui se rapproche le plus d'une spécification pour cette couche partagée, et plusieurs ont été écrits parce que le grep ne suffisait pas. L'un vérifie que chaque bibliothèque et chaque version que le dépôt confie à pip est analysable : trois modules avaient discrètement gagné une contrainte avec opérateur, produisant une exigence que pip refuse net. Le défaut est invisible sur une machine qui a déjà la bibliothèque, si bien que lancer le module en local ne le montre jamais. Le test parcourt le code source plutôt qu'une liste écrite à la main, donc une liste qui gagnera une contrainte demain est couverte.

Les autres nomment des comportements que décrivent les pages des outils (bornes, budget et contrat de progression d'ALI, règles de rapport d'ASO et d'AREG, dossier de sortie qui survit à un changement de mode), plus les tests unitaires des modules partagés eux-mêmes. Lancée sous un PythonSlicer ordinaire, la suite rapporte 188 tests et 4 erreurs, toutes quatre dues à un torch manquant dans les tests d'ALI_CBCT : une propriété de l'environnement, pas du code. Preuve.

8. Lire cette couche

Deux habitudes la rendent lisible. D'abord, chaque en-tête de module dit ce qu'il a remplacé et sur quoi les copies divergeaient : c'est là que vit le raisonnement, pas sur cette page. Ensuite, la ligne qui revient dans ces en-têtes est ce qui a été laissé de côté : les variantes qui divergent vraiment restent dans leur outil. Les méthodes de test et la fonction de choix de modèle ne sont pas dans la classe de méthode partagée parce que leurs arités diffèrent nettement d'un outil à l'autre ; les remonter aurait obligé à inventer un contrat qu'aucun des six ne respectait.

9. Problèmes connus

  • Les fichiers de premier niveau du paquet doivent rester sans imports, sinon tout import de sous-module casse dans l'environnement Conda léger. Preuve.
  • Le facteur de progression de 100 n'est documenté nulle part, et il a produit trois conventions. Preuve.
  • Un wheel pytorch3d qui ne correspond pas au torch installé plante à l'import, pas à l'installation. Preuve.
  • Vérifié : avec torch disponible, les 217 tests réussissent ; sans lui, 188 réussissent et 4 fichiers de test échouent à l'import, tous quatre pour cause de torch manquant. Preuve.
