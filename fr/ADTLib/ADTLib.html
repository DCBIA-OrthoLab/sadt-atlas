ADTLib

Pas un outil : ni interface, ni pipeline, ni modèle. ADTLib est le code que les vingt modules importent, et presque chacun de ses fichiers existe parce que la même fonction avait été copiée entre deux et quinze fois. L'en-tête de chaque module consigne combien de copies il a remplacées et sur quoi ces copies avaient commencé à diverger : ce décompte est l'objet de cette page.

Note

Cette page décrit ADT/ADTLib sur upstream/main, et c'est la seule page de cet atlas qui documente du code qu'aucun utilisateur n'ouvre jamais. Elle est là parce que le comportement des modules en dépend désormais : un lecteur qui cherche ce que fait AREG d'une surface finit dans ADTLib/io/surface.py, pas dans AREG/.

1. Où il se place

Sous tout le reste, et dans aucun pipeline. ADTLib est déclaré en premier dans le CMakeLists.txt de l'extension, « Shared code, declared before the modules that import it », et les vingt dossiers d'outils importent depuis lui. Il n'a aucun Process propre, rien à lancer et rien à télécharger.

Sa propre mesure de lui-même, d'après les en-têtes de modules : vingt et un modules, environ 3 300 lignes, qui remplacent des copies atteignant ensemble plusieurs milliers. L'en-tête de theming.py à lui seul compte 1 926 lignes de doublon, et env/conda.py 656 réparties sur quarante fonctions.

2. Comment un module l'atteint

Slicer place le répertoire qt-scripted-modules de chaque extension dans sys.path, donc un simple import ADTLib fonctionne depuis n'importe quel module de l'extension et depuis un CLI scripté. Une troisième voie compte plus qu'il n'y paraît : une fois que les modules publient les chemins de recherche de modules de Slicer dans l'environnement Conda shapeaxi, ADTLib est importable là aussi. C'est ce sur quoi s'appuie ADTLib.env.install_pytorch : il n'est jamais importé par un widget, il est lancé par python -m ADTLib.env.install_pytorch avec l'interpréteur Conda.

Piège

ADTLib/__init__.py et io/__init__.py doivent rester sans import. Ils s'exécutent aussi dans l'environnement Conda léger, qui n'a ni vtk, ni qt, ni slicer. Un seul import de l'un d'eux au niveau du paquet casserait l'import de tous les sous-modules par cette voie. Les sous-modules qui en ont besoin les importent eux-mêmes. package_root() existe pour la même raison : il renvoie le répertoire qui doit figurer dans PYTHONPATH pour que le côté Conda trouve le paquet.

3. Le contrat partagé

Trois modules portent ce que les outils se promettent les uns aux autres, plutôt que ce qu'ils calculent.

ModuleCe qu'il a remplacéCe qu'il tranche
method.pysix déclarations Method(ABC), 934 lignes faites surtout de contrat plutôt que de codeun noyau (Process, TestProcess, NumberScan, search) plus trois mixins, repères, cases à cocher, DICOM, parce que les six ne se recouvraient pas au hasard : mesurés côte à côte, trois grappes ressortaient nettement
requests.pyrien ; il nomme ce qui n'avait jamais été écrit473 accès kwargs["..."] sans liste nulle part. Chaque famille déclare désormais ses champs, une clé inconnue est rejetée à la construction, et une clé manquante vaut MISSING : elle lève le même KeyError qu'avant, au même endroit, au lieu de devenir une valeur vide silencieuse
progress_protocol.pytrois conventions non documentées sur un même canalvoir ci-dessous
Défaut confirmé dans le code

Slicer multiplie <filter-progress> par cent, et ce facteur n'est écrit nulle part. Il a produit trois conventions dans un seul dépôt : un CLI qui imprime la fraction 0.42 fait apparaître 42 et la barre avance, c'est l'usage prévu ; un CLI qui imprime l'entier 2 fait apparaître 200, ce qu'aucune barre ne peut représenter, si bien que les interfaces comparent à 200 pour apprendre qu'un patient de plus est terminé, et le CLI l'envoie sous forme d'impulsion 0 → 2 → 0 parce que Slicer ne notifie le widget que quand la valeur change ; et AMASSS, qui reçoit les deux, devinait à l'exécution laquelle il tenait (if progress > 1: progress /= 100). Les trois sont maintenant nommées, avec des constantes portant la valeur telle que l'interface la voit, puisque c'est là que la comparaison a lieu.

4. L'environnement

Quatre modules, et la seule partie d'ADTLib qui sort du processus.

Piège

Une roue pytorch3d dont l'étiquette ne correspond pas au torch installé plante avec undefined symbol à l'import, pas à l'installation. L'étiquette 0.7.9+pt2110cu128 signifie torch 2.11.0 et CUDA 12.8 ; l'index est ImageMindAnalytics.github.io/pytorch3d-wheels, car PyPI ne publie aucune roue pour les combinaisons récentes et l'ancien index fbaipublicfiles s'est arrêté à Python 3.9 / torch 2.0. torch est lui aussi installé ici, puisque calculer l'étiquette à partir du torch qui se trouve présent ne fonctionne que si ce torch a une roue : condaCreateEnv(["torch>=2.8,<2.13", …]) se résolvait en 2.12.1+cu130 le 2026-09-16, une combinaison que l'index ne publie pas.

7. Ce que les tests fixent

ADTLib livre 22 tests dans ADT/Testing/Python/, contre deux auparavant. C'est ce qui ressemble le plus à une spécification pour cette couche partagée, et plusieurs ont été écrits parce qu'un grep ne suffisait pas.

test_pip_requirements.py dit pourquoi dans son propre en-tête : chaque paire (library, version) que le dépôt passe à pip doit s'analyser correctement, parce que f'{lib}=={version}' n'est correct que tant que chaque entrée porte une version nue, et trois modules avaient discrètement acquis une contrainte avec un opérateur, produisant dicom2nifti==>=2.6.2, que pip refuse net. Le défaut est invisible sur une machine qui a déjà la bibliothèque, donc aucune exécution locale du module ne le montre. Le test parcourt les sources plutôt qu'une liste écrite à la main, si bien qu'une liste qui gagne une contrainte demain est couverte sans que personne ait à s'en souvenir.

Les autres nomment des comportements que décrivent les pages d'outils : test_ali_cbct_bounds.py, test_ali_cbct_budget.py, test_ali_progress_contract.py, test_aso_cbct_report_is_not_landmarks.py, test_aso_ios_landmark_intersection.py, test_areg_review_skips_the_report.py, test_output_folder_survives_mode_switch.py, plus les tests unitaires des modules partagés eux-mêmes, test_fs, test_labels, test_naming, test_surface, test_requests, test_progress_protocol, test_deps, test_cuda_channel, test_context_managers, test_button_style.

Vérifié

Lancée sous un PythonSlicer nu, la suite rapporte 188 tests et 4 erreurs. Les quatre sont des ModuleNotFoundError: torch dans les tests d'ALI_CBCT, qui atteignent preferred_device() d'ADTLib/env/cuda.py à l'import. Elles tiennent à l'environnement, pas au code : pas de torch, pas de sonde de périphérique.

8. Lire cette couche

Deux habitudes la rendent lisible. D'abord, l'en-tête de chaque module dit ce qu'il a remplacé et sur quoi les copies divergeaient : c'est là que se trouve le raisonnement, pas dans cette page. Ensuite, la ligne qui revient dans ces en-têtes est ce qui a été laissé de côté : les variantes qui divergent réellement restent dans leur outil. TestScan et TestModel ne sont pas dans method.py parce que leurs arités diffèrent nettement d'un outil à l'autre, jusqu'à quatre arguments dans AREG, et que getModelUrl renvoie une sélection propre à chaque outil. Les remonter aurait obligé à inventer un contrat qu'aucun des six n'honorait réellement.
