3. El pipeline

Explicación en lenguaje llano y matemáticas: página del atlas.

3.1 Comprobación de las carpetas y búsqueda de las notas

Explicación en lenguaje llano y matemáticas: página del atlas.

Una ruta notes inexistente es un FileNotFoundError (__init__.py:97-100). Si notes es una carpeta y output_dir es la misma carpeta (con los enlaces simbólicos resueltos), la ejecución se rechaza, porque las extracciones se volverían a leer como notas en la siguiente ejecución (:106-110,320-324). La herramienta crea entonces ella misma output_dir (:116); el legacy confiaba en que el panel lo creara.

El descubrimiento es recursivo y devuelve los archivos ordenados por ruta relativa (readers.py:92-123). Conserva .txt, .pdf y .docx sin distinguir mayúsculas de minúsculas (:33,78-81), omite los nombres que empiezan por ~$ (archivos de bloqueo de Word) o por un punto, y las carpetas llamadas __MACOSX (:60-61,84-90,117-118). La carpeta de salida se excluye cuando está dentro de la entrada (__init__.py:118). Si no se encuentra nada, es un 422 que nombra las tres extensiones (:119-126); el legacy salía con estado 0 en ese caso (legacy CNE_CLI/CNE_CLI.py:137-141).

3.2 Elección y carga del modelo

Explicación en lenguaje llano y matemáticas: página del atlas.

model es obligatorio. Un archivo .gguf se usa tal cual; una carpeta debe contener exactamente un .gguf, buscado de forma recursiva, o la ejecución se rechaza con los candidatos nombrados (extraction.py:89-128). Si la ruta del modelo nombra un tipo de nota y notes_type es el otro, se añade un aviso al informe; no es un rechazo (model_type_hint, extraction.py:131-143; __init__.py:132-142).

CONTEXT_TOKENS = {"TMJ": 6144, "Ortho": 2048}                # extraction.py:49
SYSTEM_PROMPTS = {"TMJ": INSTRUCTION_TMJ, "Ortho": None}      # extraction.py:51

window = context_for(notes_type, context_tokens)              # 0 means the type's default
offloading = wants_gpu and supports_gpu_offload()             # asked before the 4.4 GB load
engine = load_model(model_file, window, seed, -1 if wants_gpu else 0)   # __init__.py:144-165

load_model construye un único llama_cpp.Llama(model_path, n_ctx, n_gpu_layers, seed, verbose=False) para todo el lote (extraction.py:193-203). Su salida verbosa del cargador se captura con contextlib.redirect_stderr y se registra en nivel debug (:63-86), mientras que el legacy redirigía el descriptor de archivo 2 del proceso con os.dup2 y sin finally (legacy CNE_CLI.py:157-171). Toda importación de llama_cpp pasa por engine_module(), que primero intenta abrir el runtime de CUDA del venv (extraction.py:167-177, dependencies.py:65); en la compilación para CPU eso no hace nada. Una petición device = "cuda" en una compilación sin soporte de GPU añade un aviso y gpu_offload: false al informe (__init__.py:145-165,184).

3.4 Consulta al modelo

Explicación en lenguaje llano y matemáticas: página del atlas.

messages = []

La instrucción de TMJ es la cadena del legacy tal cual: "Using the following note, extract structured key-value pairs about the patient's symptoms and diagnoses:" (extraction.py:41-44). Ortho no recibe mensaje de sistema, como en el legacy. La herramienta no compara la longitud de la nota con la ventana: context_for solo rechaza un valor negativo (extraction.py:146-153), y cualquier error lanzado por llama.cpp se captura para esa nota (__init__.py:200-212). En llama-cpp-python 0.3.36 (llama.py:1343-1358) el motor lanza un error solo cuando el prompt por sí solo alcanza n_ctx; en caso contrario max_tokens se reduce a n_ctx menos la longitud del prompt, la nota nunca se trunca, y una generación detenida por ese límite acortado informa finish_reason == "length", lo que hace fallar la nota (__init__.py:293-297). La versión fijada es la 0.3.35, cuyo código no se leyó.

3.5 Lectura de la respuesta y escritura

Explicación en lenguaje llano y matemáticas: página del atlas.

  1. Primero JSON: se analiza el fragmento que va del primer { al último }; un dict bajo "extraction" se desenvuelve; un resultado vacío o un valor JSON que no es un objeto se rechaza (extraction.py:261-275). El recorte es el del legacy.
  2. Después, líneas key: value: una clave empieza con una letra minúscula y contiene letras minúsculas, dígitos, espacios y guiones bajos (hasta 61 caracteres, los espacios pasan a _, extraction.py:230,296), al menos el 60 % de las líneas no vacías deben coincidir, y una clave repetida conserva su primer valor (extraction.py:230-235,278-301). La fuente dice que el fine-tune de TMJ publicado responde con esta forma, 46 campos y ningún JSON (:244-245).
  3. Si no, no se escribe nada y la nota falla (__init__.py:299-305). El legacy escribía la respuesta en bruto.

Se escriben dos archivos por nota bajo el árbol reflejado (__init__.py:240-266,307-317): el JSON, canónico, y un texto key : value donde una lista se une con comas y un dict anidado se queda en JSON (extraction.py:304-328).

input   notes/P01/B_001.txt
output  output_dir/P01/Extraction_B_001.txt.json
        output_dir/P01/Extraction_B_001.txt.txt

plan_outputs comprueba que no haya dos notas que den el mismo par antes de ejecutar nada (__init__.py:240-266). CNE_report.json lleva tool, notes_type, model, system_prompt (un indicador), context_tokens, max_tokens, temperature, seed, device, gpu_offload, warnings, y por nota input, el lector y la codificación, characters, finish_reason, answer_characters, status, fields, las dos rutas de salida o un reason; luego summary y duration_seconds (__init__.py:171-187,213-216,272-317). El texto de la respuesta en sí no se pone en el informe ni en los registros.

3.6 Fallos

Explicación en lenguaje llano y matemáticas: página del atlas.

Cada nota va en su propio try: un fallo se registra con la ruta relativa de la nota y se anota en el informe, y el bucle continúa (__init__.py:191-213). Si no se escribió ninguna nota, la ejecución lanza un error: un 503 (ToolUnavailableError) cuando todos los fallos fueron por falta de lector, y si no un 422 (ValueError) que enumera el motivo de cada nota (:218-232); entonces no se escribe el informe. Obsérvese que esta línea de registro por nota nombra el archivo, a diferencia de los mensajes de progreso de CLIC.

8. Hallazgos en VISOR

Explicación en lenguaje llano y matemáticas: página del atlas.

El texto de las notas se envía al servidor

La afirmación del legacy de que CNE mantiene el texto clínico en la máquina ("no network exfiltration", página legacy §11, y el «Nothing leaves your machine» de la Guía legacy) no se sostiene en VISOR. El panel de VISOR sube las notas que se seleccionan a un servidor de herramientas donde se ejecuta el modelo (Remote README.md:24-35; CNERemote/CNERemote.py:57 y el argumento notes del lado del servidor, Argumentos y esquema). El README de Remote dice con todas las letras que el cliente actual no desidentifica (README.md:32), y la página de seguridad de VISOR enumera la desidentificación de los archivos subidos como solo especificada (Desidentificación, Transporte). Lo que la herramienta misma hace con el texto: ejecuta llama.cpp en proceso y no contiene ninguna llamada de red (un grep de urllib, requests, http y socket en tools/CNE/src/sadt_cne/ no encuentra ninguna), y el servidor escribe la respuesta en la carpeta del trabajo. El hallazgo del legacy sigue siendo cierto solo para el módulo legacy.

El cliente dice "automatic", pero nada hace corresponder el modelo con el tipo de nota

El README de Remote ("leave Model on automatic and the server uses the model fine-tuned for that note type", README.md:611-613) y la docstring de CNERemote/CNERemote.py:15-18 ("the model field defaults to (automatic)") están desfasados. model es un argumento obligatorio de la herramienta (__init__.py:49), y el cliente añade su entrada "(automatic)" solo a los argumentos opcionales (Remote ServerToolsCore/ServerToolsCoreLib/base_widget.py:1074-1076, justificación en formgen.py:107-109): el campo Model enumera los bundles alojados y envía el seleccionado. Nada deriva el modelo de notes_type (resolve_model_file recibe una ruta, extraction.py:89-128); una discordancia entre ambos es solo un aviso (siguiente callout). Leído en el código, no ejecutado en Slicer.

Solo el modelo TMJ está alojado

El manifiesto de datos prepara un bundle, TMJ/qwen-ft-q4_k_m.gguf (VISOR-serve scripts/data-manifest.yml:687-692). La herramienta acepta notes_type = "Ortho", pero no hay alojado ningún modelo Ortho, y un modelo cuya ruta nombra el otro tipo es solo un aviso en el informe, no un rechazo (__init__.py:133-139, extraction.py:131-144). El comentario del manifiesto según el cual el repositorio Ortho "answers 404 today" (data-manifest.yml:682-686, repetido en SADT-VISOR tools/CNE/README.md:205-208) está desfasado: el 2026-11-09 una petición HTTP HEAD a la antigua URL Ortho dcbia/ respondió 307 (una redirección a la organización DCBIA-OrthoLab/), y una a DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho/.../model-q4_k_m.gguf respondió 302 a una descarga (solo códigos de estado, no se descargó nada). La URL de TMJ del manifiesto también usa todavía el nombre antiguo dcbia/ y responde 307.

CPU, digan lo que digan algunos comentarios

El índice de wheels fijado para llama-cpp-python es el de CPU (SADT-VISOR tools/CNE/pyproject.toml:60-67). Tres comentarios no coinciden con él: la cabecera del mismo archivo habla de un "CUDA 12.4 wheel index below" (:8-23); la descripción publicada de device dice "it needs the CUDA build of llama.cpp, which this tool pins" (__init__.py:82-84); y el archivo compose de VISOR-serve dice que CNE no puede ejecutarse en el servicio de CPU porque incluye la compilación CUDA (docker-compose.yml:105-110). El código es la compilación para CPU, de modo que una petición cuda se informa como ignorada. El README de la herramienta coincide con el código (SADT-VISOR tools/CNE/README.md:154-165). No hay que leer "CNE necesita una GPU" en ninguna parte.

Sin guarda sobre la longitud de una nota

La preocupación del legacy por las notas largas (página legacy, §11) está cerrada solo a medias. Una respuesta cortada se rechaza ahora (__init__.py:293-297) y max_tokens vale por defecto 2048 en lugar de 500. Pero nada compara la nota con la ventana de contexto ni comprueba que max_tokens deje sitio en ella: context_for solo rechaza un valor negativo (extraction.py:146-153). Con el valor por defecto de Ortho, el límite de respuesta por sí solo iguala la ventana (2048 y 2048, :49, __init__.py:51). En llama-cpp-python 0.3.36 (llama.py:1343-1358) el motor lanza un error solo cuando el prompt por sí solo alcanza n_ctx; en caso contrario acorta max_tokens a n_ctx menos el prompt y la nota nunca se corta. Así, con Ortho una nota pasa mientras la respuesta termine dentro de lo que la nota deja, y falla (finish_reason == "length") cuando no; lo que lance el motor hace fallar solo esa nota (__init__.py:200-212).

Los nombres de salida cambiaron

Los archivos son Extraction_<note file name>.json y .txt, no Extraction_<stem>.txt (__init__.py:240-266). Cualquier cosa que lea los nombres del legacy, como el Dashboard legacy (Extraction_*.txt), no encontraría los mismos archivos.

Verificado: los fallos silenciosos del legacy están cerrados

Un PDF solo de imagen, una respuesta truncada y una respuesta que no es ni JSON ni campos hacen ahora fallar la nota en lugar de escribir un archivo verosímil (__init__.py:276-305); las notas homónimas de formatos distintos ya no se sobrescriben entre sí (:240-266); la división de grafías TMJ/tmj ha desaparecido (extraction.py:49-51); una petición de GPU que no se puede atender se informa (__init__.py:145-165). Leído en el código.
