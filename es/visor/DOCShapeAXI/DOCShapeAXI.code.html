DOCShapeAXI en VISOR: el código

Para desarrolladores: lo que hace en el código el port de DOCShapeAXI a VISOR, con referencias file:line, firmas, argumentos, entorno, las diferencias con el código legacy y los hallazgos. La explicación legible del mismo pipeline, con las matemáticas, está en la página del atlas.

VISOR Código Atlas (explicación) Página legacy Guía (VISOR)

Las referencias de esta página nombran un repositorio, luego una ruta dentro de él, luego una línea: SADT-VISOR es el catálogo de herramientas (commit 6ba2a78), VISOR-serve el servidor (e9a7e5d), Remote el cliente de Slicer (AutomatedDentalToolsRemote 19b95e8), legacy SlicerAutomatedDentalTools en 3c67957. Una ruta sin prefijo como catalog.py:50 está en SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/. Todo se leyó en el código; nada de esta página se ejecutó, salvo las dos comprobaciones nombradas donde aparecen (la comparación de archivos de shapeaxi 1.0.10 con 1.1.1, y una pequeña prueba en CPU de índices repetidos). Visión general de la pila: VISOR.

1. Posición en la cadena

Explicación en lenguaje llano y matemáticas: página del atlas.

  • Estado: portado, implementado en código, con pruebas en la herramienta (SADT-VISOR tools/DOCShapeAXI/tests/test_run.py, 91 funciones de prueba, no ejecutadas para esta página). Un servidor preparado solo con los scripts de staging de VISOR-serve no puede ejecutarla: el backbone EfficientNet que requiere no lo prepara ninguno de ellos (véase Hallazgos en VISOR).
  • Nombre en la API DOCShapeAXI (SADT-VISOR tools/DOCShapeAXI/pyproject.toml:57-59); módulos __init__.py, catalog.py, engine.py, pipeline.py.

  • Datos alojados: los cinco checkpoints están en el manifiesto de datos (VISOR-serve scripts/data-manifest.yml:597-614). No hay superficie de prueba, deliberadamente: nada público es una vía aérea, un cóndilo o una fisura (:616-622). La cabecera del manifiesto sigue diciendo "NOT PORTED YET" (:595), lo cual es falso: la herramienta y su cliente existen.

3.2 Superficies, dispositivo y red

Explicación en lenguaje llano y matemáticas: página del atlas.

  • Descubrimiento: un único .vtk, o una carpeta recorrida de forma recursiva, con los archivos ocultos omitidos, ordenada (pipeline.py:22,40-64). No encontrar nada es un ValueError, "DOCShapeAXI reads surfaces, not volumes" (__init__.py:59-64). El punto de montaje dado a shapeaxi es la carpeta de entrada, o la carpeta del archivo cuando es un archivo único (:71).
  • Dispositivo: cuda recurre a cpu con un aviso cuando no hay ninguna tarjeta visible (pipeline.py:67-72).
  • Red: load_network comprueba que la clase nombrada por el catálogo existe en shapeaxi.saxi_nets_lightning, luego que el backbone EfficientNet está preparado, después permite explícitamente las clases que el checkpoint serializa con pickle, y lo carga (pipeline.py:130-151):
network_class = getattr(saxi_nets_lightning, network_name, None)   # else ValueError
check_backbone_is_staged()      # <torch hub dir>/checkpoints/efficientnet-b0-355c32eb.pth, else FileNotFoundError
allow_checkpoint_globals()      # shapeaxi transform classes + torchvision Compose
model = network_class.load_from_checkpoint(checkpoint, strict=False)
model.eval(); model.to(device)

La lista de permitidos existe porque torch 2.6 hizo de weights_only=True el valor por defecto y estos checkpoints llevan sus transformaciones de entrenamiento en hyper_parameters (pipeline.py:108-127). strict=False se conserva del legacy (legacy DOCShapeAXI_CLI.py:135,201).

3.3 Pasada de predicción

Explicación en lenguaje llano y matemáticas: página del atlas.

La lista de archivos es un DataFrame de pandas construido en memoria (el legacy escribía un CSV en la carpeta de salida con modo 'a', DOCShapeAXI_CLI.py:111-118), que se pasa al SaxiDataset de shapeaxi con EvalTransform(scale_factor), leyéndose el factor de escala de los hiperparámetros del checkpoint (engine.py:11-34); shapeaxi 1.1.1 lo ignora después (véase la comprobación de abajo). Luego, una superficie cada vez (engine.py:37-64):

mesh = model.create_mesh(vertices, faces, normals)
points = model.sample_points_from_meshes(mesh, model.hparams.sample_levels[0])
views, _ = model.render(mesh)
output = model(points, views)
if not analysis.is_regression:
    output = torch.argmax(softmax(output).detach(), dim=1, keepdim=True)
predictions.append(float(output.reshape(-1)[0].cpu()))

Cada predicción se registra con la ruta de la superficie relativa al punto de montaje y con class (un entero) o score (un float, regresión) (__init__.py:81-90). El muestreo de puntos y el renderizado son de shapeaxi; ni la herramienta ni el legacy fijan una semilla aleatoria (ningún seed ni manual_seed en las fuentes de la herramienta).

3.4 Pasada de explicación (Grad-CAM)

Explicación en lenguaje llano y matemáticas: página del atlas.

Solo cuando explain es verdadero (__init__.py:92-95). Se reconstruye el dataset y se vuelve a renderizar cada superficie; luego, para cada clase k en range(analysis.classes) (engine.py:67-114):

cam = LayerGradCam(model, model.convnet.module._blocks[-1], device_ids=[0])
attribution = cam.attribute(inputs=(points, views), target=k, attr_dim_summation=False)
attribution = attribution.sum(dim=1).cpu().detach()
scaled = scale_attribution(attribution.numpy(), (224, 224))   # resize, clip 1/99 percentiles, rescale to [-1, 1]
projected = gradcam_process(_Namespace(device, target_class=k), scaled, faces, per_face, vertices)
surface.GetPointData().AddArray(projected)                    # array grad_cam_target_class_<k>
post_process.MedianFilter(surface, projected)
  • Redimensionado: torch.nn.functional.interpolate, bilineal, align_corners=False, en lugar del cv2.resize del legacy; el comentario dice que una prueba fija ambos a 1e-5 (pipeline.py:163-184, pyproject.toml:45-51).
  • Normalización: recortar a los percentiles 1 y 99, luego llevar a [-1, 1]; un mapa plano se convierte en ceros en lugar de NaN (pipeline.py:186-199).
  • Qué capa: el último bloque de la rama EfficientNet 2D, como en el legacy (DOCShapeAXI_CLI.py:150-151): el mapa explica la rama multivista, no la rama de nube de puntos.
  • Proyección: gradcam_process es de shapeaxi (saxi_gradcam.py:112-144 en 1.0.10 y en 1.1.1, el mismo código). Las caras empiezan en 0 y toman maximum(old, new) vista tras vista, de modo que en la malla una cara guarda max(0, max over views) y el rango es [0, 1]; el valor va al primer vértice de la cara, y los vértices que no son el primer vértice de nadie se restablecen a 0 (:134). Dentro de una vista, los píxeles que muestran la misma cara comparten un índice y la escritura que queda no está definida (la última en CPU, no el máximo); los píxeles de fondo llevan el índice -1 y escriben sobre la última cara. La prueba en CPU y los detalles están en la página de código del legacy, sección 5d; no se ejecutó nada en GPU.
  • Filtro de mediana: post_process.MedianFilter (post_process.py:294-308) sustituye cada vértice, lleno o vacío, por la mediana de sus vecinos, él mismo excluido (utils.py:363-376), no solo los vacíos.
  • Nombres de array: el índice de la clase se pasa siempre como target_class, que da nombre al array (engine.py:104-106,117-129). El legacy lo fijaba solo cuando num_classes > 1 (DOCShapeAXI_CLI.py:171-174), de modo que el checkpoint de regresión recibe ahora también un nombre por clase, grad_cam_target_class_0. Leído en el código.
  • Escritura: una vez por superficie tras todas las clases, plana en output_dir con el nombre base de la entrada (engine.py:111-113); el legacy escribía dentro del bucle de clases, en <out>/explainability/<task>/ (DOCShapeAXI_CLI.py:153,185-186).

8. Hallazgos en VISOR

Explicación en lenguaje llano y matemáticas: página del atlas.

El backbone EfficientNet es un requisito previo que nadie prepara

shapeaxi construye un EfficientNet-B0 alrededor de cada checkpoint. La herramienta se niega a dejar que se descargue en mitad de una petición y, en su lugar, lanza FileNotFoundError salvo que efficientnet-b0-355c32eb.pth ya esté bajo <torch hub dir>/checkpoints/ (SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/pipeline.py:80-105, llamado desde load_network en :146; README.md:112-121). Ni el manifiesto de datos ni ningún script de VISOR-serve mencionan este archivo (se buscó "efficientnet" en los tres repositorios: solo lo hacen el propio README.md de la herramienta, pipeline.py y tests/test_run.py). Un despliegue que sigue los pasos habituales de preparación falla por tanto en su primera llamada, después de haber subido las superficies. Leído en el código; no se comprobó si un servidor dado tiene el archivo en su caché.

La línea de estado muestra signos de interrogación

El cliente construye su resumen a partir de report.get("data_type") y report.get("checkpoint") (Remote DOCShapeAXIRemote/DOCShapeAXIRemote.py:122-130). El informe que escribe la herramienta no tiene ninguna de las dos claves: tiene model, anatomy, task, classes y network (SADT-VISOR __init__.py:97-110). El resumen del panel dirá "?" en lugar de la anatomía y del checkpoint, mientras que task y el número de superficies sí se rellenan. Leído en el código, no ejecutado en Slicer.

El cliente describe una tabla de predicciones y un selector de tarea que no existen

Los comentarios del cliente dicen que el resultado es una "prediction table" en forma de CSV (DOCShapeAXIRemote.py:76-86) y que un argumento task se restringe a la anatomía mediante una regla options_when (:12-17). La herramienta no escribe ningún CSV (__init__.py:97-110), y su esquema tiene seis argumentos, ninguno llamado task, sin options_when (salida de scripts/describe.py). La tarea se elige escogiendo el archivo de checkpoint, de modo que el usuario debe saber qué significan airways_2_class.ckpt y airways_4_regress.ckpt.

Dos entradas con el mismo nombre de archivo colisionan en la salida

Las superficies se encuentran de forma recursiva pero se escriben planas: a/s.vtk y b/s.vtk van ambas a output_dir/s.vtk (engine.py:111-112), de modo que la segunda sustituye a la primera, mientras que el informe las mantiene separadas por ruta relativa (__init__.py:84). El paso de renombrado mueve luego s.vtk a s_pred.vtk una vez por entrada (__init__.py:128-132): el segundo movimiento no encuentra ningún archivo, lo que terminaría la ejecución en un FileNotFoundError después de todo el cálculo; con un output_suffix vacío la sobrescritura es silenciosa. CLIC y CNE reproducen el árbol de entrada para evitar exactamente esto. Leído en el código, no ejecutado.

Sigue siendo cierto desde el legacy: muestreo sin semilla, saliencia de una sola rama

No se fija ninguna semilla en ninguna parte de las fuentes de la herramienta y no hay argumento seed, de modo que el muestreo aleatorio de puntos dentro de shapeaxi (engine.py:54,92) no es fijo de una ejecución a otra, como en el legacy (página legacy, trampas). La capa de Grad-CAM es el último bloque de la rama de vistas 2D (engine.py:82-83), de modo que el mapa no dice nada de la rama de nube de puntos. Leído en el código.

Comentarios que no coinciden con las versiones fijadas

El comentario sobre la versión fijada de captum habla de 0.9.0 mientras que la versión fijada es captum==0.8.0 (pyproject.toml:39-44). El manifiesto de datos sigue etiquetando la herramienta como "NOT PORTED YET" (data-manifest.yml:595). Ninguna de las dos cosas cambia lo que se ejecuta.

Verificado: la discordancia de shapeaxi del legacy está corregida aquí

El código legacy está escrito para la API de shapeaxi 1.x mientras que su instalador pide la 2.0.2 o posterior (legacy ADT/ADTLib/env/install_pytorch.py:385). VISOR fija shapeaxi==1.1.1, con el motivo en el comentario (pyproject.toml:18-30), y resuelve las clases de red desde saxi_nets_lightning, donde viven (pipeline.py:135-145). El checkpoint ya no se copia en la carpeta de salida. El EvalTransform de shapeaxi 1.1.1 tampoco respeta scale_factor: UnitSurfTransform.__call__ nunca lo reenvía (saxi_transforms.py:48-57), idéntico en 1.0.10 y en 1.1.1 (los dos paquetes difieren solo en __about__.py, comparados archivo por archivo para esta pasada; 1.1.1 descargado del índice de paquetes).
