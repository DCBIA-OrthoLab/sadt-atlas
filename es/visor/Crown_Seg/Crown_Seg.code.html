Crown_Seg en VISOR: el código

Para desarrolladores: lo que hace en el código la herramienta de VISOR Crown_Seg, con referencias file:line, firmas, argumentos, entorno, la correspondencia con el legacy y los hallazgos. La explicación legible del mismo pipeline, con las matemáticas, está en la página del atlas.

Solo VISOR Código Atlas (explicación) SADT-VISOR 6ba2a78 VISOR-serve e9a7e5d Remote 19b95e8
Sin módulo legacy

El repositorio legacy (SlicerAutomatedDentalTools en 3c67957) no contiene ningún módulo Crown_Seg ni ningún archivo con “crown” o “dentalmodelseg” en su ruta (git ls-tree sobre ese commit, observado). Lo que contiene son llamadas al módulo CrownSegmentationcli de la extensión SlicerDentalModelSeg, que es aparte, y una pequeña copia de la misma llamada dentro de la línea de comandos de ALI_IOS. La correspondencia exacta está en Homólogo legacy. Cómo ejecuta VISOR una herramienta en un servidor se describe en Arquitectura.

Rutas: SADT-VISOR cs/ es tools/Crown_Seg/src/sadt_crownseg/, ali_ios/ es tools/ALI/ALI_IOS/src/sadt_ali_ios/, y las rutas de VISOR-serve empiezan en server/ salvo que nombren docs/ o scripts/. “Observado” marca lo que se volvió a ejecutar al escribir esta página; todo lo demás se leyó en el código.

4.1 Lo que hace la herramienta alrededor del motor

Explicación en lenguaje llano y matemáticas: página del atlas.

Primero el checkpoint: find_checkpoint acepta un archivo .pth, o una carpeta explorada de forma recursiva en busca de un archivo cuyo nombre lleve val-loss; ninguno o dos es un ToolInputError que los nombra (cs/pipeline.py:186-262). model vacío significa <data_root>/Crown_Seg/models (cs/__init__.py:18-29,104). Esto ocurre antes de crear nada (cs/pipeline.py:407-413).
  2. Descubrimiento: un .vtk o .stl, o una carpeta recorrida de forma recursiva y ordenada; no encontrar nada es un 422 (cs/pipeline.py:292-320). La raíz de entrada, usada para reflejar el árbol, es la carpeta o la carpeta padre del archivo único (:323-330).
  3. Clasificación: con skip_segmented (verdadero por defecto), is_segmented abre cada malla y lee solo los nombres de sus arrays de puntos; cualquiera de PredictedID, UniversalID, Universal_ID, FDI_ID la manda a la rama de copia (cs/pipeline.py:56,267-289,449-451).
  4. Rama de copia: cada malla etiquetada se escribe como polydata .vtk en <output>/<relative folder>/<base>_<suffix>.vtk, y un .stl se convierte (cs/pipeline.py:480-487,594-613). Las etiquetas no se tocan.
  5. Rama de segmentación: las rutas restantes pasan a .crownseg_work/crownseg_input.csv bajo una cabecera surf, el dispositivo se resuelve a cuda:0 o cpu (:170-178), y se llama a shapeaxi una sola vez para toda la lista con este namespace (cs/pipeline.py:336-366,508-531):

Antes de la llamada, _import_dental_model_seg importa shapeaxi de forma diferida y, cuando saxi_nets no tiene DentalModelSeg (todas las versiones 2.0.x, según el comentario), lo apunta a saxi_nets_lightning.DentalModelSeg (cs/pipeline.py:105-167). Si la importación falla, la ejecución sigue para la rama de copia y registra engine_available: false con el error (cs/pipeline.py:466-472); una malla que necesitaba la red se queda entonces sin salida y queda failed.

4.2 Dentro de shapeaxi

Explicación en lenguaje llano y matemáticas: página del atlas.

Leído en dental_model_seg.py del checkout 2b34042 de ShapeAXI. El lock resuelve shapeaxi a 2.0.2, cuyo código fuente no se abrió aquí; las líneas citadas a continuación son idénticas en las copias que sí se abrieron (shapeaxi 1.0.10 instalado y 2.0.3, y 1.1.1 en la caché de uv):

  • la red es saxi_nets_lightning.DentalModelSeg(custom_model=args.model, device=device), con out_channels = 34 (:23,26);
  • cada superficie se carga mediante SaxiDataset con UnitSurfTransform(), tamaño de lote 1, persistent_workers=True (:82-84), y por eso num_workers debe ser al menos 1;
  • la red devuelve predicciones por vista y la cara que muestra cada píxel; las predicciones se multiplican por (PF >= 0) (cero donde un píxel no muestra ninguna cara) y luego pasan por el softmax (:97), de modo que un píxel sin cara da un 1/34 uniforme que se suma a una entrada de la tabla de caras en lugar de omitirse (:103-104); la suma por cara y el arg-max (:106) dan una etiqueta por cara, y la etiqueta de cada cara se da a su primer vértice (:107-108);
  • posprocesado: RemoveIslands para la etiqueta de encía 33 con un umbral de 500, luego para toda etiqueta con 200, luego un cierre por etiqueta, DilateLabel y después ErodeLabel, dos iteraciones cada uno (:118-130);
  • ConvertFDI si fdi == 1 (:52,225-236, sección siguiente);
  • con overwrite=0 y una entrada csv, el resultado va a <out>/<csv stem>_<suffix>/<input path without vtk_folder>_<suffix>.vtk (:154-176). Crown_Seg recalcula esta ruta en lugar de analizar la salida de shapeaxi (cs/pipeline.py:369-381), y luego marca cada malla como segmented si el archivo existe y como failed si no (:533-546).

4.3 Numeración dental: Universal y FDI

La red siempre predice números Universal: de 1 a 32 para los dientes, 33 para la encía. Con numbering = "FDI", el ConvertFDI de shapeaxi pasa cada valor por una única tabla de correspondencia (ShapeAXI 2b34042 dental_model_seg.py:225-236):

shapeaxi vuelve a escribir los enteros convertidos con el mismo nombre de array (vtk_id.SetName(args.array_name), :233-235). Como los dos sistemas comparten la mayor parte de su rango, un array FDI llamado Universal_ID se leería sin error como otros dientes: el FDI 18 es el tercer molar superior derecho, el Universal 18 un molar inferior izquierdo; el FDI 33 es un canino inferior izquierdo, el Universal 33 la encía (comentario en cs/pipeline.py:62-80). Crown_Seg nombra por tanto el array según la numeración: array_name vacío se convierte en Universal_ID o FDI_ID (array_name_for, cs/pipeline.py:58-85; cs/__init__.py:44,106). Todos los lectores posteriores buscan solo nombres Universal, de modo que ALI_IOS, ASO o AREG_IOS rechazan una malla FDI en lugar de leerla mal (véase Hallazgos). Todos los llamadores del legacy pasaban fdi 0; la salida FDI es nueva en la práctica, y Universal sigue siendo el valor por defecto (cs/__init__.py:46).

Salidas. La herramienta devuelve la carpeta de salida, de modo que no hay salidas con nombre. Pueden aparecer dos árboles, según lo que le pasó a cada malla: una malla segmentada por la red se escribe en <output>/crownseg_input_<suffix>/<relative path without extension>_<suffix>.vtk (cs/pipeline.py:369-381,514), y una malla que ya llevaba etiquetas se copia, convertida a .vtk, en <output>/<relative folder>/<base>_<suffix>.vtk (cs/pipeline.py:480-487,594-613). Se espera que el llamador lea run_report.json en lugar de adivinar. La carpeta temporal .crownseg_work/ se elimina en un finally (cs/pipeline.py:87,435-439), y el checkpoint se resuelve antes de que exista, de modo que una petición rechazada deja la carpeta de salida como la encontró (cs/pipeline.py:407-413).

run_report.json. tool, checkpoint (por nombre), array_name, suffix, numbering, device, cases (por malla: status, input, produced, y error en caso de fallo), segmented_meshes, engine_available, engine_error, un summary con los recuentos de total, segmented, already_segmented, engine_unavailable y failed, y duration_seconds (cs/pipeline.py:556-590). Una malla para la que shapeaxi no escribió nada es un caso failed; la ejecución en conjunto falla solo cuando no se produjo ninguna malla (cs/pipeline.py:540-551).

Privacidad de los registros. shapeaxi imprime la ruta de cada malla que guarda, y la ruta lleva el nombre de archivo del paciente: su salida estándar se traga (cs/pipeline.py:341-345,365-366), y las rutas de la salida se recalculan en lugar de analizarse a partir de ella (cs/pipeline.py:369-381).

8. Hallazgos en VISOR

Explicación en lenguaje llano y matemáticas: página del atlas.

Numeración FDI sobre una malla que ya está etiquetada

Con numbering = "FDI" y skip_segmented activado, una malla que ya lleva un array de etiquetas se copia sin cambios (cs/pipeline.py:480-487; _write_as_vtk convierte el formato de archivo, no las etiquetas), mientras que el informe indica array_name = "FDI_ID" y numbering = "FDI" (cs/pipeline.py:556-561). La copia conserva sus enteros Universal bajo su nombre Universal, de modo que el informe anuncia una numeración que el archivo no contiene. Observado: una malla sintética con un array Universal_ID se pasó por segment_crowns con fdi=True y array_name="FDI_ID"; el informe decía numbering: "FDI" y array_name: "FDI_ID", y el archivo de salida contenía solo Universal_ID con su valor original. El motor de segmentación no está instalado en el entorno usado, así que el estado del caso decía engine_unavailable en lugar de already_segmented; la ruta de copia es la misma. Las pruebas no cubren este cruce (tests/test_run.py:488-503).

Cuatro nombres reconocidos aquí, tres aguas abajo

Crown_Seg trata una malla como segmentada si contiene cualquiera de PredictedID, UniversalID, Universal_ID o FDI_ID (cs/pipeline.py:56). ALI_IOS, ASO y AREG_IOS leen solo los tres primeros (ali_ios/surface.py:19, SADT-VISOR tools/ASO/src/sadt_aso/markups.py:19, AREG_IOS/src/sadt_areg_ios/surfaces.py:39). Una malla que solo tiene FDI_ID pasa por tanto Crown_Seg y la rechaza la herramienta siguiente: es intencionado (lo dice el propio comentario de la herramienta, cs/pipeline.py:64-80), pero sin ningún síntoma antes de esa herramienta siguiente. El comentario de ALI_IOS que dice que son “the same three names CrownSeg writes and recognizes” (ali_ios/surface.py:18) es inexacto. Leído en el código.

Las mallas en .vtp o .obj son invisibles para Crown_Seg

Crown_Seg descubre solo .vtk y .stl (cs/pipeline.py:51,292-320), mientras que AREG_IOS acepta .vtk .vtp .stl .obj como entrada (AREG_IOS/src/sadt_areg_ios/surfaces.py:35) y, en modo Fully-Automated, entrega su carpeta a Crown_Seg (dispatch.py:172-173). Una carpeta que contenga solo esas mallas se rechaza (“No surface mesh found in the input”, cs/pipeline.py:314-319); en una carpeta mixta se quedan fuera de la salida de Crown_Seg, que es la carpeta con la que sigue AREG_IOS. La copia legacy de la llamada en ALI_IOS sí leía .vtp (segmentation.py:33-56). Leído en el código; no ejecutado.

Dos árboles de salida: leer el informe

Una malla segmentada aterriza bajo crownseg_input_<suffix>/, una malla que ya estaba etiquetada aterriza junto a su ruta relativa, de modo que un glob sobre un árbol se pierde el otro (cs/pipeline.py:369-381,480-487). ALI_IOS lee en su lugar cases[key].produced de run_report.json (ali_ios/dispatch.py:240-252), que es para lo que sirve el informe. Una malla de una instalación degradada lleva el estado engine_unavailable y aun así se copia con su ruta produced (cs/pipeline.py:495-505), de modo que un cliente que filtrara solo por already_segmented la omitiría. Leído en el código.

El grafo de herramientas de la documentación del servidor está desfasado

VISOR-serve docs/TOOL_GRAPH.md:27-28,43 enumera ALI_IOS como una hoja. El esquema que publica ALI_IOS declara calls = ['Crown_Seg'] (observado con scripts/describe.py en el entorno de ALI_IOS), porque su dispatch llama a Crown_Seg mediante una constante de módulo (ali_ios/dispatch.py:58,229). El documento dice que se genera a partir de esos esquemas y se comprueba al arrancar; la copia que hay en el repositorio es anterior al código.

Documentación que no coincide con el código

El README dice que el modelo es un argumento obligatorio (README.md:33), y también la docstring del pipeline (cs/pipeline.py:16-23); el argumento es opcional, con un valor por defecto vacío que se resuelve a la carpeta propia de la herramienta (cs/__init__.py:41, comentario en cs/__init__.py:35-40). El README nombra además la carpeta DATA/CrownSeg/testfiles (README.md:178) mientras que el código y el manifiesto usan DATA/Crown_Seg, y cuenta 176 pruebas (README.md:225,232) donde en tests/ hay 162 funciones de prueba definidas (un recuento de def test_; la parametrización puede explicar la diferencia). AREG nunca pasa device a Crown_Seg, a diferencia de ALI_IOS (SADT-VISOR tools/AREG/AREG_IOS/src/sadt_areg_ios/tools.py:113-130), de modo que en un servidor solo con CPU el valor por defecto cuda recurre a la CPU con un aviso, o lo sustituye el DEVICE del servidor. Leído en el código.

Lo que protege la herramienta

El checkpoint se resuelve antes de crear ningún archivo, de modo que una petición rechazada no deja nada atrás (cs/pipeline.py:407-413); una carpeta con dos checkpoints se rechaza nombrando a ambos, de modo que la antigüedad de los pesos nunca es silenciosa (cs/pipeline.py:244-251); la salida estándar de shapeaxi, que lleva nombres de archivo, se traga (cs/pipeline.py:365); la carpeta temporal se elimina en un finally (cs/pipeline.py:435-439); la entrada nunca se modifica. Leído en el código.

Reproducibilidad

El README de la herramienta informa de que la predicción en bruto PredictedID es idéntica bit a bit a un port de referencia, y de que el Universal_ID posprocesado varía de una ejecución a otra, incluso entre dos ejecuciones del mismo código (de 826 a 2,607 puntos de 294,260). Es la medición del README (SADT-VISOR tools/Crown_Seg/README.md:176-209, sección “Validated against”), no repetida aquí.
