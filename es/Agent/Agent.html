Agent: pipeline completo

Un asistente en lenguaje natural que elige un módulo de la extensión, extrae sus parámetros, construye la línea de comandos y lo lanza. Aquí no se llama a ninguna red neuronal médica: el Agent solo enruta y rellena formularios.

no publicado Agent_CLI Python de Slicer qwen3:8b mediante Ollama cross-encoder MiniLM-L6 Bibliografía

Todo se ejecuta en local: un LLM de 8B servido por Ollama, más un pequeño cross-encoder para preseleccionar las herramientas candidatas.

1. Posición en la cadena

Nadie llama a Agent. Un grep de slicer.modules.agent no halla ningún llamador fuera del propio módulo. Es un punto de entrada terminal.

Hacia fuera, hay dos niveles:

LlamadoCómoDónde

el módulo de destino (ALI_CBCT.py, AMASSS_CLI.py, …)subprocess.run(cli_args) (Agent/Agent.py:962)proceso hijo del widget, Python de Slicer

El inventario de destinos es puramente declarativo: vive en Agent_CLI/manifest.yaml, un archivo YAML con 16 entradas de scripts. El Agent no descubre nada por sí mismo: solo conoce este archivo.

Código muerto

AgentLogic.process() (Agent.py:1191) vuelve a ejecutar la CLI solo con folders y prompt (faltan modeagent y temp_folder, ambos obligatorios del lado del XML) y lee GetOutputText() inmediatamente después de un wait=False. Nunca se llama. Agent_CLI/Resources/UI/Agent_CLI.ui es igualmente inerte: un módulo CLI no carga un archivo .ui.

3. Los modelos

3.1 El LLM, qwen3:8b mediante Ollama

Una única constante, duplicada en ambos extremos: DEFAULT_MODEL = "qwen3:8b" (utils.py:21) y MODEL_NAME = "qwen3:8b" (Agent.py:29). get_router_model() respeta una variable de entorno ROUTER_MODEL que permite cambiar a cualquier modelo de Ollama sin tocar el código.

El mismo modelo atiende las tres llamadas: enrutamiento, extracción de parámetros, reparación. Ningún modelo especializado, ningún ajuste fino.

PuntoValorFuente
Motor de inferenciaOllama (por tanto llama.cpp por debajo), API HTTP localimport ollama, puerto 11434

El módulo nunca pasa una directiva de dispositivo. Lo decide el binario de Ollama, y el código extrae de ello una consecuencia explícita: en Linux, un Ollama instalado mediante snap está aislado, no ve la GPU de NVIDIA y recurre a la CPU, 80–90 s por respuesta con un modelo de 8B, una cifra medida y fijada en el código (Agent.py:1107). El módulo detecta /snap/ en el realpath del binario y advierte de ello, sin poder corregirlo (el servidor de snap ya ocupa el puerto 11434, y eliminarlo requiere sudo).

Cuando no se halla Ollama, install_official_ollama() (Agent.py:111) descarga el archivo portátil oficial en ~/.slicer_agent/ollama (modificable mediante SLICER_AGENT_HOME): ollama-linux-{amd64,arm64}.tgz, ollama-windows-{amd64,arm64}.zip u Ollama-darwin.zip, extraído con ditto y luego sacado de la cuarentena con xattr. Estos archivos incluyen las bibliotecas CUDA/Metal, de ahí la elección deliberada de no usar curl | sudo sh (sin contraseña de root desde la interfaz) ni el paquete snap. LD_LIBRARY_PATH apunta a <install>/lib/ollama para que el binario encuentre sus propias bibliotecas (Agent.py:67).

Solo dos ajustes de llamada, en chat_with_auto_pull (utils.py:96):

  • keep_alive="30m" en lugar de los 5 minutos por defecto, para no recargar 5 GB en la VRAM entre dos mensajes;
  • format="json" para el enrutador, la extracción y la reparación (una restricción gramatical del lado de Ollama): no para el modo consultor.

No se pasa ningún temperature, seed, num_ctx ni think. Como qwen3 es un modelo de razonamiento híbrido, el modo consultor puede por tanto dejar filtrarse texto de razonamiento según la versión de Ollama; el único posprocesamiento es output.replace("*","").replace("#","") (Agent_CLI.py:215), que elimina el markdown eliminando los caracteres.

Si el modelo no está presente, chat_with_auto_pull intercepta el mensaje not found, ejecuta ollama.pull(model, stream=True) mostrando el progreso, y luego repite el chat. Cualquier otro error se vuelve a lanzar tal cual.

3.2 El cross-encoder: ms-marco-MiniLM-L-6-v2

Es la única red real cargada en el proceso. CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") (utils.py:53), mediante sentence-transformers, es decir, pesos de transformers/safetensors descargados del Hugging Face Hub y almacenados en caché en ~/.cache/huggingface.

MiniLM, 6 capas, 22,7 M de parámetros, destilado de MiniLM-L12-H384-uncased, entrenado en MS MARCO Passage Ranking. No es un modelo de embeddings: no hay vectores ni similitud coseno. La consulta y el documento se concatenan y se introducen juntos en el transformer, que produce un único escalar de relevancia sin acotar (típicamente de −10 a +10). El dispositivo es el que sentence-transformers elige por sí solo, según la rueda de torch instalada.

La caché _cross_encoder_model no sirve de nada en la práctica: Agent_CLI.py es un proceso nuevo en cada petición, de modo que el modelo se recarga en cada mensaje. El comentario del código lo admite.

Retroceso silencioso del cross-encoder

Si falla la carga, el retroceso es brusco: scripts[:k], es decir, las tres primeras herramientas del manifiesto (ali_cbct, ali_ios, amasss_cli) sea cual sea la pregunta (utils.py:90). El operador no es informado.

4. Enrutamiento

Dos etapas, y el LLM solo interviene en la segunda.

Etapa 1, preselección con cross-encoder. cross_encoder_retrieve_candidates(manifest, prompt, k=3) construye un documento por herramienta:

docs.append(f"{s['name']}: {s['description']} (tags: {tags})")
scores = model.predict([(user_text, doc) for doc in docs])
ranked = sorted(zip(scores, scripts), reverse=True)
return [s for _, s in ranked[:k]]

16 pares puntuados, ordenados de forma descendente, top-3 fijado en el código (k=3 nunca se parametriza). El campo priority del manifiesto (valores de 1 a 23, con huecos) nunca se lee : la línea que lo leería está comentada (utils.py:216). La herramienta correcta, si quedara en 4.º lugar, se pierde definitivamente; el LLM nunca la verá.

Etapa 2, elección por el LLM. El prompt de sistema (Agent_CLI.py:105):

You are a tool router. Output ONLY one JSON object.
Schema:
{"tool": string|null, "confidence": number, "reason": string}

Rules:
- Choose tool ONLY from the candidate list provided by the user message.
- If none match, set tool = null and confidence <= 0.4.
- Do not invent tool names.
- Keep reason short (max 1 sentence).

El mensaje del usuario es USER_REQUEST: <prompt> seguido de CANDIDATES (choose exactly one name from this list): y el bloque construido por build_candidates_block: una línea por candidato, i) name — description (truncated to 140 characters) | tags: t1, t2, … (8 max).

Conviene señalar tres cosas:

  • El contexto de carpetas no se entrega al enrutador. folders_context solo se añade al prompt de extracción.
  • El historial de conversación se inyecta entre el turno del sistema y el del usuario (*history), y contiene las burbujas de chat en bruto del widget («After reflection, I would like to run …»). El enrutador JSON recibe por tanto prosa de interfaz como turnos de «assistant».
  • confidence y reason no sirven para nada. confidence se analiza, se redondea, se serializa en el JSON de salida como tool_confidence… y el widget nunca lo vuelve a leer. Ningún umbral en ninguna parte. La instrucción «confidence ≤ 0.4» no es una restricción, solo una sugerencia al modelo.

La única red de seguridad es textual: if selected_tool and selected_tool != "null" and selected_tool != "None". Un nombre de herramienta alucinado que no esté en el manifiesto pasa esta prueba, y luego hace que build_cli_args falle con un KeyError, capturado por el try global de main() y devuelto como {"error": …}.

tools = build_tool_spec(manifest) (Agent_CLI.py:72) se calcula y luego no se usa nunca: código muerto, junto con todo el manejo de la «estructura antigua» (patterns, defaults) que ninguna entrada del manifiesto actual utiliza.

5. Extracción de parámetros

Una segunda llamada al LLM, con una herramienta ya elegida, dentro de extract_parameters (utils.py:220).

Enmascaramiento de parámetros técnicos. Los parámetros llamados temp_fold, tmp_folder, temp_folder, log_path o logPath se retiran de la especificación antes de construir el prompt: no tiene sentido pedir al modelo que invente una carpeta temporal. Se reinyectan después con el valor input.temp_folder, es decir, el slicer.util.tempDirectory() que crea el widget en cada clic (Agent_CLI.py:153), y se quitan de missing_required.

El prompt de extracción (parameter_extraction_improved.py:40) enumera cada parámetro como - name (type) [REQUIRED|optional] (encode: …): description, y luego impone siete reglas: formato de las listas según encode (comma_no_brackets, space_separated, comma_separated, python_literal), booleanos y números en JSON desnudo, «si el nombre contiene folder o dir, dar una carpeta sin nombre de archivo», y sobre todo:

7. ONLY extract parameters mentioned in the user request
   - Do NOT invent values
   - Leave unmentioned optional parameters absent

Salida obligatoria: {"extracted": {...}, "confidence": 0.0-1.0, "missing_required": [...], "notes": "..."}. El missing_required producido por el modelo se ignora: lo que cuenta es el validador.

La resolución de rutas se delega por completo en el LLM

El widget pasa la lista de elementos soltados en la zona de arrastre, unidos por comas (Agent.py:770); la CLI la divide de nuevo por , y la envuelve:

FOLDERS_CONTEXT:
<one path per line>

Rules:
- Treat FOLDERS_CONTEXT as the source of truth for paths.
- If a required path parameter is missing, try to infer it from FOLDERS_CONTEXT.
- If multiple candidates exist, pick the most specific match and explain briefly in 'reason'.

Este bloque se concatena al prompt del usuario, no se pasa por separado. No hay emparejamiento heurístico, ni inspección del contenido de las carpetas, ni comprobación de existencia: le corresponde al modelo adivinar cuál de las rutas soltadas es el T1, cuál el T2, cuál la carpeta de modelos. Una ruta que contenga una coma queda cortada en dos por el split(",").

Validación (parameter_validator.py) encadena seis pasadas: campos obligatorios ausentes, coerción de tipos (bool/int/float/list/path/string), sintaxis de rutas, choices, min/max, parámetros fuera de la especificación. Dos detalles útiles:

  • encode: lower_str_bool fuerza la cadena "true"/"false" a minúsculas, porque varias CLI comparan el argumento en bruto sin .lower(): str(True) daría "True" y nunca coincidiría.
  • _check_paths solo comprueba dos cosas: que Path(str(value)) no lance una excepción (casi nunca lo hace) y que un parámetro cuyo nombre contenga folder/dir no termine con una extensión conocida. La existencia de la ruta nunca se prueba.

El resultado de la validación se descarta casi por completo: errors y warnings no salen a la superficie en ninguna parte. Su único efecto es final_confidence = confidence * 0.6 cuando no es válido, y esa confianza no la lee nadie. Solo sobreviven params y missing_required.

6. Construcción y ejecución del comando

Sí, el módulo se lanza realmente. Sin ambigüedad.

La CLI solo construye el comando. build_cli_args (utils.py:350) fusiona los valores por defecto del manifiesto con los parámetros extraídos, y luego:

return [sys.executable, tool_path] + cli

sys.executable es el intérprete del proceso Agent_CLI, es decir, el Python de Slicer. Para cli_style: positional (14 herramientas de 16), los valores se concatenan en el orden de declaración del manifiesto: positional_order está admitido pero ninguna entrada lo fija. Para cualquier otro cli_style, la ejecución cae en la rama --flag value, iterando sobre merged: los parámetros alucinados fuera de la especificación se emiten, pues, realmente.

La lista se devuelve al widget en el campo command del JSON. Es AgentWidget quien la ejecuta, y solo si missing_required == []:

  1. una burbuja de chat, «After reflection, I would like to run X»;
  2. QMessageBox.question que enumera key=value para cada parámetro (Agent.py:864);
  3. si se responde Yes → runToolWithRepair → subprocess.run(cli_args, capture_output=True).

Si missing_required no está vacío, el agente no lanza nada: muestra la lista de lo que falta junto con los valores ya conocidos, y espera un mensaje de seguimiento (al que el historial de conversación le permitirá engancharse).

Slicer se congela durante el trabajo

subprocess.run es síncrono y se ejecuta en el hilo de la interfaz: Slicer queda congelado durante toda la duración del trabajo que, para una segmentación de AMASSS o un registro de AREG, se mide en decenas de minutos.

7. El bucle de reparación

Ante un código de retorno distinto de cero, runToolWithRepair (Agent.py:943) pide al LLM que corrija los parámetros, como máximo MAX_REPAIR_ATTEMPTS = 2 veces. build_repair_prompt (utils.py:282) envía las definiciones de los parámetros, los valores usados, el comando completo y los últimos 2000 caracteres de stderr, y le pide que devuelva solo los parámetros que cambiar.

Esta vía se ejecuta dentro del proceso de Slicer, no de la CLI: _proposeRepair añade la carpeta Agent_CLI a sys.path y reimporta Agent_CLI_utils para no duplicar la lógica. La corrección vuelve a pasar por ParameterValidator y luego por build_cli_args, se muestra una diferencia old -> new y se exige una nueva confirmación Yes/No. Si la diferencia está vacía, el bucle se detiene.

_suggestFixFor (Agent.py:1240) lo complementa con un diagnóstico sin LLM, basado en palabras clave: modelo de Ollama ausente, ModuleNotFoundError, NameError: name 'nn' is not defined (una regresión conocida en transformers>=4.53.0, huggingface/transformers#43784), Numpy is not available (choque de ABI de numpy 2 con las ruedas de torch) o un fallo de conexión con Ollama.

Las rutas de los scripts no se resuelven

Un problema más fundamental que las firmas. El manifiesto solo da nombres sin ruta (path: "ALI_CBCT.py"). resolve_tool_path (utils.py:143) busca, por orden, en: $AGENT_CLI_TOOLS_DIR/<name>, <manifest_dir>/CLI files/<name>, <manifest_dir>/<name> y luego <ancestor>/CLI files/<name> subiendo 4 niveles.

Sin AGENT_CLI_TOOLS_DIR, el Agent no puede lanzar ningún módulo

No hay ninguna carpeta CLI files en ninguna parte de SlicerAutomatedDentalTools. El comentario del código cita la estructura AI_Agent/Agent_CLI/ + .../CLI files/, la del repositorio original del que se extrajo Agent_CLI. Aquí, cada script vive en la carpeta de su propio módulo (ALI_CBCT/ALI_CBCT.py, …). Ningún candidato coincide, y la función devuelve candidates[0] «so the error message points to a debuggable path», es decir, <Agent_CLI>/CLI files/ALI_CBCT.py.

subprocess.run no lanza una excepción (el ejecutable, sys.executable, existe); es Python el que sale con código 2 ante un archivo que no encuentra, lo que activa el bucle de reparación que, como corrige parámetros, estructuralmente no puede hacer nada al respecto.

E incluso con las rutas resueltas, algunos destinos seguirían fallando: DOCShapeAXI_CLI.py importa shapeaxi, un paquete que vive en un entorno conda que su módulo de Slicer invoca mediante conda run -n … o CondaSetUpCall. (MRI2CBCT ya no es un ejemplo: su nnunetv2 se ejecuta ahora en el propio Python de Slicer.) El Agent, por su parte, lo lanza todo con sys.executable, es decir, el Python de Slicer, nunca con conda.

10. Salvaguardas

Lo que existe:

  • Una confirmación modal obligatoria antes de cada ejecución, que enumera todos los parámetros, y una segunda antes de cada intento de reparación.
  • Bloqueo ante parámetros obligatorios ausentes: no se lanza nada mientras missing_required no esté vacío.
  • Coerción de tipos y comprobaciones de choices / min / max / extensión en carpetas.
  • Enmascaramiento de carpetas temporales, rellenadas desde slicer.util.tempDirectory() y no por el modelo.
  • Acotación: MAX_REPAIR_ATTEMPTS = 2, historial truncado a MAX_HISTORY_ENTRIES = 40 turnos.
  • try global en main(): stdout sigue siendo siempre JSON analizable, el traceback va a stderr.

Lo que no existe:

  • Ningún umbral de confianza. tool_confidence y parameters_confidence se calculan y se serializan, y luego se ignoran. Un enrutamiento con 0,1 se trata igual que uno con 0,95.
  • Ninguna comprobación de existencia de rutas. Una ruta alucinada pasa la validación, pasa la confirmación (el operador tiene que detectarla a ojo en el cuadro de diálogo) y solo falla cuando se lanza el módulo de destino.
  • Los errores del validador nunca se muestran. errors, warnings y extra_params se producen y luego se descartan.
  • Ninguna protección de las carpetas de salida. Si el modelo elige una carpeta de datos de entrada como output_folder, nada lo impide. Varias CLI del repositorio sobrescriben su archivo de entrada.
  • Los parámetros fuera de la especificación no se filtran en modo --flag.
  • log_path recibe una carpeta, no un archivo: los nombres log_path y logPath figuran en la lista de parámetros sustituidos por input.temp_folder. Las CLI que abran esta ruta para escritura fallarán.
  • Ninguna lista blanca de ejecutables. subprocess.run toma la lista exactamente como se construyó. La protección real es que tool_path procede del manifiesto, no del LLM: el modelo controla los valores, no el binario.

Agent_CLI.py se ejecuta en un proceso separado pero comparte los site-packages de Slicer, de ahí la instalación del lado del widget. No se crea ni se usa ningún entorno conda.

El servidor de Ollama se comprueba con una simple sonda de socket en 127.0.0.1:11434 (_ollama_responding, tiempo de espera de 0,5 s), se relanza si hace falta mediante Popen([binary, "serve"]) con una espera de hasta ~30 s en pasos de 500 ms manteniendo viva la interfaz. ensure_agent_ollama_running() se vuelve a llamar antes de cada mensaje (Agent.py:752), porque un servidor lanzado por el módulo no sobrevive a un reinicio de Slicer.

Windows: CREATE_NO_WINDOW para no hacer parpadear una ventana de consola. Sin WSL, a diferencia del resto del repositorio.

12. Trampas y puntos frágiles

  • resolve_tool_path no halla nada en este repositorio (§8). Es el obstáculo número uno. Soluciones posibles: crear una carpeta CLI files con enlaces, fijar AGENT_CLI_TOOLS_DIR, o poner rutas relativas al repositorio en el manifiesto y ampliar la búsqueda.
  • 14 firmas de 16 son erróneas, y el desplazamiento es silencioso.
  • batchdentalseg y clic no son CLI. cli_style: ui_module no se maneja en ninguna parte: cae en la rama --flag, que produce un comando que no puede funcionar sobre un módulo de Slicer con scripts.
  • input.folders.split(",") rompe cualquier ruta que contenga una coma, tanto para la lista de carpetas como para el join(",") del lado del widget.
  • El cross-encoder se recarga en cada mensaje (proceso nuevo), y su fallo degrada a las tres primeras herramientas del manifiesto sin que se informe al operador.
  • k=3 está fijado en el código. 16 herramientas, 3 candidatas: una mala puntuación del cross-encoder no la puede recuperar el LLM.
  • priority es inerte, lo que hace engañosa la clasificación del manifiesto.
  • subprocess.run bloquea el hilo de la interfaz durante toda la ejecución del módulo.
  • El historial mezcla prosa de la interfaz con contexto de enrutamiento: las burbujas de chat se reenvían tal cual como turnos de assistant a un enrutador restringido a JSON.
  • OnRetrieveButton reconstruye el historial dividiendo por el emoji 👨: / 🤖: (Agent.py:1004): un mensaje que contenga estos caracteres desincroniza la alternancia.
  • Detección del tema por muestreo de píxeles (widget.grab(), luminancia del píxel (5,5)), porque QPalette devuelve colores del tema claro incluso con un tema oscuro en Slicer (Agent.py:649). Funciona, pero depende del momento de la primera renderización, de ahí el QTimer.singleShot(0, ...) en setup.
  • Código muerto: AgentLogic.process(), build_tool_spec() (y todo el soporte de patterns/defaults a su alrededor), ValidationReport, positional_order, el campo examples del manifiesto, _cross_encoder_model, Agent_CLI/Resources/UI/Agent_CLI.ui.
  • extract_parameters devuelve 4 valores mientras que su anotación declara 3.
