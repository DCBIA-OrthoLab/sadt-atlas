Agent: pipeline completo

Un asistente en lenguaje natural que elige un módulo de la extensión, extrae sus parámetros, construye la línea de comandos y lo lanza. Aquí no se llama a ninguna red neuronal médica: el Agent solo hace enrutamiento y relleno de formularios. Esta página explica cómo, paso a paso; los detalles que necesita un desarrollador están en la página de código.

inédito Agent_CLI Python de Slicer qwen3:8b mediante Ollama cross-encoder MiniLM-L6 Código (desarrolladores) Bibliografía VISOR: parcial

Todo se ejecuta en local: un modelo de lenguaje de 8B servido por Ollama, más un pequeño cross-encoder para preseleccionar las herramientas candidatas.

Dos bases de código. Todo lo descrito aquí es el módulo legacy de Slicer (SlicerAutomatedDentalTools en 3c67957, 2026-10-26). VISOR tiene una herramienta de servidor llamada Agent, un router sobre un endpoint externo de Ollama, pero ningún cliente la llama: el panel AgentRemote que se distribuye en el cliente de VISOR es una copia del widget legacy que sigue ejecutándose en local. Ambos se describen en la página de VISOR para Agent. Evidencia.

1. Posición en la cadena

Nadie llama a Agent. Ningún otro módulo de la extensión lo usa: es un punto de entrada terminal. Hacia fuera, se llama a tres cosas:

LlamadoCómoDónde
Agent_CLIEl ejecutor de línea de comandos de Slicerproceso separado, Python de Slicer
El módulo de destino (ALI_CBCT, AMASSS_CLI, ...)iniciado como proceso hijo del panelPython de Slicer
Ollamasu cliente de Python, por HTTP en el puerto propio de la máquinaservidor local, instalado y lanzado por el módulo

El inventario de destinos es puramente declarativo: vive en manifest.yaml, un archivo YAML con 16 entradas. El Agent no descubre nada por sí solo: solo conoce este archivo.

En el códigoLos sitios de llamada con archivo y línea, y el código muerto que queda en el módulo

2. Archivos implicados

El panel (chat, zona de soltar, instalación de Ollama, confirmación, lanzamiento, reparación) se ejecuta en Slicer. Un programa de línea de comandos aparte hace el enrutamiento y la extracción y imprime JSON, sin ejecutar nada. Un archivo de utilidades contiene el manifest, el cross-encoder, la llamada a Ollama, la búsqueda de rutas y la construcción del comando. Un validador aplica coerción y comprueba los valores, y el manifest enumera las 16 herramientas direccionables. Sin entorno conda y sin GPU obligatoria: todo se ejecuta dentro del Python de Slicer; la única GPU que se usa lo es de forma indirecta, a través del servidor de Ollama.

3. Los modelos

3.1 El modelo de lenguaje, qwen3:8b mediante Ollama

Un solo modelo atiende las tres llamadas, enrutamiento, extracción de parámetros y reparación: Qwen3 con 8 mil millones de parámetros, ejecutado por Ollama (es decir, llama.cpp por debajo) en el formato GGUF que impone Ollama. No hay ningún modelo especializado ni ajuste fino. El nombre del modelo está escrito en dos lugares del código y se puede cambiar con una variable de entorno. La etiqueta por defecto pesa 5,2 GB (leído en ollama.com, no se puede determinar a partir del repositorio).

Que se ejecute en CPU o en GPU lo decide Ollama, no el módulo. El código extrae una consecuencia: en Linux, un Ollama instalado mediante snap está aislado en un sandbox, no ve la GPU de NVIDIA y recurre a la CPU, a 80 o 90 segundos por respuesta para un modelo de 8B, una cifra medida y escrita en el código. El módulo lo detecta y avisa, sin poder corregirlo.

Cuando no se encuentra ningún Ollama, el módulo descarga el archivo portátil oficial en una carpeta propia, de modo que el panel no necesita ninguna contraseña de root. Solo se usan dos ajustes de llamada: el modelo permanece cargado 30 minutos en lugar de 5, y la respuesta se restringe a JSON para el router, la extracción y la reparación (no para el modo consultor). No se pasa ninguna temperatura, semilla ni tamaño de contexto. Si el modelo no está presente, se descarga y se repite la llamada.

En el códigoLas constantes, la prueba de snap, el instalador de Ollama y los dos ajustes de llamada

3.2 El cross-encoder: ms-marco-MiniLM-L-6-v2

Es la única red neuronal real que se carga en el proceso: MiniLM, 6 capas, 22,7 millones de parámetros, entrenada en la tarea de ranking de pasajes de MS MARCO, descargada del Hugging Face Hub. No es un modelo de embeddings: la petición y el texto de la herramienta se pasan juntos al transformer, que produce un número de relevancia sin cotas. El programa de línea de comandos es un proceso nuevo en cada mensaje, así que el modelo se recarga cada vez.

Si falla la carga del cross-encoder, el recurso alternativo es brusco: las tres primeras herramientas del manifest, sea cual sea la pregunta, y el chat no se entera (solo se escribe una línea en la salida del programa). El campo priority del manifest nunca se lee.

4. Enrutamiento

Dos etapas, y el modelo de lenguaje solo interviene en la segunda. La etapa 1 es el cross-encoder de arriba. En la etapa 2 el modelo recibe la petición y los tres candidatos, una línea cada uno (nombre, descripción cortada a 140 caracteres, como máximo 8 etiquetas), y debe responder con un único objeto JSON: un nombre de herramienta, una confianza y un motivo de una frase. Conviene saber tres cosas:

  • El contexto de las carpetas no se entrega al router; solo se añade más tarde, para la extracción.
  • El historial de la conversación se inyecta tal como aparece en pantalla, incluidas las frases propias del panel como “After reflection, I would like to run ...”, de modo que el router JSON recibe prosa de la interfaz como si fueran respuestas anteriores.
  • La confianza y el motivo no sirven para nada. La confianza se analiza y se escribe, y luego nunca se vuelve a leer: no existe ningún umbral en ninguna parte, y la instrucción “confidence at most 0.4 when nothing matches” es solo una sugerencia al modelo.

La única red de seguridad es textual: la respuesta no debe ser null. Un nombre de herramienta que no esté en el manifest pasa esa prueba, y luego hace fallar al constructor del comando; el error se captura y se devuelve como mensaje de error.

En el códigoEl prompt del router, la inyección del historial y el código muerto de la especificación de herramientas

5. Extracción de parámetros

Una segunda llamada al modelo, con una herramienta ya elegida. Los parámetros técnicos (una carpeta temporal, una ruta de log) se quitan de lo que ve el modelo y los rellena después el panel: no se le pide al modelo que los invente. El prompt enumera cada parámetro con su tipo, si es obligatorio y cómo debe escribirse una lista, y luego impone siete reglas, sobre todo: extraer solo lo que menciona la petición, no inventar valores, dejar ausentes los parámetros opcionales no mencionados. La lista de parámetros obligatorios que devuelve el modelo se ignora: lo que cuenta es el validador.

El validador también fuerza a minúsculas el texto “true” o “false” cuando una herramienta compara el argumento en bruto. Por lo demás, el informe de validación se descarta casi por completo: sus errores y advertencias no aparecen en ninguna parte.

Las rutas se dejan por completo al modelo. Las carpetas soltadas en el panel se añaden a la petición, con la instrucción de tratarlas como fuente de verdad. No hay emparejamiento heurístico, ni mirada dentro de las carpetas, ni comprobación de existencia: solo el modelo adivina cuál de las rutas soltadas es el T1, cuál el T2 y cuál la carpeta del modelo. VISOR corrige solo la parte de la coma: la herramienta de servidor recibe las carpetas como una lista.

En el códigoEl prompt de extracción, las seis pasadas de validación y el bloque de rutas con su división por comas

6. Construcción y ejecución del comando

Sí, el módulo se lanza de verdad. El programa de línea de comandos solo construye el comando: combina los valores por defecto del manifest con los extraídos y antepone el intérprete propio de Slicer y la ruta del script. Para 14 de las 16 herramientas, los valores simplemente se escriben uno tras otro en el orden en que los declara el manifest (estilo posicional).

El panel ejecuta entonces el comando, y solo si no falta nada obligatorio: una burbuja de chat dice lo que querría ejecutar, un cuadro de diálogo Yes/No enumera cada parámetro, y con Yes se inicia el módulo. Si falta algo obligatorio, no se lanza nada: el panel enumera lo que falta con los valores ya conocidos, y espera un mensaje de seguimiento. El lanzamiento es síncrono y ocurre en el hilo de la interfaz: Slicer queda congelado durante todo el trabajo, que en una segmentación o un registro se mide en decenas de minutos.

En el códigoEl constructor del comando, el cuadro de diálogo y la llamada bloqueante al subproceso

7. El bucle de reparación

Esta vía se ejecuta dentro del proceso de Slicer, no en el programa de línea de comandos. La corrección vuelve a pasar por el validador y el constructor del comando, se muestra una diferencia de antiguo a nuevo, y se exige una nueva confirmación de Yes/No; una diferencia vacía detiene el bucle. Un diagnóstico basado en palabras clave, sin modelo, añade pistas para un modelo de Ollama ausente, un módulo de Python ausente, una regresión conocida en una versión reciente de transformers, un choque de numpy 2 con las ruedas de torch, y un fallo de conexión con Ollama.

En el códigoEl prompt de reparación, el truco de la reimportación y el diagnóstico por palabras clave

8. Módulos direccionables y su estado real

El manifest enumera 16 herramientas. Su lista de parámetros se comparó, archivo por archivo, con la línea de comandos real de cada script de destino. Solo 2 firmas de 16 son correctas: DOCShapeAXI y MRI2CBCT_resample. Otras dos (BatchDentalSeg y CLIC) son módulos de Slicer con script, no herramientas de línea de comandos, y no se pueden ejecutar así. AMASSS se niega de plano (“Expected 13 arguments”). A las demás les faltan entre uno y cuatro parámetros.

Como nada se nombra en la línea de comandos, una lista demasiado corta no lanza un error limpio: en AREG_IOS, por ejemplo, la ruta del archivo de log acaba como sufijo de un nombre de archivo. Ausentes del manifest, y por tanto fuera del alcance del Agent: VFACE, GreedyReg, CNE, AREG_IOSCBCT, SurgMovPred y Medical_Data_Anonymizer.

En el códigoLa tabla de 16 filas con el número de parámetros del manifest y los reales de cada script

Las rutas de los scripts no se resuelven

Un problema más fundamental que las firmas. El manifest solo da nombres sueltos de scripts. La búsqueda de rutas mira, por orden, en una carpeta indicada por la variable AGENT_CLI_TOOLS_DIR, en una carpeta “CLI files” junto al manifest, en la propia carpeta del manifest, y luego hasta cuatro niveles por encima. Ninguna de ellas existe en este repositorio, donde cada script vive en la carpeta de su propio módulo, así que ningún candidato coincide y la función devuelve el primero “so the error message points to a debuggable path”.

El lanzamiento en sí no lanza ninguna excepción (el intérprete de Slicer existe): es Python el que termina con el código 2 ante un archivo que no encuentra, lo cual activa el bucle de reparación. Incluso con las rutas resueltas, algunos destinos seguirían fallando: DOCShapeAXI necesita un paquete que vive en un entorno conda, mientras que el Agent lo lanza todo con el Python de Slicer.

9. Los dos modos

ModoLo que devuelve Agent_CLIEjecución
Agent (Automated)Un objeto JSON con la herramienta, su confianza, los parámetros, lo que falta y el comandosí, tras confirmación
Ask (Interactive)Texto libreninguna

En el modo Ask, cada línea de candidato lleva además la lista en bruto de sus parámetros, pegada tal cual en el prompt del sistema de un “expert medical image analysis consultant”. La respuesta no está restringida a JSON y se muestra tras quitar los caracteres * y #. El README llama a este modo “Consultant”, la interfaz dice “Ask (Interactive)”, y el código solo comprueba el nombre Agent, así que cualquier otro valor cae en el modo consultor.

10. Salvaguardas

Lo que existe:

  • Una confirmación obligatoria antes de cada ejecución, que enumera todos los parámetros, y una segunda antes de cada intento de reparación.
  • No se lanza nada mientras falte un parámetro obligatorio.
  • Coerción de tipos, y comprobaciones de opciones, rangos y de la extensión de los nombres que parecen carpetas.
  • Las carpetas temporales las rellena el panel, no el modelo.
  • Límites: 2 intentos de reparación, un historial de 40 turnos como máximo, y una captura global para que la salida del programa siga siendo siempre JSON analizable.

Lo que no existe:

  • Ningún umbral de confianza: un enrutamiento con 0.1 se trata igual que uno con 0.95.
  • Ninguna comprobación de que exista una ruta: una ruta alucinada pasa la validación y la confirmación (el operador tiene que detectarla a simple vista) y solo falla cuando se inicia el módulo.
  • Los errores del validador nunca se muestran.
  • Ninguna protección de las carpetas de salida: si el modelo elige una carpeta de datos de entrada como salida, nada se lo impide.
  • Ninguna lista blanca de ejecutables, pero la protección real es que la ruta del script procede del manifest, no del modelo: el modelo controla los valores, no el programa que se lanza.
En el códigoLa lista completa, incluidos los casos de la ruta del log y de los parámetros fuera de la especificación

11. Entorno

El panel instala cinco paquetes en el Python de Slicer, en un orden que importa: el cliente de Python de Ollama, un lector de YAML para el manifest, transformers anterior a la 4.53 (una regresión rompe la importación del cross-encoder), numpy anterior a la 2 (numpy 2 rompe las ruedas de torch) y, el último para no alterar las versiones fijadas, sentence-transformers. El programa de línea de comandos se ejecuta en un proceso aparte pero comparte los paquetes de Slicer. No se crea ningún entorno conda.

El servidor de Ollama se sondea en su puerto local, se inicia cuando hace falta y se espera hasta unos 30 segundos mientras la interfaz sigue viva. Se vuelve a comprobar antes de cada mensaje, porque un servidor lanzado por el módulo no sobrevive a un reinicio de Slicer. En Windows no se muestra ninguna ventana de consola; no hay soporte de WSL, a diferencia del resto del repositorio.

En el códigoLas versiones fijadas con sus motivos, la sonda de socket y la espera de arranque

12. Trampas y puntos frágiles

  • No se encuentran los scripts de los módulos, lo que bloquea toda la herramienta. Evidencia.
  • 14 firmas de 16 son incorrectas, y el desplazamiento es silencioso. Evidencia.
  • El cross-encoder recurre en silencio a una alternativa con las tres primeras herramientas, se recarga con cada mensaje y mantiene un top 3 fijado en el código. Evidencia.
  • Slicer se congela durante todo el trabajo. Evidencia.
  • La resolución de rutas se deja por completo al modelo. Evidencia.
  • Un Ollama instalado con snap se ejecuta en CPU. Evidencia.
  • Tres nombres para dos modos. Evidencia.
  • Queda código muerto: un process() sin usar, un constructor de especificación de herramientas sin usar, una caché del cross-encoder sin usar, y un archivo de interfaz que un módulo de línea de comandos nunca carga. Evidencia.
  • El historial mezcla prosa de la interfaz con contexto de enrutamiento, y cuando se vuelve a cargar una conversación guardada el historial se reconstruye dividiendo el texto por dos emojis, de modo que un mensaje que los contenga lo desincroniza (un chat en vivo conserva sus turnos como una lista).
En el códigoLos doce puntos frágiles con archivo y línea, incluidos la detección del tema y el número de valores devueltos
