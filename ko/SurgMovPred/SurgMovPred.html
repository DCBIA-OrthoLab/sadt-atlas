SurgMovPred

두부계측 측정값 스프레드시트가 들어가고, 예측된 골 변위 스프레드시트가 나온다. 목표값마다 하나씩, 스태킹된 scikit-learn 회귀기 112개이며, 신경망도, 영상도, 메시도 없다.

미발표 SurgMovPred_CLI conda 없음 — Slicer 자체 Python 참고문헌

두부계측 측정값 스프레드시트로부터 악교정 수술의 수술 이동을 예측한다. 신경망도, 영상도, 메시도 없다. 예측할 값마다 하나씩 스태킹된 scikit-learn 회귀기 112개를 Excel/CSV 파일에 행 단위로 적용한다.

1. 파이프라인에서의 위치

고립된 도구다. 저장소의 어떤 것도 이 도구를 호출하지 않고, 이 도구도 저장소의 어떤 것도 호출하지 않는다. 볼륨도, 메시도, 랜드마크도 읽지 않는다. 입력은 스프레드시트 폴더이고, 출력은 또 다른 스프레드시트다.

호출 대상방식
SurgMovPred_CLIslicer.cli.run(slicer.modules.surgmovpred_cli, …) (SurgMovPred.py:842)

모듈은 MRML 장면에 연결되어 있지 않다. vtkMRMLNode를 만들지도, 읽지도, 변환하지도 않는다. pandas 스크립트 위에 얹힌 실행용 인터페이스다.

함정

CNE 모듈(임상 노트 요약)에서 복사·붙여넣기로 남은 흔적이며, 실제 파이프라인으로 오해하면 안 된다. helpText는 "This tool helps to create summaries of clinical notes"라고 하고, parameterNodeWrapper는 notesFolder_input / modelType / notesType으로 문서화되어 있으며, process()는 여전히 인자 이름을 notesFolder_input / notesFolder_output으로 쓴다 (SurgMovPred.py:236, SurgMovPred.py:815).

3. 입력과 전처리

허용 형식. load_data_from_directory() (SurgMovPred_CLI.py:141)는 폴더 안의 모든 *.csv, *.xlsx, *.ods 파일(확장자 소문자 와 대문자 모두)을 모아 읽고(read_csv, read_excel, read_excel(engine='odf')) 이어 붙인다 (pd.concat(..., ignore_index=True)). 하위 폴더로 재귀하지 않는다. Excel 통합 문서는 첫 번째 시트만 읽는다 — 공식 테스트 파일에는 시트가 일곱 개(all_data, demographics, Invivo_ceph, surgical_mov, dolp_ceph_T0, dolp_ceph_T1, dolp_ceph_total) 있고, 첫 번째 자리에 있는 것은 all_data다.

열 이름 정규화, clean_name() (SurgMovPred_CLI.py:39)은 학습 때 쓰인 철자로 되돌리기 위해 입력에 적용된다.

  1. ", \, [, ] 제거;
  2. [0-9a-zA-Z_'] 밖의 모든 문자는 _가 된다 — 아포스트로피는 일부러 유지한다(코드 주석: Jarabak's와 SM_A'_CP를 위해);
  3. 반복된 _를 하나로 줄이고 양 끝을 잘라 냄;
  4. "total" → "Total";
  5. 이름이 숫자로 시작하면 f_ 접두어.

이 정리로 실제 특징 이름이 설명된다: SM-A-FH  (테스트 파일에서 뒤에 공백 두 개)는 SM_A_FH가 되고, Jarabak's ratio  는 Jarabak's_ratio가, FMA(MP-FH) Ang_2D는 FMA_MP_FH_Ang_2D가 된다.

환자 식별자. find_id_column() (SurgMovPred_CLI.py:81)은 대소문자를 구분하지 않는 패턴 8개 (#, id, patient id, patient number, subject, …)를 시험한 뒤, 마지막 수단으로 "patient"와 "id"를 모두 포함하는 열을 찾는다. 테스트 파일에서는 열 이름이 #이다. 실패하면 출력 열 IDPatient는 단순 경고와 함께 pd.NA로 채워진다.

값 정규화. 모델 패키지마다 자체 StandardScaler 계산(중심화 + 스케일링, with_mean=True, with_std=True)를 담고 있으며, 예측 직전에 적용된다 (SurgMovPred_CLI.py:237). 결측값 대체는 없다. 결측값은 NaN으로 출력까지 그대로 전파된다.

_T0 접미사에 대한 허용(SurgMovPred_CLI.py:223): 모델이 X_T0를 기대하는데 열 이름이 X이면 받아들인다.

참고

허용은 이것 하나뿐이다. 다른 특징이 하나라도 빠지면 모델 전체가 경고와 함께 건너뛰어지고, 해당 열은 결과에서 빠진다.

4. 모델

가중치는 저장소에 없다. onDownloadDefaultModel() (SurgMovPred.py:782)이 다음을 다운로드하고 압축을 푼다.

https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/SurgMovPred/all_models.zip
  -> Documents/SlicerDownloads/SurgMovPred/Models/all_models/

706 MB, 폴더 112개, 각각 약 13 MB짜리 stacking_package.pkl 하나. load_all_model_packages()는 재귀적으로 Path.glob("**/stacking_package.pkl")을 수행하고 package['target_name']으로 색인한다. 선택기를 all_models/에 지정하면 112개 모델이 모두 로드되고, 하위 폴더 하나를 지정하면 하나만 로드된다. CLI 도움말은 saved_models/class_1, saved_models/class_None 폴더를 언급하지만 — 골격 분류별 계층 구조는 공개된 아카이브에 존재하지 않으며, 아카이브는 평평한 구조다.

각 .pkl은 키가 네 개인 joblib 사전이며, SurgMovPred_CLI.py:212에서 그대로 사용된다.

이 정보는 all_models/Mn_MB_Genioplasty_Total_Pred/stacking_package.pkl과 all_models/Mx_ALL_APoint_P-_A_Pred/stacking_package.pkl에서 직접 읽었다(피클 스트림 검사, 실행하지 않음). 145개 특징은 두 패키지에서 동일하다. 나머지 110개도 같다는 형식적 보장은 없지만, 크기가 거의 같다(13.17–13.19 MB)는 점이 이를 강하게 시사한다.

4.2 구조

신경망은 없다. 기본 회귀기 세 개와 선형 메타 회귀기 하나로 이루어진 스태킹 앙상블이며, _sklearn_version = 1.6.1로 직렬화되었다.

역할추정기피클에서 읽을 수 있는 매개변수
기본 multitask_elasticnetElasticNetCVl1_ratio 그리드, n_alphas, eps, selection='cyclic'
기본 lgbmlightgbm.sklearn.LGBMRegressorboosting_type='gbdt', objective='regression', num_leaves=31
기본 gaussian_processGaussianProcessRegressor커널 Product(ConstantKernel, RBF), optimizer='fmin_l_bfgs_b', normalize_y

passthrough=False는 메타 모델이 원래의 특징 145개가 아니라 세 기본 모델의 예측만 본다는 뜻이다. stack_method='predict': 기본 모델마다 스칼라 값 하나, 따라서 입력이 세 개인 선형 회귀다.

파일 크기의 대부분(특징 145개에 13 MB)은 학습 행렬을 보관하는 GaussianProcessRegressor와 LightGBM 부스터에서 나온다.

학습은 저장소에 없다. 스크립트도, 데이터셋도, 지표도, 시드도 없다. 저장소로부터 알 수 없는 것: 코호트 규모, 검증 프로토콜, 목표값별 성능.

테스트 파일의 Gender, Surg, Genio, 3piece, assymetry, Skl_Cl_2 열은 검사한 두 패키지의 특징 145개에 나오지 않는다. 읽힌 뒤 무시된다.

4.4 무엇을 예측하는가

목표값 112개 = 구조 28개 × 성분 4개.

목표값 이름으로 본 성분: P-/A+(후방 음수 / 전방 양수), R-/L+(우측 음수 / 좌측 양수), Down+(수직, 아래쪽 양수), 그리고 Total. 따라서 앞의 셋은 두부계측 좌표계(CP, MSP, FH)에서 변위 벡터의 부호 있는 성분이고, 네 번째는 거의 확실히 그 크기다 — 이름에서 추론한 것이며, 단위(mm)는 어디에도 적혀 있지 않다.

구조 28개:

5. 핵심 처리

predict_all_targets()(SurgMovPred_CLI.py:194), 전체:

for target_name, pack in packages.items():
    X_target = df_cleaned[[feature_source[f] for f in pack['features_names']]]
    X_target.columns = pack['features_names']
    X_scaled = pack['scaler'].transform(X_target)
    predictions_by_target[target_name] = pack['model'].predict(
        pd.DataFrame(X_scaled, columns=..., index=df_cleaned.index))

사후 보정도, 범위 제한도, 목표값 간 일관성도, 신뢰 구간도 없다 — GaussianProcessRegressor는 표준편차를 낼 수 있지만, 요청받지 않는다. 각 목표값은 독립적으로 처리되며, 목표값마다 try/except가 있다. 충돌한 목표값은 다른 목표값을 중단시키지 않고, 해당 열이 그냥 사라진다.

112개 모델이 모두 한꺼번에 메모리에 로드된다(load_all_model_packages). 즉 데이터를 읽기도 전에 RAM 약 1.5 GB를 쓴다.

함정

결과를 다시 적용하는 과정이 전혀 없다. 행렬을 만들거나, 메시를 옮기거나, Slicer 노드를 만들거나, 뷰를 여는 것이 아무것도 없다. 예측은 스프레드시트에서 멈춘다. "예측을 어떻게 다시 적용해 시각화 가능한 결과를 만드는가"라는 질문에 이 저장소는 답하지 않는다 — 값을 수술 계획 소프트웨어로 옮기는 것은 사용자의 몫이다.

8. 실행 환경

모든 것이 Slicer의 Python 안에서 실행된다. check_dependencies() (SurgMovPred.py:156)는 Apply를 누를 때마다 호출된다.

pip_install("numpy==2.4.0")은 무조건, Apply를 누를 때마다 실행된다. 실행 중인 Slicer 세션에서 numpy를 바꿔 넣는 것은 바로 확장 기능의 다른 곳에서 scipy import를 깨뜨리는 원인이다(Slicer의 scipy는 Slicer의 numpy에 맞춰 컴파일되어 있다). 모듈에서 단연 가장 위험한 지점이며, 주 버튼이 이를 촉발한다.

설치는 conda 없이, GPU 없이, torch 없이 이루어진다.

CLI는 scikit-learn의 InconsistentVersionWarning을 숨긴다 (SurgMovPred_CLI.py:19). 패키지는 scikit-learn 1.6.1로 직렬화되었고, 그때그때 설치된 버전으로 역직렬화된다. 주석은 그 위험을 감수한다 ("models are tested for compatibility before being shipped").

9. 함정과 취약 지점

  • 실행할 때마다 pip_install("numpy==2.4.0"). 실행 중인 Slicer 세션에서 numpy를 바꿔 넣는 것은 바로 확장 기능의 다른 곳에서 scipy import를 깨뜨리는 원인이다(Slicer의 scipy는 Slicer의 numpy에 맞춰 컴파일되어 있다). 모듈에서 단연 가장 위험한 지점이며, 주 버튼이 이를 촉발한다.
  • 동작하지 않는 "test files" 버튼: DownloadTestFiles() (SurgMovPred.py:763)는 TestFiles.zip을 다운로드하기는 하지만, 입력/출력 필드를 채우는 것은 if os.path.exists(.../V_FACE/DefaultList)일 때뿐이다 — VFACE 모듈에서 복사·붙여넣기로 남은 흔적이다. VFACE의 테스트 데이터가 없으면 아카이브는 다운로드된 뒤 무시된다.
  • .ods는 광고되지만, odfpy는 설치되지 않는다(check_dependencies 기준). (다만 Anonymizer 모듈이 설치하므로, 두 모듈을 모두 쓴 컴퓨터에서는 문제가 가려질 수 있다.)
  • 특징 하나 누락 = 모델 하나가 조용히 건너뛰어짐. 로그에는 "Model 'X' skipped: missing N input feature(s)"라고 나오지만, 출력 파일 자체는 그냥 열이 하나 적을 뿐이다. 이름이 잘못 붙은 스프레드시트는 실패 없이 예측 열이 하나도 없는 predictions_outputs.xlsx를 만들 수 있다.
  • 입력 파일을 무작정 이어 붙임: 열이 서로 다른 스프레드시트 두 개는 NaN을 만들고, model.predict는 NaN에서 예외를 일으킨다 — 오류는 목표값별로 잡히므로, 결과는 일부만 나오고 그 사실은 거의 드러나지 않는다.
  • Excel 시트는 하나만 읽는다. 첫 시트가 데이터 시트가 아닌 통합 문서는 빈 결과를 낸다.
  • 모델 1.5 GB를 무조건 로드한다. 예측할 행이 하나뿐이어도, 사용자가 목표값 하나에만 관심이 있어도 마찬가지다.
  • 출력에 불확실성이 없다. 세 기본 모델 중 하나가 가우시안 프로세스인데도 그렇다.
  • 같은 분절의 점들 사이에 강체 일관성이 없다(§7).
  • helpText, 매개변수 노드의 docstring, process()의 인자 이름은 전혀 다른 도구(임상 노트 요약)를 기술한다.

10. 문헌

SurgMovPred를 다루는 논문은 없다. 저장소도, 릴리스도, README도 어떤 참고문헌을 인용하지 않으며, 모듈 이름으로 검색해도 아무것도 나오지 않는다. 이 모듈은 확장 기능의 README에도 올라 있지 않다.

출판된 맥락이며, 이 코드에 대한 기술과 혼동해서는 안 된다.

  • Machine-learning-based approach for predicting postoperative skeletal changes for orthognathic surgical planning (PubMed 35132764) — 제기된 문제는 같지만(수술 전 측정값으로 수술 후 골격 변위 예측), 이 연구가 이 가중치의 출처라는 근거는 없다.
  • Oliveira, Cevidanes, Bianchi et al., Artificial intelligence as a prediction tool for orthognathic surgery assessment, Orthodontics & Craniofacial Research, 2024 — 같은 팀(UNC/Pacific)이지만 대상이 다르다. 이동 자체가 아니라, 측면 두부계측 방사선사진으로 수술의 필요 여부를 예측한다.
  • Prediction of orthognathic surgery plan from 3D cephalometric analysis via deep learning (PMC10024836) — 같은 목표, 딥러닝 접근. 반면 SurgMovPred는 고전적인 표 형식 모델이다.

기반 도구는 문서화되어 있다: StackingRegressor 와 LightGBM.
