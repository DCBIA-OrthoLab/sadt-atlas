실행 과정, 단계별

Slicer에서의 클릭과 파일이 돌아오기까지 사이에 일어나는 일을 다룬다. 서버가 노출하는 경로, POST /run/{tool} 하나가 거치는 열다섯 단계, 관찰자가 보는 단계(phase), 실행이 접수되고 분리되고 취소되고 일시 정지되고 되감기는 방식, 그리고 각 실패가 어떤 HTTP 상태로 끝나는지다. 모든 주장은 읽어 낸 줄을 인용한다.

VISOR-serve e9a7e5d 구현됨, server/tests에 테스트 함수 857개 2026-11-09에 읽음 아키텍처 배포 보안
참고

이 페이지는 이 사이트의 나머지가 문서화하는 레거시 Slicer 코드가 아니라 서버 세대인 VISOR를 설명한다. 인용은 file:line 뒤에 저장소가 붙는다. 커밋 e9a7e5d 시점의 VISOR-serve(경로가 주어지지 않으면 server/main.py의 줄), 19b95e8 시점의 AutomatedDentalToolsRemote(Slicer 클라이언트), 6ba2a78 시점의 SADT-VISOR(도구)다. 저장소에는 자체 문서가 있고, 그중 여러 페이지는 코드보다 오래되었다. 둘이 어긋나는 곳에서는 이 페이지가 코드를 따르며 콜아웃에서 그렇다고 밝힌다. 전송과 저장된 데이터가 무엇으로 보호되는지는 보안 페이지에, 구성 요소가 어떻게 맞물리는지는 아키텍처 페이지에 있다.

1. 경로

main.py에는 경로 핸들러가 열여덟 개 선언되어 있으며, 그중 둘은 토큰 없이 답한다. 데코레이터가 유일한 권위다. docs/ARCHITECTURE.md:34-42는 다섯 개를, server/README.md:49 이후는 더 많이 나열하지만 전부는 아니다. 표의 "Gate"는 maintenance.require_accepting 의존성이다. 운영자가 POST /maintenance로 문을 닫은 동안에는 이 경로가 Retry-After: 10과 함께 503으로 답한다(wire/maintenance.py:113-146). 읽기, 취소, 삭제는 의도적으로 gate 대상이 아니므로, 이미 진행 중인 실행은 언제든 지켜보고 수거할 수 있다.

2. 정상 경로, 제출부터 정리까지

블로킹 경로의 실행 하나(클라이언트가 실행 내내 HTTP 요청 하나를 열어 둔다). 분리형(detached) 변형은 4절에 있다. 다이어그램의 세 열은 서로 다른 세 프로세스다. Slicer 모듈, FastAPI 프로세스, 그리고 도구에 속한 별도의 Python 인터프리터다.

  1. 조각 업로드. 클라이언트는 큰 입력을 POST /uploads와 PUT /uploads/{id}/parts/{n}로 보낸다. 조각은 기본 8 MB이고 서버가 1~64 MB로 제한하며(wire/transfer.py:204-215), 병렬 연결 넷, 조각마다 X-Part-SHA256에 담은 SHA-256, 조각당 최대 네 번 시도한다(AutomatedDentalToolsRemote ServerToolsCoreLib/transfer.py:62-67, 309). 블로킹 경로에서는 조각 둘에 못 미치는 파일, 즉 16 MB 미만은 폼에 인라인으로 들어가며, 클라이언트의 기본값인 분리형 경로에서는 모든 파일이 /uploads를 거친다(클라이언트 client.py:1106-1121). 서버에서 세션은 디스크에 있고, blob은 os.truncate로 미리 크기가 잡히며 각 조각은 os.pwrite로 자기 오프셋에 기록된다. 다시 조립하는 것은 없으며, 실행 시점에 blob은 복사되지 않고 작업 디렉터리로 이름이 바뀌어 들어간다(claim_upload, wire/transfer.py:279).
  2. 실행은 폼을 읽기 전에 등록된다. run_tool(main.py:1806)은 X-Run-Id를 받아 먼저 실행 디렉터리를 연다. 클라이언트가 다른 스레드에서 이벤트 스트림을 열기 때문에 둘의 순서를 정할 수 없어서다. 잘못된 id는 400, 이미 쓰인 id는 409다(wire/runs.py:178-213).
  3. 도구와 모드. _run_tool(main.py:1833)은 도구를 찾고(없으면 404), 폼을 읽고, __uploads__를 푼다. 도구가 파사드(ALI, AREG)이면 mode 필드를 제거하고 파사드를 그 대상으로 바꾸며 대상이 선언하지 않은 인자를 버린다. 모드가 없거나 알 수 없으면 422다(main.py:1888-1917).
  4. 스테이징. 각 입력은 TEMP_DIR/<mkdtemp>/<argument>/<safe name>.<ext>에 기록된다. 환자의 파일 이름은 유지되며 [A-Za-z0-9_.-]로 걸러지고(_safe_stem, main.py:1105), 단계(phase)는 staging이며 메시지는 파일 이름이 아니라 "input k of n"이다. 여기서 거부되는 것: 알 수 없는 인자(422), 스칼라 인자에 보낸 파일(400), 금지된 확장자(400), 한도를 넘는 크기(413), 빈 파일 또는 잘린 .gz(400, _reject_a_truncated_gzip, :1172). .zip을 path 인자에 주면 서버가 풀며, zip-slip, 절대 경로 멤버, 심볼릭 링크는 거부되고 풀린 크기에는 2000 MB 상한이 있다(file_utils.py:125, config.py:241).
  5. 호스팅된 파일. 이름으로 고른 모델이나 테스트 파일은 데이터 저장소를 통해 찾는다(없으면 404). DATA_DIR은 읽기 전용이므로, 폴더 인자용 아카이브는 작업 디렉터리에 풀린다.
  6. 검증, 이벤트 루프 밖에서. tool.invoke는 워커 스레드에서 CapacityLimiter 아래 실행되며, 그 한도는 MAX_CONCURRENT_TOOLS(4, main.py:183-187, :2081-2083)다. SchemaTool.invoke는 게시된 스키마에 대해 검증하고(ToolArgumentError면 422), 다중 선택 필드를 리스트로 바꾸고, dispatch.dispatch를 호출한다.
  7. Dispatch. dispatch(execution/dispatch.py:1080)는 도구에 인터프리터가 있는지 확인하고, TEMP_DIR/job_<uuid>/{input,output}을 만들고, 매개변수를 완성하고(output_dir은 항상 작업 자신의 것이고, device는 설정에서 주입되며, 이름 없는 모델 인자는 도구의 모델 폴더를 받는다), job.json을 쓰고, 타임아웃을 계산한다. deployment_config.timeout_seconds(tool.name) or None이다(dispatch.py:1137).
  8. 접수(Admission). 실행은 바이트와 코어의 예산에서 자리를 요청한다(5절). 기다려야 하면 단계는 한 번만 queued_gpu가 되며, 클라이언트는 여전히 취소할 수 있다.
  9. 도구가 시작된다. Popen([venv/python, runner.py, --job job.json])이며 stdout과 stderr는 파일로, cwd는 작업 디렉터리, start_new_session=True다(dispatch.py:618). 환경은 서버의 것이고 API_TOKEN은 제외되며, 스레드 상한(OMP_NUM_THREADS, MKL_, OPENBLAS_, NUMEXPR_, VECLIB_, ITK_GLOBAL_DEFAULT_NUMBER_OF_THREADS)과 변수 SADT_API, SADT_JOB_ID, SADT_JOB_DIR, SADT_PROGRESS_FILE, SADT_SUPERVISOR_DEADLINE이 더해진다(_child_environment, dispatch.py:540). 프로세스 그룹 id는 디스크에 기록되고, 단계는 running이다.
  10. 러너. runner.py는 도구 자신의 인터프리터가 실행하며, 표준 라이브러리만 쓰고(Python 3.9~3.13), 도구의 src/ 아래 단일 패키지를 import하고, 주석에 따라 인자를 변환하고, run()을 호출하고, _TreeSampler(runner.py:405)로 최대 VRAM, RSS, 코어를 표본 추출하고, result.json을 원자적으로 기록한다. {"result", "peak_vram_bytes", "peak_rss_bytes", "peak_cpu_cores", "channels", "vram_source"} 또는 {"error": {"type", "message"}}다.
  11. 결과를 읽는다. 종료 코드 0 뒤에 result.json이 없으면 ToolExecutionError이며, error는 ToolFailure(type, message)가 된다. 측정값은 비용 표와, measured를 실은 이벤트로 흘러간다.
  12. 패키징. _finish_run(main.py:2200)이 단계를 packaging으로 설정한다. files인 출력은 압축 수준 1로 {tool}_{stem}.zip이라는 이름의 zip이 되며, 이미 압축된 멤버(.gz, .zip, .xlsx 등)는 그대로 저장된다(file_utils.py:199-251, config.py:252). text 출력은 {"result": ...}로 응답된다.
  13. 전달. 두 방식이 있다. 기본적으로 파일은 FileResponse로 스트리밍되고 응답 뒤에 백그라운드 작업에서 제거된다. 클라이언트가 X-Result-Delivery: reference를 보냈고 그리고 파일이 최소 RESULT_REFERENCE_MIN_MB(16, config.py:249)이면 파일은 결과 저장소로 이동(이름 변경)되고 응답은 {"result_ref": {result_id, filename, media_type, size}}다(wire/transfer.py:325-349). 그러면 클라이언트는 GET /results/{id}를 Range로 연결 넷으로 가져오고, 모든 zip 멤버의 CRC를 검사하고, DELETE /results/{id}로 마친다(클라이언트 client.py:1696-1773).
  14. 실행 기록. _tracked_run(main.py:1610)이 done을 기록하고 runs.discard를 백그라운드 작업으로 예약하므로, 디렉터리는 스트림의 끝보다 오래 남는다.
  15. 정리. 스테이징된 입력은 finally(_run_tool 안)에서, 작업 디렉터리와 출력은 스트림 뒤의 백그라운드 작업에서 사라지며, 오류가 있으면 즉시 버려진다. 결과와 끝나지 않은 업로드는 900 s 동안 유휴 상태이면 reaper가 60 s마다 쓸어 낸다(config.py:245-246, _reaper_loop main.py:63-81). 서버 로그는 엔드포인트, 도구, 상태, 소요 시간, 크기를 기록하며 파일 내용, 인자 값, 진행 메시지는 결코 기록하지 않는다(_log_served, main.py:351-371).
확인됨

프로세스 모델이 설계의 요점이다. 서버는 도구를 결코 import하지 않는다. SchemaTool.invoke는 항상 dispatch를 거치고(registry/schema_tool.py:812-822) SchemaTool.run은 RuntimeError를 일으킨다(:840-844). 픽스처 둘, Example_Tool과 Test_Tool만 프로세스 안에서 import된다. 따라서 도구의 인터프리터, torch, VRAM은 실행이 끝날 때 프로세스와 함께 사라진다.

3. 단계, 상태, 이벤트 스트림

실행에는 단계(phase)(하고 있는 일)와 상태(state)(관찰자가 결론지어야 할 것)가 있다. 단계는 received, staging, queued_gpu, running, packaging, done, failed, cancelled, paused다(wire/runs.py:73-81). 상태는 pending(received, staging, queued_gpu), running(running, packaging), done, failed, cancelled(마지막 셋이 종료 상태)와, 종료 상태가 아닌 paused다(:83-93).

GET /runs/{id}/events는 Server-Sent Events 스트림이다. 관찰자가 연결되기 전에 기록된 것까지 포함해 첫 이벤트부터 시작한다. 관찰자는 두 번째 스레드에서 열리므로 POST와 순서를 정할 수 없기 때문이다(main.py:1004-1048). 파일은 워커 스레드에서 0.25 s마다 폴링되며(RUN_EVENT_POLL_SECONDS, config.py:275) 각 프레임은 data: {json}이다. 스트림은 종료 이벤트에서, 또는 실행 디렉터리가 사라졌을 때 끝난다.

이벤트는 {seq, at, state, phase, fraction, message, depth}이며, 여기에 tool(중첩 호출의 이름, [A-Za-z0-9_-]{1,64}), result(서버만 기록한다), measured(vram_bytes, ram_bytes, cpu_cores, channels)가 더해진다(_normalised, wire/runs.py:473-539). seq는 읽는 시점의 줄 번호이며 저장되지 않는다. message는 줄바꿈 없이 200자로 잘린다. 도구가 쓴 줄은 항상 running으로 읽힌다. done, failed, cancelled를 선언할 수 있는 것은 서버뿐이다.

디스크에서 TEMP_DIR/runs/<run_id>/는 events.jsonl, meta.json, pgid, cancel, 그리고 멈췄을 때 paused.json을 담는다. 추가 기록은 잠금을 쓰지 않는다. 각 레코드는 단일 write()이며 MAX_RECORD_BYTES(4096) 미만이고 POSIX에서 O_APPEND로 원자적이다(wire/runs.py:137). 스트림은 MAX_RUN_EVENTS = 2000개 이벤트로 제한되며, 상한을 넘으면 "보고되지 않음" 이벤트 하나가 전달되고 그 이상은 없으며 종료 이벤트는 결코 잘리지 않는다(_capped, wire/runs.py:611-635).

도구의 진행 상황. 도구는 {"fraction": ..., "message": ...}를, SADT_PROGRESS_FILE이 가리키는 파일에 덧붙여 진행 상황을 보고한다. sup.progress(fraction, message)도 같은 파일에 기록한다(runner._append_progress, runner.py:1058). fraction은 0과 1 사이의 숫자이거나 없으며, 클라이언트는 이를 지어내지 않는다.

함정

실패 뒤에는 실행 디렉터리가 즉시 제거된다. _tracked_run이 failed를 기록하고 같은 호흡에 runs.discard를 호출한다(main.py:1636-1642). 종료 이벤트를 아직 읽지 못한 관찰자는 디렉터리가 사라진 것을 발견하고 스트림이 그냥 끝난다. EventReader.read는 없는 파일에 finished를 설정하고 아무것도 반환하지 않는다(wire/runs.py:567-578). 실패 자체는 여전히 POST가 보고한다. 성공 뒤에는 디렉터리가 응답의 끝보다 오래 남는다.

4. 분리형 모드

X-Run-Delivery: detached를 쓰면 서버는 입력이 스테이징되는 즉시 202로 답하고, 실행은 백그라운드 작업으로 계속되며, 그 종료 이벤트가 result_ref를 싣는다(_detach main.py:1401, _detached_run :1354). X-Run-Id가 필요하고(없으면 400) 본문의 어떤 파일도 거부하며(400), 모든 입력은 /uploads를 거쳐 도착해야 한다. 클라이언트가 아직 종료 이벤트를 읽지 않았으므로 실행 디렉터리는 끝날 때 삭제되지 않으며, 읽을 때마다 갱신되는 RUN_TTL_SECONDS = 900 s의 비활성 뒤에 만료된다(config.py:263).

이유는 타임아웃이다. 헤더 위의 주석이 분명히 말한다. Slicer 클라이언트의 POST 읽기 타임아웃은 600 s에 상한이 한 시간이고, 서버는 그보다 오래 걸리는 코호트에 맞춰 설계되었으며, 연결이 끊겨도 실행이 멈춘 적은 없고 응답만 버려졌다(main.py:157-160). 분리형에서 클라이언트는 긴 요청을 붙들고 있지 않고 이벤트 스트림을 기다리며, 이 스트림은 다시 연결되고 seq로 중복을 제거한다. 클라이언트는 이를 기본으로 켜 두며(Remote 확장의 DETACHED_RUNS = True, config.py:90), stop_after를 요청할 때는 블로킹 경로로 되돌아간다. 체크포인트 기록이 POST 본문으로만 전달되기 때문이다(client.py:1094-1106).

코드에서 확인된 결함

main.py:2332는 ToolExecutionError를 일으키는데, 이는 main.py가 결코 import하지 않는 이름이다. 이 모듈은 dispatch를 import하고 dispatch.ToolFailure와 dispatch.RunCancelled를 속성으로 쓴다(파일에서 이 이름이 단독으로 나오는 곳은 그 raise뿐이다). 이 분기는 "분리된 실행이며, 결과를 참조로 저장하는 일이 OSError로 실패한 경우"다. 의도한 메시지 대신 NameError를 일으키므로 실패 보고가 틀리게 된다. 이 분기는 드물며, 이 페이지를 위해 이에 대한 테스트를 실행하지는 않았다.

5. Admission: 카운터가 아니라 예산

실행은 슬롯을 차지하는 것이 아니라 여유 공간을 예약한다. execution/admission.py의 승인 코드는 RAM 바이트, VRAM 바이트, 코어 수로 이루어진 Budget(:239)과, 그 안에 자리가 나기를 기다리는 실행 대기열을 유지한다.

  • 프로세스별 FIFO. 티켓은 순서대로 처리되며, 맨 앞의 실행만 승인될 수 있다. 모듈은 이 절충을 명시한다. 예측 가능한 순서를 얻는 대신 head-of-line blocking을 감수한다(admission.py:239-251). reserve(candidates)는 폭이 점점 줄어드는 형태를 차례로 시도해 처음으로 들어맞는 것을 택한다(:446-530).
  • 세 가지 안전 규칙. 비용이 한 번도 측정되지 않은 도구는 전체 예산을 예약하고 단독으로 실행된다. 예산보다 큰 요청도 머신이 비어 있으면 단독으로 실행된다. 카드에서 실제로 비어 있는 메모리도 함께 확인한다(admission.py:22-33). 안전 여유 1.3이 적용된다(SAFETY_MARGIN, :49).
  • 예산의 출처. resources.py는 커널보다 먼저 cgroup(v2, 그다음 v1)을 읽고, 남은 VRAM은 nvidia-smi로 읽는다. 사용 비율은 SADT_RESOURCE_SHARE = 0.75(config.py:219)이고, 예산은 SADT_EXPECTED_CLIENTS = 4(config.py:234)에 따라 작업별 몫으로 나뉜다. SADT_CPU_BUDGET, SADT_RAM_BUDGET, SADT_VRAM_BUDGET과 *_PER_JOB 형태가 이를 덮어쓰며, 75%, 8, 16GB 같은 값을 받는다(config.py:213-237). 예상 클라이언트 수는 선언이다. 공유 토큰이 하나뿐이고 클라이언트 식별 정보가 없으므로 서버는 워크스테이션 수를 셀 수 없다.
  • 코어 하한. SADT_MIN_CPUS_PER_JOB = 4(config.py:161): 이보다 적으면 실행은 자원이 모자란 채로 승인되지 않고 기다린다.
  • GPU 사용 여부. 실행이 선언한 device가 cpu 또는 mps로 해석되지 않는 한, 카드를 쓰려는 것으로 간주된다(dispatch.uses_the_gpu, :95).
  • 학습된 비용. execution/costs.py는 각 도구의 최근 COST_WINDOW = 20회 실행의 자원별 최댓값을 보관하고, 서로 다른 폭이 두 개 관측되는 즉시 고정값 + 한계값 × 폭 직선을 맞춘다(_fit :429, _predict :404). “0으로 측정됨”과 “측정된 적 없음”은 구분된다(vram_known). 카드 전체를 쓴 측정값은 단독으로 실행된 경우에만 학습된다(dispatch._keep_measurements, :826-914). 이 표는 SCHEMA_CACHE_DIR에 저장된다.
  • 폭과 채널. num_workers 또는 batch_size를 선언하는 도구(CHANNEL_ARGUMENTS, concurrency.py:145)는 여러 항목을 동시에 실행할 수 있다. width_from은 deployment.toml에서 어느 인자를 셀지 알려 준다. 도구는 sup.channels(wanted)를 호출하고 min(affordable, wanted, SADT_CHANNELS, ceiling)을 받으며, 1 미만이 되는 일은 없다(runner.py:2134). SADT_MAX_CHANNELS = 0은 상한이 없다는 뜻이다(config.py:130). 채널을 하나만 여는 실행은 예약 전체를 유지한다.
  • 메모리 재시도. 실행이 메모리 부족으로 죽으면(OutOfMemoryError, CudaOutOfMemoryError, MemoryError, 또는 result.json 없이 SIGKILL, _out_of_memory dispatch.py:933) 최대 MEMORY_RETRIES = 2회까지 다시 시작되며, 이미 머신 전체를 차지하고 있지 않은 한 매번 예약량에 MEMORY_RETRY_GROWTH = 1.5가 곱해진다. 작업은 초기화되고 queued_gpu 이벤트에는 “out of memory; waiting for more room (try N)”이 표시된다(dispatch.py:1158-1228). 20회 윈도가 안전한 이유가 바로 이것이다. 윈도에서 밀려난 최고점은 재시도로 복구된다.
  • 중첩 호출은 승인을 건너뛴다. sup.run으로 호출한 도구는 예약을 보유한 부모의 하위 프로세스다. 따라서 바이트 예산은 각 단계의 채널들에 아래쪽으로 나뉜다(concurrency.child_budget, runner._child_channel_budget :1493).
  • 대기열은 프로세스별이다. 싱글턴은 budget()(admission.py:541-553)이 threading.Condition 뒤에서 만든다. uvicorn --workers N이면 예산이 N개 생긴다. 이미지는 워커를 하나만 시작한다(docker/Dockerfile:232).
  • 두 개의 한도가 겹친다. CapacityLimiter(스레드 4개)는 승인 대기를 세고, 예산은 바이트를 센다. 동시에 다섯 번째 실행은 queued_gpu로 보이게 되기 전에 기다린다.

도구는 supervisor를 통해 다른 도구를 실행한다. supervisor는 sup 객체로, run()이 주석 없이 sup라는 이름의 키워드 전용 매개변수를 선언할 때 받는다(_takes_supervisor, runner.py:1140, 클래스 _Supervisor, :1685). sup.run(tool, **params)는 형제 도구의 인터프리터로 같은 프로세스 그룹 안에서 runner.py에 다시 진입한다. HTTP 호출도, 새 승인도 없다. 형제 도구는 <job>/sup/NN_<tool>/에서 강제 지정된 자체 output_dir로 실행된다(runner.py:1808-1963). 호출자보다 위에서 이미 실행 중인 도구는 체인을 나열하며 이름으로 거부되고, 최후의 방어선은 MAX_SUPERVISOR_DEPTH = 10이다(runner.py:196). 제공되는 도구들이 실제로 선언한 가장 깊은 체인은 네 단계로, VFACE → AREG_CBCT → ASO → ALI_CBCT이다.

함정

supervisor에 관한 낡은 문서. supervisor의 멤버는 여덟 개다. run(runner.py:1808), out(:1785), tmp(:1789), datapath(:1804), channels(:2134), declareQualityControl(:2214), progress(:2235), log(:2242)이다. docs/INTERNALS.md:80은 “five members, frozen”이라고 하고, server/README.md:652는 “five members”라고 하며, server/README.md:660은 코드에서는 열인 최후의 방어선을 다섯 단계라고 부른다.

함정

MAX_CONCURRENT_GPU_JOBS는 더 이상 존재하지 않는다(config.py). 승인 모듈은 이것이 “counted jobs, and a count cannot describe a card”라고 밝히고(admission.py:3), server/README.md:693도 그렇게 말한다. 그런데도 MIGRATING_A_TOOL.md:104, RUN_PROGRESS.md:173, benchmarks/README.md:154, CLAUDE.md:467, 그리고 클라이언트의 ServerToolsCoreLib/config.py:36(AutomatedDentalToolsRemote)은 아직 이것을 동작하는 설정으로 설명한다. 공개된 벤치마크는 이 값을 1로 두고 측정되었다. 벤치마크 절을 보라.

6. 취소와 타임아웃

취소. DELETE /runs/{id}(main.py:1050)는 두 가지를 한다. 어느 한쪽만으로는 전체 구간을 덮지 못하기 때문이다. 스테이징 중과 승인을 기다리는 동안 확인되는 cancel 마커를 쓰고, 프로세스 그룹 id가 기록되어 있으면 그룹에 SIGTERM을 보낸다(dispatch.kill_process_group, :745, pgid가 1 이하이면 거부한다). 두 시간짜리 nnU-Net을 멈추는 것이 바로 이것이다. 프로세스 핸들을 가진 워커는 RUN_CANCEL_POLL_SECONDS = 1.0 s(config.py:278)마다 마커를 확인하고 TERM을 적용하며, 10 s 뒤에는 KILL을 적용한다(_KILL_GRACE_SECONDS, dispatch.py:63, _kill_group :713). 대기 중인 POST는 499로 응답한다. 중첩 호출은 부모의 프로세스 그룹을 공유하므로 TERM 한 번이 모든 단계에 닿는다. pgid가 디스크를 거치므로 다른 워커 프로세스에서도 취소가 동작한다.

타임아웃. 실행에는 기본적으로 타임아웃이 없다. TOOL_TIMEOUT_SECONDS = 0(config.py:77)이며 server/deployment.toml의 어느 절도 timeout_seconds를 지정하지 않는다. 도구별로 deployment.toml에서든 전역으로든 타임아웃이 지정되면 단조 시계의 절대 시각으로 변환되어 SADT_SUPERVISOR_DEADLINE으로 아래에 전달되고(dispatch.py:552-561), 중첩된 각 단계는 자식에게 남은 시간만 준다(runner._remaining_seconds, :1726). 만료되면 실행은 두 설정을 모두 명시하는 ToolExecutionError로 끝나고 응답은 500이다. 저장소는 오케스트레이션 도구에 자신이 호출하는 도구들의 타임아웃 합의 1.2배 이상을 주도록 권장한다(docs/INTERNALS.md:112, server/deployment.toml.example:86).

TOOL_TIMEOUT_SECONDS는 0이고 배포되는 deployment.toml은 timeout_seconds를 지정하지 않는다. 그룹 종료 기능은 있지만(dispatch.py:713) 누군가 타임아웃을 설정해야만 도달한다. 멈춘 실행은 취소될 때까지 예약을 계속 쥐고 있다. 설정 옆의 주석은 기본값의 이유를 밝힌다. “a cohort legitimately takes hours”(config.py:77).

7. 품질 관리: 정지, 검토, 재개, 되감기

서버 실행은 중간에 멈춰서 사람이 한 단계가 만든 결과를 보고 수정한 뒤 실행을 계속 진행시키게 할 수 있다. 이것은 레거시 모듈의 검토 일시 정지(AREG_CBCT에 하나 있다)에 대응하는 서버 쪽 기능이지만 메커니즘은 완전히 다르다. 도구는 자신이 일시 정지되었다는 것을 알지 못한다.

  1. 장전. 서버는 정지 지점이 있는 모든 도구에 다중 선택 인자 stop_after를 추가하며, 모두 선택 해제된 상태로 “Quality control” 절에 둔다(registry/schema_tool.py:340-500). 선택지는 도구가 하는 호출의 이름에 선언된 지점을 더한 것이고, ASO/ALI_CBCT 같은 중첩 체인에서는 한정된 이름이 쓰인다(_stop_points, registry/__init__.py:389). 각 지점의 종류(view, landmarks, …)는 피호출자의 review_kind에서 읽어 option_kind로 GET /tools에 공개되며(main.py:633), 없으면 view를 뜻한다.
  2. 정지. 장전된 이름은 JSON 변수 SADT_STOP_AFTER로 러너에 전달되고(runner.py:121), 각 자식은 자신과 관련된 항목만 받는다. 호출이 끝난 뒤 QualityControlStop(runner.py:167)이 발생해 main()의 최상단에서 잡힌다(:2486). stopped.json이 기록되고(누적: stopped_after와 passed_stops, _record_stop, :920), keep_intermediate 설정과 무관하게 체인이 만든 모든 것이 수집되며, result.json에는 {"quality_control": true, "stopped_after", "produced"}가 담긴다.
  3. 서버는 작업을 보관한다. 서버는 작업 디렉터리를 삭제하지 않고(dispatch._kept_if_paused, :1045), paused.json을 기록하고(runs.pause), 단계를 paused로 설정한 뒤 {quality_control, stopped_after, produced, result_ref}와 함께 200으로 응답한다. 출력은 참조로 전달되는 zip이다(_finish_stopped_run, main.py:2147-2197).
  4. 클라이언트에서의 검토. Remote 기반 위젯은 체크포인트의 압축을 풀고 콘텐츠 다이제스트를 계산한 다음 VISU 모듈을 열며(REVIEW_MODULE = "VISU", base_widget.py:2290, _reviewCheckpoint :2292), 이때 open_for_review(folder, on_continue, rewind, origin)(VISU/VISU.py:491)을 통한다. VISU는 서버에 대해 아무것도 모르며 폴더와 콜백만 받는다. landmarks와 registration 체크포인트만 편집할 수 있고(EDITABLE_KINDS, base_widget.py:2328), 검토 결과는 데이터 옆에 visu-review.json으로 저장된다(VISULib/review.py:20). VISU가 없거나 폴더가 비어 있으면 실행은 서버에서 일시 정지된 채 남지 않고 즉시 재개된다.
  5. 재개. “Continue”를 누르면 클라이언트는 콘텐츠 다이제스트가 바뀐 파일만, 단계마다 zip 하나씩 단계 이름을 붙여(01_ALI_CBCT, 최대 네 단계: 01_Mid/01_Leaf) POST /runs/{id}/resume(main.py:1750, 단계 이름은 _RESUME_SLOT과 대조해 검사하고 :1442, 확장자는 그 단계가 만든 것과 대조해 검사한다. _checked_correction :1463)으로 다시 보낸다. 일시 정지가 해제되고, 실행은 다른 실행처럼 승인 대기열을 거치며, 도구는 처음부터 다시 호출된다. 이미 수행한 모든 호출은 메모(memo.json, runner._memo :1965)에서 응답하며, 순서가 어긋날 때까지 계속된다.
  6. 되감기. POST /runs/{id}/rewind에 필드 to(공개된 단계 이름, ALI_CBCT 또는 ASO/ALI_CBCT)를 넣으면 이미 지나온 체크포인트로 돌아간다. 아무것도 시작하지 않으며 메모를 삭제하지 않는다. runner.rewind_to(runner.py:971)가 to와 그 이후의 모든 것을 passed_stops에서 제거하므로, 다음 재개 때 그 단계의 출력이 그대로인 채 그곳에서 다시 멈춘다. 그 단계가 케이스 보고서(run_report.json)를 작성했다면, 재실행은 하드 링크를 이용해 수정된 케이스로 한정된다(dispatch.narrow_to_cases, :959, 스키마의 case_input이 구동). 조금이라도 의심스러우면 전체를 다시 실행하며, 더 느리지만 틀리는 일은 없다.

제공되는 도구 중 어느 것도 sup.declareQualityControl로 자신만의 지점을 선언하지 않는다(SADT-VISOR tools/*/src에서 6ba2a78 기준으로 검색: 러너 밖에는 나타나지 않음). 기존의 모든 정지 지점은 호출 경계다. 호출되는 어떤 도구든 정지 지점이 될 수 있다. 일시 정지된 실행은 PAUSED_RUN_TTL_SECONDS = 4 h 동안 유지되며, 만료되면 reap_expired가 paused.json을 읽어 작업 디렉터리와 보관 중인 입력을 삭제한다(wire/runs.py:242-313).

함정

QUALITY_CONTROL.md는 세 가지 점에서 코드보다 뒤처져 있다. “rewind to an earlier stop for flagged patients”를 구축 예정으로 나열하지만(QUALITY_CONTROL.md:174), 이는 구현되어 있다(main.py:1685, runner.rewind_to). 정지의 종류가 “declared; not yet read by the server”라고 하지만(:173), 서버는 이를 읽어 option_kind로 공개한다. 그리고 도식에는 rewind to=01_ALI_CBCT patients=[...] 다음에 “drop the memo of 01_ALI_CBCT and after”가 나오지만(:130-131), 실제 경로는 to와 파일을 받고 메모를 삭제하지 않는다.

8. 오류와 상태 코드

도구가 발생시킨 예외는 타입이 아니라 클래스 이름으로 상태 코드에 매핑된다(TOOL_ERROR_STATUS, main.py:133-138). 예외는 다른 인터프리터에서 이름과 메시지로 돌아오기 때문이다.

상태발생 원인전송되는 메시지
400잘못된 형식의 실행 id, 스칼라 인자에 보낸 파일, 허용되지 않는 확장자, 비어 있거나 잘린 .gz, 읽을 수 없는 gzip 조각, 본문에 파일이 있는 분리 요청, 없거나 도달한 적 없는 to구체적인 문구
401Authorization: Bearer 헤더가 없거나 방식이 틀림 / 토큰이 틀림“Missing or malformed Authorization header.” / “Invalid token.”(wire/security.py:13-34)
404알 수 없는 도구, 실행, 업로드, 결과 또는 테스트 파일, 일시 정지되지 않은 실행에 대한 재개 또는 되감기구체적인 문구
409이미 사용 중인 실행 id
410작업이 사라진 실행의 재개
413입력이 MAX_UPLOAD_MB(500) 또는 도구의 max_upload_mb를 초과함
416/results에서 충족할 수 없는 범위Content-Range: bytes */size
422클래스 이름으로 ToolInputError, ValueError, FileNotFoundError, 알 수 없는 인자, 잘못된 모드, 스키마 검증(ToolArgumentError)도구의 메시지가 그대로 전달됨
499RunCancelled“Run cancelled by the client.”(main.py:1629-1635)
500그 밖의 모든 예외, 그리고 실행 타임아웃“Tool execution failed.” 트레이스백은 서버 로그에만 남는다(main.py:2093-2106)
501서버 쪽 ToolUnavailableError: 도구에 가상 환경이 없음main.py:2107-2113
503도구가 ToolUnavailableError를 발생시킴(예를 들어 설치되지 않은 선택적 extra 뒤에 있는 엔진). 유지보수 게이트도 해당도구의 메시지, 게이트에서는 Retry-After: 10

클라이언트는 이들을 다르게 처리한다. 499는 대화상자 없이 패널을 닫고, 401, 404, 422, 400, 413은 서버의 detail을 보여 주며, 500은 detail에 내부 정보가 들어 있을 수 있으므로 “The tool failed on the server.”로 바뀌고, 그 밖의 것은 Server error (N)을 보여 준다. 서버 메시지는 500자로 잘려 일반 텍스트로 표시된다(AutomatedDentalToolsRemote errors.py:9-92, client.py:1948-1970).
