VISOR의 CLIC: 코드

개발자용: CLIC의 VISOR 이식이 코드에서 하는 일을 file:line 참조, 코드, 인수, 환경, 레거시 코드와의 차이, 발견 사항과 함께 다룬다. 같은 파이프라인을 수식과 함께 읽기 쉽게 설명한 것은 아틀라스 페이지에 있다.

코드 아틀라스 (해설) VISOR 신경망 1개 레거시 페이지 가이드 (VISOR)

이 페이지의 참조는 저장소, 그 안의 경로, 줄 번호 순으로 적는다. SADT-VISOR는 도구 카탈로그(커밋 6ba2a78), VISOR-serve는 서버(e9a7e5d), Remote는 Slicer 클라이언트(AutomatedDentalToolsRemote 19b95e8), legacy는 3c67957 시점의 SlicerAutomatedDentalTools다. pipeline.py:36처럼 경로만 있는 참조는 SADT-VISOR의 tools/CLIC/src/sadt_clic/에 있다. 모든 것은 코드에서 읽은 것이며, 이 페이지의 어떤 것도 실행하지 않았다. 전체 스택의 개요: VISOR.

1. 체인에서의 위치

쉬운 설명과 수식: 아틀라스 페이지.

  • 상태: 이식됨, 코드로 구현되었고 도구의 테스트가 다룬다(SADT-VISOR tools/CLIC/tests/, 이 페이지를 위해 실행하지는 않음). 어떤 서버가 이를 실행하고 있다는 말은 여기 없다.
  • API 이름 CLIC, [tool.sadt] tool = true, name = "CLIC"로 선언된다(SADT-VISOR tools/CLIC/pyproject.toml:24-26). 서버는 이 표를 가진 모든 도구 폴더를 찾아내며, 하드코딩된 목록은 없다(아키텍처).
  • 클라이언트 패널 CLICRemote, 서버의 도구 설명에서 생성되는 얇은 패널이다(Remote CLICRemote/CLICRemote.py:44,53). 확장과 함께 빌드된다(Remote CMakeLists.txt:35).
  • 호출함 / 호출됨: 양쪽 모두 없다. run()에는 sup 인수가 없으므로 sup.run이 없고(SADT-VISOR __init__.py:76-88), CLIC을 이름으로 부르는 다른 도구도 없다. 그런데도 스키마에 "supervisor": true가 들어 있는 것은 data_root가 주입되는 인수이기 때문이다(SADT-VISOR scripts/describe.py를 tools/CLIC에 실행한 출력).
  • 호스팅된 데이터: DATA/CLIC/models/final_model.pth(176 MB)와 테스트 스캔 MG_test_scan.nii.gz가 데이터 매니페스트에 있다(VISOR-serve scripts/data-manifest.yml:630-641). 이 스캔은 매복 견치가 알려져 있지 않은 두부 전체 CBCT다(SADT-VISOR tools/CLIC/README.md:116-120). 이것은 왕복 과정을 증명할 뿐 분류를 증명하지는 않는다.

3. 파이프라인

쉬운 설명과 수식: 아틀라스 페이지.

3.1 스캔 찾기

쉬운 설명과 수식: 아틀라스 페이지.

scans는 파일 하나 또는 폴더 하나다. 폴더는 os.walk로 재귀적으로 훑고, 숨김 파일은 건너뛰며, 이름이 .nii 또는 .nii.gz로 끝나는 것(대소문자 구분 없음)만 파일 경로로 남기고 정렬한다(pipeline.py:58-79). 레거시 수집기는 nibabel이 읽지 못하는 .nrrd, .mha, .mhd도 광고했고, 파일 대신 하위 폴더를 돌려주었다(레거시 §3.1).

SCAN_EXTENSIONS = (".nii", ".nii.gz")                 # pipeline.py:36
found = discover_scans(str(scans))                    # __init__.py:115
if not found:
    raise ValueError("No .nii or .nii.gz scan found in '...'. "
                     "CLIC reads NIfTI volumes; NRRD and MetaImage are not supported.")

빈 결과는 ValueError이며(__init__.py:116-123), 서버는 이를 메시지를 담은 422로 바꾼다(VISOR-serve server/execution/runner.py:243-244). 입력의 전체 경로가 아니라 기본 이름만 인용된다.

3.2 체크포인트 고르기와 불러오기

쉬운 설명과 수식: 아틀라스 페이지.

model은 선택 사항이다. 비어 있으면 도구는 <data_root>/CLIC/models를 찾아(_own_models, __init__.py:30-37) 거기 있는 .pth 하나를 사용한다. 없거나 여러 개이면 후보를 이름으로 들어 거부한다(_sole_checkpoint, :40-61). 이름을 준 폴더에도 같은 규칙이 적용되고, 이름을 준 파일은 그대로 사용된다(_resolve_checkpoint, :64-73).

클래스 수는 가정하지 않는다. 배경을 포함하여 state dict의 분류 헤드 모양에서 읽으며, 가중치를 불러오기 전에 두 헤드를 모두 그 크기로 다시 만든다(pipeline.py:96-144):

state = torch.load(checkpoint_path, map_location=device, weights_only=True)
classes = class_count(state)       # roi_heads.box_predictor.cls_score.bias .shape[0]
model = maskrcnn_resnet50_fpn(weights=None)
model.roi_heads.box_predictor  = FastRCNNPredictor(box_features, classes)
model.roi_heads.mask_predictor = MaskRCNNPredictor(mask_features, 256, classes)
model.load_state_dict(state)
model.to(device).eval()

공개된 체크포인트는 클래스가 네 개(배경, buccal, bicortical, palatal)이며, catalogs.CLASSES = len(LABELS) + 1이 기대하는 값이다(catalogs.py:23-40). 헤드가 잘못되었거나 없으면 키 이름을 담은 ValueError가 난다(pipeline.py:109-123). resolve_device는 카드가 보이면 cuda를 유지하고, 그렇지 않으면 경고와 함께 cpu로 대체한다(pipeline.py:82-93).

3.3 슬라이스 루프

쉬운 설명과 수식: 아틀라스 페이지.

각 스캔은 nibabel로 float32로 읽힌다(__init__.py:216-219). 3D가 아닌 볼륨은 그 스캔만 실패한다. 레이블 볼륨은 같은 모양의 int16 배열이다. 루프는 파일에 저장된 대로 세 번째 배열 축을 따라 돌며, 방향 재조정은 없고, 레거시 러너가 한 것과 똑같다:

for index in range(volume.shape[2]):                          # pipeline.py:170
    image = normalise(volume[..., index])                     # min-max to [0, 1]
    tensor = torch.from_numpy(image).unsqueeze(0).repeat(3, 1, 1).float().to(device)
    with torch.no_grad():
        predicted = model([tensor])[0]                        # one slice per call
    keep = predicted["scores"] >= score_threshold             # default 0.7
    masks = (predicted["masks"][keep] > MASK_BINARY_THRESHOLD).squeeze(1)   # 0.5
    for mask, label in zip(masks.cpu().numpy(), predicted["labels"][keep].cpu().numpy()):
        labels[..., index][mask] = int(label)                 # last one wins
        detections += 1
  • 정규화: 슬라이스마다 (x - min) / (max - min)이며, 평탄한 슬라이스(범위 ≤ 1e-8)는 NaN이 아니라 0이 된다(pipeline.py:147-154). 레거시 _norm도 같다(레거시 CLIC/runner/clic_runner.py:44-46).
  • 크기 조정과 ImageNet 표준화는 레거시와 마찬가지로 torchvision의 GeneralizedRCNNTransform 안에서 일어난다(레거시 §4.1). 도구 자체는 아무것도 리샘플링하지 않는다.
  • 임계값: score_threshold는 인수다(기본값 DEFAULT_SCORE_THRESHOLD = 0.7, pipeline.py:41). 마스크 임계값은 상수로 남는다. MASK_BINARY_THRESHOLD = 0.5(:44).
  • 겹침: 마스크는 신경망이 돌려주는 순서대로 기록되므로, 둘이 겹치는 곳에서는 마지막 것이 덮어쓴다. 투표도 없고 슬라이스 사이의 3D 일관성도 없다(pipeline.py:180-182).

3.4 출력과 보고서

쉬운 설명과 수식: 아틀라스 페이지.

각 스캔은 입력 루트 기준 상대 경로를 키로 쓰며, 출력 트리는 입력 트리를 그대로 따른다. 접미사를 붙이기 전에 .nii.gz 또는 .nii 확장자가 제거된다(__init__.py:223-231):

input   scans/site_A/P01.nii.gz
output  output_dir/site_A/P01_seg.nii.gz          # affine and header copied from the input

파일 하나는 그 자신이 루트이므로, 결과는 output_dir에 바로 놓인다(__init__.py:163-165). 레이블 맵은 입력의 affine과 헤더를 유지하므로(nib.Nifti1Image(labels, image.affine, image.header), :231), 스캔과 분할 결과가 정렬된 채로 열린다. 헤더를 재사용한다는 것은 레거시와 마찬가지로 파일이 입력 스캔의 데이터 형식으로 기록된다는 뜻이기도 하다. labels는 메모리에서는 int16이지만(pipeline.py:167), float32 스캔은 디스크에 float32 레이블 맵을 만든다(nibabel 5.4.2, 같은 모양을 가진 레거시 호출로 확인했으며, 값은 여전히 0에서 3까지다). 그다음 CLIC_report.json이 결과 옆에 기록되며(:201), 형태는 다음과 같다(키는 __init__.py:133-155,188-189,233-249에서 가져옴):

{
  "tool": "CLIC", "model": "final_model.pth", "classes": 4,
  "labels": {"Buccal": 1, "Bicortical": 2, "Palatal": 3},
  "label_colors": {"Buccal": [0.0, 1.0, 0.0], "Bicortical": [1.0, 1.0, 0.0], "Palatal": [0.6, 0.4, 0.2]},
  "device": "cuda", "score_threshold": 0.7,
  "cases": {
    "site_A/P01.nii.gz": {"input": "site_A/P01.nii.gz", "status": "ok", "slices": 512,
                          "detections": 37, "labels_present": [3], "detected": ["Palatal"],
                          "produced": ["site_A/P01_seg.nii.gz"]},
    "site_B/P02.nii.gz": {"input": "site_B/P02.nii.gz", "status": "failed", "reason": "ValueError: ..."}
  },
  "summary": "1/2 scan(s) segmented", "duration_seconds": 41.3
}

예시의 값(슬라이스 수, 검출 수, 소요 시간)은 설명용이며, 키는 코드의 것이다. 체크포인트의 클래스 수가 다르면 labels와 label_colors는 null이 되고, labels_note가 이유를 알려 준다. 이름 없는 정수가 틀린 이름보다 낫기 때문이다(__init__.py:146-154, catalogs.py:43-58). 검출이 없는 스캔에는 "note": "no detection cleared the score threshold"가 붙는다(:245-249).

3.5 실패, 진행률, 로그

쉬운 설명과 수식: 아틀라스 페이지.

  • 스캔 하나가 실패하면 그 스캔만 잃는다. _segment_one 안의 모든 예외는 해당 스캔의 항목에 status: failed와 reason과 함께 기록되고 루프는 계속된다(__init__.py:173-186). 실행은 기록된 스캔이 하나도 없을 때만 오류를 내며, 모든 이유를 나열한다(:191-199). 이때 보고서는 기록되지 않는다.
  • 진행률: 스캔마다 앞서 progress.report(index, total, "scan")(__init__.py:170)가 SADT_PROGRESS_FILE이 가리키는 파일에 JSON 한 줄을 덧붙인다(progress.py:3,21,89-103). 메시지는 위치만 알려 주고 파일 이름은 알려 주지 않는다. 파일 이름은 환자 메타데이터이기 때문이다(progress.py:13-15).
  • 로그: 실패 로그 줄도 파일이 아니라 위치를 이름으로 든다(__init__.py:183). 실패한 실행의 stderr는 서버의 로그에 남기 때문이다.

쉬운 설명과 수식: 아틀라스 페이지.

8. VISOR의 발견 사항

쉬운 설명과 수식: 아틀라스 페이지.

백본 다운로드에 여전히 닿을 수 있다

도구는 레거시와 마찬가지로 maskrcnn_resnet50_fpn(weights=None)으로 신경망을 만든다(SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:136). 고정된 torchvision 0.26.0(pyproject.toml:14)에서는 weights_backbone의 기본값이 ResNet50_Weights.IMAGENET1K_V1이며(torchvision/models/detection/mask_rcnn.py:416) resnet50(weights=weights_backbone)이 호출되고(:490,502), 이것이 load_state_dict_from_url을 통해 파일을 가져온다(torchvision/models/_api.py:91). 체크포인트는 그 위에 나중에 불러온다(pipeline.py:142). 네트워크 호출을 금지하는 테스트는 도구 자체의 소스에서 문자열만 검색하므로(tests/test_device_and_contract.py:163-175) 이 호출을 볼 수 없다. torchvision의 줄은 설치된 torchvision 0.26.0 사본에서 읽었으며, 아무것도 실행하지 않았고, 특정 서버가 torch 캐시에 ResNet-50 파일을 이미 갖고 있는지는 확인하지 않았다.

검출이 없는 스캔은 성공이다

아무것도 임계값을 넘지 못한 볼륨은 "note": "no detection cleared the score threshold"와 함께 전부 0인 레이블 맵으로 기록된다(__init__.py:245-249). "아무것도 기록되지 않음" 보호 장치는 검출이 아니라 기록된 스캔을 세므로(:191-199), 모든 스캔이 비어 있는 배치도 성공한 실행이다. 소스 주석은 잘못된 체크포인트도 이렇게 보인다고 말한다(:246-248).

클라이언트는 보고서를 보여 주지도 병합하지도 않는다

CLIC_report.json에는 레이블 표, 검출된 것, 실패한 스캔이 담기지만(__init__.py:133-155,173-186), 패널에는 RUN_REPORT가 없다(Remote CLICRemote/CLICRemote.py:53-72. 기본값은 빈 값, ServerToolsCore/ServerToolsCoreLib/base_widget.py:1493). CNE와 DOCShapeAXI와는 다르다. 실패한 스캔은 JSON을 열어 봐야만 보인다. 배치 하나보다 큰 폴더(기본값 25개 항목 또는 400 MB, VISOR-serve server/config.py:192,196)는 여러 번의 실행으로 전송되고, 그 폴더들은 마지막에 출력 폴더로 합쳐진다. 병합된 보고서는 RUN_REPORT를 선언한 패널에 대해서만 기록되며(base_widget.py:2192), 두 배치가 같은 파일 이름을 만들면 첫 번째가 유지된다(:2205-2224). 따라서 CLIC의 최종 CLIC_report.json은 단일 배치의 것이다. 코드에서 읽었으며, 실행하지는 않았다.

서버 주석이 다른 CLIC을 설명한다

VISOR-serve의 주석은 "순전파 한 번 안에서 슬라이스를 배치로 묶는" CLIC(server/execution/admission.py:146)을 설명하며, 여기에는 batch_size = 4 인수가 있고(server/execution/runner.py:1251,1271-1272), 폭 1에서 45까지의 CLIC 메모리 측정값을 인용한다(server/execution/costs.py:470-477). 패키지된 도구에는 batch_size 인수가 없고, model([tensor]) 호출마다 슬라이스 하나를 실행하며(pipeline.py:170-176), 정의만 되어 있는 progress.set_width를 호출하지 않는다(progress.py:41). 따라서 그 주석과 수치는 이 도구의 다른 버전을 설명한 것이다. "패스당 슬라이스 네 개"를 이 코드의 속성으로 읽어서는 안 된다.

겹침은 여전히 순서와 슬라이스별로 해소된다

슬라이스 위에서 남겨진 두 마스크가 겹치는 곳에서는 신경망이 나중에 돌려준 것이 다른 것을 덮어쓰고, 각 슬라이스는 홀로 결정된다. 클래스 간 투표도 3D 일관성도 없으므로, 견치 하나가 이웃한 슬라이스에서 두 레이블을 가질 수 있다(pipeline.py:170-182, 레거시 clic_runner.py:84-87과 같음). 코드에서 읽음.

확인됨: 레거시의 다른 결함은 사라졌다

체크포인트 선택은 모호함을 거부하고, 클래스 수는 읽어서 정하며, 불러오기는 weights_only=True이고, 출력은 올바르게 이름이 붙고 상대 경로를 키로 쓰므로 이름이 같은 두 스캔이 더 이상 서로를 덮어쓰지 않는다(SADT-VISOR __init__.py:40-73,223-231, pipeline.py:96-144). 레이블 표는 위젯에만 있지 않고 보고서에 있다.
