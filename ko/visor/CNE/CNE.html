VISOR의 CNE

CNE은 자유 형식의 임상 노트를 읽고 그 안에서 찾은 사실(증상, 진단, 점수)을 필드 : 값 줄의 목록으로 적는다. 읽는 일은 언어 모델이 하며, 그 주변의 모든 것은 모델에 무엇을 보여 줄지와 모델의 답 중 어느 것을 남길지를 정한다. VISOR에서는 모델이 서버에서 실행되므로 노트가 업로드되는데, 레거시 모듈은 이런 일을 한 적이 없다. 이 페이지는 단계와 그 안의 몇 가지 계산을 설명한다. 개발자에게 필요한 세부 사항은 코드 페이지에 있고, 레거시 모듈에는 자체 페이지가 있다.

VISOR 언어 모델 1개 코드 (개발자용) 레거시 페이지 가이드 (VISOR)

개요: 무엇이 들어가고 무엇이 나오는가

CNE
입력노트 하나, 또는 노트(.txt, .pdf, .docx)가 든 폴더, 하위 폴더 포함
선택하는 것노트 유형(TMJ 또는 Ortho), 모델 파일, 답변을 얼마나 길게 할 수 있는지
모델서버의 프로세서에서 실행되는 양자화된 언어 모델. 호스팅된 것은 TMJ 노트로 파인튜닝된 Qwen 2.5 7B다
출력노트마다 JSON 파일 하나와 필드 : 값 줄의 텍스트 파일 하나, 그리고 실행 보고서 하나

어떤 필드가 존재하고 그 값이 무엇인지는 모델 혼자 정한다. 추출 결과를 그 출처인 노트와 대조하여 검사하는 것은 없다. 도구는 모델에 무엇을 보여 주는지와 어떤 답을 기록하는지만 통제한다.

1. 실행되는 곳

Slicer에는 작은 패널(CNERemote)만 남는다. 패널은 노트를 서버에 업로드하고, 기다린 뒤, 아카이브 하나를 내려받아 선택한 폴더에 푼다. 모델은 서버의 자체 환경에서 불러와 실행되며, Slicer 장면에는 아무것도 불러오지 않는다. 결과는 텍스트다. CNE은 다른 도구를 호출하지 않으며, 어떤 도구도 CNE을 호출하지 않는다.

모델이 서버에서 실행되므로 노트의 텍스트가 워크스테이션을 떠난다. 레거시 모듈은 이를 기계 안에 두었다. 노트가 전송되기 전에 비식별화하는 것은 아무것도 없다(알려진 문제).

1.1 무엇이 어디서 실행되는가

  • 서버: 패널이 보여 주는 양식을 발행하고, 세 가지 노트 형식을 읽고, 모델을 실행하고, 결과를 기록한다. 모델은 호출마다 한 번 불러오며, 그래서 노트 폴더 전체가 호출 한 번으로 전송된다.
  • Slicer: 생성된 양식을 보여 주고, 노트를 업로드하고, 아카이브를 풀고, 상태 표시줄에 한 줄 요약(노트 몇 개가 어떤 모델 유형으로 추출되었는지, 경고가 몇 개인지)을 표시한다. 워크스테이션에는 아무것도 설치되거나 내려받지 않는다.
코드에서패널, 서버 도구, 호스팅된 것, 파일과 줄 번호 포함

2. 관련 파일

이 도구는 작은 소스 파일 다섯 개로 이루어진다. 노트에 대한 루프를 실행하는 진입점, 모델 코드(프롬프트, 불러오기, 파싱), 세 가지 형식의 리더, 선택적 패키지를 위한 로더, 패널의 레이아웃이다. 레거시 모듈에서는 추론만 이식되었고, 패널, 모델 다운로드, Dashboard는 이식되지 않았다.

코드에서줄 수가 있는 파일 목록, 그리고 CNE과 관련된 서버와 클라이언트의 파일

3. 파이프라인

도구는 실행당 한 번 폴더를 확인하고, 노트를 나열하고, 모델 파일을 고르고, 불러온다. 그다음 노트마다 텍스트를 읽고, 모델에 묻고, 답변을 남길 수 있는지 판단한다. 각 상자는 해당 단계로 가는 링크다.

3.1 폴더 확인과 노트 찾기

도구는 먼저 노트가 있는지, 그리고 결과가 노트 폴더에 기록되지 않는지 확인한다. 그렇지 않으면 다음 실행이 자기 결과를 노트로 읽게 되기 때문이다. 그다음 폴더와 그 하위 폴더의 .txt, .pdf, .docx 파일을 확장자의 대소문자와 상관없이 나열하며, Word 잠금 파일과 숨김 파일은 건너뛴다. 하나도 찾지 못하면 세 확장자를 이름으로 든 오류와 함께 실행이 멈춘다. 레거시 모듈은 그냥 조용히 끝났다.

코드에서폴더 확인, 재귀적 탐색, 건너뛰는 이름, 오류 코드

3.2 모델 고르기와 불러오기

모델은 GGUF 형식의 양자화된 파일 하나이며 llama.cpp가 실행한다. 파일은 그대로 사용하고, 폴더에는 정확히 하나가 들어 있어야 한다. 노트 유형마다 자기 컨텍스트 윈도가 있는데, 모델이 한꺼번에 담을 수 있는 텍스트의 양(노트와 답변을 합쳐 토큰으로 센 것)이다. TMJ는 6144, Ortho는 2048이다. 모델의 경로가 다른 유형의 노트를 가리키면 경고가 보고서에 들어가지만 실행은 계속된다. 4.4 GB를 불러오는 것이 느린 부분이므로 모델은 배치 전체에 대해 한 번만 불러온다. 프로세서 전용 빌드에 GPU를 요청하면 실행은 GPU 없이 계속되고 보고서에 그 사실이 적힌다.

코드에서모델 결정, 윈도 표, 불러오기, CPU 빌드

3.3 노트 읽기

텍스트 파일은 UTF-8로, 그다음 Windows-1252로, 그다음 Latin-1로 디코딩되며 먼저 통하는 것이 쓰인다. PDF는 텍스트 레이어를 페이지별로 준다. Word 파일은 머리글과 바닥글을 주고, 그다음 본문을 표와 함께 읽는 순서로 주며, 표의 한 행이 한 줄이다. 그다음 모든 노트가 같은 정리 단계를 거친다.

글자도 숫자도 없는 텍스트, 즉 스캔된 PDF가 주는 텍스트는 이름과 함께 거부된다. OCR은 없다.

코드에서세 가지 리더, 치환 표, 빈 텍스트 검사

3.4 모델에 묻기

노트는 채팅으로 전송된다. TMJ 노트에는 시스템 프롬프트가 먼저 온다. “Using the following note, extract structured key-value pairs about the patient’s symptoms and diagnoses”. Ortho 노트에는 없는데, 그 모델은 노트만으로 답하도록 파인튜닝되었기 때문이다. 답변은 기본적으로 2048토큰으로 제한되고, 샘플링 temperature는 0이며 고정된 시드를 쓰므로 같은 노트는 같은 답변을 내야 한다. 모델이 한도에 도달해서 멈추면 답변은 불완전하며 노트는 실패한다.

Ortho 기본값에서는 답변 한도가 윈도 전체와 같으므로(2048과 2048), 답변은 노트가 남긴 만큼으로 제한된다. 1,000토큰짜리 노트는 답변에 1,048토큰을 남긴다. 도구는 노트를 윈도와 결코 비교하지 않는다. 답변이 그 나머지에 도달하면 모델이 잘림을 보고하고 노트가 실패한다. 프롬프트만으로 윈도가 차면 엔진이 이를 거부하며, 이때도 그 노트만 실패한다.

코드에서메시지, 호출, 잘림 확인, 없는 길이 보호 장치

3.5 답변 읽기와 기록하기

모델은 JSON으로 답하리라고 기대되지만 그렇게 강제하는 것은 아무것도 없다. 도구는 두 가지 읽기를 이 순서로 시도하며, 둘 다 실패하면 아무것도 기록하지 않는다.

두 번 나타나는 필드는 첫 번째 값을 유지한다. 노트마다 노트를 그대로 따르는 폴더 트리에 파일 두 개가 기록된다. 정본인 JSON 파일과, 읽기용으로 목록을 쉼표로 이어 붙인 필드 : 값 줄의 텍스트 파일이다. B_001.txt의 경우 Extraction_B_001.txt.json과 Extraction_B_001.txt.txt가 된다. 실행 보고서는 노트마다 어떻게 읽혔는지, 노트와 답변이 얼마나 길었는지, 성공했는지, 필드를 몇 개 냈는지, 실패했다면 왜 실패했는지를 나열한다. 답변 텍스트 자체는 보고서나 로그에 넣지 않는다.

코드에서파싱 코드, 출력 계획기, 보고서 필드

3.6 실패

각 노트는 따로 처리된다. 실패(빈 텍스트, 잘린 답변, JSON도 필드도 아닌 답변, 모델 엔진의 오류)는 노트의 경로와 함께 로그에 남고, 이유와 함께 기록되며, 루프는 계속된다. 기록된 노트가 하나도 없을 때만 실행 전체가 실패하며, 이때는 노트마다의 이유를 나열한 오류로 끝나고 보고서는 기록되지 않는다.

코드에서어떤 오류가 어떤 상태 코드가 되는가

4. 선택할 수 있는 것

  • 노트: 노트 하나 또는 노트 폴더. 필수.
  • 노트 유형: TMJ 또는 Ortho. 시스템 프롬프트와 컨텍스트 윈도를 함께 고른다.
  • 모델: 모델 파일, 또는 정확히 하나를 담은 폴더. 목록에는 호스팅된 모델이 나오며, “automatic” 선택은 없으므로 모델은 노트 유형에서 유도되지 않는다.
  • 답변 한도: 노트당 가장 긴 답변, 기본값 2048토큰.
  • Temperature: 기본값 0, 무작위성이 없다는 뜻이다.
  • 컨텍스트 윈도: 0은 노트 유형의 기본값을 뜻한다.
  • 숨은 설정: 무작위 시드와 장치(기본값은 프로세서). 서버가 자체 장치를 채운다.
  • 출력 폴더: 서버가 채우며, 노트 폴더이면 거부된다.

시간 제한은 없으며, 호출은 서버의 500 MB 업로드 상한으로 제한된다.

코드에서형식, 기본값, 이를 강제하는 줄이 있는 인수 표

코드에서코드 안의 위치가 있는 같은 표

6. 환경

모든 것은 서버에 있는 도구 자체의 환경에서 실행된다. Python 3.11, llama-cpp-python의 프로세서 빌드, PDF용과 Word용 리더 하나씩이다. Slicer에는 아무것도 설치되지 않는다. 레거시 모듈은 패키지를 Slicer 자체의 Python에 설치하고 4.4 또는 4.9 GB 모델을 사용자의 Documents 폴더에 내려받았다.

코드에서고정된 버전, 휠 인덱스, 호스팅된 데이터, 리소스

7. 레거시 로직에서 달라진 점

TMJ 프롬프트, Ortho에는 프롬프트가 없다는 점, 두 기본 윈도는 바뀌지 않았다. 그 주변은 다음과 같다:

  • 위치: 워크스테이션의 Slicer 안이 아니라 서버에서.
  • 노트 찾기: 재귀적이며 대소문자를 구분하지 않는다. 아무것도 찾지 못하면 조용한 성공이 아니라 오류다.
  • 읽기: 텍스트 인코딩이 하나가 아니라 세 가지다. Word의 표, 머리글, 바닥글을 읽는다. 스캔된 PDF는 빈 텍스트를 모델에 보내는 대신 거부된다. 리더 패키지가 없으면 그 형식의 노트만 실패한다.
  • 생성: 답변 한도가 500이 아니라 2048이고, temperature가 0.1이 아니라 0이며, 시드가 있고, 잘린 답변은 기록되는 대신 노트를 실패시킨다.
  • 답변 읽기: JSON, 그다음 필드 줄, 아니면 아무것도 기록하지 않는다. 레거시 모듈은 원본 답변을 저장했다.
  • 출력: 노트마다 JSON 파일 하나와 텍스트 파일 하나, 그리고 실행 보고서. 같은 이름의 .txt, .pdf, .docx가 더 이상 서로를 덮어쓰지 않도록 전체 노트 이름을 쓴다.
  • GPU: 요청할 때만 요청되며, 레이어가 실제로 오프로드되었는지 보고서에 적힌다.
  • 이식되지 않음: Dashboard, 그리고 클라이언트의 모델 다운로드.
코드에서레거시와 VISOR를 항목별로 비교한 표, 양쪽의 줄 번호 포함

8. 알려진 문제

  • 노트는 비식별화 없이 그대로 서버에 업로드되므로, 임상 텍스트가 기계 안에 머문다는 레거시의 설명은 VISOR에서는 성립하지 않는다(자세히).
  • 패널과 README는 “automatic” 모델을 말하지만, 노트 유형에서 모델을 유도하는 것은 아무것도 없다(자세히).
  • TMJ 모델만 호스팅되며, 유형이 틀린 모델은 경고일 뿐이다(자세히).
  • 일부 주석이 뭐라고 하든 엔진은 프로세서 빌드이며, GPU 요청은 무시되었다고 보고된다(자세히).
  • 노트를 컨텍스트 윈도와 비교하는 것은 아무것도 없으며, Ortho 기본값에서는 답변이 노트가 남긴 만큼만 얻는다(자세히).
  • 출력 파일은 레거시와 이름이 다르게 붙으므로, 옛 이름을 읽는 도구는 그것을 찾지 못한다(자세히).
  • 수정됨: 스캔된 PDF, 잘린 답변, 읽을 수 없는 답변, 같은 이름의 노트, 조용한 GPU 요청이 더 이상 그럴듯한 파일을 만들지 않는다(자세히).
코드에서근거가 있는 일곱 가지 발견 사항

9. 문헌

파인튜닝된 모델과 그 논문은 도구의 것이다. CNE 출처 페이지를 보라. VISOR는 새 모델을 더하지 않는다.
