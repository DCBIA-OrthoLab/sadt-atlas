VISOR의 CNE: 코드

개발자용: CNE의 VISOR 이식이 코드에서 하는 일을 file:line 참조, 시그니처, 인수, 환경, 레거시 코드와의 차이, 발견 사항과 함께 다룬다. 같은 파이프라인에 들어 있는 작은 계산들을 포함한 읽기 쉬운 설명은 아틀라스 페이지에 있다.

VISOR 코드 아틀라스 (해설) 레거시 페이지 가이드 (VISOR)

이 페이지의 참조는 저장소, 그 안의 경로, 줄 번호 순으로 적는다. SADT-VISOR는 도구 카탈로그(커밋 6ba2a78), VISOR-serve는 서버(e9a7e5d), Remote는 Slicer 클라이언트(AutomatedDentalToolsRemote 19b95e8), legacy는 3c67957 시점의 SlicerAutomatedDentalTools다. readers.py:41처럼 경로만 있는 참조는 SADT-VISOR의 tools/CNE/src/sadt_cne/에 있다. 모든 것은 코드에서 읽은 것이며, 아래에 날짜가 적힌 HTTP 상태 확인을 제외하면 이 페이지의 어떤 것도 실행하지 않았다. 전체 스택의 개요: VISOR.

1. 체인에서의 위치

쉬운 설명과 수식: 아틀라스 페이지.

  • 상태: 이식됨, 코드로 구현되었고 도구에 테스트가 있다(SADT-VISOR tools/CNE/tests/test_run.py, 테스트 함수 130개, 이 페이지를 위해 실행하지는 않음). Dashboard는 이식되지 않았다. 서버의 데이터 매니페스트에는 TMJ 모델만 준비되어 있다.
  • API 이름 CNE(SADT-VISOR tools/CNE/pyproject.toml:35-37), 코드는 __init__.py, extraction.py, readers.py, dependencies.py, layout.py에 있다.
  • 클라이언트 패널 CNERemote, 얇은 패널이다(Remote CNERemote/CNERemote.py:57,61-62. 빌드됨, CMakeLists.txt:36). 실행 후 CNE_report.json을 읽어 상태 표시줄에 한 줄 요약을 보여 준다(:75-103).
  • 호출함 / 호출됨: 없음. sup 인수가 없고 sup.run도 없으며(__init__.py:46-56), CNE을 이름으로 부르는 다른 도구도 없다.
  • 호스팅된 데이터: 번들 하나, DATA/CNE/models/TMJ/qwen-ft-q4_k_m.gguf(4,683,073,408바이트)와 합성 TMJ 테스트 노트 하나(VISOR-serve scripts/data-manifest.yml:687-701).

3. 파이프라인

쉬운 설명과 수식: 아틀라스 페이지.

3.1 폴더 확인과 노트 찾기

쉬운 설명과 수식: 아틀라스 페이지.

없는 notes 경로는 FileNotFoundError다(__init__.py:97-100). notes가 폴더이고 output_dir이 같은 폴더이면(심볼릭 링크를 해소한 뒤), 다음 실행이 추출 결과를 노트로 다시 읽게 되므로 실행이 거부된다(:106-110,320-324). 그다음 도구가 output_dir을 직접 만든다(:116). 레거시는 패널이 만들어 주기를 기대했다.

탐색은 재귀적이며 상대 경로순으로 정렬된 파일을 돌려준다(readers.py:92-123). .txt, .pdf, .docx를 대소문자 구분 없이 남기고(:33,78-81), ~$(Word 잠금 파일)나 점으로 시작하는 이름, 그리고 __MACOSX 폴더는 건너뛴다(:60-61,84-90,117-118). 출력 폴더가 입력 안에 있으면 제외된다(__init__.py:118). 아무것도 찾지 못하면 세 확장자를 이름으로 든 422가 된다(:119-126). 레거시는 그 경우 상태 0으로 종료했다(레거시 CNE_CLI/CNE_CLI.py:137-141).

3.2 모델 고르기와 불러오기

쉬운 설명과 수식: 아틀라스 페이지.

model은 필수다. .gguf 파일은 그대로 사용하며, 폴더에는 재귀적으로 찾아서 정확히 .gguf 하나가 있어야 하고, 아니면 후보를 이름으로 든 채 실행이 거부된다(extraction.py:89-128). 모델 경로가 한 노트 유형을 가리키는데 notes_type이 다른 유형이면 경고가 보고서에 들어가며, 거부는 아니다(model_type_hint, extraction.py:131-143. __init__.py:132-142).

CONTEXT_TOKENS = {"TMJ": 6144, "Ortho": 2048}                # extraction.py:49
SYSTEM_PROMPTS = {"TMJ": INSTRUCTION_TMJ, "Ortho": None}      # extraction.py:51

window = context_for(notes_type, context_tokens)              # 0 means the type's default
offloading = wants_gpu and supports_gpu_offload()             # asked before the 4.4 GB load
engine = load_model(model_file, window, seed, -1 if wants_gpu else 0)   # __init__.py:144-165

load_model은 배치 전체를 위해 llama_cpp.Llama(model_path, n_ctx, n_gpu_layers, seed, verbose=False) 하나를 만든다(extraction.py:193-203). 로더의 잡음 출력은 contextlib.redirect_stderr로 가로채 debug 수준으로 기록되며(:63-86), 레거시는 프로세스의 파일 디스크립터 2를 os.dup2로 리디렉션하고 finally가 없었다(레거시 CNE_CLI.py:157-171). llama_cpp의 모든 import는 engine_module()을 거치며, 이것이 먼저 venv의 CUDA 런타임을 열어 보려고 시도한다(extraction.py:167-177, dependencies.py:65). CPU 빌드에서는 아무 일도 하지 않는다. GPU를 지원하지 않는 빌드에 device = "cuda"를 요청하면 경고가 추가되고 보고서에 gpu_offload: false가 들어간다(__init__.py:145-165,184).

3.4 모델에 묻기

쉬운 설명과 수식: 아틀라스 페이지.

messages = []
if SYSTEM_PROMPTS[notes_type]:                       # TMJ only
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": text})   # extraction.py:156-164

output = model.create_chat_completion(messages=messages,
                                      max_tokens=max_tokens, temperature=temperature)
content, finish_reason = choice["message"]["content"], choice.get("finish_reason")   # :206-223
if finish_reason == "length":   # cut off at max_tokens
    raise ValueError("the model's answer was cut off ...")                          # __init__.py:293-297

TMJ 지시문은 레거시 문자열 그대로다. "Using the following note, extract structured key-value pairs about the patient's symptoms and diagnoses:"(extraction.py:41-44). Ortho에는 레거시와 마찬가지로 시스템 메시지가 없다. 도구는 노트의 길이를 윈도와 비교하지 않는다. context_for는 음수 값만 거부하며(extraction.py:146-153), llama.cpp가 일으키는 오류는 모두 그 노트에 대해 잡힌다(__init__.py:200-212). llama-cpp-python 0.3.36(llama.py:1343-1358)에서 엔진은 프롬프트만으로 n_ctx에 도달할 때에만 오류를 내며, 그렇지 않으면 max_tokens가 n_ctx에서 프롬프트 길이를 뺀 값으로 줄어들고, 노트는 결코 잘리지 않으며, 그렇게 줄어든 한도에서 멈춘 생성은 finish_reason == "length"를 보고하여 노트가 실패한다(__init__.py:293-297). 고정된 버전은 0.3.35이며, 그 코드는 읽지 않았다.

3.5 답변 읽기와 기록하기

쉬운 설명과 수식: 아틀라스 페이지.

  1. JSON 먼저: 첫 번째 {부터 마지막 }까지의 조각을 파싱한다. "extraction" 아래의 dict는 풀어 낸다. 빈 결과나 객체가 아닌 JSON 값은 거부된다(extraction.py:261-275). 자르는 방식은 레거시의 것이다.
  2. 그다음 key: value 줄: 키는 소문자로 시작하며 소문자, 숫자, 공백, 밑줄을 담는다(최대 61자, 공백은 _가 됨, extraction.py:230,296). 비어 있지 않은 줄의 60 % 이상이 일치해야 하고, 반복된 키는 첫 번째 값을 유지한다(extraction.py:230-235,278-301). 소스는 공개된 TMJ 파인튜닝 모델이 이 형태로, 필드 46개로, JSON 없이 답한다고 말한다(:244-245).
  3. 그 밖의 경우에는 아무것도 기록되지 않고 노트가 실패한다(__init__.py:299-305). 레거시는 원본 답변을 기록했다.

노트마다 미러링된 트리 아래에 파일 두 개가 기록된다(__init__.py:240-266,307-317). 정본인 JSON과, 목록은 쉼표로 이어 붙이고 중첩된 dict는 JSON 그대로 두는 key : value 텍스트다(extraction.py:304-328).

input   notes/P01/B_001.txt
output  output_dir/P01/Extraction_B_001.txt.json
        output_dir/P01/Extraction_B_001.txt.txt

plan_outputs는 아무것도 실행하기 전에 두 노트가 같은 쌍에 대응하지 않는지 확인한다(__init__.py:240-266). CNE_report.json에는 tool, notes_type, model, system_prompt(플래그), context_tokens, max_tokens, temperature, seed, device, gpu_offload, warnings가 들어 있고, 노트마다 input, 리더와 인코딩, characters, finish_reason, answer_characters, status, fields, 두 출력 경로 또는 reason이 들어 있으며, 그다음 summary와 duration_seconds가 있다(__init__.py:171-187,213-216,272-317). 답변 텍스트 자체는 보고서나 로그에 넣지 않는다.

3.6 실패

쉬운 설명과 수식: 아틀라스 페이지.

각 노트는 자기 try 안에 있다. 실패는 노트의 상대 경로와 함께 로그에 남고 보고서에 기록되며 루프는 계속된다(__init__.py:191-213). 기록된 노트가 하나도 없으면 실행이 오류를 낸다. 모든 실패가 리더 누락이었으면 503(ToolUnavailableError), 그렇지 않으면 노트마다의 이유를 나열한 422(ValueError)이며(:218-232), 이때 보고서는 기록되지 않는다. 노트별 로그 줄은 CLIC의 진행 메시지와 달리 파일 이름을 적는다는 점에 유의하라.

8. VISOR의 발견 사항

쉬운 설명과 수식: 아틀라스 페이지.

노트의 텍스트가 서버로 전송된다

CNE이 임상 텍스트를 기계 안에 둔다는 레거시의 설명("no network exfiltration", 레거시 페이지 §11, 그리고 레거시 가이드의 "Nothing leaves your machine")은 VISOR에서는 성립하지 않는다. VISOR 패널은 선택한 노트를 모델이 실행되는 도구 서버로 업로드한다(Remote README.md:24-35. CNERemote/CNERemote.py:57과 서버 쪽 notes 인수, 인수와 스키마). Remote README는 현재 클라이언트에 비식별화가 없다고 분명히 말하며(README.md:32), VISOR 보안 페이지는 업로드된 파일의 비식별화를 명세만 된 것으로 나열한다(비식별화, 전송). 도구 자체가 텍스트로 하는 일은 이렇다. llama.cpp를 프로세스 안에서 실행하며 네트워크 호출이 없고(grep으로 urllib, requests, http, socket을 tools/CNE/src/sadt_cne/에서 찾으면 하나도 나오지 않는다), 서버는 답변을 작업 폴더에 기록한다. 레거시의 발견 사항은 레거시 모듈에 대해서만 여전히 참이다.

클라이언트는 "automatic"이라고 하지만, 노트 유형에 맞는 모델을 고르는 것은 아무것도 없다

Remote README("Model을 automatic으로 두면 서버가 그 노트 유형에 맞게 파인튜닝된 모델을 사용한다", README.md:611-613)와 CNERemote/CNERemote.py:15-18의 docstring("model 필드의 기본값은 (automatic)")은 낡았다. model은 도구의 필수 인수이며(__init__.py:49), 클라이언트는 "(automatic)" 항목을 선택 인수에만 추가한다(Remote ServerToolsCore/ServerToolsCoreLib/base_widget.py:1074-1076, 이유는 formgen.py:107-109). Model 필드는 호스팅된 번들을 나열하고 선택된 것을 보낸다. notes_type에서 모델을 유도하는 것은 없으며(resolve_model_file은 경로를 받는다, extraction.py:89-128), 둘이 맞지 않는 것은 경고일 뿐이다(다음 콜아웃). 코드에서 읽었으며, Slicer에서 실행하지는 않았다.

TMJ 모델만 호스팅된다

데이터 매니페스트는 번들 하나, TMJ/qwen-ft-q4_k_m.gguf를 준비한다(VISOR-serve scripts/data-manifest.yml:687-692). notes_type = "Ortho"는 도구가 받아들이지만 호스팅된 Ortho 모델은 없고, 경로가 다른 유형을 가리키는 모델은 거부가 아니라 보고서의 경고일 뿐이다(__init__.py:133-139, extraction.py:131-144). Ortho 저장소가 "answers 404 today"라는 매니페스트의 주석(data-manifest.yml:682-686, SADT-VISOR tools/CNE/README.md:205-208에서도 반복됨)은 낡았다. 2026-11-09에 옛 dcbia/ Ortho URL에 대한 HTTP HEAD 요청은 307(DCBIA-OrthoLab/ 조직으로의 리디렉션)로 응답했고, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho/.../model-q4_k_m.gguf에 대한 요청은 다운로드로 이어지는 302로 응답했다(상태 코드만, 내려받은 것은 없음). 매니페스트의 TMJ URL도 여전히 옛 dcbia/ 이름을 쓰며 307로 응답한다.

일부 주석이 뭐라고 하든 CPU다

llama-cpp-python의 고정된 휠 인덱스는 CPU용이다(SADT-VISOR tools/CNE/pyproject.toml:60-67). 세 주석이 이와 어긋난다. 같은 파일의 머리말은 "CUDA 12.4 wheel index below"라고 말하고(:8-23), device의 발행된 설명은 "it needs the CUDA build of llama.cpp, which this tool pins"라고 말하며(__init__.py:82-84), VISOR-serve의 compose 파일은 CNE이 CUDA 빌드를 싣고 있어서 CPU 서비스에서 실행될 수 없다고 말한다(docker-compose.yml:105-110). 코드는 CPU 빌드이므로 cuda 요청은 무시되었다고 보고된다. 도구의 README는 코드와 일치한다(SADT-VISOR tools/CNE/README.md:154-165). 어디에서도 "CNE에는 GPU가 필요하다"로 읽어서는 안 된다.

노트의 길이에 대한 보호 장치가 없다

긴 노트에 대한 레거시의 우려(레거시 페이지, §11)는 절반만 해소되었다. 잘린 답변은 이제 거부되며(__init__.py:293-297) max_tokens의 기본값은 500이 아니라 2048이다. 그러나 노트를 컨텍스트 윈도와 비교하거나 max_tokens가 그 안에 여유를 남기는지 확인하는 것은 없다. context_for는 음수 값만 거부한다(extraction.py:146-153). Ortho 기본값에서는 답변 한도만으로 윈도와 같아진다(2048과 2048, :49, __init__.py:51). llama-cpp-python 0.3.36(llama.py:1343-1358)에서 엔진은 프롬프트만으로 n_ctx에 도달할 때에만 오류를 내며, 그렇지 않으면 max_tokens를 n_ctx에서 프롬프트를 뺀 값으로 줄이고 노트는 결코 잘리지 않는다. 그래서 Ortho에서는 답변이 노트가 남긴 범위 안에서 끝나는 한 노트가 통과하고, 그렇지 않으면 실패한다(finish_reason == "length"). 엔진이 일으키는 오류는 무엇이든 그 노트 하나만 실패시킨다(__init__.py:200-212).

출력 이름이 바뀌었다

파일은 Extraction_<note file name>.json과 .txt이며, Extraction_<stem>.txt가 아니다(__init__.py:240-266). 레거시 Dashboard(Extraction_*.txt)처럼 레거시 이름을 읽는 것은 같은 파일을 찾지 못한다.

확인됨: 레거시의 조용한 실패는 막혔다

이미지로만 된 PDF, 잘린 답변, JSON도 필드도 아닌 답변은 이제 그럴듯한 파일을 쓰는 대신 노트를 실패시킨다(__init__.py:276-305). 형식이 다른 같은 이름의 노트는 더 이상 서로를 덮어쓰지 않으며(:240-266), TMJ/tmj 철자 분열은 사라졌고(extraction.py:49-51), 들어줄 수 없는 GPU 요청은 보고된다(__init__.py:145-165). 코드에서 읽음.
