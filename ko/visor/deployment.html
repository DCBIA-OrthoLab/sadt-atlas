패키징과 배포

VISOR-serve가 하나의 컨테이너로 어떻게 빌드되는지, 모델과 설정이 컨테이너 밖 어디에 있는지, 각 설정의 기본값이 무엇인지, 서버를 띄우고 최신 상태로 유지하는 스크립트가 무엇인지, 저장소와 함께 게시된 벤치마크가 무엇을 측정했고 무엇을 측정하지 않았는지, 그리고 실행 중인 인스턴스를 날짜를 정해 점검했을 때 무엇이 발견되었는지를 다룬다. 서버는 torch를 로드하지 않는 Python 3.13 API 환경 하나와, 도구마다 하드링크로 연결된 가상 환경 하나씩을 가진 Docker 이미지다.

VISOR-serve e9a7e5d 브랜치 conf/vface-deployment 2026-11-09에 읽음 아키텍처 실행 과정, 단계별 보안
참고

인용은 VISOR-serve의 file:line이며 커밋 e9a7e5d 시점이고, 이 커밋은 main(e91557e)에 server/deployment.toml만 건드리는 커밋 하나(VFACE 데이터 폴더를 선언한다)를 더한 것이다. 도구 자체는 6ba2a78 시점의 SADT-VISOR에 있다. 이 사이트에서 "Legacy"는 SlicerAutomatedDentalTools의 Slicer 모듈을 뜻하며, 아래 내용은 그것들에 적용되지 않는다. 7절이 실행 중인 인스턴스에 대해 말하는 내용은 코드가 아니라 2026-10-20자 점검에서 나온 것이다. 전송 구간 보호, 토큰, 데이터 처리에 관한 주장은 보안 페이지에, 시스템 전체의 모양은 아키텍처 페이지에 있다.

1. 이미지

모든 도구를 담는 컨테이너는 하나다. docker/Dockerfile(232줄)이 이를 여러 단계로 빌드한다. 런타임 단계는 python:3.13-slim(:76)에서 시작해, 어떤 lockfile도 공급할 수 없는 시스템 라이브러리 하나인 libgomp1(:86)을 설치하고, uv 0.12.3(:89)을 복사한 뒤, /opt/sadt/.venv에 API 환경을 만든다. 이 환경은 server/requirements-api.txt로 만들어지며, 이 파일에는 fastapi, uvicorn[standard], python-multipart, pydantic-settings만 나열되어 있다(:105-108). 따라서 서버 프로세스는 torch도, nnU-Net도, MONAI도 import하지 않는다. 각 도구의 인터프리터는 uv가 직접 설치하므로(:75), 도구마다 다른 Python 버전을 쓸 수 있다.

  • 도구는 이미지에 구워져 있다. 패키징된 각 도구는 폴더 /tools/<name>/이며, 그 안에 .venv, src/, .schema.json이 들어 있다. 그룹 폴더 안의 도구(tools/ALI/ALI_CBCT)는 탐색이 두 단계 깊이까지 내려가므로 발견된다(registry/__init__.py:114). naming/ 패키지는 도구가 경로로 이에 의존하기 때문에 /naming으로 복사된다(Dockerfile:122). 프로세스 내부 픽스처 두 개 Example_Tool과 Test_Tool은 이미지 안에 있다. COPY server/가 server/tools/를 가져가고, .dockerignore:18-30은 새 배포가 모델을 내려받기 전에 인증, 업로드, 실행, 결과를 입증할 수 있도록 제외 규칙을 없앴다고 설명한다. 실행 중인 인스턴스는 둘 다 제공한다(항목 23개).
  • uv sync 레이어는 의도적으로 하나다. 모든 도구의 uv sync --frozen --no-install-project --no-dev --all-extras가 단일 RUN(:152)에서 실행되며, UV_LINK_MODE=hardlink와 이미지 자체 파일시스템 위의 uv 캐시를 쓴다(:96-101). 레이어를 나누면 overlayfs가 파일을 위 레이어로 복사하면서 하드링크가 깨진다. Dockerfile 자체의 주석은 torch 도구 열한 개를 공유 시 약 26 GB, 중복 시 약 63 GB로 측정했다(:131-134). --all-extras는 의도된 것이다. Crown_Seg 같은 도구는 엔진을 extra 뒤에 두고 있어서, 이 옵션이 없으면 이미지는 import는 되지만 첫 실제 요청에 503으로 답한다.
  • verify_dedup.py. 링크가 조용히 사본으로 바뀌어도 눈에 보이게 실패하는 것은 없으므로 docker/verify_dedup.py가 이를 검사한다. 같은 배포판에 같은 버전으로 속하는 파일(각 환경의 RECORD에서 읽는다)에 대해 inode가 둘이면 사본이라는 뜻이다. 하나라도 있으면 0이 아닌 값으로 종료하고, 표준 라이브러리만 쓰며, 이미지의 /opt/sadt/verify_dedup.py에 포함되어 있다(Dockerfile:200). 테스트 픽스처는 numpy_old(1.26.4, Python 3.12), numpy_new(2.5.2, Python 3.13), numpy_twin이다.
  • 스키마는 빌드 시점에 생성된다. 각 도구의 describe.py를 그 도구 자신의 인터프리터로 실행하는 방식이다(:177-188). 스스로를 기술하지 못하는 도구는 보고되고 제공되지 않는다. 시작 시 오래된 스키마는 다시 생성되어 SCHEMA_CACHE_DIR(/var/cache/sadt)에 캐시된다. /tools는 서버에게 읽기 전용이기 때문이다.
  • 이미지에 없는 것: 모델과 테스트 파일(2절), 사이트별 deployment.toml(4절, 이미지에는 마운트가 대체하는 기본 사본이 들어 있다), 작업 임시 공간 /jobs, API 토큰.
  • 프로세스. USER sadt이며 root가 아니다(:227). /tools의 코드는 root 소유이고 서버에게 읽기 전용이어서 서드파티 코드가 자신의 가상 환경을 고쳐 쓸 수 없다. CMD는 uvicorn main:app --host 0.0.0.0 --port 8000이며 --reload도 --workers도 없으므로 프로세스 하나와 접수 대기열 하나만 있다(:232). HEALTHCHECK가 없다. Dockerfile에도 docker-compose.yml에도 없다.

이미지가 설정하는 환경(Dockerfile:202-216)은 SADT_DISPATCH_MODE=subprocess, TOOLS_DIR=/tools, RUNNER_PATH=/opt/sadt/server/execution/runner.py, DESCRIBE_PATH=/tools/scripts/describe.py, SCHEMA_CACHE_DIR=/var/cache/sadt, DEPLOYMENT_CONFIG=/opt/sadt/server/deployment.toml, DATA_DIR=/DATA, TEMP_DIR=/jobs, PYTHONDONTWRITEBYTECODE=1이다. SADT_DISPATCH_MODE의 config.py:37 기본값은 임시로 표시된 inprocess다. 이미지가 이를 덮어쓰므로 컨테이너가 실행하는 것은 항상 subprocess 경로다.

compose 파일은 여러 서비스를 정의한다. 실제 배포인 것은 inference-venvs(프로파일 venvs, docker-compose.yml:200)로, docker/Dockerfile을 이름 있는 빌드 컨텍스트 tools=${TOOLS_CONTEXT:-docker/fixtures}와 함께 빌드하므로, TOOLS_CONTEXT가 없으면 실제 도구가 아니라 작은 픽스처를 빌드한다. 이 서비스는 shm_size: 8gb를 설정하고(nnU-Net은 내보내기 워커 사이에서 공유 메모리로 데이터를 전달하며, 기본값 64 MB로는 엉뚱한 자원을 지목하는 메시지와 함께 실패한다), 모든 GPU를 예약하며, unless-stopped로 재시작한다. 다른 서비스는 inference(컨테이너 레지스트리의 미리 빌드된 GPU 이미지이며 ./server가 마운트되고, 시작할 때마다 pip이 실행되며 uvicorn --reload가 쓰인다), inference-cpu, 그리고 test / test-gpu 서비스다. docker-compose.dev.yml은 SADT-VISOR 체크아웃의 server/와 각 도구의 src/를 읽기 전용으로 마운트하는 오버레이다.

함정

저장소 안의 문서는 여전히 더 오래된 이미지를 설명한다. :193-195의 Dockerfile 주석은 server/tools/가 .dockerignore로 제외된다고 하지만 더는 사실이 아니다(.dockerignore:18-30). :11-12와 :217의 주석은 아직도 도구 또는 upstream을 열다섯 개로 세는데, 패키징된 도구는 19개다. docker/README.md:45-48은 한 단계 더 깊이 중첩된 도구는 "현재 서버가 발견하지 못한다"고 하지만, 탐색은 두 단계 깊이이고 제공되는 도구 다섯 개(ALI_CBCT, ALI_IOS, AREG_CBCT, AREG_IOS, AREG_IOSCBCT)가 그룹 폴더에 있다. docker/README.md:4는 runner.py를 /opt/sadt/runner.py에 두는데, 실제 위치는 server/execution/runner.py다.

2. 모델과 테스트 파일

가중치(weights)는 이미지에 들어 있지 않고, 노트북에서 업로드되지도 않는다. 가중치는 DATA/ 디렉터리에 있으며, 이 디렉터리는 /DATA에 읽기 전용으로 마운트된다. DATA/<slug>/models/<name>과 DATA/<slug>/testfiles/<name>이며, 선택적으로 한 단계 더 깊은 범위(scope)로 둘 수 있다(DATA/AREG/testfiles/CBCT_T1). LocalDataStore가 이를 읽고, 다른 백엔드는 추상 DataStore 클래스를 통해 끼워 넣을 수 있다(DATA_BACKEND, config.py:31).

  • 어느 폴더인가. slug는 도구가 선언한 data_dir이고, 없으면 그 폴더가 존재할 경우 도구 이름 그대로이며, 그것도 아니면 밑줄을 뺀 이름이다. 그래서 Batch_Dental_Seg는 DATA/BatchDentalSeg를 읽는다(deployment.data_slug, registry/deployment.py:311-325). 도구 다섯 개가 data_dir = "AREG"(도구 셋) 또는 "ALI"(도구 둘)를 통해 폴더 두 개를 공유한다.
  • 어떤 인자가 여기서 채워지는가. 명명 규칙(registry/conventions.py)에 따라 model, *_model, *_reference는 업로드가 아니라 DATA/<tool>/models/ 중에서 고른 이름으로 게시되므로, 클라이언트가 가중치를 보낼 수 없다. 이런 필드에 파일을 업로드하면 400이다(main.py:1269-1278). 그 밖의 path는 업로드하거나 testfiles/에서 채울 수 있다.
  • API가 제공하는 것. GET /tools/{tool}/data는 모델과 테스트 파일을 나열하고, GET|HEAD /tools/{tool}/testfiles/{name}은 테스트 파일을 제공한다. 모델을 제공하는 경로는 없다(download_testfile은 testfiles만 읽는다). 테스트 파일 폴더는 즉석에서 zip으로 묶여 Accept-Ranges: none과 함께 전송된다. 그렇지 않으면 클라이언트가 탐지하고 range를 확인한 뒤 339 MB 코호트를 43개 조각으로 나누고, 서버는 같은 아카이브를 43번 만들게 된다. range 방식은 39.1 s, 통째로는 1.5 s다(main.py:794-806).
  • 채우기. scripts/data-manifest.yml은 무엇이 있고, 어디서 오며, 어디로 가는지를 적는다. scripts/fetch_data.py(표준 라이브러리만 사용)가 이를 내려받고, setup-models.sh와 setup-testfiles.sh는 래퍼이며, --list는 내려받지 않고 도구별 크기를 출력한다. 항목은 name, url, 선택적인 sha256(불일치하면 파일을 버리며, 없으면 스크립트가 얻은 해시를 출력하므로 manifest에 붙여 넣으면 된다), 선택적인 size, zip을 풀고 폴더를 유지하는 extract: true, 이름을 바꾸거나 여러 아카이브를 하나의 번들 폴더로 묶는 dest를 가진다. manifest 주석은 전체를 도구 14개에 걸쳐 약 29 GB로 잡으며, 그중 12 GB가 ALI의 CBCT 모델이다.

3. 설정

함정

compose 기본값 ${API_TOKEN:-dev-token}는 .env를 쓰지 않은 설치가 공개된 토큰으로 실행된다는 뜻이다. 버전 관리되는 파일에 있기 때문이다. 포트 매핑 "${BIND_ADDR:+${BIND_ADDR:-}:}${VENVS_HOST_PORT:-8001}:8000"(docker-compose.yml:224)는 BIND_ADDR가 설정되지 않으면 모든 인터페이스에 게시한다. scripts/server_ctl.py를 거치는 경로는 토큰을 생성하고 BIND_ADDR의 기본값을 127.0.0.1로 둔다(server_ctl.py:368,398). compose를 손으로 시작하면 그렇지 않다.

4. deployment.toml

server/deployment.toml은 하나의 설치에 고유한 것을 담는다. 시작할 때 한 번 읽으며, 한 줄을 바꾸어도 이미지를 다시 빌드하지 않아도 되도록 이미지의 사본 위에 읽기 전용으로 컨테이너에 마운트된다(docker-compose.yml:215-220). 각 [tools.<name>] 테이블에는 정확히 다음 키만 올 수 있다(_TOOL_KEYS, registry/deployment.py:69): server_selectable, max_upload_mb, data_dir, hidden, timeout_seconds, dispatch, batch, width_from. server_selectable은 model, testfile, none을 받으며, 범위는 testfile:Sub_folder로 쓴다(:53, SCOPE_SEPARATOR). 읽을 수 없는 파일이나 알 수 없는 키는 치명적이다(DeploymentConfigError). 서버가 모르는 값을 거부할 때는 DEPLOYMENT-CONFIG-AHEAD-OF-SERVER 표식이 붙는다(:66). 파일은 마운트되므로 이미지보다 새로울 수 있기 때문이다.

5. 스크립트와 운영

파일하는 일
scripts/setup-server.sh아무것도 없는 상태에서 curl | sh로 저장소를 클론하고(기본은 main), Docker가 동작하는지 확인하고, 모드 0600과 생성된 토큰으로 .env를 쓰고, 하드웨어에 맞는 compose 서비스를 시작한 뒤 /health를 기다린다. 옵션은 --dir, --tool(그 도구의 데이터도 가져온다. 기본적으로는 아무것도 내려받지 않는다), --device gpu|cpu, --bind(기본값 127.0.0.1), --port, --no-start다. 다시 실행해도 안전하며, .env에 이미 있는 토큰은 유지된다.
scripts/install-docker.sh · install-docker-gpu.shLinux의 Docker Engine과 compose 플러그인이 필요하고 root 권한이 요구되며, 두 번째에는 NVIDIA container toolkit이 더해진다.
scripts/server_ctl.py배포 엔진이며 표준 라이브러리만 쓰고, Slicer 클라이언트도 이를 구동한다. 하위 명령은 status, token, up, update, watch, down, logs, catalog, models다(:1517-1600). up은 기본적으로 포트를 127.0.0.1에 게시한다.
scripts/visor-update.service호스트에서 server_ctl.py watch --branch deploy --poll 30을 실행하는 systemd user 유닛이다. 컨테이너에는 server/만 있고 .git이 없기 때문이다. Restart=always, Nice=10, 유휴 I/O 클래스다. SADT_AUTO_UPDATE가 달리 말하지 않는 한 작동하지 않는다.
run-local.shDocker 없이 SADT-VISOR 체크아웃(SADT_TOOLS, 기본값 ~/code/SADT-VISOR)을 대상으로 서버를 실행한다. TOOLS_DIR과 DESCRIBE_PATH가 그 안을 가리키고, 127.0.0.1:8001에서 수신하며, 설정하지 않으면 토큰은 local-dev-token이고, 로그는 local-server.log에 기록된다.
scripts/domain_coupling.py서버 자체 코드에서 응용 분야 단어를 세어 그 단어 목록을 게시한다. "서버는 어떤 도구도 모른다"는 말의 근거가 되는 측정이다. --max N은 예산을 넘으면 1로 종료한다.

자동 업데이트. SADT_AUTO_UPDATE는 off(기본값), notify, apply 중 하나다(server_ctl.py:838-850). apply는 /status가 실행 중인 것도 대기 중인 것도 없다고 보고할 때까지 기다리고, 60 s 임대(lease)를 갱신하면서 POST /maintenance로 문을 닫고(:911, GATE_LEASE_SECONDS), git pull --ff-only(:1178)를 실행하고, up -d --force-recreate(:1205, restart는 결코 쓰지 않는다)로 다시 띄운 뒤 문을 다시 연다. lockfile, pyproject.toml, server/requirements*, docker/의 변경은 새 이미지가 필요하므로 거부한다(:522-524). 유닛 자체의 헤더는 머신이 "공개 저장소에서 가져온 코드를 실행하게 된다"고, 그리고 현재 이 저장소들의 어떤 커밋에도 서명이 없다고 경고한다. apply로 전환하는 것은 그 머신에 책임이 있는 사람이 내릴 결정으로 기술되어 있다.

6. 역사적 문서 둘: ALI와 ASO 패키징

VISOR-serve 루트의 파일 두 개가 ALI와 ASO를 프로세스 내부 도구에서 패키징된 도구로 옮기는 작업을 기술한다. 둘 다 결정이 어떻게 내려졌는지를 날짜와 함께 남긴 기록이며 일부는 더 이상 유효하지 않다. 기준은 코드와 실시간 카탈로그다.

문서가 말하는 것문서와 날짜e9a7e5d에서 참인 것
도구 네 개가 패키징되어 처음부터 끝까지 실행되었다. AMASSS(21.8 s), Batch_Dental_Seg(71 s, 업로드 86 MB), Surg_Mov_Pred(8.6 s), Crown_Seg(0.95 s, "손대지 않고 통과").PACKAGING_ALI_AND_ASO.md, "현재 상황(2026-08-13)"그날 아침의 스냅샷. 오늘은 패키징된 도구 19개가 제공된다.
tools/ALI/와 tools/ASO/는 프로세스 내부 도구의 원본 사본을 담고 있으며, pyproject.toml도, lockfile도, venv도 없다.같은 파일둘 다 패키징되었다. ALI_CBCT, ALI_IOS, ASO는 제공되는 항목에 들어 있다(실행 중인 인스턴스의 GET /tools, SADT-VISOR의 tools/ALI와 tools/ASO).
"순서 지정은 아직 서버에 없다". depends_on 메커니즘이 제안된다.같은 파일감독자는 존재한다(sup.run, admission 절). 서버 코드에는 depends_on이 없고, 이 단어의 유일한 흔적은 server/tests/test_main.py:1394의 docstring이다.
결정 1은 ASO를 모달리티와 자동화 수준마다 하나씩, 도구 넷으로 나눌 것을 권고한다.같은 파일이루어지지 않았다. ASO는 modality와 automation 인자를 가진 하나의 도구이며, 모달리티별로 인자를 보여 주는 레이아웃을 가진다(SADT-VISOR tools/ASO/src/sadt_aso/layout.py:28-29).
ALI의 IOS 쪽은 pytorch3d가 필요한데 쓸 만한 wheel이 없으며, 선택적 extra가 빌드되기 전까지는 Crown_Seg처럼 503으로 답한다.같은 파일, "결정 2"extra 메커니즘이 오늘날 Crown_Seg가 동작하는 방식이며, Dockerfile의 --all-extras가 이를 빌드한다. 게시된 이미지에서 ALI_IOS용 pytorch3d가 빌드되는지는 이 페이지를 위해 검증하지 않았다.
"ALI라는 도구 하나"에 두 엔진이 모두 src/ 안에 있다. ALI_CBCT + ALI_IOS 두 도구로 나누는 것은 기각된 대안이다.ALI_PORT_CONTEXT.md §3.1, 상태 2026-07-31도구 둘과 파사드 ALI이며, 이 파사드의 mode는 CBCT 또는 IOS다(deployment.toml:205-210). 이 파일은 스스로를 "이유의 기록"이라 부르며, 이 파일과 코드가 어긋나면 코드가 옳다고 말한다.

7. 실행 중인 인스턴스를 점검해 알게 된 것

날짜가 있는 관찰이며, 코드의 속성이 아니다

실행 중인 인스턴스 하나를 2026-10-20에 점검했다(저장소 밖에 보관된 보고서). 그 머신에 대해 발견된 내용은 지금은 사실이 아닐 수 있다. 이 절은 코드로 설명되는 것만 남기고, 머신이나 그 네트워크를 식별할 수 있는 세부 사항은 일부러 뺐다. 이 페이지를 쓰는 동안 한 확인은 인증 없는 GET /health와 GET /tools뿐이었고, 각각 {"status":"ok"}와 항목 23개로 답했다.

  • 코드가 예측한 것은 실제로 그렇게 되었다. GET /health와 GET /tools는 토큰 없이 답했고, GET /status는 토큰 없는 요청을 거부했다(401). 카탈로그에는 23개 항목이 있었고 그중 19개는 스키마에서 온 것이었다. 시작 로그에는 건너뜀, 오류, traceback이 없었다. 유일한 경고는 ALI_CBCT, ALI_IOS, ASO의 무시된 스키마 키였으며, 아키텍처 페이지에서 설명한다.
  • 컨테이너에서 곧바로 나오는 평문 HTTP. AutomatedDentalToolsRemote의 Slicer 클라이언트는 공인 인증서가 있는 HTTPS를 요구하고 대체 수단이 없으므로(보안 페이지), 그렇게 노출된 인스턴스에는 연결할 수 없다. API를 직접 호출하는 스크립트는 연결할 수 있다.
  • .env가 없다. 인스턴스는 그것 없이 시작되었으므로 토큰을 포함해 3절에서 설명한 compose 기본값으로 실행되고 있었다.

보고서는 이어서 무인 실행을 멈출 수 있는 것들을 나열한다. 아래 각 항목은 코드와 대조해 확인했으며, 보고서는 처음 넷을 실제 실행이 아니라 코드, 설정, 로그에서 도출한 것으로 표시한다.

  1. 타임아웃 없음. TOOL_TIMEOUT_SECONDS는 0이고 deployment.toml도 아무것도 설정하지 않는다(config.py:77). 막힌 실행 넷이면 그중 어느 것도 실패하지 않은 채 서버가 얼어붙는다.
  2. 측정되지 않은 도구는 혼자 실행된다. 비용이 한 번도 측정되지 않은 도구는 예산 전체를 예약한다(execution/admission.py:22-33). 그 인스턴스에서는 대부분의 도구에 아직 측정된 비용이 없었으므로, 공지된 max_parallel_jobs: 4는 실제 처리량을 과장했다.
  3. 예약은 최근 최악의 실행을 따른다. 학습된 비용은 최근 COST_WINDOW = 20번 실행 중 최댓값이므로(config.py:106), 입력에 따라 메모리 사용량이 크게 달라지는 도구는 최악의 경우를 예약하고 직렬화된다.
  4. VRAM 수치 없음. 그 인스턴스에서 /status는 vram_bytes: null과 free_bytes: null인 카드를 반환했다. nvidia-smi를 셸로 호출하는 프로브(resources.py:193)가 아무것도 반환하지 않았고, /status는 설계상 이를 허용한다(main.py:470-474). 그러면 admission은 코어와 RAM만으로 동작한다.
  5. 실패한 실행도 비용 표를 학습시킨다. 측정값은 오류 분기 앞에서 보존되는데, 의도된 것이다. 메모리 부족으로 죽은 실행이 가장 유용한 측정이기 때문이다(execution/dispatch.py:800-803). 따라서 관련 없는 이유로 실패하는 벤치가 이후의 예약을 부풀릴 수 있다.
  6. Dockerfile에도 compose에도 healthcheck가 없다. restart: unless-stopped는 죽은 컨테이너를 다시 띄울 뿐, 살아 있지만 멈춰 버린 컨테이너를 알아채는 것은 없다.
  7. 운영자의 SIGKILL은 메모리 부족 사망처럼 보인다. SIGKILL이 있고 result.json이 없으면 커널의 메모리 부족 kill로 해석되므로(execution/dispatch.py:930-949), 실행이 다시 시작된다.

8. 서버와 함께 게시된 벤치마크

benchmarks/는 다시 실행 가능한 하네스(python -m benchmarks.run --campaign b1..b5 [--dry-run])이며 config.yaml로 설정된다. 실행 경로는 세 가지다. local(도구를 자체 인터프리터에서, HTTP 없이 실행하며, NOTES-local-path.md에 문서화된 차이가 넷 있다), loopback(같은 머신의 HTTP API), 그리고 한 번도 측정되지 않은 lan이다. server.lan_base_url이 null이다(config.yaml:22). 하네스의 HTTP 클라이언트는 Slicer 클라이언트의 프로토콜을 따른다. 8 MB 조각, 동시 전송 넷, 조각당 SHA-256, gzip, X-Result-Delivery: reference, range 다운로드다. 통계는 평균이 아니라 전체 범위를 곁들인 중앙값이며, 각 구성의 반복 1은 워밍업으로 버려지지만 원시 파일에는 warmup: true로 남고, 실패한 실행은 기록이 되며 결코 삭제되지 않는다.

함정

이 수치는 있는 그대로 읽어야 한다. 이 수치는 2026-08-25부터 단일 머신(Xeon w7-3555, 코어 28개, 125 GiB, RTX 6000 Ada 48 GB, 드라이버 595.84, 1 Gb/s 이더넷, Ubuntu 22.04.5)에서, 카드 한 장으로, MAX_CONCURRENT_GPU_JOBS=1(benchmarks/README.md:338)로 측정되었다. 즉 admission 엔진이 그 카운터를 대체하기 전이다(커밋 89393b5, 2026-09-21). 측정은 loopback 또는 local에서만 이루어졌으므로, 전송 시간은 네트워크가 아니라 localhost의 것이다. 기록은 8월의 -dirty로 표시된 도구 및 서버 트리를 가리킨다. 현재의 스케줄러를 기술하지 않는다.

local 경로와 HTTP 경로 사이의 바이트 단위 동등성은 도구 하나, AREG_IOSCBCT에 대해, 한 세션에서(n = 1쌍) 성립한다. 일반적으로 성립하는 것은 아니다. 대조군은 이 도구들 대부분이 같은 경로에서도 자기 자신을 바이트 단위로 재현하지 못함을 보여 준다. 보고서에 소요 시간이나 경로가 들어 있고, 바이트 비교로는 보고서와 데이터를 구별할 수 없기 때문이다. 이 표로는 "동등성 달성"도 "동등성 상실"도 쓸 수 없다. 저장소의 README는 하네스가 동반 논문의 모든 실행 시간 수치를 재현한다고 말하는데, 이는 요약이 있는 B1, B3, B4에서는 맞고, B2와 B5는 원시 파일에서 읽어야 한다.
