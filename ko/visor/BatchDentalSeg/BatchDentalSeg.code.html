VISOR의 BatchDentalSeg: 코드

개발자용: BatchDentalSeg의 VISOR 이식이 코드에서 하는 일을 file:line 참조, 시그니처, 인수, 환경, 레거시 코드와의 차이, 발견 사항과 함께 다룬다. 같은 파이프라인을 수식과 함께 읽기 쉽게 설명한 것은 아틀라스 페이지에 있다. BatchDentalSeg가 VISOR에서 실행되는 방식(클라이언트와 서버), 레거시 Slicer 모듈에서 바뀐 것, 이식의 코드가 하는 일을 단계별로 설명한다. 레거시 모듈은 자체 페이지에 설명되어 있다.

코드 아틀라스 (해설) VISOR Batch_Dental_Seg 레거시 페이지 가이드 (VISOR) 참고문헌

VISOR는 BatchDentalSeg를 서버에서 실행한다. Slicer가 스캔과 호스팅된 모델의 이름을 보내면, 레이블 볼륨, 레이블별 파일, 또는 메시를 받는다. 네 가지 번들 중에서 고른 nnU-Net v2 신경망 하나가 스캔의 모든 구조에 한 번의 패스로 레이블을 붙이며, 호출 한 번이 배치 전체를 다룬다. 이 페이지는 무엇이 어디서 실행되는지 말하고, 입력 파일에서 실행 보고서까지 파이프라인을 따라가고, 서버가 발행하는 인수를 나열하며, 각 단계를 레거시 모듈과 비교한다. 여기의 모든 것은 코드에서 읽은 것이지 실행 중인 서버에서 관찰한 것이 아니며, 어떤 서버가 배포되어 있다는 말은 여기 어디에도 없다.

참조는 저장소 이름을 먼저 적는다. SADT-VISOR(도구 코드, tool/vface @ 6ba2a78), VISOR-serve(서버, @ e9a7e5d), AutomatedDentalToolsRemote(Slicer 클라이언트, @ 19b95e8), 레거시(SlicerAutomatedDentalTools @ 3c67957). pipeline.py, catalogs.py, layout.py, nnunet_runner.py, low_memory.py, mesh_export.py, progress.py, __init__.py 같은 접두어 없는 파일 이름은 SADT-VISOR 패키지 tools/Batch_Dental_Seg/src/sadt_batchdentalseg/에 있다. SegmentationWidget.py, Queue.py, PythonDependencyChecker.py는 BATCHDENTALSEG/BATCHDENTALSEGLib/의 레거시 파일이다(위젯은 3c67957 시점에 3037줄이다).

1. 체인에서의 위치

Batch_Dental_Seg는 잎이다. 다른 도구를 호출하지 않으며, 이를 호출하는 도구가 하나 있다. run()은 감독자 인수를 아예 받지 않으므로(SADT-VISOR __init__.py:13-26) 실수로라도 다른 도구에 닿을 수 없다.

1.1 무엇이 어디서 실행되는가

서버클라이언트(Slicer)
스캔을 읽어 NIfTI로 변환하고, 배치 전체에 nnU-Net v2 호출 한 번(fold 0, checkpoint_final.pth), 레이블을 스캔 격자에 되돌려 놓고, 레이블 볼륨, 레이블별 파일, 메시, 보고서를 쓴다(SADT-VISOR pipeline.py:140-209, 256-398, nnunet_runner.py:192-232)스캔, 모델 이름, 내보내기 형식을 고른다. 해부학이나 모델에 관한 것은 패널에 없다(BATCHDENTALSEGRemote.py:51-59)
모델 번들은 호스팅되어 이름으로 발행된다. 패널은 GET /tools/Batch_Dental_Seg/data를 나열하며, 가중치는 노트북에서 결코 보내지 않는다(BATCHDENTALSEGRemote.py:55-59, VISOR-serve server/registry/schema_tool.py:595-609, server/registry/conventions.py:14-16)결과 아카이브의 압축을 푼다(BATCHDENTALSEGRemote.py:93-97). 결과는 최대 12개 불러온다(MAX_RESULTS_TO_LOAD, BATCHDENTALSEGRemote.py:67). 레이블 볼륨은 레이블 맵으로, .stl .obj .vtk는 모델로 불러온다(:83-91, ServerToolsCoreLib/slicer_io.py:560-562)
nnU-Net 워커를 위한 공유 메모리: 컨테이너 정의의 shm_size: 8gb(VISOR-serve docker-compose.yml:225-229). ITK 자체의 스레드 풀은 다른 수치 라이브러리와 같이 상한이 있다(server/execution/dispatch.py:499-503)Slicer에는 아무것도 설치되지 않는다. NNUNet 확장도, torch도, 모델 다운로드도 없다(BATCHDENTALSEGRemote.py:4-14)

레거시 모듈에서는 모든 것이 Slicer 안에서 실행되었다. 위젯이 각 볼륨을 내보내고, 외부 NNUNet 확장을 통해 nnUNetv2_predict를 QProcess로 시작했으며, 스캔을 하나씩 처리하고, 장면에서 레이블 맵을 다시 만들었다(레거시 §1, legacy SegmentationWidget.py:1827).

쉬운 설명과 수식: 아틀라스 페이지.

3. 파이프라인

segment()(SADT-VISOR pipeline.py:216-398)는 일직선이다. 스캔을 읽기 전에 번들을 검사하고, 모든 스캔을 폴더 하나로 변환하며, nnU-Net이 그 폴더에 한 번 실행되고, 그다음 각 스캔이 자기 격자에 다시 쓰인다. 학습된 단계는 신경망 단계뿐이다.

쉬운 설명과 수식: 아틀라스 페이지.

3.1 입력과 탐색

discover_scans()(pipeline.py:87-107)는 파일 하나는 그대로 받고, 폴더는 os.walk로 재귀적으로 돌며 확장자가 sadt_naming.VOLUME에 있는 파일을 남긴다. .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl이며 소문자로 비교한다(SADT-VISOR naming/src/sadt_naming/__init__.py:36). 폴더에서는 이 도구의 이전 출력처럼 보이는 파일을 건너뛴다.

def is_previous_output(filename, suffix):                      # pipeline.py:72-84
    base, _extension = split_scan_extension(os.path.basename(filename))
    if suffix and base.endswith(f"_{suffix}"):
        return True
    return any(base.endswith(f"_{suffix}_{name.replace(' ', '-')}")
               for model in catalogs.MODELS.values()
               for name in model.labels)

기본값 prediction_ID = "Seg"에서는 기본 이름이 _Seg로 끝나거나 네 모델 중 어느 것의 어떤 레이블에 대해서든 _Seg_<label>로 끝나는 것이 모두 해당하므로, 폴더를 제자리에서 다시 실행할 수 있다(자기 이름이 그렇게 끝나는 스캔에 대해서는 §8의 발견 사항 참조). 스캔이 하나도 없으면 ToolInputError가 난다(pipeline.py:243-248). 입력 트리는 유지된다. input_root는 폴더이거나 파일 하나의 부모이며(pipeline.py:250), 모든 케이스는 보고서에서 그에 대한 상대 경로로 기술되고 절대 경로로는 결코 기술되지 않는다(pipeline.py:264-265).

쉬운 설명과 수식: 아틀라스 페이지.

3.2 모델: 이름 하나, 번들 하나, 레이블 표 하나

resolve_model()(pipeline.py:110-133)은 스캔을 읽기 전에 실행된다. model 경로의 폴더 이름을 catalogs.MODELS에서 조회하며, 알 수 없는 이름은 알려진 모델의 목록과 함께 거부된다. 폴더 안에서 find_model_folder()는 dataset.json, plans.json, fold_0/checkpoint_final.pth를 담은 디렉터리를 찾아 트리를 돌며, 셋 모두를 검사한다(nnunet_runner.py:57-73). 네 번들은 같은 배치를 공유하지 않으며, DentalSegmentator는 자체 Dataset<n>/ 트리가 든 zip으로 도착한다(nnunet_runner.py:37-41). 불완전한 번들은 다시 준비하는 명령과 함께 거부된다(pipeline.py:126-132).

MODELS = {model.name: model for model in (                     # catalogs.py:126-152
    Model("DentalSegmentator",  _FIVE_LABELS,      "Adult dental CT/CBCT. ..."),
    Model("PediatricDentalSeg", _FIVE_LABELS,      "Paediatric dental CT/CBCT, ..."),
    Model("NasoMaxillaDentSeg", _NASO_LABELS,      "Six segments: the maxilla is separated ..."),
    Model("UniversalLab",       _UNIVERSAL_LABELS, "Every tooth labelled individually ..."),
)}

레이블 표가 폴더 이름을 따르므로, 호출하는 쪽은 한 번들을 다른 번들의 레이블과 짝지을 수 없다. 틀릴 수 있는 두 번째 인수가 없다(catalogs.py:120-125). 값은 신경망이 내는 정수이며, 코드는 이를 바꾸지 않고 쓴다.

3.3 nnU-Net 배치로의 변환

모든 스캔은 폴더 하나 <output_dir>/.batchdentalseg_work/nnunet_in/로 변환되며, 위치 기반 케이스 id가 붙는다(pipeline.py:256-277).

case_id = f"case_{index:04d}"                                   # pipeline.py:275
_convert_to_nifti(scan, os.path.join(nnunet_input, f"{case_id}_0000.nii.gz"))

def _convert_to_nifti(scan_path, destination):                  # pipeline.py:140-149
    sitk.WriteImage(sitk.ReadImage(scan_path), destination)

읽고 쓰기이며, 이름 바꾸기는 결코 아니다. nnU-Net은 확장자로 리더를 고르므로 .nii.gz로 이름을 바꾼 NRRD는 잘못 읽힌다. 복셀 유형은 그대로 두며, nnU-Net이 알아서 float32로 캐스팅한다(pipeline.py:143-145). id가 위치 기반인 이유는 nnU-Net이 출력을 입력의 id로 쓰고, 서로 다른 하위 폴더의 scan.nii.gz라는 스캔 둘이 충돌하기 때문이다(pipeline.py:256-259). 읽을 수 없는 스캔은 "could not be read"와 함께 failed로 기록되고 건너뛰며, 하나도 읽을 수 없을 때만 실행이 멈춘다(pipeline.py:278-298).

이 패키지에는 강도 윈도잉도 자르기도 쓰여 있지 않다. 패키지가 더하는 리샘플링은 선택적인 GPU 리샘플링(§3.5)과 결과를 스캔 격자에 되돌려 놓는 리샘플링(§3.6, pipeline.py:152-171) 둘뿐이다. 나머지 전처리는 각 번들의 plans.json에서 오는 nnU-Net 자체의 것이며 이 순서로 실행된다(도구 환경에 설치된 nnunetv2 2.8.1, nnunetv2/preprocessing/preprocessors/default_preprocessor.py). 전치(:56), 0이 아닌 영역으로 자르기(:65), 정규화(:82, 그 위의 주석은 리샘플링 앞에 와야 한다고 MUST로 쓴다), 그다음 plan의 간격으로 리샘플링(:88). 레거시의 자동 자르기는 일부러 이식하지 않았다. 업스트림은 메모리 검사가 실패한 뒤에만 이를 적용했고, 신경망이 보는 것을 바꾸기 때문이다(pipeline.py:18-21).

정규화는 이 저장소의 것이 아니라 nnU-Net의 것이다. 스킴이 CTNormalization인 plan에서는 plan의 0.5와 99.5 백분위수로 클립하고, 평균을 빼고, max(std, 1e-8)로 나눈다(nnunetv2/preprocessing/normalization/default_normalization_schemes.py:58-72, 숫자는 foreground_intensity_properties_per_channel에서 온다). 저장소에서 읽을 수 있는 것은 DentalSegmentator의 plans.json뿐이다(레거시의 것에서: CTNormalization, p0.5 −110, p99.5 3067, 평균 1274, 표준편차 558). 나머지 세 번들의 plan은 모델과 함께 내려받으므로, 이 스킴이 그것들에 적용된다는 것은 가정이며 검사한 것이 아니다.

쉬운 설명과 수식: 아틀라스 페이지.

3.4 추론: 배치 전체에 호출 한 번

predict_folder()(nnunet_runner.py:192-232)는 받은 입력 폴더 전체로 한 번 호출되므로(pipeline.py:302-306), 체크포인트는 스캔마다가 아니라 호출마다 한 번 불러온다. 서버 배치(25개 파일 또는 400 MB, §4)보다 큰 코호트는 이런 호출 여러 번으로 도구에 도달한다. 예측기는 nnU-Net의 Python API로 만들며, 이름이 바뀐 키워드는 인트로스펙션으로 고른다.

모델 경로는 명시적이다. 프로세스 전역인 nnUNet_results 환경 변수는 쓰지 않는다(nnunet_runner.py:202-203). 보이는 카드가 없으면 device는 경고와 함께 cuda에서 cpu로 대체된다(nnunet_runner.py:46-54). 두 갈래가 이어진다(nnunet_runner.py:210-232).

  • GPU 리샘플링이 적용되면: predict_from_files_sequential, 모든 것이 이 프로세스에서 실행된다. 생성된 워커는 각자 자기 CUDA 컨텍스트가 필요하기 때문이다.
  • 그 밖의 경우(CPU, gpu_resampling=false, 또는 다른 리샘플러를 쓰는 plan): 전처리 워커 2개와 내보내기 워커 2개로 predict_from_files. 그 워커들이 컨테이너의 shm_size가 필요한 이유이다(VISOR-serve docker-compose.yml:225-229).

패치 배치와 가중치는 nnU-Net의 것이다. 걸음은 최대 패치 크기의 tile_step_size배이며, 패치가 이미지 가장자리에서 정확히 끝나도록 줄어드므로 0.5에서는 겹침이 최소 절반이 된다(nnunetv2/inference/sliding_window_prediction.py:30-54). Gaussian 가중치의 퍼짐은 패치의 8분의 1이다(sliding_window_prediction.py:11-16, predict_from_raw_data.py:626에서 호출).

진행률에는 측정할 수 있는 끝이 둘뿐이다. 읽기는 스캔을 세어 0에서 10 %까지, 쓰기는 90에서 100 %까지이며, 그 사이에는 한 줄이 "segmenting N scan(s) in one pass"라고 말한다(pipeline.py:269-274, 301, 313, progress.py:89-103). 추론 호출이 예외를 일으키면 스크래치 폴더는 지워지고 배치 전체가 실패하며 보고서는 쓰이지 않는다(pipeline.py:302-309).

3.5 GPU 리샘플링과 클래스별 argmax

CUDA 장치에서 gpu_resampling = true(기본값)이면, _enable_gpu_resampling()(nnunet_runner.py:124-189)이 예측기 설정의 리샘플러 이름 둘을 다시 쓰며, 둘 다 nnU-Net의 기본 resample_data_or_seg_to_shape일 때만 그렇게 한다.

for key in ("resampling_fn_data", "resampling_fn_probabilities"):   # nnunet_runner.py:167-177
    configuration[key] = "resample_torch_fornnunet"
    configuration[f"{key}_kwargs"] = {"is_seg": False,
                                      "device": torch.device(device),
                                      "mode": "linear"}

그래서 입력 볼륨은 spline 차수 3에서 1로 내려가며, 코드는 이를 수치 차이의 전부라고 부른다(nnunet_runner.py:169-172). 세 번째 리샘플러, 즉 자르기 마스크용은 일부러 scipy에 둔다(nnunet_runner.py:110-116). 교체가 효과를 내도록 캐시된 속성은 지워진다(:179-183).

같은 함수가 이어서 low_memory.install(predictor)를 호출한다(nnunet_runner.py:185-188). 이는 확률 리샘플러를 다시 바꾸어, 신경망 출력을 한 번에 한 클래스씩 리샘플링하고 누적 최댓값과 레이블을 유지하게 하며, nnU-Net의 argmax를 통과 함수로 바꾼다. 도착하는 것이 이미 argmax이기 때문이다.

for index in range(data.shape[0]):                              # low_memory.py:62-79
    one = resample_torch_fornnunet(data[index:index + 1].to(device), shape, ...)[0]
    ...
    higher = one > best
    best = torch.where(higher, one, best)
    labels = torch.where(higher, index, labels)
return labels.unsqueeze(0).cpu()                                 # :86

두 절반은 함께 설치되거나 전혀 설치되지 않는다. predict_from_files_sequential을 위해 새 레이블 관리자를 만드는 팩토리도 인스턴스에서 감싸진다(low_memory.py:100-151). 모듈 docstring에 따르면 산술은 기본 경로와 같고(UniversalLab 실행에서 95 682 560개 복셀 중 다른 것 0개), 최대 사용량은 VRAM 약 30.6에서 1.25 GiB로 떨어진다(low_memory.py:14-26). 이 숫자들은 여기서 재현하지 않았다. 클래스 사이의 동점은 GPU 경로에서 낮은 인덱스로 가는데, 누적 최댓값은 엄격하게 더 높은 점수일 때만 바뀌기 때문이다(one > best, low_memory.py:75). nnU-Net 자체의 경로에서 레이블은 predicted_probabilities.argmax(0)이며(nnunetv2/utilities/label_handling/label_handling.py:178), NumPy와 PyTorch의 규약에 따라 첫 번째 최댓값을 돌려준다(argmax의 문서화된 동작이며 여기서 테스트하지는 않았다).

3.7 표면

mesh_export.write()(mesh_export.py:177-236)는 export_formats에 메시 형식이 없으면 아무것도 하지 않는다. 존재하는 각 레이블의 표면을 한 번 만들어 요청된 모든 형식으로 쓰므로, STL과 OBJ를 함께 체크해도 마칭 큐브 패스는 한 번만 치른다(:212-225).

특징 모서리 평활화는 일부러 꺼 둔다. 원시 마칭 큐브 메시에서는 모든 복셀 계단이 날카로운 모서리이므로, 그 모서리를 보호하면 계단이 남을 것이다(mesh_export.py:94-107). 단순화는 위상을 보존하고 특징 각도 60으로 vtkDecimatePro를 쓴다(:120-130). 그 기본값 0은 레거시 모듈의 STL 내보내기와 맞추기 위해 골랐으며, docstring에 따르면 레이블 하나에서 측정했다(__init__.py:84-100). 법선은 쓰이지 않는다(:132-139). STL과 VTK는 이진으로, OBJ는 이진 형식이 없으므로 텍스트로 쓴다(:45-49, 165-172). 마스크는 고유한 이름의 임시 NRRD를 거쳐 VTK에 도달하며 읽은 뒤 지워진다(:66-118). mesh_export.py는 명시적인 RAS나 LPS 변환을 적용하지 않으며, LPS로 뒤집던 레거시 VTK 내보내기와 다르다(legacy SegmentationWidget.py:2958).

입력. 파일 하나는 그대로 받는다. 폴더에서는 기본 이름이 _<ID> 또는 _<ID>_<label-name>으로 끝나는 파일이 이전 출력으로 건너뛰어지므로 폴더를 제자리에서 다시 실행할 수 있다(pipeline.py:72-107). 확장자: .nii .nii.gz .nrrd .nrrd.gz .gipl .gipl.gz. 네 가지 밖의 번들 이름은 알려진 모델의 목록과 함께 거부되며, 불완전한 번들(dataset.json, plans.json, fold_0/checkpoint_final.pth 중 하나가 없음)은 실행할 설정 명령과 함께 거부된다(pipeline.py:110-133).

출력. 스캔의 상대 폴더가 output_dir 아래에 그대로 반영된다(pipeline.py:329-336). NIFTI에서는 <base>_<ID><ext>(레이블 볼륨)이고, separate_segments가 있으면 존재하는 레이블마다 이진 파일 하나가 <base>_<ID>_<label-name><ext>로 생기며 공백과 슬래시는 대시로 바뀐다(pipeline.py:184-209, 342-350). 메시: 존재하는 레이블마다 <base>_<ID>_<label-name>.stl|.obj|.vtk와 <base>_<ID>_merged.vtk(메시 하나, 셀 배열 Label)(mesh_export.py:36-49, 143-155, 218-235). 루트에는 BatchDentalSeg_report.json(§3.8).

자원과 시간 제한. deployment.toml에 이 도구의 섹션이 없으므로 서버 기본값이 적용된다. 시간 제한 없음, 업로드 상한 500 MB, 코호트 배치는 최대 400 MB 또는 파일 25개(VISOR-serve server/config.py:77, 240, 192, 196). scans는 model과 output_dir을 제쳐 두면 유일한 필수 경로이므로, 코호트를 나누는 축이 된다(server/registry/conventions.py:158). 동시성은 메모리와 코어 허용으로 정해진다(server/execution/admission.py:1-12).

쉬운 설명과 수식: 아틀라스 페이지.

8. VISOR의 발견 사항

VFACE는 표면을 요청하지만 레이블 볼륨을 받는다

VFACE의 히트맵 경로는 이 도구를 세 개의 인수 scans, model, prediction_ID="Seg"만으로 호출하므로(SADT-VISOR tools/VFACE/src/sadt_vface/tools.py:359-364), export_formats는 기본값 ["NIFTI"]를 유지하고(SADT-VISOR __init__.py:22-24) 메시는 쓰이지 않는다(pipeline.py:342-354, mesh_export.py:187-189). 그러면 VFACE는 .vtk 또는 .vtp 파일만 찾아(heatmap.py:29, 194-204) 하나도 찾지 못하고 "No heat map could be drawn"로 끝난다(heatmap.py:246-251). 코드에서 읽었으며 실행하지는 않았다. 여기서 읽은 배포는 어차피 VFACE용 surface_model을 발행하지 않으므로(VISOR-serve server/deployment.toml:277-279), 그 서버의 패널에서는 이 경로에 닿을 수 없다.

도구의 README가 메시 내보내기와 메모리에 대해 낡았다

도구의 README는 "No vtk: the mesh exports are not ported"라고 말하며 이를 이식되지 않은 것으로 나열한다(tools/Batch_Dental_Seg/README.md:28, 95). pipeline.py의 docstring도 같은 말을 한다(SADT-VISOR pipeline.py:23-24). 코드는 그렇지 않다고 말한다. mesh_export.py는 STL, OBJ, VTK를 쓰고, export_formats는 인수이며(__init__.py:22-24), vtk 9.6.2는 의존성이다(pyproject.toml:23). 실제로 없는 것은 glTF뿐이다. README는 또한 GPU가 필요 없는 테스트를 38개로 세지만(README.md:267) 파일에는 테스트 함수가 55개 있다. 약 40 GiB보다 작은 카드에서는 UniversalLab에 gpu_resampling을 끄라는 조언(README.md:241-256, __init__.py:69-73에서 반복)은 커밋 d2fb0d8에서 마지막으로 고쳐졌다. 코드가 GPU 리샘플러와 함께 모든 번들에 설치하는 클래스별 리샘플러(nnunet_runner.py:185-188)는 그 뒤 c8899c8에서 왔으며, 그 docstring은 훨씬 낮은 최대 사용량을 알린다(low_memory.py:20-26). 여기서는 코드가 기준이며, 최대 사용량 자체는 이 페이지를 위해 측정하지 않았다.

..._Seg라는 이름의 스캔은 폴더에서 보이지 않는다

기본 식별자에서는 폴더 안의 patient_Seg.nii.gz가 이전 출력으로 간주되어 아무 메시지 없이 무시된다(SADT-VISOR pipeline.py:79-80, 104-105). scans로 전달된 단일 파일은 이름이 출력처럼 보여도 처리된다(pipeline.py:96-97).

GPU 리샘플링은 기본값으로 켜져 있고 숫자를 바꾼다

적용되면 입력 볼륨은 nnU-Net의 cubic spline 대신 GPU에서 linear 모드로 리샘플링된다. 코드는 이것이 수치 차이의 전부이며 gpu_resampling=false가 이를 끈다고 밝힌다(SADT-VISOR nnunet_runner.py:167-177). 보고서는 CUDA 장치에서는 요청된 값을, CPU에서는 false를 기록하며, plan이 거부하는 번들은 로그에만 언급된다(pipeline.py:374-378, nnunet_runner.py:163-165). 이 인수는 패널에서 숨겨져 있다.

cuDNN 자동 튜닝이 꺼져 있지 않다

BatchDentalSeg는 torch.backends.cudnn.benchmark를 결코 설정하지 않으며(패키지에 나오는 곳이 없다), nnU-Net의 예측기는 CUDA에서 이를 true로 설정한다(nnunetv2/inference/predict_from_raw_data.py:60-61, 도구 환경에 설치된 nnunetv2). AMASSS는 이를 명시적으로 끈다(SADT-VISOR AMASSS sadt_amasss/nnunet_runner.py:116). 도구의 README는 CUDA의 nnU-Net이 비트 단위로 결정적이지 않다고 말한다(README.md:113). 같은 스캔을 두 번 실행해서 비트 단위로 같은 마스크를 기대하지 말 것.

빈 내보내기 목록은 파일 없이 "ok"를 낸다(직접 호출만)

Python에서 직접 호출하면 run(..., export_formats=[])은 각 스캔을 ok로, 빈 produced 목록과 요약 "1/1 scan(s) segmented"와 함께 보고하며 아무것도 쓰지 않는다(SADT-VISOR pipeline.py:342-355, 362-386, mesh_export.py:187-189). 도구 자체는 목록을 검사하지 않는다. 서버를 통한 요청은 레이아웃이 최소 하나의 형식을 요구하므로 실행 전에 거부되며(layout.py:31-33, VISOR-serve server/base.py:855-858), 패널도 하나를 요구한다.

레이블별 파일은 NIfTI 형식에 의존한다

separate_segments는 레이블 볼륨을 나누므로 NIFTI가 선택되었을 때만 동작한다. 메시만 선택하면 상자를 체크했어도 이를 위해 아무것도 쓰이지 않는다(SADT-VISOR pipeline.py:339-350).

레이블 표는 결과와 함께 이동하지만 Slicer는 이를 읽지 않는다

보고서에는 전체 labels 표가 들어 있다(SADT-VISOR pipeline.py:364-371). Slicer 패널은 RUN_REPORT를 정의하지 않으며(기본값은 비어 있음: ServerToolsCoreLib/base_widget.py:1493) 레이블 볼륨을 단순한 loadLabelVolume으로 불러온다(slicer_io.py:560). 모듈의 주석은 색상 표를 말하지만(BATCHDENTALSEGRemote.py:79-82) 이를 적용하는 코드는 없다.

추론 호출 한 번: 진행률에는 끝이 둘이다

폴더 전체가 nnU-Net 호출 한 번으로 처리되므로, 진행 막대는 읽기(0~10 %)와 쓰기(90~100 %) 구간만 채우고 그 사이에는 중간값을 지어내지 않은 채 "segmenting N scan(s) in one pass"라고 표시한다(SADT-VISOR pipeline.py:269-274, 301). 이 호출에서 예외가 나면 임시 폴더를 정리한 뒤 배치 전체가 실패한다(pipeline.py:302-309).

확인됨: 읽을 수 없는 스캔이 배치를 멈추지 않는다

읽을 수 없는 스캔은 failed("could not be read")로 보고되고 나머지는 분할된다. 읽을 수 있는 스캔이 하나도 없을 때만 실행이 입력 오류로 멈춘다(SADT-VISOR pipeline.py:273-298).

쉬운 설명과 수식: 아틀라스 페이지.

9. 문헌

이 신경망들은 DentalSegmentator 계열이다. 참고문헌은 이 도구 자체의 것이므로 여기서 반복하지 않는다: BatchDentalSeg 출처, 그리고 레거시 페이지의 문헌 절. 매니페스트는 레거시 모듈이 내려받는 것과 같은 릴리스 URL을 가리킨다. DCBIA-OrthoLab 릴리스 세 개(VISOR-serve scripts/data-manifest.yml:542-581, legacy ADT/ADTLib/model_registry.py:59-64)와, DentalSegmentator의 경우 레거시 Resources/ML/download_info.json에 기록된 아카이브(data-manifest.yml:582-586)이다. 이 URL 뒤의 파일이 레거시 설치가 가져온 파일과 바이트 단위로 같은지는 코드만으로는 알 수 없다. 어느 쪽도 체크포인트의 해시를 기록하지 않기 때문이다.
