VISOR의 GreedyReg: 코드

개발자용: GreedyReg의 VISOR 이식판이 코드에서 하는 일을 file:line 참조, 시그니처, 인자, 환경, 레거시 코드와의 차이, 발견 사항과 함께 다룬다. 같은 파이프라인에 대한 읽기 쉬운 설명과 수식은 아틀라스 페이지에 있다. 레거시 모듈에는 별도의 코드 페이지가 있다.

VISOR 코드 아틀라스 (해설) 레거시 페이지 가이드 (VISOR)

VISOR에서 GreedyReg는 서버에서 실행되는 Python 패키지다. Slicer가 스캔이 든 폴더 두 개를 보내면, 서버가 환자별로 짝을 짓고, 쌍마다 Greedy를 두 번(아핀 탐색, 그다음 T2를 T1으로 리샘플링) 실행하여 결과를 돌려보낸다. Greedy는 더 이상 내려받는 바이너리가 아니라 picsl_greedy 패키지이며, 받는 명령은 플래그 하나하나까지 레거시의 것이다. 이 페이지는 SADT-VISOR(브랜치 tool/vface, 6ba2a78, 2026-09-30)의 이식판을 설명하며, VISOR-serve(e9a7e5d)가 이를 서비스하고 AutomatedDentalToolsRemote 확장(19b95e8)이 Slicer에서 이를 구동한다. 레거시 모듈은 별도의 페이지에 설명되어 있다. 부분적인 이식이다. 존재하는 것은 GreedyReg_CLI의 핵심이다. 두 폴더의 스캔을 환자별로 짝짓고, 선택적으로 마스크로 메트릭을 제한하며 초기 변환에서 시작하고, Greedy를 실행하고, 리샘플링한다. 수동 모드, 장면에서의 마스크 만들기, 바이너리 다운로드, Distant(랜드마크) 모드는 서버 도구에 없다. run()에는 이들 중 어느 것에 대한 인자도 없으며(SADT-VISOR GreedyReg/__init__.py:38-52), SADT-VISOR 어디에도 랜드마크 모드는 존재하지 않는다(git log --all -S"Landmark + Greedy"로 확인). README 자신의 "Not ported" 목록은 stdout 진행 프로토콜과 nibabel 설치 보호 장치만 꼽는다(README.md:60-64). 여기 있는 어떤 것도 배포된 서버를 주장하지 않는다.

이 페이지에서 참조를 읽는 방법

SADT-VISOR GreedyReg/pipeline.py:74는 6ba2a78 시점의 SADT-VISOR에서 tools/GreedyReg/src/sadt_greedyreg/pipeline.py다. 경로 없이 pipeline.py, __init__.py, layout.py만 적은 것은 같은 패키지이고, 경로 없이 README.md나 tests/…만 적은 것은 tools/GreedyReg/ 아래에 있으며, pairing.py는 tools/AREG/common/src/sadt_areg_common/pairing.py다. VISOR-serve server/…는 e9a7e5d 시점이고, AutomatedDentalToolsRemote …와 경로 없이 적은 GreedyRegRemote.py, test_greedyreg_client.py(GreedyRegRemote/ 아래)는 19b95e8 시점이다. 레거시 참조는 3c67957 시점의 SlicerAutomatedDentalTools 파일이다. GreedyReg_CLI.py는 GreedyReg_CLI/GreedyReg_CLI.py, GreedyReg.py는 GreedyReg/GreedyReg.py, Logic.py는 GreedyReg/GreedyReg_Method/Logic.py다.

4. 파이프라인, 단계별

쉬운 설명과 수식: 아틀라스 페이지.

run() 한 번의 호출이 코호트 전체를 환자별로 정합한다(SADT-VISOR GreedyReg/__init__.py:88-190).

4.1 T1과 T2 짝짓기 계산

쉬운 설명과 수식: 아틀라스 페이지.

선택지가 먼저 검사되므로, 잘못된 메트릭은 환자마다 하나가 아니라 하나의 오류다(__init__.py:92, pipeline.py:47-55). 그다음 pairing.pair(t1, t2, output_suffix)(__init__.py:102). 공유 규칙은 두 폴더를 재귀적으로 훑고, .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl을 받아들이며(pairing.py:36), 각 파일을 patient_stem으로 키를 정한다. 확장자, 이전의 ASO, AMASSS, ALI, AREG 실행이 남긴 접미사, 시점 토큰은 제거되고 하위 폴더는 접두사로 유지된다(pairing.py:175-211, 232-276). 이번 실행의 접미사가 붙은 이전 출력처럼 보이는 파일은 건너뛴다(pairing.py:214-229). 2026-11-09에 실행한 예: 01_T1.nii.gz는 01, Patient-01.nii.gz는 Patient_01, C_0001_T1_Or.nii.gz는 C_0001이 된다.

두 시점이 든 폴더는 거부되어, T1이 T1과 짝지어지는 일이 없다(pairing.py:336-358).

for label, root in (("T1", t1_root), ("T2", t2_root)):
    found = timepoints_in(root, accept)
    if len(found) > 1:
        raise ToolInputError(
            f"The {label} folder holds scans from more than one timepoint ..."

두 폴더 모두에 있는 환자가 없으면 양쪽에서 최대 열 개의 키를 나열하는 ValueError가 되며(__init__.py:112-122), 서버는 이를 422로 바꾼다.

4.2 마스크와 초기 변환 계산

쉬운 설명과 수식: 아틀라스 페이지.

_discover_masks는 마스크를 스캔과 같은 방식으로 키를 정하되, 이름이 마스크임을 말해 주는 파일에서만 구조 토큰(AREG 영역 토큰과 마스크 토큰)을 제거한다. 그래서 P1_T1_MAND_seg.nii.gz는 P1로 키가 정해지는 반면 MD_01이라는 환자는 이름을 유지한다(__init__.py:28-35, 207-228). _discover_transforms는 .mat 파일을 같은 방식으로 키를 정하고 transform을 제거하므로, 한 번의 실행에서 나온 변환을 다음 실행의 시작점으로 다시 넣을 수 있다(__init__.py:231-248). 어느 환자와도 맞지 않는 마스크와 변환은 보고서에 나열된다(__init__.py:131-135).

4.3 탐색의 시작점 계산

쉬운 설명과 수식: 아틀라스 페이지.

변환이 주어지면 Greedy는 그것을 그대로 시작점으로 삼는다(-ia, __init__.py:261-262). 그렇지 않으면 도구는 x 평행 이동을 살짝 비튼 레거시 항등 변환을 기록한다(pipeline.py:101-114, 레거시 GreedyReg_CLI.py:86-90).

matrix = np.eye(4)
matrix[0, 3] = 0.001

docstring이 이유를 밝힌다. Greedy는 정확한 항등 변환을 "초기화가 주어지지 않음"으로 읽는다(pipeline.py:102-106, Greedy의 동작이며 여기서 확인하지는 않았다). 마스크는 임시 폴더에서 0보다 큰 값으로 이진화되어 마스크 자신의 아핀을 가진 float32가 된다(pipeline.py:117-126, __init__.py:267-271). 마스크가 T1의 공간에 있는지 확인하는 것은 아무것도 없다.

4.4 두 번의 Greedy 호출 계산

쉬운 설명과 수식: 아틀라스 페이지.

아핀 탐색은 레거시 buildRegistrationCommand처럼 인자를 하나씩 쌓아 만든다(pipeline.py:74-94, 레거시 GreedyReg_CLI.py:104-125).

-d 3 -a -m NCC 4x4x4 | NMI | SSD   (4x4x4 is a radius: a 9x9x9 window)
-i <T1> <T2> -o <patient>_transform.mat
-n 100x100x50x25 -e 0.5 -search 100 10 20
-dof 6 | 12 -ia <init> [-gm <mask>]

T1은 고정 영상이고 T2는 이동 영상이다. -n은 다중 해상도 스케줄이고 -search는 그에 앞서 이루어지는 무작위 탐색이며, 둘 다 노출되지 않는다(pipeline.py:78-81). 알 수 없는 메트릭은 거부되는데, 레거시 CLI는 SSD로 넘어갔다(pipeline.py:58-71, 레거시 GreedyReg_CLI.py:107-112). 그다음 T2를 T1의 격자로 리샘플링한다(pipeline.py:97-98).

-d 3 -rf <T1> -rm <T2> <patient>_<suffix>.nii.gz -r <patient>_transform.mat

각 호출은 자식 인터프리터에서 실행되어, 이어 붙인 인자를 Greedy3D().execute에 넘기며 CASE_TIMEOUT_SECONDS = 600으로 제한된다. 0이 아닌 종료 코드는 Greedy 자신의 메시지를 담은 RuntimeError가 된다(pipeline.py:136-165).

_CHILD = """
import sys
from picsl_greedy import Greedy3D
Greedy3D().execute(" ".join(sys.argv[1:]), out=sys.stdout)
"""
finished = subprocess.run(
    [sys.executable, "-c", _CHILD, *[str(part) for part in command]],
    capture_output=True, text=True, timeout=timeout,
)

주석은 자식 프로세스의 이유를 설명한다. 프로세스 안에서 호출하면 레거시의 600 s 제한이 사라지게 되며, 서버는 자체 시간 제한을 두지 않는다(pipeline.py:129-135).

4.5 출력과 보고서 계산

쉬운 설명과 수식: 아틀라스 페이지.

쌍마다 압축되는 출력 폴더 아래에서 입력 트리를 그대로 따라 <patient>_<suffix>.nii.gz(항상 .nii.gz)와 <patient>_transform.mat이 만들어진다. 후자는 .tfm이 아니라 Greedy의 텍스트 행렬이다(__init__.py:254-259). 각 사례는 status, 파일 이름, 사용한 마스크와 초기 변환, transform_maps: "the T2 image -> the T1 frame (what greedy -r consumes)", 그리고 출력 폴더에 대한 상대 경로의 produced를 기록한다(__init__.py:143, 261-286). 실패하면 예외의 타입과 텍스트인 reason을 기록하며(__init__.py:157-167), 환자별 임시 폴더는 모든 경우에 제거된다(:168-170). 끝에는 summary와 duration_seconds가 있고(:173-178), 보고서는 적어도 한 쌍이 정합된 경우에만 기록된다(:180-189). 진행은 "n명 중 i번째 환자"이며, 파일 이름은 쓰이지 않는다(:141).

9. VISOR의 발견 사항

쉬운 설명과 수식: 아틀라스 페이지.

Slicer 클라이언트는 서버에 없는 도구를 설명한다

AutomatedDentalToolsRemote GreedyRegRemote/GreedyRegRemote.py:11-24(docstring)와 :50-57(도움말 텍스트)은 mode 인자(값은 Greedy, Landmark, Landmark + Greedy), landmark_model, 그리고 supervisor를 통해 닿는 두 번째 도구를 설명한다. 서버 도구에는 이 중 아무것도 없다. run()은 t1, t2, output_dir, masks, initial_transforms, metric, transform_type, output_suffix를 받으며(SADT-VISOR GreedyReg/__init__.py:38-52), 패키지에서 mode나 "landmark"를 검색해도 아무것도 나오지 않는다. GreedyRegRemote.py:76-77의 주석은 init 인자를 언급하지만, 실제 인자는 initial_transforms다. 클라이언트 테스트의 손으로 쓴 스키마는 mode, init, region, landmark_model(test_greedyreg_client.py:90-260)과 ALI_CBCT에 대한 calls 항목을 담고 있으므로, 그 22개 테스트는 서버가 아니라 픽스처를 검사한다. SADT-VISOR의 어떤 브랜치에도 랜드마크 모드는 없다(git log --all -S"Landmark + Greedy"가 비어 있다). Remote README.md:202,1056-1076은 예전의 세 가지 모드 설명을 반복한다. Landmark 모드가 계획 중인지 포기된 것인지는 알 수 없다.

마지막 상태 줄은 존재하지 않는 필드를 읽는다

_summarize는 {mode}를 report.get("mode")에서 서식에 넣고 len(report["cases"])를 센다(AutomatedDentalToolsRemote GreedyRegRemote/GreedyRegRemote.py:133-138). 보고서에는 mode가 없으므로(키는 인자와 스키마에 나열되어 있다), 상태 표시줄 메시지는 "GreedyReg finished in ? mode: N pair(s) registered."로 읽힌다. 또 cases에는 실패한 환자도 들어 있으므로(SADT-VISOR GreedyReg/__init__.py:166-171) N은 그들도 센다. 올바른 숫자는 summary.registered다.

파일 두 개는 쌍이 되지 않는다

클라이언트는 파일 두 개가 한 쌍이라고 말하며(GreedyRegRemote.py:75-77) 픽스처도 그에 맞게 t2를 설명한다. pairing.pair는 폴더를 훑는다(os.walk, pairing.py:232-276). a/P1_T1.nii.gz와 b/P1_T2.nii.gz로 2026-11-09에 실행했더니 아무것도 맞지 않았고, 도구는 이를 No patient appears in both the T1 and the T2 folder로 바꾼다(SADT-VISOR GreedyReg/__init__.py:112-122). 업로드된 단일 파일은 그 파일의 경로로 run()에 도달한다(VISOR-serve server/main.py:1288-1296). 도구의 테스트는 폴더만 쓴다. 서버를 통한 실행은 하지 않았다.

호스팅된 테스트 코호트는 제공된 그대로는 거부된다

서버가 GreedyReg용으로 호스팅하는 유일한 테스트 파일은 CBCT_T1_T2_pair이며(VISOR-serve scripts/data-manifest.yml:756-781), 모든 path 인자가 이를 제공한다(VISOR-serve server/registry/conventions.py:236-240, 이를 좁힐 [tools.GreedyReg] 섹션이 없다). 그 루트에는 T1/과 T2/ 폴더가 있다(준비된 사본에서 확인). pairing.pair는 시점이 둘 이상 든 폴더를 거부하며(pairing.py:336-358), GreedyReg는 스스로 T1/ 안으로 들어가지 않으며, pairing.timepoint_root를 호출하는 AREG_CBCT와 다르다. 준비된 사본의 파일 이름으로 2026-11-09에 실행한 결과: The T1 folder holds scans from more than one timepoint (T1, T2). T1/과 T2/를 각각 지정하면 C_0001이 짝지어진다. 패널에서 호스팅된 테스트 파일의 하위 폴더를 고를 수 있는지는 확인하지 않았다. 같은 관례가 masks와 initial_transforms에도 호스팅된 테스트 파일을 제공하는데, 이것들은 임상의 본인의 파일이다.

Greedy 호출만 제한되고 실행은 제한되지 않는다

각 Greedy 호출은 600 s로 제한되며(SADT-VISOR GreedyReg/pipeline.py:136,145) 한 쌍이 두 번 호출하므로(SADT-VISOR GreedyReg/__init__.py:273,276) 한 쌍은 최대 1200 s가 걸릴 수 있다. 쌍의 수에는 제한이 없고 서버도 제한을 두지 않는다(TOOL_TIMEOUT_SECONDS = 0, VISOR-serve server/config.py:77). VISOR-serve CLAUDE.md:896은 "per pair" 제한을 말하지만, 코드는 호출마다 제한한다.

아무것도 정합되지 않으면 보고서가 없다

모든 쌍이 실패하면 도구는 예외를 발생시키며(SADT-VISOR GreedyReg/__init__.py:180-187), 이는 GreedyReg_report.json을 기록하는 줄(:189)보다 앞선다. 그러면 이유는 오류 메시지로만 전달된다. 실패한 환자의 reason은 예외 텍스트다(:167).

만들어진 .mat은 Slicer 변환이 아니며, 마스크의 공간은 검사되지 않는다

<patient>_transform.mat은 Greedy가 -o로 기록하는 것이며(SADT-VISOR GreedyReg/pipeline.py:86, __init__.py:255), 패키지에는 이를 .tfm으로 변환하는 것이 없고 클라이언트도 이를 불러오지 않는다(GreedyRegRemote.py:97-104). 다중 레이블 마스크는 > 0으로 평탄화되며, 그것이 T1의 공간에 있는지 확인하는 것은 아무것도 없다(pipeline.py:117-126). 두 가지 모두 레거시 모듈의 것으로(레거시 페이지), 그대로 이어졌다. 코드에서 읽은 내용이다.

레거시 모듈과 다른 기본값

메트릭 기본값은 NCC이며 레거시 콤보는 NMI로 시작했고(SADT-VISOR GreedyReg/__init__.py:49, GreedyReg.py:575@3c67957), 변환은 기본적으로 Rigid이고, 접미사는 설정할 수 있다(output_suffix). 레거시 CLI는 _registered로 기록했다(GreedyReg_CLI.py:168@3c67957).

Greedy는 GPU를 쓰는 것으로 가정된다

도구는 device 인자를 선언하지 않으므로, 서버의 승인 단계는 모든 실행을 GPU 실행으로 취급하지만(VISOR-serve server/execution/dispatch.py:95-116) Greedy는 CPU에서 실행된다. 따라서 GreedyReg 실행이 쓰지도 않는 GPU 슬롯을 기다릴 수 있다. 코드에서 읽은 내용이다.

짝짓기와 실패가 명시적이다

짝이 없는 환자, 쓰이지 않은 마스크, 쓰이지 않은 초기 변환은 보고된다(SADT-VISOR GreedyReg/__init__.py:108,131-132). 실패하는 환자는 환자 한 명의 손실로 그치고, 메트릭과 변환 종류는 두 번 검증된다(pipeline.py:47-55). 패키지의 테스트 189개는 2026-11-09에 Greedy를 스텁으로 두고 통과했다.

10. 문헌
