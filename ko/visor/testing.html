테스트, 명명, 출처

VISOR 도구가 어떻게 구성되고, 테스트되고, 이름 붙여지고, 이식 원본인 레거시 코드까지 추적되는지, 그리고 지속적 통합(CI)이 무엇을 보장하고 보장하지 않는지. 저장소 자체 문서에 적힌 여러 규칙이 더 이상 코드나 CI와 맞지 않으며, 이 페이지는 어느 것이 그런지 밝힌다.

SADT-VISOR 6ba2a78 VISOR-serve e9a7e5d AutomatedDentalToolsRemote 19b95e8 레거시 ADT 3c67957
이 페이지를 읽는 방법

인용은 위에 적은 커밋 기준의 repository file:line 형식이다. SADT-VISOR는 도구의 저장소, VISOR-serve는 서버, Remote는 Slicer 클라이언트다. 테스트 수는 실행을 명시한 경우가 아니면 소스에서 센 것이다(def test_, 매개변수화된 케이스는 펼치지 않음). 이 페이지를 위해 실행한 것은 scripts/tests(89개 통과, 4개 건너뜀), naming/tests(26개 통과), scripts/run_tool.py --help, scripts/audit.py뿐이며, 도구 환경은 빌드하지 않았고 GPU 테스트도 실행하지 않았다. 이 아틀라스의 나머지 부분이 설명하는 것은 레거시 확장(커밋 3c67957)이며, 그 자체 테스트는 ADTLib 페이지에 있고 별개의 스위트다.

1. 도구의 구성

SADT-VISOR는 "one isolated Python project per SlicerAutomatedDentalTools tool"을 담고 있으며, 각각 자체 인터프리터, 자체 가상 환경, 자체 락파일을 갖고 도구끼리는 서로 import하지 않는다(SADT-VISOR README.md:3-5). 저장소에는 서버 코드가 없다(README.md:7-8). 도구는 다음을 담은 폴더다.

파일역할
pyproject.toml과 그 안의 [tool.sadt] 테이블tool = true와 name = "<ApiName>": 이 테이블이 폴더를 도구로 만들며, CI, 서버 레지스트리, 이미지 빌드 모두에 해당한다(CONTRIBUTING.md:50-59, 예시 tools/AMASSS/pyproject.toml:33-35)
src/sadt_<name>/__init__.py단 하나의 공개 함수 run(...)을 정의한다. 기반 클래스도, 레지스트리도 없다(README.md:41-58)
uv.lock커밋됨. CI는 --frozen으로 동기화하며, 락이 낡았으면 실패한다(CONTRIBUTING.md:603)
tests/test_run.py, tests/test_integration.py아래의 두 테스트 수준. tools/_template/은 복사해서 쓰는 뼈대다
README.md"Provenance" 블록을 포함(4절)

폴더 이름이 API 이름이다(도구의 가상 환경은 <TOOLS_DIR>/<name>/.venv/bin/python에서 찾으며, CONTRIBUTING.md:70-77). 두 개의 그룹 폴더 tools/ALI/와 tools/AREG/는 엔진(ALI_CBCT, ALI_IOS, AREG_CBCT, AREG_IOS, AREG_IOSCBCT)과 common/ 패키지를 담는다. 공유 패키지는 pyproject.toml을 가지되 [tool.sadt]는 없다. 설치는 가능하지만 발견되지도 제공되지도 않는다. [tool.uv.workspace]는 없다. 하나의 공통 락이 torch 1.13과 2.4를 같은 해석에 밀어 넣게 되기 때문이다(CONTRIBUTING.md:578-583). [tool.sadt]를 선언하는 열아홉 개의 폴더: Agent, ALI_CBCT, ALI_IOS, AMASSS, AREG_CBCT, AREG_IOS, AREG_IOSCBCT, ASO, AutoCrop3D, AutoMatrix, Batch_Dental_Seg, CLIC, CNE, Crown_Seg, DOCShapeAXI, FlexReg, GreedyReg, Surg_Mov_Pred, VFACE(CI와 같은 find로 센 것).

클라이언트가 렌더링하는 스키마는 손으로 쓰지 않는다. scripts/describe.py가 run()의 시그니처에서 이를 도출한다. 허용되는 주석은 Path, str, int, float, bool, Literal[...], 이들의 list[...], 그리고 tuple[float, float](vec2로 공개됨)이며, Optional도, 유니언도, None 기본값도 없다(describe.py:38-46,193-296). 모든 인자는 docstring의 Args: 블록에 한 줄이 있어야 한다(describe.py:807-841). 표현할 수 없는 것은 stdout에 아무것도 내지 않고 종료 코드 2로 끝난다(:1185-1187). 예전에 손으로 관리하던 "ArgSpec" 표는 "drifted"했기 때문에 폐기되었다(describe.py:8-11).

2. 테스트의 세 수준

1수준: 프로세스 안, 합성 입력

tests/test_run.py는 19개 도구 각각과 템플릿에 있다(공유 패키지인 AREG/common에는 없다). 규칙은 run()을 끝까지 호출하고, 예상 파일이 존재하며 크기가 그럴듯하고 문서화된 허용 오차 안에서 기준과 일치하는지 확인하는 것이다(CONTRIBUTING.md:605-609). 실제로는 픽스처가 테스트 안에서 만들어진다. 한 변이 8, 16 또는 48 복셀인 SimpleITK 볼륨, 삼각형 세 개짜리 VTK 메시, 일곱 점짜리 두개골, .npy 배열, 즉석에서 적합시킨 scikit-learn 모델, 그리고 스텁으로 대체한 nnU-Net 또는 shapeaxi 엔진이다(tools/AMASSS/tests/data/README.md:1-9, tools/ASO/tests/data/README.md:1-9, tools/AREG/TESTING.md:3-12). 도구별 개수(def test_): Agent 206, ALI_IOS 183, AREG_IOSCBCT 172, VFACE 164, Crown_Seg 162, GreedyReg 158, ASO 145, AutoMatrix 139, CNE 130, CLIC 124, Surg_Mov_Pred 105, AutoCrop3D 103, AREG_CBCT 94, DOCShapeAXI 91, ALI_CBCT 66, AMASSS 61, AREG_IOS 56, Batch_Dental_Seg 55, AREG/common 40, FlexReg 21, 템플릿 17.

2수준: 프로세스 밖, testkit 사용

testkit/(패키지 sadt-testkit)은 run_tool(name, **params)(sadt_testkit/__init__.py:192), tool_schema(:248), is_built(:152)와 예외 ToolNotBuilt, ToolFailed를 제공한다. 이것은 도구를 자체 인터프리터에서 중립적인 작업 디렉터리에서, "a miniature of the server's runner"인 표준 라이브러리 전용 드라이버로 시작한다(주석에 따른 같은 강제 변환, 같은 결과 파일, 같은 예외 클래스 이름, _driver.py:1-16). 밖에서만 드러나는 것을 확인하기 위해 존재한다. 도구가 output_dir 밖에는 아무것도 쓰지 않는지, 공개된 스키마가 시그니처와 일치하는지다. 규칙은 다른 도구가 빌드되지 않았을 때 실패가 아니라 건너뛰기다(CONTRIBUTING.md:629-632). Agent, ALI_CBCT, AREG_IOSCBCT, ASO, VFACE와 템플릿이 각각 파일 하나씩으로 사용한다. ASO의 LocalSup은 서버의 supervisor를 대신하도록 run_tool을 감싼 열두 줄 정도의 코드다.

3수준: 실제 데이터, CI에서는 절대 실행하지 않음

실제 모델과 스캔에 대한 테스트는 gpu와 models 마크를 달고 있으며, 파일은 배포의 DATA/에서 오고 환경 변수(SADT_AMASSS_MODELS, SADT_AMASSS_SCAN, SADT_ALI_CBCT_MODELS, SADT_CROWNSEG_MODEL, SADT_SURGMOVPRED_MODELS, SADT_CLIC_MODEL 등)로 이름이 지정된다. CI는 러너에 CUDA 장치가 없으므로 gpu를 제외하며, 저장소는 이것이 그 테스트를 작성자의 책임으로 만든다고 말한다. 직접 실행하고 결과를 풀 리퀘스트에 명시하라(CONTRIBUTING.md:638-640). 여덟 개 도구는 addopts = "-m 'not gpu and not models'"도 설정하며(Agent, CLIC, CNE, Surg_Mov_Pred, Crown_Seg, VFACE, AREG_IOSCBCT, ALI_IOS), -m models -o addopts=로 덮어써야 한다. 환자 데이터는 절대 커밋되지 않는다. CONTRIBUTING.md:611-614는 "a download script plus checksums"를 요구하지만 download.sh나 *.sha256은 존재하지 않는다. 각 tests/data/README.md는 "Nothing is committed here"라고 하며 환경 변수나 VISOR-serve의 모델 매니페스트를 가리킨다.

CI가 실행하는 것

워크플로 하나, .github/workflows/ci.yml(105줄)이며, 풀 리퀘스트와 main으로의 푸시에서 실행된다.

작업하는 일보장하는 것
discover (:16-36)두세 단계 아래의 모든 pyproject.toml 중 [tool.sadt]를 포함하는 것을 찾는다매트릭스는 디스크에서 읽는다. 도구를 추가해도 CI를 고칠 필요가 없다. 서버 레지스트리, Dockerfile과 같은 규칙이다. _template과 공유 패키지는 제외된다
tool(:38-74), 도구마다 작업 하나(19개), fail-fast: falseuv sync --frozen, 도구 자체 인터프리터에서 describe.py, pytest -m "not gpu"락이 pyproject.toml과 일치한다. 도구가 CUDA 스택 없이 import되고 시그니처로 스키마가 만들어진다("a schema the client cannot render never reaches main"). GPU를 쓰지 않는 스위트가 통과한다
scripts (:76-88)pytest scripts/tests, 그다음 scripts/audit.pydescribe.py, run_tool.py, audit.py, 그리고 벤더링된 사본의 테스트(이 페이지를 위해 실행했을 때 89개 통과, 4개 건너뜀). audit.py는 읽기 전용 보고서이며 작업을 실패시키지 않는다
testkit (:93-105)tools/_template을 빌드한 다음 testkit 자체의 스위트를 실행한다모든 통합 테스트가 신뢰하는 하니스 자체도 테스트된다

CI가 실행하지 않는 것

  • gpu 마크가 붙은 테스트는 -m "not gpu"로 제외된다(ci.yml:66-74).
  • 도구 간 통합. 각 도구에 자체 작업이 있어 다른 도구의 가상 환경이 존재하지 않으므로 테스트가 스스로 건너뛴다(ci.yml:69-70, is_built). ASO에서 ALI로, AREG에서 ASO로, VFACE에서 AREG로 이어지는 체인은 CI에서 한 번도 실행되지 않는다.
  • naming/의 테스트 26개, tools/AREG/common/tests/의 테스트 40개(둘 다 [tool.sadt]가 없어 매트릭스에 들어가지 않으며 이를 실행하는 다른 작업도 없다), 그리고 ALI의 common은, pyproject.toml이 testpaths = ["tests"]를 선언하는데도 테스트가 아예 없다.
  • pyflakes 검사는 CONTRIBUTING.md:681-685가 PR 전에 요구하지만, 워크플로에는 나타나지 않는다.
  • torch 또는 MONAI 버전 사이의 수치 재현성에 관한 모든 것. 이는 각 도구 README의 수동 검증에 맡겨져 있다.
명령줄이 덮어쓰는 마크

addopts가 models를 제외하는 여덟 개 도구는 CI에서 -m "not gpu"로 실행된다. 이를 확인하려고 만든 임시 pytest 프로젝트에서는 명령줄로 준 -m이 addopts에 있는 것을 대체했고, 그래서 models 테스트가 수집되었다. 그러면 환경 변수에 대한 자체 skipif로만 건너뛰게 된다. mark.models 사용 25건 중 9건은 네 줄 안에 skipif가 뒤따랐고(대략적인 집계), 각각이 CI에서 건너뛰는지는 하나씩 확인하지 않았다. 실제 CI 실행에서는 관찰되지 않았다.

3. 명명: sadt_naming

"Naming"은 두 가지를 다룬다. 도구의 API 이름은 [tool.sadt] name에서, 없으면 폴더에서 온다. 약어는 그대로 두고(ALI, AMASSS), 단어는 대문자로 시작해 _로 이어 붙이며(Batch_Dental_Seg), Python 패키지는 소문자로 유지한다(CONTRIBUTING.md:61-65,81-89). 이름을 바꾸는 것은 모든 클라이언트에 대한 호환성 파괴 변경이다(:91-93). describe.py는 [tool.sadt] name을 읽지 않는다는 점에 유의하라. 공개되는 name은 폴더 이름이다(describe.py:1157).

파일 이름의 어휘는 naming/ 패키지(sadt_naming)이며, 표준 라이브러리만 쓴다(dependencies = [], naming/pyproject.toml:3-12). 여기에는 확장자 계열(여섯 개 확장자를 가진 VOLUME은 .nii.gz가 .gz보다 우선하도록 먼저 구성되고, SURFACE, MARKUPS, TRANSFORM, NOTES, TABLE), 도구가 덧붙이는 열세 개의 출력 마커(_lm_Pred, _Scanreg, _MERGED, _OutReg, _SegOr, _SegOut 등, 전체 토큰으로 대소문자를 구분해 매칭됨), 열세 개의 턱 표기(u up upper maxilla max mx l low lower mandible mand md와 프랑스어 변형), 그리고 시점 t0 t1 t2가 들어 있다(naming/src/sadt_naming/__init__.py:36-175). UpperT1을 턱과 시점으로 나누고(:217), 이름을 첫 마커에서 자르되 마커로 시작하기만 하는 이름은 결코 자르지 않는다(:252).

26개 테스트(naming/tests/test_naming.py, 이 페이지를 위해 실행했을 때 26개 통과)가 이를 고정한다. 복합 확장자, ITK에는 .nrrd.gz 기록기가 없어서 .nrrd로 다시 쓰이는 .nrrd.gz, 모듈이 os 외에는 아무것도 import하지 않는다는 "contract"(도구는 표를 고치는 것이 아니라 덜 선언하는 방식으로 제한한다), patient1이 Lower가 아니라 턱 없음으로 읽히는 것, MAXILLOFACIAL_03이 상악으로 읽히지 않는 것, P_Seg1_T1이 P_Seg2_T1과 구별되는 것이다. 알려진 두 가지 한계는 그대로 고정되어 있다. MAX_01은 상악으로 읽히고 T1Upper는 읽히지 않는다. 이 26개 테스트는 어떤 CI 작업에서도 실행되지 않는다(앞 절).

누가 사용하는가. 세 도구가 여기에 의존한다. AMASSS, ASO, Batch_Dental_Seg이다(sadt-naming = { path = "../../naming" }, 각 pyproject.toml 안). 누가 표를 깨끗하게 유지하는가. 아무도 구현들을 서로 비교하지 않는다. "patient key"는 적어도 네 번 더 존재한다. ASO 자체의 PATIENT_SUFFIXES(tools/ASO/src/sadt_aso/cbct/pipeline.py:34-48), AREG의 catalogs.py:158, pairing.py:175(patient_stem), ALI의 확장자 목록(ALI/common/.../discovery.py), AutoMatrix의 patient_of(pipeline.py:33)이다. sadt_naming의 docstring은 턱과 시점 규칙을 세 번째 해석을 피하려고 sadt_areg_common.pairing에서 가져왔다고 인정한다(:203-207). 드리프트에 대한 방어는 대신 중복된 경계 테스트로 이루어진다. ASO에 23개, AREG/common에 27개, 실제 이름 400개 이상의 특성화 표(테스트 3개, 수정으로 결과가 달라진 행은 # WAS:로 표시), 그리고 페어링 테스트 10개다. 두 개의 벤더링된 파일은 바이트 단위로 동일해야 하며, progress.py(사본 14개)와 scans.py(사본 2개)이고, 테스트가 이들의 SHA-256 해시를 비교한다(scripts/tests/test_vendored_copies.py:27). 이 테스트는 CI의 scripts 작업에서 실제로 실행된다.

기여 규칙은 왕복 테스트도 요구한다. 자신의 출력을 자신의 입력 규칙으로 읽어 보는 것이다(CONTRIBUTING.md:384-427). 계기가 된 사례는 Upper_new_9.vtk와 Upper_new_9_Upper_O_Pred.json이며, ASO의 반자동 IOS 모드가 이를 두 명의 환자로 읽었다.

5. 서버 계약과 낡아 버린 것

docs/SERVER_CONTRACT.md는 서버가 도구에 기대하는 것을 설명한다. 발견, 호출, 서버로 옮겨진 작업(상한이 있는 압축 해제, GPU 승인, output_dir의 소유권, 모델 해석), 예외 클래스 이름에 의한 오류 매핑, 체인이다. 헤더는 커밋되지 않은 작업이 있는 VISOR-serve 10be711에 대해 "re-checked against the server, 2026-08-18"이라고 한다(:8-12). 그 뒤로 이 문서의 여러 진술과 README.md 및 CONTRIBUTING.md의 일부가 더 이상 코드와 맞지 않는다.

6. 클라이언트의 테스트

Slicer 클라이언트(Remote)에는 12개 스위트에 걸쳐 1484개의 unittest 테스트가 있으며, 이 아틀라스를 위해 실행했을 때 모두 통과했다(Qt, CTK, Slicer를 스텁으로 대체한 unittest만). ServerToolsCore/Testing/Python에 1047개(파일 22개, Qt, CTK, Slicer를 대신하는 qt_stubs.py 포함, test_transfer.py와 test_run_progress.py는 조각을 떨구고 틀린 합계를 보내는 적대적 테스트 서버에 대해 실제 소켓을 사용), SlicerCloud에 83개(실제 하위 프로세스), VISU에 140개, 그리고 대부분의 모듈 래퍼에 각자의 스위트가 있다(예를 들어 ASO 44, AREG 32, AutoMatrix 25, GreedyReg 22, CNE 16). 일부 모듈에는 하나도 없다. AMASSS, CLIC, Batch_Dental_Seg, VFACE, SurgMovPred, Crown_Seg, ExampleTool, Medical Data Anonymizer, Agent이다.

7. 벤치마크는 테스트가 아니라 측정이다

VISOR-serve benchmarks/는 함께 제공되는 논문의 시간 수치를 재현한다(캠페인 B1 지연 시간, B2 네트워크 단계, B3 supervisor 비용, B4 동시성, B5 로컬 경로와 HTTP 경로 사이의 바이트 일치). 기록된 실행은 2026년 8월의 것이며, 도구의 8월 코드에서 "dirty"로 표시된 작업 트리로 실행되었고, 요약은 B1, B3, B4에만 있다. 이것들은 아무것도 검증하지 않으며 일치 주장도 끌어낼 수 없다. 마지막 B5 세션에서 같은 경로 대조군은 대부분의 도구가 자기 자신과도 바이트 단위로 재현되지 않음을 보여 주었고(보고서에 소요 시간과 경로가 들어 있기 때문), 두 경로 사이에서 완전히 일치한 것은 AREG_IOSCBCT뿐이었다. 수치와 그 한계는 배포 페이지에 있다.
