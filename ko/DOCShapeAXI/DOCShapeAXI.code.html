DOCShapeAXI, 레거시: 코드

개발자용: 레거시 Slicer 모듈이 코드에서 하는 일을 file:line 참조, 시그니처, 표, 함정과 함께 다룬다. 같은 파이프라인에 대한 읽기 쉬운 설명은 수식과 함께 아틀라스 페이지에 있다.

코드 아틀라스 (해설) Prieto 2024 · SPIE DOCShapeAXI_CLI conda 환경: shapeaxi VISOR 참고문헌

Dental Oral and Craniofacial Shape Analysis eXplainability and Interpretability. 사용자 동작은 하나다. 데이터 유형, 입력 폴더, 출력 폴더를 고른다. 나머지 모두, 즉 어떤 체크포인트, 어떤 아키텍처, 클래스 수는 데이터 유형에서 추론된다.

두 코드 베이스

아래에 번호가 붙은 모든 내용은 레거시 Slicer 모듈(3c67957 시점의 SlicerAutomatedDentalTools, 2026-10-26)을 설명한다. 같은 도구를 서버에서 실행하는 VISOR 포팅은 별도 페이지 VISOR의 DOCShapeAXI에서 설명한다. 아래 콜아웃 중 VISOR에서 더 이상 맞지 않는 것은 제목에 그렇게 적혀 있다.

3. 입력과 전처리

쉬운 설명과 수식: 아틀라스 페이지.

3.1 CSV

CLI는 args.input_dir를 평탄하게 나열하여 .vtk 파일만 남기고, <output_dir>/files_<data_type>.csv를 쓰며, 헤더는 surf이고 한 줄에 파일 이름 하나를 담는다(csv_edit, DOCShapeAXI_CLI.py:105). 경로는 상대 경로이며, SaxiDataset이 mount_point = input_dir로 이를 잇는다.

data_type에는 공백이 들어 있어서("Mandibular Condyle") csv의 이름은 files_Mandibular Condyle.csv가 된다. csv는 이미 존재하지 않을 때만 다시 만들어진다(DOCShapeAXI_CLI.py:285). 출력 폴더를 비우지 않은 채 입력 폴더에 메시를 추가하면 그 메시는 처리되지 않는다.

3.2 기하 정규화

쉬운 설명과 수식: 아틀라스 페이지.

EvalTransform → UnitSurfTransform → utils.GetUnitSurf → ScaleSurf:

  1. 중심 = 바운딩 박스의 중점(무게중심이 아니다).
  2. 점들을 이 중심으로 평행 이동한다.
  3. 스케일 인자 1 / ||bounds_max - center||, 균일하게 적용된다.

따라서 메시는 실제 크기와 무관하게 단위 구 안에 들어간다. 절대 스케일 정보는 모두 사라진다. 모양이 같은 작은 하악과두와 큰 하악과두는 네트워크에게 동일하다.

확인된 버그 (shapeaxi 패키지, 레거시 모듈에 설치된 대로)

날짜 기재: 이 내용은 shapeaxi 1.0.10(Slicer 5.12.3의 shapeaxi 환경에 설치된 사본)과 1.1.1(이번 점검을 위해 내려받음. __about__.py를 제외하면 두 패키지는 바이트 단위로 동일하다)에서 읽었고, 변환은 2.0.2와 2.0.3에서도 같다. VISOR 도구는 데이터셋을 같은 방식으로 만들어 두 패스 모두에서 scale_factor를 EvalTransform에 넘기며(SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/engine.py:25-28), 고정된 shapeaxi==1.1.1(pyproject.toml:30)을 쓴다. 1.1.1도 이 값을 무시한다. 그 saxi_transforms.py는 1.0.10의 것과 동일하다(VISOR의 DOCShapeAXI). 알아 둘 점: saxi_predict는 model.hparams.scale_factor(condyles 체크포인트에서 0.0507)를 읽어 EvalTransform(scale_factor)에 넘기지만(DOCShapeAXI_CLI.py:209), UnitSurfTransform.__call__(saxi_transforms.py:48-57)은 utils.GetUnitSurf(surf)를 호출하는데, 입력이 vtkPolyData일 때 이를 전달하지 않는다. 따라서 학습 시점에 학습된 스케일 인자는 추론에서 조용히 무시되고 대상별 정규화로 대체된다. 이것은 저장소가 아니라 shapeaxi 패키지의 버그이지만 실제 전처리를 바꾼다. 그런데 saxi_gradcam은 인자 없이 EvalTransform()으로 데이터셋을 만들므로, 두 패스는 서로 일관된 상태가 된다.

3.3 DataLoader가 돌려주는 것

SaxiDataset(..., CN=True, class_column=None, scalar_column=None) → 대상마다 (V, F, CN):

  • V: 정규화 후 정점 (1, Nv, 3),
  • F: 삼각형 (1, Nf, 3),
  • CN: 색으로 인코딩된 법선, utils.ComputeNormals 후 GetColorArray(surf,"Normals")를 255로 나눈 것 → [0,1] 범위의 (1, Nv, 3).

메시 스칼라는 전혀 읽히지 않는다(surf_property=None). 기하와 법선만 들어간다. batch_size=1이고 패딩이 없으므로 크기가 다른 메시도 문제없이 통과한다.

4.2 실제로 쓰이는 아키텍처

쉬운 설명과 수식: 아틀라스 페이지.

이것은 PointNet이 아니며, 원래 ShapeAXI 논문의 ResNet-18 fly-by-CNN도 아니다. SaxiMHAFBClassification(MHA Fly-By)은 나중에 융합되는 두 갈래를 가진다.

확인됨 (레거시 체크포인트, VISOR에서도 같은 파일)

VISOR-serve의 데이터 매니페스트는 같은 shapeaxi-ckpt-v1 릴리스의 같은 체크포인트 다섯 개를 나열하며(scripts/data-manifest.yml:597-614), 도구의 카탈로그는 같은 네트워크 클래스를 키로 삼는다(catalog.py:24-25,50-71). 아래 값들은 VISOR 사본에서 다시 측정하지 않았다(VISOR의 DOCShapeAXI). 아래 값들(K=128, 256 헤드, 42 뷰, image_size=224…)은 hyper_parameters와 ico_verts 버퍼를 이전에 읽어서 확인한 것이며, 대상은 condyles_4_class.ckpt 체크포인트다. 이번 점검에서는 그 읽기를 반복하지 않았다(머신에 .ckpt가 없다). 같은 숫자는 코드의 기본값이기도 하다(saxi_nets_lightning.py:2392-2405, shapeaxi 1.0.10).

갈래 A: 포인트 클라우드.

  • sample_points_from_meshes(X_mesh, 4096)(pytorch3d): 표면에서 4096개 점을 균일하게 샘플링한다.
  • MHAEncoder: Linear(3→256), 그다음 sample_levels = [4096, 2048, 512, 128]의 4단계. 각 단계에서 MHA_KNN(K=128개 최근접 이웃으로 제한된 멀티헤드 어텐션, 헤드 256개), 그다음 잔차 FeedForward(hidden 64). 단계 사이에서는 다음 수준까지 무작위로 부분 샘플링하며, 인덱스를 앞으로 전달하여 원래 점마다 가중치를 누적한다(x_w).
  • Linear(256→256), FeedForward, 그다음 SelfAttention(가법 어텐션 Linear(256→64) → tanh → Linear(64→1) → sigmoid, 정규화 후 가중합)이 128개 토큰을 하나의 256 벡터로 줄인다.

갈래 B: 멀티뷰.

  • 세분화된 정이십면체의 꼭짓점에 놓인 카메라(subdivision_level=2, radius=1.35: --radius의 기본값, saxi_nets_lightning.py:2396. 실제로 쓰이는 반지름은 체크포인트에서 읽는 self.hparams.radius이고, :2371, 다시 읽을 체크포인트가 없었다). 체크포인트의 ico_verts 버퍼는 모양이 (42, 3)이다. 대상마다 42개 뷰다.
  • pytorch3d 렌더링: FoVPerspectiveCameras, 원점을 향한 look_at_rotation, AmbientLights(방향성 음영 없음), HardPhongShader, RasterizationSettings(image_size=224, blur_radius=0, faces_per_pixel=1, max_faces_per_bin=200000).
  • 각 뷰는 4채널 텐서다. RGB(TexturesVertex로 설정된 색 인코딩 법선) 에 z-버퍼를 더한 것이다. 따라서 in_channels=4다.
  • MONAI의 TimeDistributed(EfficientNetBN('efficientnet-b0', spatial_dims=2, in_channels=4, num_classes=256)): 42개 뷰를 배치 차원으로 펼쳐 같은 CNN에 통과시키고, 다시 (1, 42, 256)으로 reshape한다.
  • FeedForward, 42개 뷰에 대한 셀프 어텐션으로서 nn.MultiheadAttention(256, 256 heads, batch_first=True), 그다음 SelfAttention → 256 벡터.

융합. torch.cat([x_points, x_views], dim=1) → 512, 그다음 fc = Linear(512, num_classes). 회귀에서는 Linear(512, 1)과 MSE 손실이다.

렌더링은 매 패스마다 다시 수행된다. 이미지 캐시는 없다.

4.3 네트워크가 문자 그대로 출력하는 것, 그리고 거기서 클래스를 도출하는 방법

x = model(X_pc, X_views)                       # (1, num_classes), raw logits
if args.nn == 'SaxiMHAFBClassification':
    x = softmax(x).detach()
    x = torch.argmax(x, dim=1, keepdim=True)   # the class integer
predictions.append(x)

(DOCShapeAXI_CLI.py:230-235)

  • 분류: argmax만 남는다. softmax 확률은 계산된 뒤 버려지며, 어떤 신뢰도 측정값도 모듈 밖으로 나가지 않는다.
  • 회귀: Linear(512,1)의 원시 값이 그대로 쓰인다(폐쇄 비율, 학습 시점에는 0–100 척도).
  • 어차피 softmax는 argmax에 영향을 주지 않는다.

업스트림 코드에서 볼 수 있는 학습 세부 사항: 분류에서 타깃은 원-핫이 아니라 소프트 클래스 확률이다(soft_class_probabilities: [12.5, 37.5, 62.5, 87.5]를 중심으로 한 가우시안, widths = 12.5). 따라서 4개의 중증도 클래스는 실제로는 0–100 척도의 연속량의 사분위수이며, 같은 기도 데이터셋에 회귀 모델이 존재하는 이유를 설명해 준다.

5. 설명 가능성 메커니즘

쉬운 설명과 수식: 아틀라스 페이지.

참고(레거시 전용)

레거시(3c67957). VISOR에는 없다. explain: bool = True는 끌 수 있는 인자다(SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/__init__.py:22,93-95. VISOR의 DOCShapeAXI 참고). 이것은 모듈에서 가장 두드러진 부분이며 예측 뒤에 체계적으로 실행된다. 옵션도 체크박스도 아니다(saxi_gradcam, DOCShapeAXI_CLI.py:129).

a) 대상 층.

target_layer = getattr(model.convnet.module, '_blocks')
mv_cam = LayerGradCam(model, target_layer[-1], device_ids=[0])

model.convnet.module은 EfficientNet-B0이고, _blocks[-1]은 그것의 마지막 MBConv 블록이다.

함정(VISOR에서도 마찬가지)

VISOR에서도 마찬가지다. LayerGradCam(model, blocks[-1])를 model.convnet.module._blocks에 적용한다(SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/engine.py:82-83. VISOR의 DOCShapeAXI 참고). 중대한 결과: 현저성은 멀티뷰 갈래만 설명한다. 융합 벡터의 절반을 기여하는 포인트 클라우드 갈래는 맵 어디에도 나타나지 않는다. 인코더가 만들어 낼 수 있는 x_w(점별 가중치)는 가져오지도 기록하지도 않는다.

b) 클래스마다 맵 하나. for class_idx in range(num_classes) 루프에서 mv_cam.attribute(inputs=(X_pc, X_views), target=class_idx, attr_dim_summation=False)를 호출한다. Captum은 클래스 class_idx의 로짓을 블록의 활성화까지 역전파하고, 평균 그래디언트를 곱하여, 활성화 맵의 해상도(224×224에서 EfficientNet-B0의 경우 7×7)의 텐서를 돌려주며, 이는 42개 뷰 전체에 대해 한 번에 이루어진다. attr_dim_summation=False는 채널 차원을 유지하며, 이는 곧바로 mv_att.sum(dim=1)로 합쳐진다.

c) 재조정(scale_cam_image, DOCShapeAXI_CLI.py:46, pytorch-grad-cam에서 가져와 변형함): cv2.resize로 224×224로 키우고, 1번째와 99번째 백분위수에서 클리핑한 뒤, [-1, 1]로 아핀 변환한다. 백분위수 클리핑은 이상값 픽셀 하나가 전체 동적 범위를 삼키는 것을 막는다. 따라서 출력은 확률이 아니라 부호가 있는 값이다. 변환은 가드 없이 클리핑된 맵의 max - min으로 나눈다(DOCShapeAXI_CLI.py:58). 값이 모두 같은 맵은 0/0이 되어 표면이 NaN 값을 받게 된다. VISOR는 이 가드를 추가했다(SADT-VISOR pipeline.py:192-197).

d) 메시로의 재투영(gradcam_process, shapeaxi 안. 1.0.10의 saxi_gradcam.py:112-144에서 읽었으며 1.1.1에서도 동일), 메커니즘의 핵심:

P_faces = torch.zeros(1, F.shape[1])
V_gcam  = -1 * torch.ones(V.shape[1])
for pf, gc in zip(PF.squeeze(), GCAM):          # one view at a time
    P_faces[:, pf] = torch.maximum(P_faces[:, pf], gc)
faces_pid0 = F[0, :, 0].to(torch.int64)
V_gcam[faces_pid0] = P_faces
V_gcam[V_gcam < 0] = 0
  • PF는 래스터라이저의 pix_to_face다. 모든 뷰의 모든 픽셀에 대해 보이는 삼각형의 인덱스이며, 배경은 -1이다(saxi_nets_lightning.py:2455-2456). 픽셀의 값은 면으로 되돌려진다.
  • 면은 0에서 시작하고 갱신은 maximum(old, new)이므로, 뷰들에 걸친 집계는 평균이 아니라 최댓값이며 음수 값은 결코 살아남지 못한다. 메시에서 범위는 [0, 1]이므로 면의 값은 max(0, max over views)이지 max s가 아니다. 한 번 보이고 현저하다고 판단된 영역은 그 값을 유지한다.
  • 하나의 뷰 안에서 많은 픽셀이 같은 면을 보여 준다. P_faces[:, pf] = ...는 그다음 반복된 인덱스를 통해 대입하는데, PyTorch는 어느 쓰기가 유지되는지 말하지 않는다. 픽셀들에 대한 최댓값이 아니다. torch 2.12.1로 CPU에서 시험했다(인덱스 [0,0,0,1,-1,-1], 값 [.9,.1,.5,.3,.8,.2]). 면 0은 0.9가 아니라 세 픽셀 중 마지막인 0.5로 끝났다. 순서가 보장되지 않는 GPU에서는 시험하지 않았다.
  • -1 픽셀에 대해서는 같은 인덱싱이 모든 뷰에서 메시의 마지막 면에 쓴다(Python의 음수 인덱스). 그 면의 값은 배경이 쓴 것이 무엇이든 그것이다. 같은 시험에서 마지막 면이 덮어쓰이는 것이 확인되었다(0.2). 메시 전체에서 면 하나뿐이다.
  • 면에서 정점으로 가는 단계는 조잡하다. 각 면의 값은 그 첫 번째 정점에 쓰인다(F[0,:,0]). 여러 면의 첫 정점인 정점은 그 값들 중 하나를 유지한다(다시 반복된 인덱스). 삼각형의 첫 번째 점이 된 적이 없는 정점은 -1로 남았다가 마지막 줄에서 0으로 재설정된다. 따라서 맵에는 구조적인 0이 흩어져 있다.
  • 래스터화되지 않는 면(내부, 영구적인 가림)은 0으로 남는다.

버전 참고. 설치 프로그램이 오늘 가져오는 shapeaxi 2.0.2와 2.0.3(shapeaxi>=2.0.2)은 마지막 줄이 없는 같은 함수를 가지고 있다(2.0.2의 saxi_gradcam.py:31-62: V_gcam[V_gcam<0]=0이 없음). 따라서 누구의 첫 정점도 아닌 정점은 거기서 -1로 남을 것이다. 이 모듈은 어차피 2.x에서는 실행될 수 없으므로(아래 버그 참고), 여기서 설명한 동작은 명령이 작성된 대상인 1.x의 것이다.

e) 평활화와 쓰기.

surf.GetPointData().AddArray(mv_att_upscaled)
psp.MedianFilter(surf, mv_att_upscaled)

MedianFilter(post_process.py:294-308)는 모든 정점을, 채워진 것도 빈 것도, 위상적 이웃의 중앙값으로 바꾼다. 정점 자신은 제외한다(utils.py:363-376). "첫 정점" 이월이 남긴 구멍을 많이 메우고 원래 있던 값도 평활화한다(1회 패스, 제자리, 중앙값은 사본에서 구하므로 정점의 순서는 중요하지 않다). 메시에 이미 추가된 vtkDataArray를 수정하므로, 실제로 기록되는 것은 필터링된 버전이다.

9. 함정과 취약 지점

쉬운 설명과 수식: 아틀라스 페이지.

확인된 버그 (레거시, VISOR에서는 수정됨)

레거시(3c67957): 설치 프로그램은 여전히 shapeaxi>=2.0.2를 요구한다(ADT/ADTLib/env/install_pytorch.py:385). VISOR에서는 수정되었다. 도구가 shapeaxi==1.1.1을 고정하며, 그 주석은 2.x가 다섯 체크포인트 중 어느 것도 불러오지 못한다고 말한다(SADT-VISOR tools/DOCShapeAXI/pyproject.toml:15-30). 예측은 model(points, views)를 호출한다(engine.py:57. VISOR의 DOCShapeAXI 참고). CLI는 shapeaxi 1.0.x API용으로 작성되었는데 환경은 2.0.2를 설치한다. 모듈이 작동을 멈추면 가장 먼저 확인할 것이다:

shapeaxi 1.0.10shapeaxi 2.0.2
시그니처forward(self, X_pc, X_views)forward(self, X_mesh)
반환값xx, x_w, X
클래스 수 hparamout_classesnum_classes

VISOR가 고정하는 shapeaxi 1.1.1은 다시 1.0.10 패키지다. 둘은 __about__.py만 다르며(이번 점검을 위해 파일 단위로 비교함), 따라서 1.0.10 열은 1.1.1에도 해당한다.

CLI는 model(X_pc, X_views)를 호출하고 반환값을 텐서로 쓴다(DOCShapeAXI_CLI.py:230). 2.0.2에서는 이것이 TypeError(위치 인자 3개)다. 또한 공개된 체크포인트는 out_classes를 담고 있는데 2.0.2의 __init__은 이를 더 이상 읽지 않는다. load_from_checkpoint 호출은 순전파 이전에 이미 실패할 것이다. 다시 말해 이 모듈은 설치 스크립트가 설치하지 않는 고정된 shapeaxi<2 버전을 기대한다. 버전을 고정하거나, CLI를 새 API로 이식하고(X_mesh를 넘기고 세 쌍을 풀어냄) 체크포인트를 재생성해야 한다.

  • strict=False가 load_from_checkpoint에 있다(DOCShapeAXI_CLI.py:135). 없거나 남는 가중치가 조용히 통과한다. 부분적으로만 불러온 모델도 어쨌든 예측한다.
  • 모델 다운로드는 출력 폴더가 이미 존재하는 것을 조건으로 한다(if os.path.exists(args.output_dir): if not os.path.exists(...), DOCShapeAXI_CLI.py:280). 폴더가 없으면 다운로드는 건너뛰어지고 오류는 나중에 체크포인트를 불러올 때 나타난다. CLI는 output_dir를 결코 만들지 않는다.
  • process.log는 Slicer의 임시 폴더에 쓰인다(check_log_path: os.path.join(slicer.util.tempDirectory(), 'process.log'), DOCShapeAXI.py:637-646). 로직이 생성될 때마다 비워진다. :638-640의 주석은 이전의 결함을 기록하는데, 읽기 전용 설치를 깨뜨리던 모듈 옆의 로그였으며 3c67957에서 고쳐졌다. 빈 파일 DOCShapeAXI/process.log는 여전히 버전 관리되지만 아무것도 이를 쓰지 않는다. CLI는 경로를 여덟 번째 인자로 받으며(DOCShapeAXI.py:794) 표면 하나가 끝날 때마다 그 한 줄을 다시 쓴다.
죽은 코드 (정정됨: 버그 아님)

이 페이지의 이전 버전은 여기서 gradcam_save()(DOCShapeAXI_CLI.py:65)가 shutil.copy를 호출하는데 shutil이 import되지 않는다고 주장했다. 3c67957에서는 틀린 말이다. import shutil은 파일의 4번째 줄에 있고 호출은 80번째 줄에 있다. 여전히 맞는 것은 그 함수가 결코 호출되지 않는다는 점이다. CLI 상단 근처에 정의된 클래스 MultiHead와 SelfAttention(:87, :96)도 마찬가지로 결코 인스턴스화되지 않는다. 이전 페이지는 CLI의 subprocess import도 언급했다. 그런 것은 없다(import는 :2-26). subprocess는 패널이 DOCShapeAXI.py:5에서 import하고 거기서 쓴다.

  • 학습된 스케일 인자가 무시된다(§3.2 참고). UnitSurfTransform이 언젠가 자신의 scale_factor를 전달하게 되면, 이 저장소에서는 아무것도 움직이지 않았는데 전처리가 바뀔 것이다.
  • 신뢰도가 보고되지 않는다: argmax 클래스만 나온다. 이름에 "explainability"가 들어 있는 도구로서는 이것이 사각지대다. 현저성 맵은 네트워크가 어디를 보았는지는 알려 주지만, 얼마나 확신이 없었는지는 결코 알려 주지 않는다.
  • 현저성은 두 갈래 중 하나만 다룬다(§5a 참고). 주로 포인트 클라우드 기하에 의해 내려진 결정은 정보가 없는 멀티뷰 맵을 만들어 내며, 이를 알리는 것은 아무것도 없다.
  • 설명 가능성 DataLoader에는 num_workers=4가 있고(DOCShapeAXI_CLI.py:147) 예측은 쓰지 않는다. GPU가 42개 뷰를 렌더링하는 동안 네 프로세스가 .vtk 파일을 병렬로 읽는다.
  • 모델 선택은 콤보 레이블의 단어를 거친다. .ui에서 "Mandibular Condyle"을 "Condyles"로 바꾸면 find_model_name이 깨져 (None, None)을 돌려주고, 다음 호출에서 TypeError가 난다(os.path.join(output_dir, None + '.ckpt')에서).
  • check_input_parameters(DOCShapeAXI.py:296-320)는 같은 조건을 두 번 시험하므로(:298-299), else 분기("Unknown error")에는 도달할 수 없다.
  • count_num_subjects는 최상위 .vtk 파일만 센다. csv_edit와 일관되지만 둘 다 재귀적이지 않다.

10. 문헌

쉬운 설명과 수식: 아틀라스 페이지.

서로 혼동해서는 안 되는 세 가지 참고문헌:

1. 프레임워크. ShapeAXI: Shape Analysis Explainability and Interpretability, Prieto, Miranda, Gurgel, Anchling, Hutin, Barone, Al Turkestani, Aliaga, Yatabe, Bianchi, Cevidanes, Proc. SPIE Medical Imaging, 2024년 4월, DOI 10.1117/12.3007053. 하악과두에서 79.78%, 열구(cleft) 중증도에서 81.58%를 보고한다. 여기서 지원하는 세 데이터셋 중 정확히 둘이다.

코드 / 논문 불일치 (VISOR에서도 마찬가지)

VISOR에서도 마찬가지다. 도구는 같은 SaxiMHAFBClassification과 SaxiMHAFBRegression 네트워크를 불러온다(SADT-VISOR catalog.py:24-25,50-71. VISOR의 DOCShapeAXI 참고). 코드는 논문과 다르다. 논문은 정이십면체 세분화 위의 멀티뷰 렌더를 ResNet-18과 가법 어텐션으로 처리하고, 하악과두를 이진 분류로 다루는 것으로 설명한다. 여기서 배포되는 체크포인트는 SaxiMHAFB* 모델이다. 42개 뷰의 EfficientNet-B0 에 KNN 어텐션을 갖춘 두 번째 포인트 클라우드 갈래를 더한 것으로, 논문에는 없으며, condyles_4_class 체크포인트는 중증도 4⟧개 클래스다. SPIE 논문의 수치를 내려받은 모델의 수치로 제시하지 말 것.

2. 기도 데이터셋. Explainable Artificial Intelligence to Quantify Adenoid Hypertrophy-related Upper Airway Obstruction using 3D Shape Analysis, Mattos et al., J Dent 2025. 이것은 코드의 아키텍처를 정확히 설명한다. ImageNet으로 사전 학습된 EfficientNet-B0 멀티뷰 갈래 + 멀티헤드 어텐션, KNN 어텐션을 갖춘 4096점 포인트 클라우드 갈래, 그리고 "SurfGradCAM"을 통한 설명 가능성으로, §5의 메커니즘이다. 세 작업(4-class, binary, 폐쇄 비율 회귀)은 세 개의 airways_* 체크포인트에 대응한다. AUC 0.77–0.94, 비율에 대해 R = 0.854.
