AutoCrop3D

볼륨 폴더를 ROI 상자(.mrk.json)에 맞춰 일괄로 잘라낸다. 원래 격자에서 인덱스를 추출하는 방식이며, 보간도, 신경망도, conda도 없다.

미발표 autocrop3d_cli conda 없음 GPU 없음 순수 계산 참고문헌

1. 파이프라인에서의 위치

저장소에서 AutoCrop3D를 호출하는 것은 없으며, AutoCrop3D도 Slicer 외에는 아무것도 호출하지 않는다. CMakeLists.txt:39에 선언되어 있을 뿐이다.

실제로는 분할 도구의 상류(AMASSS, BATCHDENTALSEG)나 하류에 놓인다. "generate VTK" 모드는 출력 파일 이름에 seg가 들어 있을 때만 작동하는데, 이는 다른 곳에서 이미 만든 레이블맵이 입력으로 들어온다는 것을 전제한다.

호출 대상시점이유
slicer.modules.autocrop3d_cli기본 경로인덱스 추출, 리샘플링 없음
slicer.modules.cropvolume.logic()"Use module 'Crop Volume' for tilted images" 체크박스회전된 ROI의 경우를 Slicer에 넘김

모델도, .pth도, 다운로드도 없다. AutoCrop3D/ 전체에서 torch|conda|\.pth|monai|nnunet를 grep하여 확인했다 — vtkPolyData 하나(이름이 model)를 빼면 결과가 없다.

3. 자르기 상자를 정의하는 것

markups ROI json 파일(.mrk.json)이며, 다음과 같이 읽는다 (AutoCrop3D_CLI.py:70):

ROI = json.load(open(ROI_Path))['markups'][0]
ROI_Center = np.array(ROI['center'])
ROI_Size   = np.array(ROI['size'])
Lower = ROI_Center - ROI_Size / 2
Upper = ROI_Center + ROI_Size / 2

json의 세 필드가 무시되며, 이것이 예상 밖 결과의 주된 원인이다:

  • coordinateSystem. 테스트 파일 ROI.mrk.zip(AutoCrop3D/Crop_Volumes_UI/Testing/Test_data/ 안)은 "coordinateSystem": "LPS"를 선언하는데, 이는 저장소의 규약이다(모든 markups 기록 코드가 "LPS"를 하드코딩한다: ALI_CBCT, ASO_CBCT, AREG_CBCT, FlexReg, VFACE). 따라서 center는 LPS이며, SimpleITK의 TransformPhysicalPointToContinuousIndex가 기대하는 바로 그것이다. 그러나 이 필드는 결코 읽히지 않는다. RAS로 저장된 ROI라면 중심의 x와 y 부호가 반대가 되며, 아무 메시지도 나오지 않는다.
  • orientation(상자의 3×3 행렬). 무시된다. 상자가 LPS 축에 정렬되어 있다고 가정한다. 테스트 파일에서는 diag(-1,-1,1), 즉 z축 둘레 180° 회전이며, 중심이 맞춰진 상자에는 영향이 없다. 실제로 회전된 ROI는 조용히 자신의 축 정렬 경계 상자로 취급된다. 바로 이 때문에 "tilted images" 체크박스가 있다(§5).
  • 분할도, 계산된 경계 상자도 아니다. 상자는 오로지 이 json에서 온다. 레이블맵으로부터 ROI를 구하는 코드는 어디에도 없다.
함정

coordinateSystem: RAS로 저장된 ROI라면 중심의 x와 y 부호가 반대가 되며, 아무 메시지도 나오지 않는다.

orientation: 실제로 회전된 ROI는 조용히 자신의 축 정렬 경계 상자로 취급된다.

볼륨 쪽에서는 Search가 .nii.gz, .nii, .nrrd.gz, .nrrd, .gipl.gz, .gipl을 받아들인다(AutoCrop3D_CLI.py:48). glob.iglob(**, recursive=True) 뒤에 endswith를 적용하는 방식이다.

4. 상자를 적용하는 방식 — 인덱스 추출, 리샘플링 없음

핵심은 이것이다: 보간이 없다. 물리 좌표 → 인덱스 변환 뒤 자르기(AutoCrop3D_CLI.py:77):

Lower = np.array(img.TransformPhysicalPointToContinuousIndex(Lower)).astype(int)
Upper = np.array(img.TransformPhysicalPointToContinuousIndex(Upper)).astype(int)
for i in range(3):
    if Lower[i] > Upper[i]:
        Lower[i], Upper[i] = Upper[i], Lower[i]
Lower = [max(0, l) for l in Lower]
Upper = [min(img_size[i], u) for i, u in enumerate(Upper)]
img_roi = img[Lower[0]:Upper[0], Lower[1]:Upper[1], Lower[2]:Upper[2]]

swap은 겉치레가 아니다. TransformPhysicalPointToContinuousIndex는 방향 행렬의 역을 적용한다. 어떤 축에서 방향 코사인이 음수인 볼륨(CBCT에서 흔함)에서는 물리적인 "아래" 모서리가 가장 큰 인덱스가 된다. swap이 없으면 슬라이스가 비어 버린다. 이것이 direction을 올바르게 처리하는 방식이다.

SimpleITK 인덱싱이 보존하는 것. 확인 결과: sitk.Image를 슬라이싱하면 spacing과 direction은 그대로 유지되고, 추출된 모서리의 원점만 다시 계산된다. 50×60×70 볼륨, spacing 0.3, 원점 (10,20,30), direction diag(-1,-1,1)에서 img[5:20,5:20,5:20]의 원점은 (8.5, 18.5, 31.5)다 — x와 y에서 -5·0.3(음의 방향), z에서 +5·0.3 이동. 복셀 값은 입력과 비트 단위로 동일하다.

확인됨

sitk.Image를 슬라이싱하면 spacing과 direction은 그대로 유지되고, 추출된 모서리의 원점만 다시 계산된다. 복셀 값은 입력과 비트 단위로 동일하다.

"Keep the same size as input" 모드(box_Size == 'True', AutoCrop3D_CLI.py:107): 원래 기하 정보로 빈 영상을 만들고(sitk.Image(...) + CopyInformation), 추출한 블록을 같은 인덱스 위치에 다시 붙여 넣은 뒤, CopyInformation을 다시 적용한다. 기하 정보는 입력과 완전히 동일하며, ROI 밖은 모두 0이 된다. GetArrayFromImage의 축 반전(z,y,x)에 주의하라. 코드는 이를 올바르게 처리한다.

연관된 변환은 어떻게 되는가: 아무 일도 없다. vtkMRMLTransformNode도, 읽거나 쓰는 .tfm도, HardenTransform도 없다. 기하 정보는 전적으로 헤더(origin/spacing/direction)가 담고 있으며, 자르기로 인한 오프셋은 원점에 흡수된다.

참고

실무상 결과: 전체 볼륨에서 계산한 정합 행렬은 잘라낸 볼륨에서도 그대로 유효하다. 물리 좌표가 움직이지 않았기 때문이다.

5. 대체 경로 — Slicer의 Crop Volume 모듈

processCropVolume() (AutoCrop3D.py:915). "Use module 'Crop Volume' for tilted images" 체크박스로 활성화된다(커밋 9d2bbe8). CLI가 아니라 위젯 안에서 실행된다:

cropVolumeLogic = slicer.modules.cropvolume.logic()
parameters = slicer.vtkMRMLCropVolumeParametersNode()
parameters.SetInputVolumeNodeID(inputVolume.GetID())
parameters.SetROINodeID(roiNode.GetID())
parameters.SetOutputVolumeNodeID(outputVolume.GetID())
cropVolumeLogic.Apply(parameters)

설정하는 것은 ID 세 개뿐이다. 보간, 등방성, spacing 배율은 vtkMRMLCropVolumeParametersNode의 기본값을 그대로 쓴다. 보간이 켜져 있으면 Crop Volume은 ROI 자체의 좌표계에서 리샘플링한다. 바로 이 덕분에 회전된 ROI를 다룰 수 있지만, CLI 경로와 달리 복셀 값이 바뀐다는 대가가 따른다. 따라서 두 경로는 같은 파일을 만들지 않으며, 이는 의도된 것이다.

optionCheckBox()는 이 모드에서 "Keep the same size"를 숨긴다. Crop Volume에는 그에 해당하는 기능이 없기 때문이다.

이 경로는 ROI와 볼륨을 MRML 노드로 불러오므로(loadMarkups, loadVolume), 이 경로만이 coordinateSystem과 orientation을 읽는다 — json을 파싱할 때 Slicer가 처리해 준다.

6. 일괄 모드와 환자 ↔ ROI 짝짓기

len(ROIList['.mrk.json']) > 1로 구분되는 두 가지 방식이 있다 (AutoCrop3D_CLI.py:53):

  • ROI 하나 → 찾은 모든 볼륨에 적용;
  • ROI 여러 개 → ChangeKeyDict가 {basename.split('_')[0]: path}를 만들고, 각 볼륨이 자신의 키를 찾는다. 실패하면 → logger.warning('No ROI for patient:') 후 continue.

양쪽은 키를 서로 다르게 계산한다:

쪽규칙예시 MA_0001_T1_Scan.nii.gz / MA_0001_ROI.mrk.json
볼륨.split()을 _Scan _scan _Seg _seg _Or _OR _MAND _MD _MAX _MX _CB _lm _T2 _T1 _Cl에 대해 연쇄 적용한 뒤 .split('.')[0]MA_0001
ROIbasename.split('_')[0]MA

따라서 밑줄이 들어간 환자 이름은 짝짓기를 깨뜨린다. 밑줄이 없는 이름(MA0001_…)이라면 모두 잘 동작한다.

진행 상황은 파일마다 단순히 open(logPath,'r+').write(str(index))로 기록한다. 위젯은 내용은 읽지 않고 st_mtime만 본다 (AutoCrop3D.py:574).

7. 분할로부터 VTK 메시 생성

if "seg" in ScanOutPath.lower()로 작동한다 (AutoCrop3D_CLI.py:151). 이 검사는 출력 경로 전체에 대해 이루어지므로, 상위 폴더 이름이 Segmentations/이기만 해도 모든 파일에서 작동한다. 실패는 맨 except: pass가 삼켜 버린다.

convertNiftiToVTK (GenerateVTKfromSeg.py:16):

  1. padding(): sitk.ConstantPad(img, [50,50,10], [0,0,0]). 확인한 실제 시그니처: ConstantPad(image, padLowerBound, padUpperBound, constant) — 세 번째 인자가 0이므로 아래쪽 경계만 패딩된다.
    확인된 버그

    "add 50 pixels around each dimension"이라는 주석은 틀렸다. 자르기 영역의 위쪽 면에 닿는 구조는 열린 채로 남는다.

    임시 파일의 이름은 image_padded.nii.gz이며, tempdir이 아니라 프로세스의 현재 디렉터리에 기록된다.
  2. vtkNIFTIImageReader → vtkDiscreteMarchingCubes(GenerateValues(100, 1, 100)) → vtkSmoothPolyDataFilter (5회 반복, feature angle 120°, relaxation 0.6).
  3. 색칠: color_tup = LABEL_COLORS[label], 여기서 label = np.max(img_arr). 모든 셀이 같은 색이다.
    확인된 버그

    "coloring according to labels"라는 주석은 코드를 설명하지 않는다.

    또한 LABEL_COLORS에는 키 1–6만 있다. 클래스가 6개를 넘는 레이블맵은 KeyError를 일으키고, 이는 호출자의 except: pass가 삼킨다. 결국 VTK도 메시지도 없다.
  4. present_labels는 계산만 되고 쓰이지 않는다 — 사용되지 않는 코드.

VTK의 NIfTI 리더는 qform도 sform도 적용하지 않으며(코드는 이를 가져오지도 않는다), 50/50/10 복셀 패딩도 결코 보정되지 않는다. 추론이며 여기서 검증하지는 않았다: 결과 메시는 Slicer에서 잘라낸 볼륨과 겹치지 않는다.

11. 함정과 취약 지점

함정 — 파일이 하나뿐인 ROI 폴더

파일이 정확히 하나 든 ROI 폴더 → 충돌. ROI_dict는 len(ROIList) > 1일 때만 만들어진다. 그렇지 않으면 ROI_Path가 폴더로 남고, json.load(open(ROI_Path))가 IsADirectoryError를 일으킨다. 반면 Crop Volume 경로는 os.path.isdir을 검사해 이를 제대로 처리한다.

함정 — 위젯과 CLI의 확장자 불일치

위젯과 CLI는 같은 확장자를 찾지 않는다. CheckInput (AutoCrop3D.py:808)은 .nii.gz, .nrrd.gz, .gipl.gz만 찾는다. 압축되지 않은 .nii나 .nrrd 파일 폴더는 CLI가 완벽하게 처리할 수 있는데도 UI가 거부한다("Wrong type of patient file detected"). 그리고 nbFiles가 같은 목록에서 나오므로, 확장자가 섞여 있으면 진행 표시줄의 분모가 틀어진다.

함정 — 무시되는 ROI 필드

ROI의 coordinateSystem과 orientation은 CLI 경로에서 무시된다 (§3). 회전된 상자나 RAS로 저장된 ROI: 틀린 결과가 조용히 나온다.

함정 — 인덱스 절삭

.astype(int)는 0 쪽으로 절삭하므로, Upper가 축마다 최대 복셀 하나를 잃는다. 임상적 영향은 없지만, 자르기가 요청한 중심에 대해 대칭이 아니다.

함정 — 교차 검사 없음

ROI가 볼륨과 교차하는지 검사하지 않는다. 클램핑은 Lower ≥ 0과 Upper ≤ size로 제한하지만, 클램핑 뒤 Lower > Upper가 되는 것은 막지 못한다. 그러면 크기 0인 영상이 나오고, 기록은 try/except 안에서 실패하며, 이 블록은 Lower/Upper를 로그에 남긴다.

함정 — 지나치게 넓은 경로 치환

.replace(basename, filename)은 결합된 경로의 모든 등장 위치를 치환한다 (AutoCrop3D_CLI.py:129). 파일과 이름이 같은 폴더도 함께 이름이 바뀐다.

함정 — Crop Volume이 장면을 비운다

Crop Volume 경로: 환자마다 slicer.mrmlScene.Clear(0) (AutoCrop3D.py:998) — 사용자가 불러 둔 데이터까지 포함해 장면 전체를 비운다.

함정 — 메인 스레드 밖에서의 MRML 접근

Crop Volume 경로: slicer.util.saveNode를 threading.Thread에서 호출한다 (AutoCrop3D.py:979). 즉 메인 스레드 밖에서 MRML에 접근한다. 뒤따르는 while thread.is_alive(): processEvents()가 사실상 실행을 직렬화하므로, 문제를 고치지 않은 채 가려 버린다.

함정 — 부분적인 접미사

Crop Volume 경로: 접미사는 .nii.gz 파일에만 붙는다. .nrrd는 접미사 없이 같은 상대 이름으로 나온다.

함정 — 동작하지 않는 단위 테스트

단위 테스트는 아무것도 테스트하지 않는다. test_AutoCrop3D1이 두 번 정의되어 있다. docstring만 들어 있는 클래스 메서드(runTest가 호출)와, 실제 테스트를 담고 있지만 한 번도 실행되지 않는 모듈 수준 함수(AutoCrop3D.py:1097)다.

사용되지 않는 코드

사용되지 않는 코드: CropCBCT.py (자신의 docstring에 표시되어 있음), 개발 머신의 절대 경로가 아직 남아 있는 Autofill(), 그리고 registerSampleData()(저장소에 없는 파일인 AutoCrop3D2.png를 참조).

12. 문헌

AutoCrop3D를 다룬 논문은 없다. 연구실용으로 작성된 일괄 처리 유틸리티(Jeanne Claret, UoM/DCBIA)이며, 문서는 README.md:336 절과, 그 의미를 재사용하는 Slicer의 Crop Volume 모듈 도움말뿐이다:

  • Crop Volume — Slicer 문서
  • Crop Volume Sequence — Slicer 문서 (README가 AutoCrop3D가 우회하는 한계로 인용한다: 시퀀스로 불러오기에는 너무 무거운 파일)
  • SlicerAutomatedDentalTools

CLI의 documentation-url은 https://github.com/Jeanneclre/DCBIA-code를 가리키는데, 이는 프로젝트 자체의 저장소가 아니라 개인 저장소다.
