FlexReg, 레거시: 코드

개발자용: 레거시 Slicer 모듈 FlexReg가 코드에서 하는 일을(3c67957 시점의 SlicerAutomatedDentalTools) file:line 참조, 시그니처, 인자, 환경, 함정과 함께 다룬다. 같은 파이프라인에 대한 읽기 쉬운 설명은 수식과 함께 아틀라스 페이지에 있다. VISOR 포팅에는 별도의 코드 페이지가 있다.

코드 아틀라스 (해설) 미발표 FlexReg_CLI conda 환경: shapeaxi VISOR 가이드 참고문헌
두 코드 베이스

아래에 번호가 붙은 모든 내용은 레거시 Slicer 모듈(3c67957 시점의 SlicerAutomatedDentalTools, 2026-10-26)을 설명한다. 같은 도구를 서버에서 실행하는 VISOR 포팅은 별도 페이지 VISOR의 FlexReg에서 설명한다. VISOR 포팅은 패치 미리보기를 Slicer에 두고 나머지는 서버에서 하며, 자유 곡선, 패치 삭제, 점막치은 패치 계산, 자동 치관 분할은 갖고 있지 않다.

1. 체인에서의 위치

쉬운 설명과 수식: 아틀라스 페이지.

저장소의 어떤 것도 FlexReg를 호출하지 않는다. 운영자가 구동하는 말단 도구다. 그러나 사전 학습된 네트워크 두 개는 호출하며, AREG_IOS의 입력을 만들어 낸다. 두 도구는 정확히 같은 점 배열을 읽는다.

호출되는 것시점이유
dentalmodelseg(ShapeAXI / DentalModelSeg)메시에 Universal_ID 배열이 없으면치관을 분할하고 번호를 매긴다
ALI_IOS(가중치 Lower_MG_*.pth)하악궁 모드에서만점막치은 랜드마크 13개를 배치한다

하류에서 AREG_IOS.py:364는 vtkMeshTeeth(list_teeth=[1], property="Butterfly")를 수행하고 AREG_IOS.py:378는 MGL_ARRAY_NAME에 대해 같은 것을 수행한다. FlexReg에서 만든 패치는 AREG_IOS가 바로 쓸 수 있고, 그 반대도 마찬가지다. 차이는 패치가 어디서 오는가에 있다. AREG_IOS는 네트워크가 예측하게 하고(PredPatch.py, 멀티뷰 MonaiUNetHRes), FlexReg는 기하학적으로 만든다.

2. 관련 파일

쉬운 설명과 수식: 아틀라스 페이지.

참고(레거시 전용)

이 모듈의 일부는 이제 공유 계층에 있다. ADTLib는 여러 모듈이 사본으로 갖고 있던 것을 한곳에 모았다. 여기서는 geometry.py, io/landmarks.py, labels.py, 그리고 method.py의 계약이 해당한다. 각 파일이 사본 몇 개를 대체했는지는 그 페이지에 기록되어 있다.

레거시(3c67957). VISOR에는 없다: VISOR 도구는 ADTLib에서 아무것도 import하지 않으며, 그 유틸리티는 로컬 사본이다(SADT-VISOR tools/FlexReg/src/sadt_flexreg/util.py, transformation.py).

파일역할실행되는 곳
FlexReg/FlexReg.pySlicer 위젯, 4157줄: UI, 조이스틱, 미리보기, MGL 경로 전체Slicer의 Python
FlexReg_CLI/FlexReg_CLI.pyCLI: butterfly, curve, delete, icp, icp_mglslicer.cli.run을 통한 Slicer의 Python, CUDA 필요
FlexReg_Method/ (FlexReg_CLI/FlexReg_Method)방향, butterfly, 측지 팽창, ICP동일
FlexReg_utils/ (FlexReg/FlexReg_utils)butterfly 미리보기(numpy, CPU), MGL 패치(numpy/scipy), pytorch3d 설치Slicer의 Python
눈에 띄지 않는 점 (레거시 전용)

CLI는 conda 환경 안에서 실행되지 않는다. slicer.cli.run(slicer.modules.flexreg_cli, ...)(FlexReg.py:766-767)를 거치므로 Slicer 자체의 Python 안이고, 그래서 ensureBooted가 Slicer 자체에 torch를 설치한다. dentalmodelseg와 ALI_IOS만 conda run -n shapeaxi를 거친다.

레거시(3c67957). VISOR에는 없다: 도구는 자체 서버 환경(Python 3.11 또는 3.12, torch 2.8.0, vtk 9.3.1, numpy 1.26.4: SADT-VISOR tools/FlexReg/pyproject.toml:8-18)에서 실행되며, Slicer에는 아무것도 설치되지 않는다(AutomatedDentalToolsRemote FlexRegRemote/FlexRegRemote.py:8-12).

conda를 통해 CLI를 시작하게 되는 setup_cli_command()(FlexReg.py:852)는 어디서도 호출되지 않는다. 죽은 코드다.

3. 입력과 전처리

쉬운 설명과 수식: 아틀라스 페이지.

함정: 파일 변환 (레거시 전용)

ensureVtkInput()(FlexReg.py:3199)은 어떤 연산보다 먼저 .stl을 .vtk로 변환한다. 이것은 겉치레가 아니다. dental_model_seg.py는 os.remove(args.stl)를 수행하므로 .stl을 직접 넘기면 원본 파일을 파괴할 것이다(FlexReg.py:3409).

레거시(3c67957). VISOR에는 없다: read_surface는 확장자에 따라 .vtk, .vtp, .stl을 직접 읽고 빈 메시를 거부한다(SADT-VISOR sadt_flexreg/pipeline.py:50-78). 분할은 실행되지 않으므로 원본 파일이 삭제되지 않는다.

LPS ↔ RAS 뒤집기. CLI는 .vtk(LPS)를 읽고, Slicer처럼 RAS에서 작업하도록 Scale(-1,-1,1)을 적용하며, 쓰기 전에 다시 뒤집는다(FlexReg_CLI.py:228, 297). 따라서 모든 내부 계산은 RAS에서 이루어진다.

표준 틀 맞추기, 핵심 전처리 단계, orientation.py:

  1. 치아 Universal_ID 3, 5, 12, 14(UR6, UR4, UL4, UL6)의 중심.
  2. 각 쪽의 국소 기저: 세 점을 지나는 평면의 법선(중점을 향한 두 벡터의 외적), 그다음 수직 방향.
  3. 연속된 두 번의 회전, 축 = 외적, 각도 = 내적의 arccos, RotationMatrix(Rodrigues)를 통해.
  4. 중심이 일치하도록 평행 이동.

목표는 [[-0.5,-0.5,0], [0,0,0], [0.5,-0.5,0]]이다. 우측 대구치는 x<0, 좌측 대구치는 x>0, 소구치는 원점. 결과: 교합면 ≈ z=0, +y = 전방, +x = 좌측. 스케일링은 없다. 이것은 강체 3점 정합이다.

직접적인 귀결: 뒤따르는 butterfly 계산 전체는 z 성분을 그냥 무시하는 XY 평면에서의 2D 계산이다.

4. 모델

쉬운 설명과 수식: 아틀라스 페이지.

4.1 치관 분할: DentalModelSeg 예측됨

쉬운 설명과 수식: 아틀라스 페이지.

checkSegmentation()(FlexReg.py:3402)은 배열의 존재 여부를 시험하지 않는다. 위의 방향 맞추기를 시도하고 예외를 읽는다.

  • ToothNoExist → 메시는 분할되었지만 기준 치아 4개 중 하나가 없다 → 메시지, 중지.
  • NoSegmentationSurf → 분할 배열 없음 → shapeaxi_conda().
conda run -n shapeaxi python -m CrownSegmentationcli \
  <surf> None <out> 1 latest 0 Universal_ID 0 None <vtk_folder> <dentalmodelseg_path>

인자 순서: 표면, 입력 csv, 출력 폴더, overwrite=1, latest 모델, crownsegmentation=0, 배열 이름 Universal_ID, fdi=0, 접미사, vtk 폴더, dentalmodelseg 실행 파일의 경로(환경 안의 which로 찾음).

이 저장소에서 검증할 수 있는 것은 위의 명령줄과 그 효과까지다. 출력은 범용 1–32 번호 체계의 점 배열 Universal_ID이며 입력 파일에 쓰인다(overwrite=1).

아키텍처와 latest 가중치는 저장소 밖의 pip 패키지 shapeaxi에 있다. 여기서는 확인할 수 없다. 계보상(DentalModelSeg는 Fly-by-CNN에서 유래) 멀티뷰 렌더 뒤에 뷰별 2D 분할과 정점으로의 투표 재투영이 이어질 것으로 예상되지만, 카메라의 수도, 배치도, 렌더 해상도도 이 저장소에서는 검증할 수 없고, 인접한 예가 경고가 된다. PredPatch.py에서 ico_verts라는 이름의 버퍼는 정이십면체 구가 아니라 z=0.9에 몰린 카메라 7개를 담고 있다.

함정: 가정하지 말 것 (레거시 전용)

읽어 보지 않고 카메라의 구를 가정하지 말 것.

레거시(3c67957). VISOR에는 없다: FlexReg는 더 이상 어떤 분할 네트워크도 호출하지 않는다. 아치에는 이미 점별 치아 레이블이 있어야 한다(SADT-VISOR sadt_flexreg/__init__.py:82-83).

downloadModel()(FlexReg.py:3374)은 Fly-by-CNN .pth(07-21-22_val-loss0.169.pth, 릴리스 3.0)를 내려받는다. 호출되지 않는다, 죽은 코드다. 실제로 쓰이는 모델은 latest이며 dentalmodelseg 안에 번들되어 있다.

4.2 점막치은 랜드마크: ALI_IOS 예측됨

쉬운 설명과 수식: 아틀라스 페이지.

computeMGLLandmarks() (FlexReg.py:2304):

conda run -n shapeaxi python -m ALI_IOS \
  <scan> <models> None None "LL6MG LL5MG … L0MG … LR6MG" <out> 224 0 1 <log>

위치 인자: input, dir_models, lm_type=None, teeth=None, teeth_mg=<13 names>, output_dir, image_size=224, blur_radius=0, faces_per_pixel=1, log_path.

ALI_IOS도 마찬가지로 멀티뷰(PyTorch3D 렌더링)다. 분할에 따라 치아마다 카메라를 하나씩 놓고, 224×224로 뷰를 렌더링하며, 네트워크는 정점이 점의 위치를 알려 주는 히트맵을 출력한다. Universal_ID / PredictedID에서 랜드마크는 그 치아에 레이블이 있을 때만 배치된다. 그래서 ALI가 13개 점 중 k개만 배치했을 때 FlexReg의 오류 메시지가 분할을 가리킨다.

가중치는 <Documents>/SlicerDownloads/ALI/ALI_IOS/Models/Prediction에서 Lower_MG_*.pth라는 이름으로 찾으며(hasMGLModel, FlexReg.py:2374), 없으면 폴더 선택기가 열린다.

5. 알고리즘의 핵심부

쉬운 설명과 수식: 아틀라스 페이지.

5.1 경로 A: Butterfly 패치(상악궁) 계산됨

쉬운 설명과 수식: 아틀라스 페이지.

make_butterfly.py. 네트워크 없이 순수하게 기하학적이다.

a) 중심 네 개. 운영자가 치아 4개(전방 좌/우, 후방 좌/우)를 고르고, vtkMeanTeeth가 그 Universal_ID를 가진 정점을 평균한다.

b) 파라미터 세 계열을 이 중심들에 적용한다:

파라미터효과세부 사항
shift_lr, shift_ap패치 전체를 평행 이동한다같은 벡터가 중심 4개 모두에 더해진다. 랜드마크는 가중치의 합이 1인 아핀 결합이므로 이동은 보간을 통해 전달되고 모양은 바뀌지 않는다
adjust (mm)늘이기 / 줄이기±y 오프셋, 후방 치아에서는 부호가 뒤집힘: 양의 adjust는 양 끝을 바깥으로 민다
ratio너비는 보존된다r = (1-ratio)/2로 재파라미터화한 뒤 landmark = (1-r)·own_centroid + r·opposite_centroid. ratio=1 → 랜드마크가 자신의 중심 위(최대 패치). ratio=0 → 랜드마크가 중간(퇴화한 패치)

어휘에 주의할 것. UI는 top/bot이라 하고 CLI는 anterior/posterior라 한다. lineedit_teeth_left_top → tooth_anterior_left.

c) 윤곽, 네 조각:

  • 전방 선분과 후방 선분(Segment2D, 간격 0.01).
  • 우측과 좌측의 2차 베지에 곡선 둘, 제어점 (posterior_landmark, posterior_midpoint, anterior_landmark), 그다음 중심이 아니라 아치 바깥쪽으로 불룩해지도록 현을 기준으로 반사한다(sym = 2·proj − bezier). 이것이 butterfly에 그 모양을 준다.

d) 표시. 윤곽의 점과 XY로 투영된 정점 사이의 torch.cdist. radius = 0.7 mm 이내의 모든 정점이 1로 설정된다.

e) 채우기. Dilation()(propagation.py:56): 메시 위의 측지 플러드 필(flood fill)이며 형태학적 팽창이 아니다. 랜드마크 4개의 무게중심에 가장 가까운 정점에서 시작하여 이웃에서 이웃으로 전파되고(GetPointCells / GetCellPoints), 이미 1로 설정된 윤곽에서 멈춘다. GPU에서 nmb_treatment = 1000개씩 배치로 처리한다.

f) 쓰기. 배열의 이름은 Butterfly{index}이다. 각 패치는 자신의 인덱스를 가지므로 누적할 수 있다. CLI의 끝에서 모든 Butterfly1..N 배열이 torch.logical_or로 하나의 배열 Butterfly로 합쳐지며(FlexReg_CLI.py:277), ICP와 AREG_IOS가 읽는 것이 이것이다. 결과는 입력 파일에 다시 쓰인다.

delete 모드는 삭제된 인덱스 위의 배열을 다시 번호 매기고 마지막 것을 버리며, 빈칸을 남기지 않는다.

실시간 미리보기. butterfly_preview.py는 똑같은 윤곽을 순수 numpy(CPU)로 재현하고, 플러드 필을 다각형 내부 판정(matplotlib.path.Path, numpy 교차 횟수 대체 구현 포함)으로 바꾼다. 방향과 중심은 스캔마다 캐시되므로(prepare) 조이스틱을 움직일 때마다 윤곽만 다시 계산된다. 상수: 높이 맵의 CELL = 1.0 mm, 치아 위 LIFT = 0.4 mm, 변마다 샘플 NB_POINTS = 120개.

5.2 경로 B: 그린 패치 계산됨

쉬운 설명과 수식: 아틀라스 페이지.

draw()(FlexReg.py:3972), type="curve". 표면에 제약된 Slicer 곡선(SetAndObserveSurfaceConstraintNode)과 중점이 문자열로 직렬화되어 CLI에 전달된다. draw.py는 연속한 점 사이를 선형 보간하고(간격 0.2, 닫힌 루프), 1.1 mm 이내의 정점을 표시하며(3D 점에 대한 torch.cdist, draw.py:34-35: butterfly와 달리 XY로의 투영이 없다), 그다음 중점에서 똑같은 Dilation()을 실행한다. butterfly와의 유일한 차이는 윤곽을 얻는 방식이다.

곡선은 카메라를 향하도록 다시 중심을 맞춘 모델 위에 그려진다. CLI로 보내기 전에 moveCurve()가 재중심 행렬의 역을 적용하여 파일의 좌표로 되돌린다.

5.3 경로 C: MGL 패치(하악궁) 계산됨

쉬운 설명과 수식: 아틀라스 페이지.

구개는 상악궁에서 안정적인 고원을 제공하지만 하악에는 그런 것이 없다. 대체물로 선택된 것은 점막치은선이다. 이 블록 전체는 위젯 안에서 numpy/scipy로 계산된다. GPU도 CLI도 없다(FlexReg/FlexReg_utils/mgl_patch.py, 아래에서는 mgl_patch.py라 부른다. AREG_IOS/AREG_IOS_utils/mgl_patch.py는 별개의 파일이다).

a) ALI의 예측 정리. DoubtfulLandmarks()는 ALI가 점을 강제로 정했을 때(상위 k 픽셀, 치아로의 폴백, 없는 치아) json에 쓰는 description을 읽는다. 코드의 주석에 따르면 예측 364건에서 측정한 결과 이웃의 곡선에서 중앙값 4.2 mm 벗어나며, 나머지는 1.2 mm다. 시험하는 표시는 forced, fallback, arch fit, off the aim, extrapolated이고, confidence가 MIN_CONFIDENCE = 0.785 미만인 것도 포함한다(mgl_patch.py:144-162). 이 점들은 기본적으로 버려지고 스플라인이 틈을 잇는다. 남는 점이 3개 미만이 되는 경우는 예외다. 그다음 CanonicalLandmarks(옛 주석 이름 → 표준, LL7MG 또는 LR7MG의 존재로 감지)와 RecentreNames(아치 중간에서 점이 빠졌을 때 번호가 정중선에 고정된 채 유지됨).

b) 국소 틀. LocalFrames(): 치근단 축은 중심화된 랜드마크의 SVD의 세 번째 성분이다(점 띠의 법선이며 세계 공간에서의 스캔 방향과 무관). 접선은 아치를 따른 np.gradient이고, 협측은 그 둘의 외적이며 안쪽을 가리키는 곳에서는 뒤집는다. OrientApical이 치관을 기준으로 부호를 고정한다.

c) 띠 만들기, compute()마다:

  1. 운영자 오프셋(협측 / 치근단 / 접선)을 랜드마크에 적용한다.
  2. 이를 지나는 vtkParametricSpline, SAMPLES_PER_SEGMENT = 25.
  3. 각 샘플이 메시에 스냅된다(vtkPointLocator). 보간된 스플라인은 치간 오목부에서 표면을 벗어난다.
  4. 실제 길이로 가중된 에지 그래프에 대한 Dijkstra(scipy.sparse.csgraph), 이 정점들에서 시작하는 다중 소스, limit = 최대 높이, min_only=True, return_predecessors=True → 띠는 표면을 따라 자라며 결코 표면을 통과하지 않는다(능선이 얇은 곳에서 전정측 패치가 설측으로 나올 수 없다).
  5. 높이는 랜드마크 사이에서 선형으로 보간되며(np.interp) 비대칭이다. 치관 쪽에는 heights, 전정 쪽에는 heights_down를 쓰고, 어느 쪽인지는 치근단 성분의 부호로 정한다. 쓰이는 높이는 정점에 도달한 시드의 높이이므로, 높이가 다른 두 선분이 단차 없이 공존한다. 쪽은 정점에서 시드를 뺀 값을 치근단 축에 투영한 부호이며(below, mgl_patch.py:510-513), 정점은 distance <= allowed이고 allowed > 0이면 유지된다(:513-516). 따라서 높이 0은 곡선조차 포함하여 아무것도 유지하지 않는다. 두 높이의 기본값은 모두 2.5 mm(mgl_patch.py:120. 슬라이더 “Upper extension”와 “Lower extension”, FlexReg.py:1867-1868, 1966-1972)이므로 띠는 기본값에서만 대칭이다.
  6. 치관(Universal_ID 17–32, LOWER_TOOTH_LABELS = range(17, 33), 제3대구치 포함, mgl_patch.py:130-134)은 제거된다. T1과 T2 사이에 움직이기 때문이다.
  7. 랜드마크 자체는 항상 패치에 남는다.

범위: MIN_HEIGHT = 0.0, MAX_HEIGHT = 5.0, DEFAULT_HEIGHT = 2.5 mm. 모든 곳에서 높이가 0이면 ⇒ 13개 점만 남는다. 이것은 점만 쓸 때보다 띠가 무엇을 더하는지 재기 위한 의도적인 대조군이다.

에지 그래프는 np.unique(np.sort(edges))로 만들어진 뒤 coo_matrix에 들어간다. 이 중복 제거가 없으면 삼각형 둘이 공유하는 내부 에지가 희소 행렬에 의해 합산되어 길이가 두 배가 되고 패치의 도달 범위가 절반이 된다.

출력 배열: Bottom_MGL(MGL_ARRAY_NAME), Bottom_MGLPreview에서 미리 봄.

WriteLandmarks()는 편집된 랜드마크를 학습 주석처럼 LPS로 쓴다. 결과 파일은 곧바로 코퍼스에 다시 넣을 수 있다.

5.4 정합 계산

쉬운 설명과 수식: 아틀라스 페이지.

Reg.run()(FlexReg.py:1060)은 같은 CLI를 type = "icp"(위턱) 또는 "icp_mgl"(아래턱)로 다시 실행한다. T2가 움직이는 스캔(lineedit)이고, T1이 고정된 스캔(path_reg)이다.

patch_array = "Bottom_MGL" if args.type == "icp_mgl" else "Butterfly"
option = vtkMeshTeeth(list_teeth=[1], property=patch_array)
icp = ICP([vtkICP()], option=option)
output_icp = icp.run(modelNode, modelNodeT1)

vtkMeshTeeth는 이름과 달리 메시를 만들지 않는다. 패치 배열이 1인 꼭짓점만 담은 점군을 추출한다. 따라서 ICP는 치아가 아니라 패치에서만 실행된다.

icp.GetLandmarkTransform().SetModeToRigidBody()   # 6 dof, no scaling
icp.SetMaximumNumberOfIterations(1000)
icp.StartByMatchingCentroidsOn()                  # initialization

표준 vtkIterativeClosestPointTransform이다. 최근접 이웃 매칭, 강체 최소제곱 추정, 반복으로 이루어진다. 이 단계에는 학습이 없다.

이렇게 구한 4×4 행렬은 T2 메시 전체에 적용되며, 반대편 악궁이 주어지면(lower_arch) 그것에도 적용되어 같은 움직임을 따른다.

6. 후처리와 출력

메시. 패치 type은 입력 파일에 다시 쓰인다. ICP type은 LPS로 되돌린 뒤 path_output에 <T2 name without extension><suffix>.vtk로 쓰인다.

변환은 까다로운 단계다(FlexReg_CLI.py:100-106):

flip = np.diag([-1, -1, 1, 1])

sitk_tfm = sitk.AffineTransform(3)
sitk_tfm.SetMatrix(composed_inv[:3, :3].flatten())
sitk_tfm.SetTranslation(composed_inv[:3, 3])

9. 함정과 취약 지점

쉬운 설명과 수식: 아틀라스 페이지.

CLI는 CUDA를 요구한다(VISOR에서도 마찬가지이며, 패치 단계에 한정된다)

Dilation, drawPatch, 그리고 배열의 최종 병합은 모두 CPU 대체 경로 없이 .cuda()를 호출한다. 반면 MGL 패치는 위젯 쪽에서 계산되어 이것 없이 동작하므로, 아래턱 악궁의 병합을 건너뛰는 while args.type != "icp_mgl"이 있다(FlexReg_CLI.py:267-292, .cuda()는 272와 286).

패치에 대해서는 VISOR에서도 마찬가지다. Dilation은 대체 경로 없이 .cuda()를 호출하며(SADT-VISOR sadt_flexreg/propagation.py:31, 60, 66-68), make_butterfly.py:161에서 호출된다. 나머지는 더 이상 사실이 아니다. Butterfly 배열의 병합은 numpy로 이루어지고(pipeline.py:165-188), drawPatch는 호출되지 않으며, icp_mgl 루프 건너뛰기는 사라졌고, 정합 경로는 torch를 import하지 않는다(pipeline.py:191-224).

입력 파일이 덮어쓰인다(레거시 전용)

패치 모드에서 그렇고, 자동 분할도 입력 파일을 덮어쓴다(overwrite=1). 분할에 넘긴 .stl은 dentalmodelseg에 의해 아예 삭제된다. ensureVtkInput()이 존재하는 이유가 바로 이것이다.

레거시 참조: FlexReg_CLI.py:314-315(패치 모드는 args.lineedit에 쓴다), FlexReg.py:3481(분할의 overwrite 플래그).

레거시(3c67957), VISOR에는 없음: 입력은 절대 수정되지 않는다. 출력은 접미사를 붙여 output_dir 아래에 쓰이며(SADT-VISOR sadt_flexreg/__init__.py:160-163), 분할은 실행되지 않는다.

확인된 버그: vtkICP.__call__(VISOR에서도 마찬가지)

vtkICP.__call__은 변환된 메시 대신 source를 그대로 반환한다. list_icp에 방법이 하나뿐이어서 여기서는 문제가 없지만, 여러 단계를 잇는 체인은 지금 쓰인 대로는 동작하지 않을 것이다.

VISOR에서도 마찬가지다: return source, VTKMatrixToNumpy(...)(SADT-VISOR sadt_flexreg/ICP.py:113, 레거시 FlexReg_CLI/FlexReg_Method/ICP.py:104). register가 반환된 행렬을 직접 적용하므로(pipeline.py:218-224) 여전히 문제는 없다.

분할 감지가 예외를 통해 이루어진다(레거시 전용)

Universal_ID가 아닌 다른 배열 이름으로 분할된 메시는 전체 재분할을 일으킨다.

레거시(3c67957), VISOR에는 없음: 재분할은 없다. VISOR가 대신 하는 일은 다르고 더 조용하다. VISOR의 발견 사항의 "Universal_ID가 없으면 마지막 배열이 쓰인다"를 참조.

죽은 코드: downloadModel(), setup_cli_command() / find_cli_parameters().

패치가 투영된 2D에서 결정된다(VISOR에서도 마찬가지)

버터플라이 패치는 투영된 2D에서 결정된다. 방향 정렬 뒤 크게 기운 악궁에서는 윤곽이 z 방향으로 멀리 떨어진 꼭짓점까지 잡을 수 있다.

VISOR에서도 마찬가지다: 거리는 V[:,:2]를 쓰며(SADT-VISOR sadt_flexreg/make_butterfly.py:127, 133, 147, 159, 레거시 make_butterfly.py:114, 120, 134, 146), Slicer의 미리보기도 클라이언트에서 같은 일을 한다(FlexRegLib/butterfly_preview.py).

10. 문헌

쉬운 설명과 수식: 아틀라스 페이지.

발표된 토대는 AReg IOS: Automatic Registration on IntraOral Scans(Hutin, Anchling, Cevidanes 외, Lecture Notes in Computer Science, 2023)이다. DentalModelSeg에 의한 치관 분할, 공유 중심점에 의한 초기 정렬, 다중 뷰 3D 형상 분석으로 분할한 구개 ROI, 그리고 ICP로 이루어진다. FlexReg는 ROI를 예측하게 하는 대신 작업자가 그리는 쪽의 짝이다.

FlexReg나 MGL 변형을 구체적으로 다룬 논문은 없다. 후자는 아직 발표되지 않은 자체 개발로 보인다. 코드에 인용된 수치(364건의 예측에서 4.2 mm 대 1.2 mm)는 주석 밖의 어디에서도 출처가 제시되지 않는다.

  • AREG(저장소)
  • ALI_IOS(저장소)
  • SlicerAutomatedDentalTools
  • Automated Orientation and Registration of CBCT Scans, LNCS
