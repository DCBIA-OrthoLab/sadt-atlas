FlexReg

구강 스캔(IOS)을 환자별로 정합하는 도구로, 정합 패치(구개 나비꼴, 자유 곡선, 또는 치은-점막 경계 띠)를 신경망으로 예측하지 않고 손으로 만든다 — AREG_IOS의 대화형 대응물이다.

미발표 FlexReg_CLI conda 환경: shapeaxi 참고문헌

1. 파이프라인에서의 위치

저장소의 어떤 코드도 FlexReg를 호출하지 않는다. 운영자가 직접 다루는 말단 도구다. 그러나 사전 학습된 신경망 두 개를 호출하며, AREG_IOS의 입력을 만들어 낸다 — 두 도구는 정확히 같은 점 배열을 읽는다.

호출 대상시점이유
dentalmodelseg (ShapeAXI / DentalModelSeg)메시에 Universal_ID 배열이 없을 때치관을 분할하고 번호를 매김
ALI_IOS(가중치 Lower_MG_*.pth)하악 치열궁 모드에서만치은-점막 경계 랜드마크 13개 배치

하류에서 AREG_IOS.py:191은 vtkMeshTeeth(list_teeth=[1], property="Butterfly")를 수행하고, AREG_IOS.py:205는 MGL_ARRAY_NAME에 대해 같은 일을 한다. 따라서 FlexReg에서 만든 패치는 AREG_IOS가 그대로 사용할 수 있고, 그 반대도 마찬가지다. 차이는 패치의 출처다. AREG_IOS는 신경망으로 패치를 예측하고 (PredPatch.py, 다중 시점 MonaiUNetHRes), FlexReg는 기하학적으로 만든다.

3. 입력과 전처리

함정 — 파일 변환

ensureVtkInput()(FlexReg.py:3454)은 어떤 작업보다 먼저 .stl을 .vtk로 변환한다. 이는 겉치레가 아니다. dental_model_seg.py는 os.remove(args.stl)를 수행하므로, .stl을 직접 넘기면 원본 파일을 지워 버린다.

LPS ↔ RAS 뒤집기. CLI는 .vtk(LPS)를 읽고, Slicer처럼 RAS에서 작업하기 위해 Scale(-1,-1,1)을 적용하며, 쓰기 전에 다시 뒤집는다(FlexReg_CLI.py:39). 따라서 내부 계산은 모두 RAS에서 이루어진다.

정준 좌표계 맞추기 — 핵심 전처리 단계, orientation.py:

  1. Universal_ID 3, 5, 12, 14번 치아(UR6, UR4, UL4, UL6)의 무게중심;
  2. 각 측의 국소 기저: 세 점을 지나는 평면의 법선(중점을 향한 두 벡터의 외적), 그다음 그에 수직인 방향;
  3. 연속된 두 회전. 축 = 외적, 각도 = 내적의 arccos, RotationMatrix(로드리게스 공식) 사용;
  4. 무게중심을 일치시키는 평행이동.

목표는 [[-0.5,-0.5,0], [0,0,0], [0.5,-0.5,0]]이다. 우측 대구치는 x<0, 좌측 대구치는 x>0, 소구치는 원점에 온다. 결과: 교합평면 ≈ z=0, +y = 전방, +x = 좌측. 크기 조절은 없다 — 3점 강체 정합이다.

직접적인 결과로, 이어지는 나비꼴 계산 전체가 XY 평면에서의 2D 계산이며 z 성분은 그냥 무시된다.

4. 모델

4.1 치관 분할 — DentalModelSeg 예측

checkSegmentation()(FlexReg.py:3657)은 배열이 있는지를 검사하지 않는다. 위의 방향 정렬을 시도해 보고 예외를 읽는다.

  • ToothNoExist → 메시는 분할되어 있지만 기준 치아 4개 중 하나가 없음 → 메시지, 중단.
  • NoSegmentationSurf → 분할 배열 없음 → shapeaxi_conda().
conda run -n shapeaxi python -m CrownSegmentationcli \
  <surf> None <out> 1 latest 0 Universal_ID 0 None <vtk_folder> <dentalmodelseg_path>

인자 순서: 표면, 입력 csv, 출력 폴더, overwrite=1, latest 모델, crownsegmentation=0, 배열 이름 Universal_ID, fdi=0, 접미사, vtk 폴더, dentalmodelseg 실행 파일 경로(환경 안에서 which로 찾음).

이 저장소에서 확인할 수 있는 것은 위의 명령줄과 그 효과까지다. 출력은 유니버설 1–32 번호 체계의 점 배열 Universal_ID이며, 입력 파일 안에 기록된다(overwrite=1).

구조와 latest 가중치는 저장소 밖의 pip 패키지 shapeaxi에 있어 여기서는 알 수 없다. 계보(DentalModelSeg는 Fly-by-CNN의 후손이다)로 보면 다중 시점 렌더링 뒤에 시점별 2D 분할과 정점으로의 투표식 재투영이 이어질 것으로 예상되지만, 카메라 수도, 배치도, 렌더링 해상도도 이 저장소에서는 확인할 수 없다 — 이웃한 예가 경고가 된다. PredPatch.py에서 ico_verts라는 이름의 버퍼는 정이십면체 구가 아니라 z=0.9에 모여 있는 카메라 7대를 담고 있다.

함정 — 가정하지 말 것

코드를 읽어 보지 않고 카메라가 구 형태로 배치되어 있다고 가정하지 말 것.

downloadModel()(FlexReg.py:3629)은 Fly-by-CNN .pth(07-21-22_val-loss0.169.pth, 릴리스 3.0)를 내려받는다 — 한 번도 호출되지 않는 사용되지 않는 코드다. 실제로 쓰이는 모델은 latest 모델로, dentalmodelseg에 포함되어 있다.

conda run -n shapeaxi python -m ALI_IOS \
  <scan> <models> None None "LL6MG LL5MG … L0MG … LR6MG" <out> 224 0 1 <log>

위치 인자: input, dir_models, lm_type=None, teeth=None, teeth_mg=<13 names>, output_dir, image_size=224, blur_radius=0, faces_per_pixel=1, log_path.

ALI_IOS도 다중 시점 방식이다(PyTorch3D 렌더링). 분할을 바탕으로 치아마다 카메라 하나를 두고, 시점을 224×224로 렌더링하며, 신경망이 출력하는 히트맵의 최댓값이 점의 위치가 된다. 랜드마크는 해당 치아에 레이블이 있을 때만 배치된다 (Universal_ID / PredictedID) — 그래서 ALI가 13개 점 중 k개만 배치했을 때 FlexReg의 오류 메시지는 분할을 다시 보라고 안내한다.

가중치는 <Documents>/SlicerDownloads/ALI/ALI_IOS/Models/Prediction에서 Lower_MG_*.pth라는 이름으로 찾는다(hasMGLModel, FlexReg.py:2587). 없으면 폴더 선택 창이 열린다.

5. 알고리즘의 핵심

5.1 경로 A — 나비꼴(Butterfly) 패치(상악 치열궁) 계산

make_butterfly.py. 신경망 없이 순수하게 기하학적이다.

a) 무게중심 네 개. 운영자가 치아 4개 (전방 좌/우, 후방 좌/우)를 고르면, vtkMeanTeeth가 그 Universal_ID를 가진 정점들의 평균을 낸다.

b) 파라미터 세 종류를 이 무게중심들에 적용한다:

파라미터효과세부
shift_lr, shift_ap패치 전체를 평행이동같은 벡터를 무게중심 4개 모두에 더한다. 랜드마크는 가중치 합이 1인 아핀 결합이므로 이동량이 보간을 거쳐 그대로 전달되고 모양은 변하지 않는다
adjust(mm)늘이기 / 줄이기±y 방향 오프셋, 후방 치아에서는 부호가 반대: 양의 adjust는 양 끝을 모두 바깥쪽으로 민다
ratio폭이 유지됨r = (1-ratio)/2로 재매개변수화한 뒤 landmark = (1-r)·own_centroid + r·opposite_centroid. ratio=1 → 랜드마크가 자기 무게중심 위(최대 패치), ratio=0 → 랜드마크가 중간 지점(퇴화한 패치)

용어에 주의: UI는 top/bot이라 하고, CLI는 anterior/posterior라 한다. lineedit_teeth_left_top → tooth_anterior_left.

c) 윤곽선, 네 조각:

  • 전방 선분과 후방 선분(Segment2D, 간격 0.01);
  • 좌우 두 개의 2차 베지에 곡선. 제어점은 (posterior_landmark, posterior_midpoint, anterior_landmark)이며, 그다음 현(chord)을 기준으로 반사하여(sym = 2·proj − bezier) 중심이 아니라 치열궁 바깥쪽으로 부풀게 한다. 나비꼴 모양은 여기서 나온다.

d) 표시. torch.cdist로 윤곽선 점들과 XY에 투영한 정점들 사이의 거리를 계산하고, radius = 0.7 mm 이내의 모든 정점을 1로 설정한다.

e) 채우기. Dilation() (propagation.py:73): 형태학적 팽창이 아니라 메시 위의 측지 flood fill이다. 4개 랜드마크의 무게중심에 가장 가까운 정점에서 시작해 이웃에서 이웃으로 전파되며 (GetPointCells / GetCellPoints), 이미 1로 설정된 윤곽선에서 멈춘다. GPU에서 nmb_treatment = 1000 단위로 일괄 처리된다.

f) 기록. 배열 이름은 Butterfly{index}다. 패치마다 고유 인덱스를 가지므로 패치를 누적할 수 있다. CLI 끝에서 모든 Butterfly1..N 배열이 torch.logical_or로 하나의 배열 Butterfly로 병합된다 (FlexReg_CLI.py:229) — ICP와 AREG_IOS가 읽는 것이 이 배열이다. 결과는 입력 파일 안에 다시 기록된다.

delete 모드는 삭제된 인덱스보다 위의 배열들의 번호를 다시 매기고 마지막 배열을 제거하여, 빈 번호를 남기지 않는다.

실시간 미리보기. butterfly_preview.py는 완전히 같은 윤곽선을 순수 numpy(CPU)로 재현하고, flood fill 대신 점-다각형 포함 판정을 쓴다(matplotlib.path.Path, 실패 시 numpy 교차 횟수 방식으로 대체). 방향 정렬과 무게중심은 스캔마다 캐시되므로 (prepare) 조이스틱을 움직일 때마다 윤곽선만 다시 계산된다. 상수: 높이 맵의 CELL = 1.0 mm, 치아 위로 LIFT = 0.4 mm, 변마다 NB_POINTS = 120개 표본.

5.2 경로 B — 그려서 만드는 패치 계산

draw()(FlexReg.py:4239), type="curve". 표면에 구속된 Slicer 곡선 (SetAndObserveSurfaceConstraintNode)과 중간점 하나를 문자열로 직렬화하여 CLI에 넘긴다. draw.py는 연속된 점 사이를 선형 보간하고(간격 0.2, 닫힌 루프), 1.1 mm 이내의 정점을 표시한 뒤, 중간점에서 완전히 같은 Dilation()을 실행한다. 나비꼴과 다른 점은 윤곽선을 얻는 방식뿐이다.

곡선은 카메라를 향하도록 중심을 다시 맞춘 모델 위에 그린다. CLI로 보내기 전에 moveCurve()가 재중심 행렬의 역을 적용하여 파일 좌표계로 되돌린다.

5.3 경로 C — MGL 패치(하악 치열궁) 계산

상악 치열궁에서는 구개가 안정적인 평탄면을 제공하지만, 하악에는 그런 부위가 없다. 대안으로 택한 것이 치은-점막 경계선(mucogingival line)이다. 이 블록 전체는 위젯 안에서 numpy/scipy로 계산된다 — GPU도 CLI도 없다(mgl_patch.py).

a) ALI 예측 정리. DoubtfulLandmarks()는 json의 description을 읽는다. ALI가 점을 강제로 배치했을 때(top-k 픽셀, 치아로 대체, 치아 없음) 기록하는 값이다. 코드 주석에 따르면 예측 364건에서 측정한 결과, 이런 점은 이웃 점들이 이루는 곡선에서 중앙값 4.2 mm 벗어나며, 나머지는 1.2 mm다. 이 점들은 기본적으로 버려지고, 스플라인이 그 빈틈을 잇는다 — 남는 점이 3개 미만이 되는 경우는 예외다. 그다음 CanonicalLandmarks (예전 주석 명명 → 정준 명명, LL7MG 또는 LR7MG의 존재로 감지)와 RecentreNames(치열궁 중간에서 점이 빠져도 번호가 정중선에 고정되도록 함)를 적용한다.

b) 국소 좌표계. LocalFrames(): 치근단(apical) 축은 중심화한 랜드마크의 SVD 세 번째 성분이다(점들이 이루는 띠의 법선으로, 월드 좌표에서 스캔의 방향과 무관하다). 접선은 치열궁을 따른 np.gradient이고, 협측(buccal)은 둘의 외적이며, 안쪽을 향하는 곳에서는 뒤집는다. OrientApical이 치관을 기준으로 부호를 정한다.

c) 띠 만들기. compute()마다:

  1. 운영자 오프셋(협측 / 치근단 / 접선 방향)을 랜드마크에 적용;
  2. 랜드마크를 지나는 vtkParametricSpline, SAMPLES_PER_SEGMENT = 25;
  3. 각 표본을 메시 위로 붙인다(vtkPointLocator) — 보간된 스플라인은 치간 오목부에서 표면을 벗어나기 때문이다;
  4. 실제 길이로 가중된 모서리 그래프에서 이 정점들을 다중 출발점으로 하는 Dijkstra(scipy.sparse.csgraph), limit = 최대 높이, min_only=True, return_predecessors=True → 띠는 표면을 따라 자라며, 표면을 관통하지 않는다(치조정이 얇은 곳에서 전정 쪽 패치가 설측으로 튀어나올 수 없다);
  5. 높이는 랜드마크 사이에서 선형 보간되며(np.interp) 비대칭이다. 치관 쪽은 heights, 전정 쪽은 heights_down이며, 어느 쪽인지는 치근단 성분의 부호로 정한다. 쓰이는 높이는 그 정점에 도달한 시드(seed)의 높이이므로, 높이가 다른 두 구간이 계단 없이 공존한다;
  6. 치관(Universal_ID 18–31, LOWER_TOOTH_LABELS)은 제거한다 — T1과 T2 사이에 움직이기 때문이다;
  7. 랜드마크 자체는 항상 패치에 남는다.

범위: MIN_HEIGHT = 0.0, MAX_HEIGHT = 5.0, DEFAULT_HEIGHT = 2.5 mm. 모든 곳에서 높이가 0이면 점 13개만 남는다. 이는 띠가 점만 있을 때에 비해 무엇을 더하는지 측정하기 위한, 의도된 대조 조건이다.

모서리 그래프는 np.unique(np.sort(edges))로 중복을 제거한 뒤에 coo_matrix로 만든다. 이 중복 제거가 없으면, 두 삼각형이 공유하는 내부 모서리가 희소 행렬에서 합산되어 길이가 두 배가 되고 패치의 도달 범위가 절반이 된다.

출력 배열: Bottom_MGL(MGL_ARRAY_NAME), 미리보기는 Bottom_MGLPreview.

WriteLandmarks()는 편집된 랜드마크를 학습 주석과 마찬가지로 LPS로 기록한다. 따라서 결과 파일을 그대로 코퍼스에 다시 넣을 수 있다.

5.4 정합 계산

Reg.run()(FlexReg.py:1276)은 같은 CLI를 type = "icp"(상악) 또는 "icp_mgl"(하악)로 다시 실행한다. T2가 moving 스캔(lineedit), T1이 fixed 스캔(path_reg)이다.

patch_array = "Bottom_MGL" if args.type == "icp_mgl" else "Butterfly"
option = vtkMeshTeeth(list_teeth=[1], property=patch_array)
icp = ICP([vtkICP()], option=option)
output_icp = icp.run(modelNode, modelNodeT1)

vtkMeshTeeth는 이름과 달리 메시를 만들지 않는다. 패치 배열 값이 1인 정점만 담은 점 구름을 추출한다. 따라서 ICP는 패치 위에서만 실행되며, 치아 위에서는 절대 실행되지 않는다.

icp.GetLandmarkTransform().SetModeToRigidBody()   # 6 dof, no scaling
icp.SetMaximumNumberOfIterations(1000)
icp.StartByMatchingCentroidsOn()                  # initialization

표준 vtkIterativeClosestPointTransform: 최근접 이웃 대응, 강체 최소제곱 추정, 반복. 이 단계에도 학습은 없다.

4×4 행렬은 이어서 T2 메시 전체에 적용되며, 반대쪽 치열궁이 주어지면(lower_arch) 그것에도 적용되어 같은 움직임을 따르게 한다.

6. 후처리와 출력

메시. 패치 type → 입력 파일 안에 다시 기록된다. ICP type → LPS로 다시 뒤집은 뒤 path_output에 <T2 name without extension><suffix>.vtk로 기록된다.

변환, 까다로운 단계 (FlexReg_CLI.py:186):

flip = np.diag([-1, -1, 1, 1])
composed = flip @ matrix_array @ flip     # RAS -> LPS by conjugation
composed_inv = np.linalg.inv(composed)    # ITK convention: fixed -> moving
sitk_tfm = sitk.AffineTransform(3)
sitk_tfm.SetMatrix(composed_inv[:3, :3].flatten())
sitk_tfm.SetTranslation(composed_inv[:3, 3])

파일 <T2 name><suffix>.tfm은 저장소의 다른 모듈에서 재사용할 수 있다.

See 버튼. 완전히 같은 정합을 tempfile.mkdtemp(prefix="FlexReg_see_")에 실행하고, 표시되자마자 이 폴더를 삭제한다(discardTempFolder). 결과 노드는 SetSaveWithScene(False)로 표시되고 ... (preview, not saved)로 이름이 바뀐다. 그 뒤의 파일이 곧 사라지기 때문이다.

표시. 사용자 정의 레이아웃 501, 세 번째 3D 뷰에서 T1은 [255,51,200]/256, T2는 [102,102,255]/256으로 표시된다.

9. 함정과 취약 지점

CLI는 CUDA가 필요하다

Dilation, drawPatch, 그리고 배열의 최종 병합은 모두 CPU 대체 없이 .cuda()를 호출한다. 반면 MGL 패치는 위젯 쪽에서 계산되므로 CUDA 없이도 된다 — 그래서 하악 치열궁에서는 while args.type != "icp_mgl"가 병합을 건너뛴다.

입력 파일이 덮어써진다

패치 모드에서 그렇고, 자동 분할도 입력 파일을 덮어쓴다 (overwrite=1). .stl을 dentalmodelseg에 넘기면 아예 삭제된다 — ensureVtkInput()이 존재하는 이유가 바로 이것이다.

확인된 버그 — vtkICP.__call__

vtkICP.__call__은 변환된 메시가 아니라 source를 그대로 반환한다. list_icp에 방법이 하나뿐이라 여기서는 무해하지만, 여러 단계를 잇는 체인은 작성된 그대로는 동작하지 않는다.

분할 여부 감지가 예외를 통해 이루어진다

Universal_ID가 아닌 다른 배열 이름으로 분할된 메시는 전체 재분할을 일으킨다.

확인된 버그 — GetLabelSurface

GetLabelSurface(vtkSegTeeth.py:29)는 배열들을 순회하다가 선호하는 배열을 찾으면 continue를 수행한다. break여야 한다. 그 결과 반환되는 이름은 선호 배열이 아니라 목록의 마지막 배열 이름이다. automatic_property가 False로 남아 있는 한 무해하며, FlexReg에서는 모든 곳에서 그렇다.

사용되지 않는 코드: downloadModel(), setup_cli_command() / find_cli_parameters().

패치가 투영된 2D에서 결정된다

나비꼴 패치는 투영된 2D에서 결정된다. 방향 정렬 후에도 크게 기울어진 치열궁에서는, 윤곽선이 z 방향으로 멀리 떨어진 정점까지 잡을 수 있다.

10. 문헌

출판된 토대는 AReg IOS: Automatic Registration on IntraOral Scans(Hutin, Anchling, Cevidanes et al., Lecture Notes in Computer Science, 2023)다. DentalModelSeg로 치관을 분할하고, 공통 무게중심으로 초기 정렬한 뒤, 다중 시점 3D 형상 분석으로 구개 관심 영역(ROI)을 분할하고, 마지막으로 ICP를 수행한다. FlexReg는 이를 "ROI를 예측하는 대신 운영자가 그리는" 방식으로 바꾼 대응물이다.

FlexReg나 MGL 변형을 직접 다룬 논문은 없다 — MGL 변형은 지금까지 출판되지 않은 내부 개발로 보인다. 코드에 인용된 수치(예측 364건에서 4.2 mm 대 1.2 mm)는 주석 밖 어디에도 출처가 없다.

  • AREG(저장소)
  • ALI_IOS(저장소)
  • SlicerAutomatedDentalTools
  • Automated Orientation and Registration of CBCT Scans, LNCS
