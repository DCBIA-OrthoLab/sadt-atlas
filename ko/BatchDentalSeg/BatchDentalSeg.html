BatchDentalSeg

CT/CBCT 스캔 묶음에 대해 nnUNetv2_predict를 구동하는 대기열. 서로 바꿔 쓸 수 있는 가중치 번들 네 개(DentalSegmentator와 그 변형 세 개)를 쓰며, 그 주변의 안전장치, 기하 정보 복원, 내보내기 작업 전부를 담당한다.

Dot 2024 · J Dent BATCHDENTALSEG nnUNetv2_predict conda 없음 — Slicer의 Python + nnunetv2 참고문헌

CT/CBCT 스캔의 치아·악안면 일괄 분할. 이 모듈은 신경망이 아니다: 대기열이자 오케스트레이터로서 nnUNetv2_predict를 감싸며, 서로 바꿔 쓸 수 있는 가중치 번들 네 개를 쓴다. 학습은 모두 이 저장소 밖에서 이루어진다. 여기에 작성된 것은 모델 선택, 메모리 안전장치, 기하 정보 복원, 내보내기다.

1. 파이프라인에서의 위치

저장소의 다른 어떤 모듈도 BatchDentalSeg를 호출하지 않으며, BatchDentalSeg도 저장소의 다른 모듈을 호출하지 않는다. 종단 도구다. 다만 외부 Slicer 확장인 NNUNet (SlicerNNUNetLib)에 의존하며, 여기서 세 클래스를 사용한다.

호출 대상출처역할

SlicerNNUNetLib.ParameterNNUNet 확장모델 디렉터리 트리를 검증하고 명령줄을 구성

OpenAnatomyExportSlicerOpenAnatomy 확장glTF 내보내기 전용. 없으면 실행 중에 설치

이 모듈은 DentalSegmentator의 일괄 처리 변형이다(확장 gaudot/SlicerDentalSegmentator). 위젯, 아이콘, 가중치 다운로드 메커니즘을 여기서 재사용한다. BATCHDENTALSEG.py:30에 선언된 기여자에는 원래 팀(Dot, Gajny, Fenioux, Pelletier)과 UoM에서 추가된 인원(Tulissi)이 섞여 있다.

모든 것이 Slicer의 Python 안에서 실행된다. nnUNetv2_predict는 자식 프로세스(QProcess)로, 한 번에 스캔 하나씩 실행된다. AMASSS와는 다르다. AMASSS는 nnU-Net Python API를 프로세스 내에서 호출한다.

Resources/ML은 목록에 없다: MODULE_PYTHON_RESOURCES (CMakeLists.txt)에 등재되지 않았다. 따라서 설치된 확장에서는 이 폴더가 전적으로 실행 중에 생성된다. .pth 파일은 .gitignore로 제외된다.

3. 입력, 폴더 탐색, 이름 규칙

3.1 허용되는 입력

listVolumes() (Queue.py:28)는 네 패턴에 대해 비재귀적 glob을 수행한다: *.nii, *.nii.gz, *.gipl, *.gipl.gz. 하위 폴더는 방문하지 않으며, NRRD는 인식되지 않는다. NRRD는 Slicer의 기본 형식이고, 저장소의 다른 모듈들이 흔히 만들어 내는 형식이다.

volumeStem()은 복합 접미사를 떼어 낸다: case01.nii.gz → case01 (Path.stem이라면 case01.nii가 남는다).

3.2 대기열

항목 하나 = 폴더 하나가 아니라 스캔 하나다 (QueueItem, Queue.py:52): inputPath, outputDir, model, device, status, error, durationSec, autoCrop. 따라서 한 세션에서 서로 다른 모델로 여러 폴더를 쌓아 둘 수 있다.

addFolder()는 <outputDir>/<stem>_Segmentation.nii.gz가 이미 있거나(Skip scans already segmented 체크박스, 기본으로 체크됨) 이미 대기열에 있는 스캔을 건너뛴다.

영속성: 스캔마다 상태가 <outputDir>/.batchdentalseg_queue.json에 다시 기록된다. 다시 로드할 때 running 상태로 남은 스캔(추론 도중 Slicer가 종료된 경우)은 되감겨 pending이 되고, 인덱스도 그 스캔으로 돌아간다.

isChunkBoundary(): chunkSize개 스캔마다(기본 5), _coolDown()이 철저한 정리를 한다. 고아 노드 제거, torch.cuda.empty_cache() + ipc_collect(), gc.collect().

3.3 신경망이 실제로 보는 것

위젯은 아무 전처리도 하지 않는다. SegmentationLogic._prepareInferenceDir()가 slicer.util.exportNode(volumeNode, <tmp>/input/volume_0000.nii.gz)를 수행하며, 전처리는 전부 nnU-Net이 한다: transpose_forward에 따른 축 전치, 계획의 spacing으로 리샘플링, CTNormalization (학습 세트의 0.5% / 99.5% 백분위수로 자른 뒤, 그 평균과 표준편차로 표준화).

이 저장소에 작성된 유일한 전처리는 자동 잘라내기(§5.2)이며, 선택 사항이고 메모리 실패 후 재실행에만 쓰인다.

4.2 코드로 확인한 nnU-Net

그렇다, 이름만이 아니라 실제로 nnU-Net v2다. 증거는 호출 사슬에 있다: Parameter.asArgList()는 말 그대로 다음을 구성한다

nnUNetv2_predict -i <tmp>/input -o <tmp>/output
  -d Dataset111_453CT -tr nnUNetTrainer -p nnUNetPlans -c 3d_fullres
  -f 0 -npp 1 -nps 1 -step_size 0.5 -device cuda -chk checkpoint_final.pth --disable_tta

-d, -tr, -p, -c는 폴더 이름에서 추론된다: 부모 폴더가 Dataset…를 주고, 설정 폴더의 이름을 __로 나눠 (trainer, plan, configuration)을 얻는다. 그래서 다음 구조가 필요하다: Dataset<id>/<trainer>__<plan>__<conf>/fold_<i>/checkpoint_final.pth.

사용자에게 노출되지 않는 매개변수, SlicerNNUNetLib.Parameter의 기본값: stepSize = 0.5, disableTta = True(테스트 시 미러 증강 없음), folds = "0"(단일 fold, 앙상블은 절대 없음), nProcessPreprocessing = nProcessSegmentationExport = 1, macOS에서는 0으로 강제(macOS에서는 multiprocessing 때문에 nnU-Net이 쓰기 단계에서 멈춘다).

UI가 제공하는 유일한 설정은 장치다: cuda / cpu / mps. 사용할 수 없으면 대기열 전체에 대해 질문이 한 번만 나오고 (_deviceFallbackAccepted), Unattended 모드에서는 CPU 폴백이 자동으로 수락된다.

nnUNet_raw, nnUNet_preprocessed, nnUNet_results는 모두 모델 폴더를 가리킨다. 프로세스 수준 환경 변수 세 개이며, SegmentationLogic._startInferenceProcess가 기록한다. os.environ은 전역이므로, 같은 Slicer 세션에서 동시에 실행되는 두 추론은 서로 간섭할 것이다. 여기서는 대기열이 엄격히 순차적이므로 문제가 생기지 않는다.

4.3 아키텍처와 계획 — 확인 가능한 것

저장소에 JSON 파일이 있는 것은 Dataset111_453CT(DentalSegmentator)뿐이다. plans.json 요약:

UNet_class_name = PlainConvUNet     base/max features = 32 / 320

pool_op_kernel_sizes = [1,1,1], 4 x [2,2,2], [2,2,1]   conv_kernel 6 x [3,3,3]
patch_size = [128, 160, 112]    spacing = [0.4492, 0.3120, 0.4492] mm

이 plans.json은 nnU-Net 2.4 이전 형식이다(평면 UNet_class_name / pool_op_kernel_sizes 필드, architecture 블록 없음). 반면 AMASSS 번들은 새 형식을 쓴다. 둘 다 현재 nnunetv2에서 읽을 수 있다.

나머지 세 모델의 계획은 저장소로부터 확인할 수 없다: 다운로드와 함께 들어온다. 이들에 대해 알려진 것은 모두 위젯에 하드코딩된 딕셔너리(§4.4)와 README에서 나온다.

4.4 모델별 생성 레이블

_get_active_label_map() (SegmentationWidget.py:1847)이 기준 표다: 출력 NIfTI에 기록되는 값을 이 표가 정한다.

DentalSegmentator와 PediatricDentalsegmentator — 레이블 5개로 동일하며, 번들 111의 dataset.json으로 확인된다: 1 Upper Skull(상악골 포함), 2 Mandible, 3 Upper Teeth, 4 Lower Teeth, 5 Mandibular canal. 따라서 둘을 구분하는 것은 출력이 아니라 학습 데이터다: 영구치열 (453CT, 7개 기관) 대 혼합치열(380CT). 코드는 둘을 엄밀하게 똑같이 다룬다. 레이블 표도, 색도, 후처리도 같고, _modelBasePath만 다르다.

NasoMaxillaDentSeg — 레이블 6개, 상악골이 두개골에서 분리되어 있다: 1 Upper Skull, 2 Mandible, 3 Maxilla, 4 Upper Teeth, 5 Lower Teeth, 6 Mandibular canal.

UniversalLabDentalsegmentator — 레이블 55개: 영구치 32개에 하나씩 번호를 매기고(1 = 상악 우측 제3대구치(3rd molar) → 32 = 하악 우측 제3대구치(3rd molar), 상악 치열궁을 돈 뒤 하악 치열궁을 도는 순서), 이어서 유치 20개(33 → 52), 그다음 Mandible = 53, Maxilla = 54, Mandibular canal = 55. "Upper Skull"은 없다: UI 설명이 보여 주는 것, README가 말하는 것과 달리 이 모델은 두개관을 분할하지 않는다. 번호 매김은 임의가 아니다. 레이블 하나하나가 그렇다. 값 1–32는 정확히 Universal Numbering System이고(1 = 우측 상악 제3대구치 … 32 = 우측 하악 제3대구치), 33–52는 유치에 쓰는 그 체계의 문자 A–T다. 따라서 레이블의 FDI 대응 번호는 고정되어 있다 — 아래 그림이 둘을 함께 보여 준다.

함정

UI에 표시되는 UniversalLabDentalsegmentator의 설명과 저장소 README는 두개관 분할을 예고한다. 실제 모델에는 "Upper Skull" 레이블이 없다: 치아에 번호를 매기고, 하악골/상악골/하악관을 더할 뿐이다.

값은 각 세그먼트에 LabelValue 태그로 설정되며 (_segmentLabelValue), 태그가 있으면 이름보다 우선한다.

5. 학습되지 않은 핵심부

5.1 레이블 맵 재구성과 기하 정보 복원

_buildLabelArray() (SegmentationWidget.py:1912):

ExportSegmentsToLabelmapNode를 한 번만 호출하되, segmentId의 명시적 목록을 넘긴다(이것이 "내보낸 값 i+1 ↔ segIds[i]" 대응을 고정한다). 그다음 numpy LUT가 한 번의 패스로 공식 값으로 다시 매핑한다 (lut[exported]). 이전 버전은 세그먼트마다 볼륨 전체 범위를 한 번씩 래스터화했다: UniversalLab에서는 전악 CBCT를 55번 래스터화한 셈이다.

5.2 자동 잘라내기(메모리 실패 후 재실행)

선택 사항이며, 명시적 확인 후 Retry failed로 시작된다. _applyAutoCrop() (SegmentationWidget.py:1017):

  • 스케일에 관계없이 동작하는 공기/조직 임계값: array.min() < −800이면 Hounsfield 단위이며 임계값은 −500, 그렇지 않으면 min + 0.15 × (p99.5 − min);
  • 임계값을 넘는 복셀의 경계 상자를 _CROP_MARGIN_MM = 15.0 mm(축마다 복셀로 환산)만큼 확장;
  • 복셀의 _CROP_MIN_GAIN = 0.85보다 많이 남으면 잘라내기를 포기한다: 15% 미만을 줄이자고 위험을 감수할 가치는 없다;
  • 부분 볼륨은 간격과 축을 유지하며, 원점만 이동한다 (ijkToRas.MultiplyPoint([i0,j0,k0,1])). 보간은 전혀 없다.

_restoreCropToOriginalGrid()는 단순한 인덱스 오프셋으로 레이블 맵을 원래 크기의 배열에 다시 붙여 넣는다: 따라서 출력은 항상 촬영된 스캔의 격자 위에 있다.

5.3 메모리 보호 — 세 겹의 방어

코드 주석이 실제 사례를 알려 준다: 한 스캔이 125 GB 컴퓨터에서 114 GB를 채우고 OOM killer에 의해 종료되었는데, multiprocessing 워커가 살아남아 메모리를 계속 붙잡고 있었다.

a) 사전 추정, _estimatePeakRamGb() (SegmentationWidget.py:1161). 시야의 물리적 부피는 간격과 무관하므로, 리샘플링된 복셀 수는 fovMm3 / targetVoxelMm3와 같다. 최대치는 convert_predicted_logits_to_segmentation_with_correct_shape에서 도달하며, 여기서 클래스마다 다음이 공존한다: 슬라이딩 윈도 누산기(리샘플링된 격자 위의 torch.half, 2바이트), 그 float64 사본(4D 배열 전체에 한 번에 적용되는 data = data.astype(float), 8바이트), 그리고 reshaped_final(원 격자 위의 torch.half, 2바이트). 따라서 logitsGb = (10 × C × Vresampled + 2 × C × Voriginal) / 2³⁰에, 8 × (Voriginal + Vresampled)(skimage.resize의 float64 임시 배열)를 더하고, _RAM_FIXED_OVERHEAD_GB = 4.0(torch, 가중치, 워커)을 더한다. spacing과 레이블 수는 같은 설정 폴더에서 읽는다. 한 모델의 간격과 다른 모델의 레이블 수를 섞지 않기 위해서다.

예산 = free RAM × ramLimitSpinBox(기본값 85%). 이를 넘으면 스캔은 이유와 함께 failed로 표시되며, nnU-Net은 시작조차 하지 않는다.

b) 실행 중 감시: _onMemCheck가 _RAM_SAMPLE_MS = 3000 ms마다 표본을 채취한다. 종료하려면 _RAM_CONSECUTIVE_HITS = 2번 연속 초과가 필요하다(일시적 급등 때문에 멀쩡한 스캔을 버려서는 안 된다).

c) 메모리 회수: _killInferenceTree()는 트리 전체를 종료한다. QProcess.kill()은 직계 자식에게만 닿는데, nnU-Net은 multiprocessing을 쓰기 때문이다. _reclaimStrayProcesses()는 명령줄에 nnunetv2_predict, nnunetv2/inference, nnunet이 들어 있으면서 더 이상 소유자가 없는 프로세스를 정리한다. Free memory 버튼은 이를 수동으로 수행한다.

5.4 보조 완료 감지

_checkInferenceCompletionFallback() (SegmentationWidget.py:2514): nnU-Net 출력에 "done with volume" 줄이 나타나면, 타이머가 1.5초마다 출력 파일 크기를 확인한다. 연속 두 번 같은 값이면 ⇒ QProcess의 finished 시그널이 오지 않았더라도 강제로 마무리한다. 40번 시도(60초) 후에는 포기한다.

추가 안전장치: 스캔별 감시 타이머 (itemTimeoutSpinBox, 기본 60분)가 스캔을 실패로 표시하고 다음 스캔으로 넘어간다. _finishCurrentItem이 유일한 종료 지점이며, _itemFinalized로 이중 진행을 막는다.

5.5 좌우 반전 보정(UniversalLab 전용)

onResolveMirroring() (SegmentationWidget.py:1308), UniversalLab에서만 보이는 버튼. 신경망이 좌우를 자주 혼동하며, 보정은 순수하게 기하학적이다:

  1. 공식 레이블 맵 재구성(§5.1), 그다음 전경 복셀마다 RAS R 좌표를 numpy로 계산(m00·x + m01·y + m02·z + m03). 이전 버전은 복셀마다, 레이블마다 vtkMatrix4x4.MultiplyPoint를 한 번씩 호출했다;
  2. 시상면 = 네 중절치(레이블 8, 9, 24, 25)의 R 무게중심 평균. 하나라도 없으면 보정을 거부한다;
  3. 좌우가 있는 레이블마다, 평면의 반대쪽에 있는 복셀은 대칭 레이블의 값을 받는다 (이름에서 left ↔ right를 바꿔 만든 표). {53, 54, 55}는 보호된다.

결과는 새 노드 <name>_Mirrored에 들어가며, 원본은 유지된다.

5.6 빠진 후처리

함정

_postProcessSegments()는 로그 두 줄만 남긴다. _keepLargestIsland()와 _removeSmallIsland()( _minimumIslandSize_mm3 = 60을 쓸 예정이었던 것)는 어디에서도 호출되지 않는다. 원 DentalSegmentator에서 물려받은 사용되지 않는 코드다. 따라서 형태학적 정리는 전혀 적용되지 않는다: 나오는 것은 nnU-Net의 원시 출력이며, 번들에 내부 후처리가 있으면 그것만 적용된다.

6. 출력

onInferenceFinished는 어떤 형식이 체크되었든 항상 <outputFolder>/<stem>_Segmentation.nii.gz를 쓴다: _get_active_label_map의 값을 담고, 원본 볼륨의 기하 정보(간격, 원점, IJKToRAS)를 따르는 레이블 맵이다. 잘라내기가 있었다면 잘라내기 전 상태로 되돌린다. 이것이 expectedOutputPath()가 스캔이 이미 처리되었는지 판단할 때 찾는 파일이다.

추가 형식은 체크박스로 고르며, 모두 같은 폴더에 기록된다:

형식함수이름 규칙세부
STL, OBJExportSegmentsClosedSurfaceRepresentationToFiles세그먼트마다 파일 하나스무딩 1.0, 병합 없음
VTK(레이블별)_exportVTKPerLabel<segNodeName>_<labelName>.vtk정리 → vtkWindowedSincPolyDataFilter(60회, passBand 0.05, 경계/날카로운 모서리/non-manifold 스무딩) → 셀 법선 → vtkQuadricDecimation 40% → RAS→LPS 반전(Scale(-1,-1,1)), 바이너리
VTK(병합)_exportMergedVTK<segNodeName>_merged.vtkvtkDiscreteMarchingCubes 존재하는 레이블마다 윤곽선 하나, 같은 스무딩 사슬, 그다음 레이블별 임계 처리, 40% 간소화, 상수 Label 셀 배열, 연결, LPS 반전
NIfTI(체크박스)ExportSegmentsBinaryLabelmapRepresentationToFiles세그먼트마다 이진 .nii.gz 하나위의 레이블 맵과 혼동하지 말 것
glTFOpenAnatomyExport간소화 비율 조절 가능(기본 0.9). 필요하면 SlicerOpenAnatomy를 설치

메시 파일 이름은 스캔 이름이 아니라 분할 노드의 이름, <stem>_Segmentation에서 나온다. 세그먼트 이름은 re.sub(r"[^0-9A-Za-z_-]+", "_", ...)로 정리된다.

메시 내보내기 실패는 스캔을 실패로 만들지 않는다: NIfTI는 이미 기록되었고, 스캔은 done으로 표시되며 export warning이 붙는다.

확인됨 — 코드에서 수정됨

_exportMergedVTK의 코드에 기록된, 수정된 버그: vtkDiscreteMarchingCubes.SetValue는 레이블 값이 아니라 윤곽선 인덱스를 받는다. 레이블을 인덱스로 넘기면 인덱스 0이 윤곽선 값 0.0으로 남아서, 배경이 윤곽선 추출, 스무딩, 법선 계산을 거친 뒤에야 버려졌다.

8. 실행 환경

세션당 한 번, 첫 Apply 시에 _runSetupThenStartQueue() (SegmentationWidget.py:1651)가 설치한다:

  1. pip install light-the-torch, 그다음 python -m light_the_torch install torch torchvision — ltt가 감지된 드라이버에 맞는 CUDA 휠을 고르며, 버전은 고정되지 않는다;
  2. pip install numexpr>=2.10.2;
  3. pip install numpy<2.0 numexpr>=2.10.2 psutil, PipRunner(UI에 제어를 돌려주는 QProcess)를 통해;
  4. SlicerNNUNetLib.InstallLogic().setupPythonRequirements(): nnunetv2, 이 저장소 밖;
  5. PythonDependencyChecker.downloadWeightsIfNeeded(): DentalSegmentator 가중치 만.

numpy<2.0인 이유는 AMASSS와 같다: 현재 torch 휠은 numpy 1.x에 맞춰 컴파일되어 있다.

NNUNet 확장은 수동으로 설치해야 한다: 없으면 감지되어(import SlicerNNUNetLib) 설치 후 재시작하라는 메시지가 나온다. 반면 SlicerOpenAnatomy는 첫 glTF 내보내기 때 스스로 설치된다.

conda 환경도, WSL도 없다. GPU는 선택 사항이며(cpu, mps 사용 가능), 폴백 메시지에 따르면 그 대가는 "스캔당 약 1시간"이다.

9. 함정과 취약 지점

확인된 버그 — NasoMaxillaDentSeg

NasoMaxillaDentSeg에서 세그먼트 이름과 레이블 표가 어긋난다. _get_active_label_map은 Maxilla = 3, Upper Teeth = 4, Lower Teeth = 5, Mandibular canal = 6을 주는데, _updateSegmentationDisplay (SegmentationWidget.py:2385)는 Segment_1..6의 이름을 다음 목록으로 바꾼다: ["Upper Skull", "Mandible", "Upper Teeth", "Lower Teeth", "Mandibular canal", "Maxilla "].

첫 번째 효과는 내보내기 문제 이전에 화면에서 보인다: 목록이 표의 순서와 다르므로, 마지막 네 세그먼트가 잘못된 이름, 잘못된 색, 잘못된 불투명도를 받는다.

세그먼트실제 구조표시되는 이름
Segment_3Maxilla"Upper Teeth"
Segment_4Upper Teeth"Lower Teeth"
Segment_5Lower Teeth"Mandibular canal"
Segment_6Mandibular canal"Maxilla"(끝에 공백 포함)

수정 방법은 공백만 지우는 것이 아니라, 목록(과 함께 쓰이는 colors, opacities 목록)을 _get_active_label_map에 맞게 다시 정렬하는 것이다.

그런데 이름 변경은 먼저 일어나고, 그 뒤에 LabelValue 태그가 설정되며, _segmentLabelValue는 이때 이름으로 폴백한다: 실제로 레이블 3(상악골)을 담은 Segment_3은 "Upper Teeth"로 이름이 바뀌어 값 4로 내보내진다. 더 나쁜 것은, "Maxilla "에 끝 공백이 있다는 점이다: 표 조회가 실패하고, Segment_6(하악관)은 "unexpected segment"로 로그에 남은 채 NIfTI에서 사라진다. 반면 나머지 세 모델에서는 두 목록이 완벽하게 대응한다.

  • onApplyClickedForVolume의 네 분기는 복사해 붙인 것이다: UniversalLab 분기는 여전히 변수 이름이 pediatricCheckpoint이고 "Downloading pediatricdentalseg model…"을 로그에 남긴다. 겉모습의 문제이지만, 로그를 읽을 때 오해를 부른다.
함정

DentalSegmentator 가중치를 다운로드하면 나머지 세 모델이 지워진다: downloadWeights()는 shutil.rmtree(self.destWeightFolder)를 Resources/ML에 대해 수행하는데, 이 폴더에는 Dataset001_380CT, Dataset001_max4, Dataset002_380CT도 들어 있다. 그리고 areWeightsMissing()은 rglob("dataset.json")을 어디서든 찾는다(Resources/ML 아래 전체): 소아용 모델만 있어도 검사기는 DentalSegmentator가 설치되어 있다고 믿는다.

함정

취약한 릴리스 해석: 모든 릴리스의 모든 에셋 중 assets[0]을 쓰며, 인증되지 않은 GitHub 클라이언트를 통한다(IP당 시간당 60회 요청). 최신 릴리스의 맨 앞에 에셋이 추가되면 다운로드되는 모델이 바뀐다. 또한 하나씩 다운로드되는 세 체크포인트에 대해 무결성 검사가 없다: 잘린 파일과 완전한 파일을 구별할 수 없다.

  • NRRD가 인식되지 않고 하위 폴더를 탐색하지 않는다 (listVolumes). 반면 저장소의 다른 모듈들은 NRRD와 폴더 트리를 흔히 만들어 낸다. 이름 충돌이 가능하다: 다른 폴더에 있는 두 스캔이 같은 기본 이름을 가지면 같은 <stem>_Segmentation.nii.gz를 덮어쓴다.
  • 단일 fold, 앙상블은 절대 없음(folds="0"): 번들에 fold_1..4가 들어 있어도 무시된다.
  • os.environ['nnUNet_results']는 스캔마다 SegmentationLogic이 다시 쓴다: 여기서는 무해하지만(순차 대기열), 같은 Slicer 세션에서 다른 nnU-Net 추론이 실행되면 위험하다.
  • 사용되지 않는 코드: _saveSegmentationAsNifti, _postProcessSegments, _keepLargestIsland, _removeSmallIsland, onExportClicked(해당 버튼이 일괄 처리 레이아웃에 연결되어 있지 않다).
함정

Resources/ML은 CMake로 설치되지 않는다: 패키지된 확장에는 저장소의 dataset.json / plans.json이 없으며, 가중치가 다운로드되기 전까지 사전 메모리 추정(§5.3)은 None을 반환한다. 이 경우 스캔을 그대로 통과시킨다.

10. 문헌

DentalSegmentator는 발표되었다:

Dot G., Chaurasia A., Dubois G., Savoldelli C., Haghighat S., Azimian S., Rahbar Taramsari A., Sivaramakrishnan G., Issa J., Dubey A., Schouman T., Gajny L. DentalSegmentator: robust open source deep learning-based CT and CBCT image segmentation. Journal of Dentistry 147:105130, 2024. doi:10.1016/j.jdent.2024.105130 — PMID 38878813

nnU-Net v2(가중치의 Zenodo 서지 정보에 따르면 v2.2), 학습에는 7개 기관의 CT 및 CBCT 스캔 470건, 구조 5개, 256건의 hold-out 테스트 (내부 133건, 외부 123건): DSC 내부 92.2 ± 6.3%, 외부 94.2 ± 7.4%. 여기 포함된 dataset.json은 numTraining = 453을 밝히며, 기술된 말뭉치와 일치한다.

확인됨

이 모델에 대해서는 코드와 논문이 일치한다. 가중치는 Zenodo에도 CC-BY-4.0으로 공개되어 있다 (concept DOI 10.5281/zenodo.10829674). 다만 이 모듈은 Zenodo가 아니라 GitHub 릴리스에서 가중치를 가져온다.

방법론적 기반:

Isensee F., Jaeger P.F., Kohl S.A.A., Petersen J., Maier-Hein K.H. nnU-Net: a self-configuring method for deep learning-based biomedical image segmentation. Nature Methods 18(2):203-211, 2021. doi:10.1038/s41592-020-01008-z

세 변형 모델은 저장소에서 어떤 출판물과도 연결되어 있지 않다. 저장소 README는 PediatricDentalSegmentator와 UniversalLabDentalSegmentator에 대해 혼합치열 CBCT 스캔 513건을, NasoMaxillaDentalSegmentator에 대해 135건을 제시하지만, 참고문헌도 테스트 세트도 없다. 이 수치는 코드 어디에서도 확인할 수 없다: 해당 dataset.json 파일은 가중치 다운로드와 함께 들어올 뿐이다. 이를 다루는 출판물이 나올 때까지는 내부 주장으로 취급할 것.
