BatchDentalSeg, 레거시: 코드

개발자용: 레거시 Slicer 모듈이 코드에서 하는 일을 file:line 참조, 시그니처, 표, 함정과 함께 다룬다. 같은 파이프라인에 대한 읽기 쉬운 설명과 수식은 아틀라스 페이지에 있다. CT/CBCT 스캔 배치에 nnUNetv2_predict를 돌리는 대기열이며, 교체 가능한 가중치 번들 넷(DentalSegmentator와 그 변형 셋)과 그 둘레의 안전 장치, 기하 복원, 내보내기를 모두 갖춘다.

코드 아틀라스 (해설) Dot 2024 · J Dent BATCHDENTALSEG nnUNetv2_predict conda 없음: Slicer의 Python + nnunetv2 VISOR 참고문헌

CT/CBCT 스캔의 치악안면 일괄 분할. 이 모듈은 신경망이 아니다. 교체 가능한 가중치 번들 넷을 갖춘 nnUNetv2_predict 둘레의 대기열이자 오케스트레이터이다. 학습은 모두 이 저장소 밖에서 이루어지며, 여기에 쓰인 것은 모델 선택, 메모리 안전 장치, 기하 복원, 내보내기이다.

두 코드 베이스

아래에 번호가 매겨진 모든 내용은 레거시 Slicer 모듈(3c67957 시점의 SlicerAutomatedDentalTools, 2026-10-26)을 설명한다. 같은 도구를 서버에서 실행하는 VISOR 포팅은 별도 페이지인 VISOR의 BatchDentalSeg에서 설명한다.

1. 파이프라인에서의 위치

저장소의 어떤 모듈도 BatchDentalSeg를 호출하지 않으며, BatchDentalSeg도 저장소의 다른 모듈을 호출하지 않는다. 끝점에 있는 도구이다. 다만 외부 Slicer 확장인 NNUNet(SlicerNNUNetLib)에는 의존하며, 거기서 클래스 셋을 쓴다.

호출되는 것출처역할
SlicerNNUNetLib.InstallLogicNNUNet 확장setupPythonRequirements(): Slicer의 Python에 nnunetv2를 설치한다
SlicerNNUNetLib.ParameterNNUNet 확장모델 디렉터리 트리를 검증하고 명령줄을 만든다
SlicerNNUNetLib.SegmentationLogicNNUNet 확장볼륨을 NIfTI로 임시 폴더에 쓰고, nnUNetv2_predict를 QProcess로 실행하며, 분할을 다시 불러온다
OpenAnatomyExportSlicerOpenAnatomy 확장glTF 내보내기 전용이며, 없으면 그 자리에서 설치된다

이 모듈은 DentalSegmentator의 배치 변형(확장 gaudot/SlicerDentalSegmentator)이며, 위젯, 아이콘, 가중치 내려받기 메커니즘을 거기서 재사용한다. BATCHDENTALSEG.py:35-41에 선언된 기여자는 원래 팀(Dot, Gajny, Fenioux, Pelletier)과 UoM에서 더해진 사람(Tulissi)이 섞여 있다.

쉬운 설명과 수식: 아틀라스 페이지.

모든 것이 Slicer의 Python 안에서 실행된다. nnUNetv2_predict는 자식 프로세스(QProcess)로 한 번에 스캔 하나씩 실행된다. nnU-Net Python API를 같은 프로세스에서 호출하는 AMASSS와 다르다.

3.1 받아들이는 것

listVolumes()(Queue.py:28)는 비재귀 glob을 네 패턴 *.nii, *.nii.gz, *.gipl, *.gipl.gz에 대해 한다. 하위 폴더는 방문하지 않으며, NRRD는 인식되지 않는다. Slicer의 기본 형식이자 저장소의 다른 모듈이 흔히 만드는 형식인데도 그렇다.

volumeStem()은 복합 접미사를 떼어 낸다. case01.nii.gz → case01(Path.stem은 case01.nii를 남긴다).

쉬운 설명과 수식: 아틀라스 페이지.

3.2 대기열

항목 하나는 스캔 하나이며 폴더 하나가 아니다(QueueItem, Queue.py:52). inputPath, outputDir, model, device, status, error, durationSec, autoCrop을 가진다. 따라서 모델이 다른 폴더 여럿을 같은 세션에 쌓아 둘 수 있다.

addFolder()는 <outputDir>/<stem>_Segmentation.nii.gz가 이미 있거나(이미 분할된 스캔 건너뛰기 체크박스, 기본값은 체크됨) 이미 대기열에 있으면 그 스캔을 건너뛴다.

영속성: 상태는 스캔이 끝날 때마다 <outputDir>/.batchdentalseg_queue.json에 다시 쓰인다. 다시 불러올 때 running에 남아 있던 스캔(추론 도중 Slicer가 종료됨)은 pending으로 되감기고 인덱스도 그 스캔으로 돌아간다.

isChunkBoundary(): chunkSize개 스캔마다(기본값 5) _coolDown()이 깊은 정리를 하고, 고아 노드를 제거하고, torch.cuda.empty_cache() + ipc_collect(), gc.collect()를 실행한다.

쉬운 설명과 수식: 아틀라스 페이지.

3.3 신경망이 실제로 보는 것

위젯은 아무것도 전처리하지 않는다. SegmentationLogic._prepareInferenceDir()가 slicer.util.exportNode(volumeNode, <tmp>/input/volume_0000.nii.gz)를 하고, 전처리는 모두 nnU-Net의 몫이며 순서는 다음과 같다(nnunetv2 2.8.1, preprocessing/preprocessors/default_preprocessor.py, VISOR의 환경에서 읽음. 레거시 설치가 실행하는 버전은 기록되어 있지 않다). transpose_forward에 따른 전치(:56), 0이 아닌 영역으로 크롭(:65), 정규화(:82, 주석에 리샘플링보다 먼저 와야 한다고 적혀 있음), 그다음 계획의 spacing으로 리샘플링(:88). CTNormalization은 nnU-Net의 표준 정의이다(preprocessing/normalization/default_normalization_schemes.py:58-72). 학습 세트의 0.5% / 99.5% 백분위수로 계획에 따라 클립하고, 그 평균을 빼고, max(std, 1e-8)로 나눈다. 여기서 읽은 계획은 DentalSegmentator의 것뿐이며(plans.json: p0.5 −110, p99.5 3067, 평균 1274, std 558), 나머지 세 모델에 같은 방식이 적용된다는 것은 가정일 뿐 확인하지 않았다(§4.3).

이 저장소에 쓰인 유일한 전처리는 자동 크롭(§5.2)이며, 선택 사항이고 메모리 실패 뒤의 재실행에만 쓰인다.

쉬운 설명과 수식: 아틀라스 페이지.

4.2 nnU-Net, 코드에서 확인함

그렇다. 이것은 이름만이 아니라 실제로 nnU-Net v2이다. 근거는 호출 체인에 있다. Parameter.asArgList()가 말 그대로 다음을 만든다.

nnUNetv2_predict -i <tmp>/input -o <tmp>/output
  -d Dataset111_453CT -tr nnUNetTrainer -p nnUNetPlans -c 3d_fullres
  -f 0 -npp 1 -nps 1 -step_size 0.5 -device cuda -chk checkpoint_final.pth --disable_tta

-d, -tr, -p, -c는 폴더 이름에서 추론된다. 상위 폴더가 Dataset…을 주고, 설정 폴더의 이름은 __로 나뉘어 (trainer, plan, configuration)이 된다. 그래서 Dataset<id>/<trainer>__<plan>__<conf>/fold_<i>/checkpoint_final.pth라는 요구 조건이 나온다.

사용자에게 노출되지 않는 매개변수이며, 기본값은 SlicerNNUNetLib.Parameter에서 온다. stepSize = 0.5, disableTta = True(테스트 시 미러 증강 없음), folds = "0"(폴드 하나, 앙상블은 절대 아님), nProcessPreprocessing = nProcessSegmentationExport = 1이며, macOS에서는 0으로 강제된다(멀티프로세싱 때문에 nnU-Net이 거기서 쓰기 중에 멈춘다).

패치 배치와 가우시안 가중치는 모듈이 아니라 nnU-Net의 것이다. 스텝은 패치의 최대 step_size배이며 패치가 영상 가장자리에서 끝나도록 줄어들므로, 0.5에서는 적어도 절반이 겹친다(nnunetv2 2.8.1, inference/sliding_window_prediction.py:30-54). 가중치는 패치의 8분의 1을 퍼짐으로 갖는 가우시안이다(:11-16, 호출 위치는 inference/predict_from_raw_data.py:626). 복셀의 레이블은 레이블에 대한 argmax이며(utilities/label_handling/label_handling.py:178), 동점이면 첫 최댓값을 돌려준다(NumPy와 PyTorch의 문서화된 동작).

UI가 제공하는 유일한 설정은 장치이다. cuda / cpu / mps. 쓸 수 없으면 전체 대기열에 대해 질문이 한 번만 나오며(_deviceFallbackAccepted), 무인 모드에서는 CPU 대체가 자동으로 받아들여진다.

nnUNet_raw, nnUNet_preprocessed, nnUNet_results는 모두 모델 폴더를 가리킨다. 프로세스 수준 환경 변수 셋이며 SegmentationLogic._startInferenceProcess가 쓴다. os.environ은 전역이므로 같은 Slicer 세션에서 추론 둘이 동시에 돌면 서로 밟는다. 여기서는 대기열이 엄격히 순차적이어서 이 문제가 생기지 않는다.

쉬운 설명과 수식: 아틀라스 페이지.

4.3 아키텍처와 계획: 확인할 수 있는 것

JSON 파일이 저장소에 있는 것은 Dataset111_453CT(DentalSegmentator)뿐이다. plans.json의 요약은 다음과 같다.

UNet_class_name = PlainConvUNet     base/max features = 32 / 320
n_conv_per_stage encoder [2,2,2,2,2,2]  decoder [2,2,2,2,2]
pool_op_kernel_sizes = [1,1,1], 4 x [2,2,2], [2,2,1]   conv_kernel 6 x [3,3,3]
patch_size = [128, 160, 112]    spacing = [0.4492, 0.3120, 0.4492] mm
transpose_forward = transpose_backward = [1, 0, 2]     batch_size = 2, batch_dice
normalization_schemes = CTNormalization
foreground intensities: median 1317, mean 1274, s 558, p0.5 -110, p99.5 3067

이 plans.json은 2.4 이전의 nnU-Net 형식이다(평평한 UNet_class_name / pool_op_kernel_sizes 필드, architecture 블록 없음). 반면 AMASSS 번들은 더 새로운 형식을 쓴다. 둘 다 현재의 nnunetv2가 읽을 수 있다.

나머지 세 모델의 계획은 저장소에서 알 수 없다. 내려받을 때 들어오기 때문이다. 그것들에 대해 알려진 모든 것은 위젯에 하드코딩된 딕셔너리(§4.4)와 README에서 나온다.

쉬운 설명과 수식: 아틀라스 페이지.

4.4 모델별로 만들어지는 레이블

_get_active_label_map()(SegmentationWidget.py:1945)은 기준 표이다. 출력 NIfTI에 쓰이는 값을 결정한다.

DentalSegmentator와 PediatricDentalsegmentator는 레이블 5개가 같으며, 번들 111의 dataset.json이 이를 확인해 준다. 1 Upper Skull(상악 포함), 2 Mandible, 3 Upper Teeth, 4 Lower Teeth, 5 Mandibular canal. 따라서 둘을 가르는 것은 출력이 아니라 학습 데이터이다. 영구치열(453CT, 기관 7곳) 대 혼합치열(380CT)이다. 코드는 둘을 엄밀히 똑같이 다룬다. 레이블 표, 색, 후처리가 같고 _modelBasePath만 다르다.

NasoMaxillaDentSeg, 레이블 6개, 상악이 두개골에서 분리됨: 1 Upper Skull, 2 Mandible, 3 Maxilla, 4 Upper Teeth, 5 Lower Teeth, 6 Mandibular canal.

UniversalLabDentalsegmentator, 레이블 55개: 영구치 32개에 하나씩 번호가 붙으며(1 = 오른쪽 위 제3대구치 → 32 = 오른쪽 아래 제3대구치, 위 치열궁을 돈 다음 아래 치열궁을 돎), 이어서 유치 20개(33 → 52), 그다음 Mandible = 53, Maxilla = 54, Mandibular canal = 55이다. "Upper Skull"은 없다. 이 모델은 UI 설명이 보여 주는 것이나 README가 말하는 것과 달리 두개궁을 분할하지 않는다. 번호는 임의가 아니다. 레이블별로 보면 값 1–32는 정확히 범용 치아 번호 체계(Universal Numbering System)(1 = 오른쪽 위 제3대구치 … 32 = 오른쪽 아래 제3대구치)이고, 33–52는 유치의 문자 A–T이므로, 레이블의 FDI 대응은 고정되어 있으며 아래 그림이 둘 다 보여 준다.

함정(모델에 관한 사실은 VISOR에서도 유효하지만, 인터페이스 문구는 그렇지 않다)

UniversalLabDentalsegmentator에 대해 UI가 보여 주는 설명과 저장소의 README는 두개궁 분할을 알린다. 실제 모델에는 "Upper Skull" 레이블이 없다. 치아에 번호를 매길 뿐이며, 여기에 하악/상악/관이 더해진다.

레거시(3c67957): 설명은 "Segments: Upper Skull, Mandibular Canal, All teeth"로 되어 있으며(SegmentationWidget.py:68-72), 레이블 표에는 Upper Skull이 없다(SegmentationWidget.py:1949-1974). VISOR: 모델 설명이 수정되었고("Every tooth labelled individually in Universal numbering, deciduous teeth included, plus Mandible, Maxilla and Mandibular canal", SADT-VISOR sadt_batchdentalseg/catalogs.py:145-150) 55개 레이블 표에도 Upper Skull은 없다(catalogs.py:47-103). Slicer 클라이언트의 README는 여전히 이 오류를 되풀이한다(AutomatedDentalToolsRemote README.md:865-867).

값은 각 세그먼트에 LabelValue 태그(_segmentLabelValue)로 설정되며, 있으면 이름보다 우선한다.

5.2 자동 크롭(메모리 실패 뒤의 재실행)

선택 사항이며, 명시적 확인 뒤에 실패 항목 재시도로 시작된다. _applyAutoCrop()(SegmentationWidget.py:1029):

  • 공기/조직 임계값은 스케일에 민감하지 않다. array.min() < −800이면 Hounsfield 단위이며 임계값은 −500이고, 그렇지 않으면 min + 0.15 × (p99.5 − min)이다.
  • 임계값을 넘는 복셀의 경계 상자를 _CROP_MARGIN_MM = 15.0 mm만큼 확장한다. 이를 축마다 복셀로 환산한다.
  • 복셀의 _CROP_MIN_GAIN = 0.85보다 많은 부분이 남으면 크롭을 포기한다. 15% 미만의 이득은 위험을 감수할 가치가 없다.
  • 하위 볼륨은 간격과 축을 유지하며 원점만 움직인다(ijkToRas.MultiplyPoint([i0,j0,k0,1])). 보간은 전혀 없다.

_restoreCropToOriginalGrid()는 레이블 맵을 단순한 인덱스 오프셋으로 원래 크기의 배열에 다시 붙여 넣는다. 따라서 출력은 언제나 촬영된 그대로의 스캔 격자 위에 있다.

5.3 메모리 안전 장치: 세 겹의 방어선

코드 주석이 실제 사례를 든다. 어떤 스캔이 125 GB 기계에서 114 GB를 채웠고, OOM killer에 죽었으며, 멀티프로세싱 워커가 메모리를 쥔 채 살아 남았다.

a) 사전 추정, _estimatePeakRamGb()(SegmentationWidget.py:1173). 시야의 물리적 부피는 간격과 무관하므로 리샘플된 복셀 수는 fovMm3 / targetVoxelMm3와 같다. 정점은 convert_predicted_logits_to_segmentation_with_correct_shape에서 도달하며, 거기서는 클래스마다 다음이 공존한다. 슬라이딩 윈도 누산기(리샘플된 격자의 torch.half, 2바이트), 그 float64 사본(4D 배열 전체에 한 번에 data = data.astype(float), 8바이트), reshaped_final(원래 격자의 torch.half, 2바이트). 따라서 logitsGb = (10 × C × Vresampled + 2 × C × Voriginal) / 2³⁰이고, 여기에 8 × (Voriginal + Vresampled)(skimage.resize의 float64 일시 버퍼분)와 _RAM_FIXED_OVERHEAD_GB = 4.0(torch, 가중치, 워커)이 더해진다. spacing과 레이블 수는 같은 설정 폴더에서 읽으므로, 한 모델의 간격이 다른 모델의 레이블 수와 섞이지 않는다.

예산 = free RAM × ramLimitSpinBox(기본값 85%). 이를 넘으면 스캔은 nnU-Net을 시작하지도 않은 채 사유와 함께 failed로 표시된다. 다만 체크박스 여유 RAM에 비해 너무 큰 스캔 건너뛰기(ramPreflightCheckBox, 기본값은 체크됨, SegmentationWidget.py:446-447)를 해제하면 그렇지 않으며, 그 경우 추정값은 로그에만 남는다(SegmentationWidget.py:1248-1253). 예산은 그 시점에 쓸 수 있는 메모리(vm.available, SegmentationWidget.py:1243-1244)에 적용되는데, 스핀 박스에는 “% of system RAM”이라는 라벨이 붙어 있다.

b) 실행 중 모니터링: _onMemCheck는 _RAM_SAMPLE_MS = 3000 ms마다 표본을 잡으며, 종료하려면 연속 _RAM_CONSECUTIVE_HITS = 2회의 초과가 필요하다(일시적 급등이 멀쩡한 스캔을 죽여서는 안 된다).

c) 메모리 복구: _killInferenceTree()는 트리 전체를 죽인다. QProcess.kill()은 직접 자식에게만 닿는데 nnU-Net은 멀티프로세싱을 하기 때문이다. _reclaimStrayProcesses()는 명령줄에 nnunetv2_predict, nnunetv2/inference, nnunet이 들어 있고 더 이상 누구에게도 속하지 않는 프로세스를 쓸어 낸다. Free memory 버튼은 이를 손으로 한다.

쉬운 설명과 수식: 아틀라스 페이지.

5.5 거울 보정(UniversalLab 전용)

Segment_6Mandibular canal"Maxilla"(끝에 공백이 있음)

고치는 방법은 공백만 지우는 것이 아니라 목록과 함께 딸린 colors, opacities 목록을 _get_active_label_map에 맞게 재정렬하는 것이다.

그러나 이름 바꾸기는 LabelValue 태그가 설정되기 전에 일어나고, _segmentLabelValue는 그때 이름으로 되돌아간다. 실제로 레이블 3(상악)을 담은 Segment_3은 "Upper Teeth"로 이름이 바뀌고 값 4로 내보내진다. 더 나쁜 것은 "Maxilla "에 끝 공백이 있다는 점이다. 표에서의 조회가 실패하고, Segment_6(하악관)은 "unexpected segment"로 기록되어 NIfTI에서 사라진다. 그러나 두 목록은 나머지 세 모델에서는 완벽하게 대응한다.

  • onApplyClickedForVolume의 네 분기는 복사해 붙여 넣은 것이다. UniversalLab 분기는 아직도 변수 이름을 pediatricCheckpoint라 하고 "Downloading pediatricdentalseg model…"을 기록한다. 겉모습의 문제이지만 로그를 읽을 때 오해를 부른다.
함정 (레거시 전용)

DentalSegmentator 가중치를 내려받으면 나머지 세 모델이 지워진다. downloadWeights()가 shutil.rmtree(self.destWeightFolder)를 Resources/ML에 하는데(PythonDependencyChecker.py:158-160), 거기에는 Dataset001_380CT, Dataset001_max4, Dataset002_380CT도 있다. 그리고 getDatasetPath()는 rglob("dataset.json")을 Resources/ML 아래 어디서든 찾으며(PythonDependencyChecker.py:123-127), areWeightsMissing()은 처음 찾은 것 옆에 fold_*/*.pth가 있는지 확인한다(PythonDependencyChecker.py:78-96). 소아 모델만 있으면 체커는 DentalSegmentator가 설치되었다고 믿는다.

레거시(3c67957), VISOR에는 없음: 실행 중에는 아무것도 내려받지 않으며(SADT-VISOR sadt_batchdentalseg/pipeline.py:15-17), 각 번들은 서버 매니페스트에 자기 폴더(dest)를 가지고(VISOR-serve scripts/data-manifest.yml:542-586), 번들은 dataset.json, plans.json, fold_0/checkpoint_final.pth를 갖추었을 때만 받아들여진다(nnunet_runner.py:57-73).

함정(릴리스 확인은 레거시 전용이며, 무결성의 빈틈은 VISOR에서 일부만 메워졌다)

취약한 릴리스 확인: 모든 릴리스의 모든 에셋 가운데 assets[0](PythonDependencyChecker.py:98-102)을, 인증 없는 GitHub 클라이언트(IP당 시간당 60회 요청)로 가져온다. 최신 릴리스의 맨 앞에 에셋이 추가되면 내려받는 모델이 바뀐다. 그리고 하나씩 내려받는 체크포인트 셋에는 무결성 검사가 없어 잘린 파일을 완전한 파일과 구별할 수 없다.

레거시(3c67957), 확인 방식에 대해서는 VISOR에 없음: 서버 매니페스트는 릴리스 태그로 파일마다 URL 하나를 고정한다(VISOR-serve scripts/data-manifest.yml:546-585). 무결성은 일부만 해결됨: 이 도구에서 sha256이 선언된 파일은 둘뿐이며, PediatricDentalSeg의 dataset.json과 plans.json이다(data-manifest.yml:563, 568). 체크포인트와 DentalSegmentator 아카이브에는 size만 있고 해시가 없으며, 가져오기 스크립트는 해시가 있을 때만 검증한다(VISOR-serve scripts/fetch_data.py:309-319). 내려받기는 임시 폴더로 가서 완료되면 제자리로 옮겨지므로, 잘린 체크포인트가 완성된 것으로 오인되는 일은 이제 없다(fetch_data.py:300-306).

  • NRRD는 인식되지 않으며 하위 폴더도 순회되지 않는데(listVolumes), 저장소의 다른 모듈은 NRRD와 폴더 트리를 아주 쉽게 만든다. 이름 충돌이 가능하다. 서로 다른 폴더에서 온 스캔 둘이 같은 기본 이름을 가지면 같은 <stem>_Segmentation.nii.gz를 덮어쓴다.
  • 폴드 하나, 앙상블은 절대 아님(folds="0"). fold_1..4를 담아 배포된 번들이 있다면 그것들은 무시된다.
  • os.environ['nnUNet_results']는 스캔마다 SegmentationLogic이 다시 쓴다. 여기서는 해롭지 않지만(순차 대기열), 같은 Slicer 세션에서 다른 nnU-Net 추론이 돌고 있으면 위험하다.
  • 죽은 코드: _saveSegmentationAsNifti, _postProcessSegments, _keepLargestIsland, _removeSmallIsland, onExportClicked(해당 버튼은 배치 레이아웃에 연결되어 있지 않다).
함정(레거시 전용, 정정됨: CMake는 Resources/ML의 일부를 실제로 나열한다)

3c67957에서의 정정. MODULE_PYTHON_RESOURCES는 Resources/ML/download_info.json과 dataset.json, plans.json(Dataset111_453CT의 것)을 실제로 나열한다(BATCHDENTALSEG/CMakeLists.txt:28-34). 따라서 Resources/ML이 설치되지 않는다는 진술은 그 커밋에서는 틀렸다. 나머지 번들 셋의 JSON 파일은 나열되지 않는다.

유효한 것: 사전 메모리 추정(§5.3)은 계획이나 데이터셋 파일을 읽을 수 없으면 None을 돌려주며(SegmentationWidget.py:1173-1204), 그러면 RAM 검사는 스캔을 통과시킨다(SegmentationWidget.py:1239-1242).

VISOR에는 없음: Slicer 클라이언트에는 메모리 안전 장치가 없다(패널은 97줄, AutomatedDentalToolsRemote BATCHDENTALSEGRemote/BATCHDENTALSEGRemote.py:51-97). 수용 여부는 서버가 판단한다(VISOR-serve server/execution/admission.py:1-12).

쉬운 설명과 수식: 아틀라스 페이지.

10. 문헌

DentalSegmentator가 발표되었다.

Dot G., Chaurasia A., Dubois G., Savoldelli C., Haghighat S., Azimian S., Rahbar Taramsari A., Sivaramakrishnan G., Issa J., Dubey A., Schouman T., Gajny L. DentalSegmentator: robust open source deep learning-based CT and CBCT image segmentation. Journal of Dentistry 147:105130, 2024. doi:10.1016/j.jdent.2024.105130 , PMID 38878813

nnU-Net v2(가중치의 Zenodo 안내문에 따르면 v2.2), 학습에는 7개 기관의 CT와 CBCT 스캔 470개, 구조 5개, 스캔 256개(내부 133개, 외부 123개)로 홀드아웃 시험: DSC 내부 92.2 ± 6.3%, 외부 94.2 ± 7.4%. 여기에 포함된 dataset.json은 numTraining = 453을 알리며, 이는 서술된 코퍼스와 일치한다.

확인됨

이 모델에 대해서는 코드와 논문이 일치한다. 가중치는 Zenodo(concept DOI 10.5281/zenodo.10829674)에도 CC-BY-4.0으로 공개되어 있지만, 이 모듈은 Zenodo가 아니라 GitHub 릴리스에서 가져온다.

레거시: 모듈이 첫 Apply 때 직접 내려받는다. VISOR: 실행 중에는 아무것도 가져오지 않으며, 설정 스크립트가 같은 upstream 릴리스 아카이브(gaudot/SlicerDentalSegmentator, Dataset111_453CT_v100.zip, VISOR-serve scripts/data-manifest.yml:582-586)를 미리 준비해 둔다. 이 역시 Zenodo가 아니라 GitHub에서 가져온다.

방법론의 토대:

Isensee F., Jaeger P.F., Kohl S.A.A., Petersen J., Maier-Hein K.H. nnU-Net: a self-configuring method for deep learning-based biomedical image segmentation. Nature Methods 18(2):203-211, 2021. doi:10.1038/s41592-020-01008-z

변형 셋은 저장소에서 어떤 출판물에도 연결되어 있지 않다. 저장소의 README는 PediatricDentalSegmentator와 UniversalLabDentalSegmentator에 혼합치열 CBCT 스캔 513개, NasoMaxillaDentalSegmentator에 스캔 135개를 안내하지만 참고문헌도 시험 세트도 없다. 이 수치는 코드의 어디에서도 검증할 수 없다. 해당 dataset.json 파일은 가중치를 내려받을 때만 들어온다. 출판물이 이를 다루기 전까지는 내부 주장으로 취급해야 한다.

  • KitwareMedical/SlicerNNUnet: 필요한 NNUNet 확장
  • MIC-DKFZ/nnUNet
  • SlicerAutomatedDentalTools
