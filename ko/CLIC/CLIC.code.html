CLIC, 레거시: 코드

개발자용: 레거시 CLIC 모듈이 코드에서 하는 일을 file:line 참조, 코드, 인자, 환경, 함정과 함께 다룬다. 같은 파이프라인에 대한 읽기 쉬운 설명과 수식은 아틀라스 페이지에 있다.

코드 아틀라스 (해설) 미공개 VISOR clic_runner.py conda 환경: clic_env Python 3.9 참고문헌

매복 견치의 분류와 위치 파악(Classification and Localization of Impacted Canines). CBCT를 torchvision Mask R-CNN으로 2D 슬라이스별 인스턴스 분할하며, 예측된 클래스가 매복 견치의 골 내 위치를 부호화한다. 협측, 양피질, 구개측이다.

모듈 이름은 과제 둘을 약속하지만 코드에 있는 것은 신경망 하나뿐이다. 별도의 분류 신경망도, 별도의 위치 파악 신경망도, 좌표 회귀 헤드도 없다. 분류는 인스턴스 레이블(pr["labels"])이고 위치 파악은 마스크(pr["masks"])이며, 둘 다 같은 Mask R-CNN 패스에서 나온다. 아래의 모든 것이 여기서 따라 나온다.

두 코드 베이스

아래에 번호가 매겨진 모든 내용은 레거시 Slicer 모듈(3c67957 시점의 SlicerAutomatedDentalTools, 2026-10-26)을 설명한다. 같은 도구를 서버에서 실행하는 VISOR 포팅은 별도 페이지인 VISOR의 CLIC에서 설명한다. VISOR에서는 더 이상 성립하지 않는 콜아웃은 제목에 그렇게 적혀 있다.

1. 파이프라인에서의 위치

쉬운 설명과 수식: 아틀라스 페이지.

양방향으로 독립적이다. 저장소의 어떤 모듈도 CLIC를 호출하지 않으며, CLIC도 저장소의 다른 모듈을 호출하지 않는다. 자기 러너 외에는 아무것도 호출하지 않는다.

호출되는 것시점방법
CLIC/runner/clic_runner.py스캔마다 한 번CondaSetUpCall.condaRunFilePython(runner, ["--params_json=…"], "clic_env")
릴리스 CLIC_model/final_model.pthDownload Model 버튼requests.get, ~/Documents/CLIC_Models에 기록

원본 CBCT에서 출발한다. 사전 분할도, 랜드마크도, 방향 정렬도 없다. 모듈은 .nii/.nii.gz를 읽어 레이블 맵을 출력한다. AMASSS, ASO, ALI에는 어떤 식으로도 의존하지 않는다.

2. 관련 파일

쉬운 설명과 수식: 아틀라스 페이지.

파일역할실행되는 곳
CLIC/CLIC.py위젯, 3c67957에서 453줄(어두운 테마는 이제 ADTLib.theming에서 오며, conda 패치는 :78-103)Slicer Python
CLIC/runner/clic_runner.py모든 처리, 101줄clic_env conda 환경, 가능하면 GPU
CLIC/Resources/UI/CLIC.ui인터페이스–

Slicer CLI도, .xml도, MedX_Method 같은 계층도 없다. 위젯이 매개변수 JSON을 slicer.app.temporaryPath에 쓰고, conda 환경 안에서 러너를 독립 Python 스크립트로 실행한다.

위젯은 CondaSetUp을 모듈 수준에서 import하며(CLIC/CLIC.py:18) parent.dependencies에 선언하지 않는다. SlicerConda가 설치되어 있지 않으면 CLIC는 아예 로드되지 않으며, 도움이 되는 메시지도 없다.

항상 CondaSetUpCall()을 인스턴스화하고(CLIC/CLIC.py:70) CondaSetUpCallWsl은 인스턴스화하지 않는다. DOCShapeAXI나 init_conda()를 거치는 모듈(ADT/ADTLib/env/conda.py:46-59, Windows에서 CondaSetUpCallWsl()을 돌려줌)과 달리 CLIC에는 WSL 경로가 없다. 그렇다고 해서 그것만으로 Linux 전용이 되지는 않는다. CLIC/CLIC.py:269-273의 호출은 condaRunFilePython(file, [args], env)이며 이것은 네이티브 클래스의 인자 순서이고, 뒤바뀐 순서 (file, env, args)는 CondaSetUpCallWsl에만 속한다. ba426f4 시점의 SlicerConda(CondaSetUp/CondaSetUp.py, 2026-10-16)에서 네이티브 condaRunFilePython(:1746)에는 platform.system()=="Windows" 분기(:1762)가 있다. Slicer 5.12.3 확장에 포함된 더 오래된 SlicerConda는 condaRunCommand를 executable="/bin/bash"를 거쳐 실행하는데(:1586, 설치된 CondaSetUp.py) Windows에는 이것이 없다. 저장소는 SlicerConda 버전을 고정하지 않으며 Windows에서는 아무것도 실행하지 않았으므로, CLIC가 거기서 동작하는지는 어느 쪽으로도 증명되지 않았다.

함정 (레거시 전용)

레거시(3c67957), VISOR에는 없음: VISOR 패널은 스캔을 서버로 보내고 작업 PC에서 conda 환경을 실행하지 않는 얇은 클라이언트이다(Remote CLICRemote/CLICRemote.py:44,53, VISOR의 CLIC 참조). WSL 경로 없음: CondaSetUpCallWsl은 인스턴스화되지 않고 init_conda()도 쓰이지 않는다. CLIC/CLIC.py:269-273의 인자 순서는 네이티브 클래스와 일치하므로, 인자 목록이 환경 이름으로 나간다는 이전의 주장은 성립하지 않는다(그 순서는 WSL 클래스의 것이다). 네이티브 클래스가 Windows에서 동작하는지는 SlicerConda 버전에 달려 있으며(2절 참조), Windows에서는 시도하지 않았으므로 "Linux 전용"은 증명되지 않았다.

3. 입력과 전처리

쉬운 설명과 수식: 아틀라스 페이지.

3.1 스캔 수집

쉬운 설명과 수식: 아틀라스 페이지.

_collect_scans()(CLIC/CLIC.py:439)는 .nii, .nii.gz, .nrrd, .mha, .mhd를 받아들이며 두 단계 규칙을 따른다.

  1. 유효한 파일이 하나라도 든 하위 폴더가 있으면 그 하위 폴더의 목록을 돌려준다.
  2. 그렇지 않으면 폴더 안의 유효한 파일 목록을 돌려준다.

사례 1은 디렉터리 Path를 만들어 러너에 input_path로 그대로 넘기고, 러너는 nib.load(str(inp))를 하므로 즉시 실패한다. 따라서 정상 사례는 .nii.gz가 든 평평한 폴더이다.

게다가 러너는 nibabel만 쓴다. .nrrd, .mha, .mhd는 위젯의 필터는 받아들이지만 러너는 읽지 못한다.

함정 (레거시 전용)

레거시(3c67957), VISOR에는 없음: 도구는 .nii와 .nii.gz만 읽고(SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:36), 다른 파일은 건너뛰며, NIfTI가 하나도 없는 요청은 읽기 쉬운 메시지와 함께 거부한다(__init__.py:115-123, VISOR의 CLIC 참조). 위젯의 선택 필터는 .nrrd, .mha, .mhd를 .nii/.nii.gz에 더해 받아들이지만 러너는 nibabel로만 읽을 수 있다. 이 세 형식은 필터는 통과하고 로드에 실패한다.

3.2 실제 볼륨 전처리

쉬운 설명과 수식: 아틀라스 페이지.

세 줄에 들어간다(CLIC/runner/clic_runner.py:80-83).

sl = _norm(vol[..., z])                                    # min-max of the slice
t  = torch.from_numpy(sl).unsqueeze(0).repeat(3, 1, 1).float().to(device)
pr = model([t])[0]

다시 말해:

  • nibabel 배열의 3번째 축을 따라 축상 슬라이스로 나눈다. 파일의 저장 순서를 따르며 다시 계산한 해부학적 방향을 따르지 않는다. RAS/LPS로의 재정렬은 하지 않으며, 코드는 nii.affine을 다시 쓸 때를 빼고는 보지 않는다.
  • 슬라이스별 min-max 정규화(_norm, CLIC/runner/clic_runner.py:44): (x - min) / (max - min)이며, 상수 슬라이스는 0이 된다. Hounsfield 윈도잉도, 백분위수 클리핑도, 볼륨 통계도 없다. 슬라이스마다 자기 대비를 가지며, 공기만 든 슬라이스는 전체 동적 범위로 늘어난다.
  • ImageNet 백본의 RGB 입력에 맞추려고 3채널로 복제한다.
  • 크롭도, ROI도, 명시적 리샘플링도 없고, 복셀 리스케일링도 없다.

유일한 크기 조정은 torchvision 자체에서 온다. 모델에 내장된 GeneralizedRCNNTransform이 ImageNet 평균([0.485,0.456,0.406] / [0.229,0.224,0.225])으로 표준화하고, 짧은 변이 800 px이 되도록 크기를 조정하되 긴 변은 1333 px로 제한한다. 이것은 저장소에서 내린 선택이 아니라 torchvision의 기본값이다. 따라서 512×512 CBCT는 백본 앞에서 800×800으로 확대된다.

4. 모델

쉬운 설명과 수식: 아틀라스 페이지.

4.1 아키텍처

쉬운 설명과 수식: 아틀라스 페이지.

_blank_model(nc)(CLIC/runner/clic_runner.py:35-41)를 nc = 4로 호출한다.

m = maskrcnn_resnet50_fpn(weights=None)
m.roi_heads.box_predictor  = FastRCNNPredictor(in_f, nc)
m.roi_heads.mask_predictor = MaskRCNNPredictor(in_fm, 256, nc)
  • 백본: ResNet-50 + FPN(_resnet_fpn_extractor, 5단계).
  • RPN에 이어 ROI 헤드: 박스 헤드(FastRCNNPredictor: cls_score 클래스 4개, bbox_pred 출력 16개)와 마스크 헤드(MaskRCNNPredictor, 은닉층 256, 출력 채널 4개, ROI마다 28×28 마스크).
  • weights=None이지만 weights_backbone은 기본값 ResNet50_Weights.IMAGENET1K_V1을 유지한다. 모델을 만들면 ResNet-50용 ImageNet 가중치를 내려받는다(이어서 load_state_dict가 이를 덮어쓴다). 오프라인에서의 첫 실행은 실패한다. 유용한 부수 효과: is_trained가 True이므로 정규화는 FrozenBatchNorm2d이고 BatchNorm2d가 아니며, 이것이 학습 모델과 일치해야 state_dict 키가 맞는다.
함정(VISOR에서도 마찬가지)

VISOR에서도 마찬가지이다. SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:136은 여전히 maskrcnn_resnet50_fpn(weights=None)을 호출한다. VISOR의 발견 사항을 볼 것. weights_backbone은 기본값 ResNet50_Weights.IMAGENET1K_V1을 유지하며, weights=None이어도 그렇다. 모델을 만들기만 해도 ResNet-50용 ImageNet 가중치 내려받기가 일어난다. 오프라인에서의 첫 실행은 final_model.pth에 닿기도 전에 실패한다.

클래스 4개 = 배경 + 3. 레이블과 이름의 대응은 위젯의 _legend()에만 있다(CLIC/CLIC.py:354-358).

예측 신경망은 정수 1/2/3만 출력하며, 아래의 이름과 색은 위젯의 관례이고 러너에는 없다.

레이블의미색
1협측초록 (0,1,0)
2양피질노랑 (1,1,0)
3구개측갈색 (.6,.4,.2)

러너는 이 이름을 모르며 정수 1, 2, 3을 쓴다.

VISOR에서는 이름이 도구와 그 보고서에 있고, 클래스 수는 4로 고정되지 않고 체크포인트에서 읽는다. 레거시 로직에서 달라진 것을 볼 것.

4.2 가중치

쉬운 설명과 수식: 아틀라스 페이지.

하드코딩된 URL(CLIC/CLIC.py:326-329):

https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/CLIC_model/final_model.pth

저장 위치는 ~/Documents/CLIC_Models/final_model.pth이다. 러너는 이 이름을 찾지 않고 sorted(model_dir.glob("*.pth"))[0]을 취하며(CLIC/runner/clic_runner.py:67), 이는 알파벳순 첫 .pth이다. 폴더에 모델이 둘이면 파일 이름이 결정한다. 폴더가 비어 있으면 처리되지 않은 IndexError가 난다.

VISOR에서는 체크포인트를 도구가 내려받지도, 정렬 순서로 고르지도 않는다. 서버에 있는 단 하나의 .pth이며, 여럿이면 거부한다(SADT-VISOR tools/CLIC/src/sadt_clic/__init__.py:40-73).

이 파일은 Lightning 체크포인트가 아니라 순수한 state_dict(model.load_state_dict(torch.load(...)))이며, 하이퍼파라미터도, 클래스도, 버전도 없다. 학습 세트, 주석이 달린 슬라이스 수, 지표는 저장소에서 알 수 없다.

4.3 신경망이 글자 그대로 출력하는 것

쉬운 설명과 수식: 아틀라스 페이지.

신경망 슬라이스마다 model([t])[0]이 표준 torchvision 딕셔너리를 돌려준다.

키형태내용
boxes(N,4)박스 x1,y1,x2,y2, 조정된 프레임 기준이며 변환이 원래 크기로 되돌림
labels(N,)정수 1..3
scores(N,)클래스 점수, 내림차순
masks(N,1,H,W)픽셀별 확률, [0,1] 구간의 float

torchvision의 기본 상류 임계값을 따른다. box_score_thresh=0.05, box_nms_thresh=0.5, box_detections_per_img=100.

4.4 신경망 출력에서 레이블 맵까지

쉬운 설명과 수식: 아틀라스 페이지.

임계값 둘, 모두 하드코딩되어 있다(CLIC/runner/clic_runner.py:84-87).

keep = pr["scores"] >= 0.7                     # confiance d'instance
for mk, lb in zip((pr["masks"][keep] > .5).squeeze(1).cpu().numpy(),
                  pr["labels"][keep].cpu().numpy()):
    seg[..., z][mk] = int(lb)
  • 인스턴스 점수에 대해 0.7.
  • 마스크 확률에 대해 0.5이며, 이것이 이진화한다.
  • 할당은 투표가 아니라 덮어쓰기이다. 인스턴스 둘이 겹치면 마지막에 처리된 것(torchvision이 점수 내림차순으로 정렬하므로 가장 낮은 점수)이 픽셀을 차지한다. 같은 복셀에서의 협측/구개측 충돌은 가장 낮은 점수가 해결한다.
  • 도구는 슬라이스당 인스턴스 수에 자체 제한을 두지 않으며, 견치 하나에도 둘에도 마찬가지이다(torchvision은 슬라이스당 최대 100개를 유지한다, box_detections_per_img).

3D 일관성은 강제되지 않는다. 각 슬라이스는 독립적으로 분류된다. 슬라이스 간 스무딩도, 연결 성분 분석도, 스택 전체의 다수결도 없다. 이웃한 두 슬라이스가 같은 치아에 서로 다른 클래스를 담을 수 있다. "환자의 클래스"를 원하는 사람은 직접 집계해야 하며, 모듈은 이를 만들지 않는다.

함정(VISOR에서도 마찬가지)

VISOR에서도 마찬가지이다(SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:178-182: 같은 루프, 같은 덮어쓰기, VISOR의 CLIC 참조). 두 인스턴스의 겹침은 투표가 아니라 덮어쓰기로 해결된다. 마지막에 처리된, 따라서 torchvision이 점수 내림차순으로 정렬하므로 가장 낮은 점수의 인스턴스가 픽셀을 차지한다. 그리고 이웃한 슬라이스 사이의 일관성을 강제하는 것이 없으므로, 인접한 두 슬라이스가 같은 치아를 다르게 분류할 수 있다.

5. 알고리즘의 핵심부

쉬운 설명과 수식: 아틀라스 페이지.

임계값 처리 외에는 학습되지 않은 부분이 없다. ICP도, 형태학도, 성분 추출도, 계측도 없다. 러너 전체는 모델 불러오기, Z에 대한 루프, 임계값 처리, 쓰기가 전부이다. 판단 전체는 Mask R-CNN 안에 있다.

6. 후처리와 출력

쉬운 설명과 수식: 아틀라스 페이지.

out_dir  = out_root / inp.stem
out_path = out_dir / f"{inp.stem}_{suffix}.nii.gz"
nib.save(nib.Nifti1Image(seg.astype(np.int16), nii.affine, nii.header), out_path)
  • 스캔마다 하위 폴더 하나, 스캔의 이름을 따름.
  • suffixLineEdit의 접미사, 기본값 "seg".
  • Path.stem을 X.nii.gz에 쓰면 X.nii이다. 폴더 이름은 X.nii가 되고 파일은 X.nii_seg.nii.gz가 된다. 보기 흉하지만 기능상 결과는 없다.
  • affine과 header는 입력 볼륨에서 가져오며, 레이블 맵은 정합 없이 겹쳐진다. 배열은 메모리에서 int16이지만 Nifti1Image(array, affine, header)는 받은 헤더에 저장된 데이터 타입을 유지하므로, 파일은 int16이 아니라 입력 스캔의 타입으로 기록된다(nibabel 5.4.2로 확인: float32 입력은 float32 레이블 맵을, int16은 int16을, uint8은 uint8을 준다).
  • 값은 0/1/2/3이며, 메모리에서의 타입은 int16이고 디스크에서는 입력의 타입이다.

두 번째 pip install은 "'numpy<2.0'"를 넘긴다. 문자열 안에 작은따옴표가 들어 있다. 어떻게 되는지는 SlicerConda 버전에 달려 있다(ADT/ADTLib/env/conda.py:21-43이 유통되는 두 가지를 문서화한다). condaRunCommand가 bash 줄을 만드는 곳(더 오래된 버전, shell=True)에서는 bash가 따옴표를 벗긴다. argv 목록을 넘기는 곳(ba426f4의 SlicerConda, CondaSetUp.py:1796-1815)에서는 따옴표가 그대로 pip에 닿고, pip는 'numpy<2.0'를 거부한다(Slicer 5.12.3의 pip로 단독 실행: “Invalid requirement”). 그러면 패널은 돌려받은 텍스트에서 “error”를 보고 “numpy downgrade failed”에서 멈춘다. 전체 패널은 실행하지 않았다. 한편 실패 감지는 돌려받은 출력에서 "error"나 "failed"를 찾는다. 이 단어가 들어 있는 pip 경고는 모두 준비 단계를 실패시킨다.

conda 패치

쉬운 설명과 수식: 아틀라스 페이지.

CLICWidget.__init__이 SlicerConda의 getCondaExecutable을 핫패치한다.

  1. 경로에서 중복된 /bin/bin/을 고친다.
  2. 파일이 실제로 디스크에 있으면 그것을 돌려준다.
  3. 그렇지 않으면 shutil.which("conda").
  4. 그것도 아니면 원래 경로를 유지하고 경고를 기록한다.

이 패치가 있는 이유는 5.13 나이틀리에 포함된 SlicerConda가 기계 전체에 conda 경로 하나만 유지하고 디스크에 아직 있는지 확인하지 않은 채 내주기 때문이다. 다른 Slicer 설치가 이를 덮어쓰면 이 모듈은 없는 conda를 실행한다. 코드가 그렇게 말하며, 무엇이 이 패치를 불필요하게 만드는지도 말한다. 이미 5.12 릴리스에 있는 브랜치는 경로를 설치별로 키로 삼고 executableExists()로 지킨다. 나이틀리가 그 버전을 담게 되면 제거할 예정이다.

이 페이지를 쓴 뒤 정정됨(레거시 전용)

레거시 전용: VISOR에는 conda 환경도 정정할 SlicerConda 패치도 없다(VISOR의 CLIC). 2026년 9월자 이 조사는 여기서 결함을 기록했다. fixed_getCondaPath가 기계에 /home/<developer>/anaconda3 폴더가 있기만 하면, 사용자의 SlicerConda 설정을 보기도 전에 그것을 돌려주었다. 개발 기계의 경로가 버전 관리되어 우선권을 가진 것이다. 2026-10-12에 다시 확인: 사라졌다. fixed_getCondaPath는 더 이상 없으며 CLIC/CLIC.py에는 하드코딩된 경로가 남아 있지 않다. 위의 getCondaExecutable 패치만 남았으며 shutil.which로 대체한다.

함정 (레거시 전용)

레거시(3c67957), VISOR에는 없음: 서버가 output_dir을 직접 채우고 도구가 이를 만든다(SADT-VISOR tools/CLIC/src/sadt_clic/__init__.py:112-113, VISOR의 CLIC 참조). 출력 폴더를 고르지 않아도 위젯은 JSON에 "output_dir" 키를 None으로 쓴다. 러너 쪽에서 P.get("output_dir", inp.parent)는 None을 돌려주고, 키가 있으므로 기본값은 적용되지 않으며, Path(None)은 TypeError를 일으킨다. 러너가 죽는다.

  • 진행 막대와 결과의 자동 불러오기가 깨져 있다. 러너는 logger.info를 통해 표지를 내보내며, 포매터는 '%(name)s - %(levelname)s - (%(filename)s:%(lineno)d) - %(message)s'(ADT/ADTLib/logging_setup.py:21)이다. 받는 줄은 CLIC_runner - INFO - (clic_runner.py:51) - [SEG] /path 같은 모양이어서, 검사 ln.startswith("[PROGRESS]")와 ln.startswith("[SEG]")(CLIC/CLIC.py:277,279)는 참이 되는 일이 없다. 결과: 막대는 0에 머물고 만들어진 분할은 Slicer에 불러와지지 않으며, 그래도 디스크에는 제대로 기록된다. print에서 logging으로 바꾸면서 러너의 헤더(CLIC/runner/clic_runner.py:12-16)에 아직 적혀 있는 프로토콜이 깨졌다. 최소한의 수정: "[SEG]" in ln으로 파싱하고 표지부터 잘라 낸다.
  • 어차피 점진적으로 오는 것은 없다. condaRunFilePython은 subprocess.run(...).stdout을 하고 f"Result: {result.stdout}"를 돌려준다. 모든 출력이 스캔이 끝날 때 한 덩어리로 도착한다. 표지를 고쳐도 진행은 스캔마다 0에서 100%로 뛸 것이다.
  • 취소 버튼은 아무것도 하지 않는다. _on_cancel(CLIC/CLIC.py:296)은 로그 줄 하나를 쓸 뿐이다. cancel_evt도 하위 프로세스도 건드리지 않는다.
  • 출력 폴더를 고르지 않으면 러너가 죽는다. 위젯은 항상 JSON에 "output_dir" 키를 쓰되, 운영자가 아무것도 고르지 않았으면 None으로 쓴다. P.get("output_dir", inp.parent)는 그러면 None을 돌려주고, 키가 있으므로 기본값은 적용되지 않으며, Path(None)은 TypeError를 일으킨다. .ui의 Save Predictions in Input Folder 체크박스는 아무것에도 연결되어 있지 않다.

  • 대기 루프가 Slicer를 막는다. _on_predict는 while not cancel_evt.wait(0.05)에서 processEvents()와 함께 돌며 작업자 스레드가 하위 프로세스를 기다린다. UI는 반응하지만 Predict 버튼이 유일한 출구이다.

10. 문헌

쉬운 설명과 수식: 아틀라스 페이지.

CLIC를 다룬 논문은 없다. 해당 연구는 Interpretable Deep Learning for the Detection and Classification of Impacted Canines and severity of root resorption(Tulissi, Cevidanes, Prieto)라는 제목으로 알려졌으며, NA-MIC Project Week 43(몬트리올, 2025)에서 발표되었다. 진행 중인 프로젝트이며 출판물이 아니다. 원래 코드는 개인 저장소 ashmoy/maskRcnn에서 왔으며, README가 인용하는 시험 스캔(MN138.nii, UM06.nii)도 여기서 온 것이다.

이 코드를 만들지 않은 아래의 인접 연구와 혼동하지 말 것.

  • 매복 견치의 협측/구개측 위치 파악은 전통적으로 파노라마 방사선 사진에서 영상 분류 CNN으로 이루어진다(CBCT에서의 Mask R-CNN이 아니다).
  • 여러 팀이 CBCT에서 매복 견치의 3D 분할을 발표하지만(볼륨 U-Net/nnU-Net), 피질 위치를 분류하지는 않는다.

CLIC의 특수성, 즉 협측/구개측 쌍에 더해 양피질 클래스를 CBCT에서 2D 슬라이스별로 예측한다는 점은 이 논문들 어디에도 기술되어 있지 않다. 그 수치를 이 모듈의 것으로 제시하지 말 것.
