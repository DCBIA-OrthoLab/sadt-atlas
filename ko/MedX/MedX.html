MedX

로컬에서 실행되는 언어 모델(미세 조정된 BART-large-CNN)로 자유 텍스트 기록에서 TMD 임상 지표를 추출한 뒤, 코호트를 하나의 그림 패널로 집계한다. 처음부터 끝까지 텍스트만 다루며, 이름이 무엇을 암시하든 이 모듈에는 의료 영상이 전혀 들어오지 않는다.

Gaydamour 2025 · CLIP, LNCS medx_summarize medx_dashboard conda 환경: summaries 참고문헌

1. 파이프라인에서의 위치

MedX는 양방향으로 독립적이다. 저장소 안에서 MedX를 호출하는 곳도 없고, MedX가 저장소의 다른 모듈을 호출하지도 않는다. MedX를 MedX/와 MedX_CLI/ 밖에서 grep하면 README.md의 목차와 루트 CMakeLists.txt만 나온다.

서로 독립된 두 경로, 두 탭, 두 CLI:

경로버튼호출되는 실행 파일위치
요약SummarizeButtonpython -m MedX_Summarizeconda run -n summaries
대시보드DashboardButtonslicer.modules.medx_dashboardSlicer의 Python, slicer.cli.run 경유

대시보드 경로는 요약 경로의 출력(.txt 파일 폴더)을 사용하지만, 둘을 이어 주는 것은 없다. 작업자가 직접 다시 실행한다.

참고

LLM에 대한 네트워크 호출은 없다. 엔드포인트도, API 키도, ollama도, openai도 없다. MedX/와 MedX_CLI/ 전체를 grep해 확인했다. 유일한 외부 통신은 GitHub 릴리스에서 가중치를 내려받는 것이다.

GPU는 필요 없다. 요약 CLI는 cuda가 있으면 쓰고(MedX_Summarize.py:32), 없으면 CPU를 쓴다.

3. 입력과 전처리

3.1 환자별 묶기

process_notes()(MedX_Summarize.py:67)는 폴더를 비재귀적으로 훑고(os.listdir, 재귀 없음), .pdf, .docx, .txt만 남겨 file_name.split("_")[0]로 묶는다. 첫 번째 밑줄 앞부분이 모두 환자 식별자다. 같은 환자의 여러 기록은 추론 전에 하나의 텍스트로 이어 붙여진다.

그런데 진행 표시줄의 개수는 Method.search()를 쓰는데, 이는 재귀적이다(glob.iglob(..., recursive=True), Method.py:115). 하위 폴더가 있는 트리에서는 분모가 CLI가 실제로 처리하는 것보다 많은 파일을 센다.

함정

진행 개수(재귀적)와 실제 처리(비재귀적)는 같은 파일 집합을 대상으로 하지 않는다. 하위 폴더가 있으면 진행 표시줄은 결코 100%에 도달하지 않는다.

3.3 청크 분할 — 가장 공들인 부분

split_text_by_paragraphs()(utils.py:83) 다음 create_chunks_from_paragraphs()(utils.py:128).

섹션 헤더 네 개가 하드코딩되어 있다.

section_headers = ["CLINICAL EXAMINATION", "CLINICAL EVALUATION",
                   "RADIOGRAPHIC EXAMINATION", "RADIOGRAPHIC EVALUATION"]

규칙(순서대로):

  1. 두 줄 바꿈, 번호 목록의 시작(\n(?=\d+\.\s)), 글머리 기호(-, *), 또는 섹션 헤더에서 나눈다;
  2. 150자 미만의 단락은 앞 단락에 다시 합쳐진다(목록 항목은 제목과 함께 남는다);
  3. 섹션 전체(헤더 + 다음 헤더까지 이어지는 단락들)는 청크에 들어가는 한 분할할 수 없는 블록으로 취급된다. 이것이 청크 분할의 불변 조건이다. 임상 섹션이 두 프롬프트에 걸쳐 나뉘어서는 안 된다;
  4. 들어가지 않으면 단락 단위로, 그다음 문장 단위로 대체한다(re.split(r'(?<=[.!?])\s+')).

청크 크기: 3500자. generate_combined_summary(MedX_Summarize.py:29)가 넘긴다. create_chunks_from_paragraphs의 기본값(1800)은 쓰이지 않는다. 3500자 ≈ BPE 토큰 900개로 모델의 1024 한도 아래지만, 토큰화는 어쨌든 max_length=1024에서 잘린다.

4. 모델

4.1 실제로 불러오는 것

load_model_and_tokenizer()(utils.py:22):

tokenizer = BartTokenizer.from_pretrained(model_path)
model = BartForConditionalGeneration.from_pretrained(model_path)

그 밖에는 없다. peft도, 양자화도 없다. 그런데도 peft와 bitsandbytes는 환경에 설치되는 패키지 목록에 들어 있다(MedX.py:849). 이 둘과 evaluate, scikit-learn은 학습 때 남은 것이다.

4.2 가중치

URL: https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/MedX/BART.zip(summarize.py:43), 1.51 GB.

아카이브에는 표준 Hugging Face 폴더가 들어 있다: config.json, generation_config.json, model.safetensors(압축 해제 시 1.63 GB, fp32), merges.txt, vocab.json, special_tokens_map.json, tokenizer_config.json.

(아카이브 안에서 읽은) config.json이 정확한 구조를 알려 준다.

필드값

따라서 이것은 처음부터 학습한 모델이 아니라 BART-large-CNN의 미세 조정본(매개변수 약 4억 600만 개)이다. 문서가 아니라 가중치 아카이브에 포함된 config.json에서 직접 확인했다.

원본에서 물려받은 task_specific_params.summarization(max_length=142, min_length=56)은 생성 시점에 완전히 덮어쓰인다.

설정 파일에는 여전히 _num_labels: 3과 LABEL_0..2가 남아 있다. 상위 체크포인트에서 남은 것으로, BartForConditionalGeneration에는 아무 영향이 없다.

4.3 프롬프트와 생성

청크마다 생성 호출 한 번(MedX_Summarize.py:50):

prompt = f"Using the following note, extract structured key-value pairs about the patient's symptoms and diagnoses:\n\n{chunk}"
inputs = tokenizer(prompt, return_tensors="pt", truncation=True, max_length=1024)
summary_ids = model.generate(inputs["input_ids"], generation_config=generation_config)

함정

빔 탐색과 샘플링을 동시에 쓴다(num_beams=4 + do_sample=True) → transformers는 beam sample로 동작한다. 출력은 결정론적이지 않으며, 같은 기록에 두 번 실행하면 같은 요약이 나오지 않는다. 시드는 설정되어 있지 않다.

BART는 지시문 조정(instruction-tuned) 모델이 아니다. 지시 문장은 원문 앞에 그냥 붙을 뿐이다. 미세 조정을 같은 접두어로 했을 때만 효과가 있으며, 이는 저장소에서 확인할 수 없다.

신경망이 문자 그대로 만드는 것: 자유 텍스트, 즉 tokenizer.decode(..., skip_special_tokens=True)로 디코딩된 시퀀스다. key: value 형식은 이 단계에서 강제되지도 검사되지도 않는다. 학습된 성질이지 보장이 아니다. 청크별 요약은 대시 100개로 된 줄로 구분되어 이어 붙여진다.

CLI 쪽에는 키/값 쌍에 대한 검증 단계가 없다. extract_key_value_pairs()와 save_dict_to_csv()(utils.py:227)는 사용되지 않는 코드이며 한 번도 import되지 않는다(__init__.py가 다시 내보내지 않는다).

5. 알고리즘의 핵심 — 대시보드

여기에는 학습이 없다. 파싱과 matplotlib뿐이다.

5.1 텍스트 요약 → DataFrame

read_summaries()(display_figure.py:33)는 _summary.txt로 끝나는 파일만 읽으며, 키 = split("_")[0].

initialize_key_value_summary()(dashboard_utils.py:343)는 키 56개로 된 dict를 만든다. 모두 str 형이고 모두 ""로 초기화된다: patient_age, headache_intensity, disc_displacement, muscle_pain_score, sleep_disorder_type, cpap_used, pain_onset_date… 이것이 모듈의 목표 스키마이며, 저장소에서 이것이 적혀 있는 유일한 곳이다.

update_dictionary()(display_figure.py:69)는 요약을 한 줄씩 훑으며 line.split(":")를 적용한다. 정확히 두 조각이 나오지 않는 줄은 건너뛴다(따라서 :가 들어 있는 값은 사라진다). 값 안의 ; 문자는 ,가 된다. 56개 밖의 키는 무시된다.

연속된 값(같은 필드가 여러 청크에 다시 나오는 경우)의 병합이 미묘한 부분이다.

  • 기존 값이 비어 있음 → 대체;
  • 값이 이미 있음 → 아무 일도 없음;
  • 기존 값이 새 값의 부분 문자열이면 새 값으로 대체(더 자세한 표현을 유지);
  • 그 밖에는 기존 조각에 이미 들어 있지 않은 한 새 값을 " | "로 구분해 덧붙인다.

불리언 분기(if current_value in {"True", "False"})는 사용되지 않는다. 값은 ""로 초기화되고, 모델은 true/false를 소문자로 쓴다. 예시 CSV dashboard_full_dataframe.csv가 이를 보여 준다.

그다음 process_summaries()가 extract_numbers()로 6개 필드를 숫자로 변환한다: patient_age, headache_intensity, average_daily_pain_intensity, diet_score, tmj_pain_rating, disability_rating. 규칙: /가 있으면 첫 번째 / 앞의 숫자를 취하고("7/10" → 7), 없으면 찾은 모든 숫자의 평균을 취한다("8-9" → 8.5, 예시 CSV의 9.5와 41.0이 그래서 나온다).

5.2 집계기

패널마다 하나씩, 모두 dashboard_utils.py에 있으며, 모두 자유 텍스트에 대한 정규식이다.

이 집계기들에 깔린 두 가지 취약점:

  • set_upper_donuts_data는 df[metric] == "true"(소문자)로 비교하지만, set_disc_displacement_data와 set_muscle_pain_data는 먼저 .lower()를 적용한다. 모델이 True라고 쓰면 도넛 차트가 조용히 0%로 떨어진다.
  • 백분율은 항상 len(df)로 나누며, 채워진 값의 수로는 결코 나누지 않는다. 누락된 필드는 음성으로 집계된다.
확인된 버그

5.3 그림

generate_dashboard_figure(): figsize=(22,14), 2×2 gridspec(width_ratios=[3,1.5], height_ratios=[1,1.5])을 패널로 나눈다. 왼쪽 위에 나이 / 수면 장애 / 압통 원형 차트, 오른쪽에 도넛 차트 여섯 개, 아래쪽에 임상 점수 ± SD와 최대 개구량 막대 차트, 이어서 근육 통증 분포, 관절 통증 부위, 나이와 통증 지속 기간의 교차.

이 부분을 건드리기 전에 알아 둘 만한 특이점(display_figure.py:179): 이 함수는 output_folder를 인자로 받은 뒤, 자기 프레임을 들여다보며(inspect.getargvalues) 그 값을 다시 읽어 자기 자신에게 재할당한다. 아무 효과가 없는 작업이다. 매개변수만으로 충분했다.

9. 함정과 취약 지점

함정

Download 버튼은 아무것도 내려받지 않는다. setup()이 <Documents>/SlicerDownloads/MedX를 만들고(MedX.py:394), 그다음 downloadModel이 DownloadUnzip(directory=SlicerDownloadPath, folder_name=SlicerDownloadPath)를 호출한다. 절대 경로와 함께 쓰인 os.path.join은 그 경로를 절대 경로로 만들므로 out_path = 이미 만들어진 폴더가 되고, if not os.path.exists(out_path)(MedX.py:770)가 블록 전체를 건너뛴다. 결과: "Folder must have model for" 경고와 빈 lineEdit. BART.zip을 직접 받아야 한다.

확인된 버그

환경 검사 결과가 무시된다. check_env = self.onCheckRequirements(list_libs) 이후 check_env는 다시 읽히지 않는다(MedX.py:860). conda가 구성되지 않았어도 요약이 시작된다.

확인된 버그

대시보드의 진행 표시줄은 움직이지 않는다. MedX_Dashboard.py는 log_path를 받지만 거기에 아무것도 쓰지 않는다. DisplayMedX.isProgress는 그 파일이 바뀌기를 기다린다.

확인된 버그

OnEndProcess는 self.nb_scans로 나눈다(MedX.py:1289). 입력 폴더가 비어 있으면 ZeroDivisionError.

  • 비결정론적 생성(do_sample=True + 빔, 시드 없음): 두 번 실행하면 요약이 두 가지, 따라서 대시보드도 두 가지가 나온다.
  • 모든 것이 split("_")[0]에 달려 있다. 파일 BLANC_Jean_2021.pdf와 파일 BLANC_2022.docx는 같은 환자이고, 2021-05-12_B082.pdf의 식별자는 2021-05-12다.
  • :가 들어 있는 값은 파싱 중 사라진다(len(key_value) != 2).
  • 개발 머신의 하드코딩된 경로가 dashboard_utils.py:18와 display_figure.py 상단에 있다. Qwen1.5B_full_V3/predictions_500 폴더를 언급한다. 따라서 대시보드 개발에 쓰인 요약, 그리고 저장소에 커밋된 500행짜리 dashboard_full_dataframe.csv는 배포된 BART가 아니라 Qwen 1.5B가 만든 것이다. 두 출력 형식이 서로 바꿔 쓸 수 있다고 가정하지만, 이를 보장하는 것은 없다.
  • 사용되지 않는 코드: extract_key_value_pairs, save_dict_to_csv, Slicer CLI로서의 MedX_Summarize.xml, set_disc_displacement_data(계산되지만 그려지지 않음), registerSampleData(Slicer 템플릿의 예시 볼륨을 가리킴), MedXLogic.process()(pass), updateParameterNodeFromGUI(self.ui.inputSelector를 참조하는데, 이는 .ui에 없음), saveOutput, UpdateTime, UpdateProgressBar(다른 모듈에서 복사해 온 "Matrix applied with success"를 표시).
  • peft와 bitsandbytes는 환경에 설치되지만 한 번도 import되지 않는다. 약 2GB의 쓰이지 않는 의존성이다.

10. 문헌

해당 논문은 AI-Driven Multimodal TMJ Patient Modeling: From Unstructured Notes to Precision Treatment(2025, Springer LNCS)다. BART와 DeepSeek-R1을 TMD 기록 500건에서 뽑은 주석 달린 구간 1,813개로 미세 조정해 임상 지표 56개를 추출하고(initialize_key_value_summary()의 키 수와 정확히 같다), 환자 및 코호트 대시보드에 공급하는 과정을 설명한다. 논문은 ROUGE 점수가 약간 낮음에도 필드 추출 정확도에서 BART가 DeepSeek보다 낫다고 결론짓는다. 모듈이 BART를 포함하는 것과 일관된다.

논문과 저장소 코드 사이의 차이:

  • 논문은 요약을 멀티모달 프레임워크(정합된 MRI와 CBCT) 안에 놓는다. MedX에는 그중 어느 것도 없으며, 텍스트만 읽는다;
  • 개발 주석은 논문 초록에 언급되지 않은 세 번째 모델인 Qwen 1.5B를 가리킨다;
  • 논문의 지표는 저장소의 어떤 스크립트로도 재현할 수 없다(evaluate와 scikit-learn은 설치되지만 쓰이지 않는다).
