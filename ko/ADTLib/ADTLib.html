ADTLib

도구가 아닙니다. 인터페이스도, 파이프라인도, 모델도 없습니다. ADTLib는 스무 개 모듈이 import하는 코드이며, 거의 모든 파일은 같은 함수가 둘에서 열다섯 번까지 복사되어 있었기 때문에 존재합니다. 각 모듈 헤더는 사본 몇 개를 대체했는지, 그리고 사본들이 무엇을 두고 엇갈리기 시작했는지를 기록합니다. 그 개수가 이 페이지의 요점입니다. 파일 수준의 세부 내용은 코드 페이지에 있습니다.

공통 코드 코드 (개발자용)

이 페이지는 ADT/ADTLib(upstream/main 기준)를 설명하며, 사용자가 열어 볼 일이 없는 코드를 다루는 이 아틀라스의 유일한 페이지입니다. 이제 모듈의 동작이 이 코드에 의존하기 때문에 여기에 있습니다. AREG가 표면으로 무엇을 하는지 쫓아가는 독자는 AREG/가 아니라 공유 표면 리더에 도착합니다. 근거.

개요: 모듈이 여기서 가져가는 것

영역모듈이 얻는 것대체한 것
공유 계약믹스인 셋을 가진 핵심 메서드 클래스 하나, 필드가 선언된 타입 지정 요청, 이름이 붙은 진행률 관례메서드 선언 여섯 개(934줄), 요청 키를 문서 없이 읽는 곳 473군데, 한 진행률 채널 위의 관례 셋
환경Conda 도우미, 라이브러리 검사, CUDA 아키텍처 처리, 설치된 torch로부터 고른 PyTorch3D 휠여섯 번 복사된 conda 함수 마흔 개(656줄), 서로 다른 답을 내는 라이브러리 검사 사본 아홉 개
읽기, 쓰기, 이름 짓기하나의 파일 검색, 랜드마크와 표면의 리더와 라이터, 레이블 탐지, 파일 이름 정리, 기하 도우미열다섯 개 사본의 파일 검색, 네다섯 개 사본의 표면 리더와 라이터, 다섯 개 사본의 레이블 탐지
나머지로깅, 다크 모드 테마, 테스트 데이터 다운로드, 모델 릴리스 기준 경로, 텍스트 서식151개 파일에 있던 같은 열 줄의 로깅, 1 926줄의 테마, 일곱 개 사본의 다운로드

1. 위치

모든 것의 밑바닥에 있으면서, 어떤 파이프라인에도 속하지 않습니다. ADTLib는 확장의 빌드 파일에서 “이를 import하는 모듈보다 먼저 선언되는 공통 코드”로 가장 먼저 선언되며, 스무 개의 도구 디렉터리가 여기서 import합니다. 자체 처리 과정도, 실행할 것도, 다운로드할 것도 없습니다.

트리에서 센 크기는 파일 스물한 개, 약 3 100줄(3 144줄 집계)이며, 이것이 합쳐서 수천 줄에 달하던 사본들을 대체했습니다. 테마 모듈의 헤더 하나만으로 중복이 1 926줄이고, conda 도우미는 함수 마흔 개에 걸쳐 656줄입니다.

코드 속빌드 파일의 선언 순서와 모듈 헤더가 인용하는 줄 수

2. 모듈이 여기에 닿는 방법

Slicer는 각 확장의 스크립트 모듈 디렉터리를 import 경로에 올려 두므로, 단순한 import ADTLib가 확장의 어느 모듈에서든, 그리고 명령줄 모듈에서도 동작합니다. 겉보기보다 중요한 것은 세 번째 경로입니다. 모듈들이 Slicer의 모듈 검색 경로를 shapeaxi Conda 환경에 공개하고 나면 ADTLib는 그곳에서도 import할 수 있습니다. PyTorch 설치 프로그램이 의존하는 것이 바로 이것입니다. 이 모듈은 패널이 import하는 일이 없고, Conda 인터프리터가 모듈로 실행합니다.

결과적으로 패키지의 최상위 파일에는 import가 없어야 합니다. 이 파일들은 vtk도, Qt도, Slicer도 없는 가벼운 Conda 환경에서도 실행되기 때문입니다. 근거.

코드 속세 가지 import 경로와 패키지 루트 도우미

3. 공유 계약

세 모듈은 도구들이 계산하는 것이 아니라 서로에게 약속하는 것을 담고 있습니다.

모듈대체한 것정리한 것
method메서드 선언 여섯 개, 코드라기보다 계약에 가까운 934줄핵심(process, test process, 스캔 세기, 파일 검색)과 랜드마크, 체크박스, DICOM용 믹스인 셋. 여섯 개가 무작위로 겹친 것이 아니었기 때문입니다. 나란히 놓고 측정하니 세 군집이 뚜렷이 드러났습니다
requests없음. 한 번도 적힌 적 없는 것에 이름을 붙입니다목록이 어디에도 없는 요청 키 읽기 473건. 이제 계열마다 자신의 필드를 선언하고, 알 수 없는 키는 생성 시점에 거부되며, 빠진 키는 전과 같은 자리에서 같은 오류를 일으킵니다. 조용한 빈 값이 되지 않습니다
진행률 프로토콜한 채널 위의 문서화되지 않은 관례 셋아래 애니메이션 참조

그 100배라는 배수는 어디에도 적혀 있지 않으며, 한 저장소에 관례가 셋 생기게 했습니다. 분수를 출력하는 도구는 막대를 전진시키며, 이것이 의도된 사용입니다. 정수 2를 출력하는 도구는 200이 나타나게 하므로, 인터페이스는 200과 비교하여 환자 한 명이 더 끝났음을 알아내고, 도구는 Slicer가 값이 바뀔 때만 패널에 알리기 때문에 이를 0, 2, 0 펄스로 보냅니다. AMASSS는 둘 다 받아서 실행 중에 어느 쪽인지 추측했습니다. 이제 셋에 이름이 붙었고, 상수는 비교가 일어나는 곳이 인터페이스이므로 인터페이스가 보는 대로의 값을 담습니다. 근거.

코드 속세 모듈, 이름 붙은 상수, 확인된 진행률 결함

4. 환경

모듈 넷이며, 프로세스 밖에 닿는 ADTLib의 유일한 부분이다.

모듈대체한 것
conda 도우미함수마다 사본 여섯 개, 함수 마흔 개, 656줄, 세 가지 모양으로 갈라졌고, 그중 하나는 도달할 수 없는 return이 남아 있어 아무것도 바인딩하지 않은 이름 둘을 읽었습니다
라이브러리 검사설치된 라이브러리 검사의 사본 아홉 개, 같은 질문에 대한 세 가지 양립할 수 없는 답: AREG와 FlexReg는 라이브러리가 설치되어 있기만 하면 참이라고 답했으므로 버전 제약은 장식이었습니다
CUDA아키텍처 목록 문제: torch 휠은 고정된 아키텍처 목록용으로 컴파일된 커널을 담고 있습니다
PyTorch 설치 프로그램pytorch3d 휠 태그, pip에 맡기지 않고 설치된 torch로부터 계산

태그를 계산하는 이유: 태그가 설치된 torch와 맞지 않는 pytorch3d 휠은 설치 시점이 아니라 import 시점에 undefined symbol 오류로 죽습니다. 태그 0.7.9+pt2110cu128은 torch 2.11.0과 CUDA 12.8을 뜻하며, PyPI는 최신 조합에 대한 휠을 게시하지 않으므로 전용 인덱스를 씁니다. 근거.

코드 속모듈 넷, 휠 인덱스, 인덱스가 게시하지 않는 torch 해석

5. 읽기, 쓰기, 이름 짓기

모듈대체한 사본결정한 것
파일 검색사본 열다섯 개, 변형 여섯 가지의 검색여섯 개는 메서드였고 셋은 같은 것의 자유 함수였습니다. 객체를 빼면 바이트 단위로 동일합니다. 실질적인 차이 둘은 매개변수가 되었습니다
랜드마크읽기 엄밀히 동일한 사본 3개, 쓰기 2개ASO_CBCT, ALI_CBCT, ALI_IOS에서 진짜로 갈라진 변형은 제자리에 남습니다
표면읽기 5개, 쓰기 4개나머지와 달리 이들은 갈라져 있었습니다. 하나를 남기기 전에 차이를 측정했습니다
레이블레이블 읽기와 탐지 5개ASO_IOS, FlexReg, AREG_IOS에 걸쳐 그 자체가 사본이었던 다섯 개 치아 클래스의 메서드
이름 짓기같은 순서로 열네 번의 파일 이름 자르기를 이어 붙이는 여섯 곳순서가 곧 의미입니다. 더 긴 표지는 그것이 포함하는 더 짧은 표지보다 먼저 잘라야 하며, 그러지 않으면 두 파일이 더는 짝지어지지 않습니다
기하각각 두 개에서 네 개의 엄밀히 동일한 사본모듈 넷에 걸쳐 한 줄씩 측정했습니다. 진짜로 갈라진 것(FlexReg의 회전 행렬, ALI_IOS의 표면 변환)은 제외합니다
코드 속모듈 이름, 사본 위치, 측정한 차이

6. 나머지

모듈담고 있는 것
로깅151개 파일이 같은 열 줄을 담고 있었고, 각각 자신만의 핸들러를 붙여서 확장의 로깅을 조종할 수 없게 만들었습니다. 수준을 올리거나 실행 결과를 파일로 보내려면 그 파일을 전부 고쳐야 했습니다
테마재귀 패스 사본 열한 개와 다크 모드 함수 사본 아홉 개, 1 926줄, 이미 갈라지고 있었습니다
테스트 데이터다운로드 사본 일곱 개, 틀리는 방식이 서로 다른 셋, 셋 모두 재현됨: 그중에는 게시된 것이 모두 zip은 아니라는 점이 있습니다. ALI의 CBCT 항목은 .nii.gz 파일을 가리키는데도 곧바로 zip 리더로 들어갔습니다
모델 레지스트리릴리스 기준 경로만 다룹니다. 도구가 어떤 모델을 제공하는지는 의도적으로 말하지 않습니다. 그 선택은 도구의 몫입니다
MRI2CBCT 잔재MRI2CBCT를 다시 쓴 뒤로 이 모듈은 더 이상 공유 메서드 클래스를 쓰지 않으며, 레지스트리 상수 둘은 읽는 곳이 없습니다
format순수 함수, 표준 라이브러리만 사용. 확장 전체가 import하므로 어떤 것에도 의존해서는 안 됩니다
코드 속각 파일의 갈라진 세부 내용과 MRI2CBCT 잔재의 죽은 상수

7. 테스트가 고정하는 것

ADTLib는 22개의 테스트를 싣고 있으며, 이전에는 두 개였습니다. 이 공통 계층이 가진 명세에 가장 가까운 것이며, 여럿은 grep만으로는 충분하지 않아서 작성되었습니다. 하나는 저장소가 pip에 넘기는 모든 라이브러리와 버전이 파싱되는지 확인합니다. 세 모듈이 어느새 연산자가 붙은 제약을 얻어, pip가 대놓고 거부하는 요구 사항이 만들어졌기 때문입니다. 이 결함은 라이브러리가 이미 있는 기계에서는 보이지 않으므로, 모듈을 로컬에서 아무리 돌려 봐도 드러나지 않습니다. 이 테스트는 손으로 쓴 목록이 아니라 소스를 훑으므로, 내일 제약을 얻는 목록도 걸러집니다.

나머지는 도구 페이지들이 설명하는 동작(ALI의 경계, 예산, 진행률 계약, ASO와 AREG의 보고서 규칙, 모드를 전환해도 살아남는 출력 폴더)에 이름을 붙이며, 공유 모듈 자체의 단위 테스트도 있습니다. 평범한 PythonSlicer로 실행하면 이 모음은 테스트 188개와 오류 4개를 보고하며, 넷 모두 ALI_CBCT 테스트에서 torch가 없어서 생긴 것입니다. 코드가 아니라 환경의 속성입니다. 근거.

코드 속테스트 파일 이름과 실행의 정확한 결과

8. 이 계층 읽기

두 가지 습관이 이를 읽기 쉽게 만듭니다. 첫째, 모든 모듈 헤더는 무엇을 대체했는지, 그리고 사본들이 무엇을 두고 엇갈렸는지 밝힙니다. 근거는 이 페이지가 아니라 그곳에 있습니다. 둘째, 그 헤더들에 되풀이되는 줄은 제외한 것입니다. 진짜로 갈라진 변형은 각자의 도구에 남습니다. 테스트 메서드와 모델 선택 함수가 공유 메서드 클래스에 없는 것은 도구마다 인자 수가 분명히 다르기 때문이며, 이들을 끌어올리면 여섯 중 어느 것도 지킨 적 없는 계약을 지어내는 셈이 되었을 것입니다.

코드 속어떤 함수가 도구에 남았는지, 그리고 그 이유

9. 알려진 문제

  • 패키지의 최상위 파일에는 import가 없어야 합니다. 그러지 않으면 가벼운 Conda 환경에서 모든 하위 모듈 import가 깨집니다. 근거.
  • 100이라는 진행률 배수는 어디에도 문서화되어 있지 않으며, 관례가 셋 생기게 했습니다. 근거.
  • 설치된 torch와 맞지 않는 pytorch3d 휠은 import 시점에 죽으며, 설치 시점이 아닙니다. 근거.
  • 확인됨: torch를 쓸 수 있으면 테스트 217개가 모두 통과하고, 없으면 188개가 통과하며 테스트 파일 4개가 import에 실패하는데 넷 모두 torch가 없어서입니다. 근거.
