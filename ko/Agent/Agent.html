Agent — 전체 파이프라인

확장에서 모듈 하나를 고르고, 그 매개변수를 추출하고, 명령줄을 만들어 실행하는 자연어 어시스턴트다. 여기서는 의료용 신경망을 전혀 호출하지 않는다. Agent는 라우팅과 양식 채우기만 한다.

미발표 Agent_CLI Slicer Python qwen3:8b via Ollama cross-encoder MiniLM-L6 참고문헌

모든 것이 로컬에서 실행된다: Ollama가 제공하는 8B LLM, 그리고 후보 도구를 사전 선별하는 작은 cross-encoder.

1. 파이프라인에서의 위치

Agent를 호출하는 것은 없다. grep으로 slicer.modules.agent를 찾아도 모듈 자신 외에는 호출자가 없다. 종단 진입점이다.

호출하는 쪽으로는 두 단계가 있다:

대상 목록은 순전히 선언적이다: Agent_CLI/manifest.yaml, 즉 23개의 scripts 항목을 담은 YAML 파일에 있다. Agent는 스스로 아무것도 발견하지 않으며, 이 파일만 안다.

3. 모델

3.1 LLM — Ollama를 통한 qwen3:8b

양쪽 끝에 중복된 상수 하나: DEFAULT_MODEL = "qwen3:8b" (utils.py:21)와 MODEL_NAME = "qwen3:8b" (Agent.py:18). get_router_model()은 ROUTER_MODEL 환경 변수를 따르므로, 코드를 건드리지 않고 임의의 Ollama 모델로 바꿀 수 있다.

같은 모델이 세 호출을 모두 맡는다: 라우팅, 매개변수 추출, 복구. 전용 모델도, 미세조정도 없다.

항목값출처
추론 엔진Ollama(따라서 내부적으로 llama.cpp), 로컬 HTTP APIimport ollama, 포트 11434
가중치 형식GGUF — Ollama가 강제하며, transformers 체크포인트는 없음엔진에서 추론
다운로드ollama.com 레지스트리에서 ollama pull qwen3:8bAgent.py:1266, 그리고 chat_with_auto_pull의 자동 폴백
크기 / 양자화기본 태그: 5.2 GB, Q4_K_M, 매개변수 8.19 G저장소로는 확인 불가: ollama.com/library/qwen3에서 확인
CPU 또는 GPU코드가 아니라 Ollama가 결정아래 참조
snap으로 설치한 Ollama = CPU

모듈은 장치 지시를 전혀 전달하지 않는다. Ollama 바이너리가 결정하며, 코드는 여기서 명시적인 결론을 끌어낸다: Linux에서 snap으로 설치한 Ollama는 샌드박스에 격리되어 NVIDIA GPU를 보지 못하고 CPU로 폴백한다. 8B 모델에서 응답당 80–90초이며, 측정된 이 수치가 코드에 하드코딩되어 있다(Agent.py:1231). 모듈은 /snap/이 바이너리의 realpath에 들어 있는지 감지해 경고하지만, 고치지는 못한다(snap 서버가 이미 포트 11434를 점유하고 있고, 이를 제거하려면 sudo가 필요하다).

Ollama를 찾지 못하면 install_official_ollama() (Agent.py:101)가 공식 포터블 아카이브를 ~/.slicer_agent/ollama에 다운로드한다( SLICER_AGENT_HOME으로 변경 가능): ollama-linux-{amd64,arm64}.tgz, ollama-windows-{amd64,arm64}.zip, 또는 Ollama-darwin.zip이며, 마지막 것은 ditto로 압축을 풀고 xattr로 격리 속성을 제거한다. 이 아카이브들에는 CUDA/Metal 라이브러리가 포함되어 있으므로, curl | sudo sh(GUI에서는 root 비밀번호를 받을 수 없다)도 snap 패키지도 쓰지 않도록 의도적으로 선택했다. LD_LIBRARY_PATH는 <install>/lib/ollama를 가리키도록 설정되어, 바이너리가 자기 라이브러리를 찾는다(Agent.py:56).

호출 설정은 두 가지뿐이며, chat_with_auto_pull (utils.py:96)에 있다:

  • 기본값 5분 대신 keep_alive="30m": 두 메시지 사이에 5 GB를 VRAM에 다시 로드하지 않기 위해서다.
  • 라우터, 추출, 복구에는 format="json"(Ollama 쪽의 문법 제약). 상담 모드에는 적용되지 않는다.

temperature, seed, num_ctx, think 중 어느 것도 전달되지 않는다. qwen3는 하이브리드 추론 모델이므로, Ollama 버전에 따라 상담 모드에서 추론 텍스트가 새어 나올 수 있다. 유일한 후처리는 output.replace("*","").replace("#","") (Agent_CLI.py:215)로, 문자를 지워서 markdown을 제거하는 방식이다.

모델이 없으면 chat_with_auto_pull이 not found 메시지를 가로채 ollama.pull(model, stream=True)를 실행하며 진행 상황을 출력한 뒤, 채팅을 다시 실행한다. 다른 오류는 그대로 다시 발생시킨다.

3.2 cross-encoder — ms-marco-MiniLM-L-6-v2

프로세스에서 로드되는 유일한 실제 신경망이다. CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") (utils.py:53)를 sentence-transformers를 통해 로드한다. 따라서 가중치는 transformers/safetensors 형식이며, Hugging Face Hub에서 다운로드되어 ~/.cache/huggingface에 캐시된다.

MiniLM, 6개 층, 매개변수 22.7 M, MiniLM-L12-H384-uncased에서 증류되었고, MS MARCO Passage Ranking으로 학습되었다. 임베딩 모델이 아니다: 벡터도 코사인 유사도도 없다. 질의와 문서를 이어 붙여 함께 transformer에 넣으면, 범위 제한 없는 관련성 스칼라 하나(보통 −10에서 +10)가 나온다. 장치는 설치된 torch 휠에 따라 sentence-transformers가 스스로 고르는 것을 쓴다.

_cross_encoder_model 캐시는 실제로는 쓸모가 없다: Agent_CLI.py는 요청마다 새 프로세스이므로 메시지마다 모델이 다시 로드된다. 코드 주석도 이를 인정한다.

cross-encoder의 조용한 폴백

로드가 실패하면 폴백은 단순하다: scripts[:k], 즉 질문과 관계없이 매니페스트의 처음 세 도구(ali_cbct, ali_ios, amasss_cli) (utils.py:90). 사용자에게는 알리지 않는다.

4. 라우팅

두 단계이며, LLM은 두 번째 단계에서만 개입한다.

1단계 — cross-encoder 사전 선별. cross_encoder_retrieve_candidates(manifest, prompt, k=3)는 도구마다 문서 하나를 만든다:

docs.append(f"{s['name']}: {s['description']} (tags: {tags})")
scores = model.predict([(user_text, doc) for doc in docs])
ranked = sorted(zip(scores, scripts), reverse=True)
return [s for _, s in ranked[:k]]

23개 쌍에 점수를 매기고 내림차순으로 정렬한 뒤, top-3 고정(k=3은 매개변수로 바뀌는 일이 없다). 매니페스트의 priority 필드(값 1~23)는 읽히지 않는다. 이를 읽을 줄은 주석 처리되어 있다(utils.py:216). 올바른 도구가 4위라면 영영 사라지며, LLM은 그 도구를 보지 못한다.

2단계 — LLM의 선택. 시스템 프롬프트(Agent_CLI.py:105):

You are a tool router. Output ONLY one JSON object.
Schema:
{"tool": string|null, "confidence": number, "reason": string}

Rules:
- Choose tool ONLY from the candidate list provided by the user message.
- If none match, set tool = null and confidence <= 0.4.
- Do not invent tool names.
- Keep reason short (max 1 sentence).

사용자 메시지는 USER_REQUEST: <prompt> 다음에 CANDIDATES (choose exactly one name from this list):, 그리고 build_candidates_block이 만든 블록으로 구성된다. 블록은 후보마다 한 줄, i) name — description (truncated to 140 characters) | tags: t1, t2, … (8 max) 형식이다.

주목할 점 세 가지:

  • 폴더 맥락은 라우터에 전달되지 않는다. folders_context는 추출 프롬프트에만 추가된다.
  • 대화 이력이 system 턴과 user 턴 사이에 주입된다 (*history). 여기에는 위젯의 채팅 말풍선 원문("After reflection, I would like to run …")이 들어 있다. 따라서 JSON 라우터는 인터페이스 문구를 "assistant" 턴으로 받는다.
  • confidence와 reason은 아무 역할도 하지 않는다. confidence는 파싱되고 반올림되어 출력 JSON에 tool_confidence로 직렬화되지만… 위젯은 이를 다시 읽지 않는다. 임계값은 어디에도 없다. "confidence ≤ 0.4" 지시는 제약이 아니라 모델에 대한 제안일 뿐이다.

유일한 안전망은 텍스트 비교다: if selected_tool and selected_tool != "null" and selected_tool != "None". 매니페스트에 없는 환각 도구 이름은 이 검사를 통과한 뒤 build_cli_args를 KeyError로 실패시키고, 이 예외는 전역 try( main() 안)가 잡아 {"error": …}로 반환한다.

tools = build_tool_spec(manifest) (Agent_CLI.py:72)는 계산된 뒤 쓰이지 않는다: 사용되지 않는 코드이며, 현재 매니페스트의 어떤 항목도 쓰지 않는 "옛 구조" (patterns, defaults) 처리 코드 전체도 마찬가지다.

5. 매개변수 추출

도구가 이미 선택된 상태에서 두 번째 LLM 호출이 extract_parameters (utils.py:220) 안에서 일어난다.

기술적 매개변수 가리기. 이름이 temp_fold, tmp_folder, temp_folder, log_path, logPath인 매개변수는 프롬프트를 만들기 전에 명세에서 제거된다. 모델에게 임시 폴더를 지어내라고 할 이유가 없다. 이후 input.temp_folder 값으로 다시 주입되며, 이 값은 위젯이 클릭마다 만드는 slicer.util.tempDirectory()다 (Agent_CLI.py:153). 또한 missing_required에서 제거된다.

추출 프롬프트(parameter_extraction_improved.py:40)는 각 매개변수를 - name (type) [REQUIRED|optional] (encode: …): description 형식으로 나열한 뒤, 일곱 가지 규칙을 부과한다: encode에 따른 리스트 형식(comma_no_brackets, space_separated, comma_separated, python_literal), 따옴표 없는 JSON 불리언과 숫자, "이름에 folder나 dir가 들어 있으면 파일 이름 없이 폴더를 줄 것", 그리고 무엇보다:

7. ONLY extract parameters mentioned in the user request
   - Do NOT invent values
   - Leave unmentioned optional parameters absent

필수 출력: {"extracted": {...}, "confidence": 0.0-1.0, "missing_required": [...], "notes": "..."}. 모델이 만든 missing_required는 무시되며, 기준이 되는 것은 검증기다.

경로 해석은 전적으로 LLM에 맡겨진다

위젯은 드롭 영역에 놓인 항목 목록을 쉼표로 이어 전달하고 (Agent.py:790), CLI는 이를 다시 ,로 나눠 다음과 같이 감싼다:

FOLDERS_CONTEXT:
<one path per line>

Rules:
- Treat FOLDERS_CONTEXT as the source of truth for paths.
- If a required path parameter is missing, try to infer it from FOLDERS_CONTEXT.
- If multiple candidates exist, pick the most specific match and explain briefly in 'reason'.

이 블록은 별도로 전달되지 않고 사용자 프롬프트에 이어 붙는다. 휴리스틱 매칭도, 폴더 내용 검사도, 존재 확인도 없다: 드롭된 경로 중 어느 것이 T1이고 어느 것이 T2이고 어느 것이 모델 폴더인지는 모델이 추측해야 한다. 쉼표가 들어간 경로는 split(",")에 의해 둘로 잘린다.

검증(parameter_validator.py)은 여섯 단계를 연달아 거친다: 필수 필드 누락, 타입 변환(bool/int/float/list/path/string), 경로 구문, choices, min/max, 명세 밖 매개변수. 쓸모 있는 세부 두 가지:

  • encode: lower_str_bool은 "true"/"false" 문자열을 소문자로 강제한다. 여러 CLI가 원시 인자를 .lower() 없이 비교하기 때문이다. str(True)는 "True"가 되어 절대 일치하지 않는다.
  • _check_paths는 두 가지만 검사한다: Path(str(value))가 예외를 일으키지 않는지(거의 일으키지 않는다), 그리고 이름에 folder/dir가 들어간 매개변수가 알려진 확장자로 끝나지 않는지. 경로의 존재 여부는 검사하지 않는다.

검증 결과는 거의 전부 버려진다: errors와 warnings는 어디에도 표시되지 않는다. 유일한 효과는 유효하지 않을 때의 final_confidence = confidence * 0.6이며, 그 신뢰도는 아무도 읽지 않는다. 남는 것은 params와 missing_required뿐이다.

6. 명령 구성과 실행

그렇다, 모듈은 실제로 실행된다. 모호함 없이.

CLI는 명령을 구성할 뿐이다. build_cli_args (utils.py:350)는 매니페스트의 기본값과 추출된 매개변수를 병합한 뒤:

return [sys.executable, tool_path] + cli

sys.executable은 Agent_CLI 프로세스의 인터프리터, 즉 Slicer의 Python이다. cli_style: positional(도구 23개 중 21개)이면 값을 매니페스트의 선언 순서대로 이어 붙인다. positional_order는 지원되지만 이를 설정한 항목은 없다. 다른 cli_style이면 실행은 --flag value 분기로 빠지며, merged를 순회한다: 따라서 환각으로 생긴 명세 밖 매개변수도 그대로 출력된다.

이 목록은 JSON의 command 필드로 위젯에 반환된다. 이를 실행하는 것은 AgentWidget이며, missing_required == []일 때만 실행한다:

  1. 채팅 말풍선 "After reflection, I would like to run X";
  2. QMessageBox.question: 각 매개변수의 key=value를 나열(Agent.py:864);
  3. Yes → runToolWithRepair → subprocess.run(cli_args, capture_output=True).

missing_required가 비어 있지 않으면 에이전트는 아무것도 실행하지 않는다: 이미 알려진 값과 함께 부족한 항목 목록을 표시하고, 후속 메시지를 기다린다(대화 이력 덕분에 이어서 처리할 수 있다).

작업 중에는 Slicer가 멈춘다

subprocess.run은 동기식이며 GUI 스레드에서 실행된다: 작업이 끝날 때까지 Slicer가 멈춘다. AMASSS 분할이나 AREG 정합이라면 수십 분 단위다.

7. 복구 루프

반환 코드가 0이 아니면 runToolWithRepair (Agent.py:943)가 LLM에게 매개변수 수정을 요청하며, 최대 MAX_REPAIR_ATTEMPTS = 2번까지다. build_repair_prompt (utils.py:282)는 매개변수 정의, 사용된 값, 전체 명령, 그리고 stderr의 마지막 2000자를 보내고, 바꿀 매개변수만 반환하라고 요청한다.

이 경로는 CLI가 아니라 Slicer 프로세스 안에서 실행된다: _proposeRepair는 로직을 중복하지 않기 위해 Agent_CLI 폴더를 sys.path에 추가하고 Agent_CLI_utils를 다시 import한다. 수정안은 ParameterValidator와 build_cli_args를 다시 거치고, old -> new diff가 표시되며, 새로운 Yes/No 확인이 필요하다. diff가 비어 있으면 루프가 멈춘다.

_suggestFixFor (Agent.py:903)는 LLM을 쓰지 않는 키워드 기반 진단으로 이를 보완한다: Ollama 모델 누락, ModuleNotFoundError, NameError: name 'nn' is not defined(transformers>=4.53.0의 알려진 퇴행, huggingface/transformers#43784), Numpy is not available(numpy 2와 torch 휠 간의 ABI 충돌), 또는 Ollama 연결 실패.

스크립트 경로가 해석되지 않는다

시그니처보다 더 근본적인 문제다. 매니페스트는 이름만 준다 (path: "ALI_CBCT.py"). resolve_tool_path (utils.py:143)는 다음을 순서대로 찾는다: $AGENT_CLI_TOOLS_DIR/<name>, <manifest_dir>/CLI files/<name>, <manifest_dir>/<name>, 그리고 4단계까지 거슬러 올라가며 <ancestor>/CLI files/<name>.

AGENT_CLI_TOOLS_DIR이 없으면 Agent는 어떤 모듈도 실행할 수 없다

SlicerAutomatedDentalTools 어디에도 CLI files 폴더는 없다. 코드 주석은 AI_Agent/Agent_CLI/ + .../CLI files/ 구조를 언급하는데, 이는 Agent_CLI를 가져온 원래 저장소의 구조다. 여기서는 각 스크립트가 자기 모듈 폴더에 있다 (ALI_CBCT/ALI_CBCT.py, …). 어떤 후보도 일치하지 않고, 함수는 "so the error message points to a debuggable path"라는 이유로 candidates[0]을 반환한다. 즉 <Agent_CLI>/CLI files/ALI_CBCT.py다.

subprocess.run은 예외를 일으키지 않는다(실행 파일 sys.executable은 존재한다). 찾을 수 없는 파일 때문에 Python이 코드 2로 종료하고, 이것이 복구 루프를 시작시킨다. 그런데 복구 루프는 매개변수를 고치는 것이므로, 구조적으로 이 문제에 대해 아무것도 할 수 없다.

경로가 해석된다 해도 일부 대상은 여전히 실패할 것이다: DOCShapeAXI_CLI.py는 shapeaxi를, MRI2CBCT_TMJ_CROP.py는 nnunetv2를 import한다. 이 패키지들은 각 Slicer 모듈이 conda run -n …이나 CondaSetUpCall로 호출하는 conda 환경에 있다. 반면 Agent는 모든 것을 sys.executable, 즉 Slicer의 Python으로 실행하며, conda는 절대 쓰지 않는다.

10. 안전장치

있는 것:

  • 모든 실행 전 모든 매개변수를 나열하는 필수 모달 확인, 그리고 복구 시도마다 두 번째 확인.
  • 필수 매개변수 누락 시 차단: missing_required가 비어 있지 않으면 아무것도 실행되지 않는다.
  • 타입 변환과 choices / min / max / 폴더에 붙은 확장자 검사.
  • 임시 폴더 가리기: 모델이 아니라 slicer.util.tempDirectory()로 채워진다.
  • 상한: MAX_REPAIR_ATTEMPTS = 2, 이력은 MAX_HISTORY_ENTRIES = 40턴으로 잘린다.
  • 전역 try(main() 안): stdout은 항상 파싱 가능한 JSON으로 유지되고, traceback은 stderr로 간다.

없는 것:

  • 신뢰도 임계값 없음. tool_confidence와 parameters_confidence는 계산되고 직렬화된 뒤 무시된다. 0.1짜리 라우팅도 0.95짜리 라우팅과 똑같이 취급된다.
  • 경로 존재 확인 없음. 환각으로 생긴 경로는 검증을 통과하고, 확인 대화상자도 통과하며(사용자가 대화상자에서 눈으로 찾아내야 한다), 대상 모듈이 실행될 때에야 실패한다.
  • 검증기의 오류는 표시되지 않는다. errors, warnings, extra_params는 생성된 뒤 버려진다.
  • 출력 폴더 보호 없음. 모델이 입력 데이터 폴더를 output_folder로 골라도 막는 것이 없다. 저장소의 여러 CLI는 입력 파일을 덮어쓴다.
  • 명세 밖 매개변수가 걸러지지 않는다(--flag 모드).
  • log_path는 파일이 아니라 폴더를 받는다: 이름이 log_path와 logPath인 매개변수는 input.temp_folder로 대체되는 목록에 있다. 이 경로를 쓰기용으로 여는 CLI는 실패한다.
  • 실행 파일 화이트리스트 없음. subprocess.run은 구성된 목록을 그대로 받는다. 실제 보호 장치는 tool_path가 LLM이 아니라 매니페스트에서 온다는 점이다. 모델은 값을 정할 뿐, 바이너리는 정하지 않는다.

11. 실행 환경

CheckDependencies (Agent.py:1141)는 Slicer의 Python 안에서 slicer.util.pip_install을 실행하며, 이 순서가 중요하다:

패키지버전 고정 이유
ollamapython 클라이언트만 — pip는 서버를 제공하지 않음
pyyaml매니페스트 읽기
transformers<4.53.0퇴행 NameError: name 'nn' is not defined(integrations/accelerate.py), cross-encoder import가 깨짐
numpy<2numpy ≥ 2는 pip torch 휠의 ABI를 깨뜨림(RuntimeError: Numpy is not available)
sentence-transformerstorch를 끌어옴. 고정한 버전을 올려 버리지 않도록 마지막에 설치

Agent_CLI.py는 별도 프로세스에서 실행되지만 Slicer의 site-packages를 공유한다. 그래서 위젯 쪽에서 설치한다. conda 환경은 만들지도 쓰지도 않는다.

Ollama 서버는 127.0.0.1:11434에 대한 단순 소켓 검사로 확인하고 (_ollama_responding, 타임아웃 0.5초), 필요하면 Popen([binary, "serve"])로 다시 실행하며, UI를 살려 둔 채 500 ms 간격으로 최대 ~30초까지 기다린다. ensure_agent_ollama_running()은 메시지마다 다시 호출된다 (Agent.py:772). 모듈이 실행한 서버는 Slicer를 재시작하면 살아남지 못하기 때문이다.

Windows: 콘솔 창이 깜빡이지 않도록 CREATE_NO_WINDOW를 쓴다. 저장소의 나머지 부분과 달리 WSL은 쓰지 않는다.

12. 함정과 취약 지점

  • resolve_tool_path가 이 저장소에서 아무것도 찾지 못한다(§8). 이것이 첫 번째 차단 요인이다. 가능한 수정: 링크를 담은 CLI files 폴더를 만들거나, AGENT_CLI_TOOLS_DIR을 설정하거나, 매니페스트에 저장소 기준 상대 경로를 넣고 탐색을 확장한다.
  • 23개 중 17개 시그니처가 틀렸고, 밀림은 조용히 일어난다.
  • batchdentalseg와 clic는 CLI가 아니다. cli_style: ui_module은 어디에서도 처리되지 않는다: --flag 분기로 빠져서, 스크립트형 Slicer 모듈에서는 동작할 수 없는 명령을 만든다.
  • input.folders.split(",")는 쉼표가 들어간 경로를 모두 깨뜨린다. 폴더 목록에서도, 위젯 쪽의 join(",")에서도 마찬가지다.
  • cross-encoder가 메시지마다 다시 로드되며(새 프로세스), 로드 실패 시 사용자에게 알리지 않고 매니페스트의 처음 세 도구로 격하된다.
  • k=3이 하드코딩되어 있다. 도구 23개에 후보 3개: cross-encoder가 점수를 잘못 매기면 LLM이 만회할 수 없다.
  • priority는 아무 효과가 없어서, 매니페스트의 순위가 오해를 부른다.
  • subprocess.run이 GUI 스레드를 차단한다. 모듈 실행이 끝날 때까지 내내.
  • 이력에 UI 문구와 라우팅 맥락이 섞인다: 채팅 말풍선이 그대로 assistant 턴으로, JSON으로 제약된 라우터에 다시 전달된다.
  • OnRetrieveButton은 이모지로 나눠서 이력을 재구성한다 👨: / 🤖: (Agent.py:1126): 이 문자가 들어간 메시지는 번갈아 나오는 순서를 어긋나게 한다.
  • 픽셀 샘플링으로 테마 감지(widget.grab(), 픽셀 (5,5)의 휘도). Slicer에서는 다크 테마에서도 QPalette가 라이트 테마 색을 반환하기 때문이다 (Agent.py:656). 동작은 하지만 첫 렌더링 시점에 의존한다. 그래서 QTimer.singleShot(0, ...)이 setup에 있다.
  • 사용되지 않는 코드: AgentLogic.process(), build_tool_spec()(그리고 그 주변의 patterns/defaults 지원 전체), ValidationReport, positional_order, 매니페스트의 examples 필드, _cross_encoder_model, Agent_CLI/Resources/UI/Agent_CLI.ui.
  • extract_parameters는 값 4개를 반환한다. 그런데 타입 주석은 3개로 선언한다.

14. 문헌

논문 없음

이 모듈에 대해서도, 이 접근 방식에 대해서도 없다. SlicerAutomatedDentalTools + LLM 에이전트로 검색하면 저장소 문서와, 이 코드와 무관한 치의학 분야 LLM 일반 문헌만 나온다. 실제 외부 참고문헌은 사용된 두 모델의 것뿐이며, 둘 다 범용 모델이고 이 영역을 위해 학습되지 않았다.

  • Ollama의 Qwen3 — 라우팅과 추출 모델
  • cross-encoder/ms-marco-MiniLM-L-6-v2 — 사전 선별에 쓰이는 MS MARCO 재순위화 모델
  • SlicerAutomatedDentalTools

모듈의 git 이력은 커밋 세 개가 전부다(aa3330d ADD: Add the new agentic module, b463312, 2a91e33): 별도의 AI_Agent 저장소에서 가져온 최근 추가분이며, 그래서 매니페스트와 이 저장소의 실제 CLI 시그니처가 어긋나 있다.

전체 참고문헌: SOURCES — 검색을 수행했고 출판물 측면에서는 결과가 없었지만, 모듈 저자들이 서명한 NA-MIC Project Week PW45 보고서(Boston, 2026)를 찾아 이 폴더에 받아 두었다. 두 모델(Qwen3, MiniLM/MS MARCO)과 cross-encoder 방법에 관한 논문도 함께 받아 두었다.
