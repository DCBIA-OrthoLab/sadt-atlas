Agent: 전체 파이프라인

Slicer 확장에서 모듈을 고르고, 그 매개변수를 추출하고, 명령줄을 만들어 실행하는 자연어 어시스턴트이다. 여기서 호출되는 의료용 신경망은 없다. Agent는 라우팅과 양식 채우기만 한다. 이 페이지는 그 과정을 단계별로 설명하며, 개발자에게 필요한 세부 사항은 코드 페이지에 있다.

미발표 Agent_CLI Slicer Python Ollama를 통한 qwen3:8b cross-encoder MiniLM-L6 코드 (개발자용) 참고문헌 VISOR: 일부

모든 것이 로컬에서 실행된다. Ollama가 서빙하는 8B 언어 모델과, 후보 도구를 미리 추리는 작은 cross-encoder다.

코드베이스가 둘이다. 여기서 설명하는 것은 모두 레거시 Slicer 모듈(SlicerAutomatedDentalTools 3c67957, 2026-10-26)이다. VISOR에는 Agent라는 서버 도구가 있어 외부 Ollama 엔드포인트 위의 라우터 역할을 하지만, 이를 호출하는 클라이언트는 없다. VISOR 클라이언트에 들어 있는 AgentRemote 패널은 여전히 로컬에서 실행되는 레거시 위젯의 사본이다. 둘 다 VISOR의 Agent 페이지에서 설명한다. 근거.

1. 체인에서의 위치

Agent를 호출하는 것은 없다. 확장의 다른 어떤 모듈도 이를 쓰지 않는다. 종단 진입점이다. 바깥으로는 세 가지를 호출한다.

호출되는 것방법위치

대상 모듈(ALI_CBCT, AMASSS_CLI, ...)패널의 자식 프로세스로 시작됨Slicer Python

대상 목록은 순전히 선언적이다. manifest.yaml에 있으며, 항목이 16개인 YAML 파일이다. Agent는 스스로 아무것도 발견하지 않는다. 이 파일만 안다.

2. 관련 파일

패널(채팅, 드롭 영역, Ollama 설치, 확인, 실행, 복구)은 Slicer 안에서 실행된다. 별도의 명령줄 프로그램이 라우팅과 추출을 하고 JSON을 출력할 뿐 아무것도 실행하지 않는다. 유틸리티 파일이 매니페스트, cross-encoder, Ollama 호출, 경로 탐색, 명령 구성을 담당한다. 검증기가 값을 변환하고 검사하며, 매니페스트는 호출 가능한 도구 16개를 나열한다. conda 환경도 필수 GPU도 없다. 모든 것이 Slicer의 Python 안에서 실행되며, 쓰이는 GPU는 Ollama 서버를 통한 간접적인 것뿐이다.

코드에서파일 표와 각각이 어디서 실행되는지

3. 모델

3.1 언어 모델, Ollama를 통한 qwen3:8b

모델 하나가 세 번의 호출을 모두 맡는다. 라우팅, 매개변수 추출, 복구이며, 80억 파라미터의 Qwen3를 Ollama(따라서 밑바닥은 llama.cpp)가 Ollama가 강제하는 GGUF 형식으로 실행한다. 특화된 모델도 파인튜닝도 없다. 모델 이름은 코드의 두 곳에 적혀 있으며 환경 변수로 바꿀 수 있다. 기본 태그의 크기는 5.2 GB이다(ollama.com에서 읽은 값이며, 저장소에서는 확인할 수 없다).

CPU로 실행될지 GPU로 실행될지는 모듈이 아니라 Ollama가 결정한다. 코드는 한 가지 결론을 끌어낸다. Linux에서 snap으로 설치된 Ollama는 샌드박스에 갇혀 NVIDIA GPU를 보지 못하고 CPU로 폴백하며, 8B 모델에서 응답당 80에서 90초가 걸린다. 이 수치는 측정된 값으로 코드에 적혀 있다. 모듈은 이를 감지하여 경고하지만 고칠 수는 없다.

Ollama를 찾지 못하면 모듈이 공식 포터블 아카이브를 자기 전용 폴더에 내려받으므로, 패널에서 root 비밀번호가 필요 없다. 호출 설정은 두 가지만 쓴다. 모델을 5분이 아니라 30분 동안 로드된 채로 두고, 답변은 라우터, 추출, 복구에서 JSON으로 제약된다(컨설턴트 모드는 아님). temperature, seed, 컨텍스트 크기는 넘기지 않는다. 모델이 없으면 내려받고 호출을 다시 재생한다.

코드에서상수, snap 검사, Ollama 설치기, 두 가지 호출 설정

3.2 cross-encoder: ms-marco-MiniLM-L-6-v2

프로세스에 로드되는 유일한 실제 신경망이다. MiniLM, 6층, 파라미터 2270만 개이며, MS MARCO passage-ranking 과제로 학습되어 Hugging Face Hub에서 내려받는다. 임베딩 모델이 아니다. 요청과 도구 텍스트를 함께 트랜스포머에 넣으면 범위가 제한되지 않는 관련도 숫자 하나가 나온다. 명령줄 프로그램은 메시지마다 새 프로세스이므로 모델이 매번 다시 로드된다.

cross-encoder 로드가 실패하면 폴백은 단순하다. 질문과 무관하게 매니페스트의 처음 도구 세 개이며, 채팅에는 알려지지 않는다(프로그램 출력에만 한 줄이 간다). 매니페스트의 priority 필드는 읽히지 않는다.

코드에서도구 텍스트가 만들어지는 방식, 정렬, 하드코딩된 k, 조용한 폴백

4. 라우팅

두 단계이며, 언어 모델은 두 번째 단계에서만 개입한다. 1단계는 위의 cross-encoder이다. 2단계에서 모델은 요청과 후보 세 개를 받는데, 후보마다 한 줄(이름, 140자에서 자른 설명, 태그 최대 8개)이며, 도구 이름 하나, confidence 하나, 한 문장짜리 이유로 이루어진 JSON 객체 하나로 답해야 한다. 알아 둘 점이 세 가지 있다.

  • 폴더 맥락은 라우터에 전달되지 않으며, 나중에 추출 단계에서만 추가된다.
  • 대화 기록은 화면에 보이는 그대로 주입된다. "After reflection, I would like to run ..."처럼 패널 자신의 문장도 포함되므로, JSON 라우터는 인터페이스 문장을 이전 답변으로 받는다.
  • confidence와 이유는 쓸모가 없다. confidence는 파싱되어 기록되지만 다시 읽히지 않는다. 어디에도 임계값이 없으며, "일치하는 것이 없으면 confidence는 최대 0.4"라는 지시는 모델에 대한 제안일 뿐이다.

유일한 안전망은 문자열 검사다. 답이 null이면 안 된다는 것이다. 매니페스트에 없는 도구 이름은 이 검사를 통과한 뒤 명령 구성기를 실패시키며, 그 오류는 잡혀서 오류 메시지로 돌려보내진다.

코드에서라우터 프롬프트, 대화 기록 주입, 죽은 tool-spec 코드

5. 매개변수 추출

이미 도구가 정해진 상태에서 하는 두 번째 모델 호출이다. 기술적 매개변수(임시 폴더, 로그 경로)는 모델이 보는 내용에서 제거되고 이후 패널이 채워 넣는다. 모델에게 지어내라고 하지 않는 것이다. 프롬프트는 매개변수마다 그 타입, 필수 여부, 목록을 어떻게 써야 하는지를 나열한 뒤 일곱 가지 규칙을 부과하며, 무엇보다도 요청에 언급된 것만 추출하고, 값을 지어내지 말고, 언급되지 않은 선택 매개변수는 비워 둘 것이라고 한다. 모델이 돌려주는 필수 매개변수 목록은 무시되며, 중요한 것은 검증기다.

검증기는 도구가 원래 인자를 그대로 비교하는 곳에서 텍스트 “true”나 “false”를 소문자로 강제하기도 한다. 그 밖에 검증 보고서는 거의 전부 버려지며, 그 오류와 경고는 어디에도 나타나지 않는다.

경로는 전적으로 모델에 맡겨진다. 패널에 끌어다 놓은 폴더는 요청 뒤에 이어 붙여지며, 이를 진실의 원천으로 취급하라는 지시가 붙는다. 휴리스틱 매칭도, 폴더 내부 확인도, 존재 확인도 없다. 끌어다 놓은 경로 중 어느 것이 T1이고, 어느 것이 T2이며, 어느 것이 모델 폴더인지를 모델만이 짐작한다. VISOR가 고친 것은 이 중 쉼표 부분뿐이다. 서버 도구는 폴더를 목록으로 받는다.

코드에서추출 프롬프트, 여섯 단계의 검증, 쉼표로 쪼개는 경로 블록

6. 명령 구성과 실행

그렇다, 모듈은 실제로 실행된다. 명령줄 프로그램은 명령을 구성할 뿐이다. 매니페스트의 기본값을 추출된 값과 병합하고, 앞에 Slicer 자신의 인터프리터와 스크립트 경로를 붙인다. 16개 도구 중 14개는 값을 매니페스트가 선언한 순서대로 하나씩 이어 쓸 뿐이다(위치 인자 방식).

이어서 패널이 명령을 실행하는데, 필수인 것이 하나도 빠지지 않았을 때만 그렇다. 채팅 말풍선이 무엇을 실행하고 싶은지 말하고, Yes/No 대화상자가 모든 매개변수를 나열하며, Yes를 누르면 모듈이 시작된다. 필수인 것이 빠졌으면 아무것도 실행되지 않는다. 패널은 빠진 것의 목록을 이미 알려진 값과 함께 보여 주고 후속 메시지를 기다린다. 실행은 동기식이며 인터페이스 스레드에서 이루어진다. 작업 내내 Slicer가 멈추며, 분할이나 정합이라면 수십 분이 걸린다.

코드에서명령 구성기, 대화상자, 블로킹 subprocess 호출

7. 복구 루프

이 경로는 명령줄 프로그램이 아니라 Slicer 프로세스 안에서 실행된다. 수정은 검증기와 명령 구성기를 다시 거치고, 이전과 이후의 차이가 표시되며, 새로운 Yes/No 확인이 필요하다. 차이가 비어 있으면 루프가 멈춘다. 모델을 쓰지 않는 키워드 기반 진단이 Ollama 모델 없음, Python 모듈 없음, 최근 transformers 릴리스의 알려진 회귀, torch 휠과의 numpy 2 충돌, Ollama 연결 실패에 대한 힌트를 더한다.

코드에서복구 프롬프트, 재import 요령, 키워드 진단

8. 호출 가능한 모듈과 그 실제 상태

매니페스트는 도구를 16개 나열한다. 그 매개변수 목록을 대상 스크립트 각각의 실제 명령줄과 파일 하나하나 대조했다. 시그니처 16개 중 2개만 올바르다. DOCShapeAXI와 MRI2CBCT_resample이다. 둘 더(BatchDentalSeg와 CLIC)는 명령줄 도구가 아니라 스크립트형 Slicer 모듈이어서 이런 식으로는 실행할 수 없다. AMASSS는 아예 거부한다(“Expected 13 arguments”). 나머지는 각각 매개변수가 하나에서 넷까지 빠져 있다.

명령줄에서는 아무것도 이름이 없으므로, 목록이 너무 짧으면 깔끔한 오류가 나지 않는다. 예를 들어 AREG_IOS에서는 로그 파일 경로가 파일 이름 접미사가 되어 버린다. 매니페스트에 없어서 Agent가 닿을 수 없는 것: VFACE, GreedyReg, CNE, AREG_IOSCBCT, SurgMovPred, Medical_Data_Anonymizer.

코드에서스크립트마다 매니페스트와 실제 매개변수 수를 비교한 16행 표

스크립트 경로가 해석되지 않는다

시그니처보다 더 근본적인 문제다. 매니페스트는 스크립트 이름만 준다. 경로 탐색은 순서대로 AGENT_CLI_TOOLS_DIR 변수가 가리키는 폴더, 매니페스트 옆의 “CLI files” 폴더, 매니페스트 폴더 자체, 그리고 위로 최대 네 단계를 본다. 이 저장소에는 그 어느 것도 없으며 각 스크립트는 자기 모듈 폴더에 있으므로 일치하는 후보가 없고, 함수는 “오류 메시지가 디버그할 수 있는 경로를 가리키도록” 첫 번째 후보를 반환한다.

실행 자체는 예외를 내지 않는다(Slicer의 인터프리터는 존재한다). 찾지 못한 파일에 대해 코드 2로 종료하는 것은 Python이며, 이것이 복구 루프를 일으킨다. 경로가 해석되더라도 일부 대상은 여전히 실패한다. DOCShapeAXI는 conda 환경에 있는 패키지가 필요한데, Agent는 모든 것을 Slicer의 Python으로 실행한다.

코드에서해석기, 그 후보 네 개, 클라이언트 사본에 대한 콜아웃

9. 두 가지 모드

모드Agent_CLI가 돌려주는 것실행
Agent (Automated)도구, 그 confidence, 매개변수, 빠진 것, 명령을 담은 JSON 객체예, 확인 뒤에
Ask (Interactive)자유 텍스트없음

Ask 모드에서는 각 후보 줄이 매개변수의 원본 목록도 함께 싣고, 이것이 “expert medical image analysis consultant”의 시스템 프롬프트에 그대로 붙여진다. 답은 JSON으로 제약되지 않으며 문자 *와 #를 제거한 뒤 표시된다. README는 이 모드를 “Consultant”라고 부르고, 인터페이스는 “Ask (Interactive)”라고 하며, 코드는 Agent 이름만 검사하므로 다른 값은 모두 컨설턴트 모드로 떨어진다.

코드에서두 가지 출력 형태와 정확한 모드 검사

10. 안전장치

있는 것:

  • 모든 실행 전에 필수 확인이 있으며 매개변수를 모두 나열하고, 모든 복구 시도 전에도 한 번 더 있다.
  • 필수 매개변수가 빠져 있으면 아무것도 실행되지 않는다.
  • 타입 변환, 그리고 선택지, 범위, 폴더 이름 같은 이름의 확장자에 대한 검사.
  • 임시 폴더는 모델이 아니라 패널이 채운다.
  • 제한: 복구 시도 2번, 기록은 최대 40턴, 그리고 프로그램의 출력이 항상 파싱 가능한 JSON으로 남도록 하는 전역 catch.

없는 것:

  • confidence 임계값이 없다. 0.1의 라우팅도 0.95의 라우팅과 똑같이 취급된다.
  • 경로 존재 확인이 없다. 환각으로 만든 경로는 검증과 확인을 통과하며(운영자가 눈으로 알아채야 한다), 모듈이 시작될 때에야 실패한다.
  • 검증기의 오류는 결코 표시되지 않는다.
  • 출력 폴더에 대한 보호가 없다. 모델이 입력 데이터 폴더를 출력으로 고르더라도 막는 것이 없다.
  • 실행 파일 화이트리스트는 없지만, 실질적인 보호는 스크립트 경로가 모델이 아니라 매니페스트에서 온다는 점이다. 모델이 제어하는 것은 값이지 실행되는 프로그램이 아니다.
코드에서로그 경로와 명세 밖 매개변수 사례를 포함한 전체 목록

11. 환경

패널은 Slicer의 Python에 패키지 다섯 개를 설치하며, 순서가 중요하다. Ollama Python 클라이언트, 매니페스트용 YAML 리더, 4.53보다 오래된 transformers(회귀가 cross-encoder import를 깨뜨린다), 2보다 오래된 numpy(numpy 2가 torch 휠을 깨뜨린다), 그리고 고정된 버전을 올리지 않도록 마지막에 sentence-transformers이다. 명령줄 프로그램은 별도 프로세스에서 실행되지만 Slicer의 패키지를 공유한다. conda 환경은 만들어지지 않는다.

Ollama 서버는 로컬 포트로 탐침하며, 필요하면 시작하고 인터페이스를 살려 둔 채 최대 약 30초 기다린다. 모듈이 띄운 서버는 Slicer를 다시 시작하면 살아남지 못하므로 메시지마다 앞서 다시 확인한다. Windows에서는 콘솔 창이 표시되지 않으며, 저장소의 나머지와 달리 WSL 지원은 없다.

12. 함정과 취약한 지점

  • 모듈 스크립트를 찾을 수 없어 도구 전체가 막힌다. 근거.
  • 시그니처 16개 중 14개가 틀렸고, 밀림은 조용하다. 근거.
  • cross-encoder는 조용히 폴백하여 처음 도구 세 개를 취하고, 메시지마다 다시 로드되며, 상위 3개가 하드코딩되어 있다. 근거.
  • 작업 내내 Slicer가 멈춘다. 근거.
  • 경로 해석은 전적으로 모델에 맡겨진다. 근거.
  • Ollama를 snap으로 설치하면 CPU로 실행된다. 근거.
  • 모드는 둘인데 이름은 셋이다. 근거.
  • 죽은 코드가 남아 있다: 쓰이지 않는 process(), 쓰이지 않는 tool-spec 빌더, 쓰이지 않는 cross-encoder 캐시, 명령줄 모듈이 로드하지 않는 인터페이스 파일. 근거.
  • 기록이 인터페이스 문장과 라우팅 맥락을 섞는다. 저장된 대화를 다시 불러올 때는 텍스트를 이모지 두 개로 나누어 기록을 다시 만들므로, 이 이모지가 든 메시지는 기록을 어긋나게 한다(실시간 채팅은 턴을 목록으로 유지한다).
코드에서테마 감지와 반환 개수를 포함해 파일과 줄이 적힌 취약한 지점 열두 개

14. 문헌

이 모듈에 대해서도, 접근 방식에 대해서도 논문이 없다. SlicerAutomatedDentalTools와 LLM 에이전트를 검색하면 저장소의 문서와 치의학 분야 언어 모델에 관한 일반 문헌만 나온다. 진짜 외부 참고문헌은 사용된 두 모델의 것뿐이며, 둘 다 일반적인 것이고 이 영역을 위해 학습된 것이 아니다. VISOR 서버 도구도 같은 접근이며, README에는 포팅 원본인 레거시 파일을 명시한 출처 절이 있을 뿐 출판물은 없다. 근거.
