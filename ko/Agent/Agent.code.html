Agent, 레거시: 코드

개발자용: 레거시 Agent 모듈이 코드에서 하는 일을 file:line 참조, 프롬프트, 매니페스트 검사, 환경, 발견 사항과 함께 다룬다. 같은 파이프라인에 대한 읽기 쉬운 설명은 아틀라스 페이지에 있다.

Agent_CLI 코드 아틀라스 (해설) 참고문헌 VISOR: 일부

모든 것이 로컬에서 실행된다. Ollama가 서빙하는 8B LLM과, 후보 도구를 미리 추리는 작은 cross-encoder다.

두 코드 베이스

아래에 번호가 붙은 모든 것은 레거시 Slicer 모듈(SlicerAutomatedDentalTools 3c67957, 2026-10-26)을 설명한다. VISOR에는 Agent라는 서버 도구가 있어 외부 Ollama 엔드포인트 위의 라우터 역할을 하지만, 이를 호출하는 클라이언트는 없다. VISOR 클라이언트에 들어 있는 AgentRemote 패널은 여전히 로컬에서 실행되는 레거시 위젯의 사본이다. 둘 다 VISOR의 Agent 페이지에서 설명한다.

쉬운 설명과 수식: 아틀라스 페이지.

바깥으로 나가는 호출은 두 단계다.

3. 모델

쉬운 설명과 수식: 아틀라스 페이지.

3.1 LLM, Ollama를 통한 qwen3:8b

쉬운 설명과 수식: 아틀라스 페이지.

양 끝에 중복된 상수 하나: DEFAULT_MODEL = "qwen3:8b"(utils.py:21)와 MODEL_NAME = "qwen3:8b"(Agent.py:29). get_router_model()은 ROUTER_MODEL 환경 변수를 따르므로, 코드를 건드리지 않고도 어떤 Ollama 모델로든 바꿀 수 있다.

같은 모델이 세 번의 호출을 모두 맡는다. 라우팅, 매개변수 추출, 복구. 특화된 모델도 파인튜닝도 없다.

항목값출처
추론 엔진Ollama(따라서 밑바닥은 llama.cpp), 로컬 HTTP APIimport ollama, 포트 11434
가중치 형식GGUF: Ollama가 강제하며 transformers 체크포인트는 없다엔진에서 추론
다운로드ollama.com 레지스트리에서 ollama pull qwen3:8bAgent.py:1142, 그리고 chat_with_auto_pull의 자동 폴백
크기 / 양자화기본 태그: 5.2 GB, Q4_K_M, 파라미터 8.19 G저장소에서는 확인할 수 없음: ollama.com/library/qwen3에서 읽을 것
CPU 또는 GPU코드가 아니라 Ollama가 결정한다아래 참조
snap으로 설치된 Ollama = CPU · 레거시 전용

레거시 전용(3c67957). VISOR에는 없음: 클라이언트 사본에는 /snap/ 검사가 없으며(AutomatedDentalToolsRemote AgentRemote/AgentRemote.py에 일치 없음), 서버 도구는 Ollama를 설치하지도 시작하지도 않는다. 닿을 수 있는 엔드포인트가 필요하다(SADT-VISOR tools/Agent/src/sadt_agent/llm.py:1-25, 엔드포인트 결정은 :38-39).

모듈은 장치 지시를 전혀 넘기지 않는다. 결정은 Ollama 바이너리가 하며, 코드는 거기서 명시적인 결론을 끌어낸다. Linux에서 snap으로 설치된 Ollama는 샌드박스에 갇혀 NVIDIA GPU를 보지 못하고 CPU로 폴백하며, 8B 모델에서 응답당 80–90 s가 걸린다. 이 수치는 측정된 값으로 코드에 하드코딩되어 있다(Agent.py:1101-1103의 주석, 경고 대화상자에서 반복). 모듈은 /snap/을 바이너리의 realpath에서 감지해 이를 경고하지만, 고칠 수는 없다(snap 서버가 이미 포트 11434를 차지하고 있고, 제거하려면 sudo가 필요하다).

Ollama를 찾지 못하면 install_official_ollama()(Agent.py:111)가 공식 포터블 아카이브를 ~/.slicer_agent/ollama(SLICER_AGENT_HOME으로 변경 가능)에 내려받는다. ollama-linux-{amd64,arm64}.tgz, ollama-windows-{amd64,arm64}.zip 또는 Ollama-darwin.zip이며, ditto로 풀고 xattr로 격리 속성을 제거한다. 이 아카이브에는 CUDA/Metal 라이브러리가 들어 있으며, 그래서 curl | sudo sh(GUI에서는 root 비밀번호를 받을 수 없다)도 snap 패키지도 쓰지 않기로 의도적으로 선택했다. LD_LIBRARY_PATH는 <install>/lib/ollama를 가리키므로 바이너리가 자기 라이브러리를 찾는다(Agent.py:67).

chat_with_auto_pull(utils.py:96)에는 호출 설정이 두 개뿐이다.

  • keep_alive="30m"은 기본값 5분 대신이며, 메시지 두 개 사이에 VRAM으로 5 GB를 다시 올리지 않기 위한 것이다.
  • format="json"은 라우터, 추출, 복구에 쓰인다(Ollama 쪽의 문법 제약). 컨설턴트 모드에는 쓰이지 않는다.

temperature, seed, num_ctx, think는 전혀 넘기지 않는다. qwen3는 하이브리드 추론 모델이므로, 그 결과 컨설턴트 모드에서는 Ollama 버전에 따라 추론 텍스트가 새어 나올 수 있다. 유일한 후처리는 output.replace("*","").replace("#","")(Agent_CLI.py:215)이며, 문자를 지우는 방식으로 마크다운을 제거한다.

모델이 없으면 chat_with_auto_pull이 not found 메시지를 가로채고, 진행률을 출력하면서 ollama.pull(model, stream=True)를 실행한 뒤 채팅을 다시 재생한다. 그 밖의 오류는 그대로 다시 발생시킨다.

3.2 cross-encoder: ms-marco-MiniLM-L-6-v2

쉬운 설명과 수식: 아틀라스 페이지.

프로세스에 로드되는 유일한 실제 신경망이다. CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")(utils.py:53)를 sentence-transformers로 불러오므로, transformers/safetensors 가중치가 Hugging Face Hub에서 내려받아져 ~/.cache/huggingface에 캐시된다.

MiniLM, 6층, 파라미터 22.7 M이며, MiniLM-L12-H384-uncased에서 증류되어 MS MARCO Passage Ranking으로 학습되었다. 임베딩 모델이 아니다. 벡터도 코사인 유사도도 없다. 질의와 문서를 이어 붙여 함께 트랜스포머에 넣으면 범위가 제한되지 않는 관련도 스칼라 하나(보통 −10에서 +10)가 나온다. 장치는 sentence-transformers가 설치된 torch 휠에 따라 스스로 고르는 것이다.

_cross_encoder_model 캐시는 실제로는 아무 쓸모가 없다. Agent_CLI.py는 요청마다 새 프로세스이므로 메시지마다 모델이 다시 로드된다. 코드 주석도 이를 인정한다.

조용한 cross-encoder 폴백 · 레거시와 클라이언트 사본이며 서버 도구는 아님

레거시(3c67957). VISOR 서버 도구에는 없음: 서버의 랭커는 BM25이며, 신호가 있을 때만 목록을 좁힌다. 요청과 겹치는 도구가 하나도 없으면 모든 도구가 표시된다(SADT-VISOR tools/Agent/src/sadt_agent/ranking.py:222-239). cross-encoder 폴백은 클라이언트 사본에서는 여전히 사실이다(AutomatedDentalToolsRemote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:94, 레거시 Agent_CLI/Agent_CLI_utils/utils.py:94).

로드가 실패하면 폴백은 단순하다. scripts[:k], 곧 질문과 무관하게 매니페스트의 처음 도구 세 개(ali_cbct, ali_ios, amasss_cli)이다(utils.py:94). 유일한 흔적은 CLI 출력에 찍히는 한 줄(utils.py:93)이며, 채팅에는 알려지지 않는다.

4. 라우팅

쉬운 설명과 수식: 아틀라스 페이지.

두 단계이며, LLM은 두 번째 단계에서만 개입한다.

1단계, cross-encoder 사전 선별. cross_encoder_retrieve_candidates(manifest, prompt, k=3)가 도구마다 문서 하나를 만든다.

docs.append(f"{s['name']}: {s['description']} (tags: {tags})")
scores = model.predict([(user_text, doc) for doc in docs])
ranked = sorted(zip(scores, scripts), reverse=True)
return [s for _, s in ranked[:k]]

쌍 16개를 점수화하여 내림차순으로 정렬하고, 하드코딩된 상위 3개를 취한다(k=3은 매개변수로 받지 않는다). 매니페스트의 priority 필드(값 1에서 23, 빠진 번호 있음)는 읽히지 않는다. 이를 읽을 줄은 주석 처리되어 있다(utils.py:216). 올바른 도구가 4위였다면 영영 사라지며, LLM은 그것을 결코 보지 못한다.

2단계, LLM의 선택. 시스템 프롬프트(Agent_CLI.py:105):

You are a tool router. Output ONLY one JSON object.
Schema:
{"tool": string|null, "confidence": number, "reason": string}

Rules:
- Choose tool ONLY from the candidate list provided by the user message.
- If none match, set tool = null and confidence <= 0.4.
- Do not invent tool names.
- Keep reason short (max 1 sentence).

사용자 메시지는 USER_REQUEST: <prompt>에 이어 CANDIDATES (choose exactly one name from this list):와 build_candidates_block이 만든 블록이다. 후보마다 한 줄이며 i) name — description (truncated to 140 characters) | tags: t1, t2, … (8 max)이다.

주목할 만한 점이 세 가지 있다.

  • 폴더 맥락은 라우터에 전달되지 않는다. folders_context는 추출 프롬프트에만 추가된다.
  • 대화 기록은 시스템 턴과 사용자 턴 사이에 주입된다(*history). 여기에는 위젯의 채팅 말풍선이 가공 없이 들어 있다("After reflection, I would like to run …"). 그래서 JSON 라우터는 인터페이스 문장을 "assistant" 턴으로 받는다.
  • confidence와 reason은 쓸모가 없다. confidence는 파싱되고, 반올림되고, 출력 JSON에 tool_confidence로 직렬화되지만, 위젯이 다시 읽는 일은 없다. 어디에도 임계값이 없다. "confidence ≤ 0.4"라는 지시는 제약이 아니라 모델에 대한 제안일 뿐이다.

유일한 안전망은 문자열 검사다. if selected_tool and selected_tool != "null" and selected_tool != "None". 매니페스트에 없는, 환각으로 만든 도구 이름은 이 검사를 통과한 뒤 build_cli_args를 KeyError로 실패시키며, 이는 전역 try에 잡혀 main()이 {"error": …}로 돌려보내진다.

tools = build_tool_spec(manifest)(Agent_CLI.py:72)는 계산된 뒤 쓰이지 않는다. 죽은 코드이며, 현재 매니페스트의 어떤 항목도 쓰지 않는 "옛 구조"(patterns, defaults)에 대한 처리도 모두 그렇다.

5. 매개변수 추출

쉬운 설명과 수식: 아틀라스 페이지.

이미 도구가 정해진 상태에서 하는 두 번째 LLM 호출로, extract_parameters(utils.py:220) 안에서 이루어진다.

기술적 매개변수 마스킹. 이름이 temp_fold, tmp_folder, temp_folder, log_path, logPath인 매개변수는 프롬프트를 만들기 전에 명세에서 제거된다. 모델에게 임시 폴더를 지어내게 해 봐야 소용이 없기 때문이다. 이들은 이후 값 input.temp_folder로 다시 주입되며, 이는 위젯이 클릭할 때마다 만드는 slicer.util.tempDirectory()(Agent_CLI.py:153)이고, missing_required에서도 제거된다.

추출 프롬프트(parameter_extraction_improved.py:40)는 매개변수를 - name (type) [REQUIRED|optional] (encode: …): description 형태로 하나씩 나열한 뒤 규칙 일곱 가지를 부과한다. encode에 따른 목록 서식(comma_no_brackets, space_separated, comma_separated, python_literal), 따옴표 없는 JSON 불리언과 숫자, "이름에 folder 또는 dir이 들어 있으면 파일 이름 없는 폴더를 줄 것", 그리고 무엇보다도:

7. ONLY extract parameters mentioned in the user request
   - Do NOT invent values
   - Leave unmentioned optional parameters absent

의무 출력: {"extracted": {...}, "confidence": 0.0-1.0, "missing_required": [...], "notes": "..."}. 모델이 낸 missing_required는 무시되며, 중요한 것은 검증기다.

경로 해석을 전적으로 LLM에 맡긴다 · VISOR에서는 부분적으로 고쳐짐

경로 부분은 VISOR에서도 사실이며, 쉼표 부분은 고쳐졌다. 서버 도구는 folders를 목록으로 받으므로 폴더 이름의 쉼표가 더 이상 이를 쪼개지 않는다(SADT-VISOR tools/Agent/src/sadt_agent/__init__.py:40,124). 어느 경로가 어느 인자에 들어가는지는 여전히 모델만이 결정한다. validation.py는 공개된 스키마에 대해 타입과 choices를 검사할 뿐 경로가 존재하는지는 검사하지 않는다(validation.py:1-30).

위젯은 드롭 영역에 끌어다 놓은 항목 목록을 쉼표로 이어서 넘기고(Agent.py:770), CLI는 이를 ,에서 다시 쪼개어 감싼다.

FOLDERS_CONTEXT:
<one path per line>

Rules:
- Treat FOLDERS_CONTEXT as the source of truth for paths.
- If a required path parameter is missing, try to infer it from FOLDERS_CONTEXT.
- If multiple candidates exist, pick the most specific match and explain briefly in 'reason'.

이 블록은 사용자 프롬프트 뒤에 이어 붙여지며 따로 전달되지 않는다. 휴리스틱 매칭도, 폴더 내용 검사도, 존재 확인도 없다. 끌어다 놓은 경로 중 어느 것이 T1이고, 어느 것이 T2이며, 어느 것이 모델 폴더인지는 모델이 짐작해야 한다. 쉼표가 들어 있는 경로는 split(",")에 의해 둘로 잘린다.

검증(parameter_validator.py)은 여섯 단계를 잇는다. 빠진 필수 필드, 타입 변환(bool/int/float/list/path/string), 경로 구문, choices, min/max, 명세 밖 매개변수. 유용한 세부 사항이 둘 있다.

  • encode: lower_str_bool은 "true"/"false" 문자열을 소문자로 강제한다. 여러 CLI가 .lower() 없이 원래 인자를 비교하기 때문이다. str(True)는 "True"를 주므로 결코 일치하지 않는다.
  • _check_paths는 두 가지만 검사한다. Path(str(value))가 예외를 내지 않는지(거의 내지 않는다), 그리고 이름에 folder/dir가 들어 있는 매개변수가 알려진 확장자로 끝나지 않는지이다. 경로의 존재는 한 번도 검사되지 않는다.

검증 결과는 거의 전부 버려진다. errors와 warnings는 어디에도 나타나지 않는다. 유일한 효과는 유효하지 않을 때의 final_confidence = confidence * 0.6이며, 그 confidence를 읽는 곳은 없다. 살아남는 것은 params와 missing_required뿐이다.

6. 명령 구성과 실행

쉬운 설명과 수식: 아틀라스 페이지.

그렇다, 모듈은 실제로 실행된다. 의심의 여지가 없다.

CLI는 명령을 구성만 한다. build_cli_args(utils.py:350)는 매니페스트의 기본값과 추출된 매개변수를 병합한 뒤 다음을 한다.

return [sys.executable, tool_path] + cli

sys.executable은 Agent_CLI 프로세스의 인터프리터, 곧 Slicer의 Python이다. cli_style: positional(16개 중 14개 도구)에서는 값이 매니페스트의 선언 순서대로 이어 붙여진다. positional_order는 지원되지만 그것을 설정한 항목은 없다. 그 밖의 cli_style에서는 실행이 --flag value 분기로 떨어져 merged를 순회하므로, 환각으로 만든 명세 밖 매개변수도 실제로 내보내진다.

목록은 JSON의 command 필드로 위젯에 돌려보내진다. 이를 실행하는 것은 AgentWidget이며, missing_required == []일 때만 그렇다.

  1. 채팅 말풍선 하나, "After reflection, I would like to run X",
  2. QMessageBox.question이 각 매개변수의 key=value를 나열한다(Agent.py:841, 복구 단계는 다시 묻는다, :938),
  3. Yes이면 → runToolWithRepair → subprocess.run(cli_args, capture_output=True).

missing_required가 비어 있지 않으면 에이전트는 아무것도 실행하지 않는다. 빠진 것의 목록을 이미 알려진 값과 함께 표시하고, 후속 메시지를 기다린다(대화 기록 덕분에 그 메시지에 다시 이어 붙일 수 있다).

작업 중 Slicer가 멈춘다 · 레거시와 클라이언트 사본이며 서버 도구는 아님

레거시(3c67957). VISOR 서버 도구에는 없음: 서버 도구는 execute가 true일 때만 선택한 도구를 슈퍼바이저를 통해 실행한다(SADT-VISOR tools/Agent/src/sadt_agent/execution.py:70). 멈춤은 클라이언트 사본에서는 여전히 사실이다(AutomatedDentalToolsRemote AgentRemote/AgentRemote.py:767, 레거시 Agent/Agent.py:898).

subprocess.run은 동기식이며 GUI 스레드에서 실행된다. 작업 내내 Slicer가 멈추며, AMASSS 분할이나 AREG 정합이라면 수십 분이 걸린다.

7. 복구 루프

쉬운 설명과 수식: 아틀라스 페이지.

반환 코드가 0이 아니면 runToolWithRepair(Agent.py:880)가 LLM에게 매개변수 수정을 요청하며, 최대 MAX_REPAIR_ATTEMPTS = 2번이다. build_repair_prompt(utils.py:282)는 매개변수 정의, 사용된 값, 전체 명령, stderr의 마지막 2000자를 보내며, 바꿀 매개변수만 돌려 달라고 요청한다.

이 경로는 CLI가 아니라 Slicer 프로세스 안에서 실행된다. _proposeRepair가 Agent_CLI 폴더를 sys.path에 추가하고 Agent_CLI_utils를 다시 import하여 로직을 중복하지 않는다. 수정은 ParameterValidator와 build_cli_args를 다시 거치고, old -> new diff가 표시되며, 새로운 Yes/No 확인이 필요하다. diff가 비어 있으면 루프는 멈춘다.

_suggestFixFor(Agent.py:1240)는 LLM을 쓰지 않는 키워드 기반 진단으로 이를 보완한다. Ollama 모델 없음, ModuleNotFoundError, NameError: name 'nn' is not defined(transformers>=4.53.0의 알려진 회귀, huggingface/transformers#43784), Numpy is not available(torch 휠에 대한 numpy 2 ABI 충돌), 또는 Ollama 연결 실패이다.

스크립트 경로가 해석되지 않는다

쉬운 설명과 수식: 아틀라스 페이지.

시그니처보다 더 근본적인 문제다. 매니페스트는 이름만 준다(path: "ALI_CBCT.py"). resolve_tool_path(utils.py:143)는 순서대로 $AGENT_CLI_TOOLS_DIR/<name>, <manifest_dir>/CLI files/<name>, <manifest_dir>/<name>, 그리고 4단계까지 올라가며 <ancestor>/CLI files/<name>을 찾는다.

AGENT_CLI_TOOLS_DIR 없이는 Agent가 어떤 모듈도 실행하지 못한다 · 클라이언트 사본에도 해당

클라이언트 사본에도 해당하며 서버 도구에는 해당 없음. AgentRemote를 담은 확장에도 그런 폴더는 없고, 해석기는 여전히 AGENT_CLI_TOOLS_DIR을 읽는다(AutomatedDentalToolsRemote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:154, CLI 모듈은 삭제되었다, CMakeLists.txt:49-56). 서버 도구는 경로로 실행하는 것이 없다.

SlicerAutomatedDentalTools 어디에도 CLI files 폴더는 없다. 코드 주석은 AI_Agent/Agent_CLI/ + .../CLI files/ 배치를 인용하는데, Agent_CLI를 추출해 온 원래 저장소의 구조이다. 여기서는 각 스크립트가 자기 모듈 폴더에 있다(ALI_CBCT/ALI_CBCT.py, …). 일치하는 후보가 없으며, 함수는 "오류 메시지가 디버그할 수 있는 경로를 가리키도록" candidates[0], 곧 <Agent_CLI>/CLI files/ALI_CBCT.py를 반환한다.

subprocess.run은 예외를 내지 않는다(실행 파일 sys.executable은 존재한다). 찾지 못한 파일에 대해 코드 2로 종료하는 것은 Python이며, 이것이 복구 루프를 일으킨다. 복구 루프는 매개변수를 고치는 것이므로 구조적으로 이를 어쩔 수 없다.

경로가 해석되더라도 일부 대상은 여전히 실패한다. DOCShapeAXI_CLI.py는 shapeaxi를 import하는데, 이 패키지는 해당 Slicer 모듈이 conda run -n …이나 CondaSetUpCall로 호출하는 conda 환경에 있다. (MRI2CBCT는 더 이상 예가 아니다. 그 nnunetv2는 이제 Slicer 자신의 Python에서 실행된다.) 반면 Agent는 모든 것을 sys.executable, 곧 Slicer의 Python으로 실행하며, conda는 쓰지 않는다.

10. 안전장치

쉬운 설명과 수식: 아틀라스 페이지.

있는 것:

  • 모든 실행 전에 필수 모달 확인이 있으며 매개변수를 모두 나열하고, 모든 복구 시도 전에도 한 번 더 있다.
  • 필수 매개변수가 빠지면 차단: missing_required가 비어 있지 않은 동안에는 아무것도 실행되지 않는다.
  • 타입 변환과 choices / min / max / 폴더에 붙은 확장자 검사.
  • 임시 폴더 마스킹: 모델이 아니라 slicer.util.tempDirectory()로 채워진다.
  • 제한: MAX_REPAIR_ATTEMPTS = 2, 기록은 MAX_HISTORY_ENTRIES = 40턴으로 잘린다.
  • 전역 try가 main() 안에 있다. stdout은 항상 파싱 가능한 JSON으로 남고, 트레이스백은 stderr로 간다.

없는 것:

  • confidence 임계값이 없다. tool_confidence와 parameters_confidence는 계산되고 직렬화되지만 무시된다. 0.1의 라우팅도 0.95의 라우팅과 똑같이 취급된다.
  • 경로 존재 확인이 없다. 환각으로 만든 경로는 검증을 통과하고 확인도 통과하며(운영자가 대화상자에서 눈으로 알아채야 한다), 대상 모듈이 시작될 때에야 실패한다.
  • 검증기의 오류는 결코 표시되지 않는다. errors, warnings, extra_params는 만들어진 뒤 버려진다.
  • 출력 폴더에 대한 보호가 없다. 모델이 입력 데이터 폴더를 output_folder로 고르더라도 막는 것이 없다. 저장소의 여러 CLI는 자신의 입력 파일을 덮어쓴다.
  • --flag 모드에서는 명세 밖 매개변수가 걸러지지 않는다.
  • log_path가 폴더를 받는다, 파일이 아니다. log_path와 logPath라는 이름은 input.temp_folder로 대체되는 매개변수 목록에 있다. 이 경로를 쓰기용으로 여는 CLI는 실패한다.
  • 실행 파일 화이트리스트가 없다. subprocess.run은 만들어진 목록을 그대로 받는다. 실질적인 보호는 tool_path가 LLM이 아니라 매니페스트에서 온다는 점이다. 모델이 제어하는 것은 값이지 바이너리가 아니다.

11. 환경

쉬운 설명과 수식: 아틀라스 페이지.

CheckDependencies(Agent.py:1018)는 Slicer의 Python 안에서 slicer.util.pip_install을 실행하며, 순서가 중요하다.

패키지고정하는 이유
ollamapython 클라이언트뿐이다. pip는 서버를 제공하지 않는다
pyyaml매니페스트 읽기
transformers<4.53.0회귀 NameError: name 'nn' is not defined(integrations/accelerate.py에서), cross-encoder import를 깨뜨린다
numpy<2numpy ≥ 2는 pip torch 휠의 ABI를 깨뜨린다(RuntimeError: Numpy is not available)
sentence-transformerstorch를 끌어온다. 고정된 버전을 올리지 않도록 마지막에 설치한다

Agent_CLI.py는 별도 프로세스에서 실행되지만 Slicer의 site-packages를 공유하므로 설치는 위젯 쪽에서 한다. conda 환경은 만들어지지도 쓰이지도 않는다.

Ollama 서버는 127.0.0.1:11434에 대한 단순한 소켓 탐침(_ollama_responding, 타임아웃 0.5 s)으로 확인하며, 필요하면 Popen([binary, "serve"])로 다시 띄우고 UI를 살려 둔 채 500 ms 간격으로 최대 약 30 s 기다린다. ensure_agent_ollama_running()은 메시지마다 앞서 다시 호출된다(Agent.py:752). 모듈이 띄운 서버는 Slicer를 다시 시작하면 살아남지 못하기 때문이다.

Windows: 콘솔 창이 깜빡이지 않도록 CREATE_NO_WINDOW. 저장소의 나머지와 달리 WSL은 없다.

12. 함정과 취약한 지점

쉬운 설명과 수식: 아틀라스 페이지.

  • resolve_tool_path는 이 저장소에서 아무것도 찾지 못한다(§8). 이것이 첫 번째 걸림돌이다. 해결책으로는 링크가 든 CLI files 폴더를 만들거나, AGENT_CLI_TOOLS_DIR을 설정하거나, 매니페스트에 저장소 기준 상대 경로를 넣고 탐색을 확장하는 방법이 있다.
  • 시그니처 16개 중 14개가 틀렸고, 밀림은 조용하다.
  • batchdentalseg와 clic은 CLI가 아니다. cli_style: ui_module은 어디서도 처리되지 않는다. --flag 분기로 떨어지며, 스크립트형 Slicer 모듈에서는 동작할 수 없는 명령이 만들어진다.
  • input.folders.split(",")는 쉼표가 든 모든 경로를 깨뜨리며, 폴더 목록에서도 위젯 쪽의 join(",")에서도 그렇다.
  • cross-encoder는 메시지마다 다시 로드되며(새 프로세스), 로드가 실패하면 운영자에게 알리지 않은 채 매니페스트의 처음 도구 세 개로 성능이 떨어진다.
  • k=3은 하드코딩되어 있다. 도구 16개에 후보 3개이므로, cross-encoder의 잘못된 점수화를 LLM이 만회할 수 없다.
  • priority는 아무 일도 하지 않으며, 이 때문에 매니페스트의 순위는 오해를 부른다.
  • subprocess.run이 GUI 스레드를 막는다. 모듈이 실행되는 내내 그렇다.
  • 기록이 UI 문장과 라우팅 맥락을 섞는다. 채팅 말풍선이 JSON으로 제한된 라우터에 assistant 턴으로 그대로 되돌려 보내진다.
  • OnRetrieveButton은 이모지로 나누어 기록을 다시 만든다 👨: / 🤖:(Agent.py:1003-1004). 저장된 대화 파일을 다시 불러올 때만 그렇고, 이 문자들이 든 메시지는 교대 순서를 어긋나게 한다. 실시간 채팅 중에 CLI로 보내는 기록은 이모지로 나눈 텍스트가 아니라 턴의 목록이다(Agent.py:736-743).
  • 픽셀 샘플링에 의한 테마 감지(widget.grab(), 픽셀 (5,5)의 휘도). Slicer에서는 다크 테마에서도 QPalette가 라이트 테마 색을 돌려주기 때문이다(Agent.py:649). 동작은 하지만 첫 렌더링의 타이밍에 의존하며, 그래서 QTimer.singleShot(0, ...)이 setup에 있다.
  • 죽은 코드: AgentLogic.process(), build_tool_spec()(그리고 그 주변의 patterns/defaults 지원 전부), ValidationReport, positional_order, 매니페스트의 examples 필드, _cross_encoder_model, Agent_CLI/Resources/UI/Agent_CLI.ui.
  • extract_parameters는 값을 4개 돌려준다. 어노테이션은 3개라고 선언한다.

14. 문헌

쉬운 설명과 수식: 아틀라스 페이지.

논문 없음 · 변동 없음

VISOR에서도 사실이다. 서버 도구도 같은 접근(라우팅과 양식 채우기)이다. README에는 포팅 원본인 레거시 파일을 명시한 출처 절이 있을 뿐 출판물은 없다(SADT-VISOR tools/Agent/README.md:316-324).

이 모듈에 대해서도, 접근 방식에 대해서도 없다. SlicerAutomatedDentalTools + LLM agent를 검색하면 저장소의 문서와, 이 코드와 무관한 치의학 분야 LLM에 관한 일반 문헌만 나온다. 진짜 외부 참고문헌은 사용된 두 모델의 것뿐이며, 둘 다 일반적인 것이고 이 영역을 위해 학습된 것이 아니다.

  • Ollama의 Qwen3: 라우팅과 추출 모델
  • cross-encoder/ms-marco-MiniLM-L-6-v2 : 사전 선별에 쓰인 MS MARCO 리랭커
  • SlicerAutomatedDentalTools

모듈의 git 이력은 커밋 세 개(aa3330d ADD: Add the new agentic module, b463312, 2a91e33)에 들어갈 만큼 짧다. 별도의 AI_Agent 저장소에서 가져온 최근의 추가물이며, 그래서 이 저장소에서 매니페스트와 실제 CLI 시그니처가 어긋난다.

전체 참고문헌: SOURCES. 검색을 마쳤으며 출판물에 관해서는 결과가 음성이었지만, 모듈 저자들이 서명한 NA-MIC Project Week PW45 보고서(보스턴, 2026)를 찾아 이 폴더에 가져왔고, 두 모델(Qwen3, MiniLM/MS MARCO)과 cross-encoder 방법의 논문도 함께 두었다.
