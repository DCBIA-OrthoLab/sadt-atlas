AREG_IOSCBCT — 전체 파이프라인

다중 모달리티 정합: 구강 스캔(Intra Oral Scan)을 같은 환자의 CBCT 좌표계에 배치한다. CLI는 전적으로 기하 계산이며 — 가중치를 전혀 로드하지 않는다.

미발표 areg_ioscbct Slicer Python CLI에 신경망 없음 참고문헌

종단적(T1 → T2, 같은 모달리티)인 AREG_IOS와는 관계가 없다. 여기서는 두 점 구름이 서로 다른 센서에서 나오며, 공통의 "안정 패치(stable patch)"가 없다.

연속된 두 맞춤 단계이며, CLI 안에는 신경망이 없다.

  1. 교합 랜드마크 12개: 서로 다른 두 신경망(볼륨에는 ALI_CBCT, 메시에는 ALI_IOS)이 양쪽에서 예측 → 사전 정렬 역할을 하는 강체 Procrustes 변환 (vtkLandmarkTransform);
  2. ICP로 IOS 표면을 등위면(CBCT에서 marching cubes로 임계값 400에서 추출)에 맞춘다.

따라서 CLI 자체는 전적으로 기하 계산이다. 지능은 상류, 즉 오케스트레이터가 그 앞에 쌓아 두는 모듈들에 있다.

1. 파이프라인에서의 위치

AREG_IOSCBCT/AREG_IOSCBCT.py는 세 가지 모드를 정의하는 AREG/AREG_Method/IOSCBCT.py에서만 호출된다. 자신은 아무것도 호출하지 않는다.

모드클래스AREG_IOSCBCT 앞에 쌓이는 단계
RegistrationReg_IOSCBCT (IOSCBCT.py:392)없음: 사용자가 IOS, CBCT, 두 랜드마크 폴더를 제공
Semi-AutomatedSemi_IOSCBCT (IOSCBCT.py:157)CrownSegmentationcli → ALI_CBCT → ALI_IOS
Fully-AutomatedAuto_IOSCBCT (IOSCBCT.py:469)7단계, §2 참조

즉 이것은 실제로 얇은 말단 CLI를 가진 오케스트레이터다. 진짜 파이프라인은 Process()가 만드는 프로세스 목록이다.

Fully-Automated 모드의 전체 순서

3. 파일 짝짓기

getPatients()(AREG_IOSCBCT.py:339)는 네 폴더를 훑어 <patient_id>_<timepoint> 키를 만든다.

추출 대상정규식비고
시점[Tt]([0-2])T0, T1, T2만. _T3은 아무것과도 맞지 않는다 → 환자가 조용히 무시됨
치열궁(?:^|_)(?:u|upper)(?=_|\.|$), 그리고 l/lower에 대해서도 같은 식문자는 구분된 토큰이어야 한다. 이름 중간의 고립된 u는 더 이상 인정되지 않는다 — 그렇지 않으면 P001_T1_L_Surface.vtk가 "upper"로 읽혀 잘못된 랜드마크에 정합되었다
환자([A-Za-z]+)[_]?([0-9]+)[_]?[Tt][0-2]문자 + 숫자가 붙어 있음
정규화밑줄 제거, 앞의 0 제거P_0001, P001, P00001 → P1

기대하는 확장자: IOS는 .vtk만, CBCT는 .nii.gz만, 랜드마크는 .json.

환자마다 일곱 항목을 갖춰야 한다: ios_upper, ios_lower, cbct, ios_lm_upper, ios_lm_lower, cbct_lm_upper, cbct_lm_lower. 키가 하나라도 없으면 메인 루프에서 KeyError가 나고, 이는 환자별 try/except에서 잡힌다 → 환자는 오류 로그와 함께 그냥 건너뛰어진다.

같은 식별자 정규화가 위젯 쪽의 Review._normalisedId()(AREG/AREG_Method/Review.py:210)에 다시 구현되어 있다. 이름이 정규화된 정합 IOS에 대응하는 원본 CBCT를 찾기 위해서다.

4. 두 모달리티 맞추기

가능한 세 가설에 대한 짧은 답: 사전 정렬에는 공유 랜드마크, 그다음 임계값으로 CBCT에서 추출한 표면에 대한 ICP. CBCT 쪽에는 치아 분할이 없으며, IOS 쪽 분할은 ALI_IOS가 치아별로 카메라를 조준하게 하는 데만 쓰인다.

4.1 CBCT 표면

load_data() (AREG_IOSCBCT.py:315):

image = sitk.ReadImage(scan_path)
ijk_to_lps = np.eye(4)
ijk_to_lps[:3, :3] = direction @ np.diag(spacing)
ijk_to_lps[:3, 3]  = origin
vol = pv.wrap(sitk.GetArrayFromImage(image).transpose(2, 1, 0))
cbct_raw_mesh = vol.contour(isosurfaces=[400])
cbct_surface  = cbct_raw_mesh.transform(ijk_to_lps, inplace=False)
  • GetArrayFromImage는 (z,y,x)를 주고, transpose(2,1,0)가 이를 (x,y,z)로 되돌려 pv.wrap이 인덱스 공간에서 단위 spacing을 갖는 ImageData를 만들게 한다;
  • contour(isosurfaces=[400]) = 값 400에서의 marching cubes. 암묵적 단위: CBCT가 보정되어 있다면 HU. 이 임계값은 하드코딩되어 있으며 뼈와 법랑질을 구분 없이 잡는다;
  • 손으로 다시 만든 ijk_to_lps 행렬이 등위면을 물리적 LPS 좌표로 되돌린다.

이는 나머지와 일관된다. ALI_CBCT와 ALI_IOS는 둘 다 "coordinateSystem": "LPS"를 쓰고(ALI_CBCT/ALI_CBCT_utils/io.py:36, ALI_IOS/ALI_IOS_utils/io.py:85), .vtk 파일은 LPS다. 따라서 뒤집기는 필요 없으며, 수행되지도 않는다.

4.2 레이블로 랜드마크 짝짓기

_pair_landmarks()(AREG_IOSCBCT.py:54)는 양쪽에 모두 있는 레이블만 IOS 레이블 순서대로 남기고, CBCT에서 빠진 레이블을 로그에 기록한다.

중요한 수정

vtkLandmarkTransform은 원본 점과 대상 점의 수가 같아야 한다. 크기가 다른 목록을 받으면 stderr에 오류를 쓰고 항등 변환을 반환한다. 그래서 사전 정렬이 아무 표시 없이 사라지곤 했다. 또 부분 목록 두 개를 위치로 짝지으면 서로 전혀 관계없는 점들이 짝지어졌다.

4.3 강체 사전 정렬

align_by_landmarks() (AREG_IOSCBCT.py:108):

landmark_transform = vtk.vtkLandmarkTransform()
landmark_transform.SetSourceLandmarks(points_moving)   # IOS
landmark_transform.SetTargetLandmarks(points_fixed)    # CBCT
landmark_transform.SetModeToRigidBody()                # 6 dof, no scaling

안전장치 두 가지이며, 둘 다 명시적 경고와 함께 항등 변환(새 vtk.vtkMatrix4x4())으로 대체한다.

안전장치상수코드의 근거
쌍의 수MIN_LANDMARK_PAIRS = 3점 하나는 순수 이동뿐이고, 점 두 개로는 축 둘레의 회전이 자유롭게 남는다
RMS 잔차MAX_LANDMARK_RESIDUAL_MM = 10.0, 환경 변수 AREG_MAX_LANDMARK_RESIDUAL로 변경 가능강체 변환은 거리를 보존한다. 잔차가 크면 두 세트가 같은 해부 구조를 기술하지 않는다는 증거다

_alignment_residual()(AREG_IOSCBCT.py:67)은 모든 이동 랜드마크에 행렬을 적용하고 차이의 RMS를 계산한다.

변환된 메시, 행렬, 그리고 변환된 IOS 랜드마크를 반환한다 — 마지막 것이 출력 json에 들어간다.

4.4 ICP

run_icp_point_to_plane()(AREG_IOSCBCT.py:163)은 max_dist=1.0으로 호출된다(기본값 1.5는 쓰이지 않는다).

매개변수값효과
max_iterations2000
max_dist1.0 mm더 먼 대응점은 제외 (valid_mask)
rmse_threshold1e-8inlier RMSE 변화량에 대한 수렴
fitness_threshold1e-8inlier 비율 변화량에 대한 수렴
추가 정지 조건유효 대응점 < 3
자료 구조scipy.spatial.cKDTree, 고정 점 대상, 루프 밖에서 한 번 생성
질의kdtree.query(..., k=1, workers=-1)모든 코어에서 병렬 처리. 주된 비용이 여기서 든다

반복마다: 최근접 이웃 대응점, max_dist로 거르기, 그다음 중심을 맞춘 점들에 대해 SVD 기반 Kabsch로 강체 추정, 반사를 막기 위한 행렬식 보정 (Vt[-1,:] *= -1, det(R) < 0일 때). 변환은 왼쪽에서 합성되며(transformation = delta @ transformation) 매 회 원래 점에 다시 적용되므로 오차 누적을 피한다.

함수가 이름대로 동작하지 않는다

이름은 run_icp_point_to_plane이다. 고정 메시의 사본에 대해 fixed_normals를 compute_normals(inplace=True)로 계산하기는 하지만 — 결코 쓰지 않는다. 최소화되는 기준은 ‖R·s + t − d‖², 즉 고전적인 점-대-점(point-to-point)이다. 법선은 호출될 때마다, 환자당 두 번, 면이 수십만 개에 이를 수 있는 marching cubes 등위면에 대해 계산된 뒤 버려진다.

ICP가 실제로 정합하는 것: IOS 메시 전체(모든 정점이 이동 점)를 400 등위면 전체 — 치조골, 법랑질, 피질골, 아티팩트, 임계값 노이즈 — 에 대해 정합한다. 치아로의 제한도, 마스크도, 가중치도 없다. 결과를 쓸 만하게 만드는 것은 오로지 좋은 랜드마크 사전 정렬 + 1 mm 대응 창의 조합이며, 이것이 사실상 교합면 바로 아래에 있지 않은 모든 것을 걸러 낸다.

제약 없는 교합

두 치열궁은 같은 등위면에 대해 독립적으로 정합되며, 별도의 행렬 mat_icp_upper와 mat_icp_lower를 쓴다 — 상대적인 교합은 제약되지 않는다.

5. 출력

save_registered_ios()(AREG_IOSCBCT.py:272)와 apply_matrix_and_save_landmarks()(AREG_IOSCBCT.py:278), 모두 <output>(Semi와 Auto 모드에서는 = <folder_output>/Registered IOS) 안에 기록한다.

파일내용
<pid>_Reg_U.vtk상악 IOS, 랜드마크 변환 후 ICP 적용
<pid>_Reg_L.vtk같은 것, 하악
<pid>_lm_Reg_U.mrk.jsonCBCT json에서 각 position을 같은 레이블의 정합된 IOS 랜드마크 위치로 바꾼 것
<pid>_lm_Reg_L.mrk.json동일

<pid>는 정규화된 식별자다(P1이지 P_0001이 아니다). 따라서 출력 이름은 입력 이름과 닮지 않으며, 그래서 _matchAcrossNaming()이 AREG/AREG_Method/Review.py:226에 있다.

출력 json 파일은 의문스러운 선택이다. 컨테이너는 CBCT에서 오고(표시, ID, 순서) 좌표는 IOS에서 온다. _write_positions()(AREG_IOSCBCT.py:81)는 레이블로 짝짓고, IOS 대응점이 없는 CBCT 제어점은 원래 위치에 남기지 않고 버린다. 이전 버전은 위치로 인덱싱했다. 랜드마크가 하나인 CBCT와 IOS 쪽 여섯 개를 맞추면 UL1O의 좌표를 레이블 UR6O 아래에 썼다.

.tfm은 생성되지 않는다

랜드마크 행렬도 ICP 행렬도 디스크에 기록되지 않는다. 변환된 기하만 기록된다. 이는 위젯 수준에서 인정된 사항이다. 검토 페이지 ioscbct_registration의 유형은 VIEW이지 REGISTRATION이 아니며, "This step writes no matrix, so the result cannot be moved here"라는 문구가 있다 (AREG/AREG_Method/Review.py:680) — 따라서 AREG_IOS나 AREG_CBCT에서처럼 사용자가 마우스로 정합을 보정할 수 없다.

정합된 환자가 하나도 없으면 main()이 RuntimeError를 일으킨다 (AREG_IOSCBCT.py:577). 그렇지 않으면 try/except/continue 루프가 빈 출력 폴더와 함께 코드 0으로 끝나고, Slicer는 파이프라인이 성공했다고 보고했다.

다시 말해 AREG_IOSCBCT CLI는 아무것도 학습하거나 예측하지 않는다. 다른 곳에서 예측된 랜드마크 두 세트와 임계값으로 얻은 등위면을 소비할 뿐이다.

7. 함정과 취약 지점

임계값 400은 하드코딩되어 있다

그리고 결코 노출되지 않는다. HU로 보정되지 않은 CBCT나 다른 재구성 방식에서는 등위면이 다른 것을 잡고, ICP는 노이즈에 대해 정합한다. 기관마다 바꿔야 할 가능성이 가장 높은 매개변수다.

  • run_icp_point_to_plane은 점-대-점이다. 법선은 계산된 뒤 버려진다. 이름이 틀렸거나 구현이 미완성이다 — 어느 쪽이든, 점-대-면(point-to-plane; 매끄러운 표면에서 더 나은 수렴, 접선 방향 미끄러짐 감소)을 기대하는 유지보수자는 실망할 것이다.
  • 두 모달리티, 환자 키당 CBCT는 하나지만, 두 치열궁은 필수다. 상악만 스캔된 환자는 KeyError를 일으키고 로그 한 줄만 남긴 채 실행에서 사라진다.
  • CBCT는 .nii.gz여야 한다. 그런데 위젯 쪽의 NumberScan은 .nrrd .nii .gipl과 그 .gz 변형까지 센다 (IOSCBCT.py:32). 진행 표시줄이 CLI가 결코 보지 못할 환자를 표시할 수 있다.
  • 시점은 T0–T2로 제한된다([Tt]([0-2])) — TIMEPOINT-SUFFIX 주석(AREG_IOSCBCT.py:372)과 AREG_CBCT/AREG_CBCT_utils/utils.py:83의 중심 메모를 참조.
  • 정규화 후 식별자 충돌: P001과 P1은 같은 키, 즉 같은 환자가 된다. getPatients에서는 아무것도 이를 감지하지 않으며, 나중에 위젯만이 후보가 여러 개라고 경고한다(Review.py:243).
  • 사용되지 않는 코드: load_data()는 lm_cbct_U/L과 lm_ios_U/L을 get_landmarks()로 계산하지만(위치 인덱싱, 레이블 없음), 네 개 모두 곧바로 _pair_landmarks()가 덮어쓴다 (AREG_IOSCBCT.py:507). 쓰이는 것은 cbct_surface뿐이다. 마찬가지로 DisplayAREGIOSCBCT는 두 번 정의되어 있으며 (AREG/AREG_Method/Progress.py, 135행과 182행), 두 번째가 첫 번째를 가린다. 그리고 PatientScanLandmark(IOSCBCT.py:40)는 어디에서도 호출되지 않는다.
  • DisplayAREGIOSCBCT(0)는 세 모드 모두에서 nb_progress_total = 0으로 생성된다: self.progress / 0 → 진행 표시줄이 갱신되면 ZeroDivisionError. 갱신은 progress == 200 and updateProgessBar == False 조건에서만 일어나므로, 이 문제가 눈에 띄지 않는다.
  • fitness와 inlier_rmse는 ICP 루프 이후에 읽힌다. max_iterations = 0(여기서는 불가능하지만 취약함)이거나 첫 break에서 < 3 대응점으로 빠져나가는 경우에도 정의되어는 있다 — 그러나 코드는 이를 방어하지 않는다.
  • pyvista는 Slicer Python에 설치되며, 버전 0.47.3으로 고정된다. 이 모듈만을 위해 존재하는 무거운 의존성이며(pv.wrap, contour, transform, read, save), 이미 있는 VTK를 직접 써서 대체할 수 있다.
사전 정렬이 조용히 항등 변환이 될 수 있다

이는 오류가 아니라 경고로만 기록된다. 실행 전체가 사전 정렬을 전혀 받지 못하고도 파일을 출력할 수 있다. 한 묶음을 신뢰하기 전에 로그에서 Skipping the pre-alignment 줄을 확인하라.

8. 문헌

미발표

여기 구현된 형태의 AREG_IOSCBCT를 다루는 논문은 없다. 그룹이 출판한 계보는 CBCT 방향 정렬과 정합 (Automated Orientation and Registration of CBCT Scans, LNCS 2023)과 종단적 IOS 정합(AReg IOS, LNCS 2023)을 다루며, 이 모듈이 소비하는 랜드마크 모듈들은 각자의 논문이 있다 (ALI_CBCT). 다중 모달리티 IOS↔CBCT 부분은 출판되지 않은 내부 조립으로 보인다.

문헌상 방법론적으로 가까운 연구 — 비교를 위한 것이며, 이 코드에 대한 기술이 아니다.

  • Novel Procedure for Automatic Registration between CBCT and Intraoral Scan Data Supported with 3D Segmentation: 같은 문제이지만, 양쪽 모두 치아 분할을 거친 뒤 RANSAC + ICP를 쓴다. 보고된 오차 0.234 ± 0.019 mm. AREG_IOSCBCT는 명백히 더 가벼운 길을 택한다. 볼륨 분할 대신 랜드마크, 분할된 치아 대신 임계값 등위면이다.
  • Automatic multimodal registration of CBCT and intraoral scans: a systematic review and meta-analysis: 체계적 문헌고찰로, 기하적 접근(신뢰할 만하고 비용이 낮음)과 학습 기반 접근을 대비시킨다.
  • Fully automatic integration of dental CBCT images and full-arch intraoral impressions: 치아별 식별과 스티칭 오차 보정을 포함한 변형.
