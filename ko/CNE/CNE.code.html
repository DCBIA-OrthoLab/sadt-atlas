CNE, 레거시: 코드

개발자용: 레거시 Slicer 모듈 CNE가 코드에서 하는 일을(3c67957 시점의 SlicerAutomatedDentalTools) file:line 참조, 코드 블록, 인자, 환경, 주의점과 함께 다룬다. 같은 파이프라인에 대한 읽기 쉬운 설명은 아틀라스 페이지에 있다.

미발표 VISOR CNE_CLI conda 없음: Slicer의 Python 참고문헌 코드 아틀라스 (해설) 가이드

범위 경고. AutoCrop3D나 AutoMatrix와 달리 CNE는 기하 유틸리티가 아니다. 볼륨도, 메시도, 좌표도 건드리지 않는다. 자유 형식의 임상 노트를 읽고 키-값 쌍을 쓰는 LLM 추론 모듈이다. 모듈의 핵심에는 Slicer의 Python 안에서 llama-cpp-python이 불러오는 양자화된 GGUF 모델이 있다.

두 코드 베이스

아래에 번호가 붙은 모든 내용은 레거시 Slicer 모듈(3c67957 시점의 SlicerAutomatedDentalTools, 2026-10-26)을 설명한다. 같은 도구를 서버에서 실행하는 VISOR 포팅은 별도 페이지 VISOR의 CNE에서 설명한다. 읽기 전에 알아 둘 결과가 하나 있다. 이 페이지가 모델이 로컬에서 실행된다고 말하는 곳은 레거시 모듈에만 해당한다. VISOR에서는 노트 텍스트가 서버로 전송된다(VISOR의 발견 사항 참고).

0. 약어

쉬운 설명과 수식: 아틀라스 페이지.

저장소는 어떤 문서에서도 이 약어를 풀어 쓰지 않는다. README에는 CNE 절이 없고, CNE가 대체한 MedX도 더 이상 문서화하지 않아서 어느 이름도 거기에 나오지 않는다. 모듈의 도움말 텍스트(CNE.py:157)는 "This tool helps to create summaries of clinical notes"라고만 말한다.

풀이를 주는 것은 두 로그 줄뿐이다. logger.info("CNE (Clinical Notes Extraction)")(CNE.py:342와 CNE.py:663), 그리고 CLI가 같은 이름을 Slicer 감독자(supervisor)에게 알린다. <filter-name>Clinical Notes Extraction</filter-name>(CNE_CLI.py:93). CNE = Clinical Notes Extraction, 코드가 증명하고 그 밖에는 아무것도 증명하지 않는다.

알아 둘 두 가지:

함정 (레거시 전용)

레거시(3c67957). VISOR에는 없다. 워크스테이션에서는 컴파일되거나 설치되는 것이 없고, 서버 환경은 미리 빌드된 휠 인덱스에서 llama-cpp-python==0.3.35를 고정한다(SADT-VISOR tools/CNE/pyproject.toml:60-67. VISOR의 CNE 참고). install_function(CNE.py:44)은 설치 동안 CC=gcc와 CXX=g++를 강제하고 그 뒤 원래 값을 복원한다. pip가 llama-cpp-python을 소스에서 컴파일해야 하는 경우를 위한 것이다. Windows에서는 이 값들을 쓸 수 없다.

함정 (VISOR에서도 마찬가지, 이제 보고됨)

VISOR에서도 마찬가지다. 고정된 인덱스는 여전히 CPU용이다(SADT-VISOR tools/CNE/pyproject.toml:60-67). 달라진 것은 요청이 더 이상 조용하지 않다는 점이다. device는 기본값이 cpu인 명시적 인자이고, CPU 빌드가 받은 cuda 요청은 보고서에 gpu_offload와 warnings로 기록된다(src/sadt_cne/__init__.py:145-165,184-185. VISOR의 CNE 참고). 추가 인덱스는 명시적으로 CPU 휠을 가리킨다. 그런데도 CLI는 "Use GPU if available"이라는 주석과 함께 n_gpu_layers=-1을 요청한다(CNE_CLI.py:164). CPU 전용 빌드에서는 이 파라미터가 효과가 없다. 실제로는 추론이 CPU에서 실행되며, 7–8 B의 Q4 양자화 모델은 거기서 느리다(노트당 시간은 이 페이지를 위해 측정하지 않았다).

CLI는 시작할 때 세 import(llama_cpp, fitz, docx)를 다시 시험하고 하나라도 없으면 sys.exit(1)을 호출한다(CNE_CLI.py:101-117). 중복이지만 CLI가 위젯과 같은 인터프리터를 공유하므로 해롭지는 않다.

수정됨 (레거시 전용)

레거시(3c67957)의 다운로드 코드. VISOR에서는 클라이언트가 아무것도 내려받지 않는다. 모델은 서버에 호스팅되고, 데이터 매니페스트는 TMJ 번들만 스테이징한다(VISOR-serve scripts/data-manifest.yml:687-695. VISOR의 발견 사항 참고). 이 페이지는 여기에 확인된 버그를 기록하곤 했다. Ortho 모드가 저장소에 존재하지 않는 model-q4_0.gguf를 요청해서 다운로드가 HTTP 404를 돌려주고 "Download failed or was cancelled"로 실패했다. 이제 코드는 model-q4_k_m.gguf를 DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho에서(CNE.py:518-519)와 DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ의 TMJ 파일(CNE.py:525-526)을 요청한다. 2026-11-09에 두 URL에 HTTP HEAD 요청으로 확인했다. 각각 파일로 302를 응답하며, Ortho 파일은 4,920,738,880바이트이고, 따라서 다운로드 대화상자의 "approx. 4.9 GB"가 된다(CNE.py:521. TMJ 대화상자는 4.4 GB라고 하는데(CNE.py:528) 이는 측정하지 않았다).

두 Hugging Face 저장소에는 이제 모델 카드가 있으며, 이 페이지는 이전에 없다고 말했었다(ADT 저장소가 아니라 2026-11-09에 Hugging Face API로 읽음). 각 카드는 라이선스(Ortho는 Llama 3.1, TMJ는 Apache 2.0), 기반 모델, 방법(LoRA, r = 32, alpha = 64, 병합 후 Q4_K_M으로 양자화), 학습 노트가 공개되지 않은 주석 처리된 환자 데이터라는 점, 세트가 환자 단위로 분할되었다는 점을 밝힌다. Ortho 카드는 모델이 원본 노트를 시스템 프롬프트 없이 받는다고 하며 이는 코드와 일치하고(§6), 교정 특징(와이어 크기와 재질, 결찰, 엘라스틱, 수평 피개, 수직 피개 등)을 스키마로 나열한다. 어느 카드도 평가를 보고하지 않는다. TMJ 파일은 4,683,073,408바이트(HTTP HEAD, 2026-11-10)이며, 십진 단위로 4.7 GB, 이진 단위(GiB)로 4.4다. 따라서 카드와 TMJ 다운로드 대화상자(CNE.py:528)는 같은 파일을 두 가지 단위 관례로 설명한다. Ortho 대화상자(CNE.py:521)는 십진 단위를 쓴다.

5. 입력과 전처리

쉬운 설명과 수식: 아틀라스 페이지.

익명화도 PHI 필터링도 없다. 저장소의 테스트 노트는 손으로 가명 처리되어 있지만(B_001, [DOCTOR], Dr. XXX) 사용자 자신의 데이터에 대해서는 코드 어디에도 이를 보장하는 것이 없다. Medical_Data_Anonymizer_Module 모듈이 따로 존재하지만 CNE에 연결되어 있지 않다.

짚어 둘 점:

함정 (VISOR에서도 마찬가지)

VISOR에서도 마찬가지다(SADT-VISOR tools/CNE/src/sadt_cne/extraction.py:51: SYSTEM_PROMPTS = {"TMJ": INSTRUCTION_TMJ, "Ortho": None}. VISOR의 CNE 참고). Ortho 모드는 지시문을 보내지 않는다. 원본 노트만 사용자 메시지로 나가며, 작업을 담당하는 것은 Llama-Ortho 모델의 파인튜닝이어야 한다. 반면 TMJ 모드는 MedX에서 물려받은 지시문을 유지한다.

  • create_chat_completion은 GGUF에 내장된 채팅 템플릿을 적용한다. 두 모델 모두 Hugging Face에서 conversational로 태그되어 있으므로 템플릿은 실제로 존재한다. 다만 저장소에서는 볼 수도 제어할 수도 없다.
  • temperature=0.1이고 seed가 없다. 출력은 거의 결정적이지만 정확히 재현되지는 않는다.
함정 (VISOR에서는 부분적으로 마찬가지)

VISOR(SADT-VISOR tools/CNE/src/sadt_cne/): max_tokens의 기본값은 500이 아니라 2048이며(__init__.py:46-56), 한도에서 잘린 답은 그대로 쓰이는 대신 해당 노트의 실패가 된다(__init__.py:293-297). 여전히 맞는 점: 노트의 길이를 윈도와 대조하는 것이 없고, max_tokens를 윈도와 대조하는 것도 없다(extraction.py:146-153은 음수 윈도만 거부한다). 윈도를 가득 채우는 프롬프트는 llama.cpp 안에서 예외를 일으키고 노트마다 잡히며(__init__.py:200-212), 그래도 윈도에 들어가는 긴 노트는 답을 짧게 만들고 VISOR는 그것을 잘린 것으로 거부한다(VISOR의 CNE 참고). 길이 가드가 없다. n_ctx는 6144(TMJ) 또는 2048(Ortho)이고 호출은 max_tokens=500을 넘긴다. llama-cpp-python(0.3.36, llama.py:1343-1358)에서는 프롬프트만으로 n_ctx에 도달할 때만 오류가 발생한다. 그렇지 않으면 max_tokens가 n_ctx에서 프롬프트 길이를 뺀 값으로 줄어들고 답은 거기서 그냥 멈춘다. 따라서 긴 노트는 실패하지 않고 더 짧은 답을 받으며, JSON이 잘려서 json.loads가 실패하거나(CNE_CLI.py:214, 핸들러 :224-226) 닫는 중괄호를 찾지 못하고(:221-222) 원본 텍스트가 쓰인다. 윈도 전체를 채우는 프롬프트만 예외를 일으키며, 그 예외는 파일마다 잡혀 기록되고 파일은 failed_files에 추가된다. Ortho에서는 약 1,500 토큰 이상의 노트가 답을 500 토큰 미만으로 남긴다. 테스트 노트 TMJ_note1.txt는 4,731바이트이며 TMJ 모드에서는 통과한다.

  • 모델 로딩은 stderr를 /dev/null로 os.dup2를 통해 리디렉션하는 방식으로 감싸져 있으며(CNE_CLI.py:157-159), 그 대상은 Llama(...) 호출 주위이고 이후 복원한다(:169-171). 코드는 이유를 밝히지 않는다. 호출은 verbose=False도 넘긴다(:166). Llama(...)가 예외를 일으키면 복원 줄은 건너뛰어진다.

7. 응답 후처리

쉬운 설명과 수식: 아틀라스 페이지.

모델은 JSON으로 답하도록 기대되지만 코드는 이를 강제하지 않으며(response_format도, GBNF 문법도 없음) 텍스트에서 JSON을 그저 건져 낸다(CNE_CLI.py:209-214):

start_idx = ai_response.find('{')
end_idx   = ai_response.rfind('}') + 1
data = json.loads(ai_response[start_idx:end_idx])
if "extraction" in data:
    data = data["extraction"]
for key, value in data.items():
    formatted_response += f"{key} : {value}\n"

즉 첫 여는 중괄호부터 마지막 닫는 중괄호까지를 취하고, 있을 수 있는 extraction 수준을 풀어낸 뒤, key : value 줄로 평탄화한다. 파싱이 실패하면 또는 중괄호가 아예 없으면 모델의 원본 응답이 그대로 쓰인다. 출력 파일은 두 경우 중 어느 쪽이었는지 알려 주지 않는다.

함정 (VISOR에서는 부분적으로 수정됨)

VISOR: 중첩된 값은 더 이상 Python repr로 쓰이지 않는다(extraction.py:318-328). 첫 중괄호부터 마지막 중괄호까지 자르는 방식은 유지되지만(extraction.py:263-266), json.loads가 실패하면 답을 key: value 줄로 읽고, 그것도 실패하면 아무것도 쓰이지 않으며 원본 텍스트를 저장하는 대신 노트가 실패로 보고된다(extraction.py:278-301, __init__.py:299-305. VISOR의 CNE 참고). 결과: 단순한 find('{')…rfind('}') 자르기는 응답에 JSON 객체가 둘 이상 들어 있는 즉시 깨지고, 중첩된 값(리스트, 딕셔너리)은 텍스트 파일에 Python repr로 렌더링된다.

8. 출력

쉬운 설명과 수식: 아틀라스 페이지.

입력 노트마다 출력 폴더에 텍스트 파일 하나:

Extraction_<note name without extension>.txt

내용: key : value 줄, 또는 파싱이 실패했다면 모델의 원본 응답. CSV도, json도, 추출 자체에서 나오는 환자별 집계도 없다. 표와 그림은 Dashboard 버튼(§8.1)에서 나오며, 이 버튼이 나중에 이 파일들을 읽는다.

출력 폴더는 위젯 쪽에서 os.makedirs(..., exist_ok=True)로 만들어진다(CNE.py:613).

8.1 Dashboard

쉬운 설명과 수식: 아틀라스 페이지.

MedX의 "Dashboard" 절반은 2026-10-12에 포팅되었으므로, 이 페이지가 앞서 "이월되지 않았다"고 한 말은 더 이상 맞지 않는다. 코드에서 읽으면 다음과 같다.

  • 트리거. Dashboard 버튼(dashboardButton, CNE.ui 안에 있으며 CNE.py:234에서 연결)이 onDashboardButton()(CNE.py:365)을 실행한다. 이것은 의존성을 확인하고, 출력 폴더가 없으면 실행을 거부하며, 출력 폴더를 입력과 출력 모두로 삼는 CNE_Dashboard를 CNELogic.dashboard()(CNE.py:629)로 시작한다. 모델도 다운로드도 관여하지 않는다.
  • 읽기. read_summaries()(display_figure.py:23)는 폴더에서 Extraction_*.txt 파일만 남기며, 환자 식별자는 노트 이름에서 접두사를 뺀 것이다. process_summaries()(display_figure.py:135)는 initialize_key_value_summary()(dashboard_utils.py:332)가 채워 둔 56개 키(환자 id와 모델이 돌려줄 것으로 기대되는 55개 필드)의 딕셔너리를 채우고 숫자 필드 여섯 개를 변환한다.
  • 예측이 아니라 계산. 각 패널은 dashboard_utils.py에서 계산되는 결정적 집계다(연령군, 통증 점수의 평균과 SD, "33 mm" 같은 문자열에서 파싱한 최대 개구량, 동의어 목록으로 구한 두통과 관절통 위치, 좌우 디스크 변위, 근육 통증 수준). 그림은 generate_dashboard_figure()(display_figure.py:164)가 그린다.
  • 출력. dashboard.png와 patient_data.csv(display_figure.py:714-716), 그리고 그림이 그려지기 전에 쓰이는 세 번째 파일 dashboard_full_dataframe.csv(display_figure.py:183).
  • 스키마가 맞지 않으면 시끄럽게 실패한다. report_field_coverage()(display_figure.py:668)는 값이 없는 기대 키를 기록하고, show_dashboard()(display_figure.py:694)는 값이 있는 키가 하나도 없거나 폴더에 Extraction_*.txt가 없으면 예외를 일으킨다.
함정 (레거시 전용)

레거시(3c67957). VISOR에는 Dashboard가 없다(§1의 첫 번째 콜아웃과 VISOR의 CNE 참고). 이 Dashboard는 TMJ 대시보드다. 기대되는 키는 두통 강도, 턱 클릭, 디스크 변위, 최대 개구, 수면 장애 등이다(dashboard_utils.py:339-396). 이것은 TMJ 모델이 돌려줄 것으로 기대되는 키이며, Ortho 모델이 이를 쓴다고 저장소 어디에도 나와 있지 않고, Ortho 모드에는 이를 부과할 지시문도 없다. Ortho 추출 결과에서는 커버리지 검사가 "키가 일치하지 않음" 오류로 실행을 멈출 가능성이 크다. 이는 키 목록에서 도출한 추론이지 Ortho 출력에 실제로 돌려 본 것이 아니다. 키 자체는 코드가 아니라 모델이 정한다(report_field_coverage의 docstring, display_figure.py:668-679).

11. 함정과 취약한 지점

쉬운 설명과 수식: 아틀라스 페이지.

  • Dashboard는 TMJ 스키마를 기대한다(§8.1).
  • 테스트 파일의 출력 폴더. copyTestFiles()(CNE.py:454)는 존재하지 않는 경로를 출력 필드에 넣곤 했다. 이제는 출력 폴더를 만들고(CNE.py:508), 폴더를 지우지 않은 채 호출할 때마다 노트를 다시 복사하며(dirs_exist_ok=True, CNE.py:505), 사용자가 이미 고른 출력 폴더는 건드리지 않는다(CNE.py:328-330). Resources/testfiles/에는 여전히 input_ 폴더 두 개만 있다.
  • 입력 폴더의 비재귀적 스캔(§5).
  • 호출 전에 길이 검사가 없다. 긴 노트는 청크로 나뉘지 않는다. 답은 윈도가 남겨 준 만큼으로 짧아지고(잘린 JSON, 원본 텍스트가 쓰임), 윈도를 채우는 노트는 실패한다. 반면 MedX는 청크 분할을 했다(§6). 이것은 대체품의 기능적 퇴보다.
  • Ortho 모드는 시스템 지시문을 보내지 않는다(§6). 모델이 기대한 것이 아니라면 출력이 JSON이어야 할 이유가 전혀 없다.
  • 출력 형식에 제약이 없다. llama.cpp가 둘 다 제공하는데도 GBNF 문법도 response_format도 없다. 따라서 후처리는 휴리스틱으로 건져 내는 작업이다(§7).
  • 라디오 버튼이 TMJ도 Ortho도 아니게 설정됨 → notesType = ""(CNE.py:427) → getModelPath에서 repo_id가 할당되지 않고 UnboundLocalError가 "Failed to load model"로 나타난다. 이 경우는 일어나지 않아야 하지만(setExclusive(True)와 TMJ 기본값) 이를 막는 것은 없다.
  • 일관되지 않은 대소문자: notesType == "TMJ"는 n_ctx를 정하고, notesType.upper() == "TMJ"는 지시문을 정한다. 소문자 notesType은 TMJ 지시문과 2048 컨텍스트를 함께 낳는다.
  • 출처 추적 기록이 없다: Extraction_*.txt 파일에는 모델도, 그 버전도, 날짜도 적혀 있지 않다. 서로 다른 모델로 두 번 실행해도 구별할 수 없는 파일이 나온다.
  • PHI: 익명화하는 것도, 경고하는 것도 없다. 노트는 평문으로 읽히고 로컬 모델을 거친다(따라서 네트워크 유출이 없다. 이것이 유일한 안전장치이고, 의도된 것이 아니라 구조적인 것이다). 레거시 모듈에만 해당(3c67957). VISOR에서는 노트가 있는 그대로 서버에 업로드되고 그 전에 비식별화하는 것은 없다. VISOR의 발견 사항 참고.
  • 템플릿 기본값으로 남은 CLI 메타데이터: CNE_CLI.xml은 여전히 "Apply a Gaussian blur to an image"를 설명하고, 모듈을 "Andras Lasso (PerkLab)"의 것으로 돌리며, <index> 값은 0, 2, 3, 4로 index 1이 빠져 있다.
  • onCliProgress(CNE.py:651)는 caller.GetProgress()를 읽고는 아무것도 하지 않으며, 어떤 옵저버에도 연결되어 있지 않다. 죽은 코드다. 실제 진행률은 CLI의 <filter-progress> 태그를 통해 전달되며 qSlicerCLIProgressBar가 읽는다.

12. 참고 문헌

쉬운 설명과 수식: 아틀라스 페이지.

저장소는 CNE에 대해 어떤 출판물도 인용하지 않으며, 두 DCBIA-OrthoLab/* Hugging Face 모델 카드도 논문을 인용하지 않는다(코드 저장소 ortho-cde-llm-extraction을 가리키는데, 읽지는 않았다). 주석 처리된 코퍼스는 공개되지 않았고 평가도 보고되지 않았다. 둘 다 저장소만으로는 확인할 수 없다.

확인할 수 있는 것:

  • MedX → CNE 계보는 CNE_Dashboard.xml의 감사 문구("Ported from MedX_Dashboard, which CNE replaced without taking this half with it")와 display_figure.py:35 및 :675의 주석으로만 기록되어 있다. 루트 CMakeLists.txt는 더 이상 MedX를 언급하지 않으며 README에는 MedX나 CNE 절이 없다.
  • 기반 모델: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • 파인튜닝된 저장소: DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho.
  • 엔진: llama-cpp-python, llama.cpp(GGUF 형식, Q4_K_M 양자화).
  • SlicerAutomatedDentalTools

CNE를 LLM 기반 임상 정보 추출에 관한 일반 문헌과 연결 짓지 말 것. 여기서 쓰는 모델이 출판된 연구에서 나왔음을 시사하는 것은 저장소에 없다.

이 결론에 이르기 위해 무엇을 찾아보았는지, 그리고 그 과정에서 모은 인접 문헌: SOURCES.md.
