CNE

자유 서술형 임상 노트를 읽어 키–값 쌍을 추출하는 언어 모델(LLM) 추론 모듈이다. 치과 도구 모음에 속해 있지만 기하 도구도, 영상 처리 도구도 아니다.

미발표 CNE_CLI conda 없음 — Slicer의 Python 참고문헌

범위 주의. AutoCrop3D나 AutoMatrix와 달리 CNE는 기하 유틸리티가 아니다. 볼륨도, 메시도, 좌표도 다루지 않는다. 자유 서술형 임상 노트를 읽고 키–값 쌍을 쓰는 LLM 추론 모듈이다. 모듈의 핵심에는 양자화된 GGUF 모델이 있으며, Slicer의 Python 안에서 llama-cpp-python이 이를 로드한다.

0. 약어

저장소의 어떤 문서도 이 약어를 풀어 쓰지 않는다. README에는 CNE 절이 없다(CNE가 대체한 MedX는 여전히 문서화되어 있다, 참조: CMakeLists.txt:42 "Replaced by CNE"). 모듈 도움말 (CNE.py:147)은 "This tool helps to create summaries of clinical notes"라고만 적는다.

풀이를 제공하는 것은 로그 두 줄뿐이다: logger.info("CNE (Clinical Notes Extraction)") (CNE.py:329와 CNE.py:606). 그리고 CLI가 같은 이름을 Slicer 관리자에 게시한다: <filter-name>Clinical Notes Extraction</filter-name> (CNE_CLI.py:91). CNE = Clinical Notes Extraction이며, 코드 외에는 이를 뒷받침하는 것이 없다.

1. 파이프라인에서의 위치

종단 모듈이다. 이 모듈을 호출하는 것도 없고, 이 모듈이 저장소의 다른 모듈을 호출하지도 않는다. CMakeLists.txt:51에 선언되어 있다.

MedX의 "Summarization" 부분을 대체한다. MedX/와 MedX_CLI/는 트리에 남아 있지만 빌드에서 비활성화되어 있다 (CMakeLists.txt:42-44). MedX의 "Dashboard" 부분 (dashboard.png + patient_data.csv)은 CNE에 대응하는 기능이 없으며, 따라서 컴파일된 확장에서 사라진다.

3. 필요 시 설치되는 의존성

check_dependencies() (CNE.py:83)는 모듈 로드 시가 아니라 Apply 클릭 시 호출된다. 세 가지 import를 검사하고, 빠진 것이 있으면 slicer.util.pip_install 전에 확인을 요청한다:

검사하는 import설치되는 패키지용도
llama_cppllama-cpp-python --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cpu추론
fitzpymupdfPDF 텍스트 추출
docxpython-docxWord 텍스트 추출

알아 둘 점 두 가지:

함정

install_function (CNE.py:44)은 설치 중에 CC=gcc와 CXX=g++를 강제한 뒤 원래 값을 복원한다. pip가 llama-cpp-python을 소스에서 컴파일해야 하는 경우를 위한 것이다. Windows에서는 이 값들을 쓸 수 없다.

함정

추가 인덱스는 명시적으로 CPU 휠을 가리킨다. 그런데 CLI는 "Use GPU if available"이라는 주석과 함께 n_gpu_layers=-1을 요청한다 (CNE_CLI.py:162). CPU 전용 빌드에서는 이 매개변수가 아무 효과가 없다. 실제로 추론은 CPU에서 실행되며, 7–8 B 규모의 Q4 양자화 모델은 노트당 수십 초가 걸린다.

CLI는 시작 시 세 import를 다시 검사하고 하나라도 없으면 sys.exit(1)을 호출한다 (CNE_CLI.py:99-115). 중복이지만, CLI가 위젯과 인터프리터를 공유하므로 해는 없다.

4. 모델

저장소에는 가중치가 포함되어 있지 않다. getModelPath() (CNE.py:478)가 필요할 때 GGUF를 다운로드한다. urllib.request.urlretrieve를 사용하고 QProgressDialog로 진행 상황을 표시하며, 저장 위치는 <Documents>/SlicerDownloads/CNE/model/이다.

확인된 버그

Ortho 다운로드가 깨져 있다. Hugging Face API로 확인함: 저장소 dcbia/Meta-Llama-3.1-8B-Instruct-Ortho에는 .gitattributes와 model-q4_k_m.gguf만 있다. 코드가 요청하는 model-q4_0.gguf 파일은 존재하지 않는다. 해당 URL은 HTTP 404를 반환하고, q4_k_m URL은 200을 반환한다. urlretrieve가 예외를 일으키고, 부분 파일은 삭제되며, 사용자에게는 "Download failed or was cancelled"가 표시된다. 반면 TMJ 모드는 정상이다(qwen-ft-q4_k_m.gguf → 200). 수정: model-q4_0.gguf → model-q4_k_m.gguf.

두 Hugging Face 저장소 모두 모델 카드가 없다. 라이선스도, 학습 데이터셋도, 공개된 미세조정 방법도 없다. 기반 아키텍처는 태그로 식별할 수 있으며(Llama-3.1-8B-Instruct와 Qwen2 7B), 두 경우 모두 양자화는 Q4_K_M이다. 두 미세조정 모델을 구분하는 요소, 즉 주석 말뭉치, 학습된 출력 스키마, 프로토콜은 저장소로도 Hugging Face로도 확인할 수 없다.

5. 입력과 전처리

SUPPORTED_EXTENSIONS = (".txt", ".pdf", ".docx"). 탐색은 비재귀적이다: glob.glob(os.path.join(notesFolder_input, f"*{ext}")) (CNE_CLI.py:133). 저장소의 다른 모든 모듈이 iglob(**, recursive=True)를 쓰는 것과 다르다. 환자별 하위 폴더로 구성된 폴더에서는 아무것도 나오지 않는다.

텍스트 추출(CNE_CLI.py:73):

형식추출기세부
.pdffitz.open 후 "\n".join(page.get_text() for page in doc)OCR 없음: 스캔한 PDF는 빈 텍스트가 된다
.docxdocx.Document, paragraph.text표가 사라진다(doc.paragraphs는 표를 순회하지 않는다)

clean_text() (CNE_CLI.py:40)가 유일한 전처리 단계이며, 그 목적이 코드에 적혀 있다. PDF/Word 내보내기마다 달라지지만 평문 학습 노트에는 나타나지 않았던 요소를 정규화하는 것이다. 둥근 아포스트로피와 따옴표는 ASCII로, en 대시와 em 대시는 -로, 줄바꿈 없는 공백은 일반 공백으로 바꾸고, 연속된 빈 줄을 하나로 합친다. 명시된 목표: 원본 형식과 관계없이 모델이 같은 텍스트를 보게 하는 것.

익명화도, PHI 필터링도 없다. 저장소의 테스트 노트는 수작업으로 가명 처리되어 있지만(B_001, [DOCTOR], Dr. XXX) 사용자 자신의 데이터에 대해 이를 보장하는 코드는 없다. Medical_Data_Anonymizer_Module 모듈은 별도로 존재하며 CNE와 연결되어 있지 않다.

6. 추론

파일당 한 번의 패스, 분할 없음 (CNE_CLI.py:192):

messages = []
if notesType.upper() == "TMJ":
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": clinical_text})

output = llm.create_chat_completion(messages=messages, max_tokens=500, temperature=0.1)

주목할 점:

함정

Ortho 모드는 지시문을 보내지 않는다. 원본 노트만 사용자 메시지로 전달되며, 작업 수행은 Llama-Ortho 모델의 미세조정에 맡겨져 있다고 가정한다. 반면 TMJ 모드는 MedX에서 물려받은 지시문을 유지한다.

  • create_chat_completion은 GGUF에 내장된 chat template을 적용한다. 두 모델 모두 Hugging Face에서 conversational 태그가 붙어 있으므로 템플릿은 존재한다. 다만 저장소에서는 보이지도, 제어되지도 않는다.
  • temperature=0.1이고 seed가 없다: 출력은 거의 결정론적이지만 정확히 재현되지는 않는다.
함정

길이에 대한 보호 장치가 없다. n_ctx는 6144(TMJ) 또는 2048(Ortho)이고, max_tokens=500이 이 예산에서 차감된다. 예산을 넘는 노트는 llama.cpp가 예외를 일으키게 한다. 예외는 파일 단위로 잡혀 로그에 기록되고, 해당 파일은 failed_files에 추가된다. Ortho 예산은 특히 빠듯하다: 노트에 쓸 수 있는 분량이 약 1,500 토큰이다. 테스트 노트 TMJ_note1.txt는 약 4,400자로, TMJ 모드에서는 통과한다.

  • 모델 로드는 stderr를 /dev/null로 돌려서 감싼다(os.dup2 사용, CNE_CLI.py:155). llama.cpp의 잡다한 출력을 숨기기 위한 것으로, 그렇지 않으면 Slicer가 CLI 실패로 해석하는 오류 채널이 오염된다.

7. 응답 후처리

모델은 JSON으로 답할 것으로 기대되지만 코드는 이를 강제하지 않는다( response_format도, GBNF 문법도 없음). 텍스트에서 JSON을 건져낼 뿐이다(CNE_CLI.py:207):

start_idx = ai_response.find('{')
end_idx   = ai_response.rfind('}') + 1
data = json.loads(ai_response[start_idx:end_idx])
if "extraction" in data:
    data = data["extraction"]
for key, value in data.items():
    formatted_response += f"{key} : {value}\n"

즉, 첫 번째 여는 중괄호부터 마지막 닫는 중괄호까지 잘라 내고, 있을 수 있는 extraction 단계를 벗겨 낸 뒤, key : value 줄로 평탄화한다. 파싱이 실패하거나 또는 중괄호가 아예 없으면 모델의 원시 응답이 그대로 기록된다. 출력 파일은 둘 중 어떤 경우였는지 알려 주지 않는다.

함정

결과: 단순한 find('{')…rfind('}') 슬라이싱은 응답에 JSON 객체가 둘 이상 있으면 바로 깨지며, 중첩된 값(리스트, dict)은 텍스트 파일에 Python repr로 기록된다.

8. 출력

입력 노트마다 출력 폴더에 텍스트 파일 하나:

Extraction_<note name without extension>.txt

내용: key : value 줄, 또는 파싱이 실패한 경우 모델의 원시 응답. CSV도, json도, 환자별 집계도 없다. MedX의 대시보드는 이어지지 않았다.

출력 폴더는 위젯 쪽에서 os.makedirs(..., exist_ok=True)로 생성된다(CNE.py:578).

11. 함정과 취약 지점

  • Ortho 모델이 다운로드되지 않는다: 잘못된 파일명, HTTP 404(§4). 수정: model-q4_0.gguf → model-q4_k_m.gguf.
  • 테스트 파일의 출력 폴더가 존재하지 않는다. copyTestFiles() (CNE.py:409)는 input_<type> 과 output_<type>을 복사하지만, Resources/testfiles/에는 input_ 폴더 두 개만 있다. 출력 폴더의 shutil.copytree는 경고와 함께 건너뛰어지고, UI에는 아직 존재하지 않는 출력 경로가 채워진 채로 남는다.
  • 입력 폴더의 비재귀적 탐색(§5).
  • 호출 전 길이 제한 없음: 너무 긴 노트는 분할되지 않고 실패한다. MedX는 분할을 했다(§6). 대체 과정에서 생긴 기능 퇴행이다.
  • Ortho 모드는 시스템 지시문을 보내지 않는다(§6): 모델이 기대한 모델이 아니라면 출력이 JSON일 이유가 전혀 없다.
  • 출력 형식에 대한 제약 없음: llama.cpp가 GBNF 문법과 response_format을 모두 제공하는데도 둘 다 쓰지 않는다. 따라서 후처리는 휴리스틱한 건져내기 작업이다(§7).
  • 라디오 버튼이 TMJ도 Ortho도 아닌 상태 → notesType = "" (CNE.py:382) → getModelPath에서 repo_id가 할당되지 않고, UnboundLocalError가 "Failed to load model"로 나타난다. 이 경우는 일어나지 않아야 하지만(setExclusive(True), 기본값 TMJ), 이를 막는 장치는 없다.
  • 대소문자 처리 불일치: notesType == "TMJ"가 n_ctx를 정하고, notesType.upper() == "TMJ"가 지시문을 정한다. 소문자 notesType이면 TMJ 지시문에 2048 컨텍스트가 조합된다.
  • 출처 기록 없음: Extraction_*.txt 파일에는 모델도, 버전도, 날짜도 적히지 않는다. 서로 다른 모델로 두 번 실행하면 구별할 수 없는 파일이 나온다.
  • PHI: 익명화도, 경고도 없다. 노트는 평문으로 읽혀 로컬 모델을 거친다(따라서 네트워크 유출은 없다. 이것이 유일한 안전장치이며, 의도된 것이라기보다 구조상 그렇게 된 것이다).
  • CLI 메타데이터가 템플릿 기본값 그대로: CNE_CLI.xml은 여전히 "Apply a Gaussian blur to an image"라고 기술하고, 모듈 작성자를 "Andras Lasso (PerkLab)"로 표기하며, <index> 값이 0, 2, 3, 4로 인덱스 1이 빠져 있다.
  • onCliProgress (CNE.py:594)는 caller.GetProgress()를 읽고 아무것도 하지 않는다. 어떤 옵저버에도 연결되어 있지 않다. 사용되지 않는 코드다. 실제 진행 상황은 CLI의 <filter-progress> 태그를 통해 전달되며, qSlicerCLIProgressBar가 이를 읽는다.

12. 문헌

저장소는 CNE에 대해 어떤 출판물도 인용하지 않으며, 두 dcbia/* Hugging Face 저장소는 모델 카드도 참고문헌도 없이 공개되어 있다. 미세조정 프로토콜, TMJ/Ortho 주석 말뭉치, 평가는 저장소로부터 확인할 수 없다.

확인 가능한 것:

  • MedX → CNE 계보. 이를 기록한 것은 CMakeLists.txt:42와 README.md:425의 MedX 절뿐이며, 이 절은 여전히 옛 BART 파이프라인과 사라진 대시보드를 기술한다.
  • 기반 모델: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • 미세조정 저장소: dcbia/Qwen-2.5-7B-Instruct-TMJ, dcbia/Meta-Llama-3.1-8B-Instruct-Ortho.
  • 엔진: llama-cpp-python, llama.cpp(GGUF 형식, Q4_K_M 양자화).
  • SlicerAutomatedDentalTools

CNE를 LLM 기반 임상 정보 추출에 관한 일반 문헌과 연결하지 말 것. 저장소 어디에도 여기서 쓰는 모델이 발표된 연구에서 나왔다는 표시가 없다.

이 결론에 이르기 위해 무엇을 검색했는지, 그리고 그 과정에서 모은 주변 연구: SOURCES.md.
