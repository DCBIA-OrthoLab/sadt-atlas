CNE

CNE는 자유 형식의 임상 노트를 읽고, 그 안에서 찾은 사실(증상, 진단, 점수)을 필드 : 값 줄의 목록으로 쓴다. 언어 모델 모듈이며 이미지도 메시도 건드리지 않는다. 이 페이지는 레거시 Slicer 모듈의 파이프라인을 단계별로 설명하며, 코드 세부 사항은 코드 페이지에 있다.

미발표 VISOR CNE_CLI conda 없음: Slicer의 Python 참고문헌 코드 (개발자용) 가이드

CNE는 기하 도구가 아니다. 텍스트를 읽고 텍스트를 쓴다. 양자화된 언어 모델(GGUF 형식)을 llama-cpp-python이 Slicer 자체의 Python 안에서 불러온다. 이 페이지는 레거시 Slicer 모듈(3c67957 시점의 SlicerAutomatedDentalTools, 2026-10-26)을 설명한다. VISOR 포팅은 같은 도구를 서버에서 실행하며 별도 페이지가 있다. 읽기 전에 알아 둘 결과가 하나 있다. 이 페이지가 모델이 로컬에서 실행된다고 말하는 곳은 레거시 모듈에만 해당한다. VISOR에서는 노트 텍스트가 서버로 전송된다(VISOR의 알려진 문제).

개요: 무엇이 들어가고 무엇이 나오는가

CNE, 레거시
입력노트가 든 폴더(.txt, .pdf, .docx), 재귀적으로 검색하지 않음, 그리고 TMJ와 Ortho 중 선택
모델양자화된 Qwen 2.5 7B(TMJ) 또는 Llama 3.1 8B(Ortho), 처음 사용할 때 내려받아 프로세서에서 실행
출력노트마다 텍스트 파일 하나, 필드 : 값 줄, 출력 폴더에
선택 사항그 파일들을 읽어 그림 하나와 CSV 표 두 개를 그리는 Dashboard 버튼

0. 약어

CNE는 Clinical Notes Extraction의 약자다. 저장소는 문서에서 이를 밝히지 않는다. 로그 두 줄과 도구가 Slicer에 알리는 이름만이 풀이를 준다.

코드에서풀이를 증명하는 로그 줄과 필터 이름

1. 파이프라인에서의 위치

CNE는 말단 모듈이다. 어떤 것도 CNE를 호출하지 않고 CNE도 아무것도 호출하지 않는다. 이것은 MedX의 요약 절반을 대체하며, 그 절반은 2026년 3월에 “Replaced by CNE”라는 주석과 함께 빌드에서 비활성화되었다. MedX 자체는 2026-09-17에 트리에서 빠졌고 archive/medx 브랜치에 남아 있다. Dashboard 절반은 2026-10-12에 CNE로 포팅되었다(8.1절). VISOR에는 Dashboard가 없다.

대체한 MedX 요약기와 비교하면:

  • 엔진과 모델: PyTorch와 BART 모델 대신 llama.cpp와 양자화된 Llama 또는 Qwen.
  • 청크 분할 없음: MedX는 노트를 조각으로 잘랐지만, 노트 전체가 하나의 메시지로 모델에 간다.
  • 디코딩: 샘플링을 곁들인 빔 서치 대신 temperature 0.1과 최대 500 토큰.
  • 환자별 집계 없음: 파일 하나가 출력 하나를 낳는다.

TMJ 모드의 지시 문장 하나는 MedX가 쓰던 문장과 같다(MedX는 이것을 텍스트 앞에 놓았고, CNE는 별도의 시스템 메시지로 보낸다).

코드에서어떤 빌드 파일이 이를 선언하는지, 수정된 조사, MedX 비교표 전체

2. 관련 파일

네 부분이다. 위젯(의존성, 모델 다운로드, 작업 시작, Dashboard 버튼), 노트를 읽고 모델을 호출하는 명령줄 작업, 두 보조 파일을 가진 Dashboard 작업, 그리고 인터페이스 파일. 저장소에는 샘플 노트 네 개가 들어 있다. conda 환경은 없으며 모든 것이 Slicer의 Python에서 실행된다.

코드에서역할과 각각이 실행되는 위치가 있는 파일 표

3. 필요할 때 설치되는 의존성

Apply를 클릭하면 모듈은 패키지 다섯 개(llama.cpp 바인딩, PDF 리더, Word 리더, 플로팅 라이브러리, 표 라이브러리)를 확인하고, 확인을 받은 뒤 없는 것을 Slicer의 Python에 설치한다. 가리키는 휠 인덱스는 프로세서 전용 빌드다. 작업은 그래도 GPU 레이어를 요청하는데, 그 빌드에서는 효과가 없다. 실제로는 추론이 프로세서에서 실행되며, 70억~80억 파라미터 모델은 거기서 느리다(노트당 시간은 이 페이지를 위해 측정하지 않았다).

코드에서다섯 개의 import, 설치 플래그, 컴파일러 재정의, GPU 요청

4. 모델

저장소에는 가중치가 들어 있지 않다. 처음 실행하면 선택한 모드의 모델을 Documents 폴더로 내려받는다.

모드모델다운로드컨텍스트 윈도
TMJQwen 2.5 7B Instruct, 파인튜닝됨 (DCBIA-OrthoLab)약 4.4 GB6144 토큰
OrthoLlama 3.1 8B Instruct, 파인튜닝됨 (DCBIA-OrthoLab)약 4.9 GB2048 토큰

Ortho 다운로드는 존재하지 않는 파일을 요청해서 실패하곤 했으며, 이는 수정되었다(세부 사항). 두 Hugging Face 저장소는 이제 라이선스, 기반 모델, 파인튜닝 방법을 밝히고 학습 노트가 공개되지 않은 환자 데이터라고 말하는 모델 카드를 갖추고 있다. 어느 카드도 평가를 보고하지 않는다.

코드에서저장소 id, 파일 이름, URL, 그리고 이에 대해 수행한 검사

5. 입력과 전처리

모듈은 선택한 폴더에서만 .txt, .pdf, .docx 파일을 찾는다. 하위 폴더는 검색하지 않으며 다른 모든 모듈과 다르므로, 환자별로 정리된 폴더에서는 아무것도 나오지 않는다. 텍스트는 PDF에서는 OCR 없이 페이지 단위로(스캔된 PDF는 비어 있다), Word 파일에서는 문단 단위로(표는 사라진다), 텍스트 파일에서는 UTF-8로(다른 인코딩이면 그 노트가 실패한다) 추출된다.

노트를 익명화하는 것은 없다. 저장소의 테스트 노트는 손으로 가명 처리되었으며, 별도의 MedicalDataAnonymizer 모듈은 CNE에 연결되어 있지 않다.

코드에서세 추출기, 치환 표, glob 호출

6. 추론

모델은 노트마다 한 번, 청크 분할 없이 호출된다. TMJ 모드에서는 노트 앞에 지시 문장이 붙고, Ortho 모드에서는 노트만 간다. Ortho 모델이 파인튜닝으로 작업을 담당하게 되어 있기 때문이다.

답은 500 토큰으로 제한되고 temperature는 0.1이며 seed가 없으므로, 출력은 거의 결정적이지만 정확히 재현되지는 않는다. 500 토큰 미만의 공간만 남기는 노트는 오류를 일으키지 않는다. 엔진이 답을 남은 만큼으로 줄이므로 JSON이 잘리고 원본 텍스트가 쓰인다(§7). 윈도 전체를 채우는 프롬프트만 엔진이 예외를 일으키게 하며, 그 오류는 해당 노트에 대해 잡혀 기록되고 파일은 실패로 센다. 모델 자체의 채팅 템플릿이 적용되며, 저장소에서 볼 수도 바꿀 수도 없다.

코드에서호출, TMJ와 Ortho 메시지, stderr 리디렉션

7. 응답 후처리

모델이 JSON을 내도록 강제하는 것이 없으므로, 모듈은 답에서 JSON을 건져 낸다.

조각에 extraction이라는 래퍼가 들어 있으면 그 수준은 제거되고, 각 필드는 필드 : 값 줄로 쓰이며, 중첩된 값은 Python 표현 그대로 나타난다. 조각을 읽을 수 없거나 답에 중괄호가 전혀 없으면 모델의 원본 답이 그대로 쓰이며, 파일은 둘 중 어느 경우였는지 알려 주지 않는다.

코드에서자르기 코드와 부분적으로 수정된 VISOR의 동작

8. 출력

노트마다 텍스트 파일 하나, Extraction_<note name>.txt에 필드 : 값 줄 또는 원본 답이 들어 있다. CSV도, JSON도, 추출 자체에서 나오는 환자별 집계도 없다.

코드에서파일 이름 규칙, 출력 폴더 생성

8.1 Dashboard

Run 옆의 버튼이 출력 폴더의 Extraction_*.txt 파일을 읽는 두 번째 작업을 시작한다. 이 작업은 56개 키(환자 id와 모델이 돌려줄 것으로 기대되는 55개 필드)의 표를 채우고, 그중 여섯 개를 숫자로 변환하며, 그림의 패널마다 결정적 요약 하나를 계산한다. 연령군, 통증 점수의 평균과 퍼짐, 최대 개구량, 두통과 관절통의 위치, 디스크 변위, 근육 통증이다. dashboard.png와 CSV 표 두 개를 쓰며, 파일이 기대되는 필드를 담고 있지 않으면 오류로 멈춘다. 모델도 다운로드도 관여하지 않는다.

이것은 TMJ 대시보드다. 기대되는 필드는 TMJ 모델이 돌려줄 것으로 기대되는 것들이다. Ortho 모델이 이를 쓴다고 나와 있는 것은 없으므로, Ortho 추출 결과에서는 커버리지 검사가 실행을 멈출 가능성이 크다(필드 목록에서 도출한 추론이며 실행해 보지 않았다).

코드에서트리거, 리더, 집계 함수, 커버리지 검사

단계성격

코드에서같은 표에 각 블록이 어디서 실행되는지를 더한 것

10. 환경

Slicer의 Python만 쓰며, 패키지 다섯 개가 즉석에서 설치된다. 70억~80억 파라미터의 양자화된 모델은 Slicer 위에 대략 5~6 GB의 메모리가 필요하다. 가중치는 디스크에서 약 4.4 GB(TMJ) 또는 4.9 GB(Ortho)를 차지한다.

코드에서인터프리터, 패키지, GPU, 가중치 위치

11. 알려진 문제

  • Dashboard는 TMJ 필드를 기대하며 Ortho 추출 결과에서는 아마 멈출 것이다(세부 사항).
  • Ortho 모드는 지시문을 보내지 않으므로, 모델이 기대한 것이 아니면 출력이 JSON이 되도록 만드는 것이 없다(세부 사항).
  • 길이 가드가 없다. 윈도보다 긴 노트는 청크로 나뉘지 않고 실패하며, MedX에서의 퇴보다(세부 사항).
  • 답 형식에 제약이 없고, 첫 중괄호부터 마지막 중괄호까지 자르는 방식은 객체가 둘이면 깨진다(세부 사항).
  • 입력 폴더 스캔이 재귀적이지 않다(모든 함정).
  • 출력 파일에 모델도 날짜도 기록되지 않으므로, 서로 다른 모델로 한 두 번의 실행을 구별할 수 없다(모든 함정).
  • 노트를 익명화하는 것은 없다. 유일한 안전장치는 모델이 로컬에서 실행된다는 점인데, 이는 이 레거시 모듈에만 해당한다(모든 함정).
  • 프로세서 전용 빌드 때문에 GPU 요청이 무의미하다(세부 사항).
코드에서템플릿 기본값으로 남은 CLI 메타데이터를 포함한 함정 전체 목록

12. 참고 문헌

저장소는 CNE에 대해 어떤 출판물도 인용하지 않으며, 두 DCBIA-OrthoLab/* Hugging Face 모델 카드도 논문을 인용하지 않는다(코드 저장소 ortho-cde-llm-extraction을 가리키는데, 읽지는 않았다). 주석 처리된 코퍼스는 공개되지 않았고 평가도 보고되지 않았다. 둘 다 저장소만으로는 확인할 수 없다.

확인할 수 있는 것:

  • MedX → CNE 계보는 CNE_Dashboard.xml의 감사 문구("Ported from MedX_Dashboard, which CNE replaced without taking this half with it")와 Dashboard 코드의 주석으로만 기록되어 있다(코드 페이지 참고). 루트 CMakeLists.txt는 더 이상 MedX를 언급하지 않으며 README에는 MedX나 CNE 절이 없다.
  • 기반 모델: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • 파인튜닝된 저장소: DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho.
  • 엔진: llama-cpp-python, llama.cpp(GGUF 형식, Q4_K_M 양자화).
  • SlicerAutomatedDentalTools

CNE를 LLM 기반 임상 정보 추출에 관한 일반 문헌과 연결 짓지 말 것. 여기서 쓰는 모델이 출판된 연구에서 나왔음을 시사하는 것은 저장소에 없다.
