CNE

자유 서술형 임상 노트를 읽어 키–값 쌍을 추출하는 언어 모델(LLM) 추론 모듈이다. 치과 도구 모음에 속해 있지만 기하 도구도, 영상 처리 도구도 아니다.

미발표 CNE_CLI conda 없음: Slicer의 Python 참고문헌

범위 주의. AutoCrop3D나 AutoMatrix와 달리 CNE는 기하 유틸리티가 아니다. 볼륨도, 메시도, 좌표도 다루지 않는다. 자유 서술형 임상 노트를 읽고 키–값 쌍을 쓰는 LLM 추론 모듈이다. 모듈의 핵심에는 양자화된 GGUF 모델이 있으며, Slicer의 Python 안에서 llama-cpp-python이 이를 로드한다.

0. 약어

저장소의 어떤 문서도 이 약어를 풀어 쓰지 않는다. README에는 CNE 절이 없고, CNE가 대체한 MedX도 더 이상 문서화되어 있지 않다: 두 이름 모두 거기에 나오지 않는다. 모듈 도움말 (CNE.py:157)은 "This tool helps to create summaries of clinical notes"라고만 적는다.

풀이를 제공하는 것은 로그 두 줄뿐이다: logger.info("CNE (Clinical Notes Extraction)") (CNE.py:342와 CNE.py:663). 그리고 CLI가 같은 이름을 Slicer 관리자에 게시한다: <filter-name>Clinical Notes Extraction</filter-name> (CNE_CLI.py:93). CNE = Clinical Notes Extraction이며, 코드 외에는 이를 뒷받침하는 것이 없다.

1. 파이프라인에서의 위치

종단 모듈이다. 이 모듈을 호출하는 것도 없고, 이 모듈이 저장소의 다른 모듈을 호출하지도 않는다. CMakeLists.txt:50-52에 선언되어 있다(CNE, CNE_CLI, CNE_Dashboard).

알아 둘 점 두 가지:

함정

install_function (CNE.py:44)은 설치 중에 CC=gcc와 CXX=g++를 강제한 뒤 원래 값을 복원한다. pip가 llama-cpp-python을 소스에서 컴파일해야 하는 경우를 위한 것이다. Windows에서는 이 값들을 쓸 수 없다.

함정

추가 인덱스는 명시적으로 CPU 휠을 가리킨다. 그런데 CLI는 "Use GPU if available"이라는 주석과 함께 n_gpu_layers=-1을 요청한다 (CNE_CLI.py:164). CPU 전용 빌드에서는 이 매개변수가 아무 효과가 없다. 실제로 추론은 CPU에서 실행되며, 7–8 B 규모의 Q4 양자화 모델은 노트당 수십 초가 걸린다.

CLI는 시작 시 자신의 세 import(llama_cpp, fitz, docx)를 다시 검사하고 하나라도 없으면 sys.exit(1)을 호출한다 (CNE_CLI.py:101-117). 중복이지만, CLI가 위젯과 인터프리터를 공유하므로 해는 없다.

4. 모델

저장소에는 가중치가 포함되어 있지 않다. getModelPath() (CNE.py:513)가 필요할 때 GGUF를 다운로드한다. urllib.request.urlretrieve를 사용하고 QProgressDialog로 진행 상황을 표시하며, 저장 위치는 <Documents>/SlicerDownloads/CNE/model/이다.

수정됨

이 페이지는 예전에 여기에 확인된 버그를 기록했다. Ortho 모드가 저장소에 없는 model-q4_0.gguf를 요청해서 다운로드가 HTTP 404를 반환하고 "Download failed or was cancelled"와 함께 실패했다. 이제 코드는 model-q4_k_m.gguf를 DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho에서 요청하고(CNE.py:518-519), TMJ 파일은 DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ에서 요청한다(CNE.py:525-526). 2026-11-09에 두 URL에 HTTP HEAD 요청을 보내 확인했다. 둘 다 파일로 302를 응답하며, Ortho 파일은 4,920,738,880 바이트이므로 다운로드 대화 상자의 "약 4.9 GB"와 맞는다(CNE.py:521. TMJ 대화 상자는 4.4 GB라고 하는데(CNE.py:528) 이는 측정하지 않았다).

두 Hugging Face 저장소에는 이제 모델 카드가 있다. 이 페이지는 예전에 없다고 적었다 (ADT 저장소가 아니라 2026-11-09에 Hugging Face API로 읽었다). 각 카드는 라이선스(Ortho는 Llama 3.1, TMJ는 Apache 2.0), 기반 모델, 방법(LoRA, r = 32, alpha = 64, 병합 후 Q4_K_M으로 양자화), 학습 노트가 공개되지 않는 주석 달린 환자 데이터라는 점, 그리고 데이터셋을 환자 단위로 나눴다는 점을 밝힌다. Ortho 카드는 모델이 원문 노트를 시스템 프롬프트 없이 받는다고 하며, 이는 코드(§6)와 일치하고, 교정 소견(와이어 굵기와 재질, 결찰, 엘라스틱, 수평 피개, 수직 피개 등)을 스키마로 나열한다. 어느 카드도 평가를 보고하지 않는다. TMJ 카드는 파일을 4.7 GB로 적지만 다운로드 대화 상자는 4.4 GB라고 한다(CNE.py:528).

5. 입력과 전처리

SUPPORTED_EXTENSIONS = (".txt", ".pdf", ".docx"). 탐색은 비재귀적이다: glob.glob(os.path.join(notesFolder_input, f"*{ext}")) (CNE_CLI.py:135). 저장소의 다른 모든 모듈이 iglob(**, recursive=True)를 쓰는 것과 다르다. 환자별 하위 폴더로 구성된 폴더에서는 아무것도 나오지 않는다.

텍스트 추출(CNE_CLI.py:75):

clean_text() (CNE_CLI.py:42)가 유일한 전처리 단계이며, 그 목적이 코드에 적혀 있다. PDF/Word 내보내기마다 달라지지만 평문 학습 노트에는 나타나지 않았던 요소를 정규화하는 것이다. 둥근 아포스트로피와 따옴표는 ASCII로, en 대시와 em 대시는 -로, 줄바꿈 없는 공백은 일반 공백으로 바꾸고, 연속된 빈 줄을 하나로 합친다. 명시된 목표: 원본 형식과 관계없이 모델이 같은 텍스트를 보게 하는 것.

익명화도, PHI 필터링도 없다. 저장소의 테스트 노트는 수작업으로 가명 처리되어 있지만(B_001, [DOCTOR], Dr. XXX) 사용자 자신의 데이터에 대해 이를 보장하는 코드는 없다. Medical_Data_Anonymizer_Module 모듈은 별도로 존재하며 CNE와 연결되어 있지 않다.

6. 추론

파일당 한 번의 패스, 분할 없음 (CNE_CLI.py:194-203):

messages = []
if notesType.upper() == "TMJ":
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": clinical_text})

output = llm.create_chat_completion(messages=messages, max_tokens=500, temperature=0.1)

주목할 점:

함정

Ortho 모드는 지시문을 보내지 않는다. 원본 노트만 사용자 메시지로 전달되며, 작업 수행은 Llama-Ortho 모델의 미세조정에 맡겨져 있다고 가정한다. 반면 TMJ 모드는 MedX에서 물려받은 지시문을 유지한다.

  • create_chat_completion은 GGUF에 내장된 chat template을 적용한다. 두 모델 모두 Hugging Face에서 conversational 태그가 붙어 있으므로 템플릿은 존재한다. 다만 저장소에서는 보이지도, 제어되지도 않는다.
  • temperature=0.1이고 seed가 없다: 출력은 거의 결정론적이지만 정확히 재현되지는 않는다.
함정

길이에 대한 보호 장치가 없다. n_ctx는 6144(TMJ) 또는 2048(Ortho)이고, max_tokens=500이 이 예산에서 차감된다. 예산을 넘는 노트는 llama.cpp가 예외를 일으키게 한다. 예외는 파일 단위로 잡혀 로그에 기록되고, 해당 파일은 failed_files에 추가된다. Ortho 예산은 특히 빠듯하다: 노트에 쓸 수 있는 분량이 약 1,500 토큰이다. 테스트 노트 TMJ_note1.txt는 약 4,400자로, TMJ 모드에서는 통과한다.

  • 모델 로드는 stderr를 /dev/null로 돌려서 감싼다(os.dup2 사용, CNE_CLI.py:159). llama.cpp의 잡다한 출력을 숨기기 위한 것으로, 그렇지 않으면 Slicer가 CLI 실패로 해석하는 오류 채널이 오염된다.

7. 응답 후처리

모델은 JSON으로 답할 것으로 기대되지만 코드는 이를 강제하지 않는다( response_format도, GBNF 문법도 없음). 텍스트에서 JSON을 건져낼 뿐이다(CNE_CLI.py:209-214):

start_idx = ai_response.find('{')
end_idx   = ai_response.rfind('}') + 1
data = json.loads(ai_response[start_idx:end_idx])
if "extraction" in data:
    data = data["extraction"]
for key, value in data.items():
    formatted_response += f"{key} : {value}\n"

즉, 첫 번째 여는 중괄호부터 마지막 닫는 중괄호까지 잘라 내고, 있을 수 있는 extraction 단계를 벗겨 낸 뒤, key : value 줄로 평탄화한다. 파싱이 실패하거나 또는 중괄호가 아예 없으면 모델의 원시 응답이 그대로 기록된다. 출력 파일은 둘 중 어떤 경우였는지 알려 주지 않는다.

함정

결과: 단순한 find('{')…rfind('}') 슬라이싱은 응답에 JSON 객체가 둘 이상 있으면 바로 깨지며, 중첩된 값(리스트, dict)은 텍스트 파일에 Python repr로 기록된다.

8. 출력

입력 노트마다 출력 폴더에 텍스트 파일 하나:

Extraction_<note name without extension>.txt

내용: key : value 줄, 또는 파싱이 실패한 경우 모델의 원시 응답. 추출 자체에서는 CSV도, json도, 환자별 집계도 나오지 않는다. 표와 그림은 이 파일들을 나중에 읽는 Dashboard 버튼에서 나온다(§8.1).

출력 폴더는 위젯 쪽에서 os.makedirs(..., exist_ok=True)로 생성된다(CNE.py:613).

8.1 Dashboard

MedX의 "Dashboard" 부분은 2026-10-12에 이식되었으므로, 이 페이지의 이전 서술인 "이어지지 않았다"는 더 이상 맞지 않는다. 코드에서 읽은 내용은 다음과 같다.

  • 실행 계기. Dashboard 버튼(dashboardButton, CNE.ui 안에 있고 CNE.py:234에서 연결)이 onDashboardButton()(CNE.py:365)을 실행한다. 의존성을 확인하고, 출력 폴더가 없으면 실행을 거부하며, 출력 폴더를 입력과 출력으로 함께 넘겨 CNE_Dashboard를 CNELogic.dashboard()(CNE.py:629)로 실행한다. 모델도 다운로드도 관여하지 않는다.
  • 읽기. read_summaries() (display_figure.py:23)는 폴더에서 Extraction_*.txt 파일만 남긴다. 환자 식별자는 노트 이름에서 접두사를 뺀 것이다. process_summaries() (display_figure.py:135)는 initialize_key_value_summary() (dashboard_utils.py:332)가 초기화한 54개 키의 사전을 채우고 숫자 필드 여섯 개를 변환한다.
  • 예측이 아니라 계산. 각 패널은 계산됨 방식으로 dashboard_utils.py에서 이루어지는 결정론적 집계다(연령대, 통증 점수의 평균과 표준편차, "33 mm" 같은 문자열에서 파싱한 최대 개구량, 동의어 목록으로 찾은 두통과 관절통 위치, 좌우 관절원판 변위, 근육통 수준). 그림은 generate_dashboard_figure() (display_figure.py:164)가 그린다.
  • 출력. dashboard.png와 patient_data.csv (display_figure.py:714-716), 그리고 그림을 그리기 전에 기록되는 세 번째 파일 dashboard_full_dataframe.csv(display_figure.py:183).
  • 스키마가 맞지 않으면 시끄럽게 실패한다. report_field_coverage()(display_figure.py:668)는 값이 없는 기대 키를 기록하고, show_dashboard()(display_figure.py:694)는 값이 있는 키가 하나도 없거나 폴더에 Extraction_*.txt가 없으면 예외를 일으킨다.
함정

이 대시보드는 TMJ 대시보드다. 기대하는 키는 두통 강도, 턱 소리, 관절원판 변위, 최대 개구량, 수면 장애 등이다(dashboard_utils.py:339-396). TMJ 모델이 반환하기로 되어 있는 키들이며, Ortho 모델이 이를 쓴다고 저장소 어디에도 적혀 있지 않고 Ortho 모드에는 이를 강제할 지시문도 없다. Ortho 추출에서는 커버리지 검사가 "키가 일치하지 않는다"는 오류로 실행을 멈출 가능성이 크다. 이는 키 목록에서 추론한 것이며 Ortho 출력으로 실행해 본 것은 아니다. 키 자체는 코드가 아니라 모델이 정한다(report_field_coverage의 docstring, display_figure.py:668-679).

11. 함정과 취약 지점

  • Dashboard는 TMJ 스키마를 기대한다(§8.1).
  • 테스트 파일의 출력 폴더. copyTestFiles() (CNE.py:454)는 예전에 존재하지 않는 경로를 출력 필드에 넣었다. 이제 출력 폴더를 만들고(CNE.py:508), 호출할 때마다 폴더를 지우지 않고 노트를 다시 복사하며 (dirs_exist_ok=True, CNE.py:505), 사용자가 이미 고른 출력 폴더는 건드리지 않는다(CNE.py:328-330). Resources/testfiles/에는 여전히 input_ 폴더 두 개만 있다.
  • 입력 폴더의 비재귀적 탐색(§5).
  • 호출 전 길이 제한 없음: 너무 긴 노트는 분할되지 않고 실패한다. MedX는 분할을 했다(§6). 대체 과정에서 생긴 기능 퇴행이다.
  • Ortho 모드는 시스템 지시문을 보내지 않는다(§6): 모델이 기대한 모델이 아니라면 출력이 JSON일 이유가 전혀 없다.
  • 출력 형식에 대한 제약 없음: llama.cpp가 GBNF 문법과 response_format을 모두 제공하는데도 둘 다 쓰지 않는다. 따라서 후처리는 휴리스틱한 건져내기 작업이다(§7).
  • 라디오 버튼이 TMJ도 Ortho도 아닌 상태 → notesType = "" (CNE.py:427) → getModelPath에서 repo_id가 할당되지 않고, UnboundLocalError가 "Failed to load model"로 나타난다. 이 경우는 일어나지 않아야 하지만(setExclusive(True), 기본값 TMJ), 이를 막는 장치는 없다.
  • 대소문자 처리 불일치: notesType == "TMJ"가 n_ctx를 정하고, notesType.upper() == "TMJ"가 지시문을 정한다. 소문자 notesType이면 TMJ 지시문에 2048 컨텍스트가 조합된다.
  • 출처 기록 없음: Extraction_*.txt 파일에는 모델도, 버전도, 날짜도 적히지 않는다. 서로 다른 모델로 두 번 실행하면 구별할 수 없는 파일이 나온다.
  • PHI: 익명화도, 경고도 없다. 노트는 평문으로 읽혀 로컬 모델을 거친다(따라서 네트워크 유출은 없다. 이것이 유일한 안전장치이며, 의도된 것이라기보다 구조상 그렇게 된 것이다).
  • CLI 메타데이터가 템플릿 기본값 그대로: CNE_CLI.xml은 여전히 "Apply a Gaussian blur to an image"라고 기술하고, 모듈 작성자를 "Andras Lasso (PerkLab)"로 표기하며, <index> 값이 0, 2, 3, 4로 인덱스 1이 빠져 있다.
  • onCliProgress (CNE.py:651)는 caller.GetProgress()를 읽고 아무것도 하지 않는다. 어떤 옵저버에도 연결되어 있지 않다. 사용되지 않는 코드다. 실제 진행 상황은 CLI의 <filter-progress> 태그를 통해 전달되며, qSlicerCLIProgressBar가 이를 읽는다.

12. 문헌

저장소는 CNE에 대해 어떤 출판물도 인용하지 않으며, 두 DCBIA-OrthoLab/* Hugging Face 모델 카드도 논문을 인용하지 않는다(코드 저장소 ortho-cde-llm-extraction을 가리키는데, 이는 읽지 않았다). 주석 말뭉치는 공개되지 않았고 평가도 보고되지 않는다. 둘 다 저장소로부터 확인할 수 없다.

확인 가능한 것:

  • MedX → CNE 계보. 이를 기록한 것은 CNE_Dashboard.xml의 감사 문구("Ported from MedX_Dashboard, which CNE replaced without taking this half with it")와 display_figure.py:35, :675의 주석뿐이다. 루트 CMakeLists.txt는 더 이상 MedX를 언급하지 않으며 README에는 MedX나 CNE 절이 없다.
  • 기반 모델: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • 미세조정 저장소: DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho.
  • 엔진: llama-cpp-python, llama.cpp(GGUF 형식, Q4_K_M 양자화).
  • SlicerAutomatedDentalTools

CNE를 LLM 기반 임상 정보 추출에 관한 일반 문헌과 연결하지 말 것. 저장소 어디에도 여기서 쓰는 모델이 발표된 연구에서 나왔다는 표시가 없다.

이 결론에 이르기 위해 무엇을 검색했는지, 그리고 그 과정에서 모은 주변 연구: SOURCES.md.
