ALI, 레거시: 코드

개발자용: 레거시 Slicer 모듈이 코드에서 하는 일을 file:line 참조, 시그니처, 표, 함정과 함께 다룬다. 같은 파이프라인에 대한 읽기 쉬운 설명과 수식은 아틀라스 페이지에 있다. ALI는 스스로 아무것도 계산하지 않는다. 공유 코드가 없는 두 백엔드 중 하나를 고르는 디스패치 위젯이며, 두 백엔드는 ALI_CBCT(볼륨 안을 움직이는 강화학습 에이전트)와 ALI_IOS(메시에 대한 다중 뷰 렌더링과 픽셀 단위 분할)이고, 해부학적 랜드마크를 LPS로 배치한다.

코드 아틀라스 (해설) Gillot 2023 · Orthod Craniofac Res ALI_CBCT ALI_IOS CBCT: Slicer Python, IOS: shapeaxi conda 환경 VISOR 참고문헌
두 코드 베이스

아래에 번호가 붙은 모든 것은 레거시 Slicer 모듈(SlicerAutomatedDentalTools 3c67957, 2026-10-26)을 설명한다. 같은 도구를 서버에서 실행하는 VISOR 포팅은 VISOR의 ALI에서 설명한다. 콜아웃에 덧붙인 참고는 각 발견 사항이 VISOR에서도 여전히 유효한지 알려 주며, SADT-VISOR 6ba2a78을 인용하고, CB/는 tools/ALI/ALI_CBCT/src/sadt_ali_cbct/를, IO/는 tools/ALI/ALI_IOS/src/sadt_ali_ios/를 가리킨다. 아래의 모든 file:line은 3c67957에서 다시 읽었다(ALI_CBCT.py는 371줄, ALI_IOS.py는 1133줄, ALI.py는 2224줄). 콜아웃이 이전 리비전을 설명할 때는 그렇게 밝힌다.

2. 관련 파일

참고 · 레거시 전용

이 모듈의 일부는 이제 공유 계층에 있다. ADTLib는 여러 모듈이 사본으로 들고 있던 것을 한곳에 모은다. 여기서는 geometry.py, io/landmarks.py, testdata.py, 그리고 method.py의 계약이 해당한다. 각 파일이 사본 몇 개를 대체했는지는 그 페이지에 기록되어 있다.

레거시(3c67957). VISOR에는 없다. 서버 도구는 ADTLib를 import하지 않는다. 이들이 공유하는 것은 작은 sadt-ali-common 패키지(SADT-VISOR tools/ALI/common/src/sadt_ali_common/: discovery.py, markups.py)다.

자명하지 않은 점: ALI_CBCT는 conda를 거치지 않는다. Slicer 자체의 Python에서 실행되며, 그래서 itk, dicom2nifti, pydicom, monai가 install_function(ALI.py:61, 목록은 :882-898)으로 설치된다. ALI_IOS는 Slicer에 없는 pytorch3d가 필요하므로 conda run을 거친다. CUDA는 어디에서도 필수가 아니며, 둘 다 CPU로 대체되고(DEVICE = cuda if available else cpu) 그 대가는 시간이다.

쉬운 설명과 수식: 아틀라스 페이지.

3.1 전처리

두 단계이며, 둘 다 temp_fold에 기록되고 정리되지 않는다.

  1. 히스토그램 윈도잉, CorrectHisto(scan, out, 0.01, 0.99)(preprocess.py:14): 1000개 빈의 히스토그램, 정규화된 누적, 1%와 99% 백분위수로 클리핑, [-1500, 4000] HU로 하드 바운드. 출력은 int16이며 spacing/origin/direction은 보존된다. 주의: 기본 시그니처에는 max_porcent=0.95라고 되어 있지만, 호출은 0.99를 넘긴다.
  2. 등방성 리샘플링, 스케일마다 파일 하나: SetSpacing(itk, 선형 보간, 이름에 seg/Seg가 있으면 최근접 이웃)을 각 sp에 대해, spacing = [1, 0.3] mm로 적용한다. 새 크기는 size * spacing / sp이고 origin은 같은 물리적 상자 위에 다시 중심을 맞춘다.
함정 · 레거시 전용

파일 이름은 <stem>_sp<1|0-3><suffixes>이며 이미 있으면 재사용된다. 캐시인 것이다. 따라서 이름은 그대로인데 입력이 바뀌면 함정이기도 하다.

레거시(3c67957): 여전히 사실이며, ALI_CBCT/ALI_CBCT.py:199와 :215는 이미 있는 파일을 건너뛴다. VISOR에는 없다. 스캔마다 자체 스크래치 폴더를 받고 스캔이 끝나면 지워지므로(SADT-VISOR CB/engine.py:910), 한 실행이 다른 실행의 파일을 읽는 일이 없다.

로드 시점(environment.py:72)에 sitk.DICOMOrient(img, "LPS")를 호출한다. 이것이 없으면, 원본 배열만 읽고 방향 코사인은 전혀 읽지 않는 에이전트가 거울상으로 뒤집힌 볼륨 속을 걷게 된다. 그다음 EnsureChannelFirst + BorderPad(padding)를 적용하며 padding = agent_FOV/2 + 1 = [33,33,33]이다. 에이전트가 어디에 서 있든 64³ 자르기가 유효하도록 하기 위해서다.

배열은 numpy (z,y,x) 순서로 저장되고 origin은 그 순서에 맞추어 뒤집힌다. 하지만 spacing은 뒤집히지 않고 (x,y,z)로 남는다. 영향이 없는 것은 리샘플링이 spacing을 등방성으로 만들기 때문일 뿐이다.

쉬운 설명과 수식: 아틀라스 페이지.

3.2 Environment

Environment(environment.py:17)는 환자 한 명이다. {scale_key: {image, spacing, origin, size}} 딕셔너리와 예측된 랜드마크 목록으로 이루어진다. 환자당 인스턴스 하나이며, 모든 스케일이 메모리에 올라 있다.

GetZone(scale, center, crop_size)는 에이전트가 세계에 대해 보는 유일한 것이다.

cropTransform = SpatialCrop(center.tolist() + self.padding, crop_size)
rescale = ScaleIntensity(minv=-1.0, maxv=1.0, factor=None)
crop = rescale(cropTransform(self.data[scale]["image"])).type(torch.float32)

에이전트를 중심으로 한 64×64×64 복셀 정육면체이며, 자른 조각마다 [-1,1]로 재정규화된다(전역 정규화가 아니라 국소 최솟값/최댓값). 스케일 1에서는 한 변 64 mm를, 스케일 0-3에서는 19.2 mm를 덮는다.

3.3 에이전트와 그 네트워크

랜드마크마다 에이전트 하나(agent.py:149)가 한 번 인스턴스화된 뒤 모든 환자에게 재사용된다. 새 Brain이 만들어지고 그 가중치가 (환자, 랜드마크) 쌍마다 다시 로드된다(ALI_CBCT.py:123). 점 하나, 스캔 하나마다 DenseNet 2개를 다시 만들고 .pth 파일 2개를 다시 읽는다.

네트워크 DNet(brain.py:39):

self.featNet = DenseNet(spatial_dims=3, in_channels=1, out_channels=1024,
                        growth_rate=34, block_config=(6, 12, 24, 16))
self.dens = DN(in_channels=1024, out_channels=6)   # MLP 1024-512-256-128-6

monai의 3D DenseNet-121(성장률 32 대신 34)과 그 뒤의 4층 MLP. 입력은 [1, 1, 64, 64, 64], 출력은 이동마다 하나씩 6개의 점수다. Up / Down / Back / Front / Left / Right, 곧 배열의 세 축을 따라 ±1복셀이다(constants.py:29).

이것은 히트맵이 아니라 방향 분류기다. 네트워크의 예측은 점이 어디에 있는지를 말하지 않고, 어느 쪽으로 한 걸음 옮길지를 말한다. Predict는 6개 점수의 argmax를 취한다(brain.py:157).

확인된 버그 · VISOR에서도 마찬가지

DN.forward가 relu를 마지막 층에도 적용한다는 점에 유의하라. 그래서 점수는 0 이상이며, 사전 활성화가 모두 음수이면 6개가 전부 0이 되고 argmax는 늘 0("Up")을 돌려준다. 바로 아래에 주석 처리된 softmax는 이것이 의도가 아니었음을 시사한다.

VISOR에서도 마찬가지다. 이식된 헤드도 같은 식으로 끝난다(SADT-VISOR CB/brain.py:90, 레거시 ALI_CBCT_utils/brain.py:35, 3c67957 기준).

스케일마다 네트워크 하나: Brain이 scale_key마다 하나씩 인스턴스화하며, LoadModels는 <label>/1/*.pth를 로드한 뒤 <label>/0-3/*.pth를 로드한다.

쉬운 설명과 수식: 아틀라스 페이지.

3.4 탐색

Agent.Search() (agent.py:345):

  1. 스케일 0(1 mm), 위치는 볼륨의 중심.
  2. 루프: PredictAction() → Move(), speed_per_scale[scale] = 1복셀 단위의 걸음.
  3. 정지 기준 = 진동. Visited()는 현재 위치가 최근 10개 위치(shortmem_size = 10) 중에 있는지 확인한다. 에이전트가 왔던 길을 되밟으면 도착한 것으로 간주한다.
  4. UpScale(): 스케일 0-3으로 이동하고, 위치는 spacing 비율로 변환되며, 단기 기억이 비워지고, 탐색이 다시 시작된다.
  5. 마지막 스케일에서는 Visited()가 탐색을 끝낸다.

3c67957의 예산과 재생성(커밋 b87c02f, 2026-09-18). 탐색은 max_steps번의 순전파 뒤에 멈추며 기본값은 1000이다(ALI_SEARCH_MAX_STEPS, ALI_CBCT_utils/agent.py:27, :58-60, 루프 :377). 여기에 900 s의 안전 장치가 있다(ALI_SEARCH_TIME_GUARD, :33, :380-391). 이미 지나간 곳을 연속 64걸음 도는 탐색은 다시 생성된다(Cycling, :43, :402-412, :471-491). 자르기 전체를 읽을 수 있는 영역을 벗어나도 마찬가지로 다시 생성된다(Move, :279-289: 스캔의 각 면에서 한 복셀 너머, environment.py:246-272). 두 종류의 재생성은 모두 한 번의 시도로 세며, 세 번째에서 랜드마크를 버린다(search_atempt > 2, :421-428). 예산을 다 써도 -1을 돌려준다(:446-453). 재생성은 무작위다. 스케일 0에서는 어디든 가능하고, 이후 스케일에서는 그 스케일이 시작된 곳에서 spawn_radius = 10복셀 이내이며(:244-259), 시드 없이 전역 np.random을 쓴다. VISOR: 900걸음, 시간 안전 장치 없음, 64걸음 규칙 없음, 랜드마크마다 시드가 있는 생성기(SADT-VISOR CB/engine.py:55, CB/agent.py:54-68).

최종 정밀화, Focus()(agent.py:305): 찾아낸 위치에서 ±x, ±y, ±z 방향으로 4복셀(마지막 스케일에서 1.2 mm)씩 떨어진 곳에서 여섯 번 다시 시작하고, 각각은 Visited()가 될 때까지 다시 걷는다. 채택되는 위치는 여섯 착지점의 평균이다. 결과가 서브복셀이 되는 까닭이다. 여섯 탐침은 +x, -x, +y, -y, +z, -z 순서로 시작하며(:306-330), 각각 자신의 max_steps로 제한된다(:331). 탐색의 64걸음 규칙은 여기에 적용되지 않고, 읽을 수 있는 영역을 벗어난 걸음은 탐침을 무작위 위치에 다시 생성한다(Move).

참고 · 대체됨: Focus는 3c67957에서 제한된다

4.2 카메라

GenPhongRenderer (render.py:10-35):

image_size / blur_radius / faces_per_pixel은 CLI의 위치 인자이지만, 모든 호출자가 224 / 0 / 1을 넘긴다(IOS.py:280, IOSCBCT.py:333, FlexReg.py:2323). blur_radius = 0에 faces_per_pixel = 1은 하드 래스터화, 곧 픽셀당 면 하나를 뜻하며, 이것이 pix_to_face를 픽셀-면 조회표로 쓸 수 있게 한다.

텍스처는 색이 아니다. TexturesVertex(verts_features=CN)이며 CN은 정점별 법선을 RGB로 다시 매핑한 것이다((n*0.5+0.5)*255, surface.py:101). 그러니 네트워크가 보는 것은 Phong 조명을 받은 법선 맵이고, 여기에 z-버퍼가 네 번째 채널로 붙는다.

카메라는 치아마다 하나씩, 그 무게중심에서 radius만큼 떨어진 곳에 놓인다.

  • 아치 접선: 치아 label-1과 label+1의 무게중심 차이(하악 레이블 18→31은 아치를 따라 순서대로 이어진다)를 z에서 평평하게 편 것.
  • 협측 법선: 접선에 수직인 수평 방향이며, 안쪽을 향하면 뒤집는다. 이전 버전이 쓰던 방사 방향(치아 중심 − 메시 중심)은 치아 19/30에서 35°, 치아 31에서 53° 어긋난다. 카메라가 아치를 따라 보고 있었고 점이 렌더 밖에 놓였다.
  • 조준점: 치아 무게중심이 아니라 centroid + b·normal + t·tangent, z += v이며, (b,t,v)는 MG_AIM_OFFSET(model.py:35)에서 읽는다. 학습 스캔 155개에 대한 치아별 중앙값이고 산포는 0.02–0.03이다.
  • 카메라 세 개: 협측 법선, 그리고 수평면에서 ±0.35 rad 돌린 둘(x와 y 성분을 회전하므로 수직축 둘레이며, 코드 주석은 이를 Y축이라 부른다). 조준점에서 radius만큼 떨어지고 0.15·radius만큼 낮춰 놓는다.

귀결: O/C 점과 모든 ALI_CBCT 점은 품질과 무관하게 description이 비어 있다. 표시 메커니즘은 MG에만 있다.

VISOR에서도 마찬가지다. 노트는 MG 경로에서만 채워지며(SADT-VISOR IO/engine.py:571-575, :426이 기록), ALI_CBCT는 description을 넘기지 않는다(CB/engine.py:921). 차이: 3c67957에서는 이긴 MG 점도 confidence 0.xyz를 가지는 반면(ALI_IOS.py:553-554), VISOR는 강제된 점만 노트에 적는다(IO/engine.py:552). 그리고 VISOR는 품질이 떨어진 점을 실행 보고서의 landmarks_degraded에 나열한다(:414-419).

쉬운 설명과 수식: 아틀라스 페이지.

4.6 출력과 가중치

(환자, 아치, 모델)마다 파일 하나: <patient>_<Lower|Upper>_<O|C|MG>_Pred.json, coordinateSystem: "LPS"(io.py:74). 좌표는 입력 메시의 것이며 뒤집지 않는다. "LPS"라는 레이블이 맞는 것은 이 파이프라인의 .vtk 파일이 LPS이기 때문이지, 코드가 확인해서가 아니다.

GenControlPoint는 landmarks_selected로 거른다. O 모델은 늘 XO/XMB/XDB를 예측하지만, 요청된 유형만 기록된다.

가중치 탐색(_discover_models, ALI_IOS.py:228-294)은 파일 이름만으로 이루어진다.

<jaw>_<model_id>_<anything>.pth
 ^ "Lower" present in the name? otherwise "Upper"
        ^ basename.split("_")[1], must be O, C or MG

한 설치본에서 확인함: Lower_O_model.pth, Upper_C_model.pth, Lower_MG_v6.pth. 같은 쌍에 후보가 둘이면 sorted()가 정하고 경고가 발행된다. 위젯 자체는 _O_/_C_를 부분 문자열로 탐지하고(ALI.py:143-144) Lower_MG_*는 따로 탐지한다(HasMGModel, ALI.py:2196, :810과 :919에서 사용). 같은 파일에 대한 관례가 둘이다.

다운로드: https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/ALI_IOS_models/Models.zip(IOS.py:153), 과거 ALIDDM v1.0.3 아카이브의 내용에 Lower_MG_v6.pth를 더한 것이다. <Documents>/SlicerDownloads/ALI/ALI_IOS/Models/Prediction/에 압축이 풀리며, FlexReg가 찾으러 가는 바로 그 경로다.

쉬운 설명과 수식: 아틀라스 페이지.

7. 함정과 취약 지점

  • Focus()에는 안전장치가 없었다(이 페이지가 쓰인 기준 리비전에서). 대체됨: 3c67957(agent.py:325-341)과 VISOR(CB/agent.py:238-243)에서는 제한된다. 3.4의 참고를 참조.
  • Move()는 경계를 잘못 검사한다: if new_pos.all() > 0 and (...)에서 .all()은 불리언을 돌려주고 이를 0과 비교한다. 이 검사는 "음수인 좌표가 없다"가 아니라 "0인 좌표가 없다"를 확인한다(agent.py:242). 대체됨: 7d901e4(2026-09-18) 이후 레거시는 패딩된 표본 영역을 좌표별로 검사하고(ALI_CBCT_utils/agent.py:114, :279-284), VISOR는 >= 0과 < size를 검사한다(CB/agent.py:135-141).
  • int16 캐스트(argmax 앞)는 O와 C 모델에 여전히 남아 있다. MG 코드의 주석이 이것이 왜 틀렸는지 정확히 설명한다. 레거시 전용: 3c67957(ALI_IOS.py:738-739)에 아직 있으며, VISOR에는 없다(IO/engine.py:216).
  • MG가 아닌 경우 get_view_rasterize는 R/T 없이 래스터화한다: renderer.rasterizer(meshes.clone())(3c67957의 agent.py:364)는 바로 위의 렌더링이 쓴 행렬을 넘기지 않으므로, pix_to_face는 이미지를 만든 카메라가 아니라 기본 카메라에서 나온다. MG 경로는 이를 고치려고 명시적으로 작성되었다("with the SAME R,T so pix_to_face stays aligned", agent.py:267). 이것은 원래의 upstream 코드이며 O/C에는 다시 적용된 적이 없다. 레거시 전용: 3c67957의 ALI_IOS_utils/agent.py:364에 아직 있으며, VISOR는 뷰마다 R과 T를 써서 한 번 래스터화한다(IO/render.py:402-412).
  • val_pred / post_pred(ALI_IOS.py:724-728): AsDiscrete(argmax=True, to_onehot=4)가 모든 뷰에서 계산된 뒤 한 번도 읽히지 않는다. 치아 하나하나마다 발생하는 죽은 계산이다.
  • MG 이름 충돌. 출력 이름 13개 중 여섯 개는 다른 치아의 학습 이름이다. LR1MG는 치아 26의 출력이면서 치아 25의 학습 이름이다(model.py:25). 두 관례 사이의 어떤 변환도 레이블 하나씩이 아니라 레이블 집합 전체를 두고 정해야 한다.
  • 위젯의 DICOM 경로는 망가져 있다. Auto_CBCT는 NumberScanDCM도, TestScanDCM도, getTestFileListDCM도 구현하지 않으며, 기반 버전은 None을 돌려준다. "DICOM"을 체크하면 nb_patient = None이 되고, 테스트 파일을 내려받을 때 TypeError가 나고, None으로 나누는 오류가 OnEndProcess에서 난다. CLI 자체는 변환할 줄 안다.
  • Agent 매니페스트가 불완전하다. ali_cbct는 기대되는 위치 인자 10개에 매개변수 6개를 선언하고, ali_ios는 10개에 6개를 선언하며 teeth_mg를 빠뜨린다(인덱스 4). 뒤따르는 값들이 한 칸씩 밀린다(manifest.yaml:48).
  • ALI_CBCT는 temp_fold를 절대 정리하지 않으며, 리샘플링된 파일은 있으면 그대로 재사용된다. 두 실행 사이의 조용한 캐시다. 레거시 전용: 3c67957에서 재사용은 ALI_CBCT.py:199, :215에 있으며, VISOR는 스캔마다 스크래치 폴더를 지운다(CB/engine.py:910).
  • Auto_IOS.getALIModelList는 super().getALIModelList()를 돌려주는데, 이는 빈 추상 메서드 → None이다(IOS.py:159-160).
  • slicer.modules.ali_ios는 AREG가 slicer.cli.run으로 호출하므로(IOSCBCT.py:341), pytorch3d와 shapeaxi가 설치되어 있지 않은 Slicer의 Python 안에서 실행된다. ALI 위젯 자체는 이를 오직 conda run을 통해서만 호출한다. 두 경로가 같은 설치본에서 함께 동작할 수는 없다.
  • SURFACE_LANDMARKS(ALI.py:137)는 R, RIP, OIP를 제공하는데, 이들은 MODELS_DICT에 항목이 없다. 이것들만 선택하면 CLI가 "No matching models found."로 실패한다.
  • onPredictButton은 두 IOS 프로세스를 잘못 잇는다: if "CrownSegmentationcli"와 뒤따르는 if "ALI_IOS"는 상호 배타적이지 않고, 그 뒤의 else는 두 번째에 붙는다(ALI.py:992-1011). 분할이 필요하면 ALI_IOS는 onProcessUpdate에서 다시 시작되고, 아니면 onPredictButton에서 시작된다. 같은 단계에 진입점이 둘이다.

쉬운 설명과 수식: 아틀라스 페이지.

8. 문헌

두 백엔드는 각자의 논문이 있으며, 코드는 그 서술과 일치한다. ALI_IOS에는 한 가지 유보가 붙는다.

ALI_CBCT: Automatic landmark identification in cone-beam computed tomography, Gillot, Baquero, Cevidanes 외, Orthodontics & Craniofacial Research, 2023. 검출은 분류 문제로 재구성된다. 볼륨 안에 놓인 가상 에이전트가 다중 스케일 공간을 탐색하며 랜드마크로 향하는 법을 학습한다.

확인됨 · 알고리즘에 대해서는 VISOR에서도 마찬가지

보고된 평균 오차는 랜드마크 32개에서 1.54 ± 0.87 mm, 추론 4.2 s이다. 두 스케일, 1 mm / 0.3 mm를 포함해 코드가 하는 일과 정확히 같다.

알고리즘은 VISOR에서도 그대로다. 스케일 1 mm와 0.3 mm(SADT-VISOR CB/catalog.py:69), 시야 64³(CB/agent.py:39). 정확도와 4.2 s는 논문의 수치이며 어느 쪽에서도 다시 측정되지 않았다. VISOR 자체의 시간 측정 노트는 인자와 I/O에 있다.

원본 저장소: Maxlo24/ALI_CBCT.

ALI_IOS: Automatic Landmark Identification on IntraOralScans, Baquero, Gillot, Prieto, Cevidanes, Clinical Image-Based Procedures (CLIP 2022), LNCS 13746, p. 32-42.

확인됨 · VISOR에서도 마찬가지이나 디코더가 다르다

단위 구 스케일링, 치아당 5개의 2D 뷰, 뷰별 패치 분할, 패치 좌표의 평균, 다시 스케일 확대. 코드의 O 모델에 대한 서술과 글자 그대로 일치한다.

VISOR 코드에서도 마찬가지다. 단위 구(SADT-VISOR IO/surface.py:72), O에는 치아당 카메라 다섯 개(IO/render.py:39-54). 유일한 이탈은 O와 C 마스크에서의 argmax이며, 위의 int16 콜아웃을 참조.

원본 저장소: DCBIA-OrthoLab/ALI_IOS. 프로토타입 쪽은 ALIDDM.

참고 · 아치 수평 맞춤을 제외하고 VISOR에서도 마찬가지

MG 경로는 출판되지 않았다. 적응형 협측 카메라, MG_AIM_OFFSET, 12채널 쌓기, 아치 수평 맞춤, 강제된 점, description 필드. 이 중 어느 것도 구형 5뷰 방식만 아는 CLIP 논문에 나오지 않는다. 인용된 수치(학습 스캔 155개, 추정된 점의 4–21 mm, FlexReg의 임계값을 정한 예측 364개)는 코드 주석에서만 출처를 찾을 수 있다.

레벨링을 제외하면 VISOR에서도 마찬가지다. 적응형 협측 카메라(SADT-VISOR IO/render.py:211-318), MG_AIM_OFFSET(IO/catalog.py:96), 12채널 쌓기(IO/engine.py:175), 강제된 점(:538-552), description 필드(:571-575)는 모두 있다. 아치 수평 맞춤은 VISOR에 없으며(LowerArchMatrix가 ALI_IOS/src에 없다), 레거시에서는 ALI_IOS/ALI_IOS.py:817에 있다.
