ALI

ALI는 스스로 아무것도 계산하지 않는다. 공유 코드가 전혀 없는 두 백엔드 — ALI_CBCT(볼륨 안을 이동하는 강화학습 에이전트)와 ALI_IOS(메시에 대한 다시점 렌더링과 픽셀 단위 분할) — 중 하나를 골라 LPS 좌표로 해부학적 랜드마크를 배치하는 분기(dispatch) 위젯이다.

Gillot 2023 · Orthod Craniofac Res ALI_CBCT ALI_IOS CBCT: Slicer Python — IOS: shapeaxi conda 환경 참고문헌

눈에 띄지 않는 점: ALI_CBCT는 conda를 거치지 않는다. Slicer 자체의 Python에서 실행되며, 그래서 itk, dicom2nifti, pydicom, monai가 install_function(ALI.py:875)으로 설치된다. ALI_IOS는 Slicer에 없는 pytorch3d가 필요하므로 conda run을 거친다. CUDA는 어디에서도 필수가 아니다. 둘 다 CPU로 대체되며(DEVICE = cuda if available else cpu), 대신 시간이 든다.

ALI_IOS CLI는 Slicer 모듈로도 등록되어 있고(slicer.modules.ali_ios, ALI_IOS.xml), AREG는 이 경로로 호출한다. 즉 pytorch3d가 설치되지 않은 Slicer의 Python 안에서다. 취약한 경로이며 §7 참조.

3. ALI_CBCT — 볼륨 안의 에이전트

3.1 전처리

두 단계이며, 둘 다 temp_fold에 기록되고 절대 정리되지 않는다.

  1. 히스토그램 윈도잉, CorrectHisto(scan, out, 0.01, 0.99) (preprocess.py:27): 1000개 구간(bin) 히스토그램을 정규화 누적한 뒤 1%와 99% 백분위수로 자르고, [-1500, 4000] HU로 강제 제한한다. 출력은 int16이며 spacing/origin/direction은 보존된다. 주의: 기본 시그니처는 max_porcent=0.95이지만 호출은 0.99를 넘긴다.
  2. 등방성 재샘플링, 스케일마다 파일 하나: SetSpacing(itk, 선형 보간 — 이름에 seg/Seg가 있으면 최근접 이웃)을 sp마다 적용한다. 대상은 spacing = [1, 0.3] mm의 각 값이다. 새 크기는 size * spacing / sp이고 origin은 같은 물리적 상자에 맞춰 다시 중심을 잡는다.
함정

파일 이름은 <stem>_sp<1|0-3><suffixes>이고 이미 존재하면 재사용된다. 즉 캐시이며, 입력이 이름 변경 없이 바뀌면 함정이 된다.

로드 시(environment.py:81): sitk.DICOMOrient(img, "LPS") — 이것이 없으면 원시 배열만 읽고 방향 코사인은 전혀 읽지 않는 에이전트가 거울상 볼륨 안을 걷게 된다. 이어서 EnsureChannelFirst + BorderPad(padding)를 padding = agent_FOV/2 + 1 = [33,33,33]로 적용하여, 에이전트가 어디에 있든 64³ 크롭이 유효하도록 한다.

배열은 numpy (z,y,x) 순서로 저장되고 origin도 같은 순서에 맞추어 뒤집힌다. 그러나 spacing은 뒤집히지 않고 (x,y,z)로 남는다. 재샘플링이 spacing을 등방성으로 만들기 때문에만 영향이 없다.

3.2 환경

Environment(environment.py:26)는 환자 한 명이다. 사전 {scale_key: {image, spacing, origin, size}}와 예측된 랜드마크 목록으로 이루어진다. 환자당 인스턴스 하나이며, 모든 스케일을 메모리에 들고 있다.

GetZone(scale, center, crop_size)는 에이전트가 세계에 대해 볼 수 있는 유일한 것이다.

cropTransform = SpatialCrop(center.tolist() + self.padding, crop_size)
rescale = ScaleIntensity(minv=-1.0, maxv=1.0, factor=None)
crop = rescale(cropTransform(self.data[scale]["image"])).type(torch.float32)

에이전트를 중심으로 한 64×64×64 복셀 정육면체로, 크롭마다 [-1,1]로 재정규화된다(전역 정규화가 아니라 국소 최소/최대). 스케일 1에서는 한 변 64 mm, 스케일 0-3에서는 19.2 mm를 덮는다.

3.3 에이전트와 신경망

랜드마크마다 에이전트 하나(agent.py:73)가 한 번 생성되어 모든 환자에 재사용된다. 새 Brain이 만들어지고 가중치가 다시 로드되는 것은 (환자, 랜드마크) 쌍마다다(ALI_CBCT.py:194). 점 하나, 스캔 하나마다 DenseNet 2개를 다시 만들고 .pth 파일 2개를 다시 읽는다.

신경망 DNet(brain.py:48):

self.featNet = DenseNet(spatial_dims=3, in_channels=1, out_channels=1024,
                        growth_rate=34, block_config=(6, 12, 24, 16))
self.dens = DN(in_channels=1024, out_channels=6)   # MLP 1024-512-256-128-6

monai의 3D DenseNet-121(성장률 32 대신 34)에 4층 MLP가 이어진다. 입력은 [1, 1, 64, 64, 64], 출력은 이동마다 하나씩 6개의 점수다: Up / Down / Back / Front / Left / Right — 즉 배열 세 축 각각을 따라 ±1 복셀(constants.py:22).

이것은 히트맵이 아니라 방향 분류기다. 신경망의 예측은 점이 어디 있는지가 아니라 어느 쪽으로 한 걸음 갈지를 말한다. Predict는 6개 점수의 argmax를 취한다(brain.py:166).

확인된 버그

DN.forward는 relu를 마지막 층에도 적용한다. 따라서 점수는 ≥ 0이고, 활성화 전 값이 모두 음수이면 6개 모두 0이 되어 argmax는 항상 0("Up")을 반환한다. 바로 아래 주석 처리된 softmax로 보아 의도된 동작은 아니었던 듯하다.

스케일마다 신경망 하나: Brain은 scale_key마다 하나를 생성하고, LoadModels는 <label>/1/*.pth를 읽은 뒤 <label>/0-3/*.pth를 읽는다.

3.4 탐색

Agent.Search() (agent.py:242):

  1. 스케일 0(1 mm), 위치는 볼륨 중심;
  2. 반복: PredictAction() → Move(), 보폭은 speed_per_scale[scale] = 1 복셀;
  3. 정지 기준 = 진동. Visited()는 현재 위치가 최근 10개 위치(shortmem_size = 10) 안에 있는지 확인한다. 에이전트가 온 길을 되밟으면 도착한 것으로 간주한다;
  4. UpScale(): 스케일 0-3으로 옮기고, 위치를 spacing 비율로 변환하고, 단기 기억을 비운 뒤 탐색을 다시 시작한다;
  5. 최종 스케일에서 Visited()가 탐색을 끝낸다.

시간 예산: 랜드마크 하나, 환자 하나당 GPU에서 15 s, CPU에서 60 s이며 ALI_SEARCH_MAX_TIME으로 바꿀 수 있다. 초과하면 → -1, 랜드마크는 기록되지 않는다. 에이전트가 볼륨 밖으로 세 번 나가도 마찬가지다(search_atempt > 2). 나갈 때마다 무작위로 다시 배치된다(스케일 > 0에서 시작점 주변 spawn_radius = 10 복셀).

최종 정밀화, Focus()(agent.py:215): 찾은 위치에서 ±x, ±y, ±z 방향으로 4 복셀(최종 스케일에서 1.2 mm) 떨어진 곳에서 여섯 번 재시작한다. 각각 Visited()까지 다시 걷고, 채택되는 위치는 여섯 도착점의 평균이다. 결과가 복셀 이하 정밀도를 갖는 것은 이 때문이다.

함정

Focus에는 아무런 제한이 없다. 시간 제한도, 걸음 수 제한도, search_atempt 검사도 없다. 볼륨을 벗어난 에이전트는 무작위로 다시 배치되고 while not found 루프가 처음부터 다시 시작된다.

SavePredictedLandmarks(scale_keys[-1], output_dir)(environment.py:118)는 인덱스를 물리 좌표로 되돌린다.

physical_origin = abs(ref_origin / ref_spacing)
real_label_pos  = (pos - physical_origin) * ref_spacing
real_label_pos  = [real_label_pos[2], real_label_pos[1], real_label_pos[0]]  # back to x,y,z
확인된 버그

abs()는 origin이 세 축 모두에서 음수라고 가정한다. 원점을 중심으로 한 LPS 볼륨에서는 참이지만 일반적으로는 거짓이다.

점은 해부학적 계열(LABEL_GROUPS: CB, U, L, CI)로 묶이고 그룹마다 파일 하나가 기록된다: <patient without extension>_lm_Pred_<group>.mrk.json, coordinateSystem: "LPS", description은 항상 비어 있다(io.py:5). GreedyReg는 이를 다시 RAS로 뒤집는다(Logic.py:518).

4. ALI_IOS — 다시점 렌더링

4.1 입력

.vtk, .vtp, .stl, .obj, .off. 그러나 모든 것은 치아 레이블 배열에 달려 있다. 이 배열은 PredictedID, predictedId, Universal_ID 이름으로 찾는다(surface.py:207). 이것이 각 치아의 중심점, 따라서 카메라 위치를 준다. 배열이 없으면 RI는 0으로 설정되고 어떤 레이블도 찾지 못한다.

스캔에 배열이 없으면 SegmentSurface(segmentation.py:80)가 dentalmodelseg를 사본에 대해 호출한다(shapeaxi에 넘긴 .stl은 --overwrite 1이면 dental_model_seg.py가 삭제한다). 이때 csv를 거친다(--surf에 파일 하나를 넘기면 shapeaxi가 정의하지 않은 속성에서 충돌한다). 분할은 점을 옮기지 않으므로 — 주석에 따르면 11만 8천 개 점에서 5e-5 mm로 측정 — 랜드마크는 원본 파일에서도 유효하다.

정규 스케일링, ScaleSurf(surface.py:94): 경계 상자(bounding box) 중점을 중심으로 옮긴 뒤 scale = 1 / ||max - center||. 파이프라인 전체가 이 단위 구 안에서 동작하며, 마지막에 Upscale이 이를 되돌린다.

수평 맞춤(MG 전용), LowerArchMatrix(orientation.py:98): MG 카메라는 Z로 가정한 수직축을 중심으로 만들어진다. 교합평면은 치아 18–31의 중심점에 SVD로 맞추고(최소 4개 치아, 레이블 폭 ≥ 4), 치관이 위를 향하도록 부호를 정한 뒤, 최소 회전(Rodrigues)으로 법선을 +Z에 맞춘다. MAX_TILT_DEGREES = 12° 미만이면 스캔은 전혀 건드리지 않는다. 이미 수평인 스캔을 고정 좌표계로 보내면 평면 안에서 회전되어 예측이 나빠지기 때문이다. 랜드마크는 기록 전에 inv(matrix)로 되돌려진다.

4.2 카메라

GenPhongRenderer (render.py:20):

cameras = FoVPerspectiveCameras(znear=0.01, zfar=10, fov=90)
raster_settings = RasterizationSettings(image_size=224, blur_radius=0, faces_per_pixel=1)

image_size / blur_radius / faces_per_pixel는 CLI의 위치 인자이지만 모든 호출자가 224 / 0 / 1을 넘긴다(IOS.py:286, IOSCBCT.py:335, FlexReg.py:2517). blur_radius = 0과 faces_per_pixel = 1은 픽셀당 면 하나인 경성 래스터화를 뜻한다. 이 덕분에 pix_to_face를 픽셀→면 조회 테이블로 쓸 수 있다.

텍스처는 색이 아니다: TexturesVertex(verts_features=CN)에서 CN은 RGB로 재매핑한 정점별 법선이다((n*0.5+0.5)*255, surface.py:171). 따라서 신경망은 Phong 조명된 법선 맵과, 네 번째 채널로 z-buffer를 본다.

치아마다 카메라를 그 중심점에서 radius 거리에 배치한다.

dic_cam['O']의 방향은 잘못 정규화되어 있다: np.array([0.5,0,1.0]) / linalg.norm([0.5,0.5,1.0])은 다른 벡터의 노름으로 나눈다(model.py:66). 따라서 카메라는 반경 radius인 구 위에 있지 않다. 가중치가 같은 테이블로 학습되었다면 무해하다.

MG 카메라, 유일한 적응형 부분(agent.py:192):

  • 치열궁 접선: 치아 label-1과 label+1 중심점의 차(하악 레이블 18→31은 치열궁을 따라 순서대로 이어진다)를 z 방향으로 평탄화한 것;
  • 협측 법선: 접선에 수직인 수평 방향, 안쪽을 향하면 뒤집는다. 이전 버전이 쓰던 방사 방향(치아 중심 − 메시 중심)은 치아 19/30에서 35°, 치아 31에서 53° 벗어난다. 카메라가 치열궁을 따라 바라보아 점이 렌더링 밖으로 떨어졌다;
  • 조준점: 치아 중심점이 아니라 centroid + b·normal + t·tangent, z += v이며, (b,t,v)는 MG_AIM_OFFSET(model.py:35)에서 읽는다 — 학습 스캔 155개에 대한 치아별 중앙값, 산포 0.02–0.03;
  • 카메라 세 대: 협측 법선, 그리고 Y축 둘레로 ±0.35 rad. 조준점에서 radius 거리에 두고 0.15·radius만큼 낮춘다.

구조적 차이: O/C에서는 카메라 하나하나가 독립 표본이고 시점마다 자체 맵을 만든다. MG에서는 세 시점이 채널로 쌓이고 신경망은 맵 하나를 만들며, 이는 카메라 0의 좌표계로 해석된다(인덱싱 tens_pix_to_face_model[0,0,0,y,x]는 permute(1,0,4,2,3) 이후 첫 번째 카메라를 가리킨다).

이것은 가우시안 회귀라는 의미의 히트맵이 아니라 픽셀 단위 분할이다. 클래스 1이 랜드마크(MG 또는 O)이고, 2와 3은 MB/DB(O 모델) 또는 CB(C 모델)를 담는다 — MODELS_DICT와 dic_label(model.py:51) 참조.

출력 디코딩에서 두 경로가 갈린다(ALI_IOS.py:453).

# MG: argmax on the raw logits
pred_data = torch.argmax(images_pred.detach().cpu().float(), dim=1)...
# O / C: cast to int16 BEFORE the argmax
pred_data = images_pred.detach().cpu().unsqueeze(0).type(torch.int16)
pred_data = torch.argmax(pred_data, dim=2).unsqueeze(2)
확인된 버그

MG 코드의 주석이 두 번째 방식이 왜 틀렸는지 설명한다. 로짓을 정수로 자르면 가까운 클래스들이 합쳐지고, 동점이면 argmax는 인덱스 0(배경)으로 떨어진다. 수정은 MG에만 적용되었다.

4.4 픽셀에서 3D 점으로

  1. index = (pred_data == 1.).nonzero(): 목표 클래스의 픽셀;
  2. tens_pix_to_face[...]: 각 픽셀 아래에 렌더링된 면;
  3. 필터링 — 여기서 차이가 난다:
    • O/C: RemoveExtraFaces는 정점 중 적어도 하나가 해당 치아의 Universal_ID를 가진 면만 남긴다(surface.py:229);
    • MG: 치아별 필터링 없음, face >= 0만 확인. 점막치은 점은 치관이 아니라 잇몸 위에 있으므로 RemoveExtraFaces를 쓰면 모두 제거될 것이다;
  4. 남은 각 면의 정점 3개를 평균;
  5. vtkOctreePointLocator.FindClosestPoint: 평균점을 기존 정점에 스냅 — 곡면 조각의 평균은 표면 아래로 떨어지기 때문이다;
  6. Upscale(pos, mean_arr, scale_factor): 파일의 좌표로 복원.

(환자, 치열궁, 모델)마다 파일 하나: <patient>_<Lower|Upper>_<O|C|MG>_Pred.json, coordinateSystem: "LPS"(io.py:64). 좌표는 입력 메시의 좌표 그대로이며 뒤집기는 없다. "LPS" 표기가 맞는 것은 이 파이프라인의 .vtk 파일이 LPS이기 때문이지, 코드가 확인하기 때문이 아니다.

7. 함정과 취약 지점

  • Focus()에는 안전장치가 없다: 시간 예산도, search_atempt 검사도 없다. CBCT 파이프라인에서 유일하게 끝이 보장되지 않는 루프다.
  • Move()는 경계를 잘못 검사한다: if new_pos.all() > 0 and (...) — .all()은 불리언을 반환하고 이를 0과 비교한다. 이 검사는 "음수 좌표가 없다"가 아니라 "0인 좌표가 없다"를 확인한다(agent.py:193).
  • int16 캐스트를 argmax 전에 하는 코드가 O와 C 모델에는 여전히 남아 있다. MG 코드의 주석이 그것이 왜 틀렸는지 정확히 설명한다.
  • MG가 아닌 경우 get_view_rasterize는 R/T 없이 래스터화한다: renderer.rasterizer(meshes.clone())(agent.py:366)는 바로 위 렌더링에 쓰인 행렬을 넘기지 않으므로, pix_to_face는 이미지를 만든 카메라가 아니라 기본 카메라에서 나온다. MG 경로는 바로 이것을 고치려고 명시적으로 작성되었다("with the SAME R,T so pix_to_face stays aligned", agent.py:267). 이는 원래 upstream 코드이며, O/C에는 끝내 반영되지 않았다.
  • val_pred / post_pred(ALI_IOS.py:447): AsDiscrete(argmax=True, to_onehot=4)가 모든 시점에서 계산되고 한 번도 읽히지 않는다. 치아 하나하나마다 낭비되는 계산이다.
  • MG 이름 충돌. 출력 이름 13개 중 6개는 다른 치아의 학습용 이름이다. LR1MG는 치아 26의 출력 이름이자 치아 25의 학습용 이름이다(model.py:25). 두 규약 사이의 변환은 레이블 하나씩이 아니라 레이블 집합 전체에 대해 결정해야 한다.
  • 위젯의 DICOM 경로는 망가져 있다. Auto_CBCT는 NumberScanDCM도, TestScanDCM도, getTestFileListDCM도 구현하지 않으며, 기본 버전은 None을 반환한다. "DICOM"을 체크하면 nb_patient = None이 되고, 이어서 테스트 파일을 다운로드할 때 TypeError, None으로 나누기가 OnEndProcess에서 일어난다. CLI 자체는 변환할 줄 안다.
  • Agent 매니페스트가 불완전하다. ali_cbct는 위치 인자 10개가 필요한데 6개만 선언하고, ali_ios도 10개 중 6개를 선언하며 teeth_mg를 빠뜨린다(인덱스 4). 그 뒤의 값들이 한 칸씩 밀린다(manifest.yaml:48).
  • temp_fold는 ALI_CBCT가 절대 정리하지 않으며, 재샘플링된 파일이 있으면 그대로 재사용된다. 두 실행 사이의 조용한 캐시다.
  • Auto_IOS.getALIModelList는 비어 있는 추상 메서드인 super().getALIModelList()를 반환한다 → None(IOS.py:172).
  • slicer.modules.ali_ios는 AREG가 slicer.cli.run으로 호출한다(IOSCBCT.py:350). 즉 pytorch3d와 shapeaxi가 설치되지 않은 Slicer의 Python 안에서다. ALI 위젯 자체는 이를 conda run으로만 호출한다. 두 경로는 같은 설치본에서 동시에 동작할 수 없다.
  • SURFACE_LANDMARKS(ALI.py:127)는 R, RIP, OIP를 제공하지만, 이들은 MODELS_DICT에 항목이 없다. 이들만 선택하면 CLI가 "No matching models found."로 실패한다.
  • onPredictButton은 두 IOS 프로세스를 잘못 연결한다: if "CrownSegmentationcli"와 뒤따르는 if "ALI_IOS"는 상호 배타적이지 않고, 그 뒤의 else는 두 번째 if에 붙는다(ALI.py:987). 분할이 필요하면 ALI_IOS는 onProcessUpdate에서 다시 실행되고, 그렇지 않으면 onPredictButton에서 실행된다. 같은 단계에 진입점이 둘이다.
