BatchDentalSeg

Fila que conduz o nnUNetv2_predict sobre um lote de exames de TC/CBCT, com quatro pacotes de pesos intercambiáveis — o DentalSegmentator e suas três variantes — além de todo o trabalho de salvaguardas, restauração da geometria e exportação em torno deles.

Dot 2024 · J Dent BATCHDENTALSEG nnUNetv2_predict sem conda — Python do Slicer + nnunetv2 Bibliografia

Segmentação dentomaxilofacial em lote de exames de TC/CBCT. O módulo não é uma rede: é uma fila e um orquestrador em torno do nnUNetv2_predict, com quatro pacotes de pesos intercambiáveis. Todo o aprendizado acontece fora deste repositório; o que está escrito aqui é a escolha do modelo, as salvaguardas de memória, a restauração da geometria e as exportações.

1. Onde se situa no pipeline

Nenhum outro módulo do repositório chama o BatchDentalSeg, e o BatchDentalSeg não chama nenhum outro módulo do repositório. É uma ferramenta terminal. Ele depende, no entanto, de uma extensão externa do Slicer, NNUNet (SlicerNNUNetLib), da qual usa três classes.

ChamadoOrigemPapel
SlicerNNUNetLib.InstallLogicextensão NNUNetsetupPythonRequirements(): instala o nnunetv2 no Python do Slicer
SlicerNNUNetLib.Parameterextensão NNUNetvalida a árvore de diretórios do modelo e monta a linha de comando
SlicerNNUNetLib.SegmentationLogicextensão NNUNetgrava o volume como NIfTI em uma pasta temporária, executa nnUNetv2_predict como QProcess, recarrega a segmentação
OpenAnatomyExportextensão SlicerOpenAnatomyapenas exportação glTF; instalada na hora se ausente

O módulo é uma variante em lote do DentalSegmentator (extensão gaudot/SlicerDentalSegmentator), da qual reaproveita o widget, os ícones e o mecanismo de download dos pesos. Os contribuidores declarados em BATCHDENTALSEG.py:30 misturam a equipe original (Dot, Gajny, Fenioux, Pelletier) com o acréscimo da UoM (Tulissi).

Tudo roda dentro do Python do Slicer. nnUNetv2_predict é executado como processo filho (QProcess), um exame de cada vez — ao contrário do AMASSS, que chama a API Python do nnU-Net no mesmo processo.

Resources/ML não está listado em MODULE_PYTHON_RESOURCES do CMakeLists.txt: em uma extensão instalada, a pasta é criada inteiramente em tempo de execução. Os arquivos .pth estão no .gitignore.

3. Entradas, percurso das pastas, nomes

3.1 O que é aceito

listVolumes() (Queue.py:28) faz uma varredura não recursiva com glob sobre quatro padrões: *.nii, *.nii.gz, *.gipl, *.gipl.gz. As subpastas não são visitadas, e o NRRD não é reconhecido — formato padrão do Slicer, e um formato que os outros módulos do repositório produzem com frequência.

volumeStem() remove o sufixo composto: case01.nii.gz → case01 (um Path.stem deixaria case01.nii).

3.2 A fila

Uma entrada = um exame, não uma pasta (QueueItem, Queue.py:52): inputPath, outputDir, model, device, status, error, durationSec, autoCrop. Várias pastas com modelos diferentes podem, portanto, ser empilhadas na mesma sessão.

addFolder() pula um exame se <outputDir>/<stem>_Segmentation.nii.gz já existir (a caixa Skip scans already segmented, marcada por padrão) ou se ele já estiver na fila.

Persistência: o estado é regravado após cada exame em <outputDir>/.batchdentalseg_queue.json. Ao recarregar, um exame deixado em running (Slicer encerrado no meio da inferência) é rebobinado para pending e o índice volta para ele.

isChunkBoundary(): a cada chunkSize exames (padrão 5), _coolDown() faz uma limpeza profunda — remove nós órfãos, torch.cuda.empty_cache() + ipc_collect(), gc.collect().

3.3 O que a rede realmente vê

O widget não faz nenhum pré-processamento. SegmentationLogic._prepareInferenceDir() faz um slicer.util.exportNode(volumeNode, <tmp>/input/volume_0000.nii.gz), e todo o pré-processamento é do nnU-Net: transposição conforme transpose_forward, reamostragem para o spacing do plano, CTNormalization (corte nos percentis 0,5% / 99,5% do conjunto de treinamento e depois padronização pela sua média e desvio padrão).

O único pré-processamento escrito neste repositório é o recorte automático (§5.2), e ele é opcional, reservado à nova tentativa após uma falha de memória.

Os três últimos seguem o mesmo padrão: se <basePath>/fold_0/checkpoint_final.pth estiver ausente, três arquivos são baixados (checkpoint_final.pth, dataset.json, plans.json) via slicer.util.downloadFile. Sem checksum, sem versionamento, sem retomada: um download interrompido deixa um checkpoint truncado que o código considerará presente na execução seguinte.

O DentalSegmentator passa por um caminho separado, PythonDependencyChecker: Github().get_repo("gaudot/SlicerDentalSegmentator"), depois o primeiro asset do primeiro release listado, baixado em streaming e descompactado. A URL usada é guardada em Resources/ML/download_info.json, e um release mais recente dispara uma proposta de atualização. O arquivo versionado no repositório aponta para Dataset111_453CT_v100.zip.

4.2 nnU-Net, verificado no código

Sim, é o nnU-Net v2, e não só no nome. A prova está na cadeia de chamadas: Parameter.asArgList() monta literalmente

nnUNetv2_predict -i <tmp>/input -o <tmp>/output
  -d Dataset111_453CT -tr nnUNetTrainer -p nnUNetPlans -c 3d_fullres
  -f 0 -npp 1 -nps 1 -step_size 0.5 -device cuda -chk checkpoint_final.pth --disable_tta

-d, -tr, -p, -c são deduzidos dos nomes das pastas: a pasta pai dá o Dataset…, e o nome da pasta de configuração é separado em __ em (trainer, plan, configuration). Daí a exigência Dataset<id>/<trainer>__<plan>__<conf>/fold_<i>/checkpoint_final.pth.

Parâmetros não expostos ao usuário, valores padrão de SlicerNNUNetLib.Parameter: stepSize = 0.5, disableTta = True (sem aumento por espelhamento no teste), folds = "0" (um único fold, nunca um ensemble), nProcessPreprocessing = nProcessSegmentationExport = 1, forçados a 0 no macOS (o nnU-Net trava na escrita ali por causa do multiprocessing).

O único ajuste que a interface oferece é o dispositivo: cuda / cpu / mps. Se indisponível, apenas uma pergunta é feita para toda a fila (_deviceFallbackAccepted), e no modo Unattended o recurso à CPU é aceito automaticamente.

nnUNet_raw, nnUNet_preprocessed e nnUNet_results apontam todos para a pasta do modelo — três variáveis de ambiente de nível de processo, escritas por SegmentationLogic._startInferenceProcess. Como os.environ é global, duas inferências simultâneas na mesma sessão do Slicer interfeririam uma na outra; aqui a fila é estritamente sequencial, então a questão não se coloca.

4.3 Arquitetura e plano — o que é verificável

Só o Dataset111_453CT (DentalSegmentator) tem seus arquivos JSON no repositório. Resumo do plans.json:

pool_op_kernel_sizes = [1,1,1], 4 x [2,2,2], [2,2,1]   conv_kernel 6 x [3,3,3]

Este plans.json está no formato do nnU-Net anterior à 2.4 (campos planos UNet_class_name / pool_op_kernel_sizes, sem bloco architecture), enquanto os pacotes do AMASSS usam o formato mais novo. Ambos continuam legíveis pelo nnunetv2 atual.

Os planos dos outros três modelos não podem ser determinados a partir do repositório: eles chegam com o download. Tudo o que se sabe sobre eles vem dos dicionários fixados no código do widget (§4.4) e do README.

4.4 Os rótulos produzidos, por modelo

_get_active_label_map() (SegmentationWidget.py:1847) é a tabela de referência: ela decide os valores gravados no NIfTI de saída.

DentalSegmentator e PediatricDentalsegmentator — 5 rótulos idênticos, confirmados pelo dataset.json do pacote 111: 1 Upper Skull (maxila incluída), 2 Mandible, 3 Upper Teeth, 4 Lower Teeth, 5 Mandibular canal. O que os distingue, portanto, não é a saída, mas os dados de treinamento: dentição permanente (453CT, 7 instituições) versus dentição mista (380CT). O código os trata de forma rigorosamente idêntica — mesma tabela de rótulos, mesmas cores, mesmo pós-processamento; só _modelBasePath difere.

NasoMaxillaDentSeg — 6 rótulos, a maxila separada do crânio: 1 Upper Skull, 2 Mandible, 3 Maxilla, 4 Upper Teeth, 5 Lower Teeth, 6 Mandibular canal.

UniversalLabDentalsegmentator — 55 rótulos: os 32 dentes permanentes numerados um a um (1 = 3o molar superior direito → 32 = 3o molar inferior direito, percorrendo a arcada superior e depois a inferior), depois 20 dentes decíduos (33 → 52), depois Mandible = 53, Maxilla = 54, Mandibular canal = 55. Nenhum "Upper Skull": este modelo não segmenta a calota craniana, ao contrário do que mostra sua descrição na interface e do que diz o README.

Armadilha

A descrição exibida na interface para UniversalLabDentalsegmentator e o README do repositório anunciam uma segmentação da calota craniana. O modelo real não tem rótulo "Upper Skull": ele apenas numera os dentes, mais mandíbula/maxila/canal.

Os valores são definidos em cada segmento por uma tag LabelValue (_segmentLabelValue), que tem prioridade sobre o nome quando presente.

5. O núcleo não aprendido

5.1 Reconstrução do mapa de rótulos e restauração da geometria

_buildLabelArray() (SegmentationWidget.py:1912):

um único ExportSegmentsToLabelmapNode, com a lista explícita de segmentId (o que fixa a correspondência "valor exportado i+1 ↔ segIds[i]"), depois uma LUT numpy que remapeia para os valores oficiais em uma passagem (lut[exported]). A versão anterior rasterizava a extensão completa do volume uma vez por segmento: 55 rasterizações de uma CBCT de arcada completa para o UniversalLab.

5.2 Recorte automático (nova tentativa após falha de memória)

Opcional, disparado por Retry failed após confirmação explícita. _applyAutoCrop() (SegmentationWidget.py:1017):

  • limiar ar/tecido tolerante à escala: se array.min() < −800, estamos em unidades Hounsfield e o limiar é −500; caso contrário min + 0.15 × (p99.5 − min);
  • caixa delimitadora dos voxels acima do limiar, ampliada de _CROP_MARGIN_MM = 15.0 mm convertidos em voxels por eixo;
  • se mais de _CROP_MIN_GAIN = 0.85 dos voxels forem mantidos, o recorte é abandonado: ganhar menos de 15% não vale o risco;
  • o subvolume mantém seu espaçamento e seus eixos, só a origem se desloca (ijkToRas.MultiplyPoint([i0,j0,k0,1])). Nada é interpolado.

_restoreCropToOriginalGrid() recoloca o mapa de rótulos em um array do tamanho original por um simples deslocamento de índices: a saída está, portanto, sempre na grade do exame tal como adquirido.

5.3 Proteção de memória — três linhas de defesa

O comentário do código dá o caso real: um exame ocupou 114 GB em uma máquina de 125 GB, foi encerrado pelo OOM killer e deixou seus workers de multiprocessing vivos, segurando a memória.

a) Estimativa a priori, _estimatePeakRamGb() (SegmentationWidget.py:1161). Como o volume físico do campo de visão independe do espaçamento, o número de voxels reamostrados é igual a fovMm3 / targetVoxelMm3. O pico é atingido em convert_predicted_logits_to_segmentation_with_correct_shape, onde, por classe, coexistem: o acumulador da janela deslizante (torch.half na grade reamostrada, 2 bytes), sua cópia float64 (data = data.astype(float) sobre o array 4D inteiro de uma vez, 8 bytes) e reshaped_final (torch.half na grade original, 2 bytes). Daí logitsGb = (10 × C × Vresampled + 2 × C × Voriginal) / 2³⁰, mais 8 × (Voriginal + Vresampled) para os transientes float64 de skimage.resize, mais _RAM_FIXED_OVERHEAD_GB = 4.0 (torch, pesos, workers). O spacing e o número de rótulos são lidos da mesma pasta de configuração, para não cruzar o espaçamento de um modelo com o número de rótulos de outro.

Orçamento = free RAM × ramLimitSpinBox (padrão 85%). Acima disso, o exame é marcado como failed com o motivo, sem nunca iniciar o nnU-Net.

b) Monitoramento durante a execução: _onMemCheck faz uma amostragem a cada _RAM_SAMPLE_MS = 3000 ms; são necessários _RAM_CONSECUTIVE_HITS = 2 excessos consecutivos para encerrar (um pico passageiro não deve condenar um exame bom).

c) Recuperação da memória: _killInferenceTree() encerra a árvore inteira — QProcess.kill() só atinge o filho direto, mas o nnU-Net faz multiprocessing. _reclaimStrayProcesses() varre os processos cuja linha de comando contém nnunetv2_predict, nnunetv2/inference ou nnunet e que não pertencem mais a ninguém. O botão Free memory faz isso à mão.

5.4 Detecção de término alternativa

_checkInferenceCompletionFallback() (SegmentationWidget.py:2514): quando a linha "done with volume" aparece na saída do nnU-Net, um temporizador verifica o tamanho do arquivo de saída a cada 1,5 s; duas leituras iguais consecutivas ⇒ finalização forçada, mesmo que o QProcess nunca tenha emitido o sinal finished. Desiste após 40 tentativas (60 s).

Salvaguarda adicional: um watchdog por exame (itemTimeoutSpinBox, padrão 60 min) marca o exame como falho e passa ao seguinte. _finishCurrentItem é o único ponto de saída, protegido por _itemFinalized contra avanço duplo.

5.5 Correção de espelhamento (somente UniversalLab)

onResolveMirroring() (SegmentationWidget.py:1308), um botão visível apenas para o UniversalLab. A rede confunde regularmente esquerda e direita; a correção é puramente geométrica:

  1. reconstrução do mapa de rótulos oficial (§5.1), depois a coordenada RAS R de cada voxel de primeiro plano em numpy (m00·x + m01·y + m02·z + m03) — a versão anterior chamava vtkMatrix4x4.MultiplyPoint uma vez por voxel e por rótulo;
  2. plano sagital = média dos centroides R dos quatro incisivos centrais (rótulos 8, 9, 24, 25); se um estiver ausente, a correção é recusada;
  3. para cada rótulo lateralizado, os voxels do lado errado do plano recebem o valor do rótulo simétrico (uma tabela construída substituindo left ↔ right no nome); {53, 54, 55} são protegidos.

O resultado vai para um novo nó <name>_Mirrored, o original é mantido.

5.6 Pós-processamento ausente

Armadilha

_postProcessSegments() apenas registra duas linhas no log; _keepLargestIsland() e _removeSmallIsland() (que usaria _minimumIslandSize_mm3 = 60) nunca são chamados em lugar nenhum — código morto herdado do DentalSegmentator original. Nenhuma limpeza morfológica é, portanto, aplicada: o que sai é a saída bruta do nnU-Net, com seu próprio pós-processamento interno, se presente no pacote.

6. Saídas

onInferenceFinished grava sempre, independentemente dos formatos marcados, <outputFolder>/<stem>_Segmentation.nii.gz: um mapa de rótulos com os valores de _get_active_label_map, na geometria (espaçamento, origem, IJKToRAS) do volume original — sem recorte, se houve recorte. É o arquivo que expectedOutputPath() procura para decidir que um exame já foi processado.

Formatos adicionais, caixas de seleção, todos gravados na mesma pasta:

FormatoFunçãoNomeDetalhes

Os nomes dos arquivos de malha derivam do nome do nó de segmentação, <stem>_Segmentation, não do nome do exame: os nomes dos segmentos são higienizados por re.sub(r"[^0-9A-Za-z_-]+", "_", ...).

Uma falha na exportação de malha não faz o exame falhar: o NIfTI já está gravado, o exame é marcado como done com um export warning.

Verificado — corrigido no código

Um bug que foi corrigido, documentado no código de _exportMergedVTK: vtkDiscreteMarchingCubes.SetValue recebe um índice de contorno, não um valor de rótulo. Passar o rótulo como índice deixava o índice 0 com valor de contorno 0.0, de modo que o fundo era contornado, suavizado e tinha normais calculadas antes de ser descartado.

8. Ambiente

Instalado uma vez por sessão, no primeiro Apply, por _runSetupThenStartQueue() (SegmentationWidget.py:1651):

  1. pip install light-the-torch, depois python -m light_the_torch install torch torchvision — o ltt escolhe o wheel CUDA correspondente ao driver detectado, nenhuma versão é fixada;
  2. pip install numexpr>=2.10.2;
  3. pip install numpy<2.0 numexpr>=2.10.2 psutil, via PipRunner, um QProcess que devolve o controle à interface;
  4. SlicerNNUNetLib.InstallLogic().setupPythonRequirements(): nnunetv2, fora deste repositório;
  5. PythonDependencyChecker.downloadWeightsIfNeeded(): pesos do DentalSegmentator apenas.

numpy<2.0 pelo mesmo motivo que no AMASSS: os wheels atuais de torch são compilados contra numpy 1.x.

A extensão NNUNet precisa ser instalada manualmente: sua ausência é detectada (import SlicerNNUNetLib) e produz uma mensagem pedindo para instalá-la e reiniciar. O SlicerOpenAnatomy, por outro lado, instala-se sozinho na primeira exportação glTF.

Sem ambiente conda, sem WSL. A GPU é opcional (cpu, mps disponíveis), ao custo de "cerca de uma hora por exame" segundo a mensagem de fallback.

9. Armadilhas e pontos frágeis

Bug confirmado — NasoMaxillaDentSeg

Os nomes dos segmentos e a tabela de rótulos divergem para o NasoMaxillaDentSeg. _get_active_label_map dá Maxilla = 3, Upper Teeth = 4, Lower Teeth = 5, Mandibular canal = 6, enquanto _updateSegmentationDisplay (SegmentationWidget.py:2385) renomeia Segment_1..6 com a lista ["Upper Skull", "Mandible", "Upper Teeth", "Lower Teeth", "Mandibular canal", "Maxilla "].

O primeiro efeito é visível na tela, antes de qualquer questão de exportação: a lista não está na ordem da tabela, então os quatro últimos segmentos recebem o nome errado, a cor errada e a opacidade errada.

SegmentoEstrutura realNome exibido
Segment_3Maxila"Upper Teeth"
Segment_4Dentes superiores"Lower Teeth"
Segment_5Dentes inferiores"Mandibular canal"
Segment_6Canal mandibular"Maxilla" (com um espaço no final)

A correção é reordenar a lista — e as listas colors e opacities que a acompanham — para corresponder a _get_active_label_map, em vez de simplesmente remover o espaço.

Mas a renomeação acontece antes de as tags LabelValue serem definidas, e _segmentLabelValue então recorre ao nome: Segment_3, que na verdade tem o rótulo 3 (maxila), é renomeado "Upper Teeth" e exportado com o valor 4. Pior, "Maxilla " tem um espaço no final: a busca na tabela falha, Segment_6 (o canal mandibular) é registrado como "unexpected segment" e perdido do NIfTI. As duas listas, no entanto, correspondem perfeitamente para os outros três modelos.

  • Os quatro ramos de onApplyClickedForVolume são copiados e colados: o ramo UniversalLab ainda chama sua variável de pediatricCheckpoint e registra "Downloading pediatricdentalseg model…". Cosmético, mas enganoso ao ler os logs.
Armadilha

Baixar os pesos do DentalSegmentator apaga os outros três modelos: downloadWeights() faz shutil.rmtree(self.destWeightFolder) em Resources/ML, que também contém Dataset001_380CT, Dataset001_max4 e Dataset002_380CT. E areWeightsMissing() testa rglob("dataset.json") em qualquer lugar sob Resources/ML: se só o modelo pediátrico estiver presente, o verificador acredita que o DentalSegmentator está instalado.

Armadilha

Resolução frágil do release: assets[0] entre todos os assets de todos os releases, via um cliente GitHub não autenticado (60 requisições/h por IP). Um asset adicionado no topo do release mais recente muda o modelo baixado. E nenhuma verificação de integridade nos três checkpoints baixados um a um: um arquivo truncado é indistinguível de um completo.

  • O NRRD não é reconhecido e as subpastas não são percorridas (listVolumes), enquanto os outros módulos do repositório produzem facilmente NRRD e árvores de pastas. Colisão de nomes é possível: dois exames de pastas diferentes com o mesmo nome base sobrescrevem o mesmo <stem>_Segmentation.nii.gz.
  • Um único fold, nunca um ensemble (folds="0"): um pacote que trouxesse fold_1..4 os veria ignorados.
  • os.environ['nnUNet_results'] é reescrito a cada exame por SegmentationLogic: inofensivo aqui (fila sequencial), perigoso se outra inferência nnU-Net rodar na mesma sessão do Slicer.
  • Código morto: _saveSegmentationAsNifti, _postProcessSegments, _keepLargestIsland, _removeSmallIsland, onExportClicked (o botão correspondente não está ligado ao layout em lote).
Armadilha

Resources/ML não é instalado pelo CMake: em uma extensão empacotada, os dataset.json / plans.json do repositório não estão presentes, e a estimativa de memória a priori (§5.3) retorna None enquanto os pesos não forem baixados — ela então deixa o exame passar.

10. Literatura

O DentalSegmentator está publicado:

Dot G., Chaurasia A., Dubois G., Savoldelli C., Haghighat S., Azimian S., Rahbar Taramsari A., Sivaramakrishnan G., Issa J., Dubey A., Schouman T., Gajny L. DentalSegmentator: robust open source deep learning-based CT and CBCT image segmentation. Journal of Dentistry 147:105130, 2024. doi:10.1016/j.jdent.2024.105130 — PMID 38878813

nnU-Net v2 (v2.2 segundo a ficha Zenodo dos pesos), 470 exames de TC e CBCT de 7 instituições para o treinamento, 5 estruturas, testado em hold-out com 256 exames (133 internos, 123 externos): DSC 92,2 ± 6,3% interno, 94,2 ± 7,4% externo. O dataset.json fornecido aqui anuncia numTraining = 453, coerente com o corpus descrito.

Verificado

Neste modelo, código e artigo concordam. Os pesos também estão publicados sob CC-BY-4.0 no Zenodo (DOI conceito 10.5281/zenodo.10829674) — mas este módulo os busca nos releases do GitHub, não no Zenodo.

A base metodológica:

Isensee F., Jaeger P.F., Kohl S.A.A., Petersen J., Maier-Hein K.H. nnU-Net: a self-configuring method for deep learning-based biomedical image segmentation. Nature Methods 18(2):203-211, 2021. doi:10.1038/s41592-020-01008-z

As três variantes não estão ligadas a nenhuma publicação no repositório. O README do repositório anuncia 513 exames CBCT em dentição mista para o PediatricDentalSegmentator e o UniversalLabDentalSegmentator, e 135 exames para o NasoMaxillaDentalSegmentator, sem referência e sem conjunto de teste. Esses números não podem ser verificados em nenhum lugar do código: os arquivos dataset.json correspondentes só chegam com o download dos pesos.
