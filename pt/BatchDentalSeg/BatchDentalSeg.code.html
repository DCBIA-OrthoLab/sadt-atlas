BatchDentalSeg, legacy: o código

Para desenvolvedores: o que o módulo Slicer legacy faz no código, com referências file:line, assinaturas, tabelas e armadilhas. A explicação legível do mesmo pipeline, com a matemática, está na página do atlas. Fila que conduz o nnUNetv2_predict sobre um lote de scans de CT/CBCT, com quatro pacotes de pesos intercambiáveis, o DentalSegmentator e suas três variantes, além de todo o trabalho de proteção, restauração da geometria e exportação em volta deles.

Código Atlas (explicação) Dot 2024 · J Dent BATCHDENTALSEG nnUNetv2_predict sem conda: Python do Slicer + nnunetv2 VISOR Bibliografia

Segmentação dentomaxilofacial em lote de scans de CT/CBCT. O módulo não é uma rede: é uma fila e um orquestrador em torno do nnUNetv2_predict, com quatro pacotes de pesos intercambiáveis. Todo o aprendizado acontece fora deste repositório; o que está escrito aqui é a escolha do modelo, as proteções de memória, a restauração da geometria e as exportações.

Duas bases de código

Tudo o que está numerado abaixo descreve o módulo Slicer legacy (SlicerAutomatedDentalTools em 3c67957, 2026-10-26). O port VISOR, que executa a mesma ferramenta em um servidor, é descrito em sua própria página, BatchDentalSeg no VISOR.

1. Onde ele fica no pipeline

Nenhum outro módulo do repositório chama o BatchDentalSeg, e o BatchDentalSeg não chama nenhum outro módulo do repositório. É uma ferramenta terminal. Ele depende, porém, de uma extensão externa do Slicer, NNUNet (SlicerNNUNetLib), da qual usa três classes.

ChamadoOrigemPapel
SlicerNNUNetLib.InstallLogicExtensão NNUNetsetupPythonRequirements(): instala o nnunetv2 no Python do Slicer
SlicerNNUNetLib.ParameterExtensão NNUNetvalida a árvore de diretórios do modelo e monta a linha de comando
SlicerNNUNetLib.SegmentationLogicExtensão NNUNetgrava o volume como NIfTI em uma pasta temporária, lança o nnUNetv2_predict como um QProcess, recarrega a segmentação

O módulo é uma variante em lote do DentalSegmentator (extensão gaudot/SlicerDentalSegmentator), da qual reaproveita o widget, os ícones e o mecanismo de download dos pesos. Os colaboradores declarados em BATCHDENTALSEG.py:35-41 misturam a equipe original (Dot, Gajny, Fenioux, Pelletier) com o acréscimo da UoM (Tulissi).

3.1 O que é aceito

3.2 A fila

Uma entrada = um scan, e não uma pasta (QueueItem, Queue.py:52): inputPath, outputDir, model, device, status, error, durationSec, autoCrop. Várias pastas com modelos diferentes podem, portanto, ser empilhadas na mesma sessão.

addFolder() ignora um scan se <outputDir>/<stem>_Segmentation.nii.gz já existe (a caixa Skip scans already segmented, marcada por padrão) ou se ele já está na fila.

Persistência: o estado é regravado após cada scan em <outputDir>/.batchdentalseg_queue.json. Ao recarregar, um scan deixado em running (Slicer encerrado no meio da inferência) é rebobinado para pending e o índice volta a ele.

isChunkBoundary(): a cada chunkSize scans (padrão 5), _coolDown() faz uma limpeza profunda, remove nós órfãos, torch.cuda.empty_cache() + ipc_collect(), gc.collect().

3.3 O que a rede realmente vê

O widget não faz nenhum pré-processamento. SegmentationLogic._prepareInferenceDir() executa um slicer.util.exportNode(volumeNode, <tmp>/input/volume_0000.nii.gz), e todo o pré-processamento é do nnU-Net, nesta ordem (nnunetv2 2.8.1, preprocessing/preprocessors/default_preprocessor.py, lido no ambiente do VISOR; a versão que uma instalação legacy executa não está registrada): transposição conforme transpose_forward (:56), recorte para a região não nula (:65), normalização (:82, comentada como DEVE vir antes da reamostragem), depois reamostragem para o spacing do plano (:88). CTNormalization é a definição padrão do nnU-Net (preprocessing/normalization/default_normalization_schemes.py:58-72): limitar aos percentis 0,5% / 99,5% do conjunto de treino do plano, subtrair a média deles, dividir por max(std, 1e-8). O plano lido aqui é apenas o do DentalSegmentator (plans.json: p0.5 −110, p99.5 3067, média 1274, std 558); para os outros três modelos, supõe-se, sem verificar, que o mesmo esquema se aplica (§4.3).

O único pré-processamento escrito neste repositório é o recorte automático (§5.2), e ele é opcional, reservado para a repetição após uma falha de memória.

4.2 nnU-Net, verificado no código

Sim, este é o nnU-Net v2, e não apenas no nome. A prova está na cadeia de chamadas: Parameter.asArgList() monta literalmente

nnUNetv2_predict -i <tmp>/input -o <tmp>/output
  -d Dataset111_453CT -tr nnUNetTrainer -p nnUNetPlans -c 3d_fullres
  -f 0 -npp 1 -nps 1 -step_size 0.5 -device cuda -chk checkpoint_final.pth --disable_tta

-d, -tr, -p, -c são deduzidos dos nomes de pastas: a pasta pai dá o Dataset…, e o nome da pasta de configuração é dividido em __ em (trainer, plan, configuration). Daí a exigência Dataset<id>/<trainer>__<plan>__<conf>/fold_<i>/checkpoint_final.pth.

Parâmetros não expostos ao usuário, valores padrão de SlicerNNUNetLib.Parameter: stepSize = 0.5, disableTta = True (sem aumento por espelhamento no momento do teste), folds = "0" (um único fold, nunca um ensemble), nProcessPreprocessing = nProcessSegmentationExport = 1, forçados em 0 no macOS (o nnU-Net trava na escrita ali por causa do multiprocessamento).

A colocação dos patches e os pesos gaussianos são do nnU-Net, e não do módulo: o passo é no máximo step_size vezes o patch e é reduzido para que os patches terminem na borda da imagem, daí uma sobreposição de pelo menos metade para 0,5 (nnunetv2 2.8.1, inference/sliding_window_prediction.py:30-54); os pesos são gaussianos, com um desvio de um oitavo do patch (:11-16, chamado em inference/predict_from_raw_data.py:626). O rótulo de um voxel é o argmax sobre os rótulos (utilities/label_handling/label_handling.py:178), que devolve o primeiro máximo em caso de empate (comportamento documentado do NumPy e do PyTorch).

A única configuração que a interface oferece é o dispositivo: cuda / cpu / mps. Se ele não estiver disponível, só uma pergunta é feita para toda a fila (_deviceFallbackAccepted), e no modo Unattended o recurso à CPU é aceito automaticamente.

nnUNet_raw, nnUNet_preprocessed e nnUNet_results apontam todos para a pasta do modelo: três variáveis de ambiente de nível de processo, gravadas por SegmentationLogic._startInferenceProcess. Como os.environ é global, duas inferências simultâneas na mesma sessão do Slicer se atropelariam; aqui a fila é estritamente sequencial, então o problema não surge.

4.4 Os rótulos produzidos, por modelo

_get_active_label_map() (SegmentationWidget.py:1945) é a tabela de referência: ela decide os valores gravados no NIfTI de saída.

DentalSegmentator e PediatricDentalsegmentator, 5 rótulos idênticos, confirmados pelo dataset.json do pacote 111: 1 Upper Skull (maxila incluída), 2 Mandible, 3 Upper Teeth, 4 Lower Teeth, 5 Mandibular canal. O que os distingue, portanto, não é a saída, e sim os dados de treino: dentição permanente (453CT, 7 instituições) contra dentição mista (380CT). O código os trata de forma rigorosamente idêntica: mesma tabela de rótulos, mesmas cores, mesmo pós-processamento; só _modelBasePath difere.

NasoMaxillaDentSeg, 6 rótulos, a maxila separada do crânio: 1 Upper Skull, 2 Mandible, 3 Maxilla, 4 Upper Teeth, 5 Lower Teeth, 6 Mandibular canal.

UniversalLabDentalsegmentator, 55 rótulos: os 32 dentes permanentes numerados um a um (1 = 3º molar superior direito → 32 = 3º molar inferior direito, percorrendo a arcada superior e depois a inferior), depois 20 dentes decíduos (33 → 52), depois Mandible = 53, Maxilla = 54, Mandibular canal = 55. Sem "Upper Skull": este modelo não segmenta a calota craniana, ao contrário do que mostra a descrição de sua interface e do que diz o README. A numeração não é arbitrária: rótulo por rótulo, os valores 1–32 são exatamente o Universal Numbering System (1 = terceiro molar superior direito … 32 = terceiro molar inferior direito) e 33–52 são suas letras A–T para os dentes decíduos, de modo que o equivalente FDI de um rótulo é fixo; a figura abaixo mostra os dois.

Armadilha (o fato sobre o modelo vale no VISOR, o texto da interface não)

A descrição exibida na interface para UniversalLabDentalsegmentator e o README do repositório anunciam uma segmentação da calota craniana. O modelo real não tem rótulo "Upper Skull": ele só numera os dentes, além de mandíbula/maxila/canal.

Legacy (3c67957): a descrição diz "Segments: Upper Skull, Mandibular Canal, All teeth" (SegmentationWidget.py:68-72), e a tabela de rótulos não tem Upper Skull (SegmentationWidget.py:1949-1974). VISOR: a descrição do modelo foi corrigida ("Every tooth labelled individually in Universal numbering, deciduous teeth included, plus Mandible, Maxilla and Mandibular canal", SADT-VISOR sadt_batchdentalseg/catalogs.py:145-150) e a tabela de 55 rótulos também não tem Upper Skull (catalogs.py:47-103). O README do cliente Slicer ainda repete o erro (AutomatedDentalToolsRemote README.md:865-867).

Os valores são definidos em cada segmento por uma tag LabelValue (_segmentLabelValue), que tem prioridade sobre o nome quando presente.

5.2 Recorte automático (repetição após falha de memória)

Opcional, disparado por Retry failed após confirmação explícita. _applyAutoCrop() (SegmentationWidget.py:1029):

  • limiar ar/tecido tolerante à escala: se array.min() < −800, estamos em unidades Hounsfield e o limiar é −500; caso contrário, min + 0.15 × (p99.5 − min);
  • caixa delimitadora dos voxels acima do limiar, expandida em _CROP_MARGIN_MM = 15.0 mm convertidos em voxels por eixo;
  • se mais de _CROP_MIN_GAIN = 0.85 dos voxels forem mantidos, o recorte é abandonado: ganhar menos de 15% não compensa o risco;
  • o subvolume mantém seu espaçamento e seus eixos, só a origem se move (ijkToRas.MultiplyPoint([i0,j0,k0,1])). Nada é interpolado.

_restoreCropToOriginalGrid() cola o mapa de rótulos de volta em um array do tamanho original por um simples deslocamento de índice: a saída fica, portanto, sempre na grade do scan tal como adquirido.

Explicação em linguagem simples e matemática: página do atlas.

5.3 Proteção de memória: três linhas de defesa

O comentário do código dá o caso real: um scan ocupou 114 GB em uma máquina de 125 GB, foi morto pelo OOM killer e deixou seus workers de multiprocessamento vivos, segurando a memória.

a) Estimativa a priori, _estimatePeakRamGb() (SegmentationWidget.py:1173). Como o volume físico do campo de visão independe do espaçamento, o número de voxels reamostrados é igual a fovMm3 / targetVoxelMm3. O pico é atingido em convert_predicted_logits_to_segmentation_with_correct_shape, onde, por classe, coexistem: o acumulador da janela deslizante (torch.half na grade reamostrada, 2 bytes), sua cópia float64 (data = data.astype(float) sobre todo o array 4D de uma vez, 8 bytes) e reshaped_final (torch.half na grade original, 2 bytes). Daí logitsGb = (10 × C × Vresampled + 2 × C × Voriginal) / 2³⁰, mais 8 × (Voriginal + Vresampled) para os transientes float64 do skimage.resize, mais _RAM_FIXED_OVERHEAD_GB = 4.0 (torch, pesos, workers). O spacing e o número de rótulos são lidos da mesma pasta de configuração, para não cruzar o espaçamento de um modelo com o número de rótulos de outro.

Orçamento = free RAM × ramLimitSpinBox (padrão 85%). Acima dele, o scan é marcado failed com o motivo, sem nunca iniciar o nnU-Net, a menos que a caixa Skip scans too large for the free RAM (ramPreflightCheckBox, marcada por padrão, SegmentationWidget.py:446-447) seja desmarcada: a estimativa é então apenas registrada em log (SegmentationWidget.py:1248-1253). O orçamento é aplicado à memória disponível naquele momento (vm.available, SegmentationWidget.py:1243-1244), embora o spin box seja rotulado “% of system RAM”.

b) Monitoramento durante a execução: _onMemCheck amostra a cada _RAM_SAMPLE_MS = 3000 ms; são necessários _RAM_CONSECUTIVE_HITS = 2 excessos consecutivos para encerrar (um pico passageiro não deve condenar um bom scan).

c) Recuperação de memória: _killInferenceTree() encerra a árvore inteira, pois QProcess.kill() só alcança o filho direto, e o nnU-Net faz multiprocessamento. _reclaimStrayProcesses() varre os processos cuja linha de comando contém nnunetv2_predict, nnunetv2/inference ou nnunet e que não pertencem mais a ninguém. O botão Free memory faz isso manualmente.

5.4 Detecção de conclusão de reserva

_checkInferenceCompletionFallback() (SegmentationWidget.py:2611): quando a linha "done with volume" aparece na saída do nnU-Net, um temporizador verifica o tamanho do arquivo de saída a cada 1,5 s; duas leituras consecutivas iguais ⇒ finalização forçada, mesmo que a notificação do QProcess (finished) nunca tenha chegado. Desiste após 40 tentativas (60 s).

Proteção adicional: um watchdog por scan (itemTimeoutSpinBox, padrão 60 min) marca o scan como falho e passa ao seguinte. _finishCurrentItem é o único ponto de saída, protegido por _itemFinalized contra avanço duplo.

Explicação em linguagem simples e matemática: página do atlas.

5.5 Correção de espelhamento (somente UniversalLab)

onResolveMirroring() (SegmentationWidget.py:1321), um botão visível apenas para o UniversalLab. A rede confunde esquerda e direita com regularidade; a correção é puramente geométrica:

  1. reconstrução do mapa de rótulos oficial (§5.1), depois a coordenada RAS R de cada voxel de primeiro plano em numpy (m00·x + m01·y + m02·z + m03): a versão anterior chamava vtkMatrix4x4.MultiplyPoint uma vez por voxel e por rótulo;
  2. plano sagital = média dos centroides R dos quatro incisivos centrais (rótulos 8, 9, 24, 25); se um estiver ausente, a correção é recusada;
  3. para cada rótulo lateralizado, os voxels do lado errado do plano recebem o valor do rótulo simétrico (uma tabela construída substituindo left ↔ right no nome); {53, 54, 55} são protegidos.

O resultado vai para um novo nó <name>_Mirrored, e o original é mantido.

5.6 Pós-processamento ausente

Armadilha (o código morto é somente legado; a ausência de limpeza vale também no VISOR)

_postProcessSegments() apenas registra duas linhas em log (SegmentationWidget.py:2526-2528); _keepLargestIsland() e _removeSmallIsland() (que usariam _minimumIslandSize_mm3 = 60) nunca são chamadas em lugar nenhum: código morto herdado do DentalSegmentator original. 6. Saídas

onInferenceFinished sempre grava, independentemente dos formatos marcados, <outputFolder>/<stem>_Segmentation.nii.gz: um mapa de rótulos com os valores de _get_active_label_map, na geometria (espaçamento, origem, IJKToRAS) do volume original, sem recorte se um recorte ocorreu. É o arquivo que expectedOutputPath() procura para decidir que um scan já foi processado.

Os nomes dos arquivos de malha derivam do nome do nó de segmentação, <stem>_Segmentation, e não do nome do scan: os nomes dos segmentos são sanitizados por re.sub(r"[^0-9A-Za-z_-]+", "_", ...).

Uma falha de exportação de malha não faz o scan falhar: o NIfTI já foi gravado, e o scan é marcado done com um export warning.

Verificado: corrigido no código (somente legado)

Um bug que foi corrigido, documentado no código de _exportMergedVTK (SegmentationWidget.py:2823-2832): vtkDiscreteMarchingCubes.SetValue recebe um índice de contorno, e não um valor de rótulo. Passar o rótulo como índice deixava o índice 0 no valor de contorno 0.0, de modo que o fundo era contornado, suavizado e tinha as normais calculadas antes de ser descartado.

Legacy (3c67957); ausente no VISOR: o VISOR constrói uma superfície por rótulo a partir de uma máscara binária (GenerateValues(1, 1, 1), SADT-VISOR sadt_batchdentalseg/mesh_export.py:78-80) e as mescla com vtkAppendPolyData (mesh_export.py:205-207, 226-235).

8. Ambiente

Instalado uma vez por sessão, no primeiro Apply, por _runSetupThenStartQueue() (SegmentationWidget.py:1749):

  1. pip install light-the-torch, depois python -m light_the_torch install torch torchvision: o ltt escolhe a wheel CUDA correspondente ao driver detectado, nenhuma versão é fixada;
  2. pip install numexpr>=2.10.2;
  3. pip install numpy<2.0 numexpr>=2.10.2 psutil, via PipRunner, um QProcess que devolve o controle à interface;
  4. SlicerNNUNetLib.InstallLogic().setupPythonRequirements(): nnunetv2, fora deste repositório;
  5. PythonDependencyChecker.downloadWeightsIfNeeded(): somente os pesos do DentalSegmentator.

numpy<2.0 pela mesma razão do AMASSS: as wheels atuais do torch são compiladas contra o numpy 1.x.

A extensão NNUNet deve ser instalada manualmente: sua ausência é detectada (import SlicerNNUNetLib) e produz uma mensagem pedindo para instalá-la e reiniciar. O SlicerOpenAnatomy, por outro lado, se instala sozinho na primeira exportação glTF.

Sem ambiente conda, sem WSL. A GPU é opcional (cpu, mps disponíveis), ao custo de "cerca de uma hora por scan" segundo a mensagem de recurso alternativo.

Explicação em linguagem simples e matemática: página do atlas.

9. Armadilhas e pontos frágeis

Bug confirmado: NasoMaxillaDentSeg (somente legado)

Legacy (3c67957); ausente no VISOR. O VISOR não renomeia nenhum segmento: a tabela é Upper Skull 1, Mandible 2, Maxilla 3, Upper Teeth 4, Lower Teeth 5, Mandibular canal 6 (SADT-VISOR sadt_batchdentalseg/catalogs.py:35-42) e é ela que nomeia os arquivos por rótulo (pipeline.py:199-206). Segue a análise do legacy.

Os nomes dos segmentos e a tabela de rótulos divergem para o NasoMaxillaDentSeg. _get_active_label_map (SegmentationWidget.py:1977-1987) dá Maxilla = 3, Upper Teeth = 4, Lower Teeth = 5, Mandibular canal = 6, enquanto _updateSegmentationDisplay (SegmentationWidget.py:2278, lista em SegmentationWidget.py:2482) renomeia Segment_1..6 usando a lista ["Upper Skull", "Mandible", "Upper Teeth", "Lower Teeth", "Mandibular canal", "Maxilla "].

O primeiro efeito é visível na tela, antes de qualquer questão de exportação: a lista não está na ordem da tabela, de modo que os quatro últimos segmentos recebem o nome errado, a cor errada e a opacidade errada.

SegmentoEstrutura realNome exibido
Segment_3Maxila"Upper Teeth"
Segment_4Upper Teeth"Lower Teeth"
Segment_5Lower Teeth"Mandibular canal"
Segment_6Mandibular canal"Maxilla" (com um espaço no final)

A correção é reordenar a lista, e as listas colors e opacities que a acompanham, para coincidir com _get_active_label_map, e não apenas remover o espaço.

Mas a renomeação acontece antes de as tags LabelValue serem definidas, e _segmentLabelValue recorre então ao nome: Segment_3, que na verdade carrega o rótulo 3 (maxila), é renomeado "Upper Teeth" e exportado com o valor 4. Pior, "Maxilla " tem um espaço no final: a busca na tabela falha, Segment_6 (o canal mandibular) é registrado como "unexpected segment" e perdido do NIfTI. As duas listas, porém, correspondem perfeitamente para os outros três modelos.

  • Os quatro ramos de onApplyClickedForVolume foram copiados e colados: o ramo do UniversalLab ainda chama sua variável de pediatricCheckpoint e registra "Downloading pediatricdentalseg model…". Cosmético, mas enganoso ao ler os logs.
Armadilha (somente legado)

Baixar os pesos do DentalSegmentator apaga os outros três modelos: downloadWeights() executa shutil.rmtree(self.destWeightFolder) sobre Resources/ML (PythonDependencyChecker.py:158-160), que também guarda Dataset001_380CT, Dataset001_max4 e Dataset002_380CT. E getDatasetPath() procura rglob("dataset.json") em qualquer lugar de Resources/ML (PythonDependencyChecker.py:123-127), e areWeightsMissing() verifica então fold_*/*.pth ao lado do primeiro encontrado (PythonDependencyChecker.py:78-96): se só o modelo pediátrico estiver presente, o verificador acredita que o DentalSegmentator está instalado.

Legacy (3c67957); ausente no VISOR: nada é baixado durante uma execução (SADT-VISOR sadt_batchdentalseg/pipeline.py:15-17); cada pacote tem sua própria pasta (dest) no manifesto do servidor (VISOR-serve scripts/data-manifest.yml:542-586), e um pacote só é aceito se contiver dataset.json, plans.json e fold_0/checkpoint_final.pth (nnunet_runner.py:57-73).

Armadilha (a resolução do release é somente legado; a lacuna de integridade só foi parcialmente fechada no VISOR)

Resolução frágil do release: assets[0] entre todos os assets de todos os releases (PythonDependencyChecker.py:98-102), por um cliente GitHub não autenticado (60 requisições/h por IP). Um asset adicionado no topo do último release muda o modelo baixado. E nenhuma verificação de integridade nos três checkpoints baixados um a um: um arquivo truncado é indistinguível de um completo.

Legacy (3c67957); ausente no VISOR quanto à resolução: o manifesto do servidor fixa uma URL por arquivo, por tag de release (VISOR-serve scripts/data-manifest.yml:546-585). Corrigido apenas em parte quanto à integridade: um sha256 é declarado para apenas dois arquivos desta ferramenta, o dataset.json e o plans.json do PediatricDentalSeg (data-manifest.yml:563, 568); os checkpoints e o arquivo do DentalSegmentator têm um size e nenhum hash, e o script de busca só verifica quando há um hash (VISOR-serve scripts/fetch_data.py:309-319). Um download vai para uma pasta temporária e é movido para o lugar quando completo, de modo que um checkpoint truncado não é mais tomado por um terminado (fetch_data.py:300-306).

  • O NRRD não é reconhecido e as subpastas não são percorridas (listVolumes), enquanto os outros módulos do repositório produzem NRRD e árvores de pastas sem esforço. Colisão de nomes é possível: dois scans de pastas diferentes com o mesmo nome base sobrescrevem o mesmo <stem>_Segmentation.nii.gz.
  • Um único fold, nunca um ensemble (folds="0"): um pacote que trouxesse fold_1..4 os veria ignorados.
  • os.environ['nnUNet_results'] é reescrito a cada scan pelo SegmentationLogic: inofensivo aqui (fila sequencial), perigoso se outra inferência do nnU-Net rodar na mesma sessão do Slicer.
  • Código morto: _saveSegmentationAsNifti, _postProcessSegments, _keepLargestIsland, _removeSmallIsland, onExportClicked (o botão correspondente não está ligado ao layout de lote).
Armadilha (somente legado; corrigida: o CMake lista sim parte de Resources/ML)

Correção em 3c67957. O MODULE_PYTHON_RESOURCES lista de fato Resources/ML/download_info.json e o dataset.json e o plans.json de Dataset111_453CT (BATCHDENTALSEG/CMakeLists.txt:28-34), de modo que a afirmação de que Resources/ML não é instalado estava errada para aquele commit. Os arquivos JSON dos três outros pacotes não estão listados.

O que se mantém: a estimativa de memória a priori (§5.3) devolve None quando os arquivos de plano ou de dataset não podem ser lidos (SegmentationWidget.py:1173-1204), e a verificação de RAM deixa então o scan passar (SegmentationWidget.py:1239-1242).

Ausente no VISOR: o cliente Slicer não tem proteção de memória (o painel tem 97 linhas, AutomatedDentalToolsRemote BATCHDENTALSEGRemote/BATCHDENTALSEGRemote.py:51-97); a admissão é feita pelo servidor (VISOR-serve server/execution/admission.py:1-12).

10. Literatura

DentalSegmentator é publicado:

Dot G., Chaurasia A., Dubois G., Savoldelli C., Haghighat S., Azimian S., Rahbar Taramsari A., Sivaramakrishnan G., Issa J., Dubey A., Schouman T., Gajny L. DentalSegmentator: robust open source deep learning-based CT and CBCT image segmentation. Journal of Dentistry 147:105130, 2024. doi:10.1016/j.jdent.2024.105130 , PMID 38878813

nnU-Net v2 (v2.2 segundo o aviso do Zenodo para os pesos), 470 scans de CT e CBCT de 7 instituições para o treino, 5 estruturas, teste hold-out em 256 scans (133 internos, 123 externos): DSC 92,2 ± 6,3% interno, 94,2 ± 7,4% externo. O dataset.json fornecido aqui anuncia numTraining = 453, coerente com o corpus descrito.

Verificado

Para este modelo, código e artigo concordam. Os pesos também são publicados sob CC-BY-4.0 no Zenodo (DOI de conceito 10.5281/zenodo.10829674) , mas este módulo os busca nos releases do GitHub, e não no Zenodo.

Legacy: o próprio módulo os baixa no primeiro Apply. VISOR: nada é buscado durante uma execução; um script de preparação coloca em cena o mesmo arquivo de release do upstream (gaudot/SlicerDentalSegmentator, Dataset111_453CT_v100.zip, VISOR-serve scripts/data-manifest.yml:582-586), ainda do GitHub e não do Zenodo.

A base metodológica:

Isensee F., Jaeger P.F., Kohl S.A.A., Petersen J., Maier-Hein K.H. nnU-Net: a self-configuring method for deep learning-based biomedical image segmentation. Nature Methods 18(2):203-211, 2021. doi:10.1038/s41592-020-01008-z

As três variantes não estão ligadas a nenhuma publicação no repositório. O README do repositório anuncia 513 scans CBCT em dentição mista para o PediatricDentalSegmentator e o UniversalLabDentalSegmentator, e 135 scans para o NasoMaxillaDentalSegmentator, sem referência e sem conjunto de teste. Esses números não podem ser verificados em lugar nenhum do código: os arquivos dataset.json correspondentes só chegam com o download dos pesos. A tratar como afirmações internas até que uma publicação os cubra.
