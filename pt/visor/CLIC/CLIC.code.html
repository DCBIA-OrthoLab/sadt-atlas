CLIC no VISOR: o código

Para desenvolvedores: o que o port do CLIC para o VISOR faz no código, com referências file:line, código, argumentos, ambiente, as diferenças em relação ao código legado e os achados. A explicação legível do mesmo pipeline, com a matemática, está na página do atlas.

Código Atlas (explicação) VISOR 1 rede Página do legado Guia (VISOR)

As referências nesta página citam um repositório, depois um caminho dentro dele, depois uma linha: SADT-VISOR é o catálogo de ferramentas (commit 6ba2a78), VISOR-serve o servidor (e9a7e5d), Remote o cliente do Slicer (AutomatedDentalToolsRemote 19b95e8), legacy SlicerAutomatedDentalTools em 3c67957. Um caminho solto como pipeline.py:36 está em SADT-VISOR tools/CLIC/src/sadt_clic/. Tudo foi lido no código; nada nesta página foi executado. Visão geral da pilha: VISOR.

1. Posição na cadeia

Explicação em linguagem simples e matemática: página do atlas.

  • Estado: portado, implementado no código e coberto por testes na ferramenta (SADT-VISOR tools/CLIC/tests/, não executados para esta página). Nada aqui diz que um dado servidor o esteja executando.
  • Nome na API CLIC, declarado por [tool.sadt] tool = true, name = "CLIC" (SADT-VISOR tools/CLIC/pyproject.toml:24-26). O servidor descobre toda pasta de ferramenta que traz essa tabela; não há lista fixa no código (Arquitetura).
  • Painel cliente CLICRemote, um painel fino gerado a partir da descrição da ferramenta no servidor (Remote CLICRemote/CLICRemote.py:44,53), construído com a extensão (Remote CMakeLists.txt:35).
  • Chama / é chamado por: nada, nos dois lados. run() não tem argumento sup, então não há sup.run (SADT-VISOR __init__.py:76-88), e nenhuma outra ferramenta cita CLIC. O schema, no entanto, traz "supervisor": true, porque data_root é um argumento injetado (saída de SADT-VISOR scripts/describe.py sobre tools/CLIC).
  • Dados hospedados: DATA/CLIC/models/final_model.pth (176 MB) e o scan de teste MG_test_scan.nii.gz estão no manifesto de dados (VISOR-serve scripts/data-manifest.yml:630-641). O scan é um CBCT de cabeça inteira sem canino impactado conhecido (SADT-VISOR tools/CLIC/README.md:116-120): ele prova o ciclo de ida e volta, não a classificação.

3. O pipeline

Explicação em linguagem simples e matemática: página do atlas.

3.1 Encontrar os scans

Explicação em linguagem simples e matemática: página do atlas.

scans é um único arquivo ou uma pasta. Uma pasta é percorrida recursivamente com os.walk, os arquivos ocultos são ignorados, e só os nomes terminados em .nii ou .nii.gz (sem distinguir maiúsculas) são mantidos, como caminhos de arquivo, em ordem (pipeline.py:58-79). O coletor legado também anunciava .nrrd, .mha e .mhd, que o nibabel não lê, e devolvia subpastas em vez de arquivos (legacy §3.1).

SCAN_EXTENSIONS = (".nii", ".nii.gz")                 # pipeline.py:36
found = discover_scans(str(scans))                    # __init__.py:115
if not found:
    raise ValueError("No .nii or .nii.gz scan found in '...'. "
                     "CLIC reads NIfTI volumes; NRRD and MetaImage are not supported.")

Um resultado vazio é um ValueError (__init__.py:116-123), que o servidor transforma em um 422 com a mensagem (VISOR-serve server/execution/runner.py:243-244). Só o nome-base da entrada é citado, não o caminho completo.

3.2 Escolher e carregar o checkpoint

Explicação em linguagem simples e matemática: página do atlas.

model é opcional. Quando está vazio, a ferramenta procura em <data_root>/CLIC/models (_own_models, __init__.py:30-37) e pega o único .pth que houver ali; nenhum ou vários é uma recusa que nomeia os candidatos (_sole_checkpoint, :40-61). Uma pasta nomeada segue a mesma regra, um arquivo nomeado é usado como está (_resolve_checkpoint, :64-73).

O número de classes não é presumido. Ele é lido da forma da cabeça de classificação no state dict, fundo incluído, e as duas cabeças são reconstruídas com esse tamanho antes de os pesos serem carregados (pipeline.py:96-144):

state = torch.load(checkpoint_path, map_location=device, weights_only=True)
classes = class_count(state)       # roi_heads.box_predictor.cls_score.bias .shape[0]
model = maskrcnn_resnet50_fpn(weights=None)
model.roi_heads.box_predictor  = FastRCNNPredictor(box_features, classes)
model.roi_heads.mask_predictor = MaskRCNNPredictor(mask_features, 256, classes)
model.load_state_dict(state)
model.to(device).eval()

O checkpoint publicado tem quatro classes (fundo, bucal, bicortical, palatina), que é o que catalogs.CLASSES = len(LABELS) + 1 espera (catalogs.py:23-40). Uma cabeça malformada ou ausente é um ValueError que nomeia a chave (pipeline.py:109-123). resolve_device mantém cuda quando uma placa é visível e, caso contrário, recua para cpu com um aviso (pipeline.py:82-93).

3.3 O laço de fatias

Explicação em linguagem simples e matemática: página do atlas.

Cada scan é lido com o nibabel como float32 (__init__.py:216-219); um volume que não é 3D faz falhar apenas aquele scan. O volume de rótulos é um array int16 do mesmo formato. O laço percorre o terceiro eixo do array tal como armazenado no arquivo, sem reorientação, exatamente como fazia o runner legado:

for index in range(volume.shape[2]):                          # pipeline.py:170
    image = normalise(volume[..., index])                     # min-max to [0, 1]
    tensor = torch.from_numpy(image).unsqueeze(0).repeat(3, 1, 1).float().to(device)
    with torch.no_grad():
        predicted = model([tensor])[0]                        # one slice per call
    keep = predicted["scores"] >= score_threshold             # default 0.7
    masks = (predicted["masks"][keep] > MASK_BINARY_THRESHOLD).squeeze(1)   # 0.5
    for mask, label in zip(masks.cpu().numpy(), predicted["labels"][keep].cpu().numpy()):
        labels[..., index][mask] = int(label)                 # last one wins
        detections += 1
  • Normalização: por fatia, (x - min) / (max - min); uma fatia plana (amplitude ≤ 1e-8) vira zeros em vez de NaN (pipeline.py:147-154). O _norm legado é igual (legacy CLIC/runner/clic_runner.py:44-46).
  • O redimensionamento e a padronização ImageNet acontecem dentro do GeneralizedRCNNTransform do torchvision, como no legado (legacy §4.1); a ferramenta não reamostra nada por conta própria.
  • Limiares: score_threshold é um argumento (padrão DEFAULT_SCORE_THRESHOLD = 0.7, pipeline.py:41); o limiar da máscara continua uma constante, MASK_BINARY_THRESHOLD = 0.5 (:44).
  • Sobreposição: as máscaras são escritas na ordem em que a rede as devolve, de modo que, onde duas se sobrepõem, a última sobrescreve; não há votação nem consistência 3D entre fatias (pipeline.py:180-182).

3.4 Saídas e relatório

Explicação em linguagem simples e matemática: página do atlas.

Cada scan é identificado pelo seu caminho relativo à raiz da entrada, e a árvore de saída espelha a árvore de entrada. A extensão .nii.gz ou .nii é removida antes de o sufixo ser acrescentado (__init__.py:223-231):

input   scans/site_A/P01.nii.gz
output  output_dir/site_A/P01_seg.nii.gz          # affine and header copied from the input

Um único arquivo é a sua própria raiz, então seu resultado cai diretamente em output_dir (__init__.py:163-165). O mapa de rótulos mantém o affine e o header da entrada (nib.Nifti1Image(labels, image.affine, image.header), :231), de modo que scan e segmentação abrem alinhados. Reutilizar o header também significa que o arquivo é escrito no tipo de dado do scan de entrada, como no legado: labels é int16 na memória (pipeline.py:167), mas um scan float32 dá um mapa de rótulos float32 em disco (nibabel 5.4.2, verificado na chamada legada, que tem o mesmo formato; os valores continuam de 0 a 3). Depois CLIC_report.json é escrito ao lado dos resultados (:201), com este formato (chaves de __init__.py:133-155,188-189,233-249):

{
  "tool": "CLIC", "model": "final_model.pth", "classes": 4,

Os valores do exemplo (número de fatias, número de detecções, duração) são ilustrativos; as chaves são as do código. Quando o checkpoint tem outro número de classes, labels e label_colors são null e um labels_note diz por quê: um inteiro sem nome é preferível a um nome errado (__init__.py:146-154, catalogs.py:43-58). Um scan sem nenhuma detecção recebe "note": "no detection cleared the score threshold" (:245-249).

3.5 Falhas, progresso e logs

Explicação em linguagem simples e matemática: página do atlas.

  • Um scan falha, só um scan se perde. Qualquer exceção dentro de _segment_one é registrada na entrada daquele scan como status: failed com reason, e o laço continua (__init__.py:173-186). A execução só lança erro quando nenhum scan foi escrito, listando todas as razões (:191-199); o relatório então não é escrito.
  • Progresso: progress.report(index, total, "scan") antes de cada scan (__init__.py:170) acrescenta uma linha JSON ao arquivo nomeado por SADT_PROGRESS_FILE (progress.py:3,21,89-103). As mensagens dão uma posição, nunca um nome de arquivo, porque nomes de arquivo são metadados de pacientes (progress.py:13-15).
  • Logs: a linha de log da falha também cita a posição, não o arquivo (__init__.py:183), já que o stderr de uma execução com falha é mantido no log do servidor.

8. Constatações no VISOR

Explicação em linguagem simples e matemática: página do atlas.

O download do backbone ainda é alcançável

A ferramenta constrói a rede com maskrcnn_resnet50_fpn(weights=None) (SADT-VISOR tools/CLIC/src/sadt_clic/pipeline.py:136), como o legado fazia. No torchvision 0.26.0 fixado (pyproject.toml:14), weights_backbone tem como padrão ResNet50_Weights.IMAGENET1K_V1 (torchvision/models/detection/mask_rcnn.py:416) e resnet50(weights=weights_backbone) é chamado (:490,502), o que busca o arquivo por load_state_dict_from_url (torchvision/models/_api.py:91); o checkpoint é carregado por cima depois (pipeline.py:142). O teste que proíbe chamadas de rede só procura strings nas fontes da própria ferramenta (tests/test_device_and_contract.py:163-175) e não enxerga essa chamada. As linhas do torchvision foram lidas em uma cópia instalada do torchvision 0.26.0; nada foi executado, e não foi verificado se um dado servidor já guarda o arquivo do ResNet-50 em seu cache do torch.

Um scan sem detecção é um sucesso

Um volume em que nada passa do limiar é escrito como um mapa de rótulos todo zero com "note": "no detection cleared the score threshold" (__init__.py:245-249). A guarda de "nada escrito" conta scans escritos, não detecções (:191-199), então um lote em que todos os scans estão vazios é uma execução bem-sucedida. O comentário da fonte diz que é também a aparência de um checkpoint errado (:246-248).

O cliente nem mostra nem mescla o relatório

O CLIC_report.json traz a tabela de rótulos, o que foi detectado e quais scans falharam (__init__.py:133-155,173-186), mas o painel não tem RUN_REPORT (Remote CLICRemote/CLICRemote.py:53-72; padrão da base vazio, ServerToolsCore/ServerToolsCoreLib/base_widget.py:1493), ao contrário do CNE e do DOCShapeAXI. Um scan que falhou só é visível abrindo o JSON. Uma pasta maior que um lote (25 entradas ou 400 MB por padrão, VISOR-serve server/config.py:192,196) é enviada como várias execuções cujas pastas são reunidas na pasta de saída no final; o relatório mesclado só é escrito para um painel que declara RUN_REPORT (base_widget.py:2192), e quando dois lotes produzem o mesmo nome de arquivo o primeiro é mantido (:2205-2224). Para o CLIC, o CLIC_report.json final é portanto o de um único lote. Lido no código, não executado.

Comentários do servidor descrevem outro CLIC

Comentários do VISOR-serve descrevem um CLIC que "batches slices inside one forward" (server/execution/admission.py:146) com um argumento batch_size = 4 (server/execution/runner.py:1251,1271-1272), e citam medidas de memória do CLIC em larguras de 1 a 45 (server/execution/costs.py:470-477). A ferramenta empacotada não tem argumento batch_size, executa uma fatia por chamada model([tensor]) (pipeline.py:170-176) e nunca chama progress.set_width, que é apenas definido (progress.py:41). Esses comentários e números descrevem portanto outra versão da ferramenta; não leia "quatro fatias por passada" como uma propriedade deste código.

As sobreposições continuam resolvidas pela ordem, fatia a fatia

Onde duas máscaras mantidas se sobrepõem em uma fatia, a que a rede devolveu por último sobrescreve a outra, e cada fatia é decidida sozinha: não há votação entre classes nem consistência 3D, de modo que um canino pode carregar dois rótulos em fatias vizinhas (pipeline.py:170-182, igual ao clic_runner.py:84-87 do legado). Lido no código.

Verificado: os outros defeitos do legado sumiram

A escolha do checkpoint recusa a ambiguidade, o número de classes é lido, o carregamento é weights_only=True, as saídas são nomeadas corretamente e identificadas pelo caminho relativo, de modo que dois scans homônimos não se sobrescrevem mais (SADT-VISOR __init__.py:40-73,223-231, pipeline.py:96-144). A tabela de rótulos está no relatório, não só no widget.
