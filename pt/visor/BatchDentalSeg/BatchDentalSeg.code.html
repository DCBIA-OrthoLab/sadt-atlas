BatchDentalSeg no VISOR: o código

Para desenvolvedores: o que o port do BatchDentalSeg para o VISOR faz no código, com referências file:line, assinaturas, argumentos, ambiente, as diferenças em relação ao código legado e os achados. A explicação legível do mesmo pipeline, com a matemática, está na página do atlas. Como o BatchDentalSeg roda no VISOR (cliente e servidor), o que mudou em relação ao módulo legado do Slicer, e o que o código do port faz, passo a passo. O módulo legado é descrito em sua própria página.

Código Atlas (explicação) VISOR Batch_Dental_Seg Página do legado Guia (VISOR) Bibliografia

O VISOR executa o BatchDentalSeg em um servidor: o Slicer envia os scans e o nome de um modelo hospedado, e recebe volumes de labels, arquivos por label ou malhas. Uma rede nnU-Net v2, escolhida entre quatro bundles, rotula todas as estruturas de um scan em uma única passada, e uma chamada cobre o lote inteiro. Esta página diz o que roda onde, acompanha o pipeline do arquivo de entrada até o relatório da execução, lista os argumentos que o servidor publica e compara cada etapa com o módulo legado. Tudo aqui foi lido no código, não observado em um servidor em funcionamento, e nada aqui diz que um dado servidor está implantado.

As referências nomeiam primeiro o repositório: SADT-VISOR (código das ferramentas, tool/vface @ 6ba2a78), VISOR-serve (servidor, @ e9a7e5d), AutomatedDentalToolsRemote (cliente Slicer, @ 19b95e8) e legado (SlicerAutomatedDentalTools @ 3c67957). Um nome de arquivo sozinho, como pipeline.py, catalogs.py, layout.py, nnunet_runner.py, low_memory.py, mesh_export.py, progress.py ou __init__.py, está no pacote SADT-VISOR tools/Batch_Dental_Seg/src/sadt_batchdentalseg/. SegmentationWidget.py, Queue.py e PythonDependencyChecker.py são arquivos legados de BATCHDENTALSEG/BATCHDENTALSEGLib/ (o widget tem 3037 linhas em 3c67957).

3. O pipeline

segment() (SADT-VISOR pipeline.py:216-398) é uma linha reta. O bundle é verificado antes de qualquer scan ser lido, cada scan é convertido em uma só pasta, o nnU-Net roda uma vez sobre essa pasta, e depois cada scan é escrito de volta em sua própria grade. Só a etapa da rede é aprendida.

Explicação em linguagem simples e matemática: página do atlas.

3.1 Entradas e descoberta

discover_scans() (pipeline.py:87-107) toma um arquivo como está, ou percorre uma pasta recursivamente com os.walk e mantém os arquivos cuja extensão está em sadt_naming.VOLUME: .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl, comparadas em minúsculas (SADT-VISOR naming/src/sadt_naming/__init__.py:36). Em uma pasta, um arquivo é ignorado quando parece uma saída anterior desta ferramenta:

def is_previous_output(filename, suffix):                      # pipeline.py:72-84
    base, _extension = split_scan_extension(os.path.basename(filename))
    if suffix and base.endswith(f"_{suffix}"):
        return True
    return any(base.endswith(f"_{suffix}_{name.replace(' ', '-')}")
               for model in catalogs.MODELS.values()
               for name in model.labels)

Com o padrão prediction_ID = "Seg", isso vale para qualquer nome base terminado em _Seg ou em _Seg_<label> para qualquer label de qualquer um dos quatro modelos, de modo que uma pasta pode ser executada de novo no mesmo lugar (veja o achado do §8 sobre scans cujo próprio nome termina assim). Nenhum scan levanta ToolInputError (pipeline.py:243-248). A árvore de entrada é mantida: input_root é a pasta, ou o pai de um arquivo único (pipeline.py:250), e cada caso é descrito no relatório por seu caminho relativo a ela, nunca por um caminho absoluto (pipeline.py:264-265).

3.2 O modelo: um nome, um bundle, uma tabela de labels

resolve_model() (pipeline.py:110-133) roda antes de qualquer scan ser lido. O nome da pasta do caminho model é buscado em catalogs.MODELS; um nome desconhecido é recusado com a lista dos modelos conhecidos. Dentro da pasta, find_model_folder() percorre a árvore atrás do diretório que contém dataset.json, plans.json e fold_0/checkpoint_final.pth, os três verificados (nnunet_runner.py:57-73): os quatro bundles não compartilham uma mesma organização, e o DentalSegmentator chega como um zip com sua própria árvore Dataset<n>/ (nnunet_runner.py:37-41). Um bundle incompleto é recusado com o comando que o prepara de novo (pipeline.py:126-132).

MODELS = {model.name: model for model in (                     # catalogs.py:126-152
    Model("DentalSegmentator",  _FIVE_LABELS,      "Adult dental CT/CBCT. ..."),
    Model("PediatricDentalSeg", _FIVE_LABELS,      "Paediatric dental CT/CBCT, ..."),
    Model("NasoMaxillaDentSeg", _NASO_LABELS,      "Six segments: the maxilla is separated ..."),

Como a tabela de labels segue o nome da pasta, quem chama não pode emparelhar um bundle com os labels de outro: não há um segundo argumento para errar (catalogs.py:120-125). Os valores são os inteiros que a rede emite, e o código os escreve sem alterá-los.

3.3 Conversão para o layout do nnU-Net

Cada scan é convertido em uma só pasta, <output_dir>/.batchdentalseg_work/nnunet_in/, sob um id de caso posicional (pipeline.py:256-277):

case_id = f"case_{index:04d}"                                   # pipeline.py:275
_convert_to_nifti(scan, os.path.join(nnunet_input, f"{case_id}_0000.nii.gz"))

def _convert_to_nifti(scan_path, destination):                  # pipeline.py:140-149
    sitk.WriteImage(sitk.ReadImage(scan_path), destination)

Uma leitura mais uma escrita, nunca uma renomeação: o nnU-Net escolhe seu leitor pela extensão, então um NRRD renomeado para .nii.gz seria lido errado. O tipo do voxel é deixado como está; o nnU-Net converte para float32 por conta própria (pipeline.py:143-145). Os ids são posicionais porque o nnU-Net escreve sua saída sob o id da entrada, e dois scans chamados scan.nii.gz em subpastas diferentes colidiriam (pipeline.py:256-259). Um scan que não pode ser lido é registrado como failed com "could not be read" e ignorado; só quando nenhum pode ser lido a execução para (pipeline.py:278-298).

Nenhum janelamento de intensidade e nenhum corte é escrito neste pacote. As únicas reamostragens que ele acrescenta são a opcional na GPU (§3.5) e a que devolve o resultado à grade do scan (§3.6, pipeline.py:152-171). O resto do pré-processamento é do próprio nnU-Net, a partir do plans.json de cada bundle, e roda nesta ordem (nnunetv2 2.8.1 como instalado no ambiente da ferramenta, nnunetv2/preprocessing/preprocessors/default_preprocessor.py): transposição (:56), corte para a região não nula (:65), normalização (:82, o comentário acima dela diz que DEVE vir antes da reamostragem), depois reamostragem para o spacing do plano (:88). O auto-crop do legado não foi portado, de propósito: o upstream o aplicava só depois de uma verificação de memória que falhava, e ele muda o que a rede enxerga (pipeline.py:18-21).

A normalização é a do nnU-Net, não a deste repositório. Para um plano cujo esquema é CTNormalization: limitar aos percentis 0.5 e 99.5 do plano, subtrair a média, dividir por max(std, 1e-8) (nnunetv2/preprocessing/normalization/default_normalization_schemes.py:58-72, números de foreground_intensity_properties_per_channel). Só o plans.json do DentalSegmentator pode ser lido nos repositórios (no do legado: CTNormalization, p0.5 −110, p99.5 3067, média 1274, std 558). Os planos dos outros três bundles são baixados com os modelos, de modo que a aplicação desse esquema a eles é presumida, não verificada.

3.4 Inferência: uma chamada para o lote inteiro

predict_folder() (nnunet_runner.py:192-232) é chamado uma vez com a pasta de entrada inteira que recebe (pipeline.py:302-306), então o checkpoint é carregado uma vez por chamada, não uma vez por scan. Uma coorte maior que um lote do servidor (25 arquivos ou 400 MB, §4) chega à ferramenta como várias dessas chamadas. O predictor é construído pela API Python do nnU-Net, com a palavra-chave renomeada escolhida por introspecção:

options = {                                                     # nnunet_runner.py:86-95
    "tile_step_size": float(tile_step_size),   # argument, default 0.5
    "use_gaussian": True,
    "use_mirroring": False,                    # no test-time mirroring
    "device": torch.device(device),
    "verbose": False, "verbose_preprocessing": False, "allow_tqdm": False,
}
# + perform_everything_on_device (or _on_gpu) = device.startswith("cuda")   :97-100

predictor.initialize_from_trained_model_folder(                 # :204-208
    model_folder, use_folds=(0,), checkpoint_name="checkpoint_final.pth")

O caminho do modelo é explícito: nenhuma variável de ambiente nnUNet_results, que é global ao processo (nnunet_runner.py:202-203). device recua de cuda para cpu com um aviso quando nenhuma placa é visível (nnunet_runner.py:46-54). Dois caminhos se seguem (nnunet_runner.py:210-232):

  • Reamostragem na GPU aplicada: predict_from_files_sequential, tudo neste processo, porque workers criados por spawn precisariam cada um de seu próprio contexto CUDA;
  • caso contrário (CPU, gpu_resampling=false, ou planos com outro reamostrador): predict_from_files com 2 workers de pré-processamento e 2 de exportação. Esses workers são a razão do shm_size do contêiner (VISOR-serve docker-compose.yml:225-229).

O posicionamento e a ponderação dos patches são os do nnU-Net: o passo é no máximo tile_step_size vezes o tamanho do patch e é reduzido para que os patches terminem exatamente na borda da imagem, daí uma sobreposição de pelo menos metade para 0.5 (nnunetv2/inference/sliding_window_prediction.py:30-54); o peso gaussiano tem um desvio de um oitavo do patch (sliding_window_prediction.py:11-16, chamado em predict_from_raw_data.py:626).

O progresso só tem duas extremidades mensuráveis: a leitura conta scans de 0 a 10 %, a escrita de 90 a 100 %, e entre as duas uma linha diz "segmenting N scan(s) in one pass" (pipeline.py:269-274, 301, 313; progress.py:89-103). Se a chamada de inferência levanta erro, a pasta temporária é removida e o lote inteiro falha, sem relatório escrito (pipeline.py:302-309).

3.5 Reamostragem na GPU e o argmax por classe

Com gpu_resampling = true (o padrão) em um dispositivo CUDA, _enable_gpu_resampling() (nnunet_runner.py:124-189) reescreve os dois nomes de reamostrador na configuração do predictor, só se ambos forem o resample_data_or_seg_to_shape original do nnU-Net:

for key in ("resampling_fn_data", "resampling_fn_probabilities"):   # nnunet_runner.py:167-177
    configuration[key] = "resample_torch_fornnunet"
    configuration[f"{key}_kwargs"] = {"is_seg": False,
                                      "device": torch.device(device),
                                      "mode": "linear"}

O volume de entrada passa, portanto, de spline de ordem 3 para ordem 1, o que o código nomeia como toda a diferença numérica (nnunet_runner.py:169-172). O terceiro reamostrador, o da máscara de corte, é deixado de propósito no scipy (nnunet_runner.py:110-116). As propriedades em cache são limpas para que a troca tenha efeito (:179-183).

A mesma função então chama low_memory.install(predictor) (nnunet_runner.py:185-188). Isso substitui de novo o reamostrador de probabilidades por um que reamostra a saída da rede uma classe por vez e mantém um máximo e um label correntes, e substitui o argmax do nnU-Net por uma passagem direta, já que o que chega já é o argmax:

for index in range(data.shape[0]):                              # low_memory.py:62-79
    one = resample_torch_fornnunet(data[index:index + 1].to(device), shape, ...)[0]
    ...
    higher = one > best
    best = torch.where(higher, one, best)
    labels = torch.where(higher, index, labels)
return labels.unsqueeze(0).cpu()                                 # :86

As duas metades são instaladas juntas ou não são instaladas: a fábrica que constrói um label manager novo para predict_from_files_sequential também é encapsulada na instância (low_memory.py:100-151). Segundo a docstring do módulo, a aritmética é a mesma do caminho original (0 voxels diferentes em 95 682 560 em uma execução do UniversalLab) e o pico cai de cerca de 30.6 para 1.25 GiB de VRAM (low_memory.py:14-26); esses números não foram reproduzidos aqui. Empates entre classes vão para o menor índice no caminho da GPU, porque o máximo corrente só é substituído por uma pontuação estritamente maior (one > best, low_memory.py:75). No caminho do próprio nnU-Net, o label é predicted_probabilities.argmax(0) (nnunetv2/utilities/label_handling/label_handling.py:178), que devolve o primeiro máximo pela convenção do NumPy e do PyTorch (comportamento documentado do argmax, não testado aqui).

Para cada caso, a predição nnunet_out/<case_id>.nii.gz é lida; uma ausente marca aquele scan como failed e o laço continua (pipeline.py:312-321). O volume de labels é então devolvido à grade exata do scan de origem:

if (mask.GetSize() == reference.GetSize()                       # pipeline.py:162-171
        and np.allclose(mask.GetSpacing(), reference.GetSpacing(), atol=1e-4)):
    mask.CopyInformation(reference)          # same grid: copy origin and direction

return sitk.Resample(mask, reference, sitk.Transform(),
                     sitk.sitkNearestNeighbor, 0, mask.GetPixelID())

3.7 Superfícies

mesh_export.write() (mesh_export.py:177-236) não faz nada a menos que um formato de malha esteja em export_formats. Ele constrói a superfície de cada label presente uma só vez e a escreve em todos os formatos pedidos, então marcar STL e OBJ juntos custa uma só passada de marching cubes (:212-225).

smoother = vtk.vtkWindowedSincPolyDataFilter()                  # mesh_export.py:89-110
smoother.SetNumberOfIterations(max(0, int(smoothing)))          # write(smoothing=30)
smoother.SetPassBand(0.05)
smoother.BoundarySmoothingOn()
smoother.SetFeatureEdgeSmoothing(False)
smoother.NonManifoldSmoothingOn()
smoother.NormalizeCoordinatesOn()

A suavização de arestas de feature está desligada de propósito: em uma malha bruta de marching cubes, cada degrau de voxel é uma aresta viva, e proteger essas arestas manteria a escada (mesh_export.py:94-107). A decimação usa vtkDecimatePro com topologia preservada e ângulo de feature de 60 (:120-130); seu padrão de 0 foi escolhido para ficar em paridade com a exportação STL do módulo legado, medida em um label segundo a docstring (__init__.py:84-100). Nenhuma normal é escrita (:132-139). STL e VTK são escritos em binário, OBJ como texto, que não tem forma binária (:45-49, 165-172). A máscara chega ao VTK por um NRRD temporário de nome único, removido após a leitura (:66-118); o mesh_export.py não aplica nenhuma transformação RAS ou LPS explícita, ao contrário da exportação VTK do legado, que invertia para LPS (legacy SegmentationWidget.py:2958).

8. Constatações no VISOR

O VFACE pede superfícies e recebe volumes de labels

O caminho de mapa de calor do VFACE chama esta ferramenta com apenas três argumentos, scans, model e prediction_ID="Seg" (SADT-VISOR tools/VFACE/src/sadt_vface/tools.py:359-364), então export_formats mantém seu padrão ["NIFTI"] (SADT-VISOR __init__.py:22-24) e nenhuma malha é escrita (pipeline.py:342-354; mesh_export.py:187-189). O VFACE então procura só arquivos .vtk ou .vtp (heatmap.py:29, 194-204), não encontra nenhum e termina com "No heat map could be drawn" (heatmap.py:246-251). Lido no código, não executado. A implantação lida aqui não publica surface_model para o VFACE de qualquer modo (VISOR-serve server/deployment.toml:277-279), então o caminho não é alcançável a partir do painel desse servidor.

O README da ferramenta está desatualizado quanto às exportações de malha e à memória

O README da ferramenta diz "No vtk: the mesh exports are not ported" e as lista como não portadas (tools/Batch_Dental_Seg/README.md:28, 95); a docstring de pipeline.py diz o mesmo (SADT-VISOR pipeline.py:23-24). O código diz o contrário: mesh_export.py escreve STL, OBJ e VTK, export_formats é um argumento (__init__.py:22-24) e o vtk 9.6.2 é uma dependência (pyproject.toml:23). Só o glTF realmente falta. O README também conta 38 testes sem GPU (README.md:267) onde o arquivo tem 55 funções de teste. Seu conselho de desligar gpu_resampling para o UniversalLab em uma placa de menos de cerca de 40 GiB (README.md:241-256, repetido em __init__.py:69-73) foi editado pela última vez no commit d2fb0d8; o reamostrador por classe, que o código instala com o reamostrador de GPU em todo bundle (nnunet_runner.py:185-188), veio depois, em c8899c8, e sua docstring anuncia um pico muito menor (low_memory.py:20-26). O código é a referência aqui; o pico em si não foi medido para esta página.

Um scan chamado ..._Seg fica invisível em uma pasta

Com o identificador padrão, patient_Seg.nii.gz dentro de uma pasta é tomado por uma saída anterior e ignorado sem nenhuma mensagem (SADT-VISOR pipeline.py:79-80, 104-105). Um arquivo único passado como scans é processado mesmo que seu nome pareça uma saída (pipeline.py:96-97).

A reamostragem na GPU vem ligada por padrão e muda os números

Quando se aplica, o volume de entrada é reamostrado na GPU em modo linear em vez da spline cúbica do nnU-Net; o código afirma que essa é toda a diferença numérica e que gpu_resampling=false a desliga (SADT-VISOR nnunet_runner.py:167-177). O relatório registra o valor pedido em um dispositivo CUDA, e false na CPU; um bundle cujos planos não aderem só é mencionado no log (pipeline.py:374-378; nnunet_runner.py:163-165). O argumento é oculto no painel.

O autotuning do cuDNN não é desligado

O BatchDentalSeg nunca define torch.backends.cudnn.benchmark (nenhuma ocorrência no pacote), e o predictor do nnU-Net o define como true em CUDA (nnunetv2/inference/predict_from_raw_data.py:60-61, nnunetv2 como instalado no ambiente da ferramenta). O AMASSS o desliga explicitamente (SADT-VISOR AMASSS sadt_amasss/nnunet_runner.py:116). O README da ferramenta diz que o nnU-Net em CUDA não é determinístico bit a bit (README.md:113): não espere uma máscara idêntica bit a bit em duas execuções do mesmo scan.

Uma lista de exportação vazia dá "ok" sem nenhum arquivo (só em chamada direta)

Chamado diretamente em Python, run(..., export_formats=[]) relata cada scan como ok com uma lista produced vazia e um resumo "1/1 scan(s) segmented", e não escreve nada (SADT-VISOR pipeline.py:342-355, 362-386; mesh_export.py:187-189); a ferramenta em si não verifica a lista. Uma requisição pelo servidor é recusada antes da execução, já que o layout pede pelo menos um formato (layout.py:31-33; VISOR-serve server/base.py:855-858), e o painel também pede um.

Os arquivos por label dependem do formato NIfTI

separate_segments divide o volume de labels, então só funciona quando NIFTI está selecionado: só com malhas, nada é escrito para ele mesmo que a caixa esteja marcada (SADT-VISOR pipeline.py:339-350).

A tabela de labels viaja com o resultado, mas o Slicer não a lê

O relatório contém a tabela labels completa (SADT-VISOR pipeline.py:364-371). O painel do Slicer não define RUN_REPORT (padrão vazio: ServerToolsCoreLib/base_widget.py:1493) e carrega os volumes de labels com um simples loadLabelVolume (slicer_io.py:560); um comentário no módulo fala de uma tabela de cores (BATCHDENTALSEGRemote.py:79-82), mas nenhum código aplica uma.

Uma chamada de inferência: o progresso tem duas extremidades

A pasta inteira passa por uma única chamada do nnU-Net, então a barra cobre a leitura (0 a 10 %) e a escrita (90 a 100 %) e diz "segmenting N scan(s) in one pass" no intervalo, sem inventar valores intermediários (SADT-VISOR pipeline.py:269-274, 301). Uma exceção dessa chamada faz o lote inteiro falhar depois de limpar a pasta temporária (pipeline.py:302-309).

Verificado: um scan ilegível não interrompe o lote

Um scan que não pode ser lido é registrado como failed ("could not be read") e os outros são segmentados; só quando nenhum pode ser lido a execução para com um erro de entrada (SADT-VISOR pipeline.py:273-298).
