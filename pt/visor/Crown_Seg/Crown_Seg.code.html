Crown_Seg no VISOR: o código

Para desenvolvedores: o que a ferramenta Crown_Seg do VISOR faz no código, com referências file:line, assinaturas, argumentos, ambiente, a correspondência com o legado e os achados. A explicação legível do mesmo pipeline, com a matemática, está na página do atlas.

Somente VISOR Código Atlas (explicação) SADT-VISOR 6ba2a78 VISOR-serve e9a7e5d Remote 19b95e8
Nenhum módulo legado

O repositório legado (SlicerAutomatedDentalTools em 3c67957) não contém nenhum módulo Crown_Seg nem nenhum arquivo com “crown” ou “dentalmodelseg” no caminho (git ls-tree nesse commit, observado). O que ele contém são chamadas ao módulo CrownSegmentationcli da extensão separada SlicerDentalModelSeg, e uma pequena cópia da mesma chamada dentro da linha de comando do ALI_IOS. A correspondência exata está em Contraparte no legado. Como o VISOR executa uma ferramenta em um servidor está descrito em Arquitetura.

Caminhos: SADT-VISOR cs/ é tools/Crown_Seg/src/sadt_crownseg/, ali_ios/ é tools/ALI/ALI_IOS/src/sadt_ali_ios/, e os caminhos de VISOR-serve começam em server/, a menos que nomeiem docs/ ou scripts/. “Observado” marca o que foi reexecutado ao escrever esta página; todo o resto foi lido no código.

4. O pipeline

Explicação em linguagem simples e matemática: página do atlas.

4.1 O que a ferramenta faz em torno do motor

Explicação em linguagem simples e matemática: página do atlas.

  1. Primeiro o checkpoint: find_checkpoint aceita um arquivo .pth, ou uma pasta pesquisada recursivamente em busca de um arquivo cujo nome traga val-loss; nenhum ou dois é um ToolInputError que os nomeia (cs/pipeline.py:186-262). model vazio significa <data_root>/Crown_Seg/models (cs/__init__.py:18-29,104). Isso acontece antes de qualquer coisa ser criada (cs/pipeline.py:407-413).
  2. Descoberta: um .vtk ou .stl, ou uma pasta percorrida recursivamente e ordenada; nada encontrado é um 422 (cs/pipeline.py:292-320). A raiz da entrada, usada para espelhar a árvore, é a pasta ou a pasta-mãe do arquivo único (:323-330).
  3. Separação: com skip_segmented (padrão true), is_segmented abre cada malha e lê apenas os nomes dos seus arrays de pontos; qualquer um entre PredictedID, UniversalID, Universal_ID, FDI_ID a envia ao ramo de cópia (cs/pipeline.py:56,267-289,449-451).
  4. Ramo de cópia: cada malha rotulada é escrita como polydata .vtk em <output>/<relative folder>/<base>_<suffix>.vtk, e um .stl é convertido (cs/pipeline.py:480-487,594-613). Os rótulos não são tocados.
  5. Ramo de segmentação: os caminhos restantes vão para .crownseg_work/crownseg_input.csv sob um cabeçalho surf, o dispositivo é resolvido para cuda:0 ou cpu (:170-178), e o shapeaxi é chamado uma vez para a lista inteira com este namespace (cs/pipeline.py:336-366,508-531):
Namespace(surf=None, csv=csv_path, model=checkpoint, suffix=suffix, out=output_dir,
          num_workers=max(1, num_workers), crown_segmentation=0, array_name=array_name,
          fdi=1 if numbering == "FDI" else 0, overwrite=0, device=device,
          vtk_folder=input_root)
with contextlib.redirect_stdout(io.StringIO()):
    dental_model_seg.main(args)

Antes da chamada, _import_dental_model_seg importa o shapeaxi de forma tardia e, quando saxi_nets não tem DentalModelSeg (toda release 2.0.x, segundo o comentário), o aponta para saxi_nets_lightning.DentalModelSeg (cs/pipeline.py:105-167). Se o import falha, a execução segue para o ramo de cópia e registra engine_available: false com o erro (cs/pipeline.py:466-472); uma malha que precisava da rede fica então sem saída e é failed.

4.2 Dentro do shapeaxi

Explicação em linguagem simples e matemática: página do atlas.

Lido em dental_model_seg.py do checkout 2b34042 do ShapeAXI. O lock resolve o shapeaxi para 2.0.2, cuja fonte não foi aberta aqui; as linhas citadas abaixo são idênticas nas cópias que foram (shapeaxi 1.0.10 e 2.0.3 instalados, e 1.1.1 no cache do uv):

  • a rede é saxi_nets_lightning.DentalModelSeg(custom_model=args.model, device=device), com out_channels = 34 (:23,26);
  • cada superfície é carregada por meio de SaxiDataset com UnitSurfTransform(), batch size 1, persistent_workers=True (:82-84), e é por isso que num_workers deve ser pelo menos 1;
  • a rede devolve predições por vista e a face que cada pixel mostra; as predições são multiplicadas por (PF >= 0) (zero onde um pixel não mostra nenhuma face) e depois passam pelo softmax (:97), de modo que um pixel sem face dá um 1/34 uniforme que é somado a uma entrada da tabela de faces em vez de ser ignorado (:103-104); a soma por face e o arg-max (:106) dão um rótulo por face, e o rótulo de cada face é dado ao seu primeiro vértice (:107-108);
  • pós-processamento: RemoveIslands para o rótulo de gengiva 33 com um limiar de 500, depois para todo rótulo com 200, depois um fechamento por rótulo, DilateLabel e depois ErodeLabel, duas iterações cada (:118-130);
  • ConvertFDI se fdi == 1 (:52,225-236, próxima seção);
  • com overwrite=0 e uma entrada csv, o resultado vai para <out>/<csv stem>_<suffix>/<input path without vtk_folder>_<suffix>.vtk (:154-176). O Crown_Seg recalcula esse caminho em vez de interpretar a saída do shapeaxi (cs/pipeline.py:369-381), e depois marca cada malha como segmented se o arquivo existe e failed caso contrário (:533-546).

4.3 Numeração dos dentes: Universal e FDI

Explicação em linguagem simples e matemática: página do atlas.

A rede prediz sempre números Universal: 1 a 32 para os dentes, 33 para a gengiva. Com numbering = "FDI", o ConvertFDI do shapeaxi mapeia cada valor por uma única tabela de consulta (ShapeAXI 2b34042 dental_model_seg.py:225-236):

LUT = [0, 18,17,16,15,14,13,12,11, 21,22,23,24,25,26,27,28,
          38,37,36,35,34,33,32,31, 41,42,43,44,45,46,47,48, 0]
labels = LUT[labels]          # index = Universal value, entry = FDI value

o shapeaxi grava os inteiros convertidos de volta sob o mesmo nome de array (vtk_id.SetName(args.array_name), :233-235). Como os dois sistemas compartilham a maior parte da sua faixa, um array FDI chamado Universal_ID seria lido sem erro como outros dentes: FDI 18 é o terceiro molar superior direito, Universal 18 um molar inferior esquerdo; FDI 33 é um canino inferior esquerdo, Universal 33 a gengiva (comentário em cs/pipeline.py:62-80). O Crown_Seg, portanto, nomeia o array conforme a numeração: array_name deixado vazio vira Universal_ID ou FDI_ID (array_name_for, cs/pipeline.py:58-85; cs/__init__.py:44,106). Todo leitor a jusante procura apenas nomes Universal, de modo que uma malha FDI é recusada pelo ALI_IOS, ASO ou AREG_IOS em vez de ser mal interpretada (veja Achados). Todos os chamadores do legado passavam fdi 0; a saída FDI é nova na prática, e Universal continua o padrão (cs/__init__.py:46).

Saídas. A ferramenta devolve a pasta de saída, então não há saídas nomeadas. Duas árvores podem aparecer, conforme o que aconteceu com cada malha: uma malha segmentada pela rede é escrita em <output>/crownseg_input_<suffix>/<relative path without extension>_<suffix>.vtk (cs/pipeline.py:369-381,514), e uma malha que já trazia rótulos é copiada, convertida para .vtk, em <output>/<relative folder>/<base>_<suffix>.vtk (cs/pipeline.py:480-487,594-613). Espera-se que quem chama leia o run_report.json em vez de adivinhar. A pasta temporária .crownseg_work/ é removida em um finally (cs/pipeline.py:87,435-439), e o checkpoint é resolvido antes de ela existir, de modo que um pedido recusado deixa a pasta de saída como a encontrou (cs/pipeline.py:407-413).

run_report.json. tool, checkpoint (pelo nome), array_name, suffix, numbering, device, cases (por malha: status, input, produced e error em caso de falha), segmented_meshes, engine_available, engine_error, um summary com as contagens de total, segmented, already_segmented, engine_unavailable e failed, e duration_seconds (cs/pipeline.py:556-590). Uma malha para a qual o shapeaxi não escreveu nada é um caso failed; a execução como um todo só falha quando nenhuma malha foi produzida (cs/pipeline.py:540-551).

Privacidade dos logs. O shapeaxi imprime o caminho de cada malha que salva, e o caminho carrega o nome de arquivo do paciente: sua saída padrão é engolida (cs/pipeline.py:341-345,365-366), e os caminhos da saída são recalculados em vez de interpretados a partir dela (cs/pipeline.py:369-381).

8. Constatações no VISOR

Explicação em linguagem simples e matemática: página do atlas.

Numeração FDI sobre uma malha que já está rotulada

Com numbering = "FDI" e skip_segmented ligado, uma malha que já traz um array de rótulos é copiada sem mudança (cs/pipeline.py:480-487; _write_as_vtk converte o formato do arquivo, não os rótulos), enquanto o relatório declara array_name = "FDI_ID" e numbering = "FDI" (cs/pipeline.py:556-561). A cópia mantém seus inteiros Universal sob o nome Universal, de modo que o relatório anuncia uma numeração que o arquivo não contém. Observado: uma malha sintética com um array Universal_ID foi passada por segment_crowns com fdi=True e array_name="FDI_ID"; o relatório dizia numbering: "FDI" e array_name: "FDI_ID", e o arquivo de saída continha apenas Universal_ID com seu valor original. O motor de segmentação não está instalado no ambiente usado, então o status do caso foi engine_unavailable em vez de already_segmented; o caminho da cópia é o mesmo. Os testes não cobrem esse cruzamento (tests/test_run.py:488-503).

Quatro nomes reconhecidos aqui, três a jusante

O Crown_Seg trata uma malha como segmentada se ela contém qualquer um entre PredictedID, UniversalID, Universal_ID ou FDI_ID (cs/pipeline.py:56). O ALI_IOS, o ASO e o AREG_IOS leem apenas os três primeiros (ali_ios/surface.py:19, SADT-VISOR tools/ASO/src/sadt_aso/markups.py:19, AREG_IOS/src/sadt_areg_ios/surfaces.py:39). Uma malha que tem somente FDI_ID passa, portanto, pelo Crown_Seg e é recusada pela ferramenta seguinte: é intencional (o próprio comentário da ferramenta diz isso, cs/pipeline.py:64-80), mas sem nenhum sintoma antes dessa ferramenta seguinte. O comentário do ALI_IOS que diz que esses são “the same three names CrownSeg writes and recognizes” (ali_ios/surface.py:18) é inexato. Lido no código.

Malhas em .vtp ou .obj são invisíveis para o Crown_Seg

O Crown_Seg descobre apenas .vtk e .stl (cs/pipeline.py:51,292-320), enquanto o AREG_IOS aceita .vtk .vtp .stl .obj como entrada (AREG_IOS/src/sadt_areg_ios/surfaces.py:35) e, no modo Fully-Automated, entrega sua pasta ao Crown_Seg (dispatch.py:172-173). Uma pasta que contenha apenas essas malhas é recusada (“No surface mesh found in the input”, cs/pipeline.py:314-319); em uma pasta mista elas ficam fora da saída do Crown_Seg, que é a pasta com a qual o AREG_IOS continua. A cópia da chamada no ALI_IOS legado lia .vtp (segmentation.py:33-56). Lido no código; não executado.

Duas árvores de saída: leia o relatório

Uma malha segmentada cai em crownseg_input_<suffix>/, uma malha que já estava rotulada cai ao lado do seu caminho relativo, de modo que um glob sobre uma árvore deixa passar a outra (cs/pipeline.py:369-381,480-487). O ALI_IOS lê cases[key].produced do run_report.json (ali_ios/dispatch.py:240-252), que é para isso que o relatório serve. Uma malha de uma instalação degradada carrega o status engine_unavailable e, mesmo assim, é copiada com seu caminho produced (cs/pipeline.py:495-505), de modo que um cliente que filtrasse só por already_segmented a ignoraria. Lido no código.

O grafo de ferramentas na documentação do servidor está desatualizado

VISOR-serve docs/TOOL_GRAPH.md:27-28,43 lista o ALI_IOS como uma folha. O schema que o ALI_IOS publica declara calls = ['Crown_Seg'] (observado com scripts/describe.py no ambiente do ALI_IOS), porque seu dispatch chama Crown_Seg por meio de uma constante de módulo (ali_ios/dispatch.py:58,229). O documento diz que é gerado a partir desses schemas e verificado na inicialização; a cópia no repositório é mais antiga que o código.

Documentação que discorda do código

O README diz que o modelo é um argumento obrigatório (README.md:33), e a docstring do pipeline também (cs/pipeline.py:16-23); o argumento é opcional, com um padrão vazio que resolve para a pasta própria da ferramenta (cs/__init__.py:41, comentário em cs/__init__.py:35-40). O README também nomeia a pasta DATA/CrownSeg/testfiles (README.md:178) enquanto o código e o manifesto usam DATA/Crown_Seg, e conta 176 testes (README.md:225,232) onde 162 funções de teste são definidas em tests/ (uma contagem de def test_; a parametrização pode explicar a diferença). O AREG nunca passa device ao Crown_Seg, ao contrário do ALI_IOS (SADT-VISOR tools/AREG/AREG_IOS/src/sadt_areg_ios/tools.py:113-130), de modo que em um servidor só de CPU o cuda padrão recua para a CPU com um aviso, ou é substituído pelo DEVICE do servidor. Lido no código.

O que a ferramenta protege

O checkpoint é resolvido antes de qualquer arquivo ser criado, de modo que um pedido recusado não deixa nada para trás (cs/pipeline.py:407-413); uma pasta que contém dois checkpoints é recusada com os dois nomeados, de modo que a idade dos pesos nunca é silenciosa (cs/pipeline.py:244-251); a saída padrão do shapeaxi, que carrega nomes de arquivo, é engolida (cs/pipeline.py:365); a pasta temporária é removida em um finally (cs/pipeline.py:435-439); a entrada nunca é modificada. Lido no código.

Reprodutibilidade

O README da ferramenta informa que a predição bruta PredictedID é idêntica bit a bit a um port de referência, e que o Universal_ID pós-processado varia de uma execução para outra, inclusive entre duas execuções do mesmo código (826 a 2,607 pontos de 294,260).
