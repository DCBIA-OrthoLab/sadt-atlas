Empacotamento e implantação

Como o VISOR-serve é construído em um único contêiner, onde ficam os modelos e a configuração fora dele, qual é o padrão de cada configuração, quais scripts sobem um servidor e o mantêm atualizado, o que os benchmarks publicados com o repositório mediram e o que não mediram, e o que uma inspeção datada de uma instância em funcionamento encontrou. O servidor é uma imagem Docker com um único ambiente Python 3.13 de API que nunca carrega o torch, e um ambiente virtual com hardlinks por ferramenta.

Nota

As citações são file:line no VISOR-serve no commit e9a7e5d, que é o main (e91557e) mais um commit que toca apenas server/deployment.toml (ele declara a pasta de dados do VFACE). As ferramentas em si estão no SADT-VISOR em 6ba2a78. "Legado" neste site significa os módulos do Slicer do SlicerAutomatedDentalTools; nada abaixo se aplica a eles. O que a seção 7 diz sobre uma instância em funcionamento vem de uma inspeção datada de 2026-10-20, não do código. A proteção do transporte, os tokens e as afirmações sobre o tratamento de dados estão em a página de segurança; a forma do sistema inteiro está em a página de arquitetura.

1. A imagem

Há um contêiner para todas as ferramentas. O docker/Dockerfile (232 linhas) o constrói em estágios. O estágio de runtime parte de python:3.13-slim (:76), instala a única biblioteca de sistema que nenhum lockfile pode fornecer, libgomp1 (:86), copia o uv 0.12.3 (:89) e constrói o ambiente da API em /opt/sadt/.venv a partir de server/requirements-api.txt, que lista apenas fastapi, uvicorn[standard], python-multipart e pydantic-settings (:105-108). O processo do servidor, portanto, não importa torch, nem nnU-Net, nem MONAI. O interpretador de cada ferramenta é instalado pelo próprio uv (:75), de modo que as ferramentas podem usar versões diferentes do Python.

  • As ferramentas já vêm na imagem. Cada ferramenta empacotada é uma pasta /tools/<name>/ com .venv, src/ e .schema.json; as ferramentas em uma pasta de grupo (tools/ALI/ALI_CBCT) são encontradas porque a descoberta desce dois níveis (registry/__init__.py:114). O pacote naming/ é copiado para /naming porque as ferramentas dependem dele por caminho (Dockerfile:122). As duas fixtures em processo Example_Tool e Test_Tool estão na imagem: COPY server/ leva server/tools/ e o .dockerignore:18-30 explica que a exclusão foi removida, para que uma implantação nova possa provar autenticação, upload, execução e resultado antes de qualquer modelo ser baixado. A instância em funcionamento serve as duas (23 entradas).
  • Uma única camada uv sync, de propósito. O uv sync --frozen --no-install-project --no-dev --all-extras de cada ferramenta roda em um único RUN (:152), com UV_LINK_MODE=hardlink e o cache do uv no próprio sistema de arquivos da imagem (:96-101). Divididos em várias camadas, o overlayfs copia os arquivos para cima e os hardlinks se quebram; o próprio comentário do Dockerfile mede as onze ferramentas com torch em cerca de 26 GB compartilhados contra cerca de 63 GB duplicados (:131-134). O --all-extras é deliberado: uma ferramenta como Crown_Seg mantém seu motor atrás de um extra, e sem ele a imagem importa e depois responde 503 na primeira requisição real.
  • verify_dedup.py. Nada observável falha quando os links viram cópias em silêncio, então o docker/verify_dedup.py verifica isso: para arquivos que pertencem à mesma distribuição na mesma versão (lida no RECORD de cada ambiente), um segundo inode significa uma cópia. Ele sai com código diferente de zero em qualquer caso, usa apenas a biblioteca padrão e é enviado na imagem em /opt/sadt/verify_dedup.py (Dockerfile:200). As fixtures de teste são numpy_old (1.26.4, Python 3.12), numpy_new (2.5.2, Python 3.13) e numpy_twin.
  • Os esquemas são gerados na construção executando o describe.py de cada ferramenta com o interpretador dessa ferramenta (:177-188); uma ferramenta que não consegue se descrever é reportada e não é servida. Na inicialização, um esquema desatualizado é regenerado e guardado em cache em SCHEMA_CACHE_DIR (/var/cache/sadt), porque /tools é somente leitura para o servidor.
  • Fora da imagem: modelos e arquivos de teste (seção 2), o deployment.toml de cada site (seção 4; a imagem traz uma cópia padrão que um mount substitui), o espaço de trabalho dos jobs /jobs e o token da API.
  • Processo. USER sadt, não root (:227); o código em /tools pertence ao root e é somente leitura para o servidor, para que código de terceiros não possa reescrever o próprio ambiente virtual; o CMD é uvicorn main:app --host 0.0.0.0 --port 8000, sem --reload e sem --workers, portanto um processo e uma fila de admissão (:232). Não há nenhum HEALTHCHECK no Dockerfile nem no docker-compose.yml.

O ambiente que a imagem define (Dockerfile:202-216) é SADT_DISPATCH_MODE=subprocess, TOOLS_DIR=/tools, RUNNER_PATH=/opt/sadt/server/execution/runner.py, DESCRIBE_PATH=/tools/scripts/describe.py, SCHEMA_CACHE_DIR=/var/cache/sadt, DEPLOYMENT_CONFIG=/opt/sadt/server/deployment.toml, DATA_DIR=/DATA, TEMP_DIR=/jobs e PYTHONDONTWRITEBYTECODE=1. O padrão de SADT_DISPATCH_MODE em config.py:37 é inprocess, marcado como temporário; a imagem o sobrescreve, de modo que o que o contêiner executa é sempre o caminho por subprocesso.

O arquivo compose define vários serviços. O que é uma implantação real é inference-venvs (perfil venvs, docker-compose.yml:200): ele constrói o docker/Dockerfile com um contexto de build nomeado tools=${TOOLS_CONTEXT:-docker/fixtures}, de modo que, sem TOOLS_CONTEXT, constrói as pequenas fixtures, não as ferramentas reais. Ele define shm_size: 8gb (o nnU-Net passa dados entre workers de exportação por memória compartilhada; os 64 MB padrão falham com uma mensagem que nomeia o recurso errado), reserva todas as GPUs e reinicia com unless-stopped. Os outros serviços são inference (uma imagem de GPU pré-construída vinda de um registro de contêineres, com ./server montado, pip executado a cada início e uvicorn --reload), inference-cpu e os serviços test / test-gpu. O docker-compose.dev.yml é uma sobreposição que monta server/ e o src/ de cada ferramenta a partir de um checkout do SADT-VISOR, somente leitura.

Armadilha

A documentação dentro do repositório ainda descreve imagens mais antigas. O comentário do Dockerfile em :193-195 diz que server/tools/ é excluído pelo .dockerignore, o que não é mais verdade (.dockerignore:18-30). Os comentários em :11-12 e :217 ainda contam quinze ferramentas ou upstreams; há 19 ferramentas empacotadas. O docker/README.md:45-48 diz que uma ferramenta aninhada um nível mais fundo "is NOT discovered by the server today", mas a descoberta desce dois níveis e cinco ferramentas servidas (ALI_CBCT, ALI_IOS, AREG_CBCT, AREG_IOS, AREG_IOSCBCT) estão em pastas de grupo. O docker/README.md:4 coloca o runner.py em /opt/sadt/runner.py; ele está em server/execution/runner.py.

2. Modelos e arquivos de teste

Os pesos nunca estão na imagem e nunca são enviados por upload a partir de um laptop. Eles ficam em um diretório DATA/ montado somente leitura em /DATA: DATA/<slug>/models/<name> e DATA/<slug>/testfiles/<name>, opcionalmente um nível abaixo como escopo (DATA/AREG/testfiles/CBCT_T1). O LocalDataStore o lê; outro backend pode ser conectado pela classe abstrata DataStore (DATA_BACKEND, config.py:31).

  • Qual pasta. O slug é o data_dir declarado pela ferramenta; se não houver, o nome literal da ferramenta quando essa pasta existe; caso contrário, o nome sem sublinhados, de modo que Batch_Dental_Seg lê DATA/BatchDentalSeg (deployment.data_slug, registry/deployment.py:311-325). Cinco ferramentas compartilham duas pastas por meio de data_dir = "AREG" (três ferramentas) ou "ALI" (duas).
  • Quais argumentos são preenchidos a partir dela. Por convenção de nomes (registry/conventions.py): model, *_model e *_reference são publicados como um nome escolhido em DATA/<tool>/models/, nunca como upload, de modo que os pesos não podem ser enviados por um cliente. Um upload de arquivo em um desses campos resulta em 400 (main.py:1269-1278). Qualquer outro path pode ser enviado por upload ou preenchido a partir de testfiles/.
  • O que a API oferece. GET /tools/{tool}/data lista modelos e arquivos de teste; GET|HEAD /tools/{tool}/testfiles/{name} serve um arquivo de teste. Não há rota que sirva um modelo (download_testfile só lê testfiles). Uma pasta de arquivos de teste é compactada em zip na hora e enviada com Accept-Ranges: none; caso contrário, o cliente sonda, vê os ranges e divide uma coorte de 339 MB em 43 partes, com o servidor construindo o mesmo arquivo 43 vezes: 39,1 s com ranges contra 1,5 s inteiro (main.py:794-806).
  • Preenchimento. O scripts/data-manifest.yml diz o que existe, de onde vem e para onde vai; o scripts/fetch_data.py (somente biblioteca padrão) o baixa, setup-models.sh e setup-testfiles.sh são wrappers, e --list imprime os tamanhos por ferramenta sem baixar nada. Uma entrada tem um name, uma url, um sha256 opcional (uma divergência descarta o arquivo; quando ausente, o script imprime o hash obtido, para ser colado no manifesto), um size opcional, extract: true para descompactar um zip e manter a pasta, e dest para renomear ou agrupar vários arquivos em uma pasta de bundle. O comentário do manifesto estima o conjunto inteiro em cerca de 29 GB em 14 ferramentas, 12 GB deles de modelos CBCT do ALI.

Armadilha

O padrão do compose ${API_TOKEN:-dev-token} significa que uma instalação que não escreve um .env roda com um token público, porque está em um arquivo versionado. O mapeamento de porta "${BIND_ADDR:+${BIND_ADDR:-}:}${VENVS_HOST_PORT:-8001}:8000" (docker-compose.yml:224) publica em todas as interfaces quando BIND_ADDR não está definido. O caminho pelo scripts/server_ctl.py gera um token e define BIND_ADDR como 127.0.0.1 por padrão (server_ctl.py:368,398); iniciar o compose à mão não faz isso.

4. deployment.toml

O server/deployment.toml guarda o que é específico de uma instalação. Ele é lido uma vez na inicialização e montado somente leitura no contêiner sobre a cópia da imagem, de modo que mudar uma linha não exige reconstruir a imagem (docker-compose.yml:215-220). Cada tabela [tools.<name>] pode conter exatamente estas chaves (_TOOL_KEYS, registry/deployment.py:69): server_selectable, max_upload_mb, data_dir, hidden, timeout_seconds, dispatch, batch, width_from. server_selectable aceita model, testfile ou none, com um escopo escrito testfile:Sub_folder (:53, SCOPE_SEPARATOR). Um arquivo ilegível ou uma chave desconhecida é fatal (DeploymentConfigError); a recusa de um valor que o servidor não conhece traz a marca DEPLOYMENT-CONFIG-AHEAD-OF-SERVER (:66), porque o arquivo é montado e pode ser mais novo que a imagem.

O que o arquivo em e9a7e5d realmente declara (292 linhas, 14 seções, nenhuma com timeout ou limite de upload):

Uma facade (ALI, AREG) não tem pasta nem interpretador. Seu esquema é composto na inicialização a partir da tabela dispatch: um argumento mode inicial, depois a união dos argumentos dos alvos, cada um visível apenas nos modos que o têm (registry/facade.py:49-98). O mesmo nome de argumento deve ter o mesmo tipo, as mesmas extensões aceitas e a mesma obrigatoriedade em todos os alvos, caso contrário a facade é ignorada com um aviso; só é fatal se seu nome colide com uma ferramenta já servida (facade.py:282-295).

O arquivo não está vazio, apesar do que diz seu cabeçalho

O server/README.md:540 diz que o deployment.toml "is therefore an empty file of comments today", e as primeiras linhas do próprio arquivo dizem "this file has no entries" (server/deployment.toml:1-4). Ambos são falsos neste commit: o arquivo tem 14 seções, que é o que faz funcionarem as facades do AREG e do ALI, a pasta de dados do VFACE e as declarações de lote e de largura por ferramenta.

Atualização automática. SADT_AUTO_UPDATE é off (padrão), notify ou apply (server_ctl.py:838-850). O apply espera até que /status informe nenhuma execução em andamento nem em espera, fecha a porta por POST /maintenance com uma concessão de 60 s que ele renova (:911, GATE_LEASE_SECONDS), executa git pull --ff-only (:1178), relança com up -d --force-recreate (:1205, nunca restart) e reabre. Ele recusa uma mudança em um lockfile, em um pyproject.toml, em server/requirements* ou em docker/, pois esses exigem uma nova imagem (:522-524). O cabeçalho da própria unit adverte que a máquina "will execute code pulled from a public repository" e que nenhum commit nesses repositórios é assinado hoje; passá-lo para apply é descrito como uma decisão de quem responde pela máquina.

7. O que uma inspeção de uma instância em funcionamento encontrou

Uma observação datada, não uma propriedade do código

Uma instância em funcionamento foi inspecionada em 2026-10-20 (um relatório guardado fora dos repositórios). O que ele encontrou sobre aquela máquina pode já não ser verdade. Esta seção guarda o que o código explica; os detalhes que identificam a máquina ou sua rede foram deliberadamente omitidos. A única verificação feita ao escrever esta página foi um GET /health e um GET /tools sem autenticação: responderam {"status":"ok"} e 23 entradas.

  • O que o código prevê, aconteceu. GET /health e GET /tools responderam sem token, e GET /status recusou uma requisição sem token (401). O catálogo tinha 23 entradas, 19 delas a partir de um esquema. O log de inicialização não tinha nenhum skip, erro ou traceback; seus únicos avisos eram as chaves de esquema ignoradas de ALI_CBCT, ALI_IOS e ASO, explicadas em a página de arquitetura.
  • HTTP simples, direto do contêiner. O cliente Slicer do AutomatedDentalToolsRemote exige HTTPS com um certificado assinado publicamente e não tem alternativa (página de segurança), de modo que não consegue se conectar a uma instância exposta dessa forma; um script que chama a API diretamente consegue.
  • Sem .env. A instância havia sido iniciada sem um, então rodava com os padrões do compose descritos na seção 3, incluindo o token.

O relatório lista então o que pode interromper uma execução sem supervisão. Cada ponto abaixo foi conferido com o código; o relatório marca os quatro primeiros como derivados do código, da configuração e do log, não de uma execução real.

  1. Sem timeout. TOOL_TIMEOUT_SECONDS é 0 e o deployment.toml não define nenhum (config.py:77): quatro execuções bloqueadas congelam o servidor sem que nenhuma delas falhe.
  2. Uma ferramenta não medida roda sozinha. Uma ferramenta cujo custo nunca foi medido reserva o orçamento inteiro (execution/admission.py:22-33). Naquela instância, a maioria das ferramentas ainda não tinha custo medido, de modo que o max_parallel_jobs: 4 anunciado superestimava a vazão real.
  3. As reservas seguem a pior execução recente. O custo aprendido é o máximo das últimas COST_WINDOW = 20 execuções (config.py:106), de modo que uma ferramenta cujo uso de memória varia muito entre as entradas reserva seu pior caso e serializa.
  4. Sem valor de VRAM. Naquela instância, /status devolveu vram_bytes: null e uma placa com free_bytes: null: a sonda, que chama o nvidia-smi (resources.py:193), não devolveu nada, e o /status tolera isso por projeto (main.py:470-474). A admissão passa então a trabalhar com núcleos e RAM.
  5. Uma execução que falha ainda ensina a tabela de custos. A medição é guardada antes do ramo de erro, de propósito, porque uma execução com falta de memória é a medição mais útil (execution/dispatch.py:800-803). Um bench que falha por um motivo não relacionado pode, portanto, inflar reservas posteriores.
  6. Sem healthcheck no Dockerfile nem no compose: restart: unless-stopped relança um contêiner morto, mas nada detecta um contêiner vivo e travado.
  7. Um SIGKILL de operador parece uma morte por falta de memória. Um SIGKILL sem result.json é lido como o kill por falta de memória do kernel (execution/dispatch.py:930-949), e por isso a execução é iniciada de novo.

8. Os benchmarks publicados com o servidor

benchmarks/ é um harness reexecutável (python -m benchmarks.run --campaign b1..b5 [--dry-run]), configurado por config.yaml. Existem três caminhos de execução: local (a ferramenta em seu próprio interpretador, sem HTTP, com quatro diferenças documentadas em NOTES-local-path.md), loopback (a API HTTP na mesma máquina) e lan, que nunca foi medido: server.lan_base_url é null (config.yaml:22). O cliente HTTP do harness fala o protocolo do cliente Slicer: partes de 8 MB, quatro transferências simultâneas, um SHA-256 por parte, gzip, X-Result-Delivery: reference, downloads por ranges. As estatísticas são a mediana com a faixa completa, nunca a média; a repetição 1 de cada configuração é descartada como aquecimento, mas mantida no arquivo bruto com warmup: true; uma execução que falha é um registro, nunca removida.

A paridade byte a byte entre o caminho local e o caminho HTTP está estabelecida para uma ferramenta, o AREG_IOSCBCT, em uma sessão (n = 1 par). Não está estabelecida em geral. O controle mostra que a maioria dessas ferramentas nem sequer se reproduz byte a byte no mesmo caminho, porque seus relatórios trazem durações ou caminhos, e uma comparação de bytes não distingue um relatório de dados. O README do repositório diz que o harness reproduz todos os números de tempo de execução do artigo que o acompanha; isso vale para B1, B3 e B4, que têm resumos, enquanto B2 e B5 precisam ser lidos nos arquivos brutos.
