DOCShapeAXI no VISOR: o código

Para desenvolvedores: o que o port do DOCShapeAXI para o VISOR faz no código, com referências file:line, assinaturas, argumentos, ambiente, as diferenças em relação ao código legado e os achados. A explicação legível do mesmo pipeline, com a matemática, está na página do atlas.

VISOR Código Atlas (explicação) Página do legado Guia (VISOR)

As referências desta página nomeiam um repositório, depois um caminho dentro dele, depois uma linha: SADT-VISOR é o catálogo de ferramentas (commit 6ba2a78), VISOR-serve o servidor (e9a7e5d), Remote o cliente do Slicer (AutomatedDentalToolsRemote 19b95e8), legado o SlicerAutomatedDentalTools em 3c67957. Um caminho solto como catalog.py:50 está em SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/. Tudo foi lido no código; nada nesta página foi executado, exceto as duas verificações nomeadas onde aparecem (a comparação de arquivos do shapeaxi 1.0.10 com o 1.1.1, e um pequeno teste em CPU de índices repetidos). Visão geral da pilha: VISOR.

3.2 Superfícies, dispositivo e rede

Explicação em linguagem simples e matemática: página do atlas.

  • Descoberta: um único .vtk, ou uma pasta percorrida recursivamente, arquivos ocultos ignorados, ordenada (pipeline.py:22,40-64). Não encontrar nada é um ValueError, "DOCShapeAXI reads surfaces, not volumes" (__init__.py:59-64). O ponto de montagem dado ao shapeaxi é a pasta de entrada, ou a pasta do arquivo no caso de um único arquivo (:71).
  • Dispositivo: cuda recorre a cpu com um aviso quando nenhuma placa é visível (pipeline.py:67-72).
  • Rede: load_network verifica que a classe nomeada pelo catálogo existe em shapeaxi.saxi_nets_lightning, depois que o backbone EfficientNet está preparado, depois coloca em allowlist as classes que o checkpoint serializa com pickle, e o carrega (pipeline.py:130-151):
network_class = getattr(saxi_nets_lightning, network_name, None)   # else ValueError
check_backbone_is_staged()      # <torch hub dir>/checkpoints/efficientnet-b0-355c32eb.pth, else FileNotFoundError
allow_checkpoint_globals()      # shapeaxi transform classes + torchvision Compose
model = network_class.load_from_checkpoint(checkpoint, strict=False)
model.eval(); model.to(device)

A allowlist existe porque o torch 2.6 tornou weights_only=True o padrão e esses checkpoints carregam suas transformações de treinamento em hyper_parameters (pipeline.py:108-127). strict=False é mantido do legado (legado DOCShapeAXI_CLI.py:135,201).

3.3 Passagem de predição

Explicação em linguagem simples e matemática: página do atlas.

A lista de arquivos é um DataFrame do pandas montado em memória (o legado gravava um CSV na pasta de saída com o modo 'a', DOCShapeAXI_CLI.py:111-118), entregue ao SaxiDataset do shapeaxi com EvalTransform(scale_factor), sendo o fator de escala lido dos hiperparâmetros do checkpoint (engine.py:11-34); o shapeaxi 1.1.1 depois o ignora (veja a verificação abaixo). Em seguida, uma superfície por vez (engine.py:37-64):

mesh = model.create_mesh(vertices, faces, normals)
points = model.sample_points_from_meshes(mesh, model.hparams.sample_levels[0])
views, _ = model.render(mesh)
output = model(points, views)
if not analysis.is_regression:
    output = torch.argmax(softmax(output).detach(), dim=1, keepdim=True)
predictions.append(float(output.reshape(-1)[0].cpu()))

Cada predição é registrada com o caminho da superfície relativo ao ponto de montagem e com class (um inteiro) ou score (um float, regressão) (__init__.py:81-90). A amostragem de pontos e a renderização são do shapeaxi; nem a ferramenta nem o legado fixam uma semente aleatória (nenhum seed ou manual_seed nas fontes da ferramenta).

3.4 Passagem de explicação (Grad-CAM)

Explicação em linguagem simples e matemática: página do atlas.

Somente quando explain é verdadeiro (__init__.py:92-95). O dataset é reconstruído e cada superfície é renderizada de novo; depois, para cada classe k em range(analysis.classes) (engine.py:67-114):

cam = LayerGradCam(model, model.convnet.module._blocks[-1], device_ids=[0])
attribution = cam.attribute(inputs=(points, views), target=k, attr_dim_summation=False)
attribution = attribution.sum(dim=1).cpu().detach()
scaled = scale_attribution(attribution.numpy(), (224, 224))   # resize, clip 1/99 percentiles, rescale to [-1, 1]
projected = gradcam_process(_Namespace(device, target_class=k), scaled, faces, per_face, vertices)
surface.GetPointData().AddArray(projected)                    # array grad_cam_target_class_<k>
post_process.MedianFilter(surface, projected)
  • Redimensionamento: torch.nn.functional.interpolate, bilinear, align_corners=False, em vez do cv2.resize do legado; o comentário diz que um teste fixa os dois em 1e-5 (pipeline.py:163-184, pyproject.toml:45-51).
  • Normalização: corte nos percentis 1 e 99, depois mapeamento para [-1, 1]; um mapa plano vira zeros em vez de NaN (pipeline.py:186-199).
  • Qual camada: o último bloco do ramo EfficientNet 2D, como no legado (DOCShapeAXI_CLI.py:150-151): o mapa explica o ramo multivista, não o ramo de nuvem de pontos.
  • Projeção: gradcam_process é do shapeaxi (saxi_gradcam.py:112-144 no 1.0.10 e no 1.1.1, o mesmo código). As faces começam em 0 e tomam maximum(old, new) vista após vista, de modo que na malha uma face guarda max(0, max over views) e a faixa é [0, 1]; o valor vai para o primeiro vértice da face, e os vértices que não são o primeiro vértice de ninguém são zerados (:134). Dentro de uma vista, os pixels que mostram a mesma face compartilham um índice e a escrita que permanece não é definida (a última na CPU, não o máximo); os pixels de fundo carregam o índice -1 e escrevem na última face. O teste em CPU e os detalhes estão na página de código legado, seção 5d; nada foi executado na GPU.
  • Filtro de mediana: post_process.MedianFilter (post_process.py:294-308) substitui todo vértice, preenchido ou vazio, pela mediana de seus vizinhos, ele mesmo excluído (utils.py:363-376), e não apenas os vazios.
  • Nomes de array: o índice da classe é sempre passado como target_class, que nomeia o array (engine.py:104-106,117-129). O legado só o definia quando num_classes > 1 (DOCShapeAXI_CLI.py:171-174), então o checkpoint de regressão agora também recebe um nome por classe, grad_cam_target_class_0. Lido no código.
  • Gravação: uma vez por superfície depois de todas as classes, em plano em output_dir sob o nome base da entrada (engine.py:111-113); o legado gravava dentro do laço de classes, em <out>/explainability/<task>/ (DOCShapeAXI_CLI.py:153,185-186).

8. Constatações no VISOR

Explicação em linguagem simples e matemática: página do atlas.

O backbone EfficientNet é um pré-requisito que ninguém prepara

O shapeaxi constrói uma EfficientNet-B0 em torno de cada checkpoint. A ferramenta se recusa a deixá-la ser baixada no meio de um pedido e, em vez disso, levanta FileNotFoundError a menos que efficientnet-b0-355c32eb.pth já esteja em <torch hub dir>/checkpoints/ (SADT-VISOR tools/DOCShapeAXI/src/sadt_docshapeaxi/pipeline.py:80-105, chamado por load_network em :146; README.md:112-121). Nem o manifesto de dados nem nenhum script do VISOR-serve menciona esse arquivo (busca por "efficientnet" nos três repositórios: só o README.md da própria ferramenta, pipeline.py e tests/test_run.py o fazem). Uma implantação que segue as etapas usuais de staging, portanto, falha na primeira chamada, depois de as superfícies terem sido enviadas. Lido no código; não foi verificado se um servidor específico tem o arquivo em seu cache.

A linha de status mostra pontos de interrogação

O cliente monta seu resumo a partir de report.get("data_type") e report.get("checkpoint") (Remote DOCShapeAXIRemote/DOCShapeAXIRemote.py:122-130). O relatório gravado pela ferramenta não tem nenhuma das duas chaves: tem model, anatomy, task, classes e network (SADT-VISOR __init__.py:97-110). O resumo do painel mostrará "?" no lugar da anatomia e do checkpoint, enquanto task e a contagem de superfícies são preenchidos. Lido no código, não executado no Slicer.

O cliente descreve uma tabela de predições e um seletor de tarefa que não existem

Os comentários do cliente dizem que o resultado é uma "prediction table" em formato CSV (DOCShapeAXIRemote.py:76-86) e que um argumento task se restringe à anatomia por uma regra options_when (:12-17). A ferramenta não grava nenhum CSV (__init__.py:97-110), e seu esquema tem seis argumentos, nenhum chamado task, sem options_when (saída de scripts/describe.py). A tarefa é escolhida ao se escolher o arquivo de checkpoint, então o usuário precisa saber o que significam airways_2_class.ckpt e airways_4_regress.ckpt.

Duas entradas com o mesmo nome de arquivo colidem na saída

As superfícies são encontradas recursivamente mas gravadas em plano: a/s.vtk e b/s.vtk vão ambos para output_dir/s.vtk (engine.py:111-112), de modo que a segunda substitui a primeira, enquanto o relatório as mantém separadas pelo caminho relativo (__init__.py:84). A etapa de renomeação então move s.vtk para s_pred.vtk uma vez por entrada (__init__.py:128-132): a segunda movimentação não encontra arquivo, o que encerraria a execução com um FileNotFoundError depois de todo o cálculo; com um output_suffix vazio, a sobrescrita é silenciosa. O CLIC e o CNE reproduzem a árvore de entrada justamente para evitar isso. Lido no código, não executado.

Ainda verdade desde o legado: amostragem sem semente, saliência de um só ramo

Nenhuma semente é definida em lugar algum nas fontes da ferramenta e não há argumento seed, de modo que a amostragem aleatória de pontos dentro do shapeaxi (engine.py:54,92) não é fixa de uma execução para outra, como no legado (página legado, armadilhas). A camada do Grad-CAM é o último bloco do ramo de vistas 2D (engine.py:82-83), então o mapa não diz nada sobre o ramo de nuvem de pontos. Lido no código.

Comentários que discordam dos pins

O comentário acima do pin do captum fala em 0.9.0 enquanto o pin é captum==0.8.0 (pyproject.toml:39-44). O manifesto de dados ainda rotula a ferramenta como "NOT PORTED YET" (data-manifest.yml:595). Nenhum dos dois muda o que é executado.

Verificado: a incompatibilidade legada do shapeaxi está corrigida aqui

O código legado é escrito para a API 1.x do shapeaxi, enquanto seu instalador pede 2.0.2 ou posterior (legado ADT/ADTLib/env/install_pytorch.py:385). O VISOR fixa shapeaxi==1.1.1, com o motivo no comentário (pyproject.toml:18-30), e resolve as classes de rede a partir de saxi_nets_lightning, onde elas ficam (pipeline.py:135-145). O checkpoint não é mais copiado para a pasta de saída. O EvalTransform do shapeaxi 1.1.1 também não respeita scale_factor: UnitSurfTransform.__call__ nunca o repassa (saxi_transforms.py:48-57), idêntico no 1.0.10 e no 1.1.1 (os dois pacotes diferem apenas em __about__.py, comparados arquivo por arquivo para esta passada; 1.1.1 baixado do índice de pacotes).
