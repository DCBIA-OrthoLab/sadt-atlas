CNE no VISOR: o código

Para desenvolvedores: o que o port do CNE para o VISOR faz no código, com referências file:line, assinaturas, argumentos, ambiente, as diferenças em relação ao código legado e os achados. A explicação legível do mesmo pipeline, com os pequenos cálculos que ele contém, está na página do atlas.

VISOR Código Atlas (explicação) Página do legado Guia (VISOR)

As referências nesta página citam um repositório, depois um caminho dentro dele, depois uma linha: SADT-VISOR é o catálogo de ferramentas (commit 6ba2a78), VISOR-serve o servidor (e9a7e5d), Remote o cliente do Slicer (AutomatedDentalToolsRemote 19b95e8), legacy SlicerAutomatedDentalTools em 3c67957. Um caminho solto como readers.py:41 está em SADT-VISOR tools/CNE/src/sadt_cne/. Tudo foi lido no código; nada nesta página foi executado, exceto as verificações de status HTTP datadas abaixo. Visão geral da pilha: VISOR.

Explicação em linguagem simples e matemática: página do atlas.

3. O pipeline

Explicação em linguagem simples e matemática: página do atlas.

3.1 Verificar as pastas e encontrar as notas

Explicação em linguagem simples e matemática: página do atlas.

Um caminho notes ausente é um FileNotFoundError (__init__.py:97-100). Se notes é uma pasta e output_dir é a mesma pasta (symlinks resolvidos), a execução é recusada, porque as extrações seriam lidas de volta como notas pela execução seguinte (:106-110,320-324). A ferramenta então cria o output_dir por conta própria (:116); o legado dependia do painel para criá-lo.

A descoberta é recursiva e devolve os arquivos ordenados pelo caminho relativo (readers.py:92-123). Ela mantém .txt, .pdf e .docx sem distinguir maiúsculas (:33,78-81), ignora nomes que começam com ~$ (arquivos de bloqueio do Word) ou com um ponto, e pastas chamadas __MACOSX (:60-61,84-90,117-118). A pasta de saída é excluída quando está dentro da entrada (__init__.py:118). Nada encontrado é um 422 que nomeia as três extensões (:119-126); o legado saía com status 0 nesse caso (legacy CNE_CLI/CNE_CLI.py:137-141).

3.2 Escolher e carregar o modelo

Explicação em linguagem simples e matemática: página do atlas.

model é obrigatório. Um arquivo .gguf é usado como está; uma pasta deve conter exatamente um .gguf, pesquisado recursivamente, ou a execução é recusada com os candidatos nomeados (extraction.py:89-128). Se o caminho do modelo nomeia um tipo de nota e notes_type é o outro, um aviso vai para o relatório; não é uma recusa (model_type_hint, extraction.py:131-143; __init__.py:132-142).

CONTEXT_TOKENS = {"TMJ": 6144, "Ortho": 2048}                # extraction.py:49
SYSTEM_PROMPTS = {"TMJ": INSTRUCTION_TMJ, "Ortho": None}      # extraction.py:51

window = context_for(notes_type, context_tokens)              # 0 means the type's default
offloading = wants_gpu and supports_gpu_offload()             # asked before the 4.4 GB load
engine = load_model(model_file, window, seed, -1 if wants_gpu else 0)   # __init__.py:144-165

load_model constrói um único llama_cpp.Llama(model_path, n_ctx, n_gpu_layers, seed, verbose=False) para o lote inteiro (extraction.py:193-203). A tagarelice do seu carregador é capturada com contextlib.redirect_stderr e registrada em nível debug (:63-86), onde o legado redirecionava o descritor de arquivo 2 do processo com os.dup2 e sem finally (legacy CNE_CLI.py:157-171). Todo import de llama_cpp passa por engine_module(), que primeiro tenta abrir o runtime CUDA do venv (extraction.py:167-177, dependencies.py:65); no build de CPU isso não faz nada. Um pedido device = "cuda" em um build sem suporte a GPU acrescenta um aviso e gpu_offload: false ao relatório (__init__.py:145-165,184).

3.4 Perguntar ao modelo

Explicação em linguagem simples e matemática: página do atlas.

messages = []

    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": text})   # extraction.py:156-164

                                      max_tokens=max_tokens, temperature=temperature)
content, finish_reason = choice["message"]["content"], choice.get("finish_reason")   # :206-223

    raise ValueError("the model's answer was cut off ...")                          # __init__.py:293-297

A instrução do TMJ é a string do legado, literal: "Using the following note, extract structured key-value pairs about the patient's symptoms and diagnoses:" (extraction.py:41-44). O Ortho não recebe mensagem de sistema, como no legado. A ferramenta não compara o comprimento da nota com a janela: context_for só rejeita um valor negativo (extraction.py:146-153), e qualquer erro lançado pelo llama.cpp é capturado para aquela nota (__init__.py:200-212). No llama-cpp-python 0.3.36 (llama.py:1343-1358) o motor só lança erro quando o prompt sozinho atinge n_ctx; caso contrário, max_tokens é reduzido a n_ctx menos o comprimento do prompt, a nota nunca é truncada, e uma geração interrompida por esse limite reduzido informa finish_reason == "length", o que faz a nota falhar (__init__.py:293-297). A versão fixada é a 0.3.35, cujo código não foi lido.

3.5 Ler a resposta e escrevê-la

Explicação em linguagem simples e matemática: página do atlas.

  1. Primeiro JSON: o trecho do primeiro { ao último } é interpretado; um dict sob "extraction" é desembrulhado; um resultado vazio ou um valor JSON que não é objeto é recusado (extraction.py:261-275). O recorte é o do legado.
  2. Depois, linhas key: value: uma chave começa com letra minúscula e contém letras minúsculas, dígitos, espaços e sublinhados (até 61 caracteres, os espaços viram _, extraction.py:230,296), pelo menos 60 % das linhas não vazias devem casar, e uma chave repetida mantém o primeiro valor (extraction.py:230-235,278-301). A fonte diz que o fine-tune TMJ publicado responde nesse formato, 46 campos e nenhum JSON (:244-245).
  3. Caso contrário, nada é escrito e a nota falha (__init__.py:299-305). O legado escrevia a resposta bruta.

Dois arquivos são escritos por nota na árvore espelhada (__init__.py:240-266,307-317): o JSON, canônico, e um texto key : value em que uma lista é unida por vírgulas e um dict aninhado continua JSON (extraction.py:304-328).

input   notes/P01/B_001.txt
output  output_dir/P01/Extraction_B_001.txt.json
        output_dir/P01/Extraction_B_001.txt.txt

plan_outputs verifica que duas notas não correspondem ao mesmo par antes de qualquer coisa rodar (__init__.py:240-266). O CNE_report.json traz tool, notes_type, model, system_prompt (um flag), context_tokens, max_tokens, temperature, seed, device, gpu_offload, warnings e, por nota, input, o leitor e a codificação, characters, finish_reason, answer_characters, status, fields, os dois caminhos de saída ou um reason; depois summary e duration_seconds (__init__.py:171-187,213-216,272-317). O texto da resposta em si não vai para o relatório nem para os logs.

3.6 Falhas

Explicação em linguagem simples e matemática: página do atlas.

Cada nota fica em seu próprio try: uma falha é registrada no log com o caminho relativo da nota e anotada no relatório, e o laço continua (__init__.py:191-213). Se nenhuma nota foi escrita, a execução lança erro: um 503 (ToolUnavailableError) quando todas as falhas foram de leitor ausente, caso contrário um 422 (ValueError) listando a razão de cada nota (:218-232); o relatório então não é escrito. Observe que essa linha de log por nota cita o arquivo, ao contrário das mensagens de progresso do CLIC.

8. Constatações no VISOR

Explicação em linguagem simples e matemática: página do atlas.

O texto das notas é enviado ao servidor

A afirmação do legado de que o CNE mantém o texto clínico na máquina ("no network exfiltration", página do legado §11, e o "Nothing leaves your machine" do Guia do legado) não vale para o VISOR. O painel do VISOR envia as notas que você seleciona a um servidor de ferramentas onde o modelo roda (Remote README.md:24-35; CNERemote/CNERemote.py:57 e o argumento notes do lado do servidor, Argumentos e schema). O README do Remote diz com todas as letras que não há desidentificação no cliente atual (README.md:32), e a página de segurança do VISOR lista a desidentificação dos arquivos enviados como apenas especificada (Desidentificação, Transporte). O que a própria ferramenta faz com o texto: ela executa o llama.cpp no processo e não contém nenhuma chamada de rede (um grep por urllib, requests, http e socket em tools/CNE/src/sadt_cne/ não encontra nenhuma), e o servidor escreve a resposta na pasta do job. O achado do legado continua verdadeiro somente para o módulo legado.

O cliente diz "automatic", mas nada associa o modelo ao tipo de nota

O README do Remote ("leave Model on automatic and the server uses the model fine-tuned for that note type", README.md:611-613) e a docstring de CNERemote/CNERemote.py:15-18 ("the model field defaults to (automatic)") estão desatualizados. model é um argumento obrigatório da ferramenta (__init__.py:49), e o cliente acrescenta sua entrada "(automatic)" apenas aos argumentos opcionais (Remote ServerToolsCore/ServerToolsCoreLib/base_widget.py:1074-1076, justificativa em formgen.py:107-109): o campo Model lista os bundles hospedados e envia o selecionado. Nada deriva o modelo de notes_type (resolve_model_file recebe um caminho, extraction.py:89-128); uma incompatibilidade entre os dois é apenas um aviso (callout seguinte). Lido no código, não executado no Slicer.

Só o modelo TMJ está hospedado

O manifesto de dados prepara um bundle, TMJ/qwen-ft-q4_k_m.gguf (VISOR-serve scripts/data-manifest.yml:687-692). notes_type = "Ortho" é aceito pela ferramenta, mas nenhum modelo Ortho está hospedado, e um modelo cujo caminho nomeia o outro tipo é apenas um aviso no relatório, não uma recusa (__init__.py:133-139, extraction.py:131-144). O comentário do manifesto de que o repositório Ortho "answers 404 today" (data-manifest.yml:682-686, repetido em SADT-VISOR tools/CNE/README.md:205-208) está desatualizado: em 2026-11-09 uma requisição HTTP HEAD na antiga URL Ortho dcbia/ respondeu 307 (um redirecionamento para a organização DCBIA-OrthoLab/), e uma em DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho/.../model-q4_k_m.gguf respondeu 302 para um download (só códigos de status, nada foi baixado). A URL do TMJ no manifesto também ainda usa o antigo nome dcbia/ e responde 307.

CPU, apesar do que dizem alguns comentários

O índice de wheels fixado para o llama-cpp-python é o de CPU (SADT-VISOR tools/CNE/pyproject.toml:60-67). Três comentários discordam dele: o cabeçalho do mesmo arquivo fala de um "CUDA 12.4 wheel index below" (:8-23); a descrição publicada de device diz "it needs the CUDA build of llama.cpp, which this tool pins" (__init__.py:82-84); e o arquivo compose do VISOR-serve diz que o CNE não pode rodar no serviço de CPU porque traz o build CUDA (docker-compose.yml:105-110). O código é o build de CPU, então um pedido cuda é registrado como ignorado. O README da ferramenta concorda com o código (SADT-VISOR tools/CNE/README.md:154-165). Não leia "o CNE precisa de uma GPU" em lugar nenhum.

Nenhuma proteção sobre o comprimento de uma nota

A preocupação do legado com notas longas (página do legado, §11) está resolvida só pela metade. Uma resposta cortada agora é recusada (__init__.py:293-297) e max_tokens tem como padrão 2048 em vez de 500. Mas nada compara a nota com a janela de contexto nem verifica se max_tokens deixa espaço nela: context_for só rejeita um valor negativo (extraction.py:146-153). Com o padrão do Ortho, o limite de resposta sozinho é igual à janela (2048 e 2048, :49, __init__.py:51). No llama-cpp-python 0.3.36 (llama.py:1343-1358) o motor só lança erro quando o prompt sozinho atinge n_ctx; caso contrário, reduz max_tokens a n_ctx menos o prompt e a nota nunca é cortada. Assim, com o Ortho, uma nota passa desde que a resposta termine dentro do que a nota deixa, e falha (finish_reason == "length") quando não termina; o que quer que o motor lance faz falhar aquela nota (__init__.py:200-212).

Os nomes de saída mudaram

Os arquivos são Extraction_<note file name>.json e .txt, não Extraction_<stem>.txt (__init__.py:240-266). Qualquer coisa que leia os nomes do legado, como o Dashboard legado (Extraction_*.txt), não encontraria os mesmos arquivos.

Verificado: as falhas silenciosas do legado foram fechadas

Um PDF só de imagem, uma resposta truncada e uma resposta que não é nem JSON nem campos agora fazem a nota falhar em vez de escrever um arquivo plausível (__init__.py:276-305); notas homônimas de formatos diferentes não se sobrescrevem mais (:240-266); a divisão de grafia TMJ/tmj sumiu (extraction.py:49-51); um pedido de GPU que não pode ser atendido é registrado (__init__.py:145-165).
