CNE, legado: o código

Para desenvolvedores: o que o módulo legado do Slicer CNE faz no código (SlicerAutomatedDentalTools em 3c67957), com referências file:line, blocos de código, argumentos, ambiente e armadilhas. A explicação legível do mesmo pipeline está na página do atlas.

não publicado VISOR CNE_CLI sem conda: Python do Slicer Bibliografia Código Atlas (explicação) Guia

Aviso de escopo. Diferentemente do AutoCrop3D e do AutoMatrix, o CNE não é um utilitário geométrico: não toca em nenhum volume, nenhuma malha, nenhuma coordenada. É um módulo de inferência de LLM que lê notas clínicas em texto livre e escreve pares chave-valor. No centro do módulo está um modelo GGUF quantizado, carregado pelo llama-cpp-python dentro do Python do Slicer.

Duas bases de código

Tudo o que está numerado abaixo descreve o módulo legado do Slicer (SlicerAutomatedDentalTools em 3c67957, 2026-10-26). O port para o VISOR, que roda a mesma ferramenta em um servidor, é descrito em sua própria página, CNE no VISOR. Uma consequência importa antes de continuar a leitura: onde esta página diz que o modelo roda localmente, isso vale apenas para o módulo legado. Com o VISOR, o texto da nota é enviado ao servidor (veja Achados no VISOR).

0. A sigla

Explicação em linguagem simples e matemática: página do atlas.

O repositório nunca desenvolve a sigla em nenhuma documentação: o README não tem seção sobre o CNE e também não documenta mais o MedX que ele substituiu, nenhum dos dois nomes aparece nele. O texto de ajuda do módulo (CNE.py:157) diz apenas "This tool helps to create summaries of clinical notes".

Duas linhas de log, e somente elas, dão a expansão: logger.info("CNE (Clinical Notes Extraction)") (CNE.py:342 e CNE.py:663), e a CLI publica o mesmo nome ao supervisor do Slicer: <filter-name>Clinical Notes Extraction</filter-name> (CNE_CLI.py:93). CNE = Clinical Notes Extraction, atestado pelo código e por mais nada.

Legado (3c67957); ausente do VISOR: nada é compilado nem instalado na estação de trabalho, o ambiente do servidor fixa llama-cpp-python==0.3.35 a partir de um índice de wheels pré-compilados (SADT-VISOR tools/CNE/pyproject.toml:60-67; veja CNE no VISOR). install_function (CNE.py:44) força CC=gcc e CXX=g++ durante a instalação e depois restaura os valores originais: isso é para o caso em que o pip precise compilar o llama-cpp-python a partir do código-fonte. No Windows esses valores são inutilizáveis.

Armadilha (também verdadeira no VISOR, agora relatada)

Também verdadeiro no VISOR: o índice fixado ainda é o de CPU (SADT-VISOR tools/CNE/pyproject.toml:60-67). O que mudou é que o pedido não é mais silencioso: device é um argumento explícito com padrão cpu, e um pedido cuda atendido por um build de CPU é escrito no relatório como gpu_offload e warnings (src/sadt_cne/__init__.py:145-165,184-185; veja CNE no VISOR). O índice extra aponta explicitamente para as wheels de CPU. Mesmo assim, a CLI pede n_gpu_layers=-1 com o comentário "Use GPU if available" (CNE_CLI.py:164): com um build só de CPU, esse parâmetro não tem efeito. Na prática a inferência roda na CPU, e um modelo de 7–8 B quantizado em Q4 é lento nela (o tempo por nota não foi medido para esta página).

A CLI testa de novo seus três imports (llama_cpp, fitz, docx) na inicialização e chama sys.exit(1) se algum estiver faltando (CNE_CLI.py:101-117): redundante, mas inofensivo, já que a CLI compartilha o interpretador do widget.

Cada um declara sua licença (Llama 3.1 para o Ortho, Apache 2.0 para o TMJ), o modelo base, o método (LoRA, r = 32, alpha = 64, depois mesclado e quantizado em Q4_K_M), que as notas de treinamento são dados de pacientes anotados e não são publicadas, e que os conjuntos foram divididos por paciente. O card do Ortho diz que o modelo recebe a nota bruta sem prompt de sistema, o que coincide com o código (§6), e lista características ortodônticas (calibre e material do fio, ligadura, elásticos, overjet, overbite, ...) como seu esquema. Nenhum dos cards relata uma avaliação. O arquivo TMJ tem 4,683,073,408 bytes (HTTP HEAD, 2026-11-10): 4.7 GB em unidades decimais e 4.4 em unidades binárias (GiB), de modo que o card e a caixa de download do TMJ (CNE.py:528) descrevem o mesmo arquivo com duas convenções de unidade. A caixa do Ortho (CNE.py:521) usa unidades decimais.

clean_text() (CNE_CLI.py:42) é a única etapa de pré-processamento, e sua motivação está dita no código: normalizar o que varia entre exportações de PDF/Word mas nunca apareceu nas notas de treinamento em texto simples, aspas e apóstrofos tipográficos para ASCII, travessão curto e travessão longo para -, espaço sem quebra para um espaço comum, depois colapso das linhas em branco consecutivas. 6. Inferência

Explicação em linguagem simples e matemática: página do atlas.

Uma única passada por arquivo, sem divisão em blocos (CNE_CLI.py:194-203):

messages = []
if notesType.upper() == "TMJ":
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": clinical_text})

Vale notar:

Armadilha (também verdadeira no VISOR)

Também verdadeiro no VISOR (SADT-VISOR tools/CNE/src/sadt_cne/extraction.py:51: SYSTEM_PROMPTS = {"TMJ": INSTRUCTION_TMJ, "Ortho": None}; veja CNE no VISOR). O modo Ortho não envia instrução. Só a nota bruta sai como mensagem do usuário; é o fine-tuning do modelo Llama-Ortho que deve carregar a tarefa. O modo TMJ, por contraste, mantém a instrução herdada do MedX.

  • create_chat_completion aplica o template de chat embutido no GGUF. Os dois modelos estão marcados como conversational no Hugging Face, então o template existe; ele não é visível nem controlável a partir do repositório.
  • temperature=0.1 e nenhuma seed: a saída é quase determinística, mas não exatamente reproduzível.
Armadilha (parcialmente verdadeira no VISOR)

VISOR (SADT-VISOR tools/CNE/src/sadt_cne/): max_tokens tem padrão 2048 em vez de 500 (__init__.py:46-56), e uma resposta cortada pelo limite é uma falha dessa nota, em vez de ser gravada (__init__.py:293-297). Continua valendo: nada confere o tamanho da nota com a janela, e nada confere max_tokens com ela também (extraction.py:146-153 só recusa uma janela negativa); um prompt que enche a janela levanta um erro dentro do llama.cpp, capturado por nota (__init__.py:200-212), enquanto uma nota longa que ainda cabe encurta a resposta, que o VISOR então recusa como cortada (veja CNE no VISOR). Nenhuma proteção de tamanho. n_ctx é 6144 (TMJ) ou 2048 (Ortho) e a chamada passa max_tokens=500. No llama-cpp-python (0.3.36, llama.py:1343-1358) um erro só é levantado quando o prompt sozinho atinge n_ctx; caso contrário, max_tokens é reduzido a n_ctx menos o tamanho do prompt e a resposta simplesmente para ali. Então uma nota longa não falha: recebe uma resposta mais curta, o JSON fica cortado, e ou json.loads falha (CNE_CLI.py:214, tratador :224-226) ou nenhuma chave de fechamento é encontrada (:221-222), e o texto bruto é gravado. Só um prompt que enche a janela inteira levanta a exceção; ela é capturada por arquivo, registrada no log, e o arquivo é adicionado a failed_files. Com o Ortho, uma nota de cerca de 1,500 tokens ou mais deixa a resposta com menos de 500 tokens. A nota de teste TMJ_note1.txt tem 4,731 bytes, o que passa no modo TMJ.

  • O carregamento do modelo é envolvido por um redirecionamento de stderr para /dev/null via os.dup2 (CNE_CLI.py:157-159) em torno da chamada Llama(...), restaurado depois (:169-171). O código não dá motivo; a chamada também passa verbose=False (:166). Se Llama(...) levanta uma exceção, as linhas de restauração são puladas.

7. Pós-processamento da resposta

Explicação em linguagem simples e matemática: página do atlas.

Espera-se que o modelo responda em JSON; o código não impõe isso (sem response_format, sem gramática GBNF) e simplesmente pesca o JSON do texto (CNE_CLI.py:209-214):

start_idx = ai_response.find('{')
end_idx   = ai_response.rfind('}') + 1
data = json.loads(ai_response[start_idx:end_idx])
if "extraction" in data:
    data = data["extraction"]
for key, value in data.items():
    formatted_response += f"{key} : {value}\n"

Ou seja: da primeira chave de abertura até a última chave de fechamento, remoção de um possível nível extraction, depois achatamento em linhas key : value. Se a análise falha ou não há chave nenhuma, a resposta bruta do modelo é gravada como está. O arquivo de saída não diz qual dos dois casos ocorreu.

Armadilha (parcialmente corrigida no VISOR)

VISOR: valores aninhados não são mais gravados como um repr do Python (extraction.py:318-328). O corte da primeira à última chave é mantido (extraction.py:263-266), mas, quando json.loads falha, a resposta é lida como linhas key: value, e se isso também falha nada é gravado e a nota é relatada como falha, em vez de salvar o texto bruto (extraction.py:278-301, __init__.py:299-305; veja CNE no VISOR). Consequências: o corte ingênuo find('{')…rfind('}') quebra assim que a resposta contém mais de um objeto JSON, e um valor aninhado (lista, dict) é escrito no arquivo de texto pelo seu repr do Python.

8. Saídas

Explicação em linguagem simples e matemática: página do atlas.

Um arquivo de texto por nota de entrada, na pasta de saída:

Extraction_<note name without extension>.txt

Conteúdo: linhas key : value, ou a resposta bruta do modelo se a análise falhou. Nenhum CSV, nenhum json e nenhuma agregação por paciente a partir da própria extração: a tabela e a figura vêm do botão Dashboard (§8.1), que lê esses arquivos depois.

A pasta de saída é criada por os.makedirs(..., exist_ok=True) do lado do widget (CNE.py:613).

8.1 O Dashboard

Explicação em linguagem simples e matemática: página do atlas.

A metade "Dashboard" do MedX foi portada em 2026-10-12, de modo que a afirmação anterior desta página de que ela "não foi levada adiante" não vale mais. Ela é lida no código assim:

  • Gatilho. O botão Dashboard (dashboardButton em CNE.ui, conectado em CNE.py:234) executa onDashboardButton() (CNE.py:365). Ele verifica as dependências, se recusa a rodar sem uma pasta de saída e lança CNE_Dashboard por CNELogic.dashboard() (CNE.py:629) com a pasta de saída como entrada e como saída. Nenhum modelo e nenhum download estão envolvidos.
  • Leitura. read_summaries() (display_figure.py:23) mantém apenas os arquivos Extraction_*.txt da pasta; o identificador do paciente é o nome da nota menos o prefixo. process_summaries() (display_figure.py:135) preenche um dicionário de 56 chaves (o id do paciente e 55 campos que o modelo deve devolver) semeado por initialize_key_value_summary() (dashboard_utils.py:332) e converte seis campos numéricos.
  • Calculado, não predito. Cada painel é uma agregação determinística calculada em dashboard_utils.py (faixas etárias, média e DP das pontuações de dor, abertura máxima da boca lida de cadeias como "33 mm", localizações de cefaleia e de dor articular por listas de sinônimos, deslocamento de disco esquerdo e direito, nível de dor muscular). A figura é desenhada por generate_dashboard_figure() (display_figure.py:164).
  • Saídas. dashboard.png e patient_data.csv (display_figure.py:714-716), mais um terceiro arquivo, dashboard_full_dataframe.csv (display_figure.py:183), gravado antes de a figura ser desenhada.
  • Falha em voz alta quando o esquema não confere. report_field_coverage() (display_figure.py:668) registra as chaves esperadas que não carregam valor, e show_dashboard() (display_figure.py:694) levanta um erro se nenhuma carrega ou se a pasta não contém nenhum Extraction_*.txt.
Armadilha (somente legado)

Legado (3c67957); não há Dashboard no VISOR (veja o primeiro destaque da §1 e CNE no VISOR). O dashboard é um dashboard de TMJ. As chaves esperadas são intensidade da cefaleia, estalos da mandíbula, deslocamento de disco, abertura máxima, distúrbio do sono e similares (dashboard_utils.py:339-396). São as chaves que o modelo TMJ deve devolver; nada no repositório diz que o modelo Ortho as escreve, e o modo Ortho não tem instrução para impô-las. Em extrações do Ortho, a verificação de cobertura provavelmente interromperia a execução com o erro "keys do not match". Isso é uma inferência a partir da lista de chaves, não algo executado sobre uma saída do Ortho. As próprias chaves são escolhidas pelo modelo, não pelo código (docstring de report_field_coverage, display_figure.py:668-679).

  • O Dashboard espera o esquema TMJ (§8.1).
  • A pasta de saída dos arquivos de teste. copyTestFiles() (CNE.py:454) costumava colocar um caminho inexistente no campo de saída. Agora ela cria a pasta de saída (CNE.py:508), copia as notas de novo a cada chamada sem apagar a pasta (dirs_exist_ok=True, CNE.py:505) e deixa em paz uma pasta de saída já escolhida pelo usuário (CNE.py:328-330). Resources/testfiles/ ainda contém apenas as duas pastas input_.
  • Varredura não recursiva da pasta de entrada (§5).
  • Nenhuma verificação de tamanho antes da chamada: uma nota longa não é dividida em blocos. Sua resposta é encurtada ao que a janela deixa (JSON cortado, texto bruto gravado), e uma nota que enche a janela falha, enquanto o MedX dividia em blocos (§6). Isso é uma regressão funcional da substituição.
  • O modo Ortho não envia instrução de sistema (§6): se o modelo não é o esperado, não há motivo algum para a saída ser JSON.
  • Nenhuma restrição ao formato de saída: sem gramática GBNF e sem response_format, embora o llama.cpp ofereça ambos. O pós-processamento é, portanto, uma pesca heurística (§7).
  • Botão de opção marcado nem em TMJ nem em Ortho → notesType = "" (CNE.py:427) → em getModelPath, repo_id nunca é atribuído e o UnboundLocalError aparece como "Failed to load model". Esse caso não deveria ocorrer (setExclusive(True) e um padrão TMJ), mas nada o impede.
  • Capitalização inconsistente: notesType == "TMJ" define n_ctx, enquanto notesType.upper() == "TMJ" define a instrução. Um notesType em minúsculas daria a instrução TMJ com o contexto de 2048.
  • Nenhum rastro de procedência: o arquivo Extraction_*.txt não menciona nem o modelo, nem sua versão, nem a data. Duas execuções com modelos diferentes produzem arquivos indistinguíveis.
  • PHI: nada anonimiza, nada avisa. As notas são lidas em claro e passam por um modelo local (então não há exfiltração pela rede: essa é a única salvaguarda, e é estrutural, não deliberada). Somente o módulo legado (3c67957). Com o VISOR, as notas são enviadas a um servidor como estão, e nada as desidentifica antes: veja Achados no VISOR.
  • Metadados da CLI deixados no padrão do template: CNE_CLI.xml ainda descreve "Apply a Gaussian blur to an image", atribui o módulo a "Andras Lasso (PerkLab)", e seus valores de <index> são 0, 2, 3, 4, falta o índice 1.
  • onCliProgress (CNE.py:651) lê caller.GetProgress() e não faz nada com isso; nem sequer está conectado a um observador. Código morto. O progresso real passa pelas tags <filter-progress> da CLI, lidas pelo qSlicerCLIProgressBar.

12. Literatura

Nenhuma publicação é citada no repositório para o CNE, e os dois model cards do Hugging Face DCBIA-OrthoLab/* não citam nenhum artigo (eles apontam para um repositório de código, ortho-cde-llm-extraction, que não foi lido). O que é verificável:

  • A linhagem MedX → CNE, documentada apenas pela linha de agradecimento de CNE_Dashboard.xml ("Ported from MedX_Dashboard, which CNE replaced without taking this half with it") e pelos comentários em display_figure.py:35 e :675. O CMakeLists.txt da raiz não menciona mais o MedX e o README não tem seção sobre o MedX nem sobre o CNE.
  • Os modelos base: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • Os repositórios ajustados (fine-tuned): DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho.
  • O motor: llama-cpp-python, llama.cpp (formato GGUF, quantização Q4_K_M).
  • SlicerAutomatedDentalTools

Não associe o CNE à literatura geral sobre extração de informação clínica por LLM: nada no repositório indica que os modelos usados aqui vêm de um trabalho publicado.
