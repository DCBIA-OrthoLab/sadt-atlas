CNE

Um módulo de inferência de modelo de linguagem (LLM) que lê notas clínicas em texto livre e extrai delas pares chave–valor — não é nem uma ferramenta geométrica nem de processamento de imagem, apesar de seu lugar em uma suíte de ferramentas odontológicas.

não publicado CNE_CLI sem conda — Python do Slicer Bibliografia

Aviso de escopo. Ao contrário de AutoCrop3D e AutoMatrix, o CNE não é um utilitário geométrico: não mexe em nenhum volume, nenhuma malha, nenhuma coordenada. É um módulo de inferência LLM que lê notas clínicas em texto livre e escreve pares chave–valor. No núcleo do módulo está um modelo GGUF quantizado carregado por llama-cpp-python dentro do Python do Slicer.

0. A sigla

O repositório nunca explicita a sigla em nenhuma documentação: o README não contém seção sobre o CNE (ainda documenta o MedX, que o CNE substitui, cf. CMakeLists.txt:42 "Replaced by CNE"). O texto de ajuda do módulo (CNE.py:147) diz apenas "This tool helps to create summaries of clinical notes".

Duas linhas de log, e apenas elas, dão a forma por extenso: logger.info("CNE (Clinical Notes Extraction)") (CNE.py:329 e CNE.py:606), e a CLI publica o mesmo nome para o supervisor do Slicer: <filter-name>Clinical Notes Extraction</filter-name> (CNE_CLI.py:91). CNE = Clinical Notes Extraction, atestado pelo código e por nada mais.

1. Onde se situa no pipeline

Módulo terminal. Nada o chama, e ele não chama nenhum outro módulo do repositório. Declarado em CMakeLists.txt:51.

Ele substitui a metade "Summarization" do MedX. MedX/ e MedX_CLI/ ainda estão na árvore, mas desativados da compilação (CMakeLists.txt:42-44); a metade "Dashboard" do MedX (dashboard.png + patient_data.csv) não tem equivalente no CNE e, portanto, desaparece da extensão compilada.

3. Dependências, instaladas sob demanda

check_dependencies() (CNE.py:83) é chamada ao clicar em Apply, não no carregamento do módulo. Ela testa três imports e, se algum faltar, pede confirmação antes do slicer.util.pip_install:

Import testadoPacote instaladoUso

fitzpymupdfextração de texto de PDF

Dois pontos que vale conhecer:

Armadilha

install_function (CNE.py:44) força CC=gcc e CXX=g++ durante a instalação e depois restaura os valores originais — isso serve para o caso em que o pip precisa compilar llama-cpp-python a partir do código-fonte. No Windows esses valores são inutilizáveis.

Armadilha

O índice extra aponta explicitamente para os wheels de CPU. No entanto a CLI pede n_gpu_layers=-1 com o comentário "Use GPU if available" (CNE_CLI.py:162): com uma compilação apenas para CPU esse parâmetro não tem efeito. Na prática a inferência roda na CPU, e um modelo de 7–8 B quantizado em Q4 custa ali várias dezenas de segundos por nota.

A CLI testa de novo os três imports na inicialização e chama sys.exit(1) se algum faltar (CNE_CLI.py:99-115) — redundante, mas inofensivo, já que a CLI compartilha o interpretador do widget.

4. Os modelos

Nenhum peso vem no repositório. getModelPath() (CNE.py:478) baixa o GGUF sob demanda, via urllib.request.urlretrieve com um QProgressDialog, em <Documents>/SlicerDownloads/CNE/model/.

Bug confirmado

O download do Ortho está quebrado. Verificado pela API do Hugging Face: o repositório dcbia/Meta-Llama-3.1-8B-Instruct-Ortho contém apenas .gitattributes e model-q4_k_m.gguf. O arquivo model-q4_0.gguf solicitado pelo código não existe — a URL retorna HTTP 404, enquanto a URL q4_k_m retorna 200. urlretrieve lança uma exceção, o arquivo parcial é apagado e o usuário vê "Download failed or was cancelled". O modo TMJ, por outro lado, está correto (qwen-ft-q4_k_m.gguf → 200). Correção: model-q4_0.gguf → model-q4_k_m.gguf.

Os dois repositórios do Hugging Face não têm model card: nenhuma licença, nenhum conjunto de treinamento, nenhum método de fine-tuning publicado. As arquiteturas de base são identificáveis pelas tags (Llama-3.1-8B-Instruct e Qwen2 7B), com quantização Q4_K_M nos dois casos. O que distingue os dois modelos ajustados — corpus de anotação, esquema de saída aprendido, protocolo — não é determinável a partir do repositório nem do Hugging Face.

5. Entradas e pré-processamento

SUPPORTED_EXTENSIONS = (".txt", ".pdf", ".docx"). A varredura é não recursiva: glob.glob(os.path.join(notesFolder_input, f"*{ext}")) (CNE_CLI.py:133) — ao contrário de todos os outros módulos do repositório, que usam iglob(**, recursive=True). Uma pasta composta de subpastas por paciente não produzirá nada.

Extração de texto (CNE_CLI.py:73):

FormatoExtratorDetalhe
.pdffitz.open e depois "\n".join(page.get_text() for page in doc)sem OCR: um PDF digitalizado sai vazio
.docxdocx.Document, paragraph.textas tabelas se perdem (doc.paragraphs não as percorre)

clean_text() (CNE_CLI.py:40) é a única etapa de pré-processamento, e sua motivação está declarada no código: normalizar o que varia entre exportações PDF/Word mas nunca apareceu nas notas de treinamento em texto puro — apóstrofos e aspas tipográficos para ASCII, meia-risca e travessão para -, espaço inseparável para espaço comum, depois colapso de linhas em branco consecutivas. Objetivo explícito: o modelo deve ver o mesmo texto qualquer que seja o formato de origem.

Sem anonimização, sem filtragem de PHI. As notas de teste do repositório são pseudonimizadas à mão (B_001, [DOCTOR], Dr. XXX), mas nada no código garante isso para os dados do próprio usuário. O módulo Medical_Data_Anonymizer_Module existe separadamente e não é encadeado ao CNE.

6. Inferência

Uma única passagem por arquivo, sem divisão em partes (CNE_CLI.py:192):

messages = []
if notesType.upper() == "TMJ":
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": clinical_text})

output = llm.create_chat_completion(messages=messages, max_tokens=500, temperature=0.1)

A observar:

Armadilha

O modo Ortho não envia nenhuma instrução. Só a nota bruta sai como mensagem do usuário; é o fine-tuning do modelo Llama-Ortho que deve supostamente carregar a tarefa. O modo TMJ, em contrapartida, mantém a instrução herdada do MedX.

  • create_chat_completion aplica o chat template embutido no GGUF. Os dois modelos têm a tag conversational no Hugging Face, então o template existe; ele não é nem visível nem controlável a partir do repositório.
  • temperature=0.1 e nenhum seed: a saída é quase determinística, mas não exatamente reprodutível.
Armadilha

Nenhuma proteção quanto ao tamanho. n_ctx vale 6144 (TMJ) ou 2048 (Ortho) e max_tokens=500 é descontado desse orçamento. Uma nota que excede o orçamento faz o llama.cpp lançar uma exceção; ela é capturada por arquivo, registrada no log, e o arquivo é adicionado a failed_files. O orçamento do Ortho é particularmente apertado: ~1.500 tokens de nota utilizável. A nota de teste TMJ_note1.txt tem cerca de 4.400 caracteres, o que passa no modo TMJ.

  • O carregamento do modelo é envolvido por um redirecionamento de stderr para /dev/null via os.dup2 (CNE_CLI.py:155), para mascarar a verbosidade do llama.cpp, que de outro modo poluiria o canal de erro que o Slicer interpreta como falha da CLI.

7. Pós-processamento da resposta

Espera-se que o modelo responda em JSON; o código não impõe isso (nenhum response_format, nenhuma gramática GBNF) e simplesmente pesca o JSON no texto (CNE_CLI.py:207):

start_idx = ai_response.find('{')
end_idx   = ai_response.rfind('}') + 1
data = json.loads(ai_response[start_idx:end_idx])
if "extraction" in data:
    data = data["extraction"]
for key, value in data.items():
    formatted_response += f"{key} : {value}\n"

Ou seja: da primeira chave de abertura até a última chave de fechamento, remoção de um eventual nível extraction, depois achatamento em linhas key : value. Se o parse falhar ou não houver nenhuma chave, a resposta bruta do modelo é gravada tal como está. O arquivo de saída não diz qual dos dois casos ocorreu.

Armadilha

Consequências: o recorte ingênuo find('{')…rfind('}') quebra assim que a resposta contém mais de um objeto JSON, e um valor aninhado (lista, dict) é renderizado pelo seu repr Python no arquivo de texto.

8. Saídas

Um arquivo de texto por nota de entrada, na pasta de saída:

Extraction_<note name without extension>.txt

Conteúdo: linhas key : value, ou a resposta bruta do modelo se o parse falhou. Nenhum CSV, nenhum json, nenhuma agregação por paciente — o dashboard do MedX não foi mantido.

A pasta de saída é criada por os.makedirs(..., exist_ok=True) no lado do widget (CNE.py:578).

11. Armadilhas e pontos frágeis

  • O modelo Ortho não baixa: nome de arquivo errado, HTTP 404 (§4). Correção: model-q4_0.gguf → model-q4_k_m.gguf.
  • As pastas de saída dos arquivos de teste não existem. copyTestFiles() (CNE.py:409) copia input_<type> e output_<type>, mas Resources/testfiles/ contém apenas as duas pastas input_. O shutil.copytree da pasta de saída é pulado com um aviso, e a interface fica com um caminho de saída preenchido que ainda não existe.
  • Varredura não recursiva da pasta de entrada (§5).
  • Nenhum limite de tamanho antes da chamada: uma nota longa demais falha em vez de ser dividida, enquanto o MedX dividia (§6). É uma regressão funcional da substituição.
  • O modo Ortho não envia instrução de sistema (§6): se o modelo não for o esperado, não há nenhuma razão para que a saída seja JSON.
  • Nenhuma restrição de formato de saída: nenhuma gramática GBNF e nenhum response_format, embora o llama.cpp ofereça ambos. O pós-processamento é, portanto, uma pescaria heurística (§7).
  • Botão de opção nem em TMJ nem em Ortho → notesType = "" (CNE.py:382) → em getModelPath, repo_id nunca é atribuído e o UnboundLocalError aparece como "Failed to load model". Esse caso não deveria ocorrer (setExclusive(True) e TMJ como padrão), mas nada o impede.
  • Maiúsculas/minúsculas inconsistentes: notesType == "TMJ" define n_ctx, enquanto notesType.upper() == "TMJ" define a instrução. Um notesType em minúsculas daria a instrução TMJ com o contexto de 2048.
  • Nenhum rastro de proveniência: o arquivo Extraction_*.txt não menciona nem o modelo, nem sua versão, nem a data. Duas execuções com modelos diferentes produzem arquivos indistinguíveis.
  • PHI: nada anonimiza, nada avisa. As notas são lidas em texto claro, passadas por um modelo local (portanto sem exfiltração pela rede — é a única salvaguarda, e ela é estrutural, não deliberada).
  • Metadados da CLI deixados no padrão do template: CNE_CLI.xml ainda descreve "Apply a Gaussian blur to an image", atribui o módulo a "Andras Lasso (PerkLab)", e seus valores <index> são 0, 2, 3, 4 — falta o índice 1.
  • onCliProgress (CNE.py:594) lê caller.GetProgress() e não faz nada com isso; nem sequer está conectado a algum observador. Código morto. O progresso real passa pelas tags <filter-progress> da CLI, lidas por qSlicerCLIProgressBar.

12. Literatura

Nenhuma publicação é citada no repositório para o CNE, e os dois repositórios dcbia/* do Hugging Face estão publicados sem model card e sem referência. O protocolo de fine-tuning, o corpus de anotação TMJ/Ortho e a avaliação não são determináveis a partir do repositório.

O que é verificável:

  • A linhagem MedX → CNE, documentada apenas por CMakeLists.txt:42 e pela seção MedX de README.md:425, que ainda descreve o antigo pipeline BART e o dashboard desaparecido.
  • Os modelos de base: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct.
  • Os repositórios ajustados: dcbia/Qwen-2.5-7B-Instruct-TMJ, dcbia/Meta-Llama-3.1-8B-Instruct-Ortho.
  • O motor: llama-cpp-python, llama.cpp (formato GGUF, quantização Q4_K_M).
  • SlicerAutomatedDentalTools

Não vincular o CNE à literatura geral sobre extração de informações clínicas por LLM: nada no repositório indica que os modelos usados aqui vêm de trabalhos publicados.
