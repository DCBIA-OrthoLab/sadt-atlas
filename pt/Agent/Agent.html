Agent: pipeline completo

Um assistente em linguagem natural que escolhe um módulo da extensão, extrai seus parâmetros, monta a linha de comando e a lança. Nenhuma rede neural médica é chamada aqui: o Agent só faz roteamento e preenchimento de formulário. Esta página explica como, passo a passo; os detalhes de que um desenvolvedor precisa estão na página de código.

não publicado Agent_CLI Python do Slicer qwen3:8b via Ollama cross-encoder MiniLM-L6 Código (desenvolvedores) Bibliografia VISOR: parcial

Tudo roda localmente: um modelo de linguagem de 8B servido pelo Ollama, mais um pequeno cross-encoder para pré-selecionar as ferramentas candidatas.

Duas bases de código. Tudo o que é descrito aqui é o módulo legado do Slicer (SlicerAutomatedDentalTools em 3c67957, 2026-10-26). O VISOR tem uma ferramenta de servidor chamada Agent, um roteador sobre um endpoint externo do Ollama, mas nenhum cliente a chama: o painel AgentRemote distribuído no cliente do VISOR é uma cópia do widget legado que ainda roda localmente. Ambos são descritos na página do VISOR para o Agent. Evidência.

1. Posição na cadeia

Ninguém chama o Agent. Nenhum outro módulo da extensão o usa: é um ponto de entrada terminal. Na saída, três coisas são chamadas:

ChamadoComoOnde
Agent_CLIO executor de linha de comando do Slicerprocesso separado, Python do Slicer
O módulo de destino (ALI_CBCT, AMASSS_CLI, ...)iniciado como processo filho do painelPython do Slicer
Ollamaseu cliente Python, via HTTP na porta da própria máquinaservidor local, instalado e lançado pelo módulo

O inventário dos destinos é puramente declarativo: ele vive em manifest.yaml, um arquivo YAML com 16 entradas. O Agent não descobre nada por conta própria: ele só conhece este arquivo.

No códigoPontos de chamada com arquivo e linha, e o código morto que resta no módulo

2. Arquivos envolvidos

O painel (chat, zona de soltar, instalação do Ollama, confirmação, lançamento, reparo) roda no Slicer. Um programa de linha de comando separado faz o roteamento e a extração e imprime JSON, sem executar nada. Um arquivo utilitário guarda o manifest, o cross-encoder, a chamada ao Ollama, a busca de caminhos e a construção do comando. Um validador coage e verifica os valores, e o manifest lista as 16 ferramentas endereçáveis. Nenhum ambiente conda e nenhuma GPU obrigatória: tudo roda dentro do Python do Slicer; a única GPU usada é indireta, pelo servidor Ollama.

3. Os modelos

3.1 O modelo de linguagem, qwen3:8b via Ollama

Um só modelo atende as três chamadas, roteamento, extração de parâmetros e reparo: o Qwen3 com 8 bilhões de parâmetros, executado pelo Ollama (portanto llama.cpp por baixo) no formato GGUF que o Ollama impõe. Não há modelo especializado nem fine-tuning. O nome do modelo está escrito em dois lugares do código e pode ser trocado por uma variável de ambiente. A tag padrão pesa 5.2 GB (lido em ollama.com, não determinável a partir do repositório).

Se roda em CPU ou GPU é decidido pelo Ollama, não pelo módulo. O código tira uma consequência: no Linux, um Ollama instalado via snap fica em sandbox, não enxerga a GPU NVIDIA e recua para a CPU, a 80 a 90 segundos por resposta para um modelo de 8B, um número medido e escrito no código. O módulo o detecta e avisa, sem poder corrigir.

Quando nenhum Ollama é encontrado, o módulo baixa o arquivo portátil oficial para uma pasta própria, de modo que nenhuma senha de root é necessária a partir do painel. Apenas dois ajustes de chamada são usados: o modelo permanece carregado por 30 minutos em vez de 5, e a resposta é restrita a JSON para o roteador, a extração e o reparo (não para o modo consultor). Nenhuma temperatura, seed ou tamanho de contexto é passado. Se o modelo não está presente, ele é baixado e a chamada refeita.

No códigoAs constantes, o teste do snap, o instalador do Ollama e os dois ajustes de chamada

3.2 O cross-encoder: ms-marco-MiniLM-L-6-v2

É a única rede neural de verdade carregada no processo: MiniLM, 6 camadas, 22.7 milhões de parâmetros, treinado na tarefa de ranqueamento de passagens do MS MARCO, baixado do Hugging Face Hub. Ele não é um modelo de embeddings: o pedido e o texto da ferramenta são alimentados juntos no transformer, que produz um número de relevância sem limites. O programa de linha de comando é um processo novo a cada mensagem, de modo que o modelo é recarregado todas as vezes.

Se o carregamento do cross-encoder falha, o fallback é brusco: as três primeiras ferramentas do manifest, qualquer que seja a pergunta, e o chat não é avisado (uma linha vai apenas para a saída do programa). O campo priority do manifest nunca é lido.

No códigoComo o texto de cada ferramenta é construído, a ordenação, o k fixo no código e o fallback silencioso

4. Roteamento

Duas etapas, e o modelo de linguagem só entra na segunda. A etapa 1 é o cross-encoder acima. Na etapa 2 o modelo recebe o pedido e as três candidatas, uma linha cada (nome, descrição cortada em 140 caracteres, no máximo 8 tags), e deve responder com um objeto JSON: um nome de ferramenta, uma confiança e uma razão de uma frase. Três coisas merecem ser sabidas:

  • O contexto das pastas não é dado ao roteador; ele só é acrescentado depois, para a extração.
  • O histórico da conversa é injetado tal como aparece na tela, inclusive as próprias frases do painel, como “After reflection, I would like to run ...”, de modo que o roteador JSON recebe prosa da interface como respostas anteriores.
  • A confiança e a razão não servem para nada. A confiança é lida e escrita, depois nunca relida: nenhum limiar existe em lugar nenhum, e a instrução “confidence at most 0.4 when nothing matches” é apenas uma sugestão ao modelo.

A única rede de segurança é textual: a resposta não deve ser nula. Um nome de ferramenta que não está no manifest passa nesse teste, depois faz o construtor de comandos falhar; o erro é capturado e devolvido como mensagem de erro.

No códigoO prompt do roteador, a injeção do histórico e o código morto da especificação de ferramentas

5. Extração de parâmetros

Uma segunda chamada ao modelo, com uma ferramenta já escolhida. Os parâmetros técnicos (uma pasta temporária, um caminho de log) são retirados do que o modelo vê e preenchidos pelo painel depois: não se pede ao modelo que os invente. O prompt lista cada parâmetro com seu tipo, se é obrigatório e como uma lista deve ser escrita, depois impõe sete regras, acima de tudo: extrair apenas o que o pedido menciona, não inventar valores, deixar ausentes os parâmetros opcionais não mencionados. A lista de parâmetros obrigatórios que o modelo devolve é ignorada: o validador é que conta.

O validador também força o texto “true” ou “false” para minúsculas onde uma ferramenta compara o argumento bruto. De resto, o relatório de validação é quase todo descartado: seus erros e avisos não aparecem em lugar nenhum.

Os caminhos são deixados inteiramente ao modelo. As pastas soltas no painel são anexadas ao pedido, com a instrução de tratá-las como fonte da verdade. Não há correspondência heurística, nem olhada dentro das pastas, nem verificação de existência: só o modelo adivinha qual caminho solto é o T1, qual é o T2, qual é a pasta do modelo. O VISOR corrige apenas a parte da vírgula: a ferramenta de servidor recebe as pastas como lista.

6. Construção e execução do comando

Sim, o módulo é realmente lançado. O programa de linha de comando apenas constrói o comando: ele mescla os valores padrão do manifest com os extraídos e antepõe o próprio interpretador do Slicer e o caminho do script. Para 14 das 16 ferramentas os valores são simplesmente escritos um após o outro na ordem em que o manifest os declara (estilo posicional).

O painel então executa o comando, e só se nada obrigatório estiver faltando: um balão de chat diz o que ele gostaria de executar, uma caixa Yes/No lista cada parâmetro, e em Yes o módulo começa. Se algo obrigatório está faltando, nada é lançado: o painel lista o que falta com os valores já conhecidos, e espera uma mensagem de continuação. O lançamento é síncrono e acontece na thread da interface: o Slicer fica congelado durante todo o trabalho, que para uma segmentação ou um registro se mede em dezenas de minutos.

No códigoO construtor de comandos, a caixa de diálogo e a chamada bloqueante de subprocesso

7. O ciclo de reparo

Este caminho roda dentro do processo do Slicer, e não no programa de linha de comando. A correção volta pelo validador e pelo construtor de comandos, uma diferença antigo-para-novo é exibida, e uma nova confirmação Yes/No é exigida; uma diferença vazia interrompe o ciclo. Um diagnóstico por palavras-chave, sem modelo, acrescenta dicas para um modelo do Ollama ausente, um módulo Python ausente, uma regressão conhecida em uma versão recente do transformers, um conflito do numpy 2 com as wheels do torch e uma falha de conexão com o Ollama.

No códigoO prompt de reparo, o truque da reimportação e o diagnóstico por palavras-chave

8. Módulos endereçáveis e seu estado real

O manifest lista 16 ferramentas. Sua lista de parâmetros foi comparada, arquivo por arquivo, com a linha de comando real de cada script de destino. Apenas 2 assinaturas de 16 estão corretas: DOCShapeAXI e MRI2CBCT_resample. Duas outras (BatchDentalSeg e CLIC) são módulos Slicer com script, e não ferramentas de linha de comando, e não podem ser executadas assim. O AMASSS recusa de cara (“Expected 13 arguments”). As demais têm, cada uma, de um a quatro parâmetros faltando.

Como nada é nomeado na linha de comando, uma lista curta demais não levanta um erro limpo: no AREG_IOS, por exemplo, o caminho do arquivo de log acaba como sufixo de nome de arquivo. Ausentes do manifest e, portanto, fora do alcance do Agent: VFACE, GreedyReg, CNE, AREG_IOSCBCT, SurgMovPred e Medical_Data_Anonymizer.

Os caminhos dos scripts não se resolvem

Um problema mais fundamental que as assinaturas. O manifest só dá nomes simples de scripts. A busca de caminho procura, em ordem, em uma pasta nomeada pela variável AGENT_CLI_TOOLS_DIR, em uma pasta “CLI files” ao lado do manifest, na própria pasta do manifest, depois até quatro níveis acima. Nenhuma delas existe neste repositório, onde cada script vive na pasta do seu próprio módulo, de modo que nenhum candidato corresponde e a função devolve o primeiro “so the error message points to a debuggable path”.

O lançamento em si não levanta exceção (o interpretador do Slicer existe): é o Python que sai com código 2 diante de um arquivo que não encontra, o que dispara o ciclo de reparo. Mesmo com os caminhos resolvidos, alguns destinos ainda falhariam: o DOCShapeAXI precisa de um pacote que vive em um ambiente conda, enquanto o Agent lança tudo com o Python do Slicer.

9. Os dois modos

ModoO que o Agent_CLI devolveExecução
Agent (Automated)Um objeto JSON com a ferramenta, sua confiança, os parâmetros, o que falta e o comandosim, após confirmação
Ask (Interactive)Texto livrenenhuma

No modo Ask, cada linha de candidata também traz a lista bruta de seus parâmetros, colada tal como está no prompt de sistema de um “expert medical image analysis consultant”. A resposta não é restrita a JSON e é mostrada depois que os caracteres * e # são removidos. O README chama este modo de “Consultant”, a interface diz “Ask (Interactive)”, e o código só testa o nome Agent, de modo que qualquer outro valor cai no modo consultor.

10. Salvaguardas

O que existe:

  • Uma confirmação obrigatória antes de cada execução, listando todos os parâmetros, e uma segunda antes de cada tentativa de reparo.
  • Nada é lançado enquanto um parâmetro obrigatório está faltando.
  • Coerção de tipos e verificações de opções, intervalos e da extensão de nomes semelhantes a pastas.
  • As pastas temporárias são preenchidas pelo painel, e não pelo modelo.
  • Limites: 2 tentativas de reparo, um histórico de no máximo 40 turnos, e uma captura global para que a saída do programa continue sempre sendo JSON analisável.

O que não existe:

  • Nenhum limiar de confiança: um roteamento a 0.1 é tratado como um a 0.95.
  • Nenhuma verificação de que um caminho existe: um caminho alucinado passa na validação e na confirmação (o operador precisa percebê-lo a olho) e só falha quando o módulo começa.
  • Os erros do validador nunca são exibidos.
  • Nenhuma proteção das pastas de saída: se o modelo escolhe uma pasta de dados de entrada como saída, nada o impede.
  • Nenhuma lista de executáveis permitidos, mas a proteção real é que o caminho do script vem do manifest, e não do modelo: o modelo controla os valores, não o programa que é lançado.

11. Ambiente

O painel instala cinco pacotes no Python do Slicer, em uma ordem que importa: o cliente Python do Ollama, um leitor de YAML para o manifest, o transformers anterior à 4.53 (uma regressão quebra a importação do cross-encoder), o numpy anterior à 2 (o numpy 2 quebra as wheels do torch) e, por último para não alterar os pins, o sentence-transformers. O programa de linha de comando roda em um processo separado, mas compartilha os pacotes do Slicer. Nenhum ambiente conda é criado.

O servidor Ollama é sondado em sua porta local, iniciado quando necessário e aguardado por até cerca de 30 segundos enquanto a interface permanece viva. Ele é verificado de novo antes de cada mensagem, porque um servidor lançado pelo módulo não sobrevive a uma reinicialização do Slicer. No Windows nenhuma janela de console é mostrada; não há suporte a WSL, ao contrário do resto do repositório.

12. Armadilhas e pontos frágeis

  • Os scripts dos módulos não são encontrados, o que bloqueia a ferramenta inteira. Evidência.
  • 14 assinaturas de 16 estão erradas, e o deslocamento é silencioso. Evidência.
  • O cross-encoder recua silenciosamente para as três primeiras ferramentas, é recarregado a cada mensagem e mantém um top 3 fixo no código. Evidência.
  • O Slicer fica congelado durante todo o trabalho. Evidência.
  • A resolução de caminhos é deixada inteiramente ao modelo. Evidência.
  • Um Ollama instalado com snap roda na CPU. Evidência.
  • Três nomes para dois modos. Evidência.
  • Resta código morto: um process() não usado, um construtor de especificação de ferramentas não usado, um cache do cross-encoder não usado e um arquivo de interface que um módulo de linha de comando nunca carrega. Evidência.
  • O histórico mistura prosa da interface com contexto de roteamento, e quando uma discussão salva é recarregada o histórico é reconstruído dividindo o texto por dois emoji, de modo que uma mensagem que os contenha o dessincroniza (um chat ao vivo mantém seus turnos como lista).

14. Literatura

Nenhum artigo, nem sobre este módulo nem sobre a abordagem. Uma busca por SlicerAutomatedDentalTools e agentes de LLM encontra apenas a documentação do repositório e literatura geral sobre modelos de linguagem na odontologia. As únicas referências externas reais são as dos dois modelos usados, ambos genéricos e não treinados para este domínio. A ferramenta de servidor do VISOR segue a mesma abordagem; seu README traz uma seção de proveniência que nomeia os arquivos legados de onde foi portada, e não uma publicação. Evidência.
