Agent — pipeline completo

Um assistente em linguagem natural que escolhe um módulo da extensão, extrai seus parâmetros, monta a linha de comando e a executa. Nenhuma rede neural médica é chamada aqui — o Agent só faz roteamento e preenchimento de formulário.

não publicado Agent_CLI Slicer Python qwen3:8b via Ollama cross-encoder MiniLM-L6 Bibliografia

Tudo roda localmente: um LLM de 8B servido pelo Ollama, mais um pequeno cross-encoder para pré-selecionar as ferramentas candidatas.

1. Onde se situa no pipeline

Ninguém chama o Agent. Um grep por slicer.modules.agent não encontra nenhum chamador fora do próprio módulo. É um ponto de entrada terminal.

Na saída, há dois níveis:

O inventário de alvos é puramente declarativo: fica em Agent_CLI/manifest.yaml, um arquivo YAML com 23 entradas scripts. O Agent não descobre nada sozinho — só conhece este arquivo.

Código morto

AgentLogic.process() (Agent.py:1315) reexecuta a CLI apenas com folders e prompt (faltam modeagent e temp_folder, ambos obrigatórios no lado XML) e lê GetOutputText() imediatamente após um wait=False. Nunca é chamado. Agent_CLI/Resources/UI/Agent_CLI.ui também é inerte: um módulo CLI não carrega um arquivo .ui.

3. Os modelos

3.1 O LLM — qwen3:8b via Ollama

Uma única constante, duplicada nas duas pontas: DEFAULT_MODEL = "qwen3:8b" (utils.py:21) e MODEL_NAME = "qwen3:8b" (Agent.py:18). get_router_model() respeita uma variável de ambiente ROUTER_MODEL que permite trocar por qualquer modelo do Ollama sem mexer no código.

O mesmo modelo atende às três chamadas: roteamento, extração de parâmetros, reparo. Nenhum modelo especializado, nenhum fine-tuning.

PontoValorFonte
Motor de inferênciaOllama (portanto llama.cpp por baixo), API HTTP localimport ollama, porta 11434
Formato dos pesosGGUF — imposto pelo Ollama, nenhum checkpoint transformersdeduzido do motor
Downloadollama pull qwen3:8b a partir do registro ollama.comAgent.py:1266, e fallback automático em chat_with_auto_pull
Tamanho / quantizaçãotag padrão: 5,2 GB, Q4_K_M, 8,19 G parâmetrosnão determinável a partir do repositório: lido em ollama.com/library/qwen3

Ollama instalado via snap = CPU

O módulo nunca passa uma diretiva de dispositivo. O binário do Ollama decide, e o código tira disso uma consequência explícita: no Linux, um Ollama instalado via snap fica em sandbox, não enxerga a GPU NVIDIA e recorre à CPU — 80–90 s por resposta para um modelo de 8B, número medido e fixado no código (Agent.py:1231). O módulo detecta /snap/ no realpath do binário e avisa, sem conseguir corrigir (o servidor snap já ocupa a porta 11434, e removê-lo exige sudo).

Quando nenhum Ollama é encontrado, install_official_ollama() (Agent.py:101) baixa o arquivo portátil oficial em ~/.slicer_agent/ollama (substituível via SLICER_AGENT_HOME): ollama-linux-{amd64,arm64}.tgz, ollama-windows-{amd64,arm64}.zip ou Ollama-darwin.zip, extraído com ditto e depois retirado da quarentena com xattr. Esses arquivos trazem as bibliotecas CUDA/Metal, daí a escolha deliberada de não usar curl | sudo sh (nenhuma senha root a partir da GUI) nem o pacote snap. LD_LIBRARY_PATH é apontado para <install>/lib/ollama para que o binário encontre suas próprias libs (Agent.py:56).

Apenas dois parâmetros de chamada, em chat_with_auto_pull (utils.py:96):

  • keep_alive="30m" em vez do padrão de 5 minutos, para não recarregar 5 GB na VRAM entre duas mensagens;
  • format="json" para o roteador, a extração e o reparo (uma restrição de gramática no lado do Ollama) — não para o modo consultor.

Nenhum temperature, seed, num_ctx ou think é passado. Como o qwen3 é um modelo de raciocínio híbrido, o modo consultor pode, portanto, deixar vazar texto de raciocínio dependendo da versão do Ollama; o único pós-processamento é output.replace("*","").replace("#","") (Agent_CLI.py:215), que remove o markdown removendo os caracteres.

Se o modelo não estiver presente, chat_with_auto_pull intercepta a mensagem not found, executa ollama.pull(model, stream=True) exibindo o progresso e depois repete o chat. Qualquer outro erro é relançado como está.

3.2 O cross-encoder — ms-marco-MiniLM-L-6-v2

É a única rede de fato carregada no processo. CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") (utils.py:53), via sentence-transformers — portanto pesos transformers/safetensors baixados do Hugging Face Hub e guardados em cache em ~/.cache/huggingface.

MiniLM, 6 camadas, 22,7 M parâmetros, destilado de MiniLM-L12-H384-uncased, treinado no MS MARCO Passage Ranking. Não é um modelo de embeddings: não há vetores nem similaridade de cosseno. A consulta e o documento são concatenados e passados juntos ao transformer, que produz um único escalar de relevância não limitado (tipicamente de −10 a +10). O dispositivo é aquele que sentence-transformers escolhe sozinho, conforme o wheel de torch instalado.

O cache _cross_encoder_model não serve para nada na prática: Agent_CLI.py é um processo novo a cada pedido, então o modelo é recarregado a cada mensagem. O comentário do código admite isso.

Fallback silencioso do cross-encoder

Se o carregamento falhar, o fallback é grosseiro: scripts[:k], ou seja, as três primeiras ferramentas do manifesto (ali_cbct, ali_ios, amasss_cli), qualquer que seja a pergunta (utils.py:90). O operador não é informado.

4. Roteamento

Duas etapas, e o LLM só intervém na segunda.

Etapa 1 — pré-seleção pelo cross-encoder. cross_encoder_retrieve_candidates(manifest, prompt, k=3) monta um documento por ferramenta:

docs.append(f"{s['name']}: {s['description']} (tags: {tags})")
scores = model.predict([(user_text, doc) for doc in docs])
ranked = sorted(zip(scores, scripts), reverse=True)
return [s for _, s in ranked[:k]]

23 pares pontuados, ordenados de forma decrescente, top-3 fixo (k=3 nunca é parametrizado). O campo priority do manifesto (valores de 1 a 23) nunca é lido — a linha que o leria está comentada (utils.py:216). A ferramenta certa, se ficar em 4º lugar, está definitivamente perdida; o LLM nunca a verá.

Etapa 2 — escolha pelo LLM. O prompt de sistema (Agent_CLI.py:105):

You are a tool router. Output ONLY one JSON object.
Schema:
{"tool": string|null, "confidence": number, "reason": string}

Rules:
- Choose tool ONLY from the candidate list provided by the user message.
- If none match, set tool = null and confidence <= 0.4.
- Do not invent tool names.
- Keep reason short (max 1 sentence).

A mensagem do usuário é USER_REQUEST: <prompt> seguida de CANDIDATES (choose exactly one name from this list): e do bloco montado por build_candidates_block: uma linha por candidato, i) name — description (truncated to 140 characters) | tags: t1, t2, … (8 max).

Três pontos a observar:

  • O contexto de pastas não é passado ao roteador. folders_context só é adicionado ao prompt de extração.
  • O histórico da conversa é injetado entre os turnos de sistema e de usuário (*history), e ele contém os balões de chat brutos do widget ("After reflection, I would like to run …"). O roteador JSON recebe, portanto, prosa da interface como turnos "assistant".
  • confidence e reason não servem para nada. confidence é lido, arredondado, serializado no JSON de saída como tool_confidence… e nunca relido pelo widget. Nenhum limiar em lugar nenhum. A instrução "confidence ≤ 0.4" não é uma restrição, apenas uma sugestão ao modelo.

A única proteção é textual: if selected_tool and selected_tool != "null" and selected_tool != "None". Um nome de ferramenta alucinado que não esteja no manifesto passa nesse teste e depois faz build_cli_args falhar com um KeyError, capturado pelo try global em main() e devolvido como {"error": …}.

tools = build_tool_spec(manifest) (Agent_CLI.py:72) é calculado e depois nunca usado: código morto, assim como todo o tratamento da "estrutura antiga" (patterns, defaults) que nenhuma entrada do manifesto atual usa.

5. Extração de parâmetros

Uma segunda chamada ao LLM, com a ferramenta já escolhida, dentro de extract_parameters (utils.py:220).

Mascaramento dos parâmetros técnicos. Os parâmetros chamados temp_fold, tmp_folder, temp_folder, log_path ou logPath são removidos da especificação antes de montar o prompt — não faz sentido pedir ao modelo que invente uma pasta temporária. Eles são reinjetados depois com o valor input.temp_folder, ou seja, o slicer.util.tempDirectory() criado pelo widget a cada clique (Agent_CLI.py:153), e retirados de missing_required.

O prompt de extração (parameter_extraction_improved.py:40) lista cada parâmetro como - name (type) [REQUIRED|optional] (encode: …): description, depois impõe sete regras: formatação das listas conforme encode (comma_no_brackets, space_separated, comma_separated, python_literal), booleanos e números em JSON puro, "se o nome contém folder ou dir, dar uma pasta sem nome de arquivo" e, sobretudo:

7. ONLY extract parameters mentioned in the user request
   - Do NOT invent values
   - Leave unmentioned optional parameters absent

Saída obrigatória: {"extracted": {...}, "confidence": 0.0-1.0, "missing_required": [...], "notes": "..."}. O missing_required produzido pelo modelo é ignorado — o que vale é o validador.

A resolução de caminhos é inteiramente delegada ao LLM

O widget passa a lista dos itens soltos na área de soltar, unidos por vírgulas (Agent.py:790); a CLI a separa de novo em , e a envolve:

FOLDERS_CONTEXT:
<one path per line>

Rules:
- Treat FOLDERS_CONTEXT as the source of truth for paths.
- If a required path parameter is missing, try to infer it from FOLDERS_CONTEXT.
- If multiple candidates exist, pick the most specific match and explain briefly in 'reason'.

Esse bloco é concatenado ao prompt do usuário, não passado separadamente. Não há correspondência heurística, nenhuma inspeção do conteúdo das pastas, nenhuma verificação de existência: cabe ao modelo adivinhar qual dos caminhos soltos é o T1, qual é o T2, qual é a pasta de modelos. Um caminho que contenha uma vírgula é cortado em dois pelo split(",").

A validação (parameter_validator.py) encadeia seis passagens: campos obrigatórios ausentes, coerção de tipos (bool/int/float/list/path/string), sintaxe de caminhos, choices, min/max, parâmetros fora da especificação. Dois detalhes úteis:

  • encode: lower_str_bool força a string "true"/"false" para minúsculas, porque várias CLIs comparam o argumento bruto sem .lower() — str(True) daria "True" e nunca corresponderia.
  • _check_paths só verifica duas coisas: que Path(str(value)) não lança exceção (quase nunca lança) e que um parâmetro cujo nome contém folder/dir não termina com uma extensão conhecida. A existência do caminho nunca é testada.

O resultado da validação é quase inteiramente descartado: errors e warnings não aparecem em lugar nenhum. Seu único efeito é final_confidence = confidence * 0.6 quando inválido — e essa confiança não é lida por ninguém. Só params e missing_required sobrevivem.

6. Montagem e execução do comando

Sim, o módulo é realmente executado. Sem ambiguidade.

A CLI apenas monta o comando. build_cli_args (utils.py:350) mescla os valores padrão do manifesto com os parâmetros extraídos e então:

return [sys.executable, tool_path] + cli

sys.executable é o interpretador do processo Agent_CLI, ou seja, o Python do Slicer. Para cli_style: positional (21 ferramentas de 23), os valores são concatenados na ordem de declaração do manifesto — positional_order é suportado, mas nenhuma entrada o define. Para qualquer outro cli_style, a execução cai no ramo --flag value, iterando sobre merged: parâmetros alucinados fora da especificação são, portanto, emitidos.

A lista é devolvida ao widget no campo command do JSON. É o AgentWidget que a executa, e somente se missing_required == []:

  1. um balão de chat, "After reflection, I would like to run X";
  2. QMessageBox.question listando key=value para cada parâmetro (Agent.py:864);
  3. em Yes → runToolWithRepair → subprocess.run(cli_args, capture_output=True).

Se missing_required não estiver vazio, o agente não executa nada: exibe a lista do que falta junto com os valores já conhecidos e aguarda uma mensagem de acompanhamento (à qual o histórico da conversa permitirá conectar-se).

O Slicer fica congelado durante o job

subprocess.run é síncrono e roda na thread da GUI: o Slicer fica congelado durante toda a duração do job — que, para uma segmentação AMASSS ou um registro AREG, se mede em dezenas de minutos.

7. O ciclo de reparo

Com um código de retorno diferente de zero, runToolWithRepair (Agent.py:943) pede ao LLM que corrija os parâmetros, no máximo MAX_REPAIR_ATTEMPTS = 2 vezes. build_repair_prompt (utils.py:282) envia as definições dos parâmetros, os valores usados, o comando completo e os últimos 2000 caracteres do stderr, e pede que retorne apenas os parâmetros a alterar.

Esse caminho roda dentro do processo do Slicer, não na CLI: _proposeRepair adiciona a pasta Agent_CLI ao sys.path e reimporta Agent_CLI_utils para não duplicar a lógica. A correção passa de novo por ParameterValidator e depois por build_cli_args, um diff old -> new é exibido e uma nova confirmação Yes/No é exigida. Se o diff estiver vazio, o ciclo para.

_suggestFixFor (Agent.py:903) complementa com um diagnóstico sem LLM, baseado em palavras-chave: modelo Ollama ausente, ModuleNotFoundError, NameError: name 'nn' is not defined (uma regressão conhecida em transformers>=4.53.0, huggingface/transformers#43784), Numpy is not available (conflito de ABI do numpy 2 com os wheels de torch) ou uma falha de conexão com o Ollama.

Os caminhos dos scripts não se resolvem

Um problema mais fundamental que as assinaturas. O manifesto só dá nomes simples (path: "ALI_CBCT.py"). resolve_tool_path (utils.py:143) procura, em ordem, em: $AGENT_CLI_TOOLS_DIR/<name>, <manifest_dir>/CLI files/<name>, <manifest_dir>/<name>, depois <ancestor>/CLI files/<name> subindo 4 níveis.

Sem AGENT_CLI_TOOLS_DIR, o Agent não consegue executar nenhum módulo

Não existe nenhuma pasta CLI files em lugar algum do SlicerAutomatedDentalTools. O comentário do código cita o layout AI_Agent/Agent_CLI/ + .../CLI files/, o do repositório original de onde Agent_CLI foi extraído. Aqui, cada script fica na pasta do seu próprio módulo (ALI_CBCT/ALI_CBCT.py, …). Nenhum candidato corresponde, e a função retorna candidates[0] "para que a mensagem de erro aponte para um caminho depurável", ou seja, <Agent_CLI>/CLI files/ALI_CBCT.py.

subprocess.run não lança exceção (o executável, sys.executable, existe); é o Python que sai com código 2 diante de um arquivo que não encontra, o que dispara o ciclo de reparo — que, como corrige parâmetros, estruturalmente nada pode fazer.

E mesmo com os caminhos resolvidos, alguns alvos ainda falhariam: DOCShapeAXI_CLI.py importa shapeaxi, MRI2CBCT_TMJ_CROP.py importa nnunetv2. Esses pacotes ficam em ambientes conda que os respectivos módulos Slicer invocam via conda run -n … ou CondaSetUpCall. O Agent, por sua vez, executa tudo com sys.executable, ou seja, o Python do Slicer, nunca conda.

10. Salvaguardas

O que existe:

  • Uma confirmação modal obrigatória antes de cada execução, listando todos os parâmetros, e uma segunda antes de cada tentativa de reparo.
  • Bloqueio por parâmetros obrigatórios ausentes: nada é executado enquanto missing_required não estiver vazio.
  • Coerção de tipos e verificações de choices / min / max / extensão em pasta.
  • Mascaramento das pastas temporárias, preenchidas a partir de slicer.util.tempDirectory() e não pelo modelo.
  • Limites: MAX_REPAIR_ATTEMPTS = 2, histórico truncado em MAX_HISTORY_ENTRIES = 40 turnos.
  • try global em main(): o stdout sempre continua sendo JSON analisável, o traceback vai para o stderr.

O que não existe:

  • Nenhum limiar de confiança. tool_confidence e parameters_confidence são calculados e serializados, depois ignorados. Um roteamento a 0,1 é tratado como um roteamento a 0,95.
  • Nenhuma verificação de existência de caminho. Um caminho alucinado passa na validação, passa na confirmação (o operador tem que percebê-lo a olho na caixa de diálogo) e só falha quando o módulo-alvo é executado.
  • Os erros do validador nunca são exibidos. errors, warnings e extra_params são produzidos e depois descartados.
  • Nenhuma proteção das pastas de saída. Se o modelo escolher uma pasta de dados de entrada como output_folder, nada o impede. Várias CLIs do repositório sobrescrevem seu arquivo de entrada.
  • Os parâmetros fora da especificação não são filtrados no modo --flag.
  • log_path recebe uma pasta, não um arquivo: os nomes log_path e logPath estão na lista de parâmetros substituídos por input.temp_folder. As CLIs que abrem esse caminho para escrita vão falhar.
  • Nenhuma lista branca de executáveis. subprocess.run recebe a lista exatamente como montada. A proteção real é que tool_path vem do manifesto, não do LLM — o modelo controla os valores, não o binário.

11. Ambiente

CheckDependencies (Agent.py:1141) executa um slicer.util.pip_install dentro do Python do Slicer, nesta ordem, que importa:

PacoteRazão da fixação
ollamaapenas o cliente python — o pip não fornece o servidor
pyyamlleitura do manifesto
transformers<4.53.0regressão NameError: name 'nn' is not defined em integrations/accelerate.py, quebra a importação do cross-encoder
numpy<2numpy ≥ 2 quebra a ABI dos wheels pip de torch (RuntimeError: Numpy is not available)

Agent_CLI.py roda em um processo separado, mas compartilha o site-packages do Slicer, daí a instalação no lado do widget. Nenhum ambiente conda é criado ou usado.

O servidor Ollama é verificado por uma simples sondagem de socket em 127.0.0.1:11434 (_ollama_responding, timeout de 0,5 s), relançado se necessário via Popen([binary, "serve"]) com uma espera de até ~30 s em passos de 500 ms mantendo a interface responsiva. ensure_agent_ollama_running() é chamado novamente antes de cada mensagem (Agent.py:772), porque um servidor iniciado pelo módulo não sobrevive a uma reinicialização do Slicer.

Windows: CREATE_NO_WINDOW para não piscar uma janela de console. Sem WSL, ao contrário do resto do repositório.

12. Armadilhas e pontos frágeis

  • resolve_tool_path não encontra nada neste repositório (§8). É o bloqueio número um. Correções possíveis: criar uma pasta CLI files com links, definir AGENT_CLI_TOOLS_DIR, ou colocar no manifesto caminhos relativos ao repositório e ampliar a busca.
  • 17 assinaturas de 23 estão erradas, e o deslocamento é silencioso.
  • batchdentalseg e clic não são CLIs. cli_style: ui_module não é tratado em lugar nenhum: cai no ramo --flag, que produz um comando que não pode funcionar com um módulo Slicer com script.
  • input.folders.split(",") quebra qualquer caminho que contenha uma vírgula, tanto na lista de pastas quanto no join(",") do lado do widget.
  • O cross-encoder é recarregado a cada mensagem (processo novo), e sua falha degrada para as três primeiras ferramentas do manifesto sem que o operador seja informado.
  • k=3 é fixo no código. 23 ferramentas, 3 candidatas: uma má pontuação do cross-encoder não pode ser recuperada pelo LLM.
  • priority é inerte, o que torna enganosa a classificação do manifesto.
  • subprocess.run bloqueia a thread da GUI durante toda a execução do módulo.
  • O histórico mistura prosa da interface com contexto de roteamento: os balões de chat são reenviados tal qual como turnos assistant a um roteador restrito a JSON.
  • OnRetrieveButton reconstrói o histórico separando pelo emoji 👨: / 🤖: (Agent.py:1126): uma mensagem que contenha esses caracteres dessincroniza a alternância.
  • Detecção do tema por amostragem de pixel (widget.grab(), luminância do pixel (5,5)), porque QPalette retorna cores de tema claro mesmo sob um tema escuro no Slicer (Agent.py:656). Funciona, mas depende do momento da primeira renderização — daí o QTimer.singleShot(0, ...) em setup.
  • Código morto: AgentLogic.process(), build_tool_spec() (e todo o suporte a patterns/defaults ao seu redor), ValidationReport, positional_order, o campo examples do manifesto, _cross_encoder_model, Agent_CLI/Resources/UI/Agent_CLI.ui.
  • extract_parameters retorna 4 valores enquanto sua anotação declara 3.
