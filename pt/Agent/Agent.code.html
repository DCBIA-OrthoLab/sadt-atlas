Agent, legado: o código

Para desenvolvedores: o que o módulo Agent legado faz no código, com referências file:line, os prompts, a verificação do manifest, o ambiente e os achados. A explicação legível do mesmo pipeline está na página do atlas.

Agent_CLI Código Atlas (explicação) Bibliografia VISOR: parcial

Tudo roda localmente: um LLM de 8B servido pelo Ollama, mais um pequeno cross-encoder para pré-selecionar as ferramentas candidatas.

Duas bases de código

Tudo o que está numerado abaixo descreve o módulo legado do Slicer (SlicerAutomatedDentalTools em 3c67957, 2026-10-26). O VISOR tem uma ferramenta de servidor chamada Agent, um roteador sobre um endpoint externo do Ollama, mas nenhum cliente a chama: o painel AgentRemote distribuído no cliente do VISOR é uma cópia do widget legado que ainda roda localmente. Ambos são descritos na página do VISOR para o Agent.

1. Posição na cadeia

Explicação em linguagem simples e matemática: página do atlas.

Ninguém chama o Agent. Um grep por slicer.modules.agent não encontra nenhum chamador fora do próprio módulo. É um ponto de entrada terminal.

Código morto · legado e cópia do cliente

Legado (3c67957); ausente da ferramenta de servidor do VISOR. A ferramenta de servidor é um pacote Python sem widget e sem wrapper de CLI (SADT-VISOR tools/Agent/src/sadt_agent/). Nunca é chamado. Agent_CLI/Resources/UI/Agent_CLI.ui também é inerte: um módulo CLI não carrega um arquivo .ui.

3. Os modelos

Explicação em linguagem simples e matemática: página do atlas.

3.1 O LLM, qwen3:8b via Ollama

Explicação em linguagem simples e matemática: página do atlas.

Uma única constante, duplicada nas duas pontas: DEFAULT_MODEL = "qwen3:8b" (utils.py:21) e MODEL_NAME = "qwen3:8b" (Agent.py:29). get_router_model() respeita uma variável de ambiente ROUTER_MODEL que permite trocar por qualquer modelo do Ollama sem tocar no código.

O mesmo modelo atende as três chamadas: roteamento, extração de parâmetros, reparo. Nenhum modelo especializado, nenhum fine-tuning.

Somente legado (3c67957); ausente do VISOR. Não há teste de /snap/ na cópia do cliente (nenhuma ocorrência em AutomatedDentalToolsRemote AgentRemote/AgentRemote.py), e a ferramenta de servidor nem instala nem inicia o Ollama: ela precisa de um endpoint acessível (SADT-VISOR tools/Agent/src/sadt_agent/llm.py:1-25, endpoint resolvido em :38-39).

O módulo nunca passa uma diretiva de dispositivo. O binário do Ollama decide, e o código tira daí uma consequência explícita: no Linux, um Ollama instalado via snap fica em sandbox, não enxerga a GPU NVIDIA e recua para a CPU, 80–90 s por resposta para um modelo de 8B, um número medido e fixado no código (comentário em Agent.py:1101-1103, repetido na caixa de aviso). O módulo detecta /snap/ no realpath do binário e avisa, sem poder corrigir (o servidor snap já ocupa a porta 11434, e removê-lo exige sudo).

Quando nenhum Ollama é encontrado, install_official_ollama() (Agent.py:111) baixa o arquivo portátil oficial para ~/.slicer_agent/ollama (substituível via SLICER_AGENT_HOME): ollama-linux-{amd64,arm64}.tgz, ollama-windows-{amd64,arm64}.zip ou Ollama-darwin.zip, extraído com ditto e depois liberado da quarentena com xattr. Esses arquivos embutem as bibliotecas CUDA/Metal, daí a escolha deliberada de não usar curl | sudo sh (nenhuma senha de root pela GUI) nem o pacote snap. LD_LIBRARY_PATH é apontada para <install>/lib/ollama para que o binário encontre suas próprias bibliotecas (Agent.py:67).

Apenas dois ajustes de chamada, em chat_with_auto_pull (utils.py:96):

  • keep_alive="30m" em vez dos 5 minutos padrão, para não recarregar 5 GB na VRAM entre duas mensagens;
  • format="json" para o roteador, a extração e o reparo (uma restrição de gramática do lado do Ollama): não para o modo consultor.

Nenhum temperature, seed, num_ctx ou think é passado. Como o qwen3 é um modelo de raciocínio híbrido, o modo consultor pode portanto deixar vazar texto de raciocínio conforme a versão do Ollama; o único pós-processamento é output.replace("*","").replace("#","") (Agent_CLI.py:215), que remove o markdown removendo os caracteres.

Se o modelo não está presente, chat_with_auto_pull intercepta a mensagem not found, executa ollama.pull(model, stream=True) exibindo o progresso, e depois refaz o chat. Qualquer outro erro é relançado como está.

3.2 O cross-encoder: ms-marco-MiniLM-L-6-v2

Explicação em linguagem simples e matemática: página do atlas.

É a única rede neural de verdade carregada no processo. CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") (utils.py:53), via sentence-transformers, portanto pesos transformers/safetensors baixados do Hugging Face Hub e guardados em cache em ~/.cache/huggingface.

MiniLM, 6 camadas, 22.7 M de parâmetros, destilado de MiniLM-L12-H384-uncased, treinado no MS MARCO Passage Ranking. Ele não é um modelo de embeddings: não há vetores nem similaridade de cosseno. A consulta e o documento são concatenados e alimentados juntos no transformer, que produz um único escalar de relevância sem limites (tipicamente de −10 a +10). O dispositivo é aquele que o sentence-transformers escolhe por conta própria, conforme a wheel do torch instalada.

O cache _cross_encoder_model não serve para nada na prática: o Agent_CLI.py é um processo novo a cada pedido, de modo que o modelo é recarregado a cada mensagem. O comentário no código admite isso.

Fallback silencioso do cross-encoder · legado e cópia do cliente; não a ferramenta de servidor

Legado (3c67957); ausente da ferramenta de servidor do VISOR. O ranqueador do servidor é BM25 e só reduz a lista quando tem um sinal: sem nenhuma sobreposição entre o pedido e qualquer ferramenta, todas as ferramentas são mostradas (SADT-VISOR tools/Agent/src/sadt_agent/ranking.py:222-239). O fallback do cross-encoder continua valendo na cópia do cliente (AutomatedDentalToolsRemote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:94; legado Agent_CLI/Agent_CLI_utils/utils.py:94).

Se o carregamento falha, o fallback é brusco: scripts[:k], isto é, as três primeiras ferramentas do manifest (ali_cbct, ali_ios, amasss_cli) qualquer que seja a pergunta (utils.py:94). O único vestígio é uma linha impressa na saída da CLI (utils.py:93); o chat não é avisado.

4. Roteamento

Explicação em linguagem simples e matemática: página do atlas.

Duas etapas, e o LLM só entra na segunda.

Etapa 1, pré-seleção por cross-encoder. cross_encoder_retrieve_candidates(manifest, prompt, k=3) constrói um documento por ferramenta:

docs.append(f"{s['name']}: {s['description']} (tags: {tags})")
scores = model.predict([(user_text, doc) for doc in docs])
ranked = sorted(zip(scores, scripts), reverse=True)
return [s for _, s in ranked[:k]]

16 pares pontuados, ordenados em ordem decrescente, top-3 fixo no código (k=3 nunca é parametrizado). O campo priority do manifest (valores de 1 a 23, com lacunas) nunca é lido : a linha que o leria está comentada (utils.py:216). A ferramenta certa, se ficou em 4º lugar, está perdida para sempre; o LLM nunca a verá.

Etapa 2, escolha pelo LLM. O prompt de sistema (Agent_CLI.py:105):

You are a tool router. Output ONLY one JSON object.
Schema:
{"tool": string|null, "confidence": number, "reason": string}

Rules:
- Choose tool ONLY from the candidate list provided by the user message.
- If none match, set tool = null and confidence <= 0.4.
- Do not invent tool names.
- Keep reason short (max 1 sentence).

A mensagem do usuário é USER_REQUEST: <prompt> seguida de CANDIDATES (choose exactly one name from this list): e do bloco construído por build_candidates_block: uma linha por candidata, i) name — description (truncated to 140 characters) | tags: t1, t2, … (8 max).

Três coisas dignas de nota:

  • O contexto das pastas não é dado ao roteador. folders_context só é acrescentado ao prompt de extração.
  • O histórico da conversa é injetado entre o turno do sistema e o do usuário (*history), e contém os balões de chat brutos do widget ("After reflection, I would like to run …"). O roteador JSON recebe, portanto, prosa da interface como turnos de "assistant".
  • confidence e reason não servem para nada. confidence é lida, arredondada, serializada no JSON de saída como tool_confidence… e nunca relida pelo widget. Nenhum limiar em lugar nenhum. A instrução "confidence ≤ 0.4" não é uma restrição, apenas uma sugestão ao modelo.

A única rede de segurança é textual: if selected_tool and selected_tool != "null" and selected_tool != "None". Um nome de ferramenta alucinado que não está no manifest passa nesse teste, depois faz build_cli_args falhar com um KeyError, capturado pelo try global em main() e devolvido como {"error": …}.

tools = build_tool_spec(manifest) (Agent_CLI.py:72) é calculado e depois nunca usado: código morto, junto com todo o tratamento da "estrutura antiga" (patterns, defaults) que nenhuma entrada do manifest atual usa.

5. Extração de parâmetros

Explicação em linguagem simples e matemática: página do atlas.

Uma segunda chamada ao LLM, com uma ferramenta já escolhida, dentro de extract_parameters (utils.py:220).

Mascaramento dos parâmetros técnicos. Os parâmetros chamados temp_fold, tmp_folder, temp_folder, log_path ou logPath são removidos da especificação antes de construir o prompt: não adianta pedir ao modelo que invente uma pasta temporária. Eles são reinjetados depois com o valor input.temp_folder, isto é, o slicer.util.tempDirectory() criado pelo widget a cada clique (Agent_CLI.py:153), e removidos de missing_required.

O prompt de extração (parameter_extraction_improved.py:40) lista cada parâmetro como - name (type) [REQUIRED|optional] (encode: …): description, depois impõe sete regras: formatação de listas segundo encode (comma_no_brackets, space_separated, comma_separated, python_literal), booleanos e números em JSON puro, "if the name contains folder or dir, give a folder with no file name," e acima de tudo:

7. ONLY extract parameters mentioned in the user request
   - Do NOT invent values
   - Leave unmentioned optional parameters absent

Saída obrigatória: {"extracted": {...}, "confidence": 0.0-1.0, "missing_required": [...], "notes": "..."}. O missing_required produzido pelo modelo é ignorado: o validador é que conta.

A resolução de caminhos é inteiramente delegada ao LLM · corrigida em parte no VISOR

A parte dos caminhos também vale no VISOR; a parte da vírgula está corrigida. A ferramenta de servidor recebe folders como lista, de modo que uma vírgula no nome de uma pasta não a divide mais (SADT-VISOR tools/Agent/src/sadt_agent/__init__.py:40,124). O modelo continua sendo a única coisa que decide qual caminho vai em qual argumento: validation.py verifica tipos e choices contra o esquema publicado, e não que um caminho exista (validation.py:1-30).

O widget passa a lista de itens soltos na zona de soltar, unidos por vírgulas (Agent.py:770); a CLI a divide de novo em , e a envolve:

FOLDERS_CONTEXT:
<one path per line>

Rules:
- Treat FOLDERS_CONTEXT as the source of truth for paths.
- If a required path parameter is missing, try to infer it from FOLDERS_CONTEXT.
- If multiple candidates exist, pick the most specific match and explain briefly in 'reason'.

Este bloco é concatenado ao prompt do usuário, e não passado separadamente. Não há correspondência heurística, nem inspeção do conteúdo das pastas, nem verificação de existência: cabe ao modelo adivinhar qual dos caminhos soltos é o T1, qual é o T2, qual é a pasta do modelo. Um caminho que contém uma vírgula é cortado em dois pelo split(",").

A validação (parameter_validator.py) encadeia seis passagens: campos obrigatórios ausentes, coerção de tipos (bool/int/float/list/path/string), sintaxe de caminhos, choices, min/max, parâmetros fora da especificação. Dois detalhes úteis:

  • encode: lower_str_bool força a string "true"/"false" para minúsculas, porque várias CLIs comparam o argumento bruto sem .lower(): str(True) daria "True" e nunca corresponderia.
  • _check_paths só verifica duas coisas: que Path(str(value)) não levante exceção (quase nunca levanta) e que um parâmetro cujo nome contém folder/dir não termine com uma extensão conhecida. A existência do caminho nunca é testada.

O resultado da validação é quase todo descartado: errors e warnings não aparecem em lugar nenhum. Seu único efeito é final_confidence = confidence * 0.6 quando inválido, e essa confidence não é lida por ninguém. Só params e missing_required sobrevivem.

6. Construção e execução do comando

Explicação em linguagem simples e matemática: página do atlas.

Sim, o módulo é realmente lançado. Sem ambiguidade.

A CLI apenas constrói o comando. build_cli_args (utils.py:350) mescla os valores padrão do manifest com os parâmetros extraídos, depois:

return [sys.executable, tool_path] + cli

sys.executable é o interpretador do processo Agent_CLI, isto é, o Python do Slicer. Para cli_style: positional (14 ferramentas de 16), os valores são concatenados na ordem de declaração do manifest: positional_order é suportado, mas nenhuma entrada o define. Para qualquer outro cli_style, a execução cai no ramo --flag value, iterando sobre merged: parâmetros alucinados fora da especificação são, portanto, emitidos.

A lista é devolvida ao widget no campo command do JSON. É o AgentWidget que a executa, e apenas se missing_required == []:

  1. um balão de chat, "After reflection, I would like to run X";
  2. QMessageBox.question listando key=value para cada parâmetro (Agent.py:841; a etapa de reparo pergunta de novo, :938);
  3. em Yes → runToolWithRepair → subprocess.run(cli_args, capture_output=True).

Se missing_required não está vazio, o agente não lança nada: ele exibe a lista do que falta junto com os valores já conhecidos, e espera uma mensagem de continuação (à qual o histórico da conversa permitirá reconectá-la).

O Slicer congela durante o trabalho · legado e cópia do cliente; não a ferramenta de servidor

Legado (3c67957); ausente da ferramenta de servidor do VISOR. A ferramenta de servidor executa a ferramenta escolhida pelo supervisor, apenas quando execute é true (SADT-VISOR tools/Agent/src/sadt_agent/execution.py:70). O congelamento continua valendo na cópia do cliente (AutomatedDentalToolsRemote AgentRemote/AgentRemote.py:767; legado Agent/Agent.py:898).

subprocess.run é síncrono e roda na thread da GUI: o Slicer fica congelado durante todo o trabalho, que, para uma segmentação do AMASSS ou um registro do AREG, se mede em dezenas de minutos.

7. O ciclo de reparo

Explicação em linguagem simples e matemática: página do atlas.

Com um código de retorno diferente de zero, runToolWithRepair (Agent.py:880) pede ao LLM que corrija os parâmetros, no máximo MAX_REPAIR_ATTEMPTS = 2 vezes. build_repair_prompt (utils.py:282) envia as definições dos parâmetros, os valores usados, o comando completo e os últimos 2000 caracteres do stderr, e pede que devolva apenas os parâmetros a mudar.

Este caminho roda dentro do processo do Slicer, e não da CLI: _proposeRepair acrescenta a pasta Agent_CLI a sys.path e reimporta Agent_CLI_utils para não duplicar a lógica. A correção volta por ParameterValidator e depois build_cli_args, um diff old -> new é exibido, e uma nova confirmação Yes/No é exigida. Se o diff está vazio, o ciclo para.

_suggestFixFor (Agent.py:1240) complementa isso com um diagnóstico por palavras-chave, sem LLM: modelo do Ollama ausente, ModuleNotFoundError, NameError: name 'nn' is not defined (uma regressão conhecida em transformers>=4.53.0, huggingface/transformers#43784), Numpy is not available (conflito de ABI do numpy 2 com as wheels do torch), ou uma falha de conexão com o Ollama.

Ele não tem mais nenhuma entrada medx_dashboard ou medx_summarize (o MedX saiu da árvore), e a reformulação do MRI2CBCT removeu cinco outras: mri2cbct_approx, mri2cbct_reg, mri2cbct_lr_crop, mri2cbct_orient_center e mri2cbct_tmj_crop. Só mri2cbct_resample permanece. As três CLIs do novo pipeline, MRI2CBCT_PREPARE, MRI2CBCT_SEGMENT_MRI e MRI2CBCT_REGISTER, existem em MRI2CBCT_CLI/, mas não têm entrada no manifest, de modo que o Agent também não consegue alcançá-las (verificado com grep -i mri no manifest: a única ocorrência de um script é mri2cbct_resample).

Os caminhos dos scripts não se resolvem

Explicação em linguagem simples e matemática: página do atlas.

Um problema mais fundamental que as assinaturas. O manifest só dá nomes simples (path: "ALI_CBCT.py"). resolve_tool_path (utils.py:143) procura, em ordem, em: $AGENT_CLI_TOOLS_DIR/<name>, <manifest_dir>/CLI files/<name>, <manifest_dir>/<name>, depois <ancestor>/CLI files/<name> subindo 4 níveis.

Sem AGENT_CLI_TOOLS_DIR, o Agent não consegue lançar nenhum módulo · vale para a cópia do cliente

Vale também para a cópia do cliente; não se aplica à ferramenta de servidor. A extensão que distribui o AgentRemote também não tem essa pasta, e seu resolvedor ainda lê AGENT_CLI_TOOLS_DIR (AutomatedDentalToolsRemote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:154; os módulos CLI foram apagados, CMakeLists.txt:49-56). A ferramenta de servidor não lança nada por caminho.

Não existe nenhuma pasta CLI files em lugar nenhum do SlicerAutomatedDentalTools. O comentário do código cita a organização AI_Agent/Agent_CLI/ + .../CLI files/, a do repositório original de onde o Agent_CLI foi extraído. Aqui, cada script vive na pasta do seu próprio módulo (ALI_CBCT/ALI_CBCT.py, …). Nenhum candidato corresponde, e a função devolve candidates[0] "so the error message points to a debuggable path," isto é, <Agent_CLI>/CLI files/ALI_CBCT.py.

subprocess.run não levanta exceção (o executável, sys.executable, existe); é o Python que sai com código 2 diante de um arquivo que não encontra, o que dispara o ciclo de reparo, que, como corrige parâmetros, estruturalmente não pode fazer nada a respeito.

E mesmo com os caminhos resolvidos, alguns destinos ainda falhariam: DOCShapeAXI_CLI.py importa shapeaxi, um pacote que vive em um ambiente conda que seu módulo Slicer invoca via conda run -n … ou CondaSetUpCall. (O MRI2CBCT deixou de ser um exemplo: seu nnunetv2 agora roda no próprio Python do Slicer.) O Agent, por sua vez, lança tudo com sys.executable, isto é, o Python do Slicer, nunca o conda.

10. Salvaguardas

Explicação em linguagem simples e matemática: página do atlas.

O que existe:

  • Uma confirmação modal obrigatória antes de cada execução, listando todos os parâmetros, e uma segunda antes de cada tentativa de reparo.
  • Bloqueio por parâmetros obrigatórios ausentes: nada é lançado enquanto missing_required não está vazio.
  • Coerção de tipos e verificações de choices / min / max / extensão em pasta.
  • Mascaramento das pastas temporárias, preenchidas a partir de slicer.util.tempDirectory() e não pelo modelo.
  • Limitação: MAX_REPAIR_ATTEMPTS = 2, histórico truncado em MAX_HISTORY_ENTRIES = 40 turnos.
  • try global em main(): o stdout continua sempre sendo JSON analisável, o traceback vai para o stderr.

O que não existe:

  • Nenhum limiar de confiança. tool_confidence e parameters_confidence são calculados e serializados, depois ignorados. Um roteamento a 0.1 é tratado da mesma forma que um a 0.95.
  • Nenhuma verificação de existência de caminho. Um caminho alucinado passa na validação, passa na confirmação (o operador precisa percebê-lo a olho na caixa de diálogo) e só falha quando o módulo de destino é lançado.
  • Os erros do validador nunca são exibidos. errors, warnings e extra_params são produzidos e depois descartados.
  • Nenhuma proteção nas pastas de saída. Se o modelo escolhe uma pasta de dados de entrada como output_folder, nada o impede. Várias CLIs do repositório sobrescrevem seu arquivo de entrada.
  • Os parâmetros fora da especificação não são filtrados no modo --flag.
  • log_path recebe uma pasta, e não um arquivo: os nomes log_path e logPath estão na lista dos parâmetros substituídos por input.temp_folder. As CLIs que abrem esse caminho para escrita vão falhar.
  • Nenhuma lista de executáveis permitidos. subprocess.run recebe a lista exatamente como foi construída. A proteção real é que tool_path vem do manifest, e não do LLM: o modelo controla os valores, não o binário.

11. Ambiente

Explicação em linguagem simples e matemática: página do atlas.

CheckDependencies (Agent.py:1018) executa um slicer.util.pip_install dentro do Python do Slicer, nesta ordem, o que importa:

PacoteRazão do pin
ollamaapenas o cliente python: o pip não fornece o servidor
pyyamlleitura do manifest
transformers<4.53.0regressão NameError: name 'nn' is not defined em integrations/accelerate.py, quebra a importação do cross-encoder
numpy<2numpy ≥ 2 quebra a ABI das wheels do torch via pip (RuntimeError: Numpy is not available)
sentence-transformerstraz o torch junto; instalado por último para não alterar os pins

O Agent_CLI.py roda em um processo separado, mas compartilha o site-packages do Slicer, daí a instalação do lado do widget. Nenhum ambiente conda é criado ou usado.

O servidor Ollama é verificado com uma simples sonda de socket em 127.0.0.1:11434 (_ollama_responding, timeout de 0.5 s), relançado se necessário via Popen([binary, "serve"]) com uma espera de até ~30 s em passos de 500 ms mantendo a interface viva. ensure_agent_ollama_running() é chamado de novo antes de cada mensagem (Agent.py:752), porque um servidor lançado pelo módulo não sobrevive a uma reinicialização do Slicer.

Windows: CREATE_NO_WINDOW para não piscar uma janela de console. Sem WSL, ao contrário do resto do repositório.

12. Armadilhas e pontos frágeis

Explicação em linguagem simples e matemática: página do atlas.

  • resolve_tool_path não encontra nada neste repositório (§8). Este é o bloqueio número um. Correções possíveis: criar uma pasta CLI files com links, definir AGENT_CLI_TOOLS_DIR, ou pôr caminhos relativos ao repositório no manifest e ampliar a busca.
  • 14 assinaturas de 16 estão erradas, e o deslocamento é silencioso.
  • batchdentalseg e clic não são CLIs. cli_style: ui_module não é tratado em lugar nenhum: ele cai no ramo --flag, que produz um comando que não pode funcionar em um módulo Slicer com script.
  • input.folders.split(",") quebra qualquer caminho que contenha uma vírgula, tanto para a lista de pastas quanto para o join(",") do lado do widget.
  • O cross-encoder é recarregado a cada mensagem (processo novo), e sua falha degrada para as três primeiras ferramentas do manifest sem que o operador seja informado.
  • k=3 é fixo no código. 16 ferramentas, 3 candidatas: uma pontuação ruim do cross-encoder não pode ser recuperada pelo LLM.
  • priority é inerte, o que torna enganosa a classificação do manifest.
  • subprocess.run bloqueia a thread da GUI durante toda a execução do módulo.
  • O histórico mistura prosa da interface com contexto de roteamento: os balões de chat são reenviados tal como estão como turnos assistant a um roteador restrito a JSON.
  • OnRetrieveButton reconstrói o histórico dividindo pelo emoji 👨: / 🤖: (Agent.py:1003-1004), apenas quando um arquivo de discussão salvo é recarregado: uma mensagem que contenha esses caracteres dessincroniza a alternância. O histórico enviado à CLI durante um chat ao vivo é uma lista de turnos, e não texto dividido por emoji (Agent.py:736-743).
  • Detecção do tema por amostragem de pixel (widget.grab(), luminância do pixel (5,5)), porque o QPalette devolve cores do tema claro mesmo sob um tema escuro no Slicer (Agent.py:649). Funciona, mas depende do momento da primeira renderização, daí o QTimer.singleShot(0, ...) em setup.
  • Código morto: AgentLogic.process(), build_tool_spec() (e todo o suporte a patterns/defaults em torno dele), ValidationReport, positional_order, o campo examples do manifest, _cross_encoder_model, Agent_CLI/Resources/UI/Agent_CLI.ui.
  • extract_parameters devolve 4 valores enquanto sua anotação declara 3.

  • SlicerAutomatedDentalTools
