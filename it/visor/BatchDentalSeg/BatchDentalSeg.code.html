BatchDentalSeg su VISOR: il codice

Per gli sviluppatori: che cosa fa nel codice il porting di BatchDentalSeg su VISOR, con riferimenti file:line, firme, argomenti, ambiente, le differenze rispetto al codice legacy e i riscontri. La spiegazione leggibile della stessa pipeline, con la matematica, è nella pagina atlante. Come BatchDentalSeg gira in VISOR (client e server), che cosa è cambiato rispetto al modulo Slicer legacy, e che cosa fa il codice del porting, passo per passo. Il modulo legacy è descritto nella sua pagina.

Codice Atlante (spiegazione) VISOR Batch_Dental_Seg Pagina legacy Guida (VISOR) Bibliografia

VISOR esegue BatchDentalSeg su un server: Slicer invia le scansioni e il nome di un modello ospitato, e riceve volumi di etichette, file per etichetta o mesh. Una rete nnU-Net v2, scelta tra quattro bundle, etichetta ogni struttura di una scansione in un solo passaggio, e una chiamata copre l'intero batch. Questa pagina dice che cosa gira dove, segue la pipeline dal file di input al report di esecuzione, elenca gli argomenti che il server pubblica e confronta ogni passo con il modulo legacy. Tutto qui è stato letto nel codice, non osservato su un server in funzione, e nulla qui dice che un dato server sia in produzione.

I riferimenti nominano prima il repository: SADT-VISOR (codice dello strumento, tool/vface @ 6ba2a78), VISOR-serve (server, @ e9a7e5d), AutomatedDentalToolsRemote (client Slicer, @ 19b95e8) e legacy (SlicerAutomatedDentalTools @ 3c67957). Un nome di file nudo come pipeline.py, catalogs.py, layout.py, nnunet_runner.py, low_memory.py, mesh_export.py, progress.py o __init__.py si trova nel pacchetto SADT-VISOR tools/Batch_Dental_Seg/src/sadt_batchdentalseg/. SegmentationWidget.py, Queue.py e PythonDependencyChecker.py sono file legacy di BATCHDENTALSEG/BATCHDENTALSEGLib/ (il widget ha 3037 righe a 3c67957).

3. La pipeline

segment() (SADT-VISOR pipeline.py:216-398) è una linea retta. Il bundle viene controllato prima che venga letta qualsiasi scansione, ogni scansione viene convertita in un'unica cartella, nnU-Net gira una volta su quella cartella, poi ogni scansione viene riscritta sulla propria griglia. Solo il passo della rete è appreso.

Spiegazione in linguaggio semplice e matematica: pagina atlante.

3.1 Input e scoperta

discover_scans() (pipeline.py:87-107) prende un file così com'è, oppure percorre una cartella ricorsivamente con os.walk e tiene i file la cui estensione è in sadt_naming.VOLUME: .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl, confrontate in minuscolo (SADT-VISOR naming/src/sadt_naming/__init__.py:36). In una cartella, un file viene saltato quando sembra un output precedente di questo strumento:

def is_previous_output(filename, suffix):                      # pipeline.py:72-84
    base, _extension = split_scan_extension(os.path.basename(filename))
    if suffix and base.endswith(f"_{suffix}"):
        return True
    return any(base.endswith(f"_{suffix}_{name.replace(' ', '-')}")
               for model in catalogs.MODELS.values()
               for name in model.labels)

Con il valore predefinito prediction_ID = "Seg", cioè qualsiasi nome base che finisce con _Seg o con _Seg_<label> per qualsiasi etichetta di uno dei quattro modelli, così una cartella può essere rieseguita sul posto (vedi il riscontro del §8 sulle scansioni il cui nome finisce così). Nessuna scansione solleva ToolInputError (pipeline.py:243-248). L'albero di input viene conservato: input_root è la cartella, oppure il genitore di un singolo file (pipeline.py:250), e ogni caso è descritto nel report dal suo percorso relativo a essa, mai da un percorso assoluto (pipeline.py:264-265).

3.2 Il modello: un nome, un bundle, una tabella di etichette

resolve_model() (pipeline.py:110-133) gira prima che venga letta qualsiasi scansione. Il nome della cartella del percorso model viene cercato in catalogs.MODELS; un nome sconosciuto viene rifiutato con l'elenco dei modelli noti. Dentro la cartella, find_model_folder() percorre l'albero alla ricerca della directory che contiene dataset.json, plans.json e fold_0/checkpoint_final.pth, tutti e tre controllati (nnunet_runner.py:57-73): i quattro bundle non condividono una struttura, e DentalSegmentator arriva come zip con un proprio albero Dataset<n>/ (nnunet_runner.py:37-41). Un bundle incompleto viene rifiutato con il comando che lo prepara di nuovo (pipeline.py:126-132).

MODELS = {model.name: model for model in (                     # catalogs.py:126-152
    Model("DentalSegmentator",  _FIVE_LABELS,      "Adult dental CT/CBCT. ..."),
    Model("PediatricDentalSeg", _FIVE_LABELS,      "Paediatric dental CT/CBCT, ..."),
    Model("NasoMaxillaDentSeg", _NASO_LABELS,      "Six segments: the maxilla is separated ..."),

Poiché la tabella delle etichette segue il nome della cartella, un chiamante non può abbinare un bundle alle etichette di un altro: non esiste un secondo argomento da sbagliare (catalogs.py:120-125). I valori sono gli interi che la rete emette, e il codice li scrive invariati.

3.3 Conversione nel layout di nnU-Net

Ogni scansione viene convertita in un'unica cartella, <output_dir>/.batchdentalseg_work/nnunet_in/, con un identificativo di caso posizionale (pipeline.py:256-277):

case_id = f"case_{index:04d}"                                   # pipeline.py:275
_convert_to_nifti(scan, os.path.join(nnunet_input, f"{case_id}_0000.nii.gz"))

def _convert_to_nifti(scan_path, destination):                  # pipeline.py:140-149
    sitk.WriteImage(sitk.ReadImage(scan_path), destination)

Una lettura più una scrittura, mai una rinomina: nnU-Net sceglie il proprio lettore dall'estensione, quindi un NRRD rinominato in .nii.gz verrebbe letto male. Il tipo dei voxel viene lasciato com'è; nnU-Net lo converte da sé in float32 (pipeline.py:143-145). Gli id sono posizionali perché nnU-Net scrive il suo output sotto l'id dell'input, e due scansioni chiamate scan.nii.gz in sottocartelle diverse collidrebbero (pipeline.py:256-259). Una scansione che non può essere letta viene registrata come failed con "could not be read" e saltata; solo quando nessuna può essere letta l'esecuzione si ferma (pipeline.py:278-298).

In questo pacchetto non è scritto nessun windowing di intensità e nessun ritaglio. Gli unici ricampionamenti che aggiunge sono quello facoltativo su GPU (§3.5) e quello che rimette il risultato sulla griglia della scansione (§3.6, pipeline.py:152-171). Il resto del preprocessing è quello proprio di nnU-Net, dal plans.json di ciascun bundle, e gira in quest'ordine (nnunetv2 2.8.1 come installato nell'ambiente dello strumento, nnunetv2/preprocessing/preprocessors/default_preprocessor.py): trasposizione (:56), ritaglio alla regione non nulla (:65), normalizzazione (:82, il commento sopra dice che DEVE venire prima del ricampionamento), poi ricampionamento alla spaziatura del piano (:88). L'auto-crop legacy non è portato, di proposito: upstream lo applicava solo dopo un controllo di memoria fallito, e cambia ciò che la rete vede (pipeline.py:18-21).

La normalizzazione è quella di nnU-Net, non di questo repository. Per un piano il cui schema è CTNormalization: ritaglia ai percentili 0,5 e 99,5 del piano, sottrai la media, dividi per max(std, 1e-8) (nnunetv2/preprocessing/normalization/default_normalization_schemes.py:58-72, numeri da foreground_intensity_properties_per_channel). Solo il plans.json di DentalSegmentator si può leggere nei repository (in quello legacy: CTNormalization, p0,5 −110, p99,5 3067, media 1274, std 558). I piani degli altri tre bundle vengono scaricati con i modelli, quindi che questo schema si applichi a essi è presunto, non verificato.

3.4 Inferenza: una chiamata per l'intero batch

predict_folder() (nnunet_runner.py:192-232) viene chiamata una sola volta con l'intera cartella di input che riceve (pipeline.py:302-306), quindi il checkpoint viene caricato una volta per chiamata, non una volta per scansione. Una coorte più grande di un batch del server (25 file o 400 MB, §4) arriva allo strumento come più chiamate di questo tipo. Il predictor viene costruito tramite l'API Python di nnU-Net, con la parola chiave rinominata scelta per introspezione:

options = {                                                     # nnunet_runner.py:86-95
    "tile_step_size": float(tile_step_size),   # argument, default 0.5
    "use_gaussian": True,
    "use_mirroring": False,                    # no test-time mirroring
    "device": torch.device(device),
    "verbose": False, "verbose_preprocessing": False, "allow_tqdm": False,
}
# + perform_everything_on_device (or _on_gpu) = device.startswith("cuda")   :97-100

predictor.initialize_from_trained_model_folder(                 # :204-208
    model_folder, use_folds=(0,), checkpoint_name="checkpoint_final.pth")

Il percorso del modello è esplicito: nessuna variabile d'ambiente nnUNet_results, che è globale al processo (nnunet_runner.py:202-203). device ripiega da cuda a cpu con un avviso quando non è visibile nessuna scheda (nnunet_runner.py:46-54). Seguono due percorsi (nnunet_runner.py:210-232):

  • ricampionamento su GPU applicato: predict_from_files_sequential, tutto in questo processo, perché i worker avviati avrebbero ciascuno bisogno di un proprio contesto CUDA;
  • altrimenti (CPU, gpu_resampling=false, o piani con un altro ricampionatore): predict_from_files con 2 worker di preprocessing e 2 di esportazione. Quei worker sono il motivo per cui esiste lo shm_size del container (VISOR-serve docker-compose.yml:225-229).

Il posizionamento e la ponderazione delle patch sono quelli di nnU-Net: il passo è al massimo tile_step_size volte la dimensione della patch e viene ridotto in modo che le patch finiscano esattamente sul bordo dell'immagine, da cui una sovrapposizione di almeno metà per 0,5 (nnunetv2/inference/sliding_window_prediction.py:30-54); il peso gaussiano ha una dispersione di un ottavo della patch (sliding_window_prediction.py:11-16, chiamata in predict_from_raw_data.py:626).

L'avanzamento ha solo due estremi misurabili: la lettura conta le scansioni da 0 a 10 %, la scrittura da 90 a 100 %, e nel mezzo una riga dice "segmenting N scan(s) in one pass" (pipeline.py:269-274, 301, 313; progress.py:89-103). Se la chiamata di inferenza solleva un errore, la cartella di scratch viene rimossa e l'intero batch fallisce, senza che venga scritto un report (pipeline.py:302-309).

3.5 Ricampionamento su GPU e argmax per classe

Con gpu_resampling = true (il valore predefinito) su un dispositivo CUDA, _enable_gpu_resampling() (nnunet_runner.py:124-189) riscrive i due nomi di ricampionatore nella configurazione del predictor, solo se entrambi sono il resample_data_or_seg_to_shape originale di nnU-Net:

for key in ("resampling_fn_data", "resampling_fn_probabilities"):   # nnunet_runner.py:167-177
    configuration[key] = "resample_torch_fornnunet"
    configuration[f"{key}_kwargs"] = {"is_seg": False,
                                      "device": torch.device(device),
                                      "mode": "linear"}

Il volume di input passa quindi dall'ordine di spline 3 all'ordine 1, che il codice indica come l'intera differenza numerica (nnunet_runner.py:169-172). Il terzo ricampionatore, quello per la maschera di ritaglio, viene lasciato deliberatamente su scipy (nnunet_runner.py:110-116). Le proprietà in cache vengono azzerate perché lo scambio abbia effetto (:179-183).

La stessa funzione chiama poi low_memory.install(predictor) (nnunet_runner.py:185-188). Questo sostituisce di nuovo il ricampionatore delle probabilità, con uno che ricampiona l'output della rete una classe alla volta e mantiene un massimo e un'etichetta progressivi, e sostituisce l'argmax di nnU-Net con un passaggio diretto, dato che ciò che arriva è già l'argmax:

for index in range(data.shape[0]):                              # low_memory.py:62-79
    one = resample_torch_fornnunet(data[index:index + 1].to(device), shape, ...)[0]
    ...
    higher = one > best
    best = torch.where(higher, one, best)
    labels = torch.where(higher, index, labels)
return labels.unsqueeze(0).cpu()                                 # :86

Le due metà vengono installate insieme o per niente: anche la factory che costruisce un label manager nuovo per predict_from_files_sequential viene avvolta sull'istanza (low_memory.py:100-151). Secondo la docstring del modulo, l'aritmetica è la stessa del percorso originale (0 voxel diversi su 95 682 560 in un'esecuzione di UniversalLab) e il picco scende da circa 30,6 a 1,25 GiB di VRAM (low_memory.py:14-26); quei numeri non sono stati riprodotti qui. I pareggi tra classi vanno all'indice più basso sul percorso GPU, perché il massimo progressivo viene sostituito solo da un punteggio strettamente più alto (one > best, low_memory.py:75). Sul percorso proprio di nnU-Net l'etichetta è predicted_probabilities.argmax(0) (nnunetv2/utilities/label_handling/label_handling.py:178), che restituisce il primo massimo per convenzione di NumPy e PyTorch (comportamento documentato di argmax, non testato qui).

3.6 Di nuovo sulla griglia della scansione, e scrittura

Per ogni caso, viene letta la predizione nnunet_out/<case_id>.nii.gz; se manca, quella scansione viene segnata failed e il ciclo continua (pipeline.py:312-321). Il volume di etichette viene poi rimesso sulla griglia esatta della scansione sorgente:

if (mask.GetSize() == reference.GetSize()                       # pipeline.py:162-171
        and np.allclose(mask.GetSpacing(), reference.GetSpacing(), atol=1e-4)):
    mask.CopyInformation(reference)          # same grid: copy origin and direction
    return mask
return sitk.Resample(mask, reference, sitk.Transform(),
                     sitk.sitkNearestNeighbor, 0, mask.GetPixelID())

3.7 Superfici

mesh_export.write() (mesh_export.py:177-236) non fa nulla a meno che in export_formats ci sia un formato mesh. Costruisce la superficie di ogni etichetta presente una volta sola e la scrive in ogni formato richiesto, quindi spuntare STL e OBJ insieme costa un solo passaggio di marching cubes (:212-225).

smoother = vtk.vtkWindowedSincPolyDataFilter()                  # mesh_export.py:89-110
smoother.SetNumberOfIterations(max(0, int(smoothing)))          # write(smoothing=30)
smoother.SetPassBand(0.05)
smoother.BoundarySmoothingOn()
smoother.SetFeatureEdgeSmoothing(False)
smoother.NonManifoldSmoothingOn()
smoother.NormalizeCoordinatesOn()

Lo smoothing degli spigoli di feature è disattivato di proposito: su una mesh grezza di marching cubes ogni gradino di voxel è uno spigolo vivo, e proteggere quegli spigoli conserverebbe la scalinatura (mesh_export.py:94-107). La decimazione usa vtkDecimatePro con topologia preservata e un angolo di feature di 60 (:120-130); il suo valore predefinito 0 è stato scelto per parità con l'esportazione STL del modulo legacy, misurata su un'etichetta secondo la docstring (__init__.py:84-100). Non vengono scritte normali (:132-139). STL e VTK sono scritti in binario, OBJ come testo, che non ha una forma binaria (:45-49, 165-172). La maschera arriva a VTK tramite un NRRD temporaneo con nome univoco, rimosso dopo la lettura (:66-118); mesh_export.py non applica nessuna trasformazione esplicita RAS o LPS, a differenza dell'esportazione VTK legacy, che invertiva in LPS (legacy SegmentationWidget.py:2958).

8. Riscontri in VISOR

VFACE chiede superfici e ottiene volumi di etichette

Il percorso heat map di VFACE chiama questo strumento con soli tre argomenti, scans, model e prediction_ID="Seg" (SADT-VISOR tools/VFACE/src/sadt_vface/tools.py:359-364), quindi export_formats conserva il suo valore predefinito ["NIFTI"] (SADT-VISOR __init__.py:22-24) e non viene scritta nessuna mesh (pipeline.py:342-354; mesh_export.py:187-189). VFACE cerca poi solo file .vtk o .vtp (heatmap.py:29, 194-204), non ne trova, e finisce con "No heat map could be drawn" (heatmap.py:246-251). Letto nel codice, non eseguito. Il deployment letto qui comunque non pubblica nessun surface_model per VFACE (VISOR-serve server/deployment.toml:277-279), quindi il percorso non è raggiungibile dal pannello di quel server.

Il README dello strumento è obsoleto sulle esportazioni di mesh e sulla memoria

Il README dello strumento dice "No vtk: the mesh exports are not ported" e le elenca come non portate (tools/Batch_Dental_Seg/README.md:28, 95); la docstring di pipeline.py dice lo stesso (SADT-VISOR pipeline.py:23-24). Il codice dice altro: mesh_export.py scrive STL, OBJ e VTK, export_formats è un argomento (__init__.py:22-24) e vtk 9.6.2 è una dipendenza (pyproject.toml:23). Manca davvero solo glTF. Il README conta anche 38 test senza GPU (README.md:267) dove il file ha 55 funzioni di test. Il suo consiglio di disattivare gpu_resampling per UniversalLab su una scheda sotto circa 40 GiB (README.md:241-256, ripetuto in __init__.py:69-73) è stato modificato l'ultima volta nel commit d2fb0d8; il ricampionatore per classe, che il codice installa insieme al ricampionatore GPU su ogni bundle (nnunet_runner.py:185-188), è arrivato dopo, in c8899c8, e la sua docstring annuncia un picco molto più basso (low_memory.py:20-26). Il codice è il riferimento qui; il picco in sé non è stato misurato per questa pagina.

Una scansione chiamata ..._Seg è invisibile in una cartella

Con l'identificativo predefinito, patient_Seg.nii.gz dentro una cartella viene scambiato per un output precedente e ignorato senza nessun messaggio (SADT-VISOR pipeline.py:79-80, 104-105). Un singolo file passato come scans viene elaborato anche se il suo nome sembra un output (pipeline.py:96-97).

Il ricampionamento su GPU è attivo per impostazione predefinita e cambia i numeri

Quando si applica, il volume di input viene ricampionato su GPU in modo lineare invece che con la spline cubica di nnU-Net; il codice afferma che questa è l'intera differenza numerica e che gpu_resampling=false la disattiva (SADT-VISOR nnunet_runner.py:167-177). Il report registra il valore richiesto su un dispositivo CUDA, e false su CPU; un bundle i cui piani si sottraggono viene solo menzionato nel log (pipeline.py:374-378; nnunet_runner.py:163-165). L'argomento è nascosto nel pannello.

L'autotuning di cuDNN non è disattivato

BatchDentalSeg non imposta mai torch.backends.cudnn.benchmark (nessuna occorrenza nel pacchetto), e il predictor di nnU-Net lo imposta a true su CUDA (nnunetv2/inference/predict_from_raw_data.py:60-61, nnunetv2 come installato nell'ambiente dello strumento). AMASSS lo disattiva esplicitamente (SADT-VISOR AMASSS sadt_amasss/nnunet_runner.py:116). Il README dello strumento dice che nnU-Net su CUDA non è deterministico bit per bit (README.md:113): non aspettarti una maschera identica bit per bit da due esecuzioni della stessa scansione.

Un elenco di esportazione vuoto dà "ok" senza nessun file (solo chiamata diretta)

Chiamato direttamente in Python, run(..., export_formats=[]) riporta ogni scansione come ok con un elenco produced vuoto e un riepilogo "1/1 scan(s) segmented", e non scrive nulla (SADT-VISOR pipeline.py:342-355, 362-386; mesh_export.py:187-189); lo strumento stesso non controlla l'elenco. Una richiesta tramite il server viene rifiutata prima dell'esecuzione, dato che il layout chiede almeno un formato (layout.py:31-33; VISOR-serve server/base.py:855-858), e anche il pannello ne chiede uno.

I file per etichetta dipendono dal formato NIfTI

separate_segments divide il volume di etichette, quindi funziona solo quando NIFTI è selezionato: con sole mesh, non viene scritto nulla per esso anche se la casella è spuntata (SADT-VISOR pipeline.py:339-350).

La tabella delle etichette viaggia con il risultato, ma Slicer non la legge

Il report contiene l'intera tabella labels (SADT-VISOR pipeline.py:364-371). Il pannello Slicer non definisce nessun RUN_REPORT (predefinito vuoto: ServerToolsCoreLib/base_widget.py:1493) e carica i volumi di etichette con un semplice loadLabelVolume (slicer_io.py:560); un commento nel modulo parla di una tabella di colori (BATCHDENTALSEGRemote.py:79-82) ma nessun codice ne applica una.

Una chiamata di inferenza: l'avanzamento ha due estremi

L'intera cartella passa in una sola chiamata a nnU-Net, quindi la barra copre la lettura (da 0 a 10 %) e la scrittura (da 90 a 100 %) e nel mezzo dice "segmenting N scan(s) in one pass", senza inventare valori intermedi (SADT-VISOR pipeline.py:269-274, 301). Un'eccezione di quella chiamata fa fallire l'intero batch dopo aver ripulito la cartella temporanea (pipeline.py:302-309).

Verificato: una scansione illeggibile non ferma il batch

Una scansione che non si riesce a leggere è segnalata failed ("could not be read") e le altre vengono segmentate; solo quando nessuna è leggibile l'esecuzione si ferma con un errore di input (SADT-VISOR pipeline.py:273-298).
