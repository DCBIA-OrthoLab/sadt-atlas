3. La pipeline

Spiegazione in linguaggio semplice e matematica: pagina atlante.

3.1 Caricamento dei pacchetti dei modelli

Spiegazione in linguaggio semplice e matematica: pagina atlante.

model è opzionale e nascosto. Quando è vuoto, run() usa <data_root>/Surg_Mov_Pred/models (__init__.py:19,22-34,71). load_model_packages prende poi ogni stacking_package.pkl sotto di esso, in ordine alfabetico, e carica ciascuno con joblib (pipeline.py:162-195):

package_files = sorted(model.glob("**/stacking_package.pkl"))   # legacy: list(...), filesystem order
for pkl_path in package_files:
    package = joblib.load(pkl_path)        # {target_name, features_names, scaler, model}
    packages[package["target_name"]] = package

Un pacchetto illeggibile viene registrato nel log e saltato; se nessuno si carica, RuntimeError (pipeline.py:180-192). Il commento in layout.py:16-24 descrive l'insieme distribuito: 112 pacchetti, ciascuno che chiede le stesse 145 colonne, di cui 28 con il suffisso _T0 (stato preoperatorio) e 25 con il suffisso _Total (il movimento totale pianificato). La tabella contiene quindi il piano oltre alle misure, da cui l'etichetta "Measurements and plan". I regressori stacking contengono sotto-stimatori LightGBM, quindi lightgbm deve essere installato perché joblib.load riesca (pyproject.toml:18-20). I pacchetti sono stati serializzati con pickle sotto scikit-learn 1.6.1 e sono caricati sotto la 1.7.2; l'avviso di versione è silenziato di proposito, come faceva upstream (pipeline.py:101-115, README.md:72-75).

3.2 Lettura delle misure

Spiegazione in linguaggio semplice e matematica: pagina atlante.

  • Un file o una cartella piatta. Un file è letto in base all'estensione: .csv con read_csv, .xlsx con read_excel, .ods con read_excel(engine="odf") (pipeline.py:22,118-129). Una cartella non viene percorsa ricorsivamente: i suoi file con una delle tre estensioni, senza distinguere maiuscole e minuscole, sono ordinati e concatenati per righe (:132-159). Il legacy leggeva solo una cartella, cercando con glob le estensioni minuscole e maiuscole e deduplicando con set(), quindi l'ordine delle righe cambiava da un'esecuzione all'altra (legacy SurgMovPred_CLI/SurgMovPred_CLI.py:151-157).
  • Identificativo del paziente. find_id_column prova otto modelli in ordine (#, id, id patient, patient id, patient number, subject id, patient, subject, senza distinzione di maiuscole), poi qualunque colonna il cui nome contenga sia "patient" sia "id" (pipeline.py:65-98). Senza di essa, IDPatient resta vuoto con un avviso (:303-312).
  • I nomi delle colonne sono ripuliti nella forma usata in training da clean_name: spazi ai bordi tolti, virgolette, backslash e parentesi eliminati, ogni sequenza di caratteri diversi da lettere, cifre, underscore e apostrofo diventa un solo underscore, total diventa Total, una cifra iniziale riceve f_ (pipeline.py:27-50). Un nome che non può essere ripulito solleva ValueError (:51-60); il legacy restituiva 'f_unnamed', quindi due colonne di questo tipo si sovrapponevano (legacy SurgMovPred_CLI.py:63-66).

L'unica tolleranza è il suffisso _T0 mancante; qualunque altra colonna mancante toglie quel target dall'output con un avviso (pipeline.py:224-236). Un'eccezione durante la predizione di un target viene registrata nel log e il ciclo prosegue (:249-250). Una cella vuota non viene riempita: arriva allo scaler come NaN e il modello solleva un errore, quindi quel target è scartato per tutte le righe (i pacchetti contengono un ElasticNetCV; uno stack sostitutivo su una scikit-learn attuale ha sollevato ValueError: Input X contains NaN; i pacchetti distribuiti non sono stati eseguiti). Se nessun target è stato predetto, l'esecuzione solleva RuntimeError invece di scrivere tabelle senza predizioni (:252-264). Il legacy scriveva quelle tabelle.

3.4 Output

Spiegazione in linguaggio semplice e matematica: pagina atlante.

Le predizioni diventano un unico DataFrame, IDPatient è inserito come prima colonna, e la tabella è scritta due volte (pipeline.py:266,314-317,276-287):

output_dir/predictions_outputs.xlsx     df.to_excel(..., index=True)
output_dir/predictions_outputs.csv      df.to_csv(..., index=True)
columns:  <unnamed index 0..n-1>, IDPatient, <one column per predicted target>

run() restituisce {"excel": ..., "csv": ...}, un dict[str, Path], quindi il server restituisce entrambi come un insieme di file (VISOR-serve server/registry/schema_tool.py:99-103). L'ordine delle colonne dei target segue i percorsi dei pacchetti ordinati, lo stesso a ogni esecuzione. Non c'è alcun report JSON.

L'output è un dizionario con due file, predictions_outputs.xlsx e predictions_outputs.csv (pipeline.py:276-287), quindi il server li restituisce come un insieme di file (VISOR-serve server/registry/schema_tool.py:100-103). Per questo strumento non è dichiarata alcuna impostazione di risorse, timeout o batch, quindi valgono i valori predefiniti del server: nessun timeout (VISOR-serve server/config.py:77). Un commento nel codice di ammissione del server registra una misura di tempo di questo strumento: 4.60 s con un thread, 4.45 s con otto, 7.80 s con 56, su una macchina con 28 core fisici, quindi diventa più lento oltre gli otto thread (VISOR-serve server/execution/admission.py:406-421). Lo stesso commento dà questa come ragione per cui il server limita i thread che concede (:433-434).

8. Riscontri in VISOR

Spiegazione in linguaggio semplice e matematica: pagina atlante.

Colonna indice senza nome in entrambe le tabelle

Entrambi i file di risultato iniziano con una colonna che contiene 0, 1, 2 e così via, prima di IDPatient (pipeline.py:283-284). La CLI legacy fa lo stesso (legacy SurgMovPred_CLI/SurgMovPred_CLI.py:268-269). Tienine conto quando leggi le posizioni delle colonne.

Commenti obsoleti nel client

Il client dice che output_kind "is file" (Remote SurgMovPredRemote/SurgMovPredRemote.py:44) e il widget di base porta come esempio "SurgMovPred's single predictions_outputs.xlsx" (Remote ServerToolsCore/ServerToolsCoreLib/base_widget.py:1390-1391). Lo strumento restituisce due file, che il codice dello schema pubblica come un insieme di file (VISOR-serve server/registry/schema_tool.py:100-103). Il pannello li gestisce comunque, dato che scompatta qualunque zip riceva.

Percorso dei dati obsoleto nel README

Il README dello strumento indica la cartella dei modelli come /DATA/SurgMovPred/models (README.md:45), mentre il codice cerca sotto Surg_Mov_Pred (__init__.py:19,34), il nome usato anche dal manifesto dei dati (VISOR-serve scripts/data-manifest.yml:91). Fa fede il codice.

Ancora vero dal legacy: target indipendenti, nulla applicato alla scena

Ogni target è un model.predict separato sulla stessa riga (pipeline.py:216-247), quindi gli spostamenti predetti dei punti di uno stesso segmento rigido non sono vincolati a concordare tra loro (pagina legacy, insidie). L'output è solo le due tabelle: nessuna trasformazione, nessun nodo Slicer, e il pannello salva l'archivio invece di caricare qualcosa (RESULT_KIND = "save_as", Remote SurgMovPredRemote.py:46). Letto nel codice.

Un target saltato è visibile solo nel log del server

Un pacchetto le cui feature mancano nella tabella è saltato con un logger.warning, e un target la cui predizione fallisce con un logger.exception (pipeline.py:234-236,249-250). L'esecuzione riesce comunque con meno colonne. Non c'è alcun file di report, quindi l'utente vede i target mancanti solo contando le colonne. L'unica protezione è il caso del tutto o niente (:252-264). Letto nel codice.

Verificato: ordine riproducibile e nessun risultato vuoto silenzioso

Pacchetti e tabelle sono ordinati, quindi due esecuzioni sullo stesso input danno le stesse righe e colonne nello stesso ordine (pipeline.py:143-147,173); un'esecuzione in cui nessun modello predice è un errore, non due tabelle vuote (:252-264); un nome di colonna errato è un errore, non una feature sovrapposta (:51-60). Letto nel codice.
