CNE su VISOR: il codice

Per gli sviluppatori: che cosa fa nel codice il porting VISOR di CNE, con riferimenti file:line, firme, argomenti, ambiente, differenze rispetto al codice legacy e constatazioni. La spiegazione leggibile della stessa pipeline, con i piccoli calcoli che contiene, è nella pagina atlante.

VISOR Codice Atlante (spiegazione) Pagina legacy Guida (VISOR)

I riferimenti in questa pagina nominano un repository, poi un percorso al suo interno, poi una riga: SADT-VISOR è il catalogo degli strumenti (commit 6ba2a78), VISOR-serve il server (e9a7e5d), Remote il client Slicer (AutomatedDentalToolsRemote 19b95e8), legacy SlicerAutomatedDentalTools a 3c67957. Un percorso semplice come readers.py:41 è in SADT-VISOR tools/CNE/src/sadt_cne/. Tutto è stato letto nel codice; nulla in questa pagina è stato eseguito, tranne i controlli dello stato HTTP datati più sotto. Panoramica dello stack: VISOR.

1. Posizione nella catena

Spiegazione in linguaggio semplice e matematica: pagina atlante.

  • Stato: portato, implementato nel codice, con test nello strumento (SADT-VISOR tools/CNE/tests/test_run.py, 130 funzioni di test, non eseguite per questa pagina). La Dashboard non è portata. Solo il modello TMJ è preparato nel manifest dei dati del server.
  • Nome API CNE (SADT-VISOR tools/CNE/pyproject.toml:35-37), codice in __init__.py, extraction.py, readers.py, dependencies.py, layout.py.
  • Pannello client CNERemote, un pannello sottile (Remote CNERemote/CNERemote.py:57,61-62; costruito, CMakeLists.txt:36). Legge CNE_report.json dopo un'esecuzione e mostra un riepilogo di una riga nella barra di stato (:75-103).
  • Chiama / chiamato da: nulla. Nessun argomento sup, nessun sup.run (__init__.py:46-56), e nessun altro strumento nomina CNE.
  • Dati ospitati: un bundle, DATA/CNE/models/TMJ/qwen-ft-q4_k_m.gguf (4,683,073,408 byte) e una nota di prova TMJ sintetica (VISOR-serve scripts/data-manifest.yml:687-701).

3. La pipeline

Spiegazione in linguaggio semplice e matematica: pagina atlante.

3.1 Controllo delle cartelle e individuazione delle note

Spiegazione in linguaggio semplice e matematica: pagina atlante.

Un percorso notes mancante è un FileNotFoundError (__init__.py:97-100). Se notes è una cartella e output_dir è la stessa cartella (symlink risolti), l'esecuzione è rifiutata, perché le estrazioni verrebbero rilette come note dall'esecuzione successiva (:106-110,320-324). Lo strumento crea poi output_dir da sé (:116); il legacy contava sul pannello per crearla.

L'individuazione è ricorsiva e restituisce i file ordinati per percorso relativo (readers.py:92-123). Tiene .txt, .pdf e .docx senza distinzione tra maiuscole e minuscole (:33,78-81), salta i nomi che iniziano con ~$ (file di blocco di Word) o con un punto, e le cartelle chiamate __MACOSX (:60-61,84-90,117-118). La cartella di output è esclusa quando si trova dentro l'input (__init__.py:118). Se non si trova nulla è un 422 che nomina le tre estensioni (:119-126); il legacy terminava con stato 0 in quel caso (legacy CNE_CLI/CNE_CLI.py:137-141).

3.2 Scelta e caricamento del modello

Spiegazione in linguaggio semplice e matematica: pagina atlante.

model è obbligatorio. Un file .gguf è usato così com'è; una cartella deve contenere esattamente un .gguf, cercato ricorsivamente, altrimenti l'esecuzione è rifiutata con i candidati nominati (extraction.py:89-128). Se il percorso del modello nomina un tipo di nota e notes_type è l'altro, un avviso va nel report; non è un rifiuto (model_type_hint, extraction.py:131-143; __init__.py:132-142).

CONTEXT_TOKENS = {"TMJ": 6144, "Ortho": 2048}                # extraction.py:49
SYSTEM_PROMPTS = {"TMJ": INSTRUCTION_TMJ, "Ortho": None}      # extraction.py:51

window = context_for(notes_type, context_tokens)              # 0 means the type's default
offloading = wants_gpu and supports_gpu_offload()             # asked before the 4.4 GB load
engine = load_model(model_file, window, seed, -1 if wants_gpu else 0)   # __init__.py:144-165

load_model costruisce un solo llama_cpp.Llama(model_path, n_ctx, n_gpu_layers, seed, verbose=False) per l'intero batch (extraction.py:193-203). I messaggi del loader sono catturati con contextlib.redirect_stderr e registrati a livello debug (:63-86), dove il legacy reindirizzava il descrittore di file 2 del processo con os.dup2 e senza finally (legacy CNE_CLI.py:157-171). Ogni import di llama_cpp passa da engine_module(), che prima prova ad aprire il runtime CUDA dal venv (extraction.py:167-177, dependencies.py:65); sulla build CPU non fa nulla. Una richiesta device = "cuda" su una build senza supporto GPU aggiunge un avviso e gpu_offload: false al report (__init__.py:145-165,184).

3.4 Interrogare il modello

Spiegazione in linguaggio semplice e matematica: pagina atlante.

messages = []
if SYSTEM_PROMPTS[notes_type]:                       # TMJ only
    messages.append({"role": "system", "content": INSTRUCTION_TMJ})
messages.append({"role": "user", "content": text})   # extraction.py:156-164

output = model.create_chat_completion(messages=messages,
                                      max_tokens=max_tokens, temperature=temperature)
content, finish_reason = choice["message"]["content"], choice.get("finish_reason")   # :206-223
if finish_reason == "length":   # cut off at max_tokens
    raise ValueError("the model's answer was cut off ...")                          # __init__.py:293-297

L'istruzione TMJ è la stringa legacy alla lettera: "Using the following note, extract structured key-value pairs about the patient's symptoms and diagnoses:" (extraction.py:41-44). Ortho non riceve nessun messaggio di sistema, come nel legacy. Lo strumento non confronta la lunghezza della nota con la finestra: context_for rifiuta solo un valore negativo (extraction.py:146-153), e qualsiasi errore sollevato da llama.cpp viene intercettato per quella nota (__init__.py:200-212). In llama-cpp-python 0.3.36 (llama.py:1343-1358) il motore solleva un errore solo quando il prompt da solo raggiunge n_ctx; altrimenti max_tokens viene ridotto a n_ctx meno la lunghezza del prompt, la nota non è mai troncata, e una generazione fermata da quel limite accorciato riporta finish_reason == "length", che fa fallire la nota (__init__.py:293-297). La versione fissata è 0.3.35, il cui codice non è stato letto.

3.5 Lettura della risposta e scrittura

Spiegazione in linguaggio semplice e matematica: pagina atlante.

  1. Prima il JSON: si analizza la porzione dalla prima { all'ultima }; un dict sotto "extraction" viene estratto; un risultato vuoto o un valore JSON che non è un oggetto è rifiutato (extraction.py:261-275). Il taglio è quello del legacy.
  2. Poi le righe key: value: una chiave inizia con una lettera minuscola e contiene lettere minuscole, cifre, spazi e trattini bassi (fino a 61 caratteri, gli spazi diventano _, extraction.py:230,296), almeno il 60 % delle righe non vuote deve corrispondere, e una chiave ripetuta mantiene il primo valore (extraction.py:230-235,278-301). Il sorgente dice che il fine-tune TMJ pubblicato risponde in questa forma, 46 campi e nessun JSON (:244-245).
  3. Altrimenti non viene scritto nulla e la nota fallisce (__init__.py:299-305). Il legacy scriveva la risposta grezza.

Per ogni nota si scrivono due file nell'albero rispecchiato (__init__.py:240-266,307-317): il JSON, canonico, e un testo key : value in cui una lista è unita con virgole e un dict annidato resta JSON (extraction.py:304-328).

input   notes/P01/B_001.txt
output  output_dir/P01/Extraction_B_001.txt.json
        output_dir/P01/Extraction_B_001.txt.txt

plan_outputs verifica che non ci siano due note che corrispondono alla stessa coppia prima di eseguire qualsiasi cosa (__init__.py:240-266). CNE_report.json porta tool, notes_type, model, system_prompt (un flag), context_tokens, max_tokens, temperature, seed, device, gpu_offload, warnings, e per nota input, il lettore e la codifica, characters, finish_reason, answer_characters, status, fields, i due percorsi di output o un reason; poi summary e duration_seconds (__init__.py:171-187,213-216,272-317). Il testo della risposta in sé non è messo né nel report né nei log.

3.6 Fallimenti

Spiegazione in linguaggio semplice e matematica: pagina atlante.

Ogni nota è in un proprio try: un fallimento è registrato nel log con il percorso relativo della nota e annotato nel report, e il ciclo continua (__init__.py:191-213). Se nessuna nota è stata scritta l'esecuzione solleva un errore: un 503 (ToolUnavailableError) quando ogni fallimento era un lettore mancante, altrimenti un 422 (ValueError) che elenca il motivo di ciascuna nota (:218-232); il report allora non viene scritto. Si noti che questa riga di log per nota nomina il file, a differenza dei messaggi di avanzamento di CLIC.

8. Riscontri in VISOR

Spiegazione in linguaggio semplice e matematica: pagina atlante.

Il testo delle note viene inviato al server

L'affermazione legacy secondo cui CNE tiene il testo clinico sulla macchina ("no network exfiltration", pagina legacy §11, e il "Nothing leaves your machine" della Guida legacy) non vale per VISOR. Il pannello VISOR carica le note selezionate su un server di strumenti dove gira il modello (Remote README.md:24-35; CNERemote/CNERemote.py:57 e l'argomento notes lato server, Argomenti e schema). Il README di Remote dice a chiare lettere che nel client attuale non c'è alcuna de-identificazione (README.md:32), e la pagina di sicurezza di VISOR elenca la de-identificazione dei file caricati come solo specificata (De-identificazione, Trasporto). Che cosa fa lo strumento stesso con il testo: esegue llama.cpp nel processo e non contiene nessuna chiamata di rete (un grep di urllib, requests, http e socket in tools/CNE/src/sadt_cne/ non ne trova), e il server scrive la risposta nella cartella del job. La constatazione legacy resta vera solo per il modulo legacy.

Il client dice "automatic", ma nulla associa il modello al tipo di nota

Il README di Remote ("leave Model on automatic and the server uses the model fine-tuned for that note type", README.md:611-613) e il docstring di CNERemote/CNERemote.py:15-18 ("the model field defaults to (automatic)") sono obsoleti. model è un argomento obbligatorio dello strumento (__init__.py:49), e il client aggiunge la sua voce "(automatic)" solo agli argomenti facoltativi (Remote ServerToolsCore/ServerToolsCoreLib/base_widget.py:1074-1076, motivazione in formgen.py:107-109): il campo Model elenca i bundle ospitati e invia quello selezionato. Nulla ricava il modello da notes_type (resolve_model_file prende un percorso, extraction.py:89-128); una discordanza fra i due è solo un avviso (riquadro successivo). Letto nel codice, non eseguito in Slicer.

È ospitato solo il modello TMJ

Il manifest dei dati prepara un solo bundle, TMJ/qwen-ft-q4_k_m.gguf (VISOR-serve scripts/data-manifest.yml:687-692). notes_type = "Ortho" è accettato dallo strumento ma nessun modello Ortho è ospitato, e un modello il cui percorso nomina l'altro tipo è solo un avviso nel report, non un rifiuto (__init__.py:133-139, extraction.py:131-144). Il commento del manifest secondo cui il repository Ortho "answers 404 today" (data-manifest.yml:682-686, ripetuto in SADT-VISOR tools/CNE/README.md:205-208) è obsoleto: il 2026-11-09 una richiesta HTTP HEAD sul vecchio URL Ortho dcbia/ ha risposto 307 (un reindirizzamento all'organizzazione DCBIA-OrthoLab/), e una su DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho/.../model-q4_k_m.gguf ha risposto 302 verso un download (solo codici di stato, nulla è stato scaricato). Anche l'URL TMJ nel manifest usa ancora il vecchio nome dcbia/ e risponde 307.

CPU, qualunque cosa dicano alcuni commenti

L'indice di wheel fissato per llama-cpp-python è quello CPU (SADT-VISOR tools/CNE/pyproject.toml:60-67). Tre commenti non concordano: l'intestazione dello stesso file parla di un "CUDA 12.4 wheel index below" (:8-23); la descrizione pubblicata di device dice "it needs the CUDA build of llama.cpp, which this tool pins" (__init__.py:82-84); e il file compose di VISOR-serve dice che CNE non può girare nel servizio CPU perché fornisce la build CUDA (docker-compose.yml:105-110). Il codice è la build CPU, quindi una richiesta cuda viene segnalata come ignorata. Il README dello strumento concorda con il codice (SADT-VISOR tools/CNE/README.md:154-165). Da nessuna parte va letto "CNE needs a GPU".

Nessuna protezione sulla lunghezza di una nota

La preoccupazione legacy per le note lunghe (pagina legacy, §11) è chiusa solo a metà. Una risposta troncata è ora rifiutata (__init__.py:293-297) e max_tokens vale 2048 per impostazione predefinita invece di 500. Ma nulla confronta la nota con la finestra di contesto né verifica che max_tokens lasci spazio al suo interno: context_for rifiuta solo un valore negativo (extraction.py:146-153). Con il valore predefinito di Ortho il solo limite della risposta è uguale alla finestra (2048 e 2048, :49, __init__.py:51). In llama-cpp-python 0.3.36 (llama.py:1343-1358) il motore solleva un errore solo quando il prompt da solo raggiunge n_ctx; altrimenti accorcia max_tokens a n_ctx meno il prompt e la nota non viene mai tagliata. Quindi con Ortho una nota passa finché la risposta termina entro ciò che la nota lascia, e fallisce (finish_reason == "length") quando non succede; qualunque cosa il motore sollevi fa fallire quella singola nota (__init__.py:200-212).

Nomi degli output cambiati

I file sono Extraction_<note file name>.json e .txt, non Extraction_<stem>.txt (__init__.py:240-266). Qualsiasi cosa legga i nomi legacy, come la Dashboard legacy (Extraction_*.txt), non troverebbe gli stessi file.

Verificato: i fallimenti silenziosi del legacy sono chiusi

Un PDF fatto solo di immagini, una risposta troncata e una risposta che non è né JSON né campi ora fanno fallire la nota invece di scrivere un file plausibile (__init__.py:276-305); note omonime di formati diversi non si sovrascrivono più (:240-266); la divisione nell'ortografia TMJ/tmj è sparita (extraction.py:49-51); una richiesta GPU che non si può soddisfare è segnalata (__init__.py:145-165). Letto nel codice.
