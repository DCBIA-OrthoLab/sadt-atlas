Agent, legacy: โค้ด

สำหรับนักพัฒนา: สิ่งที่โมดูล Agent แบบ legacy ทำในโค้ด พร้อมอ้างอิง file:line พรอมต์ การตรวจ manifest สภาพแวดล้อม และข้อค้นพบ คำอธิบายที่อ่านง่ายของไปป์ไลน์เดียวกันอยู่ในหน้าแอตลาส

Agent_CLI โค้ด แอตลาส (คำอธิบาย) บรรณานุกรม VISOR: บางส่วน

ทุกอย่างรันในเครื่อง: LLM ขนาด 8B ที่ให้บริการโดย Ollama และ cross-encoder ขนาดเล็กที่คัดเครื่องมือผู้สมัครไว้ล่วงหน้า

โค้ดสองชุด

ทุกอย่างที่มีหมายเลขด้านล่างอธิบายโมดูล Slicer แบบ legacy (SlicerAutomatedDentalTools ที่ 3c67957, 2026-10-26) VISOR มีเครื่องมือฝั่งเซิร์ฟเวอร์ชื่อ Agent ซึ่งเป็น router บนปลายทาง Ollama ภายนอก แต่ไม่มีไคลเอนต์เรียกใช้: แผง AgentRemote ที่ส่งมากับไคลเอนต์ VISOR เป็นสำเนาของวิดเจ็ต legacy ที่ยังรันในเครื่องอยู่ ทั้งสองอธิบายไว้ในหน้า VISOR ของ Agent

3.1 LLM, qwen3:8b ผ่าน Ollama

คำอธิบายภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

ค่าคงที่ตัวเดียว ซ้ำกันทั้งสองฝั่ง: DEFAULT_MODEL = "qwen3:8b" (utils.py:21) และ MODEL_NAME = "qwen3:8b" (Agent.py:29) get_router_model() รองรับตัวแปรสภาพแวดล้อม ROUTER_MODEL ที่ให้สลับเป็นโมเดล Ollama ใดก็ได้โดยไม่ต้องแตะโค้ด

โมเดลเดียวกันรับใช้ทั้งสามการเรียก: การเลือกเส้นทาง การดึงพารามิเตอร์ การซ่อม ไม่มีโมเดลเฉพาะทาง ไม่มีการ fine-tune

หัวข้อค่าแหล่งที่มา
เอนจินอนุมานOllama (จึงมี llama.cpp อยู่ข้างใต้) HTTP API ในเครื่องimport ollama, พอร์ต 11434
รูปแบบ weightsGGUF: Ollama กำหนดมา ไม่มี checkpoint ของ transformersอนุมานจากเอนจิน
ดาวน์โหลดollama pull qwen3:8b จาก registry ของ ollama.comAgent.py:1142 และทางสำรองอัตโนมัติใน chat_with_auto_pull
ขนาด / quantizationแท็กเริ่มต้น: 5.2 GB, Q4_K_M, พารามิเตอร์ 8.19 Gระบุจากที่เก็บโค้ดไม่ได้: อ่านที่ ollama.com/library/qwen3
CPU หรือ GPUOllama เป็นผู้ตัดสิน ไม่ใช่โค้ดดูด้านล่าง
Ollama ที่ติดตั้งผ่าน snap = CPU · เฉพาะ Legacy

เฉพาะ Legacy (3c67957) ไม่มีในVISOR. ไม่มีการทดสอบ /snap/ ในสำเนาฝั่งไคลเอนต์ (ไม่พบที่ตรงกันใน AutomatedDentalToolsRemote AgentRemote/AgentRemote.py) และเครื่องมือฝั่งเซิร์ฟเวอร์ก็ไม่ติดตั้งหรือเปิด Ollama: ต้องมีปลายทางที่เข้าถึงได้ (SADT-VISOR tools/Agent/src/sadt_agent/llm.py:1-25, ปลายทางถูกแปลงที่ :38-39)

โมดูลไม่เคยส่งคำสั่งเลือกอุปกรณ์ ไบนารีของ Ollama เป็นผู้ตัดสิน และโค้ดสรุปผลตามมาอย่างชัดเจน: บน Linux Ollama ที่ติดตั้งผ่าน snap ถูกแยกอยู่ใน sandbox มองไม่เห็น GPU ของ NVIDIA และถอยไปใช้ CPU ที่ 80–90 วินาทีต่อการตอบ สำหรับโมเดล 8B ซึ่งเป็นตัวเลขที่วัดมาและกำหนดตายตัวในโค้ด (คอมเมนต์ที่ Agent.py:1101-1103 ซ้ำในกล่องคำเตือน) โมดูลตรวจพบ /snap/ ใน realpath ของไบนารีและเตือนเรื่องนี้ แต่แก้ไม่ได้ (เซิร์ฟเวอร์ snap จับพอร์ต 11434 ไว้แล้ว และการลบต้องใช้ sudo)

เมื่อไม่พบ Ollama install_official_ollama() (Agent.py:111) จะดาวน์โหลดไฟล์เก็บถาวรพกพาทางการไปไว้ที่ ~/.slicer_agent/ollama (เปลี่ยนได้ผ่าน SLICER_AGENT_HOME): ollama-linux-{amd64,arm64}.tgz, ollama-windows-{amd64,arm64}.zip หรือ Ollama-darwin.zip แตกด้วย ditto แล้วเอาการกักกันออกด้วย xattr ไฟล์เก็บถาวรเหล่านี้รวมไลบรารี CUDA/Metal ไว้ จึงเลือกโดยตั้งใจที่จะไม่ใช้ curl | sudo sh (ไม่มีรหัสผ่าน root จาก GUI) หรือแพ็กเกจ snap LD_LIBRARY_PATH ชี้ไปที่ <install>/lib/ollama เพื่อให้ไบนารีพบไลบรารีของตัวเอง (Agent.py:67)

มีเพียงสองการตั้งค่าการเรียก ใน chat_with_auto_pull (utils.py:96):

  • keep_alive="30m" แทนค่าเริ่มต้น 5 นาที เพื่อไม่ต้องโหลด 5 GB เข้า VRAM ใหม่ระหว่างสองข้อความ
  • format="json" สำหรับ router การดึงค่า และการซ่อม (ข้อจำกัดแบบ grammar ฝั่ง Ollama): ไม่ใช้กับโหมดที่ปรึกษา

ไม่มีการส่ง temperature, seed, num_ctx หรือ think เนื่องจาก qwen3 เป็นโมเดลแบบ hybrid-reasoning โหมดที่ปรึกษาจึงอาจปล่อยข้อความการให้เหตุผลหลุดออกมาได้ ขึ้นกับเวอร์ชันของ Ollama การประมวลผลหลังเดียวคือ output.replace("*","").replace("#","") (Agent_CLI.py:215) ซึ่งตัด markdown ด้วยการตัดอักขระออก

หากไม่มีโมเดลอยู่ chat_with_auto_pull จะดักข้อความ not found รัน ollama.pull(model, stream=True) พร้อมแสดงความคืบหน้า แล้วเล่นแชตซ้ำ ข้อผิดพลาดอื่นใดจะถูกส่งต่อออกไปตามเดิม

3.2 cross-encoder: ms-marco-MiniLM-L-6-v2

คำอธิบายภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

นี่คือเครือข่ายจริงเพียงตัวเดียวที่โหลดในโปรเซส CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") (utils.py:53) ผ่าน sentence-transformers จึงเป็น weights แบบ transformers/safetensors ที่ดาวน์โหลดจาก Hugging Face Hub และแคชไว้ใน ~/.cache/huggingface

MiniLM, 6 เลเยอร์, พารามิเตอร์ 22.7 M, กลั่นจาก MiniLM-L12-H384-uncased ฝึกด้วย MS MARCO Passage Ranking มันไม่ใช่โมเดล embedding: ไม่มีเวกเตอร์และไม่มี cosine similarity คำถามกับเอกสารถูกต่อกันแล้วป้อนเข้า transformer ด้วยกัน ซึ่งให้ผลลัพธ์เป็นค่าความเกี่ยวข้องค่าเดียวที่ไม่มีขอบเขต (โดยทั่วไป −10 ถึง +10) อุปกรณ์คืออันที่ sentence-transformers เลือกเองตาม torch wheel ที่ติดตั้ง

แคช _cross_encoder_model ไม่มีประโยชน์ในทางปฏิบัติ: Agent_CLI.py เป็นโปรเซสใหม่ทุกคำขอ โมเดลจึงถูกโหลดใหม่ทุกข้อความ คอมเมนต์ในโค้ดก็ยอมรับเรื่องนี้

cross-encoder สำรองแบบเงียบ · legacy และสำเนาฝั่งไคลเอนต์ ไม่ใช่เครื่องมือฝั่งเซิร์ฟเวอร์

Legacy (3c67957) เท่านั้น ไม่มีในเครื่องมือเซิร์ฟเวอร์ VISOR. ตัวจัดอันดับฝั่งเซิร์ฟเวอร์คือ BM25 และจะตัดรายการให้แคบลงเมื่อมีสัญญาณเท่านั้น: หากคำขอไม่ซ้อนกับเครื่องมือใดเลย จะแสดงทุกเครื่องมือ (SADT-VISOR tools/Agent/src/sadt_agent/ranking.py:222-239) cross-encoder สำรองยังเป็นจริงในสำเนาฝั่งไคลเอนต์ (AutomatedDentalToolsRemote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:94; legacy Agent_CLI/Agent_CLI_utils/utils.py:94)

หากโหลดล้มเหลว ทางสำรองนั้นหยาบมาก: scripts[:k] คือสามเครื่องมือแรกในmanifest (ali_cbct, ali_ios, amasss_cli) ไม่ว่าคำถามจะเป็นอะไร (utils.py:94) ร่องรอยเดียวคือบรรทัดที่พิมพ์ในเอาต์พุตของ CLI (utils.py:93) แชตไม่ได้รับแจ้ง

4. การเลือกเส้นทาง

คำอธิบายภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

สองขั้น และ LLM เข้ามาเกี่ยวข้องเฉพาะขั้นที่สอง

ขั้นที่ 1 การคัดเลือกเบื้องต้นด้วย cross-encoder cross_encoder_retrieve_candidates(manifest, prompt, k=3) สร้างเอกสารหนึ่งชิ้นต่อเครื่องมือ:

docs.append(f"{s['name']}: {s['description']} (tags: {tags})")
scores = model.predict([(user_text, doc) for doc in docs])
ranked = sorted(zip(scores, scripts), reverse=True)
return [s for _, s in ranked[:k]]

ให้คะแนน 16 คู่ เรียงจากมากไปน้อย top-3 ที่กำหนดตายตัว (k=3 ไม่เคยถูกทำเป็นพารามิเตอร์) ฟิลด์ priority ของmanifest (ค่า 1 ถึง 23 มีช่องว่าง) ไม่เคยถูกอ่าน : บรรทัดที่จะอ่านมันถูกคอมเมนต์ทิ้งไว้ (utils.py:216) เครื่องมือที่ถูกต้องหากอยู่อันดับที่ 4 จะหายไปถาวร LLM จะไม่มีวันเห็นมัน

ขั้นที่ 2 การเลือกโดย LLM system prompt (Agent_CLI.py:105):

You are a tool router. Output ONLY one JSON object.
Schema:
{"tool": string|null, "confidence": number, "reason": string}

Rules:
- Choose tool ONLY from the candidate list provided by the user message.
- If none match, set tool = null and confidence <= 0.4.
- Do not invent tool names.
- Keep reason short (max 1 sentence).

ข้อความของผู้ใช้คือ USER_REQUEST: <prompt> ตามด้วย CANDIDATES (choose exactly one name from this list): และบล็อกที่สร้างโดย build_candidates_block: หนึ่งบรรทัดต่อผู้สมัครหนึ่งราย i) name — description (truncated to 140 characters) | tags: t1, t2, … (8 max)

สามข้อที่ควรสังเกต:

  • บริบทของโฟลเดอร์ไม่ได้ส่งให้router folders_context ถูกเพิ่มเฉพาะในพรอมต์การดึงค่า
  • ประวัติการสนทนาถูกแทรกระหว่างเทิร์นของระบบกับของผู้ใช้ (*history) และมีฟองแชตดิบของวิดเจ็ต ("After reflection, I would like to run …") router แบบ JSON จึงได้รับข้อความของอินเทอร์เฟซในฐานะเทิร์นของ "assistant"
  • confidence และ reason ไม่มีประโยชน์ confidence ถูกแยกวิเคราะห์ ปัดเศษ เขียนลง JSON เอาต์พุตเป็น tool_confidence … แล้ววิดเจ็ตก็ไม่เคยอ่านกลับ ไม่มีเกณฑ์ที่ไหนเลย คำสั่ง "confidence ≤ 0.4" ไม่ใช่ข้อบังคับ เป็นเพียงข้อเสนอแนะต่อโมเดล

เครือข่ายความปลอดภัยเดียวเป็นแบบข้อความ: if selected_tool and selected_tool != "null" and selected_tool != "None" ชื่อเครื่องมือที่โมเดลมโนขึ้นซึ่งไม่อยู่ใน manifest ผ่านการทดสอบนี้ แล้วทำให้ build_cli_args ล้มเหลวด้วย KeyError ซึ่ง try ระดับรวมใน main() จับไว้และคืนเป็น {"error": …}

5. การดึงพารามิเตอร์

คำอธิบายภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

การเรียก LLM ครั้งที่สอง เมื่อเลือกเครื่องมือไว้แล้ว ภายใน extract_parameters (utils.py:220)

การซ่อนพารามิเตอร์ทางเทคนิค พารามิเตอร์ที่ชื่อ temp_fold, tmp_folder, temp_folder, log_path หรือ logPath จะถูกถอดออกจากสเปกก่อนสร้างพรอมต์: ไม่มีประโยชน์ที่จะให้โมเดลคิดโฟลเดอร์ชั่วคราวขึ้นมาเอง พวกมันถูกใส่กลับภายหลังด้วยค่า input.temp_folder คือ slicer.util.tempDirectory() ที่วิดเจ็ตสร้างทุกครั้งที่คลิก (Agent_CLI.py:153) และถูกเอาออกจาก missing_required

พรอมต์การดึงค่า (parameter_extraction_improved.py:40) ระบุพารามิเตอร์แต่ละตัวเป็น - name (type) [REQUIRED|optional] (encode: …): description แล้วกำหนดกฎเจ็ดข้อ: การจัดรูปแบบลิสต์ตาม encode (comma_no_brackets, space_separated, comma_separated, python_literal), บูลีนและตัวเลขเป็น JSON เปล่า, "ถ้าชื่อมี folder หรือ dir ให้ใส่โฟลเดอร์โดยไม่มีชื่อไฟล์" และเหนือสิ่งอื่นใด:

7. ONLY extract parameters mentioned in the user request
   - Do NOT invent values
   - Leave unmentioned optional parameters absent

เอาต์พุตบังคับ: {"extracted": {...}, "confidence": 0.0-1.0, "missing_required": [...], "notes": "..."} missing_required ที่โมเดลสร้างถูกเพิกเฉย: ตัวตรวจสอบเป็นตัวที่มีผล

การแปลงพาธมอบให้ LLM ทั้งหมด · แก้บางส่วนใน VISOR

ส่วนของพาธเป็นจริงในVISORด้วย ส่วนของเครื่องหมายจุลภาคแก้แล้ว เครื่องมือฝั่งเซิร์ฟเวอร์รับ folders เป็นลิสต์ เครื่องหมายจุลภาคในชื่อโฟลเดอร์จึงไม่ตัดมันอีก (SADT-VISOR tools/Agent/src/sadt_agent/__init__.py:40,124) โมเดลยังคงเป็นผู้ตัดสินเพียงผู้เดียวว่าพาธใดเข้าอาร์กิวเมนต์ใด: validation.py ตรวจชนิดและ choices เทียบกับสคีมาที่เผยแพร่ ไม่ได้ตรวจว่าพาธมีอยู่จริง (validation.py:1-30)

วิดเจ็ตส่งรายการที่ลากมาวางในโซนวางไฟล์ โดยเชื่อมด้วยเครื่องหมายจุลภาค (Agent.py:770) CLI แยกกลับด้วย , แล้วห่อมัน:

FOLDERS_CONTEXT:
<one path per line>

Rules:
- Treat FOLDERS_CONTEXT as the source of truth for paths.
- If a required path parameter is missing, try to infer it from FOLDERS_CONTEXT.
- If multiple candidates exist, pick the most specific match and explain briefly in 'reason'.

บล็อกนี้ถูกต่อท้ายพรอมต์ของผู้ใช้ ไม่ได้ส่งแยก ไม่มีการจับคู่เชิงฮิวริสติก ไม่มีการตรวจเนื้อหาโฟลเดอร์ ไม่มีการตรวจว่ามีอยู่จริง: โมเดลต้องเดาเองว่าพาธใดที่ลากมาเป็น T1 พาธใดเป็น T2 พาธใดเป็นโฟลเดอร์โมเดล พาธที่มีเครื่องหมายจุลภาคจะถูก split(",") ตัดเป็นสองส่วน

การตรวจสอบ (parameter_validator.py) เรียงหกรอบ: ฟิลด์ที่จำเป็นที่ขาด, การแปลงชนิด (bool/int/float/list/path/string), ไวยากรณ์พาธ, choices, min/max, พารามิเตอร์นอกสเปก รายละเอียดที่มีประโยชน์สองข้อ:

  • encode: lower_str_bool บังคับสตริง "true"/"false" เป็นตัวพิมพ์เล็ก เพราะ CLI หลายตัวเทียบอาร์กิวเมนต์ดิบโดยไม่ใช้ .lower(): str(True) จะให้ "True" และจะไม่มีวันตรงกัน
  • _check_paths ตรวจเพียงสองอย่าง: Path(str(value)) ไม่โยนข้อผิดพลาด (เกือบไม่เคยโยน) และพารามิเตอร์ที่ชื่อมี folder/dir ไม่ลงท้ายด้วยนามสกุลที่รู้จัก ไม่เคยทดสอบว่าพาธมีอยู่จริง

ผลการตรวจสอบถูกทิ้งเกือบทั้งหมด: errors และ warnings ไม่ปรากฏที่ไหนเลย ผลเดียวของมันคือ final_confidence = confidence * 0.6 เมื่อไม่ถูกต้อง และไม่มีใครอ่านค่า confidence นั้น มีเพียง params และ missing_required ที่รอดไป

เป็นจริงกับสำเนาฝั่งไคลเอนต์ด้วย ไม่เกี่ยวกับเครื่องมือฝั่งเซิร์ฟเวอร์ ส่วนขยายที่ส่ง AgentRemote มาก็ไม่มีโฟลเดอร์นั้นเช่นกัน และตัว resolve ของมันยังอ่าน AGENT_CLI_TOOLS_DIR (AutomatedDentalToolsRemote Agent_CLIRemote/Agent_CLIRemote_utils/utils.py:154; โมดูล CLI ถูกลบแล้ว CMakeLists.txt:49-56) เครื่องมือฝั่งเซิร์ฟเวอร์ไม่เปิดอะไรด้วยพาธเลย

ไม่มีโฟลเดอร์ CLI files ที่ไหนเลยใน SlicerAutomatedDentalTools คอมเมนต์ในโค้ดอ้างถึงโครงสร้าง AI_Agent/Agent_CLI/ + .../CLI files/ ซึ่งมาจากที่เก็บโค้ดต้นฉบับที่ Agent_CLI ถูกแยกออกมา ที่นี่สคริปต์แต่ละตัวอยู่ในโฟลเดอร์ของโมดูลตัวเอง (ALI_CBCT/ALI_CBCT.py, …) ไม่มีผู้สมัครรายใดตรง และฟังก์ชันคืน candidates[0] "เพื่อให้ข้อความข้อผิดพลาดชี้ไปยังพาธที่ดีบักได้" คือ <Agent_CLI>/CLI files/ALI_CBCT.py

subprocess.run ไม่โยนข้อผิดพลาด (ตัวรันได้ sys.executable มีอยู่) แต่เป็น Python ที่ออกด้วยโค้ด 2 บนไฟล์ที่หาไม่พบ ซึ่งกระตุ้นวงจรซ่อม ที่ซึ่งเนื่องจากมันแก้พารามิเตอร์ โดยโครงสร้างจึงทำอะไรไม่ได้

และแม้พาธ resolve แล้ว บางเป้าหมายก็ยังล้มเหลว: DOCShapeAXI_CLI.py import shapeaxi ซึ่งเป็นแพ็กเกจที่อยู่ในสภาพแวดล้อม conda ที่โมดูล Slicer ของมันเรียกผ่าน conda run -n … หรือ CondaSetUpCall (MRI2CBCT ไม่ใช่ตัวอย่างอีกต่อไป: nnunetv2 ของมันตอนนี้รันใน Python ของ Slicer เอง) ส่วน Agent เปิดทุกอย่างด้วย sys.executable คือ Python ของ Slicer ไม่เคยใช้ conda

สิ่งที่มี:

  • กล่อง modal ยืนยันที่บังคับก่อนการรันทุกครั้ง แสดงพารามิเตอร์ทั้งหมด และอีกกล่องหนึ่งก่อนความพยายามซ่อมทุกครั้ง
  • การบล็อกเมื่อขาดพารามิเตอร์ที่จำเป็น: ไม่มีอะไรถูกเปิดตราบที่ missing_required ไม่ว่าง
  • การแปลงชนิด และการตรวจ choices / min / max / นามสกุลบนโฟลเดอร์
  • การซ่อมโฟลเดอร์ชั่วคราว เติมจาก slicer.util.tempDirectory() แทนที่จะให้โมเดลเติม
  • การจำกัดขอบเขต: MAX_REPAIR_ATTEMPTS = 2, ประวัติถูกตัดเหลือ MAX_HISTORY_ENTRIES = 40 เทิร์น
  • try ระดับรวมใน main(): stdout เป็น JSON ที่แยกวิเคราะห์ได้เสมอ traceback ไปที่ stderr

สิ่งที่ไม่มี:

  • ไม่มีเกณฑ์ confidence tool_confidence และ parameters_confidence ถูกคำนวณและเขียนออก แล้วถูกเพิกเฉย การเลือกเส้นทางที่ 0.1 ถูกปฏิบัติเหมือนที่ 0.95
  • ไม่มีการตรวจว่าพาธมีอยู่จริง พาธที่โมเดลมโนขึ้นผ่านการตรวจสอบ ผ่านการยืนยัน (ผู้ปฏิบัติงานต้องสังเกตเองด้วยตาในกล่องโต้ตอบ) และล้มเหลวเมื่อโมดูลเป้าหมายเปิดเท่านั้น
  • ข้อผิดพลาดของตัวตรวจสอบไม่เคยแสดง errors, warnings และ extra_params ถูกสร้างแล้วทิ้ง
  • ไม่มีการป้องกันโฟลเดอร์เอาต์พุต หากโมเดลเลือกโฟลเดอร์ข้อมูลอินพุตเป็น output_folder ไม่มีอะไรห้าม CLI หลายตัวในที่เก็บโค้ดเขียนทับไฟล์อินพุตของตัวเอง
  • พารามิเตอร์นอกสเปกไม่ถูกกรอง ในโหมด --flag
  • log_path ได้รับโฟลเดอร์ ไม่ใช่ไฟล์: ชื่อ log_path และ logPath อยู่ในรายการพารามิเตอร์ที่ถูกแทนด้วย input.temp_folder CLI ที่เปิดพาธนี้เพื่อเขียนจะล้มเหลว
  • ไม่มี whitelist ของไฟล์ที่รันได้ subprocess.run รับลิสต์ตามที่สร้างทุกประการ การป้องกันที่แท้จริงคือ tool_path มาจากmanifest ไม่ใช่จาก LLM: โมเดลควบคุมค่า ไม่ใช่ไบนารี
