Agent: pipeline ทั้งหมด

ผู้ช่วยภาษาธรรมชาติที่เลือกโมดูลจากส่วนขยาย สกัดพารามิเตอร์ของมัน สร้างบรรทัดคำสั่ง และเปิดใช้งาน ที่นี่ไม่มีการเรียกเครือข่ายประสาทเทียมทางการแพทย์: Agent ทำเพียงการกำหนดเส้นทางและการกรอกแบบฟอร์ม

ยังไม่ตีพิมพ์ Agent_CLI Python ของ Slicer qwen3:8b ผ่าน Ollama cross-encoder MiniLM-L6 บรรณานุกรม

ทุกอย่างรันในเครื่อง: LLM ขนาด 8B ที่ให้บริการโดย Ollama และ cross-encoder ขนาดเล็กสำหรับคัดเครื่องมือผู้สมัครเบื้องต้น

3. โมเดล

3.1 LLM, qwen3:8b ผ่าน Ollama

ค่าคงที่เดียวที่ซ้ำกันทั้งสองฝั่ง: DEFAULT_MODEL = "qwen3:8b" (utils.py:21) และ MODEL_NAME = "qwen3:8b" (Agent.py:29) get_router_model() รับตัวแปรสภาพแวดล้อม ROUTER_MODEL ที่ให้สลับเป็นโมเดล Ollama ใดก็ได้โดยไม่ต้องแตะโค้ด

โมเดลเดียวกันให้บริการทั้งสามการเรียก: การกำหนดเส้นทาง การสกัดพารามิเตอร์ การซ่อมแซม ไม่มีโมเดลเฉพาะทาง ไม่มีการ fine-tune

ประเด็นค่าที่มา
เอนจินอนุมานOllama (ข้างใต้จึงเป็น llama.cpp) API แบบ HTTP ในเครื่องimport ollama, พอร์ต 11434
รูปแบบน้ำหนักGGUF: Ollama กำหนดให้ ไม่มี checkpoint ของ transformersอนุมานจากเอนจิน
การดาวน์โหลดollama pull qwen3:8b จาก registry ของ ollama.comAgent.py:1142 และ fallback อัตโนมัติใน chat_with_auto_pull
ขนาด / quantizationแท็กเริ่มต้น: 5.2 GB, Q4_K_M, พารามิเตอร์ 8.19 Gไม่สามารถระบุได้จากที่เก็บโค้ด: อ่านได้ที่ ollama.com/library/qwen3
CPU หรือ GPUOllama เป็นผู้ตัดสิน ไม่ใช่โค้ดดูด้านล่าง
Ollama ที่ติดตั้งผ่าน snap = CPU

โมดูลไม่เคยส่งคำสั่งเลือกอุปกรณ์ ไบนารีของ Ollama เป็นผู้ตัดสิน และโค้ดสรุปผลที่ตามมาไว้อย่างชัดเจน: บน Linux Ollama ที่ติดตั้งผ่าน snap ถูกแยกใน sandbox มองไม่เห็น GPU ของ NVIDIA และถอยไปใช้ CPU 80–90 วินาทีต่อหนึ่งคำตอบสำหรับโมเดล 8B ซึ่งเป็นตัวเลขที่วัดแล้วและฮาร์ดโค้ดไว้ในโค้ด (Agent.py:1107) โมดูลตรวจพบ /snap/ ใน realpath ของไบนารีและเตือน โดยแก้ไม่ได้ (เซิร์ฟเวอร์ snap ถือพอร์ต 11434 อยู่แล้ว และการลบต้องใช้ sudo)

เมื่อไม่พบ Ollama install_official_ollama() (Agent.py:111) ดาวน์โหลดไฟล์เก็บแบบพกพาอย่างเป็นทางการไปที่ ~/.slicer_agent/ollama (เปลี่ยนได้ด้วย SLICER_AGENT_HOME): ollama-linux-{amd64,arm64}.tgz, ollama-windows-{amd64,arm64}.zip หรือ Ollama-darwin.zip แตกด้วย ditto แล้วถอดกักกันด้วย xattr ไฟล์เก็บเหล่านี้รวมไลบรารี CUDA/Metal ไว้ จึงเป็นเหตุผลที่จงใจไม่ใช้ curl | sudo sh (GUI ขอรหัสผ่าน root ไม่ได้) และไม่ใช้แพ็กเกจ snap LD_LIBRARY_PATH ถูกชี้ไปที่ <install>/lib/ollama เพื่อให้ไบนารีหาไลบรารีของตัวเองเจอ (Agent.py:67)

มีการตั้งค่าการเรียกเพียงสองอย่าง ใน chat_with_auto_pull (utils.py:96):

  • keep_alive="30m" แทนค่าเริ่มต้น 5 นาที เพื่อไม่ต้องโหลด 5 GB เข้า VRAM ใหม่ระหว่างสองข้อความ;
  • format="json" สำหรับตัวกำหนดเส้นทาง การสกัด และการซ่อมแซม (ข้อจำกัดทางไวยากรณ์ฝั่ง Ollama): ไม่ใช้กับโหมด consultant

ไม่มีการส่ง temperature, seed, num_ctx หรือ think เนื่องจาก qwen3 เป็นโมเดล hybrid-reasoning โหมด consultant จึงอาจปล่อยข้อความการให้เหตุผลหลุดออกมาได้ขึ้นกับรุ่นของ Ollama; การประมวลผลหลังเพียงอย่างเดียวคือ output.replace("*","").replace("#","") (Agent_CLI.py:215) ซึ่งลบ markdown โดยลบตัวอักษรเหล่านั้น

ถ้าไม่มีโมเดล chat_with_auto_pull จะดักข้อความ not found รัน ollama.pull(model, stream=True) พร้อมพิมพ์ความคืบหน้า แล้วเล่นการแชตซ้ำ ข้อผิดพลาดอื่นใดจะถูกยกซ้ำตามเดิม

3.2 cross-encoder: ms-marco-MiniLM-L-6-v2

เป็นเครือข่ายจริงเพียงตัวเดียวที่ถูกโหลดใน process CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2") (utils.py:53) ผ่าน sentence-transformers จึงเป็นน้ำหนัก transformers/safetensors ที่ดาวน์โหลดจาก Hugging Face Hub และแคชใน ~/.cache/huggingface

MiniLM 6 ชั้น พารามิเตอร์ 22.7 M กลั่นมาจาก MiniLM-L12-H384-uncased ฝึกบน MS MARCO Passage Ranking มันไม่ใช่โมเดล embedding: ไม่มีเวกเตอร์และไม่มี cosine similarity คำค้นกับเอกสารถูกต่อกันแล้วป้อนเข้า transformer ด้วยกัน ซึ่งส่งออกค่าสเกลาร์ความเกี่ยวข้องเพียงค่าเดียวที่ไม่มีขอบเขต (โดยทั่วไป −10 ถึง +10) อุปกรณ์คืออะไรก็ตามที่ sentence-transformers เลือกเอง ตาม torch wheel ที่ติดตั้ง

แคช _cross_encoder_model ไม่มีประโยชน์ในทางปฏิบัติ: Agent_CLI.py เป็น process ใหม่ทุกคำขอ โมเดลจึงถูกโหลดใหม่ทุกข้อความ คอมเมนต์ในโค้ดยอมรับเรื่องนี้

cross-encoder ถอยไปใช้ทางเลือกสำรองโดยไม่มีเสียง

ถ้าการโหลดล้มเหลว ทางเลือกสำรองหยาบมาก: scripts[:k] คือสามเครื่องมือแรกใน manifest (ali_cbct, ali_ios, amasss_cli) ไม่ว่าคำถามจะเป็นอะไร (utils.py:90) ผู้ปฏิบัติงานไม่ได้รับแจ้ง

4. การกำหนดเส้นทาง

สองขั้น และ LLM เข้ามาเฉพาะขั้นที่สอง

ขั้นที่ 1 การคัดเลือกเบื้องต้นด้วย cross-encoder cross_encoder_retrieve_candidates(manifest, prompt, k=3) สร้างเอกสารหนึ่งชิ้นต่อเครื่องมือ:

docs.append(f"{s['name']}: {s['description']} (tags: {tags})")
scores = model.predict([(user_text, doc) for doc in docs])
ranked = sorted(zip(scores, scripts), reverse=True)
return [s for _, s in ranked[:k]]

ให้คะแนน 16 คู่ เรียงจากมากไปน้อย top-3 ที่ฮาร์ดโค้ด (k=3 ไม่เคยถูกทำให้เป็นพารามิเตอร์) ฟิลด์ priority ของ manifest (ค่า 1 ถึง 23 โดยมีช่องว่าง) ไม่เคยถูกอ่าน: บรรทัดที่จะอ่านมันถูกคอมเมนต์ไว้ (utils.py:216) เครื่องมือที่ถูกต้อง ถ้ามันอยู่อันดับที่ 4 จะหายไปถาวร LLM จะไม่มีวันเห็นมัน

ขั้นที่ 2 LLM เป็นผู้เลือก system prompt (Agent_CLI.py:105):

You are a tool router. Output ONLY one JSON object.
Schema:
{"tool": string|null, "confidence": number, "reason": string}

Rules:
- Choose tool ONLY from the candidate list provided by the user message.
- If none match, set tool = null and confidence <= 0.4.
- Do not invent tool names.
- Keep reason short (max 1 sentence).

ข้อความของผู้ใช้คือ USER_REQUEST: <prompt> ตามด้วย CANDIDATES (choose exactly one name from this list): และบล็อกที่สร้างโดย build_candidates_block: หนึ่งบรรทัดต่อผู้สมัคร i) name — description (truncated to 140 characters) | tags: t1, t2, … (8 max)

มีสามเรื่องที่ควรสังเกต:

  • บริบทของโฟลเดอร์ไม่ถูกส่งให้ตัวกำหนดเส้นทาง folders_context ถูกเพิ่มเข้า prompt การสกัดเท่านั้น
  • ประวัติการสนทนาถูกแทรกระหว่าง system กับ turn ของผู้ใช้ (*history) และมีบับเบิลแชตดิบของวิดเจ็ต ("After reflection, I would like to run …") ตัวกำหนดเส้นทางแบบ JSON จึงได้รับร้อยแก้วของอินเทอร์เฟซเป็น turn ของ "assistant"
  • confidence และ reason ไม่มีประโยชน์ confidence ถูกแยกวิเคราะห์ ปัดเศษ เขียนลง JSON เอาต์พุตเป็น tool_confidence … และวิดเจ็ตไม่เคยอ่านกลับ ไม่มีเกณฑ์ใดเลย คำสั่ง "confidence ≤ 0.4" ไม่ใช่ข้อบังคับ เป็นเพียงข้อเสนอแนะต่อโมเดล

ตาข่ายนิรภัยเดียวเป็นแบบข้อความ: if selected_tool and selected_tool != "null" and selected_tool != "None" ชื่อเครื่องมือที่ภาพหลอนขึ้นมาและไม่อยู่ใน manifest ผ่านการทดสอบนี้ แล้วทำให้ build_cli_args ล้มเหลวด้วย KeyError ซึ่งถูกจับโดย try ระดับสากลใน main() และคืนเป็น {"error": …}

tools = build_tool_spec(manifest) (Agent_CLI.py:72) ถูกคำนวณแล้วไม่เคยใช้: โค้ดที่ไม่ได้ใช้ พร้อมการจัดการ "old structure" ทั้งหมด (patterns, defaults) ที่ไม่มีรายการใดใน manifest ปัจจุบันใช้

5. การสกัดพารามิเตอร์

การเรียก LLM ครั้งที่สอง เมื่อเลือกเครื่องมือแล้ว ภายใน extract_parameters (utils.py:220)

การปิดบังพารามิเตอร์ทางเทคนิค พารามิเตอร์ที่ชื่อ temp_fold, tmp_folder, temp_folder, log_path หรือ logPath ถูกนำออกจากข้อกำหนดก่อนสร้าง prompt: ไม่มีประโยชน์ที่จะขอให้โมเดลคิดโฟลเดอร์ชั่วคราวขึ้นเอง จากนั้นจะถูกใส่กลับด้วยค่า input.temp_folder คือ slicer.util.tempDirectory() ที่วิดเจ็ตสร้างทุกครั้งที่คลิก (Agent_CLI.py:153) และถูกนำออกจาก missing_required

prompt การสกัด (parameter_extraction_improved.py:40) ระบุแต่ละพารามิเตอร์เป็น - name (type) [REQUIRED|optional] (encode: …): description แล้วกำหนดกฎเจ็ดข้อ: การจัดรูปแบบรายการตาม encode (comma_no_brackets, space_separated, comma_separated, python_literal) ค่าบูลีนและตัวเลขเป็น JSON เปล่า "if the name contains folder or dir, give a folder with no file name" และเหนือสิ่งอื่นใด:

7. ONLY extract parameters mentioned in the user request
   - Do NOT invent values
   - Leave unmentioned optional parameters absent

เอาต์พุตบังคับ: {"extracted": {...}, "confidence": 0.0-1.0, "missing_required": [...], "notes": "..."} missing_required ที่โมเดลสร้างถูกเพิกเฉย: ตัวตรวจสอบต่างหากที่มีผล

การแปลงพาธถูกมอบหมายให้ LLM ทั้งหมด

วิดเจ็ตส่งรายการสิ่งที่ลากมาวางในโซนวางไฟล์ ต่อกันด้วยจุลภาค (Agent.py:770) CLI แยกกลับด้วย , และห่อมัน:

FOLDERS_CONTEXT:
<one path per line>

Rules:
- Treat FOLDERS_CONTEXT as the source of truth for paths.
- If a required path parameter is missing, try to infer it from FOLDERS_CONTEXT.
- If multiple candidates exist, pick the most specific match and explain briefly in 'reason'.

บล็อกนี้ถูกต่อท้าย prompt ของผู้ใช้ ไม่ได้ส่งแยก ไม่มีการจับคู่เชิงประมาณ ไม่มีการตรวจเนื้อหาโฟลเดอร์ ไม่มีการตรวจว่ามีอยู่จริง: ขึ้นกับโมเดลว่าจะเดาพาธไหนที่ลากมาคือ T1 อันไหนคือ T2 อันไหนคือโฟลเดอร์โมเดล พาธที่มีจุลภาคจะถูก split(",") ตัดเป็นสองส่วน

การตรวจสอบ (parameter_validator.py) ต่อโซ่หกรอบ: ฟิลด์จำเป็นที่ขาด การแปลงชนิด (bool/int/float/list/path/string) ไวยากรณ์ของพาธ choices min/max พารามิเตอร์นอกข้อกำหนด มีรายละเอียดที่มีประโยชน์สองข้อ:

  • encode: lower_str_bool บังคับสตริง "true"/"false" ให้เป็นตัวพิมพ์เล็ก เพราะ CLI หลายตัวเปรียบเทียบอาร์กิวเมนต์ดิบโดยไม่มี .lower(): str(True) จะได้ "True" และจะไม่มีวันตรงกัน
  • _check_paths ตรวจเพียงสองอย่าง: Path(str(value)) ไม่ยกข้อผิดพลาด (แทบไม่เคยยก) และพารามิเตอร์ที่ชื่อมี folder/dir ไม่ลงท้ายด้วยนามสกุลที่รู้จัก ไม่เคยทดสอบว่าพาธมีอยู่จริง

ผลการตรวจสอบเกือบทั้งหมดถูกทิ้ง: errors และ warnings ไม่ปรากฏที่ใด ผลเพียงอย่างเดียวคือ final_confidence = confidence * 0.6 เมื่อไม่ผ่าน และไม่มีใครอ่านค่า confidence นั้น มีเพียง params และ missing_required ที่รอด

6. การสร้างและการรันคำสั่ง

ใช่ โมดูลถูกเปิดใช้จริง ไม่กำกวม

CLI เพียงสร้างคำสั่ง build_cli_args (utils.py:350) รวมค่าเริ่มต้นของ manifest กับพารามิเตอร์ที่สกัดได้ แล้ว:

return [sys.executable, tool_path] + cli

sys.executable คืออินเทอร์พรีเตอร์ของ process Agent_CLI คือ Python ของ Slicer สำหรับ cli_style: positional (14 เครื่องมือจาก 16) ค่าต่าง ๆ ถูกต่อกันตามลำดับการประกาศใน manifest: positional_order รองรับแต่ ไม่มีรายการใดตั้งค่า สำหรับ cli_style อื่นใด การรันตกเข้ากิ่ง --flag value โดยวนซ้ำบน merged: พารามิเตอร์นอกข้อกำหนดที่ภาพหลอนขึ้นมาจึงถูกส่งออกจริง

รายการถูกส่งคืนให้วิดเจ็ตในฟิลด์ command ของ JSON AgentWidget เป็นผู้รัน และเฉพาะเมื่อ missing_required == []:

  1. บับเบิลแชต "After reflection, I would like to run X";
  2. QMessageBox.question แสดง key=value ของแต่ละพารามิเตอร์ (Agent.py:864);
  3. เมื่อตอบ Yes → runToolWithRepair → subprocess.run(cli_args, capture_output=True)

ถ้า missing_required ไม่ว่าง เอเจนต์จะไม่เปิดอะไร: มันแสดงรายการสิ่งที่ขาดพร้อมค่าที่รู้แล้ว และรอข้อความตามมา (ซึ่งประวัติการสนทนาจะช่วยให้ต่อเรื่องได้)

Slicer ค้างระหว่างงาน

subprocess.run เป็นแบบซิงโครนัสและรันบนเธรด GUI: Slicer ค้างตลอดระยะเวลาของงาน ซึ่งสำหรับการแบ่งส่วนด้วย AMASSS หรือการลงทะเบียนภาพของ AREG วัดเป็นหลายสิบนาที

7. วงจรซ่อมแซม

เมื่อ return code ไม่เป็นศูนย์ runToolWithRepair (Agent.py:943) ขอให้ LLM แก้พารามิเตอร์ อย่างมาก MAX_REPAIR_ATTEMPTS = 2 ครั้ง build_repair_prompt (utils.py:282) ส่งนิยามพารามิเตอร์ ค่าที่ใช้ คำสั่งเต็ม และ2000 ตัวอักษรสุดท้ายของ stderr และขอให้คืนเฉพาะพารามิเตอร์ที่ต้องเปลี่ยน

เส้นทางนี้รันภายใน process ของ Slicer ไม่ใช่ CLI: _proposeRepair เพิ่มโฟลเดอร์ Agent_CLI เข้า sys.path และ import Agent_CLI_utils ใหม่ เพื่อไม่ต้องทำตรรกะซ้ำ การแก้ไขวนกลับผ่าน ParameterValidator แล้ว build_cli_args แสดงส่วนต่าง old -> new และต้องมีการยืนยัน Yes/No ใหม่ ถ้าส่วนต่างว่าง วงจรหยุด

_suggestFixFor (Agent.py:1240) เสริมด้วยการวินิจฉัยแบบไม่ใช้ LLM โดยอิงคีย์เวิร์ด: ไม่มีโมเดล Ollama, ModuleNotFoundError, NameError: name 'nn' is not defined (การถดถอยที่รู้จักใน transformers>=4.53.0, huggingface/transformers#43784), Numpy is not available (ABI ของ numpy 2 ชนกับ torch wheel) หรือการเชื่อมต่อ Ollama ล้มเหลว

ไม่มีโฟลเดอร์ CLI files ที่ใดเลยใน SlicerAutomatedDentalTools คอมเมนต์ในโค้ดอ้างถึงโครงสร้าง AI_Agent/Agent_CLI/ + .../CLI files/ ซึ่งมาจากที่เก็บโค้ดดั้งเดิมที่ Agent_CLI ถูกสกัดมา ที่นี่แต่ละสคริปต์อยู่ในโฟลเดอร์ของโมดูลตัวเอง (ALI_CBCT/ALI_CBCT.py, …) ไม่มีผู้สมัครตัวใดตรง และฟังก์ชันคืน candidates[0] "so the error message points to a debuggable path" คือ <Agent_CLI>/CLI files/ALI_CBCT.py

subprocess.run ไม่ยกข้อผิดพลาด (ไฟล์ปฏิบัติการ sys.executable มีอยู่) เป็น Python ที่ออกด้วยรหัส 2 กับไฟล์ที่หาไม่เจอ ซึ่งทริกเกอร์วงจรซ่อมแซม ที่ซึ่งเพราะมันแก้พารามิเตอร์ โดยโครงสร้างจึงทำอะไรกับเรื่องนี้ไม่ได้

และแม้พาธถูกแปลงแล้ว เป้าหมายบางตัวก็ยังล้มเหลว: DOCShapeAXI_CLI.py import shapeaxi ซึ่งเป็นแพ็กเกจที่อยู่ในสภาพแวดล้อม conda ที่โมดูล Slicer ของมันเรียกผ่าน conda run -n … หรือ CondaSetUpCall (MRI2CBCT ไม่ใช่ตัวอย่างอีกต่อไป: nnunetv2 ของมันตอนนี้รันใน Python ของ Slicer เอง) ส่วน Agent เปิดทุกอย่างด้วย sys.executable คือ Python ของ Slicer ไม่เคยใช้ conda

10. ราวกั้น

สิ่งที่มี:

  • กล่องยืนยันแบบ modal ที่บังคับก่อนการรันทุกครั้ง แสดงพารามิเตอร์ทั้งหมด และอีกกล่องหนึ่งก่อนความพยายามซ่อมแซมทุกครั้ง
  • การบล็อกเมื่อขาดพารามิเตอร์ที่จำเป็น: ไม่มีอะไรถูกเปิดตราบที่ missing_required ไม่ว่าง
  • การแปลงชนิด และการตรวจ choices / min / max / นามสกุลบนโฟลเดอร์
  • การปิดบังโฟลเดอร์ชั่วคราว เติมจาก slicer.util.tempDirectory() ไม่ใช่โดยโมเดล
  • การจำกัดขอบเขต: MAX_REPAIR_ATTEMPTS = 2 ประวัติถูกตัดเหลือ MAX_HISTORY_ENTRIES = 40 turn
  • try ระดับสากลใน main(): stdout เป็น JSON ที่แยกวิเคราะห์ได้เสมอ traceback ไปที่ stderr

สิ่งที่ไม่มี:

  • ไม่มีเกณฑ์ confidence tool_confidence และ parameters_confidence ถูกคำนวณและเขียนออก แล้วถูกเพิกเฉย การกำหนดเส้นทางที่ 0.1 ถูกปฏิบัติเหมือนที่ 0.95
  • ไม่มีการตรวจว่าพาธมีอยู่จริง พาธที่ภาพหลอนขึ้นมาผ่านการตรวจสอบ ผ่านการยืนยัน (ผู้ปฏิบัติงานต้องสังเกตเองด้วยตาในกล่องโต้ตอบ) และล้มเหลวเมื่อโมดูลเป้าหมายเริ่มทำงานเท่านั้น
  • ข้อผิดพลาดของตัวตรวจสอบไม่เคยถูกแสดง errors, warnings และ extra_params ถูกสร้างแล้วทิ้ง
  • ไม่มีการป้องกันโฟลเดอร์เอาต์พุต ถ้าโมเดลเลือกโฟลเดอร์ข้อมูลอินพุตเป็น output_folder ไม่มีอะไรหยุดมัน CLI หลายตัวในที่เก็บโค้ดเขียนทับไฟล์อินพุตของตัวเอง
  • พารามิเตอร์นอกข้อกำหนดไม่ถูกกรองในโหมด --flag
  • log_path ได้รับโฟลเดอร์ ไม่ใช่ไฟล์: ชื่อ log_path และ logPath อยู่ในรายการพารามิเตอร์ที่ถูกแทนด้วย input.temp_folder CLI ที่เปิดพาธนี้เพื่อเขียนจะล้มเหลว
  • ไม่มีรายการขาวของไฟล์ปฏิบัติการ subprocess.run รับรายการตามที่สร้างทุกประการ การป้องกันจริงคือ tool_path มาจาก manifest ไม่ใช่จาก LLM: โมเดลควบคุมค่า ไม่ใช่ไบนารี

Windows: CREATE_NO_WINDOW เพื่อไม่ให้หน้าต่างคอนโซลวาบขึ้น ไม่มี WSL ต่างจากส่วนอื่นของที่เก็บโค้ด

12. กับดักและจุดเปราะบาง

  • resolve_tool_path ไม่พบอะไรในที่เก็บโค้ดนี้ (§8) นี่คือตัวขวางอันดับหนึ่ง วิธีแก้ที่เป็นไปได้: สร้างโฟลเดอร์ CLI files พร้อมลิงก์ ตั้ง AGENT_CLI_TOOLS_DIR หรือใส่พาธสัมพัทธ์กับที่เก็บโค้ดใน manifest และขยายการค้นหา
  • 14 ลายเซ็นจาก 16 ผิด และการเลื่อนเงียบ
  • batchdentalseg และ clic ไม่ใช่ CLI cli_style: ui_module ไม่ถูกจัดการที่ใดเลย: มันตกเข้ากิ่ง --flag ซึ่งสร้างคำสั่งที่ใช้กับโมดูล Slicer แบบสคริปต์ไม่ได้
  • input.folders.split(",") ทำให้พาธที่มีจุลภาคพัง ทั้งสำหรับรายการโฟลเดอร์และสำหรับ join(",") ฝั่งวิดเจ็ต
  • cross-encoder ถูกโหลดใหม่ทุกข้อความ (process ใหม่) และเมื่อมันล้มเหลวจะลดระดับเป็นสามเครื่องมือแรกใน manifest โดยผู้ปฏิบัติงานไม่ได้รับแจ้ง
  • k=3 ถูกฮาร์ดโค้ด 16 เครื่องมือ 3 ผู้สมัคร: คะแนนที่ผิดพลาดของ cross-encoder LLM กู้คืนไม่ได้
  • priority ไม่ทำงาน ทำให้การจัดอันดับของ manifest ชวนให้เข้าใจผิด
  • subprocess.run บล็อกเธรด GUI ตลอดการรันของโมดูล
  • ประวัติปนร้อยแก้วของ UI กับบริบทการกำหนดเส้นทาง: บับเบิลแชตถูกส่งกลับตามที่เป็นเป็น turn ของ assistant ให้ตัวกำหนดเส้นทางที่ถูกจำกัดเป็น JSON
  • OnRetrieveButton สร้างประวัติใหม่โดยแยกที่อีโมจิ 👨: / 🤖: (Agent.py:1004): ข้อความที่มีอักขระเหล่านี้ทำให้การสลับลำดับเสียจังหวะ
  • การตรวจจับธีมด้วยการสุ่มพิกเซล (widget.grab() ความสว่างของพิกเซล (5,5)) เพราะ QPalette คืนสีของธีมสว่างแม้ใน Slicer ที่เป็นธีมมืด (Agent.py:649) ใช้งานได้ แต่ขึ้นกับจังหวะเวลาของการเรนเดอร์ครั้งแรก จึงมี QTimer.singleShot(0, ...) ใน setup
  • โค้ดที่ไม่ได้ใช้: AgentLogic.process(), build_tool_spec() (และการรองรับ patterns/defaults ทั้งหมดรอบมัน), ValidationReport, positional_order, ฟิลด์ examples ของ manifest, _cross_encoder_model, Agent_CLI/Resources/UI/Agent_CLI.ui
  • extract_parameters คืน 4 ค่า ขณะที่ annotation ประกาศ 3
