CLIC

CLIC หาเขี้ยวฝังบน CBCT และบอกว่าแต่ละซี่อยู่ด้านแก้ม ด้านเพดานปาก หรือคร่อมกระดูก หน้านี้อธิบายทีละขั้นพร้อมคณิตศาสตร์: อะไรเข้า แต่ละขั้นทำอะไรกับมัน และอะไรออกมา ไฟล์ บรรทัด และข้อควรระวังอยู่ในหน้าโค้ด; การพอร์ต VISOR อยู่ในหน้าของมันเอง

โค้ด (นักพัฒนา) ยังไม่เผยแพร่ VISOR clic_runner.py conda env: clic_env Python 3.9 บรรณานุกรม

ภาพรวม: อะไรเข้า อะไรออก

CLIC มองหาเขี้ยวที่ฝังอยู่ในภาพสแกน CBCT โดยอ่านสแกนทีละสไลซ์ ในแต่ละสไลซ์ โครงข่ายที่ฝึกแล้วจะวาดเส้นขอบเขี้ยวที่พบ และในรอบเดียวกันก็บอกว่าแต่ละซี่อยู่ตรงไหนเทียบกับกระดูก คือด้านแก้ม (buccal) ด้านเพดานปาก (palatal) หรือคร่อมกระดูก (bicortical) ชื่อบอกว่ามีสองงาน แต่โครงข่ายมีเพียงตัวเดียว: เส้นขอบคือการระบุตำแหน่ง และคลาสคือการจำแนก

CLIC โมดูล legacy
อินพุตCBCT หนึ่งชุดเป็นไฟล์ NIfTI หรือโฟลเดอร์ที่มี CBCT หลายชุด เลือกในแผงของ Slicer
วิธีการต่อหนึ่งสไลซ์: ปรับสเกลค่าสีเทา ส่งสไลซ์ให้ Mask R-CNN เก็บเฉพาะผลตรวจจับที่มั่นใจ แล้ววาดลงในวอลุ่มป้ายกำกับ
เอาต์พุตlabel map หนึ่งชุดต่อสแกน บนกริดเดียวกับสแกน: 0 พื้นหลัง, 1 buccal, 2 bicortical, 3 palatal
ที่ไหนแผงทำงานใน Slicer ส่วนการคำนวณทำงานในสภาพแวดล้อม conda แยกต่างหากบนเครื่องของผู้ใช้ และใช้การ์ดจอเมื่อมี

หน้านี้อธิบายโมดูล Slicer แบบ legacy (SlicerAutomatedDentalTools ที่ 3c67957) ส่วนพอร์ต VISOR ซึ่งรันโครงข่ายเดียวกันบนเซิร์ฟเวอร์ มีหน้าของตัวเอง ชื่อไฟล์ เลขบรรทัด และข้อควรระวังทุกข้ออยู่ในหน้าโค้ด

ในโค้ดโค้ดเบสนี้อธิบายฉบับไหน และพอร์ต VISOR อยู่ที่ใด

1. ตำแหน่งในไปป์ไลน์

CLIC ทำงานเดี่ยวทั้งสองทิศทาง: ไม่มีโมดูลอื่นเรียกมัน และมันไม่เรียกโมดูลอื่น เริ่มจาก CBCT ดิบ ไม่ต้องมีการแบ่งส่วน landmark หรือการจัดทิศทางมาก่อน และไม่พึ่ง AMASSS, ASO หรือ ALI ใช้เพียงสคริปต์ runner ของตัวเอง ซึ่งเริ่มทำงานหนึ่งครั้งต่อสแกน กับไฟล์น้ำหนักที่แผงดาวน์โหลดได้จาก GitHub release

ในโค้ดวิดเจ็ตเรียกอะไรและเรียกอย่างไร พร้อมอาร์กิวเมนต์ของ conda

2. ไฟล์ที่เกี่ยวข้อง

โมดูลประกอบด้วยสามไฟล์: แผง Slicer กับส่วนติดต่อผู้ใช้ และสคริปต์ runner ที่รวมการประมวลผลทั้งหมด แผงเขียนพารามิเตอร์ลงไฟล์เล็ก ๆ เริ่ม runner ภายสภาพแวดล้อม conda แล้วอ่านผลลัพธ์ แผงต้องมีตัวช่วย SlicerConda จึงจะโหลดได้เลย โดยใช้คลาส conda ของ SlicerConda เอง และไม่มีเส้นทาง WSL การรันบน Windows ได้หรือไม่ขึ้นกับเวอร์ชันของ SlicerConda และยังไม่เคยลองบน Windows

ในโค้ดตารางไฟล์พร้อมจำนวนบรรทัด การนำเข้า CondaSetUp และเส้นทาง WSL ที่ไม่มี

3. อินพุตและการประมวลผลก่อน

ก่อนถึงโครงข่ายมีสองขั้น: แผงรวบรวมสแกน และ runner เตรียมแต่ละสไลซ์

3.1 การรวบรวมสแกน

แผงรับไฟล์หรือโฟลเดอร์ และกรองตามนามสกุล NIfTI, NRRD และ MetaImage แต่ runner อ่านได้เฉพาะ NIfTI ดังนั้นรูปแบบอื่นจึงผ่านตัวกรองแล้วไปล้มทีหลัง ถ้าโฟลเดอร์ที่เลือกมีโฟลเดอร์ย่อยที่เก็บสแกน แผงจะคืนโฟลเดอร์ย่อยแทนไฟล์ ซึ่ง runner โหลดไม่ได้เช่นกัน กรณีที่ใช้งานได้คือโฟลเดอร์แบนที่มีไฟล์ .nii.gz

ในโค้ดฟังก์ชันที่รวบรวมไฟล์ กฎสองขั้นของมัน และความล้มเหลวที่ตามมา

3.2 พรีโปรเซสวอลุ่มจริง

runner ตัดวอลุ่มเป็นสไลซ์แนว axial ตามแกนอาร์เรย์ที่สาม ตามลำดับที่เก็บในไฟล์ โดยไม่ปรับทิศทางใหม่ จากนั้นแต่ละสไลซ์ถูกจัดการแยกกัน

การปรับสเกลนี้มีผลตามมา: ไม่มี Hounsfield window และไม่มีสถิติระดับวอลุ่ม ดังนั้นแต่ละสไลซ์จึงมีคอนทราสต์ของตัวเอง และสไลซ์ที่มีแต่อากาศก็ถูกยืดให้เต็มช่วงเหมือนสไลซ์อื่น หลังจากนั้นสไลซ์ถูกคัดลอกเป็นสามช่องที่เหมือนกันเพื่อให้ตรงกับอินพุตสีของ backbone แบบ ImageNet ของโครงข่าย โมดูลไม่มีการครอป ไม่มี region of interest และไม่มีการ resample ภายในโครงข่าย torchvision ขยายภาพให้ด้านสั้นยาว 800 พิกเซล (ด้านยาวไม่เกิน 1333) และทำ standardise ด้วยค่าเฉลี่ยและส่วนเบี่ยงเบนของ ImageNet ดังนั้นสแกนขนาด 512 คูณ 512 จึงถูกขยายเป็น 800 คูณ 800

ในโค้ดสามบรรทัดของลูป ฟังก์ชัน normalisation และ transform ของ torchvision

4. โมเดล

ทุกอย่างสำหรับหนึ่งสไลซ์ ตามลำดับ คลิกกล่องเพื่ออ่านส่วนของมัน

ในโค้ดโมเดลถูกสร้าง โหลด และป้อนข้อมูลอย่างไร

4.1 สถาปัตยกรรม

โครงข่ายคือ Mask R-CNN: backbone แบบ ResNet-50 พร้อม feature pyramid มองภาพ ขั้น proposal เสนอบริเวณผู้สมัคร และสำหรับแต่ละบริเวณ head สองตัวทำนายคลาส (พร้อมกล่อง) และมาสก์ โครงข่ายถูกสร้างด้วยสี่คลาส: พื้นหลังและตำแหน่งเขี้ยวสามแบบ ชื่อและสี (1 buccal เขียว, 2 bicortical เหลือง, 3 palatal น้ำตาล) อยู่เฉพาะในแผง ซึ่งใช้ระบายสีผลลัพธ์ ส่วน runner เขียนเพียงจำนวนเต็ม 1, 2 และ 3

ในโค้ดตัวสร้างโมเดล head ของมัน การดาวน์โหลด backbone และตารางคลาส

4.2 น้ำหนักโมเดล

น้ำหนักไม่ได้อยู่ในรีโพซิทอรี: แผงดาวน์โหลดได้จาก GitHub release ลงโฟลเดอร์เอกสารของผู้ใช้ runner ไม่ได้มองหาชื่อนั้น แต่หยิบไฟล์ .pth ไฟล์แรกของโฟลเดอร์ที่เลือกตามลำดับตัวอักษร ดังนั้นถ้ามีสองโมเดลในโฟลเดอร์ ชื่อไฟล์เป็นตัวตัดสิน ไฟล์เป็นดิกชันนารีน้ำหนักเปล่า ๆ ไม่มี hyperparameter ไม่มีจำนวนคลาส และไม่มีข้อมูลการฝึก จึงไม่อาจระบุชุดฝึกและเมทริกซ์ชี้วัดได้จากรีโพซิทอรี

ในโค้ดที่อยู่ดาวน์โหลด glob และคำสั่งโหลด

4.3 สิ่งที่โครงข่ายออกมาจริง ๆ

สำหรับแต่ละสไลซ์ โครงข่ายคืนรายการผู้สมัคร ผู้สมัครแต่ละรายมีกล่อง คลาสตั้งแต่ 1 ถึง 3 คะแนนความมั่นใจ และมาสก์: ภาพขนาดเท่าสไลซ์ที่เก็บความน่าจะเป็นระหว่าง 0 ถึง 1 ต่อพิกเซล torchvision ใช้ตัวกรองแรกของมันเองก่อนที่เครื่องมือจะทำอะไร (ตัดคะแนนต่ำมาก ตัดกล่องที่ซ้อนทับ และไม่เกิน 100 ผู้สมัครต่อสไลซ์) และเรียงผู้สมัครตามคะแนนจากมากไปน้อย

ในโค้ดคีย์ของดิกชันนารี รูปร่าง และเกณฑ์เริ่มต้นของ torchvision

4.4 จากเอาต์พุตของโครงข่ายถึง label map

threshold สองค่า ซึ่งเขียนไว้ในสคริปต์ทั้งคู่ เปลี่ยนผู้สมัครเป็นป้ายกำกับ จากนั้นมาสก์ถูกวาดตามลำดับ

เพราะผู้สมัครมาเรียงตามคะแนนจากมากไปน้อย อันที่วาดทีหลังสุดจึงเป็นอันที่คะแนนต่ำสุด: การซ้อนทับระหว่างผู้สมัคร buccal กับ palatal จึงถูกตัดสินให้ฝ่ายที่มั่นใจน้อยกว่าชนะ เครื่องมือไม่ได้เพิ่มขีดจำกัดของตัวเองต่อจำนวนผู้สมัครต่อสไลซ์ (torchvision เก็บไม่เกิน 100) และไม่มีการบังคับให้สอดคล้องกันแบบ 3D: แต่ละสไลซ์ถูกจำแนกลำพัง ไม่มีการทำให้เรียบระหว่างสไลซ์ ไม่มี connected-component analysis และไม่มีการโหวต สไลซ์ข้างเคียงสองสไลซ์จึงอาจให้คลาสต่างกันสำหรับฟันซี่เดียวกัน และใครที่ต้องการคลาสเดียวต่อผู้ป่วยต้องรวมผลเอง

ในโค้ดthreshold สองค่าในลูป และข้อควรระวังเรื่องการเขียนทับ

5. แกนอัลกอริทึม

ไม่มีแกนกลางที่ไม่ใช่การเรียนรู้นอกจาก threshold: ไม่มีการลงทะเบียนภาพ ไม่มี morphology ไม่มีการสกัดคอมโพเนนต์ และไม่มีการวัด runner ทั้งตัวคือ: โหลดโมเดล วนลูปตามสไลซ์ ทำ threshold แล้วเขียน การตัดสินใจทั้งหมดอยู่ใน Mask R-CNN

ในโค้ดโครงร่างเต็มของ runner

6. การประมวลผลหลังและเอาต์พุต

runner เขียนโฟลเดอร์ย่อยที่ตั้งชื่อตามสแกน และข้างในคือlabel map ตั้งชื่อจากสแกนและคำต่อท้ายที่พิมพ์ในแผง (ค่าเริ่มต้นคือ seg) เพราะนามสกุลถูกตัดเพียงครั้งเดียว สแกน X.nii.gz จึงได้โฟลเดอร์ X.nii และไฟล์ X.nii_seg.nii.gz: ไม่สวย แต่ไม่มีผลเสียตามมา label map เก็บจำนวนเต็ม 0 ถึง 3 (runner สร้างเป็นจำนวนเต็ม 16 บิต) และใช้ affine กับ header ของสแกนอินพุต จึงซ้อนทับสแกนได้โดยไม่ต้องลงทะเบียนภาพ เพราะ header ของสแกนถูกนำมาใช้ซ้ำ ไฟล์จึงถูกบันทึกในชนิดข้อมูลของสแกนเอง: สำหรับสแกนที่เก็บเป็นเลขทศนิยม label map ก็เป็นเลขทศนิยมด้วย ด้วยค่า 0 ถึง 3 เดิม

แผงถูกเขียนให้โหลดผลลัพธ์เป็น segmentation และระบายสีส่วนต่าง ๆ ตามลำดับการสร้าง ไม่ใช่ตามค่าป้ายกำกับ ดังนั้นถ้ามีคลาสหนึ่งไม่อยู่ในวอลุ่ม สีจะเลื่อน และมันยังวาดคำอธิบายสัญลักษณ์ข้อความเล็ก ๆ สามอันในมุมมอง Red, Yellow และ Green ทุกวันนี้ขั้นนี้ไปไม่ถึง เพราะแผงไม่เคยรู้จักบรรทัดผลลัพธ์ของ runner (ดูปัญหาที่ทราบด้านล่าง)

ในโค้ดบรรทัดที่บันทึก กฎการตั้งชื่อ และรูทีนคำอธิบายสัญลักษณ์

7. ทำนายหรือคำนวณ

ขั้นตอนลักษณะ
การปรับสเกลแต่ละสไลซ์ การปรับขนาดและ standardise ภายใน torchvisionคำนวณ เลขคณิตธรรมดา
การตรวจจับ คลาส และมาสก์ของเขี้ยวแต่ละซี่ทำนายโดยโครงข่าย บนการ์ดจอเมื่อมี
threshold 0.7 และ 0.5 กับการเขียนลงวอลุ่มคำนวณ
สีและคำอธิบายสัญลักษณ์Slicer ทำโดยแผง

เนื้อหาทางคลินิกทั้งหมด ไม่ว่าจะเป็นเขี้ยวที่ฝังอยู่หรือไม่ และอยู่ด้านไหนของกระดูก cortical มาจากโครงข่ายเพียงอย่างเดียว ไม่มีสิ่งใดตรวจสอบมันหลังจากนั้น

ในโค้ดตารางเดียวกันพร้อมที่ที่แต่ละบล็อกทำงาน

8. สภาพแวดล้อม

โมดูลสร้างสภาพแวดล้อม conda ของตัวเอง ชื่อ clic_env ด้วย Python 3.9 และแพ็กเกจวิทยาศาสตร์บางตัว จากนั้นติดตั้ง PyTorch ผ่าน pip จากช่องทาง wheel ที่ตรงกับการ์ดจอของเครื่อง และสุดท้ายติดตั้ง NumPy รุ่นก่อนเวอร์ชัน 2 (การเรียกครั้งสุดท้ายนั้นใส่เครื่องหมายคำพูดให้อาร์กิวเมนต์ในแบบที่ใช้ได้กับ SlicerConda รุ่นเก่าเท่านั้น ดูหน้าโค้ด) การเตรียมนี้ถูกทำซ้ำทุกครั้งที่คลิก Predict ซึ่งช้าแต่ไม่เป็นอันตราย GPU ไม่จำเป็น: ถ้าไม่มี runner ใช้ตัวประมวลผล

แพตช์ conda

แผงแพตช์วิธีที่ SlicerConda หาโปรแกรม conda เพราะ Slicer nightly ที่มันเขียนให้ใช้ เก็บเส้นทาง conda เดียวสำหรับทั้งเครื่องโดยไม่ตรวจว่ายังมีอยู่หรือไม่ แพตช์แก้โฟลเดอร์ที่ซ้ำกันในเส้นทาง ตรวจว่าไฟล์อยู่จริง และไม่เช่นนั้นค้นหาในเส้นทางของระบบ มีไว้ให้ถอดออกเมื่อ nightly รวมการแก้ที่อยู่ในรุ่น 5.12 แล้ว

ในโค้ดตารางสภาพแวดล้อมพร้อมบรรทัด การเรียก pip และตัวแพตช์เอง

9. ปัญหาที่ทราบ

  • แถบความคืบหน้าไม่เคยขยับ และผลลัพธ์ไม่เคยถูกโหลดเข้า Slicer แม้จะถูกเขียนลงดิสก์แล้ว: บรรทัดล็อกของ runner ไม่ขึ้นต้นด้วยเครื่องหมายที่แผงมองหาอีกต่อไป ดูบั๊ก
  • แม้แก้เครื่องหมายแล้ว ผลลัพธ์ทั้งหมดของสแกนจะมาเป็นก้อนเดียวตอนท้ายสแกน ความคืบหน้าจึงกระโดดจาก 0 ไป 100 เปอร์เซ็นต์ ดูรายการ
  • ปุ่ม Cancel เพียงเขียนบรรทัดหนึ่งลงล็อก ดูรายการ
  • ถ้าไม่ได้เลือกโฟลเดอร์ผลลัพธ์ runner จะล่ม ดูข้อควรระวัง
  • การสร้างโครงข่ายอาจดึง backbone ResNet-50 จากอินเทอร์เน็ต การรันครั้งแรกขณะออฟไลน์จึงล้มเหลว ดูข้อควรระวัง
  • การซ้อนทับถูกตัดสินตามลำดับ และสไลซ์ข้างเคียงไม่ถูกทำให้สอดคล้องกัน ดูข้อควรระวัง
  • NRRD และ MetaImage ผ่านตัวกรองไฟล์แต่อ่านไม่ได้ ดูข้อควรระวัง
  • ขั้น NumPy ของการเตรียมสภาพแวดล้อมอาจล้มเหลวกับ SlicerConda รุ่นใหม่ ซึ่งจะหยุด Predict ก่อน runner เริ่ม ดูส่วนสภาพแวดล้อม
  • โมดูลไม่มีเส้นทาง WSL การรันบน Windows ได้หรือไม่ขึ้นกับเวอร์ชันของ SlicerConda และยังไม่เคยลอง ดูข้อควรระวัง
  • การปรับสเกลต่อสไลซ์ทำให้ฟันซี่เดียวกันอาจดูต่างกันสำหรับโครงข่ายในสองสแกนที่มี field of view ต่างกัน ดูรายการ
ในโค้ดรายการข้อควรระวังทั้งหมดพร้อมบรรทัดที่แน่นอน และแผนภาพรูปแบบล็อก

10. วรรณกรรม

ไม่มีบทความใดครอบคลุม CLIC งานนี้ถูกประกาศภายใต้ชื่อ Interpretable Deep Learning for the Detection and Classification of Impacted Canines and severity of root resorption (Tulissi, Cevidanes, Prieto) นำเสนอที่ NA-MIC Project Week 43 (Montreal, 2025): โครงการที่ยังดำเนินอยู่ ไม่ใช่สิ่งตีพิมพ์ โค้ดดั้งเดิมมาจากรีโพซิทอรีส่วนตัว ashmoy/maskRcnn ส่วน Mask R-CNN เองอธิบายโดย He et al. (2017) และ implement ไว้ใน torchvision

บรรณานุกรมโดยละเอียด ไฟล์ที่ดึงมา และลิงก์ที่ควรเยี่ยมชม: หน้าแหล่งอ้างอิง ลิงก์และการเปรียบเทียบกับงานใกล้เคียงอยู่ในหน้าโค้ด
