CLIC

CLIC แบ่งส่วนภาพ CBCT ทีละสไลซ์ด้วย Mask R-CNN และจำแนกแต่ละอินสแตนซ์ที่ตรวจพบว่าเป็นฟันเขี้ยวคุดแบบ buccal, bicortical หรือ palatal — การจำแนกและการระบุตำแหน่งได้มาจากการประมวลผลผ่านโครงข่ายรอบเดียวกัน

ยังไม่ตีพิมพ์ clic_runner.py สภาพแวดล้อม conda: clic_env Python 3.9 บรรณานุกรม

Classification and Localization of Impacted Canines. การแบ่งส่วนระดับอินสแตนซ์ (instance segmentation) แบบ 2D ทีละสไลซ์บนภาพ CBCT ด้วย torchvision Mask R-CNN โดย คลาสที่ทำนายได้เข้ารหัสตำแหน่งในกระดูกของฟันเขี้ยวคุด: buccal, bicortical, palatal

ชื่อโมดูลสัญญาว่าทำสองงาน แต่โค้ดมีโครงข่ายเพียงตัวเดียว ไม่มี โครงข่ายจำแนกแยกต่างหาก ไม่มีโครงข่ายระบุตำแหน่งแยกต่างหาก และไม่มี head สำหรับถดถอยพิกัด การจำแนกคือป้ายของอินสแตนซ์ (pr["labels"]) การระบุตำแหน่งคือมาสก์ (pr["masks"]) ทั้งสองได้มา จากการประมวลผล Mask R-CNN รอบเดียวกัน ทุกอย่างด้านล่างสืบเนื่องจากข้อนี้

ข้อควรระวัง

ไม่มีเส้นทาง WSL: CondaSetUpCallWsl ไม่เคยถูกสร้าง บน Windows ลำดับอาร์กิวเมนต์ของ condaRunFilePython ที่เส้นทาง Unix คาดหวัง (ซึ่งถูกใช้ โดยผิดพลาด) ไม่ตรงกับของเส้นทาง WSL รายการอาร์กิวเมนต์จะถูกส่งไปเป็น ชื่อสภาพแวดล้อม ในทางปฏิบัติ CLIC ใช้ได้บน Linux เท่านั้น

3. อินพุตและการเตรียมข้อมูล

3.1 การรวบรวมภาพสแกน

_collect_scans() (CLIC/CLIC.py:316) รับ .nii, .nii.gz, .nrrd, .mha, .mhd และใช้กฎสองขั้น:

  1. หากมีโฟลเดอร์ย่อยที่มีไฟล์ที่ใช้ได้อย่างน้อยหนึ่งไฟล์ จะคืนรายการโฟลเดอร์ย่อยเหล่านั้น
  2. มิฉะนั้น คืนรายการไฟล์ที่ใช้ได้ในโฟลเดอร์

กรณีที่ 1 ได้ Path ที่เป็นไดเรกทอรี ซึ่งถูกส่งไปตามเดิมเป็น input_path ให้ runner ซึ่งเรียก nib.load(str(inp)): ล้มเหลวทันที กรณีปกติจึงเป็นโฟลเดอร์แบบแบนที่มีไฟล์ .nii.gz

นอกจากนี้ runner ใช้เพียง nibabel: .nrrd, .mha, .mhd ผ่านตัวกรองของ widget แต่ runner อ่านไม่ได้

ข้อควรระวัง

ตัวกรองการเลือกของ widget ยอมรับ .nrrd, .mha และ .mhd นอกเหนือจาก .nii/.nii.gz แต่ runner โหลดได้ด้วย nibabel เท่านั้น: สามรูปแบบนี้ผ่านตัวกรองแต่โหลดไม่สำเร็จ

3.2 การเตรียมวอลุ่มที่เกิดขึ้นจริง

มีเพียงสามบรรทัด (CLIC/runner/clic_runner.py:88):

sl = _norm(vol[..., z])                                    # min-max of the slice
t  = torch.from_numpy(sl).unsqueeze(0).repeat(3, 1, 1).float().to(device)
pr = model([t])[0]

กล่าวคือ:

  • ตัดเป็นสไลซ์แนวแกน (axial) ตามแกน 3rd ของอาร์เรย์ nibabel ตามลำดับการจัดเก็บในไฟล์ ไม่ใช่ตามการจัดแนวทางกายวิภาค ที่คำนวณใหม่ ไม่มีการจัดแนวใหม่เป็น RAS/LPS โค้ดไม่เคยดู nii.affine ยกเว้นตอนเขียนกลับ
  • การทำ normalization แบบ min-max ต่อสไลซ์ (_norm, CLIC/runner/clic_runner.py:53): (x - min) / (max - min) และสไลซ์ที่มีค่าคงที่จะกลายเป็นศูนย์ ไม่มี windowing ตามหน่วย Hounsfield ไม่มีการตัด ตามเปอร์เซ็นไทล์ ไม่มีสถิติระดับวอลุ่ม: แต่ละสไลซ์มีคอนทราสต์ ของตัวเอง สไลซ์ที่มีแต่อากาศจะถูกยืดให้เต็ม ช่วงไดนามิก
  • ทำซ้ำเป็น 3 ช่องสัญญาณ ให้ตรงกับอินพุต RGB ของ backbone ImageNet
  • ไม่มีการครอป ไม่มี ROI ไม่มีการ resample อย่างชัดแจ้ง ไม่มีการปรับสเกลวอกเซล

การปรับขนาดเพียงอย่างเดียวมาจาก torchvision เอง: GeneralizedRCNNTransform ที่ฝังอยู่ในโมเดลทำ standardization ด้วย ค่าเฉลี่ยของ ImageNet ([0.485,0.456,0.406] / [0.229,0.224,0.225]) และปรับขนาดให้ ด้านสั้นเป็น 800 px โดยด้านยาวไม่เกิน 1333 px นี่เป็นค่าเริ่มต้นของ torchvision ไม่ใช่การเลือกในรีโพสิทอรี ภาพ CBCT ขนาด 512×512 จึงถูกขยายเป็น 800×800 ก่อนเข้า backbone

4. โมเดล

4.1 สถาปัตยกรรม

_blank_model(nc) (CLIC/runner/clic_runner.py:44) ถูกเรียก ด้วย nc = 4:

m = maskrcnn_resnet50_fpn(weights=None)
m.roi_heads.box_predictor  = FastRCNNPredictor(in_f, nc)
m.roi_heads.mask_predictor = MaskRCNNPredictor(in_fm, 256, nc)
  • backbone: ResNet-50 + FPN (_resnet_fpn_extractor, 5 ระดับ)
  • RPN ตามด้วย ROI heads: box head (FastRCNNPredictor: cls_score 4 คลาส, bbox_pred 16 เอาต์พุต) และ mask head (MaskRCNNPredictor, ชั้นซ่อน 256, 4 ช่องเอาต์พุต มาสก์ 28×28 ต่อ ROI)
  • weights=None แต่ weights_backbone ยังคงค่าเริ่มต้น ResNet50_Weights.IMAGENET1K_V1: การสร้างโมเดลจะดาวน์โหลด น้ำหนัก ImageNet ของ ResNet-50 (จากนั้น load_state_dict จึงเขียนทับ) การรัน ครั้งแรกแบบออฟไลน์ = ล้มเหลว ผลข้างเคียงที่มีประโยชน์: เนื่องจาก is_trained เป็น True normalization จึงเป็น FrozenBatchNorm2d แทน BatchNorm2d ซึ่งต้อง ตรงกับโมเดลตอนฝึก เพื่อให้คีย์ของ state_dict ตรงกัน
ข้อควรระวัง

weights_backbone ยังคงค่าเริ่มต้น ResNet50_Weights.IMAGENET1K_V1 แม้ เมื่อ weights=None: เพียงแค่สร้างโมเดลก็ทำให้เกิดการดาวน์โหลด น้ำหนัก ImageNet ของ ResNet-50 การรันครั้งแรกแบบออฟไลน์ = ล้มเหลว ก่อนจะ ถึง final_model.pth เสียอีก

4.2 น้ำหนัก

URL ที่ฝังไว้ในโค้ด (CLIC/CLIC.py:333):

https://github.com/DCBIA-OrthoLab/SlicerAutomatedDentalTools/releases/download/CLIC_model/final_model.pth

ปลายทาง ~/Documents/CLIC_Models/final_model.pth runner ไม่ได้ ค้นหาชื่อนี้: ใช้ sorted(model_dir.glob("*.pth"))[0] (CLIC/runner/clic_runner.py:76) คือไฟล์ .pth แรกตาม ลำดับตัวอักษร หากมีสองโมเดลในโฟลเดอร์ ชื่อไฟล์เป็นตัวตัดสิน และเกิด IndexError ที่ไม่ถูกจัดการหากโฟลเดอร์ว่าง

ไฟล์เป็น state_dict เปล่า (model.load_state_dict(torch.load(...))) ไม่ใช่ checkpoint ของ Lightning: ไม่มีไฮเปอร์พารามิเตอร์ ไม่มีคลาส ไม่มีเวอร์ชัน ชุด ข้อมูลฝึก จำนวนสไลซ์ที่กำกับข้อมูล และตัวชี้วัด ไม่สามารถ ทราบได้จากรีโพสิทอรี

4.3 สิ่งที่โครงข่ายส่งออกจริง

โครงข่าย สำหรับแต่ละสไลซ์ model([t])[0] คืน dictionary มาตรฐานของ torchvision:

คีย์รูปร่างเนื้อหา
boxes(N,4)กล่อง x1,y1,x2,y2 ในกรอบที่ปรับขนาดแล้ว ซึ่ง transform แปลงกลับเป็นขนาดเดิม
labels(N,)จำนวนเต็ม 1..3
scores(N,)คะแนนคลาส เรียงจากมากไปน้อย
masks(N,1,H,W)ความน่าจะเป็นต่อพิกเซล ค่า float ใน [0,1]

พร้อมค่าเกณฑ์ต้นทางเริ่มต้นของ torchvision: box_score_thresh=0.05, box_nms_thresh=0.5, box_detections_per_img=100

4.4 จากเอาต์พุตของโครงข่ายสู่ label map

ค่าเกณฑ์สองค่า ทั้งคู่ฝังไว้ในโค้ด (CLIC/runner/clic_runner.py:93):

keep = pr["scores"] >= 0.7                     # confiance d'instance
for mk, lb in zip((pr["masks"][keep] > .5).squeeze(1).cpu().numpy(),
                  pr["labels"][keep].cpu().numpy()):
    seg[..., z][mk] = int(lb)
  • 0.7 กับคะแนนของอินสแตนซ์
  • 0.5 กับความน่าจะเป็นของมาสก์ เพื่อแปลงเป็นค่าไบนารี
  • การกำหนดค่าเป็นการเขียนทับ ไม่ใช่การโหวต: หากสองอินสแตนซ์ ซ้อนทับกัน อินสแตนซ์ที่ประมวลผลหลังสุด (ซึ่งคือคะแนนต่ำสุด เพราะ torchvision เรียงตามคะแนนจากมากไปน้อย) จะได้พิกเซลนั้น ความขัดแย้ง buccal/palatal บนวอกเซลเดียวกันจึงตัดสินด้วยคะแนนต่ำสุด
  • ไม่มีสิ่งใดจำกัดจำนวนอินสแตนซ์ต่อสไลซ์ ไม่ว่าจะเป็นฟันเขี้ยวหนึ่งซี่ หรือสองซี่

ไม่มีการบังคับความสอดคล้องแบบ 3D แต่ละสไลซ์ถูกจำแนกอย่างอิสระ ไม่มีการปรับให้เรียบระหว่างสไลซ์ ไม่มีการวิเคราะห์ connected component ไม่มี การโหวตเสียงข้างมากตลอดทั้งชุดสไลซ์ สไลซ์ที่อยู่ติดกันสองสไลซ์อาจมีคลาส ต่างกันสำหรับฟันซี่เดียวกัน ผู้ที่ต้องการ "คลาสของผู้ป่วย" ต้องรวมผลเอง โมดูลไม่ได้สร้างให้

ข้อควรระวัง

การซ้อนทับระหว่างสองอินสแตนซ์ตัดสินด้วยการเขียนทับ ไม่ใช่การโหวต: อินสแตนซ์ที่ประมวลผลหลังสุด ซึ่งคือคะแนนต่ำสุด เพราะ torchvision เรียงตามคะแนนจากมากไปน้อย จะได้พิกเซลนั้น และเนื่องจากไม่มีสิ่งใดบังคับ ความสอดคล้องระหว่างสไลซ์ข้างเคียง สไลซ์ที่ติดกันสองสไลซ์จึงอาจจำแนก ฟันซี่เดียวกันต่างกัน

10. เอกสารอ้างอิง

ไม่มีบทความใดครอบคลุม CLIC งานที่เกี่ยวข้องประกาศไว้ภายใต้ ชื่อ Interpretable Deep Learning for the Detection and Classification of Impacted Canines and severity of root resorption (Tulissi, Cevidanes, Prieto) นำเสนอที่ NA-MIC Project Week 43 (Montreal, 2025) เป็นโครงการที่กำลัง ดำเนินอยู่ ไม่ใช่งานตีพิมพ์ โค้ดต้นฉบับมาจากรีโพสิทอรีส่วนตัว ashmoy/maskRcnn ซึ่งเป็นที่มาของภาพสแกนทดสอบที่อ้างถึงใน README ด้วย (MN138.nii, UM06.nii)

อย่าสับสนกับงานที่เกี่ยวข้องด้านล่าง ซึ่งไม่ได้สร้าง โค้ดนี้:

  • การระบุตำแหน่ง buccal/palatal ของฟันเขี้ยวคุดโดยทั่วไปทำ บนภาพรังสีพาโนรามิก ด้วย CNN จำแนกภาพ (ไม่ใช่ Mask R-CNN บน CBCT)
  • หลายทีมตีพิมพ์การแบ่งส่วนแบบ 3D ของฟันเขี้ยวคุดบน CBCT (U-Net/nnU-Net แบบวอลุ่ม) โดยไม่จำแนกตำแหน่งเทียบกับ คอร์เทกซ์

ลักษณะเฉพาะของ CLIC คือคลาส bicortical ที่เพิ่มจากคู่ buccal/palatal ซึ่งทำนายทีละสไลซ์แบบ 2D บน CBCT ไม่มีการอธิบายไว้ใน บทความเหล่านี้เลย อย่านำตัวเลขของบทความเหล่านั้นมาเสนอว่าเป็นของโมดูลนี้
