SADT Atlas › การลงทะเบียนภาพ

FlexReg

การลงทะเบียนภาพ (registration) ภาพสแกนในช่องปาก (IOS) รายผู้ป่วย โดยใช้ patch สำหรับลงทะเบียนภาพที่สร้างด้วยมือ (รูปผีเสื้อบนเพดานปาก เส้นโค้งอิสระ หรือแถบ mucogingival) แทนการทำนายด้วยโครงข่าย — เป็นคู่แบบโต้ตอบของ AREG_IOS

ยังไม่ตีพิมพ์ FlexReg_CLI สภาพแวดล้อม conda: shapeaxi บรรณานุกรม

1. ตำแหน่งใน pipeline

ไม่มีสิ่งใดในคลังโค้ดเรียก FlexReg: เป็นเครื่องมือปลายทางที่ผู้ใช้ ควบคุมเอง อย่างไรก็ตาม FlexReg เรียกโครงข่ายที่ฝึกไว้แล้วสองตัว และ สร้างอินพุตให้ AREG_IOS — เครื่องมือทั้งสองอ่าน อาร์เรย์จุดเดียวกันทุกประการ

สิ่งที่ถูกเรียกเมื่อใดเพื่ออะไร
dentalmodelseg (ShapeAXI / DentalModelSeg)หากเมชไม่มีอาร์เรย์ Universal_IDแบ่งส่วนและกำหนดหมายเลขตัวฟัน
ALI_IOS (น้ำหนัก Lower_MG_*.pth)เฉพาะโหมดขากรรไกรล่างวางจุดสังเกตทางกายวิภาค (landmark) mucogingival 13 จุด

ปลายน้ำ AREG_IOS.py:191 เรียก vtkMeshTeeth(list_teeth=[1], property="Butterfly") และ AREG_IOS.py:205 ทำแบบเดียวกันกับ MGL_ARRAY_NAME: patch ที่สร้างใน FlexReg จึงใช้ใน AREG_IOS ได้โดยตรง และ กลับกัน ความต่างอยู่ที่ที่มาของ patch: AREG_IOS ให้โครงข่ายทำนาย (PredPatch.py ซึ่งเป็น MonaiUNetHRes แบบหลายมุมมอง) ส่วน FlexReg สร้างด้วยเรขาคณิต

3. อินพุตและการเตรียมข้อมูล

ข้อควรระวัง — การแปลงไฟล์

ensureVtkInput() (FlexReg.py:3454) แปลง .stl เป็น .vtk ก่อนการทำงานใด ๆ นี่ไม่ใช่ เรื่องผิวเผิน: dental_model_seg.py เรียก os.remove(args.stl) และจะลบไฟล์ต้นฉบับทิ้งหาก ได้รับ .stl โดยตรง

การพลิก LPS ↔ RAS CLI อ่าน .vtk (LPS) ใช้ Scale(-1,-1,1) เพื่อทำงานใน RAS แบบเดียวกับ Slicer และ พลิกกลับก่อนเขียนไฟล์ (FlexReg_CLI.py:39) การคำนวณภายใน ทั้งหมดจึงอยู่ใน RAS

การจัดกรอบมาตรฐาน (canonical) — ขั้นการเตรียมข้อมูลที่สำคัญที่สุด orientation.py:

  1. centroid ของฟัน Universal_ID 3, 5, 12, 14 (UR6, UR4, UL4, UL6)
  2. ฐานเฉพาะที่ในแต่ละข้าง: เวกเตอร์ตั้งฉากของระนาบที่ผ่านสามจุด (ผลคูณไขว้ของสองเวกเตอร์ที่ชี้ไปยังจุดกึ่งกลาง) แล้วจึงทิศทางที่ตั้งฉาก
  3. การหมุนสองครั้งต่อเนื่องกัน แกน = ผลคูณไขว้ มุม = arccos ของผลคูณจุด ผ่าน RotationMatrix (Rodrigues)
  4. การเลื่อนตำแหน่งเพื่อให้ centroid ตรงกัน

เป้าหมายคือ [[-0.5,-0.5,0], [0,0,0], [0.5,-0.5,0]]: ฟันกราม ขวาที่ x<0 ฟันกรามซ้ายที่ x>0 ฟันกรามน้อยที่จุดกำเนิด ผลลัพธ์: ระนาบ บดเคี้ยว ≈ z=0 +y = ด้านหน้า +x = ด้านซ้าย ไม่มีการย่อขยาย — เป็นการลงทะเบียนภาพแบบแข็งเกร็ง (rigid) ด้วย 3 จุด

ผลที่ตามมาโดยตรง: การคำนวณ butterfly ทั้งหมดที่ตามมาเป็น การคำนวณ 2D ในระนาบ XY โดยไม่สนใจองค์ประกอบ z

5. แกนหลักของอัลกอริทึม

5.1 เส้นทาง A — patch รูปผีเสื้อ (ขากรรไกรบน) คำนวณ

make_butterfly.py ไม่มีโครงข่าย เป็นเรขาคณิตล้วน

a) centroid สี่จุด ผู้ใช้เลือกฟัน 4 ซี่ (หน้า ซ้าย/ขวา หลัง ซ้าย/ขวา) vtkMeanTeeth หาค่าเฉลี่ยของ vertex ที่มี Universal_ID นั้น

b) พารามิเตอร์สามกลุ่ม ที่ใช้กับ centroid เหล่านี้:

พารามิเตอร์ผลรายละเอียด
shift_lr, shift_apเลื่อน patch ทั้งชิ้นเวกเตอร์เดียวกันถูกบวกเข้ากับ centroid ทั้ง 4 เนื่องจาก landmark เป็นผลรวมเชิงสัมพรรค (affine) ที่น้ำหนักรวมเป็น 1 การเลื่อนจึงส่งผ่านการประมาณค่าในช่วงไปได้ และรูปร่างไม่เปลี่ยน
adjust (mm)ยืด / หดค่าชดเชยในแนว ±y กลับเครื่องหมายสำหรับฟันหลัง: adjust ที่เป็นบวกจะดันปลายทั้งสองออกด้านนอก
ratioคงความกว้างไว้เปลี่ยนตัวแปรเป็น r = (1-ratio)/2 แล้ว landmark = (1-r)·own_centroid + r·opposite_centroid ratio=1 → landmark อยู่บน centroid ของตัวเอง (patch ใหญ่สุด) ratio=0 → landmark อยู่กึ่งกลาง (patch เสื่อม)

ระวังเรื่องคำศัพท์: UI ใช้ top/bot ส่วน CLI ใช้ anterior/posterior lineedit_teeth_left_top → tooth_anterior_left

c) เส้นขอบ มีสี่ส่วน:

  • ส่วนเส้นตรงด้านหน้าและด้านหลัง (Segment2D, ขั้น 0.01)
  • เส้นโค้ง Bézier กำลังสองสองเส้น ขวาและซ้าย จุดควบคุม (posterior_landmark, posterior_midpoint, anterior_landmark) แล้วสะท้อนข้ามคอร์ด (sym = 2·proj − bezier) ให้โป่งออกไปทางด้านนอกของส่วนโค้งฟันแทนที่จะเข้าหาจุดกึ่งกลาง นี่คือสิ่งที่ทำให้ butterfly มีรูปร่างเช่นนี้

d) การทำเครื่องหมาย torch.cdist ระหว่างจุดบน เส้นขอบกับ vertex ที่ฉายลงบน XY vertex ทุกตัว ที่อยู่ภายใน radius = 0.7 mm จะถูกตั้งเป็น 1

e) การเติม Dilation() (propagation.py:73): เป็นการเติมแบบ flood fill เชิง geodesic บน เมช ไม่ใช่ morphological dilation เริ่มจาก vertex ที่ใกล้ barycenter ของ landmark ทั้ง 4 มากที่สุด แล้วแพร่ไปทีละ เพื่อนบ้าน (GetPointCells / GetCellPoints) และ หยุดที่เส้นขอบ ซึ่งถูกตั้งเป็น 1 ไว้แล้ว ทำเป็นชุดละ nmb_treatment = 1000 บน GPU

f) การเขียน อาร์เรย์มีชื่อว่า Butterfly{index}: patch แต่ละชิ้นมีดัชนีของตัวเอง ทำให้ สะสมหลายชิ้นได้ เมื่อ CLI ทำงานจบ อาร์เรย์ Butterfly1..N ทั้งหมดจะถูกรวมด้วย torch.logical_or เป็นอาร์เรย์เดียวชื่อ Butterfly (FlexReg_CLI.py:229) — ซึ่งเป็นอาร์เรย์ที่ ICP และ AREG_IOS อ่าน ผลลัพธ์ถูกเขียนกลับลงในไฟล์อินพุต

โหมด delete จะเรียงหมายเลขอาร์เรย์ที่อยู่เหนือดัชนีที่ถูกลบ ใหม่ แล้วทิ้งอาร์เรย์สุดท้าย แทนที่จะปล่อยให้มีช่องว่าง

ภาพตัวอย่างแบบเรียลไทม์ butterfly_preview.py สร้าง เส้นขอบแบบเดียวกันทุกประการซ้ำด้วย numpy ล้วน (CPU) และแทน flood fill ด้วยการทดสอบจุดในรูปหลายเหลี่ยม (matplotlib.path.Path โดยมี crossing-number ของ numpy เป็นทางสำรอง) การจัดแนวและ centroid ถูก cache ไว้ต่อ ภาพสแกน (prepare) จึงคำนวณใหม่เฉพาะเส้นขอบทุกครั้งที่ ขยับจอยสติก ค่าคงที่: CELL = 1.0 mm สำหรับ height map LIFT = 0.4 mm เหนือฟัน NB_POINTS = 120 ตัวอย่างต่อขอบ

5.2 เส้นทาง B — patch ที่วาดเอง คำนวณ

draw() (FlexReg.py:4239), type="curve" เส้นโค้งของ Slicer ที่ถูกบังคับให้อยู่บนพื้นผิว (SetAndObserveSurfaceConstraintNode) พร้อมจุดกึ่งกลางหนึ่งจุด แปลงเป็นสตริงแล้วส่งให้ CLI draw.py ประมาณค่าในช่วง แบบเชิงเส้นระหว่างจุดที่ต่อเนื่องกัน (ขั้น 0.2, วงปิด) ทำเครื่องหมาย vertex ที่อยู่ภายใน 1.1 mm แล้วรัน Dilation() ตัวเดียวกันทุกประการจาก จุดกึ่งกลาง ความต่างจาก butterfly มีเพียงวิธีได้มาซึ่งเส้นขอบ

เส้นโค้งถูกวาดบนโมเดลที่จัดกึ่งกลางใหม่ให้หันเข้าหากล้อง ก่อน ส่งให้ CLI moveCurve() จะใช้ inverse ของ เมทริกซ์จัดกึ่งกลางใหม่เพื่อนำกลับสู่พิกัดของไฟล์

5.3 เส้นทาง C — patch MGL (ขากรรไกรล่าง) คำนวณ

เพดานปากให้พื้นที่ราบที่คงที่บนขากรรไกรบน แต่ขากรรไกรล่าง ไม่มี สิ่งที่เลือกมาแทนคือเส้น mucogingival ส่วน นี้ทั้งหมดคำนวณภายในวิดเจ็ต ด้วย numpy/scipy — ไม่ใช้ GPU ไม่ใช้ CLI (mgl_patch.py)

a) การคัดกรองผลทำนายของ ALI DoubtfulLandmarks() อ่าน description ที่ ALI เขียน ลงใน json เมื่อบังคับวางจุด (พิกเซล top-k, ถอยไปใช้ฟัน, ฟันหายไป) ตามคอมเมนต์ในโค้ด ซึ่งวัดจากการทำนาย 364 ครั้ง: ค่ามัธยฐานของความเบี่ยงจากเส้นโค้งของจุดข้างเคียง 4.2 mm เทียบกับ 1.2 mm สำหรับจุดที่เหลือ จุดเหล่านี้ถูกตัดทิ้งโดยค่าเริ่มต้น และ spline จะเชื่อม ช่องว่าง — เว้นแต่จะเหลือจุดน้อยกว่า 3 จุด จากนั้น CanonicalLandmarks (แปลงการตั้งชื่อ annotation แบบเก่า → แบบมาตรฐาน ตรวจพบจากการมี LL7MG หรือ LR7MG) และ RecentreNames (การ นับยังยึดอยู่ที่เส้นกึ่งกลางเมื่อมีจุดหายไประหว่าง ส่วนโค้งฟัน)

b) กรอบเฉพาะที่ LocalFrames(): แกน apical คือองค์ประกอบที่สามของ SVD ของ landmark ที่จัดกึ่งกลางแล้ว (เวกเตอร์ตั้งฉากของแถบจุด ไม่ขึ้นกับ การวางตัวของภาพสแกนในพิกัดโลก) tangent คือ np.gradient ตามแนวส่วนโค้งฟัน buccal คือ ผลคูณไขว้ของทั้งสอง โดยกลับทิศในจุดที่ชี้เข้าด้านใน OrientApical กำหนดเครื่องหมายโดยอิงตัวฟัน

c) การสร้างแถบ ทุกครั้งที่เรียก compute():

  1. ค่าชดเชยที่ผู้ใช้กำหนด (buccal / apical / tangential) ถูกใช้กับ landmark
  2. vtkParametricSpline ลากผ่านจุดเหล่านั้น SAMPLES_PER_SEGMENT = 25
  3. แต่ละตัวอย่างถูก snap ลงบนเมช (vtkPointLocator) — spline ที่ประมาณค่าในช่วงจะลอยหลุดจากพื้นผิวในส่วนเว้าระหว่างฟัน
  4. Dijkstra (scipy.sparse.csgraph) บนกราฟของขอบที่ถ่วงน้ำหนักด้วยความยาวจริง แบบหลายต้นทางจาก vertex เหล่านี้ limit = ความสูงสูงสุด min_only=True, return_predecessors=True → แถบขยายไปตามพื้นผิว ไม่เคยทะลุผ่าน (patch ด้าน vestibular จึงโผล่ออกด้าน lingual ซึ่งสันเหงือกบางไม่ได้)
  5. ความสูงประมาณค่าเชิงเส้นระหว่าง landmark (np.interp) และไม่สมมาตร: heights ด้านตัวฟัน heights_down ด้าน vestibular โดยตัดสินด้านจากเครื่องหมายขององค์ประกอบ apical ความสูงที่ใช้คือของ seed ที่ไปถึง vertex นั้น ส่วนสองส่วนที่ความสูงต่างกันจึงอยู่ร่วมกันได้โดยไม่มีขั้นบันได
  6. ตัวฟัน (Universal_ID 18–31, LOWER_TOOTH_LABELS) ถูกตัดออก — เพราะเคลื่อนที่ระหว่าง T1 และ T2
  7. ตัว landmark เองยังอยู่ใน patch เสมอ

ขอบเขต: MIN_HEIGHT = 0.0, MAX_HEIGHT = 5.0, DEFAULT_HEIGHT = 2.5 mm ความสูงเป็นศูนย์ทุกที่ ⇒ เหลือเพียง 13 จุด: นี่คือกรณีควบคุมที่ตั้งใจไว้ เพื่อ วัดว่าแถบเพิ่มอะไรจากการใช้เพียงจุด

กราฟของขอบสร้างด้วย np.unique(np.sort(edges)) ก่อน coo_matrix: หากไม่ตัดรายการซ้ำนี้ ขอบภายใน ที่สามเหลี่ยมสองรูปใช้ร่วมกันจะถูกบวกรวม โดย sparse matrix ทำให้ความยาวเป็นสองเท่าและระยะเอื้อมของ patch ลดลงครึ่งหนึ่ง

อาร์เรย์เอาต์พุต: Bottom_MGL (MGL_ARRAY_NAME) แสดงตัวอย่างใน Bottom_MGLPreview

WriteLandmarks() เขียน landmark ที่แก้ไขแล้วใน LPS เช่นเดียวกับ annotation สำหรับการฝึก: ไฟล์ ที่ได้จึงป้อนกลับเข้าคลังข้อมูลได้โดยตรง

5.4 การลงทะเบียนภาพ คำนวณ

Reg.run() (FlexReg.py:1276) เรียก CLI ตัวเดิมอีกครั้ง ด้วย type = "icp" (ขากรรไกรบน) หรือ "icp_mgl" (ขากรรไกรล่าง) T2 คือภาพสแกน moving (lineedit) T1 คือภาพ fixed (path_reg)

patch_array = "Bottom_MGL" if args.type == "icp_mgl" else "Butterfly"
option = vtkMeshTeeth(list_teeth=[1], property=patch_array)
icp = ICP([vtkICP()], option=option)
output_icp = icp.run(modelNode, modelNodeT1)

vtkMeshTeeth ไม่ได้สร้างเมชแม้ชื่อจะสื่อเช่นนั้น: มัน ดึงกลุ่มจุด (point cloud) ที่มีเฉพาะ vertex ซึ่ง อาร์เรย์ patch มีค่าเท่ากับ 1 ICP จึงทำงานบน patch เท่านั้น ไม่เคยทำบนตัวฟัน

icp.GetLandmarkTransform().SetModeToRigidBody()   # 6 dof, no scaling
icp.SetMaximumNumberOfIterations(1000)
icp.StartByMatchingCentroidsOn()                  # initialization

vtkIterativeClosestPointTransform มาตรฐาน: จับคู่ nearest-neighbor ประมาณค่าแบบ rigid ด้วยกำลังสองน้อยที่สุด แล้ววนซ้ำ ไม่มีการเรียนรู้ใดใน ขั้นนี้

จากนั้นเมทริกซ์ 4×4 ถูกนำไปใช้กับเมช T2 ทั้งหมด และกับขากรรไกรฝั่งตรงข้ามหากมีการระบุ (lower_arch) เพื่อให้ เคลื่อนตามการเคลื่อนที่เดียวกัน

6. การประมวลผลภายหลังและเอาต์พุต

เมช type แบบ patch → เขียนทับ ลงในไฟล์อินพุต type แบบ ICP → เขียน ลงใน path_output เป็น <T2 name without extension><suffix>.vtk หลัง พลิกกลับเป็น LPS

Transform ขั้นที่ละเอียดอ่อน (FlexReg_CLI.py:186):

flip = np.diag([-1, -1, 1, 1])
composed = flip @ matrix_array @ flip     # RAS -> LPS by conjugation
composed_inv = np.linalg.inv(composed)    # ITK convention: fixed -> moving
sitk_tfm = sitk.AffineTransform(3)
sitk_tfm.SetMatrix(composed_inv[:3, :3].flatten())
sitk_tfm.SetTranslation(composed_inv[:3, 3])

ไฟล์ <T2 name><suffix>.tfm ซึ่ง โมดูลอื่นในคลังโค้ดนำไปใช้ต่อได้

ปุ่ม See รันการลงทะเบียนภาพแบบเดียวกันทุกประการ ลงใน tempfile.mkdtemp(prefix="FlexReg_see_") ซึ่งถูกลบ ทันทีที่แสดงผล (discardTempFolder) โหนดที่ได้ ถูกตั้งเป็น SetSaveWithScene(False) และเปลี่ยนชื่อเป็น ... (preview, not saved): ไฟล์เบื้องหลังกำลังจะ หายไป

การแสดงผล layout กำหนดเอง 501 T1 ใช้สี [255,51,200]/256 และ T2 ใช้สี [102,102,255]/256 ใน มุมมอง 3D ที่สาม

9. ข้อควรระวังและจุดเปราะบาง

CLI ต้องมี CUDA

Dilation, drawPatch และการรวม อาร์เรย์ขั้นสุดท้ายล้วนเรียก .cuda() โดยไม่มีทางสำรองไปใช้ CPU ส่วน patch MGL คำนวณฝั่งวิดเจ็ตและไม่ต้องใช้ — จึงมี while args.type != "icp_mgl" ที่ข้ามการรวม สำหรับขากรรไกรล่าง

ไฟล์อินพุตถูกเขียนทับ

ในโหมด patch และการแบ่งส่วนอัตโนมัติก็เขียนทับเช่นกัน (overwrite=1) ไฟล์ .stl ที่ส่งให้ dentalmodelseg จะถูกลบทิ้งไปเลย — นี่คือ เหตุผลทั้งหมดที่ ensureVtkInput() มีอยู่

บั๊กที่ยืนยันแล้ว — vtkICP.__call__

vtkICP.__call__ คืนค่า source โดยไม่เปลี่ยนแปลง แทนที่จะ คืนเมชที่แปลงแล้ว ไม่มีผลเสียในที่นี้เพราะ list_icp มีเพียงวิธีเดียว แต่ลำดับหลายขั้นจะไม่ทำงานตามที่ เขียนไว้

การตรวจหา segmentation อาศัย exception

เมชที่แบ่งส่วนไว้ภายใต้ชื่ออาร์เรย์อื่นที่ไม่ใช่ Universal_ID จะทำให้เกิดการแบ่งส่วนใหม่ทั้งหมด

บั๊กที่ยืนยันแล้ว — GetLabelSurface

GetLabelSurface (vtkSegTeeth.py:29) วนลูปบน อาร์เรย์และทำ continue เมื่อพบอาร์เรย์ที่ ต้องการ แทนที่จะ break: ชื่อที่คืนกลับมาคือของ อาร์เรย์สุดท้ายในรายการ ไม่จำเป็นต้องเป็นตัวที่ต้องการ ไม่มีผลเสียตราบที่ automatic_property ยังเป็น False ซึ่งเป็น เช่นนั้นทุกที่ใน FlexReg

โค้ดที่ไม่ถูกใช้งาน: downloadModel(), setup_cli_command() / find_cli_parameters()

patch ถูกกำหนดบนภาพฉาย 2D

patch รูปผีเสื้อถูกกำหนดบนภาพฉาย 2D: บน ขากรรไกรที่เอียงมากหลังการจัดแนว เส้นขอบอาจเก็บ vertex ที่อยู่ห่างกันมากในแนว z

10. เอกสารอ้างอิง

รากฐานที่ตีพิมพ์แล้วคือ AReg IOS: Automatic Registration on IntraOral Scans (Hutin, Anchling, Cevidanes et al., Lecture Notes in Computer Science, 2023): การแบ่งส่วนตัวฟันด้วย DentalModelSeg การจัดแนวเริ่มต้นด้วย centroid ร่วม ROI บนเพดานปากที่แบ่งส่วนด้วยการวิเคราะห์ รูปร่าง 3D แบบหลายมุมมอง แล้วจึง ICP FlexReg คือคู่ของงานนี้ในแบบ "ผู้ใช้วาด ROI เองแทนการให้โมเดลทำนาย"

ไม่มีบทความใดกล่าวถึง FlexReg หรือรูปแบบ MGL โดยเฉพาะ — รูปแบบหลังดูเหมือนเป็นการพัฒนาภายในที่ยังไม่ได้ตีพิมพ์ จนถึงปัจจุบัน ตัวเลขที่อ้างในโค้ด (4.2 mm เทียบกับ 1.2 mm จากการทำนาย 364 ครั้ง) ไม่มีแหล่งที่มาใดนอกจากคอมเมนต์
