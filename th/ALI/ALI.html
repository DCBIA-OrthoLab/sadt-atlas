3. ALI_CBCT — เอเจนต์ภายในวอลุ่ม

3.1 การเตรียมข้อมูล

สองขั้นตอน ทั้งคู่เขียนลงใน temp_fold และ ไม่เคยถูกล้าง:

  1. การกำหนดหน้าต่างฮิสโตแกรม CorrectHisto(scan, out, 0.01, 0.99) (preprocess.py:27): ฮิสโตแกรม 1000 bin แบบสะสมที่ทำให้เป็นมาตรฐาน ตัดที่เปอร์เซ็นไทล์ 1% และ 99% และจำกัดขอบเขตตายตัวที่ [-1500, 4000] HU เอาต์พุตเป็น int16 คง spacing/origin/direction ไว้ ข้อควรระวัง: signature ค่าเริ่มต้นระบุ max_porcent=0.95 แต่การเรียกส่ง 0.99
  2. การ resample แบบ isotropic หนึ่งไฟล์ต่อสเกล: SetSpacing (itk, interpolation เชิงเส้น — nearest-neighbor หากชื่อมี seg/Seg) สำหรับแต่ละ sp ใน spacing = [1, 0.3] mm ขนาดใหม่คือ size * spacing / sp และ origin ถูกจัดให้อยู่กึ่งกลางกล่องทางกายภาพเดิม
ข้อควรระวัง

ไฟล์ถูกตั้งชื่อเป็น <stem>_sp<1|0-3><suffixes> และ ถูกใช้ซ้ำหากมีอยู่แล้ว: เป็นแคช และจึงเป็นกับดักด้วยหากอินพุตเปลี่ยนโดยไม่เปลี่ยนชื่อ

ขณะโหลด (environment.py:81): sitk.DICOMOrient(img, "LPS") — หากไม่มีขั้นตอนนี้ เอเจนต์ซึ่งอ่านเพียงอาร์เรย์ดิบและไม่เคยอ่าน direction cosines จะเดินอยู่ในวอลุ่มที่กลับด้าน จากนั้น EnsureChannelFirst + BorderPad(padding) ด้วย padding = agent_FOV/2 + 1 = [33,33,33] เพื่อให้การครอป 64³ ใช้ได้ไม่ว่าเอเจนต์จะอยู่ที่ใด

อาร์เรย์ถูกเก็บในลำดับ numpy (z,y,x) และ origin ถูก กลับลำดับ ให้ตรงกัน — แต่ spacing ไม่ถูกกลับ ยังคงเป็น (x,y,z) สิ่งนี้ไม่มีผลเพียงเพราะการ resample ทำให้ spacing เป็น isotropic

3.2 Environment

Environment (environment.py:26) คือผู้ป่วยหนึ่งราย: dictionary {scale_key: {image, spacing, origin, size}} พร้อมรายการ landmark ที่ทำนาย หนึ่งอินสแตนซ์ต่อผู้ป่วย เก็บทุกสเกลไว้ในหน่วยความจำ

GetZone(scale, center, crop_size) คือสิ่งเดียวที่เอเจนต์มองเห็นจากโลก:

cropTransform = SpatialCrop(center.tolist() + self.padding, crop_size)
rescale = ScaleIntensity(minv=-1.0, maxv=1.0, factor=None)
crop = rescale(cropTransform(self.data[scale]["image"])).type(torch.float32)

ลูกบาศก์ขนาด 64×64×64 วอกเซล ที่มีเอเจนต์อยู่กึ่งกลาง ปรับค่าใหม่ ต่อการครอปแต่ละครั้ง ให้อยู่ใน [-1,1] (min/max เฉพาะที่ ไม่ใช่การทำให้เป็นมาตรฐานแบบทั้งภาพ) ที่สเกล 1 ครอบคลุมด้านยาว 64 mm ที่สเกล 0-3 ครอบคลุม 19.2 mm

3.3 เอเจนต์และโครงข่าย

เอเจนต์หนึ่งตัวต่อ landmark (agent.py:73) สร้างครั้งเดียวแล้วใช้ซ้ำกับผู้ป่วยทุกราย Brain ตัวใหม่ถูกสร้างและโหลดน้ำหนักใหม่ สำหรับทุกคู่ (ผู้ป่วย, landmark) (ALI_CBCT.py:194) — สร้าง DenseNet 2 ตัวใหม่และอ่านไฟล์ .pth 2 ไฟล์ซ้ำต่อจุดต่อภาพสแกน

โครงข่าย DNet (brain.py:48):

self.featNet = DenseNet(spatial_dims=3, in_channels=1, out_channels=1024,
                        growth_rate=34, block_config=(6, 12, 24, 16))
self.dens = DN(in_channels=1024, out_channels=6)   # MLP 1024-512-256-128-6

DenseNet-121 แบบ 3 มิติจาก monai (growth rate 34 แทน 32) ตามด้วย MLP 4 ชั้น อินพุต [1, 1, 64, 64, 64] เอาต์พุตเป็นคะแนน 6 ค่า หนึ่งค่าต่อการเคลื่อนที่: Up / Down / Back / Front / Left / Right — คือ ±1 วอกเซลตามแต่ละแกนทั้งสามของอาร์เรย์ (constants.py:22)

นี่ไม่ใช่ heatmap: เป็นตัวจำแนกทิศทาง การทำนาย ของโครงข่ายไม่ได้บอกว่าจุดอยู่ที่ใด แต่บอกว่าควรก้าวไปทางไหน Predict ใช้ argmax ของคะแนน 6 ค่า (brain.py:166)

บั๊กที่ยืนยันแล้ว

สังเกตว่า DN.forward ใช้ relu กับชั้นสุดท้ายด้วย คะแนนจึง ≥ 0 และหาก pre-activation ทั้งหมดเป็นลบ ทั้ง 6 ค่าจะเป็น 0 และ argmax จะคืนค่า 0 ("Up") เสมอ softmax ที่ถูกคอมเมนต์ไว้ข้างล่างบ่งชี้ว่านี่ไม่ใช่ความตั้งใจ

หนึ่งโครงข่ายต่อสเกล: Brain สร้างหนึ่งตัวต่อ scale_key และ LoadModels โหลด <label>/1/*.pth แล้วจึง <label>/0-3/*.pth

3.4 การค้นหา

Agent.Search() (agent.py:242):

  1. สเกล 0 (1 mm) ตำแหน่ง ที่กึ่งกลางวอลุ่ม
  2. ลูป: PredictAction() → Move() ทีละก้าวขนาด speed_per_scale[scale] = 1 วอกเซล
  3. เกณฑ์การหยุด = การแกว่ง Visited() ตรวจว่าตำแหน่งปัจจุบันอยู่ในตำแหน่ง 10 ตำแหน่งล่าสุดหรือไม่ (shortmem_size = 10) เมื่อเอเจนต์ย้อนรอยตัวเอง ถือว่ามาถึงแล้ว
  4. UpScale(): ย้ายไปสเกล 0-3 แปลงตำแหน่งตามอัตราส่วน spacing ล้างหน่วยความจำระยะสั้น และเริ่มการค้นหาใหม่
  5. ที่สเกลสุดท้าย Visited() ยุติการค้นหา

งบเวลา: 15 s บน GPU, 60 s บน CPU ต่อ landmark ต่อผู้ป่วย ปรับแทนได้ด้วย ALI_SEARCH_MAX_TIME เกินเวลา → -1 ไม่เขียน landmark เช่นเดียวกันหากเอเจนต์ออกนอกวอลุ่มสามครั้ง (search_atempt > 2) ทุกครั้งที่ออก จะถูกวางใหม่แบบสุ่ม (spawn_radius = 10 วอกเซลรอบจุดเริ่ม ที่สเกล > 0)

การปรับละเอียดขั้นสุดท้าย Focus() (agent.py:215): จากตำแหน่งที่พบ เริ่มใหม่หกครั้งที่ระยะ 4 วอกเซล (1.2 mm ที่สเกลสุดท้าย) ตาม ±x, ±y, ±z แต่ละครั้งเดินใหม่จนถึง Visited() ตำแหน่งที่เลือกคือ ค่าเฉลี่ยของจุดหยุดทั้งหก นี่คือสิ่งที่ทำให้ผลลัพธ์ละเอียดกว่าระดับวอกเซล

ข้อควรระวัง

Focus ไม่มีขอบเขตใด ๆ เลย: ไม่มีจำกัดเวลา ไม่มีการนับก้าว ไม่มีการตรวจ search_atempt เอเจนต์ที่ออกนอกวอลุ่มจะถูกวางใหม่แบบสุ่ม และลูป while not found เริ่มต้นใหม่ทั้งหมด

4. ALI_IOS — การเรนเดอร์หลายมุมมอง

4.1 อินพุต

.vtk, .vtp, .stl, .obj, .off แต่ ทุกอย่างขึ้นกับอาร์เรย์ป้ายกำกับฟัน ซึ่งค้นหาภายใต้ชื่อ PredictedID, predictedId หรือ Universal_ID (surface.py:207): อาร์เรย์นี้ให้จุดศูนย์ถ่วงของแต่ละซี่ และจึงให้ตำแหน่งกล้อง หากไม่มีอาร์เรย์ RI จะถูกตั้งเป็นศูนย์และไม่พบป้ายกำกับใด

หากภาพสแกนไม่มีอาร์เรย์นี้ SegmentSurface (segmentation.py:80) จะเรียก dentalmodelseg บน สำเนา (ไฟล์ .stl ที่ส่งให้ shapeaxi พร้อม --overwrite 1 จะถูกลบโดย dental_model_seg.py) ผ่านไฟล์ csv (การส่งไฟล์เดียวให้ --surf ทำให้ shapeaxi แครชเพราะแอตทริบิวต์ที่ไม่ได้กำหนด) การแบ่งส่วนไม่ขยับจุด — วัดได้ 5e-5 mm บนจุด 118k จุดตามคอมเมนต์ — landmark จึงยังใช้ได้ในไฟล์ต้นฉบับ

การปรับสเกลมาตรฐาน ScaleSurf (surface.py:94): จัดกึ่งกลางที่จุดกึ่งกลางของ bounding box แล้ว scale = 1 / ||max - center|| pipeline ทั้งหมดทำงานภายใน ทรงกลมหนึ่งหน่วย นี้ และ Upscale ย้อนกระบวนการในตอนท้าย

การปรับระนาบ (เฉพาะ MG) LowerArchMatrix (orientation.py:98): กล้อง MG ถูกสร้างรอบแกนตั้งที่สมมุติว่าเป็น Z ระนาบบดเคี้ยว ถูก fit ด้วย SVD บนจุดศูนย์ถ่วงของฟันซี่ 18–31 (อย่างน้อย 4 ซี่ กระจายอย่างน้อย 4 ป้ายกำกับ) โดยกำหนดเครื่องหมายให้ตัวฟันชี้ขึ้น จากนั้น การหมุนน้อยที่สุด (Rodrigues) นำ normal มาอยู่บน +Z หากเอียงน้อยกว่า MAX_TILT_DEGREES = 12° ภาพสแกนจะไม่ถูกแตะเลย — การส่งภาพสแกนที่ได้ระดับอยู่แล้วเข้ากรอบตายตัวจะหมุนมันภายในระนาบและทำให้การทำนายแย่ลง landmark ถูกส่งกลับผ่าน inv(matrix) ก่อนเขียน

กล้อง MG ส่วนเดียวที่ปรับตัวได้ (agent.py:192):

  • เส้นสัมผัสส่วนโค้งฟัน: ผลต่างระหว่างจุดศูนย์ถ่วงของฟัน label-1 และ label+1 (ป้ายกำกับล่าง 18→31 เรียงต่อเนื่องตามส่วนโค้ง) ทำให้แบนในแกน z
  • normal ด้านแก้ม: แนวนอนตั้งฉากกับเส้นสัมผัส พลิกกลับหากชี้เข้าด้านใน ทิศทางรัศมี (กึ่งกลางฟัน − กึ่งกลางเมช) ที่ใช้ในเวอร์ชันก่อนคลาดไป 35° ที่ฟัน 19/30 และ 53° ที่ฟัน 31: กล้องมอง ตาม ส่วนโค้ง และจุดตกออกนอกภาพเรนเดอร์
  • จุดเล็ง: ไม่ใช่จุดศูนย์ถ่วงของฟัน แต่เป็น centroid + b·normal + t·tangent, z += v โดย (b,t,v) อ่านจาก MG_AIM_OFFSET (model.py:35) — ค่ามัธยฐานรายซี่จากภาพสแกนฝึก 155 ภาพ การกระจาย 0.02–0.03
  • กล้องสามตัว: normal ด้านแก้ม บวก ±0.35 rad รอบแกน Y วางที่ระยะ radius จากจุดเล็ง และลดต่ำลง 0.15·radius

  4. จุดยอด 3 จุดของแต่ละหน้าที่เก็บไว้ ถูก เฉลี่ย
  5. vtkOctreePointLocator.FindClosestPoint: จุดเฉลี่ยถูก snap ไปยังจุดยอดที่มีอยู่ — ค่าเฉลี่ยของแพตช์โค้งจะตกอยู่ใต้พื้นผิว

  • patch_dentalmodelseg() (install_pytorch.py:210) เขียนซอร์สของ shapeaxi ที่ติดตั้งแล้วใหม่: ในเวอร์ชัน 2.0.0–2.0.2 dental_model_seg.py เรียก saxi_nets.DentalModelSeg ซึ่งเป็นคลาสที่ย้ายไปอยู่ใน saxi_nets_lightning แล้ว

7. ข้อควรระวังและจุดเปราะบาง

  • Focus() ไม่มีกลไกป้องกัน: ไม่มีงบเวลา ไม่มีการตรวจ search_atempt เป็นลูปเดียวที่ไม่มีขอบเขตใน pipeline ของ CBCT
  • Move() ตรวจขอบเขตผิด: if new_pos.all() > 0 and (...) — .all() คืนค่า boolean แล้วนำไปเทียบกับ 0 การทดสอบจึงตรวจว่า "ไม่มีพิกัดใดเป็นศูนย์" ไม่ใช่ "ไม่มีพิกัดใดเป็นลบ" (agent.py:193)
  • การแปลงเป็น int16 ก่อน argmax ยังอยู่ในโมเดล O และ C คอมเมนต์ในโค้ด MG อธิบายอย่างแม่นยำว่าทำไมจึงผิด
  • get_view_rasterize สำหรับกรณีที่ไม่ใช่ MG ทำ rasterize โดยไม่มี R/T: renderer.rasterizer(meshes.clone()) (agent.py:366) ไม่ได้ส่งเมทริกซ์ที่ใช้ในการเรนเดอร์ข้างบน pix_to_face จึงมาจากกล้องค่าเริ่มต้น ไม่ใช่กล้องที่สร้างภาพ เส้นทาง MG ถูกเขียนขึ้นโดยเจตนาเพื่อแก้ปัญหานี้ ("with the SAME R,T so pix_to_face stays aligned", agent.py:267) นั่นคือโค้ด upstream ดั้งเดิม และไม่เคยถูกนำมาใช้ซ้ำกับ O/C
  • val_pred / post_pred (ALI_IOS.py:447): AsDiscrete(argmax=True, to_onehot=4) ถูกคำนวณในทุกมุมมองแล้วไม่เคยถูกอ่าน เป็นการคำนวณที่สูญเปล่าในทุกซี่
  • ชื่อ MG ชนกัน หกในสิบสามชื่อเอาต์พุตเป็นชื่อที่ใช้ตอนฝึกของฟัน อีกซี่: LR1MG เป็นชื่อเอาต์พุตของฟัน 26 และเป็นชื่อตอนฝึกของฟัน 25 (model.py:25) การแปลงระหว่างสองแบบแผนต้องตัดสินจากชุดป้ายกำกับทั้งหมด ห้ามทำทีละป้ายกำกับ
  • เส้นทาง DICOM ของ widget ใช้ไม่ได้ Auto_CBCT ไม่ได้ implement ทั้ง NumberScanDCM, TestScanDCM และ getTestFileListDCM: เวอร์ชันฐานคืนค่า None การเลือก "DICOM" ให้ nb_patient = None ตามด้วย TypeError เมื่อดาวน์โหลดไฟล์ทดสอบ และการหารด้วย None ใน OnEndProcess ตัว CLI เองแปลงได้
  • manifest ของ Agent ไม่ครบ ali_cbct ประกาศพารามิเตอร์ 6 ตัวจาก 10 ตัวตามตำแหน่งที่คาดไว้ ali_ios ประกาศ 6 จาก 10 และ ละ teeth_mg (ดัชนี 4): ค่าที่ตามมาเลื่อนไปหนึ่งช่อง (manifest.yaml:48)
  • temp_fold ไม่เคยถูกล้าง โดย ALI_CBCT และไฟล์ที่ resample แล้วถูกใช้ซ้ำตามที่เป็นหากมีอยู่: แคชเงียบระหว่างการรันสองครั้ง
  • Auto_IOS.getALIModelList คืนค่า super().getALIModelList() ซึ่งเป็นเมธอด abstract ว่าง → None (IOS.py:172)
  • slicer.modules.ali_ios ถูก AREG เรียกผ่าน slicer.cli.run (IOSCBCT.py:350) จึงทำงานใน Python ของ Slicer ที่ไม่ได้ติดตั้ง pytorch3d และ shapeaxi ตัว widget ของ ALI เองเรียกผ่าน conda run เท่านั้น สองเส้นทางนี้ไม่สามารถทำงานได้ทั้งคู่บนการติดตั้งเดียวกัน
  • SURFACE_LANDMARKS (ALI.py:127) มีตัวเลือก R, RIP, OIP ซึ่งไม่มีรายการใน MODELS_DICT: การเลือกเฉพาะตัวเหล่านี้ทำให้ CLI ล้มเหลวด้วย "No matching models found."
  • onPredictButton ต่อกระบวนการ IOS สองขั้นอย่างไม่ถูกต้อง: if "CrownSegmentationcli" และ if "ALI_IOS" ที่ตามมาไม่ได้แยกกันเด็ดขาด และ else ที่ตามหลังผูกกับตัวที่สอง (ALI.py:987) เมื่อต้องแบ่งส่วน ALI_IOS จะถูกเริ่มใหม่จาก onProcessUpdate มิฉะนั้นจาก onPredictButton สองจุดเริ่มต้นสำหรับขั้นตอนเดียวกัน
