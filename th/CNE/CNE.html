CNE

โมดูลการอนุมานด้วยโมเดลภาษา (LLM) ที่อ่านบันทึกทางคลินิกแบบข้อความอิสระ แล้วสกัดคู่คีย์–ค่าออกมาจากบันทึกนั้น: ไม่ใช่เครื่องมือด้านเรขาคณิต และไม่ใช่เครื่องมือประมวลผลภาพ แม้จะอยู่ในชุดเครื่องมือทางทันตกรรม

ยังไม่ตีพิมพ์ CNE_CLI ไม่มี conda: Python ของ Slicer บรรณานุกรม

คำเตือนเรื่องขอบเขต CNE ไม่เหมือน AutoCrop3D และ AutoMatrix: มันไม่ใช่เครื่องมือเสริมด้านเรขาคณิต ไม่แตะวอลุ่ม ไม่แตะเมช ไม่แตะ พิกัดใดเลย มันเป็นโมดูลการอนุมานด้วย LLM ที่อ่านบันทึกทางคลินิก แบบข้อความอิสระ แล้วเขียนออกมาเป็นคู่คีย์–ค่า แกนกลางของโมดูลคือโมเดล GGUF แบบ quantise ที่โหลดด้วย llama-cpp-python ภายใน Python ของ Slicer

0. ตัวย่อ

ที่เก็บโค้ดไม่เคยเขียนชื่อเต็มของตัวย่อนี้ในเอกสารใดเลย: README ไม่มีหัวข้อ CNE และไม่ได้บันทึกถึง MedX ที่ CNE เข้ามาแทนที่อีกต่อไปแล้วเช่นกัน ไม่มีชื่อใดปรากฏอยู่ในนั้น ข้อความช่วยเหลือของโมดูล (CNE.py:157) ระบุเพียงว่า "This tool helps to create summaries of clinical notes"

มีบรรทัด log เพียงสองบรรทัด และมีเพียงสองบรรทัดนั้น ที่บอกคำเต็มของตัวย่อ: logger.info("CNE (Clinical Notes Extraction)") (CNE.py:342 และ CNE.py:663) และ CLI ประกาศชื่อเดียวกันนี้ต่อตัวควบคุมของ Slicer: <filter-name>Clinical Notes Extraction</filter-name> (CNE_CLI.py:93) CNE = Clinical Notes Extraction ยืนยันได้จากโค้ด และไม่มีที่อื่นยืนยัน

1. ตำแหน่งใน pipeline

โมดูลปลายทาง ไม่มีใครเรียกมัน และมันก็ไม่เรียกโมดูลอื่นใดในที่เก็บโค้ด ประกาศไว้ใน CMakeLists.txt:50-52 (CNE, CNE_CLI, CNE_Dashboard)

  • temperature=0.1 และไม่มี seed: เอาต์พุตเกือบจะเป็นค่าเดิมทุกครั้ง แต่ ทำซ้ำให้เหมือนเดิมทุกตัวอักษรไม่ได้

ไม่มีการป้องกันเรื่องความยาว n_ctx เท่ากับ 6144 (TMJ) หรือ 2048 (Ortho) และ max_tokens=500 ถูกหักออกจากงบนั้น บันทึกที่เกินงบจะทำให้ llama.cpp โยนข้อผิดพลาด ข้อยกเว้นถูกจับเป็นรายไฟล์ บันทึกลง log และไฟล์นั้น ถูกเพิ่มเข้า failed_files งบของ Ortho คับแคบเป็นพิเศษ: เหลือบันทึกที่ใช้ได้ราว 1,500 token บันทึกทดสอบ TMJ_note1.txt ยาวราว 4,400 ตัวอักษร ซึ่งผ่านได้ในโหมด TMJ

  • การโหลดโมเดลถูกห่อด้วยการเปลี่ยนทาง stderr ไปที่ /dev/null ด้วย os.dup2 (CNE_CLI.py:159) เพื่อ กลบข้อความรบกวนของ llama.cpp ซึ่งไม่เช่นนั้นจะไปปนในช่องสัญญาณข้อผิดพลาดที่ Slicer ตีความว่า CLI ล้มเหลว

7. การประมวลผลคำตอบภายหลัง

คาดหวังว่าโมเดลจะตอบเป็น JSON แต่โค้ดไม่ได้บังคับ (ไม่มี response_format ไม่มีไวยากรณ์ GBNF) และเพียงคุ้ยหา JSON ออกจากข้อความ (CNE_CLI.py:209-214):

start_idx = ai_response.find('{')
end_idx   = ai_response.rfind('}') + 1
data = json.loads(ai_response[start_idx:end_idx])
if "extraction" in data:
    data = data["extraction"]
for key, value in data.items():
    formatted_response += f"{key} : {value}\n"

กล่าวคือ: จากปีกกาเปิดอันแรกถึงปีกกาปิดอันสุดท้าย แกะชั้น extraction ออกถ้ามี แล้วแบนให้เป็นบรรทัด key : value หาก การแปลงล้มเหลวหรือไม่มีปีกกาเลย คำตอบดิบของโมเดลจะถูกเขียนลงไป ตามที่เป็น ไฟล์เอาต์พุตไม่บอกว่าเกิดกรณีใดจากสองกรณีนี้

ข้อควรระวัง

ผลที่ตามมา: การตัดช่วงอย่างง่ายด้วย find('{')…rfind('}') พังทันทีที่ คำตอบมีอ็อบเจกต์ JSON มากกว่าหนึ่งชุด และค่าที่ซ้อนกัน (list, dict) จะ ถูกเขียนลงไฟล์ข้อความด้วย repr ของ Python

8. เอาต์พุต

ไฟล์ข้อความหนึ่งไฟล์ต่อบันทึกอินพุตหนึ่งฉบับ ในโฟลเดอร์เอาต์พุต:

Extraction_<note name without extension>.txt

เนื้อหา: บรรทัด key : value หรือคำตอบดิบของโมเดลหากการแยกวิเคราะห์ล้มเหลว ไม่มี CSV ไม่มี json และไม่มีการรวมค่ารายผู้ป่วยจากการสกัดนี้เอง: ตารางและรูปมาจากปุ่ม Dashboard (§8.1) ซึ่งอ่านไฟล์เหล่านี้ภายหลัง

โฟลเดอร์เอาต์พุตถูกสร้างด้วย os.makedirs(..., exist_ok=True) ฝั่งวิดเจ็ต (CNE.py:613)

8.1 Dashboard

ครึ่ง "Dashboard" ของ MedX ถูกพอร์ตเมื่อ 2026-10-12 ดังนั้นข้อความก่อนหน้าของหน้านี้ที่ว่า "ไม่ได้ถูกนำมาด้วย" จึงใช้ไม่ได้อีกต่อไป อ่านจากโค้ดได้ดังนี้:

  • ตัวกระตุ้น ปุ่ม Dashboard (dashboardButton ใน CNE.ui เชื่อมที่ CNE.py:234) รัน onDashboardButton() (CNE.py:365) มันตรวจการพึ่งพา ปฏิเสธที่จะรันถ้าไม่มีโฟลเดอร์เอาต์พุต และเปิด CNE_Dashboard ผ่าน CNELogic.dashboard() (CNE.py:629) โดยใช้โฟลเดอร์เอาต์พุตเป็นทั้งอินพุตและเอาต์พุต ไม่ใช้โมเดลและไม่มีการดาวน์โหลด
  • การอ่าน read_summaries() (display_figure.py:23) เก็บเฉพาะไฟล์ Extraction_*.txt ในโฟลเดอร์ รหัสผู้ป่วยคือชื่อบันทึกที่ตัดคำนำหน้าออก process_summaries() (display_figure.py:135) เติมพจนานุกรม 54 คีย์ที่กำหนดค่าเริ่มต้นโดย initialize_key_value_summary() (dashboard_utils.py:332) และแปลงฟิลด์ตัวเลขหกฟิลด์
  • คำนวณ ไม่ใช่ทำนาย แต่ละแผงเป็นการรวมค่าแบบกำหนดแน่นอน คำนวณ ใน dashboard_utils.py (กลุ่มอายุ ค่าเฉลี่ยและ SD ของคะแนนความเจ็บปวด การอ้าปากสูงสุดที่แยกจากสตริงอย่าง "33 mm" ตำแหน่งปวดศีรษะและปวดข้อต่อจากรายการคำพ้องความหมาย การเคลื่อนของหมอนรองข้อต่อซ้ายและขวา ระดับความเจ็บปวดของกล้ามเนื้อ) รูปถูกวาดโดย generate_dashboard_figure() (display_figure.py:164)
  • เอาต์พุต dashboard.png และ patient_data.csv (display_figure.py:714-716) และไฟล์ที่สาม dashboard_full_dataframe.csv (display_figure.py:183) ซึ่งเขียนก่อนวาดรูป
  • ล้มเหลวอย่างเสียงดังเมื่อสคีมาไม่ตรงกัน report_field_coverage() (display_figure.py:668) บันทึกคีย์ที่คาดหวังแต่ไม่มีค่า และ show_dashboard() (display_figure.py:694) ยกข้อผิดพลาดหากไม่มีคีย์ใดมีค่า หรือหากโฟลเดอร์ไม่มี Extraction_*.txt
ข้อควรระวัง

dashboard นี้เป็น dashboard ของ TMJ คีย์ที่คาดหวังคือความรุนแรงของอาการปวดศีรษะ ข้อต่อมีเสียงคลิก การเคลื่อนของหมอนรองข้อต่อ การอ้าปากสูงสุด ความผิดปกติของการนอน และอื่น ๆ ทำนองเดียวกัน (dashboard_utils.py:339-396) คีย์เหล่านี้คือคีย์ที่โมเดล TMJ ควรคืนมา ไม่มีสิ่งใดในที่เก็บโค้ดบอกว่าโมเดล Ortho เขียนคีย์เหล่านี้ และโหมด Ortho ไม่มีคำสั่งที่บังคับให้เป็นเช่นนั้น กับผลสกัดของ Ortho การตรวจความครอบคลุมน่าจะหยุดการรันด้วยข้อผิดพลาด "keys do not match" นี่เป็นข้อสรุปจากรายการคีย์ ไม่ได้ทดลองรันกับเอาต์พุตของ Ortho คีย์เองถูกเลือกโดยโมเดล ไม่ใช่โดยโค้ด (docstring ของ report_field_coverage, display_figure.py:668-679)

11. ข้อควรระวังและจุดเปราะบาง

  • Dashboard คาดหวังสคีมาของ TMJ (§8.1)
  • โฟลเดอร์เอาต์พุตของไฟล์ทดสอบ copyTestFiles() (CNE.py:454) เคยใส่พาธที่ไม่มีอยู่จริงลงในช่องเอาต์พุต ตอนนี้มันสร้างโฟลเดอร์เอาต์พุต (CNE.py:508) คัดลอกบันทึกอีกครั้งในทุกการเรียกโดยไม่ลบโฟลเดอร์ (dirs_exist_ok=True, CNE.py:505) และไม่แตะโฟลเดอร์เอาต์พุตที่ผู้ใช้เลือกไว้แล้ว (CNE.py:328-330) Resources/testfiles/ ยังคงมีเพียงโฟลเดอร์ input_ สองโฟลเดอร์
  • การสแกนที่ไม่ไล่ลงโฟลเดอร์ย่อย ของโฟลเดอร์อินพุต (§5)
  • ไม่มีการจำกัดความยาว ก่อนเรียกโมเดล: บันทึกที่ยาวเกินจะล้มเหลว ทั้งฉบับ แทนที่จะถูกแบ่งเป็นช่วง ขณะที่ MedX แบ่งเป็นช่วง (§6) นี่คือ การถอยหลังในแง่หน้าที่ของสิ่งที่มาแทน
  • โหมด Ortho ไม่ส่งคำสั่งระบบ (§6): ถ้าโมเดลไม่ใช่ตัวที่ คาดไว้ ก็ไม่มีเหตุใดที่เอาต์พุตจะเป็น JSON เลย
  • ไม่มีการบังคับรูปแบบเอาต์พุต: ไม่มีไวยากรณ์ GBNF และไม่มี response_format ทั้งที่ llama.cpp มีให้ทั้งสองอย่าง การประมวลผลภายหลังจึงเป็น การคุ้ยหาแบบใช้วิธีเดาเอา (§7)
  • radio button ไม่ได้ตั้งเป็น TMJ หรือ Ortho → notesType = "" (CNE.py:427) → ใน getModelPath ตัวแปร repo_id ไม่เคยถูก กำหนดค่า และ UnboundLocalError ปรากฏเป็นข้อความ "Failed to load model" กรณีนี้ ไม่ควรเกิด (มี setExclusive(True) และค่าเริ่มต้นเป็น TMJ) แต่ไม่มีอะไร ขัดไว้
  • การใช้ตัวพิมพ์ไม่สอดคล้องกัน: notesType == "TMJ" กำหนดค่า n_ctx ขณะที่ notesType.upper() == "TMJ" กำหนดคำสั่ง หาก notesType เป็นตัวพิมพ์เล็ก จะได้คำสั่งของ TMJ พร้อมบริบทขนาด 2048
  • ไม่มีร่องรอยที่มา: ไฟล์ Extraction_*.txt ไม่ระบุทั้ง โมเดล รุ่นของโมเดล และวันที่ การรันสองครั้งด้วยโมเดลที่ต่างกันจะ ให้ไฟล์ที่แยกจากกันไม่ออก
  • PHI: ไม่มีอะไรลบข้อมูลระบุตัวตน ไม่มีอะไรเตือน บันทึกถูกอ่านแบบไม่ปิดบัง แล้วส่งผ่านโมเดลในเครื่อง (จึงไม่มีการรั่วออกทางเครือข่าย, นั่นคือ เกราะป้องกันเพียงอย่างเดียว และเป็นผลจากโครงสร้างมากกว่าความตั้งใจ)
  • เมทาดาทาของ CLI ยังเป็นค่าเริ่มต้นจากเทมเพลต: CNE_CLI.xml ยังเขียนว่า "Apply a Gaussian blur to an image" ระบุผู้เขียนโมดูลว่า "Andras Lasso (PerkLab)" และค่า <index> เป็น 0, 2, 3, 4, ขาด index 1 ไป
  • onCliProgress (CNE.py:651) อ่าน caller.GetProgress() แล้วไม่ทำอะไรกับค่านั้นเลย และยังไม่ได้ถูกเชื่อมกับ observer ใด ๆ ด้วย เป็น โค้ดที่ไม่ถูกใช้งาน ความคืบหน้าจริงส่งผ่าน tag <filter-progress> ของ CLI ซึ่ง qSlicerCLIProgressBar เป็นตัวอ่าน
