CNE

โมดูลการอนุมานด้วยโมเดลภาษา (LLM) ที่อ่านบันทึกทางคลินิกแบบข้อความอิสระ แล้วสกัดคู่คีย์–ค่าออกมาจากบันทึกนั้น — ไม่ใช่เครื่องมือด้านเรขาคณิต และไม่ใช่เครื่องมือประมวลผลภาพ แม้จะอยู่ในชุดเครื่องมือทางทันตกรรม

ยังไม่ตีพิมพ์ CNE_CLI ไม่มี conda — Python ของ Slicer บรรณานุกรม

คำเตือนเรื่องขอบเขต CNE ไม่เหมือน AutoCrop3D และ AutoMatrix: มันไม่ใช่เครื่องมือเสริมด้านเรขาคณิต ไม่แตะวอลุ่ม ไม่แตะเมช ไม่แตะ พิกัดใดเลย มันเป็นโมดูลการอนุมานด้วย LLM ที่อ่านบันทึกทางคลินิก แบบข้อความอิสระ แล้วเขียนออกมาเป็นคู่คีย์–ค่า แกนกลางของโมดูลคือโมเดล GGUF แบบ quantise ที่โหลดด้วย llama-cpp-python ภายใน Python ของ Slicer

0. ตัวย่อ

รีโพสิทอรีไม่เคยขยายตัวย่อนี้ไว้ในเอกสารใดเลย: README ไม่มีหัวข้อ CNE (ยังคงอธิบาย MedX ซึ่ง CNE เข้ามาแทน ดู CMakeLists.txt:42 "Replaced by CNE") ข้อความช่วยเหลือของโมดูล (CNE.py:147) บอกเพียงว่า "This tool helps to create summaries of clinical notes"

มีบรรทัด log เพียงสองบรรทัด และมีเพียงสองบรรทัดนั้น ที่บอกคำเต็มของตัวย่อ: logger.info("CNE (Clinical Notes Extraction)") (CNE.py:329 และ CNE.py:606) และ CLI ประกาศชื่อเดียวกันนี้ต่อตัวควบคุมของ Slicer: <filter-name>Clinical Notes Extraction</filter-name> (CNE_CLI.py:91) CNE = Clinical Notes Extraction ยืนยันได้จากโค้ด และไม่มีที่อื่นยืนยัน

CLI ทดสอบการ import ทั้งสามรายการอีกครั้งเมื่อเริ่มทำงาน และเรียก sys.exit(1) หากขาด รายการใด (CNE_CLI.py:99-115) — ซ้ำซ้อน แต่ไม่เป็นโทษ เพราะ CLI ใช้อินเทอร์พรีเตอร์ร่วมกับ widget

ข้อสังเกต:

ข้อควรระวัง

โหมด Ortho ไม่ส่งคำสั่งใดเลย มีเพียงบันทึกดิบที่ถูกส่งออกไปเป็น ข้อความของผู้ใช้ และเป็นการปรับละเอียดของโมเดล Llama-Ortho เองที่ควรจะ แบกงานนี้ไว้ ส่วนโหมด TMJ ยังคงเก็บคำสั่งที่สืบทอดมาจาก MedX

  • create_chat_completion ใช้ chat template ที่ฝังอยู่ในไฟล์ GGUF โมเดลทั้งสองติด tag conversational บน Hugging Face แสดงว่า template มีอยู่จริง แต่มองไม่เห็นและควบคุมไม่ได้จากรีโพสิทอรี
  • temperature=0.1 และไม่มี seed: เอาต์พุตเกือบจะเป็นค่าเดิมทุกครั้ง แต่ ทำซ้ำให้เหมือนเดิมทุกตัวอักษรไม่ได้
ข้อควรระวัง

ไม่มีการป้องกันเรื่องความยาว n_ctx เท่ากับ 6144 (TMJ) หรือ 2048 (Ortho) และ max_tokens=500 ถูกหักออกจากงบนั้น บันทึกที่เกินงบจะทำให้ llama.cpp โยนข้อผิดพลาด ข้อยกเว้นถูกจับเป็นรายไฟล์ บันทึกลง log และไฟล์นั้น ถูกเพิ่มเข้า failed_files งบของ Ortho คับแคบเป็นพิเศษ: เหลือบันทึกที่ใช้ได้ราว 1,500 token บันทึกทดสอบ TMJ_note1.txt ยาวราว 4,400 ตัวอักษร ซึ่งผ่านได้ในโหมด TMJ

  • การโหลดโมเดลถูกห่อด้วยการเปลี่ยนทาง stderr ไปที่ /dev/null ด้วย os.dup2 (CNE_CLI.py:155) เพื่อ กลบข้อความรบกวนของ llama.cpp ซึ่งไม่เช่นนั้นจะไปปนในช่องสัญญาณข้อผิดพลาดที่ Slicer ตีความว่า CLI ล้มเหลว

7. การประมวลผลคำตอบภายหลัง

คาดหวังว่าโมเดลจะตอบเป็น JSON แต่โค้ดไม่ได้บังคับ (ไม่มี response_format ไม่มีไวยากรณ์ GBNF) และเพียงคุ้ยหา JSON ออกจากข้อความ (CNE_CLI.py:207):

end_idx   = ai_response.rfind('}') + 1

กล่าวคือ: จากปีกกาเปิดอันแรกถึงปีกกาปิดอันสุดท้าย แกะชั้น extraction ออกถ้ามี แล้วแบนให้เป็นบรรทัด key : value หาก การแปลงล้มเหลวหรือไม่มีปีกกาเลย คำตอบดิบของโมเดลจะถูกเขียนลงไป ตามที่เป็น ไฟล์เอาต์พุตไม่บอกว่าเกิดกรณีใดจากสองกรณีนี้

ข้อควรระวัง

ผลที่ตามมา: การตัดช่วงอย่างง่ายด้วย find('{')…rfind('}') พังทันทีที่ คำตอบมีอ็อบเจกต์ JSON มากกว่าหนึ่งชุด และค่าที่ซ้อนกัน (list, dict) จะ ถูกเขียนลงไฟล์ข้อความด้วย repr ของ Python

11. ข้อควรระวังและจุดเปราะบาง

  • โมเดล Ortho ดาวน์โหลดไม่ได้: ชื่อไฟล์ผิด HTTP 404 (§4) วิธีแก้: model-q4_0.gguf → model-q4_k_m.gguf
  • โฟลเดอร์เอาต์พุตของไฟล์ทดสอบไม่มีอยู่จริง copyTestFiles() (CNE.py:409) คัดลอก input_<type> และ output_<type> แต่ Resources/testfiles/ มีเพียงโฟลเดอร์ input_ สองโฟลเดอร์ การ shutil.copytree ของโฟลเดอร์ เอาต์พุตจึงถูกข้ามพร้อมคำเตือน และหน้าจอลงเอยด้วยเส้นทางเอาต์พุต ที่กรอกไว้แต่ยังไม่มีอยู่
  • การสแกนที่ไม่ไล่ลงโฟลเดอร์ย่อย ของโฟลเดอร์อินพุต (§5)
  • ไม่มีการจำกัดความยาว ก่อนเรียกโมเดล: บันทึกที่ยาวเกินจะล้มเหลว ทั้งฉบับ แทนที่จะถูกแบ่งเป็นช่วง ขณะที่ MedX แบ่งเป็นช่วง (§6) นี่คือ การถอยหลังในแง่หน้าที่ของสิ่งที่มาแทน
  • โหมด Ortho ไม่ส่งคำสั่งระบบ (§6): ถ้าโมเดลไม่ใช่ตัวที่ คาดไว้ ก็ไม่มีเหตุใดที่เอาต์พุตจะเป็น JSON เลย
  • ไม่มีการบังคับรูปแบบเอาต์พุต: ไม่มีไวยากรณ์ GBNF และไม่มี response_format ทั้งที่ llama.cpp มีให้ทั้งสองอย่าง การประมวลผลภายหลังจึงเป็น การคุ้ยหาแบบใช้วิธีเดาเอา (§7)
  • radio button ไม่ได้ตั้งเป็น TMJ หรือ Ortho → notesType = "" (CNE.py:382) → ใน getModelPath ตัวแปร repo_id ไม่เคยถูก กำหนดค่า และ UnboundLocalError ปรากฏเป็นข้อความ "Failed to load model" กรณีนี้ ไม่ควรเกิด (มี setExclusive(True) และค่าเริ่มต้นเป็น TMJ) แต่ไม่มีอะไร ขัดไว้
  • การใช้ตัวพิมพ์ไม่สอดคล้องกัน: notesType == "TMJ" กำหนดค่า n_ctx ขณะที่ notesType.upper() == "TMJ" กำหนดคำสั่ง หาก notesType เป็นตัวพิมพ์เล็ก จะได้คำสั่งของ TMJ พร้อมบริบทขนาด 2048
  • ไม่มีร่องรอยที่มา: ไฟล์ Extraction_*.txt ไม่ระบุทั้ง โมเดล รุ่นของโมเดล และวันที่ การรันสองครั้งด้วยโมเดลที่ต่างกันจะ ให้ไฟล์ที่แยกจากกันไม่ออก
  • PHI: ไม่มีอะไรลบข้อมูลระบุตัวตน ไม่มีอะไรเตือน บันทึกถูกอ่านแบบไม่ปิดบัง แล้วส่งผ่านโมเดลในเครื่อง (จึงไม่มีการรั่วออกทางเครือข่าย — นั่นคือ เกราะป้องกันเพียงอย่างเดียว และเป็นผลจากโครงสร้างมากกว่าความตั้งใจ)
  • เมทาดาทาของ CLI ยังเป็นค่าเริ่มต้นจากเทมเพลต: CNE_CLI.xml ยังเขียนว่า "Apply a Gaussian blur to an image" ระบุผู้เขียนโมดูลว่า "Andras Lasso (PerkLab)" และค่า <index> เป็น 0, 2, 3, 4 — ขาด index 1 ไป
  • onCliProgress (CNE.py:594) อ่าน caller.GetProgress() แล้วไม่ทำอะไรกับค่านั้นเลย และยังไม่ได้ถูกเชื่อมกับ observer ใด ๆ ด้วย เป็น โค้ดที่ไม่ถูกใช้งาน ความคืบหน้าจริงส่งผ่าน tag <filter-progress> ของ CLI ซึ่ง qSlicerCLIProgressBar เป็นตัวอ่าน

12. เอกสารอ้างอิง

รีโพสิทอรีไม่ได้อ้างงานตีพิมพ์ใดสำหรับ CNE และรีโพสิทอรี dcbia/* ทั้งสองบน Hugging Face ก็เผยแพร่โดยไม่มี model card และไม่มี เอกสารอ้างอิง ระเบียบวิธีการปรับละเอียด คลังข้อมูลที่กำกับไว้สำหรับ TMJ/Ortho และ การประเมินผล ระบุไม่ได้จากรีโพสิทอรี

สิ่งที่ตรวจสอบได้:

  • สายสืบทอดจาก MedX → CNE ซึ่งมีเอกสารยืนยันเพียง CMakeLists.txt:42 และหัวข้อ MedX ใน README.md:425 ซึ่งยังอธิบาย pipeline แบบ BART เดิมและ dashboard ที่หายไปแล้ว
  • โมเดลพื้นฐาน: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct
  • รีโพสิทอรีของโมเดลที่ปรับละเอียดแล้ว: dcbia/Qwen-2.5-7B-Instruct-TMJ, dcbia/Meta-Llama-3.1-8B-Instruct-Ortho
  • เอนจิน: llama-cpp-python, llama.cpp (รูปแบบ GGUF, quantisation Q4_K_M)
  • SlicerAutomatedDentalTools
