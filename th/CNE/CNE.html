CNE

CNE อ่านบันทึกทางคลินิกแบบข้อความอิสระ และเขียนข้อเท็จจริงที่พบ (อาการ การวินิจฉัย คะแนน) เป็นรายการบรรทัด field : value เป็นโมดูลโมเดลภาษา: ไม่แตะภาพและไม่แตะเมช หน้านี้อธิบายไปป์ไลน์ของโมดูล Slicer แบบ legacy ทีละขั้น รายละเอียดของโค้ดอยู่ในหน้าโค้ด

ยังไม่ตีพิมพ์ VISOR CNE_CLI ไม่ใช้ conda: Python ของ Slicer บรรณานุกรม โค้ด (นักพัฒนา) คู่มือ

CNE ไม่ใช่เครื่องมือเรขาคณิต: อ่านข้อความและเขียนข้อความ โมเดลภาษาที่ quantise (รูปแบบ GGUF) ถูกโหลดโดย llama-cpp-python ภายใน Python ของ Slicer เอง หน้านี้อธิบายโมดูล Slicer แบบ legacy (SlicerAutomatedDentalTools ที่ 3c67957, 2026-10-26) พอร์ต VISOR รันเครื่องมือเดียวกันบนเซิร์ฟเวอร์และมีหน้าของตัวเอง ผลที่ตามมาข้อหนึ่งสำคัญก่อนอ่านต่อ: เมื่อหน้านี้บอกว่าโมเดลรันในเครื่อง นั่นจริงเฉพาะโมดูล legacy เท่านั้น กับ VISOR ข้อความบันทึกจะถูกส่งไปยังเซิร์ฟเวอร์ (ปัญหาที่ทราบใน VISOR)

ภาพรวม: อะไรเข้า อะไรออก

CNE, legacy
อินพุตโฟลเดอร์บันทึก (.txt, .pdf, .docx) ไม่ค้นลงโฟลเดอร์ย่อย และตัวเลือกระหว่าง TMJ กับ Ortho
โมเดลQwen 2.5 7B (TMJ) หรือ Llama 3.1 8B (Ortho) ที่ quantise แล้ว ดาวน์โหลดเมื่อใช้ครั้งแรก และรันบนตัวประมวลผล
เอาต์พุตไฟล์ข้อความหนึ่งไฟล์ต่อบันทึก บรรทัด field : value ในโฟลเดอร์ผลลัพธ์
ไม่บังคับปุ่ม Dashboard ที่อ่านไฟล์เหล่านั้นและวาดภาพกับตาราง CSV สองตาราง

0. ตัวย่อ

CNE ย่อมาจาก Clinical Notes Extraction รีโพซิทอรีไม่เคยบอกไว้ในเอกสาร: มีเพียงสองบรรทัดล็อกและชื่อที่เครื่องมือประกาศให้ Slicer ที่ให้ความหมายเต็ม

ในโค้ดบรรทัดล็อกและชื่อ filter ที่ยืนยันความหมายเต็ม

1. ตำแหน่งในไปป์ไลน์

CNE เป็นโมดูลปลายทาง: ไม่มีอะไรเรียกมัน และมันไม่เรียกอะไร มันมาแทนครึ่งการสรุปความของ MedX ซึ่งถูกปิดจาก build ในเดือนมีนาคม 2026 พร้อมความเห็น “Replaced by CNE” MedX เองออกจากต้นไม้ไฟล์เมื่อ 2026-09-17 และอยู่บนบรานช์ archive/medx ครึ่ง Dashboard ถูกพอร์ตเข้า CNE เมื่อ 2026-10-12 (ส่วน 8.1) VISOR ไม่มี Dashboard

เมื่อเทียบกับตัวสรุปของ MedX ที่มันมาแทน:

  • เอนจินและโมเดล: llama.cpp และ Llama หรือ Qwen ที่ quantise แทน PyTorch และโมเดล BART
  • ไม่แบ่งชิ้น: บันทึกทั้งฉบับไปที่โมเดลในข้อความเดียว ขณะที่ MedX ตัดเป็นชิ้น
  • การถอดรหัส: temperature 0.1 และไม่เกิน 500 โทเค็น แทน beam search พร้อมการสุ่ม
  • ไม่มีการรวมต่อผู้ป่วย: หนึ่งไฟล์ให้หนึ่งผลลัพธ์

ประโยคคำสั่งเดียวของโหมด TMJ เป็นประโยคเดียวกับที่ MedX ใช้ (MedX วางไว้หน้าข้อความ CNE ส่งเป็นข้อความระบบแยกต่างหาก)

ในโค้ดไฟล์ build ใดประกาศมัน การสำรวจที่แก้ไขแล้ว ตารางเปรียบเทียบ MedX แบบเต็ม

2. ไฟล์ที่เกี่ยวข้อง

สี่ส่วน: วิดเจ็ต (dependency การดาวน์โหลดโมเดล การเริ่มงาน ปุ่ม Dashboard) งานบรรทัดคำสั่งที่อ่านบันทึกและเรียกโมเดล งาน Dashboard พร้อมไฟล์ช่วยสองไฟล์ และไฟล์อินเทอร์เฟซ มีบันทึกตัวอย่างสี่ฉบับมากับรีโพซิทอรี ไม่มีสภาพแวดล้อม conda: ทุกอย่างรันใน Python ของ Slicer

ในโค้ดตารางไฟล์พร้อมบทบาทและที่ที่แต่ละไฟล์รัน

3. Dependency ที่ติดตั้งตามต้องการ

เมื่อคลิก Apply โมดูลตรวจแพ็กเกจห้าตัว (ตัวผูก llama.cpp ตัวอ่าน PDF ตัวอ่าน Word ไลบรารีวาดกราฟ และไลบรารีตาราง) และหลังการยืนยัน จะติดตั้งตัวที่ขาดลงใน Python ของ Slicer wheel index ที่ชี้ไปคือbuild แบบตัวประมวลผลอย่างเดียว งานยังขอเลเยอร์ GPU ซึ่งไม่มีผลกับ build นั้น: ในทางปฏิบัติ inference รันบนตัวประมวลผล และโมเดลขนาด 7 ถึง 8 พันล้านพารามิเตอร์ช้าบนตัวประมวลผล (ไม่ได้วัดเวลาต่อบันทึกสำหรับหน้านี้)

ในโค้ดการนำเข้าทั้งห้า แฟลกการติดตั้ง การ override คอมไพเลอร์ คำขอ GPU

4. โมเดล

ไม่มีน้ำหนักมากับรีโพซิทอรี การรันครั้งแรกดาวน์โหลดโมเดลของโหมดที่เลือกลงโฟลเดอร์ Documents

โหมดโมเดลดาวน์โหลดContext window
TMJQwen 2.5 7B Instruct, fine-tune แล้ว (DCBIA-OrthoLab)ประมาณ 4.4 GB6144 โทเค็น
OrthoLlama 3.1 8B Instruct, fine-tune แล้ว (DCBIA-OrthoLab)ประมาณ 4.9 GB2048 โทเค็น

การดาวน์โหลด Ortho เคยล้มเหลวเพราะขอไฟล์ที่ไม่มีอยู่ ซึ่งแก้แล้ว (รายละเอียด) รีโพซิทอรี Hugging Face ทั้งสองแห่งตอนนี้มี model card ที่ระบุใบอนุญาต โมเดลฐาน และวิธี fine-tune และบอกว่าบันทึกที่ใช้ฝึกเป็นข้อมูลผู้ป่วยที่ไม่เผยแพร่ ทั้งสองการ์ดไม่รายงานการประเมินผล

ในโค้ดid ของรีโพซิทอรี ชื่อไฟล์ URL และการตรวจที่ทำกับมัน

5. อินพุตและการประมวลผลเบื้องต้น

โมดูลมองหาไฟล์ .txt, .pdf และ .docx ในโฟลเดอร์ที่เลือกเท่านั้น: ไม่ค้นโฟลเดอร์ย่อย ต่างจากโมดูลอื่นทุกตัว ดังนั้นโฟลเดอร์ที่จัดตามผู้ป่วยจะไม่ให้ผลอะไรเลย ข้อความถูกดึงจาก PDF ทีละหน้าโดยไม่มี OCR (PDF ที่เป็นภาพสแกนว่างเปล่า) จากไฟล์ Word ทีละย่อหน้า (ตารางหายไป) และจากไฟล์ข้อความเป็น UTF-8 (การเข้ารหัสอื่นทำให้บันทึกนั้นล้มเหลว)

ไม่มีอะไรทำให้บันทึกไม่ระบุตัวตน บันทึกทดสอบในรีโพซิทอรีถูกใส่นามแฝงด้วยมือ และโมดูล MedicalDataAnonymizer ที่แยกต่างหากไม่ได้ต่อเข้ากับ CNE

ในโค้ดตัวดึงข้อความทั้งสาม ตารางการแทนที่ และการเรียก glob

6. Inference

โมเดลถูกเรียกหนึ่งครั้งต่อบันทึก ไม่แบ่งชิ้น ในโหมด TMJ บันทึกมีประโยคคำสั่งนำหน้า ในโหมด Ortho บันทึกไปเดี่ยว ๆ เพราะโมเดล Ortho ควรแบกงานนี้ไว้ใน fine-tuning ของมัน

คำตอบถูกจำกัดที่ 500 โทเค็น และ temperature เป็น 0.1 โดยไม่มี seed ผลลัพธ์จึงเกือบแน่นอนแต่ทำซ้ำได้ไม่เป๊ะ บันทึกที่ทำให้เหลือที่ว่างไม่ถึง 500 โทเค็นไม่ทำให้เกิดข้อผิดพลาด: เอนจินทำให้คำตอบสั้นลงเท่าที่เหลือ JSON จึงถูกตัดและข้อความดิบถูกเขียน (§7) มีเพียง prompt ที่เต็มทั้ง window เท่านั้นที่ทำให้เอนจินเกิดข้อผิดพลาด ข้อผิดพลาดถูกจับสำหรับบันทึกนั้น ถูกล็อก และไฟล์ถูกนับว่าล้มเหลว chat template ของโมเดลเองถูกนำมาใช้ และมองไม่เห็นหรือเปลี่ยนไม่ได้จากรีโพซิทอรี

ในโค้ดการเรียก ข้อความ TMJ และ Ortho การเปลี่ยนทิศทาง stderr

7. การประมวลผลหลังได้คำตอบ

ไม่มีอะไรบังคับให้โมเดลให้ JSON โมดูลจึงงัดมันออกจากคำตอบ

ถ้าชิ้นที่ตัดมีตัวห่อชื่อ extraction ระดับนั้นจะถูกเอาออก จากนั้นแต่ละฟิลด์ถูกเขียนเป็นบรรทัด field : value และค่าซ้อนปรากฏในรูปแทนแบบ Python ถ้าอ่านชิ้นที่ตัดไม่ได้ หรือคำตอบไม่มีวงเล็บปีกกาเลย คำตอบดิบของโมเดลจะถูกเขียนตามเดิม และไฟล์ไม่ได้บอกว่าเกิดกรณีใด

ในโค้ดโค้ดที่ตัด และพฤติกรรมของ VISOR ที่แก้บางส่วน

8. เอาต์พุต

ไฟล์ข้อความหนึ่งไฟล์ต่อบันทึก Extraction_<note name>.txt เก็บบรรทัด field : value หรือคำตอบดิบ ไม่มี CSV ไม่มี JSON และไม่มีการรวมต่อผู้ป่วยจากตัว extraction เอง

ในโค้ดการตั้งชื่อไฟล์ การสร้างโฟลเดอร์ผลลัพธ์

8.1 Dashboard

ปุ่มข้างปุ่ม Run เริ่มงานที่สองซึ่งอ่านไฟล์ Extraction_*.txt ของโฟลเดอร์ผลลัพธ์ มันเติมตารางที่มี 56 คีย์ (id ผู้ป่วยและ 55 ฟิลด์ที่โมเดลถูกคาดหวังให้คืน) แปลงหกฟิลด์เป็นตัวเลข และคำนวณสรุปแบบกำหนดแน่นอนหนึ่งชุดต่อแผงของภาพ: กลุ่มอายุ ค่าเฉลี่ยและการกระจายของคะแนนความปวด การอ้าปากสูงสุด ตำแหน่งที่ปวดศีรษะและปวดข้อต่อ disc displacement ความปวดกล้ามเนื้อ มันเขียน dashboard.png และตาราง CSV สองตาราง และหยุดด้วยข้อผิดพลาดเมื่อไฟล์ไม่มีฟิลด์ที่คาดไว้ ไม่เกี่ยวกับโมเดลและไม่มีการดาวน์โหลด

เป็น Dashboard ของ TMJ: ฟิลด์ที่คาดไว้คือฟิลด์ที่โมเดล TMJ ถูกคาดหวังให้คืน ไม่มีอะไรบอกว่าโมเดล Ortho เขียนมัน ดังนั้นกับ extraction ของ Ortho การตรวจความครอบคลุมน่าจะหยุดการรัน (ข้อสันนิษฐานจากรายการฟิลด์ ไม่ได้รัน)

ในโค้ดตัวกระตุ้น ตัวอ่าน ฟังก์ชันรวมค่า และการตรวจความครอบคลุม

9. ทำนายหรือคำนวณ

ขั้นตอนลักษณะ
การดึงข้อความจาก PDF และ Wordคำนวณ PyMuPDF และ python-docx
การทำความสะอาดตัวอักษรคำนวณ ตารางตายตัวของการแทนที่เจ็ดรายการ
การดึงฟิลด์ทำนาย โมเดลภาษา Qwen 2.5 7B TMJ หรือ Llama 3.1 8B Ortho ในรูปแบบ GGUF ที่ quantise
การจัดรูปแบบคำนวณ การตัด การอ่าน JSON ลูปแผ่ค่า

เนื้อหาทางคลินิกทั้งหมดของผลลัพธ์มาจากโมเดล ไม่มีกฎ ไม่มีพจนานุกรมศัพท์ และไม่มีการตรวจสกีมา: โมเดลเขียนอะไร สิ่งนั้นก็ถูกบันทึก

ในโค้ดตารางเดียวกันพร้อมที่ที่แต่ละบล็อกทำงาน

10. สภาพแวดล้อม

Python ของ Slicer เท่านั้น พร้อมแพ็กเกจห้าตัวที่ติดตั้งระหว่างทาง โมเดลที่ quantise ขนาด 7 ถึง 8 พันล้านพารามิเตอร์ต้องใช้หน่วยความจำราว 5 ถึง 6 GB นอกเหนือจาก Slicer น้ำหนักใช้ประมาณ 4.4 GB (TMJ) หรือ 4.9 GB (Ortho) บนดิสก์

ในโค้ดอินเทอร์พรีเตอร์ แพ็กเกจ GPU และตำแหน่งของน้ำหนัก

11. ปัญหาที่ทราบ

  • Dashboardคาดหวังฟิลด์ TMJ และน่าจะหยุดกับ extraction ของ Ortho (รายละเอียด)
  • โหมด Ortho ไม่ส่งคำสั่ง ดังนั้นจึงไม่มีอะไรทำให้ผลลัพธ์เป็น JSON ถ้าโมเดลไม่ใช่ตัวที่คาดไว้ (รายละเอียด)
  • ไม่มีตัวป้องกันความยาว: บันทึกที่ยาวกว่า window ล้มเหลวแทนที่จะถูกตัดเป็นชิ้น ซึ่งเป็นการถดถอยจาก MedX (รายละเอียด)
  • รูปแบบคำตอบไม่ถูกจำกัด และการตัดจากวงเล็บปีกกาแรกถึงอันสุดท้ายพังกับวัตถุสองอัน (รายละเอียด)
  • การสแกนโฟลเดอร์อินพุตไม่ลงลึกโฟลเดอร์ย่อย (ข้อควรระวังทั้งหมด)
  • ไฟล์ผลลัพธ์ไม่บันทึกทั้งโมเดลและวันที่ การรันสองครั้งด้วยโมเดลต่างกันจึงแยกไม่ออก (ข้อควรระวังทั้งหมด)
  • ไม่มีอะไรทำให้บันทึกไม่ระบุตัวตน มาตรการป้องกันเดียวคือโมเดลรันในเครื่อง ซึ่งจริงเฉพาะโมดูล legacy นี้ (ข้อควรระวังทั้งหมด)
  • build แบบตัวประมวลผลอย่างเดียวทำให้คำขอ GPU ไม่มีความหมาย (รายละเอียด)
ในโค้ดรายการข้อควรระวังทั้งหมด รวมถึงเมทาดาทา CLI ที่ยังเป็นค่าเริ่มต้นของเทมเพลต

12. เอกสารอ้างอิง

ไม่มีสิ่งตีพิมพ์ใดถูกอ้างในรีโพซิทอรีสำหรับ CNE และ model card Hugging Face ของ DCBIA-OrthoLab/* ทั้งสองแห่งไม่อ้างบทความใด (ชี้ไปที่รีโพซิทอรีโค้ด ortho-cde-llm-extraction ซึ่งยังไม่ได้อ่าน) คลังข้อมูล annotation ไม่เผยแพร่ และไม่มีการรายงานการประเมินผล ทั้งสองเรื่องไม่อาจระบุได้จากรีโพซิทอรี

สิ่งที่ตรวจสอบได้:

  • สายสัมพันธ์ MedX → CNE ซึ่งมีบันทึกเพียงบรรทัดกิตติกรรมประกาศของ CNE_Dashboard.xml ("Ported from MedX_Dashboard, which CNE replaced without taking this half with it") และความเห็นในโค้ด Dashboard (ดูหน้าโค้ด) CMakeLists.txt ที่ราก ไม่กล่าวถึง MedX อีกต่อไป และ README ไม่มีส่วน MedX หรือ CNE
  • โมเดลฐาน: Meta-Llama-3.1-8B-Instruct, Qwen2.5-7B-Instruct
  • รีโพซิทอรีที่ fine-tune แล้ว: DCBIA-OrthoLab/Qwen-2.5-7B-Instruct-TMJ, DCBIA-OrthoLab/Llama-3.1-8B-Instruct-Ortho
  • เอนจิน: llama-cpp-python, llama.cpp (รูปแบบ GGUF, quantization Q4_K_M)
  • SlicerAutomatedDentalTools

อย่าผูก CNE กับวรรณกรรมทั่วไปว่าด้วยการสกัดข้อมูลทางคลินิกด้วย LLM: ไม่มีอะไรในรีโพซิทอรีบ่งชี้ว่าโมเดลที่ใช้ที่นี่มาจากงานที่ตีพิมพ์
