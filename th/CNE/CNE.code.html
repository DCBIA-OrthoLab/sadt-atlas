CNE, legacy: โค้ด

สำหรับนักพัฒนา: สิ่งที่โมดูล Slicer แบบ legacy ชื่อ CNE ทำในโค้ด (SlicerAutomatedDentalTools ที่ 3c67957) พร้อมการอ้างอิง file:line บล็อกโค้ด อาร์กิวเมนต์ สภาพแวดล้อม และข้อควรระวัง คำอธิบายที่อ่านง่ายของไปป์ไลน์เดียวกันอยู่ในหน้าแอตลาส

ยังไม่ตีพิมพ์ VISOR CNE_CLI ไม่ใช้ conda: Python ของ Slicer บรรณานุกรม โค้ด แอตลาส (คำอธิบาย) คู่มือ

คำเตือนเรื่องขอบเขต ต่างจาก AutoCrop3D และ AutoMatrix CNE ไม่ใช่เครื่องมือเรขาคณิต: ไม่แตะวอลุ่ม เมช หรือพิกัดใด ๆ มันคือโมดูล inference ของ LLM ที่อ่านบันทึกทางคลินิกแบบข้อความอิสระและเขียนคู่ key–value แกนกลางของโมดูลคือโมเดล GGUF ที่ผ่านการ quantize โหลดโดย llama-cpp-python ภายใน Python ของ Slicer

โค้ดสองชุด

ทุกอย่างที่มีเลขกำกับด้านล่างอธิบายโมดูล Slicer แบบ legacy (SlicerAutomatedDentalTools ที่ 3c67957, 2026-10-26) ส่วนพอร์ต VISOR ซึ่งรันเครื่องมือเดียวกันบนเซิร์ฟเวอร์ อธิบายไว้ในหน้าของตัวเอง CNE บน VISOR ผลที่ตามมาข้อหนึ่งสำคัญก่อนอ่านต่อ: เมื่อหน้านี้บอกว่าโมเดลรันในเครื่อง นั่นจริงเฉพาะโมดูล legacy เท่านั้น กับ VISOR ข้อความบันทึกจะถูกส่งไปยังเซิร์ฟเวอร์ (ดูข้อค้นพบใน VISOR)

ข้อควรระวัง (เฉพาะ legacy)

Legacy (3c67957) ไม่มีใน VISOR: ไม่มีอะไรถูกคอมไพล์หรือติดตั้งบนเวิร์กสเตชัน สภาพแวดล้อมของเซิร์ฟเวอร์ปักหมุด llama-cpp-python==0.3.35 จาก wheel index ที่สร้างไว้ล่วงหน้า (SADT-VISOR tools/CNE/pyproject.toml:60-67 ดูCNE บน VISOR) install_function (CNE.py:44) บังคับ CC=gcc และ CXX=g++ ระหว่างการติดตั้ง แล้วคืนค่าเดิม: สำหรับกรณีที่ pip ต้องคอมไพล์ llama-cpp-python จากซอร์ส บน Windows ค่าเหล่านี้ใช้ไม่ได้

ข้อควรระวัง (จริงใน VISOR ด้วย รายงานแล้ว)

เป็นจริงใน VISOR ด้วย: index ที่ปักหมุดยังเป็นแบบ CPU (SADT-VISOR tools/CNE/pyproject.toml:60-67) สิ่งที่เปลี่ยนคือคำขอไม่เงียบอีกต่อไป: device เป็นอาร์กิวเมนต์ที่ระบุชัดโดยมีค่าเริ่มต้นเป็น cpu และคำขอ cuda ที่พบ build แบบ CPU ถูกเขียนลงรายงานเป็น gpu_offload และ warnings (src/sadt_cne/__init__.py:145-165,184-185 ดูCNE บน VISOR) extra index ชี้ไปที่ wheel แบบ CPU อย่างชัดเจน แต่ CLI ขอ n_gpu_layers=-1 พร้อมความเห็น "Use GPU if available" (CNE_CLI.py:164): กับ build แบบ CPU อย่างเดียว พารามิเตอร์นี้ไม่มีผล ในทางปฏิบัติ inference รันบน CPU และโมเดล 7–8 B ที่ quantize แบบ Q4 ช้าบน CPU (ไม่ได้วัดเวลาต่อบันทึกสำหรับหน้านี้)

CLI ทดสอบการนำเข้าสามตัวของมัน (llama_cpp, fitz, docx) ซ้ำตอนเริ่มต้น และเรียก sys.exit(1) ถ้าขาดตัวใด (CNE_CLI.py:101-117): ซ้ำซ้อน แต่ไม่เป็นอันตรายเพราะ CLI ใช้อินเทอร์พรีเตอร์เดียวกับวิดเจ็ต

รีโพซิทอรี Hugging Face ทั้งสองแห่งตอนนี้มีmodel card ซึ่งหน้านี้เคยบอกว่าไม่มี (อ่านผ่าน Hugging Face API เมื่อ 2026-11-09 ไม่ได้อ่านจากรีโพซิทอรี ADT) แต่ละอันระบุใบอนุญาต (Llama 3.1 สำหรับ Ortho, Apache 2.0 สำหรับ TMJ) โมเดลฐาน วิธีการ (LoRA, r = 32, alpha = 64, merge แล้ว quantize เป็น Q4_K_M) ว่าบันทึกที่ใช้ฝึกเป็นข้อมูลผู้ป่วยที่ annotate และไม่เผยแพร่ และว่าชุดข้อมูลถูกแบ่งตามผู้ป่วย การ์ด Ortho บอกว่าโมเดลรับบันทึกดิบโดยไม่มี system prompt ซึ่งตรงกับโค้ด (§6) และระบุลักษณะทางทันตกรรมจัดฟัน (ขนาดและวัสดุลวด ligation ยางดึง overjet overbite ...) เป็นสกีมาของมัน ทั้งสองการ์ดไม่รายงานการประเมินผล ไฟล์ TMJ ขนาด 4,683,073,408 ไบต์ (HTTP HEAD, 2026-11-10): 4.7 GB ในหน่วยทศนิยม และ 4.4 ในหน่วยไบนารี (GiB) ดังนั้นการ์ดและกล่องดาวน์โหลด TMJ (CNE.py:528) จึงอธิบายไฟล์เดียวกันด้วยสองระบบหน่วย กล่อง Ortho (CNE.py:521) ใช้หน่วยทศนิยม

  • ไม่มีการตรวจความยาวก่อนการเรียก: บันทึกยาวไม่ถูกแบ่งชิ้น คำตอบถูกทำให้สั้นเท่าที่ window เหลือ (JSON ถูกตัด ข้อความดิบถูกเขียน) และบันทึกที่เต็ม window จะล้มเหลว ขณะที่ MedX แบ่งชิ้นให้ (§6) นี่คือการถดถอยเชิงฟังก์ชันของตัวที่มาแทน
  • โหมด Ortho ไม่ส่งคำสั่งระบบ (§6): ถ้าโมเดลไม่ใช่ตัวที่คาดไว้ ก็ไม่มีเหตุผลที่ผลลัพธ์จะเป็น JSON เลย
  • ไม่มีข้อจำกัดรูปแบบผลลัพธ์: ไม่มีไวยากรณ์ GBNF และไม่มี response_format ทั้งที่ llama.cpp มีให้ทั้งสองอย่าง การประมวลผลหลังได้คำตอบจึงเป็นการงัดเอาข้อมูลออกมาแบบฮิวริสติก (§7)
  • ปุ่มวิทยุตั้งไว้ที่ไม่ใช่ทั้ง TMJ และ Ortho → notesType = "" (CNE.py:427) → ใน getModelPath ไม่เคยกำหนด repo_id และ UnboundLocalError ปรากฏเป็น "Failed to load model" กรณีนี้ไม่ควรเกิด (setExclusive(True) และค่าเริ่มต้นเป็น TMJ) แต่ไม่มีอะไรกั้นไว้
  • การใช้ตัวพิมพ์ไม่สอดคล้องกัน: notesType == "TMJ" ตั้ง n_ctx ขณะที่ notesType.upper() == "TMJ" ตั้งคำสั่ง notesType ที่เป็นตัวพิมพ์เล็กจะได้คำสั่ง TMJ กับ context 2048
  • ไม่มีร่องรอยที่มา: ไฟล์ Extraction_*.txt ไม่ระบุทั้งโมเดล เวอร์ชัน หรือวันที่ การรันสองครั้งด้วยโมเดลต่างกันให้ไฟล์ที่แยกไม่ออก
  • PHI: ไม่มีอะไรทำให้ไม่ระบุตัวตน ไม่มีอะไรเตือน บันทึกถูกอ่านแบบข้อความธรรมดา ผ่านโมเดลในเครื่อง (จึงไม่มีการรั่วทางเครือข่าย: นั่นคือมาตรการป้องกันเดียว และเป็นผลจากโครงสร้างมากกว่าความตั้งใจ) เฉพาะโมดูล legacy (3c67957) กับ VISOR บันทึกถูกอัปโหลดไปเซิร์ฟเวอร์ตามเดิม และไม่มีอะไรลบข้อมูลระบุตัวตนก่อน: ดูข้อค้นพบใน VISOR
  • เมทาดาทา CLI ที่ยังเป็นค่าเริ่มต้นของเทมเพลต: CNE_CLI.xml ยังอธิบายว่า "Apply a Gaussian blur to an image" ระบุโมดูลเป็นของ "Andras Lasso (PerkLab)" และค่า <index> ของมันคือ 0, 2, 3, 4 ขาด index 1
  • onCliProgress (CNE.py:651) อ่าน caller.GetProgress() แล้วไม่ทำอะไรกับมัน มันไม่ได้ต่อกับ observer ใดเลยด้วยซ้ำ โค้ดตาย ความคืบหน้าจริงผ่านแท็ก <filter-progress> ของ CLI ซึ่งอ่านโดย qSlicerCLIProgressBar

12. เอกสารอ้างอิง

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส
