SurgMovPred

SurgMovPred ทำนายการเคลื่อนหลังผ่าตัดของจุด landmark 28 จุด จากตารางการวัดและแผนการผ่าตัด หน้านี้อธิบายทีละขั้นว่าทำอย่างไร พร้อมคณิตศาสตร์: อะไรเข้า แต่ละขั้นทำอะไรกับมัน และอะไรออกมา ไฟล์ บรรทัด และข้อควรระวังอยู่ในหน้าโค้ด การพอร์ต VISOR อยู่ในหน้าของมันเอง

โค้ด (นักพัฒนา) ยังไม่ตีพิมพ์ SurgMovPred_CLI ไม่ใช้ conda: ใช้ Python ของ Slicer เอง บรรณานุกรม VISOR

ภาพรวม: อะไรเข้า อะไรออก

SurgMovPred ทำนายว่ากระดูกจะถูกเคลื่อนไปไกลเท่าใดในการผ่าตัดขากรรไกร มันอ่านตารางที่มีหนึ่งแถวต่อผู้ป่วย (การวัดเซฟาโลเมตริกก่อนผ่าตัด บวกการเคลื่อนที่วางแผนไว้) และเขียนตารางของการเคลื่อนหลังผ่าตัดที่ทำนาย: จุด landmark 28 จุด จุดละสี่ค่า มันไม่อ่านสแกนหรือเมช และไม่เปลี่ยนอะไรในฉากของ Slicer

SurgMovPred โมดูล legacy
อินพุตโฟลเดอร์ของตาราง CSV, XLSX หรือ ODS เลือกในแผงของ Slicer
วิธีการโมเดลที่ฝึกแล้ว 112 ตัว หนึ่งตัวต่อเป้าหมาย แต่ละตัวปรับสเกลอินพุต 145 ตัวของมันใหม่และทำนายด้วยstack ของ regressor สามตัว
เอาต์พุตตารางสองตารางเนื้อหาเดียวกัน predictions_outputs.xlsx และ .csv
ที่ไหนภายใน Python ของ Slicer เอง บนซีพียู

หน้านี้อธิบายโมดูล Slicer แบบ legacy (SlicerAutomatedDentalTools ที่ 3c67957) การพอร์ต VISOR ซึ่งรันอัลกอริทึมเดียวกันบนเซิร์ฟเวอร์ มีหน้าของตัวเอง ชื่อไฟล์ หมายเลขบรรทัด และข้อควรระวังอยู่ในหน้าโค้ด

1. ตำแหน่งในไปป์ไลน์

SurgMovPred เป็นเครื่องมือแยกเดี่ยว: ไม่มีอะไรในที่เก็บโค้ดเรียกมัน และมันไม่เรียกสิ่งใด อินพุตคือโฟลเดอร์ของสเปรดชีตและเอาต์พุตคือสเปรดชีตอีกไฟล์ โมดูลไม่ได้ต่อเข้ากับฉากของ Slicer: มันเป็นอินเทอร์เฟซสำหรับเรียกใช้ที่วางอยู่บนสคริปต์ pandas

ในโค้ดแผนภาพไปป์ไลน์ในโค้ด สถานะการ build และชื่ออาร์กิวเมนต์ที่ตกค้าง

2. ไฟล์ที่เกี่ยวข้อง

โมดูลคือแผงของ Slicer (ตัวเลือกโฟลเดอร์สามตัวและสี่ปุ่ม) กับสคริปต์บรรทัดคำสั่งที่ถือการประมวลผลทั้งหมด มีเพียงสามโฟลเดอร์ที่ส่งให้สคริปต์: อินพุต โมเดล และเอาต์พุต ไม่มีอะไรอื่นที่ปรับได้: ไม่มี threshold ไม่มีการเลือกเป้าหมาย ไม่มีตัวเลือกประเภทโครงกระดูก

ในโค้ดตารางไฟล์และพารามิเตอร์ที่ประกาศใน XML

3. อินพุตและการประมวลผลเบื้องต้น

สคริปต์อ่านทุกสเปรดชีตในโฟลเดอร์อินพุตและต่อกันจากบนลงล่าง (ไม่มีโฟลเดอร์ย่อย สำหรับสมุดงาน Excel อ่านเฉพาะชีตแรก) จากนั้นทำความสะอาดชื่อคอลัมน์ให้เป็นการสะกดที่ใช้ตอนฝึก หาคอลัมน์รหัสผู้ป่วยโดยลองรายการชื่อที่ใช้บ่อย และก่อนการทำนาย ปรับสเกลอินพุต

แต่ละโมเดลมี scaler ของตัวเองที่ fit บนข้อมูลฝึกของมัน ไม่มีการเติมค่า: เซลล์ว่างยังคงว่างตลอดการปรับสเกล แล้วโมเดลปฏิเสธมัน ข้อผิดพลาดถูกจับและบันทึก และเป้าหมายนั้นหายไปจากผลลัพธ์สำหรับทุกผู้ป่วย ไม่ใช่เฉพาะแถวที่มีช่องว่าง ความยืดหยุ่นเรื่องชื่อคอลัมน์มีเพียง suffix _T0: หากโมเดลคาดหวัง X_T0 และตารางมี X จะถูกยอมรับ คอลัมน์อื่นที่ขาดไปทำให้ทั้งโมเดลถูกข้ามพร้อมคำเตือน และคอลัมน์ของมันไม่มีในผลลัพธ์

ในโค้ดฟังก์ชันอ่าน กฎการทำความสะอาดทั้งห้า รูปแบบตัวระบุ และบรรทัดของ scaler

4. โมเดล

น้ำหนักไม่ได้อยู่ในที่เก็บโค้ด: แผงดาวน์โหลดไฟล์เก็บถาวรหนึ่งไฟล์ของโฟลเดอร์โมเดล 112 โฟลเดอร์ (ประมาณ 740 MB) จาก GitHub release ได้ ชี้ตัวเลือกโมเดลไปที่โฟลเดอร์บนสุดจะโหลดทั้ง 112 โมเดล ชี้ไปที่โฟลเดอร์ย่อยจะโหลดเฉพาะตัวนั้น ทั้ง 112 ตัวอยู่ในหน่วยความจำพร้อมกัน (ประมาณ 1.5 GB) แม้สำหรับผู้ป่วยเพียงหนึ่งราย

ในโค้ดที่อยู่ดาวน์โหลด การค้นหาแบบเรียกซ้ำ และลำดับชั้นของโฟลเดอร์ที่ไม่มีอยู่จริง

4.1 เนื้อหาของแพ็กเกจ

ไฟล์โมเดลแต่ละไฟล์เก็บสี่อย่าง ได้แก่ ชื่อของ target รายการคอลัมน์อินพุต 145 คอลัมน์เรียงตามลำดับ scaler ที่ฟิตแล้ว และโมเดล stacking ที่ฟิตแล้ว ข้อมูลเหล่านี้อ่านตรงจากแพ็กเกจสองชุดโดยไม่ได้รันมัน ส่วนไฟล์ผังของ VISOR ระบุเช่นเดียวกันนี้สำหรับทั้งชุดที่จัดส่ง

ในโค้ดตารางคีย์และการตรวจสอบที่ได้ทำไว้

4.2 สถาปัตยกรรม

ไม่มีโครงข่ายประสาทเทียม แต่ละ target ถูกทำนายด้วย stack ของตัวถดถอยพื้นฐานสามตัว ซึ่งนำค่าประมาณของทั้งสามมารวมกันด้วยการถดถอยเชิงเส้น ทั้งสามตัวคือ ElasticNetCV (โมเดลเชิงเส้นที่มีค่าปรับที่เลือกด้วย cross-validation) LightGBM (ต้นไม้ตัดสินใจเล็ก ๆ จำนวนมากที่เพิ่มต่อกันทีละต้น) และ Gaussian process (เส้นโค้งเรียบที่พาดผ่านจุดข้อมูลฝึก) เหตุผลที่เลือกทั้งสามตัวนี้ไม่ได้เขียนไว้ที่ใดในที่เก็บโค้ด เพราะโค้ดสำหรับการฝึกไม่ได้อยู่ที่นั่น

ในโค้ดตัวประมาณค่าและพารามิเตอร์ที่อ่านได้

4.3 ฟีเจอร์ 145 ตัว

อินพุต 145 ตัวแบ่งเป็นสี่กลุ่ม 78 ตัวเป็นตำแหน่งของจุดที่วัดเทียบกับระนาบอ้างอิงสามระนาบ (Frankfort horizontal, midsagittal และ coronal) โดย 24 ตัวในจำนวนนี้เป็นจุดเนื้อเยื่ออ่อน ซึ่งมีเครื่องหมายอะพอสทรอฟีในชื่อ 14 ตัวเป็นการวัดเซฟาโลเมตริกอื่น ๆ ได้แก่ มุม อัตราส่วน และความกว้าง ส่วน 53 ตัวสุดท้ายเป็นการวัดocclusalที่ให้ไว้สองชุด คือ 28 ตัวเป็นสถานะก่อนผ่าตัด (ชื่อลงท้ายด้วย _T0) และ 25 ตัวเป็นการเคลื่อนที่รวมที่วางแผนไว้ (ลงท้ายด้วย _Total) ซึ่งส่วนใหญ่มีทั้งสองชุด ความหมายที่แน่นอนของสองชุดนี้ไม่ได้บันทึกไว้ที่ใดในที่เก็บโค้ด การตีความว่าโมเดลได้รับทั้งสถานะเริ่มต้นและผลลัพธ์ที่วางแผนไว้เป็นเพียงข้อสันนิษฐานจากชื่อ

ในโค้ดตารางตระกูลพร้อมตัวอย่าง และคอลัมน์ที่ถูกอ่านแล้วถูกละเลย

4.4 สิ่งที่ถูกทำนาย

target 112 ตัวคือโครงสร้าง 28 โครงสร้างคูณ 4 องค์ประกอบ สามองค์ประกอบเป็นทิศทางที่มีเครื่องหมายของการเคลื่อนที่ (หลังหรือหน้า ขวาหรือซ้าย ลง) และองค์ประกอบที่สี่น่าจะเป็นขนาดของมันมาก หน่วยไม่ได้เขียนไว้ที่ใดเลย โครงสร้างคือจุดที่ยึดติดกับส่วนของกระดูก ได้แก่ 10 จุดบนขากรรไกรบน 17 จุดบนขากรรไกรล่าง และอีกหนึ่งจุดสำหรับ genioplasty สิ่งที่ถูกทำนายจึงเป็นการเคลื่อนที่ของแต่ละจุดแยกกัน ไม่ใช่การแปลงแบบแข็งของส่วนกระดูกทั้งส่วน

ในโค้ดรายการโครงสร้างทั้ง 28 และการตั้งชื่อองค์ประกอบ

5. การประมวลผลหลัก

สำหรับแต่ละแพ็กเกจ สคริปต์จะนำคอลัมน์ของโมเดลมาปรับสเกลแล้วทำนาย ไม่มีการแก้ไขหลังการทำนาย ไม่มีการจำกัดขอบเขต ไม่มีความสอดคล้องระหว่าง target และไม่มีช่วงความเชื่อมั่น ทั้งที่ตัวถดถอยพื้นฐานตัวหนึ่งในสามตัวสามารถให้ได้ แต่ละ target มีการป้องกันของตัวเอง target ที่ล้มเหลวจะไม่ทำให้ตัวอื่นหยุด เพียงแต่คอลัมน์ของมันหายไป

ในโค้ดลูปการทำนายฉบับเต็ม

6. เอาต์พุต

สคริปต์เขียนไฟล์สองไฟล์ที่มีเนื้อหาเหมือนกัน เป็นตารางที่มีรหัสผู้ป่วย ตามด้วยหนึ่งคอลัมน์ต่อหนึ่ง target ที่ถูกทำนาย ตั้งชื่อตามไฟล์โมเดล ทั้งสองไฟล์ขึ้นต้นด้วยคอลัมน์ลำดับเลขที่ไม่มีชื่อ ไม่มีสิ่งใดถูกนำกลับไปใช้กับสแกน เมช หรือฉากของ Slicer การทำนายจบที่สเปรดชีต และผู้ปฏิบัติงานนำค่าไปใส่ในซอฟต์แวร์วางแผนของตนเอง

ในโค้ดฟังก์ชันบันทึก ตารางไฟล์ และการที่ไม่มีการนำกลับไปใช้

7. ทำนายหรือคำนวณ

ขั้นตอนลักษณะ
การทำความสะอาดคอลัมน์ การตรวจหารหัสผู้ป่วยคำนวณ กำหนดแน่นอน
การปรับสเกลคำนวณ scaler ที่เรียนรู้จากข้อมูลฝึก
การเคลื่อนที่ 112 ค่าทำนายด้วยตัวถดถอยแบบ stack
การเคลื่อนที่ที่สอดคล้องกันของส่วนกระดูกทั้งส่วนไม่มีอยู่
ในโค้ดตารางที่ระบุว่าแต่ละบล็อกรันที่ไหน และข้อควรระวังเรื่อง target ที่ทำนายแยกกัน

8. สภาพแวดล้อม

ทุกอย่างรันใน Python ของ Slicer เอง ไม่มี conda ไม่มีการ์ดจอ และไม่มี torch ทุกครั้งที่คลิก Apply ระบบจะตรวจสอบและติดตั้งแพ็กเกจ Python ที่จำเป็น และบังคับเวอร์ชัน numpyให้คงที่ ไม่ว่าโมดูลอื่นของ extension จะต้องการอะไร รายละเอียดอยู่ในหน้าโค้ด บน macOS จะมีการดาวน์โหลดไลบรารีเพิ่มสำหรับ LightGBM

ในโค้ดรายการแพ็กเกจ การตรึงเวอร์ชัน numpy และขั้นตอนบน macOS

9. ปัญหาที่ทราบ

  • เวอร์ชัน numpyถูกตั้งเป็น 2.4.0 ทุกครั้งที่กด Apply ใน Python ตัวเดียวกับที่โมดูลอื่นของ extension ตั้งเป็น numpy 1.26.4 ดูรายละเอียด
  • ปุ่มไฟล์ทดสอบดาวน์โหลดไฟล์เก็บถาวรของตาราง แล้วละเลยมันเว้นแต่จะมีข้อมูลของโมดูลอื่นอยู่ และยังดาวน์โหลดโมเดลด้วย ดูรายการ
  • ไฟล์ ODS ถูกโฆษณาว่ารองรับ แต่โมดูลไม่ได้ติดตั้งแพ็กเกจสำหรับอ่าน ดูรายการ
  • คอลัมน์อินพุตที่ขาดไปจะลบ target ออกจากผลลัพธ์อย่างเงียบ ๆ ดูรายการ
  • สเปรดชีตที่มีคอลัมน์ต่างกันจะถูกต่อกันแบบไม่ตรวจสอบ (เซลล์ว่างเซลล์เดียวทำให้ target ทั้งตัวหลุดไป) และอ่านเฉพาะชีต Excel แรกเท่านั้น ดูรายการ
  • target ถูกทำนายแยกกัน ดังนั้นจุดต่าง ๆ ของส่วนกระดูกเดียวกันจึงไม่จำเป็นต้องเคลื่อนที่สอดคล้องกัน ดูข้อควรระวัง
  • ไม่มีการให้ค่าความไม่แน่นอน และไม่มีสิ่งใดถูกนำไปใช้กับฉาก ดูข้อควรระวัง
ในโค้ดรายการข้อควรระวังทั้งหมดพร้อมเลขบรรทัด

10. วรรณกรรม

วิธีการและแหล่งที่มาอธิบายอยู่ในหน้าแหล่งที่มา หน้าโค้ดรวบรวมรายการสิ่งพิมพ์และระบุว่าแต่ละชิ้นใช้ได้กับโมดูลนี้มากน้อยเพียงใด
