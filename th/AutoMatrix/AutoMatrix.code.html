AutoMatrix, legacy: โค้ด

สำหรับนักพัฒนา: สิ่งที่โมดูล AutoMatrix แบบ legacy ทำในโค้ด พร้อมอ้างอิง file:line บล็อกโค้ด รูปแบบที่อ่านจริง กฎการจับคู่ และข้อควรระวัง คำอธิบายที่อ่านง่ายของไปป์ไลน์เดียวกันพร้อมคณิตศาสตร์อยู่ในหน้าแอตลาส

ไม่จริงใน VISOR .txt ที่มีเมทริกซ์ 4x4 ธรรมดาถูกอ่านด้วยทางสำรองเมื่อ sitk.ReadTransform ปฏิเสธมัน (SADT-VISOR AutoMatrix/pipeline.py:138-180) รันเมื่อ 2026-11-09: เมทริกซ์สี่บรรทัดใน P1_matrix.txt ให้วอลุ่มที่แปลงแล้วหนึ่งชุด

เรื่องเดียวกันกับ "เมทริกซ์ข้อความ": นั่นไม่ใช่รูปแบบเมทริกซ์ แต่เป็นรูปแบบข้อความของ ITK

4.1 ทิศทางของการแปลง

คำอธิบายภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

ITK เป็นfixed → moving: sitk.Transform ที่ส่งให้ resampler แมปจุดกายภาพเอาต์พุตไปยังจุดกายภาพอินพุตที่จะสุ่มค่า เนื้อหาที่มองเห็นจึงเคลื่อนตาม T⁻¹

โค้ดใช้ประโยชน์จากเรื่องนี้ทั้งสองฝั่ง และสอดคล้องกัน:

  • วอลุ่ม (Automatrix_CLI.py:182): resampler.SetTransform(transform) การแปลงถูกส่งตามที่เป็น เนื้อหาเคลื่อนตาม T⁻¹
  • Landmark (Automatrix_CLI.py:149,156): 
    tfm_inverted = transform.GetInverse()
point['position'] = list(tfm_inverted.TransformPoint(point['position']))
    T⁻¹ ถูกใช้กับจุดอย่างชัดเจน มันจึงเคลื่อนเหมือนเนื้อหาของวอลุ่ม
ตรวจสอบแล้ว

เป็นจริงในVISORด้วย (SADT-VISOR AutoMatrix/pipeline.py:121 ส่งการแปลงให้ resampler; :83 และ :99 ผกผันมันสำหรับจุด)

ข้อสรุปสำคัญ: .tfm เดียวกันที่ใช้กับสแกนและกับ landmark ของมัน ทำให้เคลื่อนด้วยการเคลื่อนที่เดียวกัน นี่คือคุณสมบัติที่ทำให้โมดูลใช้งานได้ และเป็นที่เดียวในโค้ดที่มีการผกผันปรากฏ

ข้อควรระวัง

Legacy (3c67957) เปลี่ยนใน VISOR Legacy: คำเตือนและ return ไม่มีไฟล์ (Automatrix_CLI.py:148-152@3c67957) VISOR: RuntimeError ไม่ถูกกลืนอีก (SADT-VISOR AutoMatrix/pipeline.py:74-78,83) มันถูกบันทึกใต้ cases[patient].failed (SADT-VISOR AutoMatrix/__init__.py:144-155) และวอลุ่มของผู้ป่วยรายนั้นยังถูกเขียน สองเอาต์พุตจึงยังไม่ตรงกันได้ แต่รายงานบอกไว้ ฟิลด์การกระจัดเป็นศูนย์โยนข้อผิดพลาดบน GetInverse() (รันเมื่อ 2026-11-09) การรันล้มเหลวก็ต่อเมื่อไม่มีอะไรถูกเขียนเลย (:164) แผง Slicer ไม่แสดงความล้มเหลว ดูข้อค้นพบในหัวข้อ VISOR

4.2 RAS / LPS: การพลิกเกิดที่ไหน ไม่มีที่ไหนเลย

คำอธิบายภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

ใน AutoMatrix ไม่มีการพลิก นี่ถูกต้อง และนี่คือเหตุผล:

  • ไฟล์ ITK .tfm อยู่ใน LPS โดยธรรมชาติ
  • sitk.ReadImage / WriteImage ทำงานใน LPS ทั้งสองฝั่งตรงกัน ไม่ต้องทำอะไรกับวอลุ่ม
  • ไฟล์ .mrk.json ของที่เก็บโค้ดกำหนด LPS ตายตัวทุกที่: ALI_CBCT/ALI_CBCT_utils/io.py:39, ALI_IOS/ALI_IOS_utils/io.py:74, FlexReg/FlexReg_utils/mgl_patch.py:222, VFACE/VFACE_utils/functionaq3dc.py:1724 และเนื่องจาก ASO_CBCT และ AREG_CBCT ตอนนี้ re-export WriteJson แทนที่จะมีของตัวเอง จึงมี ADTLib/io/landmarks.py:92 นี่ก็เป็นค่าเริ่มต้นของ Slicer ตอนเขียนเช่นกัน ดังนั้น point['position'] อยู่ใน LPS แล้ว และการใช้มันกับการแปลง ITK โดยตรงจึงถูกต้อง
ข้อควรระวัง

เป็นจริงในVISORด้วย (SADT-VISOR AutoMatrix/pipeline.py:71-104 ไม่เคยอ่านมัน) รันเมื่อ 2026-11-09: ไฟล์ที่ประกาศ RAS พร้อมจุดควบคุม [1,2,3] และการเลื่อนตำแหน่ง (5,0,0) ออกมาเป็น x = -4 และยังประกาศ RAS Legacy: Automatrix_CLI.py:154-156@3c67957

จุดเปราะบางคือฟิลด์ coordinateSystem ไม่เคยถูกอ่าน FlexReg อ่านมัน (FlexReg.py:2221) AutoMatrix ไม่อ่าน json ที่ประกาศ "coordinateSystem": "RAS" ซึ่งคำอธิบายประกอบเก่าหรือเครื่องมืออื่นเขียน จะถูกแปลงด้วย x และ y ที่เครื่องหมายผิด โดยไม่มีข้อความ ไฟล์เอาต์พุตจะยังคง coordinateSystem: RAS เดิมด้วยซ้ำ เพราะ json ถูกอ่านกลับและเขียนใหม่ตามที่เป็น

เพื่อเป็นข้อมูลอ้างอิง โมดูลที่สร้างเมทริกซ์ทำการพลิกเอง: FlexReg_CLI.py:100-105 คำนวณ flip @ matrix_array @ flip โดย flip = np.diag([-1, -1, 1, 1]) แล้วผกผัน ก่อนเขียน .tfm (:107-109) AutoMatrix ใช้ผลของงานนั้นจึงไม่เหลืออะไรให้ทำซ้ำ
