1. ตำแหน่งใน pipeline

ไม่มีสิ่งใดในรีโพสิทอรีเรียกใช้ AutoCrop3D และ AutoCrop3D ไม่เรียกสิ่งใดนอกจาก Slicer มีการประกาศไว้ใน CMakeLists.txt:39 และมีเพียงเท่านั้น

ในทางปฏิบัติ มันอยู่ต้นทางของเครื่องมือแบ่งส่วน (AMASSS, BATCHDENTALSEG) หรือ ปลายทางของเครื่องมือเหล่านั้น: โหมด "generate VTK" ทำงานเฉพาะเมื่อชื่อไฟล์เอาต์พุต มีคำว่า seg ซึ่งสันนิษฐานว่าได้รับ labelmap ที่สร้าง จากที่อื่นมาแล้ว

สิ่งที่ถูกเรียกเมื่อใดเหตุผล
slicer.modules.autocrop3d_cliเส้นทางค่าเริ่มต้นดึงตามดัชนี ไม่รีแซมเปิล
slicer.modules.cropvolume.logic()ช่องทำเครื่องหมาย "Use module 'Crop Volume' for tilted images"ส่งกรณี ROI ที่หมุนให้ Slicer จัดการ

ไม่มีโมเดล ไม่มี .pth ไม่มีการดาวน์โหลด: ตรวจสอบแล้วด้วยการ grep torch|conda|\.pth|monai|nnunet ทั่วทั้ง AutoCrop3D/ — ไม่พบเลย นอกจาก vtkPolyData ที่ชื่อ model

3. สิ่งที่กำหนดกล่องครอป

ไฟล์ markups ROI json (.mrk.json) ซึ่งอ่านดังนี้ (AutoCrop3D_CLI.py:70):

ROI = json.load(open(ROI_Path))['markups'][0]
ROI_Center = np.array(ROI['center'])
ROI_Size   = np.array(ROI['size'])
Lower = ROI_Center - ROI_Size / 2
Upper = ROI_Center + ROI_Size / 2

มีสามฟิลด์ใน json ที่ถูกละเลย และเป็นต้นเหตุหลักของ ความประหลาดใจ:

  • coordinateSystem ไฟล์ทดสอบ ROI.mrk.zip (ใน AutoCrop3D/Crop_Volumes_UI/Testing/Test_data/) ระบุ "coordinateSystem": "LPS" ซึ่งเป็นข้อตกลงของรีโพสิทอรี (ตัวเขียน markups ทุกตัวกำหนดตายตัวเป็น "LPS": ALI_CBCT, ASO_CBCT, AREG_CBCT, FlexReg, VFACE) center จึงอยู่ใน LPS ตรงกับที่ TransformPhysicalPointToContinuousIndex ของ SimpleITK คาดหวัง แต่ฟิลด์นี้ ไม่เคยถูกอ่าน: ROI ที่บันทึกใน RAS จะให้จุดศูนย์กลางที่ x และ y มี เครื่องหมายตรงข้าม โดยไม่มีข้อความใด ๆ เลย
  • orientation (เมทริกซ์ 3×3 ของกล่อง) ถูกละเลย: ถือว่ากล่อง ขนานกับแกน LPS ในไฟล์ทดสอบคือ diag(-1,-1,1) การหมุน 180° รอบแกน z — ไม่มีผลกับกล่องที่อยู่กึ่งกลาง ROI ที่หมุนจริงจะถูกมองเป็นกล่องล้อมรอบที่ขนานกับแกนของตัวเอง โดยไม่แจ้งเตือน นั่นคือเหตุผลที่มี ช่องทำเครื่องหมาย "tilted images" (§5)
  • ไม่ใช้การแบ่งส่วนหรือกล่องล้อมรอบที่คำนวณ: กล่องมาจาก json นี้เท่านั้น ไม่มีโค้ดใดที่สร้าง ROI จาก labelmap
ข้อควรระวัง

coordinateSystem: ROI ที่บันทึกใน RAS จะให้จุดศูนย์กลางที่ x และ y มีเครื่องหมายตรงข้าม โดยไม่มีข้อความใด ๆ เลย

orientation: ROI ที่หมุนจริงจะถูกมองเป็นกล่องล้อมรอบที่ขนานกับแกนของตัวเองโดยไม่แจ้งเตือน

ฝั่งวอลุ่ม Search รับ .nii.gz, .nii, .nrrd.gz, .nrrd, .gipl.gz, .gipl (AutoCrop3D_CLI.py:48) ผ่าน glob.iglob(**, recursive=True) แล้วตามด้วย endswith

4. การใช้กล่อง — ดึงตามดัชนี ไม่รีแซมเปิล

นี่คือประเด็นสำคัญ: ไม่มีการประมาณค่าในช่วง การแปลงพิกัดกายภาพ → ดัชนี แล้วตามด้วยการครอป (AutoCrop3D_CLI.py:77):

Lower = np.array(img.TransformPhysicalPointToContinuousIndex(Lower)).astype(int)
Upper = np.array(img.TransformPhysicalPointToContinuousIndex(Upper)).astype(int)
for i in range(3):
    if Lower[i] > Upper[i]:
        Lower[i], Upper[i] = Upper[i], Lower[i]
Lower = [max(0, l) for l in Lower]
Upper = [min(img_size[i], u) for i, u in enumerate(Upper)]
img_roi = img[Lower[0]:Upper[0], Lower[1]:Upper[1], Lower[2]:Upper[2]]

swap ไม่ใช่เรื่องเล็กน้อย TransformPhysicalPointToContinuousIndex ใช้อินเวอร์สของเมทริกซ์ทิศทาง บนวอลุ่มที่ direction cosine เป็นลบในบางแกน (พบบ่อยใน CBCT) มุม "ล่าง" ทางกายภาพ จะกลายเป็นดัชนีที่ใหญ่ที่สุด: หากไม่ swap การตัดจะได้ผลว่างเปล่า นี่คือการจัดการ direction ที่ถูกต้อง

สิ่งที่การอ้างดัชนีของ SimpleITK คงไว้ ตรวจสอบแล้ว: การตัด sitk.Image คง spacing และ direction ไว้เหมือนเดิม และคำนวณจุดกำเนิดใหม่ตาม มุมที่ดึงออกมา บนวอลุ่ม 50×60×70, spacing 0.3, จุดกำเนิด (10,20,30), direction diag(-1,-1,1) คำสั่ง img[5:20,5:20,5:20] ให้จุดกำเนิด (8.5, 18.5, 31.5) — เลื่อน -5·0.3 บนแกน x และ y (ทิศทางลบ) +5·0.3 บนแกน z ค่าวอกเซลตรงกับอินพุตทุกบิต

ตรวจสอบแล้ว

การตัด sitk.Image คง spacing และ direction ไว้เหมือนเดิม และคำนวณใหม่เพียงจุดกำเนิดของมุมที่ดึงออกมา ค่าวอกเซลตรงกับอินพุตทุกบิต

โหมด "Keep the same size as input" (box_Size == 'True', AutoCrop3D_CLI.py:107): สร้างภาพว่าง ด้วยเรขาคณิตต้นฉบับ (sitk.Image(...) + CopyInformation) วางบล็อกที่ดึงออกมากลับที่ตำแหน่งดัชนี เดิม แล้วใช้ CopyInformation อีกครั้ง เรขาคณิตเหมือนกับ อินพุตทุกประการ โดยทุกส่วนนอก ROI มีค่าเป็น 0 สังเกตการกลับแกน ของ GetArrayFromImage (z,y,x) ซึ่งโค้ดจัดการได้ถูกต้อง

การแปลงที่เกี่ยวข้อง (ถ้ามี) เป็นอย่างไร: ไม่มีอะไรเกิดขึ้น ไม่มี vtkMRMLTransformNode ไม่มีการอ่านหรือเขียน .tfm ไม่มี HardenTransform เรขาคณิตถูกเก็บทั้งหมดไว้ในส่วนหัวไฟล์ (origin/spacing/direction) และ ระยะเลื่อนของการครอปถูกดูดซับไว้ในจุดกำเนิด

หมายเหตุ

ผลในทางปฏิบัติ: เมทริกซ์การลงทะเบียนภาพ (registration) ที่คำนวณบนวอลุ่มเต็มยังคงใช้ได้ตามเดิมบนวอลุ่มที่ครอปแล้ว เพราะพิกัดกายภาพไม่ได้เปลี่ยน

5. เส้นทางทางเลือก — โมดูล Crop Volume ของ Slicer

processCropVolume() (AutoCrop3D.py:915) เปิดใช้ด้วยช่องทำเครื่องหมาย "Use module 'Crop Volume' for tilted images" (commit 9d2bbe8) รันภายในวิดเจ็ต ไม่ใช่ใน CLI:

cropVolumeLogic = slicer.modules.cropvolume.logic()
parameters = slicer.vtkMRMLCropVolumeParametersNode()
parameters.SetInputVolumeNodeID(inputVolume.GetID())
parameters.SetROINodeID(roiNode.GetID())
parameters.SetOutputVolumeNodeID(outputVolume.GetID())
cropVolumeLogic.Apply(parameters)

กำหนดเพียงสาม ID: การประมาณค่าในช่วง ความเป็นไอโซทรอปิก และสเกลของ spacing คงเป็นค่าเริ่มต้นของ vtkMRMLCropVolumeParametersNode เมื่อ เปิดการประมาณค่า Crop Volume จะรีแซมเปิลในกรอบพิกัดของ ROI เอง ซึ่งเป็นสิ่งที่ทำให้จัดการ ROI ที่หมุนได้ — แลกกับการ เปลี่ยนค่าวอกเซล ต่างจากเส้นทาง CLI ทั้งสอง เส้นทางจึงไม่ได้ไฟล์เดียวกัน และเป็นความตั้งใจ

optionCheckBox() ซ่อน "Keep the same size" ในโหมดนี้ เพราะ Crop Volume ไม่มี สิ่งที่เทียบเท่า

เส้นทางนี้โหลด ROI และวอลุ่มเป็นโหนด MRML (loadMarkups, loadVolume) ดังนั้นเส้นทางนี้เท่านั้นที่อ่าน coordinateSystem และ orientation — Slicer จัดการให้เมื่อแยกวิเคราะห์ json

11. ข้อควรระวังและจุดเปราะบาง

ข้อควรระวัง — โฟลเดอร์ ROI ที่มีไฟล์เดียว

โฟลเดอร์ ROI ที่มีไฟล์เดียวพอดี → โปรแกรมล่ม ROI_dict ถูกสร้างเฉพาะเมื่อ len(ROIList) > 1 มิฉะนั้น ROI_Path ยังคงเป็นโฟลเดอร์ และ json.load(open(ROI_Path)) เกิด IsADirectoryError ในทางกลับกัน เส้นทาง Crop Volume ทดสอบ os.path.isdir และจัดการได้ถูกต้อง

ข้อควรระวัง — นามสกุลไม่สอดคล้องกันระหว่างวิดเจ็ตกับ CLI

วิดเจ็ตและ CLI ไม่ได้ค้นหานามสกุลเดียวกัน CheckInput (AutoCrop3D.py:808) ค้นหาเพียง .nii.gz, .nrrd.gz, .gipl.gz โฟลเดอร์ของไฟล์ .nii หรือ .nrrd ที่ไม่บีบอัดจะถูก UI ปฏิเสธ ("Wrong type of patient file detected") แม้ CLI จะจัดการได้อย่างสมบูรณ์ และเนื่องจาก nbFiles มาจากรายการ เดียวกันนั้น ตัวหารของแถบความคืบหน้าจึงผิดทันทีที่มีนามสกุล ปะปนกัน

ข้อควรระวัง — ฟิลด์ของ ROI ที่ถูกละเลย

coordinateSystem และ orientation ของ ROI ถูกละเลยโดยเส้นทาง CLI (§3) กล่องที่หมุนหรือ ROI ที่บันทึกใน RAS: ผลลัพธ์ผิดโดยไม่แจ้งเตือน

ข้อควรระวัง — การตัดเศษของดัชนี

.astype(int) ตัดเศษเข้าหาศูนย์ ดังนั้น Upper อาจเสียไปได้ถึงหนึ่งวอกเซลต่อ แกน ไม่มีผลทางคลินิก แต่การครอปไม่สมมาตรรอบ จุดศูนย์กลางที่ขอ

ข้อควรระวัง — ไม่ตรวจสอบการตัดกัน

ไม่มีการตรวจสอบว่า ROI ตัดกับวอลุ่ม การจำกัดค่าบังคับ Lower ≥ 0 และ Upper ≤ size แต่ไม่มีสิ่งใดป้องกัน Lower > Upper หลัง การจำกัด: ได้ภาพขนาดศูนย์และการเขียนล้มเหลวภายใน try/except ที่บันทึก Lower/Upper

ข้อควรระวัง — การแทนที่พาธที่กว้างเกินไป

.replace(basename, filename) แทนที่ทุกตำแหน่งที่พบใน พาธที่ต่อกัน (AutoCrop3D_CLI.py:129): โฟลเดอร์ที่มีชื่อเดียวกับไฟล์จะถูกเปลี่ยนชื่อด้วย

ข้อควรระวัง — Crop Volume ล้างฉาก

เส้นทาง Crop Volume: slicer.mrmlScene.Clear(0) ทุกผู้ป่วย (AutoCrop3D.py:998) — ล้าง ฉากทั้งหมด รวมถึงข้อมูลใด ๆ ที่ผู้ใช้โหลดไว้

ข้อควรระวัง — การเข้าถึง MRML นอกเธรดหลัก

เส้นทาง Crop Volume: slicer.util.saveNode ถูกเรียกจาก threading.Thread (AutoCrop3D.py:979) หมายถึง เข้าถึง MRML นอกเธรดหลัก while thread.is_alive(): processEvents() ที่ตามมา ทำให้การทำงานเป็นลำดับโดยปริยาย ซึ่งซ่อนปัญหาไว้โดยไม่ได้แก้

ข้อควรระวัง — ส่วนต่อท้ายที่ใช้ไม่ครบ

เส้นทาง Crop Volume: ส่วนต่อท้ายใช้เฉพาะกับไฟล์ .nii.gz ไฟล์ .nrrd ออกมาโดยไม่มีส่วนต่อท้าย ด้วยชื่อสัมพัทธ์เดิม

ข้อควรระวัง — unit test ที่ใช้การไม่ได้

unit test ไม่ได้ทดสอบอะไรเลย test_AutoCrop3D1 ถูกนิยามสองครั้ง: เมธอดของคลาสที่มีเพียง docstring (ถูกเรียกโดย runTest) แล้วตามด้วยฟังก์ชันระดับโมดูล (AutoCrop3D.py:1097) ซึ่งมีการทดสอบจริงแต่ไม่เคยถูกรัน

โค้ดที่ไม่ถูกใช้งาน

โค้ดที่ไม่ถูกใช้งาน: CropCBCT.py (ระบุไว้ใน docstring ของตัวเอง) Autofill() ซึ่งยังมีพาธสัมบูรณ์ จากเครื่องที่ใช้พัฒนา registerSampleData() ซึ่งอ้างถึง AutoCrop3D2.png — ไฟล์ที่ไม่มีในรีโพสิทอรี
