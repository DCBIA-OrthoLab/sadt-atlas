ไฟล์ markups ROI json (.mrk.json) อ่านดังนี้ (AutoCrop3D_CLI.py:63-68):

ROI = json.load(open(roi_path))['markups'][0]
roi_center = np.array(ROI['center'])
roi_size = np.array(ROI['size'])

lower = roi_center - roi_size / 2

สามฟิลด์ของ json ถูกเพิกเฉย และนั่นคือที่มาหลักของความประหลาดใจ:

  • coordinateSystem ไฟล์ทดสอบ ROI.mrk.zip (ใน AutoCrop3D/Crop_Volumes_UI/Resources/testfiles/AutoCrop3D/) ประกาศ "coordinateSystem": "LPS" ซึ่งเป็นแบบแผนของที่เก็บโค้ด (ตัวเขียน markups ทุกตัวกำหนด "LPS" ตายตัว: ALI_CBCT, ASO_CBCT, AREG_CBCT, FlexReg, VFACE) center จึงอยู่ใน LPS ตรงกับที่ TransformPhysicalPointToContinuousIndex ของ SimpleITK คาดหวัง แต่ไม่เคยอ่านฟิลด์นี้: ROI ที่บันทึกใน RAS จะให้จุดศูนย์กลางที่ x และ y มีเครื่องหมายตรงข้าม โดยไม่มีข้อความใดเลย
  • orientation (เมทริกซ์ 3×3 ของกล่อง) ถูกเพิกเฉย: สมมุติว่ากล่องเรียงตามแกน LPS ในไฟล์ทดสอบมันคือ diag(-1,-1,1) การหมุน 180° รอบ z: ไม่มีผลกับกล่องที่อยู่กึ่งกลาง ROI ที่หมุนจริงจะถูกปฏิบัติเงียบ ๆ เหมือนกล่องขอบเขตที่เรียงตามแกนของมันเอง นั่นคือเหตุผลที่แท้จริงที่ช่องทำเครื่องหมาย "tilted images" มีอยู่ (§5)
  • ไม่ใช่การแบ่งส่วนหรือกล่องขอบเขตที่คำนวณ: กล่องมาจาก json นี้เท่านั้น ไม่มีโค้ดที่ไหนเลยที่หา ROI จาก labelmap

4. กล่องถูกใช้อย่างไร: การดึงตามดัชนี ไม่มีการ resample

คำอธิบายภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

นี่คือจุดสำคัญ: ไม่มีการ interpolate การแปลงจากพิกัดจริงเป็นดัชนี ตามด้วยการตัด (AutoCrop3D_CLI.py:70-80, การ slice ที่ :96-98):

lower = np.array(img.TransformPhysicalPointToContinuousIndex(lower)).astype(int)
upper = np.array(img.TransformPhysicalPointToContinuousIndex(upper)).astype(int)
for i in range(3):
    if lower[i] > upper[i]:
        lower[i], upper[i] = upper[i], lower[i]
lower = [max(0, l) for l in lower]
upper = [min(img_size[i], u) for i, u in enumerate(upper)]
img_roi = img[lower[0]:upper[0], lower[1]:upper[1], lower[2]:upper[2]]

swap ไม่ใช่เรื่องตกแต่ง TransformPhysicalPointToContinuousIndex ใช้ตัวผกผันของเมทริกซ์ทิศทาง บนวอลุ่มที่ direction cosine เป็นลบในบางแกน (นั่นคือ บนสแกนบางชุด) มุม "ล่าง" ทางกายภาพกลายเป็นดัชนีที่ใหญ่ที่สุด: หากไม่มี swap การ slice จะว่างเปล่า นี่คือการจัดการ direction ที่ถูกต้อง

สิ่งที่การทำดัชนีของ SimpleITK รักษาไว้ ตรวจแล้ว: การ slice sitk.Image คง spacing และ direction เหมือนเดิมและคำนวณ origin ใหม่ของมุมที่ดึงออก บนวอลุ่ม 50×60×70 spacing 0.3 origin (10,20,30) direction diag(-1,-1,1) การ slice img[5:20,5:20,5:20] ให้ origin เป็น (8.5, 18.5, 31.5): เลื่อน -5·0.3 บน x และ y (ทิศทางลบ) และ +5·0.3 บน z ค่า voxel เหมือนอินพุตทุกบิต

ตรวจสอบแล้ว

เป็นจริงในVISORด้วย (SADT-VISOR AutoCrop3D/pipeline.py:301 slice แบบเดียวกัน) README ของ VISOR อ้างว่าเอาต์พุตเหมือนกันทุกไบต์กับ CLI ของ legacy บนสแกนทดสอบหนึ่งชุด (SADT-VISOR AutoCrop3D/README.md:204-221) การเปรียบเทียบนั้นไม่ได้รันซ้ำที่นี่

การ slice sitk.Image คง spacing และ direction เหมือนเดิม และคำนวณเฉพาะ origin ของมุมที่ดึงออกใหม่ ค่า voxel เหมือนอินพุตทุกบิต

โหมด "Keep the same size as input" (original_size=='True' อ่านจากอาร์กิวเมนต์ box_Size, AutoCrop3D_CLI.py:35,100-110): สร้างภาพว่างที่มีเรขาคณิตเดิม (sitk.Image(...) + CopyInformation) วางบล็อกที่ดึงออกกลับที่ตำแหน่งดัชนีเดิม และใช้ CopyInformation อีกครั้ง เรขาคณิตเหมือนอินพุตทุกประการ โดยทุกอย่างนอก ROI ถูกตั้งเป็น 0 สังเกตการกลับแกนของ GetArrayFromImage (z,y,x) ซึ่งโค้ดจัดการถูกต้อง

สิ่งที่เกิดกับการแปลงที่เกี่ยวข้อง: ไม่มีอะไร ไม่มี vtkMRMLTransformNode ไม่อ่านหรือเขียน .tfm ไม่มี HardenTransform เรขาคณิตถูกส่งผ่านด้วยเฮดเดอร์ทั้งหมด (origin/spacing/direction) และออฟเซ็ตของการตัดถูกซึมซับโดย origin

หมายเหตุ

ผลในทางปฏิบัติ: เมทริกซ์การลงทะเบียนที่คำนวณบนวอลุ่มเต็มยังใช้ได้ตามที่เป็นบนวอลุ่มที่ตัดแล้ว เพราะพิกัดทางกายภาพไม่ได้ขยับ นี่เป็นผลจากวิธีคำนวณ origin ใหม่ ไม่ได้รันการลงทะเบียนเพื่อตรวจ
