ADTLib: โค้ด

สำหรับนักพัฒนา: โค้ดร่วมที่ทุกโมดูลนำเข้า พร้อมโมดูลที่มันเข้ามาแทนที่ จำนวนสำเนา ข้อบกพร่องที่พบในโค้ด และสิ่งที่ เทสต์ ตรึงไว้ ภาพรวมที่อ่านง่าย พร้อมแอนิเมชันของโปรโตคอลความคืบหน้า อยู่ในหน้าแอตลาส

โค้ดร่วม โค้ด แอตลาส (คำอธิบาย)
หมายเหตุ

หน้านี้อธิบาย ADT/ADTLib บน upstream/main และเป็นหน้าเดียวของแอตลาสนี้ที่บันทึกโค้ดซึ่งผู้ใช้ไม่เคยเปิดดู ที่มีหน้านี้ก็เพราะพฤติกรรมของโมดูลต่าง ๆ ขึ้นอยู่กับมันในตอนนี้ ผู้อ่านที่ตามหาว่า AREG ทำอะไรกับ surface จะต้องไปจบที่ ADTLib/io/surface.py ไม่ใช่ AREG/

1. ตำแหน่งของมัน

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

อยู่ใต้ทุกสิ่ง และไม่อยู่ในไปป์ไลน์ใดเลย ADTLib ถูกประกาศเป็นอันดับแรกใน CMakeLists.txt ของ extension, "Shared code, declared before the modules that import it" และไดเรกทอรีเครื่องมือทั้งยี่สิบแห่งนำเข้าจากมัน มันไม่มี Process ของตัวเอง ไม่มีอะไรให้รัน และไม่มีอะไรให้ดาวน์โหลด

ขนาดของมัน นับจากต้นไม้ไฟล์: ยี่สิบเอ็ดไฟล์ ประมาณ 3 100 บรรทัด (3 144) แทนที่สำเนาที่รวมกันยาวหลายพันบรรทัด (ส่วนหัวของไฟล์ระบุขนาดของสำเนา ไม่ใช่ขนาดของแพ็กเกจ) ส่วนหัวของ theming.py ไฟล์เดียวก็เป็นบรรทัดซ้ำถึง 1 926 บรรทัด และ env/conda.py เป็น 656 บรรทัดใน 40 ฟังก์ชัน

2. โมดูลเข้าถึงมันอย่างไร

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

Slicer วางไดเรกทอรี qt-scripted-modules ของแต่ละ extension ไว้บน sys.path ดังนั้น import ADTLib ธรรมดาจึงใช้ได้จากทุกโมดูลของ extension และจาก CLI แบบ scripted เส้นทางที่สามสำคัญกว่าที่เห็น: เมื่อโมดูลเผยแพร่เส้นทางค้นหาโมดูลของ Slicer เข้าไปใน Conda environment ชื่อ shapeaxi แล้ว ADTLib ก็นำเข้าได้ที่นั่นด้วย นี่คือสิ่งที่ ADTLib.env.install_pytorch พึ่งพา: ไม่เคยถูกนำเข้าโดยวิดเจ็ต แต่ถูกรันเป็น python -m ADTLib.env.install_pytorch โดยอินเทอร์พรีเตอร์ของ Conda

ข้อควรระวัง

ADTLib/__init__.py และ io/__init__.py ต้องไม่มีการนำเข้าใด ๆ เพราะไฟล์เหล่านี้รันใน Conda environment แบบเบาด้วย ซึ่งไม่มีทั้ง vtk, qt และ slicer การนำเข้าตัวใดตัวหนึ่งเหล่านั้นเพียงครั้งเดียวในระดับแพ็กเกจจะทำให้การนำเข้าทุก submodule บนเส้นทางนั้นพัง submodule ที่ต้องใช้พวกมันจึงนำเข้าเอง package_root() มีอยู่ด้วยเหตุผลเดียวกัน: มันคืนไดเรกทอรีที่ต้องอยู่บน PYTHONPATH เพื่อให้ฝั่ง Conda หาแพ็กเกจเจอ

3. สัญญาร่วม

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

สามโมดูลถือสิ่งที่เครื่องมือสัญญาต่อกัน ไม่ใช่สิ่งที่พวกมันคำนวณ

โมดูลสิ่งที่มันแทนที่สิ่งที่มันกำหนดให้ชัด
method.pyการประกาศ Method(ABC) หกรายการ 934 บรรทัดที่ส่วนใหญ่เป็นสัญญามากกว่าโค้ดแกนหลัก (Process, TestProcess, NumberScan, search) พร้อม mixin สามตัว ได้แก่ landmark, checkbox, DICOM เพราะทั้งหกไม่ได้ทับซ้อนกันแบบสุ่ม: เมื่อวัดเทียบกันแล้ว มีสามกลุ่มที่เด่นชัดไม่ใช่ความบังเอิญ
requests.pyไม่มี มันเพียงตั้งชื่อสิ่งที่ไม่เคยถูกเขียนไว้การเข้าถึง kwargs["..."] จำนวน 473 ครั้งโดยไม่มีรายการที่ใดเลย ตอนนี้แต่ละตระกูลประกาศฟิลด์ของตัวเอง คีย์ที่ไม่รู้จักจะถูกปฏิเสธตอนสร้างอ็อบเจกต์ และคีย์ที่ขาดคือ MISSING: ยก KeyError ตัวเดิม ณ จุดเดิม แทนที่จะกลายเป็นค่าว่างแบบเงียบ ๆ
progress_protocol.pyธรรมเนียมที่ไม่มีเอกสารสามแบบบนช่องทางเดียวดูด้านล่าง
ข้อบกพร่องที่ยืนยันในโค้ด

Slicer คูณ <filter-progress> ด้วยหนึ่งร้อย และตัวคูณนั้นไม่ได้ถูกเขียนไว้ที่ใดเลย มันทำให้เกิดสามธรรมเนียมในที่เก็บโค้ดเดียว: CLI ที่พิมพ์เศษส่วน 0.42 ทำให้ 42 ปรากฏและแถบเลื่อนไปข้างหน้า ซึ่งเป็นการใช้งานที่ตั้งใจไว้; CLI ที่พิมพ์จำนวนเต็ม 2 ทำให้ 200 ปรากฏ ซึ่งแถบใดก็แสดงไม่ได้ อินเทอร์เฟซจึงเทียบกับ 200 เพื่อรู้ว่าผู้ป่วยอีกหนึ่งรายเสร็จแล้ว และ CLI ส่งมันเป็นพัลส์ 0 → 2 → 0 เพราะ Slicer แจ้งวิดเจ็ตก็ต่อเมื่อค่าเปลี่ยน; ส่วน AMASSS ซึ่งรับทั้งสองแบบ ก็เดาตอนรันว่าตัวไหนที่ได้รับ (if progress > 1: progress /= 100) ตอนนี้ทั้งสามถูกตั้งชื่อแล้ว โดยค่าคงที่เก็บค่าตามที่อินเทอร์เฟซเห็น เพราะนั่นคือจุดที่เกิดการเปรียบเทียบ

4. สภาพแวดล้อม

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

สี่โมดูล และเป็นส่วนเดียวของ ADTLib ที่เอื้อมออกไปนอกโพรเซส

โมดูลสิ่งที่มันแทนที่
env/conda.pyฟังก์ชันละหกสำเนา 40 ฟังก์ชัน 656 บรรทัด เพี้ยนไปเป็นสามรูปแบบ หนึ่งในนั้นยังมี return ที่ไปไม่ถึงใน check_lib_wsl ซึ่งอ่านสองชื่อที่ไม่มีอะไรผูกไว้
env/deps.pycheck_lib_installed เก้าสำเนาภายใต้คำตอบสามแบบที่เข้ากันไม่ได้สำหรับคำถามเดียวกัน: AREG และ FlexReg เขียน if required_version: pass ซึ่งเป็นจริงทันทีที่ติดตั้งไลบรารีไว้เลย เงื่อนไขเวอร์ชันจึงเป็นแค่ของประดับ
env/cuda.pyปัญหารายการสถาปัตยกรรม: wheel ของ torch มีเคอร์เนลที่คอมไพล์ไว้สำหรับรายการสถาปัตยกรรมที่ตายตัว
env/install_pytorch.pyแท็กของ wheel pytorch3d คำนวณจาก torch ที่ติดตั้งอยู่ แทนที่จะปล่อยให้ pip เลือก
ข้อควรระวัง

wheel ของ pytorch3d ที่แท็กไม่ตรงกับ torch ที่ติดตั้งอยู่จะขัดข้องด้วย undefined symbol ตอนนำเข้า ไม่ใช่ตอนติดตั้ง แท็ก 0.7.9+pt2110cu128 หมายถึง torch 2.11.0 และ CUDA 12.8; ดัชนีคือ ImageMindAnalytics.github.io/pytorch3d-wheels เพราะ PyPI ไม่มี wheel สำหรับชุดเวอร์ชันสมัยใหม่ และดัชนีเดิม fbaipublicfiles หยุดอยู่ที่ Python 3.9 / torch 2.0 torch ถูกติดตั้งที่นี่ด้วย เพราะการคำนวณแท็กจาก torch ตัวใดก็ตามที่มีอยู่จะใช้ได้ก็ต่อเมื่อ torch ตัวนั้นมี wheel อยู่แล้วเท่านั้น: condaCreateEnv(["torch>=2.8,<2.13", …]) ได้ผลเป็น 2.12.1+cu130 เมื่อวันที่ 2026-09-16 ซึ่งเป็นชุดที่ดัชนีไม่มีให้

5. การอ่าน การเขียน การตั้งชื่อ

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

โมดูลสำเนาที่ถูกแทนที่สิ่งที่ตัดสินใจไว้
io/fs.pysearch ในสิบห้าสำเนา หกรูปแบบหกรายการเป็นเมธอด search(self, …) และสามรายการเป็นสิ่งเดียวกันในรูปฟังก์ชันอิสระ: ตรงกันทุกไบต์เมื่อเอา self ออก ความต่างที่มีสาระจริงมีเพียงสองข้อ และกลายเป็นพารามิเตอร์
io/landmarks.pyLoadJsonLandmarks ×3 เหมือนกันทุกประการ, WriteJson ×2รูปแบบที่แตกต่างกันจริง ๆ ได้แก่ของ ASO_CBCT, ALI_CBCT, ALI_IOS อยู่ที่เดิม
io/surface.pyReadSurf ×5, WriteSurf ×4ต่างจากส่วนที่เหลือ กลุ่มนี้เพี้ยนไปจากกัน; จึงวัดความต่างก่อนเลือกเก็บไว้หนึ่งแบบ
labels.pyGetLabelSurface และ isLabelSurface ×5เมธอดของคลาส vtkTeeth ห้าคลาสที่เองก็เป็นสำเนา ข้าม ASO_IOS_utils, FlexReg_utils, FlexReg_Method ×2 และ AREG_IOS_utils
naming.pyหกจุดที่ต่อการเรียก .split(...)[0] สิบสี่ครั้งตามลำดับเดียวกันลำดับนี้สำคัญ: ตัวกำกับที่ยาวกว่าต้องถูกตัดก่อนตัวที่สั้นกว่าซึ่งอยู่ในมัน ไม่เช่นนั้น _Scanreg จะเสียส่วนท้ายให้ _Scan และไฟล์สองไฟล์จะจับคู่กันไม่ได้
geometry.pyสองถึงสี่สำเนาที่เหมือนกันทุกประการในแต่ละรายการวัดทีละบรรทัดข้าม AREG_IOS_utils, ASO_IOS_utils, FlexReg_Method, ASO_CBCT_utils; ตัวที่แตกต่างกันจริง ๆ (RotationMatrix ของ FlexReg, TransformSurf ของ ALI_IOS) อยู่นอกเรื่องนี้

6. ส่วนที่เหลือ

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

โมดูลสิ่งที่มันบรรจุ
logging_setup.py151 ไฟล์มีสิบบรรทัดเดียวกัน แต่ละไฟล์ตั้ง propagate = False และผูก StreamHandler ของตัวเอง ซึ่งเป็นสิ่งที่ทำให้ควบคุมการบันทึก log ของ extension ไม่ได้: การยกระดับ log หรือส่งการรันไปยังไฟล์ ต้องแก้ทุกไฟล์
theming.pyสำเนาของรอบเวียนซ้ำสิบเอ็ดชุด และ applyDarkModeStyles เก้าชุด 1 926 บรรทัด ที่เริ่มเพี้ยนแล้ว: !important ที่ไม่มีผลที่หนึ่ง และอีกสำเนาหนึ่งขาดการ์ด hasattr ที่กันไม่ให้การเวียนซ้ำเลยไปถึงวิดเจ็ตแม่
testdata.pyDownloadUnzip เจ็ดสำเนาที่มีความผิดพลาดสามแบบที่ต่างกัน และทั้งสามถูกทำซ้ำได้: หนึ่งในนั้นคือ ไม่ใช่ทุกอย่างที่เผยแพร่เป็น zip โดย CBCT ของ ALI ชี้ไปที่ MG_test_scan.nii.gz และถูกส่งตรงเข้า zipfile.ZipFile
model_registry.pyเฉพาะฐานของรุ่นที่เผยแพร่ เท่านั้น โดยตั้งใจไม่ระบุว่าเครื่องมือหนึ่งเสนอโมเดลใดบ้าง: การเลือกนั้นเป็นของเครื่องมือ ซึ่งเป็นเหตุที่พจนานุกรม getModelUrl อยู่ที่เดิม
ส่วนที่ตกค้างของ MRI2CBCTตั้งแต่ MRI2CBCT ถูกเขียนใหม่ โมดูลไม่ได้นำเข้า method.py อีกต่อไป (ส่วนหัวของ method.py ยังระบุชื่อมันไว้ในหกตัวนั้น); MRI2CBCT_TEST_FILES และ TMJ_CROP_MODEL ใน model_registry.py ไม่มีผู้อ่าน และ TMJ_CROP_MARKERS ใน naming.py ถูกอ่านโดย test_naming.py เท่านั้น สิ่งที่แผงใช้จริง: testdata, env.deps, env.cuda
format.pyฟังก์ชันล้วน ใช้ไลบรารีมาตรฐานเท่านั้น: ถูกนำเข้าโดยทั้ง extension จึงต้องไม่พึ่งพาสิ่งใด

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

ADTLib มีเทสต์ 22 รายการใน ADT/Testing/Python/ เพิ่มจากสองรายการ เทสต์เหล่านี้ใกล้เคียงข้อกำหนดที่สุดที่ชั้นร่วมนี้มี และหลายรายการถูกเขียนขึ้นเพราะการ grep อย่างเดียวไม่พอ

test_pip_requirements.py บอกเหตุผลไว้ในส่วนหัวของมันเอง: ทุกคู่ (library, version) ที่ที่เก็บโค้ดส่งให้ pip ต้องแยกวิเคราะห์ได้ เพราะ f'{lib}=={version}' ถูกต้องก็ต่อเมื่อทุกรายการมีเวอร์ชันเปล่า ๆ เท่านั้น และสามโมดูลได้เงื่อนไขที่มีตัวดำเนินการเข้ามาโดยไม่ทันสังเกต ทำให้เกิด dicom2nifti==>=2.6.2 ซึ่ง pip ปฏิเสธทันที ข้อบกพร่องนี้มองไม่เห็นบนเครื่องที่ติดตั้งไลบรารีไว้แล้ว ดังนั้นต่อให้รันโมดูลบนเครื่องกี่ครั้งก็ไม่เจอ เทสต์นี้เดินผ่านซอร์สแทนที่จะใช้รายการที่เขียนด้วยมือ รายการที่วันพรุ่งนี้มีเงื่อนไขเพิ่มเข้ามาจึงถูกครอบคลุมโดยไม่ต้องมีใครจำ

เทสต์อื่น ๆ ตั้งชื่อพฤติกรรมที่หน้าเครื่องมืออธิบายไว้: test_ali_cbct_bounds.py, test_ali_cbct_budget.py, test_ali_progress_contract.py, test_aso_cbct_report_is_not_landmarks.py, test_aso_ios_landmark_intersection.py, test_areg_review_skips_the_report.py, test_output_folder_survives_mode_switch.py บวกยูนิตเทสต์ของโมดูลร่วมเอง ได้แก่ test_fs, test_labels, test_naming, test_surface, test_requests, test_progress_protocol, test_deps, test_cuda_channel, test_context_managers, test_button_style

ตรวจสอบแล้ว

รันเมื่อ 2026-11-10 ด้วย PythonSlicer -m unittest discover ใน ADT/Testing/Python (Slicer 5.12.4, สำเนาของต้นไม้ 3c67957): เมื่อมี torch 2.2.0 217 เทสต์ ผ่านทั้งหมด เมื่อทำให้ torch นำเข้าไม่ได้ การรันเดิมรายงาน192 เทสต์: ผ่าน 188 และผิดพลาด 4 ทั้งสี่คือ ModuleNotFoundError: torch ตอนนำเข้าไฟล์เทสต์ ALI_CBCT สี่ไฟล์ ซึ่งไปถึง ADTLib/env/cuda.py และ preferred_device() ของมันตอนนำเข้า นี่เป็นคุณสมบัติของสภาพแวดล้อม ไม่ใช่ของโค้ด: ไม่มี torch ก็ไม่มีการตรวจอุปกรณ์

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

นิสัยสองข้อทำให้อ่านเข้าใจได้ ข้อแรก ส่วนหัวของทุกโมดูลระบุว่ามันแทนที่อะไรและสำเนาเหล่านั้นไม่ลงรอยกันเรื่องอะไร: เหตุผลอยู่ตรงนั้น ไม่ใช่ในหน้านี้ ข้อที่สอง บรรทัดที่ซ้ำอยู่ในส่วนหัวเหล่านั้นคือสิ่งที่ถูกปล่อยไว้: รูปแบบที่แตกต่างกันจริง ๆ อยู่ในเครื่องมือของมันต่อไป TestScan และ TestModel ไม่อยู่ใน method.py เพราะจำนวนอาร์กิวเมนต์ของมันต่างกันชัดเจนจากเครื่องมือหนึ่งไปอีกเครื่องมือหนึ่ง สูงสุดสี่ตัวใน AREG และ getModelUrl คืนการเลือกเฉพาะของแต่ละเครื่องมือ การยกมันขึ้นมาจะหมายถึงการประดิษฐ์สัญญาที่ไม่มีเครื่องมือใดในหกตัวนั้นเคยปฏิบัติตามจริง
