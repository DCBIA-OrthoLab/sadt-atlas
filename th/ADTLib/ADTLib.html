ADTLib

ไม่ใช่เครื่องมือ: ไม่มีอินเทอร์เฟซ ไม่มี pipeline ไม่มีโมเดล ADTLib คือโค้ดที่โมดูลทั้งยี่สิบ import ไปใช้ และแทบทุกไฟล์ของมันมีอยู่เพราะฟังก์ชันเดียวกันเคยถูกคัดลอกไปมาระหว่างสองถึงสิบห้าครั้ง ส่วนหัวของแต่ละโมดูลบันทึกว่ามันเข้ามาแทนที่สำเนากี่ชุด และสำเนาเหล่านั้นเริ่มขัดแย้งกันเรื่องอะไร: ตัวเลขนั้นคือใจความของหน้านี้

หมายเหตุ

หน้านี้อธิบาย ADT/ADTLib บน upstream/main และเป็นหน้าเดียวของแอตลาสนี้ที่บันทึกโค้ดซึ่งไม่มีผู้ใช้คนใดเปิดดู ที่มีอยู่เพราะพฤติกรรมของโมดูลขึ้นกับมันแล้ว: ผู้อ่านที่ตามหาว่า AREG ทำอะไรกับพื้นผิว จะไปจบที่ ADTLib/io/surface.py ไม่ใช่ AREG/

1. ตำแหน่งของมัน

อยู่ใต้ทุกอย่าง และไม่อยู่ใน pipeline ใด ADTLib ถูกประกาศเป็นอันดับแรกใน CMakeLists.txt ของส่วนขยาย "Shared code, declared before the modules that import it" และไดเรกทอรีเครื่องมือทั้งยี่สิบ import จากมัน มันไม่มี Process ของตัวเอง ไม่มีอะไรให้รัน และไม่มีอะไรให้ดาวน์โหลด

การวัดตัวเองของมัน จากส่วนหัวของโมดูล: ยี่สิบเอ็ดโมดูล ราว 3 300 บรรทัด เข้ามาแทนที่สำเนาที่รวมกันยาวหลายพันบรรทัด ส่วนหัวของ theming.py เพียงไฟล์เดียวบันทึกส่วนซ้ำซ้อน 1 926 บรรทัด และ env/conda.py บันทึก 656 บรรทัดข้ามสี่สิบฟังก์ชัน

2. โมดูลเข้าถึงมันอย่างไร

Slicer วางไดเรกทอรี qt-scripted-modules ของแต่ละส่วนขยายไว้ใน sys.path ดังนั้น import ADTLib ธรรมดาจึงใช้ได้จากทุกโมดูลของส่วนขยายและจาก CLI แบบสคริปต์ เส้นทางที่สามสำคัญกว่าที่เห็น: เมื่อโมดูลต่าง ๆ เผยแพร่พาธค้นหาโมดูลของ Slicer เข้าไปในสภาพแวดล้อม Conda ของ shapeaxi ADTLib ก็ import ได้ที่นั่นด้วย นั่นคือสิ่งที่ ADTLib.env.install_pytorch พึ่งพา: วิดเจ็ตไม่เคย import มัน แต่ถูกรันเป็น python -m ADTLib.env.install_pytorch โดยอินเทอร์พรีเตอร์ของ Conda

ข้อควรระวัง

ADTLib/__init__.py และ io/__init__.py ต้องไม่มี import ทั้งสองไฟล์ทำงานในสภาพแวดล้อม Conda แบบเบาด้วย ซึ่งไม่มีทั้ง vtk, qt และ slicer การ import สิ่งเหล่านั้นเพียงตัวเดียวที่ระดับแพ็กเกจจะทำให้การ import ซับโมดูลทุกตัวบนเส้นทางนั้นพัง ซับโมดูลที่ต้องการสิ่งเหล่านี้ import เอง package_root() มีอยู่ด้วยเหตุผลเดียวกัน: มันคืนไดเรกทอรีที่ต้องอยู่ใน PYTHONPATH เพื่อให้ฝั่ง Conda หาแพ็กเกจเจอ

3. สัญญาร่วม

สามโมดูลบรรจุสิ่งที่เครื่องมือสัญญาต่อกัน ไม่ใช่สิ่งที่พวกมันคำนวณ

โมดูลสิ่งที่มันเข้ามาแทนที่สิ่งที่มันตกลงให้ชัด
method.pyประกาศ Method(ABC) หกชุด 934 บรรทัดที่ส่วนใหญ่เป็นสัญญามากกว่าโค้ดแกนหลัก (Process, TestProcess, NumberScan, search) พร้อม mixin สามชุด คือ landmark, checkbox, DICOM เพราะทั้งหกชุดไม่ได้ซ้อนกันแบบสุ่ม: เมื่อวัดเทียบกันแล้ว มีสามกลุ่มโดดเด่นชัดเจน
requests.pyไม่มีอะไร; มันตั้งชื่อสิ่งที่ไม่เคยถูกเขียนไว้การเข้าถึง kwargs["..."] 473 ครั้งโดยไม่มีรายการอยู่ที่ใดเลย ตอนนี้แต่ละตระกูลประกาศฟิลด์ของตัวเอง คีย์ที่ไม่รู้จักถูกปฏิเสธตอนสร้าง และคีย์ที่ขาดคือ MISSING: ยก KeyError เดิมที่ตำแหน่งเดิม แทนที่จะกลายเป็นค่าว่างที่ไม่มีเสียง
progress_protocol.pyข้อตกลงที่ไม่มีเอกสารสามแบบบนช่องทางเดียวดูด้านล่าง
ข้อบกพร่องที่ยืนยันในโค้ด

Slicer คูณ <filter-progress> ด้วยหนึ่งร้อย และตัวคูณนั้นไม่ได้เขียนไว้ที่ใดเลย ทำให้เกิดข้อตกลงสามแบบในที่เก็บโค้ดเดียว: CLI ที่พิมพ์เศษส่วน 0.42 ทำให้ 42 ปรากฏและแถบเดินหน้า ซึ่งเป็นการใช้ตามเจตนา; CLI ที่พิมพ์จำนวนเต็ม 2 ทำให้ 200 ปรากฏ ซึ่งแถบใดแสดงไม่ได้ อินเทอร์เฟซจึงเปรียบเทียบกับ 200 เพื่อรู้ว่าผู้ป่วยอีกหนึ่งคนเสร็จแล้ว และ CLI ส่งมันเป็นพัลส์ 0 → 2 → 0 เพราะ Slicer แจ้งวิดเจ็ตเฉพาะเมื่อค่าเปลี่ยน; และ AMASSS ซึ่งได้รับทั้งสองแบบ เดาตอนรันว่าตัวเองถืออะไรอยู่ (if progress > 1: progress /= 100) ตอนนี้ทั้งสามมีชื่อแล้ว โดยค่าคงที่เก็บค่าตามที่อินเทอร์เฟซเห็น เพราะการเปรียบเทียบเกิดขึ้นที่นั่น

4. สภาพแวดล้อม

สี่โมดูล และเป็นส่วนเดียวของ ADTLib ที่ยื่นออกไปนอก process

โมดูลสิ่งที่มันเข้ามาแทนที่
env/conda.pyฟังก์ชันละหกสำเนา สี่สิบฟังก์ชัน 656 บรรทัด ที่เบี่ยงเบนไปเป็นสามรูปแบบ หนึ่งในนั้นยังมี return ที่ไปไม่ถึงใน check_lib_wsl ซึ่งอ่านชื่อสองตัวที่ไม่มีอะไรผูกไว้
env/deps.pycheck_lib_installed เก้าสำเนาที่ให้คำตอบสามแบบที่เข้ากันไม่ได้ต่อคำถามเดียวกัน: AREG และ FlexReg เขียน if required_version: pass ซึ่งเป็นจริงทันทีที่ไลบรารีถูกติดตั้ง เงื่อนไขของรุ่นเป็นเพียงของประดับ
env/cuda.pyปัญหารายการสถาปัตยกรรม: torch wheel บรรจุ kernel ที่คอมไพล์ไว้สำหรับรายการสถาปัตยกรรมคงที่
env/install_pytorch.pyแท็กของ pytorch3d wheel คำนวณจาก torch ที่ติดตั้งอยู่ ไม่ปล่อยให้ pip เลือก
ข้อควรระวัง

pytorch3d wheel ที่แท็กไม่ตรงกับ torch ที่ติดตั้งจะล่มด้วย undefined symbol ตอน import ไม่ใช่ตอนติดตั้ง แท็ก 0.7.9+pt2110cu128 หมายถึง torch 2.11.0 และ CUDA 12.8; ดัชนีคือ ImageMindAnalytics.github.io/pytorch3d-wheels เพราะ PyPI ไม่เผยแพร่ wheel สำหรับชุดรุ่นสมัยใหม่ และดัชนี fbaipublicfiles ดั้งเดิมหยุดอยู่ที่ Python 3.9 / torch 2.0 torch ถูกติดตั้งที่นี่ด้วย เพราะการคำนวณแท็กจาก torch ใดก็ตามที่มีอยู่จะใช้ได้ก็ต่อเมื่อ torch ตัวนั้นมี wheel อยู่แล้ว: condaCreateEnv(["torch>=2.8,<2.13", …]) เคย resolve เป็น 2.12.1+cu130 เมื่อ 2026-09-16 ซึ่งเป็นชุดที่ดัชนีไม่ได้เผยแพร่

5. การอ่าน การเขียน การตั้งชื่อ

โมดูลสำเนาที่ถูกแทนที่สิ่งที่ตัดสินใจ
io/fs.pysearch ในสิบห้าสำเนา หกรูปแบบหกชุดเป็นเมธอด search(self, …) และสามชุดเป็นสิ่งเดียวกันในรูปฟังก์ชันอิสระ: เหมือนกันทุกไบต์เมื่อเอา self ออก ความต่างที่มีสาระมีเพียงสองข้อ และกลายเป็นพารามิเตอร์
io/landmarks.pyLoadJsonLandmarks ×3 เหมือนกันทุกประการ, WriteJson ×2รูปแบบที่แตกต่างกันจริง คือของ ASO_CBCT, ALI_CBCT, ALI_IOS อยู่ที่เดิม
io/surface.pyReadSurf ×5, WriteSurf ×4ต่างจากส่วนที่เหลือ กลุ่มนี้เบี่ยงเบนไปแล้ว ความต่างถูกวัดก่อนจะเลือกเก็บแบบใดแบบหนึ่ง
labels.pyGetLabelSurface และ isLabelSurface ×5เมธอดของคลาส vtkTeeth ห้าคลาสที่ตัวมันเองก็เป็นสำเนา ข้าม ASO_IOS_utils, FlexReg_utils, FlexReg_Method ×2 และ AREG_IOS_utils
naming.pyหกจุดที่ต่อการเรียก .split(...)[0] สิบสี่ครั้งในลำดับเดียวกันลำดับนั้นแบกภาระไว้: ต้องตัดเครื่องหมายที่ยาวกว่าก่อนเครื่องหมายที่สั้นกว่าที่อยู่ในมัน ไม่เช่นนั้น _Scanreg จะเสียส่วนท้ายให้ _Scan และสองไฟล์จะหยุดจับคู่กัน
geometry.pyสองถึงสี่สำเนาที่เหมือนกันทุกประการต่อหนึ่งฟังก์ชันวัดทีละบรรทัดข้าม AREG_IOS_utils, ASO_IOS_utils, FlexReg_Method, ASO_CBCT_utils; ส่วนที่แตกต่างกันจริง (RotationMatrix ของ FlexReg, TransformSurf ของ ALI_IOS) ไม่ถูกรวมเข้ามา

6. ส่วนที่เหลือ

โมดูลสิ่งที่มันบรรจุ
logging_setup.py151 ไฟล์มีสิบบรรทัดเดียวกัน แต่ละไฟล์ตั้ง propagate = False และผูก StreamHandler ของตัวเอง ซึ่งเป็นสิ่งที่ทำให้การควบคุม logging ของส่วนขยายเป็นไปไม่ได้: การยกระดับ log หรือส่งการรันไปยังไฟล์ต้องแก้ทุกไฟล์
theming.pyสิบเอ็ดสำเนาของการเดินแบบเรียกซ้ำ และเก้าสำเนาของ applyDarkModeStyles 1 926 บรรทัด ที่เริ่มเบี่ยงเบนแล้ว: มี !important ที่ไม่ทำงานอยู่ที่หนึ่ง และมีสำเนาหนึ่งที่ขาดตัวป้องกัน hasattr ที่กันไม่ให้การเรียกซ้ำเข้าไปที่วิดเจ็ตแม่
testdata.pyเจ็ดสำเนาของ DownloadUnzip ที่ผิดสามแบบต่างกัน และทั้งสามถูกทำซ้ำ: ในนั้นมีกรณีที่ไม่ใช่ทุกอย่างที่เผยแพร่เป็น zip จุดเข้า CBCT ของ ALI ชี้ไปที่ MG_test_scan.nii.gz และถูกส่งตรงเข้า zipfile.ZipFile
model_registry.pyเฉพาะฐานของ releaseเท่านั้น มันจงใจไม่ระบุว่าเครื่องมือเสนอโมเดลตัวไหน: การเลือกนั้นเป็นของเครื่องมือ นั่นคือเหตุผลที่พจนานุกรม getModelUrl อยู่ที่เดิม
ส่วนที่เหลือของ MRI2CBCTตั้งแต่การเขียน MRI2CBCT ใหม่ โมดูลไม่ import method.py อีก (ส่วนหัวของ method.py ยังระบุชื่อมันไว้ในหกโมดูล); MRI2CBCT_TEST_FILES และ TMJ_CROP_MODEL ใน model_registry.py ไม่มีผู้อ่าน และ TMJ_CROP_MARKERS ใน naming.py ถูกอ่านโดย test_naming.py เท่านั้น สิ่งที่แผงใช้จริง: testdata, env.deps, env.cuda
format.pyฟังก์ชันล้วน ใช้เฉพาะไลบรารีมาตรฐาน: ถูก import โดยทั้งส่วนขยาย จึงห้ามพึ่งพาอะไรเลย

7. สิ่งที่การทดสอบตรึงไว้

ADTLib มาพร้อมการทดสอบ 22 ชุดใน ADT/Testing/Python/ เพิ่มจากสองชุดเดิม ซึ่งเป็นสิ่งที่ใกล้เคียงข้อกำหนดที่สุดที่ชั้นร่วมนี้มี และหลายชุดถูกเขียนขึ้นเพราะ grep ไม่เพียงพอ

test_pip_requirements.py บอกเหตุผลไว้ในส่วนหัวของตัวเอง: ทุกคู่ (library, version) ที่ที่เก็บโค้ดส่งให้ pip ต้องแยกวิเคราะห์ได้ เพราะ f'{lib}=={version}' ถูกต้องเฉพาะเมื่อทุกรายการมีรุ่นเปล่า ๆ และสามโมดูลเคยเพิ่มเงื่อนไขที่มีตัวดำเนินการอย่างเงียบ ๆ จนเกิด dicom2nifti==>=2.6.2 ซึ่ง pip ปฏิเสธทันที ข้อบกพร่องนี้มองไม่เห็นบนเครื่องที่มีไลบรารีอยู่แล้ว การรันโมดูลในเครื่องจึงไม่เคยแสดงให้เห็น การทดสอบเดินผ่านซอร์สโค้ดแทนรายการที่เขียนด้วยมือ ดังนั้นรายการที่เพิ่มเงื่อนไขในวันพรุ่งนี้ก็ถูกครอบคลุมโดยไม่ต้องมีใครจำ

ชุดอื่น ๆ ตั้งชื่อพฤติกรรมที่หน้าของเครื่องมืออธิบายไว้: test_ali_cbct_bounds.py, test_ali_cbct_budget.py, test_ali_progress_contract.py, test_aso_cbct_report_is_not_landmarks.py, test_aso_ios_landmark_intersection.py, test_areg_review_skips_the_report.py, test_output_folder_survives_mode_switch.py และการทดสอบหน่วยของโมดูลร่วมเอง คือ test_fs, test_labels, test_naming, test_surface, test_requests, test_progress_protocol, test_deps, test_cuda_channel, test_context_managers, test_button_style

ตรวจสอบแล้ว

เมื่อรันภายใต้ PythonSlicer ธรรมดา ชุดทดสอบรายงาน 188 การทดสอบและ 4 ข้อผิดพลาด ทั้งสี่คือ ModuleNotFoundError: torch ในการทดสอบ ALI_CBCT ซึ่งไปถึง ADTLib/env/cuda.py ที่ฟังก์ชัน preferred_device() ตอน import นั่นเป็นคุณสมบัติของสภาพแวดล้อม ไม่ใช่ของโค้ด: ไม่มี torch ก็ไม่มีการตรวจอุปกรณ์

8. วิธีอ่านชั้นนี้

มีนิสัยสองข้อที่ทำให้อ่านเข้าใจได้ ข้อแรก ส่วนหัวของทุกโมดูลระบุว่ามันเข้ามาแทนที่อะไรและสำเนาขัดแย้งกันเรื่องอะไร: เหตุผลอยู่ที่นั่น ไม่ใช่ในหน้านี้ ข้อสอง บรรทัดที่ซ้ำไปมาในส่วนหัวเหล่านั้นคือสิ่งที่ถูกทิ้งไว้: รูปแบบที่แตกต่างกันจริงอยู่ในเครื่องมือของมันเอง TestScan และ TestModel ไม่อยู่ใน method.py เพราะจำนวนอาร์กิวเมนต์ต่างกันชัดเจนจากเครื่องมือหนึ่งไปอีกเครื่องมือหนึ่ง สูงสุดสี่ตัวใน AREG และ getModelUrl คืนการเลือกเฉพาะเครื่องมือ การยกพวกมันขึ้นมาจะหมายถึงการประดิษฐ์สัญญาที่ไม่มีโมดูลใดในหกโมดูลปฏิบัติตามจริง
