CLIC บน VISOR: โค้ด

สำหรับนักพัฒนา: สิ่งที่พอร์ต VISOR ของ CLIC ทำในโค้ด พร้อมการอ้างอิงแบบ file:line โค้ด อาร์กิวเมนต์ สภาพแวดล้อม ความต่างจากโค้ด legacy และข้อค้นพบ คำอธิบายที่อ่านง่ายของไปป์ไลน์เดียวกัน พร้อมคณิตศาสตร์ อยู่ในหน้าแอตลาส

โค้ด แอตลาส (คำอธิบาย) VISOR เครือข่าย 1 ตัว หน้า Legacy คู่มือ (VISOR)

การอ้างอิงในหน้านี้ระบุรีโพซิทอรี แล้วพาธในนั้น แล้วบรรทัด: SADT-VISOR คือแค็ตตาล็อกเครื่องมือ (commit 6ba2a78), VISOR-serve คือเซิร์ฟเวอร์ (e9a7e5d), Remote คือไคลเอนต์ Slicer (AutomatedDentalToolsRemote 19b95e8), legacy คือ SlicerAutomatedDentalTools ที่ 3c67957 พาธเปล่าๆ เช่น pipeline.py:36 อยู่ใน SADT-VISOR tools/CLIC/src/sadt_clic/ ทุกอย่างอ่านจากโค้ด ไม่มีอะไรในหน้านี้ถูกรัน ภาพรวมของสแต็ก: VISOR

3.1 การค้นหาสแกน

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

scans เป็นไฟล์เดียวหรือโฟลเดอร์ โฟลเดอร์ถูกเดินแบบเรียกซ้ำด้วย os.walk ข้ามไฟล์ที่ซ่อน และเก็บเฉพาะชื่อที่ลงท้ายด้วย .nii หรือ .nii.gz (ไม่แยกตัวพิมพ์) เป็นพาธไฟล์ เรียงลำดับ (pipeline.py:58-79) ตัวรวบรวมของ legacy ยังโฆษณา .nrrd, .mha และ .mhd ซึ่ง nibabel อ่านไม่ได้ และคืนโฟลเดอร์ย่อยแทนไฟล์ (legacy §3.1)

SCAN_EXTENSIONS = (".nii", ".nii.gz")                 # pipeline.py:36
found = discover_scans(str(scans))                    # __init__.py:115
if not found:
    raise ValueError("No .nii or .nii.gz scan found in '...'. "
                     "CLIC reads NIfTI volumes; NRRD and MetaImage are not supported.")

ผลลัพธ์ว่างเป็น ValueError (__init__.py:116-123) ซึ่งเซิร์ฟเวอร์แปลงเป็น 422 พร้อมข้อความ (VISOR-serve server/execution/runner.py:243-244) อ้างถึงเฉพาะชื่อฐานของอินพุต ไม่ใช่พาธเต็ม

3.2 การเลือกและโหลด checkpoint

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

model เป็นทางเลือก เมื่อว่าง เครื่องมือมองใน <data_root>/CLIC/models (_own_models, __init__.py:30-37) และรับ .pth ตัวเดียวที่นั่น ไม่มีหรือมีหลายตัวคือการปฏิเสธที่ระบุชื่อตัวเลือก (_sole_checkpoint, :40-61) โฟลเดอร์ที่ระบุชื่อได้กฎเดียวกัน ไฟล์ที่ระบุชื่อใช้ตามที่เป็น (_resolve_checkpoint, :64-73)

จำนวนคลาสไม่ได้สมมติ อ่านจากรูปร่างของ classification head ใน state dict รวมพื้นหลัง และ head ทั้งสองถูกสร้างใหม่ตามขนาดนั้นก่อนโหลดน้ำหนัก (pipeline.py:96-144):

state = torch.load(checkpoint_path, map_location=device, weights_only=True)
classes = class_count(state)       # roi_heads.box_predictor.cls_score.bias .shape[0]
model = maskrcnn_resnet50_fpn(weights=None)
model.roi_heads.box_predictor  = FastRCNNPredictor(box_features, classes)
model.roi_heads.mask_predictor = MaskRCNNPredictor(mask_features, 256, classes)
model.load_state_dict(state)
model.to(device).eval()

checkpoint ที่เผยแพร่มีสี่คลาส (พื้นหลัง buccal bicortical palatal) ซึ่งเป็นสิ่งที่ catalogs.CLASSES = len(LABELS) + 1 คาดหวัง (catalogs.py:23-40) head ที่ผิดรูปหรือขาดหายเป็น ValueError ที่ระบุคีย์ (pipeline.py:109-123) resolve_device คง cuda เมื่อมองเห็นการ์ด และไม่เช่นนั้นถอยไปใช้ cpu พร้อมคำเตือน (pipeline.py:82-93)

3.3 ลูปสไลซ์

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

แต่ละสแกนถูกอ่านด้วย nibabel เป็น float32 (__init__.py:216-219) volume ที่ไม่ใช่ 3 มิติทำให้ล้มเหลวเฉพาะสแกนนั้น label volume เป็นอาร์เรย์ int16 รูปร่างเดียวกัน ลูปรันตามแกนอาร์เรย์ที่สามตามที่เก็บในไฟล์ โดยไม่ปรับทิศทาง เหมือนที่ runner แบบ legacy ทำ:

for index in range(volume.shape[2]):                          # pipeline.py:170
    image = normalise(volume[..., index])                     # min-max to [0, 1]
    tensor = torch.from_numpy(image).unsqueeze(0).repeat(3, 1, 1).float().to(device)
    with torch.no_grad():
        predicted = model([tensor])[0]                        # one slice per call
    keep = predicted["scores"] >= score_threshold             # default 0.7
    masks = (predicted["masks"][keep] > MASK_BINARY_THRESHOLD).squeeze(1)   # 0.5
    for mask, label in zip(masks.cpu().numpy(), predicted["labels"][keep].cpu().numpy()):
        labels[..., index][mask] = int(label)                 # last one wins
        detections += 1
  • การทำให้เป็นบรรทัดฐาน: ต่อสไลซ์ (x - min) / (max - min) สไลซ์เรียบ (ช่วง ≤ 1e-8) กลายเป็นศูนย์แทนที่จะเป็น NaN (pipeline.py:147-154) _norm ของ legacy เหมือนกัน (legacy CLIC/runner/clic_runner.py:44-46)
  • การปรับขนาดและการทำมาตรฐานแบบ ImageNet เกิดภายใน GeneralizedRCNNTransform ของ torchvision เหมือนใน legacy (legacy §4.1) เครื่องมือไม่สุ่มตัวอย่างอะไรใหม่เอง
  • เกณฑ์: score_threshold เป็นอาร์กิวเมนต์ (ค่าเริ่มต้น DEFAULT_SCORE_THRESHOLD = 0.7, pipeline.py:41) เกณฑ์ของ mask ยังเป็นค่าคงที่ MASK_BINARY_THRESHOLD = 0.5 (:44)
  • การซ้อนทับ: mask ถูกเขียนตามลำดับที่เครือข่ายคืนมา ดังนั้นเมื่อสองอันซ้อนกัน อันสุดท้ายเขียนทับ ไม่มีการโหวตและไม่มีความสอดคล้อง 3 มิติระหว่างสไลซ์ (pipeline.py:180-182)

3.4 ผลลัพธ์และรายงาน

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

แต่ละสแกนใส่คีย์ด้วยพาธสัมพัทธ์กับรากอินพุต และทรีผลลัพธ์สะท้อนทรีอินพุต นามสกุล .nii.gz หรือ .nii ถูกตัดออกก่อนเพิ่มคำต่อท้าย (__init__.py:223-231):

input   scans/site_A/P01.nii.gz
output  output_dir/site_A/P01_seg.nii.gz          # affine and header copied from the input

ไฟล์เดี่ยวเป็นรากของตัวเอง ผลลัพธ์จึงลงตรงๆ ใน output_dir (__init__.py:163-165) label map คง affine และ header ของอินพุต (nib.Nifti1Image(labels, image.affine, image.header), :231) สแกนและเซกเมนเทชันจึงเปิดมาตรงกัน การใช้ header ซ้ำยังหมายความว่าไฟล์ถูกเขียนในชนิดข้อมูลของสแกนอินพุต เหมือนใน legacy: labels เป็น int16 ในหน่วยความจำ (pipeline.py:167) แต่สแกน float32 ได้ label map แบบ float32 บนดิสก์ (nibabel 5.4.2 ตรวจกับการเรียกของ legacy ซึ่งมีรูปแบบเดียวกัน ค่ายังเป็น 0 ถึง 3) จากนั้น CLIC_report.json ถูกเขียนข้างผลลัพธ์ (:201) ด้วยรูปแบบนี้ (คีย์จาก __init__.py:133-155,188-189,233-249):

{

CLIC_report.json มีตาราง label สิ่งที่ตรวจพบ และสแกนที่ล้มเหลว (__init__.py:133-155,173-186) แต่แผงไม่มี RUN_REPORT (Remote CLICRemote/CLICRemote.py:53-72; ค่าเริ่มต้นของ base ว่าง, ServerToolsCore/ServerToolsCoreLib/base_widget.py:1493) ต่างจากCNEและDOCShapeAXI สแกนที่ล้มเหลวมองเห็นได้เฉพาะเมื่อเปิด JSON โฟลเดอร์ที่ใหญ่กว่าหนึ่งชุด (25 รายการหรือ 400 MB โดยค่าเริ่มต้น, VISOR-serve server/config.py:192,196) ถูกส่งเป็นหลายการรันที่โฟลเดอร์ผลลัพธ์ถูกพับกลับเข้าโฟลเดอร์ผลลัพธ์ตอนท้าย รายงานที่รวมแล้วถูกเขียนเฉพาะกับแผงที่ประกาศ RUN_REPORT (base_widget.py:2192) และเมื่อสองชุดผลิตไฟล์ชื่อเดียวกัน ไฟล์แรกถูกเก็บไว้ (:2205-2224) สำหรับ CLIC CLIC_report.json สุดท้ายจึงเป็นของชุดเดียว อ่านในโค้ด ไม่ได้รัน

คอมเมนต์ของ VISOR-serve อธิบาย CLIC ที่ "batches slices inside one forward" (server/execution/admission.py:146) ด้วยอาร์กิวเมนต์ batch_size = 4 (server/execution/runner.py:1251,1271-1272) และอ้างอิงการวัดหน่วยความจำของ CLIC ที่ width 1 ถึง 45 (server/execution/costs.py:470-477) เครื่องมือที่แพ็กเกจจริงไม่มีอาร์กิวเมนต์ batch_size รันหนึ่งสไลซ์ต่อการเรียก model([tensor]) (pipeline.py:170-176) และไม่เคยเรียก progress.set_width ซึ่งมีเพียงการนิยาม (progress.py:41) คอมเมนต์และตัวเลขเหล่านั้นจึงอธิบายอีกเวอร์ชันหนึ่งของเครื่องมือ อย่าอ่าน "four slices per pass" เป็นคุณสมบัติของโค้ดนี้

การทับกันยังถูกตัดสินตามลำดับ ทีละสไลซ์

เมื่อมาสก์ที่เก็บไว้สองอันทับกันบนสไลซ์ อันที่เครือข่ายคืนมาทีหลังเขียนทับอีกอัน และแต่ละสไลซ์ถูกตัดสินโดยลำพัง: ไม่มีการโหวตระหว่างคลาสและไม่มีความสอดคล้องแบบ 3D ฟันเขี้ยวซี่เดียวจึงมีสองป้ายกำกับบนสไลซ์ที่อยู่ติดกันได้ (pipeline.py:170-182, เหมือน clic_runner.py:84-87 ของ legacy) อ่านในโค้ด

ตรวจแล้ว: ข้อบกพร่องอื่นของ legacy หายไปแล้ว

การเลือก checkpoint ปฏิเสธความกำกวม อ่านจำนวนคลาส โหลดด้วย weights_only=True ตั้งชื่อผลลัพธ์ถูกต้อง และใช้พาธสัมพัทธ์เป็นคีย์ ทำให้สแกนสองอันที่ชื่อเหมือนกันไม่เขียนทับกันอีก (SADT-VISOR __init__.py:40-73,223-231, pipeline.py:96-144) ตาราง label อยู่ในรายงาน ไม่ใช่เฉพาะใน widget
