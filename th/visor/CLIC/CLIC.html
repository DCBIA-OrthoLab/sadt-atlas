CLIC บน VISOR

CLIC หาเขี้ยวฝังคุดใน CBCT และบอกว่าแต่ละซี่อยู่ด้านแก้ม ด้านเพดานปาก หรือคร่อมกระดูก หน้านี้อธิบายว่าทำอย่างไรทีละขั้นพร้อมคณิตศาสตร์: อะไรเข้า แต่ละขั้นทำอะไรกับมัน และอะไรออกมา ไฟล์ บรรทัด อาร์กิวเมนต์ และข้อค้นพบอยู่ในหน้าโค้ด โมดูล Slicer ฉบับ legacy อยู่ในหน้าของมันเอง

โค้ด (นักพัฒนา) VISOR 1 เครือข่าย หน้า Legacy คู่มือ (VISOR)

เมื่อหน้านี้เอ่ยถึง repository หมายถึงแค็ตตาล็อกเครื่องมือ SADT-VISOR ที่ 6ba2a78 เซิร์ฟเวอร์ VISOR-serve ที่ e9a7e5d ไคลเอนต์ Slicer AutomatedDentalToolsRemote ที่ 19b95e8 และโมดูล legacy SlicerAutomatedDentalTools ที่ 3c67957 ชื่อไฟล์ เลขบรรทัด และข้อค้นพบทุกข้ออยู่ในหน้าโค้ด ทุกอย่างที่นี่อ่านจากโค้ด ไม่มีอะไรถูกรันเพื่อหน้านี้

ภาพรวม: อะไรเข้า อะไรออก

CLIC มองหาเขี้ยวฝังคุดในสแกน CBCT มันไม่ดูทั้งวอลุ่มพร้อมกัน: มันอ่านสแกนทีละสไลซ์ และในแต่ละสไลซ์ เครือข่ายที่ฝึกแล้วจะวาดเค้าโครงของเขี้ยวที่พบ และในรอบเดียวกันก็บอกด้วยว่าแต่ละซี่อยู่ตรงไหนเมื่อเทียบกับกระดูก: ด้านแก้ม (buccal) ด้านเพดานปาก (palatal) หรือคร่อมกระดูก (bicortical) มีเครือข่ายเดียวและไม่มีตัวจำแนกแยก: เค้าโครงและคลาสออกมาพร้อมกัน

CLIC บน VISOR
อินพุตCBCT หนึ่งชุดเป็นไฟล์ NIfTI (.nii หรือ .nii.gz) หรือโฟลเดอร์ของไฟล์เหล่านั้นที่ค้นแบบเรียกซ้ำ
วิธีการต่อสไลซ์: ปรับสเกลค่าเทา ส่งสไลซ์ให้ Mask R-CNN เก็บการตรวจจับที่มั่นใจ ระบายลงในวอลุ่ม label
เอาต์พุตlabel map หนึ่งอันต่อสแกน บนกริดเดียวกับสแกน: 0 คือพื้นหลัง 1 buccal 2 bicortical 3 palatal และ CLIC_report.json สรุปสิ่งที่พบและสิ่งที่ล้มเหลว
ที่ไหนบนเซิร์ฟเวอร์เท่านั้น แผง Slicer อัปโหลดสแกนและโหลด label map

เครือข่ายและวิธีทีละสไลซ์เป็นของ legacy ไม่มีการฝึกใหม่ สิ่งที่เปลี่ยนคือวิธีหาสแกน วิธีเลือกไฟล์น้ำหนัก วิธีตั้งชื่อผลลัพธ์ และวิธีจัดการสแกนที่ล้มเหลว (สิ่งที่เปลี่ยน)

1. ตำแหน่งในสายโซ่

CLIC ทำงานอิสระ ไม่มีเครื่องมืออื่นเตรียมอินพุตและไม่มีเครื่องมืออื่นอ่านผลลัพธ์ จึงรันกับ CBCT NIfTI ใดก็ได้ ไม่ว่าก่อนหน้านั้นทำอะไรกับมันมา ใน VISOR แผงใน Slicer ถูกสร้างจากคำอธิบายเครื่องมือของเซิร์ฟเวอร์ มันอัปโหลดสแกน รอ และดาวน์โหลดไฟล์เก็บถาวรหนึ่งไฟล์ที่มีlabel mapและรายงาน เครื่องมือมีเทสต์อัตโนมัติใน repository ของมัน (ไม่ได้รันสำหรับหน้านี้) ส่วนเซิร์ฟเวอร์ใดกำลังรันมันอยู่หรือไม่ หน้านี้บอกไม่ได้

ในโค้ดชื่อ API, น้ำหนักที่โฮสต์ไว้, สิ่งที่ schema ประกาศ, ใครเรียกใคร

1.1 อะไรรันที่ไหน

เซิร์ฟเวอร์ทำทุกอย่างที่สำคัญ: อ่านสแกน รันเครือข่ายบนการ์ดจอเมื่อมี ใช้เกณฑ์ และเขียนไฟล์ ฝั่ง Slicer เพียงเลือกสแกนและโฟลเดอร์ผลลัพธ์ แสดงความคืบหน้า แตกไฟล์เก็บถาวร และถ้าขอ ก็แสดง label map ได้ถึงสิบสองอันพร้อมพรีเซ็ต volume rendering รายงานถูกเขียนโดยเซิร์ฟเวอร์ แต่แผงไม่แสดง

ในโค้ดตารางหน้าที่ของเซิร์ฟเวอร์และไคลเอนต์ พร้อมบรรทัด

2. ไฟล์ที่เกี่ยวข้อง

เครื่องมือมีขนาดเล็ก: ไฟล์หลักหนึ่งไฟล์ที่จัดระเบียบการรัน หนึ่งไฟล์ที่ทำการประมวลผลภาพ ตารางชื่อและสีของคลาส และตัวเขียนความคืบหน้า แผงฝั่งไคลเอนต์ยาวราวแปดสิบบรรทัด บรรทัดและเทสต์ระบุไว้ในหน้าโค้ด

ในโค้ดตารางไฟล์พร้อมจำนวนบรรทัด และ repository อื่นที่เกี่ยวข้อง

3. ไปป์ไลน์

การรันมีสี่ระดับ: หนึ่งครั้งต่อการรัน เครื่องมือหาสแกนและโหลดเครือข่าย; หนึ่งครั้งต่อสแกน มันอ่านวอลุ่ม; หนึ่งครั้งต่อสไลซ์ มันเตรียมภาพ รันเครือข่าย และระบายผลลัพธ์; ตอนท้ายมันเขียนไฟล์ คลิกกล่องเพื่ออ่านส่วนของมัน

ในโค้ดฟังก์ชันที่อยู่เบื้องหลังแต่ละกล่องของแผนภาพ

3.1 การค้นหาสแกน

ไฟล์เดียวใช้ตามที่เป็น โฟลเดอร์ถูกค้นแบบเรียกซ้ำ ข้ามไฟล์ที่ซ่อน และเก็บเฉพาะชื่อที่ลงท้ายด้วย .nii หรือ .nii.gz โมดูลเก่ายังปล่อยรูปแบบอื่นที่โค้ดเครือข่ายของมันอ่านไม่ได้ผ่านไป ส่วนตัวนี้ปฏิเสธตั้งแต่ต้นพร้อมข้อความ ถ้าไม่พบอะไร คำขอถูกปฏิเสธด้วยข้อผิดพลาดที่อ่านเข้าใจได้

ในโค้ดนามสกุล การเดินค้น ข้อผิดพลาดที่ยกเมื่อไม่พบอะไร

3.2 การเลือกและโหลด checkpoint

ไฟล์น้ำหนักผู้ใช้ไม่ได้เป็นผู้เลือก เมื่อไม่ได้ระบุ เครื่องมือใช้ไฟล์ .pth ไฟล์เดียวในโฟลเดอร์โมเดลบนเซิร์ฟเวอร์ ถ้าไม่มีหรือมีหลายไฟล์ จะถูกปฏิเสธโดยระบุชื่อตัวเลือก เพื่อไม่ให้ไฟล์ที่สองที่หลงอยู่เปลี่ยนผลลัพธ์อย่างเงียบ ๆ เครือข่ายคือ Mask R-CNN: backbone ResNet-50 พร้อม feature pyramid ดูภาพ เสนอบริเวณผู้สมัคร และสำหรับแต่ละบริเวณทำนายคลาส กล่อง และมาสก์ จำนวนคลาสไม่ได้สมมติไว้แต่อ่านจากไฟล์น้ำหนัก และเลเยอร์เอาต์พุตถูกสร้างตามขนาดนั้นก่อนโหลดน้ำหนัก น้ำหนักที่เผยแพร่มีสี่คลาส: พื้นหลังและตำแหน่งของเขี้ยวสามแบบ

น้ำหนักถูกโหลดในโหมดที่ไม่อาจรันโค้ดที่ฝังอยู่ในไฟล์ ถ้ามองเห็นการ์ดจอ เครือข่ายรันบนมัน มิฉะนั้นถอยไปใช้โปรเซสเซอร์พร้อมคำเตือน

ในโค้ดกฎของ checkpoint จำนวนคลาส การเรียกโหลด และการเลือกอุปกรณ์

3.3 ลูปสไลซ์

แต่ละสแกนถูกอ่านเป็นชั้นของตัวเลขและตัดตามแกนอาร์เรย์ที่สาม ตามลำดับที่เก็บในไฟล์ เครื่องมือไม่ปรับทิศทางสแกนใหม่ วอลุ่มที่ไม่ใช่สามมิติทำให้เฉพาะสแกนนั้นล้มเหลว

ก่อนถึงเครือข่าย แต่ละสไลซ์ถูกปรับสเกลและคัดลอกเป็นสามแชนเนลที่เหมือนกัน (เครือข่ายถูกออกแบบมาสำหรับภาพสี) ภายในเครือข่าย ภาพยังถูกขยายให้ด้านสั้นยาว 800 พิกเซล และทำมาตรฐานด้วยค่าเฉลี่ยและการกระจายของ ImageNet ซึ่ง torchvision เป็นผู้ทำ เครื่องมือไม่ทำอะไรตรงนั้น

เนื่องจากทุกสไลซ์ถูกปรับสเกลโดยลำพัง สไลซ์ที่เกือบว่างจึงถูกยืดให้เต็มช่วงเหมือนสไลซ์ของกระดูก: เครือข่ายไม่เคยเห็นค่า Hounsfield สัมบูรณ์ นี่คือพฤติกรรมของ legacy ที่คงไว้

แต่ละสไลซ์ถูกตัดสินโดยลำพัง ไม่มีอะไรเชื่อมผลของสไลซ์หนึ่งกับสไลซ์ข้างเคียง เขี้ยวซี่เดียวกันจึงมีสองป้ายกำกับบนสองสไลซ์ที่ติดกันได้ และไม่มีอะไรแปลงผลเป็นคำตอบเดียวต่อผู้ป่วย

ในโค้ดลูป เกณฑ์ทั้งสาม กฎการเขียนทับ และฟังก์ชัน normalisation

3.4 ผลลัพธ์และรายงาน

โฟลเดอร์ผลลัพธ์สะท้อนโฟลเดอร์อินพุต: สแกน site_A/P01.nii.gz ให้ site_A/P01_seg.nii.gz ผู้ป่วยสองคนที่มีไฟล์ชื่อเดียวกันในโฟลเดอร์ต่างกันจึงไม่เขียนทับกัน label mapคัดลอก geometry ของสแกน จึงเปิดแล้วเรียงตรงกับสแกน มันยังใช้ header ของสแกนซ้ำ ไฟล์จึงถูกบันทึกในชนิดข้อมูลของสแกนเอง (สแกนที่เก็บเป็นจำนวนทศนิยมให้ label map ที่เป็นทศนิยม) ค่ายังคงเป็น 0 ถึง 3 รายงานระบุสำหรับทุกสแกนว่าสำเร็จหรือไม่ อ่านกี่สไลซ์ เก็บการตรวจจับไว้กี่รายการ และปรากฏคลาสใดบ้าง พร้อมชื่อคลาส สี และเกณฑ์ที่ใช้ สแกนที่ไม่มีการตรวจจับถูกเขียนเป็น label map ว่างและบันทึกไว้เช่นนั้น

ในโค้ดการตั้งชื่อผลลัพธ์ คีย์ของรายงานพร้อมตัวอย่าง หมายเหตุสำหรับสแกนว่าง

3.5 ความล้มเหลว ความคืบหน้า และล็อก

สแกนเสียหนึ่งอันไม่หยุดอันอื่น: มันถูกบันทึกว่าล้มเหลวพร้อมเหตุผล และลูปไปต่อ การรันล้มเหลวก็ต่อเมื่อเขียนสแกนไม่ได้เลยสักอัน ความคืบหน้าถูกรายงานเป็นตำแหน่ง (สแกนที่ 3 จาก 12) ไม่เคยเป็นชื่อไฟล์ เพราะชื่อไฟล์อาจเป็นข้อมูลของผู้ป่วย log ใช้กฎเดียวกัน

ในโค้ดการจัดการข้อยกเว้น ไฟล์ความคืบหน้า และบรรทัด log

4. สิ่งที่เลือกได้

  • สแกน: ไฟล์เดียวหรือโฟลเดอร์ของวอลุ่ม NIfTI
  • เกณฑ์คะแนน: ค่าเริ่มต้น 0.7 การเพิ่มค่าจะเก็บเฉพาะการตรวจจับที่มั่นใจที่สุด การลดจะเก็บมากขึ้นพร้อมผลบวกลวงที่มากขึ้น
  • suffix ของผลลัพธ์: ค่าเริ่มต้น seg ต่อท้ายชื่อสแกน
  • ไม่เปิดให้ตั้ง: ไฟล์น้ำหนัก (ของเซิร์ฟเวอร์เอง) อุปกรณ์ (การตั้งค่าของเซิร์ฟเวอร์ พร้อมถอยไปใช้โปรเซสเซอร์) และโฟลเดอร์ผลลัพธ์ (เซิร์ฟเวอร์กำหนด) เกณฑ์มาสก์ 0.5 คงที่
ในโค้ดตารางอาร์กิวเมนต์พร้อมชนิด ค่าเริ่มต้น และการมองเห็น ค่าที่คืน ขีดจำกัดทรัพยากร

5. ค่าทำนายหรือค่าคำนวณ

ขั้นตอนลักษณะ
การหาสแกน, การเลือกน้ำหนัก, การปรับสเกลแต่ละสไลซ์, การปรับขนาดคำนวณ เลขคณิตธรรมดาและการจัดการไฟล์
เขี้ยวอยู่ที่ไหน เค้าโครงของมัน และคลาสของมันทำนาย โดยเครือข่าย หนึ่ง forward pass ต่อสไลซ์
เกณฑ์, การระบายสี, การเขียนไฟล์และรายงานคำนวณ

เนื้อหาทางคลินิกทั้งหมดมาจากเครือข่าย ไม่มีอะไรตรวจมันหลังจากนั้น

ในโค้ดตารางเต็มของบล็อก พร้อมที่ที่แต่ละบล็อกรัน

6. สภาพแวดล้อม

เครื่องมือมีสภาพแวดล้อม Python ของตัวเองบนเซิร์ฟเวอร์ (Python 3.11 พร้อมเวอร์ชันที่ตรึงของ torch, torchvision, nibabel และ numpy) สร้างจากไฟล์ล็อกเมื่อสร้าง image ของเซิร์ฟเวอร์ ไม่มีอะไรถูกติดตั้งบนเวิร์กสเตชัน ไฟล์น้ำหนักใหญ่ราว 176 MB และจัดเตรียมไว้บนเซิร์ฟเวอร์ล่วงหน้า

ในโค้ดเวอร์ชันและที่ที่ตรึงไว้ ขนาดไฟล์น้ำหนัก และการตั้งค่า timeout

7. สิ่งที่เปลี่ยนไปจากตรรกะ legacy

เครือข่าย การปรับสเกลรายสไลซ์ สามแชนเนล แกนสไลซ์ และเกณฑ์ เหมือนเดิม รอบ ๆ สิ่งเหล่านั้น:

  • การรันหนึ่งครั้งจัดการทุกสแกนในโปรเซสเดียว แทนที่จะหนึ่งโปรเซสต่อสแกนที่แผง Slicer เป็นผู้เริ่ม
  • รับเฉพาะ NIfTI และคำขอที่ไม่มี NIfTI ถูกปฏิเสธด้วยข้อความที่ชัดเจน
  • ไฟล์น้ำหนักต้องเป็น .pth ไฟล์เดียวของโฟลเดอร์ โค้ดเก่าหยิบไฟล์แรกตามลำดับตัวอักษรอย่างเงียบ ๆ
  • จำนวนคลาสอ่านจากน้ำหนักแทนที่จะกำหนดตายตัวที่สี่ และชื่อคลาสอยู่ในเครื่องมือและในรายงานแทนที่จะอยู่เฉพาะในแผง
  • ผลลัพธ์สะท้อนโฟลเดอร์อินพุตและตั้งชื่อ X_seg.nii.gz ในขณะที่โค้ดเก่าเขียน X.nii_seg.nii.gz
  • สแกนที่ล้มเหลวถูกบันทึกในรายงาน และความคืบหน้าผ่านไฟล์ความคืบหน้าที่ไคลเอนต์อ่านได้ แทนเครื่องหมายข้อความที่ไม่เคยตรงกัน
  • น้ำหนักถูกโหลดในโหมดปลอดภัย และไม่มีปุ่มดาวน์โหลดโมเดล
ในโค้ดตารางเทียบ legacy กับ VISOR ทีละจุด พร้อมบรรทัด

8. ปัญหาที่ทราบ

  • การสร้างเครือข่ายอาจยังพยายามดึง backbone ResNet-50 จากอินเทอร์เน็ตก่อนที่น้ำหนักจะถูกโหลดทับ ดูข้อค้นพบ
  • สแกนที่ตรวจไม่พบอะไรนับเป็นความสำเร็จ ซึ่งก็คือหน้าตาของไฟล์น้ำหนักที่ผิดด้วย ดูข้อค้นพบ
  • แผงไม่แสดงรายงาน สแกนที่ล้มเหลวจึงมองเห็นได้เฉพาะเมื่อเปิด JSON ดูข้อค้นพบ
  • คอมเมนต์ของเซิร์ฟเวอร์บางอันอธิบาย CLIC ที่ทำหลายสไลซ์ต่อรอบ ซึ่งเครื่องมือนี้ไม่ทำ ดูข้อค้นพบ
  • การทับกันยังถูกตัดสินตามลำดับ ทีละสไลซ์ ดูข้อค้นพบ
  • ในแง่ดี ข้อบกพร่องอื่นของ legacy ถูกตรวจแล้วและหายไปแล้ว ดูการตรวจ
ในโค้ดcallout ทั้งหกพร้อมหลักฐาน

9. เอกสารอ้างอิง

วิธีการและสิ่งพิมพ์เป็นของเครื่องมือ ไม่ว่าอะไรจะรันมัน: ดูหน้าแหล่งอ้างอิงของ CLIC VISOR ไม่เพิ่มโมเดลใหม่
