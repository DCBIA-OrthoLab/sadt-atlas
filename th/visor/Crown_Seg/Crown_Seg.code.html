Crown_Seg บน VISOR: โค้ด

สำหรับนักพัฒนา: สิ่งที่เครื่องมือ VISOR Crown_Seg ทำในโค้ด พร้อมการอ้างอิง file:line signature อาร์กิวเมนต์ สภาพแวดล้อม ความสอดคล้องกับ legacy และข้อค้นพบ คำอธิบายที่อ่านง่ายของไปป์ไลน์เดียวกัน พร้อมคณิตศาสตร์ อยู่ในหน้าแอตลาส

เฉพาะ VISOR โค้ด แอตลาส (คำอธิบาย) SADT-VISOR 6ba2a78 VISOR-serve e9a7e5d Remote 19b95e8
ไม่มีโมดูล legacy

repository ของ legacy (SlicerAutomatedDentalTools ที่ 3c67957) ไม่มีโมดูล Crown_Seg และไม่มีไฟล์ที่พาธมี “crown” หรือ “dentalmodelseg” (git ls-tree บน commit นั้น สังเกตแล้ว) สิ่งที่มีคือการเรียกโมดูล CrownSegmentationcli ของส่วนขยาย SlicerDentalModelSeg ที่แยกต่างหาก และสำเนาเล็ก ๆ ของการเรียกเดียวกันใน command line ของ ALI_IOS ความสอดคล้องที่แน่นอนอยู่ในส่วนคู่เทียบใน Legacy วิธีที่ VISOR รันเครื่องมือบนเซิร์ฟเวอร์อธิบายในสถาปัตยกรรม

พาธ: SADT-VISOR cs/ คือ tools/Crown_Seg/src/sadt_crownseg/, ali_ios/ คือ tools/ALI/ALI_IOS/src/sadt_ali_ios/ และพาธ VISOR-serve ขึ้นต้นที่ server/ เว้นแต่ระบุ docs/ หรือ scripts/ “Observed” ทำเครื่องหมายสิ่งที่รันซ้ำระหว่างเขียนหน้านี้ ที่เหลือทั้งหมดอ่านจากโค้ด

4.1 สิ่งที่เครื่องมือทำรอบ engine

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

  1. checkpoint ก่อน: find_checkpoint รับไฟล์ .pth หรือโฟลเดอร์ที่ค้นแบบเรียกซ้ำหาไฟล์ที่ชื่อมี val-loss ถ้าไม่มีหรือมีสองไฟล์ จะเป็น ToolInputError ที่ระบุชื่อ (cs/pipeline.py:186-262) model ว่างหมายถึง <data_root>/Crown_Seg/models (cs/__init__.py:18-29,104) ทั้งหมดนี้เกิดก่อนมีอะไรถูกสร้าง (cs/pipeline.py:407-413)
  2. การค้นหา: .vtk หรือ .stl หนึ่งไฟล์ หรือโฟลเดอร์ที่เดินค้นแบบเรียกซ้ำและเรียงลำดับ ไม่พบอะไรคือ 422 (cs/pipeline.py:292-320) รากอินพุต ซึ่งใช้สะท้อนโครงสร้างต้นไม้ คือโฟลเดอร์หรือโฟลเดอร์แม่ของไฟล์เดี่ยว (:323-330)

4.2 ภายใน shapeaxi

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

อ่านใน dental_model_seg.py ของ checkout ShapeAXI 2b34042 ไฟล์ล็อกแก้ shapeaxi เป็น 2.0.2 ซึ่งไม่ได้เปิดซอร์สที่นี่ บรรทัดที่อ้างด้านล่างเหมือนกันในสำเนาที่เปิดอ่าน (shapeaxi 1.0.10 และ 2.0.3 ที่ติดตั้งไว้ และ 1.1.1 ใน cache ของ uv):

  • เครือข่ายคือ saxi_nets_lightning.DentalModelSeg(custom_model=args.model, device=device) โดย out_channels = 34 (:23,26);
  • แต่ละพื้นผิวถูกโหลดผ่าน SaxiDataset ด้วย UnitSurfTransform(), batch size 1, persistent_workers=True (:82-84) ซึ่งเป็นเหตุผลที่ num_workers ต้องเป็นอย่างน้อย 1;
  • เครือข่ายคืนค่าทำนายรายมุมมองและหน้าที่แต่ละพิกเซลแสดง ค่าทำนายถูกคูณด้วย (PF >= 0) (ศูนย์ที่ที่พิกเซลไม่แสดงหน้าใด) แล้วผ่าน softmax (:97) พิกเซลที่ไม่มีหน้าจึงให้ค่าสม่ำเสมอ 1/34 ซึ่งถูกบวกเข้าช่องหนึ่งของตารางหน้าแทนที่จะถูกข้าม (:103-104) ผลรวมต่อหน้า และ arg-max (:106) ให้หนึ่ง label ต่อหน้า และ label ของแต่ละหน้าถูกให้กับจุดยอดแรกของมัน (:107-108);
  • การประมวลผลหลัง: RemoveIslands สำหรับ label เหงือก 33 ด้วยเกณฑ์ 500 แล้วสำหรับทุก label ด้วย 200 จากนั้นclosingต่อ label คือ DilateLabel แล้ว ErodeLabel อย่างละสองรอบ (:118-130);
  • ConvertFDI ถ้า fdi == 1 (:52,225-236, ส่วนถัดไป);
  • เมื่อ overwrite=0 และอินพุตเป็น csv ผลลัพธ์ไปที่ <out>/<csv stem>_<suffix>/<input path without vtk_folder>_<suffix>.vtk (:154-176) Crown_Seg คำนวณพาธนี้ใหม่แทนที่จะ parse เอาต์พุตของ shapeaxi (cs/pipeline.py:369-381) แล้วทำเครื่องหมายแต่ละเมชเป็น segmented ถ้าไฟล์มีอยู่ และ failed ถ้าไม่ (:533-546)

8. ข้อค้นพบใน VISOR

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

การเลข FDI ทับเมชที่มี label อยู่แล้ว

เมื่อ numbering = "FDI" และเปิด skip_segmented เมชที่มีอาร์เรย์ label อยู่แล้วถูกคัดลอกโดยไม่เปลี่ยน (cs/pipeline.py:480-487; _write_as_vtk แปลงรูปแบบไฟล์ ไม่ใช่ label) ขณะที่รายงานระบุ array_name = "FDI_ID" และ numbering = "FDI" (cs/pipeline.py:556-561) สำเนายังคงจำนวนเต็ม Universal ไว้ใต้ชื่อ Universal รายงานจึงประกาศระบบการเลขที่ไฟล์ไม่ได้เก็บ Observed: เมชสังเคราะห์ที่มีอาร์เรย์ Universal_ID ถูกส่งผ่าน segment_crowns ด้วย fdi=True และ array_name="FDI_ID" รายงานอ่านว่า numbering: "FDI" และ array_name: "FDI_ID" และไฟล์ผลลัพธ์มีเฉพาะ Universal_ID ด้วยค่าเดิม engine สำหรับ segmentation ไม่ได้ติดตั้งในสภาพแวดล้อมที่ใช้ สถานะของกรณีจึงอ่านว่า engine_unavailable แทน already_segmented เส้นทางการคัดลอกเหมือนกัน เทสต์ไม่ครอบคลุมจุดตัดนี้ (tests/test_run.py:488-503)

สี่ชื่อที่รู้จักที่นี่ สามชื่อที่ปลายทาง

Crown_Seg ถือว่าเมช segment แล้วถ้ามีชื่อใดของ PredictedID, UniversalID, Universal_ID หรือ FDI_ID (cs/pipeline.py:56) ALI_IOS, ASO และ AREG_IOS อ่านเฉพาะสามชื่อแรก (ali_ios/surface.py:19, SADT-VISOR tools/ASO/src/sadt_aso/markups.py:19, AREG_IOS/src/sadt_areg_ios/surfaces.py:39) เมชที่มีเพียง FDI_ID จึงผ่าน Crown_Seg และถูกเครื่องมือถัดไปปฏิเสธ: ตั้งใจให้เป็นเช่นนั้น (คอมเมนต์ของเครื่องมือเองบอกไว้, cs/pipeline.py:64-80) แต่ไม่มีอาการใดก่อนถึงเครื่องมือถัดไป คอมเมนต์ของ ALI_IOS ที่บอกว่านี่คือ “the same three names CrownSeg writes and recognizes” (ali_ios/surface.py:18) ไม่ถูกต้องเป๊ะ อ่านในโค้ด

เมชแบบ .vtp หรือ .obj มองไม่เห็นสำหรับ Crown_Seg

Crown_Seg ค้นหาเฉพาะ .vtk และ .stl (cs/pipeline.py:51,292-320) ขณะที่ AREG_IOS รับ .vtk .vtp .stl .obj เป็นอินพุต (AREG_IOS/src/sadt_areg_ios/surfaces.py:35) และในโหมด Fully-Automated ส่งโฟลเดอร์ของมันให้ Crown_Seg (dispatch.py:172-173) โฟลเดอร์ที่มีเฉพาะเมชแบบนั้นถูกปฏิเสธ (“No surface mesh found in the input”, cs/pipeline.py:314-319); ในโฟลเดอร์ผสมมันถูกทิ้งจากผลลัพธ์ของ Crown_Seg ซึ่งเป็นโฟลเดอร์ที่ AREG_IOS ทำต่อ สำเนาการเรียกของ ALI_IOS ฉบับ legacy อ่าน .vtp ได้ (segmentation.py:33-56) อ่านในโค้ด ไม่ได้รัน

ต้นไม้ผลลัพธ์สองแบบ: อ่านรายงาน

เมชที่ segment ไปอยู่ใต้ crownseg_input_<suffix>/ เมชที่มี label อยู่แล้วไปอยู่ข้างพาธสัมพัทธ์ของมัน glob บนต้นไม้หนึ่งจึงพลาดอีกต้น (cs/pipeline.py:369-381,480-487) ALI_IOS อ่าน cases[key].produced จาก run_report.json แทน (ali_ios/dispatch.py:240-252) ซึ่งเป็นหน้าที่ของรายงาน เมชของการติดตั้งที่เสื่อมสภาพมีสถานะ engine_unavailable แต่ถูกคัดลอกพร้อมพาธ produced (cs/pipeline.py:495-505) ไคลเอนต์ที่กรองด้วย already_segmented อย่างเดียวจึงจะข้ามมัน อ่านในโค้ด

เอกสารที่ขัดกับโค้ด

README บอกว่า model เป็นอาร์กิวเมนต์ที่จำเป็น (README.md:33) และ docstring ของไปป์ไลน์ก็เช่นกัน (cs/pipeline.py:16-23); แต่อาร์กิวเมนต์เป็นแบบไม่บังคับ มีค่าเริ่มต้นว่างที่แก้เป็นโฟลเดอร์ของเครื่องมือเอง (cs/__init__.py:41, คอมเมนต์ที่ cs/__init__.py:35-40) README ยังเรียกโฟลเดอร์ว่า DATA/CrownSeg/testfiles (README.md:178) ขณะที่โค้ดและ manifest ใช้ DATA/Crown_Seg และนับเทสต์ 176 รายการ (README.md:225,232) ทั้งที่นิยามฟังก์ชันเทสต์ 162 ฟังก์ชันใน tests/ (นับ def test_ การทำ parametrisation อาจอธิบายส่วนต่าง) AREG ไม่เคยส่ง device ให้ Crown_Seg ต่างจาก ALI_IOS (SADT-VISOR tools/AREG/AREG_IOS/src/sadt_areg_ios/tools.py:113-130) ดังนั้นบนเซิร์ฟเวอร์ที่มีแต่ CPU ค่าเริ่มต้น cuda ถอยไปใช้ CPU พร้อมคำเตือน หรือถูกแทนที่ด้วย DEVICE ของเซิร์ฟเวอร์ อ่านในโค้ด

สิ่งที่เครื่องมือปกป้อง

checkpoint ถูกแก้ก่อนไฟล์ใดถูกสร้าง คำขอที่ถูกปฏิเสธจึงไม่ทิ้งอะไรไว้ (cs/pipeline.py:407-413); โฟลเดอร์ที่มีสอง checkpoint ถูกปฏิเสธโดยระบุทั้งสอง ที่มาของน้ำหนักจึงไม่เคยเงียบ (cs/pipeline.py:244-251); เอาต์พุตมาตรฐานของ shapeaxi ซึ่งมีชื่อไฟล์ ถูกกลืน (cs/pipeline.py:365); โฟลเดอร์ scratch ถูกลบใน finally (cs/pipeline.py:435-439); อินพุตไม่เคยถูกแก้ อ่านในโค้ด
