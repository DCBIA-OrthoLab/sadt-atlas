ALI บน VISOR: โค้ด

สำหรับนักพัฒนา: การพอร์ต VISOR ของ ALI ทำอะไรในโค้ด พร้อมการอ้างอิง file:line ซิกเนเจอร์ อาร์กิวเมนต์ สภาพแวดล้อม ความต่างจากโค้ด legacy และข้อค้นพบ คำอธิบายที่อ่านง่ายของไปป์ไลน์เดียวกัน พร้อมคณิตศาสตร์ อยู่ในหน้าแอตลาส

VISOR โค้ด แอตลาส (คำอธิบาย) หน้า Legacy คู่มือ (VISOR)

VISOR รันเครื่องมือทันตกรรมบนเซิร์ฟเวอร์: Slicer เก็บไว้เพียงแผงที่ส่งข้อมูลและโหลดผลลัพธ์ (ดูสถาปัตยกรรม) หน้านี้อธิบายการพอร์ต VISOR ของ ALI อ่านจากโค้ดของที่เก็บที่ระบุชื่อด้านล่าง และเทียบกับโมดูล Slicer แบบ legacy ที่ 3c67957 ซึ่งมีหน้าของตัวเอง "Run for this page" ทำเครื่องหมายสิ่งที่ถูกรันระหว่างตรวจ ส่วนที่เหลือทั้งหมดอ่านจากโค้ด ตัวย่อที่ใช้ในการอ้างอิง:

  • CB/ = SADT-VISOR 6ba2a78, tools/ALI/ALI_CBCT/src/sadt_ali_cbct/; IO/ = SADT-VISOR, tools/ALI/ALI_IOS/src/sadt_ali_ios/; CM/ = SADT-VISOR, tools/ALI/common/src/sadt_ali_common/;
  • VISOR-serve = VISOR-serve e9a7e5d ไฟล์ใต้ server/ เว้นแต่พาธขึ้นต้นด้วย scripts/; Remote = AutomatedDentalToolsRemote 19b95e8;
  • legacy = SlicerAutomatedDentalTools 3c67957; พาธ legacy เช่น ALI_CBCT_utils/agent.py อยู่ใต้ ALI_CBCT/ และ ALI_IOS_utils/ อยู่ใต้ ALI_IOS/

ในหนึ่งย่อหน้า: เครื่องมือที่ผู้ใช้เลือกคือ facade ชื่อ ALI ที่มีสองโหมด โหมด CBCT รัน ALI_CBCT เอเจนต์เรียนรู้แบบเสริมกำลังหนึ่งตัวต่อ landmark เดินในวอลุ่มทีละ voxel ที่ 1 mm แล้ว 0.3 mm (หัวข้อ 3) โหมด IOS รัน ALI_IOS ซึ่งเรนเดอร์แต่ละซี่ฟันของเมชในช่องปากที่มีป้ายกำกับจากกล้องคงที่ แบ่งส่วนภาพเรนเดอร์ด้วย UNet 2D และฉายมาสก์กลับลงบนเมช (หัวข้อ 4) ทั้งสองเขียน .mrk.json หนึ่งไฟล์ต่อสแกน พร้อม run_report.json โครงข่ายและน้ำหนักเป็นของ legacy สิ่งที่เปลี่ยนคือสิ่งรอบข้าง และการแก้ไข legacy รุ่นหลังหลายอย่าง (การปรับทิศทาง DICOM, ตัวป้องกันงบจำนวนขั้น, ชุดการปรับแต่ง Mucogingival ทั้งหมด) ไม่เคยถูกนำมา (หัวข้อ 8)

จุด O และ C และทุกจุดของ ALI_CBCT มี description ว่างไม่ว่าคุณภาพจะเป็นอย่างไร: บันทึกถูกกรอกเฉพาะโดยเส้นทาง MG (IO/engine.py:567-575 เขียนโดย :426) และ ALI_CBCT ไม่ส่งอะไรเลย (CB/engine.py:921) landmarks_degraded ของรายงานการรัน (IO/engine.py:414-419) เป็นอีกที่หนึ่งที่บันทึกความสงสัยเกี่ยวกับ MG

หมายเหตุ · สิ่งรบกวนในรายงานการรัน IOS

ALI_IOS ได้รับโฟลเดอร์โมเดลทั้งโฟลเดอร์ ซึ่งมีเช็กพอยต์ของ CBCT ด้วย (VISOR-serve scripts/data-manifest.yml:121-130) และแสดงรายการทุกไฟล์ .pth ที่ชื่อไม่มีโทเค็นของเครือข่าย (O, C, MG) หรือโทเค็นของขากรรไกรไว้ใต้ models_unrecognized (IO/engine.py:98-111, :703) บน bundle ครบชุด นั่นคือรายชื่อไฟล์ CBCT ยาวเหยียดในรายงาน IOS ทุกฉบับ ไม่ใช่ความล้มเหลว ยังไม่ได้วัดบน bundle ครบชุด

หมายเหตุ · ส่วนซ้ำที่ไม่ได้ใช้ใน ALI_CBCT

CB/engine.py:644-650 และ :651-657 เป็นบล็อกเดียวกัน (คำนวณ processed ยก "ALI produced no landmarks for any scan" ถ้าว่าง) สองครั้งติดกัน ไม่มีผลอะไร

ตรวจสอบแล้ว · ตารางกล้อง O ถูกทำซ้ำโดยเจตนา

ทิศทาง O สองทิศทางถูกหารด้วยบรรทัดฐานของเวกเตอร์คนละตัว (np.array([0.5, 0.0, 1.0]) / _norm([0.5, 0.5, 1.0])) จึงมีความยาว 0.913 หรือ 0.791 แทนที่จะเป็น 1 (คำนวณได้: 1.118/1.2247 และ 1.118/1.414) พอร์ตเก็บไว้โดยตั้งใจ เพราะน้ำหนักโมเดลถูกฝึกบนมุมมองเหล่านี้ (IO/render.py:8-12, ตาราง :39-54; legacy ALI_IOS_utils/model.py:66-77)

ตรวจสอบแล้ว · landmark เป็นอิสระต่อกัน การค้นหามีขอบเขต

ผลของ landmark หนึ่งขึ้นกับสแกน น้ำหนักโมเดล และ seed เท่านั้น ไม่เคยขึ้นกับว่าขอ landmark อื่นอะไรบ้าง (CB/agent.py:54-68 นี่คือสิ่งที่ทำให้ ASO ขอ 7 จุด และการรันแบบเดี่ยวขอ 119 จุดได้) ขอบเขตการเคลื่อนที่ถูกทดสอบทีละพิกัด (CB/agent.py:135-141) และทั้งการค้นหาและการปรับแต่งหยุดด้วยตัวนับก้าวเดียวกัน (CB/agent.py:238-243, :272-286) น้ำหนักโมเดลโหลดด้วย weights_only=True (CB/brain.py:133-135)
