GreedyReg บน VISOR: โค้ด

สำหรับนักพัฒนา: พอร์ต VISOR ของ GreedyReg ทำอะไรในโค้ด พร้อมการอ้างอิง file:line ซิกเนเจอร์ อาร์กิวเมนต์ สภาพแวดล้อม ความแตกต่างจากโค้ด legacy และข้อค้นพบ คำอธิบายที่อ่านง่ายของไปป์ไลน์เดียวกัน พร้อมคณิตศาสตร์ อยู่ในหน้าแอตลาส โมดูล legacy มีหน้าโค้ดของตัวเอง

VISOR โค้ด แอตลาส (คำอธิบาย) หน้า Legacy Guide (VISOR)

ใน VISOR GreedyReg เป็นแพ็กเกจ Python ที่รันบนเซิร์ฟเวอร์: Slicer ส่งสองโฟลเดอร์ของสแกน เซิร์ฟเวอร์จับคู่ตามผู้ป่วย รัน Greedy สองครั้งต่อคู่ (การค้นหาแบบ affine แล้ว resample T2 ลงใน T1) และส่งผลลัพธ์กลับมา Greedy ไม่ใช่ไบนารีที่ดาวน์โหลดอีกต่อไป แต่เป็นแพ็กเกจ picsl_greedy และคำสั่งที่มันได้รับคือของ legacy ทุกแฟลก หน้านี้อธิบายพอร์ตใน SADT-VISOR (สาขา tool/vface, 6ba2a78, 2026-09-30) ที่ VISOR-serve ให้บริการ (e9a7e5d) และขับจาก Slicer โดย extension AutomatedDentalToolsRemote (19b95e8) โมดูล legacy อธิบายอยู่ในหน้าของมันเอง นี่เป็นพอร์ตบางส่วน สิ่งที่มีอยู่คือแกนของ GreedyReg_CLI: จับคู่สแกนของสองโฟลเดอร์ตามผู้ป่วย จำกัดเมตริกด้วย mask และเริ่มจาก transform เริ่มต้นได้ตามต้องการ รัน Greedy และ resample โหมดแมนนวล การสร้าง mask ในฉาก การดาวน์โหลดไบนารี และโหมด Distant (landmark) ไม่อยู่ในเครื่องมือฝั่งเซิร์ฟเวอร์: run() ไม่มีอาร์กิวเมนต์สำหรับสิ่งใดเลย (SADT-VISOR GreedyReg/__init__.py:38-52) และไม่มีโหมด landmark ที่ใดใน SADT-VISOR (ตรวจด้วย git log --all -S"Landmark + Greedy") รายการ "Not ported" ของ README เองระบุเพียงโปรโตคอลความคืบหน้าทาง stdout และตัวกัน nibabel install (README.md:60-64) ไม่มีอะไรที่นี่อ้างว่ามีเซิร์ฟเวอร์ที่ deploy แล้ว

4.1 การจับคู่ T1 กับ T2 คำนวณ

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

ตัวเลือกถูกตรวจก่อน ดังนั้นเมตริกที่ผิดเป็นข้อผิดพลาดเดียว ไม่ใช่หนึ่งต่อผู้ป่วย (__init__.py:92 pipeline.py:47-55) จากนั้น pairing.pair(t1, t2, output_suffix) (__init__.py:102) กฎที่ใช้ร่วมกันเดินทั้งสองโฟลเดอร์แบบเรียกซ้ำ รับ .nii.gz .nrrd.gz .gipl.gz .nii .nrrd .gipl (pairing.py:36) และใช้ patient_stem เป็นคีย์ของแต่ละไฟล์: นามสกุล ส่วนต่อท้ายใด ๆ ที่การรัน ASO, AMASSS, ALI หรือ AREG ก่อนหน้าทิ้งไว้ และโทเค็นจุดเวลา ถูกลบออก และโฟลเดอร์ย่อยถูกเก็บไว้เป็นคำนำหน้า (pairing.py:175-211, 232-276) ไฟล์ที่ดูเหมือนเอาต์พุตก่อนหน้าของส่วนต่อท้ายของการรันนี้ถูกข้าม (pairing.py:214-229) ตัวอย่างที่รันเมื่อ 2026-11-09: 01_T1.nii.gz ให้ 01, Patient-01.nii.gz ให้ Patient_01, C_0001_T1_Or.nii.gz ให้ C_0001

4.2 mask และ transform เริ่มต้น คำนวณ

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

_discover_masks ใช้คีย์ของ mask เหมือนสแกนของมัน และตัดโทเค็นโครงสร้าง (โทเค็นบริเวณของ AREG และโทเค็น mask) ออกเฉพาะจากไฟล์ที่ชื่อบอกว่าเป็น mask ดังนั้น P1_T1_MAND_seg.nii.gz ได้คีย์ P1 ขณะที่ผู้ป่วยชื่อ MD_01 คงชื่อของเขาไว้ (__init__.py:28-35, 207-228) _discover_transforms ใช้คีย์ไฟล์ .mat แบบเดียวกันและตัด transform ออก ดังนั้น transform ของการรันหนึ่งป้อนกลับเป็นจุดเริ่มของการรันถัดไปได้ (__init__.py:231-248) mask และ transform ที่ไม่ตรงกับผู้ป่วยคนใดถูกแสดงในรายงาน (__init__.py:131-135)

4.3 จุดเริ่มของการค้นหา คำนวณ

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

เมื่อมี transform ให้มา Greedy เริ่มจากมันตามที่เป็น (-ia, __init__.py:261-262) ไม่เช่นนั้นเครื่องมือเขียน identity แบบ legacy ที่ขยับการเลื่อนตามแกน x เล็กน้อย (pipeline.py:101-114 legacy GreedyReg_CLI.py:86-90):

matrix = np.eye(4)
matrix[0, 3] = 0.001

docstring ให้เหตุผล: Greedy อ่าน identity ที่แน่นอนเป็น "no initialisation given" (pipeline.py:102-106 เป็นพฤติกรรมของ Greedy ไม่ได้ตรวจที่นี่) mask ถูกทำเป็นค่าสองค่าเหนือศูนย์เป็น float32 ด้วย affine ของ mask เอง ในโฟลเดอร์ชั่วคราว (pipeline.py:117-126 __init__.py:267-271) ไม่มีอะไรตรวจว่า mask อยู่ในปริภูมิของ T1

4.4 สองการเรียก Greedy คำนวณ

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

การค้นหาแบบ affine สร้างทีละอาร์กิวเมนต์เหมือน buildRegistrationCommand ของ legacy (pipeline.py:74-94 legacy GreedyReg_CLI.py:104-125):

-d 3 -rf <T1> -rm <T2> <patient>_<suffix>.nii.gz -r <patient>_transform.mat

เฉพาะการเรียก Greedy ที่ถูกจำกัด ไม่ใช่ทั้งการรัน

แต่ละการเรียก Greedy จำกัดที่ 600 s (SADT-VISOR GreedyReg/pipeline.py:136,145) และหนึ่งคู่ทำสองครั้ง (SADT-VISOR GreedyReg/__init__.py:273,276) ดังนั้นหนึ่งคู่อาจใช้เวลาได้ถึง 1200 s ไม่มีขีดจำกัดจำนวนคู่ และเซิร์ฟเวอร์ไม่ตั้งไว้ (TOOL_TIMEOUT_SECONDS = 0, VISOR-serve server/config.py:77) VISOR-serve CLAUDE.md:896 พูดถึงขีดจำกัด "ต่อคู่" แต่โค้ดจำกัดแต่ละการเรียก

ไม่มีรายงานเมื่อไม่มีอะไรลงทะเบียนสำเร็จ

ถ้าทุกคู่ล้มเหลว เครื่องมือยก exception (SADT-VISOR GreedyReg/__init__.py:180-187) ก่อนบรรทัดที่เขียน GreedyReg_report.json (:189) เหตุผลจึงเดินทางไปกับข้อความผิดพลาดเท่านั้น reason ของผู้ป่วยที่ล้มเหลวคือข้อความ exception (:167)

.mat ที่ผลิตไม่ใช่ transform ของ Slicer ปริภูมิของ mask ไม่ถูกตรวจ

<patient>_transform.mat คือสิ่งที่ Greedy เขียนด้วย -o (SADT-VISOR GreedyReg/pipeline.py:86 __init__.py:255) ไม่มีอะไรในแพ็กเกจแปลงมันเป็น .tfm และไคลเอนต์ไม่โหลดมัน (GreedyRegRemote.py:97-104) mask หลายเลเบลถูกทำให้แบนด้วย > 0 และไม่มีอะไรตรวจว่ามันอยู่ในปริภูมิของ T1 (pipeline.py:117-126) ทั้งสองข้อเป็นของโมดูล legacy (หน้า legacy) ที่ส่งต่อมาโดยไม่เปลี่ยน อ่านจากโค้ด

ค่าเริ่มต้นที่ต่างจากโมดูล legacy

เมตริกเริ่มต้นคือ NCC ขณะที่ combo ของ legacy เริ่มด้วย NMI (SADT-VISOR GreedyReg/__init__.py:49, GreedyReg.py:575@3c67957) transform เป็น Rigid โดยค่าเริ่มต้น และส่วนต่อท้ายตั้งค่าได้ (output_suffix) ขณะที่ CLI ของ legacy เขียน _registered (GreedyReg_CLI.py:168@3c67957)

Greedy ถูกสมมติว่าใช้ GPU

เครื่องมือไม่ประกาศอาร์กิวเมนต์ device การรับเข้า (admission) ของเซิร์ฟเวอร์จึงมองทุกการรันเป็นการรัน GPU (VISOR-serve server/execution/dispatch.py:95-116) ขณะที่ Greedy รันบน CPU การรัน GreedyReg จึงอาจรอช่อง GPU ที่มันไม่ใช้ อ่านจากโค้ด

การจับคู่และความล้มเหลวชัดเจน

ผู้ป่วยที่ไม่ตรงกัน mask ที่ไม่ได้ใช้ และ transform เริ่มต้นที่ไม่ได้ใช้ถูกรายงาน (SADT-VISOR GreedyReg/__init__.py:108,131-132) ผู้ป่วยที่ล้มเหลวหนึ่งคนเสียแค่หนึ่งคน เมตริกและชนิด transform ถูกตรวจสองครั้ง (pipeline.py:47-55) 189 เทสต์ของแพ็กเกจผ่านเมื่อ 2026-11-09 โดยใช้ Greedy ปลอม

10. วรรณกรรม

คำอธิบายแบบภาษาง่ายและคณิตศาสตร์: หน้าแอตลาส

เอนจินลงทะเบียนคือ Greedy เหมือนในโมดูล legacy และบรรณานุกรมเป็นของเครื่องมือ: แหล่งที่มาของ GreedyReg สำหรับกลไกของ VISOR ที่ทุกเครื่องมือใช้ร่วมกัน ดูสถาปัตยกรรมและการรันทีละขั้น สำหรับการใช้แผง ดูคู่มือ VISOR
