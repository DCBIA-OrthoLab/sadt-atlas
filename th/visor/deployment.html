1. อิมเมจ

มีคอนเทนเนอร์ เดียว สำหรับทุกเครื่องมือ docker/Dockerfile (232 บรรทัด) บิลด์เป็นหลายสเตจ สเตจรันไทม์เริ่มจาก python:3.13-slim (:76) ติดตั้งไลบรารีระบบหนึ่งตัวที่ lockfile ใดก็ให้ไม่ได้ คือ libgomp1 (:86) คัดลอก uv 0.12.3 (:89) และสร้างสภาพแวดล้อม API ที่ /opt/sadt/.venv จาก server/requirements-api.txt ซึ่งระบุเพียง fastapi, uvicorn[standard], python-multipart และ pydantic-settings (:105-108) โพรเซสเซิร์ฟเวอร์จึงไม่นำเข้า torch ไม่นำเข้า nnU-Net และไม่นำเข้า MONAI อินเทอร์พรีเตอร์ของแต่ละเครื่องมือถูกติดตั้งโดย uv เอง (:75) เครื่องมือจึงอยู่บน Python คนละเวอร์ชันได้

  • เครื่องมือถูกอบรวมไว้แล้ว เครื่องมือที่แพ็กเกจแต่ละตัวคือโฟลเดอร์ /tools/<name>/ ที่มี .venv, src/ และ .schema.json เครื่องมือในโฟลเดอร์กลุ่ม (tools/ALI/ALI_CBCT) ถูกพบเพราะการค้นหาลงไปสองระดับ (registry/__init__.py:114) แพ็กเกจ naming/ ถูกคัดลอกไปที่ /naming เพราะเครื่องมือพึ่งพามันด้วยพาธ (Dockerfile:122) fixture ในโพรเซสสองตัว Example_Tool และ Test_Tool อยู่ ใน อิมเมจ: COPY server/ หยิบ server/tools/ ไปด้วย และ .dockerignore:18-30 อธิบายว่าการยกเว้นถูกเอาออกแล้ว เพื่อให้การติดตั้งใหม่พิสูจน์ auth, upload, run และผลลัพธ์ได้ก่อนดาวน์โหลดโมเดลใด อินสแตนซ์ที่กำลังรันให้บริการทั้งสองตัว (23 รายการ)
  • หนึ่ง layer uv sync โดยเจตนา uv sync --frozen --no-install-project --no-dev --all-extras ของทุกเครื่องมือรันใน RUN เดียว (:152) พร้อม UV_LINK_MODE=hardlink และแคชของ uv บนระบบไฟล์ของอิมเมจเอง (:96-101) หากแยกข้าม layer overlayfs จะคัดลอกไฟล์ขึ้นไปและ hardlink ขาด คอมเมนต์ใน Dockerfile เองวัดเครื่องมือ torch สิบเอ็ดตัวได้ราว 26 GB เมื่อใช้ร่วมกัน เทียบกับราว 63 GB เมื่อซ้ำซ้อน (:131-134) --all-extras ตั้งใจใส่ไว้: เครื่องมืออย่าง Crown_Seg เก็บเอนจินไว้หลัง extra และหากไม่มี อิมเมจจะนำเข้าได้ แล้วตอบ 503 ตั้งแต่คำขอจริงครั้งแรก
  • verify_dedup.py ไม่มีสิ่งใดที่สังเกตได้ล้มเหลวเมื่อลิงก์กลายเป็นสำเนาโดยเงียบ docker/verify_dedup.py จึงตรวจเรื่องนี้: สำหรับไฟล์ที่อยู่ใน distribution เดียวกัน ที่เวอร์ชันเดียวกัน (อ่านจาก RECORD ของแต่ละสภาพแวดล้อม) inode ที่สองหมายถึงสำเนา สคริปต์จบด้วยค่าไม่ใช่ศูนย์เมื่อพบสำเนาใด ใช้เฉพาะไลบรารีมาตรฐาน และถูกส่งมาในอิมเมจที่ /opt/sadt/verify_dedup.py (Dockerfile:200) fixture ทดสอบคือ numpy_old (1.26.4, Python 3.12), numpy_new (2.5.2, Python 3.13) และ numpy_twin
  • schema ถูกสร้างตอนบิลด์ โดยรัน describe.py ของแต่ละเครื่องมือด้วยอินเทอร์พรีเตอร์ของเครื่องมือนั้นเอง (:177-188) เครื่องมือที่อธิบายตัวเองไม่ได้จะถูกรายงานและไม่ถูกให้บริการ ตอนเริ่มระบบ schema ที่ล้าสมัยจะถูกสร้างใหม่และแคชใน SCHEMA_CACHE_DIR (/var/cache/sadt) เพราะ /tools เป็นแบบอ่านอย่างเดียวสำหรับเซิร์ฟเวอร์
  • ไม่อยู่ในอิมเมจ: โมเดลและไฟล์ทดสอบ (หัวข้อ 2) deployment.toml ประจำไซต์ (หัวข้อ 4 อิมเมจมีสำเนาเริ่มต้นที่การ mount เข้าไปแทนที่ได้) พื้นที่ scratch ของงาน /jobs และโทเค็น API
  • โพรเซส USER sadt ไม่ใช่ root (:227) โค้ดใน /tools เป็นของ root และอ่านอย่างเดียวสำหรับเซิร์ฟเวอร์ เพื่อให้โค้ดของบุคคลที่สามเขียนทับ virtual environment ของตัวเองไม่ได้ CMD คือ uvicorn main:app --host 0.0.0.0 --port 8000 โดยไม่มี --reload และไม่มี --workers จึงมีหนึ่งโพรเซสและหนึ่งคิว admission (:232) ไม่มี HEALTHCHECK ใน Dockerfile หรือใน docker-compose.yml

สภาพแวดล้อมที่อิมเมจตั้ง (Dockerfile:202-216) คือ SADT_DISPATCH_MODE=subprocess, TOOLS_DIR=/tools, RUNNER_PATH=/opt/sadt/server/execution/runner.py, DESCRIBE_PATH=/tools/scripts/describe.py, SCHEMA_CACHE_DIR=/var/cache/sadt, DEPLOYMENT_CONFIG=/opt/sadt/server/deployment.toml, DATA_DIR=/DATA, TEMP_DIR=/jobs และ PYTHONDONTWRITEBYTECODE=1 ค่าเริ่มต้นของ SADT_DISPATCH_MODE ใน config.py:37 คือ inprocess ซึ่งระบุว่าเป็นชั่วคราว อิมเมจเขียนทับค่านี้ ดังนั้นสิ่งที่คอนเทนเนอร์รันจึงเป็นเส้นทาง subprocess เสมอ

ไฟล์ compose นิยามหลายบริการ บริการที่เป็นการติดตั้งใช้งานจริงคือ inference-venvs (โปรไฟล์ venvs, docker-compose.yml:200): มันบิลด์ docker/Dockerfile ด้วย named build context tools=${TOOLS_CONTEXT:-docker/fixtures} ดังนั้นหากไม่มี TOOLS_CONTEXT มันจะบิลด์ fixture ขนาดเล็ก ไม่ใช่เครื่องมือจริง มันตั้ง shm_size: 8gb (nnU-Net ส่งข้อมูลระหว่าง export worker ผ่านหน่วยความจำร่วม ค่าเริ่มต้น 64 MB ล้มเหลวพร้อมข้อความที่ชี้ผิดทรัพยากร) จองทุก GPU และรีสตาร์ตแบบ unless-stopped บริการอื่นคือ inference (อิมเมจ GPU สำเร็จรูปจาก container registry พร้อม mount ./server รัน pip ทุกครั้งที่เริ่ม และ uvicorn --reload), inference-cpu และบริการ test / test-gpu docker-compose.dev.yml เป็น overlay ที่ mount server/ และ src/ ของแต่ละเครื่องมือจาก checkout ของ SADT-VISOR แบบอ่านอย่างเดียว

2. โมเดลและไฟล์ทดสอบ

น้ำหนักโมเดลไม่เคยอยู่ในอิมเมจ และไม่เคยอัปโหลดจากแล็ปท็อป มันอยู่ในไดเรกทอรี DATA/ ที่ mount ที่ /DATA แบบ อ่านอย่างเดียว: DATA/<slug>/models/<name> และ DATA/<slug>/testfiles/<name> โดยอาจลึกลงอีกหนึ่งระดับเป็นขอบเขต (DATA/AREG/testfiles/CBCT_T1) LocalDataStore อ่านมัน แบ็กเอนด์อื่นเสียบเข้าได้ผ่านคลาสนามธรรม DataStore (DATA_BACKEND, config.py:31)

  • โฟลเดอร์ไหน slug คือ data_dir ที่เครื่องมือประกาศ หากไม่มี ใช้ชื่อเครื่องมือตามตัวอักษรเมื่อมีโฟลเดอร์นั้น มิฉะนั้นใช้ชื่อที่ไม่มีขีดล่าง ดังนั้น Batch_Dental_Seg อ่าน DATA/BatchDentalSeg (deployment.data_slug, registry/deployment.py:311-325) เครื่องมือห้าตัวใช้สองโฟลเดอร์ร่วมกันผ่าน data_dir = "AREG" (สามเครื่องมือ) หรือ "ALI" (สองเครื่องมือ)
  • อาร์กิวเมนต์ใดถูกเติมจากมัน ตามข้อตกลงการตั้งชื่อ (registry/conventions.py): model, *_model และ *_reference ถูกเผยแพร่เป็น ชื่อที่เลือกจาก DATA/<tool>/models/ ไม่เคยเป็นการอัปโหลด น้ำหนักโมเดลจึงส่งจากไคลเอนต์ไม่ได้ การอัปโหลดไฟล์ในช่องเช่นนั้นคือ 400 (main.py:1269-1278) path อื่นใดอัปโหลดได้หรือเติมจาก testfiles/
  • API เสนออะไร GET /tools/{tool}/data แสดงรายการโมเดลและไฟล์ทดสอบ GET|HEAD /tools/{tool}/testfiles/{name} ให้บริการไฟล์ทดสอบ ไม่มีเส้นทางที่ให้บริการโมเดล (download_testfile อ่านเฉพาะ testfiles) โฟลเดอร์ไฟล์ทดสอบถูกบีบเป็น zip ทันทีและส่งพร้อม Accept-Ranges: none มิฉะนั้นไคลเอนต์จะ probe เห็น range แล้วแบ่ง cohort ขนาด 339 MB เป็น 43 ส่วน โดยเซิร์ฟเวอร์สร้างอาร์ไคฟ์เดียวกัน 43 ครั้ง: 39.1 s แบบ range เทียบกับ 1.5 s แบบทั้งก้อน (main.py:794-806)
  • การเติมข้อมูล scripts/data-manifest.yml บอกว่ามีอะไร มาจากไหน และไปที่ไหน scripts/fetch_data.py (ไลบรารีมาตรฐานเท่านั้น) ดาวน์โหลดมัน setup-models.sh และ setup-testfiles.sh เป็นตัวห่อ และ --list พิมพ์ขนาดต่อเครื่องมือโดยไม่ดาวน์โหลด แต่ละรายการมี name, url, sha256 ที่ไม่บังคับ (หากไม่ตรง ไฟล์จะถูกทิ้ง หากไม่มี สคริปต์จะพิมพ์แฮชที่ได้ เพื่อวางลงใน manifest), size ที่ไม่บังคับ, extract: true เพื่อคลาย zip และเก็บโฟลเดอร์ และ dest เพื่อเปลี่ยนชื่อหรือรวมหลายอาร์ไคฟ์เป็นโฟลเดอร์ bundle เดียว คอมเมนต์ใน manifest ประเมินทั้งชุดที่ราว 29 GB ใน 14 เครื่องมือ ซึ่ง 12 GB เป็นโมเดล CBCT ของ ALI

ข้อสังเกตที่ลงวันที่ ไม่ใช่คุณสมบัติของโค้ด

มีการตรวจอินสแตนซ์ที่กำลังรันหนึ่งตัวเมื่อ 2026-10-20 (รายงานที่เก็บไว้นอกที่เก็บโค้ด) สิ่งที่พบเกี่ยวกับเครื่องนั้นอาจไม่เป็นจริงอีกต่อไป หัวข้อนี้เก็บสิ่งที่โค้ดอธิบายได้ ส่วนรายละเอียดที่ระบุตัวเครื่องหรือเครือข่ายถูกตัดออกโดยเจตนา การตรวจเดียวที่ทำระหว่างเขียนหน้านี้คือ GET /health และ GET /tools แบบไม่ยืนยันตัวตน: ตอบ {"status":"ok"} และ 23 รายการ

  • สิ่งที่โค้ดทำนาย มันเป็นเช่นนั้น GET /health และ GET /tools ตอบโดยไม่ต้องมีโทเค็น GET /status ปฏิเสธคำขอที่ไม่มีโทเค็น (401) แค็ตตาล็อกมี 23 รายการ ซึ่ง 19 รายการมาจาก schema บันทึกตอนเริ่มระบบไม่มี skip, error หรือ traceback คำเตือนเดียวคือคีย์ของ schema ที่ถูกละเลยของ ALI_CBCT, ALI_IOS และ ASO ซึ่งอธิบายไว้ในหน้าสถาปัตยกรรม
  • HTTP ธรรมดา ตรงจากคอนเทนเนอร์ ไคลเอนต์ Slicer ของ AutomatedDentalToolsRemote ต้องใช้ HTTPS ที่มีใบรับรองลงนามสาธารณะและไม่มี fallback (หน้าความปลอดภัย) จึงเชื่อมต่อกับอินสแตนซ์ที่เปิดแบบนั้นไม่ได้ สคริปต์ที่เรียก API โดยตรงทำได้
  • ไม่มี .env อินสแตนซ์ถูกเริ่มโดยไม่มีมัน จึงรันด้วยค่าเริ่มต้นของ compose ที่อธิบายในหัวข้อ 3 รวมถึงโทเค็น

รายงานจากนั้นไล่รายการสิ่งที่อาจหยุดการรันแบบไม่มีคนเฝ้า แต่ละข้อด้านล่างถูกตรวจกับโค้ด รายงานระบุว่าสี่ข้อแรกอนุมานจากโค้ด ค่ากำหนด และบันทึก ไม่ใช่จากการรันจริง

  1. ไม่มี timeout TOOL_TIMEOUT_SECONDS เป็น 0 และ deployment.toml ไม่ตั้งอะไร (config.py:77): สี่การรันที่ถูกบล็อกทำให้เซิร์ฟเวอร์ค้างโดยไม่มีตัวใดล้มเหลว
  2. เครื่องมือที่ยังไม่เคยวัดรันตัวเดียว เครื่องมือที่ยังไม่เคยวัดต้นทุนจะจองงบทั้งหมด (execution/admission.py:22-33) บนอินสแตนซ์นั้น เครื่องมือส่วนใหญ่ยังไม่มีต้นทุนที่วัดได้ ดังนั้น max_parallel_jobs: 4 ที่ประกาศจึงประเมินปริมาณงานจริงสูงเกินไป
  3. การจองตามการรันที่แย่ที่สุดล่าสุด ต้นทุนที่เรียนรู้คือค่าสูงสุดของ COST_WINDOW = 20 การรันล่าสุด (config.py:106) เครื่องมือที่ใช้หน่วยความจำต่างกันมากระหว่างอินพุตจึงจองกรณีเลวร้ายที่สุดและทำงานเรียงลำดับ
  4. ไม่มีตัวเลข VRAM บนอินสแตนซ์นั้น /status คืน vram_bytes: null และการ์ดที่มี free_bytes: null: โพรบซึ่งเรียก nvidia-smi (resources.py:193) ไม่คืนอะไร และ /status ยอมรับเรื่องนี้โดยการออกแบบ (main.py:470-474) admission จึงทำงานบนคอร์และ RAM
  5. การรันที่ล้มเหลวก็ยังสอนตารางต้นทุน การวัดถูกเก็บก่อนสาขา error โดยเจตนา เพราะการรันที่หน่วยความจำไม่พอคือการวัดที่มีประโยชน์ที่สุด (execution/dispatch.py:800-803) เบนช์ที่ล้มเหลวด้วยเหตุที่ไม่เกี่ยวข้องจึงอาจทำให้การจองครั้งต่อ ๆ ไปพองเกินจริง
  6. ไม่มี healthcheck ใน Dockerfile หรือใน compose: restart: unless-stopped เริ่มคอนเทนเนอร์ที่ตายแล้วใหม่ แต่ไม่มีสิ่งใดตรวจจับคอนเทนเนอร์ที่ยังมีชีวิตแต่ค้าง
  7. SIGKILL ของผู้ดูแลระบบดูเหมือนการตายเพราะหน่วยความจำไม่พอ SIGKILL ที่ไม่มี result.json ถูกอ่านว่าเป็นการ kill เพราะหน่วยความจำไม่พอของเคอร์เนล (execution/dispatch.py:930-949) การรันจึงเริ่มใหม่
