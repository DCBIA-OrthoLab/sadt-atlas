FlexReg บน VISOR

FlexReg ลงทะเบียนส่วนโค้งฟันในช่องปากหนึ่งไปบนอีกส่วนหนึ่งโดยมองเพียงเพดานปาก ส่วนของปากที่ไม่ขยับระหว่างสองครั้งที่มาพบ มันวาดpatch รูปผีเสื้อบนเพดานปากก่อน จากฟันสี่ซี่ แล้วเลื่อน patch ของสแกนหนึ่งไปบน patch ของอีกสแกน หน้านี้อธิบายวิธีการทีละขั้นพร้อมคณิตศาสตร์ ตรงที่โค้ดทำสิ่งที่ควรตรวจ จะมีลิงก์ไปยังหน้าโค้ด โมดูล legacy อธิบายอยู่ในหน้าของมันเอง

VISOR โค้ด (นักพัฒนา) หน้า Legacy Guide (VISOR)

ภาพรวม: อะไรเข้า อะไรออก

ระหว่างสองครั้งที่มาพบ ฟันอาจเคลื่อน เหงือกก็เช่นกัน เพดานปากแทบไม่เคลื่อน FlexReg ใช้ข้อนั้น: มันทำเครื่องหมาย patch ของเพดานปากบนแต่ละส่วนโค้งฟัน และลงทะเบียนส่วนโค้งฟันบน patch นั้นเท่านั้น เพื่อให้ตัวฟันเองเคลื่อนได้อย่างอิสระ patch ถูกสร้างด้วยเรขาคณิต ไม่ใช้เครือข่าย จากฟันสี่ซี่ที่เลือกบนส่วนโค้งฟัน

คืออะไร
อินพุตพื้นผิวในช่องปาก (.vtk, .vtp หรือ .stl) ที่มีเลขฟันบนทุกจุดอยู่แล้ว หรือโฟลเดอร์ของพื้นผิวเหล่านั้น และส่วนโค้งฟัน reference ที่จะลงทะเบียนไปบน
แนวคิดcentroid ของฟันสี่ซี่ให้สี่มุม มุมให้เส้นขอบ เส้นขอบถูกเติมทั่วพื้นผิว และ ICP แบบแข็งจัด patch ของส่วนโค้งฟันหนึ่งให้ตรงกับ patch ของอีกส่วนหนึ่ง
เอาต์พุตพื้นผิวที่ลงทะเบียนแล้ว transform .tfm ที่ Slicer โหลดได้ และ FlexReg_report.json

สามโหมด: Patch สร้างเฉพาะ patch Register ลงทะเบียนพื้นผิวที่มี patch อยู่แล้ว Patch and register ทำทั้งสองอย่าง

1. ตำแหน่งในสายโซ่

FlexReg ไม่เรียกเครื่องมืออื่น และไม่มีเครื่องมือใดเรียกมัน ในโมดูล legacy widget รันการ segment ครอบฟันเมื่อส่วนโค้งฟันไม่มีเลเบลฟัน ใน VISOR ส่วนโค้งฟันต้องมาถึงพร้อมเลเบลอยู่แล้ว เช่นจากการรัน Crown_Seg ไม่มีอะไรคำนวณ patch เหงือกอีกต่อไป

ในโค้ดสถานะของพอร์ต การเรียก และสิ่งที่คาดหวังจากต้นทาง

2. ไฟล์ที่เกี่ยวข้อง

เครื่องมือคือแพ็กเกจ Python ธรรมดา: แกนเรขาคณิตของมัน (การวางทิศทาง patch การแพร่ ICP การเลือกฟัน) คือโค้ด legacy ที่เปลี่ยนชื่อตัวแปร และส่วนใหม่คือจุดเข้ากับฟังก์ชันอ่าน รวม ลงทะเบียน และเขียนรอบ ๆ มัน ไลบรารีเล็ก ๆ ในไคลเอนต์ Slicer เล่นเส้นขอบซ้ำสำหรับตัวอย่าง

ในโค้ดทุกไฟล์พร้อมขนาดและบทบาท ทั้งบนเซิร์ฟเวอร์และในไคลเอนต์

3. อะไรรันที่ไหน

เซิร์ฟเวอร์สร้าง patch จริง (การเติมต้องใช้ GPU) ลงทะเบียน และเขียนทุกอย่าง แผง Slicer เพียงแสดงตัวอย่างเส้นขอบ: ขณะที่คุณลากจอยสติ๊ก เส้นขอบถูกคำนวณใหม่ในเครื่องด้วยค่าคงที่เดียวกันและวาดในฉาก โดยไม่ต้องไปกลับกับเซิร์ฟเวอร์ การเติม patch ปล่อยให้เป็นหน้าที่ของเซิร์ฟเวอร์ ตัวอย่างทำงานเมื่อพื้นผิวอยู่ในฉาก Slicer แล้วเท่านั้น ไม่ใช่สำหรับโฟลเดอร์

ในโค้ดแต่ละฝั่งคำนวณอะไร และตัวอย่างเล่นเซิร์ฟเวอร์ซ้ำอย่างไร

4. ไปป์ไลน์ ทีละขั้น

หนึ่งการรันจัดการหนึ่งพื้นผิวหรือโฟลเดอร์ของพื้นผิว

ในโค้ดลำดับของการเรียกในจุดเข้า

4.1 การตรวจก่อนอ่าน คำนวณ

โหมดตัดสินว่าจะลงทะเบียนหรือไม่ และจะลงทะเบียนบนอาร์เรย์ใด: Butterfly สำหรับเพดานปาก Bottom_MGL สำหรับเส้น mucogingival การลงทะเบียนที่ไม่มี reference ถูกปฏิเสธก่อนอ่านไฟล์ใด ๆ และ reference ถูกอ่านครั้งเดียวสำหรับทั้ง batch โฟลเดอร์ถูกเดินแบบเรียกซ้ำและเรียงลำดับ ดังนั้นสองการรันตั้งชื่อเอาต์พุตแบบเดียวกัน

ในโค้ดการปฏิเสธ การเดินโฟลเดอร์ และนามสกุล

4.2 การอ่านและการพลิกพิกัด คำนวณ

ไฟล์ถูกอ่านตามนามสกุล และเมชว่างถูกปฏิเสธโดยระบุชื่อ เรขาคณิตทั้งหมดถูกเขียนใน RAS ขณะที่ไฟล์ Slicer อยู่ใน LPS พื้นผิวจึงถูกสะท้อนใน x และ y ก่อน (การหมุนครึ่งรอบรอบแกนตั้ง) การดำเนินการเดียวกันพลิกมันกลับก่อนเขียน เมทริกซ์ที่พบภายหลังถูกแปลงแบบเดียวกัน ดู 4.6

ในโค้ดตัวอ่าน การปรับสเกลด้วย (-1, -1, 1) และการตรวจเมชว่าง

4.3 patch เพดานปาก ("butterfly") คำนวณ

สร้างเฉพาะเมื่อโหมดมี Patch และ patch คือเพดานปาก ส่วนโค้งฟันถูกวางทิศทางแบบมาตรฐานก่อน จาก centroid ของฟันสี่ซี่ที่คงที่ (3, 5, 12, 14 คือ UR6, UR4, UL4, UL6 เลขฟันเป็นระบบ Universal 1 ถึง 16 ตามส่วนโค้งบนจากฟันกรามซี่ที่สามขวา 17 ถึง 32 ตามส่วนโค้งล่างจากฟันกรามซี่ที่สามซ้าย): ระนาบสบฟันอยู่ใกล้ z = 0, +y ชี้ไปด้านหน้า และ +x ไปทางซ้ายของผู้ป่วย สำเนาที่วางทิศทางแล้วนี้ใช้เพื่อวาด patch เท่านั้น (patch ถูกเขียนกลับลงพื้นผิวเดิม) ไม่ใช่กรอบ RAS ที่ใช้สำหรับการลงทะเบียน ฟันสี่ซี่ที่ขับเคลื่อนมุมจากนั้นถูกเฉลี่ยเป็น centroid โดยค่าเริ่มต้นคือฟันซี่ 6, 11, 3 และ 14 และฟันที่หายไปเป็นข้อผิดพลาดของอินพุตที่ระบุชื่อมัน

อาร์เรย์ patch ถูกเขียนลงในพื้นผิวเดิม ไม่ใช่ในสำเนาที่วางทิศทางแล้ว

ในโค้ดหกขั้นพร้อมค่าคงที่ การกัน และเลขบรรทัด

4.4 การรวมอาร์เรย์ patch คำนวณ

เมื่อมีหลาย patch ที่มีหมายเลขบนเมช (Butterfly1, Butterfly2 และอื่น ๆ) พวกมันถูกรวมด้วย logical OR เป็นอาร์เรย์ Butterfly เดียว ซึ่งรันทันทีหลังสร้าง patch ในการรันเดียวกันเท่านั้น

ในโค้ดฟังก์ชันรวมและเวลาที่มันถูกเรียก

4.5 การลงทะเบียนบน patch คำนวณ

พื้นผิวที่เคลื่อนต้องมีอาร์เรย์ patch ไม่เช่นนั้นถูกปฏิเสธ ICP เก็บไว้ในทั้งสองส่วนโค้งฟัน เฉพาะจุดที่อาร์เรย์เท่ากับ 1 และลงทะเบียนจุดเหล่านั้น เมทริกซ์ที่มันพบจากนั้นถูกนำไปใช้กับเมชที่เคลื่อนทั้งก้อน รวมฟัน พื้นผิวที่คุณให้คือตัวที่เคลื่อน และ reference คือตัวที่คงที่

ในโค้ดการเรียก การตั้งค่า VTK และการปฏิเสธเมื่อไม่มีอาร์เรย์

4.6 Transform และการเขียน คำนวณ

พื้นผิวถูกพลิกกลับและเขียนเป็นไฟล์ VTK legacy แบบไบนารี ไม่ว่านามสกุลอินพุตจะเป็นอะไร เอาต์พุตสะท้อนต้นไม้โฟลเดอร์อินพุตใต้โฟลเดอร์เอาต์พุต พร้อมส่วนต่อท้าย อินพุตไม่ถูกแก้ไขเลย พื้นผิวที่ยกข้อผิดพลาดของอินพุตถูกบันทึกเป็น failed และการรันทำต่อ

ในโค้ดการสร้างเมทริกซ์ ตัวเขียน และชื่อเอาต์พุต

4.7 รายงาน คำนวณ

FlexReg_report.json ระบุต่อพื้นผิว patch ที่ใช้ อาร์เรย์ที่ลงทะเบียนบน ไฟล์ transform และเอาต์พุต และสถานะ และจบด้วยสรุปยอดรวม มันถูกเขียนก่อนการปฏิเสธสุดท้าย "none of the surfaces could be processed" ดังนั้นการรันที่ไม่สำเร็จเลยก็ยังทิ้งเหตุผลไว้

ในโค้ดโครงสร้างของรายงานและข้อความความคืบหน้า

5. สิ่งที่เลือกได้

  • พื้นผิว: ส่วนโค้งฟันที่มีเลเบลหนึ่งอันหรือโฟลเดอร์ มีไฟล์ทดสอบที่โฮสต์ให้เลือก
  • โหมด: Patch, Register หรือ Patch and register (ค่าเริ่มต้น)
  • patch: เพดานปาก (butterfly) หรือเส้น mucogingival อย่างหลังลงทะเบียนได้ก็ต่อเมื่ออาร์เรย์มีอยู่แล้วเท่านั้น
  • reference ที่จะลงทะเบียนไปบน ต้องมี patch ของมันอยู่แล้ว
  • จอยสติ๊กสี่ตัว หนึ่งต่อมุม: ratio (0 ถึง 1 จากกึ่งกลางไปที่ฟัน) และการปรับ (-5 ถึง 5 mm ตามส่วนโค้งฟัน) และจอยสติ๊กตัวที่ห้าที่เลื่อนทั้ง patch ได้สูงสุด 15 mm
  • ส่วนต่อท้ายของชื่อเอาต์พุต (_Reg โดยค่าเริ่มต้น) เลขฟันทั้งสี่มีอยู่แต่ถูกซ่อน
ในโค้ดทุกอาร์กิวเมนต์พร้อมชนิด ขอบเขต และการมองเห็น และกฎการแบ่ง batch

6. อะไรทำนาย อะไรคำนวณ

บล็อกลักษณะ
ป้ายกำกับฟันทำนายที่ต้นทาง โดยสิ่งใดก็ตามที่ติดเลเบลส่วนโค้งฟัน FlexReg ไม่ได้รัน
การวางทิศทาง centroid มุม เส้นขอบคำนวณทางเรขาคณิต (เล่นซ้ำในไคลเอนต์สำหรับตัวอย่างด้วย)
การเติม patchคำนวณ geodesic flood fill บน GPU
การรวมอาร์เรย์ patchคำนวณ logical OR
การลงทะเบียนภาพคำนวณ ICP แบบแข็ง (VTK) จำกัด 1000 รอบ บน CPU
patch เหงือกไม่ถูกคำนวณที่ใดใน VISOR

FlexReg บน VISOR ไม่รันเครือข่ายเลย: อินพุตที่ทำนายสองอย่างของโมดูล legacy คือการ segment ครอบฟันและlandmark mucogingival อยู่นอกพอร์ตทั้งคู่

ในโค้ดแต่ละบล็อกรันที่ไหน

7. สภาพแวดล้อม

เครื่องมือมีสภาพแวดล้อม Python ของตัวเองพร้อม torch (สำหรับการเติมเท่านั้น), vtk, numpy และ SimpleITK เซิร์ฟเวอร์สมมติว่าใช้ GPU ทุกโหมด รวมถึงการลงทะเบียนธรรมดา ไม่มีอะไรติดตั้งใน Slicer ไลบรารีตัวอย่างต้องการเพียง vtk และ numpy

ในโค้ดเวอร์ชันที่ปักไว้ ไฟล์ทดสอบที่โฮสต์ และขีดจำกัด

8. อะไรเปลี่ยนไปจากตรรกะของ legacy

เรขาคณิตของ patch และของการลงทะเบียนเป็นโค้ดเดียวกัน สิ่งที่เปลี่ยนคือสิ่งที่ห่อหุ้มมัน

  • ฟันที่หายไป ตอนนี้เป็นข้อผิดพลาดที่ทำให้พื้นผิวนั้นล้มเหลว ส่วน legacy บันทึกลงล็อก เขียนเมชโดยไม่มี patch และดูเหมือนสำเร็จ
  • อินพุต: .vtk, .vtp และ .stl ถูกอ่านโดยตรง
  • เอาต์พุตไปที่โฟลเดอร์แยกพร้อมส่วนต่อท้าย ส่วน legacy เขียนไฟล์อินพุตใหม่ในโหมด patch
  • การรวม patch ที่มีหมายเลขรันบน CPU และเฉพาะหลังสร้าง patch เท่านั้น
  • ไม่มี: patch ที่วาดอิสระ การลบ patch การคำนวณ patch เหงือก การ segment ครอบฟัน และการพาส่วนโค้งฟันที่สองไปพร้อมกับส่วนแรก
  • พารามิเตอร์เป็นจอยสติ๊กที่มีขอบเขต ตรวจโดยเซิร์ฟเวอร์ ส่วน legacy รับตัวเลขที่พิมพ์
ในโค้ดตารางเต็มพร้อมการอ้างอิงของ legacy และ VISOR

9. ปัญหาที่ทราบใน VISOR

  • "Patch and register" ใส่ patch เฉพาะพื้นผิวที่เคลื่อน ดังนั้น reference ต้องมี patch ของมันอยู่แล้ว (รายละเอียด)
  • เฉพาะข้อผิดพลาดของอินพุตที่ถูกรายงานต่อพื้นผิว exception อื่นใดหยุดทั้ง batch และไม่ทิ้งรายงาน (รายละเอียด)
  • เส้น mucogingival ไม่สามารถถูกผลิตโดยสิ่งใดใน VISOR (รายละเอียด)
  • ถ้าไม่มีอาร์เรย์เลเบลฟัน อาจเลือกอาร์เรย์ผิดโดยไม่มีเสียง (รายละเอียด)
  • ฟันสี่ซี่สำหรับวางทิศทางคงที่ ดังนั้นส่วนโค้งฟันที่ขาดซี่ใดซี่หนึ่งในนั้นล้มเหลว แม้ฟันสี่ซี่ที่เลือกจะมีอยู่ (รายละเอียด)
  • อินพุต .stl หรือ .vtp ได้ไฟล์ที่มีนามสกุลนั้นแต่เนื้อหาเป็น VTK (รายละเอียด)
  • การสร้าง patch จริงไม่มีเทสต์ (รายละเอียด)

10. วรรณกรรม

วิธีการเป็นของ legacy ดังนั้นบรรณานุกรมของมันคือของเครื่องมือ: แหล่งที่มาของ FlexReg สำหรับกลไกของ VISOR ที่ทุกเครื่องมือใช้ร่วมกัน ดูสถาปัตยกรรมและการรันทีละขั้น สำหรับการใช้แผง ดูคู่มือ VISOR
