2. การยืนยันตัวตน: token ร่วมหนึ่งตัว

ทุกเส้นทางที่ทำงานขึ้นอยู่กับ verify_token: scheme ต้องเป็น Bearer และข้อมูลรับรองถูกเปรียบเทียบกับ API_TOKEN ด้วย secrets.compare_digest ซึ่งเป็นการเปรียบเทียบแบบ constant-time; อย่างอื่นคือ 401 (VISOR-serve server/wire/security.py:13-31) การทดสอบป้อน header ที่ผิดรูปแบบและผิดค่า และตรวจว่า token ไม่เคยถูกสะท้อนกลับ (server/tests/test_security.py:43,50) เส้นทางที่เกี่ยวข้องรวมถึง /status (main.py:447), /maintenance (:518), /uploads (:833), /results/{id} (:918), /runs/{id} (:990) และ POST /run/{tool} (:1806)

มีtoken เดียวสำหรับทุกคน การตั้งค่าบอกเองว่า: "there is one shared API token and no client identity anywhere" (VISOR-serve server/config.py:226-227) เซิร์ฟเวอร์แยกไม่ออกระหว่างสิบเวิร์กสเตชันกับเครื่องเดียวที่คลิกสิบครั้ง และไม่มีอะไรทำให้ token หมดอายุ หมุนเวียน หรือเพิกถอน ไคลเอนต์เก็บมันแบบข้อความธรรมดาในไฟล์ตั้งค่าเนทีฟของ Slicer (qt.QSettings, Remote .../settings_qt.py:63-66)

เส้นทางที่ไม่มี token

GET /health (main.py:422, คืน {"status":"ok"}) และ GET /tools (main.py:551) ตอบโดยไม่ต้องมีข้อมูลรับรอง ตัวหลังคืนสคีมาของทุกเครื่องมือที่ลงทะเบียน: ชื่อ อาร์กิวเมนต์ ชนิด นามสกุล นี่เป็นความตั้งใจ การทดสอบเรียกสองเส้นทางนี้ว่า "deliberately unauthenticated" และตรวจว่า /run ไม่ใช่ (test_security.py:59-63) และ audit ของเซิร์ฟเวอร์เองรายการมันเป็นช่องโหว่ระดับปานกลาง (VISOR-serve SECURITY.md, ตารางของส่วนที่ 2 แถว 6)

token เริ่มต้นและการเปิดเผยต่อเครือข่าย

API_TOKEN ไม่มีค่าเริ่มต้นในการตั้งค่าของเซิร์ฟเวอร์ (server/config.py:27) แต่ไฟล์ compose ให้ไว้: API_TOKEN=${API_TOKEN:-dev-token} (VISOR-serve docker-compose.yml:86,115,208) ไคลเอนต์ส่งค่าเดียวกันมาเป็นค่าเริ่มต้น (Remote .../config.py:21) ข้างที่อยู่เซิร์ฟเวอร์ตัวแทน https://set-your-server.invalid ดังนั้นจะไม่มีอะไรถูกส่งก่อนตั้งค่าเซิร์ฟเวอร์ ตัวช่วยติดตั้งทำได้ดีกว่า: scripts/server_ctl.py up สร้าง secrets.token_urlsafe(32) (:396) เขียนลง .env ด้วยโหมด 0600 (:335) และเก็บไว้ในการรันครั้งต่อไป

พอร์ตที่เผยแพร่ตาม BIND_ADDR: ถ้าไม่ตั้ง จะเผยแพร่บนทุกอินเทอร์เฟซ (docker-compose.yml:35 และคอมเมนต์ที่ :23-27 อธิบายว่านี่ตั้งใจให้เซิร์ฟเวอร์แล็บที่อยู่หลัง TLS terminator); server_ctl.py เขียน BIND_ADDR=127.0.0.1 สำหรับการติดตั้งในเครื่อง (:368,398)

ตรวจแล้วในไฟล์ compose

เมื่อเริ่มด้วย docker compose up โดยไม่มี API_TOKEN ใน environment เซิร์ฟเวอร์รันด้วย token dev-token และเมื่อไม่มี BIND_ADDR มันฟังบนทุกอินเทอร์เฟซ token ที่สร้างและการผูกกับ loopback มาจาก server_ctl.py เท่านั้น

3. การส่งข้อมูล: ไคลเอนต์เข้มงวด เซิร์ฟเวอร์ HTTP ธรรมดา

ไคลเอนต์ require_https ปฏิเสธทุก URL ที่ไม่ใช่ https:// รวมถึง http://localhost (Remote ServerToolsCore/ServerToolsCoreLib/tls.py:68-82) ใบรับรองถูกตรวจกับ bundle ของ certifi ซึ่งระบุชื่ออย่างชัดเจนเพื่อไม่ให้ตัวแปร environment ใดสลับหน่วยงานรับรองได้ (tls.py:84-93); ไม่มี CA กำหนดเอง ไม่มี pinning และไม่เคยมี verify=False (tls.py:15-19) เส้นทาง deploy ที่สร้างบน urllib ก็ปฏิเสธทุก redirect เช่นกัน เพราะ redirect คือวิธีที่ https:// จะกลายเป็น http:// (tls.py:96-103) และ session ของ requests เมานต์ adapter ที่ปฏิเสธ http:// (client.py:607,663) ค่าตั้ง VerifyTls แบบเก่าไม่ถูกอ่านกลับอีกต่อไป ดังนั้นเครื่องที่เคยเก็บค่า False ไว้จะไม่ปิดการตรวจสอบค้างอยู่ (settings_qt.py:51-57)

เซิร์ฟเวอร์ พูด HTTP ธรรมดา: uvicorn.run(app, host="0.0.0.0", port=8000) (VISOR-serve server/main.py:2368) และอิมเมจรัน uvicorn โดยไม่มีตัวเลือกใบรับรองใด (docker/Dockerfile:232) server/README.md:138-155 แสดงใบรับรอง self-signed "for local development only" ที่ส่งให้ uvicorn ด้วยมือ .env.example ระบุผลที่ตามมา: การเปิดพอร์ตนั้น "only acceptable behind a TLS terminator"

ตรวจแล้ว: สองฝั่งพบกันผ่าน terminator เท่านั้น

ไคลเอนต์ปฏิเสธ HTTP ธรรมดา และตาม docstring ของมันเอง ปฏิเสธใบรับรอง self-signed ที่เซิร์ฟเวอร์แสดงบนพอร์ตของตัวเอง "including when it runs on this very machine" (tls.py:21-26) ไคลเอนต์ Slicer จึงคุยกับคอนเทนเนอร์เปล่า ๆ ไม่ได้: ต้องมี terminator ที่ใช้ใบรับรองลงนามสาธารณะอยู่ด้านหน้า ว่ามี terminator อยู่หน้าอินสแตนซ์ใดหรือไม่เป็นข้อเท็จจริงของการติดตั้งใช้งานนั้น ไม่ใช่ของที่เก็บโค้ด

4. ไฟล์และไฟล์เก็บถาวร

extract_zip (VISOR-serve server/file_utils.py:125-174) ตรวจทุกสมาชิกก่อนแตกอะไร: เป้าหมายที่แก้ค่าแล้วต้องอยู่ใต้ราก extract (os.path.commonpath, :159) สมาชิกที่เป็น symbolic link ถูกปฏิเสธ (:163) และหลังจากนั้นเท่านั้น extractall จึงรัน (:172) การทดสอบครอบคลุม zip slip สมาชิกพาธสัมบูรณ์ และ symbolic link (server/tests/test_security.py:211,221,229)

ตัวระบุและชื่อก็ถูกปฏิบัติเป็นอันตรายเช่นกัน id ของการอัปโหลดและผลลัพธ์คือ secrets.token_urlsafe(24) (wire/transfer.py:176); id ที่ผิดรูปแบบไม่เคยสร้างพาธ และชื่ออัปโหลดเช่น ../, ไบต์ NUL หรือ $(whoami) อยู่ในไดเรกทอรีทำงานต่อไป (test_security.py:112,147,176); id ผลลัพธ์ที่ไม่รู้จักไม่เปิดเผยว่ามันเคยมีอยู่หรือไม่ (:273) ขีดจำกัด: MAX_UPLOAD_MB 500 (HTTP 413 เมื่อเกิน), MAX_EXTRACTED_MB 2000, ไดเรกทอรีการถ่ายโอนและการรันหมดอายุหลัง 900 s และรันที่หยุดที่จุดควบคุมคุณภาพเก็บข้อมูลไว้ได้ถึง 4 ชม. (server/config.py:240,241,245,263,271) ไดเรกทอรีชั่วคราวถูกลบแม้เครื่องมือจะยกข้อยกเว้น (file_utils.py:20-81) timeout เริ่มต้นของเครื่องมือเป็นศูนย์ หมายถึงไม่มี (config.py:77)

เพดานที่คอมเมนต์สัญญาไว้แต่โค้ดไม่ได้ใช้

เพดานขนาดหลังคลายการบีบอัดบังคับใช้เฉพาะเมื่อผู้เรียกส่ง max_total_bytes (ค่าเริ่มต้น None, file_utils.py:125-130) อาร์กิวเมนต์โฟลเดอร์ของรันปกติส่ง (main.py:291-296 โดย _MAX_EXTRACTED_BYTES มาจาก MAX_EXTRACTED_MB, :113) ผลรวมคำนวณจาก member.file_size คือขนาดที่ไฟล์เก็บถาวรประกาศ (file_utils.py:167)

เส้นทาง resume ข้ามเพดานการแตกไฟล์

เส้นทาง resume แตกไฟล์เก็บถาวรที่อัปโหลดด้วย file_utils.extract_zip(landed, destination) และไม่มี max_total_bytes (VISOR-serve server/main.py:1594) ขณะที่คอมเมนต์เหนือขึ้นไปสองบรรทัดบอกว่า "refuses zip slip, symlink members and anything over MAX_EXTRACTED_MB before a byte is written" (:1592-1593) บนเส้นทางนั้นใช้เฉพาะการตรวจพาธ เพดาน 2000 MB ไม่ถูกใช้ ไม่ได้ทดสอบว่าขนาดที่ประกาศซึ่งโกหกเรื่องขนาดจริงจะถูกใช้ประโยชน์ได้หรือไม่

ไคลเอนต์ปกป้องตัวเองแบบเดียวกันจากเซิร์ฟเวอร์ที่ประพฤติผิด ก่อนเขียนไบต์ใดของผลลัพธ์ จุดตรวจ หรือไฟล์ทดสอบที่โฮสต์ไว้ มันปฏิเสธไฟล์เก็บถาวรที่เกิน UNZIP_MAX_MEMBERS = 100 000 สมาชิก หรือ UNZIP_MAX_BYTES = 20 GiB (Remote .../config.py:97-98, slicer_io.py:276-282)

5. ประตูบำรุงรักษา

สามารถสั่งเซิร์ฟเวอร์ให้หยุดรับงานใหม่ขณะอัปเดตได้ ตัวอัปเดตรันบนโฮสต์ ไม่ใช่ในคอนเทนเนอร์ ซึ่งมีเพียง server/ ที่เมานต์อยู่ มันจึงเข้าไปผ่าน POST /maintenance (ต้องมี token, VISOR-serve main.py:518-548) body {accepting, seconds, reason}

  • การปิดคือเส้นตาย ไม่ใช่ธง: close() จำกัดไว้ที่ MAX_CLOSE_SECONDS = 300 และประตูเปิดเองเมื่อนาฬิกา monotonic ผ่านเส้นตาย (wire/maintenance.py:38,51-66,80-89) สถานะอยู่ในหน่วยความจำ ดังนั้นการรีสตาร์ตจะเปิดมันอีกครั้ง หากไม่มี seconds เส้นทางขอ 60 s (main.py:540)
  • ขณะปิด require_accepting ตอบ 503 พร้อม Retry-After (maintenance.py:113-146) บนสี่เส้นทางพอดี: POST /uploads (main.py:833), POST /run/{tool} (:1806), POST /runs/{id}/rewind (:1685) และ POST /runs/{id}/resume (:1750) การติดตามรัน การดึงผลลัพธ์ และการยกเลิกยังใช้ได้
  • /status รายงานประตูและไม่พกข้อความความคืบหน้า เพราะข้อความอาจระบุชื่อไฟล์และจึงระบุผู้ป่วย (main.py:455-467)
ขีดจำกัดของประตู

เส้นทางนี้ถูกป้องกันด้วย token ร่วมตัวเดียวกับทุกอย่างอื่น ใครก็ตามที่ถือมันปฏิเสธรันใหม่ได้ครั้งละถึง 300 s และทำอีกได้ทันทีที่หน้าต่างจบ เพดานป้องกันการล็อกถาวร ไม่ใช่การล็อกซ้ำ ข้อนี้เป็นผลจากโค้ด ไม่ได้ลองบนเซิร์ฟเวอร์จริง

6. การลบข้อมูลระบุตัวตน: มีข้อกำหนด ยังไม่ได้สร้าง

Remote DEIDENTIFICATION_SPEC.md (เวอร์ชัน 1.0 กรกฎาคม 2026) กำหนดไปป์ไลน์ฝั่งไคลเอนต์: สามด่าน (ingestion, transformation, verification) ผ่านจุดคอขวดจุดเดียวในไคลเอนต์ ไปป์ไลน์ทีละขั้นสำหรับ DICOM และวอลุ่ม การรั่วไหลเฉพาะของ Slicer (ชื่อโหนด ฐานข้อมูล DICOM ในเครื่อง log ไฟล์ .mrml และ .mrb) โปรไฟล์แบบประกาศต่อเครื่องมือ และ roadmap มันเปิดด้วยการบอกว่าวันนี้ไม่มีการประมวลผลลบข้อมูลระบุตัวตน และคอมเมนต์ของเซิร์ฟเวอร์ที่อ้างเป็นอย่างอื่น "describes an intention, not a reality" หลักการของมันคือ fail-closed จุดคอขวดจุดเดียว และหลักฐานหนึ่งชิ้นต่อการอัปโหลด และไม่เคยเป็นช่องติ๊กที่บอกว่า "I anonymised"

ไม่มีอะไรของมันที่ทำแล้ว README ของไคลเอนต์บอกไว้ตรง ๆ: "There is no de-identification in the current client. Files are streamed to the server as they are on disk, with their names, their DICOM headers and whatever identifiers they contain" (Remote README.md:30-35) การค้นหาใน Remote, VISOR-serve และ SADT-VISOR หาไลบรารีลบข้อมูลระบุตัวตน (dicognito, pydicom) และโค้ดทำให้ไม่ระบุตัวตน ไม่พบนอกข้อกำหนด ประกาศการอัปโหลด และโมดูลข้อความด้านล่าง; pydicom ปรากฏเป็นเพียง version pin ใน MRI2CBCTRemote ซึ่งเป็นโมดูลที่ไม่ได้ build เซิร์ฟเวอร์ก็ไม่มี gate เช่นกัน: ร่องรอยเดียวคือ header ของ main.py ซึ่งระบุว่าการลบข้อมูลระบุตัวตน "happens on the client side before upload" (main.py:4-5)

ไคลเอนต์เตือนผู้ใช้ หนึ่งครั้งต่อโฮสต์

เมื่อผู้ใช้บันทึกเซิร์ฟเวอร์ที่ไม่ใช่เครื่องในเครื่อง ไคลเอนต์แสดงกล่องโต้ตอบที่เริ่มด้วย "Files are uploaded unmodified. This client does not de-identify anything" (Remote .../settings_qt.py:101-132 เรียกจาก ServerToolsSettings.py:145 และ SlicerCloud.py:1059) ข้ามสำหรับ loopback และติดตามต่อโฮสต์ (settings_qt.py:73-88) คอมเมนต์ header ของ main.py:4-5 จึงเป็นเท็จสำหรับไคลเอนต์ปัจจุบัน; ข้อกำหนดและ SECURITY.md:130 ต่างก็บอกเช่นนั้น

อย่าสับสน: Medical Data Anonymizer

ส่วนขยาย Remote มี Medical_Data_Anonymizer_ModuleRemote (768 บรรทัด) มันทำให้เอกสารข้อความ (DOCX, PDF, TXT, CSV, XML, ODT) ไม่ระบุตัวตนด้วย Presidio บนเครื่องในเครื่อง และไม่ส่งอะไรออกไป (Remote README.md:24-30) มันไม่ใช่ไปป์ไลน์ของข้อกำหนด มันไม่แตะไฟล์ DICOM หรือวอลุ่ม และไม่ได้วางไว้ในเส้นทางอัปโหลดของเครื่องมืออื่นใด โมดูล legacy อธิบายอยู่ในหน้าของมันเอง โมดูล Remote ในหน้า VISOR ของมัน; ข้อแตกต่างเดียวกันนี้ใช้กับทั้งสอง

7. Attestation และการแลกเปลี่ยนกุญแจ: ไม่อยู่ใน VISOR

ไม่มีในสามที่เก็บโค้ดของ VISOR

VISOR-serve, AutomatedDentalToolsRemote และ SADT-VISOR ไม่มี attestation ไม่มีการแลกเปลี่ยนกุญแจ และไม่มีการเข้ารหัสไฟล์ระดับแอปพลิเคชัน การค้นหา attestation, TEE, nonce, ECDH, X25519, HPKE, enclave และ key exchange ในนั้น และในต้นไม้ legacy/ สองต้น พบเพียงผลที่ไม่เกี่ยวข้อง (คำสั่งเชลล์ tee คำแนะนำให้เลือก ECDHE ในการตั้งค่า TLS และ "Confidentiality Profile" ของ DICOM) การป้องกันข้อมูลขณะส่งคือ TLS อย่างเดียว ส่วนที่ 3

โปรโตคอลมีอยู่ในต้นแบบวิจัยแยกต่างหาก volume_crypto (บรานช์ crypto/two-machine-chain คอมมิต d975dab) ซึ่งเป็นที่เก็บโค้ดของตัวเองที่ในโค้ดไม่อ้างถึง VISOR-serve หรือส่วนขยาย Remote มันไม่ได้ติดตั้งใช้งานที่ใดที่แอตลาสนี้รู้จักและไม่ได้เชื่อมกับเซิร์ฟเวอร์ VISOR สิ่งต่อไปนี้อธิบายสิ่งที่ต้นแบบนั้นทำ ไม่เกินนั้น

โค้ดทำอะไร

  • Measurement measure_code คือ SHA-256 แบบสะสมบนไฟล์ (ชื่อและเนื้อหา) ซึ่งเอกสารระบุว่าเป็นของจริง ไม่ใช่จำลอง (voltcrypt/attestation.py:66-82) ชุดที่วัดคือ manifest: โมดูลโปรโตคอล โมดูลที่จัดการข้อมูลธรรมดา runner และ policy ที่ประกาศ (cryptoserve/measure.py:41-53,123-142) ดังนั้นการเปลี่ยนหนึ่งบรรทัดของไฟล์ใดก็ตามจะเปลี่ยน digest และไคลเอนต์จะปฏิเสธไม่ปล่อยกุญแจ
  • หลักฐาน record ที่มีเวอร์ชัน ชนิด measurement กุญแจสาธารณะชั่วคราว nonce ของไคลเอนต์ report_data = SHA-512(public key || nonce) policy และวันที่ ลงนามด้วย Ed25519 (attestation.py:98-134)
  • ลำดับการตรวจสอบ (attestation.py:162-206): ลายเซ็นก่อน แล้วเวอร์ชัน แล้ว nonce (ไม่มี replay) แล้วความเชื่อมโยงระหว่าง report_data กับกุญแจสาธารณะที่แสดง (ไม่มี relay ของหลักฐานจากเซิร์ฟเวอร์อื่น) แล้ว measurement และ policy (debug ปิด swap ปิด)
  • การปล่อยกุญแจ ไคลเอนต์สร้างคู่กุญแจ X25519 ชั่วคราวของตัวเอง derive กุญแจห่อด้วย HKDF-SHA256 (info = ป้ายเวอร์ชัน กุญแจชั่วคราว และกุญแจของผู้รับ) และปิดผนึกกุญแจวอลุ่มด้วย AES-256-GCM โดยมี job id และ nonce เป็น authenticated data (voltcrypt/keyexchange.py:65-117) docstring เรียกมันว่าสิ่งเทียบเท่าแบบง่ายของ HPKE (RFC 9180): มันไม่ใช่ HPKE มาตรฐาน
  • ข้อมูลธรรมดา กุญแจส่วนตัว X25519 ของเซิร์ฟเวอร์ถูกสร้างตอนเริ่มระบบและไม่เคยถูกเขียนลงที่ใด (cryptoserve/enclave.py) ข้อความธรรมดาถูกจำกัดอยู่ในฟังก์ชันเดียวใน cryptoserve/boundary.py โดยมีการทดสอบการนำเข้าเฝ้าอยู่
  • เครื่องมือจริง runner เปิด <tool>/.venv/bin/python <runner> --job job.json ซึ่งเป็นสัญญาเดียวกับ VISOR-serve (cryptoserve/runners/subprocess_tool.py)

trust root ของมันเป็นของจำลอง

ประกาศโดยต้นแบบเอง

header ของ voltcrypt/attestation.py:3-24 เป็นคำเตือนในกรอบ "simulated trust root": กุญแจลงนามเป็นกุญแจ Ed25519 ซอฟต์แวร์บนดิสก์ของเซิร์ฟเวอร์ ซึ่งผู้ดูแลเซิร์ฟเวอร์อ่านได้เพื่อปลอม attestation เท็จ cryptoserve/enclave.py:32-43 ประกาศ "tee": "SIMULATED, aucune protection materielle" และ "gpu_confidential": False และ debug: False กับ swap: False เป็นค่าคงที่ที่เซิร์ฟเวอร์เลือก ไม่ได้อ่านจากฮาร์ดแวร์ ต้นแบบป้องกันเซิร์ฟเวอร์ที่ถูกแก้ไขโดยความผิดพลาด (เวอร์ชันผิด ไฟล์เสียหาย เครื่องผิด) ไม่ได้ป้องกันเซิร์ฟเวอร์ที่เจตนาร้าย hardware root (HardwareRoot ใน cryptoserve/roots.py) ยก NotImplementedError: ไม่มีอุปกรณ์ AMD SEV-SNP, Intel TDX หรือ NVIDIA confidential-computing ถูกใช้ ปรากฏเฉพาะในคอมเมนต์

ขีดจำกัดอื่นที่ประกาศไว้: การส่งข้อมูลเป็น HTTP ธรรมดาโดยไม่มี TLS และไม่มีการยืนยันตัวตนของไคลเอนต์ (PIPELINE.md, "Limites"); การล้างหน่วยความจำไม่รับประกันใน Python; โหมด --trust-on-first-use ยอมรับ measurement ใดก็ตามที่เซิร์ฟเวอร์ประกาศ ซึ่ง runbook ห้ามสำหรับ measurement จริง; ผลลัพธ์ถูกเข้ารหัสใหม่ด้วยกุญแจวอลุ่ม ซึ่งเป็นการทำให้ง่ายขึ้น

การทดสอบและหลักฐาน ชุดทดสอบถูกรันสำหรับหน้านี้: ผ่าน 155 ข้าม 3 (ต้องใช้ GPU และเครื่องมือที่ serve) 26 subtest ใน 15.7 s ซึ่งรวมการทดสอบการปฏิเสธ (nonce ที่เล่นซ้ำ ลายเซ็นปลอม relay attack กุญแจไม่เคยอยู่ในรูปข้อความธรรมดาในแพ็กเก็ต กุญแจผูกกับงาน เซิร์ฟเวอร์ที่ถูกแก้ไขถูกปฏิเสธ) และ state machine ของโปรโตคอล README ของที่เก็บโค้ดเองยังบอก 158 การทดสอบ บันทึกแบบ end-to-end ที่คอมมิตที่ d975dab (evidence/endtoend.json) รัน BatchDentalSeg หลัง gate บนสแกน 138.9 MB: 78.9 s จากฝั่งไคลเอนต์ โดย 78.3 s นั้นข้อมูลธรรมดาค้างอยู่ในหน่วยความจำขณะเครื่องมือรัน; ต้นไม้ทำงานมีการรันซ้ำที่ไม่ได้คอมมิตบนสแกน 98.6 MB (61.4 s) การรันฝ่ายตรงข้ามที่บันทึกใน evidence/adversary_twomachine.json มุ่งไปที่ที่อยู่ของเครื่องที่โฮสต์ VISOR ด้วย ดังนั้น "สองเครื่องจริง" จึงยังไม่ได้รับการยืนยัน

8. สิ่งที่ขาด

  • ไม่มีตัวตนต่อผู้ใช้ token ร่วมหนึ่งตัว (ส่วนที่ 2) ไคลเอนต์ยังเรียก GET /clients/me เพื่อถามว่าเซิร์ฟเวอร์จะรัน batch ของ cohort อย่างไร (Remote .../client.py:809 ใน batch_policy) และเส้นทางนั้นไม่มีอยู่ใน VISOR-serve: ไม่มีเส้นทาง /clients ที่กำหนดใต้ server/ ไคลเอนต์ถือคำตอบที่ไม่สำเร็จทุกแบบว่า "no policy" และคง concurrency ของตัวเอง (client.py:799-818) จึงไม่มีอะไรพัง แต่ตัวตนต่อเวิร์กสเตชันที่เส้นทางนี้ชวนให้คิดว่ามีนั้นไม่มีอยู่
  • ไม่มี audit trail ไม่มีโมดูลบันทึกว่าใครรันอะไร; log ถูกทำให้จืดโดยเจตนา header ของ main.py อ้างว่าเซิร์ฟเวอร์ไม่เคยบันทึกเนื้อหา ค่าอาร์กิวเมนต์ หรือเมทาดาทาของผู้ป่วย (:5-6); ข้ออ้างนั้นไม่ได้ตรวจกับทุกการเรียก logger
  • ไม่มีการเข้ารหัสขณะจัดเก็บ ไฟล์ชั่วคราวอยู่เป็นข้อความธรรมดาใน TEMP_DIR จนกว่าคำขอจะถูกให้บริการ; รันที่หยุดที่จุดควบคุมคุณภาพถือมันไว้ได้ถึง 4 ชม.
  • ไม่มีการจำกัดอัตราหรือการล็อก สำหรับการลอง token
  • ไม่มีการลบข้อมูลระบุตัวตน (ส่วนที่ 6) และไม่มี TLS ในเซิร์ฟเวอร์ (ส่วนที่ 3)
  • ไม่ได้ทบทวน: การรันซับโปรเซสของเครื่องมือ (server/execution/) และ environment ที่มันสืบทอด ซึ่งอาจเป็นพื้นผิวความปลอดภัยของตัวเอง

VISOR-serve SECURITY.md (522 บรรทัด, "Version 1.0, July 2026") มีชื่อว่า "Security and HIPAA compliance report" มันเป็นการตรวจสอบและชุดข้อเสนอแนะ ไม่ใช่คำอธิบายของการทำงานจริง: มันมุ่งไปที่ OIDC และ JWT, envelope encryption ขณะจัดเก็บ, key vault, audit trail, การจำกัดอัตรา, mTLS และ roadmap เป็นเฟส มันบอกเกี่ยวกับเซิร์ฟเวอร์ที่ตรวจสอบว่า "non conforme HIPAA en l'état" (SECURITY.md:11) ด้วยเหตุผลเชิงโครงสร้างสี่ข้อที่ยังจริงในโค้ด: token สถิตร่วม ไม่มี audit trail ถาวร การลบข้อมูลระบุตัวตนที่สมมติแต่ไม่ได้ตรวจ และไฟล์ชั่วคราวเป็นข้อความธรรมดา ตารางช่องโหว่สิบสองข้อของมัน (:67-84) เป็นส่วนที่บอกสถานะของระบบ; ทุกอย่างที่มันเขียนเป็นเป้าหมาย ("il faut", "recommandé") คือมีเพียงข้อกำหนดหรือข้อเสนอแนะ รายงานเขียนเป็นภาษาฝรั่งเศส มีแท็กอ้างอิงตกค้าง (cite index=, บรรทัด 48-52) และอ้าง "autumn 2026 Unified Agenda" ในเอกสารลงวันที่กรกฎาคม 2026 ให้ถือว่ามันเป็นรายการอ่านของสิ่งที่ขาด ไม่ใช่คำรับรองความสอดคล้อง

สมมติฐานเบื้องหลังการออกแบบ

ข้อโต้แย้งหลักของรายงานคือ ข้อมูลที่ลบข้อมูลระบุตัวตนจริงบนไคลเอนต์จะทำให้เซิร์ฟเวอร์พ้นขอบเขตของ HIPAA ซึ่งต้องมีการลบข้อมูลระบุตัวตนที่พิสูจน์ได้ ซึ่งส่วนที่ 6 แสดงว่ายังไม่มี จนกว่าจะมี ต้องปฏิบัติต่อเซิร์ฟเวอร์ในฐานะเซิร์ฟเวอร์ที่รับตัวระบุของผู้ป่วย ผ่าน token ที่ผู้ใช้ทุกคนใช้ร่วมกัน
