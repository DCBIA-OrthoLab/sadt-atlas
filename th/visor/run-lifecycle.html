การรันทีละขั้น

สิ่งที่เกิดขึ้นระหว่างการคลิกใน Slicer จนถึงไฟล์ที่ส่งกลับมา: เส้นทางที่เซิร์ฟเวอร์เปิดให้ใช้ สิบห้าขั้นที่ POST /run/{tool} หนึ่งครั้งผ่าน เฟสที่ผู้เฝ้าดูเห็น วิธีที่รันถูกรับเข้า แยกตัว ยกเลิก หยุดชั่วคราว และย้อนกลับ และ HTTP status ที่แต่ละความล้มเหลวจบลง ทุกข้ออ้างอ้างบรรทัดที่อ่านมา

VISOR-serve e9a7e5d ทำแล้ว มีฟังก์ชันทดสอบ 857 ตัวใน server/tests อ่านเมื่อ 2026-11-09 สถาปัตยกรรม การติดตั้งใช้งาน ความปลอดภัย
หมายเหตุ

หน้านี้อธิบายVISOR รุ่นเซิร์ฟเวอร์ ไม่ใช่โค้ด Slicer แบบ legacy ที่ส่วนที่เหลือของเว็บไซต์นี้บันทึกไว้ การอ้างอิงเป็น file:line ตามด้วยที่เก็บโค้ด: VISOR-serve ที่คอมมิต e9a7e5d (บรรทัดของ server/main.py เว้นแต่ระบุพาธ), AutomatedDentalToolsRemote (ไคลเอนต์ Slicer) ที่ 19b95e8, SADT-VISOR (เครื่องมือ) ที่ 6ba2a78 ที่เก็บโค้ดมีเอกสารของตัวเอง และหลายหน้าของมันเก่ากว่าโค้ด เมื่อสองอย่างขัดกัน หน้านี้ยึดตามโค้ดและบอกไว้ใน callout สิ่งที่ปกป้องการส่งข้อมูลและข้อมูลที่เก็บไว้อยู่ในหน้าความปลอดภัย; ส่วนประกอบเข้ากันอย่างไรอยู่ในหน้าสถาปัตยกรรม

2. เส้นทางปกติ ตั้งแต่ส่งจนถึงล้างข้อมูล

หนึ่งรันบนเส้นทางแบบบล็อก (ไคลเอนต์เปิดคำขอ HTTP หนึ่งคำขอค้างไว้ตลอดการรัน) ตัวแปร detached อยู่ในส่วนที่ 4 สามคอลัมน์ของแผนภาพคือสามโปรเซสที่ต่างกัน: โมดูล Slicer โปรเซส FastAPI และอินเทอร์พรีเตอร์ Python แยกต่างหากที่เป็นของเครื่องมือ

  1. อัปโหลดเป็นส่วน ๆ ไคลเอนต์ส่งอินพุตขนาดใหญ่ผ่าน POST /uploads และ PUT /uploads/{id}/parts/{n}: ส่วนละ 8 MB โดยค่าเริ่มต้น เซิร์ฟเวอร์บีบให้อยู่ระหว่าง 1–64 MB (wire/transfer.py:204-215) สี่การเชื่อมต่อพร้อมกัน SHA-256 ของแต่ละส่วนใน X-Part-SHA256 ลองได้สูงสุดสี่ครั้งต่อส่วน (AutomatedDentalToolsRemote ServerToolsCoreLib/transfer.py:62-67, 309) บนเส้นทางแบบบล็อก ไฟล์ที่เล็กกว่าสองส่วน คือ 16 MB จะไปแบบ inline ในฟอร์มแทน; บนเส้นทาง detached ซึ่งเป็นค่าเริ่มต้นของไคลเอนต์ ทุกไฟล์ผ่าน /uploads (ไคลเอนต์ client.py:1106-1121) บนเซิร์ฟเวอร์ เซสชันอยู่บนดิสก์ blob ถูกจองขนาดไว้ล่วงหน้าด้วย os.truncate และแต่ละส่วนถูกเขียนที่ offset ของมันด้วย os.pwrite: ไม่มีการประกอบใหม่ และตอนรัน blob ถูกเปลี่ยนชื่อเข้าไปในไดเรกทอรีทำงานแทนการคัดลอก (claim_upload, wire/transfer.py:279)
  2. รันถูกลงทะเบียนก่อนอ่านฟอร์ม run_tool (main.py:1806) รับ X-Run-Id และเปิดไดเรกทอรีของรันก่อน เพราะไคลเอนต์เปิดสตรีมอีเวนต์จากเธรดอื่นและทั้งสองจัดลำดับกันไม่ได้ id ผิดรูปแบบคือ 400 id ที่ถูกใช้แล้วคือ 409 (wire/runs.py:178-213)
  3. เครื่องมือและโหมด _run_tool (main.py:1833) หาเครื่องมือ (404 หากไม่รู้จัก) อ่านฟอร์ม แกะ __uploads__ หากเครื่องมือเป็นfacade (ALI, AREG) มันลบฟิลด์ mode แทนที่ facade ด้วยเป้าหมาย และทิ้งอาร์กิวเมนต์ใดที่เป้าหมายไม่ได้ประกาศ; โหมดที่ขาดหรือไม่รู้จักคือ 422 (main.py:1888-1917)
  4. Staging อินพุตแต่ละตัวถูกเขียนไปที่ TEMP_DIR/<mkdtemp>/<argument>/<safe name>.<ext> ชื่อไฟล์ของผู้ป่วยถูกเก็บไว้ โดยกรองให้เหลือ [A-Za-z0-9_.-] (_safe_stem, main.py:1105) และเฟสคือ staging พร้อมข้อความ “input k of n” ไม่เคยเป็นชื่อไฟล์ สิ่งที่ถูกปฏิเสธที่นี่: อาร์กิวเมนต์ที่ไม่รู้จัก (422) ไฟล์ที่ส่งให้อาร์กิวเมนต์สเกลาร์ (400) นามสกุลต้องห้าม (400) ขนาดเกินขีดจำกัด (413) ไฟล์ว่างหรือ .gz ที่ถูกตัดทอน (400, _reject_a_truncated_gzip, :1172) .zip ที่ให้กับอาร์กิวเมนต์ path ถูกแตกโดยเซิร์ฟเวอร์ โดยปฏิเสธ zip-slip สมาชิกที่เป็นพาธสัมบูรณ์ และ symbolic link และมีเพดาน 2000 MB สำหรับขนาดที่แตกออกมา (file_utils.py:125, config.py:241)
  5. ไฟล์ที่โฮสต์ไว้ โมเดลหรือไฟล์ทดสอบที่เลือกด้วยชื่อถูกหาผ่าน data store (404 หากไม่มี) DATA_DIR เป็นแบบอ่านอย่างเดียว ดังนั้นไฟล์เก็บถาวรของอาร์กิวเมนต์โฟลเดอร์จึงถูกแตกเข้าไปในไดเรกทอรีทำงาน
  6. การตรวจสอบ นอก event loop tool.invoke รันในเธรดของ worker ภายใต้ CapacityLimiter ของ MAX_CONCURRENT_TOOLS (4; main.py:183-187, :2081-2083) SchemaTool.invoke ตรวจสอบกับสคีมาที่เผยแพร่ (422 เมื่อเป็น ToolArgumentError) แปลงฟิลด์ multichoice เป็นลิสต์ และเรียก dispatch.dispatch
  7. Dispatch dispatch (execution/dispatch.py:1080) ตรวจว่าเครื่องมือมีอินเทอร์พรีเตอร์ สร้าง TEMP_DIR/job_<uuid>/{input,output} เติมพารามิเตอร์ให้ครบ (output_dir เป็นของงานเองเสมอ device ถูกฉีดจากการตั้งค่า อาร์กิวเมนต์โมเดลที่ไม่มีชื่อได้รับโฟลเดอร์โมเดลของเครื่องมือ) เขียน job.json และคำนวณ timeout: deployment_config.timeout_seconds(tool.name) or None (dispatch.py:1137)
  8. การรับเข้า รันขอพื้นที่ในงบประมาณของไบต์และคอร์ (ส่วนที่ 5) หากต้องรอ เฟสจะกลายเป็น queued_gpu หนึ่งครั้ง; ไคลเอนต์ยังยกเลิกได้
  9. เครื่องมือเริ่มทำงาน Popen([venv/python, runner.py, --job job.json]) โดย stdout และ stderr ไปยังไฟล์ cwd คือไดเรกทอรีของงาน และ start_new_session=True (dispatch.py:618) environment เป็นของเซิร์ฟเวอร์ ไม่มี API_TOKEN พร้อมเพดานจำนวนเธรด (OMP_NUM_THREADS, MKL_, OPENBLAS_, NUMEXPR_, VECLIB_, ITK_GLOBAL_DEFAULT_NUMBER_OF_THREADS) และตัวแปร SADT_API, SADT_JOB_ID, SADT_JOB_DIR, SADT_PROGRESS_FILE และ SADT_SUPERVISOR_DEADLINE (_child_environment, dispatch.py:540) process-group id ถูกเขียนลงดิสก์; เฟสคือ running
  10. Runner runner.py ถูกเรียกใช้โดยอินเทอร์พรีเตอร์ของเครื่องมือเอง ใช้เฉพาะไลบรารีมาตรฐาน (Python 3.9 ถึง 3.13) นำเข้าแพ็กเกจเดียวใต้ src/ ของเครื่องมือ แปลงอาร์กิวเมนต์ตาม annotation เรียก run() สุ่มวัด VRAM สูงสุด RSS และคอร์ด้วย _TreeSampler (runner.py:405) และเขียน result.json แบบอะตอมมิก: {"result", "peak_vram_bytes", "peak_rss_bytes", "peak_cpu_cores", "channels", "vram_source"} หรือ {"error": {"type", "message"}}
  11. อ่านผลลัพธ์ หากไม่มี result.json หลังโค้ดออก 0 จะเป็น ToolExecutionError; error กลายเป็น ToolFailure(type, message) ค่าที่วัดได้ป้อนเข้าตารางต้นทุนและอีเวนต์ที่มี measured
  12. การแพ็กเกจ _finish_run (main.py:2200) ตั้งเฟสเป็น packaging เอาต์พุตที่เป็น files กลายเป็น zip ชื่อ {tool}_{stem}.zip ที่ระดับการบีบอัด 1 โดยสมาชิกที่ถูกบีบอัดอยู่แล้ว (.gz, .zip, .xlsx และทำนองเดียวกัน) ถูกเก็บแบบ stored (file_utils.py:199-251, config.py:252) เอาต์พุต text ตอบเป็น {"result": ...}
  13. การส่งมอบ มีสองวิธี โดยค่าเริ่มต้นไฟล์ถูกสตรีมด้วย FileResponse และถูกลบใน background task หลัง การตอบ หากไคลเอนต์ส่ง X-Result-Delivery: reference และ ไฟล์มีขนาดอย่างน้อย RESULT_REFERENCE_MIN_MB (16; config.py:249) ไฟล์จะถูกย้าย (เปลี่ยนชื่อ) เข้า result store และคำตอบคือ {"result_ref": {result_id, filename, media_type, size}} (wire/transfer.py:325-349); จากนั้นไคลเอนต์ดึง GET /results/{id} ด้วย Range สี่การเชื่อมต่อ ตรวจ CRC ของสมาชิก zip ทุกตัว และปิดท้ายด้วย DELETE /results/{id} (ไคลเอนต์ client.py:1696-1773)
  14. บันทึกการรัน _tracked_run (main.py:1610) เขียน done และกำหนด runs.discard เป็น background task เพื่อให้ไดเรกทอรีอยู่นานกว่าจุดจบของสตรีม
  15. การล้างข้อมูล อินพุตที่ stage ไว้ไปอยู่ใน finally ของ _run_tool; ไดเรกทอรีทำงานและเอาต์พุตอยู่ใน background task หลังสตรีม; ข้อผิดพลาดใดก็ตามทิ้งทันที ผลลัพธ์และการอัปโหลดที่ไม่เสร็จถูกกวาดโดย reaper ทุก 60 s เมื่อว่างครบ 900 s (config.py:245-246, _reaper_loop main.py:63-81) log ของเซิร์ฟเวอร์บันทึก endpoint เครื่องมือ สถานะ ระยะเวลา และขนาด และไม่เคยบันทึกเนื้อหาไฟล์ ค่าอาร์กิวเมนต์ หรือข้อความความคืบหน้า (_log_served, main.py:351-371)

3. เฟส สถานะ และสตรีมอีเวนต์

รันมีเฟส (สิ่งที่มันกำลังทำ) และสถานะ (สิ่งที่ผู้เฝ้าดูควรสรุป) เฟสคือ received, staging, queued_gpu, running, packaging, done, failed, cancelled, paused (wire/runs.py:73-81) สถานะคือ pending (received, staging, queued_gpu), running (running, packaging), done, failed, cancelled (สามตัวสุดท้ายเป็นสถานะสิ้นสุด) และ paused ซึ่งไม่ใช่สถานะสิ้นสุด (:83-93)

GET /runs/{id}/events เป็นสตรีม Server-Sent Events เริ่มที่อีเวนต์แรก รวมถึงอีเวนต์ที่เขียนก่อนผู้เฝ้าดูเชื่อมต่อ เพราะผู้เฝ้าดูถูกเปิดจากเธรดที่สองและจัดลำดับเทียบกับ POST ไม่ได้ (main.py:1004-1048) ไฟล์ถูก poll ทุก 0.25 s จากเธรดของ worker (RUN_EVENT_POLL_SECONDS, config.py:275) และแต่ละเฟรมคือ data: {json} สตรีมจบที่อีเวนต์สิ้นสุด หรือเมื่อไดเรกทอรีของรันหายไป

อีเวนต์คือ {seq, at, state, phase, fraction, message, depth} บวก tool (ชื่อของการเรียกซ้อน, [A-Za-z0-9_-]{1,64}), result (เขียนโดยเซิร์ฟเวอร์เท่านั้น) และ measured (vram_bytes, ram_bytes, cpu_cores, channels) (_normalised, wire/runs.py:473-539) seq คือหมายเลขบรรทัดตอนอ่านและไม่เคยถูกเก็บ message ถูกตัดที่ 200 ตัวอักษรโดยไม่มีการขึ้นบรรทัด บรรทัดที่เครื่องมือเขียนถูกอ่านเป็น running เสมอ: มีเพียงเซิร์ฟเวอร์ที่ประกาศ done, failed หรือ cancelled ได้

บนดิสก์ TEMP_DIR/runs/<run_id>/ เก็บ events.jsonl, meta.json, pgid, cancel และเมื่อหยุดจะมี paused.json การต่อท้ายไม่ใช้ล็อก: แต่ละ record เป็น write() ครั้งเดียวภายใต้ MAX_RECORD_BYTES (4096) เป็นอะตอมมิกด้วย O_APPEND บน POSIX (wire/runs.py:137) สตรีมถูกจำกัดที่ MAX_RUN_EVENTS = 2000 อีเวนต์; เกินเพดานแล้วจะส่งอีเวนต์ “not reported” หนึ่งตัวและไม่มีอะไรอีก โดยอีเวนต์สิ้นสุดไม่เคยถูกตัด (_capped, wire/runs.py:611-635)

ความคืบหน้าจากเครื่องมือ เครื่องมือรายงานความคืบหน้าด้วยการต่อท้าย {"fraction": ..., "message": ...} ลงในไฟล์ที่ระบุโดย SADT_PROGRESS_FILE; sup.progress(fraction, message) เขียนลงไฟล์เดียวกัน (runner._append_progress, runner.py:1058) fraction เป็นตัวเลขระหว่าง 0 ถึง 1 หรือไม่มี และไคลเอนต์ไม่คิดค่าขึ้นเอง

ข้อควรระวัง

หลังความล้มเหลว ไดเรกทอรีของรันถูกลบทันที: _tracked_run เขียน failed และเรียก runs.discard ในจังหวะเดียวกัน (main.py:1636-1642) ผู้เฝ้าดูที่ยังไม่ได้อ่านอีเวนต์สิ้นสุดจะพบว่าไดเรกทอรีหายไป และสตรีมของมันก็แค่จบลง: EventReader.read ตั้ง finished บนไฟล์ที่หายไปและไม่คืนอะไร (wire/runs.py:567-578) ความล้มเหลวเองยังถูกรายงานโดย POST หลังสำเร็จ ไดเรกทอรีอยู่ต่อหลังการตอบจบ

4. โหมด Detached

เมื่อใช้ X-Run-Delivery: detached เซิร์ฟเวอร์ตอบ 202 ทันทีที่อินพุตถูก stage แล้ว และรันดำเนินต่อเป็น background task; อีเวนต์สิ้นสุดของมันพก result_ref (_detach main.py:1401, _detached_run :1354) ต้องมี X-Run-Id (มิฉะนั้น 400) และปฏิเสธไฟล์ใด ๆ ใน body (400): ทุกอินพุตต้องมาถึงผ่าน /uploads ไดเรกทอรีของรันไม่ถูกลบเมื่อจบ เพราะไคลเอนต์ยังไม่ได้อ่านอีเวนต์สิ้นสุด; มันหมดอายุหลัง RUN_TTL_SECONDS = 900 s ของความไม่เคลื่อนไหว โดยรีเฟรชทุกครั้งที่อ่าน (config.py:263)

เหตุผลคือ timeout คอมเมนต์เหนือ header บอกไว้ชัดเจน: read timeout ของ POST ฝั่งไคลเอนต์ Slicer คือ 600 s โดยมีเพดานหนึ่งชั่วโมง เซิร์ฟเวอร์ถูกขนาดมาสำหรับ cohort ที่ใช้เวลานานกว่านั้น และการตัดการเชื่อมต่อไม่เคยหยุดรัน มันแค่ทิ้งคำตอบ (main.py:157-160) ในโหมด detached ไคลเอนต์ไม่ถือคำขอที่ยาว: มันรอบนสตรีมอีเวนต์ ซึ่งเชื่อมต่อใหม่และกำจัดซ้ำด้วย seq ไคลเอนต์เปิดโหมดนี้เป็นค่าเริ่มต้น (DETACHED_RUNS = True, config.py:90 ของส่วนขยาย Remote) และถอยกลับไปเส้นทางแบบบล็อกเมื่อขอ stop_after เพราะ record ของจุดตรวจถูกส่งใน body ของ POST เท่านั้น (client.py:1094-1106)

ข้อบกพร่องที่ยืนยันในโค้ด

main.py:2332 ยก ToolExecutionError ซึ่งเป็นชื่อที่ main.py ไม่เคยนำเข้า: โมดูลนำเข้า dispatch และใช้ dispatch.ToolFailure กับ dispatch.RunCancelled ผ่านแอตทริบิวต์ (ที่เดียวที่ชื่อเปล่า ๆ ปรากฏในไฟล์คือ raise นั้น) กิ่งนี้คือ “detached run, and storing the result by reference failed with OSError” มันยก NameError แทนข้อความที่ตั้งใจ ดังนั้นรายงานความล้มเหลวจะผิด กิ่งนี้เกิดยาก และไม่ได้รันการทดสอบกับมันสำหรับหน้านี้

5. การรับเข้า: งบประมาณ ไม่ใช่ตัวนับ

รันไม่ได้ใช้ช่อง แต่จองพื้นที่ โค้ดการรับเข้าใน execution/admission.py เก็บ Budget (:239) ของไบต์ RAM ไบต์ VRAM และคอร์ กับคิวของรันที่รอพื้นที่ในนั้น

  • FIFO ต่อหนึ่งโปรเซส ตั๋วถูกเรียกตามลำดับ มีเพียงรันที่อยู่หัวคิวที่รับเข้าได้ โมดูลระบุข้อแลกเปลี่ยนไว้: head-of-line blocking แลกกับลำดับที่คาดเดาได้ (admission.py:239-251) reserve(candidates) ลองรูปทรงที่กว้างลดหลั่นลงไปและเลือกอันแรกที่พอดี (:446-530)
  • กฎความปลอดภัยสามข้อ เครื่องมือที่ไม่เคยวัดต้นทุนจะจองทั้งหมดของงบประมาณและรันตัวเดียว คำขอที่ใหญ่กว่างบประมาณยังรันได้ ตัวเดียว เมื่อเครื่องว่าง หน่วยความจำที่ว่างจริงบนการ์ดก็ถูกตรวจด้วย (admission.py:22-33) ใช้ส่วนเผื่อความปลอดภัย 1.3 (SAFETY_MARGIN, :49)
  • งบประมาณมาจากไหน resources.py อ่าน cgroup (v2 แล้วจึง v1) ก่อนเคอร์เนล และ nvidia-smi สำหรับ VRAM ที่ว่าง สัดส่วนคือ SADT_RESOURCE_SHARE = 0.75 (config.py:219); งบประมาณถูกแบ่งเป็นส่วนแบ่งต่องานโดย SADT_EXPECTED_CLIENTS = 4 (config.py:234); SADT_CPU_BUDGET, SADT_RAM_BUDGET, SADT_VRAM_BUDGET และรูปแบบ *_PER_JOB ใช้แทนค่าเหล่านั้นและรับค่าเช่น 75%, 8 หรือ 16GB (config.py:213-237) Expected clients เป็นการประกาศ: มี token ร่วมหนึ่งตัวและไม่มีตัวตนของไคลเอนต์ เซิร์ฟเวอร์จึงนับเวิร์กสเตชันไม่ได้
  • ขั้นต่ำของคอร์ SADT_MIN_CPUS_PER_JOB = 4 (config.py:161): ต่ำกว่านั้นรันจะรอแทนที่จะถูกรับเข้าทั้งที่ขาดแคลน
  • GPU หรือไม่ รันถูกสมมติว่าต้องการการ์ด เว้นแต่จะประกาศ device ที่แก้ค่าเป็น cpu หรือ mps (dispatch.uses_the_gpu, :95)
  • ต้นทุนที่เรียนรู้ execution/costs.py เก็บค่าสูงสุดของ COST_WINDOW = 20 รันล่าสุดของแต่ละเครื่องมือ ต่อทรัพยากร และฟิตเส้นตรง คงที่ + ส่วนเพิ่ม × ความกว้าง ทันทีที่เห็นความกว้างต่างกันสองค่า (_fit :429, _predict :404) “Measured at 0” กับ “never measured” เป็นคนละอย่าง (vram_known) ค่าที่อ่านจากทั้งการ์ดถูกเรียนรู้จากรันที่ทำงานอยู่ตัวเดียวเท่านั้น (dispatch._keep_measurements, :826-914) ตารางอยู่ใน SCHEMA_CACHE_DIR
  • ความกว้างและ channel เครื่องมือที่ประกาศ num_workers หรือ batch_size (CHANNEL_ARGUMENTS, concurrency.py:145) รันหลายรายการพร้อมกันได้; width_from ใน deployment.toml บอกว่าให้นับอาร์กิวเมนต์ใด เครื่องมือขอ sup.channels(wanted) และได้ min(affordable, wanted, SADT_CHANNELS, ceiling) ไม่ต่ำกว่า 1 (runner.py:2134) SADT_MAX_CHANNELS = 0 หมายถึงไม่มีเพดาน (config.py:130) รันที่เปิดเพียง channel เดียวคงการจองทั้งหมดไว้
  • ลองใหม่เมื่อหน่วยความจำไม่พอ หากรันตายเพราะหน่วยความจำหมด (OutOfMemoryError, CudaOutOfMemoryError, MemoryError หรือ SIGKILL โดยไม่มี result.json, _out_of_memory dispatch.py:933) มันจะเริ่มใหม่ได้สูงสุด MEMORY_RETRIES = 2 ครั้ง โดยการจองคูณด้วย MEMORY_RETRY_GROWTH = 1.5 ทุกครั้ง เว้นแต่ถือทั้งเครื่องอยู่แล้ว งานถูกรีเซ็ตและอีเวนต์ queued_gpu อ่านว่า “out of memory; waiting for more room (try N)” (dispatch.py:1158-1228) นี่คือสิ่งที่ทำให้หน้าต่าง 20 รันปลอดภัย: ค่าสูงสุดที่หลุดออกจากหน้าต่างไปแล้วถูกกู้คืนด้วยการลองใหม่
  • การเรียกซ้อนข้ามการรับเข้า เครื่องมือที่เรียกด้วย sup.run เป็นซับโปรเซสของโปรเซสแม่ ซึ่งถือการจองอยู่ งบประมาณไบต์จึงถูกแบ่งลงไปทาง channel ของแต่ละระดับ (concurrency.child_budget, runner._child_channel_budget :1493)
  • คิวเป็นของแต่ละโปรเซส singleton ถูกสร้างโดย budget() (admission.py:541-553) หลัง threading.Condition: uvicorn --workers N จะสร้าง N งบประมาณ อิมเมจเริ่ม worker ตัวเดียว (docker/Dockerfile:232)
  • สองขีดจำกัดซ้อนกัน CapacityLimiter (4 เธรด) นับการรอการรับเข้า; งบประมาณนับไบต์ รันที่ห้าพร้อมกันจะรอก่อนที่จะมองเห็นเป็น queued_gpu

เครื่องมือรันเครื่องมืออื่นผ่านsupervisor คืออ็อบเจกต์ sup ที่ run() ได้รับเมื่อประกาศพารามิเตอร์แบบ keyword-only ชื่อ sup โดยไม่มี annotation (_takes_supervisor, runner.py:1140; คลาส _Supervisor, :1685) sup.run(tool, **params) เข้า runner.py ใหม่ด้วยอินเทอร์พรีเตอร์ของเครื่องมือพี่น้อง ใน process group เดียวกัน: ไม่มีการเรียก HTTP ไม่มีการรับเข้าใหม่ เครื่องมือพี่น้องรันใน <job>/sup/NN_<tool>/ พร้อม output_dir ที่บังคับเป็นของตัวเอง (runner.py:1808-1963) เครื่องมือที่กำลังรันอยู่เหนือผู้เรียกจะถูกปฏิเสธด้วยชื่อ โดยแสดงลูกโซ่; ตัวรองรับสุดท้ายคือ MAX_SUPERVISOR_DEPTH = 10 (runner.py:196) ลูกโซ่ที่ลึกที่สุดที่เครื่องมือที่ serve ประกาศไว้จริงคือสี่ระดับ VFACE → AREG_CBCT → ASO → ALI_CBCT

6. การยกเลิกและ timeout

ยกเลิก DELETE /runs/{id} (main.py:1050) ทำสองอย่างเพราะไม่มีอย่างใดครอบคลุมช่วงเวลาทั้งหมด มันเขียนเครื่องหมาย cancel ซึ่งถูกเห็นระหว่าง staging และระหว่างรอการรับเข้า; และหากมี process-group id ที่บันทึกไว้ มันส่ง SIGTERM ไปยังกลุ่ม (dispatch.kill_process_group, :745 ซึ่งปฏิเสธ pgid ที่เป็น 1 หรือน้อยกว่า) ซึ่งเป็นสิ่งที่หยุด nnU-Net ที่รันสองชั่วโมงได้ worker ที่ถือ process handle ตรวจเครื่องหมายทุก RUN_CANCEL_POLL_SECONDS = 1.0 s (config.py:278) และส่ง TERM แล้วตามด้วย KILL หลัง 10 s (_KILL_GRACE_SECONDS, dispatch.py:63; _kill_group :713) POST ที่ค้างอยู่ตอบ 499 การเรียกซ้อนใช้ process group เดียวกับแม่ ดังนั้น TERM ครั้งเดียวถึงทุกระดับ เนื่องจาก pgid ผ่านดิสก์ การยกเลิกจึงทำงานได้จากโปรเซส worker อื่น

Timeout รันไม่มี timeout โดยค่าเริ่มต้น TOOL_TIMEOUT_SECONDS = 0 (config.py:77) และไม่มีส่วนใดของ server/deployment.toml ตั้ง timeout_seconds เมื่อมีการตั้ง ไม่ว่าต่อเครื่องมือใน deployment.toml หรือทั้งระบบ มันจะถูกแปลงเป็นช่วงเวลาสัมบูรณ์แบบ monotonic ที่ส่งลงไปเป็น SADT_SUPERVISOR_DEADLINE (dispatch.py:552-561) และแต่ละระดับซ้อนให้ลูกเฉพาะเวลาที่เหลือ (runner._remaining_seconds, :1726) เมื่อหมดเวลา รันจบด้วย ToolExecutionError ที่ระบุทั้งสองค่าตั้ง และคำตอบคือ 500 ที่เก็บโค้ดแนะนำให้เครื่องมือที่ประสานงานได้ timeout อย่างน้อย 1.2 เท่าของผลรวม timeout ของเครื่องมือที่มันเรียก (docs/INTERNALS.md:112, server/deployment.toml.example:86)

7. การควบคุมคุณภาพ: หยุด ทบทวน รันต่อ ย้อนกลับ

รันบนเซิร์ฟเวอร์หยุดกลางทางได้ เพื่อให้คนดูสิ่งที่ขั้นตอนหนึ่งผลิตออกมา แก้ไข แล้วปล่อยให้รันต่อ มันคือคู่ฝั่งเซิร์ฟเวอร์ของจุดหยุดตรวจทานของโมดูล legacy (AREG_CBCT มีหนึ่งจุด); กลไกต่างกันโดยสิ้นเชิง เครื่องมือไม่รู้ว่าตัวเองถูกหยุด

  1. การเตรียมพร้อม เซิร์ฟเวอร์เพิ่มอาร์กิวเมนต์ multichoice ชื่อ stop_after ให้ทุกเครื่องมือที่มีจุดหยุด โดยไม่ติ๊กไว้ทั้งหมด ในส่วน “Quality control” (registry/schema_tool.py:340-500) ตัวเลือกคือชื่อของการเรียกที่เครื่องมือทำ บวกจุดที่ประกาศไว้ โดยระบุชื่อเต็มสำหรับลูกโซ่ซ้อนเช่น ASO/ALI_CBCT (_stop_points, registry/__init__.py:389) ชนิดของแต่ละจุด (view, landmarks, …) อ่านจาก review_kind ของผู้ถูกเรียกและเผยแพร่เป็น option_kind ใน GET /tools (main.py:633); ถ้าไม่มีหมายถึง view
  2. การหยุด ชื่อที่เตรียมพร้อมไว้ไปถึง runner เป็นตัวแปร JSON SADT_STOP_AFTER (runner.py:121); ลูกแต่ละตัวได้รับเฉพาะรายการที่เกี่ยวกับมัน หลังการเรียก QualityControlStop (runner.py:167) ถูกยกและถูกจับที่ส่วนบนของ main() (:2486); stopped.json ถูกเขียน (สะสม: stopped_after และ passed_stops, _record_stop, :920) ทุกอย่างที่ลูกโซ่ผลิตถูกเก็บรวบรวมไม่ว่า keep_intermediate จะบอกอย่างไร และ result.json บอกว่า {"quality_control": true, "stopped_after", "produced"}
  3. เซิร์ฟเวอร์เก็บงานไว้ มันไม่ลบไดเรกทอรีของงาน (dispatch._kept_if_paused, :1045) เขียน paused.json (runs.pause) ตั้งเฟสเป็น paused และตอบ 200 พร้อม {quality_control, stopped_after, produced, result_ref} โดยเอาต์พุตเป็น zip แบบอ้างอิง (_finish_stopped_run, main.py:2147-2197)
  4. การทบทวนบนไคลเอนต์ วิดเจ็ตฐานของ Remote แตกจุดตรวจ คำนวณ content digest และเปิดโมดูล VISU (REVIEW_MODULE = "VISU", base_widget.py:2290, _reviewCheckpoint :2292) ผ่าน open_for_review(folder, on_continue, rewind, origin) (VISU/VISU.py:491) VISU ไม่รู้อะไรเกี่ยวกับเซิร์ฟเวอร์: มันรับโฟลเดอร์และ callback เฉพาะจุดตรวจชนิด landmarks และ registration เท่านั้นที่แก้ไขได้ (EDITABLE_KINDS, base_widget.py:2328); การทบทวนถูกบันทึกเป็น visu-review.json ข้างข้อมูล (VISULib/review.py:20) หากไม่มี VISU หรือโฟลเดอร์ว่าง รันจะถูกสั่งรันต่อทันทีแทนที่จะถูกทิ้งให้หยุดค้างบนเซิร์ฟเวอร์
  5. รันต่อ เมื่อกด “Continue” ไคลเอนต์ส่งกลับเฉพาะไฟล์ที่ content digest เปลี่ยน หนึ่ง zip ต่อขั้น ตั้งชื่อตามขั้น (01_ALI_CBCT ได้สูงสุดสี่ระดับ: 01_Mid/01_Leaf) ไปที่ POST /runs/{id}/resume (main.py:1750; ชื่อขั้นถูกตรวจกับ _RESUME_SLOT, :1442; นามสกุลถูกตรวจกับสิ่งที่ขั้นนั้นผลิต, _checked_correction :1463) การหยุดถูกล้าง รันผ่านคิวการรับเข้าเหมือนรันอื่น และเครื่องมือถูกเรียกอีกครั้งตั้งแต่ต้น: ทุกการเรียกที่ทำไปแล้วตอบจาก memo ของมัน (memo.json, runner._memo :1965) จนกว่าลำดับจะต่างออกไป
  6. ย้อนกลับ POST /runs/{id}/rewind พร้อมฟิลด์ to (ชื่อขั้นที่เผยแพร่ไว้ ALI_CBCT หรือ ASO/ALI_CBCT) ย้อนไปยังจุดตรวจที่ผ่านมาแล้ว มันไม่เริ่มอะไรและไม่ลบ memo: runner.rewind_to (runner.py:971) ลบ to และทุกอย่างหลังจากนั้นออกจาก passed_stops ดังนั้นการรันต่อครั้งถัดไปจะหยุดที่นั่นอีกพร้อมเอาต์พุตของขั้นนั้นครบถ้วน หากขั้นนั้นเขียนรายงานกรณี (run_report.json) การเล่นซ้ำจะจำกัดเฉพาะกรณีที่ถูกแก้ ด้วย hard link (dispatch.narrow_to_cases, :959 ขับเคลื่อนโดย case_input ของสคีมา); ความสงสัยใดก็ตามหมายถึงเล่นซ้ำทั้งหมด ช้ากว่าแต่ไม่เคยผิด

ไม่มีเครื่องมือที่ serve ตัวใดประกาศจุดของตัวเองด้วย sup.declareQualityControl (ค้นใน SADT-VISOR tools/*/src ที่ 6ba2a78: ไม่พบนอก runner) จุดหยุดที่มีอยู่ทั้งหมดเป็นขอบเขตของการเรียก: เครื่องมือที่ถูกเรียกตัวใดก็เป็นจุดหยุดได้ รันที่หยุดอยู่มีชีวิต PAUSED_RUN_TTL_SECONDS = 4 ชม. และเมื่อหมดอายุ reap_expired อ่าน paused.json เพื่อลบไดเรกทอรีของงานและอินพุตที่เก็บไว้ (wire/runs.py:242-313)
