สถาปัตยกรรม VISOR

ชิ้นส่วนต่าง ๆ ประกอบกันอย่างไร: อะไรอยู่ใน Slicer อะไรที่เซิร์ฟเวอร์ทำก่อนที่เครื่องมือจะรัน และเครื่องมือประกาศตัวเองอย่างไรเพื่อไม่ให้ใครต้องเขียนอินเทอร์เฟซของมันด้วยมือ การรันตั้งแต่อัปโหลดถึงผลลัพธ์อยู่ในหน้าของมันเอง; image ความปลอดภัย และเทสต์ ก็เช่นกัน การอ้างอิงอ่านว่า repository path:line และอ้างถึง commit ของภาพรวม: VISOR-serve คือ e9a7e5d, SADT-VISOR คือ 6ba2a78, Remote คือ AutomatedDentalToolsRemote 19b95e8

1. รูปร่างของมัน

สองเครื่อง หนึ่งขอบเขต ฝั่งแพทย์ Slicer มีโมดูล Remote ที่แผงถูกสร้างโดย formgen จาก descriptor ของเครื่องมือจากเซิร์ฟเวอร์ ฝั่งเซิร์ฟเวอร์ โปรเซส FastAPI เดียวตรวจสอบคำขอ หาเครื่องมือใน registry รอที่ว่างในงบทรัพยากร และเริ่มเครื่องมือในซับโปรเซสที่ใช้อินเทอร์พรีเตอร์ของเครื่องมือเอง โปรเซสเซิร์ฟเวอร์ไม่มี torch; ไลบรารีหนักอยู่เฉพาะในสภาพแวดล้อมของเครื่องมือ

โค้ด: container คือ Python 3.13 ที่ติดตั้งเฉพาะข้อกำหนดของ API ใน /opt/sadt/.venv เครื่องมืออยู่ใต้ /tools/<name>/.venv (VISOR-serve docker/Dockerfile รายละเอียดในหน้า deployment); SchemaTool.invoke dispatch เสมอ และ SchemaTool.run โยน RuntimeError (VISOR-serve server/registry/schema_tool.py:812-844); Popen(..., start_new_session=True) อยู่ที่ server/execution/dispatch.py:649

2. สามกฎที่กำหนดทุกอย่างที่เหลือ

1. หนึ่งเครื่องมือ หนึ่งโฟลเดอร์ หนึ่ง venv

เครื่องมือคือไดเรกทอรีที่มีอินเทอร์พรีเตอร์และ lockfile ของตัวเอง เซิร์ฟเวอร์ไม่เคย import มัน มีเพียงสอง fixture คือ Example_Tool และ Test_Tool ที่เป็นคลาส Python ที่โหลดในโปรเซสเดียวกัน

2. การค้นพบถูกประกาศ

โฟลเดอร์เป็นเครื่องมือเพราะ pyproject.toml ของมันระบุ [tool.sadt] tool = true และอาจมี name ด้วย การสแกนลงลึกสองระดับ โฟลเดอร์กลุ่มเช่น tools/ALI/ จึงใช้ได้

3. เครื่องมือเรียกเครื่องมือผ่าน supervisor

ไม่เคยด้วย import เครื่องมือหนึ่งระบุอีกตัวด้วยสตริง schema เผยแพร่ชื่อนั้นไว้ใต้ calls และเซิร์ฟเวอร์ตรวจตอนเริ่มระบบว่าทุกชื่อเป็นเครื่องมือที่มันให้บริการ

โค้ด: กฎข้อ 1 VISOR-serve server/registry/schema_tool.py:812-844, SADT-VISOR README.md:3-8 ("no HTTP, FastAPI, authentication or storage" ในที่เก็บโค้ดของเครื่องมือ); กฎข้อ 2 server/registry/__init__.py:114-185, SADT-VISOR CONTRIBUTING.md:50-59; กฎข้อ 3 server/registry/__init__.py:353 และกฎที่ว่าการเรียกต้องอยู่ใน src/ ของเครื่องมือเอง ไม่เคยอยู่ในแพ็กเกจที่ใช้ร่วมกัน มิฉะนั้น calls จะออกมาว่างและการตรวจตอนเริ่มระบบจะไม่ตรวจอะไรเลย (SADT-VISOR CONTRIBUTING.md:481-507)

4. จากลายเซ็นของ run() ถึง schema

เครื่องมือไม่เผยแพร่อินเทอร์เฟซด้วยมือ scripts/describe.py (1,197 บรรทัด) อ่านลายเซ็นของ run() annotation ของมัน และบล็อก Args: ของ docstring รวมทั้ง AST สำหรับการเรียกที่ถูกกำกับดูแล และพิมพ์ .schema.json ต้องรันด้วยอินเทอร์พรีเตอร์ของเครื่องมือเอง และยังเข้ากันได้กับ Python 3.9 เพื่อให้รันในสภาพแวดล้อมเก่าได้ สำหรับสิ่งใดที่มันแทนไม่ได้ มันพิมพ์ข้อความทาง stderr และออกด้วยรหัส 2 schema ที่ "ถูกเกือบหมด" จึงไม่เคยถูกปล่อยออกมา (SADT-VISOR scripts/describe.py:1-18, 1185-1187)

6. Facade: ALI และ AREG

ALI และ AREG แต่ละตัวกลายเป็นหลายเอนจิน (ALI_CBCT และ ALI_IOS; AREG_CBCT, AREG_IOS และ AREG_IOSCBCT) แต่แผง Slicer ยังขอ "ALI" หรือ "AREG" facade ประสานสองฝั่งเข้าด้วยกัน มันไม่ใช่โฟลเดอร์และไม่ใช่อินเทอร์พรีเตอร์: folder คือ None และ run() โยน RuntimeError (VISOR-serve server/registry/facade.py:68, 80-81) schema ของมันถูกประกอบตอนเริ่มระบบจากตาราง dispatch ของ deployment.toml: อาร์กิวเมนต์ mode นำหน้า แล้วยูเนียนของอาร์กิวเมนต์ของเป้าหมาย แต่ละตัวแสดงเฉพาะในโหมดที่มีมัน และเป็นตัวเลือกเว้นแต่ทุกเป้าหมายต้องการ (facade.py:42, 98) ถ้าสองเป้าหมายประกาศอาร์กิวเมนต์เดียวกันด้วย (type, accepts, required) ที่ต่างกัน facade จะถูกข้ามพร้อมคำเตือน; ร้ายแรงก็ต่อเมื่อชื่อของมันเป็นเครื่องมือที่ให้บริการอยู่แล้ว (facade.py:282-295)

ตอนรัน _run_tool ลบ mode หาเป้าหมาย (422 เมื่อไม่มีโหมดหรือโหมดไม่รู้จัก) ทิ้งอาร์กิวเมนต์ที่เป้าหมายไม่ได้ประกาศ แล้วรันเป้าหมายตามปกติ: การตรวจสอบ admission และไดเรกทอรีงานของมันเอง ไม่มีสิ่งใดต่อจากนั้นรู้ว่ามี facade เข้ามาเกี่ยวข้อง (VISOR-serve server/main.py:1888-1917) ตาราง dispatch คือ "CBCT"→AREG_CBCT, "IOS"→AREG_IOS, "IOS to CBCT"→AREG_IOSCBCT และ "CBCT"→ALI_CBCT, "IOS"→ALI_IOS (server/deployment.toml:193, 210) ทั้งสอง facade เผยแพร่รวมกัน 11 อาร์กิวเมนต์ (ALI) และ 31 (AREG) นับบนอินสแตนซ์ที่รันอยู่

ตัวอย่างที่ล้าสมัยใน docstring

7. กราฟการเรียกที่มีอยู่จริง

ฟิลด์ calls ของแต่ละ schema ระบุเครื่องมือที่ตั้งชื่อใน sup.run("X", …) เมทริกซ์ด้านล่างคือฟิลด์นั้นสำหรับหกเครื่องมือที่เรียกตัวอื่น ตรวจเทียบกับจุด sup.run ใน SADT-VISOR tools/ (เช่น tools/ALI/ALI_IOS/src/sadt_ali_ios/dispatch.py:229, tools/ASO/src/sadt_aso/dispatch.py:537, tools/VFACE/src/sadt_vface/tools.py:145-359) สิบสองเครื่องมือไม่เรียกใครเลย; Agent ก็เรียกเครื่องมือเช่นกันแต่ไม่ประกาศตัวใด (ดู callout ด้านล่าง)

อ่านดังนี้: VFACE แตกไปหกเครื่องมือ; เอนจิน AREG แต่ละตัวเรียกเครื่องมือที่ต้องการผลลัพธ์ของมัน (การแบ่งส่วน CBCT การจัดทิศทาง การกำหนดเลขฟัน landmark); และ ALI_IOS เรียก Crown_Seg เมื่อเมชไม่มีป้ายกำกับฟัน ดังนั้น Crown_Seg จึงถูกเข้าถึงจากทั้งสามเอนจินที่เกี่ยวกับ IOS (SADT-VISOR tools/ALI/ALI_IOS/src/sadt_ali_ios/dispatch.py:229) ห่วงโซ่ที่ลึกที่สุดมีสี่ระดับ ห่วงโซ่ไปได้สูงสุดสิบ (MAX_SUPERVISOR_DEPTH) วงจรถูกปฏิเสธตามชื่อที่การเรียกครั้งแรก และเครื่องมือหนึ่งอาจปรากฏสองครั้งบนสาขาต่างกัน (หัวข้อถัดไป)

docs/TOOL_GRAPH.md ล้าสมัย

VISOR-serve docs/TOOL_GRAPH.md วาดเอนจิน AREG และ ASO ทำเครื่องหมาย ALI_IOS เป็น leaf (:27) ละ VFACE และระบุว่าห่วงโซ่จริงที่ลึกที่สุดมีสามระดับ คือ AREG_IOSCBCT → ASO → ALI_CBCT (:53) ในโค้ด ALI_IOS เรียก Crown_Seg และห่วงโซ่ที่ลึกที่สุดมีสี่ระดับ ผ่าน VFACE Agent อยู่นอกกราฟโดยโครงสร้าง: มันเรียกเครื่องมือผ่าน supervisor.run(…) ไม่ใช่ sup.run(…) เพื่อให้ describe.py ซึ่งยืนยันชื่อตัวอักษร ไม่ล้มกับมัน (SADT-VISOR tools/Agent/src/sadt_agent/execution.py:9-30, 70) การตรวจตอนเริ่มระบบจึงไม่ครอบคลุมมัน เหลือเพียงการตรวจตอนรัน

จุดหยุดตามกราฟเดียวกัน ทุกเครื่องมือที่ถูกเรียกเป็นจุดหยุดได้ และจุดหยุดตั้งชื่อด้วยเส้นทางของมัน (ALI_CBCT หรือ ASO/ALI_CBCT) (VISOR-serve server/registry/__init__.py:389, 425) ไม่มีเครื่องมือที่ให้บริการตัวใดเรียก declareQualityControl จุดหยุดที่มีอยู่ทั้งหมดจึงเป็นขอบเขตของการเรียก (grep บน SADT-VISOR tools/*/src) การรันหยุด ถูกแก้ และทำต่ออย่างไรอยู่ในหน้าการรัน

8. สิ่งที่อยู่ฝั่งไคลเอนต์

ที่เก็บโค้ดไคลเอนต์มีโฟลเดอร์โมดูล 23 โฟลเดอร์ สิบห้าในนั้นเป็นหน้าด่านของเครื่องมือเซิร์ฟเวอร์: AMASSS, ALI, ASO, AREG, AutoMatrix, AutoCrop3D, FlexReg, BATCHDENTALSEG, DOCShapeAXI, CLIC, CNE, VFACE, GreedyReg, SurgMovPred และ Crown_Seg (Remote CMakeLists.txt:24-48) ทุกตัวสืบทอด ServerToolWidgetBase ซึ่งทำงานส่วนกลาง:

  • แผง ตอนตั้งค่ามันเรียก GET /health แล้ว GET /tools หาเครื่องมือของตัวเอง (ชื่อตรงตัว แล้วไม่สนตัวพิมพ์และตัวคั่น) และ formgen แปลง schema เป็นวิดเจ็ต: สเกลาร์ ตัวเลือก multichoice จอยสติ๊ก vec2 และแถวไฟล์ที่รับไฟล์หรือโฟลเดอร์ โมดูลประกาศเฉพาะสิ่งที่ schema พูดไม่ได้ ผ่าน FILE_INPUTS, RESULT_KIND, SCENE_INPUTS และ hook ไม่กี่ตัว (Remote ServerToolsCoreLib/base_widget.py:359-368; formgen.py:1-30)

  • การโหลดผลลัพธ์ เมื่อ zip กลับมา โมดูลแตกไฟล์และโหลดสิ่งที่ตาราง _LOADABLE ของมันระบุเข้าฉาก (base_widget.py:1427): วอลุ่ม label map โมเดล markups *.mrk.json บางตัวอ่านรายงานเล็ก ๆ เพื่อเรียบเรียงข้อความสุดท้าย (เช่น run_report.json สำหรับ ALI)

ฝั่งไคลเอนต์แทบไม่มีอะไรเกิดขึ้นอีก และข้อยกเว้นคือสิ่งที่ตารางในภาพรวมชี้ไว้ FlexRegRemote คำนวณเส้นขอบของแพตช์ในเครื่องใหม่เพื่อให้จอยสติกตอบสนอง (ราว 18 ms บนส่วนโค้งฟัน 294,000 จุด ส่วนแพตช์จริงคำนวณที่เซิร์ฟเวอร์ตอน Apply) และแสดงเป็นโหนดที่ไม่ถูกบันทึกในฉาก (Remote FlexRegRemote/FlexRegRemote.py:14-18) โมดูลในเครื่องสองตัว คือ Medical_Data_Anonymizer_ModuleRemote (ข้อความเท่านั้น ใช้ Presidio และ spaCy) กับ AgentRemote (Ollama) ไม่นำเข้าไลบรารีของเซิร์ฟเวอร์เลย

MRI2CBCT ไม่ถูกส่งมอบ

MRI2CBCTRemote และ MRI2CBCT_CLIRemote ยังอยู่ในต้นไม้ไฟล์ แต่ไม่มี add_subdirectory (Remote CMakeLists.txt:31-32) และคำอธิบายของ extension ระบุว่า "MRI2CBCT is temporarily not shipped until it is ported to the server" (:10) SADT-VISOR ไม่มีเครื่องมือ MRI2CBCT สิ่งที่เหลืออยู่คือโค้ดในเครื่องแบบ legacy (slicer.cli.run, การ pip_install ของ torch) ซึ่งเข้าถึงไม่ได้จาก extension ที่บิลด์แล้ว ดูโค้ดนั้นได้ที่ หน้า VISOR ของ MRI2CBCT และ หน้า legacy ของมัน

9. ซูเปอร์ไวเซอร์: sup

การซ้อนเรียก sup.run เข้า runner.py ใหม่ด้วยอินเทอร์พรีเตอร์ของเครื่องมือพี่น้อง ในฐานะซับโพรเซสของโพรเซสแม่: ไม่มีคำขอ HTTP ใหม่ และไม่มีการรับงานเข้า (admission) ใหม่ โฟลเดอร์ของการเรียกคือ <job>/sup/NN_<tool>/ พร้อมตัวนับสองหลัก และ output_dir ของมันถูกกำหนดให้ ไม่ใช่ของโพรเซสแม่ มิฉะนั้น keep_intermediate จะไม่พบสิ่งใดให้คัดลอก (runner.py:1808-1840) การเรียกเครื่องมือที่กำลังรันอยู่ด้านบนแล้วจะถูกปฏิเสธโดยระบุชื่อ พร้อมแสดงสายการเรียก ตัวกันสำรองคือ MAX_SUPERVISOR_DEPTH = 10 (runner.py:196, 1810-1818) เครื่องมือเดียวกันบนสองกิ่งที่ต่างกันไม่ถือเป็นวงวน

เส้นตาย เมื่อกำหนด timeout ไว้ เซิร์ฟเวอร์จะแปลงเป็นเวลา monotonic สัมบูรณ์ แล้วส่งต่อลงไปทาง SADT_SUPERVISOR_DEADLINE แต่ละระดับให้ลูกเฉพาะเวลาที่เหลือ (VISOR-serve server/execution/dispatch.py:552-561; runner.py:201) หากไม่ได้กำหนด timeout ซึ่งเป็นค่าเริ่มต้น ก็ไม่มีเส้นตาย

กลุ่มโพรเซส โพรเซสระดับบนสุดเริ่มด้วย start_new_session=True และ id กลุ่มของมันถูกเขียนลงดิสก์ การเรียกซ้อนไม่เริ่มเซสชันใหม่ แต่สืบทอดกลุ่ม ดังนั้น SIGTERM ของเซิร์ฟเวอร์เมื่อยกเลิกจึงไปถึงทุกระดับ (server/execution/dispatch.py:649, 713-745; runner.py:2063)

เอกสารนับจำนวนสมาชิกผิด

docstring ของคลาสเขียนว่า "six members" (runner.py:1686) VISOR-serve docs/INTERNALS.md:80 เขียนว่า "five members, frozen" และ server/README.md:652 เขียนว่า "five members" ส่วน SADT-VISOR scripts/run_tool.py implement ซูเปอร์ไวเซอร์ในเครื่องที่มีห้าตัว (run, out, tmp, progress, log; run_tool.py:300-364) ซึ่งไม่มีการตรวจวงวน ไม่มีขีดจำกัดความลึก และไม่มี declareQualityControl เซิร์ฟเวอร์มีแปดตัว ตามรายการด้านบน server/README.md:660 ยังเขียนว่า "five deep is the backstop" แต่ค่าคงที่คือ 10

10. อ่านต่อที่ไหน

  • สิ่งที่เกิดขึ้นระหว่างการคลิก Apply กับผลลัพธ์ในฉาก: การรันทีละขั้น
  • อิมเมจ โปรไฟล์ compose และวิธีสร้างสภาพแวดล้อม: การแพ็กเกจและการติดตั้งใช้งาน
  • มาตรการป้องกันใดที่ implement แล้ว ระบุไว้ในสเปก หรือไม่มี: ความปลอดภัยและความเป็นส่วนตัว
  • เครื่องมือ ชื่อ และที่มาของมันถูกทดสอบอย่างไร: การทดสอบและที่มา
  • ภาพรวม ทีละเครื่องมือ: VISOR สถานะของแต่ละเครื่องมือ
