BatchDentalSeg บน VISOR: โค้ด

สำหรับนักพัฒนา: สิ่งที่พอร์ต VISOR ของ BatchDentalSeg ทำในโค้ด พร้อมการอ้างอิงแบบ file:line ซิกเนเจอร์ อาร์กิวเมนต์ สภาพแวดล้อม ความต่างจากโค้ด legacy และข้อค้นพบ คำอธิบายที่อ่านง่ายของไปป์ไลน์เดียวกัน พร้อมคณิตศาสตร์ อยู่ในหน้าแอตลาส BatchDentalSeg รันใน VISOR อย่างไร (ไคลเอนต์และเซิร์ฟเวอร์) อะไรเปลี่ยนจากโมดูล Slicer แบบ legacy และโค้ดของพอร์ตทำอะไรทีละขั้น โมดูล legacy อธิบายอยู่ในหน้าของมันเอง

โค้ด แอตลาส (คำอธิบาย) VISOR Batch_Dental_Seg หน้า Legacy คู่มือ (VISOR) บรรณานุกรม

VISOR รัน BatchDentalSeg บนเซิร์ฟเวอร์: Slicer ส่งสแกนและชื่อโมเดลที่โฮสต์ไว้ แล้วรับ label volume ไฟล์ต่อป้ายกำกับ หรือเมช เครือข่าย nnU-Net v2 หนึ่งตัว ที่เลือกจากสี่ bundle ใส่ป้ายกำกับทุกโครงสร้างของสแกนในรอบเดียว และหนึ่งการเรียกครอบคลุมทั้งแบตช์ หน้านี้บอกว่าอะไรรันที่ไหน ตามไปป์ไลน์จากไฟล์อินพุตถึงรายงานการรัน แสดงรายการอาร์กิวเมนต์ที่เซิร์ฟเวอร์เผยแพร่ และเปรียบเทียบแต่ละขั้นกับโมดูล legacy ทุกอย่างที่นี่อ่านจากโค้ด ไม่ได้สังเกตบนเซิร์ฟเวอร์ที่กำลังรัน และไม่มีอะไรที่นี่บอกว่ามีเซิร์ฟเวอร์ใดถูกใช้งานจริง

การอ้างอิงระบุชื่อรีโพซิทอรีก่อน: SADT-VISOR (โค้ดเครื่องมือ tool/vface @ 6ba2a78), VISOR-serve (เซิร์ฟเวอร์ @ e9a7e5d), AutomatedDentalToolsRemote (ไคลเอนต์ Slicer @ 19b95e8) และ legacy (SlicerAutomatedDentalTools @ 3c67957) ชื่อไฟล์เปล่าๆ เช่น pipeline.py, catalogs.py, layout.py, nnunet_runner.py, low_memory.py, mesh_export.py, progress.py หรือ __init__.py อยู่ในแพ็กเกจ SADT-VISOR tools/Batch_Dental_Seg/src/sadt_batchdentalseg/ ส่วน SegmentationWidget.py, Queue.py และ PythonDependencyChecker.py เป็นไฟล์ legacy ของ BATCHDENTALSEG/BATCHDENTALSEGLib/ (วิดเจ็ตมี 3037 บรรทัดที่ 3c67957)

8. ข้อค้นพบใน VISOR

VFACE ขอพื้นผิวแต่ได้ label volume

เส้นทาง heat map ของ VFACE เรียกเครื่องมือนี้ด้วยอาร์กิวเมนต์สามตัวเท่านั้น คือ scans, model และ prediction_ID="Seg" (SADT-VISOR tools/VFACE/src/sadt_vface/tools.py:359-364) ดังนั้น export_formats คงค่าเริ่มต้น ["NIFTI"] (SADT-VISOR __init__.py:22-24) และไม่มีเมชถูกเขียน (pipeline.py:342-354; mesh_export.py:187-189) จากนั้น VFACE มองหาเฉพาะไฟล์ .vtk หรือ .vtp (heatmap.py:29, 194-204) ไม่พบเลย และจบด้วย "No heat map could be drawn" (heatmap.py:246-251) อ่านจากโค้ด ไม่ได้รัน การติดตั้งที่อ่านที่นี่ไม่เผยแพร่ surface_model สำหรับ VFACE อยู่แล้ว (VISOR-serve server/deployment.toml:277-279) เส้นทางนี้จึงเข้าถึงไม่ได้จากแผงของเซิร์ฟเวอร์นั้น

README ของเครื่องมือล้าสมัยเรื่องการส่งออกเมชและหน่วยความจำ

README ของเครื่องมือบอกว่า "No vtk: the mesh exports are not ported" และระบุว่ายังไม่ได้พอร์ต (tools/Batch_Dental_Seg/README.md:28, 95) docstring ของ pipeline.py ก็บอกเช่นเดียวกัน (SADT-VISOR pipeline.py:23-24) โค้ดบอกต่างออกไป: mesh_export.py เขียน STL, OBJ และ VTK, export_formats เป็นอาร์กิวเมนต์ (__init__.py:22-24) และ vtk 9.6.2 เป็น dependency (pyproject.toml:23) มีเพียง glTF ที่ขาดไปจริง README ยังนับเทสต์ที่ไม่ใช้ GPU ได้ 38 รายการ (README.md:267) ทั้งที่ไฟล์มีฟังก์ชันเทสต์ 55 ตัว คำแนะนำให้ปิด gpu_resampling สำหรับ UniversalLab บนการ์ดที่เล็กกว่าประมาณ 40 GiB (README.md:241-256 ซ้ำใน __init__.py:69-73) แก้ไขล่าสุดใน commit d2fb0d8 ตัวสุ่มตัวอย่างใหม่ต่อคลาส ซึ่งโค้ดติดตั้งพร้อมตัวสุ่มตัวอย่างใหม่บน GPU กับทุกbundle (nnunet_runner.py:185-188) มาทีหลังใน c8899c8 และ docstring ของมันประกาศค่าสูงสุดที่ต่ำลงมาก (low_memory.py:20-26) โค้ดคืออ้างอิงที่นี่ ตัวค่าสูงสุดเองไม่ได้วัดสำหรับหน้านี้

สแกนที่ชื่อ ..._Seg มองไม่เห็นในโฟลเดอร์

เมื่อใช้ identifier เริ่มต้น patient_Seg.nii.gz ภายในโฟลเดอร์ถูกเข้าใจว่าเป็นผลลัพธ์ก่อนหน้าและถูกเมินโดยไม่มีข้อความใดๆ (SADT-VISOR pipeline.py:79-80, 104-105) ไฟล์เดี่ยวที่ส่งเป็น scans ถูกประมวลผลแม้ชื่อจะดูเหมือนผลลัพธ์ (pipeline.py:96-97)

การสุ่มตัวอย่างใหม่บน GPU เปิดเป็นค่าเริ่มต้นและเปลี่ยนตัวเลข

เมื่อมีผล volume อินพุตถูกสุ่มตัวอย่างใหม่บน GPU แบบ linear แทน cubic spline ของ nnU-Net โค้ดระบุว่านี่คือความต่างเชิงตัวเลขทั้งหมด และ gpu_resampling=false ปิดมัน (SADT-VISOR nnunet_runner.py:167-177) รายงานบันทึกค่าที่ร้องขอบนอุปกรณ์ CUDA และ false บน CPU bundle ที่แผนของมันไม่เลือกใช้ถูกกล่าวถึงในล็อกเท่านั้น (pipeline.py:374-378; nnunet_runner.py:163-165) อาร์กิวเมนต์นี้ซ่อนอยู่ในแผง

ไม่ได้ปิดการปรับแต่งอัตโนมัติของ cuDNN

BatchDentalSeg ไม่เคยตั้ง torch.backends.cudnn.benchmark (ไม่มีให้เห็นในแพ็กเกจ) และ predictor ของ nnU-Net ตั้งเป็น true บน CUDA (nnunetv2/inference/predict_from_raw_data.py:60-61 nnunetv2 ตามที่ติดตั้งในสภาพแวดล้อมของเครื่องมือ) AMASSS ปิดมันอย่างชัดแจ้ง (SADT-VISOR AMASSS sadt_amasss/nnunet_runner.py:116) README ของเครื่องมือบอกว่า nnU-Net บน CUDA ไม่กำหนดได้ระดับบิต (README.md:113): อย่าคาดหวัง mask ที่เหมือนกันทุกบิตจากการรันสองครั้งของสแกนเดียวกัน

รายการส่งออกที่ว่างให้ "ok" โดยไม่มีไฟล์ (เฉพาะการเรียกโดยตรง)

เมื่อเรียกตรงๆ ใน Python run(..., export_formats=[]) รายงานแต่ละสแกนเป็น ok พร้อมรายการ produced ที่ว่างและสรุป "1/1 scan(s) segmented" และไม่เขียนอะไรเลย (SADT-VISOR pipeline.py:342-355, 362-386; mesh_export.py:187-189) ตัวเครื่องมือไม่ตรวจรายการ คำขอผ่านเซิร์ฟเวอร์ถูกปฏิเสธก่อนการรัน เพราะเลย์เอาต์ต้องการอย่างน้อยหนึ่งรูปแบบ (layout.py:31-33; VISOR-serve server/base.py:855-858) และแผงก็ขอหนึ่งรูปแบบเช่นกัน

ไฟล์ต่อป้ายกำกับขึ้นกับรูปแบบ NIfTI

separate_segments แยก label volume จึงใช้ได้เฉพาะเมื่อเลือก NIFTI: ถ้าเลือกเมชอย่างเดียว จะไม่มีอะไรถูกเขียนสำหรับมัน แม้ติ๊กช่องไว้ (SADT-VISOR pipeline.py:339-350)

ตารางป้ายกำกับเดินทางไปกับผลลัพธ์ แต่ Slicer ไม่อ่าน

รายงานมีตาราง labels ครบ (SADT-VISOR pipeline.py:364-371) แผง Slicer ไม่กำหนด RUN_REPORT (ค่าเริ่มต้นว่าง: ServerToolsCoreLib/base_widget.py:1493) และโหลด label volume ด้วย loadLabelVolume ธรรมดา (slicer_io.py:560) คอมเมนต์ในโมดูลพูดถึงตารางสี (BATCHDENTALSEGRemote.py:79-82) แต่ไม่มีโค้ดใดใช้มัน

การเรียกอนุมานครั้งเดียว: ความคืบหน้ามีสองปลาย

ทั้งโฟลเดอร์ผ่านการเรียก nnU-Net ครั้งเดียว แถบความคืบหน้าจึงครอบคลุมการอ่าน (0 ถึง 10 %) และการเขียน (90 ถึง 100 %) และบอก "segmenting N scan(s) in one pass" ตรงกลาง โดยไม่ประดิษฐ์ค่ากลาง (SADT-VISOR pipeline.py:269-274, 301) exception จากการเรียกนั้นทำให้ทั้งแบตช์ล้มเหลวหลังล้างโฟลเดอร์ชั่วคราว (pipeline.py:302-309)

ตรวจแล้ว: สแกนที่อ่านไม่ได้ไม่หยุดแบตช์

สแกนที่อ่านไม่ได้ถูกรายงานเป็น failed ("could not be read") และสแกนอื่นถูกทำเซกเมนเทชัน จะหยุดการรันด้วยข้อผิดพลาดอินพุตก็ต่อเมื่ออ่านไม่ได้เลยสักตัว (SADT-VISOR pipeline.py:273-298)
