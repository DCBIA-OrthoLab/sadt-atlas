CNE บน VISOR

CNE อ่านบันทึกทางคลินิกที่เป็นข้อความอิสระและจดข้อเท็จจริงที่พบในนั้น (อาการ การวินิจฉัย คะแนน) เป็นรายการบรรทัด field : value โมเดลภาษาเป็นผู้อ่าน ทุกอย่างรอบมันตัดสินว่าโมเดลเห็นอะไรและคำตอบใดของมันถูกเก็บไว้ ใน VISOR โมเดลรันบนเซิร์ฟเวอร์ บันทึกจึงถูกอัปโหลด ซึ่งโมดูล legacy ไม่เคยทำ หน้านี้อธิบายขั้นตอนและการคำนวณไม่กี่อย่างในนั้น รายละเอียดที่นักพัฒนาต้องใช้อยู่ในหน้าโค้ด และโมดูล legacy มีหน้าของมันเอง

VISOR 1 โมเดลภาษา โค้ด (นักพัฒนา) หน้า Legacy คู่มือ (VISOR)

ภาพรวม: อะไรเข้า อะไรออก

CNE
อินพุตบันทึกหนึ่งฉบับ หรือโฟลเดอร์ของบันทึก (.txt, .pdf, .docx) รวมโฟลเดอร์ย่อย
สิ่งที่คุณเลือกชนิดของบันทึก (TMJ หรือ Ortho) ไฟล์โมเดล และความยาวสูงสุดของคำตอบ
โมเดลโมเดลภาษาแบบ quantised ที่รันบนโปรเซสเซอร์ของเซิร์ฟเวอร์ ตัวที่โฮสต์ไว้คือ Qwen 2.5 7B ที่ fine-tune บนบันทึก TMJ
เอาต์พุตต่อบันทึก ไฟล์ JSON หนึ่งไฟล์และไฟล์ข้อความของบรรทัด field : value รวมถึงรายงานการรันหนึ่งฉบับ

โมเดลเพียงตัวเดียวตัดสินว่ามีฟิลด์ใดและค่าของมันคืออะไร ไม่มีอะไรตรวจการสกัดข้อมูลเทียบกับบันทึกต้นทาง เครื่องมือควบคุมเพียงสิ่งที่โมเดลเห็นและคำตอบใดที่ถูกจดไว้

1. รันที่ไหน

Slicer เก็บไว้เพียงแผงเล็ก ๆ (CNERemote) มันอัปโหลดบันทึกไปยังเซิร์ฟเวอร์ รอ แล้วดาวน์โหลดไฟล์เก็บถาวรหนึ่งไฟล์และแตกลงโฟลเดอร์ที่เลือก โมเดลถูกโหลดและรันบนเซิร์ฟเวอร์ในสภาพแวดล้อมของตัวเอง และไม่มีอะไรถูกโหลดเข้าฉาก Slicer: ผลลัพธ์เป็นข้อความ CNE ไม่เรียกเครื่องมืออื่นและไม่มีเครื่องมือใดเรียก CNE

เพราะโมเดลรันบนเซิร์ฟเวอร์ ข้อความของบันทึกจึงออกจากเวิร์กสเตชัน โมดูล legacy เก็บมันไว้ในเครื่อง ไม่มีอะไรลบข้อมูลระบุตัวตนของบันทึกก่อนส่ง (ปัญหาที่ทราบ)

1.1 อะไรรันที่ไหน

  • เซิร์ฟเวอร์: เผยแพร่ฟอร์มที่แผงแสดง อ่านรูปแบบบันทึกทั้งสาม รันโมเดล เขียนผลลัพธ์ โมเดลถูกโหลดครั้งเดียวต่อการเรียก ซึ่งเป็นเหตุผลที่ทั้งโฟลเดอร์ของบันทึกถูกส่งในการเรียกเดียว
  • Slicer: แสดงฟอร์มที่สร้างอัตโนมัติ อัปโหลดบันทึก แตกไฟล์เก็บถาวร และพิมพ์สรุปหนึ่งบรรทัดในแถบสถานะ (สกัดบันทึกได้กี่ฉบับ ด้วยโมเดลชนิดใด และมีคำเตือนกี่รายการ) ไม่มีอะไรถูกติดตั้งหรือดาวน์โหลดบนเวิร์กสเตชัน
ในโค้ดแผง เครื่องมือฝั่งเซิร์ฟเวอร์ สิ่งที่โฮสต์ไว้ พร้อมไฟล์และบรรทัด

2. ไฟล์ที่เกี่ยวข้อง

เครื่องมือมีไฟล์ซอร์สเล็ก ๆ ห้าไฟล์: จุดเข้าที่รันลูปบนบันทึก โค้ดโมเดล (prompt การโหลด การ parse) ตัวอ่านของสามรูปแบบ ตัวโหลดสำหรับแพ็กเกจที่ไม่บังคับ และ layout ของแผง จากโมดูล legacy พอร์ตเฉพาะการอนุมาน ส่วนแผง การดาวน์โหลดโมเดล และ Dashboard ไม่ได้พอร์ต

ในโค้ดรายการไฟล์พร้อมจำนวนบรรทัด และไฟล์ฝั่งเซิร์ฟเวอร์และไคลเอนต์ที่เกี่ยวกับ CNE

3. ไปป์ไลน์

ครั้งเดียวต่อการรัน เครื่องมือตรวจโฟลเดอร์ ลิสต์บันทึก เลือกไฟล์โมเดล และโหลดมัน จากนั้นทีละบันทึก มันอ่านข้อความ ถามโมเดล และตัดสินว่าเก็บคำตอบได้หรือไม่ แต่ละกล่องเป็นลิงก์ไปยังขั้นของมัน

3.1 การตรวจโฟลเดอร์และการหาบันทึก

เครื่องมือตรวจก่อนว่าบันทึกมีอยู่และผลลัพธ์จะไม่ถูกเขียนลงโฟลเดอร์บันทึก ไม่เช่นนั้นการรันครั้งถัดไปจะอ่านผลลัพธ์ของตัวเองเป็นบันทึก จากนั้นลิสต์ไฟล์ .txt, .pdf และ .docx ในโฟลเดอร์และโฟลเดอร์ย่อย ไม่ว่านามสกุลจะเป็นตัวพิมพ์ใด ข้ามไฟล์ล็อกของ Word และไฟล์ที่ซ่อน ถ้าไม่พบเลย การรันหยุดด้วยข้อผิดพลาดที่ระบุนามสกุลทั้งสาม โมดูล legacy เพียงจบไปเงียบ ๆ

ในโค้ดการตรวจโฟลเดอร์ การค้นแบบเรียกซ้ำ ชื่อที่ข้าม รหัสข้อผิดพลาด

3.2 การเลือกและการโหลดโมเดล

โมเดลคือไฟล์ quantised หนึ่งไฟล์ในรูปแบบ GGUF รันโดย llama.cpp ไฟล์เดียวใช้ตามที่เป็น โฟลเดอร์ต้องมีไฟล์เดียวพอดี บันทึกแต่ละชนิดมีหน้าต่างบริบทของตัวเอง คือปริมาณข้อความ (บันทึกกับคำตอบรวมกัน นับเป็น token) ที่โมเดลถือได้ในคราวเดียว: 6144 สำหรับ TMJ, 2048 สำหรับ Ortho ถ้าพาธของโมเดลระบุบันทึกอีกชนิด คำเตือนจะลงในรายงานแต่การรันดำเนินต่อ โมเดลถูกโหลดครั้งเดียวสำหรับทั้งชุด เพราะการโหลด 4.4 GB เป็นส่วนที่ช้า และถ้าขอ GPU จากbuild ที่มีเฉพาะโปรเซสเซอร์ การรันไปต่อโดยไม่มี GPU และบอกไว้ในรายงาน

ในโค้ดการหาโมเดล ตารางหน้าต่าง การโหลด และ build สำหรับ CPU

3.3 การอ่านบันทึก

ไฟล์ข้อความถูกถอดรหัสเป็น UTF-8 แล้ว Windows-1252 แล้ว Latin-1 อย่างใดอย่างหนึ่งที่ใช้ได้ก่อน PDF ให้ชั้นข้อความทีละหน้า ไฟล์ Word ให้ header และ footer แล้วเนื้อหาตามลำดับการอ่านพร้อมตาราง หนึ่งแถวตารางต่อหนึ่งบรรทัด จากนั้นทุกบันทึกผ่านขั้นตอนทำความสะอาดเดียวกัน

ข้อความที่ไม่มีตัวอักษรและตัวเลขเลย ซึ่งเป็นสิ่งที่ PDF ที่สแกนให้ ถูกปฏิเสธโดยระบุชื่อ: ไม่มี OCR

ในโค้ดตัวอ่านทั้งสาม ตารางการแทนที่ การตรวจข้อความว่าง

3.4 การถามโมเดล

บันทึกถูกส่งเป็นแชต สำหรับบันทึก TMJ system prompt มาก่อน: “Using the following note, extract structured key-value pairs about the patient’s symptoms and diagnoses” บันทึก Ortho ไม่มี เพราะโมเดลของมันถูก fine-tune ให้ตอบจากบันทึกเพียงอย่างเดียว คำตอบถูกจำกัดที่ 2048 token โดยค่าเริ่มต้น sampling temperature เป็น 0 และใช้ seed คงที่ บันทึกเดียวกันจึงควรให้คำตอบเดียวกัน ถ้าโมเดลหยุดเพราะถึงขีดจำกัด คำตอบไม่สมบูรณ์และบันทึกล้มเหลว

ด้วยค่าเริ่มต้นของ Ortho ขีดจำกัดคำตอบเท่ากับทั้งหน้าต่าง (2048 และ 2048) คำตอบจึงถูกจำกัดโดยสิ่งที่บันทึกเหลือไว้: บันทึก 1,000 token เหลือ 1,048 ให้คำตอบ เครื่องมือไม่เคยเทียบบันทึกกับหน้าต่าง เมื่อคำตอบถึงส่วนที่เหลือนั้นโมเดลรายงานว่าถูกตัดและบันทึกล้มเหลว เมื่อ prompt อย่างเดียวเต็มหน้าต่าง engine ปฏิเสธ และอีกครั้ง ล้มเหลวเฉพาะบันทึกนั้น

ในโค้ดข้อความ การเรียก การตรวจการตัดกลางคัน และตัวป้องกันความยาวที่ไม่มี

3.5 การอ่านคำตอบและการเขียน

คาดว่าโมเดลจะตอบเป็น JSON แต่ไม่มีอะไรบังคับ เครื่องมือลองสองวิธีอ่านตามลำดับนี้ และไม่เขียนอะไรถ้าล้มทั้งสอง

ฟิลด์ที่ปรากฏสองครั้งเก็บค่าแรก ต่อบันทึกเขียนสองไฟล์ในต้นไม้โฟลเดอร์ที่สะท้อนบันทึก: ไฟล์ JSON ซึ่งเป็นผลลัพธ์มาตรฐาน และไฟล์ข้อความของบรรทัด field : value สำหรับอ่าน ที่ list ถูกต่อด้วยจุลภาค สำหรับ B_001.txt คือ Extraction_B_001.txt.json และ Extraction_B_001.txt.txt รายงานการรันระบุต่อบันทึกว่าอ่านอย่างไร บันทึกและคำตอบยาวเท่าใด สำเร็จหรือไม่ ให้กี่ฟิลด์ และเหตุผลที่ล้มเหลวถ้าล้ม ตัวข้อความคำตอบเองไม่ถูกใส่ในรายงานหรือใน log

ในโค้ดโค้ด parse ตัววางแผนผลลัพธ์ ฟิลด์ของรายงาน

3.6 ความล้มเหลว

แต่ละบันทึกถูกจัดการโดยลำพัง ความล้มเหลว (ข้อความว่าง คำตอบถูกตัด คำตอบที่ไม่ใช่ทั้ง JSON และฟิลด์ ข้อผิดพลาดใน engine ของโมเดล) ถูกบันทึก log พร้อมพาธของบันทึก บันทึกพร้อมเหตุผล และลูปไปต่อ การรันทั้งหมดล้มเหลวเฉพาะเมื่อไม่มีบันทึกใดถูกเขียนเลย จากนั้นจบด้วยข้อผิดพลาดที่ลิสต์เหตุผลของแต่ละบันทึก และไม่มีการเขียนรายงาน

ในโค้ดข้อผิดพลาดใดกลายเป็นรหัสสถานะใด

4. สิ่งที่เลือกได้

  • บันทึก: บันทึกหนึ่งฉบับหรือโฟลเดอร์ของบันทึก จำเป็น
  • ชนิดบันทึก: TMJ หรือ Ortho เลือกsystem promptและหน้าต่างบริบทพร้อมกัน
  • โมเดล: ไฟล์โมเดล หรือโฟลเดอร์ที่มีเพียงหนึ่งไฟล์ รายการแสดงโมเดลที่โฮสต์ไว้ ไม่มีตัวเลือก “automatic” โมเดลจึงไม่ได้อนุมานจากชนิดบันทึก
  • ขีดจำกัดคำตอบ: คำตอบที่ยาวที่สุดต่อบันทึก ค่าเริ่มต้น 2048 token
  • Temperature: ค่าเริ่มต้น 0 หมายถึงไม่มีความสุ่ม
  • หน้าต่างบริบท: 0 หมายถึงค่าเริ่มต้นของชนิดบันทึก
  • การตั้งค่าที่ซ่อน: seed สุ่มและอุปกรณ์ (โปรเซสเซอร์โดยค่าเริ่มต้น) เซิร์ฟเวอร์กรอกอุปกรณ์ของตัวเอง
  • โฟลเดอร์ผลลัพธ์: เซิร์ฟเวอร์กรอกให้ และถูกปฏิเสธถ้าเป็นโฟลเดอร์บันทึก

ไม่มีเวลาจำกัด และการเรียกหนึ่งครั้งถูกจำกัดโดยเพดานอัปโหลด 500 MB ของเซิร์ฟเวอร์

ในโค้ดตารางอาร์กิวเมนต์พร้อมชนิด ค่าเริ่มต้น และบรรทัดที่บังคับใช้

6. สภาพแวดล้อม

ทุกอย่างรันในสภาพแวดล้อมของเครื่องมือเองบนเซิร์ฟเวอร์: Python 3.11, build สำหรับโปรเซสเซอร์ของ llama-cpp-python และตัวอ่านอย่างละหนึ่งสำหรับ PDF และ Word ไม่มีอะไรถูกติดตั้งใน Slicer โมดูล legacy ติดตั้งแพ็กเกจลงใน Python ของ Slicer เอง และดาวน์โหลดโมเดลขนาด 4.4 หรือ 4.9 GB ลงโฟลเดอร์ Documents ของผู้ใช้

ในโค้ดเวอร์ชันที่ตรึง wheel index ข้อมูลที่โฮสต์ ทรัพยากร

7. สิ่งที่เปลี่ยนไปจากตรรกะ legacy

prompt ของ TMJ การไม่มี prompt สำหรับ Ortho และหน้าต่างเริ่มต้นสองค่า ไม่เปลี่ยน รอบ ๆ สิ่งเหล่านั้น:

  • ที่ไหน: บนเซิร์ฟเวอร์แทนที่จะอยู่ใน Slicer บนเวิร์กสเตชัน
  • การหาบันทึก: แบบเรียกซ้ำและไม่สนตัวพิมพ์ การไม่พบอะไรเป็นข้อผิดพลาดแทนที่จะเป็นความสำเร็จเงียบ ๆ
  • การอ่าน: encoding ข้อความสามแบบแทนแบบเดียว อ่านตาราง header และ footer ของ Word ได้ PDF ที่สแกนถูกปฏิเสธแทนที่จะส่งข้อความว่างให้โมเดล แพ็กเกจตัวอ่านที่หายไปทำให้ล้มเฉพาะบันทึกของรูปแบบนั้น
  • การสร้างคำตอบ: ขีดจำกัดคำตอบ 2048 แทน 500 temperature 0 แทน 0.1 มี seed และคำตอบที่ถูกตัดทำให้บันทึกล้มเหลวแทนที่จะถูกเขียน
  • การอ่านคำตอบ: JSON แล้วบรรทัดฟิลด์ มิฉะนั้นไม่เขียนอะไร ในขณะที่โมดูล legacy บันทึกคำตอบดิบ
  • ผลลัพธ์: ไฟล์ JSON และไฟล์ข้อความต่อบันทึก ใช้ชื่อบันทึกเต็มเพื่อให้ .txt, .pdf และ .docx ที่ชื่อเดียวกันไม่เขียนทับกันอีก และรายงานการรัน
  • GPU: ขอเฉพาะเมื่อร้องขอ และรายงานบอกว่าเลเยอร์ถูก offload จริงหรือไม่
  • ไม่ได้พอร์ต: Dashboard และการดาวน์โหลดโมเดลโดยไคลเอนต์
ในโค้ดlegacy เทียบ VISOR ทีละจุด พร้อมบรรทัดทั้งสองฝั่ง

8. ปัญหาที่ทราบ

  • บันทึกถูกอัปโหลดไปยังเซิร์ฟเวอร์ตามที่เป็น โดยไม่ลบข้อมูลระบุตัวตน ข้อความของ legacy ที่ว่าข้อความทางคลินิกอยู่ในเครื่องจึงใช้ไม่ได้กับ VISOR (รายละเอียด)
  • แผงและ README พูดถึงโมเดล “automatic” แต่ไม่มีอะไรอนุมานโมเดลจากชนิดบันทึก (รายละเอียด)
  • โฮสต์เฉพาะโมเดล TMJ และโมเดลผิดชนิดเป็นเพียงคำเตือน (รายละเอียด)
  • engine คือ build สำหรับโปรเซสเซอร์ ไม่ว่าคอมเมนต์บางอันจะบอกอะไร คำขอ GPU ถูกรายงานว่าถูกเมิน (รายละเอียด)
  • ไม่มีอะไรเทียบบันทึกกับหน้าต่างบริบท และค่าเริ่มต้นของ Ortho ให้คำตอบเพียงสิ่งที่บันทึกเหลือไว้ (รายละเอียด)
  • ไฟล์ผลลัพธ์ตั้งชื่อต่างจากของ legacy เครื่องมือที่อ่านชื่อเก่าจึงจะไม่พบ (รายละเอียด)
  • แก้แล้ว: PDF ที่สแกน คำตอบที่ถูกตัด คำตอบที่อ่านไม่ได้ บันทึกชื่อเหมือนกัน และคำขอ GPU เงียบ ๆ ไม่ก่อไฟล์ที่ดูสมเหตุสมผลอีก (รายละเอียด)
ในโค้ดข้อค้นพบทั้งเจ็ดพร้อมหลักฐาน
